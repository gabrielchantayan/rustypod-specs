# F-b0987b51cfe6

## Purpose

F-b0987b51cfe6 coordinates a two-stage operation against an object obtained through a caller-supplied reference. It returns a status represented in a pointer-sized result.

On the fully successful path, it updates three fields of that object and clears a field in a second caller-supplied record. If the object is absent, or either stage returns a nonzero status, it instead invokes a finalization dependency and returns the selected status.

The operation’s application-level meaning is not established. In particular, the evidence does not establish whether the two stages prepare, transfer, register, or release anything. The successful counter and flag changes are established behavior; interpreting them as ownership transfer or reference accounting would be inferred intent.

## Interface

### Inputs

The function accepts two arguments:

1. **Object-reference address.** An address from which the function reads one 32-bit word when both arguments are nonzero. That word is subsequently used as the object address.
2. **Record address.** An integer-form address. The function passes an address 28 bytes beyond this value to the first dependency. On full success, it writes a 32-bit zero four bytes beyond this value.

Both arguments are tested for zero before either caller-provided memory location is accessed directly.

A nonzero object-reference address does not imply a nonzero object address. A zero word stored at the object-reference address selects a distinct finalization path rather than the immediate invalid-argument return.

### Result

The result has a pointer-shaped representation, but the visible behavior treats it as a status carrier. No dereference of the result occurs within this function.

The possible result sources are:

| Condition | Result |
|---|---|
| Either input argument is zero | Fixed address-shaped value `0xFFFFFFCE`, corresponding to −50 when interpreted as a signed 32-bit word |
| Both inputs are nonzero, but the object word is zero | Value read from an external status slot |
| First dependency returns nonzero | That dependency’s result |
| First dependency returns zero and second dependency returns nonzero | The second dependency’s result |
| Both dependencies return zero | Zero |

The finalization dependency’s return value, if any, does not replace the selected result.

The externally supplied default status is not established to be nonzero. Consequently, a zero return alone does not prove that the success-path field updates occurred.

### Widths and layouts

The supplied representation uses 32-bit words for the object address, integer inputs, status representation, and explicitly accessed fields. It also exposes one 16-bit value passed between dependencies.

The directly relevant layouts are:

| Region | Byte offset | Width | Visible use |
|---|---:|---:|---|
| Object-reference storage | 0 | 32 bits | Read as the object address |
| Object | 16 | 32 bits | Read, decremented by one, then written on success |
| Object | 44 | 32 bits | Read, combined with bit mask 1, then written on success |
| Object | 52 | 32 bits | Read, incremented by one, then written on success |

The function also provides temporary storage to dependencies:

- A 128-byte scratch region.
- A separate four-byte scratch region.
- A 20-byte metadata region comprising five 32-bit slots.
- A four-byte region comprising two 16-bit slots.

Only the first 32-bit metadata slot is explicitly initialized, to zero. The remaining temporary contents are not initialized by the visible function.

These region sizes describe the storage supplied by this function. They do not establish how much each dependency reads or writes.

## Behavior

### 1. Reject zero input arguments

If either argument is zero, the function returns `0xFFFFFFCE`.

On this path:

- It does not read through the object-reference address.
- It does not access the record.
- It does not read the external default-status slot.
- It does not invoke any dependency.
- It does not perform the success-path object updates.

This applies even when the other argument is nonzero but points to inaccessible storage.

The first metadata slot is initialized to zero regardless of argument validity. That is a local-storage action, not a caller-memory write.

### 2. Obtain the object and default status

If both arguments are nonzero, the function:

1. Reads the 32-bit object word from the object-reference address.
2. Reads a pointer-sized default status from an external slot.

The default-status read occurs even if the object word is nonzero and a later dependency will replace the selected status. It therefore cannot be omitted from a contract that accounts for observable reads or faults.

The object word is retained for subsequent dependency arguments and direct object accesses. The function does not visibly reload it from the caller’s reference after a dependency call.

If the object word is zero, both operational stages are skipped. The function invokes F-b0f922796692 with a zero object argument and the metadata-region address, then returns the previously read default status.

### 3. Invoke the first stage

For a nonzero object word, F-5d3e17c1b8e7 receives these arguments, in interface order:

1. The object word.
2. The record address advanced by 28 bytes.
3. The 128-byte scratch-region address.
4. The separate four-byte scratch-region address.
5. The 20-byte metadata-region address.
6. The two-slot, 16-bit-region address.

The supplied evidence does not establish evaluation order among argument expressions. It does establish that the call completes before its result determines whether the second stage runs.

If F-5d3e17c1b8e7 returns nonzero:

- F-2ce20348c424 is not called.
- The nonzero result becomes the selected result.
- F-b0f922796692 is called with the object word and metadata-region address.
- The function returns the selected first-stage result.

There are no direct success-path object or record writes on this branch. The dependencies may nevertheless have side effects.

### 4. Invoke the second stage

If the first stage returns zero, F-2ce20348c424 receives:

1. The same object word.
2. The 128-byte scratch-region address.
3. The metadata-region address.
4. The first 16-bit slot from the two-slot region.
5. The integer value 1.

The first 16-bit slot is read after the first dependency has returned. Its value is not initialized by F-b0987b51cfe6 itself.

The source representation establishes a 16-bit value at this interface boundary but does not settle the exact machine-level extension convention. No signed interpretation should be assigned without further evidence.

If F-2ce20348c424 returns nonzero:

- That result becomes the selected result.
- F-b0f922796692 is called with the object word and metadata-region address.
- The function returns the selected second-stage result.

Again, the direct success-path field changes are skipped.

### 5. Commit the successful state changes

If both stages return zero, F-b0987b51cfe6 does not call F-b0f922796692. It performs the following direct memory operations in this order:

1. Read the 32-bit field at object offset 52, add one, and write the result to that field.
2. Read the 32-bit field at object offset 16, subtract one, and write the result to that field.
3. Read the 32-bit field at object offset 44, set bit 0, and write the result to that field.
4. Write a 32-bit zero to record offset 4.

It then returns zero.

The object-field reads occur after both dependencies. Thus, these updates use the field contents present after the dependency calls, not snapshots taken before them.

The flag update preserves the other 31 bits of the value read at offset 44. There is no visible range check, saturation rule, underflow guard, overflow guard, or validation of the relationship between the two counters.

## Side effects

### Direct effects

The function directly:

- Initializes the first metadata slot.
- Reads caller-provided object-reference storage on valid-input paths.
- Reads the external default-status slot on every valid-input path.
- Updates three object fields and clears one record field only after both stages return zero.

It does not directly overwrite the caller’s object-reference word, except insofar as that storage aliases a success-path write destination.

### Dependency effects

Dependency side effects are unknown. The function supplies object addresses and temporary-region addresses, but their use does not establish:

- Allocation or deallocation.
- Resource acquisition or release.
- Ownership transfer.
- Global-state preservation.
- Whether supplied object or record storage remains valid.
- Whether temporary addresses are retained.

The label “finalization” describes where F-b0f922796692 is invoked, not a proven ownership or cleanup guarantee.

A dependency may modify globals, including the external default-status slot. The status selected from that slot is read before dependency execution; the visible function does not reread it afterward.

### Aliasing and partial completion

No non-aliasing condition is checked.

If writable regions overlap, the ordered reads and writes govern the result. For example, if record offset 4 is the same location as object offset 52, the final zero write overwrites the earlier increment.

The object field updates are not transactional. There is no visible rollback if a later read or write faults. A failure during the decrement, flag update, or final record write may occur after earlier writes have completed.

There is no visible synchronization or atomic read-modify-write operation. Concurrent modification guarantees are unknown.

### Storage lifetime

Temporary regions belong to this invocation. No valid lifetime beyond the function’s return is established. Retaining their addresses requires an external lifetime arrangement not shown here.

The function does not directly allocate or free memory.

## Acceptance examples

These examples are conditional on accessible memory, normally returning dependencies, and no unlisted interference. They are not runtime observations.

### Zero object-reference address

With a zero first argument and any second argument, the result is `0xFFFFFFCE`. No dependency is called and no caller memory is accessed directly.

### Zero record address

With a nonzero first argument and a zero second argument, the result is `0xFFFFFFCE`. The function does not dereference the first argument, even if it would be invalid to do so.

### Reference containing a zero object

With both arguments nonzero and the object-reference word equal to zero:

- The external default status is read.
- Neither operational stage is called.
- F-b0f922796692 receives object value zero and the metadata address.
- The previously read default status is returned.
- The direct success-path writes do not occur.

If the external status is zero, this path returns zero without performing the successful commit.

### First-stage rejection

With a nonzero object and a first-stage result of `0x20`, the second stage is skipped. Finalization is invoked and `0x20` is returned, regardless of the finalization dependency’s ordinary return value.

### Second-stage rejection

With first-stage result zero and second-stage result `0x30`, finalization is invoked and `0x30` is returned. The three direct object updates and record clearing do not occur.

### Successful non-overlapping update

Suppose, after both dependencies return zero:

- Object offset 52 contains 7.
- Object offset 16 contains 3.
- Object offset 44 contains `0xA4`.
- Record offset 4 is a separate writable location.

The resulting values are 8, 2, `0xA5`, and zero, respectively. The result is zero and finalization is not invoked.

### Dependency-modified counter

Suppose object offset 52 initially contains 7, but a dependency changes it to 12 before both stages finish successfully. The direct increment produces 13, because the field is read after both calls.

### Overlapping final destination

If record offset 4 aliases object offset 52, the success path first increments that location and later overwrites it with zero. A non-overlapping-layout assumption would incorrectly predict the final value.
