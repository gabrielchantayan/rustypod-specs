# F-2706939fe3c5

## Purpose

F-2706939fe3c5 repeatedly obtains a 32-bit status word and selects one of four numeric outcomes. A status bit can force immediate completion; another bit requests continued processing through external dependencies. Once continued processing is no longer requested, a third status bit determines the final outcome.

The established behavior is status processing and dependency invocation. Interpreting the routine as a timeout, polling loop, synchronization operation, or device operation is inferred intent only. The supplied evidence does not establish the meaning of the status bits, the units of the second input, or the semantics of the external dependencies.

## Interface

The function accepts four positional inputs and returns a 32-bit value.

| Position | Representation in supplied evidence | Established use |
|---|---|---|
| First | Integer-form address, apparently 32 bits | Locates a field at byte offset `0x3c`; the field supplies a base address used for status processing. |
| Second | Signed integer, apparently 32 bits | Multiplied by decimal `1000` to produce an argument for an external dependency. |
| Third | Opaque 32-bit value | Not referenced by the visible body. |
| Fourth | Unsigned 32-bit value | Initializes a writable, per-invocation status word. |

The visible return values are:

| Value | Selection condition |
|---|---|
| `1` | A continued-processing iteration reaches its second external operation, and that operation returns nonzero. |
| `2` | The status word has mask `0x00000001` set immediately after a status-update call. |
| `3` | The status word has neither mask `0x00000001` nor mask `0x00000080` set, and mask `0x00000008` is clear. |
| `4` | The status word has neither mask `0x00000001` nor mask `0x00000080` set, and mask `0x00000008` is set. |

These are numeric outcomes, not established success or error categories.

### Memory layout and validity

The first input must support a readable field at byte offset `0x3c`. That field is interpreted as an address-sized integer in the apparent 32-bit model. The status-update dependency receives an address formed by adding byte offset `0x1c` to the captured field value.

The function itself does not visibly dereference that derived address. What storage must exist there, how large it must be, and whether it must be readable or writable depend on F-0951c41713db and remain unknown.

The function also reads one global 32-bit word. That word is passed by value to an external dependency; its contents and meaning are unspecified.

No bounds check, null check, alignment check, address-overflow check, or argument-range check is visible. Valid memory accesses and valid arguments for the dependencies are preconditions for a defined execution. The evidence does not establish how an invalid address or invalid dependency argument is handled.

## Behavior

### Initialization and capture order

The function first reads the field at offset `0x3c` from the first input’s referenced storage. This captures the base used for all subsequent status-update calls.

The fourth input initializes the invocation’s writable 32-bit status word. The function then calls F-EXT-001 with no visible arguments and retains its return value as an opaque 32-bit value.

After F-EXT-001 returns, the function reads the global 32-bit word and retains that value separately.

This ordering matters:

- The base field is captured before F-EXT-001 runs.
- The global word is captured after F-EXT-001 runs.
- The visible body does not reread either source during the loop.

Consequently, a change to the original base field during F-EXT-001 does not alter the already captured base. A change to the global word during that call can affect the value subsequently captured, provided the call returns normally.

The fourth input is not inspected before the first status-update call. Its bits therefore do not, by themselves, determine the result: F-0951c41713db receives writable access to the status word before any decision is made.

### Status-update phase

Every iteration begins by calling F-0951c41713db with:

1. The captured base plus byte offset `0x1c`.
2. The address of the invocation’s writable 32-bit status word.

The dependency’s return value is not used by the visible body. The decisions that follow inspect the status word after the dependency returns.

The status word is initialized only once. It is not reset to the fourth input before later iterations. Any value left by one status-update call becomes the value supplied by address to the next call, unless another dependency has modified it through an independently available alias.

### Decision precedence

Immediately after each status-update call, the function checks mask `0x00000001`.

If that bit is set, it returns `2`. No continued-processing dependency call occurs for that iteration. This condition takes precedence over every other tested bit, including masks `0x00000080` and `0x00000008`.

If mask `0x00000001` is clear, the function checks mask `0x00000080`.

- If `0x00000080` is clear, repeated processing ends and final result selection occurs.
- If `0x00000080` is set, the continued-processing phase runs.

Bits outside the three tested masks have no direct influence on the visible branch decisions. They may still matter to F-0951c41713db or other dependencies.

### Continued-processing phase

For each status result with mask `0x00000001` clear and mask `0x00000080` set, the function performs the following ordered interactions.

First, it calls F-EXT-002 with the opaque value returned by F-EXT-001 and the captured global word.

If F-EXT-002 returns nonzero, the function calls F-233fe84cf225 with the numeric argument `10`. The return value of F-233fe84cf225 is not used.

Whether or not that optional call occurred, the function next calls F-EXT-002 again. This call receives the same captured opaque value and a second argument formed by multiplying the second input by decimal `1000`.

If this second F-EXT-002 call returns nonzero, the function returns `1`.

If it returns zero, another iteration begins with F-0951c41713db.

A nonzero result from the first F-EXT-002 call therefore does not directly terminate the function. It only selects the intervening F-233fe84cf225 call. The second F-EXT-002 call still occurs if the optional call returns normally.

There is no visible status-bit check between these two F-EXT-002 calls. There is also no visible iteration limit or locally maintained elapsed-time counter. Repetition can continue indefinitely if the dependencies continue to return normally, each status update retains mask `0x00000080` without mask `0x00000001`, and every second F-EXT-002 call returns zero.

### Final result selection

When a status update leaves both mask `0x00000001` and mask `0x00000080` clear, the function checks mask `0x00000008`.

- Set: return `4`.
- Clear: return `3`.

Mask `0x00000008` is not a termination condition while mask `0x00000080` remains set.

### Integer arithmetic

The status is explicitly represented as an unsigned 32-bit word. The masks select bit positions 0, 3, and 7.

The second input is represented as a signed integer. Its multiplication by `1000` has no visible widening, saturation, range check, or overflow handling. The supplied representation alone does not establish machine behavior for signed overflow.

Under a 32-bit signed interpretation, the product is representable for second-input values from `-2,147,483` through `2,147,483`, inclusive. Behavior beyond that range is **documented_only** pending instruction-level or ABI evidence. A portable reconstruction must not silently substitute either wrapping arithmetic or rejection as established behavior.

The multiplication is reached only during continued processing. Negative inputs are not rejected by the visible body; their acceptability to F-EXT-002 is unknown.

## Side effects

- Reads the global word after F-EXT-001 returns.
- Passes writable access to the status word to F-0951c41713db.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Dependency results and status updates are stipulated; all invoked dependencies are assumed to return normally unless specified otherwise.

1. **Immediate priority outcome.**  
   The first status update leaves `0x00000089`. The result is `2`. Neither F-EXT-002 nor F-233fe84cf225 is called, despite the continued-processing and final-selection bits also being set.

2. **Final result without repetition.**  
   The first status update leaves `0x00000008`. The result is `4`. F-EXT-001 and the status-update dependency have already run; neither continued-processing call occurs.

3. **Unrelated status bits.**  
   The first status update leaves `0x00000002`. The result is `3`, because all three tested masks are clear.

4. **Direct continued-processing exit.**  
   A status update leaves `0x00000080`. The first F-EXT-002 call returns zero, so F-233fe84cf225 is skipped. The second F-EXT-002 call returns nonzero, producing result `1` without another status update.

5. **Optional call followed by another iteration.**  
   A status update leaves `0x00000088`. The first F-EXT-002 call returns nonzero, so F-233fe84cf225 receives `10`. The second F-EXT-002 call returns zero. Processing repeats rather than returning `4`; mask `0x00000008` has no final-selection effect while continued processing is active.

6. **Initial status can be replaced.**  
   The fourth input is `0x00000001`, but the first status update replaces it with zero. The result is `3`, not `2`.

7. **Representable scaled input.**  
   With second input `7`, each reached second F-EXT-002 call receives `7000` as its second argument. This does not establish that the value denotes any particular time unit.

8. **Persistent repetition.**  
   Every status update leaves `0x00000080`, and every second F-EXT-002 call returns zero. No return is forced by the visible body.
