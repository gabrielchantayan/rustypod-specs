# F-774d5a2aa94a

## Purpose

F-774d5a2aa94a performs an assignment-like operation between two descriptors representing storage traversed in 12-byte units. Every normal return yields the original destination descriptor address.

The established control flow distinguishes:

- Identical descriptor addresses: return without descriptor access or dependency calls.
- Insufficient capacity-like result: obtain replacement storage, perform a transfer-like operation, invoke a release-like dependency, and install new descriptor fields.
- Sufficient capacity-like result with a shorter destination range: perform a prefix operation, update the logical endpoint, and perform a tail operation.
- Sufficient capacity-like result with an equal or longer destination range: perform a range operation, traverse the remaining destination range, and set both endpoint fields to one computed address.

“Assignment,” “capacity,” “allocation,” “transfer,” and “release” describe inferred intent. The dependency implementations are unavailable; their element operations, ownership effects, and preservation guarantees are not established.

A material distinction is explicit: extension within existing storage does not directly write the third destination field, whereas equal-or-shorter reuse sets that field equal to the newly computed logical endpoint.

## Interface

### Arguments and return value

The function receives four arguments:

| Argument | Representation and use |
|---|---|
| Destination descriptor | Address of an object containing at least three consecutive 32-bit fields accessible as required by the selected path |
| Source descriptor | Address of an object whose first two consecutive 32-bit fields are read directly; dependencies may require more |
| First auxiliary value | Unsigned 32-bit value |
| Second auxiliary value | Unsigned 32-bit value |

The return value is the original destination descriptor address, not its storage-start field.

The auxiliary values do not influence any visible branch, dependency argument, descriptor write, or return value. On a distinct-descriptor call they are initially retained internally, but the replacement path overwrites both retained values before selecting an extent. Other paths do not consume them.

There is no explicit error return or status output.

### Descriptor representation

| Byte offset | Established direct use | Inferred meaning |
|---|---|---|
| 0 | Read as a storage address; written during replacement | Storage beginning |
| 4 | Read as a traversal endpoint; written on every completed nonidentity path | Logical end |
| 8 | Written during replacement and equal-or-shorter reuse; never directly read here | Capacity or storage-limit endpoint |

Each field occupies 32 bits in the supplied representation. Address-valued fields cannot be silently widened into a different native pointer representation.

The only established element-layout property is the 12-byte stride. Element contents, alignment, and lifetime requirements are unknown.

### Preconditions and validity limits

The function contains no explicit checks for null descriptors, invalid fields, overlapping storage, arithmetic overflow, allocation failure, or inconsistent endpoints.

Ordinary successful use requires:

- Accessible descriptor fields for the accesses actually performed.
- Arguments acceptable to each invoked dependency.
- Valid storage relationships for those dependencies’ undisclosed operations.
- Termination of any selected equality-based traversal.
- Meaningful address calculations under the actual execution model.

These are validity requirements, not checks implemented by this function. Descriptor identity avoids all direct descriptor-field accesses, but the legality of comparing or returning a particular pointer value still depends on the execution environment.

## Behavior

### Descriptor identity

The first decision compares the two descriptor addresses.

If they are identical, the function immediately returns the destination address. It makes no dependency call and directly reads or writes no descriptor field.

Equal descriptor contents or equal storage-start fields do not trigger this shortcut when descriptor addresses differ.

### Initial branch selection

For distinct descriptors, the function calls, in order:

1. F-32a0cd51a77a with the source descriptor.
2. F-ff4e8fed3f72 with the destination descriptor.

Their results are compared as unsigned 32-bit values. If the second result is less than the first, replacement is selected. Otherwise, storage reuse is selected.

The first dependency has an inferred count-like role; the second has an inferred capacity-like role. These roles do not establish that either dependency is observationally pure.

Results and descriptor fields are obtained again later. An implementation must not substitute a single entry-time descriptor snapshot or cache all repeated count-like calls without an independent preservation guarantee.

### Replacement: selecting the extent

After replacement is selected, F-32a0cd51a77a is called again, first on the source and then on the destination.

Let these new unsigned 32-bit results be \(s\) and \(d\). Two growth candidates are calculated:

\[
g=\left(d+\lfloor d/2\rfloor+\lfloor d/8\rfloor\right)\bmod 2^{32}
\]

\[
b=(d+32)\bmod 2^{32}
\]

The selected extent \(n\) is the unsigned maximum of \(g\), \(b\), and \(s\). The shifts used to form the fractional terms are unsigned right shifts. The comparisons occur after the candidate additions have wrapped, if necessary.

The allocation-size argument is:

\[
q=(12n)\bmod 2^{32}
\]

No overflow check is present. In particular, the nonoverflowing growth formula must not replace these wrapped calculations at boundary values.

### Replacement: obtaining and using storage

F-871e64ddc6de receives \(q\) and a literal zero. Its result is retained as the proposed new storage address. The function does not explicitly test that result for failure.

Next, F-7a5eff9d82aa receives:

- The source’s current first field.
- The source’s current second field.
- The retained allocation result.
- The destination descriptor address.

These source-field reads occur after F-871e64ddc6de returns. The return value of F-7a5eff9d82aa is ignored.

After that call returns, the destination’s current first field is captured. A cursor starts at this captured address and advances by 12 until it equals the destination’s observed second field. The traversal body contains no visible element access, destructor call, or storage write.

After traversal termination:

1. F-ff4e8fed3f72 is called with the destination descriptor.
2. F-ff1bdc376dcd receives the captured traversal-start address, the result of that call, and zero.

The captured address is not refreshed after F-ff4e8fed3f72. Its result is passed directly as the second argument to F-ff1bdc376dcd; this function does not multiply that argument by 12.

### Replacement: installing descriptor fields

Only after F-ff1bdc376dcd returns does the function directly write the retained allocation result into the destination’s first field.

It then:

1. Calls F-32a0cd51a77a with the source descriptor.
2. Reads the destination’s then-current first field and uses the newly returned count-like result to compute the second-field endpoint.
3. Writes that endpoint to the destination’s second field.
4. Reads the destination’s first field again and computes the third-field endpoint using the retained extent \(n\).
5. Writes that endpoint to the destination’s third field.

The endpoint offsets are 12 times the corresponding result or extent, subject to the arithmetic qualifications below.

The final first field is not unconditionally guaranteed to equal the allocation result. The intervening F-32a0cd51a77a call may change it. Likewise, the source result used for the logical endpoint need not equal any earlier source result, including the one used to select \(n\).

### Reuse: selecting extension or equal-or-shorter handling

After the initial comparison selects reuse, F-32a0cd51a77a is called on the destination and then on the source. These fresh results are compared as unsigned 32-bit values.

A smaller destination result selects extension. Otherwise, equal-or-shorter handling is selected. The earlier capacity-like comparison is not repeated.

### Reuse with extension

F-32a0cd51a77a is called once more on the destination. Let its retained result be \(p\).

F-cd3da9d8a1a0 then receives:

- The source’s current first field.
- That source start plus \(12p\).
- The destination’s current first field.

Its return value is ignored.

Next, F-32a0cd51a77a is called with the source descriptor. The function computes an endpoint using that result and the destination’s then-current first field, and writes it to the destination’s second field.

Only after this write, F-7a5eff9d82aa receives:

- The source’s current first field plus \(12p\).
- The source’s current second field.
- The destination’s current first field plus \(12p\).
- The destination descriptor address.

The retained \(p\) is not refreshed, although the descriptor fields are read again for this call.

The function then returns immediately. It does not directly write the first or third destination field on this path. The final dependency may nevertheless modify any fields it can access.

### Reuse with an equal or longer destination

F-cd3da9d8a1a0 receives the source’s current first and second fields and the destination’s current first field.

Its result becomes a traversal cursor. The cursor advances by 12 until it equals the destination’s observed second field. As on replacement, this traversal has an empty body.

After termination, F-32a0cd51a77a is called on the source. The destination’s then-current first field and this new result determine one endpoint. That computed endpoint is written first to the second destination field and then to the third.

Thus, if the third field represents capacity, this path contracts the reported capacity to the computed logical end. The two equal writes are established; their capacity interpretation is inferred.

### Arithmetic and read-order boundaries

Unsigned comparisons, growth calculations, and allocation-size multiplication have the 32-bit behavior specified above.

Some count-like results are subsequently held in signed 32-bit intermediates, and some endpoint calculations combine signed intermediates with address-valued fields. The supplied representation does not settle language-level signed-overflow or invalid-pointer behavior. It is not sufficient evidence to declare every endpoint calculation safely wrapping modulo \(2^{32}\).

Reads supplying one dependency call occur after the preceding call and before that dependency begins. A left-to-right evaluation order among the arguments of a single call is not established. Loop conditions observe the destination’s second field; it is not explicitly captured once before the loop.

### Ownership and element effects

The visible sequence resembles allocation, transfer, release, and installation. It does not establish that:

- New storage is owned by the destination.
- Old storage is actually released.
- Either transfer-like dependency copies, moves, assigns, or constructs elements.
- The source remains unchanged.
- Dependencies preserve descriptors or global state.
- Empty traversal bodies perform element destruction.

No explicit release-like call occurs on either reuse path.

### Errors and partial state

There is no explicit failure branch, rollback, exception handler, or restoration operation.

In particular, extension writes the new second field before its final dependency call. Replacement installs the allocation result before its final count-like call. Failure or abnormal exit after either write can leave partially updated state.

Dependency failures, memory faults, nonlocal exits, and nontermination remain unspecified.

## Acceptance examples

These are conditional static expectations, not runtime results.

Except for the identity and explicitly mutating examples, assume:

- Distinct, nonoverlapping descriptor objects and valid nonoverlapping represented storage.
- Count-like and capacity-like results remain as stated.
- Every dependency returns normally.
- Dependencies and external actors preserve both descriptors’ fields and the stated range relationships throughout the example. The only descriptor changes are this function’s direct writes.
- Count-like values agree with the stated 12-byte ranges.
- Arithmetic is representable without problematic overflow, and traversals terminate.

These are example-only assumptions, not guarantees supplied by the dependencies.

### Identity

When both descriptor arguments are the same address, the result is that address. There are no dependency calls or direct descriptor-field accesses. No dependency-preservation assumptions are needed.

### Replacement dominated by the minimum increment

For source count 20, destination count 10, and destination capacity 15, replacement is selected.

The growth candidates are 42 and 16. The selected extent is 42, so F-871e64ddc6de receives 504 and zero.

If it returns address \(A\), the final destination fields are \(A\), \(A+240\), and \(A+504\), under the preservation assumptions above.

The four-argument transfer-like call precedes the release-like call. Installation of \(A\) follows the release-like call.

### Replacement dominated by proportional growth

For source count 121, destination count 100, and destination capacity 120, the candidates are 132 and 162. The selected extent is 162, and the allocation-size argument is 1,944.

Under the preservation assumptions, the final logical endpoint is 1,452 bytes beyond the installed start, and the third field is 1,944 bytes beyond it.

### Mutation after replacement installation

Use the first replacement example, but replace its preservation assumption for the final F-32a0cd51a77a call.

Suppose that call returns 20 while changing the destination’s first field from installed address \(A\) to another valid address \(B\). Assume no other mutations and valid arithmetic for \(B\).

The final fields are then \(B\), \(B+240\), and \(B+504\). The direct installation of \(A\) still occurred, but it does not determine the final first field or the bases used by the subsequent endpoint calculations.

### Extension within existing storage

For destination count 2, source count 5, and destination capacity 8, the retained prefix length is 2.

Under the preservation assumptions, the prefix call spans 24 source bytes. The second destination field is then written to destination start plus 60. Only afterward does the four-argument call receive tail ranges beginning 24 bytes beyond their respective starts.

There is no direct third-field write.

### Shorter source with reuse

For destination count 5, source count 2, and destination capacity 8, suppose F-cd3da9d8a1a0 returns destination start plus 24.

Under the preservation assumptions, the destination’s second field still denotes start plus 60 during traversal. The cursor advances through offsets 24, 36, and 48 before reaching 60. Both endpoint fields are subsequently written to start plus 24.

Without preservation of the old second field and relevant range relationships, this traversal expectation would not follow merely from the returned cursor and stable count-like results.

### Empty source

With source count zero on equal-or-shorter reuse, and the stated preservation and termination assumptions, both endpoint fields become the destination’s first field. No explicit release-like call occurs.

### Wrapped growth boundary

If replacement is selected and the fresh source and destination results are both \(2^{32}-1\), the wrapped minimum-increment candidate is 31 and the proportional candidate is 2,684,354,557.

The source result therefore determines \(n=2^{32}-1\), and the allocation-size argument is 4,294,967,284. This establishes argument arithmetic only; it does not imply allocation success or valid subsequent address calculations.

## Uncertainties

The following remain **documented_only**:

- Exact dependency operations, preservation guarantees, failure modes, and ownership effects.
- Whether count and capacity interpretations hold for every descriptor state.
- Permitted descriptor overlap, storage aliasing, and source mutation.
- Element representation, alignment, construction, assignment, and destruction requirements.
- Signed-overflow and pointer-validity behavior in endpoint calculations.
- Whether any external mutation or concurrency is permitted.
- Why the traversals have no visible element operation.

Traversal termination uses equality, not an ordered boundary condition. Under a purely wrapping 32-bit cursor model, repeated additions of 12 can reach only endpoints in the same residue class modulo 4. That arithmetic observation does not establish actual signed-overflow behavior or storage validity.

Repeated dependency calls and later field reads remain semantically significant unless preservation is independently established.
