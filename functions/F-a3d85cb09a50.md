# F-a3d85cb09a50

## Purpose

F-a3d85cb09a50 performs an in-place rearrangement of linked records. Under a conventional binary-tree interpretation, it is a left rotation: the original record’s right child moves into its position, the promoted record’s left subtree becomes the original record’s right subtree, and the original record becomes the promoted record’s left child.

The established behavior is a sequence of 32-bit memory reads and writes. Tree terminology describes the apparent structural roles of those locations; it does not establish that callers maintain a valid tree, that the records contain keys, or that any ordering or balancing invariant is checked.

The operation also updates either a separately stored root link or one link in the original record’s parent. It performs no validation, allocation, deallocation, balancing-metadata update, or recovery.

## Interface

### Inputs

The function takes two values represented as 32-bit integers in the supplied source:

- **Context address:** used to locate an indirect root-link container.
- **Pivot address:** identifies the record being moved downward.

Both values are used as memory addresses. The apparent target model uses 32-bit address-bearing fields. The source does not independently establish the platform ABI, alignment rules, or pointer provenance requirements.

The function has no explicit return value.

### Relevant memory layout

The function accesses the following fields. All offsets are byte offsets, and all accessed fields are 32 bits wide.

| Object | Offset | Operational role |
|---|---:|---|
| Context | `0x10` | Address of the root-link container |
| Root-link container | `0x04` | Root record address |
| Linked record | `0x04` | Parent link |
| Linked record | `0x08` | Left-child link |
| Linked record | `0x0c` | Right-child link |

These are partial layouts, not complete object definitions. No behavior is established for other bytes in these objects.

For this contract:

- **Pivot** is the record supplied by the second argument.
- **Promoted record** is the address initially read from the pivot’s right-child field.
- **Transfer record** is the record designated by the promoted record’s left-child field, when that field is nonzero.
- **Root slot** is the field at offset `0x04` in the container reached through context offset `0x10`.

Zero is treated as absence only when testing the promoted record’s left-child link. The function does not check whether the pivot, promoted record, root-link container, or required parent address is zero.

### Preconditions for ordinary tree behavior

A caller expecting a valid rotation must provide:

- Readable and writable storage for every field reached by the selected execution path.
- A valid pivot with a valid, nonzero right child.
- A valid root-link container reachable through the context.
- If the pivot is not the root, a valid parent whose appropriate child link identifies the pivot.
- If the transferred left child is nonzero, a valid writable parent field in that child.
- A structurally coherent, non-overlapping arrangement that does not create unintended aliases among the accessed fields.
- No interfering mutation during the operation.

These are caller obligations, not checks performed by the function. The context and container fields used only for reads need not themselves be writable.

## Behavior

### Observable access sequence

The following ordering is established by the supplied source at its recovered-operation level. It does not claim instruction-level access counts, atomicity, or memory-ordering guarantees.

1. The function reads the pivot’s right-child field and retains that address as the promoted record for the remainder of the operation.

2. It reads the promoted record’s left-child field and writes that 32-bit value into the pivot’s right-child field.

3. It reads the promoted record’s left-child field again and tests whether the value is nonzero.

   If it is nonzero, the function reads that field again to obtain the destination record address, then writes the pivot address into that record’s parent field.

   If it is zero, this parent-field write is skipped.

4. It reads the pivot’s parent field and writes that value into the promoted record’s parent field.

5. It reads the container address from context offset `0x10`, forms the root-slot address by adding `0x04`, and reads the root slot.

6. It chooses exactly one reconnection path:

   - **Root match:** If the root-slot value equals the pivot address, it writes the promoted record address into that root slot.
   - **No root match:** It reads the pivot’s parent field again, then reads that parent’s left-child field. If the left-child value equals the pivot address, it writes the promoted record address into that left-child field. Otherwise, it writes the promoted record address into that parent’s right-child field.

7. It writes the pivot address into the promoted record’s left-child field.

8. It writes the promoted record address into the pivot’s parent field.

The function then returns without an explicit result.

The root-slot address selected in step 5 is the address used for the root-match write. The context’s container field is not reread for that write. Likewise, the promoted record remains the address obtained in step 1; the pivot’s right-child field is not reread to choose it.

### Result for a coherent, non-aliased structure

With stable memory and the ordinary tree preconditions satisfied, the final relationships are:

- The promoted record occupies the pivot’s former position in the surrounding tree.
- The promoted record’s parent is the pivot’s former parent.
- The pivot’s parent is the promoted record.
- The promoted record’s left child is the pivot.
- The pivot’s right child is the promoted record’s former left child.
- If that former left child was nonzero, its parent is the pivot.
- The former incoming link to the pivot—either the root slot or a parent child-link—now names the promoted record.

The pivot’s left-child field and the promoted record’s right-child field are not directly written. Neither are payloads, comparison keys, colors, heights, subtree counts, or other unshown metadata.

### Branch precedence and inconsistent structures

The root-slot comparison takes precedence over parent-link inspection. When the root slot equals the pivot address, the function does not inspect the pivot parent’s child fields. It nevertheless has already copied the pivot’s parent value into the promoted record’s parent field.

When the root slot does not equal the pivot address:

- A matching parent left-child link selects the left-link update.
- Every nonmatching left-child value selects the right-link update.
- The function does not check that the parent’s right-child link actually names the pivot.

Thus, an inconsistent structure is not rejected. In particular, a non-root pivot whose parent names it in neither child field still causes the parent’s right-child field to be overwritten.

### Repeated reads and aliasing

The transfer link and pivot parent are read more than once. Their values are not universally snapshotted at entry.

For a valid, stable, non-aliased tree, these repeated reads normally observe unchanged values. With overlapping records, unusual field aliases, or external interference, earlier writes may affect later reads. The simple rotation result is therefore conditional on the structural preconditions.

The established access sequence, rather than an assumed abstract rotation, governs such cases to the extent the underlying execution model permits them. This contract does not promise useful behavior for invalid overlapping objects or concurrent data races.

## Side effects

For an ordinary valid invocation, the function performs five unconditional 32-bit field writes:

1. Pivot right-child link.
2. Promoted record parent link.
3. One root or parent child-link.
4. Promoted record left-child link.
5. Pivot parent link.

A nonzero transfer link adds one write to the transfer record’s parent field, for six field-write operations in total.

These counts describe operations, not necessarily distinct addresses when aliases exist.

No allocation, deallocation, ownership transfer, callback, external call, or I/O appears in the supplied body. The function changes structural references; it does not establish who owns any referenced record.

The update is not transactional. Intermediate states include partially rewired relationships. No lock, atomic publication mechanism, rollback, or failure-status path is shown. An invalid access could occur after earlier writes have already modified memory; the source provides no cleanup for that situation.

No synchronization or concurrent-reader safety guarantee is established.

## Acceptance examples

The following are conditional acceptance cases derived from static inspection. They are not results of runtime tests. Unless stated otherwise, all objects are valid, distinct where required, non-overlapping, and stable during execution.

### Root pivot with no transfer record

Initially:

- The root slot names the pivot.
- The pivot’s parent is zero.
- The pivot’s right child is the promoted record.
- The promoted record’s left child is zero.

After normal completion:

- The root slot names the promoted record.
- The promoted record’s parent is zero.
- The promoted record’s left child is the pivot.
- The pivot’s parent is the promoted record.
- The pivot’s right child is zero.

No transfer-record parent write occurs.

### Root pivot with a transfer record

Initially, the root slot names the pivot, and the promoted record’s left child names a valid transfer record.

After normal completion:

- The promoted record replaces the pivot in the root slot.
- The pivot’s right child names the transfer record.
- The transfer record’s parent names the pivot.
- The promoted record’s left child names the pivot.
- The pivot’s parent names the promoted record.
- The promoted record’s parent equals the pivot’s original parent value.

The transfer record’s own child links are not directly changed.

### Non-root pivot in a left-child position

Initially:

- The root slot does not name the pivot.
- The pivot’s parent names a valid parent record.
- That parent’s left child names the pivot.

After normal completion, the parent’s left child names the promoted record. Its right-child field is not directly written. The remaining relationships follow the rotation result described above.

### Non-root pivot in a right-child position

Initially, the root slot does not name the pivot, the parent’s left child does not name the pivot, and its right child does.

After normal completion, the parent’s right child names the promoted record. The parent’s left-child field is not directly written.

### Inconsistent parent links

Initially, the root slot does not name the pivot, and neither child link in the pivot’s valid parent names the pivot.

The established behavior is still to overwrite that parent’s right-child field with the promoted record address. Acceptance of a faithful behavioral description requires documenting this fallback rather than inventing validation or an error return.

### Root match with a nonzero parent value

Initially, the root slot names the pivot, but the pivot’s parent contains a nonzero value.

The function copies that value into the promoted record’s parent field and updates the root slot. It does not normalize the promoted record’s parent to zero or inspect child fields through the copied value on this branch.

### Missing promoted record

Initially, the pivot’s right-child field is zero.

The function does not treat this as a no-op. It attempts to read the left-child field at offset `0x08` from that zero-valued address. No successful completion or controlled error response is established.
