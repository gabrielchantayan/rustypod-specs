# F-795a1ebd3a79

## Purpose

F-795a1ebd3a79 inserts a caller-supplied node into a singly linked chain at the first position whose existing node has a signed key greater than the supplied node’s key, or at the end if no such position exists.

The operation modifies links in place. It does not allocate a node, copy node contents, validate the chain, or return a status.

For an initially nondecreasing chain and a distinct, detached node, the resulting chain remains nondecreasing. Existing nodes with equal keys precede the inserted node. This ordering property is conditional on those structural preconditions; the function neither checks nor establishes that the input chain is sorted.

## Interface

### Inputs

The function receives two pointer arguments:

- **Root-link address:** the address of a writable slot containing the address of the first node, or a null address for an empty chain. This slot can be a standalone head field or a link field embedded in another object.
- **Incoming-node address:** the address of the node to insert.

Neither argument is optional. A null value stored in the root-link slot represents an empty chain; a null root-link address does not.

### Node layout

The function accesses two consecutive integer-sized fields in each node:

| Field | Position | Interpretation |
|---|---|---|
| Key | First integer-sized field | Signed integer used for ordering |
| Successor | Second integer-sized field | Integer representation of the next node’s address; zero denotes the end |

The incoming node must provide writable storage for its successor field. Its key must be readable whenever a comparison is reached. Existing nodes need readable key and successor fields, and the predecessor link selected for insertion must be writable.

The root-link slot uses the same address representation as a node’s successor field.

### Widths and address representation

The supplied representation stores node addresses in integer fields and converts between integer values and pointers. Its intended interpretation is consistent with a 32-bit address model:

- A signed 32-bit key.
- A 32-bit successor-address field.
- A successor-field offset of four bytes.
- Eight bytes covering the two accessed node fields.

**The exact ABI is not established by the function alone.** The established layout is two consecutive integer-sized fields, with the second field one integer-sized element after the first. Treating those elements and addresses as 32 bits requires an ABI in which these address conversions preserve the relevant pointers.

Under the 32-bit interpretation, the key range is −2,147,483,648 through 2,147,483,647. Comparisons are signed. No key addition, subtraction, or increment occurs, so key arithmetic cannot overflow within this function.

A port must not silently substitute unsigned key ordering or assume that a wider pointer can be stored losslessly in the existing integer-sized address field.

### Output

The function has no return value. Its observable result is the changed link structure.

There is no success indicator, insertion index, duplicate-key report, or error result.

## Behavior

### Search boundary

The search begins by reading the address stored in the root-link slot.

At each non-null node reached, the function compares that node’s key with the incoming node’s key:

- If the existing key is less than or equal to the incoming key, traversal continues through that existing node.
- If the existing key is greater, traversal stops before that node.
- If a null successor is reached, traversal stops at the end.

The incoming key is consulted for each comparison; it is not established as a once-only snapshot. With stable input memory, every comparison sees the same value.

The search records the link slot through which insertion will occur. Initially this is the supplied root-link slot. After passing an existing node, it becomes that node’s successor field.

Consequently, the chosen position is the first strictly greater key encountered along the actual chain. The function does not search beyond that boundary.

### Insertion and write order

After traversal stops, the function performs two stores in this order:

1. It replaces the incoming node’s successor field with the address at which traversal stopped. That address is either the first greater-key node or null.
2. It replaces the selected insertion-link slot with the incoming node’s address.

This order matters when storage aliases. The incoming successor is written before the incoming node is linked through the selected slot.

On a normal insertion involving distinct storage, the former incoming successor is discarded, the incoming node points to the remainder of the chain, and the predecessor or root points to the incoming node.

The incoming key is not assigned. Existing node keys are not assigned. Existing successor fields remain unchanged except for the one selected as the insertion-link slot, if that slot belongs to an existing node.

### Read order and conditional accesses

The following ordering is established at the behavioral level:

- The root-link value is read before any node key.
- A null current address terminates traversal without a key comparison.
- At a non-null current address, both the current key and the incoming key are needed to decide whether traversal continues.
- A current node’s successor is read only after that node satisfies the less-than-or-equal comparison.
- Both insertion stores occur after traversal finishes.
- The incoming-successor store precedes the insertion-link store.

The supplied expression does not establish which of the two key reads occurs first within an individual comparison. A contract requiring one particular operand-read order would exceed the available evidence.

For an empty chain, no key comparison is performed. The function still needs writable incoming-successor storage and a writable root-link slot.

These are logical memory accesses established by the representation, not a specification of individual machine loads, atomic operations, or memory barriers.

### Equal keys

The comparison admits existing nodes whose keys equal the incoming key. Therefore, within a nondecreasing chain, the incoming node is placed after all existing nodes with that key.

This is stable placement relative to the nodes already present. It is not a duplicate-elimination operation: equal keys do not prevent insertion.

### Unsorted input

Sortedness is not checked.

For an unsorted chain, the function stops at the first greater key even if a later node has a smaller or equal key. The resulting chain follows this local insertion rule and need not be globally sorted.

For example, an incoming key of 5 presented to a chain with keys 2 → 9 → 1 is inserted between 2 and 9. The later key 1 is never examined.

### Termination

Termination requires traversal eventually to encounter either:

- A null link; or
- A node whose key is greater than the incoming key.

A finite, acyclic chain satisfies this condition.

A cyclic chain can also terminate if a greater-key node is encountered before traversal becomes trapped in the cycle. If traversal repeatedly encounters only keys less than or equal to the incoming key, it does not terminate. There is no cycle detection or traversal limit.

## Side effects

### Memory changes

On normal completion, the function executes two link stores. They need not address two distinct memory locations.

For ordinary detached-node insertion:

- The incoming node’s old successor value is overwritten.
- Exactly one link in the existing chain, or the root-link slot, is redirected.
- No key is changed.
- No other node storage is copied or initialized.

The function makes no external calls and performs no explicit allocation, deallocation, logging, or I/O.

### Ownership and lifetime

The caller supplies all storage. The function neither creates nor releases ownership of an allocation.

After successful ordinary insertion, the chain contains a reference to the supplied node. The caller must keep that node alive for as long as consumers can reach it. The function supplies no lifetime tracking or reclamation mechanism.

An existing value in the incoming successor field is not followed, released, or preserved merely because it was present before insertion.

### Aliasing and preconditions

For the ordinary insertion guarantee, the incoming node should be distinct from every node reachable from the supplied root, and its storage should not overlap the root-link slot or existing nodes.

These separation conditions are not checked.

If the incoming node is already reachable, the function does not first unlink it. Reinsertion can create a cycle or otherwise change reachability. In particular, if traversal passes the incoming node and then stops at its immediate successor, the selected insertion-link slot is the incoming node’s own successor field. The final store then makes that field point to the incoming node itself.

More general overlapping storage can cause link stores to overwrite keys or other fields. Such cases do not receive the sorted-insertion guarantee.

### Errors and concurrency

There is no explicit error handling for invalid pointers, inaccessible storage, malformed links, misalignment, or incompatible address representations. Such inputs can cause invalid memory accesses or behavior not defined by the applicable execution environment; no particular failure result is promised.

No synchronization is present. The function does not establish atomic insertion for concurrent readers or writers. Concurrent mutation also invalidates assumptions about stable keys and links.

## Acceptance examples

These examples are conditional behavioral expectations derived from static evidence. They have not been executed. Unless stated otherwise, nodes are distinct, links are valid, memory is stable, and the incoming node is detached.

### Empty chain

Given a root-link slot containing null and an incoming node with key 7:

- The incoming successor becomes null.
- The root-link slot becomes the incoming node’s address.
- No key comparison is required.
- Any previous incoming successor value is discarded.

### Insertion before the first node

Given keys 4 → 8 and an incoming key of 1:

- The result is 1 → 4 → 8.
- The incoming successor is set to the former first node.
- The root-link slot is then changed to the incoming node.
- The existing nodes’ links remain unchanged.

### Interior insertion

Given keys 1 → 4 → 9 and an incoming key of 6:

- The result is 1 → 4 → 6 → 9.
- The links through keys 1 and 4 are traversed.
- The key-9 node is the stopping boundary.
- The incoming successor is set to the key-9 node before the key-4 successor is redirected.

### Placement after equal keys

Given keys 2 → 5 → 5 → 8 and an incoming key of 5:

- The result is 2 → 5 → 5 → 5 → 8.
- Both pre-existing key-5 nodes remain ahead of the incoming node.
- No existing duplicate is removed or replaced.

### Append at the end

Given keys −3 → 0 → 12 and an incoming key of 20:

- Traversal reaches the null successor after key 12.
- The incoming successor becomes null.
- The former last node points to the incoming node.
- The root-link value remains unchanged.

### Signed boundary behavior

Under the 32-bit key interpretation, given an existing key of −1 and an incoming key of 0:

- The existing node is passed because −1 is less than 0.
- The incoming node is inserted after it if no later node blocks traversal.

Likewise, a minimum signed key precedes larger keys, and a maximum signed key follows all existing nodes in a sorted chain. These outcomes require signed, not unsigned, comparison.

### Unsorted chain

Given keys 2 → 9 → 1 and an incoming key of 5:

- The result is 2 → 5 → 9 → 1.
- The operation does not repair the existing disorder.
- The key-1 node is not examined.

### Incoming node already present

Given a one-node chain whose sole node is also supplied as the incoming node:

- The equal-key comparison passes that node.
- Traversal reaches its null successor.
- The final link store makes the node point to itself.
- The result is a self-cycle, not an unchanged one-node chain.

This example demonstrates why detached-node separation is necessary for the ordinary insertion guarantee.
