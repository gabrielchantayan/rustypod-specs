# F-43da6b23bd44

## Purpose

F-43da6b23bd44 conditionally invokes an indirect operation, optionally issues notifications before and after it, and returns the operation’s pointer-shaped result. On one result path, it also copies a single byte from shared storage to the returned address.

A signed first argument greater than zero enables processing. A nonpositive first argument produces a null result without dereferencing a dispatch record or invoking a dependency. Evaluation of the shared dispatch reference nevertheless precedes this decision.

The dispatch reference used for the initial zero store is evaluated separately from the reference captured for subsequent indexed accesses. Likewise, each notification-presence check is distinct from the later evaluation that supplies its call target. These distinctions matter if shared state changes between evaluations; the representation does not establish safe concurrent mutation or a fixed machine-level load count.

“Operation” and “notification” describe call roles only. Allocation, instrumentation, and buffer initialization are possible interpretations, not established purposes.

## Interface

### Arguments

| Position | Width and interpretation |
|---|---|
| First | Signed 32-bit integer. Controls eligibility, is forwarded to dependencies, and determines whether a non-null result receives the final byte write. |
| Second | Opaque 32-bit value, forwarded unchanged. |
| Third | Opaque 32-bit value, forwarded unchanged. |
| Fourth | Opaque 32-bit value. Becomes the principal dependency’s fifth argument unless the entry-notification branch is taken, in which case zero is passed instead. |

The function does not directly dereference the second, third, or fourth arguments. Their interpretation by dependencies is unknown.

### Result

The result is a byte-addressable, pointer-shaped value in the represented 32-bit address model:

- A nonpositive first argument returns null.
- A positive first argument returns the principal dependency’s result, provided subsequent processing completes normally.
- Notification return values do not replace that result.

A non-null result establishes neither ownership nor an allocation size. It does not identify an appropriate release operation or guarantee that storage remains valid after notifications.

### Shared storage

A shared reference supplies dispatch-record addresses. One evaluation captures the record reference used for subsequent indexed accesses. A later evaluation supplies the address for the initial zero store on the positive-input path.

The relevant dispatch layout uses four-byte words:

| Byte offset | Slot | Observed use |
|---|---:|---|
| 0 | 0 | Receives a four-byte zero through the separately evaluated shared reference. |
| 4 | 1 | Receives a four-byte zero through the captured reference when the entry-notification check succeeds. |
| 12 | 3 | Supplies the principal call target and its fourth argument through the captured reference. |
| 40 | 10 | Supplies notification-presence checks and, separately, notification call targets through the captured reference. |

The highest accessed dispatch word occupies offsets 40 through 43. This layout does not assign meanings to intervening fields.

A separate shared reference supplies the address of a readable byte. That reference and byte are used only for the final conditional write.

Four-byte dispatch words and signed 32-bit control arithmetic are established. No wider-address adaptation, byte-order requirement, or exact machine-level calling convention is established.

### Preconditions

For processing to complete normally on a positive first argument:

- The address selected by the shared-reference evaluation for the initial store must permit a four-byte write.
- The captured record must support the indexed accesses actually taken.
- Slot 1 of the captured record must permit a four-byte write if the entry-notification check succeeds.
- The principal call target must be callable with the described interface.
- Each notification target actually evaluated for a call must be callable with the notification interface.
- Required record storage must remain accessible across dependency calls.
- If the final write is selected, the byte-source address must be readable and the retained result must permit a one-byte write.

The function performs no explicit validation or lifetime checks. There is no established recoverable response for invalid addresses or incompatible callees.

For nonpositive input, no dispatch-record storage is dereferenced. The initial evaluation of the shared reference still occurs.

## Behavior

### Entry and disabled path

The function first captures the shared dispatch reference and establishes a null result.

If the first argument is zero or negative, it returns null. It does not:

- Store zero into a dispatch word.
- Read a principal or notification address from a dispatch record.
- Invoke a dependency.
- Read the separate byte source.
- Write through a returned address.

This path avoids record dereferences, not the preceding shared-reference evaluation. No volatile, atomic, or synchronization semantics are established for that evaluation.

### Initial store and record selection

For a positive first argument, the function evaluates the shared dispatch reference again and writes four zero bytes at the address supplied by that evaluation.

Subsequent indexed dispatch accesses use the reference captured before the eligibility check. The initial store therefore is not established as necessarily targeting slot 0 of the captured record.

With a stable shared reference, both evaluations identify the same record. If the evaluations yield different addresses, the store affects the later-selected address, while notification and principal selection still use the captured record. Depending on address overlap, the store could also affect storage subsequently read through the captured reference.

These are distinctions in the supplied representation. They do not establish how many machine loads occur or guarantee consistent observations under concurrent mutation.

### Entry-notification selection

After the initial store, the function checks slot 10 of the captured record.

If the checked value is zero:

- It does not clear slot 1.
- It retains the caller’s fourth argument for the principal dependency’s fifth argument.
- It does not take the entry-notification call branch.

If the checked value is nonzero:

1. It writes a four-byte zero to slot 1 of the captured record.
2. It changes the value intended for the principal dependency’s fifth argument to zero.
3. It evaluates slot 10 again to obtain the entry-notification call target.
4. It invokes that target.

The successful presence check does not explicitly retain the checked address for the call. The target evaluation is separate and is not followed by another null check. If intervening mutation makes it zero or invalid, the representation does not convert that situation into a skipped notification or defined error.

The principal’s fifth-argument substitution is controlled by the successful entry-presence check. It is not reversed by later changes to slot 10.

### Entry notification

The entry notification receives five arguments:

| Position | Value |
|---|---|
| First | Null |
| Second | Original first argument |
| Third | Original second argument |
| Fourth | Original third argument |
| Fifth | Zero |

Its return value is ignored.

The principal address is obtained after this notification returns. Changes the notification makes to slot 3 of the captured record can therefore affect principal selection. Changes to slot 10 can affect later notification processing.

No dependency is assumed to preserve globals, record contents, storage lifetimes, or ownership.

### Principal operation

The function invokes the principal dependency using slot 3 of the captured record. There is no null-target guard.

Its five arguments are:

| Position | Value |
|---|---|
| First | Original first argument |
| Second | Original second argument |
| Third | Original third argument |
| Fourth | A function-address value evaluated from slot 3 of the captured record |
| Fifth | Original fourth argument if the entry-presence check was zero; otherwise zero |

The call target and fourth argument each come from slot 3 at this stage. With stable contents during call preparation, they identify the same address. The representation does not establish a relative evaluation order or consistency between them under intervening mutation.

The principal result is retained for the eventual return and subsequent processing. A null principal result does not suppress the exit-notification check.

### Exit-notification selection and call

After the principal dependency returns, the function checks slot 10 of the captured record again.

A zero check result skips the exit notification. A nonzero check result causes a separate evaluation of slot 10 to obtain the call target. The checked value is not explicitly retained as the target, and no additional null check is shown.

The selected target receives:

| Position | Value |
|---|---|
| First | Retained principal result, including null |
| Second | Original first argument |
| Third | Original second argument |
| Fourth | Original third argument |
| Fifth | One |

The notification’s return value is ignored.

Entry and exit notification branches are independent. An exit notification may occur without an entry notification, or vice versa. They may invoke different addresses. The principal dependency may enable, disable, or replace the exit notification by changing the captured record.

Changing the shared dispatch reference during a dependency does not retarget later indexed accesses: those continue through the captured reference. Changing the captured record’s contents can affect those accesses.

### Final conditional byte write

After any exit notification returns, the function performs a one-byte write if both conditions hold:

- The retained principal result is non-null.
- The original first argument is strictly greater than 2,048.

It obtains one byte through the separate shared byte-source reference and writes that byte at offset zero of the retained result.

The threshold is supported by the represented 32-bit arithmetic. On the active path, the first argument ranges from 1 through 2,147,483,647. Subtracting 2,048 yields −2,047 through 2,147,481,599, so signed overflow cannot occur. The comparison accepts the nonnegative subtraction cases, while a separate equality exclusion removes exactly 2,048.

Consequently:

| First argument | Final write with a non-null result |
|---|---|
| 1 through 2,047 | No |
| 2,048 | No |
| 2,049 through 2,147,483,647 | Yes |

A null result prevents access to the byte source and prevents the write.

The source byte is obtained after notifications. Dependencies can therefore change its reference or contents before it is read. An exit notification can also modify or invalidate the result storage before the write; no revalidation is performed.

Exactly one byte is written by this operation. It is not a range fill, requested-length copy, or general initialization.

## Side effects

Direct storage changes are:

- A four-byte zero store through a fresh evaluation of the shared dispatch reference on the positive-input path.
- A four-byte zero store to slot 1 of the captured record when the entry-presence check succeeds.
- A one-byte store through the retained principal result when the final condition holds.

The initial store precedes the entry-presence check. The slot-1 store precedes the entry call-target evaluation. The final result-byte store follows the exit notification, if one returns normally.

Cleared words are not restored. Dependencies or aliasing can change them again, so zero values at return are not guaranteed.

The function does not directly allocate, release, or resize an object. Indirect dependencies may do so; their effects and ownership rules are unknown.

Aliasing is not prohibited. A result pointing into dispatch storage can cause the final byte write to alter that storage. A source byte overlapping the destination still supplies the byte to be stored; no multi-byte copy behavior follows.

No synchronization, rollback, retry, exception recovery, or error translation is established. Safe concurrent mutation of dispatch references, dispatch words, or result storage is not established.

## Acceptance examples

These are conditional expectations derived from static evidence, not executed tests. Unless a scenario states otherwise, assume stable relevant storage, callable targets, valid required addresses, and normal dependency returns.

### Nonpositive input

With a first argument of zero or −1, the function returns null. It evaluates the shared dispatch reference initially but neither dereferences a record nor invokes a dependency. No zero store or byte-source read occurs.

### Stable reference without notifications

With first argument 16, an unchanged shared dispatch reference, and slot 10 remaining zero:

- Slot 0 of that record receives zero.
- Slot 1 is not directly changed.
- The principal’s fifth argument equals the caller’s fourth argument.
- Neither notification runs.
- No final byte write occurs.

### Distinct reference evaluations

If the initial capture and later store-address evaluation yield different record addresses, the four-byte zero store targets the later-selected address. Subsequent indexed selection uses the initially captured record.

The captured record’s slot 0 is not guaranteed to be cleared. This is a conditional account of distinct evaluations, not a concurrency guarantee.

### Stable notifications

With slot 10 remaining a stable, nonzero callable address throughout:

- The entry check succeeds.
- Slot 1 is cleared before the entry call.
- Entry receives null first and zero fifth.
- The principal receives zero fifth.
- Exit receives the principal result first and one fifth.

At first argument 2,049 with a valid non-null result, the final byte write follows exit.

### Check and target differ

If a notification-presence check observes a nonzero address but the subsequent target evaluation observes a different callable address, the latter supplies the target. This distinction applies independently to entry and exit.

If the later evaluation instead produces zero or an invalid address, defined skipping or successful completion is not established.

### Threshold and null boundaries

With a valid non-null principal result:

- At 2,048, this function performs no result-byte write.
- At 2,049, it copies the late-read source byte to the result’s first byte.

With a null result at either value, it does not read the byte source. An enabled exit notification still receives null.

### Notification state changes

If entry slot 10 is zero and the principal installs a valid notification address in the captured record, exit can run without entry. The principal still receives the original fourth argument as its fifth argument.

If an entry notification clears slot 10 and it remains zero, exit is skipped. The principal still receives zero fifth.

If a dependency redirects only the shared dispatch reference, later indexed accesses remain on the captured record.

## Evidence

It also establishes separate notification-presence and call-target evaluations, conditional fifth-argument substitution, principal selection through slot 3, independent exit selection, retention of the principal result, and the post-notification one-byte write.

The strict greater-than-2,048 threshold follows from bounded signed 32-bit arithmetic and the explicit equality exclusion.
