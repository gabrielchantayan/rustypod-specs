# F-be6b9a282197

## Purpose

F-be6b9a282197 advances a storage-management state through one of two paths:

- If a reusable-entry head is nonzero, replace it with the first word of the referenced entry and return.
- Otherwise, obtain and link a new storage block if the sequential cursor exactly equals its limit, then advance the cursor by 12 bytes.

The function has no explicit return value. Its observable results are state mutations, two ordered dependency calls when growth occurs, and initialization of a newly obtained descriptor.

**Inferred intent:** the state appears to support reservation of fixed-size, 12-byte entries through a reusable-entry chain and sequential backing regions. The evidence does not establish how another operation obtains the consumed entry’s address, initializes its payload, or eventually releases storage.

## Interface

### Arguments and state layout

The first argument addresses a state record containing at least four consecutive 32-bit words:

| Byte offset | Contract name | Observed role |
|---|---|---|
| 0 | Block head | Address representation of the current block descriptor, or zero |
| 4 | Reusable head | Address representation of an entry whose first word supplies its successor, or zero |
| 8 | Cursor | Signed 32-bit integer-valued sequential address |
| 12 | Limit | Signed 32-bit state word used in an exact-equality comparison with the cursor |

The second argument is a signed 32-bit mode selector. Only its equality with zero affects behavior:

- Zero enables the normal growth-capacity calculation.
- Any nonzero value selects capacity one when growth is needed.

The mode has no effect on reusable-entry consumption or on sequential advancement without growth.

The address-bearing state words use integer representations. Conversion between these words and actual addresses depends on the represented environment; this contract does not establish portability to another pointer width or address model.

### Descriptor layout

A newly obtained descriptor occupies 12 bytes:

| Byte offset | Contract name | Observed role |
|---|---|---|
| 0 | Previous block | Block head read after both dependency calls |
| 4 | Capacity | Selected unsigned 32-bit capacity assigned into a signed 32-bit descriptor word |
| 8 | Storage base | Signed 32-bit value returned by the second dependency call |

When an existing capacity is inspected, its word at offset 4 is read as unsigned 32-bit.

For selected capacities above the signed 32-bit maximum, assignment into the descriptor’s signed capacity word introduces an out-of-range unsigned-to-signed conversion. The supplied body does not establish the implementation’s conversion behavior. The subsequent size and limit calculations use the already selected unsigned capacity, not a reread of that signed descriptor word.

### Outputs and validity requirements

There is no explicit result value or error-status output.

Normal execution requires valid accesses for every path actually taken:

- The state fields read or written must be accessible.
- A nonzero reusable head must identify a readable first word.
- A descriptor used for capacity selection must have a readable capacity word.
- The first dependency result must support the three descriptor writes.
- The integer-to-address conversions and descriptor-field address calculations must be valid in the represented environment.
- The final signed cursor increment must be representable if defined signed arithmetic is required.

The function does not validate these conditions.

Nonoverlap is not checked. State, entries, descriptors, and returned regions must not be assumed independent unless that is an explicit surrounding precondition. The ordinary final-state descriptions below assume nonoverlapping objects and no dependency-induced state mutation; exceptions are identified separately.

## Behavior

### 1. Reusable-entry consumption takes priority

The function first inspects the reusable head.

If it is nonzero:

1. Read the first 32-bit word at the represented address.
2. Write that word into the state’s reusable-head field.
3. Return immediately.

On this path:

- Cursor and limit are not examined for exhaustion.
- No dependency call occurs.
- The referenced entry is not explicitly modified.
- No address is returned to the caller.
- Block head, cursor, and limit receive no explicit writes.

Thus, a nonzero reusable head suppresses sequential advancement even when cursor and limit are equal.

### 2. Unequal cursor and limit cause advancement without growth

If the reusable head is zero, the function compares cursor and limit for exact equality. The source establishes the comparison, not a meaningful ordering between the two operand reads.

If they differ, the function makes no dependency call and performs no block initialization. It reads the cursor, adds 12 using signed 32-bit integer addition, writes the result back, and returns.

There is no ordering check, remaining-space check, or stride-alignment check. A cursor above the limit still advances. A cursor fewer than 12 bytes below the limit also advances.

If adding 12 exceeds the signed 32-bit range, the supplied evidence does not establish a defined wrapped result. This is a signed-addition issue, distinct from the unsigned arithmetic used to construct a new limit.

### 3. Exact exhaustion selects an unsigned capacity

Growth occurs only after observing both:

- A zero reusable head.
- Equal cursor and limit.

For nonzero mode, selected capacity is one. The existing descriptor’s capacity is not inspected.

For zero mode:

- A zero block head selects capacity 32.
- A nonzero block head causes its capacity word to be read as unsigned 32-bit.

For an existing unsigned capacity \(c\), the two candidates are:

- \(c + 32\), reduced modulo \(2^{32}\).
- \(c + \lfloor c/2\rfloor + \lfloor c/8\rfloor\), reduced modulo \(2^{32}\).

Both shifts use the original unsigned capacity. The larger candidate under unsigned comparison becomes the selected capacity. Equality chooses the shift-based candidate but does not change the numerical result.

There is no subsequent validation or minimum-capacity correction. Near the unsigned boundary, this calculation is not equivalent to an unbounded growth rule.

### 4. Growth makes two ordered dependency calls

After capacity selection, F-871e64ddc6de is called twice:

| Order | First argument expression | Second argument | Result use |
|---|---|---|---|
| First | 12 | 0 | Address of the new descriptor |
| Second | Selected capacity multiplied by 12, modulo \(2^{32}\) | 0 | Storage-base value |

The size expression for the second call is unsigned 32-bit. Its multiplication wraps modulo \(2^{32}\). The dependency’s formal parameter types and any further argument conversion are not supplied.

Both calls occur before explicit descriptor initialization. Neither result is checked before use.

The selected capacity remains the previously computed value across the calls. In contrast, the block head used for linking is read afterward.

### 5. Descriptor initialization and state publication are ordered

If both calls return normally, explicit operations proceed in this order:

1. Write the second result into the new descriptor’s storage-base word.
2. Read the state’s current block head and write it into the descriptor’s previous-block word.
3. Assign the selected unsigned capacity into the descriptor’s signed capacity word.
4. Convert the descriptor address to the state’s integer address representation and write it into block head.
5. Read the descriptor’s storage-base word back.
6. Write that signed value into cursor.
7. Calculate the new limit using the unsigned arithmetic described below, then assign it into the signed limit word.
8. Read the current cursor, add 12 using signed integer addition, and write it back.

The block head captured for the new descriptor’s link is therefore the value present after both dependency calls, not necessarily the value used during capacity selection.

The descriptor is linked into state after its three fields have been written, but before cursor and limit are updated. No atomic-publication or synchronization guarantee is established.

Aliasing can make the ordered writes and reread significant. For example, the storage base used for cursor initialization is explicitly reread after the block-head write. Without a nonoverlap guarantee, it must not automatically be replaced in the behavioral model by the original second-call result.

### 6. Limit construction and cursor advancement have different arithmetic

Let the unsigned backing-size expression be the selected capacity multiplied by 12 modulo \(2^{32}\).

For **limit construction**, the storage-base value is signed 32-bit, but the backing-size expression is unsigned 32-bit. The arithmetic conversions convert the storage-base operand to unsigned 32-bit before addition.

Consequently:

- Conversion of a negative storage-base value to unsigned is modulo \(2^{32}\).
- The limit addition itself is unsigned 32-bit.
- That addition wraps modulo \(2^{32}\).
- There is no unresolved signed-overflow question for this addition.

The resulting unsigned value is then assigned into the signed 32-bit limit word. That assignment is a separate conversion:

- Values through 2,147,483,647 are representable without change.
- For larger values, the supplied body does not establish the implementation’s out-of-range conversion semantics.
- A negative signed representation must not be promised merely because it is common on particular targets.

For **final cursor advancement**, both the cursor read and the value 12 participate in signed integer addition. Overflow here remains an unresolved target/source-semantics boundary; unsigned limit arithmetic does not make the cursor increment wrap.

Under ordinary nonoverlapping, nonmutating conditions, with representable values and conversions, growth leaves:

- Block head pointing to the new descriptor.
- Cursor equal to storage base plus 12.
- Limit equal to the signed assignment of the modulo-\(2^{32}\) unsigned base-plus-backing-size result.

For capacity one, cursor and limit are equal when the relevant additions and conversions produce their ordinary representable results. That equality is not an unconditional guarantee across signed-overflow cases.

## Side effects

### Explicit memory effects

On the reusable-entry path, only reusable head is explicitly written.

On the sequential path without growth, only cursor is explicitly written.

On the growth path, the function explicitly writes:

- All three new descriptor words.
- State block head.
- State cursor, first with the base and then with the incremented value.
- State limit.

There is no explicit reusable-head write on the growth path.

The function contains no explicit operation to:

- Clear the consumed reusable entry’s link.
- Initialize an entry payload or the backing region.
- Release a reusable entry, old descriptor, or old backing region.
- Validate capacity, size overflow, cursor ordering, returned addresses, or allocation success.
- Return an error status.
- Roll back partial state changes.

### Ownership and failure

**Established:** returned addresses are retained in the descriptor and state, and the previous block head is retained through the descriptor link.

**Inferred intent:** descriptors likely preserve access to backing regions for later management.

**Unknown:** ownership transfer, initialization, alignment, release responsibility, and lifetime guarantees.

The function does not establish a recoverable failure protocol. If a dependency returns an unusable address, the subsequent accesses are not guarded. If the second call does not return normally, this body provides no explicit cleanup of the first result. If execution stops during descriptor or state writes, no rollback is shown.

Dependency effects must not be assumed limited to returned storage. Indirect state changes may affect the later head read, descriptor accesses, and final state.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Except where specified, assume accessible nonoverlapping objects, successful dependency returns, no dependency-induced mutation, valid address conversions, and representable signed additions.

### Reuse overrides exhaustion

Given a nonzero reusable head whose first word is zero, and equal cursor and limit:

- Reusable head becomes zero.
- No dependency call occurs.
- Cursor, limit, and block head remain unchanged.
- The consumed entry receives no explicit write.
- Mode does not affect the outcome.

### Unequal addresses advance even outside the apparent range

Given reusable head zero, cursor 4096, and limit 4120:

- Cursor becomes 4108.
- Limit and block head remain unchanged.
- No dependency call occurs.

With cursor 4132 and the same limit, cursor becomes 4144. With cursor 4116, it becomes 4128 despite crossing the limit.

### Initial normal growth

Given reusable head zero, equal cursor and limit, block head zero, and mode zero:

- Selected capacity is 32.
- Dependency first-argument expressions are 12 and 384, in that order.
- The descriptor links to zero.
- Its capacity word receives 32.
- With storage base 4096, cursor becomes 4108 and limit becomes 4480.

### Nonzero mode

Given reusable head zero, equal cursor and limit, and any nonzero mode:

- Capacity is one without inspecting the existing capacity.
- Both request-size expressions are 12.
- The new descriptor links to the block head read after both calls.
- With storage base 4096, final cursor and limit are both 4108.

### Limit conversion is separate from addition

For capacity 32 and storage base 2,147,483,632:

- Backing size is 384.
- The unsigned limit addition produces 2,147,484,016 without signed overflow.
- Assignment of that value into the signed limit word is out of range; its result is not established here.
- The final cursor addition is independently representable and yields 2,147,483,644, provided execution reaches it normally.

For the arithmetic subcase of signed storage base −16 and capacity 32:

- Conversion of the base to unsigned yields 4,294,967,280.
- Adding 384 wraps to 368.
- Assignment of 368 into limit is representable.
- The signed cursor increment yields −4.

These arithmetic observations do not establish that either base denotes a valid returned storage region.

### Dependency changes the head

Suppose capacity selection reads descriptor A, but a dependency call changes block head to descriptor B.

After normal returns and absent interfering overlap:

- Selected capacity remains based on A.
- The new descriptor’s previous-block field receives B.
