# F-12ca48c1a4b0

## Purpose

F-12ca48c1a4b0 populates a caller-provided 20-byte record, reads two 16-bit memory values, and performs further 32-bit stores selected by whether its second explicit input is zero. On normal completion, it returns a 64-bit value containing the record address and the first explicit input.

The zero-input case is **not a null-safe alternative**. Both memory reads precede branch selection, so a zero second input still requires a 16-bit read at address `0x00000004`.

The behavior also depends on an incoming register value absent from the explicit argument list. One record field receives a stack-relative address whose target and lifetime are unresolved. These dependencies prevent treating the visible argument list as a complete, independently established calling interface.

This contract describes static evidence, not demonstrated execution. It does not establish that the function is callable under an ordinary application ABI or that any referenced address is accessible.

## Interface

### Explicit inputs

| Input | Represented width | Behavioral role |
|---|---:|---|
| Payload | 32 bits | Becomes the low 32 bits of the return value; otherwise uninterpreted. |
| Address selector | 32 bits | Supplies the base for one memory read, is copied into the record, and selects the zero or nonzero behavior. |
| Record address | 32-bit address representation | Identifies the destination record and becomes the high 32 bits of the return value. |
| Adjustment input | 32-bit signed integer | Supplies the value stored at record offset 8 after subtraction of 31. |

The address selector has both address and scalar roles. Branch selection depends on this input itself, not on a subsequent read of its stored copy.

The payload is not dereferenced. The record address is used directly; no destination allocation or capacity discovery is shown.

### Implicit input

A hidden incoming register value contributes to address formation. The function derives an address base by multiplying that value by `0x10000000`.

The representation uses 32-bit signed arithmetic for this calculation. For values whose product is representable, the resulting numerical base is established. Overflow behavior is **documented_only**: the supplied evidence does not justify imposing either universal modular wrapping or a particular language-level overflow consequence.

How the caller supplies this hidden value, and which values are valid, are also unresolved.

### Record layout

The record contains five consecutive 32-bit fields:

| Byte offset | Width | Value supplied during initialization |
|---:|---:|---|
| 0 | 32 bits | Zero |
| 4 | 32 bits | The record address |
| 8 | 32 bits | Adjustment input minus 31 |
| 12 | 32 bits | A stack-relative address |
| 16 | 32 bits | The address selector |

Initialization therefore requires a 20-byte destination region. These are the initialization values, not an unconditional guarantee about the final record contents: later stores can overwrite them if destinations alias the record.

The stack-relative address is associated with offset `0x2F0` in the supplied stack model. The evidence does not identify the stack origin, referenced object, permitted uses, or validity interval. Storing this address does not copy the referenced storage or extend its lifetime.

### Result

On normal completion, the returned 64-bit bit pattern contains:

- The represented record address in bits 63–32.
- The payload in bits 31–0.

For example, record address `0x00004000` and payload `0x11223344` produce `0x0000400011223344`.

The result is not established as a success indicator, allocation result, or error code. No alternate return value for failed accesses is shown.

All reached memory accesses must be supported by the execution environment. This includes:

The zero-selector path additionally requires readable low memory at address 4 and writable low memory at address `0x30`. No validation establishes these conditions.

## Behavior

### Record publication precedes memory sampling

The record is initialized before either of the two explicit memory reads. Its fields are written separately, in ascending byte-offset order: 0, 4, 8, 12, then 16.

This is not an established atomic publication operation. An observer, or a failure during initialization, may encounter a partially updated record. There is no shown rollback.

The adjustment field uses 32-bit signed subtraction in the supplied representation. A value of 31 produces zero; a value of 30 produces negative one, represented in the 32-bit field. Subtraction is mathematically representable for adjustment inputs from `−2147483617` through `2147483647`. Behavior below that range is not resolved by the supplied evidence.

After initialization, the hidden input determines the derived base. The function then obtains two unsigned 16-bit samples:

- First, from the address selector plus 4.
- Second, from the derived base plus `0x28`.

Both samples are acquired before the address selector is tested for zero. Consequently, neither branch can avoid either read. In particular, the first sample comes from address 4 when the selector is zero.

The samples are retained for subsequent use; no explicit reread is shown after later stores. Whenever a sample supplies a 32-bit stored value, it is zero-extended. A sample of `0xFFFF` therefore contributes `0x0000FFFF`, not `0xFFFFFFFF`.

### Nonzero-selector outcome

With a nonzero address selector, the only post-initialization store is a 32-bit write at the derived base plus `0x30`. Its value is the zero-extended sample obtained from the derived base plus `0x28`.

The other sample has no subsequent value-bearing use on this path. Its read nevertheless remains part of the behavior: it can require accessible memory, fail, or have device-specific effects.

None of the five named global destinations is written on this path. Once the final store completes, the function returns the composite result described above.

### Zero-selector outcome

With a zero address selector, five global destinations and two address-derived destinations receive 32-bit stores.

This contract calls the global destinations **G1–G5**, assigned by their first-write order. The labels identify storage destinations only. They do not assert separate allocations, nonoverlap, or any external semantic role.

The zero-selector effects have the following values:

| Destination | 32-bit stored value |
|---|---|
| G1 | Derived base minus 5 |
| Derived base plus `0x3B` | Zero-extended sample from derived base plus `0x28` |
| G2 | `0xFFFFFB00` |
| G3 | Zero |
| G4 | Zero-extended sample from address 4 |
| G5 | Derived base |
| Absolute address `0x00000030` | `0x0000008D` |

Order is significant. G1 is written before the store at base plus `0x3B`; that store precedes G2, followed by G3, G4, and G5. The absolute-address store occurs last.

The offset `0x3B` is exact. No alignment adjustment is shown. For an aligned derived base, this is an unaligned 32-bit destination; whether the environment permits that access remains unresolved.

The final destination is absolute address `0x30`, **not** the derived base plus `0x30`. Its value is the constant `0x8D`, independent of both samples. The earlier sample from the derived base is still required because it supplies the store at base plus `0x3B`.

The return composition is unchanged by selecting this path.

### Aliasing and intermediate observations

No disjointness guarantee is established among the record, sampled addresses, global destinations, and subsequent store destinations.

The contract therefore concerns ordered accesses, not merely independent final field values:

- Record initialization can change the bytes subsequently sampled.
- Post-initialization stores can overwrite record fields.
- A global store can affect another global view or another accessed location.
- If destinations overlap, later stores determine the affected bytes according to the actual address layout and byte order.

For example, when the address selector equals the record address, the first sample reads the beginning of the already-written self-address field at offset 4. The observed 16-bit value depends on byte order. It is not a sample of the record’s pre-call contents.

Similarly, if a later store overwrites a sampled location, the function still uses the sample already obtained. The represented sequence contains no reload to reflect that overwrite.

The supplied global-storage warning specifically permits overlapping views of named storage. Treating G1–G5 as independent variables would therefore strengthen the evidence improperly.

### Failure and incomplete execution

If an access cannot complete, earlier completed writes are not undone by any operation in the supplied body. Whether the environment raises an exception, terminates execution, emulates the access, or permits resumption is **documented_only**.

If the read at address 4 fails on the zero-selector path, the represented sequence has already initialized the record but has not yet performed the derived-base read or any zero-selector store. This describes access order, not a guaranteed platform fault mechanism.

## Acceptance examples

### Nonzero selector with high-bit samples

Given:

- Payload `0x11223344`.
- Address selector `0x00002000`.
- Record address `0x00004000`.
- Adjustment input `0x60`.
- Hidden input 1, producing derived base `0x10000000`.
- A 16-bit sample of `0xABCD` at `0x00002004`.
- A 16-bit sample of `0xFEDC` at `0x10000028`.

The record receives zero, `0x00004000`, `0x00000041`, the unresolved stack-relative address, and `0x00002000`, in field order. Both reads follow initialization.

The subsequent store writes `0x0000FEDC` at `0x10000030`. G1–G5 receive no stores. The normal return is `0x0000400011223344`.

The `0xABCD` sample must still be read even though this path does not use it in a store.

### Zero selector in an environment supporting low addresses

Given hidden input 1, a zero selector, sample `0xABCD` at address 4, and sample `0x1234` at `0x10000028`, the post-initialization effects are:

- G1 receives `0x0FFFFFFB` before `0x1000003B` receives `0x00001234`.
- G2 then receives `0xFFFFFB00`, followed by zero at G3.
- G4 receives `0x0000ABCD`, followed by `0x10000000` at G5.
- The final store writes `0x0000008D` at absolute address `0x00000030`.

This criterion requires support for the potentially unaligned store at `0x1000003B`. The zero selector supplies no exemption from low-address accessibility requirements.

### Failure at the first sample

If record initialization completes but address 4 cannot supply the required 16-bit read, a zero selector does not bypass that access.

The static ordering places the failing access before the derived-base read and all zero-selector stores. No normal return or recovery behavior is established. No shown operation restores the record’s previous contents.

### Unsigned widening on either selected path

If the derived-base sample is `0xFFFF`, the corresponding 32-bit value is `0x0000FFFF`:

- At base plus `0x30` for a nonzero selector.
- At base plus `0x3B` for a zero selector.

If the address-4 sample is `0x8000`, G4 receives `0x00008000` on the zero-selector path.

### Record aliasing with the first sample

Suppose the nonzero selector equals the record address `0x00004000`, and the environment is little-endian. The self-address field is written before sampling, so the first sample is `0x4000`, regardless of that field’s prior contents.

Under big-endian byte order, the same first sample would be `0x0000`. Neither result changes the nonzero path’s final stored value, which comes from the other sample.
