# F-7d4d9cf29058

## Purpose

F-7d4d9cf29058 performs mode-dependent bookkeeping on an addressed object.

- Mode exactly 1 sets an object byte, invokes an embedded-state dependency, and selects either scheduler-record processing or shared registration.
- Every other mode invokes a lifecycle-related dependency, then selects either an attached-object indirect call or shared-registration removal.

These operations are established by the supplied static representation. “Scheduler,” “registration,” “membership,” and “cleanup” describe inferred roles, not independently established application semantics.

There is no represented return value. Observable results consist of memory accesses, writes, dependency calls, indirect calls, and a cleanup path containing a dependency marked nonreturning.

## Interface

### Arguments and results

| Input | Width | Interpretation |
|---|---:|---|
| Object address | 32 bits | Base address for fixed-offset accesses. |
| Mode | 32 bits | Compared with exactly 1; every other value selects the alternate branch. |

The object and other reached addresses must support the accesses described below. The alternate branch contains a late null-object check, but dereferences the object before reaching it; that check does not establish null-input safety.

No explicit status, error object, allocation-failure result, or rollback mechanism is exposed.

### Directly used layouts

All offsets are in bytes. Pointer values and words are 32 bits unless identified otherwise.

| Object offset | Access |
|---|---|
| 0x148 | Word controlling access to shared-registration processing. |
| 0x14C | Word selecting scheduler processing within mode 1. |
| 0x150 | Byte written with 1 in mode 1. |
| 0x154 | Address passed to F-ca73cb512206; extent unknown. |
| 0x1A8 | Attached-object pointer, conditionally called through and cleared. |
| 0x1AC | Pointer passed to lifecycle dependencies and used as a scheduler-record address. |

A manager has a dispatch-table pointer at offset 0, a collection pointer at offset 4, and an auxiliary pointer at offset 8. Manager dispatch slots 8 and 0xC are used as entry and exit operations; synchronization semantics are unknown.

A scheduler record has a next pointer at offset 0, interval-like word at 4, deadline-like word at 8, global-value copies at 0x18 and 0x20, and a membership-like word at 0x1C.

The auxiliary structure has a header pointer at offset 0x10 and comparator storage addressed at offset 0x19. Traversed nodes expose links at offsets 8 and 0xC, key-related storage at 0x10, and a count at 0x14. The header’s offset-4 word supplies the traversal’s initial link.

### Global identities

The following descriptive labels identify distinct global storage locations, without assigning ownership:

- **Control-holder global:** supplies the argument to F-338d16f9ce72 and is read again for the final pointer-holder dereference.
- **List-holder global:** contains the address of the scheduler list’s head-storage word.
- **Record-copy globals:** separately supply scheduler offsets 0x18 and 0x20.
- **Notification global:** supplies the argument to F-5bcae2eff9a7.
- **Indirect-target global:** supplies the final conditional indirect-call target.

The control-holder and list-holder globals are distinct. Reloading either global is different from continuing to use a previously captured holder address.

## Behavior

### Entry and mode selection

Every invocation first calls F-9aa3a9791e88 without explicit arguments. All subsequent accesses occur after that dependency; its effects are unknown.

For mode 1, the function writes byte 1 at object offset 0x150, calls F-ca73cb512206 with the address at offset 0x154, and then reads offset 0x14C. No visible early return reverses the byte write.

### Mode 1: scheduler processing

When offset 0x14C is nonzero:

1. The pointer at object offset 0x1AC is passed to F-6904f7699031.
2. That object field is read again, and the resulting record address is retained.
3. F-936a8728139d is called without an explicit argument in this branch.
4. The offset-0x20 record-copy global is read and written to the retained record.
5. The record’s offset-0x1C word is tested. A nonzero value returns immediately.

The first lifecycle dependency can therefore replace the record pointer used subsequently. The second is crossed using the retained address; its validity afterward is a precondition, not an established dependency guarantee.

If the membership-like word is zero, the control-holder global is read and its value passed to F-338d16f9ce72. F-add44d4e9aaa then receives the retained record. The interval-like word at record offset 4 is read and retained.

For a nonzero interval, a current-value provider is called. Its opaque function ID is unavailable. After it returns, the following order is established:

- Capture the holder address from the list-holder global.
- Write the provider result plus the retained interval multiplied by 1000 to record offset 8.
- Read the offset-0x18 record-copy global and copy it into the record.
- Read the initial list head through the captured holder address.

Thus, changes to the interval during the provider call do not replace the captured interval. Changes to the list-holder global during that call do affect which holder is captured. Later global replacements do not redirect this invocation’s retained holder.

Traversal starts with no predecessor. For each nonnull current node, F-0d70d6f9010c receives the current node’s offset-8 address and the new record’s offset-8 address, in that order. A zero result advances traversal: the current node’s next pointer is read after the comparison, and the current node becomes the predecessor. A nonzero result stops at that node. A null link stops without another comparison.

Insertion writes occur in this order:

- With no predecessor, write the record address through the retained head holder; otherwise write it to the predecessor’s next field.
- Write 1 at record offset 0x1C.
- Write the stopping node, possibly null, at record offset 0.

Comparator calls may replace the list-holder global without changing the retained head-insertion destination. They may also alter node links before subsequent link reads. Comparator ordering and equality semantics are unknown.

The arithmetic uses represented 32-bit operands and a 32-bit destination. The interval is represented as signed. No widening, checked overflow, saturation, or normalization is visible; exact overflow semantics remain documented_only.

A zero interval skips the provider, holder capture, deadline and offset-0x18 writes, traversal, and insertion. Whether the interval was zero or nonzero, execution then:

- Reads the notification global and passes it to F-5bcae2eff9a7.
- Reloads the **same control-holder global** previously used for F-338d16f9ce72.
- Dereferences that newly obtained holder to obtain a pointer.
- If the pointer is nonnull, reads its first word.
- If both pointer and word are nonzero, invokes the indirect-target global without explicit arguments.

The control holder itself is dereferenced without a visible null check. The final pointer and first-word checks do not validate that holder.

### Mode 1: shared registration

When offset 0x14C is zero, offset 0x148 is read. Zero returns immediately. Otherwise, F-283eda65a14c is called, and its result and constant 5 are passed to F-682adfd5a561 to obtain a manager.

F-c7ba4c901230 receives the manager and object address. A nonzero result returns. Otherwise, an ordering token is initialized to 0x7FFFFFFF, an unsigned 32-bit threshold is captured from F-f4c5ae40135d, and manager dispatch slot 8 is invoked with the manager.

The manager’s collection field is then read. If null, initialization proceeds:

- Request 0x10 bytes through F-8157a180d901; its direct result is not visibly retained.
- Call F-e194f3fbdfaa and store its result in the manager’s collection field.
- Request 0x1C bytes through F-8157a180d901.
- Zero the returned allocation’s word at 0, words at 0x10 and 0x14, bytes at 0x18 and 0x19, then words at 0xC, 8, and 4, in that order.
- Pass the allocation to F-2ca62cf8d9c9 and store its result at allocation offset 0x10.
- Set the returned header’s offset-4 word to zero and its offset-8 and offset-0xC words to the header address.
- Store the allocation in manager offset 8.
- Call F-39af4974f3d2 with the manager.

After optional initialization, including F-39af4974f3d2 when reached, the manager’s auxiliary pointer is captured. F-f5d5922924e8 receives that retained auxiliary pointer and a stack-resident key address. The returned count-storage word is incremented and written back. A second call receives the **same retained auxiliary pointer and key address**, and its returned word is read as unsigned.

A replacement of the manager’s auxiliary field during the first lookup does not redirect the second lookup. The registration key’s contents are not recoverable from the supplied representation.

If the second count is at least 2, iteration and insertion are skipped. Otherwise:

- F-538044b67754 initializes an iterator using the collection pointer read from the manager **at this point**, plus 0xFFFFFFFE.
- F-6e4651b532dc repeatedly receives the iterator address and output storage.
- Zero ends iteration. Otherwise, the produced element’s unsigned word at offset 0x10 is compared with the captured threshold.
- Values less than or equal to the threshold continue iteration. The first strictly greater value causes F-999d5c439412 to supply the ordering token.
- F-944b595e25e9 receives the iterator address.
- After that call, the collection field is read from the manager to obtain the insertion dispatch target and receiver. Collection slot 0x20 receives that collection, the token, and the registration-key address.

Iteration exhaustion leaves the token at 0x7FFFFFFF. The insertion collection need not be the iterator’s collection: F-944b595e25e9 may replace the manager field.

Finally, manager dispatch slot 0xC is invoked with the retained manager.

### Every other mode: attachment handling

The pointer at object offset 0x1AC is passed to F-936a8728139d, with an explicit argument here.

If object offset 0x1A8 is nonnull, the function invokes the target selected through that object’s dispatch-table slot 4, without an explicit receiver argument in the representation. It then clears the parent’s offset-0x1A8 field and returns.

The field remains uncleared during the indirect call. Neither release semantics nor ownership transfer is established. No direct write clears offset 0x150.

### Every other mode: shared removal

If the attachment is null, a zero at offset 0x148 returns. Otherwise, manager acquisition uses F-283eda65a14c and F-682adfd5a561 with constant 5.

A null object address or null manager collection returns at this late check. The removal key is two 32-bit words: object address followed by zero. Manager slot 8 receives the manager, and its result is retained.

If the collection is nonnull after entry, the auxiliary pointer is captured. Traversal reads the header’s offset-4 link, then reads the header pointer again to initialize a candidate.

At each nonnull node, F-a073c1bc0f3f receives:

- Captured auxiliary address plus 0x19.
- Current node address plus 0x10.
- Removal-key address.

On a zero result, the node’s offset-8 link is loaded; **both the next traversal node and candidate become that loaded link value**, not the node just compared. On a nonzero result, traversal follows offset 0xC without replacing the candidate.

After traversal:

1. The auxiliary header is read again into addressable temporary storage.
2. F-3ee46ff4f2dc receives the candidate’s address and that captured header’s address.
3. If its result is zero, F-f8ae48a15441 receives the candidate value as it exists after the helper. F-a073c1bc0f3f then receives comparator storage, the removal-key address, and the latter helper’s result. This reverses the traversal’s key order.
4. Only a zero result from this second comparison selects the candidate’s current value. A nonzero result, or a nonzero first helper result, selects a newly read auxiliary header instead.
5. The selected value is copied into separate addressable storage. The header is freshly read again into another temporary.
6. F-3ee46ff4f2dc receives the addresses of that selected value and fresh header.

These address-passed temporaries may be modified by the helpers. Neither helper call is established as a pure equality test. The subsequent count address uses the selected value **after** the second helper.

A nonzero second-helper result skips count access and cleanup eligibility, proceeding to manager exit. A zero result causes a count read at selected offset 0x14. A zero count also proceeds directly to exit.

Otherwise the count is read again, decremented, and written back. A nonzero result proceeds directly to exit. If it becomes zero, the collection currently obtained through the manager supplies dispatch slot 0x28 and the receiver; the removal key is passed. Its return value is retained, and the selected count is written to zero again afterward. The selected storage must remain valid across that call.

### Removal cleanup

Cleanup eligibility is reached after removal reaches zero, or when the collection was null immediately after manager entry. The retained result is respectively the collection-removal result or manager-entry result.

Cleanup requires all of:

- Result differs from -1.
- Manager’s currently read collection pointer is nonnull.
- That collection’s word at offset 4 is zero.

Then F-c719314a16bb receives the manager. The collection is checked again afterward; if nonnull, its dispatch slot 4 is invoked without an explicit receiver argument. The manager’s collection field is then cleared.

If the auxiliary field is nonzero, F-c8eefdf96f4b and then F-feee9156a257 are called without explicit arguments. The latter is marked nonreturning; the subsequent auxiliary clear and manager exit are not reached on that represented path.

Otherwise, the auxiliary field is cleared. Manager slot 0xC is invoked on ordinary exit paths.

## Side effects

Established direct effects include the mode-1 byte write, attachment clearing, scheduler-record changes, list-link writes, allocation initialization, manager-field updates, and count increments or decrements.

Writes are not transactional. The active byte remains set across later early returns. Attachment clearing follows its indirect call. Scheduler publication precedes the membership and next-link writes. Removal writes the zero count both before and after the collection call.

No dependency is assumed to preserve globals, manager fields, retained storage, or memory ownership. Accessible retained addresses across calls are required where later accesses use them. Allocation failure is not visibly checked before initialization writes.

Count operations use 32-bit storage without visible overflow checks. Exact signed-overflow interpretation, including registration increment, remains documented_only.

## Acceptance examples

These are conditional static examples, not executed tests. They assume valid storage and normal return except where stated.

1. **Mode distinction:** Mode 2 takes the alternate branch and performs no direct active-byte write.

2. **Early scheduler return:** A nonzero membership word still permits the offset-0x20 copy, then prevents subsequent scheduler calls.

3. **Holder identity:** If F-5bcae2eff9a7 replaces the control-holder global, the final dereference uses its replacement, not the value earlier passed to F-338d16f9ce72.

4. **Retained list destination:** If a comparator replaces the list-holder global and the insertion has no predecessor, publication still writes through the holder captured before the deadline write.

5. **Zero interval:** No deadline or list insertion occurs, but notification and the final conditional-call check still occur.

6. **Auxiliary replacement:** If the first count lookup changes manager offset 8, the second lookup still receives the previously captured auxiliary address.

7. **Collection replacement:** If iterator finalization replaces manager offset 4, insertion uses the replacement collection’s dispatch target and receiver.

8. **Threshold boundary:** Equality with the unsigned threshold continues iteration; a strictly greater value stops it.

9. **Candidate mutation:** If the first address-based helper returns zero after changing the candidate, F-f8ae48a15441 receives that changed candidate.

10. **Count-check selection:** If the second address-based helper changes the selected address and returns zero, count access uses the changed address. A nonzero result skips count access entirely.

11. **Removal transition:** Count 3 becomes 2 and skips cleanup eligibility. Count 1 becomes zero, invokes removal, and is written zero again. A removal result of -1 prevents cleanup.

12. **Nonreturning cleanup:** Reaching F-feee9156a257 does not reach the later auxiliary clear or manager exit.
