# F-4d36537ce2ca

## Purpose

F-4d36537ce2ca conditionally dispatches callbacks from a collection obtained through a dependency. It copies the collection’s 32-bit entry values into temporary storage before dispatching, then processes that copy in ascending index order.

The copied values are references to callback descriptors, not copies of the descriptors themselves. Consequently, the function stabilizes the sequence of entry values it initially collects, but does not establish immutable callback targets or callback data.

The function returns a 32-bit success indicator. Success means the normal processing path completed, including cases where the collection count is zero or negative or every entry is skipped. It does not report how many callbacks ran or whether they succeeded.

## Interface

The interface has four arguments:

| Argument | Established role |
|---|---|
| First argument | A 32-bit value not read or forwarded by this function. |
| Second argument | A 32-bit value forwarded as the first argument of each invoked callback. |
| Third argument | An address of a 32-bit output slot. Also passed directly to notification, per-index preparation, and callback operations. |
| Fourth argument | A 32-bit value forwarded as the last argument of both notification operations. |

The return value is a 32-bit word containing either zero or one on the explicit return paths.

The third argument must identify writable storage when initial lookup succeeds: the function writes zero to that storage without checking the address. Dependencies receiving this address may impose additional requirements not established here.

The following memory layouts are visible:

- The nonzero object returned by initial lookup contains a 32-bit collection reference at byte offset 4.
- Temporary storage holds consecutive 32-bit entry values, with a stride of 4 bytes.
- Each nonzero entry used as a callback descriptor has at least three 32-bit fields:
  - Offset 0: first descriptor payload.
  - Offset 4: second descriptor payload.
  - Offset 8: callback address.

These are access layouts, not evidence of complete object sizes, alignment guarantees, or ownership rules. The source uses 32-bit address-bearing values; this contract does not imply native 64-bit pointer compatibility.

## Behavior

### 1. Initial lookup and early failure

The function first invokes F-2abff646f58d with no arguments.

If its result is zero:

- The function returns zero.
- It does not directly write the output slot.
- It performs neither notification, collection traversal, allocation, callback dispatch, nor release.

This does not establish that F-2abff646f58d has no side effects. In particular, the output’s value after this path is not guaranteed unchanged by all possible indirect effects; only the absence of a direct write by this function is established.

If initial lookup returns a nonzero object reference, the function proceeds without validating that reference.

### 2. Output initialization and first notification

The function writes a 32-bit zero to the output slot.

It then calls F-890414d1fd99 with six arguments, in this order:

1. 5.
2. 2.
3. 0.
4. 0.
5. The output-slot address.
6. The fourth argument.

The notification’s return value is unused. The function does not restore the output slot to zero afterward. Changes made by this dependency can therefore remain visible during subsequent processing.

The initial object’s collection field is read only after this notification returns. A notification that changes that field can affect which collection is counted.

### 3. Count acquisition and temporary storage

The function reads the 32-bit field at offset 4 of the initial object and passes that value to F-10b760faca36.

The returned count is interpreted as a signed 32-bit integer for subsequent comparisons and loop bounds. The function obtains this count once; it does not refresh it later.

If the count is positive, the function requests temporary storage from F-43da6b23bd44 with:

- A byte-size argument expressed as the count multiplied by 4.
- A second argument of zero.
- A third argument of zero.

A zero result means allocation failure for this function. Any nonzero result is treated as a usable storage address without further validation.

The requested size uses 32-bit count arithmetic. There is no visible check that the multiplication is representable or that the returned region is large enough for all requested entries. For ordinary positive counts whose product with 4 is representable as a signed 32-bit integer, the intended request is exactly four bytes per entry. Behavior for overflowing size arithmetic is not established sufficiently to promise safe truncation, rejection, or allocation.

If the count is zero or negative, the allocation dependency is not called.

### 4. Copying collection entries

When the count is positive and allocation returns nonzero storage, the function visits every index from zero through count minus one.

At each index, it:

- Reads the collection reference again from offset 4 of the original lookup object.
- Calls F-6bbddce1b930 with that collection reference and the current index.
- Stores the returned 32-bit value in the corresponding temporary slot.

Each retrieval completes before its value is written, and each slot write completes before the next iteration.

The repeated collection-field reads are significant. The function does not retain one collection reference for all retrievals. If a dependency changes the field during copying, later entries may be retrieved from a different collection while still using the original count.

No callback dispatch occurs until all entries have been copied. This creates a snapshot of entry values, not an atomic or deep snapshot of the underlying collection and descriptors.

If allocation fails, no entries are retrieved.

### 5. Second notification

After count acquisition and any attempted copying, the function calls F-890414d1fd99 again, with:

1. 6.
2. 2.
3. 0.
4. 0.
5. The output-slot address.
6. The fourth argument.

The return value is unused.

This notification occurs before dispatch or allocation-failure reporting. It also occurs for zero and negative counts, and after a positive-count allocation failure, provided earlier operations returned normally.

The values 5 and 6 distinguish the two calls. Interpreting them as locking, transaction, or lifecycle operations is inferred intent only; no such guarantee is established.

### 6. Dispatch or allocation-error path

After the second notification:

- A nonpositive count proceeds to normal success without dispatch.
- A positive count with nonzero temporary storage proceeds to dispatch.
- A positive count with zero temporary storage takes the allocation-error path.

For each dispatch index, in ascending order, the function reads the corresponding descriptor reference from temporary storage.

If the reference is zero, the entry is skipped without calling the per-index preparation dependency.

For a nonzero descriptor reference, the function reads its callback field at offset 8. If that field is zero, the entry is likewise skipped.

If both the descriptor reference and the inspected callback field are nonzero, the function calls F-1aed8c556fc7 with:

1. The output-slot address.
2. The current zero-based index.

The returned 32-bit value becomes the callback’s second argument.

After preparation returns, the function reads the descriptor reference from the same temporary slot again. It then invokes the callback found at offset 8 of this reread descriptor, with six arguments:

1. The function’s second argument.
2. The value returned by F-1aed8c556fc7.
3. The output-slot address.
4. The current zero-based index.
5. The descriptor’s 32-bit field at offset 0.
6. The descriptor’s 32-bit field at offset 4.

The callback return value, if any, is ignored.

The initial nonzero callback check is not repeated after preparation. The descriptor used for the actual call is obtained after preparation, and its payload fields are also used at that later stage. Thus, preparation-time mutations can affect the actual target and payload. The function does not protect against the reread descriptor or callback becoming invalid.

The evidence does not establish a finer evaluation order among the callback-target read and the two payload reads. Their values must not be treated as an atomic descriptor snapshot.

After a callback returns normally, processing continues with the next index. No callback result terminates traversal or changes the stored count.

### 7. Completion and failure reporting

After normal traversal, the function releases nonzero temporary storage through F-5990a26eaaa3, then returns one.

For a zero or negative count, there is no temporary allocation to release, and the function returns one.

For a positive count whose allocation returned zero, the function calls F-4fc89ec41a6d with five arguments:

1. 15.
2. 108.
3. 65.
4. 0.
5. 0.

If that dependency returns normally, the function returns zero. Its nonlocal behavior, including whether it can terminate or transfer control elsewhere, is unknown.

## Side effects

Established direct effects are:

- One 32-bit zero write to the output slot after successful initial lookup.
- One 32-bit write per retrieved entry into temporary storage.
- Reads of the initial object’s collection field, temporary entry slots, and callback descriptor fields.
- Dependency and callback invocations in the order described above.
- Release of successfully allocated temporary storage on normal completion.

The output slot is shared across both notifications, every eligible per-index preparation call, and every callback. The function neither resets it per entry nor validates its final contents. A successful return therefore does not imply a zero, nonzero, initialized-object, or otherwise semantically valid final output value.

Only the temporary entry array is explicitly released. The function does not explicitly release the lookup object, collection, descriptors, callback payloads, or any object represented by the output slot. Ownership transfers or releases performed inside dependencies remain unknown.

There is no visible cleanup mechanism for a dependency or callback that fails to return normally. Temporary storage release is established only along normal completion of dispatch.

There is no visible synchronization, reentrancy guard, exception handling, cancellation check, or recovery from invalid addresses. Dependency names or paired notification values do not establish any of those properties.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Each assumes valid accessed memory, representable size arithmetic where relevant, and normal return from invoked dependencies.

1. **Lookup returns zero.**  
   The function returns zero without directly writing the output slot or making either notification.

2. **Count is zero.**  
   After successful lookup, the output slot is zeroed, notification 5 runs, the count is obtained, and notification 6 runs. There is no allocation, retrieval, preparation, callback, or release. The return is one.

3. **Count is negative.**  
   A count of −1 follows the same allocation-free and callback-free success path as zero. It is not treated as a large unsigned entry count.

4. **Positive-count allocation fails.**  
   For a count of three and a zero allocation result, the request is for 12 bytes. No entries are retrieved. Notification 6 precedes F-4fc89ec41a6d. If error reporting returns, the result is zero.

5. **Null and callback-free descriptors are skipped.**  
   For three copied entries consisting of a null reference, a valid descriptor with a zero callback field, and a valid callable descriptor, only index two receives preparation and callback invocation. Its callback receives index two, not a compacted index zero.

6. **A callback runs more than once for duplicate entries.**  
   If two slots contain the same valid descriptor and it remains callable at each check, both indices are processed. There is no deduplication.

7. **The second notification mutates a descriptor.**  
   If notification 6 clears a copied descriptor’s callback field before dispatch, that entry is skipped. Copying its reference earlier does not preserve its previous callback.

8. **Preparation changes callback data.**  
   If preparation changes the current descriptor’s payload fields, the callback uses the subsequently read payloads. If it invalidates the descriptor or callback address, safe recovery is not guaranteed.

9. **The collection reference changes during copying.**  
   If the first retrieval changes the initial object’s collection field, the second retrieval uses the changed reference. The traversal bound remains the original count.

10. **Callbacks modify output.**  
    A callback may alter the output slot, and subsequent preparation calls and callbacks receive the same slot address. No automatic reset occurs before the next entry or before return.
