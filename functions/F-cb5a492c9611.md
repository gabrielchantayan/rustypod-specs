# F-cb5a492c9611

## Purpose

F-cb5a492c9611 performs an ordered teardown and accounting sequence for a non-null object-like pointer. It replaces the first 32-bit word of the supplied storage, invokes a dependency on that pointer, obtains a global context, validates a preceding metadata word, updates several context accounting fields, and passes the metadata address to another dependency.

A null input is a no-op.

**Inferred intent:** The sequence resembles object destruction followed by allocator accounting and storage release. That interpretation is not needed to define the observable behavior. In particular, the available evidence does not establish that any dependency actually releases memory, acquires a lock, or restores a previous state.

## Interface

### Input

One pointer, called the **object pointer** in this contract.

For the non-null path, the visible operations require access to:

| Location relative to object pointer | Width | Visible use |
|---|---:|---|
| −8 bytes | 32 bits | Metadata validation, masked amount extraction, and address passed to a dependency |
| −4 bytes | 16 bits | First accounting-table selector |
| −2 bytes | 16 bits | Second accounting-table selector |
| 0 bytes | 32 bits | Overwritten with a value read from a fixed global location |

The pointer identifies the object-facing address, not the beginning of the preceding eight-byte metadata region.

These are access requirements of the visible sequence, not validation performed by this function. There are no explicit bounds, alignment, lifetime, or write-permission checks.

### Output

The function has no explicit return value.

There are two established normal outcomes:

- Null input: immediate return without visible reads, writes, or dependency calls.
- Non-null input: return after all dependencies and accounting operations complete normally.

There is also a metadata-rejection path that invokes a dependency represented as non-returning. No ordinary error result is produced.

### Data widths and arithmetic

The supplied representation uses:

- 32-bit words for object contents, the metadata word, context counters, and the captured context address.
- Unsigned 16-bit values for both selectors.
- A 32-bit integer result from the accounting-index dependency.
- Four-byte spacing between accounting-table entries.

Counter arithmetic is stored back into 32-bit fields. This contract expresses those stored results modulo \(2^{32}\); no saturation, underflow check, or overflow report is visible.

Address expressions use the shown 32-bit target representation. Safe use requires that the resulting addresses identify accessible storage. The evidence does not establish portable language-level behavior for invalid pointers or address overflow.

## Behavior

### 1. Null handling and initial object update

If the object pointer is null, return immediately.

Otherwise:

1. Read a 32-bit value from a fixed global location.
2. Store that value at the object pointer.
3. Invoke **F-22abefe7f288** with the object pointer.

The initial write precedes every dependency call and all metadata validation. Consequently, metadata rejection does not imply that the object or external state is unchanged: the first word has already been replaced, and F-22abefe7f288 has already run.

There is no visible read of the old first word and no local mechanism for restoring it.

The supplied sequence includes additional null comparisons after this point. They compare the same locally held pointer value; no visible operation assigns a different value to that pointer. They do not provide a memory-lifetime or validity check.

### 2. Setup and context capture

After F-22abefe7f288 returns:

1. Invoke **F-2fd8826557a4** with no explicit arguments.
2. Read a global pointer-bearing location and capture its 32-bit context address.

This global read occurs after both earlier dependencies. The function therefore uses the context value present at that point, not necessarily the value present on entry.

The captured address remains the base for subsequent visible accounting operations and context arguments. There is no later visible reload of the global context source.

### 3. Metadata validation

The metadata address is eight bytes before the object pointer.

The function rejects the metadata if either condition holds:

- The 32-bit metadata word is zero.
- Bit 0 of that word is set.

The test is short-circuited: the zero comparison occurs first; the bit-0 test is needed only when the first comparison is false. The supplied expression does not establish that the metadata word is loaded exactly once.

On rejection, invoke **F-a817d8d58c10** with no explicit arguments. This dependency is represented as non-returning. There are no visible accounting updates or calls to the later context dependencies on that path.

Successful validation establishes only that the checked word was nonzero and had bit 0 clear at the relevant reads. It does not establish that:

- The masked accounting amount is nonzero.
- Either selector is within a valid table range.
- Any counter is large enough for subtraction.
- The context address is valid.
- The metadata will remain unchanged across later dependency calls.

### 4. Enter the context-dependent accounting phase

Invoke **F-c0fc6d033caa** with the captured context address.

Only after this dependency returns does the function obtain the first selector and the accounting amount used for the next four updates. Thus, metadata changes made by this dependency can affect those operations.

### 5. Update four amount-accounting fields

Let the captured context address be the base of the following layout:

| Context-relative location | Width | Visible role |
|---|---:|---|
| `0x224 + 4 × first selector` | 32 bits | First selected amount field |
| `0x30c` | 32 bits | First aggregate amount field |
| `0xe0 + 4 × second selector` | 32 bits | Second selected amount field |
| `0x220` | 32 bits | Second aggregate amount field |

Perform these operations in order:

1. Read the unsigned 16-bit first selector at object offset −4 and determine the first selected field address.
2. Read the 32-bit metadata word at offset −8 and retain its value masked by `0x3ffffffc`.
3. Read the first selected field, subtract the retained amount, and write the 32-bit result.
4. Read the aggregate field at `0x30c`, subtract the same retained amount, and write the result.
5. Read the unsigned 16-bit second selector at object offset −2 and determine the second selected field address.
6. Read the second selected field, subtract the same retained amount, and write the result.
7. Read the aggregate field at `0x220`, subtract the same retained amount, and write the result.

The mask preserves bits 2 through 29 and discards bits 0, 1, 30, and 31. The retained amount is therefore a multiple of four from zero through `0x3ffffffc`, inclusive.

The amount used for all four subtractions is the same retained value. In contrast, the two selectors are read at different stages.

No disjointness between these fields, metadata, or other accessible storage is checked. If addresses alias, later reads observe earlier writes according to this sequence. The four updates must not be treated as an atomic batch or collapsed into independent updates to assumed-distinct fields.

### 6. Update count fields

Invoke **F-09dcb55e8e0a** with no explicit arguments and use its returned integer as an accounting index.

Then:

1. At context offset `0x310 + 4 × accounting index`, read a 32-bit field, decrement it by one, and write the result.
2. At context offset `0x390`, read a 32-bit field, decrement it by one, and write the result.

The index is not validated here. Negative or out-of-range results are not explicitly rejected.

The second decrement reads its field after the first decrement has been stored. If the two addresses coincide, that same field is decremented twice.

### 7. Update the remaining amount field

At context offset `0x08`:

1. Read the current 32-bit counter.
2. Read the metadata word again and mask it with `0x3ffffffc`.
3. Subtract that masked amount and store the 32-bit result.

The evidence establishes the subtraction and final store, but not a strict order between the two operand reads within this expression.

This operation does **not** reuse the retained amount from the earlier four subtractions. If the metadata has changed, including through F-09dcb55e8e0a or an overlapping earlier write, the amount subtracted here may differ.

### 8. Final dependencies and return

Invoke these dependencies in order:

1. **F-cc6c9b4a0f68**, with the captured context address and the metadata address.
2. **F-e586bff64fb7**, with the captured context address.

Return after both complete normally.

No further visible object or metadata access follows F-cc6c9b4a0f68. Its effect on memory ownership is nevertheless unknown.

## Side effects

The visible non-null path can modify:

- The first 32-bit word at the object pointer.
- Four context amount fields, each using one retained masked metadata value.
- Two context count fields.
- A context amount field at offset `0x08`, using a newly read masked metadata value.
- Any state modified by invoked dependencies.

There is no visible rollback. Failure or non-return in a dependency can leave all earlier effects in place.

No synchronization guarantee follows from the ordering alone. The names, placement, and arguments of the context dependencies are insufficient to establish locking or thread safety.

### Ownership and lifetime requirements

The caller must supply storage that remains usable for the accesses actually reached. In particular, after F-22abefe7f288 returns, this function continues to access the preceding metadata. After F-c0fc6d033caa returns, it accesses both selectors and the metadata again.

If any dependency invalidates storage needed by a subsequent visible operation, the available evidence provides no recovery behavior.

There is no established ownership transfer, reference-count contract, allocation-family requirement, or guarantee that the object is released by the end of this function. Those matters remain dependency-level unknowns.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, assume valid accessible addresses, normally returning dependencies, stable metadata, and distinct accounting fields.

### Null input

Given a null object pointer, the function returns without invoking dependencies or accessing the global replacement value, global context source, object storage, or metadata.

### Ordinary accounting

Given:

- Metadata word `0x00000024`.
- First selector 3.
- Second selector 5.
- Accounting-index result 2.

The masked amount is 36. The amount fields at context offsets `0x230`, `0x30c`, `0xf4`, and `0x220` each decrease by 36. The count fields at `0x318` and `0x390` each decrease by one. The amount field at `0x08` decreases by 36.

These effects follow the earlier object-word replacement and setup calls, and precede the final two dependencies.

### Rejected metadata

If the checked metadata word is zero, or is nonzero with bit 0 set, F-a817d8d58c10 is invoked.

Before that invocation, the object-word replacement, F-22abefe7f288, F-2fd8826557a4, and context capture have already occurred. No later accounting operation is reached under the non-returning dependency contract.

### Accepted metadata with zero accounting amount

A stable metadata word of `0x00000002` passes validation but produces a masked amount of zero.

The four early amount updates and the final amount update still perform their visible read/write operations, leaving those values numerically unchanged when fields do not alias. The two count fields still decrease.

### Metadata changed by a dependency

Suppose the four early updates use metadata `0x00000024`, but F-09dcb55e8e0a changes it to `0x00000044`.

Then the four early subtractions use 36, while the later subtraction at context offset `0x08` uses 68. The function does not revalidate the changed metadata before that final subtraction.

### Underflow and overlapping count fields

If a distinct count field initially contains zero, decrementing it stores `0xffffffff`.

If the accounting-index result is 32, the selected count address is context offset `0x390`. Both count updates then target the same word. With no intervening external mutation, an initial value of 5 becomes 3, not 4.
