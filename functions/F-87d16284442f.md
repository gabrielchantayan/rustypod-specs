# F-87d16284442f

## Purpose

F-87d16284442f records a requested object in a receiver and, when the previous and requested objects differ, performs a sequence of indirect notifications followed by a receiver callback.

The changed-object path can also derive the callback’s argument by following a chain of objects obtained through F-682adfd5a561. A nonzero caller-supplied argument bypasses that derivation.

**Established behavior:** recording the requested object happens even when the previous and requested objects are identical. Equality suppresses all subsequent work.

**Inferred intent:** the indirect calls with arguments zero and one appear to deactivate and activate objects, and the zeroed receiver field may represent transition state. These interpretations are not established contracts. This specification describes the calls and stored values without assigning those meanings.

## Interface

### Inputs

The function has four inputs:

| Input | Role |
|---|---|
| Receiver | Address of an object containing writable state fields and an indirect-call table reference. |
| Previous object | Object address compared with the requested object. May be null on the changed-object path. |
| Requested object | Object address stored in the receiver and used for indirect calls on the changed-object path. |
| Selection value | A recovered 32-bit integer passed to the final receiver callback, or replaced by a derived value when initially zero. |

The comparison between the previous and requested objects is address equality, not object-content equality.

### Width and layout model

The supplied static representation uses four-byte integer slots, pointer values stored in those slots, and byte offsets into indirect-call tables. This specification therefore describes the recovered **32-bit address/value model**. It does not establish portability to an environment with wider pointers or different integer widths.

Relevant receiver fields are:

| Byte offset | Access | Observed role |
|---|---|---|
| +0x00 | Read on the changed-object path | Indirect-call table address. |
| +0x28 | Read after the requested-object notification | Address compared with the requested object. |
| +0x2C | Conditionally read | Address of an additional object to notify. |
| +0x34 | Always written | Requested-object address. |
| +0x38 | Written only when object addresses differ | Set to the 32-bit value zero. |

Objects called indirectly expose a table address at byte offset +0x00. The relevant table entries are at byte offsets +0xA0, +0xE8, +0x120, and +0x1E8. These are table-entry offsets, not offsets of executable code within an object.

No range arithmetic, count arithmetic, or numeric comparison other than zero/nonzero testing is visible. Pointer equality is used separately.

### Output

No return value is specified. Observable results consist of receiver writes, indirect calls, dependency calls, and any effects those calls produce.

The selection value is passed by value. Replacing it internally does not directly update caller storage.

### Preconditions

For a normal execution:

- The receiver must permit the initial four-byte write at +0x34.
- If the previous and requested objects differ, the receiver must also permit the write at +0x38 and the later field and table reads.
- Every object that is dereferenced must remain valid when that dereference occurs.
- Every table entry that is invoked must designate a callable target compatible with the observed arguments.
- If the previous object is nonnull on the changed-object path, it must support the +0xA0 invocation.
- The requested object must support +0xA0 on the changed-object path, and +0xE8 when derivation is selected.
- If the receiver’s +0x28 field matches the requested object, the object obtained from +0x2C must support +0xA0.
- Any nonnull object returned by F-682adfd5a561 and subsequently queried must support +0x120.

No null checks protect the requested object, the receiver’s +0x2C object, or their table addresses on paths that use them.

## Behavior

### 1. Record the requested object

The first visible operation writes the requested-object address to receiver offset +0x34.

This precedes the equality-based early return, both notifications, any traversal, and the final receiver callback. A later failure does not undo this write.

### 2. Handle equal object addresses

If the previous-object address equals the requested-object address, the function returns immediately.

On this path:

- Receiver offset +0x34 has been written.
- Receiver offset +0x38 is not written by this function.
- No indirect call is made.
- F-682adfd5a561 is not called.
- The selection value is not used.

This includes the case where both object arguments are null, provided the receiver’s initial write is valid.

### 3. Begin a changed-object transition

When the two object addresses differ, the function writes zero to receiver offset +0x38.

It then performs these notifications in order:

1. If the previous object is nonnull, invoke its table entry at +0xA0 with the previous object as the receiver and a second argument of zero.
2. Invoke the requested object’s table entry at +0xA0 with the requested object as the receiver and a second argument of one.

The null check applies only to the previous object. A null requested object on this path is not converted into a no-op or a reported error.

The requested object’s table entry is obtained when that call is reached, after the previous-object call has returned. The function does not establish that the previous-object call leaves the requested object, its table, or shared state unchanged.

### 4. Conditionally notify an additional object

After the requested-object notification returns, the function reads receiver offset +0x28 and compares the stored address with the requested-object argument.

If they match, it obtains an object through receiver offset +0x2C and invokes that object’s +0xA0 table entry with that object as the receiver and a second argument of one.

If they do not match, this additional invocation is omitted.

The comparison uses the receiver field as read **after** the earlier notifications. It is not established to use a snapshot taken before them.

No null check is performed on the +0x2C object. Nor is a notification suppressed merely because that object happens to equal an object already notified.

### 5. Choose the final selection value

If the supplied selection value is nonzero, it is forwarded unchanged to the final receiver callback. The +0xE8 call, all +0x120 calls, and all F-682adfd5a561 calls are skipped.

Negative 32-bit values are nonzero and take this bypass path. There is no visible validation that a nonzero value is a pointer, identifier, or otherwise meaningful to the final callback.

If the supplied selection value is zero, the function derives a replacement as follows.

#### Initial candidate

It invokes the requested object’s table entry at +0xE8 with three observed arguments:

- The requested object.
- One.
- One.

The returned 32-bit value becomes the initial candidate.

The function then calls F-682adfd5a561 with that candidate and the fixed value **0x1100**. This happens even when the candidate is zero.

The result is treated as an object address for the traversal. A null result terminates traversal immediately, retaining the initial candidate.

#### Traversal

For each nonnull resolved object, the function invokes its +0x120 table entry with that object and two arguments of one.

- If this query returns zero, traversal stops. The previously retained candidate is used.
- If it returns a nonzero value, the function calls F-682adfd5a561 with that value and 0x1100.
- After that dependency call returns, the nonzero query value becomes the retained candidate.
- The dependency’s returned address determines whether another object query occurs.

Consequently, a nonzero query result is retained even if resolving it produces null. Conversely, a zero query result is a termination signal and does not replace the candidate.

There is no visible cycle detection, visited-object tracking, or iteration bound. If resolution continually returns nonnull objects and their queries continually return nonzero values, the function does not reach its final callback.

### 6. Invoke the receiver callback

After the notifications and any completed derivation, the function obtains the receiver’s table entry at +0x1E8 and invokes it with:

- The receiver.
- The selected 32-bit value.

The receiver’s table is read at this stage, after the preceding calls. The supplied evidence does not justify treating it as a table cached before those calls.

The recovered representation treats the final indirect transfer as a call followed by return. The exact low-level transfer mechanism is not established; the observable contract supported here is the invocation and its arguments, not a particular call-stack implementation.

## Side effects

### Direct writes

The function directly performs only these identified receiver writes:

1. Requested-object address to +0x34, unconditionally.
2. Zero to +0x38, only when the object arguments differ.

These are ordinary writes in the supplied representation. No atomicity, memory ordering, synchronization, or thread-safety guarantee is established.

### Effects through dependencies

All invoked targets may have additional effects. Their implementations are not supplied. In particular, this contract does not assume that they:

- Preserve receiver fields, object tables, globals, or other shared state.
- Avoid reentry.
- Leave object lifetimes unchanged.
- Allocate, retain, release, or transfer ownership in any particular way.
- Return normally.

Later receiver-field reads and indirect lookups occur after earlier calls and can therefore observe state changes made by them.

### Ownership and failure

There is no visible direct allocation, release, reference-count operation, or ownership-transfer operation in this function. Storing the requested-object address does not by itself establish retention or ownership.

There is no explicit error return, rollback, exception handling, or retry. If an invocation fails or does not return, later operations are not established to occur. Writes and calls already completed are not reversed by this function.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Unless otherwise stated, all required accesses are valid, callees return normally, and callees do not alter state relevant to the example.

### Equal objects

Given identical previous and requested addresses and an existing nonzero value at receiver +0x38:

- +0x34 receives the requested address.
- +0x38 retains its existing value.
- No dependency or indirect target is invoked.

The same behavior applies when both object addresses are null.

### Changed objects with a supplied selection

Given distinct nonnull objects, selection value 7, and a nonmatching receiver +0x28 field:

- Write +0x34, then zero +0x38.
- Notify the previous object with zero.
- Notify the requested object with one.
- Invoke the receiver callback with 7.
- Perform no candidate derivation.

A supplied value of −1 follows the same bypass rule.

### No previous object

Given a null previous object and a valid nonnull requested object:

- Skip the previous-object notification.
- Continue with the requested-object notification and subsequent applicable behavior.

### Conditional notification observes updated state

If an earlier notification changes receiver +0x28 to the requested-object address and installs a valid object at +0x2C, the additional notification occurs using the subsequently read receiver state.

If +0x28 instead does not match at the comparison, the additional notification is skipped.

### Initial resolution fails

Suppose selection is zero, the +0xE8 invocation returns candidate A, and F-682adfd5a561 returns null for A.

The final receiver callback receives A. This remains true if A is zero; the resolution call still occurs.

### Query returns zero

Suppose A resolves to an object whose +0x120 query returns zero.

The final receiver callback receives A. There is no resolution call for that zero query result.

### Later resolution fails

Suppose A resolves to an object whose query returns nonzero B, and resolving B returns null.

The final receiver callback receives B, not A.

### Nonterminating traversal

If every resolution returns a nonnull object and every object query returns a nonzero candidate, there is no established termination. The receiver writes and notifications precede that traversal, but the final receiver callback is not reached.

## Uncertainties

The following remain **documented_only**:

- Semantic names and invariants for the receiver fields.
- Whether object notifications represent activation, focus, selection, or another operation.
- The meaning and permitted domain of candidates and of 0x1100.
- Ownership and lifetime guarantees across all dependency calls.
- Effects of reentry and concurrent mutation.
- Invalid-pointer, invalid-table, and incompatible-target behavior.
- Whether traversal is guaranteed to terminate under application-level invariants.
- Exact ABI details and the final indirect transfer’s low-level form.

The recovered four-byte layout is the basis for the offsets above. A separate ABI or type declaration was not supplied.
