# F-2807e1ac933c

## Purpose

F-2807e1ac933c searches up to 32 fixed-stride entries for the first entry satisfying a presence check, an exact one-byte eligibility check, and two 32-bit key comparisons. It reports the matching entry’s zero-based index through a caller-provided output address.

The established result convention is:

- **0:** a match was found and its index was written.
- **1:** all 32 entries were examined without a match; this function did not write the output.

Each examined entry is bracketed by calls to F-f0216cff9365 and F-2bb3dbfa7286. Their placement suggests an entry-level synchronization protocol, but their actual effects are unknown. This contract therefore describes the calls and their ordering without claiming mutual exclusion, memory ownership, or stability of the inspected data.

## Interface

### Inputs

The function has five input positions:

| Position | Meaning established by this function |
|---|---|
| 1 | Base address of the containing memory region. |
| 2 | An unused 32-bit value. The function does not inspect or forward it. |
| 3 | First requested 32-bit key, compared against a candidate’s field at offset +8. |
| 4 | Second requested 32-bit key, compared against a candidate’s field at offset +12. |
| 5 | Address at which to write a 32-bit unsigned entry index on success. |

Although the third input corresponds to the lower candidate-field offset, the comparison against the **fourth** input occurs first.

The supplied representation uses 32-bit address values and four-byte scalar accesses. It does not establish a portable interface for systems with wider pointers.

### Return value

The return is a 32-bit value, restricted on normal completion to 0 or 1. It is not the index itself.

A successful output index is in the inclusive range 0–31.

### Container layout

Entry number \(i\) begins at:

\[
\text{base} + 20i,\qquad 0 \le i \le 31.
\]

The function uses the following locations:

| Location | Access or use |
|---|---|
| Entry start +4 | Read as a four-byte candidate address. Zero means absent. |
| Entry start +8 | Read as a one-byte eligibility value. Only the value 1 passes. |
| Entry start +12 | Address passed as the second argument to both dependencies. |
| Container base +652 | Read as the four-byte first argument to each dependency call. |

The 32 entry starts range from base +0 through base +620. Their nominal 20-byte spans occupy offsets 0–639. The shared dependency argument is read separately at offset 652, or hexadecimal 0x28C.

The function does not establish what occupies unused entry bytes, what object begins at entry offset +12, or how much memory either dependency may access through that address.

### Candidate layout

For a nonzero candidate address, the function may read:

| Candidate offset | Meaning in this search |
|---|---|
| +12 | Four-byte value compared with input position 4. |
| +8 | Four-byte value compared with input position 3, but only if the +12 comparison succeeds. |

These are equality comparisons. Signed versus unsigned interpretation does not change which 32-bit bit patterns compare equal. No ordering, range, or arithmetic interpretation of the keys is established.

### Preconditions for normal completion

Every access actually reached must address readable or writable memory as appropriate:

- The container’s shared argument field must be readable each time it is loaded.
- Each examined entry’s candidate-address field must be readable.
- An examined entry’s eligibility byte must be readable when its candidate address is nonzero.
- A candidate’s +12 field must be readable when that candidate is present and eligible.
- A candidate’s +8 field must be readable when its +12 field matches.
- The output address must support a four-byte write if a match is found.
- Both dependencies must accept the supplied arguments and return normally.

Any additional alignment, synchronization, or storage requirements of the dependencies are unknown. Address arithmetic must resolve to the intended objects without invalid address wrapping.

The function performs no explicit pointer validation. An output address is not directly dereferenced on a no-match path, but this does not establish that arbitrary invalid pointers are supported by a broader calling interface.

## Behavior

### Search order and dependency bracketing

The search begins at entry 0 and advances in ascending index order. It never intentionally inspects an entry after the first matching entry.

For each examined entry, the observable sequence established by the supplied representation is:

1. Read the four-byte shared argument from container offset +652 and call F-f0216cff9365 with that value and the entry’s offset-12 address.
2. After that call returns, read the entry’s candidate address.
3. Evaluate the candidate conditions in the order described below.
4. Invoke F-2bb3dbfa7286 for the examined entry, with the success output write occurring before this invocation when a match was found.

The entry’s candidate address is therefore obtained **after** F-f0216cff9365 returns. The function does not inspect it before that call.

The shared argument is loaded again for F-2bb3dbfa7286. It is not guaranteed to equal the argument supplied to F-f0216cff9365. A dependency, another actor, or an aliased output write could change the field between loads.

### Matching conditions and conditional reads

An entry matches only when all four conditions hold:

1. Its candidate address is nonzero.
2. Its eligibility byte is exactly 1.
3. The four-byte value at candidate offset +12 equals input position 4.
4. The four-byte value at candidate offset +8 equals input position 3.

Evaluation is short-circuited:

- A zero candidate address prevents the eligibility-byte read and both candidate-field reads.
- An eligibility byte other than 1 prevents both candidate-field reads.
- A mismatch at candidate offset +12 prevents the read at candidate offset +8.

In particular, eligibility is not a general nonzero test. Values such as 2 or 255 fail.

The candidate address is read once for this evaluation. Both candidate-field reads use that captured address; the entry’s candidate-address field is not reloaded between the two comparisons.

### Nonmatching entry

For a nonmatching entry, the function:

- Reloads the shared argument at container offset +652.
- Calls F-2bb3dbfa7286 with that value and the same entry offset-12 address used for the first dependency call.
- Advances to the next entry after the call returns.

If entry 31 also fails to match, the function returns 1. It does not access entry 32 and does not directly write the output.

An unsuccessful complete search makes 32 calls to each dependency, for 64 dependency calls in total, assuming all calls return normally.

### Matching entry

For the first matching entry, the function:

- Writes the current zero-based index as a four-byte unsigned value to the output address.
- Reloads the shared argument at container offset +652.
- Calls F-2bb3dbfa7286 with that value and the matching entry’s offset-12 address.
- Returns 0 after that call returns.

The output store precedes the final dependency call. Success is not returned until that call completes normally.

A match at index \(k\) causes \(k+1\) calls to each dependency, or \(2(k+1)\) dependency calls overall.

The output write does not determine the address passed for the final entry: that address is calculated from the current search index and the container base. Thus an output location overlapping container memory does not cause the function to obtain its final entry address by reading the newly written output.

### Arithmetic boundaries

The search index is a 32-bit unsigned quantity initialized to zero. It increases by one only after a nonmatching entry’s second dependency call. Reaching 32 ends the search.

Within a normal search, the largest entry displacement is \(31 \times 20 = 620\), and the largest entry-relative address directly formed for a dependency argument is base +632. These bounded displacements do not overflow a 32-bit unsigned value on their own. Whether adding them to a particular base produces a valid address remains a caller-side requirement.

## Side effects

The function’s only explicit data write is the successful four-byte output store. It does not explicitly clear the output before searching, mark a matching entry, rewrite candidate fields, allocate memory, or release memory.

Those statements do not constrain dependency effects. Either dependency may mutate memory or external state; its implementation is not supplied.

Ownership is consequently limited to the following established facts:

- The function receives addresses and forwards an entry-interior address to dependencies.
- No ownership-transfer operation is visible.
- No direct allocation or deallocation operation is visible.
- Whether either dependency acquires, releases, retains, or destroys any resource is unknown.

Output aliasing is not checked. If the output overlaps the shared argument field, the successful index write occurs before the field is reloaded for the final F-2bb3dbfa7286 call. If the output overlaps other container or candidate storage, the write may alter that storage before the final dependency executes. No non-aliasing guarantee is established.

There is no explicit error recovery or abnormal-exit cleanup. A fault during a read or output write, or a dependency that does not return normally, can prevent later calls and the normal return. In particular, a fault in the successful output store prevents the final dependency call from being reached.

No concurrency guarantee is established. The dependency placement suggests protected inspection, but neither atomicity nor candidate lifetime can be inferred without the dependency contracts and the surrounding memory model.

## Acceptance examples

These are conditional acceptance criteria, not executed tests. Unless noted otherwise, memory accesses are valid, dependencies return normally, and relevant data remains stable except for the stated changes.

1. **First-entry match.** Entry 0 has a nonzero candidate address, eligibility byte 1, and both matching fields. The function writes 0 to the output, calls F-2bb3dbfa7286 afterward, and returns 0. No later entry is visited.

2. **First matching entry wins.** Entries 4 and 9 both satisfy the conditions; entries 0–3 do not. The output becomes 4. Entry 9 is never inspected.

3. **All entries absent.** Every visited candidate-address field is zero. The function reads no eligibility bytes or candidate fields, makes 32 calls to each dependency, returns 1, and performs no direct output write.

4. **Noncanonical eligibility.** Entry 0 has a nonzero candidate address and eligibility byte 2. It does not match even if both candidate fields would match. Those candidate fields are not read for this entry.

5. **Higher-offset key mismatch.** A present, eligible candidate has a +12 value different from input position 4. Its +8 field is not read.

6. **Last-entry match.** Only entry 31 matches. The function writes 31, makes 32 calls to each dependency, and returns 0 without forming an entry-32 visit.

7. **Unused input variation.** Changing only input position 2 does not change this function’s explicit reads, writes, dependency arguments, or branch conditions.

8. **Shared argument changes during a visit.** If F-f0216cff9365 changes the field at container offset +652, the subsequent F-2bb3dbfa7286 call receives the later value, assuming no further change intervenes.

9. **Output overlaps the shared argument.** If the output address is exactly container offset +652 and entry 7 matches, the successful store writes 7 there before the final shared-argument load. Absent an intervening change, the final dependency receives 7 as its first argument.

10. **Final dependency does not return.** If a match is found and its final dependency call does not return, the output has already been written, but this function does not deliver a normal success return.
