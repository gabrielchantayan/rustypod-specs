# F-051feb68d086

## Purpose

F-051feb68d086 rearranges links around a supplied node and the object identified by that node’s field at byte offset `+8`. It promotes the latter object into the supplied node’s previous root or parent-child position, transfers a link between them, and makes the supplied node a child of the promoted object.

**Established static behavior:** The operation consists of ordered four-byte field accesses, equality comparisons, and conditional link updates. It does not validate structural consistency before modifying memory.

**Inferred intent:** The observed arrangement is consistent with a right rotation in a parent-linked binary tree, with `+4` representing a parent, `+8` a left child, and `+12` a right child. These names describe the apparent roles; declared object types and broader tree invariants are not established.

The operation’s ordinary rotation postconditions require valid, stable, appropriately distinct objects. Where objects overlap or links change during execution, the ordered accesses—not the tree interpretation—define the supported static description.

## Interface

The function accepts two 32-bit address-like arguments and has no explicit return value.

| Input | Observed role |
|---|---|
| Context address | Identifies storage whose four-byte field at `+16` supplies the base address of an object containing a root slot at `+4`. |
| Supplied-node address | Identifies the node being demoted. Its initial four-byte field at `+8` supplies the promoted-object address. |

The arguments and link fields are represented as 32-bit values in the supplied body. They are used as addresses or compared for equality. This does not establish a portable native-pointer interface, a calling convention, or behavior for addresses outside that representation.

Relevant fields are:

| Object role | Byte offset | Accessed role |
|---|---:|---|
| Context | `+16` | Read to locate the root-slot-containing object |
| Root-slot-containing object | `+4` | Root link; read and conditionally replaced |
| Supplied node | `+4` | Parent link; read and ultimately replaced |
| Supplied node | `+8` | Promoted-object link; read and replaced |
| Promoted object | `+4` | Parent link; replaced |
| Promoted object | `+12` | Transferred-object link; repeatedly read, then replaced |
| Transferred object | `+4` | Parent link; conditionally replaced |
| Parent selected on the non-root path | `+12` | Read, then replaced if it identifies the supplied node |
| Parent selected on the fallback path | `+8` | Replaced without checking its previous value |

All listed field accesses are four bytes wide. Offsets are in bytes.

For successful completion, every reached read must address accessible readable storage, and every reached write must address accessible writable storage for the complete four-byte field. The function does not check these requirements. In particular, it does not check that the promoted-object link is nonzero before using it as an address.

No allocation or deallocation operation appears in the body. **Whether these link changes transfer logical ownership, and which component is responsible for managing object lifetimes, are unknown.** The absence of allocation or deallocation does not establish an ownership convention.

## Behavior

### Promotion selection and transferred-link handling

The promoted-object address is taken from the supplied node’s `+8` field at the beginning of the operation. That selected address is retained for subsequent promoted-object accesses; it is not reselected after the supplied node’s `+8` field changes.

The promoted object’s `+12` field is read and copied into the supplied node’s `+8` field. This is the first explicit write. It occurs before the context or root slot is examined.

The promoted object’s `+12` field is then read again and compared with zero:

- A zero result skips the transferred-object parent update.
- A nonzero result causes another read of that same field. This further result supplies the address whose `+4` field receives the supplied-node address.

There are therefore two reads of the promoted object’s `+12` field when the zero test fails, and three when it succeeds. The copied value, tested value, and address used for the conditional write are not established as one snapshot.

With stable, nonoverlapping storage, these reads identify the same transferred object. Without those conditions, the value copied into the supplied node can differ from the tested or subsequently addressed value. The nonzero check applies to the test read, not independently to the later address read.

### Promoted parent assignment

After the transferred-link handling, the supplied node’s `+4` field is read and copied into the promoted object’s `+4` field.

Under the tree interpretation, this gives the promoted object the supplied node’s former parent. More precisely, it copies the value present at this point in execution. An earlier write through an overlapping object role could already have changed that field.

This parent assignment precedes both root-slot comparison and external reconnection.

### Root or parent-child reconnection

The context’s `+16` field is read to obtain a base address. The root slot is the four-byte field four bytes beyond that base. Its value is compared with the supplied-node address.

**If the root slot matches:** The selected promoted-object address replaces the root-slot value. No parent child-link field is inspected on this path. The parent value already copied into the promoted object is retained; the function does not normalize it to zero or any sentinel value.

**If the root slot does not match:** The supplied node’s `+4` field is read again to select a parent object. This is a new read, not reuse of the value previously copied into the promoted object.

The selected parent’s `+12` field determines which parent link is overwritten:

- If it equals the supplied-node address, that `+12` field receives the promoted-object address.
- Otherwise, the parent’s `+8` field receives the promoted-object address.

The fallback does not read or verify the parent’s `+8` value before overwriting it. It applies even if neither parent child-link field previously identified the supplied node.

Root status is determined by root-slot equality, not by the supplied node’s parent value. A zero parent does not select the root path.

### Final local links

After either external reconnection path, the promoted object’s `+12` field receives the supplied-node address. The supplied node’s `+4` field then receives the promoted-object address. This supplied-node parent update is the final explicit write.

For coherent, distinct objects with stable links, completion has these effects:

- The promoted object occupies the supplied node’s former root or parent-child position.
- The promoted object’s former `+12` link becomes the supplied node’s `+8` link.
- A nonzero transferred object points back to the supplied node through its `+4` field.
- The promoted object receives the supplied node’s former parent value.
- The promoted object’s `+12` field identifies the supplied node.
- The supplied node’s `+4` field identifies the promoted object.

The supplied node’s `+12` field and the promoted object’s `+8` field are not explicitly accessed through those roles. Their contents remain unchanged only if they do not overlap storage written through another role.

## Side effects

There are five unconditional four-byte write operations, in this order:

1. Replacement of the supplied node’s `+8` field.
2. Replacement of the promoted object’s `+4` field.
3. Replacement of exactly one external slot: the root slot, the selected parent’s `+12`, or that parent’s `+8`.
4. Replacement of the promoted object’s `+12` field.
5. Replacement of the supplied node’s `+4` field.

A nonzero transferred-link test inserts one additional four-byte write between the first and second unconditional writes. That write targets offset `+4` of the address obtained by the subsequent transferred-link read.

These are counts of write operations, not distinct modified locations. Aliasing may cause several operations to reach the same storage.

The changes are incremental. The supplied node’s `+8` link changes before root status is known, and external reconnection occurs before the final local links are installed. No rollback, transaction mechanism, or synchronization operation appears in the body.

No allocation, release, callback, logging operation, or explicit error-reporting result appears. **The logical ownership consequences of the link updates and responsibility for maintaining or ending object lifetimes remain unknown.** Independently of those conventions, all accesses actually reached must be valid for successful completion.

Invalid memory and inconsistent structures have no explicit recovery path. The body does not establish a particular trap, exception, diagnostic, or final memory state following an access failure.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed tests. Unless stated otherwise, all referenced fields are accessible, objects are distinct and nonoverlapping, and relevant memory remains stable during execution.

### Root promotion with a nonzero transferred link

Initially, the root slot identifies the supplied node. The supplied node’s `+8` field identifies the promoted object, and the promoted object’s `+12` field identifies a nonzero transferred object.

On completion:

- The root slot identifies the promoted object.
- The supplied node’s `+8` field identifies the transferred object.
- The transferred object’s `+4` field identifies the supplied node.
- The promoted object’s `+4` field contains the supplied node’s original parent value.
- The promoted object’s `+12` field identifies the supplied node.
- The supplied node’s `+4` field identifies the promoted object.

Any original root-parent value is copied unchanged. Root promotion does not require that value to be zero.

### Non-root promotion through the parent’s `+12` field

Initially, the root slot does not identify the supplied node. The supplied node’s parent identifies an object whose `+12` field equals the supplied-node address.

The parent’s `+12` field is replaced with the promoted-object address. Its `+8` field receives no explicit write through the parent role. The root slot is read but not written.

The transferred-link and final local-link updates still occur.

### Non-root fallback despite inconsistent links

Initially, the root slot does not identify the supplied node. The selected parent’s `+12` field identifies a different object, and its `+8` field also identifies an unrelated object.

The parent’s `+8` field is nevertheless overwritten with the promoted-object address. There is no consistency rejection and no requirement that the overwritten link previously identify the supplied node.

### Stable zero transferred link

If the promoted object’s `+12` field remains zero for the relevant reads, the supplied node’s `+8` field becomes zero and no transferred-object parent write occurs.

External reconnection and the final two local writes still occur. This does not describe a zero promoted-object link: the initially selected promoted-object address is dereferenced without a zero check.

### Root mismatch with a zero parent

If the root slot does not match and the supplied node’s `+4` field is zero when reread, the function proceeds to a parent-relative access at offset `+12` from that value. It does not return a null-parent error.

Successful completion cannot be required unless that access and every subsequent reached access are valid in the execution environment.

### Different values across transferred-link reads

If the relevant reads observe different values, the first value is copied into the supplied node’s `+8` field. A zero result from the second read skips the conditional parent write, regardless of the first value.

If the second read is nonzero, the third read supplies the address used for that write, even if it differs from both earlier values. These criteria describe the exposed access sequence; they do not establish that concurrent mutation is supported.
