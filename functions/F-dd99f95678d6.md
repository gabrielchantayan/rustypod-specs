# F-dd99f95678d6

## Purpose

F-dd99f95678d6 advances an incremental redistribution of linked entries between two regions of a table of 32-bit bucket-head slots. Each invocation processes one source bucket, partitions its entries between that bucket and a destination bucket, and advances a progress field.

When the progress field reaches an unsigned threshold, the function requests a larger backing region through F-8b998a07b5e1. A nonzero result leads to initialization of additional bucket heads and publication of updated table state. A zero result resets progress and increments a separate counter, without undoing the redistribution already performed.

The interpretation as an incrementally expanded hash table is inferred from the structure of the operations. The established behavior is the bucket manipulation and state-update sequence described below; neither dependency’s full semantics is supplied.

## Interface

### Input and return

The function receives one pointer to a mutable state record. It has no explicit return value. Its observable results are writes to that record, bucket-head storage, entry links, and any effects of its dependencies.

The supplied representation uses four-byte state elements and four-byte entry fields. This contract describes the evident 32-bit representation: 32-bit integer fields, 32-bit stored addresses, and four-byte bucket slots. A different ABI is not established by the available evidence.

### State layout

The following names describe roles in this function, not independently established data-type definitions.

| Byte offset | Width | Role |
|---|---:|---|
| 0 | 32 bits | Address of the bucket-head storage |
| 12 | 32 bits | Counter incremented at entry |
| 16 | 32 bits | Partition parameter and growth-size parameter |
| 20 | 32 bits | Redistribution progress |
| 24 | 32 bits | Redistribution threshold and destination displacement |

The record must expose all fields accessed on the path taken. The highest explicitly accessed field occupies bytes 92–95. The function does not itself validate the record pointer or its extent.

### Bucket and entry layout

Bucket storage consists of four-byte head slots. A zero head denotes an empty chain; a nonzero head is treated as an entry address.

Each visited entry must support:

| Entry-relative byte offset | Width | Use |
|---|---:|---|
| 4 | 32 bits | Address of the next entry, or zero |
| 8 | 32 bits | Value passed to F-d7be9cfb4000 |

No use of the entry’s first four bytes is shown.

### Preconditions for ordinary, terminating operation

The state, bucket slots, and traversed entries must be readable or writable as required. Bucket calculations must identify valid storage. Entry chains must terminate, and mutations by dependencies must not invalidate addresses that this function continues to use.

For the usual partition interpretation, source and destination slots must be distinct, and clearing the destination must not discard a live chain. These conditions are not checked. Violating them can change the actual graph manipulation substantially; there is no rejection or recovery path.

## Behavior

### 1. Entry accounting and bucket selection

The function performs these state updates in order:

1. Increment the field at byte offset 12.
2. Increment the field at byte offset 40.
3. Read the old progress value from byte offset 20, retain it, and write back that value plus one.

These updates occur even when the selected source bucket is empty or a later growth request returns zero.

Using the retained old progress, the function selects:

- A source head slot at the bucket-storage address plus four times the old progress.
- A destination head slot at the bucket-storage address plus four times the sum of the threshold and old progress.

The two computed slot addresses are retained for the redistribution. They are not recomputed from state fields after dependency calls.

The destination head is written to zero before the source chain is examined. This is an unconditional write. If the destination was nonempty, the function does not first preserve, traverse, or release its former contents.

After clearing the destination, the function reads and retains the partition parameter from byte offset 16. That retained value is used for every classification call during this invocation.

### 2. Redistribution

The function maintains a writable link position, initially the selected source head slot. At each iteration it reads the entry address stored at that position.

A zero value ends redistribution. Otherwise:

- The current entry address is retained.
- The four-byte value at that entry’s offset 8 is read.
- F-d7be9cfb4000 is called with that value and the retained partition parameter.
- A secondary result associated with the call is compared with the retained old progress.

The evidence exposes this secondary result through a machine-result representation rather than a declared return type. It does not establish a conventional, single-value function signature for F-d7be9cfb4000.

#### Secondary result equals old progress

The current entry remains on the source chain.

After the call, the function rereads the entry address at the current link position and advances the link position to that entry’s offset-4 link field. Consequently, if the dependency changed the current link, traversal follows the post-call value rather than necessarily the entry that was passed to the dependency.

#### Secondary result differs from old progress

The retained current entry is moved to the front of the destination chain:

1. Reread the entry address at the current link position.
2. Read that entry’s offset-4 next link.
3. Write that next link into the current link position, unlinking an entry from the source chain.
4. Read the current destination head.
5. Write that head into the retained current entry’s offset-4 link.
6. Write the retained current entry address into the destination head.

The link position does not advance on this branch. The next iteration examines the entry now stored there.

If the dependency does not alter relevant links or storage, this produces a stable retained subsequence in the source bucket and a reversed moved subsequence in the destination bucket. Without that condition, even the entry unlinked from the source need not be the same entry subsequently inserted into the destination.

No entry allocation, release, or payload write is explicitly performed by this function.

### 3. Completion decision

After redistribution terminates, the function reads the threshold and progress fields and compares them as unsigned 32-bit values.

- If threshold is greater than progress, the function returns without requesting growth.
- If threshold is less than or equal to progress, it proceeds to growth.

This is not a signed comparison. High-bit-set field values therefore participate as large unsigned values at this decision point.

These reads occur after classification calls. They must not be replaced in the contract by entry-time snapshots: a dependency may have changed the record.

### 4. Growth request

Before calling F-8b998a07b5e1, the function retains a proposed new parameter equal to the current partition parameter shifted left by one.

It invokes F-8b998a07b5e1 with four arguments:

1. The bucket-storage address read from the record.
2. The partition parameter shifted left by three.
3. Zero.
4. Zero.

The second argument has the arithmetic shape of a byte size for twice as many four-byte slots. Its actual API meaning is not established.

The supplied expression does not establish an ordering among individual argument reads. It does establish that the proposed doubled parameter is computed before the dependency call and remains retained afterward.

#### Zero result

If the dependency returns zero:

1. Progress is written to zero.
2. The counter at byte offset 92 is incremented.
3. The function returns.

The function does not undo the earlier counter increments, destination clearing, or entry movements. It also does not itself restore any state modified by the dependency.

#### Nonzero result

A nonzero result is treated as a writable bucket-storage address.

After the dependency returns, the function rereads the partition parameter and uses it as an unsigned initialization index. While that index is less than the previously retained doubled parameter, the function writes zero to the corresponding four-byte slot in the returned region and increments the index.

Thus, if the dependency leaves the parameter unchanged at a value \(M\), and doubling does not wrap, the initialized slots are exactly \(M\) through \(2M-1\). If the dependency changes the parameter, the lower bound changes; the upper bound remains the retained pre-call doubled value.

After initialization, the function publishes state in this order:

1. Write the current partition parameter into the threshold field.
2. Write the retained doubled parameter into the partition-parameter field.
3. Write the returned address into the bucket-storage field.
4. Write zero into progress.
5. Increment the counter at byte offset 44.
6. Return.

The value copied into the threshold is read after the dependency and after initialization. It is not guaranteed to equal the value used to calculate the growth request.

### Arithmetic boundaries

Four-byte slot scaling, progress increments, counter increments, destination-index addition, and left shifts have no explicit overflow checks.

The unsigned initialization index and unsigned comparison have 32-bit semantics. At the represented 32-bit arithmetic level, left shifts discard high bits; a proposed doubled parameter can therefore become zero or smaller than the post-call initialization index, causing no initialization writes.

Some increments and address expressions are presented using signed integer types. The supplied representation alone does not settle every overflow consequence of an independently reconstructed source-language implementation. A faithful implementation must resolve the intended machine arithmetic rather than silently introducing wider arithmetic, saturation, or new validation.

## Side effects

The function can modify:

- The two entry counters.
- Progress, threshold, partition parameter, and bucket-storage address.
- The selected destination head, including an unconditional initial clear.
- Source-chain head or next-link fields during removals.
- Moved entries’ next-link fields.
- A range of bucket heads in the nonzero growth-result region.
- One growth-outcome counter.

The function invokes external behavior once per visited nonzero entry and, conditionally, once for growth. Those dependencies may have additional effects not described here.

There is no explicit locking, callback isolation, rollback, or atomic publication. Intermediate states are observable to dependencies that can access the same storage. In particular, classification calls occur after counters and progress have changed and after the destination has been cleared.

Ownership is unresolved. The function itself does not explicitly release the old bucket region or entries. Whether F-8b998a07b5e1 moves, frees, preserves, or replaces storage is unknown.

## Dependencies

### F-d7be9cfb4000

**Established interaction:** Receives the current entry’s offset-8 value and the retained partition parameter. A secondary result determines whether the entry remains in the source bucket.

**Inferred intent:** Classify an entry under the current table partition scheme.

**Unknown:** Full signature, primary return value, secondary-result convention, argument interpretation, mutation behavior, ownership effects, and global-state effects. No preservation of state or links may be assumed unconditionally.

### F-8b998a07b5e1

**Established interaction:** Receives a bucket-storage address, a shifted size-like value, and two zero arguments. Zero selects the reset-and-counter path; nonzero is subsequently used as writable storage.

**Inferred intent:** Resize or replace bucket-head storage.

**Unknown:** Allocation API, size units, contents retained, alignment guarantees, old-storage ownership, failure side effects, and mutations to accessible state. The successful initialization path does not establish that the dependency preserved the lower bucket slots.

## Acceptance examples

These examples are conditional on valid, nonaliasing storage, terminating chains, ordinary nonoverflowing arithmetic, and dependencies leaving relevant state and links unchanged except for the stated results.

### Empty bucket without growth

Given old progress 2 and threshold 8, an empty source bucket at index 2 results in:

- Both entry counters incremented.
- Progress set to 3.
- Destination slot 10 cleared.
- No classification calls.
- No growth call.

### Mixed partition

Given old progress 1, threshold 4, and source order A → B → C → D, suppose classification results for A and C equal 1, while those for B and D do not.

After redistribution:

- Source slot 1 contains A → C.
- Destination slot 5 contains D → B.
- Classification occurred in the original traversal order A, B, C, D.
- Progress is 2, so growth is not requested.

### Zero growth result

Given old progress 3, threshold 4, and parameter 8, redistribution completes before the growth request.

The request receives the existing bucket address, 64, zero, and zero. If it returns zero, progress becomes zero and the byte-offset-92 counter increments. Completed entry movements remain in place. The function performs no success-path publication.

### Nonzero growth result

Under the same starting values, suppose growth returns writable storage and leaves the record unchanged.

The function clears returned slots 8–15, then publishes threshold 8, parameter 16, the returned storage address, progress zero, and an incremented byte-offset-44 counter, in that order.

### Growth dependency changes the parameter

Suppose the retained doubled parameter is 16, but the growth dependency changes the record parameter to 12 before returning nonzero.

Initialization clears slots 12–15, not 8–15. The subsequently published threshold is 12, while the published parameter is 16. This follows the observed rereads; assuming dependency preservation would conceal it.
