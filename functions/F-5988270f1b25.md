# F-5988270f1b25

## Purpose

F-5988270f1b25 conditionally updates compact state associated with a current context. It accepts a target, a parameter selector, and a parameter value. Recognized requests produce either one byte write or an ordered pair of byte writes. Rejected requests enter a shared error handler that writes `0x0500` only if the context’s error word is zero when that handler reads it.

The function does not preserve the error word’s value at function entry as an invariant. Dependencies run before some or all rejection paths and have no established preservation guarantees.

The token values and field arrangement suggest a graphics texture-parameter operation. That interpretation is inferred intent, not a prerequisite for this contract.

A null current context causes an immediate return without target or selector validation. There is no explicit return value.

## Behavior

### Acquisition and observable dispatch order

F-7fba0909c452 is called without explicit arguments before any validation.

If it returns null, the function returns. It makes no subsequent resolver or converter call and performs no direct state or error write. This does not exclude effects inside context acquisition itself.

With a nonnull context:

1. A target other than `0x0DE1` enters error recording without calling the resolver.
2. An accepted target causes F-1411dcc31aed to be called with the context.
3. After the resolver returns, the function reads the value constant and retains that value.
4. Selector dispatch follows.

Consequently, every accepted-target request with a nonnull context calls the resolver, including requests later rejected for an unsupported selector or value.

Selector dispatch first compares the selector with the selector constant for equality. Equality selects the converter branch described below. If equality fails, another read of the selector constant determines whether the selector belongs to the signed upper or lower group:

- Upper group: selector greater than or equal to that read of the selector constant.
- Lower group: selector less than that read.

The upper group recognizes `0x2803` and `0x8191`. The lower group recognizes `0x2800` and `0x2801`. Other selectors are rejected.

The literal selectors are therefore not unconditionally recognized. Their behavior depends on the selector constant and dispatch precedence. For example, a selector constant of `0x8191` makes selector `0x8191` select the equality converter branch, not the boolean branch.

Separate global reads need not agree. The available evidence supplies no synchronization or immutability guarantee.

### Selector equal to the selector constant

F-63f3c76ed3e0 receives the complete 32-bit parameter value.

- A signed 32-bit result of exactly `-1` causes rejection.
- Any other result causes its low eight bits to be written at associated-state offset `0x0107`.
- The function then returns.

The sentinel check precedes byte truncation. Result `255` is accepted and writes `0xFF`; result `-1` is rejected even though its low byte is also `0xFF`. No other result-range restriction is visible.

### Upper-group behavior

For selector `0x2803`, the function calls F-63f3c76ed3e0 with the parameter value. Result handling matches the equality branch, except that a successful result is written at associated-state offset `0x0108`.

For selector `0x8191`, the function writes one byte at context offset `0x090A`:

| Parameter value | Written byte |
|---|---:|
| Zero | `0` |
| Any nonzero value, including a negative value | `1` |

This branch does not call the converter. The resolver and retained value-constant read have already occurred.

Any other upper-group selector is rejected.

### Lower-group selector `0x2800`

This branch directly classifies the parameter value:

| Condition, in priority order | Outcome |
|---|---|
| Value equals `0x2600` | Write `1` at associated-state offset `0x0105`. |
| Otherwise, value equals a fresh read of the value constant | Write `2` at offset `0x0105`. |
| Neither condition holds | Reject without a direct classification write. |

The literal comparison takes precedence. If the value constant is `0x2600`, that input writes `1`, not `2`.

The earlier retained snapshot is not the value used by this branch’s global comparison. No converter call occurs.

### Lower-group selector `0x2801`

This branch classifies the input into two bytes.

Before classification, it forms three derived tokens, in order, by adding `0x100`, `0x101`, and `0x102` to separate reads of the value constant. These are called the **first**, **second**, and **third derived tokens** below. They are retained for both components.

The represented calculations are 32-bit integer additions. The evidence does not establish overflow semantics; claims involving these derived tokens require defined additions. Signed ordering is used for comparison with the first derived token.

The first component is selected as follows:

| Position relative to first derived token | Matching condition, in priority order within that position | First byte |
|---|---|---:|
| Equal | Equality itself | `2` |
| Below | Value equals `0x2600` | `1` |
| Below | Otherwise, value equals a fresh read of the value constant | `2` |
| Below | Otherwise, value equals `0x2700` | `1` |
| Above | Value equals the second derived token | `1` |
| Above | Otherwise, value equals the third derived token | `2` |
| Any position | No applicable match | Reject |

The positional conditions matter. Matching a literal or a derived token outside its specified position does not independently establish acceptance. Within the below-first-token region, `0x2600` takes precedence over the fresh global comparison, which takes precedence over `0x2700`. In the above-first-token region, the second derived token takes precedence over the third if they coincide.

If classification fails, neither paired destination is directly written.

If classification succeeds, the first byte is written at associated-state offset `0x0104`. Only after that write does the function select and write the second byte at offset `0x0106`:

| Condition, in priority order | Second byte |
|---|---:|
| Value equals the first derived token | `1` |
| Otherwise, value is below that token and equals `0x2600` or the retained value snapshot | `0` |
| Otherwise, value is below that token and equals `0x2700` | `1` |
| Otherwise, value is above that token and equals the second or third derived token | `2` |
| No applicable condition | `0xFF` |

The second component uses the retained snapshot from immediately after resolver return, not the fresh global read used during first-component classification.

The `0xFF` outcome is a successful-path fallback. It does not invoke error recording or undo the first write. It can matter when different reads of the value constant disagree.

### Error recording

All visible rejection paths share this behavior:

- Read the 32-bit error word at context offset zero.
- If the read yields zero, write `0x0500` there.
- Otherwise, perform no direct error-word write.
- Return.

The decision depends on the word read by the handler, not its value at function entry.

Context acquisition can affect the error word before even an invalid-target rejection. The resolver can affect it before selector or value rejection. The converter can affect it before a converter-sentinel rejection. None has an established preservation guarantee.

Successful branches do not explicitly inspect or clear the error word. No distinct error codes are visible for invalid targets, unsupported selectors, invalid direct classifications, or converter rejection.

## Side effects

Direct successful writes affect the selected byte, except for the paired branch, which writes offset `0x0104` before offset `0x0106`. No atomic pair update, rollback, lock, or memory-ordering primitive is shown.

Rejection performs no direct parameter-field write. It may write the error word according to the handler’s current read. Dependency effects can already have occurred and are not rolled back.

No direct allocation, release, ownership transfer, or lifetime extension is visible. The function uses dependency results as addresses; ownership and lifetime obligations remain unresolved.

Dependency effects must be distinguished from direct effects:

- Context acquisition can have effects even when it returns null.
- The resolver can alter globals or memory before subsequent global reads and dispatch.
- The converter can alter memory before the final byte write or rejection handler.
- No dependency is established to preserve the context, associated state, globals, or their validity.

The context, associated-state region, and globals are not established to be disjoint. A direct byte write might therefore also affect another described location if aliasing exists. Assertions about unchanged logical fields require appropriate non-aliasing and external-preservation assumptions.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless an example states otherwise, assume valid memory, normally returning dependencies, stable globals, no concurrent interference, and non-overlapping state regions. These assumptions do **not** require dependencies to preserve the error word.

1. **Null context.** If F-7fba0909c452 returns null, an invalid target still causes no resolver call, converter call, or direct state/error write. Effects within acquisition remain unspecified.

2. **Invalid target with zero at error recording.** With a nonnull context and target `0`, the resolver is not called. If the error word is zero when the rejection handler reads it, the function writes `0x0500`. A zero error at function entry alone is insufficient: acquisition might change it first.

3. **Nonzero word at error recording.** For any rejection, if the handler reads `0x0502`, it performs no error-word write. Without dependency preservation, this does not imply that a function-entry value of `0x0502` survives until the handler.

4. **Entry value can differ from handler value.** If the error word is zero at entry but acquisition changes it to `0x0502` before returning a nonnull context, an invalid target leaves that handler-observed value intact. Conversely, if acquisition changes an entry value of `0x0502` to zero, an invalid target causes the handler to write `0x0500`.

5. **Converter truncation and sentinel.** On selector-constant equality, converter result `0x1234` writes `0x34` at associated-state offset `0x0107`. Result `255` writes `0xFF`. Result `-1` instead enters error recording without a direct write to that destination; its error outcome depends on the word observed after the converter returns.

6. **Boolean normalization.** If selector `0x8191` reaches its upper-group branch, value `-7` writes `1` at context offset `0x090A`; value zero writes `0`. Both requests have already called the resolver.

7. **Conditional conventional token set.** With a stable selector constant of `0x2802` and value constant of `0x2601`, selector `0x2801` produces:

   | Parameter value | Offset `0x0104` | Offset `0x0106` |
   |---|---:|---:|
   | `0x2600` | `1` | `0` |
   | `0x2601` | `2` | `0` |
   | `0x2700` | `1` | `1` |
   | `0x2701` | `2` | `1` |
   | `0x2702` | `1` | `2` |
   | `0x2703` | `2` | `2` |

   Value `0x2704` is rejected without either paired write.

8. **Dispatch precedence.** With selector constant `0x8191`, selector `0x8191` invokes the converter and targets offset `0x0107`; it does not select boolean normalization.

9. **Success does not directly clear errors.** A successful direct classification performs its byte write without inspecting or writing the error word. If the dependencies also preserve a preexisting error and there is no aliasing or concurrent interference, that error remains unchanged. Without those additional assumptions, preservation from function entry is not guaranteed.
