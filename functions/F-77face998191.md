# F-77face998191

## Purpose

F-77face998191 scans a byte interval, collects addresses of encoded operands, and dispatches operator bytes through a shared descriptor table. A matched descriptor selects conversion into destination storage, cumulative output, or a callback.

The routine initializes selected fields in a caller-supplied context and modifies context and destination memory in place. Processing is not transactional: an error does not undo earlier context writes, destination writes, or dependency effects.

**Established static behavior:** byte classification, operand-address collection, descriptor traversal, conversion dispatch, storage widths, pending-state resets, and return construction.

**Inferred intent:** the input resembles a compact operand-and-operator encoding. No external format identity, operator vocabulary, or destination schema is established.

## Interface

### Arguments and storage model

The routine receives three pointers in a 32-bit address model:

1. A writable context.
2. The input-start address.
3. The exclusive input-end address.

Ordinary valid use requires a readable input interval and sufficient writable context and destination storage. The routine does not validate allocation boundaries, pointer provenance, destination capacity, or alignment.

Relevant context fields are:

| Byte offset | Width | Meaning |
|---|---:|---|
| 0 | 4 bytes | Input-start address, initialized at entry |
| 4 | 4 bytes | Input-end address, initialized at entry |
| 8 | 4 bytes | Duplicate input-start address, initialized at entry |
| 12–395 | 96 four-byte slots | Pending operand addresses |
| 396 | 4 bytes | Operator-address slot when 96 operands are pending |
| 400 | 4 bytes | Address of the next pending slot |
| 404 | 4 bytes | Operator-match configuration word |
| 408 | 4 bytes | Destination-base address |

The configuration word and destination base are not initialized here. They must already be suitable for paths that use them.

This layout describes visible accesses, not necessarily the complete context required by dependencies. Slots containing operand addresses refer to the input buffer; they do not contain copied encodings. The input must remain readable for any dependency that accesses those addresses.

### Return value

The result is 64 bits:

- Upper 32 bits: the original input-start address representation.
- Lower 32 bits: status.

Locally generated statuses are:

- **0:** scanning reached or passed input end without a locally detected error.
- **6:** a visible malformed-input or operand-count condition occurred.

A descriptor-selected callback can return another nonzero 32-bit status, which is propagated unchanged. Its public signedness and meaning are not established.

The upper half is not a final cursor. It remains the original input-start address.

## Behavior

### Initialization and scan position

Before checking input availability, the routine writes, in this order:

1. The pending-slot pointer at offset 400, setting it to context offset 12.
2. The input-start address at offset 0.
3. The input-end address at offset 4.
4. The duplicate input-start address at offset 8.

The local scan position begins at input start. At each iteration boundary, a position at or beyond input end terminates scanning.

The routine does not update context offset 8 as scanning advances. Its local scan position and input-end argument are separate from the context fields. Dependency changes to those fields do not, by themselves, redirect the local scan.

### Operand classification and collection

An unsigned input byte is an operator introducer if it is below 27 or equals 31. Every other byte enters the operand path.

For an operand, the routine checks capacity before appending its address. With an aligned, unmodified pending-slot pointer:

- Operands 1 through 96 are accepted.
- Operand 97 causes status 6.
- The rejected operand's address is not appended.

For an accepted operand, the pending-slot pointer is advanced by four bytes **before** the current input address is written into the previous slot. No operand bytes are copied.

The leading byte controls scan advancement:

| Leading byte | Total movement |
|---|---|
| 28 | Three bytes |
| 29 | Five bytes |
| 30 | Through and including the first subsequent byte containing an F nibble |
| 247–255 | Two bytes |
| Other operand bytes | One byte |

For fixed-length forms, skipped payload bytes are neither read nor checked for availability by this scanner. If advancement passes input end without address wraparound, the next iteration returns status zero rather than reporting truncated payload.

For byte 30, scanning advances to subsequent bytes and reads them individually. A byte terminates this operand when either its high or low nibble equals hexadecimal F. The terminating byte is consumed. Reaching input end before finding such a byte returns status 6. The operand address has already been appended.

### Operator recording and escaped keys

On an operator introducer, the routine first computes the pending operand count from the pending-slot pointer relative to context offset 12. The visible calculation uses 32-bit address arithmetic followed by an arithmetic right shift of two bits.

It then writes the operator's input address into the current pending slot without advancing the pending-slot pointer. With 96 pending operands, this write uses offset 396.

For introducers other than 12, the key is the unsigned byte value.

For byte 12:

- The scan position advances to the following byte.
- If that position is not before input end, status 6 is returned.
- Otherwise, the following byte supplies the low eight bits of a key with bit 8 set.

The recorded operator address remains the address of byte 12. Successful processing advances past both bytes.

### Descriptor lookup and read lifetime

After obtaining a complete operator key, the routine loads the shared table-pointer global. **This load occurs anew for each operator lookup.** A final byte 12 with no following byte fails before that lookup.

The selected table is traversed in 28-byte records:

| Field index | Width | Use |
|---|---:|---|
| 0 | 4 bytes | Action kind; zero terminates lookup |
| 1 | 4 bytes | Match value |
| 2 | 4 bytes | Destination offset |
| 3 | 4 bytes | Low-byte storage selector and cumulative stride |
| 4 | 4 bytes | Callback address |
| 5 | 4 bytes | Cumulative-output maximum count |
| 6 | 4 bytes | Cumulative count-byte destination offset |

For each visited record:

- Action kind zero ends lookup before any match comparison for that record.
- For a nonterminal record, the match comparison uses the operator key bitwise-ORed with the context word at offset 404.
- **The context word at offset 404 is read for each nonterminal comparison.** The routine does not visibly cache one combined match value for the whole traversal.
- A mismatch advances to the next record.
- The first matching nonterminal record is selected.

The OR is not addition or concatenation. Configuration bits can make distinct keys produce the same comparison value.

The loaded table pointer and the selected record address remain local to the current lookup and action. If a dependency replaces the shared table-pointer global, that replacement does **not** redirect the current action to another table. It can affect the next operator lookup. Writes to the currently selected record itself can still affect fields read later during the current action.

A reachable match or zero-kind terminator is required for bounded lookup. Table contents, allocation extent, and ownership are not supplied.

If lookup reaches a zero-kind record without a match, the operator is ignored. Pending operands are discarded by resetting the pending-slot pointer to context offset 12, and scanning continues.

### Matched-action prerequisites

After a match, the routine forms a destination address from the context destination base and descriptor field 2. It then reads the action kind used for dispatch.

Every matched kind except 6 requires a nonzero captured operand count. A zero count returns status 6 without invoking the action or performing the normal pending reset.

Kind 6 permits zero operands.

The destination-address calculation precedes this operand-count rejection. Address calculation alone does not establish a destination-memory read or write.

### Single-result actions

Conversion selection is:

| Action kind | Dependency |
|---|---|
| 1, 4, 5 | F-d6e929d3f234 |
| 2 | F-703a21d21b61 |
| 3 | F-71c99e18b641 |

Each dependency receives the address of the first operand-pointer slot, at context offset 12. The visible result is 32 bits.

After the dependency returns, descriptor field 3 determines the store width:

- Low byte 1: store the low 8 result bits.
- Low byte 2: store the low 16 result bits.
- Any other low byte: store all 32 result bits.

The destination address was formed before the call; it is not recomputed from the destination-base field afterward. The width decision, however, reads the selected descriptor after the call. A converter that changes that record can change the resulting store width.

The return is treated as data, not a conversion status. Extra pending operands are not visibly rejected. The dependency's actual operand consumption remains unknown.

After the store, the routine resets pending state and continues scanning.

### Cumulative-output action

For kind 6, the selected count is the unsigned minimum of the captured pending count and descriptor field 5.

Before conversion, the routine writes the low eight bits of that count to the address formed from the context destination base and descriptor field 6. This count destination is separate from the output address previously formed using field 2.

A 32-bit accumulator starts at zero. For each selected operand slot, in order:

- F-d6e929d3f234 receives that slot's address.
- Its 32-bit result is added to the accumulator, retaining 32 bits.
- The accumulated value is stored at the current output address.
- The output address advances by the unsigned low byte of descriptor field 3.

Store width follows the same low-byte rule as single-result actions. Width decisions and the subsequent stride read use the locally selected record after the conversion call; they are not a pre-call snapshot of field 3. A dependency can therefore alter later storage behavior by modifying that record. Replacing only the shared table-pointer global does not have that effect on the current action.

Consequences:

- Zero selected operands still produce the count-byte write.
- No conversion or cumulative-value store occurs for zero selected operands.
- Stride zero repeatedly targets the same address.
- A selector other than 1 or 2 produces four-byte stores, even if its stride is less than four.
- Stores may overlap.
- The count byte is truncated to eight bits, but iteration uses the full selected count.
- Operands beyond the selected count are discarded at reset.
- Accumulation wraps at 32 bits; narrow stores further truncate to 8 or 16 bits.

### Callback actions

Any matched nonzero kind outside 1 through 6 invokes the callback address in descriptor field 4, passing the context.

- Return zero: reset pending state and continue.
- Return nonzero: return that status immediately, without the normal pending reset or ordinary scan advance.

Callbacks still require at least one pending operand. Their context mutations, global effects, and ownership behavior are not established.

### End of input

Reaching input end with pending operands returns status zero. The routine does not flush, convert, or reject those operands. Their addresses remain recorded, and the pending-slot pointer remains advanced.

## Side effects

Visible effects include entry initialization, operand-address appends, operator-address writes, pending resets, destination stores, and dependency calls.

Errors preserve earlier effects. An unterminated byte-30 operand leaves its address appended. A missing escaped-key byte leaves the introducer address recorded.

No allocation, explicit deallocation, or input-buffer write is visible in this routine. This does not constrain dependencies.

Input, context, destination, and table storage are not checked for overlap. Aliasing can cause earlier writes to alter later reads, including pending state, descriptor fields, configuration, or input bytes. The ordinary behavior descriptions assume suitable nonoverlapping storage unless stated otherwise.

The shared table-pointer global is reloaded between operator lookups, not during an action. Descriptor contents are not copied wholesale. Dependencies must not be assumed to preserve globals, context configuration, selected-record contents, or destination memory.

No rollback, ownership transfer, or release obligation is established.

## Acceptance examples

These are static, conditional expectations, not executed tests. Unless overridden, they require valid nonoverlapping storage, ordinary aligned pending state, no address wraparound, and a reachable table match or terminator.

1. **Empty interval.** Equal start and end addresses produce entry initialization and status zero without an input-byte read.

2. **Unused operand.** One ordinary single-byte operand followed by input end leaves its address pending and returns zero without conversion.

3. **Capacity boundary.** Ninety-six ordinary operands ending at input end return zero. A ninety-seventh operand instead causes status 6 before its address is appended.

4. **Operator after 96 operands.** The operator address is written at context offset 396. That write does not itself trigger the operand-capacity error.

5. **Missing escaped key.** A final byte 12 is recorded as an operator, then causes status 6. No table-pointer load for that operator is reached.

6. **Fixed-length truncation.** An interval containing only byte 28 causes its address to be appended and the scan position to advance three bytes. Without address wraparound, scanning then returns zero.

7. **Byte-30 termination.** Byte 30 followed by a byte with either nibble F consumes both bytes. Without a later matched operator, no converter is called.

8. **Byte-30 failure.** Byte 30 followed only by bytes lacking F nibbles returns status 6 at input end, retaining the appended operand address.

9. **Unmatched operator.** Pending operands followed by an operator with no matching record before the terminator are discarded by pending reset; scanning continues.

10. **Missing operand.** A matching kind-2 descriptor with zero pending operands causes status 6 without calling F-703a21d21b61.

11. **Narrow conversion result.** Given a pending operand and a matching kind-1 descriptor, require field 3 to remain selector 1 throughout the post-conversion width decision. Require the converter to return 0x12345678 without invalidating the established destination address, changing relevant selected-record fields, or making writes that interfere with the stated destination result. With the destination disjoint from subsequent context writes, the action stores exactly the byte 0x78 there.

12. **Cumulative values.** Given three pending operands, require a kind-6 descriptor whose maximum remains two and whose field 3 remains 2 throughout both conversions, width decisions, and stride reads. Require valid, disjoint count and output destinations, stable relevant descriptor fields, and converters returning 3 then 5 without writes that invalidate or alter these destination results or remaining operand slots. The count byte becomes 2; two-byte stores at the initial output address and two bytes later contain 3 and 8. Reset discards the third operand.

13. **Callback termination.** With at least one pending operand, a matched callback returning 9 produces low return word 9 and the original input-start address in the upper word. No post-callback pending reset occurs.

14. **Table replacement lifetime.** If a converter replaces only the shared table-pointer global, leaving the current record and other relevant state intact, the current action continues using its original selected record. A later operator lookup loads the replacement pointer.

15. **Per-record configuration read.** If the context configuration word has different values at two successive nonterminal comparisons, each comparison uses the value read for that comparison. A single lookup-wide cached OR result would not satisfy this rule. The source of such intervening mutation and any concurrency guarantees remain unspecified.

Unknown dependency effects do not make the visible read timing unknown: table selection is per operator, configuration is read per nonterminal comparison, and selected-record width and stride reads occur after conversion where used.
