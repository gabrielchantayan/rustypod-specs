# F-e56e350a7e04

## Purpose

F-e56e350a7e04 conditionally dispatches an event associated with an object. It has two ordered stages:

1. Under a particular object-flag pattern, offer selected event types to one of two preliminary handlers.
2. If the object’s main enable byte is nonzero and no preliminary handler supplied a nonzero result, match another event type against primary or secondary criteria and invoke an indirect object operation.

The enable check occurs **after** preliminary dispatch. An object whose enable byte is zero can therefore still cause preliminary dependency calls. Conversely, a nonzero preliminary result is discarded if the subsequent enable-byte read yields zero.

“Object,” “event,” “enable,” “primary,” and “secondary” are descriptive labels for the observed structure and decisions. They do not establish application-level meanings.

## Interface

### Inputs and access requirements

The function receives two address-bearing arguments:

- **Object address:** identifies storage containing the fields and dispatch-table reference described below. Fields directly accessed on the selected path must be readable. The function performs no direct object writes.
- **Event address:** identifies a record whose fields are read conditionally. Only fields actually accessed on the selected path require readable storage for this function’s direct accesses.

There is no unconditional requirement that the object be writable. A path that invokes no dependencies requires only readable storage for the fields it accesses. Any additional readability, writability, lifetime, or other requirements imposed by invoked dependencies are **documented_only** unknowns.

The supplied representation uses 32-bit integers and byte-addressed offsets. Its dispatch-table address is carried in a represented 32-bit field. Exact platform ABI, native pointer representation, byte order, and calling conventions are not independently established.

### Object fields

| `0x40` | 32 bits | Primary first comparison value |

The function can read the event type at several decision points. It does not establish a single immutable event-type snapshot for the invocation.

### Global inputs

Two distinct 32-bit global values participate in later matching:

- **Primary alternate value:** accepted as an alternative to the object’s primary first comparison value.
- **Secondary expected value:** required by the secondary first-value comparison.

Their meanings, initial values, validity rules, ownership, and relationship are not established.

### Return value

The result is a represented 32-bit integer:

- `0` if the main enable byte is zero, later matching fails, or the event is otherwise unhandled.
- The exact nonzero preliminary-handler result if the subsequent enable-byte read is nonzero.
- `1` after a successful later match invokes either indirect object operation and that operation returns normally.

A negative preliminary result is nonzero and is propagated under the same rule as a positive result. Neither indirect operation’s return value determines the result of this function.

### Preconditions and invalid inputs

Every address actually accessed must be valid and readable, with alignment suitable for the target ABI. Selected indirect entries must designate callable operations with compatible signatures. Invoked dependencies may impose additional requirements that are not established here.

There is no visible null check, record-length check, dispatch-table validation, or memory-access recovery. Invalid inputs are not specified to produce a controlled zero return.

Requirements are path-dependent. For example, when preliminary dispatch is excluded by the flags and the main enable byte is zero, the function directly reads neither the event nor the dispatch table.

## Behavior

### Preliminary dispatch

The preliminary result starts at zero.

The function first reads the 32-bit flags at object offset `0x48`. Preliminary dispatch is eligible exactly when masking that value with `0x1800` produces `0x0800`. Thus:

- Bit `0x0800` must be set.
- Bit `0x1000` must be clear.
- Bits outside that mask do not affect eligibility.

If this condition fails, preliminary processing does not read the event type and does not call a preliminary dependency.

If the condition succeeds, the function reads the event type and compares it with `0x0D`:

- On equality, F-682adfd5a561 receives the event address and `0x0A00`.
- Its 32-bit result is passed, together with the object address, to F-a442f4c617e9.
- The latter dependency’s integer result becomes the preliminary result.

If that first event-type comparison fails, the event type is read again and compared with `0x15`:

- On equality, F-682adfd5a561 receives the event address and `0x3500`.
- Its 32-bit result is passed, together with the object address, to F-c655d21a6b1a.
- That dependency’s integer result becomes the preliminary result.

If neither comparison succeeds, the preliminary result remains zero.

Only one preliminary-handler route can execute in an invocation. The result from F-682adfd5a561 is forwarded without a local validity or zero/nonzero check; a zero result does not suppress the selected handler.

### Enable gate and result precedence

After preliminary processing completes, the function reads the byte at object offset `0x122`.

1. If it is zero, the function returns `0`.
2. Otherwise, if the preliminary result is nonzero, the function returns that exact result.
3. Otherwise, the function proceeds to later matching.

This ordering permits preliminary dependencies to affect the enable decision. No assumption is made that those dependencies preserve the object, event, or globals.

A nonzero preliminary result does not override a zero enable byte. Conversely, with a nonzero enable byte, a nonzero preliminary result prevents all later event-type and comparison-field reads.

### Later event selection

The function next reads the event type again. Only `0x13` enters later matching; every other value returns `0`.

This read occurs after any preliminary calls. A dependency can therefore affect which type is observed, subject to its unknown behavior. Earlier observations do not freeze the event type for later decisions.

### Primary matching

For event type `0x13`, the function reads the event’s second comparison value at `0x0C` and retains it for possible secondary matching. It compares that value with the object’s primary second comparison value at `0x44`.

If the second values differ, primary matching fails without reading the primary first comparison value or primary alternate global for this route.

If the second values match:

1. The function reads the event’s first comparison value at `0x08`.
2. It reads the object’s primary first comparison value at `0x40`.
3. If those values differ, it reads the primary alternate global.
4. Primary matching accepts if the event’s first value equals the object’s primary first value or, when consulted, the primary alternate global.

The primary alternate global is not read when the direct first-value comparison already succeeds.

On primary acceptance, the function reads the object’s dispatch-table address, obtains the operation at byte offset `0xD4`, and invokes it with the object address. After that operation returns normally, the function returns `1`.

Primary acceptance prevents secondary matching. There is no subsequent enable-byte recheck.

### Secondary matching

If primary matching does not accept, the function reads the 32-bit object field at `0x9C`.

If that field is zero, it returns `0` without reading the secondary second comparison value, consulting the secondary expected global, or calling the secondary dependencies.

If the field is nonzero, the function compares the retained event second value with the object’s secondary second comparison value at `0x98`.

A mismatch returns `0`. In that case, the secondary path does not read the event’s first comparison value or the secondary expected global.

On a second-value match:

1. The function reads the event’s first comparison value at `0x08`.
2. It reads the secondary expected global.
3. It compares those values for equality.

This event-field read is separate from any first-value read performed during unsuccessful primary matching. The second event value, by contrast, is retained rather than reread for the secondary comparison.

If the first values differ, the function returns `0`.

If they match, the function calls F-5710a8628cba without visible arguments and retains its byte-width result. **After that call returns**, it obtains the object’s dispatch-table address and the operation at byte offset `0xA0`. It invokes that operation with the object address and the retained byte value, then returns `1` after normal completion.

The dispatch target is not captured before F-5710a8628cba. If that dependency changes the dispatch-table reference, the subsequent lookup uses the reference then observed. No enable-byte or match-condition recheck follows that dependency.

### Widths and arithmetic

Flags and comparison fields are 32-bit quantities. The enable field and the retained result from F-5710a8628cba are byte-width quantities.

Matching uses equality and zero/nonzero decisions, not signed ordering. No addition, subtraction, scaling, or range arithmetic is applied to the comparison values. The visible arithmetic consists of flag masking and address-offset calculations.

The represented 32-bit field widths do not independently establish portable pointer arithmetic or behavior on another ABI.

## Acceptance examples

These are conditional consequences of static inspection, not executed tests. Unless stated otherwise, assume valid accessed storage, normally returning dependencies, and no unmentioned mutation.

1. **Readable storage without a writable-object requirement.**  
   The flags exclude preliminary dispatch, and the enable byte is zero. Only the flags and enable byte need to be readable for the function’s direct accesses. It returns `0`, reads no event fields, and invokes no dependency. This path does not require writable object storage.

2. **Preliminary processing before a disabled main path.**  
   The masked flags equal `0x0800`, the preliminary event type is `0x0D`, and the enable byte is zero when subsequently read. F-682adfd5a561 receives `0x0A00`, and F-a442f4c617e9 receives its result. The function returns `0` even if the handler returned a nonzero value. Dependency-specific storage requirements remain unknown.

3. **Exact negative-result propagation.**  
   Preliminary dispatch selects type `0x15`; F-c655d21a6b1a returns `-7`; the subsequent enable-byte read is nonzero. The function returns `-7` without later matching.

4. **Mask exclusion does not disable later matching.**  
   The flags yield `0x1800` under the mask. Preliminary dispatch is skipped. A nonzero enable byte and later type `0x13` still permit primary and secondary matching.

5. **Primary direct acceptance.**  
   The later event type is `0x13`, and both event values equal their primary object values. The primary alternate global is not read. Entry `0xD4` is invoked, and the function returns `1`.

6. **Primary alternate acceptance.**  
   The primary second values match. The event’s first value differs from the object’s primary first value but equals the primary alternate global. Entry `0xD4` is invoked; secondary matching does not occur.

7. **Secondary acceptance after primary failure.**  
   Primary matching fails, `0x9C` is nonzero, the retained event second value matches `0x98`, and the secondary first-value comparison succeeds. F-5710a8628cba runs, its byte result is forwarded to entry `0xA0`, and the function returns `1`.

8. **Secondary short-circuit rejection.**  
   After primary failure, a zero field at `0x9C` prevents further secondary reads. Alternatively, a nonzero field followed by a second-value mismatch prevents the secondary first-value read and global read. Both cases return `0`.

9. **Preliminary mutation affects later decisions.**  
   A preliminary handler returns zero, changes the event type to `0x13`, and leaves the enable byte nonzero. The later type read permits matching. If instead the enable byte is cleared, the function returns `0` before that later type read.

10. **Secondary target obtained after the dependency.**  
    Secondary matching succeeds, and F-5710a8628cba changes the dispatch-table reference. The indirect lookup uses the reference observed after that call, not a previously cached target.
