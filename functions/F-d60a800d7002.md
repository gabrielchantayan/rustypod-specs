# F-d60a800d7002

## Purpose

F-d60a800d7002 repeatedly removes records from a shared linked structure, changes their state, obtains a context through each record, and optionally copies one payload element into shared storage. It returns the 32-bit value zero when it encounters an empty shared head and its terminal dependencies return normally.

This is a source-facing contract derived from static evidence only. The apparent role resembles queue draining with indexed payload storage, but queue ownership, scheduling semantics, and circular-buffer intent are not established.

The function depends on ambient machine state in addition to its three explicit arguments. A caller cannot determine its behavior from those arguments alone.

| Record offset | Width | Use |
|---|---:|---|
| `0x00` | 32-bit pointer | Next record; may later be overwritten for insertion into another chain. |
| `0x04` | 32 bits | Updated when this record becomes the successor head. |

The intermediate object contains a context pointer at offset `0x04`.

The selected context is accessed at:

- Offset `0x04`: receives the literal `0x08001FCC`.
- Offset `0x10`: contains a 32-bit value passed to F-2489d48d501c, or a pointer dereferenced for a payload copy, depending on the path.

## Behavior

### Initial dependency call and re-entry

On entry, the function initializes an internal address-arithmetic seed to `0x08001FBC`.

Before examining the list, it invokes F-2489d48d501c with two observed arguments:

1. The shared storage-base value plus the product of the ambient element width and the seed.
2. The 32-bit value read from the current context at offset `0x10`.

The first argument is an arithmetic result; it is not necessarily the storage-base value or a validated destination address. Even with element width zero, the dependency call and the context read still occur.

The function does not directly use this dependency’s return value. Its possible effects on memory and ambient state remain relevant and are not constrained by the visible caller.

For widths other than 0, 1, 2, and 4, execution can return to this call after processing a record. On that re-entry, the seed is the shared index captured after that record’s index update, and the context is the context selected from that record.

For widths 0, 1, 2, and 4, the visible control flow continues examining records without revisiting this dependency call.

### Bookkeeping before each head examination

Each examination begins with these visible operations:

1. Read the high-water field.
2. Increment the iteration counter.
3. Compare the high-water field and shared count as unsigned 32-bit values. If the former is smaller, assign the count to the high-water field.
4. If the shared count equals one and the gate is nonzero, call F-6ad030b1b8cc.
5. Read the shared head.

This bookkeeping also occurs on the iteration that discovers an empty head. Consequently, the iteration counter is not simply a count of removed records.

The high-water update precedes the count increment associated with a record removal. There is no second high-water update immediately after that increment; the next head examination provides another opportunity.

The conditional dependency runs before the head is selected. No preservation of shared state across that call is established.

### Empty-head termination

If the head read is null, the function performs a conditional notification followed by an unconditional terminal call:

- Read the primary structure’s 32-bit field at offset `0x08`.
- If it is nonzero, invoke the notification dependency with that value.
- If it is zero, read the secondary structure’s fields at offsets `0x08` and `0x0C`.
  - If those values differ, invoke the notification dependency with the value from offset `0x08`.
  - If they are equal, read the primary structure’s byte at offset `0x01`.
    - A zero byte suppresses notification.
    - A nonzero byte causes notification with that byte zero-extended to 32 bits.
- Invoke the terminal dependency regardless of whether notification occurred.
- Return zero if execution returns from those calls.

The secondary structure is not read on the nonzero-primary-field branch. The primary byte is read only when the primary 32-bit field is zero and the two secondary fields are equal.

Neither terminal dependency has a supplied opaque function ID. Their implementations, ownership effects, and return behavior are unknown.

### Removing a non-null head

For a non-null head, the function retains that record as the record being processed and reads its next pointer.

If the next pointer is non-null:

1. Assign it to the shared head.
2. Write the literal `0x08001FD0` into the successor record at offset `0x04`.
3. Reload the shared head and assign the reloaded value back to the shared head.

If the next pointer is null, assign null to the shared head.

The final shared-head assignment is visible even when the successor branch has already assigned it. The supplied representation does not justify removing this observable write from the contract.

Next, the function reads the removed record’s state word at offset `0x1C`, clears bit `0x80`, and writes the result back. All other bits are preserved.

If the resulting entire 32-bit word is zero, it also:

1. Reads the primary structure’s field at offset `0x08`.
2. Stores that value into the removed record’s offset-`0x00` field.
3. Stores the removed record’s address into the primary structure at offset `0x08`.

This is an observed chain insertion. It is not evidence that the record has been freed, transferred to a particular allocator, or made safe for reuse.

### Per-record dependency and context update

After the state-word handling:

- If the removed record’s offset-`0x08` field is nonzero, invoke F-f46257aeeddc.
- After that call returns, write the literal `0x08001FCC` into the same record field.
- If the field was zero, neither this call nor this write occurs.

No explicit arguments to F-f46257aeeddc are shown. An implicit calling convention or dependency on ambient state is not ruled out.

The function then obtains a context by reading the pointer at record offset `0x10`, followed by the context pointer at that object’s offset `0x04`. It writes `0x08001FCC` into the selected context at offset `0x04`.

These accesses occur after F-f46257aeeddc. The contract therefore does not assume that the intermediate pointer or context was captured before that call.

### Count, index, and payload handling

For each processed record, the function then:

1. Increments the unsigned shared count.
2. Increments the shared index.
3. Compares the updated index with the ambient index limit.
4. If they are equal, replaces the index with the literal `0x08001FCC`.

The replacement is not zero and is not the current count. The equality comparison does not implement a general greater-than-or-equal bounds check.

Payload behavior depends on the element width:

| Width | Behavior after index update |
|---:|---|
| 0 | No payload read or payload write; immediately begin another head examination. |
| 1 | Read the payload pointer from context offset `0x10`, copy one byte to storage base plus index, then continue examining records. |
| 2 | Read that pointer, copy one 16-bit value to storage base plus twice the index, then continue. |
| 4 | Read that pointer, copy one 32-bit value to storage base plus four times the index, then continue. |
| Any other value | No direct payload copy; capture the index as the next arithmetic seed and revisit F-2489d48d501c. |

Thus the destination uses the **updated, possibly replaced index**, not the index from before record processing.

The copy widths are established. Byte order, permitted alignment, memory-mapped behavior, and overlapping-access guarantees are not.

## Side effects

The function can modify every shared field listed above except the storage-base and gate fields through its own visible assignments. Dependencies may modify those fields too; preservation is not established.

Other direct writes include:

- Successor-record back-link information.
- The removed record’s state word.
- The removed record’s next pointer on the zero-state path.
- The primary structure’s offset-`0x08` field on that same path.
- The removed record’s offset-`0x08` field after F-f46257aeeddc.
- The selected context’s offset-`0x04` field.
- One payload destination element for widths 1, 2, or 4.

No explicit allocation or deallocation is visible. No ownership or release guarantee can be inferred for a dependency.

These effects are incremental. No rollback path is visible if a dependency does not return or a memory access fails. No synchronization mechanism is established.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, dependencies return normally without relevant state changes, accessed memory is valid, and affected objects do not alias.

1. **Empty head without notification.**  
   Given a null head, primary offset `0x08` equal to zero, equal secondary comparison fields, and primary byte `0x01` equal to zero: the initial F-2489d48d501c call still occurs; bookkeeping runs; notification is skipped; the terminal dependency runs; the function returns zero. No record is processed.

2. **Notification argument precedence.**  
   Given an empty head and a nonzero primary offset-`0x08` field, that field supplies the notification argument. The secondary comparison fields and primary byte are not read on this path.

3. **Notification with a zero argument.**  
   Given an empty head, zero primary offset `0x08`, secondary offset `0x08` equal to zero, and secondary offset `0x0C` nonzero: notification occurs with argument zero. A zero notification argument does not imply notification suppression.

4. **Clearing the state bit.**  
   A removed record with state word `0x00000080` becomes zero and is inserted into the primary chain. A record with state word `0x00000081` becomes `0x00000001` and is not inserted by this condition.

5. **Two-byte payload destination.**  
   With width two, index initially five, and index limit other than six, the record’s payload is copied as one 16-bit value to storage base plus twelve bytes. The copy uses index six.

6. **Exact index-limit match.**  
   If an index increment reaches the limit, the index becomes `0x08001FCC` before payload addressing. An implementation that substitutes zero would not match this evidence.

7. **Zero width still processes records.**  
   Width zero suppresses payload copying, not record removal, state updates, context access, or count/index increments. The initial context-offset-`0x10` read also remains required.

8. **Unsupported width.**  
   With width three and a nonempty head, one record is processed without a direct payload copy. Execution revisits F-2489d48d501c using the updated index as the arithmetic seed and the newly selected context.
