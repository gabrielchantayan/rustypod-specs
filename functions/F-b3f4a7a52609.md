# F-b3f4a7a52609

## Purpose

The established behavior is a three-stage memory lookup followed by an indirect control transfer. The supplied representation shows no validation, explicit memory write, allocation, release, or result transformation around that transfer.

An object-oriented dispatch mechanism is a plausible interpretation of the layout, but it is not established. The contract therefore describes address relationships without assigning class, ownership, or application semantics to the referenced structures.

The recovered representation explicitly warns that the indirect control transfer was not fully resolved and was treated as a call. Consequently, the lookup behavior has stronger static support than the apparent call-and-return behavior.

## Behavior

### Address relationships

The first lookup reads a pointer from the location at input base plus 236 bytes. No read of the input base itself is shown before this offset lookup.

The second lookup reads an integer-sized value from the address supplied by that first pointer. There is no intervening offset at this stage. The recovered representation then uses that integer-sized value as the base for the final lookup.

The third lookup reads a callable address from the location 368 bytes beyond the second lookup’s value. It is this loaded callable address—not the slot address and not either earlier loaded value—that supplies the indirect destination.

Normal dispatch requires these lookups to resolve in dependency order:

1. The input-relative pointer becomes available.
2. That pointer supplies the location of the intermediate integer-sized value.
3. That value supplies the base for the callable-address lookup.
4. The callable-address value supplies the indirect destination.

This is the logical order supported by the representation. It does not establish processor-level ordering guarantees, synchronization semantics, atomicity, or behavior under concurrent modification.
