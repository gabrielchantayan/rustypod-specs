# F-00475122f531

## Purpose

F-00475122f531 creates or updates a primary resource associated with a caller-supplied object. It then either clears an existing secondary-resource association through a provider-directed operation, or prepares temporary data and creates or updates the secondary resource.

Primary processing uses the full unsigned 32-bit size in both dimension positions. Secondary preparation uses the low 16 bits of that size to describe a square input and an output with half that width as its height, rounded down. Secondary creation and secondary update do not use identical width sources.

The apparent purpose is to maintain a primary square representation and an optional transformed representation. Resource types, data format, and transformation semantics are not established. “Creation,” “update,” “allocation,” and “release” describe roles inferred from the visible data flow, not verified dependency contracts.

This specification separates directly established behavior from inferred intent and unresolved dependency behavior. No runtime tests have been performed.

## Interface

The function accepts four arguments and has no explicit return value.

| Argument | Width and interpretation | Established use |
|---|---|---|
| Object address | 32-bit address-like value | Locates resource fields at byte offsets `0x54` and `0x94`. |
| Input value | Opaque 32-bit value | Passed to primary processing and placed in the secondary input descriptor. |
| Size | Unsigned 32-bit integer | Used without truncation for primary dimensions and secondary creation width; narrowed for secondary descriptors. |
| Secondary selector | 32-bit integer | Zero disables secondary processing; every nonzero value selects secondary preparation and creation or update. |

The following object fields are directly accessed:

| Offset | Width | Observed significance |
|---|---|---|
| `0x54` | 32 bits | Zero selects primary creation; nonzero selects primary update. Creation stores its result here. |
| `0x94` | 32 bits | Zero selects secondary creation when enabled; nonzero selects update or the disabling operation. |

The resource fields contain opaque values. This function does not directly dereference those values.

### Preconditions

The object address must permit the field reads and writes required by the selected paths. Relevant object storage must remain accessible across intervening dependency calls.

A global provider-reference location must be readable at entry, because the function captures its address-like contents unconditionally. Further requirements depend on the path:

- **Primary creation:** the global provider reference is read again. The address obtained from this separate read must support a 32-bit provider-value read.
- **Secondary creation or disabling an existing secondary resource:** the address captured at entry must support a 32-bit provider-value read when that later operation occurs.
- **Update-only paths:** no provider-value dereference is directly required by the shown update calls, although the entry capture still occurs.

The entry-captured address and the address obtained for primary creation are not guaranteed to be equal. Readability of one does not establish readability of the other.

The input value must satisfy the invoked dependencies’ requirements. Whether it denotes memory, and any associated extent, alignment, mutability, or lifetime requirements, are unknown.

No visible validation protects against invalid object storage, invalid provider references, unsuitable input, unsupported sizes, or allocation failure.

## Behavior

### Provider-reference capture and subsequent reads

At entry, the function reads the global provider reference and retains the resulting address-like value. This precedes the primary-field condition.

There are two distinct provider-access routes:

1. **Primary creation** separately rereads the global provider reference and reads the provider value through that newly obtained address.
2. **Secondary creation and secondary disabling** read the provider value through the address captured at entry.

Capturing the address does not capture the provider value stored there. Consequently:

- A change to the global reference between the entry capture and the primary-creation read can cause primary creation to use a different provider location.
- A later replacement of the global reference does not redirect the explicit secondary provider reads.
- A change to the value stored at the entry-captured address can affect a later secondary provider argument.
- The evidence does not establish that captured storage remains valid across calls.

No synchronization or equality guarantee for these separate global reads is shown.

### Primary processing

The function reads the 32-bit field at object offset `0x54` to choose creation or update.

If the condition observes zero, F-a29c8be2c8c1 is invoked with these logical arguments:

1. Provider value obtained through a fresh read of the global provider reference.
2. Original 32-bit input value.
3. Zero.
4. Original unsigned 32-bit size.
5. Original unsigned 32-bit size.

After normal return, the returned 32-bit value is written to offset `0x54`. No success check precedes the store; zero is stored if zero is returned.

If the condition observes nonzero, the field is read again for the resource argument to F-93dc585d2452. That dependency receives:

1. The primary-resource value read for the call.
2. Original input value.
3. Full 32-bit size.
4. Full 32-bit size.

The supplied representation contains separate field accesses for the condition and update argument. Without a stability guarantee, their values must not be assumed identical.

No result from primary update is consumed, and no explicit primary-field write follows that call.

Primary processing always precedes secondary processing. A zero secondary selector does not bypass the primary operation.

### Secondary disabled

When the selector is zero, the function reads the field at offset `0x94`.

If it observes zero, no secondary dependency is called and no secondary-field write occurs.

If it observes nonzero:

1. The function reads the provider value through the entry-captured address.
2. It calls F-9ad23bf5b97e with that provider value as its sole explicit argument.
3. After normal return, it writes zero to offset `0x94`.

The old secondary-resource value controls the branch but is not passed explicitly to F-9ad23bf5b97e. The evidence therefore establishes a provider-directed operation followed by a field clear, not destruction of a particular resource handle.

The clear occurs after the call. It can overwrite a secondary-field value changed indirectly during that call.

### Secondary preparation

When the selector is nonzero, preparation occurs after primary processing and before the secondary-field decision.

For unsigned 32-bit size \(S\), define:

- \(W = S \bmod 65{,}536\).
- \(H = \lfloor W/2 \rfloor\).
- \(B = 2WH\).

Here, \(W\) is between 0 and 65,535, and \(H\) is between 0 and 32,767. The maximum allocation-size value is:

\[
B_{\max}=65{,}535 \times 32{,}767 \times 2
=4{,}294{,}770{,}690.
\]

Both the intermediate product \(WH\) and the final product fit in unsigned 32-bit arithmetic. The final result can exceed the positive signed 32-bit range. Whether F-d33f6d597e5d accepts that range is unknown.

Two local descriptors have the following supplied layout:

| Byte offset | Width | Output descriptor | Input descriptor |
|---|---|---|---|
| `0` | 32 bits | Result returned by F-d33f6d597e5d | Original input value |
| `4` | 16 bits | \(W\) | \(W\) |
| `6` | 16 bits | \(H\) | \(W\) |

Each descriptor occupies eight bytes in the supplied layout. Byte order and any broader descriptor protocol are not established.

The dimension fields and input leading value are initialized before allocation. F-d33f6d597e5d receives \(B\), and its 32-bit result initializes the output descriptor’s leading field.

F-6ee71f0e99b3 is then called with:

1. Address of the output descriptor.
2. Address of the input descriptor.

These are addresses of local descriptor storage, not copies of the descriptor fields. No return value is consumed. No check prevents transformation when the allocation result is zero or another failure sentinel.

Because the descriptors are passed by address, subsequent behavior must account for possible mutation. Preservation of their contents is not established.

### Secondary creation or update

Only after F-6ee71f0e99b3 returns does the function inspect offset `0x94`.

If the condition observes zero, F-a29c8be2c8c1 receives:

1. Provider value read through the entry-captured address.
2. Output descriptor’s current leading 32-bit value.
3. Zero.
4. Original full 32-bit size.
5. Output descriptor’s current 16-bit height field.

The returned 32-bit value is stored at offset `0x94` without checking success.

If the condition observes nonzero, the secondary field is read again for F-93dc585d2452, which receives:

1. Secondary-resource value read for the call.
2. Output descriptor’s current leading 32-bit value.
3. Output descriptor’s current 16-bit width field.
4. Output descriptor’s current 16-bit height field.

No result is consumed and no explicit secondary-field write follows update. As with primary update, the branch read and argument read are distinct in the supplied representation; equality requires a stability assumption.

The width asymmetry is part of the established behavior:

- Secondary creation uses the original full-width size.
- Secondary update uses the current narrowed descriptor width.

Creation ignores the output descriptor’s width field. Transformation can affect update width by changing that field, but cannot thereby change the original size supplied as creation width.

The exact dependency parameter types and argument-extension conventions for 16-bit fields remain unresolved.

### Temporary release

After secondary creation or update returns normally, F-5e3309c9d083 receives the output descriptor’s current leading 32-bit value.

This call occurs after either enabled secondary branch, including creation returning zero. The function does not preserve a separate original allocation value for release. If the descriptor’s leading value changes, the release argument follows its current contents rather than necessarily identifying the original allocation.

## Side effects

### Direct writes

The function explicitly performs these object writes:

- Primary creation result to offset `0x54`.
- Zero to offset `0x94` after a secondary-disabling call returns normally.
- Secondary creation result to offset `0x94`.

It also initializes local descriptor storage. It does not explicitly replace resource fields after update calls or write the global provider reference.

These statements concern direct operations only. Dependency calls may have additional effects on object storage, provider state, descriptors, or other memory.

### Observable ordering

The established ordering is:

1. Capture the global provider reference.
2. Read the primary field for branch selection.
3. On primary creation, separately reread the global reference, read the provider through that address, call creation, and store its result.
4. Otherwise, read the primary field for the update argument and perform update.
5. Enter the selected secondary path.
6. On the disabled path, inspect the secondary field and, if nonzero, read through the entry-captured provider address, call the disabling dependency, and clear the field.
7. On the enabled path, prepare descriptors, allocate, and transform before inspecting the secondary field.
8. Create or update the secondary resource.
9. Call the release-like dependency with the current output leading value.

A primary dependency can therefore affect the secondary state later observed. Allocation and transformation also precede the enabled secondary decision. A primary dependency that merely replaces the global provider reference does not redirect subsequent explicit secondary provider reads; changing the contents or validity of the captured location can matter.

The evidence does not establish a total order among independent argument reads within a single call expression. Nor does it supply concurrency, atomicity, or reentrancy guarantees.

### Ownership and lifetime

The original input value is not directly released.

Temporary data follows an allocation-like, transformation, resource-consumption, release-like sequence. This suggests temporary caller-managed storage, but does not establish ownership transfer or dependency guarantees.

In particular, the evidence does not establish that:

- Transformation preserves the output leading value or dimensions.
- Resource processing copies data before returning.
- Dependencies refrain from retaining descriptor addresses or data values.
- Release accepts zero, a substituted value, or the allocator’s failure sentinel.
- The disabling dependency releases the resource represented by the field subsequently cleared.

Descriptor storage is local to this invocation. Any retention beyond its lifetime requires an external contract not supplied here.

### Errors and interrupted execution

There is no explicit error result, diagnostic, retry, rollback, or failure branch.

Normally returned creation values are stored regardless of their meaning. Normally returned allocation values proceed to transformation without validation.

If a dependency does not return normally, later stores, calls, and temporary release are not guaranteed. No visible cleanup mechanism compensates for such interruption.

## Acceptance examples

These are conditional static contract examples, not executed tests. Unless an example states otherwise, assume normal dependency returns, stable relevant object and provider state, and unchanged descriptor fields after transformation.

### Both resources absent, secondary enabled, size 5

Primary creation receives dimensions `5 × 5`, using the provider obtained through the separately reread global reference. Its result is stored.

Allocation receives `20`, since \(W=5\) and \(H=2\). Transformation receives descriptors initially describing output `5 × 2` and input `5 × 5`.

Secondary creation uses the provider read through the entry-captured address and receives dimensions `5 × 2`. Its result is stored, then the temporary leading value is passed to release.

### Both resources present, secondary enabled, size 5

Primary update precedes allocation and transformation. Secondary update follows transformation and receives dimensions `5 × 2`. Neither resource field is explicitly replaced. Temporary release follows.

### Entry capture and primary reread differ

Suppose the entry capture obtains address A, but the separate global-reference read for primary creation obtains address B.

Primary creation receives the provider value read at B. If secondary creation or disabling later occurs, its provider value is read at A. The function does not reconcile the addresses or substitute B for A.

### Captured provider contents change

Suppose a normally returning primary dependency changes the provider value stored at the entry-captured address without invalidating that storage. A later secondary provider read observes the value present at that later read, not a provider value saved at entry.

### Secondary disabled

Primary processing still occurs.

If the secondary field is nonzero when checked, the disabling dependency receives the provider from the entry-captured location, not the secondary-resource value. The field is cleared after normal return.

If the field is zero, no secondary dependency or temporary release follows.

### Size 65,537

Primary dimensions are `65,537 × 65,537`.

Secondary preparation uses \(W=1\), \(H=0\), and allocation size zero. Transformation still occurs. Secondary creation receives width `65,537` and height `0`; secondary update receives width `1` and height `0`.

### Size 0 or 1

The allocation request is zero. That alone does not skip transformation, secondary creation or update, or release. Dependency acceptance of zero-size data remains unknown.

### Transformation changes output fields

If transformation replaces the output leading value, secondary processing uses the replacement. Release also uses that value if it remains unchanged until release.

If transformation changes width and height, secondary update uses both changed fields. Secondary creation uses only the changed height; its width remains the original full-size argument.

### Creation returns zero

The corresponding resource field is written with zero, with no immediate retry. Secondary creation returning zero does not prevent the subsequent release call after normal return.

## Evidence

Established static evidence includes the two object-field offsets and widths, zero/nonzero branches, separate update-argument field reads, full-width primary dimensions, narrowed secondary descriptors, bounded unsigned allocation arithmetic, dependency argument sources, direct stores, and call ordering.

Provider access is specifically split between an unconditional entry capture, a separate global-reference read for primary creation, and later secondary dereferences through the entry-captured address.

Resource roles, transformation purpose, and ownership interpretations are inferred from data flow rather than proven dependency behavior. No runtime tests have been performed; all acceptance examples are conditional deductions from the supplied static evidence.
