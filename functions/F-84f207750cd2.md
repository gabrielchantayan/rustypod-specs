# F-84f207750cd2

## Purpose

F-84f207750cd2 coordinates a count-bounded sequence of lookups. Each nonzero lookup result causes two ordered operation calls. Before processing, the function acquires a context, captures an iteration bound, and invokes a setup dependency.

Two distinct termination paths are established:

- **Count exhaustion:** reread a field from the retained context, invoke the completion dependency with that value, and return.
- **Zero lookup result:** return immediately, without the completion call or its associated context-field read.

Setup occurs on both paths, including when the input is null or the captured count is zero. Completion is therefore not guaranteed to balance setup.

“Context,” “setup,” “lookup,” “operation,” and “completion” describe observable roles, not established domain semantics. The evidence does not identify a locking, transaction, rendering, or ownership protocol.

This contract describes static evidence, conditional on valid memory accesses and dependencies returning normally. No runtime tests have been performed.

### Directly accessed layouts

**Retained context**

- Once, after count capture, to obtain the setup argument.
- Once more, only on count exhaustion, to obtain the completion argument.

The context is acquired once. Completion uses the original context address, not a newly acquired context.

**Input object**

2. An unsigned two-byte field at offset `0x2E` from the address obtained by the first read.

If B is zero, neither input-object read occurs, and the iteration bound is zero.

The source representation establishes these offsets and access widths. It does not independently establish byte order, alignment requirements, allocation sizes, or structure meanings.

## Behavior

### Acquisition and count capture

The first dependency invocation is F-8ff48652068d, with no explicit arguments. Its result becomes the retained context address.

Only after that invocation returns does the function determine the iteration bound. Consequently, effects of context acquisition that alter memory subsequently read through B can affect the captured count.

For nonzero B, the address-bearing input field is read before the two-byte count field. For zero B, both reads are skipped.

The count is captured once. Neither setup nor later processing causes it to be reread. Changes to the input object's count or address-bearing field after capture do not change the retained bound.

### Setup

After count capture, the function reads the four-byte context field at offset `0xF60` and passes its value as the sole argument to F-94b6eb7b70a5.

This establishes the following order:

1. Context acquisition.
2. Input-object reads, if B is nonzero.
3. Setup-time context-field read.
4. Setup call.

Setup occurs even when the captured bound is zero. A null input does not bypass context acquisition, the setup-time context read, or setup itself.

No result from setup controls subsequent execution, provided setup returns normally.

### Lookup sequence

Processing uses a 32-bit unsigned index initially equal to zero.

Before each prospective lookup, the index is compared with the captured unsigned bound. An index greater than or equal to the bound selects count-exhaustion completion. Otherwise, F-f8ec0897aceb receives these five arguments, in order:

| Position | Value |
|---|---|
| First | B |
| Second | C |
| Third | D |
| Fourth | Current unsigned index |
| Fifth | D again |

The third and fifth arguments contain identical original 32-bit values. This is not evidence of two reads through D, two distinct resources, or any ownership operation.

The 32-bit lookup result is tested only for equality with zero:

- Zero selects immediate termination.
- Any nonzero value selects the two per-item operations.

Although the lookup result is represented as a signed integer, there is no negative-result branch. A result with its highest bit set follows the nonzero path; this function does not reject it as a negative error code.

### Successful-item operations

For each nonzero lookup result, the function invokes:

1. F-e03d34f0b7e4, receiving `1`, B, and A.
2. F-455544658bc7, receiving `1`, the retained lookup result, and A.

The first operation returns before the second is invoked. The same lookup result is retained across the first operation and passed to the second; no replacement lookup occurs.

Neither operation’s result is inspected. Once the second operation returns, the unsigned index increases by one and the next bound comparison occurs.

There is no visible retry, rollback, compensating call, or conditional suppression of the second operation based on the first operation’s return value. This statement assumes the first operation returns normally; exceptional transfer or non-return is not established.

### Count-exhaustion completion

When the index is at least the captured bound, the function reads the four-byte field at offset `0xF60` from the retained context address again. It passes that freshly obtained value as the sole argument to F-0b8b101e723b and returns after that call returns.

Completion does not reuse the setup argument. If setup or another dependency changes the context field, completion can receive a different value.

The retained context address itself does not change merely because a dependency changes a global context reference. The function does not reacquire the context. Continued validity of the retained address remains a precondition.

For a zero bound, completion follows setup without any lookup or per-item operation.

### Zero-result termination

A zero lookup result terminates the invocation immediately:

- Neither per-item operation runs for that lookup.
- The index is not incremented.
- No later lookup occurs.
- The completion-time context read is omitted.
- F-0b8b101e723b is not called.

The same behavior applies if zero is returned at the last permitted lookup index. The function reaches exhaustion only after a nonzero result has been processed and the index has advanced to the bound.

Previously completed per-item operations are not undone.

### Integer boundaries

The unsigned 16-bit count constrains the entire loop:

- Maximum captured bound: 65,535.
- Maximum number of lookup calls: 65,535.
- Maximum lookup index: 65,534.
- Maximum index after increment: 65,535.

The 32-bit unsigned index therefore cannot overflow during the established normal sequence.

The count is not interpreted as signed. For example, a two-byte count value of `0xFFFF` denotes 65,535, not a negative bound.

These bounded-loop properties do not resolve address-arithmetic overflow. In particular, B's signed representation and its use in adding `0x40` do not establish a portable overflow rule or a machine-level wrapping guarantee.

## Acceptance examples

These are conditional expectations derived from static evidence, not executed tests. Each assumes valid required accesses and normally returning dependencies.

### Null B

With B equal to zero:

- Acquire the context.
- Skip both input-object reads.
- Read the context field and call setup.
- Perform no lookup or per-item operation.
- Reread the context field and call completion.

No status distinguishes this path from other normal returns.

### Nonzero B with zero count

With valid input-object accesses yielding zero:

- Perform both input-object reads after context acquisition.
- Call setup.
- Perform no lookup.
- Call completion with a fresh context-field value.

This has the same dependency-call sequence as null B, but different memory-access requirements.

### Two successful lookups

With a captured count of two and nonzero results at indices zero and one:

- Call setup once.
- At each index, call lookup, then the first operation, then the second operation.
- Call completion after processing index one.
- Never query index two.

Both lookup calls receive identical D values in their third and fifth positions.

### First lookup returns zero

With a positive count and zero at index zero:

- Call setup and lookup.
- Call neither per-item operation.
- Omit completion and its context-field read.
- Return immediately.

### Zero at the final permitted index

With a count of two, a nonzero result at index zero, and zero at index one:

- Fully process index zero.
- Query index one.
- Return without completion, even though index one was the last permitted lookup index.
- Do not undo index-zero operations.

### Changed context field

If setup or a later dependency changes the field at the retained context address:

- Setup receives the value read before setup was invoked.
- Exhaustion completion receives the value present at its later read.
- A zero lookup result prevents that later read entirely.

These expectations require the retained context storage to remain valid.

### Changed stored count

If the captured count is two and setup changes the stored count to zero, the function still attempts indices zero and one unless a lookup returns zero. The count is not reread.

### Highest-bit lookup result

If lookup returns a 32-bit value with the highest bit set and the value is otherwise valid for the dependencies, both per-item operations run. The second receives that same result value. No signed-negative rejection occurs.

### Maximum count

With a count of `0xFFFF` and all lookup results nonzero:

- Exactly 65,535 lookups occur, at indices zero through 65,534.
- Each lookup is followed by both operations.
- Completion follows the last pair of operations.
- The index does not overflow.
