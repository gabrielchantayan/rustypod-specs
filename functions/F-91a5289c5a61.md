# F-91a5289c5a61

## Purpose

F-91a5289c5a61 performs an ordered update on a caller-supplied object. It optionally invokes an object callback, conditionally clears an object flag and invokes another callback, optionally obtains two byte-sized values through dependencies, and finally invokes a completion dependency.

On every normally returning path, the function returns the 32-bit value **1**. This result does not report whether either optional value was found or written.

The apparent intent is to refresh two adjacent object fields from an external source while handling a pending notification. That interpretation is inferred. The established contract is the sequence of calls, reads, and writes described below; names such as “query,” “conversion,” and “cleanup” do not establish the dependencies’ internal semantics.

## Behavior

### 1. Optional initial callback

If mode is nonzero, the function reads the object’s dispatch-table pointer, selects the entry at table offset `+0x118`, and invokes it with the object pointer.

This callback precedes the flag test, global snapshots, temporary construction, and field updates. Its effects are not constrained by the visible function. In particular, subsequent reads must not be interpreted as observing the object or globals as they existed before this callback.

If mode is zero, this callback is skipped.

### 2. Conditional flag clearing and notification

The function examines the 32-bit object word starting at `+0xD4`, narrowed to a character-sized value. If that narrowed value is zero, this entire notification path is skipped.

If it is nonzero:

1. F-6a21f4f07f67 is called without explicit arguments.
2. Its result is checked against a null pointer.
3. A null result causes F-a817d8d58c10 to be called. The supplied source identifies this dependency as non-returning.
4. For a nonnull result, one zero byte is written at object offset `+0xD4`.
5. The notification object’s dispatch table is then read, and its callback at table offset `+0x90` is invoked.

The flag-clearing write precedes the notification callback. It does not precede F-6a21f4f07f67 or the null-result failure call.

The condition and write should not be conflated without an endianness assumption: the condition narrows a 32-bit word, whereas the write targets the first addressed byte of that word. On a little-endian representation these select the same low-order byte. Byte order is not independently established by the supplied material.

This notification path is independent of mode. It may run when mode is zero.

### 3. Capture shared state and prepare local storage

After the notification path completes, the function captures the descriptor-table base.

It also prepares local storage containing:

- A copy of the original object pointer.
- A copy of mode.
- A copy of the auxiliary word.
- A four-word, 16-byte temporary region whose first word is initialized from the initial temporary word.

No initialization of the remaining three words of that region is visible.

The addresses of these local values are passed to dependencies later. They are therefore mutable scratch state, not immutable argument snapshots from a dependency’s perspective.

If mode is zero, the function skips all temporary-construction and optional field-update work and proceeds to the final dependency.

### 4. First optional field update

For nonzero mode, the function first constructs a temporary through F-9b9c1c7483f4, supplying:

- The address of the 16-byte temporary region.
- The 32-bit descriptor at offset `+0x0C` from the descriptor-table base read through the global at this point.
- The address of the local auxiliary-word copy.

The construction result is an opaque 32-bit value.

Only after construction returns does the function read and retain the external context global. It then calls F-8094c3d72052 with that context and the construction result.

After the query returns, F-8a5aadac202f is called with the temporary-region address. This cleanup-shaped call occurs regardless of whether the query result is zero or nonzero.

If the query result is zero, no direct write to object offset `+0xB0` occurs.

If the query result is nonzero:

1. F-9b9c1c7483f4 is called again, now with the address of the local mode copy as its first argument.
2. Its descriptor is read from offset `+0x0C` using the previously captured descriptor-table base.
3. Its third argument is the address of the local object-pointer copy.
4. F-cf946f91e683 receives the retained external context and the new construction result.
5. The byte-sized value obtained from that dependency is written to object offset `+0xB0`.
6. F-8a5aadac202f is called with the address of the local mode copy.

The byte write precedes this last cleanup-shaped call. If that call does not return normally, the write has nevertheless already occurred.

There is no check that the descriptor word used by the second construction equals the word used by the first. Dependencies may have changed the descriptor table between those reads.

### 5. Second optional field update

Still on the nonzero-mode path, the function performs a corresponding sequence for descriptor offset `+0x10` and destination byte `+0xB1`.

It first calls F-9b9c1c7483f4 using:

- The same 16-byte temporary region used for the first query.
- The descriptor word read at `+0x10` from the captured descriptor-table base.
- The same local auxiliary-word address.

It then queries through F-8094c3d72052 using the retained external context and calls F-8a5aadac202f on the temporary region.

A zero query result causes no direct write to `+0xB1`.

A nonzero query result causes another construction using the local mode-copy address, the descriptor at `+0x10` from the captured base, and the local object-pointer-copy address. F-cf946f91e683 then supplies the byte written to `+0xB1`, followed by F-8a5aadac202f on that construction’s storage address.

The two field updates are independent conditional decisions, but their execution is ordered: the entire first sequence precedes the second.

The local storage is not visibly reinitialized between these sequences. Mutations made through the auxiliary-word address, object-pointer-copy address, mode-copy address, or temporary-region address can therefore affect later dependency calls.

The retained external context is reused throughout both sequences. The function does not reread its global after the first construction, even if a later dependency changes that global.

### 6. Final dependency and return

After the preceding paths complete, F-876f4b90d114 is called with the **original object pointer and original mode value**.

Changes to the local object-pointer or mode copies do not redirect these final arguments. Likewise, direct destination writes use the original object pointer.

If this dependency returns normally, the function returns `1`. Its return value, if any, is not used.

## Side effects

The function directly performs at most three one-byte object writes:

- Zero at `+0xD4` on the successful notification path.
- A dependency-derived byte at `+0xB0` when the first query is nonzero.
- A dependency-derived byte at `+0xB1` when the second query is nonzero.

A skipped field update means only that this function does not perform that particular direct write. It does **not** guarantee that the byte is unchanged: earlier callbacks or dependencies may modify the object.

No direct allocation, ownership transfer, release of the caller’s object, or global write is visible. Dependency calls may have additional effects that are not established here.

F-8a5aadac202f is consistently called after query use or after the corresponding byte write. This supports an inferred cleanup role, but does not prove destruction, deallocation, reference-count adjustment, or ownership consumption.

Local addresses are passed to dependencies. The visible function does not establish whether those dependencies retain them. Validity beyond the invocation, or safe asynchronous use, cannot be promised.

There is no visible rollback or exceptional-unwind cleanup. Normal-return call ordering does not establish what happens after a fault, exception, termination, or nonlocal transfer.

## Acceptance examples

The following are conditional static acceptance scenarios, not executed tests.

1. **Zero mode, zero narrowed flag.**  
   The initial callback, notification dependencies, temporary construction, queries, conversions, and temporary cleanup calls are skipped. F-876f4b90d114 receives the original object and zero. A normal return is `1`.

2. **Zero mode, nonzero narrowed flag, valid notification object.**  
   F-6a21f4f07f67 runs; the byte at `+0xD4` is cleared; notification dispatch `+0x90` runs; the final dependency runs. Neither optional field-update sequence runs.

3. **Nonzero mode, both queries return zero.**  
   The initial object callback runs. After any notification handling, both query sequences run, each followed by cleanup. Neither destination byte receives a direct write from this function. The final dependency still receives the original nonzero mode, not a normalized Boolean.

4. **First query nonzero, second query zero.**  
   If the first conversion supplies byte value `0xA5`, that value is written at `+0xB0` before its associated cleanup. No direct write to `+0xB1` occurs. The second query and final dependency still run if all earlier calls return.

5. **Both queries nonzero.**  
   Each destination receives its respective conversion byte. The first write and cleanup precede construction for the second query. There are four construction calls, four cleanup-shaped calls, and two conversion calls.

6. **External context global changes during the first construction.**  
   The context read after that construction observes the then-current global value. If it changes again later, subsequent queries and conversions still receive the retained value.

7. **Notification lookup returns null.**  
   F-a817d8d58c10 is invoked before any direct flag clear. Under its stated non-returning behavior, no later update sequence, final dependency, or normal return occurs.

8. **A dependency mutates a local argument copy.**  
   Later calls receiving that same local address may observe the mutation. Direct destination writes and the final dependency continue to use the original object pointer; the final dependency receives the original mode.
