# F-9c7ab0d1891b

## Purpose

F-9c7ab0d1891b performs a format-dependent sequence of backend operations using a context, selects a 32-bit identifier, and publishes that identifier and its successor after successful final submission.

Two modes are accepted. Depending on the captured format variant and mode, a preliminary submission precedes the final submission. Preliminary status 33 causes identifier advancement and retry only in the matching format variant.

**Inferred intent:** the sequence resembles creation or allocation followed by metadata registration. Object identity, mode meanings, and transactional guarantees are not established.

The operation is not visibly atomic. Retry-related context changes can survive failure. Successful final submission causes output and counter writes before subsequent operations whose errors can become the function’s return value.

## Interface

### Inputs and return value

| Input | Representation | Established use |
|---|---|---|
| Context | Pointer to storage containing 16-bit and 32-bit fields | Format selection, backend selection, identifier state, and dependency input |
| Selector | 32-bit value | Passed to lookup, preparation, and resolution dependencies |
| Additional input | 32-bit value | Passed to resolution |
| Mode | Signed 32-bit integer | Only 1 and 2 are accepted |
| Identifier output | Pointer to a 32-bit unsigned word | Receives the selected identifier after successful final submission |

The return value is a signed 32-bit status. Some dependencies supply statuses observed through signed 16-bit results; these are sign-extended before return or comparison.

The identifier output is not initialized on entry. The function’s only direct write to it follows a zero result from final submission. A later failure does not undo that write.

### Directly accessed context layout

Offsets are byte offsets from the context base.

| Offset | Width | Use |
|---|---:|---|
| 0 | 16 bits | Read-modify-write with mask `0xFF00` during low-range adjustment |
| 2 | 16 bits | Compared with `0x482B` at entry |
| 12 | 16 bits | Read-modify-write with mask `0x1000` during low-range adjustment |
| 24 | 32 bits | Candidate identifier; later receives its successor |
| 344 | 32-bit pointer representation | Loaded and dereferenced to read a 32-bit backend handle |

The **matching variant** means that the entry-time field at offset 2 equals `0x482B`. Every other value selects the **alternate variant**.

These observations occur at different times:

1. The format marker is read before initialization calls and mode validation.
2. The backend handle is captured after mode validation.
3. The candidate identifier is read after the backend check succeeds.

Dependency mutations between these observations can therefore affect later reads. The captured format decision and backend handle are not explicitly refreshed.

### Local storage and descriptor layout

The visible representation uses 32-bit addresses and values.

Two distinct 552-byte backend workspaces are supplied to an initializer. Call them the **first workspace** and **second workspace**, in initialization order. Each has an identified interior address 28 bytes after its beginning. The first workspace’s interior is also used as resolution storage; the second workspace’s interior is used for per-attempt preparation.

Two other buffers are distinct:

- A preliminary local buffer occupying 524 bytes, represented as 262 signed 16-bit elements.
- A final local buffer occupying 520 bytes, represented as 260 signed 16-bit elements.

A reused local descriptor has three consecutive 32-bit fields:

| Descriptor offset | Width | Meaning established at this call site |
|---|---:|---|
| 0 | 32 bits | Buffer pointer |
| 4 | 32 bits | Auxiliary value, initially populated as described below |
| 8 | 32 bits | Set to 1 before each construction stage |

The request constructors receive buffer pointers, **not the descriptor address**. Submission receives the descriptor address.

A separate 32-bit **preliminary quantity carrier** has its address exposed to preliminary construction. Its subsequent writes are part of the observable contract even though later calls do not explicitly receive its address.

### Preconditions

The context must permit the accesses reached on the chosen path. Even an unsupported mode requires a readable format marker. Supported modes additionally require readable indirect backend-handle storage.

The output location must be writable if final submission succeeds. No visible null checks, alignment checks, or storage-size checks enforce these requirements.

Requirements imposed by dependencies on selector values, backend state, record contents, and writable buffer extents remain undocumented.

## Behavior

### Entry and mode rejection

The function captures the format comparison, then invokes an external initializer twice:

1. First workspace, size 552.
2. Second workspace, size 552.

The initializer’s semantics are unknown. In particular, these calls do not establish that either workspace is zero-filled.

Only afterward is the mode checked. A mode other than 1 or 2 returns **−50**. Thus unsupported-mode rejection still follows the format read and both initializer calls.

### Lookup and format-dependent record interpretation

For a supported mode, the function captures the indirect backend handle.

F-ac6340dcc280 receives the context, selector, and three local output addresses, including the beginning of a record. A nonzero result is returned unchanged.

On success, F-56433c4250f4 receives the context and selector. Its result is not tested. The record’s leading 16-bit field is then checked:

- Matching variant: required value `0x0003`.
- Alternate variant: required value `0x0300`.
- Otherwise: return **−120**.

The record also supplies information retained for post-submission processing:

| Offset relative to checked field | Established use |
|---|---|
| 0 | Checked 16-bit field |
| 4 | Directly read 32-bit metadata value for matching variant |
| 8 | Matching-variant data pointer |
| 10 | Address passed to F-4055be9c3f18 for alternate variant |
| 14 | Alternate-variant data pointer |

For the alternate variant, F-4055be9c3f18’s result supplies the metadata value. Its input width and decoding convention are not established. The differing validation constants alone do not establish byte order.

### Resolution, backend check, and candidate capture

Before resolution, the preliminary quantity carrier is assigned the address of a separate local 32-bit value later consumed by final construction. The displayed resolution arguments do not explicitly pass that address.

F-a0c5d57d1d48 receives:

- Context.
- Selector.
- Additional input.
- Zero.
- The first workspace’s interior address.

A nonzero result is returned unchanged.

The preliminary quantity carrier is then overwritten with the first workspace’s base address. F-7cae4aaa5e45 receives that workspace address together with the captured backend handle, `0xFFFFFFFF`, zero, and zero.

Its observed result is signed 16-bit. Only **32** permits continuation. Every other result produces **49**.

The candidate is then read from context offset 24. For the alternate variant, candidate `0xFFFFFFFF` returns **−34**. No corresponding sentinel rejection exists for the matching variant.

### Preliminary construction

The preliminary stage is taken for:

- Matching variant, mode 1.
- Matching variant, mode 2.
- Alternate variant, mode 1.

Alternate-variant mode 2 skips it.

Before construction, the descriptor receives:

1. The preliminary buffer’s address.
2. The current preliminary quantity carrier value: the first workspace’s address.
3. The 32-bit value 1.

Consequently, immediately before the constructor call, both the carrier and the descriptor’s second field contain the first workspace’s address.

F-4f1b961063bb receives, in order:

1. Context.
2. Mode.
3. Resolved storage address.
4. The preliminary buffer pointer.
5. The address of the preliminary quantity carrier.

The fourth argument does not provide direct access to the descriptor. The fifth argument permits modification of the carrier. No return result is tested.

The descriptor’s second field is a copied value, not a reference to the carrier. Updating the carrier through its address does not, by itself, update that descriptor field.

### Preliminary attempts and retries

Each attempt performs these calls in order:

1. F-360d49b83f75 receives the candidate, zero, the captured variant flag, and the second workspace’s interior address.
2. F-f874cbec901b receives the captured backend handle, second workspace base, descriptor address, and the **current low 16 bits of the preliminary quantity carrier**.

The submission quantity is therefore not necessarily the low bits of the workspace address. Preliminary construction can replace the carrier’s value; other dependency effects through available aliases are not excluded.

The signed 16-bit submission result controls continuation:

| Result | Matching variant | Alternate variant |
|---|---|---|
| 0 | Continue to final construction | Continue to final construction |
| 33 | Advance candidate and retry | Return 33 |
| Any other value | Return sign-extended result | Return sign-extended result |

Retry advancement is a 32-bit increment by one. If the resulting unsigned value is below 16:

1. The local candidate is replaced with 16.
2. Context offset 12 is updated by OR with `0x1000`.
3. Context offset 0 is updated by OR with `0xFF00`.

The increment is byte-unit numeric advancement, not multiplication by the size of a pointer target. Its relevant boundary behavior is 32-bit wraparound.

The function does not directly publish the candidate to context offset 24 during retry. Flag changes remain visible even if a subsequent attempt fails. There is no explicit retry bound.

### Final construction and submission

The descriptor is repopulated, in order, with:

1. The original 520-byte final buffer’s address.
2. The current value of a separate local 32-bit final-quantity location.
3. The value 1.

The final-quantity location’s initialization before this copy is not established.

The preliminary quantity carrier is then overwritten with the selected candidate. This write occurs even when the preliminary stage was skipped.

F-3e37657386e2 receives:

1. Context.
2. Mode.
3. The separate local 32-bit construction input whose production is unresolved.
4. The original final buffer pointer.
5. The final-quantity location’s address.

The fourth argument is not the descriptor address. The constructor receives writable access to the final buffer and final quantity through explicit arguments, but no explicit descriptor pointer. Its return result is not tested.

F-f874cbec901b then receives the captured backend handle, first workspace base, descriptor address, and the current final quantity masked to 16 bits.

As in the preliminary stage, the descriptor’s second field was copied before construction. A subsequent write to the final-quantity location does not automatically refresh that field.

### Successful final submission

For a zero final submission result, the direct actions are ordered as follows:

1. Write the selected candidate to the caller’s identifier output.
2. Compute its 32-bit successor.
3. If the successor is below 16, OR `0x1000` into context offset 12, then OR `0xFF00` into context offset 0, and replace the successor with 16.
4. Write the successor to context offset 24.
5. Overwrite the address-exposed preliminary quantity carrier with **1**.
6. Invoke F-5ff5fde1145e.

F-5ff5fde1145e receives the context, previously selected metadata value, previously selected data pointer, the signed first 16-bit element of the original final buffer promoted to 32 bits, and zero.

If its result is nonzero, that result is returned. The output, counter, and carrier writes have already occurred.

If it returns zero, the function reads the first signed 16-bit final-buffer element again and passes the promoted value to F-133067dd521d with the context and 1. This second read need not equal the first if an intervening dependency changed the buffer through an available alias. F-133067dd521d’s result is not tested.

Finally, F-92a758c7556d receives the context, and its result becomes the function result.

### Failed final submission

A nonzero final status is sign-extended from 16 bits, with one translation: **33 becomes 49**.

For alternate-variant mode 2, the resulting status is returned directly.

For either matching-variant mode, or alternate-variant mode 1, F-b0987b51cfe6 first receives the captured backend handle and second workspace. Its result is not tested; the previously determined status is returned.

This cleanup-like call is not visibly made for preliminary submission failure or post-submission metadata failure.

## Side effects

Direct context mutations are limited to the flag read-modify-writes and successor publication described above. Direct caller-output publication occurs only after final submission succeeds. These statements do not constrain unknown dependency effects.

The preliminary quantity carrier has the following visible lifecycle:

| Point | Assigned value |
|---|---|
| Before resolution | Address of the unresolved final-construction input location |
| Before backend check | First workspace address |
| Preliminary construction, if taken | Dependency may replace it through its address |
| Before final construction | Selected candidate |
| After successful final submission and counter publication | 1 |

Once its address has been passed to F-4f1b961063bb, a dependency could retain an alias for the remainder of the invocation. Through such an alias, later dependencies could observe the candidate assignment or the subsequent assignment of 1. Preservation and retention behavior are unknown; these writes must not be treated as invisible solely because the carrier is local.

The function visibly performs no heap allocation or release. This establishes neither dependency ownership nor absence of dependency allocation. Local workspace, buffer, descriptor, and carrier addresses cease to designate live invocation storage when the function returns. Safe retention beyond that lifetime requires a dependency contract not supplied here.

There is no visible rollback. Read-modify-write flag updates use the context contents present when each update executes, rather than an entry-time snapshot.

## Acceptance examples

These are conditional static expectations, not executed tests. Assume valid storage and the prerequisite dependency results for each path. Unless specified otherwise, dependencies do not introduce additional mutations affecting the example.

1. **Unsupported mode:** Mode 3 causes the format read and both initialization calls, then returns −50. The function makes no direct identifier-output write.

2. **Format validation:** A record field of `0x0003` passes matching-variant validation but produces −120 in the alternate variant.

3. **Backend normalization:** Backend-check results 0, −1, and 33 each produce 49 before the candidate field is read.

4. **Carrier versus descriptor:** Before preliminary construction, both the carrier and descriptor field at offset 4 equal the first workspace address. If construction writes `0x12345678` through the carrier address, preliminary submission receives quantity `0x5678`. The descriptor’s second field remains the copied workspace address absent another mutation.

5. **Constructor argument identity:** Preliminary construction receives the 524-byte preliminary buffer pointer. Final construction receives the original 520-byte final buffer pointer. Submission receives the descriptor address; neither constructor receives that address through its fourth argument.

6. **Matching retry:** Candidate 20 and preliminary results 33, then 0, produce attempts for 20 and 21. Successful final submission publishes output 21 and successor 22.

7. **Retry wrap:** Matching candidate `0xFFFFFFFF` followed by preliminary status 33 wraps, sets the flag masks, and retries with 16. The retry does not directly update context offset 24.

8. **Alternate restrictions:** Alternate candidate `0xFFFFFFFF` returns −34. With a nonsentinel candidate in mode 1, preliminary status 33 returns 33 without retry or the cleanup-like call.

9. **Skipped preliminary stage:** Alternate mode 2 proceeds without preliminary construction. Final status 33 returns 49 without F-b0987b51cfe6.

10. **Retained carrier alias:** If preliminary construction retained the carrier address without later changing its value, a final-construction dependency observing that alias sees the selected candidate. After successful final submission and counter publication, F-5ff5fde1145e can observe 1 through the same alias.

11. **Publication before failure:** With selected candidate 40, successful final submission writes output 40, counter 41, and carrier 1 before a nonzero F-5ff5fde1145e result is returned.

12. **Signed element and reread:** Final-buffer bits `0xFFFF` produce argument −1 for F-5ff5fde1145e. If that dependency returns zero after changing the element to 2 through an available alias, F-133067dd521d receives 2.

## Uncertainties

The following remain **documented_only**:

- Initializer semantics and dependency-specific storage requirements.
- Meanings of modes, backend operations, metadata, and status numbers.
- The alternate decoder’s input width and encoding.
- Dependency ownership, allocation, release, alias retention, and mutation behavior.
- Whether untested return values represent statuses.
- Request contents and descriptor fields beyond directly established assignments.

Two local data-flow gaps remain significant:

- The 32-bit input passed to final construction has no explicit producing write in the supplied operations. Assigning its address to the carrier before resolution does not establish that resolution receives or fills it.
- The final quantity is copied into the descriptor before final construction receives its address. Initialization of that earlier read is not established.

These gaps are not repaired by assuming hidden arguments, zero initialization, or undocumented writes. They prevent a complete independent specification of request bytes.
