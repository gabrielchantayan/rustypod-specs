# F-08d0b4a01103

## Purpose

F-08d0b4a01103 accepts a context reference, a requested index, and an output reference. It returns a 32-bit status and performs path-dependent writes to two adjacent 16-bit output fields.

A context field selects between two behaviors:

- A delegated lookup using F-5ef10d079522.
- A local search over a table of 32-bit words.

The first output field is not a success indicator. The local path sets it to one before validating its table reference. The delegated path derives it from a dependency-accessible 32-bit quantity after the dependency returns, regardless of the returned status.

On local completion, the function directly writes both output fields. On delegation, it directly writes only the first field and passes the second field’s address to the dependency. A zero delegated status does not, by itself, establish that the second field was written.

The application-level meanings of the context, index, table, and output fields are not established.

## Interface

| Item | Established representation |
|---|---|
| Context reference | 32-bit address-like value |
| Requested index | 32-bit quantity, interpreted both as signed and unsigned |
| Output reference | Address of two adjacent 16-bit fields |
| Result | 32-bit status bit pattern |

The output layout is:

| Byte offset | Width | Role |
|---|---:|---|
| 0 | 16 bits | First output field |
| 2 | 16 bits | Second output field |

No byte order is established here. Field widths, byte offsets, and resulting bit patterns describe the accesses without requiring an endian assumption.

### Status values

- **0xFFFFFFCE**, equivalent to signed 32-bit −50: explicit rejection.
- **Zero:** completion of the local table path.
- **Dependency result:** F-5ef10d079522’s 32-bit status, returned unchanged on delegation.

Zero can also be returned by the delegated path. No symbolic interpretation of these statuses is established.

Invalid memory access is not shown as a recoverable status condition. In particular, the first output write occurs before the output reference is checked for null.

### Context layout and identity

The following fields are accessed as 32-bit quantities:

| Byte offset | Observed use |
|---|---|
| 0xEEC | Reference to an array of four-byte entry references |
| 0xEF0 | Dispatch field, later reread as the local table reference |
| 0xEF4 | Unsigned index limit |
| 0xF60 | Reference used to form a delegated argument |

Three context references must remain distinct:

1. The original argument.
2. The first reference returned by F-8ff48652068d.
3. The second reference returned by F-8ff48652068d, obtained only after delegated validation succeeds.

Their equality is not established. The original context supplies initial range validation. The first resolved context supplies dispatch, delegated range validation, the local table reference, and one delegated argument chain. The second resolved context supplies the field at offset 0xF60.

### Preconditions and ownership

Ordinary completion requires valid storage for every reached access, including output fields, context fields, nested references, array entries, table words, and dependency-accessible storage.

The explicit checks do not establish all of these conditions. There are no visible checks for context validity, nested-reference validity, array extent, table extent, or the validity of either resolved context.

The visible function performs no explicit allocation, release, or ownership transfer. Dependency allocation, release, retention, and ownership behavior remain unknown. Passing an address to a dependency does not establish that the dependency owns or preserves its target.

## Behavior

### Entry and initial validation

The first visible direct memory operation writes zero to the first output field.

F-8ff48652068d is then called with the original context reference. Its result becomes the first resolved context.

Initial validation follows, with short-circuit checks in this order:

1. Reject if the output reference is null.
2. Otherwise, reject if the requested index is negative under signed 32-bit interpretation.
3. Otherwise, read the unsigned limit at original-context offset 0xEF4 and reject if the index is greater than or equal to that limit.

Each rejection returns 0xFFFFFFCE.

Consequences:

- A null output reference can cause an invalid access before validation.
- The first resolution call precedes rejection of a negative or out-of-range index.
- An index with bit 31 set is rejected by the signed test, if execution reaches that test.
- The original-context limit is read after the resolution call. Dependency mutations can therefore affect its observed value.
- The visible body does not write the second field on initial rejection. Dependency effects are separate and unknown.

After validation, the function reads the field at first-resolved-context offset 0xEF0. Zero selects delegation; nonzero selects the local table path.

### Delegated validation

On entering delegation, the function writes zero to the first output field again.

It then requires, in short-circuit order:

1. A nonnull output reference.
2. A nonnegative signed interpretation of the index.
3. An index strictly below the unsigned limit at first-resolved-context offset 0xEF4.

Failure returns 0xFFFFFFCE.

This limit need not equal the original-context limit. Passing initial validation does not establish that delegated validation will pass.

### Delegated arguments and call

After delegated validation succeeds, F-8ff48652068d is called with the first resolved context. Its result becomes the second resolved context.

A local 32-bit unsigned quantity is then initialized to the requested index. F-5ef10d079522 receives four arguments:

1. An address formed by reading the reference at second-resolved-context offset 0xF60 and adding 0xC0 bytes.
2. A 32-bit value reached through the first resolved context:
   - Its field at offset 0xEEC supplies an array reference.
   - The requested index selects a four-byte entry reference.
   - Entry offset 0x20 supplies another reference.
   - Offset 0x28 within that referenced object supplies the argument value.
3. The address of the second output field.
4. The address of the local 32-bit quantity.

Both argument-reading chains occur after the second resolution call and before F-5ef10d079522 is invoked. Their relative evaluation order is not established. Within each chain, the reads supplying addresses necessarily precede accesses through those addresses.

### Delegated completion and first-field transformation

After F-5ef10d079522 returns normally, the function reads the local quantity and constructs the first output field from **original quantity bits 1 through 16**, inclusive. Those bits become output bits 0 through 15.

For a post-call quantity \(q\), the resulting 16-bit pattern is:

\[
(q \mathbin{\mathrm{>>}} 1)\ \mathbin{\&}\ \text{0xFFFF}
\]

This follows from a 32-bit unsigned left shift by 15, discarding bits beyond width 32, followed by a logical right shift by 16. Original bit 16 survives as output bit 15; that output bit is not necessarily zero. Original bit 0 and original bits 17 through 31 do not contribute.

The final first-field write occurs regardless of whether the dependency’s status is zero or nonzero. The function then returns that status unchanged.

The visible caller does not directly write the second output field on this path. Whether the dependency changes that field, changes the local quantity, or modifies other storage is unresolved.

### Local setup

The local path performs these actions in order:

1. Write one to the first output field.
2. Reread first-resolved-context offset 0xEF0 to obtain the table reference.
3. Reject with 0xFFFFFFCE if that reference is null.
4. Otherwise, reject with the same status if the address of the second output field compares equal to null.

The table reference is reread rather than retained from dispatch. The intervening output write can change the reread value if storage aliases.

The second-field address check does not establish valid writable storage and cannot protect the earlier output writes. Its behavior at address-arithmetic extremes is not established.

### Table layout

The table consists of 32-bit words:

| Word position | Interpretation |
|---|---|
| 0 | Signed 32-bit record count |
| \(2r+1\) | Payload for record \(r\) |
| \(2r+2\) | Unsigned threshold for record \(r\) |

Records are numbered from zero.

The search can also access word \(2r\) as a predecessor threshold and word \(2r+4\) as a successor threshold.

For record zero, the predecessor word is the count word, compared as unsigned. For the last counted record, the successor word lies beyond the last counted threshold. No visible extent check or sentinel validation protects these accesses.

### Search state and arithmetic

The lower bound starts at signed zero. The upper bound is the signed count minus one. The selected record initially is zero.

Before each midpoint calculation, the signed bounds are compared. If the upper bound is below the lower bound, selection ends without another midpoint calculation.

Otherwise, the selected record becomes the signed result of adding the bounds and right-shifting their sum by one. For nonnegative bounds with a representable sum, this is the lower integer midpoint.

Signed overflow and extreme address arithmetic are not assigned portable behavior by this contract. No explicit overflow rejection is visible.

Bounds exhaustion is not an error. It retains the most recently selected record, or record zero if no midpoint was calculated.

### Conditional reads and selection

The current record’s threshold is first read and compared with the index as unsigned.

**When that first threshold value is no greater than the index:**

- The current threshold is read again.
- If the index is no greater than this second value, the current record is selected immediately. No successor read occurs.
- Otherwise, the successor threshold is read.
- If the index is strictly below that value, the current record is selected.
- Otherwise, the successor threshold is read again.
- Equality between this second successor value and the index selects the next record.
- If equality fails, the lower bound moves to one record above the current record, and searching continues.

The second current-threshold comparison is not inherently an equality check: its value can differ from the first read. The two successor reads are likewise distinct.

**When the first current-threshold value is greater than the index:**

- The predecessor word is read and compared as unsigned.
- If its value is no greater than the index, the preceding record is selected.
- Otherwise, the upper bound moves to one record below the current record, and searching continues.

This route does not reread the current threshold or read the successor threshold.

Only under stable threshold values can the forward route be summarized as selecting the current record at its threshold or strictly before its successor, selecting the next record at the successor threshold, and advancing the lower bound above the successor threshold. That summary does not replace the distinct conditional reads.

### Local completion

After selection, including selection through bounds exhaustion, the function reads the selected payload, writes its low 16 bits to the second output field, and returns zero.

There is no dedicated rejection for zero or negative counts, unsorted thresholds, incomplete coverage, or a selected record outside the counted range. Such conditions can produce unusual selections or invalid memory accesses.

## Side effects

### Direct output writes

| Path | Direct writes by this function |
|---|---|
| Initial rejection | First field receives zero |
| Delegated validation rejection | First field receives zero at entry and again on delegation |
| Delegated normal return | The two zero writes, followed by the transformed local quantity |
| Local rejection | First field receives zero, then one |
| Local completion | First field receives zero, then one; second field receives the selected payload’s low 16 bits |

The second field is not cleared merely because a request is rejected.

Both payload conversion and delegated transformation produce 16-bit patterns. Payload conversion retains bits 0–15; delegated transformation retains quantity bits 1–16. Neither operation saturates or validates a numeric range.

### Aliasing and dependency effects

No non-aliasing restriction is enforced. Output writes can therefore alter context fields, table words, or other subsequently accessed storage when addresses overlap.

The supplied representation distinguishes repeated threshold reads and the final payload read. Stable-table reasoning requires those values to remain stable; no locking, snapshot mechanism, or rollback is shown.

Neither dependency is assumed to preserve globals, contexts, tables, or output storage. Dependency mutations may affect later reads. Apart from dependency effects, visible writes to context or table storage can arise through output aliasing.

## Acceptance examples

These examples are conditional static deductions, not executed tests. Unless stated otherwise, assume valid reached storage, stable relevant values, no interfering dependency effects, and representable arithmetic.

### Initial rejection

For index 10 and an original-context limit of 10:

- The first field is written zero.
- F-8ff48652068d is called.
- Initial validation returns 0xFFFFFFCE.
- The visible body does not write the second field.

For a negative signed index, rejection occurs without reading the original-context limit.

### Different limits

- Initial validation passes.
- Delegated validation fails.
- F-5ef10d079522 is not called.
- The first field is zero.
- The visible body leaves the second field untouched.

### Delegated transformation and status

If F-5ef10d079522 returns zero, leaves the local quantity at 6, and does not write the second field, the caller returns zero and writes 3 to the first field. The second field retains its prior contents if no other operation changes it.

If the dependency returns a nonzero status and leaves the quantity at 0x00010003, the caller writes **0x8001**, then propagates the nonzero status.

A quantity of **0xFFFFFFFF produces 0xFFFF**. A quantity of 0x00010000 produces 0x8000, demonstrating that output bit 15 can be set.

### Stable-table selection

For count three, thresholds 10, 20, and 30, and corresponding payloads 0x12345678, 0x0000ABCD, and 0x00008001:

- Index 15 selects the first payload and writes 0x5678.
- Index 20 selects the second payload and writes 0xABCD.
- Index 30 selects the third payload and writes 0x8001.

Each example additionally requires an original-context limit above the index and selection of the local path. The first field becomes one; the status is zero.

### Changing threshold reads

For index 15, suppose a reached current threshold first reads as 10 and then as 20. The forward route is taken, and the second comparison selects the current record without a successor read. Neither observed current threshold equals the index.

Alternatively, suppose both current reads yield 10, while the successor reads yield 12 and then 15. The strict successor comparison fails, but the subsequent equality succeeds, selecting the next record.

### Empty count and boundary accesses

With count zero and readable word 1, the upper bound starts at −1. No midpoint is calculated; word 1 supplies the payload, and the function returns zero.

A request above the final threshold can cause a successor read beyond the counted records. Storage sufficient only for the count and counted records does not establish sufficient readable extent.

A null output reference does not guarantee a −50 return: the initial write precedes the null check.
