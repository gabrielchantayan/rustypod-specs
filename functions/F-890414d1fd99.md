# F-890414d1fd99

## Purpose

F-890414d1fd99 dispatches a four-word request according to the signed interpretation of its second word.

A nonnegative second word selects optional direct forwarding. A negative second word selects resolution followed by a different dispatch callback. After successful negative dispatch, the function may inspect a collection entry, decrement its counter, request removal, and invoke an ordered finalization sequence.

These branches and operations are established by the supplied static representation. Descriptions such as “reference count,” “removal,” “notification,” and “finalization” identify apparent roles, not proven ownership or synchronization contracts.

Global-root accesses matter independently of field accesses. Several presence checks use a freshly read global root, while later operations use an earlier retained address. The function does not generally guarantee that a checked callback and an invoked callback belong to the same object or have the same target.

## Interface

### Arguments and result

The supported interface consists of four 32-bit argument words:

| Position | Established interpretation |
|---|---|
| First | Opaque request word. Forwarded unchanged during initial dispatch. |
| Second | Signed 32-bit routing value. Its sign selects the path; a negative value also determines a collection index. |
| Third | Opaque word. Forwarded unchanged during initial dispatch. |
| Fourth | Opaque word. Forwarded unchanged during initial dispatch. |

The static representation includes additional machine-state values at one recursive invocation. Their presence does not establish additional public arguments. The exact ABI is documented_only.

No defined return value is established. Callback results are not consumed by the visible behavior. A zero resolver result invokes F-a817d8d58c10, which the representation marks as non-returning.

Missing optional callbacks, ineligible indices, and absent entries do not produce an explicit status result.

### Referenced memory

|---|---:|---|

### Preconditions

Every root, field address, entry address, and callback target actually accessed must be valid for its use. Explicit zero checks do not establish broader validity.

In particular:

- A callback presence check may inspect a different object from the later invocation.
- Resolution may change the retained dispatch object or its callback field.
- Collection callbacks and dependencies may change collection handles or entry contents.
- The entry must remain usable after the removal request and closing notification if selected-entry processing continues.
- The finalization +24 callback has no explicit null check.
- A callback field that passed a check is not protected against subsequent change.

No dependency is assumed to preserve globals, retain memory, release memory, or provide synchronization.

## Behavior

### Dispatch entry and nonnegative routing

At the start of each local dispatch iteration, the function captures the current dispatch-configuration root as a retained address. It then tests whether the second argument is nonnegative.

For a nonnegative second argument:

1. It reads the dispatch global root again and checks that object’s +8 callback field.
2. If the checked field is zero, it returns.
3. Otherwise, it separately reads the dispatch global root and its +8 callback field for invocation.
4. The invoked callback receives the four current argument words in their original order.
5. The function returns without collection processing.

The retained dispatch address from the start of the iteration is not used for this callback invocation. The check and invocation are separate root-and-field accesses. No explicit dependency call occurs between them, but the representation does not establish that independently observed roots or callback targets must coincide under mutation.

The indirect transfer’s exact call-versus-tail-transfer mechanics are documented_only.

### Negative routing and resolution

For a negative second argument, the function uses a fresh read of the dispatch global root to check the +24 field. This presence check does **not** use the retained dispatch address captured at iteration entry.

If the checked field is zero, the function returns without resolution or collection processing.

Otherwise:

1. F-c103ec6f01cb receives the original signed second argument.
2. A zero 32-bit result selects F-a817d8d58c10. No normal continuation after that dependency is established.
3. For a nonzero result, the function reads the +24 callback field from the **retained dispatch object** and invokes it with:
   - the original first word;
   - the resolver’s result word;
   - the original third word;
   - the original fourth word.

The invocation target is read after resolution. It need not be the target inspected by the presence check: the check used a fresh global-root read, and resolution may also modify either roots or fields.

### Collection-state capture and gate

After the negative dispatch callback returns, the function captures the current collection-state root. Subsequent collection-handle accesses and the later payload callback use this retained collection-state address.

The collection index is derived from the original negative routing argument:

\[
\text{index}=-(\text{second argument}+1)
\]

Within the signed 32-bit negative-input domain, this calculation is representable and produces values from 0 through 2,147,483,647:

- −1 selects index 0.
- −2 selects index 1.
- −2,147,483,648 selects index 2,147,483,647.

A zero-specific alternative exists in the representation, but this stage is reached only with a negative original argument. The resolver result does not affect the index.

After capturing the collection-state address and deriving the index, the function reads the **global collection-state root again** and checks that object’s +28 field.

If this freshly checked field is zero, it returns. The completed negative dispatch is not undone.

If the field is nonzero, processing continues using the previously retained collection-state address. The gate therefore does not establish that the retained object’s +28 field is nonzero, nor that the checked and retained objects are identical.

### Opening notification and eligibility

An enabled collection path first recursively invokes F-890414d1fd99 with:

**(9, 29, 0, 0)**

The second word is nonnegative, so this nested request follows ordinary nonnegative dispatch. Its callback is optional. “Opening notification” denotes placement only; no locking semantics are established.

After that invocation returns:

1. The function reads the collection handle at +4 of the retained collection-state object.
2. A zero handle skips both the count query and lookup.
3. A nonzero handle permits a call to F-10b760faca36, with no visible arguments.
4. The derived index is compared with that dependency’s signed 32-bit result.
5. Lookup is permitted only when the index is strictly less than the result.

Since every derived index is nonnegative, a zero or negative count-like result cannot admit an index.

If the handle is zero or the comparison fails, the function replaces its current request with **(10, 29, 0, 0)** and repeats the local dispatch loop. This iteration captures the dispatch root again, takes the nonnegative branch, optionally forwards the closing request, and returns.

This skipped-lookup path does not perform a separate recursive closing call.

### Lookup and counter update

When the eligibility comparison succeeds, F-6bbddce1b930 receives:

- a new read of the handle at +4 of the retained collection-state object;
- the derived index.

This handle read occurs after the count query. The lookup handle is not guaranteed to equal the earlier nonzero handle.

A null lookup result produces no counter write and no removal request.

For a nonnull entry:

1. Its signed 32-bit counter at +0 is read.
2. The function computes the counter minus one and writes that result to +0.
3. If the decremented result is less than one, the entry remains selected and F-c2674fa3e73d is invoked.
4. Otherwise, the entry is no longer selected for later processing.

F-c2674fa3e73d receives another read of the retained collection-state object’s +4 handle, the index, and zero. Its result is not consumed. That handle need not equal the lookup handle.

The counter write precedes the removal request. Selection applies to every representable decremented result below one, not only a transition from one to zero.

For an initial counter of −2,147,483,648, mathematical subtraction exceeds the signed 32-bit range. The supplied representation does not establish wrapping, trapping, or another overflow behavior. The ordinary transition rules above are conditional on representable arithmetic.

### Closing notification

After an eligible lookup attempt, the function recursively invokes F-890414d1fd99 with:

**(10, 29, 0, 0)**

This occurs after each of these outcomes:

- lookup returned null;
- the counter was decremented but the entry was not selected;
- the counter was decremented and removal was requested.

If no entry is selected, the function returns after this closing invocation.

Selection is not reconsidered by rereading the counter after the closing notification. The notification may affect accessible state, but no subsequent counter-based selection test is visible.

### Selected-entry callback and finalization

For a selected entry, the function invokes the callback at +28 of the **retained collection-state object**, passing **(payload, 0, 0)**. The payload comes from the entry’s +4 word.

Both the payload read and callback-field read occur after the closing notification and supply this indirect invocation. Their relative evaluation order is **not established** by the supplied representation. Neither may be specified as necessarily preceding the other.

Only after that callback returns does the function capture the current finalization-configuration root. Finalization then proceeds as follows:

1. A fresh read of the finalization global root supplies the +48 presence check.
2. If the checked field is nonzero, another fresh global-root and +48 field access supplies the callback invoked with **(entry address, 0)**.
3. The function invokes the +24 callback from the **retained finalization object**, passing the entry address.
4. It reads +48 from that same retained object into a callback target.
5. If this final target is zero, it returns. Otherwise, it invokes that loaded target with **(0, 1)** and returns.

The initial +48 check and invocation do not use the retained address. They also do not guarantee an identical checked and invoked target.

The later +24 invocation and final +48 read do use the retained address. A later reassignment of the global root alone does not redirect those accesses, although mutation of the retained object can affect them.

The two +48 invocations are independently conditional. They need not be paired, need not use the same configuration object, and need not invoke the same callback.

## Side effects

Established effects include:

- Optional forwarding of original or internally generated request words.
- A direct four-byte counter write after a nonnull eligible lookup.
- A removal request for a representable decremented counter below one.
- Selected-entry and finalization callbacks in the ordering described above.
- Repeated global-root, field, handle, and callback-target reads that may observe intervening changes.

No direct allocation, deallocation, atomic counter operation, or local synchronization primitive is established.

The removal request occurs before the closing notification, payload read, and entry-address callbacks. It must not be assumed to free the entry immediately. Conversely, the function itself does not establish that it preserves the entry. Safe continuation depends on an external lifetime contract.

The payload used later is read after removal and the closing notification, not captured at lookup time. Changes to that payload can therefore affect the later callback.

No rollback is visible for a completed write, removal request, or callback if subsequent execution fails or does not return.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless stated otherwise, dependencies return normally, invoked targets are valid, referenced memory remains accessible, and counter arithmetic is representable.

1. **Nonnegative forwarding.** For second word 29, a zero +8 presence-check result causes immediate return. Otherwise, the separately selected invocation target receives all four original words unchanged. Collection processing does not occur.

2. **Distinct dispatch objects.** If the initial dispatch capture selects object A, the negative presence check selects object B, and B’s +24 field is nonzero, resolution proceeds. The post-resolution invocation uses A’s then-current +24 field, not B’s checked field.

3. **Resolution failure.** A zero resolver result invokes F-a817d8d58c10 before negative dispatch or collection processing. No returning continuation is specified.

4. **Resolution differs from indexing.** With original second word −2 and resolver result 700, negative dispatch receives 700 as its second word; collection processing uses index 1.

5. **Distinct collection objects.** If collection capture selects A but the subsequent global-root gate selects B, a nonzero B +28 field enables processing. Handles and the eventual payload-callback field are obtained from A.

6. **Disabled collection path.** A zero collection gate returns after negative dispatch, without opening or closing notifications.

7. **Missing handle.** If the retained collection object’s handle is zero after the opening notification, no count query or lookup occurs. The local dispatch loop handles **(10, 29, 0, 0)**.

8. **Strict boundary.** Index 3 with count-like result 3 does not permit lookup. A negative count-like result likewise excludes every derived index.

9. **Retained entry.** Counter 2 becomes 1. No removal or selected-entry callback occurs; the recursive closing notification follows the write.

10. **Selected entry.** Counter 1 becomes 0. Removal precedes the recursive closing notification, which precedes the payload callback and finalization.

11. **Already exhausted entry.** Counter 0 becomes −1 and satisfies the same removal-selection condition. The function does not reject it merely because the original counter was zero.

12. **Payload mutation.** If the closing callback changes the selected entry’s payload, the subsequent payload read uses that later value. No ordering is required between that read and the collection callback-field read.

13. **Distinct finalization objects.** If finalization capture selects A while the initial +48 accesses select other objects, the initial hook uses its separately observed target. The +24 invocation and final +48 read still use A.

14. **Independent final hook.** If the retained object’s +48 field is cleared before the final read, the **(0, 1)** call is omitted. If it becomes nonzero before that read, the call may occur even when the initial +48 check was zero.

15. **Minimum routing value.** Second word −2,147,483,648 produces index 2,147,483,647 without overflow in index derivation. This does not establish counter-decrement behavior at the minimum signed value.

**Inferred intent:** The counter resembles a reference count, the collection operation resembles removal, and the callback sequence resembles retirement or finalization. Notification placement may suggest protocol boundaries. None establishes resource ownership or locking.

**Documented_only unknowns:**

- Pointer representation and complete object layouts.
- Counter arithmetic behavior outside the representable signed range.
- Whether the non-returning dependency terminates, traps, unwinds, or transfers control elsewhere.
- Dependency effects on globals, handles, entries, callback fields, and object lifetimes.
- Reentrancy, concurrency, and memory-ordering guarantees.

## Evidence

Established behavior is derived from the supplied static representation: argument widths, signed branch conditions, byte offsets, distinct retained-address and global-root accesses, dependency arguments, counter writes, and call ordering.
