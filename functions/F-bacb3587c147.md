# F-bacb3587c147

## Purpose

F-bacb3587c147 resolves a two-word position into a 32-bit location and a 32-bit length, using a preferred mapping lookup and, when necessary, a fallback lookup.

Its established behavior includes:

- Capturing a scale before calling either lookup dependency.
- Falling back on any nonzero preferred-lookup status.
- Computing two unsigned 32-by-32-bit products.
- Capping one product against a stored 64-bit limit using unsigned comparisons.
- Passing a mapping-relative position to a conversion dependency.
- Computing the location using a format-dependent base and a mapping component read **after** the conversion dependency returns.
- Selecting the length by comparing a wrapped difference, interpreted as signed 64-bit, against the unsigned 32-bit request.

The mapping component used for the location is not necessarily its earlier lookup-derived value. Its storage address is exposed to the preferred dependency. A dependency may retain that address, and the conversion dependency may subsequently change the still-live storage through shared dependency state.

The apparent intent is position translation with a scale involving 512-unit increments and a bounded remaining length. Units, storage-format semantics, and the conversion dependency’s operation remain inferred or unknown.

## Behavior

### 1. Capture the scale

The function reads the unsigned 32-bit field at Context offset `0x160`. Denote this captured value by \(S\).

This read precedes the preferred lookup. Subsequent calculations use \(S\), not a later reread of that field. A dependency’s later change to the Context scale does not replace the captured value.

### 2. Resolve the mapping

F-9b61ee28728d receives:

- Context and Object.
- The two input position words.
- Addresses of three local 32-bit result objects.

The consumed result roles are:

- An unsigned relative-origin quantity, \(J\).
- A 32-bit location component, represented as signed.
- An unsigned boundary quantity, \(N\).

A zero status accepts this path and skips fallback. Any nonzero status invokes F-0c688a5353e6; the preferred status is not directly propagated.

F-0c688a5353e6 receives Context, Object, the position words, and addresses designating:

- A 12-byte scratch region.
- A table containing sixteen 32-bit words.
- A signed 32-bit selected index.
- A 4-byte scratch region.
- The boundary-result object.

The scratch regions have no visible initialization before the call.

If the fallback returns nonzero, the function returns that exact 32-bit status immediately. Neither explicit caller-output store occurs.

On fallback success, the selected index identifies a pair of table words. The function first copies the pair’s first word into the location-component object. It then subtracts the second word from \(N\), modulo \(2^{32}\), and stores the result as \(J\).

Indices 0 through 7 select complete pairs within the sixteen-word table. No visible bounds check enforces this range. Behavior for other indices is not established as a valid table access.

The location-component object is the same object whose address was supplied to the preferred dependency, including when that dependency returned nonzero. Thus fallback assignment does not eliminate the possibility of a later dependency-mediated modification.

### 3. Calculate and cap the boundary

The function computes the exact unsigned 64-bit product:

\[
C = S \times N.
\]

Both operands are unsigned 32-bit quantities, so the mathematical product fits in 64 bits.

It compares \(C\) against Object’s limit using unsigned word comparisons:

1. Compare the candidate’s high word against the stored high word.
2. Read the stored high word again to determine equality.
3. If the high words match, compare the low words.
4. If the candidate is rejected, read the stored limit as a 64-bit value and select that replacement.

With stable Object storage, the selected boundary is:

\[
E = \min_{\mathrm{unsigned}}(C,\text{Object limit}).
\]

This minimum interpretation depends on stability. The limit is not captured once before comparison: repeated high-word reads and a separate replacement read are visible. No atomicity or synchronization guarantee is established.

### 4. Form the relative position and call the conversion dependency

Using the mapping-origin result, the function forms another exact unsigned product:

\[
M = S \times J.
\]

It subtracts \(M\) from \(P\) with low-word subtraction and a borrow into the high word. The resulting pair represents:

\[
R = P-M \pmod{2^{64}}.
\]

No local check requires \(P \ge M\).

F-7071f254f784 receives four 32-bit arguments, in this order:

1. Low word of \(R\).
2. High word of \(R\).
3. `0x200`, meaning 512.
4. Zero.

Its 32-bit return value, denoted \(Q\), contributes directly to the location calculation. The caller does not interpret it as an error status.

The argument pattern suggests a conversion or division involving 512. Division semantics, signedness, rounding, and exceptional behavior are not established by the supplied body.

### 5. Read the base and the current location component

After F-7071f254f784 returns, the function reads Context’s 16-bit discriminator.

- For `0x482b`, the base is the unsigned field at offset `0x174`, logically shifted right by 9.
- Otherwise, the base is the signed 16-bit field at offset `0x12`, sign-extended and converted into the 32-bit arithmetic domain.

Denote the selected base by \(B\).

The location-component object is read for the location expression **after the conversion call and after base selection**. Denote its value at this read by \(A_{\text{late}}\).

The earlier lookup-derived or fallback-assigned component does not unconditionally determine \(A_{\text{late}}\). In particular:

- F-9b61ee28728d received the object’s address.
- That object remains live during F-7071f254f784.
- The supplied body imposes no requirement that the preferred dependency discard the address or that the conversion dependency preserve the object.
- Shared dependency state can therefore permit the conversion dependency to modify the object before this read.

The location store receives:

\[
L =
B + (S \mathbin{\mathrm{shr}} 9)
    \times \operatorname{u32}(A_{\text{late}})
  + \operatorname{u32}(Q)
\pmod{2^{32}}.
\]

Here, \(\operatorname{u32}\) means the corresponding 32-bit bit pattern interpreted as unsigned.

The scale is shifted before multiplication. Its low nine bits do not contribute to this term. Negative location components contribute through their unsigned 32-bit representations, with the sum wrapping modulo \(2^{32}\).

The discriminator, selected base, and location component are all read after the conversion dependency. None is guaranteed to reflect the state immediately after lookup.

### 6. Select and store the length

The function subtracts the original input position from the previously selected boundary:

\[
D = E-P \pmod{2^{64}}.
\]

The subtraction uses low-word arithmetic and a borrow into the high word.

The final branch’s sign and signed-overflow conditions are equivalent to comparing the signed 64-bit interpretation of \(D\) against Requested length extended to a nonnegative signed 64-bit value.

- If signed \(D \le \text{Requested length}\), store the low 32 bits of \(D\).
- Otherwise, store Requested length.

Consequences:

- A nonnegative \(D\) larger than `0xffffffff` selects Requested length.
- A negative \(D\) selects its low word, not zero.
- Equality selects the difference’s low word.
- A zero request does not force a zero result when \(D\) is negative.
- The result need not be numerically bounded by Requested length.

The function returns zero after the length store.

## Side effects

On success, the explicit caller-output stores occur in this order:

1. Location output.
2. Length output.

If the destinations are identical, the final word contains the selected length. No overlap detection or compensation is visible.

Important ordering boundaries are:

- Scale capture precedes both lookups.
- Fallback table extraction follows fallback success.
- Boundary selection and relative-position formation precede the conversion call.
- The conversion call precedes discriminator, base, and location-component reads.
- Those reads precede the location store.
- The location store precedes the length store and final zero return.

The function uses automatic scratch and result storage. It contains no visible dynamic allocation, release, or explicit ownership transfer. Passing local addresses establishes their availability for the calls; it does not establish that dependencies refrain from retaining them.

Retained pointers do not gain a supported lifetime beyond the function’s return. Conversely, their possible use while the objects remain live cannot be excluded. This distinction is material to the late location-component read.

A fallback error prevents this function’s two explicit output stores, but does not imply that the complete call left memory unchanged. Dependencies may modify Context, Object, globals, shared state, or other reachable storage. Their allocation and ownership behavior is unknown.

No rollback is visible.

## Acceptance examples

These are conditional static examples, not runtime observations. Assume valid memory and stable directly read fields unless stated otherwise. Stability of those fields alone does **not** imply stability of the address-exposed location component.

1. **Preferred success suppresses fallback.**  
   If F-9b61ee28728d returns zero with usable results, F-0c688a5353e6 is not called. If the remaining operations complete, both output stores occur and the status is zero.

2. **Fallback status replaces preferred failure.**  
   If the preferred lookup returns 7 and fallback returns 11, the function returns 11 without either explicit output store. Dependency side effects remain possible.

3. **Fallback pair extraction.**  
   Suppose fallback succeeds with index 2, boundary quantity 20, and selected words 9 and 6. The function assigns 9 to the location-component object and derives \(J=14\). The later location uses 9 only if that object still contains 9 when read. If the second word is instead 21, \(J=\texttt{0xffffffff}\).

4. **Unsigned boundary cap.**  
   With \(S=1024\), \(N=10\), and stable limit 9000, \(E=9000\). With limit 12000, \(E=10240\).

5. **Ordinary location with an unchanged component.**  
   Let \(S=1024\), \(N=10\), limit at least 10240, and \(P=2500\). Let the matching-format base field be 4096 and the conversion return be 4. If \(A_{\text{late}}=3\), the location is:
   \[
   8+2\times3+4=18.
   \]
   Requested length 1000 produces length 1000 because \(D=7740\). The location result requires the stated late component value, not merely an earlier lookup result of 3.

6. **Conversion changes the exposed component.**  
   Under the same values as example 5, suppose lookup initially writes 3, but the conversion dependency uses a retained address obtained through shared dependency state and changes the component to 5. The location is then:
   \[
   8+2\times5+4=22.
   \]
   Stable Context and Object fields do not exclude this outcome.

7. **Signed alternate base.**  
   With a nonmatching discriminator, alternate base −1, and both remaining location contributions zero at evaluation, the location bit pattern is `0xffffffff`.

8. **Position beyond the boundary.**  
   If \(E=100\) and \(P=101\), \(D\) represents signed −1. The length is `0xffffffff`, including when Requested length is zero. No local error status is generated.

9. **Large positive difference.**  
   If \(D=\texttt{0x0000000100000000}\) and Requested length is 32, the length is 32 rather than the difference’s zero low word.

10. **Negative signed interpretation despite a large unsigned value.**  
    If \(D=\texttt{0x8000000000000005}\), the length is 5 for every unsigned 32-bit request.

11. **Coincident outputs.**  
    If both output addresses designate the same writable word, success leaves the selected length there, overwriting the earlier location store.
