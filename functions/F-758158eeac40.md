# F-758158eeac40

## Purpose

F-758158eeac40 obtains a node address, conditionally initializes part of its payload, increments a container counter, attaches the node at a supplied position, performs state-dependent structural repair, and writes the acquired node address to a caller-provided output slot.

**Established static evidence:** the routine operates on 32-bit links, a 32-bit counter, one-byte node states, a header-like object, and two structural-update dependencies. It does not search for an insertion position or validate the supplied position.

**Inferred intent:** this is insertion into a red-black tree, with a sentinel header holding the root and cached extremes. Under that interpretation, state zero means red, state one means black, and the structural-update dependencies perform rotations.

The visible routine alone does not establish those dependencies’ behavior or guarantee that the resulting structure satisfies tree invariants.

## Behavior

### Acquisition and payload handling

The first dependency call is F-6e3d6d0cc5b4, supplied with the container address. Its result is retained as the acquired node address throughout the routine.

The routine forms the address 16 bytes beyond that result and tests the derived address against zero. It does **not** test the acquired node address itself for zero.

If the derived address is nonzero, the routine calls F-f4fd698ba468 with that payload address and the input-object address. After the call returns, the visible memory-access order is:

1. Read the 32-bit input word at offset 8.
2. Read the 32-bit input word at offset 4.
3. Write the offset-4 word to offset 4 from the dependency’s returned address.
4. Write the previously captured offset-8 word to offset 8 from that returned address.

The returned destination is not checked and is not established to equal the supplied payload address. Both input reads occur after the dependency returns, so they observe any changes it made to the input.

This ordering matters for overlapping storage: the offset-8 source value is captured before either destination store.

If the derived payload address is zero, the call and both copies are skipped, but the rest of the routine still executes. Under ordinary 32-bit address arithmetic, an acquired address of zero produces a derived address of 16 and therefore does not take this skip path. Exceptional or wrapped-address behavior is not otherwise established.

### Counter update

After payload handling, the routine reads the container’s 32-bit counter at offset 20, adds one, and writes it back.

This precedes insertion-side selection, any comparison call, structural linking, repair, and the final output write. Consequently, a later failure can occur after the counter has changed.

The supplied representation expresses the addition using a signed 32-bit value. It provides no explicit overflow check. Portable behavior at the signed maximum, including whether execution wraps or fails, is **documented_only** rather than guaranteed.

### Insertion-side selection

The routine selects the left-link path without calling F-31a0b2b5649a when either:

- The header address read from the container equals the proposed parent address; or
- The third argument is nonzero.

The header-equality condition is evaluated first.

Otherwise, F-31a0b2b5649a is called with:

- The address 25 bytes into the container.
- The input-object address.
- The address 16 bytes into the proposed parent.

A nonzero result selects the left-link path; zero selects the right-link path.

Two retained values, initially equal to the third and fourth arguments, are both set to zero on the comparison-call path. They remain zero even if the comparison result selects left insertion. Their later significance is described under Dependencies.

No ordering relation, duplicate policy, or purity guarantee is established for the comparison dependency. Subsequent header reads use memory as it exists after the call.

### Attachment and header maintenance

On the left-link path, the first structural store writes the acquired node address to offset 8 of the proposed parent. The routine then reloads the container’s header address.

- If the reloaded header differs from the proposed parent, its offset-8 field is replaced only if that field currently equals the proposed parent.
- If the reloaded header equals the proposed parent, its offset-4 field is set to the acquired node address. The container’s header address is then loaded again, and the acquired node address is written to offset 12 of that header.

On the right-link path, the acquired node address is first written to offset 12 of the proposed parent. The routine then reloads the container’s header address. That header’s offset-12 field is replaced only if its current value equals the proposed parent.

After these operations, the proposed parent address is written to offset 4 of the acquired node.

Under the conventional sentinel interpretation, inserting through a stable header initializes its left extreme, root, and right extreme in that order. Other insertions update the applicable cached extreme only when the proposed parent is its current target.

Those higher-level results require suitable storage and aliasing conditions. The visible contract is the access sequence: it does not promise that repeated header loads or link traversals produce identical values.

There is no check that the selected child link is empty, that the proposed parent belongs to this container, or that insertion preserves ordering.

### Repair entry and stopping conditions

The acquired node initially becomes the current repair node.

At the beginning of each iteration, the routine reloads the header and its offset-4 link. If the current node equals that apparent root, repair stops without testing its parent’s state.

Otherwise, the routine loads the current node’s parent. A nonzero parent state stops repair. Only a parent state of zero enters the repair branches.

The routine then loads the parent’s parent as the grandparent and compares the parent address with the grandparent’s left link. Equality selects one branch; every other case selects the opposite branch. There is no separate check that the parent equals the grandparent’s right link.

### Parent matches the grandparent’s left link

The grandparent’s right link supplies the uncle address.

If the uncle is nonzero and its state is zero, the routine:

- Writes state one to the parent and uncle.
- Follows the current node’s parent and grandparent links to write state zero to the reached grandparent.
- Follows those links again to choose the next current node.

Repair then continues upward.

If the uncle is zero or has nonzero state, the routine checks whether the current node equals the parent’s right child.

- If so, it calls F-447693a4cb8d with the container and parent, then makes the previously saved parent address the current node.
- It then writes state one to the current node’s parent and state zero to its grandparent, using the links available at those accesses.
- It calls F-c9e19efcf19b with the container and the grandparent address obtained through the current node’s links.

The next iteration repeats the root and parent-state checks.

### Parent does not match the grandparent’s left link

The previously loaded grandparent’s left link supplies the uncle address.

A nonzero uncle with state zero causes the same parent-and-uncle recoloring and upward continuation described above.

Otherwise, the routine checks whether the current node equals the parent’s left child.

- If so, it calls F-c9e19efcf19b using the six-argument occurrence described under Dependencies, then makes the previously saved parent address the current node.
- It writes state one to the current node’s parent and state zero to its grandparent.
- It calls F-447693a4cb8d with the container and the grandparent address obtained through the current node’s links.

State tests distinguish zero from nonzero, not exclusively zero from one. For example, a preexisting state byte of 128 stops the parent-state test just as a state byte of one does.

Structural dependencies are not assumed to preserve links, state bytes, header fields, or globals. Subsequent traversals use the memory contents then present. Aliasing can also affect later traversals after the routine’s own writes.

### Completion

After repair stops, the routine reloads the container’s header address, follows its offset-4 link, and writes state one at that linked address. No null check protects this final root-state store.

Only afterward does the routine write the originally acquired node address to the output slot. It returns without a direct result.

The output is the acquired node, not the current repair node, which may have moved upward.

### Six-argument occurrence of F-c9e19efcf19b

This occurrence is reached in the branch where the parent does not match the grandparent’s left link, the uncle is absent or has nonzero state, and the current node matches the parent’s left child.

The six supplied values, in order, are:

1. Container address.
2. Saved parent address.
3. Observed uncle address.
4. A 32-bit value determined by the uncle check.
5. Retained insertion-control value.
6. Retained proposed-parent value.

The fourth value has exactly two established cases:

- **Nonnull uncle:** the uncle’s nonzero state byte, widened unsigned to 32 bits. The byte is assigned before comparison with zero; the supplied value is not the comparison result.

A nonnull uncle with state zero instead takes the recoloring path and does not reach this call in that iteration.

The final two values retain the original third and fourth arguments when insertion-side selection skipped F-31a0b2b5649a. Both are zero when that dependency was called.

## Acceptance examples

These are conditional expectations from static evidence, not executed tests.

1. **Insertion through a stable empty header.**  
   Given valid storage, a proposed parent equal to the unchanged header, and dependencies preserving the relevant fields, no comparison call occurs. Header offsets 8, 4, and 12 receive the acquired node address in that order. The node’s parent becomes the header. Repair recognizes the node as root, writes state one, and writes its address to the output slot.

2. **Explicit left insertion.**  
   With a nonzero insertion-control value and a non-header parent, no comparison call occurs. The parent’s left link is overwritten even if occupied. The header’s left-extreme field changes only if it equals that parent when checked.

3. **Comparison-selected right insertion.**  
   With zero insertion control, a non-header parent, and comparison result zero, the parent’s right link is overwritten. The header’s right-extreme field changes only on equality with the parent. The retained fifth and sixth values for any later six-argument repair call are both zero.

4. **Nonzero parent state.**  
   If the acquired node is not root and its parent state is 128, repair stops at that test. Final root recoloring and the output write still occur, assuming their accesses are valid.

5. **Zero-state uncle.**  
   With zero-state parent and nonnull zero-state uncle, the parent and uncle receive state one and the reached grandparent receives state zero. Repair continues upward; the six-argument structural call is not taken in that iteration.

6. **Nonnull uncle at the six-argument call.**  
   Given the required branch relationships and uncle state 128, the fourth supplied value is 128 widened to 32 bits—not zero and not one.

7. **Null uncle at the six-argument call.**  
   Given the required branch relationships and a null uncle, the third supplied value is zero and the fourth is the previously loaded grandparent address. No uncle-state read occurs.

8. **Overlapping payload storage.**  
   If an offset-4 destination store overlaps the offset-8 input word, the final offset-8 destination store still uses the value captured before that first store.

9. **Zero acquisition result.**  
   A zero result is not treated as an allocation failure. Under ordinary 32-bit address arithmetic, the derived payload address is 16 and payload initialization is attempted. No graceful error return is established.
