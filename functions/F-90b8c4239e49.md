# F-90b8c4239e49

## Purpose

F-90b8c4239e49 maps a pair of integer inputs to a result restricted to 16 bits. It has three possible resolution paths:

1. A direct arithmetic mapping for a restricted pair of input ranges.
2. An arithmetic extension of a restricted first-input range, conditional on a secondary result from F-870c4fcf7295.
3. An exact-key search in a shared table, followed, when the matching descriptor is nonzero, by F-9b364c7d5a0a.

The first successful arithmetic path bypasses the table. A failed secondary-result check on the second path returns zero immediately; it does not fall back to the table.

The constants resemble rules for composing Hangul characters. That interpretation is **inferred intent**, not an established requirement. The numeric behavior below is the contract; character validity or encoding semantics must not be added independently.

## Interface

### Inputs

Under the recovered 32-bit data model:

- **First input:** a signed 32-bit integer. Some range checks interpret its bit pattern through unsigned 32-bit subtraction.
- **Second input:** an unsigned 32-bit integer.

Neither input is treated as a caller-supplied pointer.

### Output

The function returns an unsigned 32-bit value in the inclusive range `0x0000` through `0xFFFF`.

For ordinary completion, the selected arithmetic or dependency result is masked with `0xFFFF`. Consequently:

- High result bits are discarded, not validated.
- Zero can mean a failed lookup, a rejected arithmetic extension, or a successful computation whose low 16 bits are zero.
- No distinct error code identifies which condition produced zero.

The secondary-result rejection path returns zero directly, with the same observable return width and value.

| Arithmetic bias | Added to the first path’s arithmetic expression |

## Behavior

### 1. Gate the arithmetic paths by the second input

The arithmetic paths are considered only when unsigned subtraction of `0x1161` from the second input produces a value less than `0x62`.

This selects the inclusive interval:

- Lower endpoint: `0x1161`
- Upper endpoint: `0x11C2`
- Number of values: 98

A second input outside that interval proceeds directly to the table path.

### 2. Attempt the first arithmetic mapping

Within that interval, the function compares the second input with the shared threshold.

When the comparison is true, it forms the unsigned range offset of the first input from `0x1100`. It then performs another threshold comparison and requires the selected offset to be less than `0x13`.

For a stable threshold, this path therefore requires both:

- Second input strictly below the threshold.
- First input in the inclusive interval `0x1100` through `0x1112`.

The threshold itself is excluded.

When selected, the result before masking is:

**588 × first input + 28 × second input + arithmetic bias**

Only its low 16 bits are returned. No dependency is called and no table lookup occurs.

There are two threshold comparisons in the supplied representation. The first controls whether the range offset is replaced by the first-input offset; the second controls whether the arithmetic mapping may be selected. If the shared threshold can change between those observations, the stable-threshold range description is insufficient. In particular, if the first comparison is false but the second becomes true, the offset tested against `0x13` remains the second-input offset from `0x1161`. Actual load count and concurrent-change semantics are not established.

### 3. Attempt the arithmetic extension

If the first mapping was not selected, the function considers another arithmetic path.

Within the enclosing second-input interval, its second-input conditions reduce to:

- Second input in `0x11A8` through `0x11C2`, inclusive.

The first input must satisfy either of these unsigned-offset checks:

- Offset from `0xAC00` is less than `0x2800`.
- Offset from `0xD400` is less than `0x3A4`.

These adjacent intervals together select:

- First input in `0xAC00` through `0xD7A3`, inclusive.

The first arithmetic path retains precedence if it has already been selected.

For an eligible pair, the function calls F-870c4fcf7295 with:

1. First input minus `0xAC00`.
2. The constant `0x1C`, or 28.

The function then examines a secondary machine result associated with that call, rather than its ordinary primary result.

- **Secondary result nonzero:** return zero immediately.
- **Secondary result zero:** return the low 16 bits of  
  **first input + second input − `0x11A7`**.

A nonzero secondary result does not initiate a table search.

The checked secondary result may be a remainder, but that interpretation is not established by this caller alone.

For eligible inputs, the successful arithmetic result lies between `0xAC01` and `0xD7BE`. Thus this path’s own result does not lose high bits during the final mask.

### 4. Search the shared table

If neither arithmetic path returns, the function uses the second input as an exact search key.

The table layout consists of 53 records. Each record contains two consecutive 32-bit unsigned words:

| Word within record | Meaning |
|---|---|
| First | Search key |
| Second | Packed descriptor |

Each record occupies eight bytes under the recovered data model. The last record’s key is at word offset 104 from the table base; its descriptor is at word offset 105.

Before searching, the function checks the endpoint keys:

1. Read the first record’s key and require it to be no greater than the second input.
2. Only if that succeeds, read the last record’s key and require the second input to be no greater than it.

Failure of either comparison produces a zero descriptor and therefore a zero return.

If both bounds checks succeed, the function performs an inclusive binary search over the 53 records:

- Comparisons are unsigned.
- The midpoint is the lower of the two middle records when a candidate interval has an even number of records.
- A smaller search input discards the midpoint and all later records.
- A larger search input discards the midpoint and all earlier records.
- Equality selects that record’s descriptor.
- Exhaustion without equality selects a zero descriptor.

The function does not validate key ordering. Ascending ordering is a precondition for reliable lookup of arbitrary stored keys. Duplicate keys are not rejected; if duplicates contain different descriptors, the search traversal determines which descriptor is selected, not an explicit first-match or last-match policy.

### 5. Interpret the selected descriptor

A descriptor equal to zero causes a zero return without calling F-9b364c7d5a0a.

For a nonzero descriptor:

- Its low 16 bits select an offset measured in four-byte units.
- Its high 16 bits form a separate unsigned argument.

The function calls F-9b364c7d5a0a with:

1. Lookup-data base plus four times the descriptor’s low 16 bits.
2. The descriptor’s high 16 bits.
3. The original first input.

The dependency result is masked to 16 bits and returned.

The maximum encoded byte offset is `0x3FFFC`, or 262,140 bytes. The caller does not establish that this address or any region subsequently accessed by the dependency is valid.

A nonzero descriptor may have either half equal to zero:

- A zero high half still results in a call.
- A zero low half passes the unadjusted lookup-data base.
- Only an entirely zero descriptor suppresses the call.

## Side effects

### Reads and their ordering

The established logical ordering is:

1. Test the second-input arithmetic gate.
2. If inside that gate, perform the threshold-dependent checks.
3. If the first mapping succeeds, obtain the arithmetic bias and return the arithmetic result.
4. Otherwise, if the extension is eligible, call F-870c4fcf7295 and act on its secondary result.
5. Only when no arithmetic path returns, inspect the table endpoint keys and perform the search.
6. Only after selecting a nonzero descriptor, obtain the lookup-data base and call F-9b364c7d5a0a.
7. After that dependency returns, mask its result and return.

Short-circuit behavior matters: the last table key need not be accessed when the first endpoint comparison fails. Descriptor reads occur only after a key equality is found.

This is logical access ordering supported by the supplied representation, not a guarantee about exact machine load counts, caching, or instruction ordering.

### Writes, ownership, and lifetime

No direct write to shared memory or caller-owned memory is shown. The function itself performs no visible allocation or release.

That does **not** establish that its dependencies are pure:

- Either dependency may modify global state.
- F-9b364c7d5a0a may access or modify the memory reached through its first argument.
- Neither dependency’s allocation, retention, or release behavior is known.
- No ownership transfer or borrowed-lifetime guarantee can be inferred merely from passing an address.

After either dependency call, this function performs no further shared-data lookup on that returning path.

### Errors and invalid storage

No explicit error-reporting channel, bounds exception, or storage-validation mechanism is shown.

The normal contract requires readable table storage when the fallback path accesses it, and suitable lookup storage when a nonzero descriptor is delegated. Behavior for invalid addresses, unavailable storage, or a dependency that does not return is not defined here.

## Acceptance examples

These are conditional static acceptance examples, not executed tests.

### Direct arithmetic mapping

Given:

- First input `0x1100`.
- Second input `0x1161`.
- A stable threshold greater than `0x1161`.
- Arithmetic bias equal to some established value.

The function returns the low 16 bits of **2,683,548 plus that bias**. Neither dependency is called, and the table is not searched.

For the same stable threshold conditions, first input `0x1113` fails the first-input range check. It does not receive this direct mapping.

### Threshold equality

If the second input equals the stable threshold, the first arithmetic mapping is not selected. Evaluation continues to the extension conditions and, if those are not satisfied, the table path.

### Successful extension

Given first input `0xAC00` and second input `0x11A8`, the first mapping is ineligible because of the first input.

F-870c4fcf7295 receives zero and 28. If its checked secondary result is zero, the function returns `0xAC01`. The table is not searched.

### Rejected extension

For that same input pair, if the checked secondary result is nonzero, the function returns zero immediately—even if the table would contain a matching key with a nonzero descriptor.

### Extension boundaries

- First input `0xD7A3` and second input `0x11C2`, with a zero checked secondary result, produce `0xD7BE`.
- First input `0xD7A4` fails the extension’s first-input range requirement.
- Second input `0x11C3` bypasses both arithmetic paths entirely.
- Second input `0x11A7` is excluded from the extension.

Inputs rejected by those eligibility checks proceed to the table rather than being rejected outright.

### Descriptor-based delegation

Suppose the fallback search finds descriptor `0x00030002`.

F-9b364c7d5a0a receives:

- Lookup-data base plus eight bytes.
- The value 3.
- The original first input.

If it returns `0x12345678`, this function returns `0x5678`.

### Zero and partially zero descriptors

- Descriptor `0x00000000`: return zero without delegation.
- Descriptor `0x00000002`: delegate using base plus eight bytes and second argument zero.
- Descriptor `0x00030000`: delegate using the unadjusted base and second argument three.

### Search miss

If the second input is outside the table endpoint bounds, or the ordered-table search exhausts its interval without equality, the function returns zero without calling F-9b364c7d5a0a.
