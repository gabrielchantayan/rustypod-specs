# F-c8c1f4d887d3

## Purpose

F-c8c1f4d887d3 conditionally replaces a caller-designated integer and conditionally invokes a caller-supplied callback. Its classification depends on the integer’s **previous value**, not on the replacement stored at that location.

The callback’s presence controls whether the integer is accessed at all. A null callback produces status **26** without accessing the integer or the two external data sources. A non-null callback permits replacement before the classification outcome is known. Consequently, a classification rejection does not imply that the integer was left unchanged.

The represented normal statuses are **0** and **26**:

- **0** accompanies either a zero classification result without callback invocation, or a selected callback invocation that returns normally.
- **26** accompanies either an absent callback or a classification rejection. Neither case directly invokes the callback.

These are structural meanings, not established application-level success or error definitions. The function does not establish ownership of the supplied storage.

## Interface

### Supplied integer location

The first input designates a signed integer object. The supplied representation explicitly gives the pointee a signed integer type; its signedness is therefore not wholly unknown. However, the representation does not independently specify that type’s byte width, alignment, padding, or complete value representation.

When the callback is non-null, the function reads the previous integer and assigns an externally obtained replacement through the same pointer. There is no represented pointer-validity check before those accesses.

The pointer is not dereferenced when the callback is null. In particular, a null integer pointer and a null callback produce the null-callback outcome without an attempted integer access.

No array length, record layout, subordinate pointer, or variable-sized payload is present in this interface.

### Supplied callback

The second input is a nullable callable target. A selected invocation supplies no explicit arguments. This does not establish the target’s complete prototype or calling convention.

Nullness is the only represented validation of this input. A non-null address is not thereby established to be executable, compatible, or safe to invoke.

The callback’s ordinary result is not used to select the enclosing function’s return status.

### External data

Two external storage locations participate:

- The **replacement source** supplies the value assigned to the integer object.
- The **adjustment source** supplies the other operand of the classification additions.

Their declarations are not included. Their widths, signedness, qualifiers, initialization requirements, and synchronization rules are therefore unresolved. Assignment to the supplied integer may involve a conversion whose details depend on those missing declarations.

These names identify behavioral roles only. Neither source has an established application meaning or ownership relationship.

### Return value

The result has a represented size of four bytes. Its only explicit normal values are decimal **0** and decimal **26**.

The four-byte result does not establish the width of the separately accessed integer object or either external source. Pointer widths and byte order are also not supplied.

The previous integer, replacement value, adjustment value, and callback result are not returned.

### Preconditions for defined normal completion

With a non-null callback, the supplied location must support the represented integer read and write. Reached external-source accesses and arithmetic must also be valid under the applicable type and execution rules.

Callback compatibility and normal return are required only when invocation is selected. A non-null but incompatible target is not inspected further on paths that do not select invocation.

The body provides no clean-error contract for inaccessible storage, incompatible invocation, invalid arithmetic, or violated object-lifetime rules. Status 26 must not be interpreted as a general validation failure covering those conditions.

## Behavior

### Classification contract

The previous integer is retained before replacement. Classification combines that retained value with the adjustment source. It does not read the destination again to discover the replacement.

There are two conditional classification observations:

- The first determines whether the computed sum is zero.
- Only a nonzero first result permits the second, which determines whether its computed sum is decimal 14.

The adjustment source appears in each reached classification expression. There is no represented capture requiring both expressions to use one shared adjustment observation.

The complete normal-outcome relation is:

| Callback and classification conditions | Replacement assignment | Direct callback invocation | Normal result |
|---|---|---|---|
| Callback is null | Absent | Absent | 26 |
| Callback is non-null; first sum is zero | Present | Absent | 0 |
| Callback is non-null; first sum is nonzero; second sum is 14 | Present | Once | 0 after normal callback return |
| Callback is non-null; first sum is nonzero; second sum is not 14 | Present | Absent | 26 |

The second sum has no behavioral role when the first sum is zero because its expression is not reached.

This relation establishes that every represented normal return of 26 excludes direct callback invocation by this execution. A return of 0 does not establish whether invocation occurred. Neither status, by itself, identifies the final contents of storage that a callback could modify.

### Replacement is independent of acceptance

For every non-null-callback path that reaches classification normally, replacement has already occurred. Neither classification rejection nor the zero-result outcome restores the previous integer.

The assigned replacement need not equal the retained integer. Its numeric value does not directly replace the retained operand in classification. It can nevertheless affect classification indirectly if the destination validly aliases the adjustment source.

No rollback mechanism is represented.

### Stable and changing adjustment observations

When the adjustment remains stable and both additions have the same defined arithmetic interpretation, the outcomes simplify:

- A sum of zero produces status 0 without invocation.
- A sum of 14 selects invocation.
- Any other defined sum produces status 26 without invocation.

Stability is a condition for that simplification, not a guarantee supplied by this function.

If the applicable execution model permits different observations of the adjustment source, the first observation controls whether further classification is reached, and the second controls callback selection. A second observation cannot cause invocation after a first sum of zero.

The separate expressions do not prove that two physical memory transactions occur. Whether an implementation may reuse a load, and whether externally changing values are validly observable, depends on declarations and execution rules not supplied here.

### Arithmetic and conversions

The constants used for classification are exactly zero and decimal 14. The rejection status is exactly decimal 26.

Although the retained operand is a signed integer, the addition’s effective type cannot be determined without the adjustment source’s type. Promotions or conversions may produce a different arithmetic domain. Neither arbitrary-precision mathematics nor fixed-width modular arithmetic is established.

Accordingly:

- Signed overflow is not assigned a wrapping result by this contract.
- A negative operand is not assumed to remain negative after all applicable conversions.
- The replacement assignment is not assumed to preserve an external source value that the destination type cannot represent.
- Boundary cases require the missing type and platform rules before an outcome can be specified.

Small representable examples are useful conditional obligations. They do not resolve behavior at integer limits.

### Callback completion

Selected invocation follows replacement and both reached classification expressions. At most one direct invocation occurs in this execution.

After the callback returns normally, the enclosing function returns 0 without another represented integer access, external-source evaluation, or restoration assignment. The callback’s ordinary result does not change that status.

A callback that does not return normally prevents this path from reaching its represented normal return. Faults, nonlocal exits, and nontermination have no handling specified by the supplied body.

Reentrant executions are distinct executions. The one-direct-invocation limit does not limit invocations caused by recursion or other callback activity.

## Side effects

### Access ordering

The previous-value read precedes replacement. The replacement source is obtained for the assignment before the destination write completes. The write precedes all reached adjustment evaluations, and callback invocation follows the classification that selects it.

There is one explicit read and one explicit write through the supplied integer pointer before any selected callback invocation. No subsequent access through that pointer is represented.

With a null callback, none of these integer accesses or external-source evaluations is reached.

These are source-level access and sequencing properties. They do not establish atomicity, hardware transaction counts, inter-thread visibility, or a synchronization protocol.

### Aliasing and layout

No non-aliasing restriction is supplied. Valid aliasing must therefore be considered without granting permission for otherwise invalid overlaps or incompatible accesses.

If the integer destination and adjustment source designate the same compatible object, replacement can change the adjustment observed during classification. The retained operand still reflects the destination’s earlier value.

If the destination aliases the replacement source, the assignment obtains its source value before overwriting the destination. This does not establish how partial overlap or differing access widths would behave.

The representation supplies no record offsets, byte-level encoding, or justification for interpreting partially overlapping objects as interchangeable.

### Ownership and lifetime

The body contains no direct allocation, deallocation, ownership transfer, or retained-pointer operation.

The caller’s ability to supply a pointer does not prove that the caller owns the referenced object. Likewise, the absence of a post-callback dereference does not independently authorize the callback to release that object.

Callback effects remain unknown. The callback may modify accessible memory, change external data, interact with resources, or reenter this function if permitted by its own contract. No assumption that it preserves globals or preserves the replaced integer is justified.

## Acceptance examples

These examples describe conditional requirements, not executed tests. Unless an example says otherwise, assume valid compatible storage, defined representable arithmetic and conversions, stable non-aliased external values, and a compatible callback that returns normally.

| Conditions | Required observable outcome |
|---|---|
| Callback is null | Status 26; no integer access, external-source evaluation, or direct callback invocation. |
| Callback and integer pointer are both null | The same null-callback outcome; no attempted dereference. |
| Previous integer is 5, adjustment is −5, replacement is 100, and the applicable arithmetic makes the sum zero | Store 100; return 0 without invoking the callback. |
| Previous integer is 5, adjustment is 9, replacement is 100 | Store 100; invoke the callback once; return 0 after its normal return. |
| Previous integer is 5, adjustment is 8, replacement is 100 | Store 100; return 26 without invoking the callback. |

**Retained-value distinction.** In the 5-plus-9 case, storing 100 does not change classification to 100 plus 9. The retained operand remains 5.

**Rejection still mutates.** In the 5-plus-8 case, status 26 does not imply an unchanged integer. The required replacement has already occurred.

**Zero short-circuit.** When the first sum is zero, there is no second adjustment evaluation and no direct callback invocation, regardless of what a hypothetical later observation might have yielded.

**Valid destination/adjustment aliasing.** Suppose the destination and adjustment source are the same compatible object, initially 5, and the replacement source supplies 9. If the access and conversion rules permit this arrangement, classification uses retained 5 with post-replacement adjustment 9. Stable observations select the callback.

**Different permitted observations.** Suppose a valid execution permits adjustment 8 for the first classification and 9 for the second, with retained integer 5. The first sum permits further classification; the second selects invocation. This example supplies no concurrency protocol and does not legitimize a data race.

**Callback mutation.** If the selected callback changes the destination to 77 and returns normally, this function performs no later restoration write. Its normal status remains 0.

**Callback result.** A selected callback’s ordinary returned value does not change the enclosing status from 0.

**Invalid storage.** With a non-null callback and an inaccessible integer pointer, clean rejection with 26 is not required. The represented integer access precedes classification.

**Arithmetic boundary.** No unconditional result is required for operands whose outcome depends on unresolved overflow or conversion rules.
