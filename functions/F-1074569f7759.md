# F-1074569f7759

## Purpose

F-1074569f7759 selects a bucket in a linked structure, examines its chain, and returns the address of a link slot. It returns either when a previously read link contains null or when a node passes both a stored-value equality check and a callback-based comparison.

The function also publishes a callback-produced 32-bit value and directly increments three state counters at defined points.

The result is a **slot address, not a node address or a separate success indicator**. On acceptance, the returned address is the retained slot through which the examined node was reached. The function does not recheck that slot or node after the comparison callback. Acceptance therefore does not guarantee that the slot still contains the examined node, that the node still contains the matching value, or that either allocation remains alive.

**Inferred intent:** A bucketed lookup primitive returning a location suitable for finding an existing entry or identifying an insertion position. The produced value appears hash-like. These interpretations do not establish insertion, ownership, or dependency arithmetic.

## Interface

### Arguments and result

The function accepts:

1. **State address:** Addresses a structure accessed as four-byte words.
2. **Lookup value:** An uninterpreted 32-bit value passed to the value-producing and comparison callbacks.
3. **Output address:** Receives the value-producing callback’s retained 32-bit result.

The observed representation uses 32-bit address-bearing words and four-byte link slots. Behavior under a different pointer-width model is not established.

The return value is a link-slot address. It can address either a bucket entry or a node’s next-link field. There is no separate result distinguishing acceptance from chain exhaustion.

### Preconditions and limits

Normal completion requires every executed memory access to be valid and every invoked target to be callable under the actual calling convention. Objects must remain accessible for the operations that use them. No argument, callback, bucket-index, or chain validation is visible.

Unsigned bucket-address arithmetic wraps at 32 bits. Such wrapping is not itself prohibited by the observed arithmetic, but it does not establish that the resulting address is accessible or suitably aligned.

The counter updates use signed-word addition in the supplied representation. Their behavior at signed-overflow boundaries is **documented_only**.

A chain that never produces null or an accepted node can prevent termination. Callback nontermination can do so independently.

## Behavior

### Value production and output publication

The function reads the value-producing callback address from state offset 8 and invokes it with the original lookup value as its sole explicit argument.

After that callback returns, the function retains its 32-bit result and, in this order:

1. Reads, increments, and writes the counter at state offset 56.
2. Writes the retained result to the output address.

The callback therefore executes before either direct write. Its mutations can affect the counter value subsequently read.

The produced value remains retained independently of the output storage. Later changes to that storage do not refresh the retained value. However, the output write can affect subsequent execution if its destination aliases a later-read state field, link slot, node field, or other relevant storage. Counter writes can likewise affect aliased storage.

If the callback does not return normally, subsequent operations are not established.

### Bucket selection

After the output write, the function reads the word at state offset 24 and invokes F-d7be9cfb4000 with two explicit arguments:

- The retained produced value.
- The word just read from offset 24.

A 32-bit unsigned value supplied through a secondary-result channel becomes the initial index candidate. The evidence does not identify that value as an ordinary primary return value.

After this invocation returns, the function reads state offset 20 and compares the candidate with that threshold as unsigned 32-bit values:

- A candidate greater than or equal to the threshold remains selected.
- A candidate less than the threshold causes a second invocation of F-d7be9cfb4000. Only the retained produced value is explicitly supplied in the available representation. The second invocation’s secondary result replaces the candidate.

There is no second threshold comparison or visible bucket-count check.

F-d7be9cfb4000’s operation is unresolved. Neither a remainder operation nor a complete argument list for the conditional invocation may be assumed.

### Initial link-slot selection

After bucket selection finishes, the function reads and retains the comparison-callback address from state offset 4. It then reads the bucket-array base word from offset 0.

The initial slot address is formed by multiplying the selected unsigned index by four and adding the base word, with both operations reduced modulo \(2^{32}\). The unsigned index causes this address expression to use unsigned arithmetic despite the base word’s signed-word representation.

The resulting 32-bit word is converted to a link-slot address. The function reads that slot to obtain the initial node address.

The timing matters:

- The first dependency invocation can change the threshold before its read.
- Either dependency invocation can change the callback field or bucket base before their reads.
- After capture, the comparison-callback address is not refreshed during traversal.

No dependency is established to preserve those fields.

### Traversal and acceptance

Traversal retains both the current slot address and the node address previously read through it.

If that retained node address is null, the function returns the current slot address immediately. This invocation performs no node-counter increment or node-field read for that null observation.

For each nonnull retained node address, the function:

1. Reads, increments, and writes the state counter at offset 88.
2. Reads the node’s stored value at offset 8.
3. Checks equality with the full retained 32-bit produced value.

A mismatch skips the comparison callback.

On equality, the function first reads, increments, and writes the counter at state offset 60. It then reads the node’s offset-0 field and invokes the retained comparison callback with that field and the original lookup value.

A zero callback result accepts the node and returns the retained current slot address. Every nonzero result rejects it; no further significance is attached to the result’s sign or magnitude.

Acceptance depends on the **earlier equality observation** and the subsequent zero callback result. The offset-60 counter write or callback may have changed the stored value or incoming slot in between. There is no equality recheck, incoming-slot reread, or lifetime validation before returning.

### Advancement after rejection

After either a stored-value mismatch or a nonzero comparison result, the next current slot becomes the field at offset 4 within the retained node. Reading that field supplies the next node address.

When the comparison callback runs, this next-link read occurs afterward. A rejecting callback can therefore redirect traversal by changing the retained node’s next link.

Changing only the incoming slot does not replace the already retained node used for advancement. If a rejecting callback invalidates that node, the subsequent next-link access has no established safe outcome.

### Counters and failure behavior

The three increment sites are direct operations of this invocation:

- Offset 56: once after the value-producing callback returns.
- Offset 88: once per nonnull node examined.
- Offset 60: once per observed stored-value equality, before comparison.

These counts describe executed increment operations, **not net changes in counter contents**. Callees may overwrite counters or invoke this function reentrantly. Normal return, distinct storage, preserved lifetimes, and absence of concurrent activity do not exclude those synchronous effects.

No saturation, overflow check, explicit ordinary error result, or recovery path is visible. Invalid execution conditions do not have an established null-return contract.

## Side effects

### Direct writes

Subject to execution reaching each operation, this invocation directly writes:

- The incremented offset-56 counter.
- The retained 32-bit produced value to the output destination.
- The incremented offset-88 counter for each examined nonnull node.
- The incremented offset-60 counter for each stored-value equality.

There are no explicit assignments to bucket links or node fields. Nevertheless, those locations can change through output or counter aliasing, callback activity, or F-d7be9cfb4000.

A simple entry-to-exit counter delta requires additional assumptions: relevant storage does not alias other writes, callees do not modify the counters directly or reentrantly, and no unresolved overflow occurs. Without these assumptions, even a counter with no direct increment by this invocation may change.

### Calls and retained values

On a normally completed path:

- The value-producing callback runs once.
- F-d7be9cfb4000 runs once or twice according to the unsigned threshold decision.
- The comparison callback runs only for stored-value equality, and traversal stops at its first zero result.

The original lookup value, produced value, and captured comparison-callback address remain retained rather than being reloaded from their originating storage.

No callee is established to preserve counters, other state, globals, links, or allocations. Reentrant calls are not excluded.

### Ownership and lifetime

No ownership transfer is established for the arguments, node fields, produced value, or returned address. The output receives a 32-bit value, not an established owned allocation.

The function directly performs no allocation or release. This does not constrain its callees’ allocation or release behavior.

No synchronization, pinning, or lifetime extension is visible. A callback can invalidate the allocation containing a slot before the function returns its retained address. Such a return does not establish that dereferencing the result is safe.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Unless varied, assume normally returning callees, valid executed accesses, distinct storage, no concurrent mutation, preserved object lifetimes, and counters away from unresolved overflow boundaries.

**Counter counts below refer only to increment operations directly executed by this invocation.** They exclude callee writes and increments performed by reentrant invocations. The shared assumptions do not require callees to preserve counters.

### Empty selected bucket

Given selected index 3, base word 0x1000, and null in slot 0x100C:

- The output receives the produced value.
- This invocation executes one offset-56 increment.
- It executes no offset-88 or offset-60 increment.
- It makes no comparison-callback invocation.
- It returns 0x100C.

Either bucket-selection invocation may nevertheless change any counter. No final traversal-counter value follows from the absence of direct traversal increments.

### First-node acceptance with preservation

If the first node’s stored value matches, the comparison callback returns zero, and that callback preserves the node and incoming slot:

- This invocation executes one increment at each of offsets 56, 88, and 60.
- It returns the bucket-slot address.
- That slot still contains the accepted node.
- It does not subsequently read that node’s next link.

The increment counts alone do not establish entry-to-exit counter deltas.

### Acceptance after mutation

If the comparison callback clears the incoming slot and returns zero:

- The function returns the retained incoming-slot address without rereading it.
- The returned slot can contain null despite acceptance.

If the callback instead changes the node’s stored value, acceptance still occurs without rechecking equality. If it invalidates the slot’s allocation, the returned address has no established dereference safety.

### Mismatch followed by acceptance

If the first node mismatches and its next link reaches a second node that matches and is accepted:

- This invocation executes two offset-88 increments and one offset-60 increment.
- Only the second node triggers its comparison callback.
- The returned address is the first node’s next-link slot.

These are direct-operation counts, regardless of additional counter effects inside callees.

### Matching value followed by rejection

If a sole node matches, its callback returns nonzero, and its next link remains null:

- This invocation executes one offset-88 increment and one offset-60 increment.
- It reads the next link after the callback.
- It returns that next-link field’s address after observing null.

### Callee mutation of counters

Suppose the selected bucket is empty, and the first F-d7be9cfb4000 invocation writes 9 to offset 88, with no later write to that counter.

The final offset-88 value is 9 even though this invocation executes no offset-88 increment. A reentrant callee could instead produce additional counter changes through nested traversal. Neither case contradicts the direct-operation counts.

### Threshold boundary

An initial secondary result equal to the unsigned threshold does not trigger a second dependency invocation.

A smaller result does trigger it. The replacement result is selected without another threshold check, even if it is also below the threshold.

### Wrapped bucket address

For selected index 0x40000408 and base word 0xFFFFFFF0:

- Multiplication by four wraps to 0x00001020.
- Addition wraps to 0x00001010.
- The initial slot read uses the address converted from 0x00001010.

Normal traversal remains conditional on that converted address being valid. The function does not require the unbounded product or sum to fit in 32 bits.

### Changes affecting later reads

If a rejecting callback changes the retained node’s next link to another valid node, traversal follows that changed link.

Changing the state’s comparison-callback field does not replace the already captured target.

If the output address aliases state offset 24, the output write replaces that word before it is read for the first dependency invocation.
