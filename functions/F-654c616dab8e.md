# F-654c616dab8e

## Purpose

F-654c616dab8e constructs two related collections from an input context: a counted table of 16-bit values and a table of addresses of length-prefixed byte buffers. It derives the number of buffers from the value table using a 32-bit global and arithmetic comparisons. Completed collections are published into a destination object.

The established behavior is structural. Interpreting the values as identifiers, the global as a format boundary, or the buffers as text is inferred intent, not an established format contract.

Successful publication ends with an explicit zero return. Other exits return the contents of a writable status location after any applicable cleanup. Because dependencies receive that location’s address and their retained-access behavior is unspecified, a zero return alone does not establish that publication occurred.

No runtime tests have been performed.

## Interface

### Arguments and accessed fields

The function receives two 32-bit address-valued arguments: a destination object and an input context.

The destination has these accessed fields:

| Byte offset | Access width | Meaning |
|---|---:|---|
| `0x108` | 16 bits | Unsigned capacity for the initial value count |
| `0x264` | 16 bits | Published initial count |
| `0x266` | 16 bits | Published derived count |
| `0x268` | 32 bits | Published value-table address |
| `0x26c` | 32 bits | Published pointer-table address |

The input context contains a 32-bit resource-context value at offset `0x1c`. This value is read before the first dependency call and retained for subsequent allocation and cleanup calls. Changes to that field afterward do not change the retained argument.

The function performs no direct validation of argument addresses, accessible ranges, alignment, or address-arithmetic overflow. Defined execution requires storage suitable for the accesses actually performed, including accesses through dependency-returned addresses.

### Constructed storage

The value table consists of consecutive 16-bit elements, at a two-byte stride.

The pointer table consists of consecutive 32-bit addresses, at a four-byte stride.

Each successfully completed byte buffer contains a payload of 0 through 255 bytes followed by an explicitly written zero byte. Embedded zero bytes are permitted by the visible behavior; no character encoding or text validation is established.

### Status interface

A writable 32-bit status location is supplied to several dependencies. It is not visibly initialized before the initial count dependency. That dependency must establish a usable status before the function examines it.

There are two return mechanisms:

- After the four publication writes, the function returns the literal value zero.
- All other exits return the status location’s contents when that final return is reached.

Capacity rejection explicitly writes status `3` and reaches the final return without intervening dependency calls. Other failure paths may perform cleanup before the final status read.

## Behavior

### Initial count and capacity

The function first caches the resource-context value, then calls F-8f49ed59b67e with the input context and status address.

Its 16-bit return is interpreted as an unsigned initial count, ranging from 0 through 65,535. If status is nonzero, the function proceeds directly to the final status-based return. It does not directly read capacity, allocate storage, or publish results on that path.

When status is zero, the function reads the destination’s 16-bit unsigned capacity. A count greater than capacity sets status to `3` and exits. Equality passes.

The capacity read therefore occurs after the initial dependency call. Dependency changes to the destination before that read can affect acceptance.

### Value-table construction

For an accepted count, F-6dd003795db7 receives, in order:

1. The cached resource context.
2. Element size `2`.
3. Zero.
4. The initial count.
5. Zero.
6. The status address.

The returned 32-bit value is retained as the value-table address. The meanings of the two zero arguments are unknown.

If status is zero, F-d036abe1e536 receives the input context and twice the initial count. Its 32-bit return replaces status. This requested byte quantity ranges from 0 through 131,070; the multiplication does not overflow 32 bits.

If that operation succeeds, F-7efb5338f0fa is called exactly once per initial element. Each returned 16-bit value is immediately stored into the next value-table slot, in ascending order. There is no status check between these element reads.

After the last store, F-9787e15c337d is called once with the input context. Its return is ignored. There is no status check between this call and the derived-count scan.

For an initial count of zero, the allocation, zero-byte F-d036abe1e536 call, and F-9787e15c337d call still occur when preceding stages succeed. There are no individual value reads.

### Derived count and global observations

The derived count begins at zero. The function scans the stored values in ascending order, reading each as an unsigned 16-bit quantity widened to 32 bits.

The scan uses a **32-bit global**, not a threshold captured at entry. Its observations occur after F-9787e15c337d. Any preceding dependency may have changed it; no dependency contract establishes otherwise.

For each element, the supplied representation evaluates the global in four separate expressions, in this order:

| Observation | Role |
|---|---|
| First | Determines whether signed subtraction of the global from the element would overflow |
| Second | Supplies the subtrahend for a 32-bit difference |
| Third | Supplies the value for an equality comparison with the element |
| Fourth | Supplies the signed lower-bound comparison against the element |

No single per-element snapshot is established.

If the fourth observation, interpreted as signed 32-bit, is less than or equal to the element, the update decision uses the element minus 257 instead of the preceding comparison results. This difference replaces the derived count only when it is strictly greater than the current count under a signed 32-bit comparison. The stored replacement is its low 16 bits.

If the fourth observation is greater than the element, the earlier three observations govern the decision. Replacement occurs when:

- The element differs from the third observation; and
- The sign of the 32-bit difference formed using the second observation matches the signed-overflow indicator formed using the first observation.

A replacement on this latter path stores the original element’s low 16 bits. With differing global observations, that decision is not necessarily a comparison against one coherent threshold or against the current derived count.

**Conditional stable-global interpretation.** If every global observation throughout the scan sees the same signed value, the derived count is the maximum of zero and all positive differences “element minus 257” for elements at least that value. Under this condition:

- Elements at or below 257 cannot increase the count.
- Updates never decrease the count.
- The result is between 0 and 65,278 inclusive.

Without that stability condition, the unconditional range is **0 through 65,535**, because every replacement is masked to 16 bits. Inconsistent observations can permit replacement by an original element, including 65,535, or permit a decrease from an earlier derived count. The stable-global maximum characterization must not be applied unconditionally.

The source establishes neither synchronization for this global nor whether its observations can actually differ during a scan.

### Pointer-table allocation

F-6dd003795db7 next receives the cached resource context, element size `4`, zero, the derived count, zero, and the status address. Its return becomes the pointer-table address.

This call occurs even when the derived count is zero. The unconditional maximum requested pointer storage is 262,140 bytes; under the stable-global interpretation it is 261,112 bytes.

A nonzero status skips entry construction and proceeds to outer cleanup. With zero status and zero derived count, the function proceeds directly to publication.

### Buffer construction

Entries are constructed in ascending pointer-table order.

For each entry, F-6fa39a8df0d4 receives the input context and status address. Only the low eight bits of its return are retained as the payload length. A nonzero status stops entry construction before allocating that entry’s buffer.

Otherwise, F-6dd003795db7 receives the cached resource context, element size `1`, zero, payload length plus one, zero, and the status address. Requested buffer sizes therefore range from 1 through 256 bytes.

The returned buffer address is written into the current pointer-table slot **before** allocation status is checked.

If allocation status is zero, F-0c21b5cad025 receives the input context, that returned address, and the payload length. Its 32-bit return replaces status.

If payload status is zero, the function rereads the buffer address from the current pointer slot and writes a zero byte at the payload-length offset. Thus the terminator uses the address currently stored in the slot, not necessarily the address originally returned by allocation. Dependencies are not established to preserve aliased table contents.

Only after that terminator write does processing advance. The increment clears bit 16 of the resulting index. Since the derived count cannot exceed 65,535, this mask does not alter the visited construction or cleanup indices.

A zero-length payload still causes allocation of one byte, a zero-length payload call, and a terminator write.

### Publication

After every required entry is complete, the function performs these direct destination writes in order:

1. Initial count at `0x264`, using 16 bits.
2. Derived count at `0x266`, using 16 bits.
3. Value-table address at `0x268`, using 32 bits.
4. Pointer-table address at `0x26c`, using 32 bits.

It then explicitly returns zero without calling F-bf7242c98d06 on the constructed storage.

These are sequential stores. Atomic publication and synchronization are not established. The function does not read or release previous result addresses before overwriting them.

### Cleanup and final status

The direct cleanup sequence depends on the stage reached:

| Exit cause | Cleanup calls |
|---|---|
| Initial count reports nonzero status | None |
| Count exceeds capacity | None |
| Value-table allocation reports nonzero status | F-bf7242c98d06 on zero, then on the returned value-table address |
| F-d036abe1e536 returns nonzero | F-bf7242c98d06 on zero, then on the value-table address |
| Pointer-table allocation reports nonzero status | F-bf7242c98d06 on the returned pointer-table address, then on the value-table address |
| Entry length, buffer allocation, or payload operation reports nonzero status | Full slot cleanup, then pointer-table cleanup, then value-table cleanup |

Full slot cleanup visits **every pointer slot below the derived count**, including unconstructed slots. For each slot, the function reads its 32-bit contents, calls F-bf7242c98d06 with the cached resource context and that value, then writes zero into the slot.

A failed buffer allocation has already had its returned address stored in the current slot. A failed length read has not written that entry’s slot. Future slots have not been initialized by this function.

After slot cleanup, the pointer-table address is passed to F-bf7242c98d06, followed by the value-table address. Cleanup return values are ignored.

The function then reads and returns the status location. It does not save and restore the triggering status around cleanup. Earlier dependencies received the status address, and the supplied contracts do not exclude cleanup modifying that location through retained access or shared state. Consequently, cleanup may change the returned status, including to zero, without causing publication.

No direct publication stores occur on these cleanup paths. This does not constrain writes performed by dependencies themselves.

## Side effects

### Input and shared state

Input operations occur in this order: count acquisition; capacity comparison; value allocation; the twice-count operation; individual value acquisition and stores; F-9787e15c337d; the derived scan; pointer allocation; then repeated length acquisition, buffer allocation, payload operation, and terminator write.

No input-position rollback is visible. Even capacity rejection occurs after the count dependency has run.

The resource-context field is cached before dependencies run. In contrast, the global used by the scan is observed later and repeatedly. Neither input state nor global preservation is guaranteed by the supplied dependency information.

### Storage and ownership

Construction writes the value table, pointer slots, buffer terminators, and any payload storage written by dependencies. Failure cleanup also zeroes pointer slots after their cleanup calls.

Successful publication makes the constructed addresses reachable through the destination. This suggests transfer to a result consumer, but actual ownership transfer, allocator lifetime, and eventual disposal obligations remain unknown.

F-bf7242c98d06 is used in a cleanup role. Its actual release behavior, acceptance of zero, treatment of arbitrary slot contents, and ownership effects are not established. Safe cleanup of unconstructed slots therefore requires additional dependency guarantees.

Replacing existing destination results has no visible built-in disposal step. No assumption is made that any dependency preserves aliased memory, globals, or ownership.

## Acceptance examples

These are conditional static expectations, not executed tests. They assume accessible storage and the stated dependency behavior.

1. **Capacity rejection.** If count acquisition returns 6 with status zero and the subsequently read capacity is 5, status becomes `3`. No allocation, cleanup, or direct publication occurs. Capacity 6 would pass.

2. **Empty sequence.** With initial count zero and successful operations, both table-allocation calls occur, as do the zero-byte preparation operation and F-9787e15c337d. No values or lengths are individually acquired. Publication stores two zero counts and the returned table addresses.

3. **Stable global.** For values 257, 258, and 260, if every scan observation sees a signed global value at most 258, the derived count is 3. If all observations instead see a value greater than 260, it is zero.

4. **Global changed before scanning.** If the global is 258 at entry but a preceding dependency changes it to 261 and it remains 261 during the scan, the preceding value sequence produces zero, not 3.

5. **Small value under stable observations.** If every relevant observation admits element 1, that element still does not increase the count. Its difference from 257 is negative under the signed comparison.

6. **Inconsistent observations.** For element 65,535, suppose the first three global observations are zero and the fourth is 65,536. The fourth observation rejects the subtraction-by-257 path, while the earlier comparison results permit replacement by 65,535. This conditional case demonstrates why 65,278 is not an unconditional bound; it does not establish that such intra-iteration changes occur.

7. **Length truncation.** A length result of `0x1234` with zero status produces payload length 52, allocation count 53, and, after a successful payload operation, a terminator at offset 52. A low byte of zero instead requires a one-byte allocation and a zero-length payload operation.

8. **Early entry failure.** If the derived count is three and the first length operation fails, cleanup still reads and processes all three slots. Safety depends on their contents being acceptable to F-bf7242c98d06.

9. **Payload failure.** The current buffer address is already stored. No terminator is written for that entry. All pointer slots are subsequently processed by cleanup.

10. **Status changed by cleanup.** If a payload operation returns status 7 but cleanup changes the retained status location to zero, the function returns zero without direct publication. If cleanup leaves status unchanged, it returns 7. Neither preservation nor mutation is guaranteed.
