# F-111863ad315a

## Purpose

F-111863ad315a prepares state in a caller-supplied object, invokes an operation through an associated object's dispatch table, and returns a one-byte status.

The established behavior has three principal outcomes:

- If no associated object exists and an acquisition dependency returns a nonzero result, the function stores and returns status **3**.
- If acquisition is unnecessary or reports success, the function transfers selected descriptor fields into the primary object and invokes the associated object's operation. A nonzero status left in the primary object by that operation ends processing.
- Otherwise, the function optionally invokes another dependency, invokes a final processing dependency, and stores its one-byte result as the status.

The business meanings of the copied fields, associated object, and status values are not established. “Acquisition,” “descriptor,” and “status” are behavioral labels, not verified domain terminology.

## Behavior

### Entry and acquisition gate

The first established write clears the primary object's status byte at `0x6A8` to zero. Any prior status is discarded.

The function then reads the 32-bit associated-object slot at `0x61C`.

If that slot is nonzero, acquisition is skipped.

If that slot is zero, the function calls F-6651d6fbf9ca with these ordered arguments:

1. Primary-object address plus `0x61A`.
2. The context value.
3. The address of the associated-object slot at `0x61C`.

The acquisition result is tested as a 32-bit integer for zero versus nonzero.

- A nonzero result selects the failure path: store byte value **3** at `0x6A8`, then read and return that byte.
- A zero result continues processing.

The acquisition result, not the post-call value of the associated-object slot, determines this branch. The function performs no separate validity check on the associated object after a zero acquisition result.

A nonzero acquisition result prevents all subsequent calls and descriptor transfers performed by this function. It does not undo effects already performed by F-6651d6fbf9ca.

### Preparation dependency

On the continuing path, the function calls F-fac138f80b6d with:

1. Primary-object address plus `0x58`.
2. The context value.
3. The numeric value `0x400`, or 1024.

Its return value is not used.

The third argument does not, by itself, prove that the dependency copies, initializes, or otherwise accesses exactly 1024 bytes. Its units and meaning are unknown.

All descriptor transfers described next occur after this call returns. Consequently, they use descriptor contents as available after any effects of this dependency, rather than a snapshot taken on entry.

### Descriptor transfer

The following transfer order is established:

1. Read the descriptor's 32-bit field at `0x00` and write it to primary-object offset `0x458`.
2. Read the descriptor's 32-bit field at `0x04` and write it to primary-object offset `0x45C`.
3. Read the descriptor's 32-bit field at `0x0C` and retain that value.
4. Read the descriptor's 32-bit field at `0x08` and write it to primary-object offset `0x08`.
5. Write the retained value from descriptor offset `0x0C` to primary-object offset `0x0C`.
6. Read descriptor byte `0x11` and write it to primary-object offset `0x460`.
7. Read descriptor byte `0x10` and write it to primary-object offset `0x10`.

These are width-preserving transfers. No numeric conversion, byte-order reversal, or interpretation of the fields is established.

The ordering matters if source and destination storage overlap. In particular, the field at descriptor offset `0x0C` is captured before the write to primary-object offset `0x08`. The operation is not established as a simultaneous descriptor snapshot or a general overlap-safe copy.

### Associated-object dispatch

After the transfers, the function obtains the associated-object pointer from primary-object offset `0x61C`, follows that object's leading dispatch-table pointer, and invokes the callable entry at table byte offset `0x1C`.

The arguments are:

1. The associated-object pointer as receiver.
2. The descriptor address plus `0x18`.

No dispatch return value is used.

The dispatch uses the associated-object state available at this stage, after the preparation dependency and descriptor writes. The function does not preserve an entry-time associated-object pointer for later dispatch.

On return from dispatch, the function reads the primary object's status byte at `0x6A8`.

- If nonzero, it skips the optional and final dependencies and proceeds directly to a fresh read of the status byte for return.
- If zero, processing continues.

This is a gate on the status present after dispatch. The source does not establish which earlier participant, if any, produced that value.

### Optional and final processing

When the post-dispatch status is zero, the function reads the primary object's byte at `0x10`.

If that byte is nonzero, F-d86d14a75ba2 is called with:

1. Primary-object address plus `0x20`.
2. Primary-object address plus `0x58`.

Its return value is unused. No intervening status check occurs after this optional call.

The function then calls F-d0f88f4a6898 with the primary-object address. Its one-byte result is written to the status field at `0x6A8`.

Finally, the function reads the status field and returns that byte.

Thus, a status written by the optional dependency does not itself cause an early return. If the final dependency returns normally, its returned byte becomes the function's explicit final status assignment.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

### Acquisition rejected

Given an initially zero associated-object slot, if F-6651d6fbf9ca returns any nonzero 32-bit value:

- Status is cleared before acquisition.
- The function subsequently stores and returns **3**.
- It performs no descriptor transfers and invokes none of the later dependencies.
- Acquisition's other effects are not rolled back.

### Existing associated object

Given an initially nonzero associated-object slot and valid downstream storage:

- F-6651d6fbf9ca is not called.
- F-fac138f80b6d runs before descriptor fields are read for transfer.
- Dispatch follows the descriptor transfers.

This holds regardless of the status value present before entry, because that value is first cleared.

### Acquisition reports success but supplies no usable object

Given an initially zero slot and a zero acquisition result, but no usable associated object afterward:

- The function does not convert this condition into status **3**.
- It continues toward preparation, transfer, and indirect dispatch.
- Successful completion is not established; the downstream pointer precondition is unmet.

### Dispatch leaves status nonzero

Suppose the status is **7** immediately after dispatch and remains unchanged through return:

- Neither F-d86d14a75ba2 nor F-d0f88f4a6898 is called.
- The function returns **7**.
- Previously transferred descriptor fields remain subject to any mutations already performed by dependencies.
