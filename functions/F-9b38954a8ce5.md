# F-9b38954a8ce5

## Purpose

F-9b38954a8ce5 selects an output representation for an unsigned 32-bit input and invokes a caller-supplied callback with an address and a requested byte count. Successful returns are one, two, three, six, or ten. The two-byte case consists of two ordered one-byte callback requests; every other case uses one request.

For inputs below 256, selection depends on the selection mask and, below 128, a classification byte reached through a globally stored address-resolution value. One selected path optionally writes a notification byte before invoking the callback. For larger inputs, unsigned range comparisons determine the visible formatting path and requested length.

The established contract covers local initialization, address-resolution and classification reads, branch precedence, dependency arguments, callback ordering, notification writes, and result handling. It does not establish exact output bytes or successful delivery of the requested number of bytes.

An escaping or hexadecimal-formatting purpose is inferred intent, not a guaranteed encoding.

## Interface

The function accepts five arguments, in order:

| Argument | Established interpretation |
|---|---|
| Input value | Unsigned 32-bit value, from zero through 4,294,967,295. |
| Selection mask | Unsigned 32-bit value. Copied into local storage on entry; used explicitly in low-input classification and branch selection. |
| Notification pointer | Nullable pointer. Copied into local storage on entry; conditionally used for a one-byte store on the notification path. |
| Output callback | Callable address. Initially copied into a local code-pointer-typed object and used as the target of output requests. |
| Callback context | Opaque 32-bit value passed as the first argument of each output callback. The visible body does not dereference it. |

Each callback receives:

1. The callback context.
2. An address identifying storage.
3. A requested byte count.

The callback result is tested only against zero. Zero means failure; every nonzero result means success for this function. No result is compared with the requested count. Under the recovered signed 32-bit result interpretation, negative callback results also count as success.

The function returns a 32-bit result:

| Result | Meaning |
|---|---|
| 1 | The selected one-byte callback request returned nonzero. |
| 2 | Both ordered one-byte requests returned nonzero. |
| 3, 6, or 10 | The corresponding single callback request returned nonzero. |
| 0xFFFFFFFF | A callback returned zero. |

The failure result represents negative one under signed 32-bit interpretation. Successful results report the selected representation length, not a verified delivered count.

The callback must support the observed argument contract. A non-null notification pointer must permit a one-byte write when the notification path is selected. Invalid addresses, dependency faults, or nonreturning calls have no visible recovery mechanism.

Pointer widths, byte order, complete calling conventions, and integer-to-code-pointer representation are not independently established.

## Behavior

### Entry state and local storage

Before range selection, the supplied body initializes local objects in this order:

1. A 32-bit object receives the original input.
2. A 32-bit object receives the original selection mask.
3. A pointer object receives the notification pointer.
4. A code-pointer-typed object receives the callback address.

These initializations occur on every path, including the six- and ten-byte formatting paths. They describe the visible body’s local state, not independently verified machine-level layout or capacity.

Every formatting call receives the address of the first object: the 32-bit object initialized with the original input. Its initial four-byte object representation therefore contains that input, in an unspecified byte order. The visible body makes no intervening assignment to that object before formatting.

For inputs below 256, the code-pointer-typed object is subsequently overwritten with the input masked by 0xFF and converted to that object’s pointer type. Its initial callback-address value is thus replaced on all low-input paths. Direct one-byte output and the second prefix request receive the address of this overwritten object.

For larger inputs, no such overwrite appears before formatting. The local copies of the mask and notification pointer, and the code-pointer-typed object initially containing the callback address, remain part of the established pre-formatting local state. Their relative addresses, padding, and accessibility from the formatter’s destination are not established.

The visible larger-input branch selection and explicit formatter argument selection do not use the selection mask or notification pointer. This is narrower than independence of output or side effects: unknown formatter behavior and destination extent prevent that broader guarantee.

### Classification and global address resolution

For an input below 128, the function obtains a classification byte through two ordered reads:

1. It reads a global address-resolution value.
2. It uses that value together with the low-input index to address and read one classification byte.

The classification byte is treated as unsigned and intersected with the supplied selection mask. This intersection produces the effective mask used for branch selection. Because the classification operand is an unsigned byte, only the low eight bits of the selection mask can survive.

The global read precedes the classification-byte read, which precedes the mask intersection and branch tests. The source does not establish a fixed classification-table base independent of that global value. Neither immutability of the global value nor its preservation by dependencies is established.

For inputs from 128 through 255, the effective mask is the selection mask intersected with 0x04. This path performs neither the global address-resolution read nor the classification-byte read. Its effective mask is therefore either zero or 0x04.

For inputs of at least 256, neither classification read occurs in the visible body.

The classification address expression identifies the low-input indexing behavior, but pointer width and address-arithmetic overflow rules are not independently established. Valid readable classification storage is a precondition for normal execution of the below-128 path.

### Low-input branch precedence

The effective mask selects processing in this order:

1. If its intersection with 0x61 is nonzero, select prefix or notification processing according to bit 0x08.
2. Otherwise, if its intersection with 0x06 is nonzero, select three-byte formatting.
3. Otherwise, select direct one-byte output.

Bit 0x08 alone does not select notification. It matters only when the 0x61 test succeeds. Other effective bits have no visible branch-selection effect.

Once classification has completed, no classification re-read appears in the selected callback sequence. A dependency’s later modification of accessible global state is not assumed impossible, but it does not cause an explicit reclassification in this invocation.

### Prefix path

If the effective mask intersects 0x61 and lacks bit 0x08:

1. Invoke the callback with the context, the fixed prefix-byte address, and count one.
2. If the result is nonzero, invoke the callback with the context, the address of the overwritten code-pointer-typed local object, and count one.
3. Return two if the second result is also nonzero.

A zero result from either callback returns 0xFFFFFFFF. Failure of the first prevents the second invocation. Failure of the second does not undo effects of the first.

There is no notification store on this path. The prefix byte’s value is unavailable.

The second request supplies the address of the local object, not the numeric input interpreted as an output-storage address. Equality between that object’s first byte and the input’s numeric low byte depends on pointer representation and byte order. Effects of the first callback on memory it can access are not excluded.

### Notification path

If the effective mask intersects 0x61 and contains bit 0x08:

1. If the notification pointer is non-null, store the byte value one through it.
2. Invoke the callback with the context, the address of the overwritten code-pointer-typed object, and count one.
3. Return one for a nonzero callback result, or 0xFFFFFFFF for zero.

A null pointer suppresses only the notification store, not the callback.

The store precedes callback invocation. The function performs no later clearing or restoration, including on failure. Nevertheless, the final notification value is not guaranteed: the callback may modify that location through an alias or other accessible state.

### Direct one-byte path

If neither higher-priority selection applies, invoke the callback with the context, the address of the overwritten code-pointer-typed object, and count one.

Return one for a nonzero result and 0xFFFFFFFF for zero. No notification store or formatter call occurs.

On a target with a compatible little-endian, value-preserving integer-to-pointer representation, the requested first byte would equal the input byte. That relationship is conditional, not independently established.

## Side effects

### Observable ordering and failure

The visible sequencing establishes:

- All four entry initializations precede range selection.
- The low-input code-pointer overwrite precedes classification or output.
- Below 128, the global address-resolution read precedes the classification-byte read and mask intersection.
- Formatting returns before its corresponding output callback.
- A notification store precedes its callback.
- The first prefix callback must return nonzero before the second occurs.
- A zero callback result terminates the selected sequence with failure.

Passing an address and count does not establish whether, when, or how the callback reads that storage.

The function does not retry, validate a delivered count, compensate for partial effects, or roll back writes. Failure may follow externally visible callback effects.

No preservation of globals by either dependency is established. In particular, the global address-resolution value must not be treated as invariant across calls merely because this body does not explicitly assign to it.
