# F-992b83e9731d

## Purpose

F-992b83e9731d replaces a descriptor’s storage with storage requested for a caller-selected number of four-byte elements. It copies an initial portion of the descriptor’s current storage, fills any additional elements from a caller-supplied four-byte value, invokes a dependency with the descriptor’s storage address, and publishes the replacement address and element count.

The inferred intent is resizing an owned array of opaque 32-bit elements. Allocation, deallocation, ownership transfer, and failure semantics are not established by this function alone. They depend on F-fab3799b3190 and F-58ba61416cc9.

The contract distinguishes the ordinary array-resizing interpretation from the actual observable access order. In particular:

- The descriptor is first read after the replacement-storage request.
- The source base is not held constant for every use.
- The fill value is read separately for each added element.
- The address passed to F-58ba61416cc9 is read after copying and filling.
- Descriptor publication occurs after F-58ba61416cc9 returns.

These distinctions matter if dependencies or aliased writes change memory that the function subsequently reads.

## Interface

### Inputs

1. **Descriptor address**

   A pointer to a descriptor represented by two consecutive 32-bit fields:

   | Byte offset | Width | Meaning in this function |
   |---|---:|---|
   | 0 | 4 bytes | Address representation of the element storage |
   | 4 | 4 bytes | Existing element count, interpreted as unsigned for count selection |

   The first field is read as an address and eventually overwritten with the replacement address. The second field is read as a count and eventually overwritten with the requested count.

   No additional descriptor fields are accessed explicitly.

2. **Requested element count**

   An unsigned 32-bit value. Each element occupies four bytes.

   The storage-request argument is the requested count shifted left by two bits in 32-bit unsigned arithmetic. It is therefore the low 32 bits of four times the requested count, not an overflow-checked byte count.

3. **Fill-value address**

   A pointer from which a four-byte value is read for each element added beyond the copied prefix.

   The function does not explicitly read this address when no added elements are needed. When filling is required, the pointed-to value is not cached across iterations.

### Output

The function returns the address obtained from F-fab3799b3190.

On a normal return, the final two explicit descriptor writes store:

1. The requested count at byte offset 4.
2. The returned replacement address at byte offset 0.

There is no separate success flag, error code, or explicitly implemented failure return.

### Representation and access requirements

The supplied representation uses four-byte elements, 32-bit integer fields, and a 32-bit storage-address field. Byte order is not established here. Elements are copied as opaque four-byte quantities; no element-level interpretation, construction, or destruction is visible.

For ordinary defined operation, all executed descriptor, source, destination, and fill-value accesses must address appropriately accessible memory. The implementation does not check these conditions.

The source does not establish portable behavior for invalid pointers, unsuitable alignment, inaccessible memory, arithmetic that produces invalid addresses, or overlapping objects whose accesses violate the underlying execution model.

## Behavior

### 1. Request replacement storage

The first explicit operation is a call to F-fab3799b3190 with the wrapped 32-bit byte count.

This call occurs even when:

- The requested count equals the existing count.
- The requested count is smaller than the existing count.
- The requested count is zero.

There is no same-size shortcut, in-place growth request, zero-count shortcut, or preliminary descriptor validation.

The returned address is retained as the replacement-storage address. No explicit null check follows.

Because the descriptor has not yet been read, any descriptor changes made by this dependency affect the state subsequently observed by this function.

### 2. Read source state and select the prefix length

After F-fab3799b3190 returns, the function reads the descriptor’s storage-address field to establish the initial source cursor. It then reads the existing-count field.

The number of elements selected for copying is the unsigned minimum of:

- The requested count.
- The descriptor count observed at this stage.

An existing-count field whose high bit is set is treated as a large unsigned count, not rejected as negative.

This selected prefix length remains fixed throughout the copy phase. The descriptor count is not repeatedly read to adjust it.

### 3. Copy four-byte elements in forward order

The destination cursor starts at the replacement-storage address. The source cursor starts at the storage address read after the storage-request call.

Each completed copy iteration:

1. Reads one four-byte source element.
2. Writes that value to the current four-byte destination element.
3. Advances both cursors by four bytes.

The implementation uses an endpoint comparison rather than a separate decreasing copy counter. Before each potential iteration, including the terminating check, it reads the descriptor’s storage-address field again and forms an endpoint by adding four times the selected prefix length.

Consequently, copying exactly the selected number of elements requires the descriptor’s storage-address field to remain stable during the copy phase, together with valid address arithmetic and valid source and destination ranges.

If a copy write aliases the descriptor’s storage-address field, the next endpoint check can observe the changed address. The function does not protect against this. It is therefore incorrect to promise fixed-length copying for arbitrary overlap.

The copy is forward, not overlap-safe relocation. If the replacement region overlaps unread source elements, a write can affect a later source read. There is no temporary snapshot of the source contents.

Under stable, non-overlapping ordinary conditions, the copied prefix consists of the first selected elements of the observed source storage.

### 4. Fill any additional elements

Once the copy loop terminates, filling begins at the selected prefix index and continues through the element immediately before the requested count.

For every filled element:

1. The function reads four bytes from the fill-value address.
2. It writes those four bytes into the corresponding replacement-storage element.

The fill address is the same input address each time, but its contents are re-read. If earlier writes change that location, a later fill can observe the changed value. The function does not guarantee that all added elements receive a value captured at entry.

When the requested count is no greater than the observed existing count, this phase performs no fill-value reads.

### 5. Invoke the old-storage dependency

After copying and filling, the function reads the descriptor’s storage-address field again and passes that value to F-58ba61416cc9.

This argument is not necessarily the initial source address. It is the address contained in the descriptor at this later point.

The inferred purpose of this call is to release the previous allocation. The function itself does not establish that the dependency frees memory, accepts null, leaves other state unchanged, or avoids touching the replacement storage.

At call entry, this function has not yet explicitly published the requested count or replacement address into the descriptor. Absent intervening mutations, the descriptor still contains its prior fields.

### 6. Publish the replacement

After F-58ba61416cc9 returns, the function writes the requested count to the descriptor’s second field, then writes the replacement address to its first field.

The ordering is observable: there is an intermediate state in which the count has been updated but the storage-address field has not yet received its final value.

The function then returns the replacement address retained from F-fab3799b3190. It does not reload its return value from the descriptor.

## Side effects

### Explicit memory effects

The function can perform:

- Four-byte reads from the descriptor.
- Four-byte reads from source elements.
- Four-byte writes to replacement elements.
- Repeated four-byte reads from the fill-value address.
- Two final four-byte descriptor writes.

No source elements beyond the selected prefix are explicitly copied under the stable-descriptor interpretation. Shrinking discards the suffix from the replacement representation without invoking any visible per-element cleanup.

Replacement storage is populated before the final descriptor writes. There is no explicit rollback if an access or dependency fails partway through.

### Dependency effects and ownership

All effects of F-fab3799b3190 and F-58ba61416cc9 remain relevant. Neither dependency may be assumed to preserve globals, descriptor memory, source contents, fill contents, or replacement contents without a separate contract.

The ordinary ownership interpretation requires additional premises:

- F-fab3799b3190 returns usable replacement storage.
- The supplied source address is acceptable to F-58ba61416cc9.
- That dependency does not invalidate the replacement storage or descriptor.
- The returned storage has the ownership and lifetime expected by the caller.

These are not enforced by F-992b83e9731d.

### Failure and exceptional behavior

There is no explicit handling for:

- Replacement-storage request failure.
- Byte-count overflow.
- Invalid descriptor fields.
- Inaccessible source or fill memory.
- Invalid destination storage.
- Dependency failure or non-return.
- Harmful aliasing.

A null replacement address is not itself converted into an error result. If element writes are required, the function proceeds toward those writes without checking the address. With zero requested elements, no element writes are needed, but the later dependency call and descriptor writes still occur.

No atomicity, locking, synchronization, or concurrent-reader safety is established.

## Acceptance examples

The following examples are conditional. They assume dependencies return normally, requested storage is usable, addresses and arithmetic are valid, the descriptor remains stable during copying, and memory does not overlap harmfully unless stated otherwise.

### Growth

Given an existing count of 2, source elements `11` and `22`, a requested count of 5, and a fill location containing `7` throughout filling:

- F-fab3799b3190 receives 20.
- The replacement receives `11, 22, 7, 7, 7`.
- The fill location is read three times.
- F-58ba61416cc9 receives the descriptor’s storage address observed after filling.
- The descriptor count is written as 5 before its address is written as the replacement address.
- The function returns that replacement address.

### Shrink

Given an existing count of 4 and a requested count of 2:

- The storage-request argument is 8.
- Only the first two elements are copied.
- The fill location is not read.
- The old-storage dependency is still invoked.
- The descriptor is updated to count 2 and the replacement address.

No visible operation preserves the discarded suffix elsewhere or performs per-element cleanup.

### Unchanged count

Given an existing count and requested count both equal to 3:

- The function still requests 12 bytes.
- It copies three elements.
- It performs no fill reads.
- It still invokes F-58ba61416cc9 and republishes the descriptor.

Equal counts do not imply a no-op or preservation of the original address.

### Zero requested count

Given a requested count of zero and otherwise valid descriptor access:

- F-fab3799b3190 receives zero.
- The copy phase performs no element reads or writes under a stable descriptor.
- The fill location is not read.
- F-58ba61416cc9 is called with the descriptor’s then-current storage address.
- The final descriptor count is zero, and its address field receives the dependency’s returned replacement address.

That address is not required by this function to be null.

### Storage-request mutation

If F-fab3799b3190 changes the descriptor before returning, prefix selection and the initial source address use the post-call descriptor state. They do not use an entry-time snapshot.

### Wrapped byte count

For a requested count of 1,073,741,824, the 32-bit storage-request argument is zero because multiplication by four wraps modulo 2³².

The requested element count itself remains 1,073,741,824 for subsequent decisions. This example establishes the argument calculation, not safe completion or sufficient storage.

### Fill-value aliasing

If an earlier destination write changes the memory at the fill-value address, later fill iterations read that changed memory. Acceptance must not require a single entry-time fill-value snapshot.
