# F-c357f0d7c693

## Purpose

F-c357f0d7c693 performs an ordered, synchronous device-initialization sequence: an initial command, readiness polling, an identification-stage command, two address-bearing commands, and a final status check.

Normal completion returns a 32-bit value of **1** only after every command has returned nonzero, readiness has been observed, and the final status check meets both required conditions. Each explicit failure selects a stage-specific diagnostic, invokes the diagnostic dependency once, and returns a 32-bit value of **0**, provided that dependency returns normally.

The command sequence and diagnostic labels suggest initialization of an MMC-like device into a transfer state. That is inferred intent, not a complete protocol specification. The established behavior consists of the visible arguments, reads, calls, branches, and return values described below.

## Interface

### Explicit and implicit inputs

The represented interface has no ordinary explicit parameters. Its behavior nevertheless depends on:

- An incoming 32-bit machine-register value used to initialize a local working word.
- A global context pointer read at three distinct entry-time sites.
- Context-relative 32-bit fields.
- Global 32-bit command selectors and a readiness-command argument.
- Results and side effects of dependencies.

The incoming register value does not control an explicit branch before being overwritten. Every normally continuing path that reaches the final status check has already replaced the working word with a readiness response having bit 31 set. The incoming value therefore does not determine the normal result.

### Context fields and pointer selection

The visible context layout is:

| Byte offset | Field width | Use |
|---|---:|---|
| 0x0C | 32 bits | Source of each address-bearing command argument |
| 0x10 | 32 bits | Value captured for subsequent timeout checks |
| 0x14 | 32 bits | Fourth command argument |

There is **not** a single context-pointer snapshot governing all these reads.

The supplied representation establishes three separate entry-time reads of the global pointer, in this order:

1. Read the pointer and retain its value for later context-field accesses.
2. Read the global pointer again and obtain the timeout value from offset 0x10 of that selected context.
3. During initial-command argument preparation, read the global pointer again and obtain the fourth argument from offset 0x14 of that selected context.

Initialization of the local working word occurs after the timeout-value capture and before initial-command submission.

The three pointer reads need not identify the same object if the global pointer changes between them. The representation does not establish instruction-level load coalescing, synchronization, or a stable-pointer invariant.

After the initial command, all visible context-field accesses use the pointer retained by the **first** read. The timeout checks use the value already captured through the **second** read. The initial command’s fourth argument comes through the **third** read.

### Output and failure boundary

The ordinary result is a 32-bit word:

- **1:** the final status dependency returns nonzero and the final working word satisfies the required masked comparison.
- **0:** an explicit failure is detected and diagnostic reporting returns normally.

No stage-specific numeric error code is returned. The diagnostic selection distinguishes failure stages.

These guarantees do not cover invalid memory accesses, dependencies that fail to return, or other abnormal interruption. No visible branch validates context pointers or converts memory-access faults into a normal failure result.

## Behavior

### Entry and initial command

After the entry-time captures described above, F-6e46c43c3113 receives four arguments:

| Argument position | Value |
|---|---|
| First | 32-bit constant 0x00200000 |
| Second | Zero |
| Third | Zero |
| Fourth | 32-bit value at offset 0x14, reached through the third entry-time global-pointer read |

A zero result selects the initial-command failure diagnostic. Timing initialization, readiness polling, and all later commands are skipped.

A nonzero result is passed to dependency D-01, the timing-initialization dependency. Its returned 32-bit value is retained as the token for every subsequent timeout check.

After D-01 returns, two readiness constants are captured in an established order:

1. The readiness command’s **second argument** is read.
2. The readiness command’s **selector**, used as its first argument, is read.

Both are 32-bit global values. Their numeric contents are unavailable. Once captured, both are reused throughout the readiness loop without further reads of those globals.

This ordering between the two separate assignments is established. It is distinct from the unresolved evaluation order of multiple reads within an individual command’s argument list.

### Readiness polling

At least one readiness-loop iteration is entered after successful initial-command completion and timing initialization.

Each iteration has this observable call order:

1. Call D-02, the timeout-check dependency, with the retained timing token and captured timeout value.
2. If D-02 returns nonzero, select the timeout diagnostic and stop initialization.
3. Call F-233fe84cf225 with the numeric argument 1.
4. Submit the readiness command through F-6e46c43c3113.
5. If submission returns zero, select the readiness-command failure diagnostic and stop.
6. Pass the nonzero command result to F-7b608acf5ce9.
7. Replace the local working word with that dependency’s 32-bit result and inspect bit 31.

The readiness submission uses the retained selector, retained second argument, zero as the third argument, and a fresh 32-bit read at offset 0x14 through the first, retained context pointer as the fourth argument.

Polling continues while bit 31 of the extracted response is clear. It ends successfully when:

**response AND 0x80000000 is nonzero.**

No other response bit affects readiness-loop exit.

The timeout decision precedes the delay-like call and command submission in every iteration. There is no additional timeout check after response extraction or between readiness completion and the identification-stage command. A condition that would make a later timeout check fail does not independently invalidate a readiness response already accepted in the current iteration.

No iteration-count limit is visible. The loop can continue indefinitely if timeout checks keep returning zero, commands keep succeeding, and responses keep bit 31 clear. Actual timing, timeout arithmetic, and the behavior of the delay-like dependency are undocumented.

### Identification-stage command

Once readiness is observed, F-6e46c43c3113 receives:

- A stage-specific global selector.
- Zero.
- Zero.
- A fresh read of offset 0x14 through the retained context pointer.

A zero result selects the identification-command failure diagnostic.

A nonzero result is followed by F-233fe84cf225 with argument 0x32, decimal 50. The caller does not visibly extract or inspect identification data from the successful command result.

### First address-bearing command

The next command uses:

- A stage-specific global selector.
- The 32-bit field at offset 0x0C through the retained pointer, shifted left by 16 bits.
- Zero.
- A fresh 32-bit read at offset 0x14 through the retained pointer.

Its diagnostic identifies this stage with relative-address assignment.

No visible range check constrains the address field to 16 bits. Under the ordinary 32-bit machine-shift interpretation, the argument consists of the field’s low 16 bits placed in bits 31 through 16, with bits 15 through 0 cleared; source bits above bit 15 are discarded.

The representation describes the source field as signed. It does not establish portable signed-language semantics for negative values or overflowing positive values. Exact instruction-level confirmation of the shift behavior remains documented_only.

A zero result selects the relative-address failure diagnostic. A nonzero result is followed by F-233fe84cf225 with argument 50.

### Second address-bearing command

The selection-stage command uses another global selector and independently rereads both context fields:

- Its second argument comes from a new offset-0x0C read, shifted left by 16 bits.
- Its fourth argument comes from a new offset-0x14 read.
- Its third argument is zero.

Both field reads use the retained pointer, not a fresh read of the global context pointer.

The address-bearing argument is recomputed. It can differ from the preceding command’s argument if the underlying field changes between accesses.

A zero result selects the selection-command failure diagnostic. A nonzero result is followed by F-233fe84cf225 with argument 50.

### Final status check

After the third successful post-command call with argument 50, F-692a921cdbdb receives a writable pointer to the local 32-bit working word.

Immediately before this call, the word contains the readiness response that ended polling; no intervening visible assignment replaces it.

Success requires both conditions:

1. F-692a921cdbdb returns nonzero.
2. The word after that call satisfies **word AND 0x00001E00 equals 0x00000800**.

The mask covers bits 9 through 12. Acceptance requires bit 11 set and bits 9, 10, and 12 clear. Other bits do not affect this comparison.

A zero dependency result causes failure without requiring the masked comparison to succeed or be evaluated. A nonzero result with a mismatching word also causes failure. Both select the same final-state diagnostic.

The caller does not establish that F-692a921cdbdb writes the word on every nonzero return. If it leaves the word unchanged, the comparison uses the retained readiness response.

### Failure completion

The visible failure categories are:

- Initial command.
- Readiness timeout.
- Readiness command.
- Identification command.
- Relative-address command.
- Selection command.
- Final status or state.

Each explicit failure selects its corresponding diagnostic and calls F-1b7fa166ef25 once. Its return value is ignored. If the call returns normally, F-c357f0d7c693 returns 0.

No later initialization stage is executed after failure selection. No rollback, reset, cancellation, or compensating command is visible.

## Side effects

### Reads, captures, and mutations

The caller directly reads globals and context fields but does not directly write the context or global pointer. It initializes and replaces its local working word and exposes that word to the final status dependency.

The following distinctions are observable:

- A global-pointer change between entry reads can make the retained context, timeout source, and initial-command argument source different objects.
- Changing the global pointer after those entry reads does not redirect subsequent visible context accesses.
- Changing offset 0x10 after capture does not change later timeout arguments, even if the changed field belongs to the context from which the timeout was obtained.
- Changing offset 0x14 in the retained context can affect later commands.
- Changing offset 0x0C in the retained context can affect either address-bearing command independently.
- Changing readiness constants after their ordered capture does not change later loop submissions.

No supplied dependency contract establishes preservation of globals, context memory, device state, or other shared state. These effects must not be ruled out merely because the caller has no direct writes to those objects.

Order between separate assignments and calls is established as described. Relative evaluation order of selector and field reads within an individual command’s argument list is not established.

### Lifetime and ownership

Every context object selected during entry must be readable for the particular access made through it. The retained context must remain readable for all later field accesses actually reached. The object used only for timeout capture need not remain accessible merely to reuse the copied value; likewise, the initial command receives the copied fourth-argument value rather than a context pointer.

No allocation or release is directly visible. That does not establish that dependencies allocate nothing or retain nothing.

Nonzero command results are forwarded to another dependency for the initial command and readiness commands only. No result is visibly released. Whether results are handles, pointers, status words, or another representation is undocumented; ownership transfer and leak conclusions are therefore unsupported.

The final status dependency receives local storage valid during its call. The caller establishes no safe lifetime for access after the function returns. Whether the dependency retains that pointer is unknown.

Diagnostic storage is supplied to F-1b7fa166ef25 without any visible ownership-management operation.

## Acceptance examples

These are conditional acceptance criteria, not executed tests. Dependencies are assumed to return normally, and relevant memory accesses are assumed valid.

1. **Initial command fails.**  
   If the initial submission returns zero, the initial-command diagnostic is reported and the function returns 0. D-01 and readiness polling are not reached.

2. **Entry reads select different contexts.**  
   If the first pointer read selects context A, the second selects B, and the third selects C, the timeout value comes from B at offset 0x10 and the initial command’s fourth argument comes from C at offset 0x14. Subsequent command-field reads use A.

3. **Ordered readiness capture.**  
   After D-01 returns, the readiness second argument is read before its selector. If either global later changes, subsequent loop iterations still use its captured value.

4. **Timeout before polling command.**  
   If the first D-02 call returns nonzero, timeout is reported and the function returns 0. Neither the call with argument 1 nor a readiness submission occurs.

5. **Two polling iterations.**  
   If timeout checks return zero and extracted responses are first 0x00000000, then 0x80000000, two readiness commands occur. Each has a preceding timeout check and call with argument 1. The second response advances initialization.

6. **Readiness submission fails.**  
   A zero readiness-command result causes the readiness-command diagnostic. F-7b608acf5ce9 is not called for that result, and later commands are skipped.

7. **Complete success.**  
   If all commands return nonzero, readiness completes, and F-692a921cdbdb returns nonzero while leaving 0x00000800 in the word, the function returns 1 without diagnostic reporting.

8. **Ignored and rejected status bits.**  
   With otherwise successful prerequisites, 0x80000801 passes the final mask. By contrast, 0x00000A00 fails because an additional masked bit is set. The latter causes final-state reporting and return 0.

9. **Status-result precedence.**  
   A zero final status result causes failure even when the word is 0x00000800.

10. **Recomputed address.**  
    Under the 32-bit shift interpretation, address field 0x00001234 produces argument 0x12340000. If the retained context’s field becomes 0x00005678 before the selection-stage read, that command receives 0x56780000.

11. **No final write.**  
    If the terminating readiness response is 0x80000800 and the final status dependency returns nonzero without writing, the retained word passes. A retained response of 0x80000000 instead fails.
