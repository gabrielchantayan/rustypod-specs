# F-550f5c65f73c

## Purpose

F-550f5c65f73c obtains a four-component baseline through a dependency, selects a second four-component source, derives a scalar extent from two components of that source, and writes two baseline-derived four-component results into the supplied object.

The established behavior is numeric and positional. Interpreting the four components as rectangle coordinates, the scalar as a width or height, and the two results as opposing edge regions is plausible intent, not a proven semantic contract.

The function has no explicit return value. Its observable results are dependency calls and writes to the supplied object.

## Interface

### Input

The function accepts one address-bearing argument identifying a mutable object. The supplied representation expresses this argument as an integer rather than a typed object pointer. The target address representation and calling convention are not independently established.

The following object-relative locations participate directly:

| Offset | Access width | Role |
|---|---:|---|
| `0xB8` | 1 byte | Zero/nonzero selector, read at multiple decision points |
| `0xC8` | 32 bits | First result, component 0 |
| `0xCC` | 32 bits | First result, component 1 |
| `0xD0` | 32 bits | First result, component 2 |
| `0xD4` | 32 bits | First result, component 3 |
| `0xD8` | 32 bits | Optional dependency argument; zero means not selected |
| `0x19C` | 32 bits | Second result, component 0 |
| `0x1A0` | 32 bits | Second result, component 1 |
| `0x1A4` | 32 bits | Second result, component 2 |
| `0x1A8` | 32 bits | Second result, component 3 |
| `0x26C` | 1 byte | Mode selector; exactly `1` selects one branch |
| `0x2AC` | 32 bits | Derived scalar extent |

The four-component values are represented as four consecutive 32-bit integer slots, occupying 16 bytes in total. No byte order is established by the supplied material.

### Output and ownership

There is no explicit returned value or status. On an ordinary completed execution, the function writes nine 32-bit object fields: the scalar extent followed by the eight result components.

The function itself does not allocate, free, or retain memory in the supplied body. It passes addresses of temporary four-component storage to dependencies. Whether either dependency retains those addresses, changes other reachable state, or performs allocation or release is unknown.

The input object must remain accessible throughout the call. Its directly accessed fields must support the indicated reads and writes. Dependency-specific validity requirements are additional and are not supplied here.

## Behavior

### 1. Obtain and snapshot the baseline

The first action is a call to **F-960363c07b32**, with:

1. The supplied object argument.
2. An address for temporary four-component output.

Call the resulting ordered components the **baseline**, written as \(B_0, B_1, B_2, B_3\).

After that call returns, the function copies all four components into each of two separate working results. Both initially equal the baseline:

- First result: \((B_0, B_1, B_2, B_3)\).
- Second result: \((B_0, B_1, B_2, B_3)\).

These copies precede the optional second dependency call. They are snapshots of the first dependency’s output, not later rereads from the object’s result fields.

The supplied body does not establish that F-960363c07b32 always initializes all four components. Defined completed behavior requires that every subsequently consumed component have a valid value.

### 2. Select the extent source

After preparing both working results, the function reads the byte at `0xB8`.

- If that byte is nonzero, it does not read `0xD8` for this decision and uses the baseline as the extent source.
- If that byte is zero, it reads the 32-bit value at `0xD8`.
  - If this value is zero, it uses the baseline as the extent source.
  - If this value is nonzero, it calls **F-59fa3fd3efc5** and uses that dependency’s four-component output as the extent source.

For the optional call, the dependency receives the value obtained from `0xD8` and an address for temporary four-component output. The source expression contains a further load of `0xD8` to supply the call argument after the nonzero test. Thus the tested value and the passed value are not explicitly cached as one observation.

Call the chosen extent-source components \(S_0, S_1, S_2, S_3\). When the optional dependency is not called, \(S_i = B_i\).

No function-owned object writes occur before this selection completes. Dependencies may nevertheless have side effects of their own.

### 3. Select the component pair and derive the extent

The function next reads the byte at `0x26C`.

- Exactly `1` selects the **mode-1 branch**.
- Every other byte value selects the **other-mode branch**.

Within the selected branch, the function reads `0xB8` again. This is a separate observation from the read used to choose the extent source. It occurs after any optional dependency call.

The scalar calculation is:

| Mode observed at `0x26C` | Later byte observed at `0xB8` | Extent |
|---|---|---|
| Exactly `1` | Zero | \(S_3 - S_1\) |
| Exactly `1` | Nonzero | \(S_2 - S_0\) |
| Any other value | Zero | \(S_2 - S_0\) |
| Any other value | Nonzero | \(S_3 - S_1\) |

The two observations of `0xB8` must not be collapsed into a single logical input. For example, F-59fa3fd3efc5 may change that byte through independently reachable state. Its preservation behavior is unknown.

The computed extent is written to the 32-bit field at `0x2AC` before either four-component result is written.

### 4. Modify the working results

The function reads the stored extent from `0x2AC` to update the first result, then reads that field again to update the second result.

For mode exactly `1`:

- First result component 3 becomes baseline component 1 plus the first extent reread.
- Second result component 1 becomes baseline component 3 minus the second extent reread.
- All other components retain their baseline values.

Without intervening modification of `0x2AC`, this gives:

- First result: \((B_0, B_1, B_2, B_1 + E)\).
- Second result: \((B_0, B_3 - E, B_2, B_3)\).

For every other mode value:

- First result component 2 becomes baseline component 0 plus the first extent reread.
- Second result component 0 becomes baseline component 2 minus the second extent reread.
- All other components retain their baseline values.

Without intervening modification of `0x2AC`, this gives:

- First result: \((B_0, B_1, B_0 + E, B_3)\).
- Second result: \((B_2 - E, B_1, B_2, B_3)\).

Here \(E\) denotes the stored extent. The compact formulas assume the two rereads observe that value unchanged. The function itself makes no dependency calls between the extent store and these rereads.

### 5. Publish the results

After calculating both working results, the function writes their components individually in this order:

1. First result component 0 at `0xC8`.
2. First result component 1 at `0xCC`.
3. First result component 2 at `0xD0`.
4. First result component 3 at `0xD4`.
5. Second result component 0 at `0x19C`.
6. Second result component 1 at `0x1A0`.
7. Second result component 2 at `0x1A4`.
8. Second result component 3 at `0x1A8`.

There is no aggregate publication operation, completion flag, or synchronization mechanism in the supplied body. An observer of intermediate writes is not guaranteed to see a coherent pair of results.

### Arithmetic and boundary behavior

The arithmetic operands and stored numeric results are represented as 32-bit integers. The operations are subtraction for the extent, followed by one addition and one subtraction for the result adjustments.

No explicit checks enforce:

- Nonnegative extents.
- Ordered source components.
- Result containment within the baseline.
- An extent no larger than the baseline span.

A zero extent is not specially rejected. A negative extent is not normalized. An extent larger than a baseline span is not clamped.

The supplied representation does not establish the executable’s overflow semantics. In particular, this contract does not assume either signed-overflow trapping or modulo-\(2^{32}\) wrapping. The formulas are unambiguous when all intermediate arithmetic is representable in signed 32-bit values; overflow cases remain documented_only.

## Side effects

The function’s direct object writes are limited to `0x2AC`, the four fields beginning at `0xC8`, and the four fields beginning at `0x19C`.

The direct ordering is:

1. Initial dependency call.
2. Baseline snapshots.
3. Extent-source selection, including an optional dependency call.
4. Mode and later selector reads.
5. Extent store.
6. Two extent rereads and working-result updates.
7. Eight component stores in the order listed above.

This is the order expressed by the supplied body. It is not an independently established machine-level memory-ordering guarantee for concurrent observers or memory-mapped devices.

There is no explicit error branch, rollback, logging, or status reporting. Dependency return statuses are not inspected. If a dependency does not return normally, the subsequent function-owned writes are not established as occurring.

Invalid addresses, inaccessible fields, incomplete dependency outputs, and dependency failures have no specified recovery behavior here. The function does not validate those conditions.
