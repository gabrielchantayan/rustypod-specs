# F-9a1677119f2d

## Purpose

F-9a1677119f2d clears one byte in a caller-supplied memory region, then performs a caller-selected number of calls to F-93c705790509. Each call receives the address of the cleared byte, a four-byte value selected from a table, and the constant 64.

The table selection is refreshed before every call. The table base, however, is captured once, before the byte is cleared. Consequently, changes made by a dependency to the selector can affect subsequent calls, while changes to the global table-base slot do not redirect this invocation’s subsequent table reads.

This is a source-facing contract based on static evidence only. The operation performed by F-93c705790509 is unknown. In particular, this contract does not classify the repeated calls as copying, filling, decoding, transmitting, allocating, or releasing memory.

## Behavior

### Entry actions

The function first reads the global table-base slot and retains that value for its own subsequent table accesses.

It then writes zero to the single byte at object offset 0x215. This happens regardless of the repetition count. No selector read or table-entry read precedes this write.

A zero repetition count therefore does not make the function a no-op: the global slot is still read, and the destination byte is still cleared.

### Repeated operation

For every iteration whose unsigned index is less than the supplied count, the function:

- Reads the unsigned selector byte at object offset 0x14.
- Reads a four-byte value from the entry selected within the captured table.
- Calls F-93c705790509 with the fixed destination address, the value just read, and 64.

This is the observable ordering of the function’s own accesses and calls. It is not a claim about memory barriers, cross-thread visibility, or physical bus transactions.

The selector is read anew on every iteration. The function does not capture it once at entry. The selected entry’s value is also read anew on every iteration; it is not cached across calls.

The destination address remains object base plus 0x215 throughout the invocation. There is no iteration-dependent destination displacement. The function also does not advance the table entry automatically: a different entry is selected only if a later selector read produces a different byte value.

### Repetition count and arithmetic

The loop starts at zero and advances by one after each dependency call returns normally. For an unsigned 32-bit count, all values from zero through 4,294,967,295 are representable.

If the count is 4,294,967,295 and every call returns normally, the function makes exactly that many calls. The counter reaches the count and the loop stops; this case does not require the counter to wrap from its maximum value to zero.

The selector multiplication is bounded:

- Minimum displacement: 0 bytes.
- Maximum displacement: 255 × 4 = 1,020 bytes.
- Maximum selected four-byte entry: bytes 1,020 through 1,023 relative to the captured table base.

Thus, the selector multiplication itself fits within 32 bits. This does not establish that adding the displacement to an arbitrary table base produces a valid address.

The object-offset additions likewise require valid address results. The supplied evidence does not define portable behavior for an overflowing object-address calculation.

### Changes made during dependency calls

A dependency call completes before the next iteration reads the selector. Subject to ordinary valid-memory execution, changes made by that call to the selector or selected table entries can therefore affect later iterations.

A change to the global table-base slot has a different effect: this invocation continues using the previously captured table base. The function does not reread the global slot inside the loop.

The destination byte is cleared only once. It is not cleared again between dependency calls or immediately before return. Its final value therefore need not be zero when the count is nonzero.

### Completion and abnormal execution
