# F-e7852cdf3c73

## Purpose

F-e7852cdf3c73 prepares provider-derived and optionally child-derived state, compares that state, and conditionally invokes a provider action.

The action is selected when either:

- Two dependency-produced 64-bit values differ.
- Those values are equal, but an indirect comparison of the provider-derived snapshot and candidate object returns zero.

Normal execution also includes optional opening and closing receiver notifications, an unconditional final provider operation, and ordered cleanup.

**Established static behavior:** the comparisons, calls, field accesses, and normal-path ordering described below.

**Inferred intent:** detecting a state difference and requesting a corresponding action. The source does not establish the application meaning of that state or action.

Pointers, object header words, and the explicitly copied complete words are 32 bits in the supplied representation. Dispatch offsets are byte offsets, not ordinal method indices.

### Preconditions

For the normal returning path, every reached memory access and indirect call must have valid storage and a suitable target. In particular:

- The receiver must support its reached header and child-field accesses.
- The first provider result, after the adjustment described below, must support the source-field accesses and provider operations.
- Each dependency-returned address used for further construction must support the subsequent address calculation and write or call.
- A child used for dispatch must remain suitable for that dispatch.
- The second provider lookup must return a pointer suitable for direct dispatch.
- Dependencies receiving working-object addresses must support the states and storage supplied to them.

The function does not validate these requirements. Null provider results do not select a supported empty-state path.

All working objects described here are stack-backed. Their addresses are supplied to synchronous calls, but the dependency contracts do not establish whether a callee retains them or how such retention would be made safe.

## Behavior

### 1. Optional opening notification

When the notification selector is nonzero, invoke the receiver operation at dispatch-table byte offset `0xDC`, passing only the receiver as an explicit argument.

This occurs before descriptor preparation, provider lookup, header initialization, and child inspection. Its effects may therefore influence all later work. The function establishes no preservation of receiver fields or global state across this call.

2. Read a 32-bit value from a fixed static location and write it at descriptor offset `0x00`.

The descriptor’s remaining contents and semantic extent are not established.

Next, perform the following sequence:

1. Call F-b7af80e829ec with no explicit arguments.
2. Read a 32-bit header value from another fixed static location and write it to candidate-object offset `0x00`.
3. If the lookup result is nonzero, subtract 20 bytes to obtain the retained first-provider base. If the result is zero, retain zero.
4. Separately read that same header static location and write the newly read value to snapshot offset `0x00`.
5. Read an additional 32-bit value from a different static location and write it to snapshot offset `0x04`.

The candidate-header read precedes the conditional pointer adjustment. The snapshot-header read follows that adjustment.

These are **two separate reads from the same header location**, not one captured value copied twice. Stability of the static location is not established, so equality of the candidate and snapshot header values is not guaranteed by this function.

The provider adjustment is a 20-byte subtraction in the observed 32-bit address representation. No bounds or underflow validation is present. The resulting address must be usable for subsequent accesses.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Each assumes all other reached accesses and calls are valid.

1. **Separate header captures.** If the candidate-header read observes value A and the later snapshot-header read observes value B, the respective explicit writes store A and B. The contract does not require them to match. The candidate write occurs before provider adjustment; the snapshot write occurs after it.

2. **Descriptor ordering.** The descriptor’s offset-`0x04` zero-byte write precedes its offset-`0x00` static-word read and write.

3. **Notifications.** Selector zero suppresses both receiver notifications. Values `1`, `2`, and `0xFFFFFFFF` all enable both. The closing call includes `0xFFFFFFFF`; the opening call has no corresponding explicit argument.

4. **Full-width inequality.** Results `0x0000000100000000` and `0x0000000000000000` select provider `0x54` without invoking the snapshot comparison, despite matching low 32 bits.

5. **Equal values and zero comparison.** Equal 64-bit results cause the snapshot comparison with final argument `1`. A zero comparison result then selects provider `0x54`.

6. **Equal values and nonzero comparison.** A nonzero snapshot-comparison result skips both the three action-specific temporary writes and provider `0x54`. The second lookup, final provider operation, enabled closing notification, and normal cleanup remain reachable.

7. **Initially absent child.** A zero initial child pointer skips both child operations and temporary-result cleanup. The initialized second comparison record still participates in the later value-producing call.

8. **Child replacement.** If the first child operation installs another valid child and that field remains stable through the second invocation, the second child operation uses the replacement.

9. **Selected-action write order.** If the fresh action-time child read yields pointer P, the explicit stores are P at temporary offset `0x08`, then `3` at `0x00`, then `3` at `0x04`, followed by provider `0x54`. This does not prove that the action receives that temporary as payload.

10. **Byte truncation.** A provider word of `0x123456AB` at offset `0x9F4` produces the byte `0xAB` at snapshot offset `0x14`.

11. **Return-directed construction.** If a construction dependency returns an address different from its destination argument, the next destination follows the returned address plus the specified displacement, not an assumed contiguous layout.

12. **Provider lookup distinction.** Different valid lookup results lead to action dispatch through the adjusted first result and final `0x28` dispatch through the unadjusted second result.

13. **Null provider result.** A zero first result still leads toward unguarded source accesses. A zero second result still leads toward unguarded dispatch. Neither is a specified successful no-op case.
