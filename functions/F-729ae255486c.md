# F-729ae255486c

## Purpose

F-729ae255486c performs an unconditional preparation sequence, conditionally updates two one-byte fields of a destination object, and then invokes an unconditional final operation with its first two inputs.

The conditional portion uses two identifiers obtained from a shared table. For each identifier, the function first constructs a temporary value and asks a dependency whether to proceed. A nonzero result causes a second temporary construction, a one-byte conversion, and a write to the corresponding destination field.

This describes the established control flow, not the application meaning of the fields. Interpreting the two fields as flags, the table entries as property names, or the dependencies as lookup and conversion services is inferred intent only.

On every path that reaches the explicit return, the function returns the 32-bit value 1. That value does not distinguish skipped updates from completed updates.

## Interface

### Inputs and result

The function takes four machine-word arguments:

| Input | Established representation | Direct use |
|---|---|---|
| Destination | 32-bit address-bearing value | Supplies the object base, an interior address for preparation, an initial scratch value, and the first argument to the final operation. |
| Selector | 32-bit integer | Gates the conditional portion by comparison with zero, initializes a scratch cell, and supplies the second argument to the final operation. |
| Context word | Uninterpreted 32-bit value | Initializes a scratch cell whose address is passed to temporary construction. |
| Seed word | Uninterpreted 32-bit value | Initializes the first element of a four-word scratch area used for temporary construction. |

The selector is tested only for equality with zero. Negative values and positive values both enable the conditional portion.

The destination is used as an address without a visible null check, bounds check, or alignment check. Its representation as a signed integer in the supplied material does not establish a valid signed numeric domain for addresses.

The following byte offsets from the destination are directly relevant:

The byte offsets are address displacements, not field indices. The supplied evidence does not establish the total size, alignment, or ownership of either the destination or the shared table.

## Behavior

### 1. Unconditional preparation

The function invokes these dependencies in order:

1. F-6a21f4f07f67, with no explicit arguments.
2. F-d57e37ae0dcc, with no explicit arguments.
3. F-46f0b3cb316e, with the destination address plus `0xBC` and the 32-bit result from F-d57e37ae0dcc.

The result of F-6a21f4f07f67 is not used. No result from F-46f0b3cb316e is used.

Only after these calls does the function capture the shared table base. Consequently, changes those calls make to the table-base global can affect the conditional portion.

No stronger conclusion about these dependencies is established. They may affect destination storage, shared state, or resources.

### 2. Scratch initialization and gate

After capturing the table base, the function initializes local scratch storage from all four original arguments:

- One 32-bit cell receives the destination value.
- A second 32-bit cell receives the selector.
- A third 32-bit cell receives the context word.
- The first element of a four-element, 32-bit scratch area receives the seed word.

The other three elements of that scratch area are not explicitly initialized by this function before the first construction call.

These are addressable storage locations, not merely immutable copies. Later dependencies receive pointers to them. Their contents must not be assumed to remain equal to the original inputs.

If the original selector is zero, the entire two-entry conditional sequence is skipped. Execution proceeds to the final operation.

### 3. First entry: predicate phase

For a nonzero selector, the function:

1. Reads the first 32-bit identifier through the current shared table-base global at offset `0x0C`.
2. Calls F-9b9c1c7483f4 with:
   - The address of the four-word scratch area.
   - That identifier.
   - The address of the context scratch cell.
3. Captures the separate shared service global **after** that construction call.
4. Calls F-8094c3d72052 with the captured service value and the construction result.
5. Saves the predicate result.
6. Calls F-8a5aadac202f with the scratch-area address.
7. Tests the saved predicate result for zero.

The predicate result is represented as a 32-bit integer. Every nonzero value takes the update branch; it need not equal 1.

Cleanup therefore precedes the branch decision. A zero predicate does not suppress cleanup.

The table base used for this first identifier read is obtained through the global, whereas later identifier reads use the previously saved table base. With no intervening mutation, they designate the same table. The distinction matters if shared state can change asynchronously.

### 4. First entry: optional update

If the first predicate result is nonzero, the function:

1. Reads the 32-bit entry at offset `0x0C` from the saved table base.
2. Calls F-9b9c1c7483f4 with:
   - The address of the selector scratch cell.
   - The newly read identifier.
   - The address of the destination scratch cell.
3. Calls F-cf946f91e683 with the saved service value and this construction result.
4. Stores the resulting one-byte value at destination offset `0xB0`.
5. Calls F-8a5aadac202f with the selector scratch-cell address.

The identifier is read again rather than reused from the predicate phase. If a dependency changes the table entry between reads, the two constructions can receive different identifiers.

The byte store occurs before cleanup of the second temporary. If that cleanup does not return normally, the store has already occurred.

If the predicate result is zero, this function performs no direct store to destination offset `0xB0`.

### 5. Second entry: predicate phase

Whether or not the first update branch ran, normal execution continues with the second entry:

1. Read the 32-bit identifier at offset `0x10` from the saved table base.
2. Call F-9b9c1c7483f4 with the same scratch-area address and context-cell address used in the first predicate phase.
3. Call F-8094c3d72052 with the previously captured service value and the new construction result.
4. Save the predicate result.
5. Call F-8a5aadac202f with the scratch-area address.
6. Test the saved predicate result for zero.

Neither the scratch area nor the context cell is explicitly restored to its original input value before reuse. Mutations made during the first entry’s calls can therefore affect the second entry.

The service global is not reread for this phase. A dependency may replace that global, but this function continues passing the captured service value.

The saved table base likewise remains the addressing base. The contents at that base are read at the time each identifier is needed; the function does not snapshot the table entries together.

### 6. Second entry: optional update

If the second predicate result is nonzero, the function:

1. Rereads the 32-bit identifier at saved table base plus `0x10`.
2. Calls F-9b9c1c7483f4 with the selector scratch-cell address, that identifier, and the destination scratch-cell address.
3. Calls F-cf946f91e683 with the saved service value and the construction result.
4. Stores the resulting byte at destination offset `0xB1`.
5. Calls F-8a5aadac202f with the selector scratch-cell address.

The scratch cells used here are not explicitly reinitialized after the first entry. In particular, if the first optional update changed them through a dependency, those changed contents remain available to the second update.

If the predicate result is zero, this function performs no direct store to destination offset `0xB1`.

### 7. Final operation and return

After either skipping or completing the conditional portion, the function calls F-876f4b90d114 with the original destination and original selector.

These are the original argument values, not values reloaded from the mutable scratch cells.

The final dependency’s result is ignored. If it returns normally, F-729ae255486c returns the 32-bit value 1.

## Side effects

### Direct writes and ordering

The only direct destination writes shown are the conditional one-byte stores at `0xB0` and `0xB1`. If both occur, the `0xB0` store precedes the `0xB1` store.

Each is a byte-sized store. The evidence does not justify describing the result as a canonical Boolean or as a wider integer field. Adjacent destination bytes are not directly overwritten by these stores.

The absence of a direct store does **not** establish that a byte remains unchanged: dependencies receive the destination or an interior address, can access shared state, and may have additional side effects.

The final dependency runs after all reached temporary cleanup calls and direct byte writes. It may change the object again. Thus the direct byte-store values are not necessarily the final observable field values at function return.

### Temporary storage and ownership

The function supplies local storage to F-9b9c1c7483f4 and later supplies the same relevant destination address to F-8a5aadac202f.

Every normally completed construction sequence shown has a corresponding cleanup call:

- One cleanup after each predicate call.
- One additional cleanup after each taken conversion branch.

The interface shape suggests temporary construction and release, but that interpretation is not a proven ownership contract. The evidence does not establish whether resources are allocated, transferred, retained, reference-counted, or released.

The function does not itself retain these local addresses after returning. Whether dependencies retain them is unknown. Safe retention requirements cannot be inferred from the caller alone.

### Errors and abnormal completion

There is no visible explicit error return, exception handler, rollback, retry, or failure aggregation.

A zero predicate means only “skip this direct update branch.” It does not cause an early return or suppress the second predicate or final operation.

Failures inside dependencies, invalid memory accesses, nonlocal exits, and process termination are outside the established normal-return behavior. Cleanup and finalization are not guaranteed after an interrupted call.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Each assumes valid reached accesses and normal dependency returns.

### Zero selector

Given a selector of zero:

- The three preparation calls still occur.
- Scratch initialization and the table-base capture still occur.
- No identifier entry is read by the conditional portion.
- No predicate, temporary-construction, conversion, or temporary-cleanup call from that portion occurs.
- F-876f4b90d114 receives the original destination and zero.
- The result is 1.

No claim is made that preparation or finalization leaves destination bytes unchanged.

### Both predicates zero

Given a nonzero selector and both predicate results equal to zero:

- Two predicate-phase constructions and two associated cleanup calls occur.
- No conversion call occurs.
- Neither conditional byte store occurs.
- The second predicate and final operation still run.
- The result is 1.

### Only the first predicate nonzero

Given a nonzero first predicate and a zero second predicate:

- The first identifier is read once for its predicate and again for its update.
- One conversion result is written as one byte at destination offset `0xB0`.
- That store precedes its cleanup and the second predicate phase.
- No direct store occurs at `0xB1`.

### Both predicates nonzero

Given two nonzero predicate results:

- Four constructions, two predicates, two conversions, and four associated cleanup calls occur.
- The first conversion byte is stored at `0xB0`; the second is stored at `0xB1`.
- The final operation follows both update sequences.
- The normal result remains 1, independent of the byte values.

### Shared service replacement

If the first predicate-phase construction changes the service global before returning, the subsequently captured replacement is used. If a later dependency changes that global again, subsequent calls still receive the previously captured value.

### Table-entry mutation

If a dependency changes an entry in the saved table between its predicate-phase read and its update-phase read, the later construction receives the later entry value. Reusing the earlier identifier would not match the observed behavior.
