# F-ffb470581057

## Purpose

F-ffb470581057 installs a 32-bit payload and an associated callback address into an indexed table attached to an owner object. Before replacement, it conditionally invokes an indirect callable selected from either the existing entry or a retained candidate value.

For stable entry contents, the ordinary replacement rule is to invoke the existing entry’s callback only when both its payload and callback are nonzero. This rule is incomplete when the payload changes between two distinct reads: the function can instead invoke an index-derived address or an unresolved register-derived address without reading the entry’s callback.

The function requests table allocation or growth through F-eb8708ae5ace. A negative index or a null result from that dependency takes an alternate path that invokes the incoming callback with the incoming payload, if the callback is nonnull.

These are established static behaviors. Descriptions such as registry, allocator, initializer, destructor, or ownership transfer express possible intent, not established guarantees.

## Interface

### Inputs

The supplied representation exposes four 32-bit inputs:

| Input | Interpretation |
|---|---|
| Owner address | Address of an object containing a header word, table pointer, and dependency context. |
| Entry index | A 32-bit word interpreted as signed for the negative-index check and table-count comparison. |
| Incoming payload | An uninterpreted 32-bit value to store or pass to the incoming callback. |

Apparent callable types in the supplied representation do not establish that the owner or index represents executable code. Their uses establish an object address and an index. The index’s bit pattern does, however, also initialize the indirect-call candidate on the no-growth path.

### Output and completion

No explicit return value or status is established. Normal completion returns control without reporting whether installation occurred.

The contract below describes continuation when external operations return normally. Faults, exceptions, nonlocal exits, and nontermination originating in dependencies or indirect calls are not resolved by the supplied evidence.

## Behavior

### Negative-index path

The function first interprets the index as a signed 32-bit integer.

For a negative index:

1. It skips owner and table inspection.
2. If the incoming callback is null, it returns.
3. Otherwise, it invokes the incoming callback with the incoming payload as the one explicit argument, then returns if that invocation returns normally.

There are no explicit owner or table writes on this path. The callback may have effects of its own.

### Table inspection and growth decision

For a nonnegative index, the function reads the table address from owner offset 4.

If that address is nonnull, it reads the table count. Growth is required when the table is null or the signed 32-bit count is less than or equal to the index. A nonnull table with a signed count strictly greater than the index takes the no-growth path.

The count comparison accounts for signed subtraction overflow; it is not merely a sign test on a wrapped subtraction result. A count with its high bit set therefore compares as negative and requires growth for every accepted nonnegative index.

On the no-growth path, the function does not refresh the table header or count. The indirect-call candidate initially holds the index’s 32-bit bit pattern.

### Growth request and failure

When growth is required, the function obtains an old count:

- Zero if the retained table address is null.
- A second read of the count field if the retained table address is nonnull.

The count used for growth calculations can therefore differ from the count used for the growth decision if the table changes between reads.

F-eb8708ae5ace receives, in order:

1. The 32-bit context read from owner offset 24.
2. The retained table address, possibly null.
3. A requested byte size corresponding to \(8i + 16\).

For nonoverflowing arithmetic, this size accommodates the header and entries zero through \(i\).

If the dependency returns null, the function takes the alternate callback path: it invokes the incoming callback with the incoming payload if that callback is nonnull, then returns. It does not explicitly store the null result into the owner.

This does not establish failure atomicity. F-eb8708ae5ace receives the old table address, and its effects on that allocation, globals, and reachable owner state are unknown.

### Successful-growth ordering

For a nonnull result, the explicit operations occur in this order:

1. Store the returned table address into owner offset 4.
2. Invoke F-unresolved-1 with a computed region address and byte quantity.
3. Store the new count into returned-table offset 4.
4. Read owner offset 0 and copy that word into returned-table offset 0.
5. Continue to selected-entry inspection.

For old count \(c\), the region address corresponds to returned-table byte offset \(8 + 8c\), and the byte quantity corresponds to \(8(i + 1 - c)\).

With valid, nonoverflowing counts, this is the newly added entry region, including the requested entry. The source does not establish what F-unresolved-1 does to that region. In particular, zero initialization is not guaranteed.

The new count is the 32-bit result corresponding to \(i + 1\). The copied header word is read after F-unresolved-1 returns; it is not a snapshot taken before either external dependency.

After successful growth, the indirect-call candidate is the unresolved register output associated with F-unresolved-1, rather than the index-derived value. The source establishes that this output supplies the candidate, but not its value or meaning.

Publication precedes initialization: the returned address is installed in the owner before the external memory operation, count update, and header copy. No explicit synchronization or rollback surrounds this sequence.

### Two payload reads and candidate selection

Entry inspection uses the retained table address, not a fresh read of the owner’s table pointer.

The established sequence is:

1. Read the selected entry’s payload.
2. If that first read is nonzero, read the entry’s callback word and replace the candidate with it.
3. Read the selected entry’s payload again.
4. If the second read is nonzero and the candidate is nonnull, invoke the candidate without explicit arguments.

If the first payload read is zero, the entry’s callback word is not read. The candidate remains:

- The index’s bit pattern on the no-growth path.
- The unresolved register output from F-unresolved-1 after successful growth.

Consequently, the two-read outcomes are:

| First payload read | Second payload read | Callable selection and invocation |
|---|---|---|
| Zero | Zero | Candidate retained; no invocation. |
| Zero | Nonzero | Retained candidate invoked if nonnull; entry callback is not loaded. |
| Nonzero | Zero | Entry callback loaded as candidate; no invocation. |
| Nonzero | Nonzero | Loaded entry callback invoked if nonnull. |

On the no-growth path, index zero supplies a null initial candidate. If the first read is zero and the second is nonzero, index zero therefore suppresses invocation. Any positive accepted index supplies a nonnull initial candidate, so the same read transition attempts an indirect call to the index-derived address.

After growth, that transition invokes the unresolved register-derived address if it is nonnull. There is no established requirement that this value be a valid callback.

Under stable-memory conditions, the simpler rule remains valid: zero payload suppresses invocation; nonzero payload causes the entry callback to be loaded and invoked only if nonnull.

No explicit argument is supplied to this pre-replacement indirect call. The evidence does not establish that it receives the old payload, owner, or index.

### Replacement writes

If an indirect call occurs, the function waits for its normal return before performing replacement.

The final stores are ordered:

1. Incoming callback to the selected entry’s callback word.
2. Incoming payload to the selected entry’s payload word.

These stores also occur when no pre-replacement call was made. A zero incoming payload and nonzero incoming callback are stored as supplied, as are a nonzero payload and null callback.

The pair is not established as atomic. Between stores, memory contains the new callback and the preceding payload.

The function does not reload the table address or validate the selected entry after the indirect call. Subsequent writes still target the retained table location.

## Side effects

### Explicit state changes

Depending on the path, this function explicitly:

- Publishes a returned table address in the owner.
- Updates the returned table’s count and header.
- Replaces the selected entry’s callback and payload.

The source shows no direct release of the old table or either payload. Allocation, relocation, release, clearing, and other changes performed by dependencies remain outside the established local effects.

### Ownership

No general ownership transfer rule is established.

Passing the incoming payload to the alternate-path callback does not prove consumption or release. Storing the payload does not prove exclusive ownership. The pre-replacement callable is not explicitly passed the old payload and, under differing payload reads, need not even come from the entry’s callback word.

Callers must not infer universal “consumed on entry,” “freed on failure,” or “destroyed before replacement” semantics.

### Interference and reentrancy

No lock, reentrancy guard, or post-call validation is established. Dependencies and callbacks must not be assumed to preserve globals, owner contents, table contents, or storage lifetime.

The consequence of differing payload reads is established dataflow, not wholly unspecified concurrency behavior: a zero first read retains the path-dependent candidate, and a nonzero second read enables its invocation. What remains unknown is whether and how interference occurs, the applicable memory-model guarantees, and the external register value after growth.

Returning external operations must leave all subsequently accessed addresses valid for safe completion. A callback that releases or relocates the retained table can make the final stores unsafe. Reentrant writes to the same entry may be overwritten by the outer invocation.

These are conditional static acceptance cases, not executed tests. They assume valid storage, nonoverflowing arithmetic, and normally returning external operations unless stated otherwise.

1. **Negative index, null incoming callback.**

2. **Negative index, nonnull incoming callback.**

## Uncertainties

### Integer and address boundaries — documented_only

Accepted nonnegative signed indices extend through \(2^{31}-1\), but the absence of a negative-index rejection does not establish safe allocation or addressing.

For an unsigned 32-bit byte quantity, \(8i + 16\) fits without overflow only through index 536,870,909. If interpreted as signed 32-bit, its nonnegative representable range ends at index 268,435,453. The dependency’s size interpretation is not established.

Entry offsets, region addresses, and region quantities introduce additional arithmetic and address-range requirements. A negative or changing old count can also make the region calculation unsuitable for the returned allocation.

At index \(2^{31}-1\), the 32-bit count increment corresponds to bit pattern 0x80000000, which is negative in subsequent signed comparisons. No explicit overflow rejection is shown. Exact machine arithmetic and address behavior at these boundaries remain unresolved; oversized inputs are not promised successful installation.

### External operation and register output — documented_only

Initialization of newly added entries is plausible intent, but clearing is unproven. The post-growth candidate’s provenance from the external operation is established; its actual value and validity as a callable address are not.

### ABI, interference, and failures — documented_only

The pre-replacement callable’s argument ABI is unresolved. Atomicity, concurrent-access guarantees, failure rollback, exception policy, and payload ownership remain unestablished. The specified two-read candidate selection does not resolve those broader contracts.
