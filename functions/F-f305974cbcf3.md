# F-f305974cbcf3

## Purpose

F-f305974cbcf3 prepares a caller-supplied object from parsed input, publishes selected parsed tables into that object, and conditionally constructs an encoding-to-name mapping.

The operation is not transactional. It writes an acquisition result into the object before checking acquisition status. After parsing, it can publish additional tables and construct the mapping even when the parsing dependency returned an error. Cleanup runs after both success and ordinary error paths.

The apparent domain is font-face initialization, with character-name tables and an encoding map. That interpretation is inferred from the data flow and the `.notdef` sentinel. The established contract below concerns the actual fields, calls, comparisons, and writes, rather than a complete font-format specification.

## Interface

### Input and result

The function accepts one 32-bit address-like argument identifying a writable object. It returns a signed 32-bit status.

No null check, object-size check, buffer-capacity check, or pointer-validity check is visible. The caller and dependencies must provide valid storage for every access reached by the selected execution path.

### Temporary state

The function supplies a 304-byte temporary workspace to an initialization operation. A separate signed 32-bit status slot is passed by address to the acquisition dependency.

Five 32-bit workspace fields are explicitly set to zero after initialization: the eventual published name count, two additional temporary fields, the field tested for missing character data, and the encoding metadata later published at `0x170`.

Other workspace values—including callback pointers, a cleanup flag, table pointers, and arguments to later dependencies—depend on the initializer and subsequent dependencies. Their initial values cannot be inferred merely from the initialization call.

## Behavior

### 1. Capture inputs and initialize workspace

The function first reads the 32-bit values at object offsets `0x064` and `0x1E4`, in that order. These captured values are reused later; changes to those object fields by a dependency do not replace the captured inputs.

It then invokes the workspace initializer with the workspace address and the size `304`, followed by the five explicit zero writes described above.

The initializer’s implementation is unavailable. In particular, the evidence does not establish that it is simply a zero-fill operation.

### 2. Acquire an object-associated value

F-3ce007b692cc is invoked with:

- The captured value from `0x064`.
- The integer constant `12`.
- The address of the status slot.

Its 32-bit result is written to object offset `0x1EC` before the status slot is tested. Thus, the write occurs whether the dependency reports success or failure.

If the resulting status is nonzero, preparation, parsing, table publication, and mapping construction are skipped. Execution proceeds to cleanup, with that status retained.

The dependency must initialize the status slot for defined execution. No prior initialization of that slot is established.

### 3. Prepare parsed input

When acquisition status is zero, F-4101250ce71e is invoked with:

- The workspace address.
- The current 32-bit object value at `0x068`.
- The captured value from `0x064`.
- The captured value from `0x1E4`.

Its result replaces the status.

If that result is nonzero, execution proceeds directly to cleanup. The value already stored at `0x1EC` remains written; no rollback is performed.

### 4. Parse into the object and workspace

When preparation succeeds, F-305cf266ef49 receives:

- The object address.
- The workspace address.
- Two 32-bit workspace values.

Its result replaces the status. That result is not checked before the next stage.

Instead, the function reads the object byte at `0x1AD` after the dependency returns:

- If the byte is not `0x2A`, status is replaced with `2`, and publication and mapping are skipped.
- If the byte is `0x2A`, publication proceeds even if the parsing dependency returned a nonzero status.

Consequently, a parse error can survive alongside newly published object state, or can be replaced by a later status.

### 5. Publish tables for the accepted marker

For the accepted marker, the function performs these operations in order:

1. Copies the workspace name count into object offset `0x19C`.
2. Checks a workspace field representing the presence of character data.
3. If that field is zero, invokes F-4457a9a44a68 with a fixed diagnostic message and then sets status to `3`.
4. Sets that workspace presence field to zero, regardless of its previous value.
5. Copies five workspace values into object offsets `0x188`, `0x1A4`, `0x1A8`, `0x18C`, and `0x1A0`, in that order.
6. Clears the workspace values that supplied `0x18C` and `0x1A0`.

The missing-data diagnostic does not stop publication or prevent the optional mapping stage.

These source-field clears suggest ownership transfer or cleanup disarming. They do not establish which allocation owns the underlying storage, or what each cleanup callback releases. Some published values remain present in the workspace; their lifetime cannot be inferred from the copies alone.

### 6. Optionally construct an encoding map

The mapping stage runs only if the object byte at `0x16C` equals exactly `1`. Other nonzero values do not enable it.

The stage initializes two signed 32-bit accumulators:

- Lower bound: `32000`.
- Upper bound: `-32000`.

It then visits encoding slots in ascending order, starting at zero and continuing while the index is less than a signed 32-bit workspace slot count. A zero or negative count causes no slot iterations.

For each visited slot, the visible operations occur in this order:

1. Write zero to the corresponding 16-bit destination index.
2. Write a pointer to the fixed `.notdef` name into the corresponding 32-bit destination name entry.
3. Read that slot’s requested-name pointer from the workspace source table.
4. If the requested-name pointer is null, leave the defaults in place.
5. Otherwise, search the published name table in ascending index order.

The search compares the requested name against each candidate using a string-comparison dependency. A zero comparison result denotes a match.

For the first matching candidate:

- The candidate index is stored in the destination index entry using only its low 16 bits.
- The candidate name pointer is stored in the destination name entry.
- The candidate is compared against `.notdef`.
- If that comparison is nonzero, the lower and upper bound accumulators are updated using the encoding-slot index.
- The search ends for that slot.

Duplicate matching candidate names therefore select the earliest matching table entry. The stored name pointer is the candidate pointer, not the requested-name pointer.

A match to `.notdef` still replaces the destination index and name pointer, but does not contribute to the bounds. An unmatched name leaves index zero and the fixed default pointer; there is no separate unmatched-slot status.

After all slots, the function writes:

1. The lower-bound accumulator to `0x174`.
2. The upper-bound accumulator to `0x178`.
3. The workspace encoding metadata to `0x170`.

If mapping mode is not enabled, these three fields and both destination arrays are not directly written by this stage.

### 7. Cleanup and return

Cleanup is reached after every ordinary control-flow path. It is not conditional on a zero status.

Four workspace callback slots are examined in a fixed order. Each non-null callback is invoked with its associated workspace region. The callback’s slot is checked when its turn is reached; the function does not visibly capture all four callback pointers before making the calls.

After those callbacks:

- If a workspace flag byte is zero, F-bf7242c98d06 is called with two workspace values.
- The second of those workspace values is then set to zero.
- A final workspace callback is invoked unconditionally with the workspace address.
- The current status is returned.

The final callback is not null-checked. Valid execution requires the initialization and dependency sequence to provide a callable value there, including on early acquisition failure.

There is no visible recovery for a callback that does not return normally, accesses invalid memory, or invalidates state needed by later cleanup operations.

## Side effects

### Object mutation

The function directly writes `0x1EC` on every path that completes acquisition. Additional writes depend on the accepted marker and mapping mode, not solely on status success.

The function does not restore prior values on failure. In particular:

- An acquisition failure can leave a new value at `0x1EC`.
- An invalid marker can leave mutations performed by F-305cf266ef49.
- A missing-character-data result can leave published tables and a constructed map.
- A nonzero parsing result can coexist with all normal publication writes.

No direct release of old object values is visible before overwriting them. Whether dependencies manage existing state is unknown.

### Memory and ownership

Mapping requires writable index and name-pointer arrays large enough for the workspace slot count. For a positive name count, the candidate table must contain that many readable 32-bit entries. Names passed to the comparison dependency must meet its string-access requirements.

The mapping copies pointers; it does not visibly duplicate string contents or allocate output arrays.

Workspace cleanup remains active after publication. The cleared source fields support an inferred transfer convention, but preservation of all published storage after cleanup is a dependency requirement, not a demonstrated property.

### Arithmetic and aliasing

Destination index entries have a two-byte stride; pointer tables have a four-byte stride. No visible checks guard address arithmetic, buffer bounds, or truncation of candidate indices to 16 bits.

The bounds use sentinel initial values rather than the full signed 32-bit range. If all qualifying slots exceed `32000`, the lower bound remains `32000`, even though no qualifying match occurred there.

The visible code does not enforce non-aliasing among source tables, destination arrays, and object fields. Aliasing can make an earlier write affect a later read. Likewise, dependencies and callbacks cannot be assumed to preserve object fields, workspace fields, or global state unless their own contracts establish that.

## Acceptance examples

These examples are conditional on valid storage and dependencies that return normally without additional interfering mutations.

1. **Acquisition failure.**  
   If F-3ce007b692cc returns value `V` and writes status `7`, `V` is stored at `0x1EC`. Preparation and parsing are not called. Cleanup runs, and the returned status is `7`.

2. **Preparation failure.**  
   If acquisition succeeds and F-4101250ce71e returns `9`, parsing and publication are skipped. Cleanup runs, and the returned status is `9`.

3. **Marker overrides parsing status.**  
   If parsing returns `11` but leaves `0x1AD` unequal to `0x2A`, the returned status is `2`, subject to normal cleanup completion. No direct publication stage follows.

4. **Parsing error does not prevent publication.**  
   If parsing returns `11`, the marker is accepted, and the character-data presence field is nonzero, the publication writes occur. Status remains `11`. Mapping also occurs if mode is exactly `1`.

5. **Missing character data overrides status.**  
   If the marker is accepted but the presence field is zero, the diagnostic dependency is called and status becomes `3`. Tables are still published, and mapping remains eligible.

6. **First matching name wins.**  
   If a requested name matches candidate entries `4` and `9`, the slot stores index `4` and the pointer from candidate entry `4`. Entry `9` is not selected.

7. **Default and unmatched slots.**  
   A null requested-name pointer produces index zero and the fixed `.notdef` pointer without a candidate search. A non-null name with no match produces the same defaults.

8. **Bounds exclude `.notdef`.**  
   If the only matched candidate names compare equal to `.notdef`, the final bounds are `32000` and `-32000`, despite successful name matches.

9. **Index truncation.**  
   If the first matching candidate has index `65536`, the stored 16-bit index is zero. The name pointer still identifies that candidate. No range error is visibly generated.

10. **Empty mapping.**  
    With mapping mode `1` and a nonpositive slot count, no array entries are written. Bounds become `32000` and `-32000`, and encoding metadata is still published.
