# F-6372ad19c9b6

## Purpose

F-6372ad19c9b6 performs an in-place transformation of linked records. It promotes the record referenced at offset 8 of a selected record, reconnects a possible intervening record, redirects an incoming link, and makes the selected record a child of the promoted record.

The field relationships are consistent with a right rotation in a parent-linked binary tree. That interpretation is **inferred intent**, not a requirement established by field names or external documentation. The established behavior is the sequence of four-byte reads, comparisons, and writes described below.

The function returns no value. Its observable result is the modified memory graph. It does not explicitly allocate memory, release memory, invoke another function, validate the graph, or report an error.

## Interface

### Inputs

The function takes two address-bearing arguments:

| Argument role | Required use |
|---|---|
| Owner | Identifies a record whose offset-16 field supplies the address of a separate root-reference record. |
| Selected node | Identifies the node to be transformed. Its offset-8 field supplies the address of the promoted node. |

The following names describe roles within this contract, not additional arguments:

- **Promoted node:** the address initially read from selected-node offset 8.
- **Transfer node:** the address read from promoted-node offset 12 when transferring that link to the selected node.
- **Root-reference record:** the address read from owner offset 16.
- **Existing parent:** the address read from selected-node offset 4 on the non-root path.

### Accessed layout

All explicitly accessed fields occupy four bytes.

| Record role | Byte offset | Observed use |
|---|---:|---|
| Owner | 16 | Address of the root-reference record |
| Root-reference record | 4 | Link compared with the selected-node address and conditionally replaced |
| Selected node | 4 | Parent-like link, eventually replaced by the promoted-node address |
| Selected node | 8 | Link initially identifying the promoted node; replaced by its offset-12 link |
| Promoted node | 4 | Parent-like link copied from selected-node offset 4 |
| Promoted node | 12 | Transfer link initially; replaced by the selected-node address at the end |
| Transfer node, when nonzero | 4 | Parent-like link replaced by the selected-node address |
| Existing parent, on the non-root path | 12 | Incoming-link candidate compared with the selected-node address |
| Existing parent, on the fallback path | 8 | Incoming link overwritten without a comparison |

These offsets establish only the accessed layout. They do not establish complete record sizes, allocation boundaries, field names, or the meanings of unaccessed bytes.

The supplied representation uses integer-valued addresses and four-byte link fields, consistent with a 32-bit address model. A wider-pointer adaptation is not established. The function performs no explicit widening, narrowing, overflow checking, or address validation.

### Outputs and ownership

## Behavior

### Ordered memory transformation

The following describes the order expressed by the supplied function body. It does not claim machine-level atomicity, synchronization, or independently verified instruction ordering.

1. **Obtain the promoted node.**  
   Read four bytes from selected-node offset 8 and use that value as the promoted-node address. The promoted node is not checked for zero before it is dereferenced.

2. **Replace the selected node’s offset-8 link.**  
   Read four bytes from promoted-node offset 12 and write that value to selected-node offset 8.

3. **Conditionally repair the transferred link’s parent-like field.**  
   Read promoted-node offset 12 again and compare it with zero.

   - If the value is zero, perform no transfer-node write.
   - If it is nonzero, read promoted-node offset 12 again to obtain the destination address, then write the selected-node address at that destination’s offset 4.

   The transfer link is therefore not read once and retained for all uses. In an ordinary, non-overlapping graph without concurrent modification, the repeated reads agree. The body itself does not enforce that agreement.

4. **Copy the selected node’s former parent-like link.**  
   Read selected-node offset 4 and write its value to promoted-node offset 4.

5. **Locate and inspect the root reference.**  
   Read owner offset 16 to obtain the root-reference-record address. Read that record’s offset-4 field and compare it with the selected-node address.

6. **Redirect one incoming reference.**

   - **Root-reference match:** If root-reference-record offset 4 equals the selected-node address, replace that field with the promoted-node address. This branch does not inspect an existing parent’s child fields.
   - **Root-reference mismatch:** Read selected-node offset 4 again to obtain the existing-parent address. Read existing-parent offset 12.
     - If it equals the selected-node address, replace existing-parent offset 12 with the promoted-node address.
     - Otherwise, replace existing-parent offset 8 with the promoted-node address.

   The fallback does not verify that existing-parent offset 8 previously referred to the selected node.

7. **Link the promoted node to the selected node.**  
   Write the selected-node address to promoted-node offset 12.

8. **Update the selected node’s parent-like link.**  
   Write the promoted-node address to selected-node offset 4.

The function then returns without a value.

### Conventional graph interpretation

If offsets 4, 8, and 12 represent parent, left-child, and right-child links respectively, the transformation has the conventional right-rotation interpretation:

- The selected node’s left child becomes its parent.
- The promoted node’s former right child becomes the selected node’s left child.
- A non-null transferred child receives the selected node as its parent.
- The former incoming reference to the selected node is redirected to the promoted node.
- The selected node becomes the promoted node’s right child.

This interpretation requires a consistent starting graph. The function does not establish or check that consistency.

### Root selection and branch precedence

The root-reference comparison has precedence over parent-child inspection. When it matches, the function redirects the root reference even if the selected node’s offset-4 value is zero, a sentinel, or inconsistent with ordinary parent semantics. That value is still copied to promoted-node offset 4.

When the root reference does not match, the selected node’s offset-4 value is dereferenced. A valid parent-like destination is therefore required on that path.

### Aliasing and changing memory

The function assumes no explicitly checked separation between records. Overlapping records can make an earlier write change a field that is read later. Consequently, the ordinary tree-rotation outcome is conditional on a suitable non-overlapping layout.

In particular:

- Selected-node offset 8 is written before promoted-node offset 12 is reread.
- Promoted-node offset 4 is written before the owner’s root-reference address is read.
- Selected-node offset 4 is read again on the non-root path rather than relying on the earlier copied value.
- The final two link writes occur only after the incoming reference has been redirected.

For overlapping storage, the ordered accesses—not an abstract simultaneous graph replacement—define the available static description. No general postcondition for malformed or overlapping graphs is established.

## Side effects

For a stable, non-overlapping graph, the function performs five unconditional four-byte writes:

1. Selected-node offset 8.
2. Promoted-node offset 4.
3. Exactly one incoming-link location.
4. Promoted-node offset 12.
5. Selected-node offset 4.

It additionally writes transfer-node offset 4 when the transfer link passes the nonzero check.

Thus the ordinary path contains five writes with a null transfer link, or six with a non-null transfer link. Overlap can cause these writes to target the same physical bytes.

There are no explicit writes outside these locations, and no explicit I/O or function calls. The body contains no named global access. That does not prove global state is unchanged: supplied addresses may designate globally stored objects.

The transformation is not transactional. Earlier writes occur before later dereferences and before the final parent-child links are installed. The body contains no rollback, locking, or failure recovery. Unsynchronized observers are not given a consistent intermediate-state guarantee.

### Preconditions for the ordinary rotation result

The following are caller obligations, not checks performed by this function:

- The selected node and promoted node must support all accessed four-byte fields.
- The owner must provide a readable offset-16 field leading to a usable root-reference record.
- Every location written on the chosen path must be writable.
- A nonzero transfer link must identify a record with writable storage at offset 4.
- On the non-root path, the selected node’s parent-like link must identify a usable parent record.
- For a structurally correct tree result, the incoming reference and reciprocal parent-child links must already agree.
- Storage must satisfy the target platform’s access and alignment requirements.
- Concurrent mutation must not invalidate the assumptions needed for a stable graph transformation.

Zero is explicitly accepted only for the transfer-link check. Other dereferenced addresses are not protected by null checks.

## Acceptance examples

These examples are conditional contracts for stable, valid, non-overlapping storage. They are not results of runtime tests.

### Root case with a transfer node

Assume:

- The root reference points to the selected node.
- Selected-node offset 8 points to the promoted node.
- Promoted-node offset 12 points to a nonzero transfer node.
- Selected-node offset 4 contains a valid root-parent marker.

Expected result:

- The root reference points to the promoted node.
- Promoted-node offset 4 contains the former root-parent marker.
- Selected-node offset 8 points to the transfer node.
- Transfer-node offset 4 points to the selected node.
- Promoted-node offset 12 points to the selected node.
- Selected-node offset 4 points to the promoted node.

The root-parent marker is copied, not dereferenced through the non-root branch.

### Non-root case selected through offset 12

Assume the root reference does not identify the selected node, selected-node offset 4 identifies an existing parent, and existing-parent offset 12 identifies the selected node.

Expected result:

- Existing-parent offset 12 points to the promoted node.
- Existing-parent offset 8 is not explicitly written.
- Promoted-node offset 4 receives the existing-parent address.
- The remaining selected/promoted/transfer links change as described above.

### Non-root fallback through offset 8

Assume the root reference does not identify the selected node and existing-parent offset 12 does not equal the selected-node address.

Expected result: existing-parent offset 8 is overwritten with the promoted-node address, regardless of its previous value.

For this to be a valid tree rotation, that previous value should identify the selected node. If it does not, the function still takes the same write path; it does not report the inconsistency.

### Null transfer link

Assume promoted-node offset 12 remains zero throughout its reads.

Expected result:

- Selected-node offset 8 becomes zero.
- No transfer-node parent field is written.
- Incoming-reference redirection and the final selected/promoted links still occur.

### Missing promoted node

Assume selected-node offset 8 is zero.

There is no defined successful outcome established by this body. The function attempts to read through that value before any null rejection. No error return or safe no-op is provided.
