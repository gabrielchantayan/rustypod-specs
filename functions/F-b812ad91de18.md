# F-b812ad91de18

## Purpose

F-b812ad91de18 rearranges references in caller-supplied records around a target record. Under a conventional parent-linked binary-tree interpretation, the operation is a right rotation: the target’s child at byte offset +8 is promoted, the promoted node’s child at +12 is transferred to the target, and the target becomes the promoted node’s child at +12.

The rotation interpretation is inferred intent. Established behavior consists of ordered four-byte memory accesses, conditional replacement of an incoming reference, and updates to parent-like fields. The function does not validate a tree, enforce consistency between references, or update balancing metadata.

For consistent, non-overlapping records in stable ordinary memory, these accesses produce conventional rotation postconditions. For overlapping or inconsistent records, the ordered accesses remain the contract; the structural interpretation may no longer apply.

## Interface

The function accepts two address-bearing arguments and returns no value:

- **Context address:** identifies storage whose field at byte offset +16 supplies the address of a root-holder record.
- **Target address:** identifies the record around which references are rearranged.

The supplied representation uses integer-typed arguments as addresses. Relevant stored references and field transfers are four bytes wide. This establishes the field width in the supplied representation, not an independently verified machine pointer width or calling convention.

The following role names describe only the accessed layout:

| Record role | Byte offset | Width | Use |
|---|---:|---:|---|
| Context | +16 | 4 bytes | Read to obtain the root-holder address |
| Root holder | +4 | 4 bytes | Compared with the target; conditionally replaced |
| Target | +4 | 4 bytes | Read as the existing parent reference; finally replaced |
| Target | +8 | 4 bytes | Initially supplies the promoted-node address; then replaced |
| Promoted node | +4 | 4 bytes | Receives the target’s current parent reference |
| Promoted node | +12 | 4 bytes | Supplies the transferred-subtree reference; finally receives the target |
| Transferred subtree, when selected | +4 | 4 bytes | Receives the target address |
| Existing parent, on the non-root branch | +12 | 4 bytes | Read and conditionally replaced |
| Existing parent, on the fallback branch | +8 | 4 bytes | Replaced without checking its previous value |

The **promoted node** is the address read initially from target +8. That address is retained throughout the operation, even after target +8 is overwritten.

The **transferred subtree** ordinarily means the record referenced by promoted node +12. That field is read more than once; the function does not retain an entry-time snapshot for every later use.

### Preconditions

Normal completion requires every executed read and write to address suitable accessible storage:

- Target +8 must be readable and writable.
- The address read initially from target +8 must permit the accesses to promoted node +12 and +4.
- Target +4 must be readable and writable.
- Context +16 must be readable, and the resulting root-holder address must permit a read at +4.
- On the root-replacement branch, root holder +4 must also be writable.
- If the subtree condition is nonzero, the address obtained by the subsequent subtree-field read must permit a write at +4.
- On the non-root branch, the address obtained from the later target +4 read must permit a read at +12 and a write at whichever child offset is selected.

These are access requirements, not checks performed by the function. There is no explicit rejection of a zero target, zero promoted-node reference, zero root-holder reference, or invalid parent reference.

Conventional tree postconditions additionally require compatible layouts, consistent incoming references, absence of unexpected overlap, and no interfering mutation. Ownership and lifetime must already make the accesses valid.

## Behavior

### Ordered memory effects

The following sequence describes the accesses established by the supplied representation. Separate reads are not automatically entry-time snapshots.

1. **Obtain and retain the promoted-node address.**  
   Read four bytes from target +8. Retain that value as the promoted-node address for the remaining operation.

2. **Replace the target’s child reference.**  
   Read four bytes from promoted node +12 and write that value to target +8.

3. **Conditionally update the transferred subtree’s parent reference.**  
   Read promoted node +12 again and compare the value with zero.

   If the value is nonzero, read promoted node +12 once more to obtain an address, then write the target address to that address +4.

   The store in step 2 occurs between the initial subtree-field read and the condition read. If the destination of that store overlaps the subtree field in a way that changes its bytes, the condition can observe a different value from the value initially copied.

   In contrast, there is **no intervening store by this function between the condition read and the address reread**. Under stable ordinary-memory semantics, those two reads observe the same value, even when records overlap. A difference between those two reads requires interference or other externally changing memory behavior; overlap alone does not explain it.

   When the condition reads zero, no transferred-subtree parent write occurs.

4. **Copy the target’s current parent reference to the promoted node.**  
   Read target +4 and write the four-byte value to promoted node +4.

   This reads the value present at this point, not necessarily the value present on entry. Earlier stores may matter when storage overlaps.

5. **Locate and replace the incoming reference.**  
   Read context +16 to obtain the root-holder address. Read root holder +4 and compare it with the target address.

   - **Root-holder match:** write the promoted-node address to that same root holder +4 field.
   - **No root-holder match:** read target +4 again and retain the result as the existing-parent address. Read existing parent +12:
     - If it equals the target address, write the promoted-node address to existing parent +12.
     - Otherwise, write the promoted-node address to existing parent +8.

   The root-holder address is obtained once for this decision. The non-root parent address is also retained after its read. The fallback does not read or validate the previous value of existing parent +8.

6. **Attach the target beneath the promoted node.**  
   Write the target address to promoted node +12.

7. **Replace the target’s parent reference.**  
   Write the promoted-node address to target +4.

The function then returns without a result value.

### Conventional structural result

For stable, non-overlapping records with consistent tree references:

- Target +8 receives the promoted node’s original +12 reference.
- If that transferred reference is nonzero, the transferred subtree’s +4 field receives the target address.
- Promoted node +4 receives the target’s original +4 reference.
- One incoming reference is changed to identify the promoted node.
- Promoted node +12 receives the target address.
- Target +4 receives the promoted-node address.

The incoming reference is selected in this order:

1. Root holder +4, if it identifies the target.
2. Otherwise, existing parent +12, if it identifies the target.
3. Otherwise, existing parent +8, without verifying that it identifies the target.

The root-holder match takes precedence over the parent-child tests. On that branch, the target’s parent value is copied but is not dereferenced as a parent address.

### Aliasing and repeated reads

Aliasing can affect more than the transferred-subtree check. For example, a write through the transferred-subtree address can affect fields read later, and the write to promoted node +4 can affect a later target +4 read if those locations overlap.

Consequently, the parent reference copied to the promoted node and the parent reference subsequently used on the non-root branch are not guaranteed to be equal for arbitrary overlapping storage.

This does not imply that every overlap changes a value. In particular, a four-byte copy whose source and destination are exactly the same field leaves that field unchanged under stable ordinary-memory semantics. Whether another overlap changes later observations depends on the actual byte ranges and stored values.

### Widths and arithmetic

Every explicit field transfer is four bytes. Address selection uses byte offsets +4, +8, +12, and +16.

The only value tests are equality with zero or equality with the target address. There are no ordering comparisons, counters, lengths, or size calculations.

No explicit range, alignment, or address-overflow check is present. The supplied representation does not independently establish the concrete rules for address arithmetic, invalid pointer conversion, or overflow. It therefore does not justify a portable wraparound or fault guarantee.

## Side effects

The function changes existing storage. On every normally completing path, it executes five four-byte writes:

- Target +8.
- Promoted node +4.
- One selected incoming-reference field.
- Promoted node +12.
- Target +4.

It executes one additional four-byte write when the transferred-subtree condition is nonzero. These are counts of write operations; aliasing may cause several operations to affect the same storage.

Root holder +4 is read on every normally progressing path and written only when its read value equals the target address. Existing-parent child fields are accessed only on the non-root branch.

Under the non-overlapping interpretation, target +12 and promoted node +8 are not written. No payload, color, balance, height, count, or other metadata update is shown. Arbitrary overlap prevents a general promise that logically separate fields remain unchanged.

There are no explicit calls, allocations, releases, callbacks, I/O operations, or synchronization operations. No separately identified global variable is directly assigned, but the supplied addresses may refer to global storage.

The function does not establish or transfer ownership. Replacing a reference is not evidence that the referenced record is acquired, released, or destroyed.

There is no explicit rollback or error result. If execution cannot continue after an earlier store, no restoration mechanism is shown. The operation is not presented as atomic: intermediate states can contain child and parent references that disagree. Cross-thread visibility and fault consequences remain unspecified.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Unless stated otherwise, assume valid, non-overlapping storage, stable ordinary memory, and sufficient lifetime for every accessed record.

### Root replacement with a nonzero transferred subtree

Given:

- Root holder +4 identifies the target.
- Target +8 identifies the promoted node.
- Promoted node +12 identifies a nonzero transferred subtree.
- Target +4 contains an existing parent value.

After completion:

- Root holder +4 identifies the promoted node.
- Promoted node +4 contains the original target parent value.
- Promoted node +12 identifies the target.
- Target +4 identifies the promoted node.
- Target +8 identifies the transferred subtree.
- Transferred subtree +4 identifies the target.

The copied parent value need not be zero. On this branch, the function does not dereference that value as an existing-parent address.

### Non-root replacement through offset +12

Given that root holder +4 does not identify the target, target +4 identifies an existing parent, and that parent’s +12 field identifies the target:

- Existing parent +12 is replaced with the promoted-node address.
- Existing parent +8 is not explicitly written.
- The remaining local reference updates occur as described above.

### Non-root unchecked fallback

Given that root holder +4 does not identify the target and existing parent +12 also does not identify the target:

- Existing parent +8 is overwritten with the promoted-node address.
- Its previous value is not checked.
- The behavior is unchanged even if that field previously identified an unrelated record.

This is an unchecked replacement, not a validated repair of an inconsistent tree.

### Zero transferred-subtree reference

Given promoted node +12 is zero and remains zero through the initial copy and condition read:

- Target +8 becomes zero.
- No transferred-subtree parent write occurs.
- Incoming-reference replacement and the final target/promoted-node updates still occur.

### Missing promoted node

Given target +8 contains zero, the function attempts a read at offset +12 from that retained value. There is no explicit early return or error result.

The resulting fault, successful access to mapped storage, or other platform behavior is documented_only.

### Overlap affecting the earlier subtree observation

Suppose the four-byte destination at target +8 partially overlaps the field at promoted node +12, and the copy changes bytes of that source field.

The condition then reads the field after that store. It may differ from the value initially copied into target +8. Any subsequent subtree-parent write follows the later field value, not an entry-time snapshot.

If the two fields instead coincide exactly, the copy alone does not change their value under stable ordinary-memory semantics.

### Stable condition and address reread

Suppose the subtree condition reads a nonzero value. Even with overlapping records, if memory remains stable between that read and the immediate address reread, the reread supplies the same value.

A contract permitting those two reads to differ solely because records overlap would not match the established access sequence. A difference requires an external change or other non-stable memory behavior.
