# F-cc3be638e231

## Purpose

F-cc3be638e231 scans size-and-type records through a caller-supplied stream interface, maintains a logical 64-bit position, resolves records through opaque dependencies, and updates resolved objects. It can remember one resolved object for classification by a later record.

**Established behavior:** the 32-bit result is either zero or one. One indicates either a nonzero initial positioning result or a positioning span smaller than eight under a signed 64-bit comparison. Zero covers incomplete type reads, nonzero later positioning results, control suppression, and ordinary stopping conditions. It is not a comprehensive success indicator.

**Inferred intent:** the routine appears to traverse a structured container and associate attributes with selected records. Format names, record meanings, and object-update semantics are not established.

The contract below distinguishes explicit operations from assumptions about opaque dependencies. In particular, storage supplied as a read destination can escape to a dependency. Subsequent accesses to that storage are not necessarily accesses to an immutable snapshot.

The eight-byte destination places its low 32-bit word before its high word. This layout does not establish byte-order semantics for either read mode.

There are no visible null checks. Reached accesses require valid control storage, stream storage, method-table entries, and callable dependencies. Dependencies receiving destination addresses must obey whatever memory-access and lifetime requirements apply to those destinations; those requirements are not supplied here.

## Behavior

### Initialization and suppression

Initially, no object is remembered, and both sticky stopping flags are clear.

The first external call is the positioning operation with the origin words.

- A nonzero result returns one immediately, without reading the control byte.
- A zero result permits scanning initialization and the control-byte read.

The logical position starts at the origin. The boundary starts at the maximum signed 64-bit value. The limit sentinel is normalized as described above.

The control byte is read once. Exactly one returns zero without reading a record. Every other byte value permits scanning.

There is no limit comparison before the first record attempt. A zero or negative limit does not by itself prevent that attempt.

### Header reads and recognition precedence

At each attempt, the ordinary-size and type words are initialized to all ones. The two size-storage words are initialized to zero.

The routine requests the four-byte ordinary size first and the four-byte type second. It ignores the size-read result.

Before checking the type-read result, it performs an ordered recognition decision:

1. Read the external boundary-type constant and compare it with the current type word.
2. On equality, replace the boundary with the current logical position plus the **sign-extended current ordinary-size word**.
3. Only on inequality, read the stop-enabling constant and compare it with the current type word. Equality sets the sticky stop-enabling flag.

Boundary recognition therefore suppresses the stop-enabling comparison. If both constants would match, that attempt performs only the boundary action. An already-set stop-enabling flag remains set.

This decision occurs even when the type read returns fewer or more than four. It uses the destination contents present after that read. A partial or otherwise unsuccessful read can therefore affect a boundary or flag before termination.

After recognition, a type-read result other than four ends scanning with zero. There is no extended-size read or lookup for that attempt.

The boundary calculation uses the ordinary-size word, not the two-word size storage or a later transformed span. A word equal to one contributes one; a word with its top bit set contributes a negative displacement.

The ordinary-size destination has already escaped through its read. Its value at recognition is not guaranteed to equal the value immediately produced by the first read if a subsequent dependency can modify retained destinations.

### Preparing size storage

After a complete type read, the routine independently tests the **then-current ordinary-size word**:

- If it equals one, request eight bytes into the two-word size storage.
- Otherwise, copy the current ordinary-size word into the low size word. The high size word is not rewritten at this point.

The high word was initialized to zero before the header reads. Thus, absent intervening mutation of retained storage, the non-extended branch produces a zero-extended ordinary size. The unconditional operation is a low-word copy, not a fresh assignment of both words.

The extended-size read result is ignored. Unwritten bytes retain their previous contents if the read operation leaves them untouched.

Zero has no special open-ended interpretation.

### Lookup and size-read timing

For every complete type read, F-1150b6e2691f receives the lookup context. Its result becomes the first argument to F-7e7a566f4283; the other arguments are the then-current type word and zero.

Only **after both calls return** does the routine load the two size words as its initial advancement span. This is not a snapshot taken immediately after size acquisition.

A zero result from F-7e7a566f4283 selects unresolved processing. The span loaded after lookup determines advancement and subsequent span adjustment. No resolved-object updates or metadata processing occur.

A nonzero result selects resolved processing, in this order:

1. The two size words are read again as arguments to F-79946efb9e4f, together with the then-current type and transformation context. Its 64-bit result replaces the advancement span.
2. F-adfb976015af receives the resolved object, the transformed span’s high word, and the current logical position’s low and high words.
3. **After F-adfb976015af returns**, the size words are read again for F-0e9fcfc62715. Its other arguments are the resolved object and an additional machine-level value of unresolved provenance.
4. The ordinary-size word is checked again for equality with one. That result is supplied as a Boolean to F-80ae6cd293bc with the resolved object.

The initial post-lookup span load and the transformation arguments are separate evaluations, although no external call intervenes between them. The size arguments supplied after F-adfb976015af are a later evaluation across an external call.

The extended-size destination has escaped through the stream operation when that branch is taken; its address may also have escaped on an earlier iteration using the same storage. Without preservation contracts, dependencies can potentially change these words through retained addresses. Consequently:

- The post-lookup span need not equal the size initially read.
- Transformation inputs need not equal that initially read size.
- F-0e9fcfc62715 need not receive either the initially read size or the transformation inputs.

Calling its arguments the “original size” would therefore be too strong.

The next logical position is the current position plus the advancement span, modulo 64 bits. For a resolved record, advancement uses the transformation result, not the later size words supplied to F-0e9fcfc62715.

All resolved-object update calls precede minimum-span validation. They can occur even when the routine subsequently returns one.

### Remembering and metadata

After resolved-object updates, the routine compares the current type word with the external remembering-type constant. A match replaces the remembered reference with the resolved object. Unresolved processing never replaces it.

It then independently compares the current type word with the metadata-type constant. These decisions are not mutually exclusive. If both match, remembering precedes metadata processing.

Type storage also escapes through a read. Lookup, transformation, remembering, and metadata recognition use the type at their respective evaluation points; dependency preservation is not established.

A resolved metadata match causes three separate four-byte, mode-2 reads. All three destinations are initialized to all ones before the first read. They occupy consecutive 32-bit words, but reads proceed from the highest-addressed word to the middle word and then the lowest-addressed word.

Only the lowest-addressed word—the destination of the third read—is used for classification. All three return values are ignored. An earlier destination can therefore have changed without directly affecting classification; retained-pointer effects on the final candidate remain dependency-dependent.

Classification is attempted only when the remembered reference is nonzero. Let A and B denote external signed 32-bit comparison values, and C, D, and E denote external 32-bit difference-comparison values. The candidate is interpreted as signed for ordering:

| Ordered condition | Classification |
|---|---:|
| Candidate equals A | 1 |
| Candidate is signed-greater than A, and candidate minus A equals D | 3 |
| Candidate is signed-greater than A, the preceding test fails, and candidate minus A minus D equals E | 5 |
| Candidate is signed-less than A, and equals B | 2 |
| Candidate is signed-less than A, is not B, and candidate minus B equals C | 4 |

A match invokes F-c70c4aa95828 with the remembered reference and classification. No match means no call.

Difference arithmetic is 32-bit, without a visible checked-overflow path. Constants are read at their uses; the table describes branch precedence, not an entry-time snapshot of global values.

Resolved metadata processing subtracts twelve from the positioning span whether or not classification occurs. This does not reduce the already-computed logical advancement. Unresolved records do not enter this metadata path.

### Independent ordinary-size checks and positioning adjustment

The routine does not preserve a single “extended-size selected” Boolean. It checks the ordinary-size destination independently at three points:

1. Before lookup, to decide whether to request eight size bytes.
2. After F-0e9fcfc62715, to form the Boolean passed to F-80ae6cd293bc.
3. After resolved metadata processing, or directly after unresolved advancement, to decide whether to subtract eight from the positioning span.

At the third check, a current value of one subtracts eight, regardless of whether an extended-size read actually occurred. Conversely, an earlier extended-size read does not guarantee this subtraction.

The three decisions coincide only under a suitable preservation assumption for ordinary-size storage. Intervening dependencies include object-update calls and, when reached, metadata reads and classification.

After the optional twelve-byte and eight-byte subtractions, the adjusted span is compared with eight as signed 64-bit:

- Smaller than eight: return one immediately.
- Greater than eight: call the positioning operation with adjusted span minus eight.
- Exactly eight: make no positioning call.

All adjustments wrap at 64 bits. The logical next position remains based on the full advancement span.

Before a reached later positioning call, the storage used as the third metadata destination is assigned one. Since that destination may previously have escaped, this write is not necessarily invisible to a dependency retaining its address.

The exact-eight branch subsequently consults a positioning-result value that it does not assign. An earlier iteration may have assigned it; no initialization is visible before its first possible use. First-use continuation on this branch remains unresolved.

### Boundary and stopping checks

After the positioning stage, the routine sets the sticky boundary-reached flag if the next logical position is signed-greater than or equal to the boundary. This occurs before consulting the later-positioning result.

It then stops, with zero, at the first satisfied condition:

1. The consulted later-positioning result is nonzero.
2. The wrapped 64-bit difference between next position and origin is signed-greater than or equal to the effective limit.
3. Both sticky flags are set.

Otherwise scanning continues from the computed logical position.

Boundary-reached remains set even if a later record replaces the boundary. Stop-enabling is also sticky. Recognizing a stop-enabling record does not bypass that record’s remaining processing.

## Side effects

Established effects include the initial positioning call, one conditional control-byte read, ordered stream reads, external-constant reads, opaque object-update calls, optional classification, and conditional later positioning.

Recognition precedence affects observable reads: a boundary match suppresses the stop-enabling constant read, even on an incomplete type read.

The routine initializes and updates its working storage. Ordinary-size, type, two-word size, and metadata destinations are exposed to stream operations. Later direct writes and rereads of that storage must not be treated as inaccessible implementation details when considering a dependency that retains destination addresses.

No direct caller-output field is established. The final logical position is not returned separately.

No allocation, release, or reference-count operation is explicitly established. Remembering stores an object reference locally without a visible ownership operation. Replacement and termination do not visibly release it. Opaque dependencies may have ownership effects; none are assumed.

There is no rollback of stream activity or object updates when later validation or stopping ends the scan.

## Acceptance examples

These are conditional static expectations, not executed tests. Numerical examples assume no unmentioned destination mutation or arithmetic wrap.

1. **Initial failure:** a nonzero initial positioning result returns one without reading control or records.

2. **Suppression:** successful initial positioning and control byte one return zero without header reads.

3. **Incomplete type with boundary match:** a type-read result of three still permits boundary recognition. A match updates the boundary using the current sign-extended ordinary size, suppresses the stop-enabling comparison, and then returns zero without lookup.

4. **Equal recognition constants:** if both recognition constants equal the current type, only boundary recognition occurs. A clear stop-enabling flag remains clear.

5. **Unresolved ordinary record:** an ordinary size of 24, preserved through lookup, advances the logical position by 24 and supplies 16 to later positioning.

6. **Undersized unresolved record:** a preserved size of seven still reaches lookup. Minimum-span validation then returns one without later positioning.

7. **Preserved extended record:** ordinary size one and extended size 32, both preserved, produce advancement 32, adjusted span 24, and positioning argument 16.

8. **Size mutation across lookup and updates:** suppose an extended read produces 32. F-1150b6e2691f changes retained size storage to 40; lookup resolves an object. Transformation therefore receives 40. If it returns 48 and F-adfb976015af then changes the size storage to 56, F-0e9fcfc62715 receives 56 while logical advancement remains 48.

9. **Extended read without later subtraction:** suppose ordinary size one selects an extended read yielding 32, lookup is unresolved, and a lookup dependency changes the ordinary-size destination to two while preserving size storage. Advancement is 32. The final ordinary-size check does not subtract eight, so later positioning receives 24.

10. **Boolean and final adjustment disagree:** suppose an extended read occurred and the ordinary-size word is still one when F-80ae6cd293bc is called. It receives true. If that call changes the retained ordinary-size destination to two, the later adjustment does not subtract eight.

11. **Resolved metadata:** transformed span 40, no final eight-byte subtraction, and a metadata match cause three additional reads. Advancement remains 40; the adjusted span is 28 and positioning receives 20.

12. **Remembering and metadata coincide:** when both current comparisons match, the object is remembered before metadata reads. A matching classification targets that newly remembered reference.

13. **Later positioning failure:** a nonzero later positioning result stops with zero. Object updates remain performed, and boundary-reached evaluation precedes this stop.

14. **Exact-eight first use:** an adjusted span of eight causes no positioning call. If no earlier iteration assigned the consulted result, continuation remains documented_only rather than assumed successful.

## Uncertainties

Size acquisition, post-lookup loading, transformation arguments, later update arguments, and the three ordinary-size checks cannot unconditionally be collapsed into one snapshot.
- **documented_only — exact-eight continuation:** the consulted positioning-result storage lacks visible initialization before first use on this path. A preceding assignment can constrain later uses, but does not resolve first use.
- **documented_only — extra argument:** the additional machine-level input to F-0e9fcfc62715 has unresolved provenance and meaning.
- **documented_only — stream behavior:** byte order, mode meanings, partial-write behavior, positioning convention, and untested error conventions are unknown.
- **documented_only — external state and ownership:** constant values, preservation across calls, object validity, destination retention, and retention or release obligations require dependency contracts.
- **documented_only — extreme arithmetic:** wrapping and signed comparisons are visible; validity of overflowed positions is not established.
