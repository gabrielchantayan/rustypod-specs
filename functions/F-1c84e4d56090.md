# F-1c84e4d56090

## Purpose

F-1c84e4d56090 updates an object reached through a caller-supplied record and selects further actions according to whether a decremented four-byte count is zero.

The established behavior is:

- If the record’s object pointer is null, return without writing memory or invoking dependencies.
- Otherwise, decrement the initially referenced object’s count.
- If the decrement result is nonzero, invoke an auxiliary dependency and, if it returns, clear two fields of the caller record.
- If the decrement result is zero, conditionally invoke a resource-related dependency and perform a subsequent field clear, invoke the auxiliary dependency, and transfer control to a dependency marked nonreturning.

“Count,” “resource,” and “release” are descriptive interpretations. Reference-counted release is inferred intent; the supplied representation does not establish ownership rules, resource types, or which dependency, if any, deallocates memory.

Memory locations described by different field roles may overlap. A statement that a particular store is not executed does not establish that its destination remains unchanged: another store or a dependency may affect the same bytes through aliasing.

## Interface

The relevant caller-record layout is:

| Byte offset | Access width | Role |
|---|---:|---|
| +4 | 4 bytes | Associated-object pointer, initially read and conditionally cleared |
| +8 | 4 bytes | Field cleared on ordinary completion |

There is no explicit access addressed as caller-record offset +0.

The relevant associated-object layout is:

| Byte offset | Access width | Role |
|---|---:|---|
| +0 | 4 bytes | Count read and replaced by its decremented value |

F-U1 is a document-local opaque identifier for the auxiliary dependency whose mapping was not supplied. It does not assert an externally assigned identity.

The representation establishes four-byte field accesses and four-byte spacing between indexed object elements. This contract describes that apparent 32-bit layout, not a layout using arbitrary native pointer widths. Endianness and alignment requirements are not established.

For clarity:

- The **record** is the address supplied by the caller.
- The **initial object** is the nonnull pointer obtained by the first read of record offset +4.
- A **fresh object pointer** is a later read of record offset +4.

These identify access origins, not necessarily separate allocations. Neither record/object disjointness nor stability of the record’s object-pointer field is established.

### Output and completion

No explicit return value is provided.

There are three principal outcomes:

1. Normal return after the initial object-pointer read finds null.
2. Normal return on the nonzero-decrement path, after F-U1 returns and the two ordinary-completion stores execute.
3. A call to F-feee9156a257 on the zero-decrement path, after preceding dependencies return. That dependency is marked nonreturning.

Faults or dependencies that do not return can prevent later operations. There is no locally defined error result.

### Preconditions

Execution requires valid memory for each access when that access occurs:

- Record offset +4 must initially support a four-byte read.
- A nonnull initial object must support a four-byte count read and write.
- Subsequent object-field reads must remain valid at their actual execution times.
- The nonzero-decrement path requires writable record offsets +4 and +8 after F-U1 returns.
- The conditional resource-field store requires a valid destination obtained from a fresh record-pointer read after F-8349c252c168 returns.
- Dependency arguments must satisfy requirements not supplied here.

The record address itself is not checked for null. Later fresh object pointers are not checked for null before their associated accesses.

No atomic operation, lock, or other synchronization is shown. Safe concurrent use requires an external protocol.

## Behavior

### Initial read and null case

The first relevant operation reads the four-byte object pointer at record offset +4.

If it is null, the function returns immediately:

- No count is accessed.
- No dependency is invoked.
- Record offset +8 is neither read nor written.
- No store to record offset +4 is executed.

This path does not normalize or clear the record.

For a nonnull value, the function retains the initial object pointer for the count update, the later auxiliary-value read, and the final dependency argument.

### Count update and branch selection

The function reads the four-byte count at initial-object offset +0, subtracts one, and stores the result at that same address. This store precedes every dependency call.

Branch selection uses the decrement of the value already read, rather than a separate reread of the stored count.

For arithmetic representable in the displayed integer model:

| Initial count | Stored result | Selected path |
|---:|---:|---|
| 1 | 0 | Zero-decrement path |
| 2 | 1 | Nonzero-decrement path |
| 0 | −1 | Nonzero-decrement path |
| −1 | −2 | Nonzero-decrement path |

There is no explicit count validation, saturation, underflow guard, or error report. Four-byte storage alone does not establish defined signed wraparound at the minimum representable value.

The count store can affect other logical fields if their addresses overlap. In particular, it can alter record storage before any later fresh record-pointer read. Retaining the initial object pointer does not imply that the record still contains that pointer.

### Nonzero-decrement path

When the decrement result is nonzero, the ordered operations are:

1. Read the four-byte value at initial-object offset +8.
2. Invoke F-U1 with that value.
3. If F-U1 returns, store four-byte zero at record offset +4.
4. Store four-byte zero at record offset +8.
5. Return.

F-U1 is invoked even if its argument is zero.

The two record stores are separate and ordered. They are not an atomic record update.

This path has no separate store addressed as an object resource-field clear. Nevertheless, either record store may affect object storage if the record and object overlap. Conversely, the earlier count store may already have affected record storage.

If F-U1 does not return, neither ordinary-completion store is reached. The count update has already occurred; no rollback is shown.

### Zero-decrement path

When the decrement result is zero, the function first rereads the pointer at record offset +4. It uses that fresh pointer to read a four-byte value at object offset +4.

This read does not necessarily address initial-object offset +4. The record’s pointer field may have changed through an earlier overlapping write or external activity.

If the resource-related value is nonzero:

1. F-8349c252c168 receives that value and the integer constant 43.
2. If the dependency returns, the function rereads record offset +4.
3. It writes four-byte zero at offset +4 of the object reached by this latest pointer.

The dependency argument and the subsequent clear therefore need not refer to the same object. The post-call clear follows the freshly read pointer without a null check.

If the resource-related value is zero, both F-8349c252c168 and the associated post-call clear are skipped.

After either alternative, the function:

1. Reads the four-byte value at initial-object offset +8.
2. Invokes F-U1 with that value.
3. If F-U1 returns, invokes F-feee9156a257 with the initial object pointer.

The auxiliary value is read after the optional resource call and clear. It is not cached before them. Dependency effects or overlapping writes can therefore change the value supplied to F-U1.

The final argument remains the initial object pointer regardless of later changes to record offset +4. Its continued validity is not established merely by retaining its address.

Under the supplied nonreturn annotation, the ordinary-completion stores to record offsets +4 and +8 are not executed on this path. Other writes may affect those locations through aliasing; dependencies may also modify them.

## Side effects

### Direct writes and their order

The function directly performs only the following described stores:

| Condition | Addressing basis | Stored value |
|---|---|---|
| Initial object pointer is nonnull | Initial object, +0 | Count minus one |
| Zero decrement, nonzero resource-related value, and F-8349c252c168 returns | Fresh post-call object pointer, +4 | Four-byte zero |
| Nonzero decrement and F-U1 returns | Record, +4 | Four-byte zero |
| Immediately after the preceding store | Record, +8 | Four-byte zero |

The table describes how each destination is selected. It does not establish that the destinations are disjoint.

Consequences of aliasing include:

- A count update can modify a record field.
- A resource-field clear can modify record storage.
- An ordinary-completion record clear can modify object storage.
- A later read can observe a change caused by an earlier store even without any dependency modifying memory.

No general preservation guarantee applies to a field merely because no store is explicitly addressed using that field’s logical name.

### Ownership and lifetime

The operation resembles relinquishing a reference and performing final cleanup when the count reaches zero. That interpretation is not an established ownership contract.

Specifically:

- F-8349c252c168 is not established to release, retain, or consume its first argument.
- F-U1 is not established to release, retain, or merely inspect its argument.
- F-feee9156a257 is not established to deallocate the initial object.
- Clearing record storage does not prove object deallocation.
- Skipping the ordinary-completion stores does not prove record preservation.

No dependency is known to preserve globals, reachable memory, or allocation state. Continued accesses after dependency calls require the accessed storage to remain valid.

## Acceptance examples

These are conditional static acceptance examples, not runtime results. Unless stated otherwise, addresses are valid, arithmetic is representable, dependencies preceding the final call return normally, and dependencies do not modify relevant memory. Disjoint storage is assumed only where explicitly stated.

### Null object pointer

Given a null value at record offset +4 and any value at record offset +8:

- The function returns.
- No dependency is invoked.
- No count access or direct store occurs.
- Record offset +8 remains unchanged by this function.

### Count two with disjoint storage

Given a record and object with nonoverlapping storage and initial count two:

- The object count becomes one.
- F-U1 receives the object’s offset +8 value.
- Record offset +4 is cleared.
- Record offset +8 is then cleared.
- F-8349c252c168 and F-feee9156a257 are not invoked.

### Final decrement with no resource-related value

Given initial count one and a zero resource-related value at the address reached by the subsequent fresh pointer read:

- The count becomes zero.
- F-8349c252c168 is skipped.
- The conditional resource-field store is skipped.
- F-U1 receives the value subsequently read from initial-object offset +8.
- F-feee9156a257 receives the initial object pointer.
- The ordinary-completion stores to record offsets +4 and +8 are not executed; other writes may affect those locations through aliasing.

### Count storage overlaps record offset +8

Given:

- Record offset +4 points to record offset +8.
- The four-byte value at record offset +8 is one.
- The resource-related value at record offset +12 is zero.
- The auxiliary value at record offset +16 is readable.

Then:

- The initial object begins at record offset +8.
- Decrementing its count writes zero to record offset +8.
- The zero-decrement path is selected.
- F-8349c252c168 and its associated clear are skipped.
- F-U1 receives the value at record offset +16.
- F-feee9156a257 receives the initial object address.
- The ordinary-completion stores are not executed, but record offset +8 has nevertheless been cleared by the count update.

This case requires no dependency mutation.

### Final decrement with a nonzero resource-related value

Given disjoint record and object storage, initial count one, and a nonzero resource-related value:

- The count becomes zero.
- F-8349c252c168 receives the resource-related value and 43.
- After its return, the resource field reached through a fresh record-pointer read is cleared.
- F-U1 is invoked next.
- F-feee9156a257 is invoked last.

### Pointer replacement during resource handling

Given that F-8349c252c168 changes record offset +4 to another valid object:

- The post-call resource clear targets the replacement object’s offset +4.
- The subsequent auxiliary read still uses initial-object offset +8.
- The final call still receives the initial object pointer.

If the replacement object overlaps the initial object, the clear can affect the later auxiliary value.

### Initial count zero

Given initial count zero and valid storage for the nonzero-decrement path:

- The count becomes negative one.
- F-U1 is invoked.
- If it returns, the ordinary-completion stores execute.
- Final-count cleanup is not selected merely because the initial count was zero.

### Auxiliary dependency does not return

Given a nonzero decrement result and an F-U1 invocation that does not return:

- The count update has occurred.
- Neither ordinary-completion store executes.
- This does not guarantee that record fields retain their entry values, because the count write may alias them.
