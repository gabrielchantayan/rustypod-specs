# F-3e23cad76c41

## Purpose

F-3e23cad76c41 processes two adjacent records within a selected group. For each record whose handle field is nonzero, it derives a quantity from a stored 32-bit value, caps that quantity at 16,384, calls an external dependency with the handle and quantity, and then clears the stored value.

The established behavior is a conditional call followed by a state reset. The meaning of the handle and quantity is not established. In particular, the dependency must not be described as freeing memory, transferring data, or releasing a resource without additional evidence.

This contract describes statically visible behavior. No runtime tests have been performed.

## Interface

The function accepts two arguments:

| Argument | Recovered representation | Role |
|---|---|---|
| Base | 32-bit integer used in address formation | Establishes the origin of the record storage. |
| Selector | 32-bit integer | Selects a group using a 56-byte stride. |

There is no explicit return value and no status result.

The function processes exactly two record positions, in ascending order. Each record occupies a 28-byte stride. For ordinary, nonoverflowing address calculations:

- The first record begins at Base plus Selector multiplied by 56.
- The second record begins 28 bytes after the first.
- Each record’s handle field is at byte offset 12.
- Each record’s quantity-source field is at byte offset 16.

The relevant layout is therefore:

| Group-relative offset | Width | Meaning |
|---|---:|---|
| 12 | 4 bytes | First record’s handle |
| 16 | 4 bytes | First record’s quantity source |
| 40 | 4 bytes | Second record’s handle |
| 44 | 4 bytes | Second record’s quantity source |

The routine does not inspect the remaining record bytes in the visible body. Their purpose, initialization requirements, and ownership are unknown.

The handle is read as a 32-bit integer and tested against zero. Its interpretation by the dependency is unknown. A nonzero value is sufficient to select the call path; no further handle validation is visible.

The quantity source is read as a 32-bit integer. The derived quantity is held in a 32-bit unsigned value before its cap is applied. Clearing the source is an explicit four-byte write of zero.

### Preconditions

For defined, ordinary execution:

- Address calculations must identify accessible storage without relying on unspecified overflow behavior.
- Each visited handle field must be readable.
- A record’s quantity-source field must be readable and writable if its handle is nonzero.
- The external dependency must accept the supplied handle and quantity for execution to continue normally.
- Storage needed after an external call must remain valid when that call returns.

No bounds, accessibility, alignment, or handle-validity checks are visible. A zero handle avoids the visible quantity-field access for that record, but does not avoid the handle read itself.

Byte order and alignment requirements are not established by the supplied material.

## Behavior

### Record traversal

The first record is fully processed before the second record is examined.

For each record, the function first reads the four-byte handle at record offset 12.

If that read produces zero:

- No dependency call is made for that record.
- The quantity-source field is not read by this function.
- The quantity-source field is not cleared by this function.
- Processing continues to the next record, if any.

If the handle is nonzero, the function reads the four-byte quantity source at record offset 16 and derives the dependency’s second argument.

### Quantity derivation

The visible operation shifts the quantity source left by two bit positions and places the result in a 32-bit unsigned value. The comparison that follows is unsigned:

- Values from 0 through 16,383 are retained.
- Values greater than 16,383 are replaced with 16,384.

Thus, whenever the intermediate shift has defined arithmetic meaning, the outgoing quantity is no greater than 16,384. There is no requirement that it be positive. A nonzero handle with a zero quantity source still produces a dependency call, with quantity zero.

For nonnegative source values whose signed left shift is defined, the result can be described as follows:

- A source from 0 through 4,095 produces four times that source.
- A source of 4,096 produces 16,384.
- Larger sources within the defined signed-shift range also produce the capped value 16,384.

The cap is applied after the shift, not before it. This distinction matters for source values outside the defined signed-shift range. The supplied representation reads the source as signed before shifting, so negative values and values whose shifted result cannot be represented require separate qualification. The unsigned destination does not, by itself, establish defined signed-shift behavior for all possible source bit patterns.

If a target-level interpretation instead establishes a fixed-width, wrapping shift, the cap applies to the resulting 32-bit pattern interpreted as unsigned. Such semantics could differ from multiplying an unrestricted mathematical integer by four and then capping it. That interpretation is not established here.

### Dependency invocation and reset

For an active record, the external dependency receives two arguments:

1. A handle read from record offset 12 at the call site.
2. The derived, capped quantity.

The visible representation contains a handle read for the zero test and another handle read used to supply the call argument. It does not explicitly preserve the tested value as the call argument. If the storage is stable during processing, both reads yield the same handle.

After the dependency returns normally, the function writes four zero bytes to the current record’s quantity-source field.

The reset is unconditional with respect to any dependency return value: no result is inspected. There is no visible success/failure branch.

The handle is not explicitly cleared. No other field is explicitly changed by this function.

### Completion and interruption

Following normal completion of the second record, the function returns without a value.

There is no explicit recovery path for invalid memory, arithmetic problems, dependency failure, or a dependency that does not return normally. If execution stops during the first record, processing of the second record is not guaranteed. If a dependency does not return normally, the following quantity reset is not guaranteed to occur.

## Side effects

The directly visible memory accesses are limited to the handle and quantity-source fields described above.

For each record, the observable logical sequence is:

- Read the handle for the nonzero decision.
- On the active path, read the quantity source and derive the quantity.
- Obtain the handle argument from the handle field and invoke the dependency.
- After normal return, clear the quantity source.
- Proceed to the next record.

The quantity reset occurs after the external call, not before it. Consequently, at call entry the function has not yet cleared that field. The dependency may itself inspect or change the field; its behavior is unknown.

There is no snapshot of both records before processing begins. In particular, the second record’s handle and quantity are not read until after the first record’s call and reset have completed. Changes made to the second record by the first dependency invocation can therefore affect whether the second invocation occurs and what arguments it receives.

The function’s own reset also follows any changes made by the dependency to the current quantity-source field. If that storage remains valid, a value written there by the dependency is overwritten with zero when the call returns.

### Ownership and lifetime

No allocation, deallocation, or ownership transfer is explicitly established by the visible body.

The handle’s storage type does not establish that it is a pointer. Likewise, the external call does not establish whether the dependency borrows, retains, consumes, or releases any associated resource.

The caller must not assume that the dependency preserves unrelated memory or global state. Conversely, this contract does not assert that the dependency modifies them. Those effects remain unknown.

If the dependency invalidates the current record’s storage, the subsequent reset may be invalid. The visible function contains no lifetime check before that write.
