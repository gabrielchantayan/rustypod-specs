# F-80e671e6c24b

## Purpose

F-80e671e6c24b coordinates two dependency calls, publishes two resulting 32-bit words to caller-supplied destinations, and returns a normalized status.

The established behavior is not a conventional “produce outputs only on success” operation. Both dependency calls occur, and both destination writes follow, regardless of whether the first dependency reports zero or nonzero, provided execution returns normally from each call and the memory accesses complete.

The names, domain meaning, and ownership of the resulting words are unknown. They must not be assumed to be allocated objects, handles, or valid pointers merely because the temporary locations containing them are initially populated with pointer values.

## Interface

### Inputs

The function takes four arguments:

| Argument | Established role | Width and requirements |
|---|---|---|
| First destination | Address at which the first result word is written | Pointer representation is 32 bits in the supplied representation; destination must support a 32-bit write when reached |
| Second destination | Address at which the second result word is written | Pointer representation is 32 bits in the supplied representation; destination must support a 32-bit write when reached |
| First input word | Initial contents of the first scalar temporary | Exactly 32 bits; no interpretation or range restriction is established |
| Second input word | Initial contents of the second scalar temporary | Exactly 32 bits; no interpretation or range restriction is established |

The two destination arguments serve two roles:

1. Their address values initialize a temporary result pair.
2. Their original address values identify the destinations for the final explicit stores.

The function does not initialize the temporary result pair by reading the contents of either destination. Existing destination contents therefore do not directly determine that initialization. Dependencies may nevertheless access those contents through addresses available to them.

There is no explicit destination validation, null check, alignment check, or input-word validation in the supplied body. Readability, alignment, and any additional accessibility requirements imposed by the dependencies are not established.

### Return value

The function returns one 32-bit word:

| First dependency’s returned status | Final return word |
|---|---|
| Zero | `0x00000000` |
| Any nonzero value | `0xFFFFFFFB` |

If interpreted as a signed 32-bit integer, `0xFFFFFFFB` represents −5. If interpreted as unsigned, it represents 4,294,967,291. The bit pattern is established; a symbolic error name or application-specific meaning is not.

The first dependency’s exact nonzero status is discarded. Positive and negative nonzero statuses receive the same final mapping.

The second dependency supplies no status used by this function.

## Behavior

### Temporary state and initialization

Before calling either dependency, the function establishes four local 32-bit words:

- A first result slot initialized with the first destination’s address value.
- A second result slot initialized with the second destination’s address value.
- A first scalar slot initialized with the first input word.
- A second scalar slot initialized with the second input word.

These are copies of the argument values, not copies of memory addressed by those arguments.

The supplied representation places the two result slots at consecutive four-byte offsets and the two scalar slots at consecutive four-byte offsets. This supports treating them as two ordered, eight-byte temporary regions for describing the call interface:

| Region | Offset | Initial contents |
|---|---:|---|
| Result region | 0 | First destination address |
| Result region | 4 | Second destination address |
| Scalar region | 0 | First input word |
| Scalar region | 4 | Second input word |

The visible calls pass the address of the first slot of each applicable region. The dependency implementations are unavailable, so their actual access extent is unknown. The apparent adjacency does not establish a documented aggregate type, a terminator, or permission for arbitrary additional accesses.

### First dependency call

### Second dependency call

1. The address of the first result slot.
2. The address of the first scalar slot.

This call is unconditional with respect to the first dependency’s status. A nonzero first status does not bypass it.

The scalar region is the same local storage supplied to the first dependency, including any changes made before the second call. The function does not make a fresh scalar copy for this call.

No returned value from this dependency influences the visible status mapping. Its effects on local storage or external state may still affect execution.

### Output publication

After the second dependency returns normally, the function performs these explicit destination operations in order:

1. It obtains the current first result-slot value and writes that 32-bit word to the original first destination.
2. It obtains the current second result-slot value and writes that 32-bit word to the original second destination.

Changing a result slot does not redirect the corresponding final store. For example, replacing the first result slot with a different address-shaped word changes the word published to the first destination, not the destination address used by the wrapper.

The second result-slot value is obtained for its store after the first store in the supplied operation order. The function does not establish an atomic two-word publication or a transaction.

If both destinations identify the same writable 32-bit location, the second store is the last explicit wrapper store to that location. In the ordinary case where the first store does not alter the second result slot, the location therefore ends with the second result value.

If destinations overlap without being identical, the visible ordering remains first store then second store. Exact overlapping-byte results depend on the execution environment’s byte order, alignment behavior, and treatment of such accesses; those details are not established here.

### Status completion

After the two explicit output stores, the function returns the normalized status determined by the first dependency’s earlier returned value.

There is no explicit rollback, output clearing, retry, or compensating action on a nonzero status. There is also no arithmetic on the input words or result words. No increment, size calculation, range conversion, or overflow behavior is involved in the visible body.

## Side effects

### Directly established effects

The function:

- Creates and initializes temporary local storage.
- Calls F-a8da4de9bd1d before F-1b1da0aa8204.
- Exposes local scalar storage to both dependencies.
- Exposes local result storage to the second dependency.
- Writes one 32-bit word to each destination, in argument order, on normal completion.
- Returns a 32-bit normalized status.

The wrapper performs no explicit read of either destination’s existing contents. This does not establish that the full operation is write-only with respect to those locations: dependencies may read them.

### Ownership and lifetime

The visible body contains no explicit allocation or release operation. That observation does not establish that the dependencies allocate nothing or release nothing.

The result words have no established ownership semantics. A caller must not infer that a returned word grants ownership, requires release, remains valid for a particular duration, or denotes memory at all.

The temporary regions have invocation-local lifetime. Their addresses are passed to dependencies, but no retained-reference protocol is shown. Whether a dependency retains either address is unknown. No validity after this invocation is established for such a retained address.

### Failure boundaries

No explicit recovery path handles an invalid destination or a dependency that fails to return normally.

Because destination validation is absent:

- Dependency effects can occur before an invalid final destination is encountered.
- The first destination write can complete before the second destination write fails.
- A nonzero first status does not protect either destination from being written.
- Neither return pattern is guaranteed if execution is interrupted before normal return.

These are ordering consequences, not claims about a particular fault, exception, or signal mechanism.

## Acceptance examples

These are conditional contract examples, not executed tests. Each assumes normal dependency returns and valid accesses unless stated otherwise.

### Zero status with changed result words

Suppose the first dependency returns zero. Suppose the second dependency leaves the result slots containing `0x11223344` and `0xAABBCCDD`.

Expected behavior:

- The first destination receives `0x11223344`.
- The second destination receives `0xAABBCCDD`.
- The function returns `0x00000000`.

The second dependency’s internal reason for producing those values is outside this contract.

### Nonzero status still publishes outputs

Suppose the first dependency returns a nonzero status and the second dependency leaves result values `0x01020304` and `0x55667788`.

Expected behavior:

- The second dependency is still called.
- Both values are published in destination order.
- The function returns `0xFFFFFFFB`.

Returning the first dependency’s original nonzero value, skipping the second dependency, or suppressing output publication would not match the visible behavior.

### Dependencies leave temporary contents unchanged

Suppose both dependencies return normally and leave all four temporary words unchanged.

Expected behavior:

- The first destination receives its own original address representation.
- The second destination receives its own original address representation.
- The return value depends only on whether the first dependency returned zero.

This example distinguishes address-value initialization from initialization using the destinations’ previous contents.

### Scalar mutation reaches the second dependency

Suppose the first input word is `0xFFFFFFFF`, and the first dependency replaces the first scalar slot with `0x00000007`.

Expected behavior:

- The second dependency receives a pointer to scalar storage whose first slot now contains `0x00000007`.
- The wrapper does not restore `0xFFFFFFFF` before that call.
- The wrapper itself imposes no signedness interpretation on either word.

### Identical destinations

Suppose both destination arguments identify the same valid 32-bit location. Suppose the result slots contain two different words and remain unchanged during publication.

Expected behavior:

- The first result word is stored first.
- The second result word is stored second.
- After both stores, that location contains the second result word.
- Destination aliasing does not itself change the status mapping.

### Invalid second destination

Suppose dependencies return normally, the first destination is valid, and the second destination cannot accept the required store.

The established ordering permits the first store to occur before the invalid second access. No rollback or ordinary return value is promised. The precise failure mechanism is documented_only.
