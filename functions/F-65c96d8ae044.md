# F-65c96d8ae044

## Purpose

F-65c96d8ae044 interprets a ten-byte input as three unsigned fields: a 15-bit leading field and two 32-bit words. It selects one of two stored 32-bit results for distinguished field combinations. Otherwise, it constructs a result through an ordered sequence of seven dependency calls.

The highest bit of the first input byte does not participate in the extracted fields or in any subsequent operation visible in this function. In particular, this function does not visibly apply that bit as a sign.

The layout and dependency sequence suggest a numeric-format conversion, possibly involving an exponent and a split significand. That interpretation is **inferred intent**, not an established semantic contract. The dependency implementations and stored constant values are unavailable. The established contract is therefore expressed in terms of field extraction, fixed-width arithmetic, call order, and returned bits.

## Interface

### Input

The function accepts one pointer to byte-addressable storage.

For the behavior described here, the pointer must make offsets 0 through 9 readable. There is no length argument, null-pointer check, or accessible-storage check. Bytes beyond offset 9 are not explicitly read by this function.

The input layout is:

| Byte offsets | Interpretation |
|---|---|
| 0–1 | A 15-bit unsigned field, formed from the low seven bits of byte 0 followed by all eight bits of byte 1 |
| 2–5 | A 32-bit unsigned word, with byte 2 most significant and byte 5 least significant |
| 6–9 | A 32-bit unsigned word, with byte 6 most significant and byte 9 least significant |

This document calls these fields the **selector**, **upper word**, and **lower word**, respectively. These are descriptive labels, not assertions about a particular external numeric format.

The selector ranges from 0 through 32,767. Each word ranges from 0 through 4,294,967,295.

Byte-wise extraction does not itself require an aligned input address. Platform-specific pointer validity and memory-access restrictions remain outside the supplied evidence.

## Behavior

### Field extraction and input access

All three fields are extracted before the branch selection.

At the level of the supplied representation, the access groups occur in this order:

1. Bytes 0–1 are used to form the selector.
2. Bytes 2–5 are used to form the upper word.
3. Bytes 6–9 are used to form the lower word.

The exact order of individual byte reads within each group is not established. The contract does not require ascending-address reads within a group.

The high bit of byte 0 is masked out. With otherwise identical, stable input bytes, changing only that bit leaves all three extracted fields unchanged.

Both 32-bit words are assembled in most-significant-byte-first order, independently of the machine’s native byte order. This does not establish the byte order of the separately stored global results.

There are no further explicit input-byte reads after extraction. Consequently, changes to the input storage made by a dependency do not cause this function to recompute its already extracted fields. Dependencies may nevertheless observe shared state through mechanisms not visible here.

### All-zero field case

If the selector, upper word, and lower word are all zero, the function reads and returns one 32-bit value from a designated global location, called the **zero-case result storage** in this document.

The ignored high bit of byte 0 does not affect this test. Thus, either value of that bit can lead to the same zero-case selection.

This branch makes no calls to the three mapped dependencies.

The numeric value and interpretation of the stored result are unknown. “Zero-case” describes the branch condition, not a proven zero-valued return.

### Maximum-selector case

If the selector is 32,767, the function reads and returns one 32-bit value from a different designated global location, called the **maximum-selector result storage**.

The upper and lower words do not affect the selected return storage on this branch, but their input bytes have already been read.

This branch makes no calls to the mapped dependencies. It does not distinguish different upper-word or lower-word payloads once the maximum selector has been identified.

There is no established basis for calling this result infinity, a not-a-number value, an error, or a saturation value.

### Ordinary case

All remaining inputs take the ordinary path:

- The selector is not 32,767; and
- At least one of the three extracted fields is nonzero.

This path contains seven dependency invocations, in a fixed sequence.

First, the upper word is increased by 2,147,483,648 using 32-bit unsigned arithmetic. Overflow wraps modulo 4,294,967,296.

For a 32-bit word, this operation toggles its most significant bit. It is not saturation and does not establish signed conversion semantics.

Next, F-1b22d7e17791 receives four 32-bit arguments, in this order:

1. The low 32 bits of that intermediate.
2. Its high 32 bits.
3. A 32-bit value read from the first ordinary-path global constant location.
4. A 32-bit value read from the second ordinary-path global constant location.

The first constant location precedes the second in argument position. The relative timing of those two global reads is not established.

The 64-bit result from this invocation is then passed to F-56f339d3de83 as low and high 32-bit halves, followed by a third 32-bit argument. That third argument is the selector minus 16,414, calculated with 32-bit unsigned arithmetic.

The returned 64-bit value is retained as the upper-word contribution.

#### Lower-word contribution

Only after the upper-word contribution has been obtained does the function begin the lower-word contribution.

The lower word undergoes the same modulo-32-bit addition of 2,147,483,648 and is passed to F-b3a54d881220.

1. The low 32 bits of this new intermediate.
2. Its high 32 bits.

2. The high half of the lower-word contribution.
3. The low half of the upper-word contribution.

## Acceptance examples

These examples are conditional static acceptance criteria. No runtime tests have been performed.

### Zero fields with either ignored-bit value

For ten input bytes all equal to zero, the function must select the zero-case result storage and make no mapped dependency calls.

If only the high bit of byte 0 is changed, the same branch must be selected. Under unchanged global storage, the returned 32-bit pattern must be the same.

Neither example establishes that the return pattern itself is numeric zero.

### Maximum selector with arbitrary payload

When the low seven bits of byte 0 are all set and byte 1 is 255, the selector is 32,767.

For any values in bytes 2–9, the function must select the maximum-selector result storage and make no mapped dependency calls. The upper and lower word bytes are nevertheless read before that selection.

Changing only the high bit of byte 0 must not change the selected branch.

### Zero selector with a nonzero word

If the selector and upper word are zero but the lower word is one, the all-zero shortcut must not be taken.

The ordinary path must execute all seven dependency calls. The third arguments supplied to F-56f339d3de83 must carry the unsigned 32-bit representations of −16,414 and −16,446, respectively.

The upper-word calculation must still occur despite its extracted word being zero.
