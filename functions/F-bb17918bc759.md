# F-bb17918bc759

## Purpose

F-bb17918bc759 processes a caller-supplied byte buffer as a sequence of framed units. It selects units whose classified type is 1 or 5, delegates their header interpretation, requests that their remaining payload bytes be compacted into the beginning of the supplied buffer, constructs per-unit records in a mutable context, and invokes a final processing dependency.

This purpose is inferred from the data flow. The directly established behavior is the sequence of reads, writes, dependency calls, pointer calculations, and return propagation described below. In particular, the implementations of the external memory-operation dependencies are unavailable; their apparent clearing and copying roles are not independently established.

The function is not transactional. It writes the input pointer into the context before validating the input arguments. On the accepted-input path, context updates and dependency calls precede the final result, and a context counter is incremented regardless of whether that final result denotes success.

## Interface

### Arguments

The function accepts five arguments:

1. **Context reference:** a 32-bit address identifying writable state. It is dereferenced before input validation.
2. **Input-buffer reference:** a byte address. A null reference is explicitly rejected.
3. **Declared input length:** an unsigned 32-bit quantity. Accepted values are 1 through 262,144 inclusive.
4. **First opaque processing argument:** a 32-bit value retained for the final dependency call.
5. **Second opaque processing argument:** a 32-bit value passed to that same final dependency.

The result is a 32-bit value:

- Explicit argument rejection returns the bit pattern `0xffffffff`.
- Otherwise, the result is the value returned by F-94d3fda99b32, without local interpretation.

No context-size, alignment, buffer-capacity, framing, or record-capacity argument is supplied.

## Behavior

### 1. Entry and explicit rejection

The first observable context operation is a 32-bit read at `0x40`. That captured value is reused as the framing-prefix width throughout the scan.

Next, the function stores the supplied input-buffer address at `0x14`.

Only then does it reject any of the following:

- Declared length is zero.
- Input-buffer reference is null.
- Declared length exceeds 262,144.

On rejection, it returns `0xffffffff`. It does not locally initialize the remaining-input field, record count, record areas, or derived state on this path.

Consequently, even an invalid input requires a context valid for the initial read and pointer store. A null context is not handled.

### 2. Accepted-input initialization

For accepted arguments, the function performs these operations in order:

1. Stores the declared length at `0x24`.
2. Preserves the initial length and first opaque processing argument for later use.
3. Calls F-000000000001 with the address `context + 0x4c` and extent `0x78`.
4. Writes zero to the 32-bit field at `0x1e4`.
5. Calls F-000000000001 with `context + 0x1e8` and extent `0x78`.
6. Calls F-000000000001 with `context + 0x19c` and extent `0x48`.
7. Writes zero to the 32-bit field at `0x30`.

The three calls have the shape of region initialization, but their actual write semantics are unknown.

The source cursor and compacted-output cursor both initially point to the input-buffer start. The selected-unit count and a signed 16-bit difference baseline both begin at zero.

### 3. Scan continuation and framing

Before each iteration, the remaining-input field is read from the context. Scanning continues only when:

- Its signed 32-bit interpretation is greater than zero; and
- Its unsigned interpretation is no greater than the original declared length.

These are guards on context state, not direct bounds checks on the current source cursor.

For each iteration:

1. F-01ff447d595e receives the current source cursor and the captured prefix width.
2. Its signed 32-bit result is treated as the framed unit’s length.
3. The unit-header address is calculated by advancing the source cursor by the captured prefix width.
4. The remaining-input field is reduced by the sum of the prefix width and returned unit length.
5. One byte is read from the unit-header address and passed to F-1fc83df66bd7.
6. The source cursor is advanced to the unit-header address plus the returned unit length.

F-1fc83df66bd7 receives two separate four-byte scratch areas. Only the first byte of each is used locally: one as a category, the other as a unit type. The function does not initialize those scratch areas before the call. Valid execution therefore requires the dependency to define the bytes subsequently read.

There is no local check that:

- The prefix width is nonnegative or sensible.
- Enough bytes remain for the framing dependency or header-byte read.
- The unit length is positive.
- The calculated unit end lies within the input buffer.
- The scan makes forward progress.

A malformed length can therefore affect pointer validity, termination, and subsequent context state before the loop condition is reevaluated.

### 4. Unselected units

Types other than 1 and 5 receive no selected-record processing.

Their framing has already been consumed, the remaining-input field has already been reduced, and the source cursor has already advanced. They do not advance the compacted-output cursor or selected-unit count through any direct action of this function.

Dependency side effects remain possible.

### 5. Selected-unit parsing and record construction

For type 1 or type 5, the current primary record is selected using the current selected-unit count.

The function first writes the record’s category-derived flag. It then calls F-233adfcc915a with:

- The byte immediately following the unit header.
- The calculated unit-end address.
- Parsing state at `context + 0x19c`.
- Auxiliary state at `context + 0xc4`.
- The classifier’s category byte.
- The classifier’s type byte.

The signed 32-bit result is subsequently treated as a bit count.

After this call, if the 32-bit field at `0x30` is zero, the function reads the byte at `0x1dd`, interprets it as unsigned, and stores that value at `0x30`. A zero value does not latch: a later selected unit can trigger another read and assignment.

For every selected unit except the first, the function then:

- Reads the signed 16-bit value at `0x19c`.
- Subtracts the retained signed 16-bit baseline.
- Stores the low 16 bits of the difference in the preceding primary record’s `0x02` field.
- Updates the retained baseline from the signed 16-bit value at `0x19c`.

The first selected unit does not update the baseline. Thus the difference stored while processing the second selected unit is relative to zero, not to the first selected unit’s parsing-state value.

The function next stores the low byte of the current selected ordinal at record offset `0x01`, then calls F-60be95ab6e12 with the record address and the two parsing-state addresses.

This call precedes the payload metadata writes. It may alter bytes that were just set; no preservation guarantee is visible.

### 6. Payload extraction and output advancement

Let the parser result be a signed bit count. The function derives a whole-byte component using a signed right shift by three, and computes:

- Payload source: unit-header address plus one header byte plus that whole-byte component.
- Payload length: unit length minus one minus that whole-byte component.

It calls F-000000000002 with the current compacted-output address, calculated payload source, and calculated payload length.

No local validation prevents a negative payload length or a source outside the unit. The third argument’s interpretation inside the dependency is unknown.

After that call, the function:

1. Increments the selected-unit count.
2. Stores the current output address minus the context’s then-current 32-bit value at `0x14` into record offset `0x0c`.
3. Stores the parser result’s low three bits at record offset `0x14`.
4. Advances the output cursor by the payload length rounded upward using a 32-bit unsigned add-three-and-mask operation.
5. Stores the payload length at record offset `0x10`.

For ordinary nonnegative lengths without overflow, output advancement is to the next multiple of four bytes. No direct write initializes any alignment gap.

Because the context’s buffer-reference field is reread after the payload dependency, the recorded offset need not be relative to the originally supplied buffer if a dependency changes that field.

### 7. Post-scan processing

After the scan ends:

1. The byte at `0x34` is read. If zero, the 32-bit field at `0x30` is cleared.
2. F-bb8d18c47e90 receives the parsing-state and auxiliary-state addresses.
3. Its signed 16-bit result, minus the retained baseline, is stored as a 16-bit difference at offset `0x36 + 0x18 × selected_count`.
4. The selected-unit count is stored at `0x1e4`.
5. For each selected ordinal in ascending order, F-000000000003 receives the corresponding secondary-record address, primary-record address, and extent `0x18`.
6. F-94d3fda99b32 receives the context and both opaque processing arguments.
7. The current 32-bit field at `0x28` is read, incremented, and written back.
8. The final dependency’s saved return value is returned.

For a nonzero selected count, the terminal difference lands in the final primary record’s `0x02` field. For a zero selected count, it lands at context offset `0x36`, outside the primary record area.

## Side effects

- **Context mutation:** Begins before explicit input validation and continues throughout accepted-input processing.
- **Input-buffer mutation:** A dependency is called with destinations beginning at the supplied buffer start. In-place payload compaction is inferred intent; exact writes and overlap safety are unknown.
- **Record publication:** Selected records are supplied to the secondary-record dependency in ascending ordinal order.
- **Counter mutation:** The counter at `0x28` is incremented after the final dependency returns, including when that dependency returns a failure-like value.
- **No local rollback:** Earlier writes are not undone after malformed framing, dependency side effects, or an unfavorable final result.
- **Ownership:** No explicit allocation, release, or ownership transfer is visible. Dependency ownership behavior is unknown. The function stores the caller’s buffer address in the context, so the required lifetime of that reference cannot be limited to this call from the available evidence.
- **Aliasing:** No checks prevent overlap among the context, input buffer, parsing state, or output regions. Such overlap can change subsequent reads.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

1. **Rejected zero-length input.** With a valid context and declared length zero, the function reads `0x40`, stores the supplied buffer reference at `0x14`, and returns `0xffffffff`. It does not enter accepted-input initialization.

2. **Upper boundary.** Length 262,144 passes the explicit length test when the buffer is nonnull. Length 262,145 fails it. Passing the test does not establish safe framing or adequate backing storage.

3. **No selected units.** If framing progresses safely and all classified types differ from 1 and 5, no payload-extraction or selected-record calls occur. The final difference is written at `0x36`, the selected count is stored as zero, and final processing still occurs.

4. **One selected payload.** Suppose a unit length is 10 and its parser result is 19. The whole-byte component is 2, payload source is three bytes after the unit header, payload length is 7, residual-bit metadata is 3, and output advancement is 8 bytes. These results assume ordinary non-overflowing address arithmetic and dependencies that do not alter the relevant state.

5. **Difference baseline behavior.** Suppose two selected units leave signed parsing-state values 7 and 11, and the terminal dependency returns 15. Assuming no other relevant mutations, the first record’s difference becomes 11 and the second record’s difference becomes 4. The first observed value, 7, is not retained as the baseline.

6. **Final failure-like result.** If F-94d3fda99b32 returns `0xffffffff`, that value is returned, but the counter at `0x28` is still incremented after the dependency returns.

7. **Capacity overrun risk.** A sixth selected unit is not rejected locally. Its primary record starts at `0xc4`, overlapping the auxiliary-state address. Safe behavior for that case requires additional, unavailable layout or input constraints.
