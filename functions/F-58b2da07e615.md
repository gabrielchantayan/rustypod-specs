# F-58b2da07e615

## Purpose

F-58b2da07e615 conditionally removes a designated node from a linked, color-marked binary tree, places the removed node on a container-maintained singly linked list, decrements a 32-bit count, and writes a 32-bit result to caller-provided storage.

The structure and dependencies suggest an ordered-tree erase operation returning an advanced position. That interpretation is **inferred intent**, not a complete established contract: dependency behavior is unavailable, and the visible repair logic must not be replaced with an assumed textbook red-black-tree deletion algorithm.

The contract below distinguishes directly established behavior from interpretation and unknowns. All successful-completion statements are conditional on valid memory, terminating traversals, and normally returning dependencies.

## Interface

The function has three logical inputs and no explicit return value:

| Input | Representation | Use |
|---|---|---|
| Result destination | Address of writable 4-byte storage | Receives the final result word |
| Container address | 32-bit address-like value | Locates tree metadata and the removed-node list |
| Position storage | Address of readable 4-byte storage | Supplies the initial comparison word and, after a dependency call, the node address |

All visible pointer-bearing fields occupy four bytes. Addresses are therefore described using a 32-bit target model; the listing does not establish portability to wider pointers.

### Container layout

### Header and node layout

The tree header has these observed fields:

| Offset | Width | Observed role |
|---|---:|---|
| +4 | 4 bytes | Root pointer |
| +8 | 4 bytes | Cached minimum pointer |
| +12 | 4 bytes | Cached maximum pointer |

Ordinary tree nodes have:

| Offset | Width | Observed role |
|---|---:|---|
| +0 | 1 byte | Color or repair-state marker |
| +4 | 4 bytes | Parent pointer |
| +8 | 4 bytes | Left-child pointer |
| +12 | 4 bytes | Right-child pointer; overwritten as a list link after removal |

The repair logic treats marker value 0 as red-like and value 1 as black-like. Some tests distinguish exactly 1 from other nonzero values, so arbitrary nonzero values are not interchangeable with 1.

Padding bytes between the marker and parent field are not directly accessed. Node payload layout, allocation size, alignment requirements, and byte order are not established.

### Preconditions and validity

There is no visible input validation or error return. Safe completion requires:

- Readable position storage and writable result storage.
- Valid container and header storage whenever accessed.
- A readable, writable selected node on the removal path.
- Valid parent, child, and sibling links for every taken branch.
- Termination of downward and upward traversals.
- Dependency-specific preconditions, which are unavailable.

For ordinary tree semantics, parent/child links, root metadata, and cached extrema must be consistent. The function does not validate these invariants.

Result storage is not written until the end. Aliasing it with container metadata or node fields can therefore overwrite an otherwise completed structural update. Such aliasing is not explicitly rejected, but a normal erase interpretation requires noninterfering output storage.

## Behavior

### Initial comparison and result preparation

The first visible actions, in order, are:

1. Read the four-byte word from position storage into a local result word.
2. Read the container’s header pointer into a separate local word.
3. Call F-2b931655bb54 with addresses of those two local words.
4. Inspect that dependency’s integer result.

The dependency receives writable local storage. Its effects on those locals, other memory, or globals are unknown.

If the dependency returns nonzero:

- The function rereads the header pointer from container offset +16.
- That freshly read value replaces the local result word.
- The function writes the result word to the result destination and returns.

This branch performs no direct tree mutation, list insertion, or count decrement. It does not establish that the dependency was side-effect-free.

If the dependency returns zero:

- F-2f0be07eb2b5 receives the address of the local result word.
- After that dependency returns, the function rereads position storage.
- The reread word is interpreted as the node to remove.

Consequently, the selected node is not necessarily the word captured before the first call. Either dependency may have changed position storage through effects not visible here. Likewise, the eventual result is whatever remains in the local result word after these calls; it is not independently recomputed from the final tree.

### Structural removal: no children

When the selected node has neither left nor right child, its parent becomes the repair candidate.

If that parent equals the header pointer currently stored in the container, the function performs these writes:

1. Header maximum becomes the parent/header pointer.
2. Header minimum becomes the parent/header pointer.
3. Header root becomes zero.

Otherwise:

- The parent’s left-child field is read.
- If it equals the selected node, the parent’s left link is cleared.
- Otherwise, the parent’s right link is cleared without an additional equality check.
- The corresponding cached extremum is examined: minimum for a left-link removal, maximum otherwise.
- If that cached extremum equals the selected node, it is replaced by the parent.

The four-byte child-link clearing is expressed as four one-byte zero writes, in increasing address order. This differs observably from a single four-byte store in environments where intermediate writes matter.

The selected node remains the node later added to the removed-node list.

### Structural removal: exactly one child

The nonnull child replaces the selected node.

The visible update order is:

1. Copy the selected node’s parent pointer into the replacement child’s parent field.
2. Examine the header’s root field.
3. If the selected node is the root, replace that root field.
4. Otherwise, replace its parent’s left link if that link equals the selected node; replace the parent’s right link otherwise.
5. Update the cached minimum if it equals the selected node.
6. Update the cached maximum if it equals the selected node.

For a minimum update:

- If the selected node has no right child, the new minimum is its parent.
- Otherwise, it is the leftmost node reachable from the replacement.

For a maximum update:

- If the selected node has no left child, the new maximum is its parent.
- Otherwise, it is the rightmost node reachable from the replacement.

These conditions matter even though valid ordered-tree invariants make some combinations impossible. The function relies on those invariants rather than checking them.

The replacement child becomes the repair candidate.

### Structural removal: two children

The function identifies the leftmost node in the selected node’s right subtree. This successor is moved structurally into the selected node’s former position; node payloads are not copied.

The successor’s right child is recorded as the initial repair candidate. The selected node’s left child is then attached to the successor:

1. The left child’s parent becomes the successor.
2. The successor’s left link becomes the selected node’s left link.

There are then two cases.

**Successor is the immediate right child**

- Its right link remains unchanged.
- If its right child exists, that child’s parent is set to the successor.

**Successor is deeper in the right subtree**

- If its right child exists, that child receives the successor’s former parent.
- The successor’s former parent’s left link becomes that right child, including zero when absent.
- The successor’s right link becomes the selected node’s right link.
- The original right-subtree root’s parent becomes the successor.

Next:

- The header root, or the selected node’s incoming parent link, is changed to the successor.
- The successor receives the selected node’s parent pointer.
- The successor’s original marker byte is saved.
- If its recorded right child was null, the successor itself becomes the repair candidate.
- The successor receives the selected node’s marker.
- The selected node receives the successor’s original marker.

The originally selected node—not the successor—is ultimately added to the removed-node list.

No cached-minimum or cached-maximum update appears in this two-child branch.

### Repair entry conditions

After structural removal, the function rereads the header pointer.

Repair is entered only if both conditions hold:

- The repair candidate differs from that header pointer.
- The marker byte of the node being removed is nonzero.

For the two-child case, that marker is now the successor’s original marker because of the preceding swap.

If repair is skipped, there is no final marker normalization by this function.

The candidate is chosen differently across branches:

- No children: the selected node’s parent.
- One child: that child.
- Two children: the successor’s former right child, or the relocated successor if that child was null.

These choices are established behavior. They must not be silently replaced with a null-leaf abstraction from a conventional deletion algorithm.

### Repair transitions

At each repair-loop check, processing stops if the candidate is the current root or its marker is not exactly 1. On exit from repair, the current candidate’s marker is set to 1.

Otherwise, the function reads the candidate’s parent and determines the candidate’s side by comparing it with the parent’s left child. Failure of that comparison is treated as the right-child case.

For a left-side candidate, the sibling is the parent’s right child. For a right-side candidate, it is the parent’s left child.

The two sides are structurally mirrored:

- A marker-0 sibling is changed to 1, the parent is changed to 0, and a rotation-like dependency is invoked around the parent.
- Parent and sibling pointers are then reread.
- If the sibling is absent, the current candidate is changed to marker 0, the parent becomes the candidate, and the loop continues.
- If both sibling children are absent or have marker 1, the sibling becomes marker 0, the parent becomes the candidate, and the loop continues.
- If the sibling’s far child is absent or has marker 1, the near child is set to 1 when present, the sibling becomes 0, and the opposite rotation-like dependency is invoked. The sibling is then reread.
- If that reread sibling is absent, repair exits through the final candidate-marker write.
- Otherwise, the sibling receives the parent’s marker, the parent becomes 1, and the sibling’s far child becomes 1 when present.
- A final rotation-like dependency is invoked around the parent, followed by repair exit.

“Near” means toward the candidate: the sibling’s left child for a left-side candidate, and its right child for a right-side candidate. “Far” means the other child.

Rotation argument details are not uniformly recoverable; see Dependencies.

### List insertion, count update, and output

After structural work and any repair, the function:

1. Reads the current list head from container offset +4.
2. Stores it into the removed node’s offset +12.
3. Stores the removed node address as the new list head.
4. Reads the 32-bit count at container offset +20.
5. Writes that count decreased by one.
6. Writes the local result word to result storage.

No count-underflow check appears. At the raw 32-bit representation level, decrementing zero gives all one bits under ordinary wrapping subtraction; a signed source-language overflow policy is not established.

The removed node’s parent and left-child fields are not directly cleared. Its marker may already have changed during structural removal.

## Side effects

Established direct effects include:

- Tree-root and cached-extremum updates.
- Parent and child link rewrites.
- One-byte marker changes.
- Reuse of the removed node’s right-child field as a list link.
- List-head insertion.
- One 32-bit count decrement on the removal path.
- One final four-byte result write.

There is no explicit allocation, deallocation, payload destruction, logging, or error reporting in the visible body. This does not prove that dependencies perform none of those actions.

The removed node remains addressable long enough for final list insertion. Calling the list a free list or asserting that memory ownership has ended would exceed the evidence. Its later reuse or release is unknown.

No synchronization or transactional rollback is visible. Structural changes occur before count and output updates. Faults or nonlocal exits can therefore leave partially updated state.

## Acceptance examples

These examples are conditional static expectations, not executed tests.

1. **Nonzero initial dependency result.** If F-2b931655bb54 returns nonzero, output must equal the header pointer reread after that call. Direct removal, list insertion, and count decrement must not occur.

2. **Single-node tree.** If the selected node has no children and its parent is the header, root becomes zero and both extrema become the header. Repair is skipped because its candidate equals the header. The node is prepended to the list and the count decreases once.

3. **Leaf stored as a left child.** The parent’s left link is cleared using four ordered byte writes. If the cached minimum equals the leaf, it becomes the parent. Repair uses the parent as candidate, subject to the removed marker and current-root checks.

4. **Root with one right child.** The child receives the header as parent and becomes root. If the old root was cached minimum, the minimum becomes the leftmost node of the replacement subtree. Any repair entered with the replacement as current root ends by marking it 1.

5. **Two children with a deeper successor.** The successor’s former parent loses its left link to that successor and instead receives the successor’s former right child. The successor occupies the selected node’s former position. The selected node, not the successor, becomes the new list head.

6. **Null successor replacement.** If that successor had no right child, the relocated successor is the repair candidate. Acceptance must not substitute a null candidate or an invented sentinel.

7. **Count initially zero.** Removal is not rejected on that basis. The count update is still attempted; under 32-bit wrapping interpretation its stored representation becomes all one bits.

8. **Dependency changes position storage.** If the initial comparison permits removal and a dependency changes the position word before the later reread, the reread value determines the selected node. The original captured word does not override it.
