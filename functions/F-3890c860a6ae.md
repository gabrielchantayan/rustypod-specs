# F-3890c860a6ae

## Purpose

F-3890c860a6ae performs an in-place structural transformation on linked records. Under a conventional binary-tree interpretation, the transformation is a right rotation: the selected record’s left child takes its former position, the promoted child’s former right subtree becomes the selected record’s left subtree, and the selected record becomes the promoted child’s right child.

That tree interpretation is inferred intent. The established behavior is a sequence of 32-bit field reads and writes. The function does not validate that its inputs describe a tree, that reciprocal links agree, or that any addressed storage is accessible.

The function returns no value. Its observable result is the modified memory.

## Interface

### Inputs

Two arguments are represented as 32-bit integer quantities and used as addresses:

- **Context address:** identifies an object containing a 32-bit address field at byte offset 16.
- **Selected-record address:** identifies the record to be moved downward by the transformation.

The context’s offset-16 field identifies a separate object, called the **anchor** here. The anchor has a 32-bit field at byte offset 4 that is treated as the root link.

These names describe roles, not established source-level types.

### Accessed layout

The function accesses the following fields. Every listed field is four bytes wide.

| Object | Byte offset | Role in this contract |
|---|---:|---|
| Context | 16 | Address of the anchor |
| Anchor | 4 | Root link |
| Selected record | 4 | Parent link |
| Selected record | 8 | Left-child link |
| Promoted record | 4 | Parent link |
| Promoted record | 12 | Right-child link |
| Transferred record, if present | 4 | Parent link |
| Former parent, on the non-root path | 8 | Left-child link |
| Former parent, on the non-root path | 12 | Right-child link |

The **promoted record** is the address initially read from the selected record’s offset-8 field. The **transferred record** is the address read from the promoted record’s offset-12 field during the transfer.

The function does not establish complete object sizes or layouts. In particular, it does not access record offset 0, the promoted record’s offset-8 field, or the selected record’s offset-12 field as part of the ordinary, non-overlapping transformation.

### Result and ownership

There is no returned status, resulting-root address, or error code. A caller that needs the updated root must obtain it through the anchor’s root link.

No allocation, release, reference-count operation, or ownership-transfer mechanism is visible. Existing records remain at their existing addresses. The operation changes links; it does not visibly create or destroy records.

### Preconditions for a conventional rotation

A caller seeking the ordinary tree result must provide:

- Accessible context and anchor storage.
- An accessible, writable selected record.
- A nonzero selected left-child link identifying an accessible, writable promoted record.
- Accessible, writable transferred-record storage if the promoted right-child link is nonzero.
- Accessible, writable former-parent storage when the anchor’s root link does not equal the selected-record address.
- A stable, consistent link structure without conflicting concurrent modification or overlapping field storage.

These are conditions needed for the interpreted result, not checks performed by the function. A zero transferred-child address is explicitly supported. A zero promoted-record address is not.

## Behavior

### Established access sequence

The following describes the order of the supplied representation’s memory operations. It does not assert a processor memory model, atomicity, or synchronization guarantee.

1. **Select the record to promote.**  
   The function reads the selected record’s offset-8 field once and retains that address as the promoted record.

2. **Replace the selected record’s left link.**  
   It reads the promoted record’s offset-12 field and writes that four-byte value into the selected record’s offset-8 field.

3. **Conditionally repair the transferred record’s parent link.**  
   It reads the promoted record’s offset-12 field again and compares the value with zero.

   If that read is nonzero, the function reads the same field again to obtain the destination record address, then writes the selected-record address to that destination’s offset-4 field.

   The transferred-child address is therefore not captured once for all uses. In stable, non-overlapping storage, these reads identify the same record. With concurrent mutation or aliasing, the value copied into the selected left link, the value tested for zero, and the destination used for the parent update need not agree.

4. **Give the promoted record the selected record’s current parent link.**  
   It reads the selected record’s offset-4 field and writes that value into the promoted record’s offset-4 field.

5. **Locate and inspect the root link.**  
   It reads the context’s offset-16 field to obtain the anchor address, then reads the anchor’s offset-4 field and compares it with the selected-record address.

6. **Reconnect the promoted record at the selected record’s former position.**
   - If the root link equals the selected-record address, the function writes the promoted-record address into that root link.
   - Otherwise, it reads the selected record’s offset-4 field again to obtain the former-parent address. It reads that parent’s offset-12 field.
     - If the parent’s offset-12 field equals the selected-record address, that field is replaced with the promoted-record address.
     - Otherwise, the parent’s offset-8 field is replaced with the promoted-record address.

   The fallback does not first verify that the parent’s offset-8 field actually points to the selected record.

7. **Make the selected record the promoted record’s right child.**  
   It writes the selected-record address into the promoted record’s offset-12 field.

8. **Finish the reciprocal parent link.**  
   It writes the promoted-record address into the selected record’s offset-4 field and returns.

There are five unconditional four-byte writes on an ordinary completing execution, plus one additional four-byte write when the transferred-child check is nonzero. The root and non-root reconnection paths each contribute one of those unconditional writes.

### Result for a valid, stable structure

For distinct, appropriately linked records with stable storage, the resulting relationship is:

| Relationship | Before | After |
|---|---|---|
| Selected record’s left child | Promoted record | Former promoted right child |
| Promoted record’s right child | Transferred record or zero | Selected record |
| Selected record’s parent | Former parent | Promoted record |
| Promoted record’s parent | Selected record, in a consistent tree | Former selected parent |
| Transferred record’s parent, if present | Promoted record | Selected record |
| External link formerly identifying selected record | Selected record | Promoted record |

If the selected record was the root according to the anchor, the external link is the anchor’s root field. Otherwise, it is a child field in the former parent.

The promoted record’s left subtree and the selected record’s right subtree are not directly changed. No payload, key, ordering metadata, balance factor, color, height, or subtree count is visibly updated.

### Branch precedence and inconsistent inputs

Root identity takes precedence over parent-child links. When the anchor’s root link equals the selected-record address, the function updates that root link without inspecting the selected record’s former parent’s child fields.

On the non-root path, the former parent’s right-child link is checked first. If it equals the selected record, that link is updated even if the left-child link also equals the selected record. Otherwise, the left-child link is overwritten unconditionally.

The function does not check that the promoted record’s old parent is the selected record. It overwrites the promoted parent link regardless of its prior value.

### Widths and address arithmetic

All explicit data-field transfers are 32 bits wide. The visible offset displacements are 4, 8, 12, and 16 bytes. There are no element counts, variable-length copies, size multiplications, or numeric result calculations.

The supplied representation uses 32-bit integer values as addresses. It does not establish portable behavior for address arithmetic that exceeds the address domain, violates alignment requirements, or designates inaccessible storage. No overflow, range, or alignment check is visible.

## Side effects

The normal side effects are limited to the link fields described above. The context’s offset-16 field is read but not directly written.

The operation is not transactional. It changes the selected record’s left link before reconnecting the promoted record at the root or former parent, and completes the selected record’s new parent link last. Intermediate memory therefore need not satisfy ordinary tree invariants.

No lock, synchronization primitive, rollback, or recovery path is visible. A failure during a later access can occur after earlier writes have already happened; the supplied representation does not establish the exact failure mechanism or resulting recovery behavior.

Aliasing can change these effects materially. If a record field overlaps another accessed field, an earlier write can alter a later read or write destination. Consequently, the ordinary rotation result is conditional on appropriate storage separation. The visible implementation neither rejects aliasing nor defines a separate alias-safe transformation.

There are no visible external calls, logging operations, I/O operations, allocation operations, or deallocation operations.

## Dependencies

No dependency function calls are visible. No additional opaque function IDs are required.

The behavior depends on caller-provided memory and its existing link values:

- The context must lead to usable anchor storage when that field is read.
- The selected left-child link must lead to usable promoted-record storage.
- A nonzero transferred-child link must lead to writable parent-link storage when used.
- The non-root path requires the selected parent link to lead to usable former-parent storage.

No callee behavior needs to be assumed. In particular, this contract makes no assumption about another function preserving globals or taking responsibility for memory ownership.

## Acceptance examples

These examples are conditional expectations derived from static evidence, not results of execution. Unless stated otherwise, all named records are distinct, accessible, writable, and stable throughout the operation.

### Root rotation with no transferred subtree

Initially:

- The anchor’s root link identifies the selected record.
- The selected record’s left link identifies the promoted record.
- The promoted record’s right link is zero.
- The selected record’s parent field contains the structure’s root-parent representation.

Expected result:

- The anchor’s root link identifies the promoted record.
- The selected record’s left link is zero.
- The promoted record’s right link identifies the selected record.
- The selected record’s parent identifies the promoted record.
- The promoted record’s parent contains the selected record’s former parent value.

No transferred-record parent write occurs. The root-parent representation is copied as a four-byte value; it is not normalized or checked.

### Rotation with a transferred subtree

Initially, the promoted record’s right link identifies a third record.

Expected result:

- The selected record’s left link identifies that third record.
- The third record’s parent identifies the selected record.
- The promoted record’s right link identifies the selected record.
- The external root or parent-child link is reconnected to the promoted record.

The third record’s own child links are not directly modified.

### Non-root selected record occupying a right-child position

Initially, the anchor’s root link differs from the selected-record address, and the selected record’s parent has its right-child link pointing to the selected record.

Expected result:

- That parent’s right-child link identifies the promoted record.
- That parent’s left-child link is not directly written.
- The anchor’s root link is not directly written.

The remaining rotation links change as described above.

### Non-root selected record occupying a left-child position

Initially, the anchor’s root link differs from the selected-record address, the former parent’s right-child link does not identify the selected record, and its left-child link does.

Expected result:

- The former parent’s left-child link identifies the promoted record.
- Its right-child link remains unchanged.
- The anchor’s root link remains unchanged.

### Inconsistent former-parent links

Initially, the non-root path is selected, but neither child link of the former parent identifies the selected record.

Expected behavior is not rejection. The former parent’s left-child link is overwritten with the promoted-record address. This can disconnect an unrelated subtree.

If both former-parent child links identify the selected record, only the right-child link is replaced by the reconnection step.

### Missing promoted record

Initially, the selected record’s left-child link is zero.

No successful no-op behavior is established. The function attempts to access the promoted record’s offset-12 field without a preceding null check. The outcome depends on the execution environment and memory accessibility.

- **Concurrency semantics:** repeated reads are visible in the representation, but no supported concurrent-use contract or memory-order guarantee is established.

- **Tree family and metadata requirements:** a right-rotation interpretation is strongly supported by the link transformation. Whether callers use this within a particular balancing algorithm is unknown.

- **Untouched storage semantics:** absence of a direct field write does not protect that storage if it aliases a written field.
