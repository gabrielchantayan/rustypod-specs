# F-2643b51fb55a

## Purpose

F-2643b51fb55a initializes selected fields in supplied and dependency-returned storage, initializes two records using address-bearing slots, and returns a 32-bit result derived from the final dependency return.

**Established static behavior:** five dependency invocations occur, involving four distinct dependencies. Between those calls, the function performs ordered four-byte and one-byte stores. The result calculation subtracts `0x68` (104) from the final dependency result.

**Inferred intent:** the record initialization resembles creation of self-linked sentinels, and the surrounding operations resemble staged construction of an object with nested components. These interpretations do not establish container semantics, ownership, or any relationship between the returned result and the original storage address.

The body establishes the result calculation, not how callers interpret it. An address, status, count, or other application-level meaning cannot be confirmed from this function alone.

This contract describes static evidence. No runtime tests have been performed.

The next two word stores use the contents of S + `0x14`:

| Order | Destination | Stored value |
|---:|---|---|
| 1 | Address loaded from S + `0x14`, plus `0x08` | Another load from S + `0x14` |

## Acceptance examples

These are conditional specification examples, not executed tests.

### Independent records: events versus final state

Assume normal dependency returns. Suppose the writable record fields at A + `0x04` through A + `0x0F` and C + `0x04` through C + `0x0F` are disjoint from each other and from all S-relative and B-relative direct-write locations. Suppose dependencies leave those records and their address slots unchanged after their respective initialization.

The required record-initialization events are:

- A is stored at S + `0x14`.
- A + `0x04` receives zero; A + `0x08` and A + `0x0C` receive A.
- C is stored at B + `0x30`.
- C + `0x04` receives zero; C + `0x08` and C + `0x0C` receive C.

Under these assumptions, the record fields retain those values at return. The slot assignments are stated as **store events**: record independence alone does not guarantee that S + `0x14` still contains A at return.

For both slots to retain their assigned addresses, additionally require that no later direct store overlaps either slot and that subsequent dependencies preserve them. No value is established for the words at A + `0x00` or C + `0x00`.

### A later direct store overwrites the first slot

Assume B equals S + `0x34`, all accesses are valid, and no other writes or dependency effects subsequently alter S + `0x14`.

The store of A to S + `0x14` still occurs. Later, the K₂ store at B − `0x20` targets those same four bytes. At return, that slot contains K₂, not necessarily A.

This remains possible even when A and C identify independent records.

### Conditional return of the original address

Assume B equals S + `0x20`, the records do not overlap affected storage, and later operations preserve the relevant fields. The K₂ store replaces K₁ at S.

If D additionally equals S + `0x68` and subtraction is valid, the returned representation equals S. Neither address equality is unconditional, and this example does not establish how callers interpret the result.

### Forwarded inputs

For distinct third and fourth inputs, F-UNMAPPED-01 receives them in the order third, fourth, third, fourth after its first two arguments.

Changing only the second input changes no explicit argument, address calculation, or direct store in the visible body.

### Untouched gaps

Assume no aliasing and no dependency writes to the bytes in question. S + `0x1E` and S + `0x1F` retain their previous contents. B + `0x44` and B + `0x45` likewise retain theirs.
