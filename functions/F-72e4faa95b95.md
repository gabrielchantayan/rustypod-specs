# F-72e4faa95b95

## Purpose

F-72e4faa95b95 selects a handler from a byte obtained through an input object's indirect method, transfers a 32-bit result through shared result storage, and publishes that storage into two 16-bit fields of a context object.

Most selector values invoke either a dedicated handler or a fallback handler. Selector `0xC6` instead requests another byte pointer and dispatches on the byte at offset one from that second pointer. Unsupported secondary selectors bypass both handler execution and finalization, but still publish the current contents of the shared result storage.

The established behavior is dispatch and result publication. The meanings of the selected operations, the byte stream, and the published value are not established. Interpreting this function as a decoder or parser is inferred intent, not part of the contract.

## Interface

### Arguments

The function accepts four arguments and has no explicit return value.

| Argument | Established use |
|---|---|
| First argument | A 32-bit opaque value passed to F-603a53835f04. This function does not otherwise interpret it. |
| Context | An address-sized value represented as a 32-bit integer in the supplied material. Passed unchanged to handlers; also used as the base for final 16-bit writes at offsets `0x5C` and `0x5E`. |
| Input object | A pointer to an object whose first word supplies an indirect-method table address. A method entry at byte offset `8` in that table is invoked with the object as its argument. Passed unchanged to handlers. |
| Initial result value | A 32-bit value used to initialize a local result word. It is available to ordinary handlers before they modify that word. |

The represented interface uses 32-bit words and addresses, 16-bit publication units, and unsigned 8-bit selectors. Porting this behavior to a different address width requires an explicit ABI decision; widening the address representation does not imply widening the result or publication fields.

### Local state exposed to dependencies

Before calling any dependency, the function initializes three local words:

1. A word containing the context argument.
2. A word containing the input-object pointer.
3. A word containing the initial result value.

Ordinary dispatch passes the address of the third word to its handler and later to F-9b718979506d.

Recognized extended dispatch passes the address of the first word to its handler and later to F-9b718979506d. Before that handler is called, the second local word has been replaced with the pointer returned by the second indirect-method invocation.

The supplied representation suggests a three-word local record. It does not independently establish a portable aggregate layout or authorize arbitrary access beyond the addressed word. Any dependency requirement concerning adjacent words remains dependency-specific.

### Preconditions

For completion without invalid memory access:

- The input object must support the described first-word and method-table accesses.
- Each invoked indirect method must return a pointer readable at the byte offset subsequently accessed.
- F-603a53835f04 must return storage supporting 16-bit accesses at offsets zero and two.
- The context address must support 16-bit writes at offsets `0x5C` and `0x5E`.
- These addresses must remain usable at the time of each access, including after intervening dependency calls.
- Each called dependency must satisfy its own unknown preconditions.

The function performs no visible null checks, size checks, alignment checks, or lifetime validation.

## Behavior

### Initialization and first selector read

The observable call and access sequence begins as follows:

1. Initialize the three local words described above.
2. Invoke F-603a53835f04 with the first argument followed by three zero-valued arguments.
3. Retain its returned address as the shared result-storage address.
4. Resolve the input object's indirect method through the table entry at byte offset `8`, and invoke it with the original input-object pointer.
5. Read the unsigned byte at offset zero of the returned pointer.

F-603a53835f04 is therefore called before selector retrieval. It can have side effects even if subsequent dispatch takes an unsupported extended-selector path.

The first selector byte is captured once. Later changes to the underlying byte do not change that dispatch decision.

The handler receives, in order:

- The address of the local result word, initially containing the fourth argument.
- The original context argument.
- The original input-object pointer.

The handler's return value is not used. Its changes to the addressed local result word determine the subsequent transfer.

After the handler returns normally:

1. Write the low 16 bits of the local result word into shared result storage at offset zero.
2. Write its upper 16 bits into shared result storage at offset two.
3. Call F-9b718979506d with the address of that same local result word.
4. Publish the shared result storage into the context fields as described below.

There is no second transfer from the local result word after F-9b718979506d. Changes that this dependency makes only to that local word do not, by themselves, replace the already-transferred result. Changes it makes to shared result storage can affect publication.

### Extended dispatch: primary selector `0xC6`

When the first selector is `0xC6`, the function resolves and invokes the input object's indirect method again. This is a distinct invocation, not reuse of the first returned pointer.

The method-table access is also performed again. If earlier dependencies changed the input object's table pointer or method entry, the second invocation can resolve differently.

The second returned pointer replaces the second local word. The function then reads the unsigned byte at offset one from this second pointer. It does not require the second pointer to equal the first pointer and does not recheck the byte at offset zero.

| Secondary byte | Handler |
|---|---|
| `0x90` | F-ea0a32c346df |
| `0x91` | F-5cc4c61e2110 |
| `0x92` | F-e68a5e3cc333 |
| `0x94` | F-53eb30bcf031 |
| `0x95` | F-a90d836b8130 |

For these five values, the selected handler receives:

- The address of the first local word, initially containing the context argument.
- The original context argument.
- The original input-object pointer.

The second handler argument remains the original context value even if the handler changes the first local word. Likewise, the third handler argument is the original object pointer, not the byte pointer stored in the second local word.

After a recognized extended handler returns normally:

1. Transfer the low 16 bits of the first local word into shared result storage at offset zero.
2. Transfer its upper 16 bits into shared result storage at offset two.
3. Invoke F-9b718979506d with the address of that first local word.
4. Publish the shared result storage into the context.

The fourth argument is not the word selected for result transfer on this path.

### Unsupported extended selectors

Every secondary value outside `0x90`, `0x91`, `0x92`, `0x94`, and `0x95` is unsupported. In particular, `0x93` is unsupported.

For these values:

- No dispatch handler is called.
- The ordinary fallback handler is not called.
- No local result word is transferred into shared result storage.
- F-9b718979506d is not called.
- Publication into the context still occurs.

Consequently, this path publishes whatever the shared result storage contains at the time of publication. That content may have been established or changed by F-603a53835f04, the indirect-method calls, or other dependency effects. It is not established to be zero, the context value, or the fourth argument.

### Final publication

Every path that reaches the normal epilogue performs the following ordered accesses:

1. Read a 16-bit value from shared result storage at offset zero.
2. Write that value to the original context address plus `0x5C`.
3. Read a 16-bit value from shared result storage at offset two.
4. Write that value to the original context address plus `0x5E`.

These are two separate 16-bit transfers, not an established atomic 32-bit write. No locking or synchronization is visible.

The source reads occur after F-9b718979506d on paths that call it. Publication must therefore not be described as necessarily publishing an immutable snapshot of the handler result.

The original context argument supplies the destination base even on an extended path whose first local word has changed.

The order also matters if source and destination storage overlap: the first destination write precedes the second source read. Equivalence to copying a previously captured 32-bit value requires noninterference or an independently justified aliasing condition.

## Side effects

### Directly established effects

The function directly:

- Invokes F-603a53835f04 once.
- Invokes the input object's indirect method once, or twice when the primary selector is `0xC6`.
- Reads one selector byte, or two selector bytes on the extended path.
- Calls exactly one dispatch handler on ordinary and recognized extended paths.
- Writes two 16-bit halves into shared result storage on those handled paths.
- Calls F-9b718979506d once on those handled paths.
- Writes two 16-bit context fields on every normally completing path.

The described result-store writes precede finalization; the context writes follow it.

### Ownership and lifetime

No explicit allocation, deallocation, retain, or release operation is established independently of the opaque dependencies.

F-603a53835f04 supplies a storage address, but its ownership and lifetime rules are unknown. F-9b718979506d receives a local-word address, but its name or call position is not evidence that it releases memory.

Dependencies receive addresses into local state. Whether they retain those addresses is unknown; this function provides no visible mechanism extending that local state's lifetime beyond the invocation.

The shared result address is reused after intervening calls without visible revalidation. Correct execution requires it to remain valid. The same limitation applies to the context destination.

### Errors and abnormal completion

There is no explicit status return, error sentinel, or dedicated error branch. Unsupported primary values use the fallback; unsupported secondary values still publish shared storage.

If a dependency does not return normally, later transfers and publication are not established to occur. Invalid pointers or inaccessible storage have no specified recovery behavior in the supplied evidence.

## Acceptance examples

These examples are conditional static expectations, not executed tests. All assume valid accesses and normal dependency returns.

1. **Ordinary result transfer.**  
   The first returned pointer contains primary byte `0x28`. F-ad64f7eac2e3 must receive the local result-word address, the original context, and the original input object. If it leaves the result word as `0x12345678`, the function writes `0x5678` to shared offset zero, then `0x1234` to shared offset two. If subsequent effects do not change those halves, context offsets `0x5C` and `0x5E` receive those respective values.

2. **Fallback is not rejection.**  
   Primary byte `0x29` selects F-a9ade5367302. It does not skip result transfer or finalization merely because no dedicated handler exists.

3. **The fourth argument can survive ordinary handling.**  
   If an ordinary handler leaves its addressed word unchanged, that word still holds the fourth argument, absent other writes to it. Its two halves are then transferred before finalization.

4. **Extended selection uses the second pointer.**  
   The first method result has byte zero equal to `0xC6`. The second method result is a different pointer whose byte one is `0x94`. F-53eb30bcf031 is selected from the second pointer's byte. The first pointer's byte one is irrelevant to this selection.

5. **Extended result uses the first local word.**  
   For secondary `0x90`, if F-ea0a32c346df changes the first local word to `0xA1B2C3D4`, shared storage receives `0xC3D4` followed by `0xA1B2`. The destination base remains the original context argument.

6. **Unsupported extended selector bypasses finalization.**  
   With primary `0xC6` and secondary `0x93`, no handler or F-9b718979506d call occurs. If shared storage contains halves `0x1122` and `0x3344` at publication time, those halves are written to the context.

7. **Finalization can affect publication.**  
   If a handled path transfers a result and F-9b718979506d then changes shared storage through an available alias, publication reads the changed storage. Assuming that finalization preserves it would contradict the established access order unless separately supported.
