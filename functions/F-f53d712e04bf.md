# F-f53d712e04bf

## Purpose

F-f53d712e04bf conditionally processes an incoming record, updates receiver-associated state, and dispatches receiver callbacks.

Static evidence supports three categories of accepted-record behavior:

- Dispatch based on a primary record kind and an operation byte.
- Update selected receiver state under a pair of external operations, then issue a notification callback.
- Dispatch a separate status-like record kind using one of four unavailable global values.

The meanings of the operations, stored fields, notification values, and callbacks are not established. This is **DOCUMENTED ONLY**, not an implementation-ready protocol specification: required external contracts and global values are missing.

## Interface

### Inputs

Five positional inputs are visible:

| Position | Contract role |
|---|---|
| First | Address of a receiver-associated interior region, called the **receiver anchor** below. |
| Second | Gate value; processing requires zero. |
| Third | Gate value; processing requires either 1 or 2. |
| Fourth | Address of an incoming record. |
| Fifth | Size-like gate value; processing requires either 12 or 44. |

The size-like interpretation of the fifth input is inferred. The function only compares it against two constants; it does not use it to bound memory access.

The visible interface uses 32-bit address-bearing and integer values. Record accesses include 8-bit, 16-bit, and 32-bit quantities. Native multibyte loads and stores are used; the function contains no explicit byte-order conversion. The target byte order is not independently established by the supplied evidence.

### Return and reporting

There is no explicit return value, success indicator, or error result. Callback and external-operation results are not used.

An ignored record and a successfully dispatched record are therefore indistinguishable through a direct return value.

### Receiver layout

Offsets below are byte displacements relative to the receiver anchor, not absolute addresses.

| Relative location | Visible use |
|---|---|
| −64 | Base of the callback receiver object. Its first 32-bit word supplies the dispatch-table address. |
| +4 through +7 | Receives the record’s initial 32-bit word whenever all three input gates pass. |
| +10 through +11 | Existing 16-bit state passed to one status callback variant. |
| +14 and +15 | Two bytes replaced by one state-update variant. |
| +16 | One byte replaced by another state-update variant. |
| +80 through +111 | Destination of a transfer request for 32 bytes. |
| +116 | Address passed to both external operations surrounding state changes. |

The callback receiver passed to indirect callbacks is the object at anchor −64, not the anchor itself.

### Record layout

The initial record pointer remains the reference point for these offsets:

| Offset | Width | Use |
|---|---:|---|
| 0 | 32 bits | Copied into receiver state for every gate-accepted record. |
| 4 | 16 bits | Primary kind discriminator. Recognized values are 44 and 49. |
| 8 | 8 bits | Additional zero-required field for kind 49. |
| 9 | 8 bits | Operation selector. |
| 10 | 8 bits | Subselector for kind 44, operation 6; zero-required field for kind 49. |
| 12 | Variable | Beginning of operation-dependent arguments or transfer data. |

The function does not validate pointer nullness, allocation sizes, alignment, callback availability, or the relationship between the fifth input and the selected operation’s actual memory needs. Valid, accessible storage and callable dispatch entries are preconditions for defined processing.

### Ownership and lifetime

No allocation, deallocation, or explicit ownership transfer is visible.

The function sometimes passes a pointer into the incoming record, and sometimes passes a 32-bit value loaded from the record that may represent a pointer. Whether callbacks retain, modify, or take ownership of these values is unknown.

## Behavior

### Admission and common state update

Processing occurs only when all of the following hold:

- The second input is zero.
- The third input is 1 or 2.
- The fifth input is 12 or 44.

If any condition fails, no record field is dereferenced and no receiver state is written in the visible body.

If all conditions pass, the function first copies the record’s initial 32-bit word to receiver offset +4. This happens before evaluating the primary kind or operation selector. Consequently, an unsupported kind or operation can still change this receiver field.

The fifth input does not otherwise select behavior. Either accepted value permits every supported branch.

### Primary kind 44: operation dispatch

The operation selector is the byte at record offset 9.

The following table gives dispatch-table byte offsets, relative to the table address held by the callback receiver. Every listed callback receives the callback receiver as its first argument.

| Operation | Dispatch-table offset | Additional arguments, in order |
|---:|---:|---|
| 0 | 132 | Byte at record offset 12; byte at offset 13. |
| 3 | 136 | Byte at offset 12; byte at offset 13. |
| 4 | 144 | Zero-extended 16-bit quantity at offset 12. |
| 6 | Depends on subselector | See below. |
| 8 | 156 | Byte at offset 19; 32-bit quantity at offset 12; 16-bit quantity at offset 16; byte at offset 18. |
| 11 | 160 | 32-bit quantity loaded from offset 12, used as an address-like argument. |
| 15 | 164 | Address of record offset 12 itself. |
| 17 | 172 | 32-bit quantity loaded from offset 12, used as an address-like argument. |
| 19 | 176 | Zero-extended byte at offset 12. |

All other operation values cause no further visible action after the common state update.

The distinction between operations 11 or 17 and operation 15 is significant: the former pass the contents of a 32-bit field, while the latter passes the location of the inline field.

The semantic type and ownership of the address-like arguments for operations 11 and 17 remain unknown. The function does not dereference them itself.

### Kind 44, operation 6: subselector behavior

The subselector is the byte at record offset 10.

| Subselector | Behavior |
|---:|---|
| 0 | Invoke dispatch-table offset 144 with the zero-extended 16-bit quantity at record offset 12. |
| 1 | Invoke dispatch-table offset 140 with bytes at record offsets 12 and 13. |
| 2 | Replace two receiver bytes under the external operation pair, then notify. |
| 3 | Replace one receiver byte under the external operation pair, then notify. |
| 4 | Request a 32-byte transfer under the external operation pair, then notify. |
| Any other value | No further visible action. |

For subselector 2:

- The two incoming bytes at offsets 12 and 13 are captured before the first external operation.
- The entry external operation receives receiver anchor +116.
- Receiver bytes +14 and +15 are replaced with those captured bytes, preserving their order.
- The exit external operation receives receiver anchor +116.
- The callback at dispatch-table offset 20 receives the callback receiver, an unavailable notification value specific to this variant, and zero.

For subselector 3:

- The incoming byte at offset 12 is captured before the entry external operation.
- The same entry and exit operations surround assignment of that byte to receiver offset +16.
- The callback at dispatch-table offset 20 receives the callback receiver, a different unavailable notification value, and zero.

For subselector 4:

- The entry external operation receives receiver anchor +116.
- A separate external operation is called with destination receiver anchor +80, source record offset 12, and count 32.
- The exit external operation receives receiver anchor +116.
- The callback at dispatch-table offset 20 receives the callback receiver, a third unavailable notification value, and zero.

No external-operation return value is checked. The function contains no explicit recovery path for a failure or abnormal termination in these operations.

### Primary kind 49: status-like dispatch

This kind is eligible for further processing only when both the byte at record offset 8 and the byte at offset 10 are zero.

If either is nonzero, processing ends after the common state update.

When both are zero, the byte at offset 9 selects one of four variants. Each invokes the callback at dispatch-table offset 16 with four arguments:

1. The callback receiver.
2. An unavailable global value specific to the selected variant.
3. A 16-bit state argument.
4. Zero.

| Selector at offset 9 | State argument |
|---:|---|
| 0 | Existing 16-bit receiver state at anchor +10. |
| 1 | Zero. |
| 2 | Zero. |
| 3 | Zero. |

Each selector uses a distinct global-value reference, although the values themselves could coincide; their contents are unavailable.

All other selector values cause no further action after the common state update.

### Unsupported primary kinds

Any primary kind other than 44 or 49 is ignored after the common state update. No error callback or explicit error result is visible.

### Required record extent

The fifth input is not an enforced bound. The selected branch determines the actual access requirements:

- Every gate-accepted record requires its initial 32-bit word and 16-bit kind field.
- Kind 44 requires access to the operation byte at offset 9.
- Kind 49 requires access through offset 10 for its eligibility checks.
- Two-byte argument and 16-bit argument branches require access through offset 13.
- Operations 11 and 17 require access through offset 15.
- Operation 8 requires access through offset 19.
- Subselector 4 supplies the range at offsets 12 through 43 to the external transfer operation.

Thus a fifth input of 12 can admit a branch whose arguments lie beyond a genuinely 12-byte allocation. The function provides no truncation rejection. Supplying an allocation too small for the selected branch violates its memory-access preconditions.

## Side effects

### Directly established effects

For every gate-accepted record:

- Receiver offsets +4 through +7 are overwritten, including when later dispatch is unsupported.

Additional direct receiver writes occur only in the visible subselector 2 and 3 branches:

- Subselector 2 replaces bytes +14 and +15.
- Subselector 3 replaces byte +16.

Subselector 4 requests an external operation over the 32-byte receiver region beginning at +80; actual transfer semantics depend on the unknown operation.

### Calls and ordering

A supported branch invokes at most one indirect receiver callback in the visible body.

For the three state-update variants, the callback occurs after the exit external operation returns. The common 32-bit state update occurs before these external operations.

The incoming record is not directly written by this function. Callbacks and external operations may have additional side effects that are not available in the evidence.

### Concurrency and failure boundaries

The paired operations around state changes suggest synchronization intent, but mutual exclusion, memory ordering, reentrancy, and failure behavior are not established.

The common update at receiver offset +4 is outside those pairs.

No null checks, exception handling, rollback, or explicit error reporting are visible. In particular, a callback failure would occur after the common state update and, for the update variants, after the direct state changes or transfer request.

## Acceptance examples

These are static contract examples, not executed tests. Multibyte quantities are expressed as decoded native values rather than assumed byte encodings.

1. **Rejected gate does not touch record storage.**  
   If the second input is nonzero, no record dereference, receiver write, or callback is performed by the visible body, regardless of the other input values.

2. **Unknown primary kind still records the initial word.**  
   With accepted gates, an initial word of 305419896 and a primary kind other than 44 or 49 cause receiver offset +4 to receive 305419896. No indirect callback follows.

3. **Two-byte operation preserves argument order.**  
   For kind 44, operation 3, and bytes 18 and 52 at offsets 12 and 13, the callback at table offset 136 receives the callback receiver followed by 18 and 52.

4. **Operation 4 and operation 6, subselector 0 share a callback shape.**  
   Given the same 16-bit field value of 4660 at offset 12, both routes invoke table offset 144 with 4660 after the receiver argument. The operation-6 route additionally reads its subselector.

5. **Operation 8 uses a non-record-order argument sequence.**  
   If offset 19 holds 7, the 32-bit field at offset 12 is 1000, the 16-bit field at offset 16 is 500, and offset 18 holds 9, the callback at table offset 156 receives additional arguments 7, 1000, 500, and 9.

6. **Pointer value and inline pointer are distinct.**  
   For operation 11, the callback receives the 32-bit value stored at record offset 12. For operation 15, it receives the address of record offset 12. These are not interchangeable.

7. **Two-byte state update precedes notification.**  
   For kind 44, operation 6, subselector 2, and payload bytes 21 and 22, the bytes are captured, the entry operation is called, receiver offsets +14 and +15 become 21 and 22, and the exit operation is called before the notification callback.

8. **Status selector 0 forwards existing state.**  
   For kind 49 with bytes 8 and 10 both zero, selector 0 forwards the existing 16-bit receiver state at +10 to table offset 16, together with the selector-specific unavailable global value and a trailing zero.

9. **Status eligibility failure preserves only the common update.**  
   For kind 49 with byte 8 nonzero, no status callback occurs, but the initial record word has already been copied to receiver offset +4.

10. **The accepted size-like value is not a safety guarantee.**  
    A fifth input of 12 does not prevent kind 44, operation 6, subselector 4 from requesting a transfer of 32 bytes beginning at record offset 12. A caller must provide sufficient actual storage independently of that gate value.

## Uncertainties

### Inferred intent

- The incoming data appears to be an event or message record.
- The fifth input appears size-related because its accepted values correspond to plausible record extents.
- The entry and exit operations appear intended to protect selected receiver updates.
- The three-argument external transfer appears intended to copy bytes.

None of these interpretations establishes an external protocol or dependency contract.

No runtime behavior has been measured. The contract describes visible static behavior and explicitly bounded inferences, not measured compatibility.
