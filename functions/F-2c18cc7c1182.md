# F-2c18cc7c1182

## Purpose

F-2c18cc7c1182 performs a partial initialization or update of a caller-supplied memory region. It copies a value from a global 32-bit storage location into the first word of that region, copies a supplied 32-bit value into the fourth word, and clears the second word.

The established behavior is three assignments. The interpretation as object initialization is inferred intent, not an established object model. No evidence identifies a structure type, a field meaning, a type tag, or a lifecycle transition.

The third word is not directly accessed. The function therefore must not be specified as clearing or fully initializing a four-word object.

## Behavior

### Normal execution

The source establishes the following order:

1. Obtain the current four-byte value from the global source and assign it to the destination word at offset 0.
2. Assign the supplied value to the destination word at offset 12.
3. Assign zero to the destination word at offset 4.
4. Return without a result value.

This is an ordered behavioral description of the presented source. It is not evidence of memory barriers, volatile accesses, bus transaction order, or an inter-thread synchronization guarantee.

There is one explicit global value access and three explicit destination assignments. No destination contents are consulted to select a path or compute a result.

### Value handling and widths

All three assigned values occupy four-byte destination units.

The first assignment transfers the value obtained from the global source. The second transfers the supplied 32-bit value. The last assigns numeric zero to a 32-bit unit.

There is no arithmetic on the supplied value. In particular:

- High bits are not explicitly discarded.

The destination offsets are fixed by indexing four-byte units: the first, fourth, and second words are assigned, in that order. No input-dependent length, iteration count, or offset computation appears.

No byte order is specified. The contract identifies four-byte value assignments and offsets; mapping nonzero values to individual bytes requires the target representation.

### Preserved contents

### Aliasing with the global source

The global value is obtained for the first assignment, before the later two destination assignments. If a later destination write aliases the global source, that write can change the global storage. It does not cause the first assignment to fetch the global value again.

For example, if the destination word at offset 4 is the global source location, the first assignment uses the value obtained before the final zeroing assignment. Normal completion then leaves that global location zero.

This does not establish that every overlapping or misaligned arrangement is valid. Object-access legality, alignment, and storage representation remain environmental preconditions.

### Repeated calls

These are conditional acceptance cases derived from static evidence. They are not reports of executed tests.

### Ordinary independent storage

Given:

- Four destination words initially containing, in order, `0x11111111`, `0x22222222`, `0x33333333`, and `0x44444444`.
- A separate global source containing `0xA1B2C3D4`.

- Valid ordinary memory and no concurrent modification.

Normal completion must leave the destination words as:

| Offset | Expected value |
|---|---|
| 0 | `0xA1B2C3D4` |
| 4 | `0x00000000` |
| 8 | `0x33333333` |
| 12 | `0x55667788` |

The global source remains unchanged because it is separate from all destination write ranges.

### Supplied value with all bits set

With valid separate storage and a supplied value of `0xFFFFFFFF`, the destination word at offset 12 must receive `0xFFFFFFFF`. The function does not reject it or reinterpret it through a signed comparison.

The word at offset 4 must still become zero.

### No full-region clearing

If the destination word at offset 8 initially contains `0xDEADBEEF`, that word must remain `0xDEADBEEF` after normal completion under ordinary, non-overlapping memory conditions.

An implementation that clears all four words would violate this behavior.

### Changing global source between calls

If the global source changes from `0x01020304` to `0xAABBCCDD` between two calls, the second call must assign `0xAABBCCDD` at destination offset 0, assuming no further modification interferes.

Reusing the first call’s captured global value would not match the source behavior.

### Global source aliases the second destination word

Conditional on such aliasing being legal in the execution environment, suppose the global source occupies destination offset 4 and initially contains `0x12345678`.

Normal completion must leave:

- Destination offset 0 containing the initially obtained value, `0x12345678`.
- Destination offset 12 containing the supplied value.
- Destination offset 4, and therefore the global source, containing zero.

This case distinguishes the initial global fetch from any hypothetical fetch after the zeroing assignment.

### Invalid destination
