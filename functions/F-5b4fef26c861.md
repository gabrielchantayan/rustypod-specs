# F-5b4fef26c861

## Purpose

F-5b4fef26c861 coordinates two alternating transfer paths, designated A and B. It partitions a remaining quantity into bounded chunks, prepares operations at a carried position, checks two status records, invokes an indirect transfer operation, and publishes one selected status through a caller-provided destination.

Publication is not always a read-only operation on the status records. **Every B-selection path overwrites status A’s second 16-bit field with status B’s second field before writing the second output element.** Both records are subsequently finalized, A first. This mutation therefore affects the record supplied to A’s finalizer even when all storage is disjoint.

The alternating-transfer interpretation is inferred intent. The established contract consists of the visible arithmetic, memory accesses, dependency calls, branch conditions, publication, and finalization order.

### Outputs and normal completion

There is no explicit return value.

Every visible normal-return path:

1. Writes the first output element as a 16-bit value.
2. Writes the second output element as a 16-bit value.
3. Calls F-9b718979506d with status A.
4. Calls F-9b718979506d with status B.
5. Returns.

B selection additionally writes A’s second field between the two output writes. Publication is not an atomic four-byte operation. Byte order within each halfword is not established.

### Preconditions

All memory and indirect entries reached on the chosen path must be valid for the visible accesses and calls. Status storage must support both dependency access and the direct A-second-field write. Output storage must permit two halfword writes.

There are no visible null checks, allocation checks, bounds checks, or arithmetic-overflow checks. No nonaliasing guarantee is established. Examples below assume valid, noninterfering storage unless expressly stated otherwise.

## Behavior

### Arithmetic and branch conventions

Remaining quantities, chunk limits, pending quantities, transfer results, and their comparisons use unsigned 32-bit values.

At each iteration, the A chunk is the unsigned minimum of the remaining quantity and the chunk limit. After a matching B transfer, an intermediate remainder is the remaining quantity minus that A chunk. The next pending B quantity is the unsigned minimum of the intermediate remainder and the limit.

These locally calculated subtractions cannot underflow: the A chunk does not exceed the remaining quantity, and the newly calculated pending B quantity does not exceed the intermediate remainder. This establishes no corresponding bound for the inherited initial pending B quantity.

Position additions use values represented as signed 32-bit integers. There is no overflow guard, and the evidence does not establish a portable overflow policy. Representable arithmetic is required for the numeric position examples below.

F-d7be9cfb4000 has two observed result-consumption widths:

- Preparation uses a 16-bit value.
- Position advancement and replacement of the next increment use a 32-bit value.

The result’s formula, units, and complete calling convention are unknown.

A status predicate from F-ec61551795ee permits a transfer when nonzero and selects an exit path when zero. A preparation operation instead permits continuation when its result is zero and selects an exit path when nonzero. Neither convention establishes the semantic meaning of “success.” Transfer completion uses exact equality with the requested quantity.

### Iteration entry and A preparation

Each iteration first adds the current increment to the current position, then calculates the A chunk.

A preparation occurs only if the suppression value is zero and the remaining quantity is nonzero. No visible assignment clears or otherwise changes the suppression value; this condition is evaluated on each iteration.

When enabled:

1. Read the owner’s object pointer.
2. Invoke that object’s indirect entry at dispatch-table byte offset 36.
3. Pass the A chunk and the queried value to F-d7be9cfb4000.
4. Retain the preparation value at 16-bit width.
5. Copy the A descriptor’s four 32-bit words into temporary storage, in increasing word order.
6. Invoke the retained object’s byte-8 entry with the object, descriptor copy, current position, and preparation value.

The retained pointer identifies the preparation object; the code does not substitute a new owner lookup for that invocation.

If the preparation operation returns nonzero, call F-fceaba74ea88 with the owner-relative byte-84 address and select A. Neither status predicate nor transfer is reached on this path.

If preparation returns zero, or preparation is suppressed, continue to the B-side processing below.

### B status and transfer

Call F-fceaba74ea88 with the owner-relative byte-84 address. Then call F-ec61551795ee with status B.

If the predicate returns zero:

- When the remaining quantity is nonzero, call F-fceaba74ea88 with the owner-relative byte-88 address.
- Select B.

If the predicate returns nonzero, copy the four B-descriptor words into temporary storage in increasing word order. Invoke the transfer-interface object’s byte-16 entry with the interface object, pending B quantity, and descriptor copy.

Compare its unsigned 32-bit result with the pending B quantity:

- **Unequal:** Call F-7f008c1060db with status B and the values 34, 0, and 0. If the remaining quantity is nonzero, call F-fceaba74ea88 with the byte-88 address. Select B.
- **Equal, remaining quantity zero:** Select B immediately, without the byte-88 call.
- **Equal, remaining quantity nonzero:** Continue with position advancement.

Both smaller and larger transfer results are mismatches. A zero pending quantity does not suppress the transfer: a nonzero B predicate still causes a zero-quantity invocation, whose result must be zero to match.

### Position advancement and B preparation

After a matching B transfer with nonzero remaining quantity:

1. Subtract the A chunk from the remaining quantity to obtain the intermediate remainder.
2. Read the owner’s current object pointer and invoke its byte-36 entry.
3. Pass the A chunk and queried value to F-d7be9cfb4000, consuming a 32-bit result.
4. Set the pending B quantity to the unsigned minimum of the intermediate remainder and the chunk limit.
5. Add the helper result to the current position.

If the intermediate remainder is nonzero, prepare B:

1. Read the owner’s object pointer again.
2. Invoke that object’s byte-36 entry.
3. Pass the new pending B quantity and queried value to F-d7be9cfb4000.
4. Retain the preparation value at 16-bit width.
5. Copy the B descriptor’s four words into temporary storage.
6. Invoke the retained object’s byte-8 entry with the object, descriptor copy, updated position, and preparation value.

A nonzero B-preparation result selects B immediately. That branch performs no subsequent byte-88 dependency call, A predicate, or A transfer.

If the intermediate remainder is zero, B preparation is skipped. Otherwise, a zero B-preparation result continues below.

### A status and transfer

Call F-fceaba74ea88 with the owner-relative byte-88 address. Call F-ec61551795ee with status A.

A zero predicate selects A without an A transfer.

For a nonzero predicate, copy the A descriptor’s four words into temporary storage. Invoke the transfer-interface byte-16 entry with the interface object, A chunk, and descriptor copy.

If the unsigned 32-bit result differs from the A chunk:

1. Call F-7f008c1060db with status A and 34, 0, and 0.
2. If the intermediate remainder is nonzero, call F-fceaba74ea88 with the byte-84 address.
3. Select A.

If the transfer matches and the intermediate remainder is zero, select B. Thus, a terminal matching A transfer publishes B, including the A-second-field mutation associated with all B selections.

### Continuation

After a matching A transfer with a nonzero intermediate remainder:

1. Replace the remaining quantity with the intermediate remainder minus the pending B quantity.
2. Read the owner’s object pointer and invoke its byte-36 entry.
3. Pass the pending B quantity and queried value to F-d7be9cfb4000.
4. Replace the next iteration’s increment with the helper’s 32-bit result.

Execution returns to iteration entry, which adds that increment before calculating the next A chunk.

A zero chunk limit can prevent progress when the remaining quantity is nonzero: both newly selected chunks remain zero, and a continuing cycle leaves the remaining quantity unchanged. Termination is not guaranteed by the visible quantity arithmetic.

### Status publication and finalization

**A selection has this direct access order:**

1. Read A’s first 16-bit field and write it to output element zero.
2. Read A’s second 16-bit field and write it to output element one.
3. Finalize A, then B.

There is no separate direct status-field assignment on this path, apart from effects caused by output aliasing.

**B selection has this direct access order:**

1. Read B’s first 16-bit field and write it to output element zero.
2. Read B’s second 16-bit field.
3. Assign that value to A’s second 16-bit field.
4. Use A’s second field as the source for the write to output element one.
5. Finalize A, then B.

This is not equivalent to copying B directly to the output. With disjoint storage, the published halfwords equal B’s fields, but A’s second field has also changed. A’s first field is not directly replaced on this path.

The first output write occurs before B’s second-field read. Consequently, aliasing may change the value subsequently read from B. The assignment to A may itself affect overlapping output or status storage. No snapshot of both selected fields is established before publication.

A’s finalizer is called after the A-second-field overwrite on every B-selection path. The function makes no intervening direct restoration. Unknown finalizer effects prevent assuming that B remains unchanged between the two finalization calls or that output remains unchanged after finalization.

## Side effects

Direct effects include:

- Reading owner, object, and dispatch-table pointers.
- Copying four 32-bit descriptor words into a reused 16-byte temporary area for each reached preparation or transfer.
- Updating carried quantities, position, and the next increment.
- Writing two output halfwords.
- **Writing B’s second halfword into A’s second halfword on every B-selection path.**
- Invoking dependencies in the branch-specific order above.

Each descriptor copy consists of ordered word accesses, not an established atomic 16-byte snapshot. Descriptors are read again when later operations are reached.

There is no visible direct allocation, deallocation, or ownership transfer. Dependencies may nevertheless allocate, release, retain pointers, modify globals, or mutate accessible memory; none of these behaviors is ruled out.

The temporary descriptor address is supplied instead of the original descriptor address. A valid lifetime for retaining that temporary pointer beyond the call is not established.

Owner queries are repeated across phases. Results must not be treated as one cached, invariant value.

## Acceptance examples

These are conditional static scenarios, not runtime results. Unless stated otherwise, dependencies return normally, memory is valid and disjoint, and position arithmetic is representable.

1. **A preparation rejects.** With nonzero remaining quantity, zero suppression, and nonzero A-preparation result, the byte-84 dependency runs and A is published. No status predicate or transfer runs. A and then B are finalized.

2. **B predicate rejects.** A zero B predicate selects B. A nonzero remaining quantity adds the byte-88 call before publication; zero remaining quantity omits it. Both cases overwrite A’s second field during publication.

3. **B transfer mismatch in either direction.** For pending B quantity 5, results 4 and 6 both invoke F-7f008c1060db on B with 34, 0, 0. The eventual publication uses the status contents available after that call and any applicable byte-88 call, not necessarily B’s entry contents.

4. **Zero B request remains observable.** With pending B quantity zero and nonzero B predicate, the transfer runs with request zero. Result zero matches; any nonzero result takes the mismatch path.

5. **B preparation rejects.** A nonzero intermediate remainder and nonzero B-preparation result select B without another byte-88 call, A predicate, or A transfer. Publication still mutates A’s second field.

6. **Terminal A match selects B.** After a matching B transfer, zero intermediate remainder, nonzero A predicate, and matching A transfer, B is published. B preparation is absent; the byte-88 call and A transfer precede publication.

7. **Nonterminal A mismatch selects A.** With nonzero intermediate remainder and unequal A-transfer result, the A mismatch dependency runs, followed by the byte-84 call. A is published without the B-selection assignment.

8. **Chunk progression.** Remaining quantity 10 and limit 4 produce A chunk 4. After matching B transfer, the intermediate remainder is 6 and new pending B quantity is 4. After matching A transfer, the next remaining quantity is 2. Position changes remain helper-dependent.

9. **Disjoint B publication changes A.** Immediately before B publication, suppose A contains halfwords 10 and 20, and B contains 30 and 40. Publication writes output zero as 30, overwrites A’s second field with 40, and writes output one as 40. A’s finalizer is invoked with A containing 10 and 40, subject to that finalizer’s own subsequent effects.

10. **First output write can affect the second source.** If output element zero aliases B’s second field, B publication first writes B’s first value into that location. The subsequent B-second-field read observes the resulting value; it is then assigned to A’s second field and used for output element one.

11. **Consumption widths differ.** Where a helper result has significant bits above bit 15, a preparation use retains only the 16-bit value. A position-update use consumes a 32-bit value. No equality of resulting numeric increments is required.

## Evidence

Established static evidence consists solely of the supplied function representation: operand widths, minimum calculations, branch conditions, descriptor-copy accesses, dispatch offsets, dependency arguments, status-selection paths, and finalization order.

In particular, the shared B-publication path writes B’s first field to the output, assigns B’s second field to A’s second field, and then uses A’s second field for the second output write. Both finalizers follow those writes, A before B.

Alternating-transfer, preparation, synchronization, and finalization terminology describes observed roles or inferred intent; it does not establish dependency internals, ownership, or runtime guarantees.
