# F-94a20de85fc5

## Purpose

F-94a20de85fc5 checks a narrow compatibility marker, prepares selected fields in a caller-supplied context, invokes an indirect callback, and initializes selected fields using the callback’s nonzero result.

The established behavior is selective initialization of bytes and 32-bit words. The supplied representation does not establish a complete object type, allocation contract, ownership transfer, or release policy.

The function returns a 32-bit status:

| Return bit pattern | Signed 32-bit interpretation | Established condition |
|---|---:|---|
| `0x00000000` | 0 | The final initialization sequence completes. |
| `0xfffffffa` | −6 | The marker address is zero, its first byte is not `0x31`, or the compatibility value is not `0x38`. |
| `0xfffffffe` | −2 | The context address is zero after successful marker validation, or the later context-link read yields zero. |
| `0xfffffffc` | −4 | The indirect callback returns zero. |

Labels such as “invalid version,” “invalid stream,” and “out of memory” would be interpretations, not established error meanings.

## Interface

### Inputs

The supplied representation exposes three arguments:

1. **Context address:** a 32-bit address-like value. Zero is rejected after marker validation. A nonzero value must support the context accesses below.
2. **Marker address:** an address of readable byte storage. Only its first byte is examined.
3. **Compatibility value:** a 32-bit integer required to equal `0x38`, decimal 56. It is not visibly used as a memory-access bound.

The marker must begin with `0x31`, conventionally the character `1`. The function does not inspect a terminator or any subsequent marker byte.

### Context layout

Offsets are byte displacements from the context address. Every listed access is 32 bits wide.

| Offset | Visible role |

### Outputs and storage requirements

The direct output is the status word. Context storage and result-related storage carry additional outputs.

Two result-related addresses must be distinguished:

- **Returned base:** the nonzero value returned by F-indirect-0020.
- **Selected base:** the nonzero value later reread from context offset `0x1c`.

Under stable, disjoint-memory conditions, these are equal. The function does not enforce their equality.

The returned base must support the initial writes at offsets `0x08`, `0x24`, and `0x34`. The selected base must support the final accesses through offset `0x6f`. When both bases coincide, a region covering the listed accesses through `0x6f` suffices for the visible writes, subject to valid address arithmetic and target memory rules.

The function also forms selected base plus `0x530` and stores that address in three fields. It does not access storage at that displacement. The visible behavior therefore does not establish that such storage exists or that the returned allocation has any particular size.

## Behavior

### Validation and precedence

Marker validation precedes context validation:

- A zero marker address returns −6 without reading marker storage.
- A nonzero marker address causes its first byte to be read.
- A first byte other than `0x31` returns −6.
- If the first byte is `0x31`, a compatibility value other than `0x38` returns −6.
- Only after those checks succeed does a zero context address return −2.

No context write or callback occurs on these validation-failure paths.

Consequently, an invalid marker takes precedence over a zero context address. A nonzero but unreadable marker is not converted into one of the documented statuses: the byte read is attempted before the context address is checked.

### Preliminary preparation

After successful validation, the function performs these ordered memory operations:

1. Writes zero to context offset `0x18`.
2. Reads and captures the global value that will supply the callback’s third argument.
3. Reads context offset `0x20`.
4. If that slot is zero, reads its global default value, stores the default at `0x20`, and then writes zero to context offset `0x28`.
5. Reads context offset `0x24`.
6. If that slot is zero, reads its separate global default value and stores it at `0x24`.

The default installations are independently conditional:

- A nonzero callback slot avoids both its replacement and the associated clearing of `0x28`.
- A zero callback slot causes `0x28` to be cleared even if that argument slot previously held a nonzero value.
- Defaulting `0x24` does not itself clear `0x28`.

These statements describe the direct operations. Aliasing between memory locations can introduce additional effects; the function does not check for such overlap.

The installed callback default is not checked for zero before the indirect call. The target represented by `0x24` is not called by this body.

### Callback invocation and zero result

After preliminary preparation, the function invokes F-indirect-0020 through context offset `0x20`, using the arguments described in the interface.

The third argument is the previously captured global value. The function does not reread that global after the callback to obtain an updated value.

If the callback returns zero, the function returns −4. On this path, the function itself does not:

- Store a replacement link at context offset `0x1c`.
- Perform result-relative initialization.
- Undo preliminary context writes.
- Invoke a release operation.

The callback may independently modify context storage, globals, unrelated memory, or external resources. No preservation or rollback guarantee is established for those effects.

### Initial writes through the returned base

For a nonzero callback result, the following 32-bit writes occur in order:

| Order | Destination | Value |
|---:|---|---|
| 1 | Context `+0x1c` | Returned base |
| 2 | Returned base `+0x08` | 1 |
| 3 | Returned base `+0x24` | `0x0f` |
| 4 | Returned base `+0x34` | 0 |

The function then rereads context offset `0x1c`. That read selects the base for the remaining initialization; the function does not unconditionally reuse the original callback result.

If the reread yields zero, the function returns −2 without undoing the preceding writes.

A repeated zero-context check is also present at this stage. The context argument has already passed its earlier check and is not reassigned in the visible body, so this repeated check does not create another ordinary failure case.

With disjoint storage and no intervening mutation, the reread returns the value just stored. With overlap, an initial result-relative write can change the link before it is read. Other mutation may also affect the read, although no concurrency guarantees are established. A different nonzero link is accepted without comparison to the returned base.

## Side effects

Direct writes target the context, the returned base, and the selected base at the offsets listed above. These locations can overlap; the ordered write descriptions do not imply independent final fields under overlap.

The function visibly reads global data but contains no direct global assignment. That does not establish that global values remain unchanged: a destination could alias global storage, and F-indirect-0020 has unspecified side effects.

The operation is not visibly atomic. No synchronization or publication mechanism is shown. The stated order describes the supplied static representation, not a cross-thread visibility guarantee.

There is no visible release call, rollback, whole-object clearing operation, or cleanup of the previous context link. A nonzero callback result replaces the old link without a preceding operation on its former contents.

This replacement alone does not prove a leak because ownership and callback-side handling are unknown. It also provides no basis for relying on the function to release the old value.

## Acceptance examples

These are conditional static acceptance examples, not executed tests.

### Invalid marker takes precedence

Given a zero context address and a zero marker address, the return is −6, with no marker read, context write, or callback.

Given a zero context address, a readable first marker byte of `0x31`, and compatibility value `0x38`, the return is −2.

### A one-byte marker is sufficient

Given valid context storage and compatibility value `0x38`, a marker consisting of one readable byte `0x31` satisfies the visible marker check. No terminating byte is required.

If that byte is instead `0x32`, the return is −6 before any context preparation.

### Callback failure leaves preparation in place

Assume valid marker arguments, disjoint valid storage, a zero callback slot, a valid callable default, and a callback that returns zero without modifying the context.

The return is −4. Context offset `0x18` is zero, `0x20` contains the installed default, and `0x28` is zero. Offset `0x24` also contains its default if initially zero. The function itself has not replaced the old link at `0x1c`.

### An existing callback retains its argument value

Assume context offset `0x20` already contains a valid nonzero callback address, `0x28` contains a chosen 32-bit value, and no aliasing or intervening mutation changes those locations.

The callback receives that chosen value as its first argument. A zero value at `0x24` causes its own default installation but does not cause `0x28` to be cleared.

### Successful initialization is selective

Assume a normally returning callback supplies a valid disjoint writable region, the context remains stable, and all listed accesses and address calculations are valid.

The function returns zero. The context link contains the returned base. The result fields at `0x6c`, `0x50`, and `0x4c` all contain returned base plus `0x530`.

If result bytes `+0x01` through `+0x03` initially contain nonzero values, those bytes remain unchanged by this body under these assumptions. The zero store at result `+0x00` affects only that byte; the first final result-relative store instead clears the 32-bit field at `+0x1c`.

### Link overlap can alter the outcome

Assume valid memory arrangements in which the initial returned-base store at `+0x34` overlaps context `+0x1c`. That store clears the link before its reread, so the function returns −2 after the initial writes.

More generally, if the reread produces another nonzero valid address, final initialization uses that selected base. The function does not reject the difference from the callback result.
