# F-f175fb000823

## Purpose

F-f175fb000823 computes an unsigned 64-bit aggregate from a nullable tagged object and a caller-supplied table.

Its established behavior has three cases:

- A null object produces zero without accessing the table.
- A terminal object searches the table. The first matching position determines a return calculation.
- Any other object invokes two recursive evaluations and two opaque dependencies, then combines their results with bitwise OR.

**Inferred intent:** terminal objects identify entries in a table, and nonterminal objects combine membership masks. This interpretation is consistent with ordinary matching positions but is not a complete arithmetic contract. Some positions encounter oversized shifts or signed shifts whose mathematical results are not representable. Those cases remain **documented_only**, rather than being assigned an assumed mask value.

This specification rests on static evidence. No runtime tests have been performed.

## Interface

### Inputs and result

| Input | Interpretation |
|---|---|
| Table reference | Address of a signed 32-bit count followed by 32-bit candidate values |
| Object reference | Null, or an address supporting the accesses required by the selected object path |

The result is an unsigned 64-bit value. There is no separate status result or output parameter.

Zero is not an error indicator. It can mean that the object was null, a terminal search had no match, the count prevented any comparison, or all four nonterminal contributions combined to zero.

### Table layout

Positions are zero-based.

| Byte offset | Width | Meaning |
|---|---:|---|
| `0x00` | 4 bytes | Signed 32-bit candidate count |
| `0x04 + 4 × position` | 4 bytes | Candidate at that position |

Candidate matching compares 32-bit integer values for equality. The object’s terminal comparison value is also a 32-bit integer.

No independent allocation size or capacity accompanies the table reference. The count therefore does not establish that the advertised candidate storage is readable.

### Object layout

| Byte offset | Width | Meaning established by use |
|---|---:|---|
| `0x00` | 1 byte | Tag |
| `0x08` | 4 bytes | Representation used as the second recursive object reference |

The terminal path does not access the four aggregation fields. The aggregation path does not directly access the terminal comparison field.

### Preconditions

A defined, normally returning execution requires:

- Readable storage for every access actually reached.
- Valid address calculations, alignment, and representations for those accesses.
- Sufficient table storage for every candidate examined.
- Continued validity of parent and table storage across intervening calls.
- Satisfaction of dependency-specific preconditions.
- Normal return from every reached call.
- Finite traversal within available execution resources.
- Defined arithmetic for the selected return calculation.

These requirements are path-dependent. A null object needs no readable table. A terminal object with a nonpositive count needs no readable candidate or terminal comparison field. A nonterminal object need not directly access the table header, although its descendants and dependencies may do so.

No explicit capacity check, object-size check, cycle detection, recursion limit, or recovery mechanism is established.

## Behavior

### Dispatch and early return

Nullness is resolved before any object access. A null object returns zero without reading a tag, table count, candidate, or other object field, and without invoking dependencies.

For a non-null object, the tag determines the entire local processing path. Only the terminal tag selects table search. All other tag values require the aggregation fields, regardless of any external interpretation of those tags.

### Aggregation and call ordering

A nonterminal evaluation has four contributions with the following strict call order:

| Order | Contribution | Argument obtained from the object |
|---:|---|---|
| 1 | Recursive F-f175fb000823 result | Four-byte reference at `0x0C` |
| 2 | Recursive F-f175fb000823 result | Four-byte reference at `0x08` |
| 3 | F-7183fcb6e0d1 result | Four-byte value at `0x10` |
| 4 | F-92ede6886f09 result | Four-byte value at `0x38` |

Every call receives the same table reference received by the parent invocation. After all four calls return normally, their 64-bit results are combined by bitwise OR.

There is no result-dependent short-circuiting. Even an earlier contribution containing all 64 set bits does not suppress later calls.

The ordering also governs argument acquisition: each listed object field is read after the preceding call returns. The fields are not collectively captured before traversal. Consequently:

- A recursive evaluation may change the reference subsequently read at `0x08`.
- Earlier calls may change either opaque argument before its field is read.
- Changes to shared table storage may affect later calls.
- Invalidating parent storage during a call may make a subsequent field access invalid.

These are consequences of access order, not guarantees that mutation is permitted or synchronized. The visible body provides no protection against invalidation.

If any call fails to return normally, no subsequent call or final combined result is established.

### Terminal matching

Terminal processing selects the earliest equal candidate within the count-delimited search.

Candidates are considered in increasing position order, beginning at zero. A signed count check precedes every candidate comparison. A position is eligible only when the count exceeds that position interpreted as signed 32-bit.

Accordingly:

- An initial zero or negative count returns zero without reading a candidate or the terminal comparison field.
- The first equal candidate ends the search.
- Later duplicates are not inspected and cannot contribute additional bits.
- An unsuccessful search returns zero once its next position is outside the count.

Each reached comparison requires both the candidate and the four-byte comparison value at object offset `0x24`. Their relative read order is not established. Both follow the successful count check.

The count and comparison value occur as repeated access expressions, rather than as explicit whole-search snapshots. The contract therefore does not promise that either value is captured once. Conversely, this is not a promise of fresh physical memory loads, atomic reads, or support for concurrent mutation.

For a stable positive count, the compared positions range from zero through count minus one. Since the count is signed 32-bit, the greatest such position is 2,147,483,646. An unsuccessful search then terminates at the next count check; unsigned position wraparound is not needed. Validating arithmetic bounds does not establish that an allocation or address space can hold such a table.

### Position-dependent result

The selected position controls a calculation involving 32-bit words and a 64-bit result. It is not established as an unrestricted 64-bit single-bit operation.

For reachable positions below 32, the calculation constructs separate lower and upper 32-bit words. The lower contribution uses a signed 32-bit one shifted left by the position. The upper contribution includes an unsigned 32-bit right shift whose distance is 32 minus the position. The represented shift-distance reductions retain eight low bits, rather than explicitly reducing distances to the width of a 32-bit operand.

For positions at least 32, the calculation first performs a signed 32-bit left shift. Its distance is the remainder, modulo 256, of the position minus 32. Only after that shift is the result converted to unsigned 32-bit, widened, and placed in the upper half of the 64-bit return.

These widths establish the following limits:

| First matching position | Return status |
|---|---|
| 1–30 | Exactly the bit corresponding to that position |
| 32–62 | Exactly the bit corresponding to that position |
| 0 | **documented_only:** the upper-word calculation includes a 32-bit right shift by 32 |
| 31 | **documented_only:** the signed 32-bit left-shift result is not representable |
| 63 | **documented_only:** the inner signed 32-bit left-shift result is not representable |
| 64 and above | Depends on the eight-bit distance and the arithmetic limits below |

For the upper-half calculation:

- Distances 0–30 yield exactly bit 32 plus the distance.
- Distance 31 has an unrepresentable signed result.
- Distances 32–255 exceed the 32-bit operand’s permitted shift range.

Conversion after the inner shift does not make an otherwise invalid shift valid.

Some larger positions consequently have established aliases. Positions 288 and 318 produce the same established results as positions 32 and 62, respectively. Position 319 remains unresolved because its inner distance is 31.

No rejection, saturation, clamping, or modulo-64 mask interpretation is established. Unknown arithmetic cases must not be assigned a numerical result merely because a particular processor might mask shift distances.

## Side effects

The visible body performs memory reads and calls. It contains no explicit memory writes, allocation, deallocation, ownership transfer, or named global-state access.

This does not establish purity for the complete invocation. Recursive descendants can reach the opaque dependencies, whose effects are unknown. They may affect table storage, object storage, global state, resources, or ownership.

No ownership guarantee should be inferred from the absence of direct allocation or release. In particular, the available evidence does not establish that dependencies:

- Preserve the validity of passed storage.
- Avoid retaining references.
- Avoid releasing resources.
- Preserve globals.
- Leave arguments or indirectly reachable storage unchanged.

Caller-visible storage must remain valid through every later access that actually occurs.

There is no local conversion of invalid memory access, arithmetic invalidity, dependency failure, resource exhaustion, or nontermination into a status value. Returning zero is not a general failure-handling policy.

## Acceptance examples

These are conditional specification cases, not executed tests. Unless an example concerns unresolved behavior, assume readable storage, valid representations and address calculations, stable terminal inputs, defined arithmetic, and normally returning dependencies.

1. **Null object, unreadable table reference.**  
   The result is zero. No table access or dependency invocation occurs.

2. **Terminal object, count zero.**  
   The result is zero after the tag and count accesses. Neither a candidate nor offset `0x24` is accessed.

3. **Terminal object, count −1.**  
   The result is zero before candidate comparison. The negative count is not treated as a large unsigned length.

4. **Three candidates, no match.**  
   Positions zero, one, and two are compared in that order. The following count check ends the search with zero.

5. **Duplicate matches at positions 2 and 5.**  
   The result is `0x0000000000000004`. The later duplicate is not examined.

6. **Lower-half boundary.**  
   A first match at position 30 returns `0x0000000040000000`. A first match at position 31 has a **documented_only** numerical result; `0x0000000080000000` is not established by the available arithmetic evidence.

7. **Upper-half boundaries.**  
   Position 32 returns `0x0000000100000000`; position 62 returns `0x4000000000000000`. Position 63 is **documented_only**, not an established return of `0x8000000000000000`.

8. **First-position match.**  
   Position zero is selected without examining later candidates. Its numerical return remains **documented_only** because the represented upper-word operation includes a shift by 32. An exact return of one is not established.

9. **Match at position 64.**  
   The inner shift distance is 32. The numerical result is **documented_only**; neither zero nor a masked hardware result is required.

10. **Larger-position aliases.**  
    Position 288 returns `0x0000000100000000`; position 318 returns `0x4000000000000000`. Position 319 remains **documented_only**.

11. **Four aggregation contributions.**  
    Contributions of `0x01`, `0x04`, `0x10`, and `0x40`, in the established call order, produce `0x55`. All four calls occur.

12. **An early all-ones contribution.**  
    If the first recursive evaluation returns all 64 set bits and the remaining calls return normally, those remaining calls still occur. The combined result has all 64 bits set.

13. **Mutation of a later recursive reference.**  
    If the first recursive evaluation validly changes the field at `0x08`, and the parent remains readable, the second recursive evaluation receives the subsequently read value.

## Uncertainties

The following remain **documented_only**:

- Execution-level results for oversized shifts, including positions zero and 64.
- Execution-level results for unrepresentable signed shifts, including positions 31, 63, and corresponding larger-position aliases.
- Whether the represented arithmetic faithfully describes the intended target operations.
- Dependency validation, mutation, allocation, retention, release, global effects, and failure behavior.
- Complete object layouts, byte order, alignment rules, and reference encoding beyond the established four-byte fields.
- External table-size, count, or matching-position restrictions.
- Structural guarantees preventing cycles or excessive recursion.
- Concurrency, synchronization, and atomicity guarantees.

The membership-mask interpretation is **inferred intent**. It cannot resolve these unknowns or justify extending the established numerical cases.

## Evidence

Static evidence establishes the null-object early return, terminal tag distinction, accessed field widths and offsets, signed count comparison, earliest-match selection, ordered calls, and four-result bitwise OR.

The arithmetic evidence distinguishes signed 32-bit left-shift operands from an unsigned 32-bit right-shift operand. It also places conversion and widening after the upper-half inner shift. These distinctions require separate treatment of excessive distances and unrepresentable signed results.

No dependency implementations, target-level shift contract, external structural invariants, or runtime observations were supplied.

No runtime tests have been performed. All acceptance examples describe conditional consequences of the available static evidence, not observed execution.
