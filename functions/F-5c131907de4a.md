# F-5c131907de4a

## Purpose

F-5c131907de4a performs an ordered, index-based search over a source represented by an opaque 32-bit value. For each eligible index, it obtains a 32-bit candidate and passes that candidate to an indirect callback associated with a separate receiver. It returns the first candidate whose callback result is nonzero. If the current index is no longer below the source’s reported signed extent, it returns zero.

“Search,” “source,” “candidate,” and “receiver” describe the observable roles of the values. They do not establish an underlying collection type, object model, or ownership convention.

The extent is queried before every candidate retrieval, rather than captured once. Consequently, dependency or callback side effects can affect which later indices are visited.

## Interface

The function accepts three arguments:

|---|---|---|
| Receiver | 32-bit integer used as an address base | Locates an indirect callback slot and is passed as the callback’s first argument. |
| Source | Opaque 32-bit value | Passed unchanged to both source-related dependencies. |
| Context | Opaque 32-bit value | Passed unchanged as the callback’s second argument. |

The receiver’s numeric value is used to address a callback slot at byte offset **48** from the receiver base. The supplied representation treats that slot as containing a callable function pointer. It does not establish a complete receiver layout, alignment requirement, allocation size, or concrete type.

The source and context may represent addresses, handles, integers, or other bit patterns. Their meanings are not established.

### Output

The function returns one 32-bit value:

- The exact candidate value obtained for the first callback invocation returning nonzero.
- Zero if an extent check ends the search before any callback has accepted a candidate.

The callback’s result is used only as a zero/nonzero decision. It is not returned.

A zero candidate can be accepted. In that case, the function returns zero, which is numerically indistinguishable from the exhaustion result. The interface provides no separate success flag.

## Behavior

### Initial state and extent checks

The current index begins at zero.

Before attempting to retrieve any candidate, the function calls F-10b760faca36 with the source. It compares the returned extent with the current index using signed 32-bit ordering.

If the extent is less than or equal to the index, the function returns zero immediately. At that point it does not retrieve a candidate or resolve or invoke the receiver’s callback.

Therefore:

- An initial extent of zero causes immediate exhaustion.
- An initial negative extent also causes immediate exhaustion.
- A positive extent permits retrieval at index zero.
- The reported extent is an exclusive upper bound for that particular check, not necessarily a permanent property of the source.

A negative extent is not distinguished from ordinary exhaustion. If F-10b760faca36 uses negative values as errors, this function does not preserve that distinction in its return value.

### Candidate processing order

When the current extent is greater than the index, the function performs these observable operations in order:

1. Calls F-6bbddce1b930 with the source and current index.
2. Retains the returned 32-bit candidate.
3. Reads the indirect callback target from the receiver’s slot at byte offset 48.
4. Invokes that target with the receiver, context, and retained candidate.
5. Tests whether the callback result is zero.

The callback target is resolved after candidate retrieval. It is not established as a target captured at function entry or before the retrieval call. If retrieval changes the callback slot, the subsequent invocation uses the target obtained after that change.

The function does not validate the candidate before passing it to the callback. Every candidate bit pattern, including zero, follows the same path.

### Acceptance and continuation

If the callback result is nonzero, the function returns the retained candidate immediately. It performs no further extent query or candidate retrieval.

If the callback result is zero, the function increments the index by one and begins another iteration with a new call to F-10b760faca36.

Thus, while the function continues normally:

- Candidate retrieval indices are consecutive, beginning at zero.
- Each retrieved candidate receives exactly one callback invocation.
- No index is retried or skipped by this function.
- A rejection is followed by another extent query, not directly by another retrieval.
- An acceptance ends processing regardless of the callback result’s particular nonzero value.

There is no explicit source reread after acceptance. If the callback changes the source, the return value is still the candidate value retained before that callback ran. This preserves the 32-bit value, not necessarily the validity or lifetime of anything it might reference.

### Mutable extent and callback state

The function makes no visible snapshot of the source extent or callback target.

If an initially positive extent shrinks to the next index or below after a rejection, the next extent check ends the search. If the extent grows, additional indices can become eligible. Eligibility is determined by the extent returned for the current iteration.

Likewise, a callback-slot change can affect a later invocation because the slot is resolved again after each retrieval. No guarantee is made that dependencies or callbacks preserve globals, source state, receiver contents, or externally reachable memory.

### Integer boundaries

The index and extent comparison are represented as signed 32-bit operations. The index begins at zero and advances only after a retrieved candidate is rejected.

Under the represented control flow, retrieval can occur only at indices **0 through 2,147,483,646**. At index **2,147,483,647**, no signed 32-bit extent can be greater than the index, so the next extent check must end the search.

Accordingly, ordinary index progression does not require signed overflow. At most **2,147,483,647** candidates can be retrieved and presented to callbacks during one normally progressing invocation. This bound does not imply timely completion: a dependency or callback may fail to return.

## Side effects

The function contains no explicit allocation, deallocation, ownership transfer, source update, receiver update, or global write.

Its direct data-memory access outside its internal execution state is the callback-slot read. Its calls may have arbitrary side effects not described by the supplied evidence. Those effects remain observable even if the function later returns zero.

Important ordering consequences include:

- The extent query occurs before any callback-slot read on that iteration.
- Retrieval occurs before callback-slot resolution.
- Callback effects occur before the next extent query following rejection.
- Acceptance prevents all later iterations.
- Initial exhaustion avoids this function’s callback-slot access entirely.

The last property does not establish that an arbitrary receiver value is universally safe: a dependency could independently access shared state related to that receiver.

There is no established cleanup path. In particular, the function does not explicitly release rejected candidates or retain accepted candidates through an ownership API. Whether candidates require either action is unknown. It is also unknown whether dependency calls themselves perform such actions.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests.

1. **Empty source:** If the first extent query returns zero, the result is zero. There are no candidate retrievals, callback-slot reads, or callback invocations by this function.

2. **Negative initial extent:** If the first extent query returns negative one, the result is zero. The negative value is not returned as an error.

3. **Immediate acceptance:** If the first extent is positive, retrieval at index zero produces candidate A, and the callback returns any nonzero value, the result is A. There is exactly one extent query and one retrieval.

4. **Rejection followed by acceptance:** If index zero produces A and is rejected, the function queries the extent again. If that extent exceeds one, index one produces B, and its callback accepts, the result is B.

5. **Stable finite exhaustion:** If every extent query returns three and all callbacks reject, retrieval occurs at indices zero, one, and two. The extent query at index three ends the search. The result is zero, with four extent queries and three callback invocations.

6. **Shrinking extent:** If index zero is rejected and the next extent is one, the search ends before retrieving index one, even if the first extent was larger.

7. **Accepted zero candidate:** If retrieval produces zero and the callback accepts it, the function returns zero immediately. It does not continue searching for a nonzero candidate.

8. **Changed callback target:** If retrieval changes the receiver’s callback slot from target A to target B, the subsequent slot resolution selects B, provided the memory access and invocation are valid.

9. **Signed extent boundary:** If an extent’s 32-bit representation has its sign bit set, it compares as negative. With the initially nonnegative index, that extent ends the search rather than authorizing a large unsigned range.
