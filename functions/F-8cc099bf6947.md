# F-8cc099bf6947

## Purpose

F-8cc099bf6947 conditionally installs a three-field configuration in a caller-supplied object and replaces a four-bit selection field in that object’s flags.

The established behavior has three accepted selector values:

- `0x100`: use the caller-supplied address and a validated count.
- `0x200`: use the caller-supplied address and a validated count.
- `0x400`: use an address inside the object and a fixed count of one.

All accepted requests also require the object’s flags to pass an eligibility gate. Rejected requests return failure without performing any explicit object writes.

The duplicated address fields, count field, and embedded address suggest a buffer-configuration operation. That interpretation is **inferred intent**, not an established semantic identity for the object or selectors.

## Behavior

### Eligibility gate

The flags word at offset `+0x0c` controls whether selector handling is reached.

First, the function checks whether at least one of bits 0 and 1 is set. If neither is set, the request is rejected immediately.

If that first check passes, the function evaluates the flags again and requires bit 22, represented by mask `0x00400000`, to be clear. If that bit is set, the request is rejected.

Thus, under stable-memory conditions, eligibility requires both:

- The flags masked by `0x00000003` are nonzero.
- The flags masked by `0x00400000` are zero.

Either low bit is sufficient. Both low bits may also be set.

The supplied representation contains two distinct flags accesses in this gate, with the second conditional on the first check passing. It does not establish one immutable flags snapshot for the entire call.

### Selector and count acceptance

Once eligibility passes, the function recognizes only the exact selector values `0x100`, `0x200`, and `0x400`.

For selector `0x100` or `0x200`:

- The selected address is the supplied address, unchanged.
- The selected count is the supplied count, unchanged.
- Acceptance requires the unsigned 32-bit result of subtracting one from the supplied count to be less than `0x00ffffff`.

That arithmetic accepts exactly the count bit patterns from `0x00000001` through `0x00ffffff`, inclusive: decimal 1 through 16,777,215.

Consequences include:

- Zero is rejected because subtracting one wraps to `0xffffffff`.
- `0x00ffffff` is accepted.
- `0x01000000` is rejected.
- All bit patterns representing negative signed 32-bit integers are rejected.
- Validation does not round, clamp, or otherwise modify an accepted count.

For selector `0x400`:

- The selected address is the object address plus `0x24`.
- The selected count is one.
- Both the supplied address and the supplied count are ignored for the resulting configuration.
- The supplied count need not satisfy the range required by the other two selectors.

Every other selector is rejected. This includes zero, combinations such as `0x300`, and values that contain an accepted selector together with additional bits. Selector handling is not a general bitmask interface.

### Successful update

After acceptance, the function performs these explicit stores in this order:

1. Store the selected address at object offset `+0x10`.
2. Store the selected count at object offset `+0x1c`.
3. Store the selected address at object offset `+0x04`.
4. Update the flags word at object offset `+0x0c`.

For the flags update, the function reads the flags word again, clears bits 8 through 11, and inserts the accepted selector. Equivalently, it retains the bits selected by `0xfffff0ff` and combines them with the selector.

Because each accepted selector lies entirely within bits 8 through 11, the resulting four-bit field is exactly:

- `1` for selector `0x100`;
- `2` for selector `0x200`;
- `4` for selector `0x400`.

All flags outside that field are retained from the flags value used for this final update. The function then returns zero.

The final flags read occurs after the three preceding configuration stores in the supplied representation. It is not expressed as reuse of either eligibility-gate value.

### Rejection

If any acceptance condition fails, the function returns one without executing any of the four explicit stores.

Rejection does not clear a previous configuration, replace the count, or normalize the selector field. Reads of the flags word may still have occurred.

Given flags `0x00000b03`, selector `0x100`, any supplied address, and count 12:

### Ineligible object

With flags zero, even selector `0x400` is rejected. Only the first eligibility condition is evaluated before returning one.

With flags `0x00400001`, the first condition passes but the bit-22 condition fails. No explicit stores occur.

### Exact selector matching

With eligible flags and an otherwise valid count, selectors `0x300`, `0x500`, and `0x10000100` are rejected. Containing an accepted selector’s bits does not suffice.

### Null supplied address

With eligible flags, selector `0x100`, supplied address zero, and count one, the request is accepted and zero is stored into both address fields. No dereference or null-address rejection occurs here.
