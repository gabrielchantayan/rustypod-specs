# F-eb035a816079

## Purpose

F-eb035a816079 conditionally transfers a source range into a destination descriptor and returns the destination descriptor address.

The established behavior is a three-way choice between obtaining replacement storage, reusing storage while extending the destination range, and reusing storage without extension. Identical source and destination descriptor addresses bypass all processing.

The apparent intent is assignment of a sequence with 12-byte elements. That interpretation is inferred from the range operations, repeated multiplication by 12, and three-field descriptor updates. Element semantics, allocation guarantees, destruction behavior, and ownership transfer are not established by this function alone.

A significant observable detail is that the non-extending reuse path writes the destination’s third field to the newly calculated end, rather than preserving its previous value. The extending reuse path does not explicitly write that third field.

## Interface

**Inputs**

1. **Destination descriptor address.** A writable descriptor containing at least three consecutive machine-word fields.
2. **Source descriptor address.** A readable descriptor containing at least two consecutive machine-word fields, and satisfying whatever additional requirements the dependencies impose.
3. **First auxiliary unsigned value.**
4. **Second auxiliary unsigned value.**

**Output**

On every visible normal return, the result is the original destination descriptor address. There is no separate success flag, error code, or returned allocation address.

**Descriptor interpretation**

The supplied representation uses three consecutive 32-bit fields for the destination:

| Offset | Role in this function |
|---|---|
| 0 bytes | Base address or base-address encoding |
| 4 bytes | Current end address or end-address encoding |
| 8 bytes | Storage-limit address or storage-limit encoding |

The source’s first two fields are supplied to range-processing dependencies. The third source field is not directly accessed here, although dependencies may inspect it.

“Base,” “end,” and “storage limit” describe the apparent roles of these fields, not independently established validity guarantees. The function does not directly verify that they form ordered, aligned, accessible ranges.

**Widths and arithmetic**

The visible representation uses 32-bit signed fields and 32-bit unsigned quantities. Size and capacity comparisons are unsigned. The replacement-storage request is the selected capacity multiplied by 12 in unsigned arithmetic; on a 32-bit interpretation, this multiplication wraps modulo \(2^{32}\).

Growth calculations also use unsigned arithmetic. Endpoint calculations mix signed-looking field values with counts and multiplication by 12. The source representation alone does not establish a safe portable overflow interpretation for every such expression. Valid, non-overflowing address arithmetic is therefore a precondition for the ordinary sequence interpretation.

**Auxiliary inputs**

The two auxiliary values are copied into temporary storage for distinct descriptors, but those copies are replaced before any value derived from them is used for an allocation or descriptor update. They do not affect the visible result or dependency arguments in the displayed normal execution paths.

## Behavior

### 1. Identical descriptor addresses

The function first compares the two descriptor addresses.

If they are identical:

- No descriptor fields are explicitly read or written.
- No dependency is called.
- Neither auxiliary value affects processing.
- The destination descriptor address is returned.

This is address identity, not equality of contents or backing storage. Distinct descriptors referring to the same storage do not receive this bypass.

### 2. Initial size and capacity decision

For distinct descriptors, the first observable dependency calls are:

1. F-250da423e5f7 with the source descriptor.
2. F-ccb8260361ca with the destination descriptor.

Their returned values are compared as unsigned quantities.

The apparent interpretation is source element count versus destination capacity. The function itself does not prove those meanings.

If the destination query result is smaller than the source query result, processing follows the replacement-storage path. Otherwise, processing follows a reuse path.

The function does not retain a consistent snapshot of all descriptor sizes. It repeatedly invokes the queries. Results returned later, after intervening calls, are used where described below.

### 3. Replacement-storage path

#### Capacity selection

The function queries the source again through F-250da423e5f7, then queries the destination through that same dependency.

Let:

- \(S\) be this second source query result.
- \(D\) be this destination query result.
- \(M=2^{32}\).

The selected capacity is calculated as follows:

\[
A=(D+32)\bmod M
\]

\[
B=\left(D+\left\lfloor D/2\right\rfloor+\left\lfloor D/8\right\rfloor\right)\bmod M
\]

\[
C=\max(A,B,S)
\]

All comparisons selecting these values are unsigned. The right shifts correspond to division by two and eight for unsigned quantities.

This calculation is not saturation arithmetic. Overflow can make either growth candidate smaller than the original destination count.

#### Allocation and range processing

The function calls F-871e64ddc6de with:

- A byte-count argument equal to \((12C)\bmod M\).
- A second argument of zero.

It saves the returned value as the prospective replacement base.

There is no explicit null check, allocation-failure check, alignment check, or exception handler before the next operation.

The next dependency calls occur in this order:

1. **F-0d07845d70ac**, receiving the source’s then-current base and end fields, the saved replacement base, and the destination descriptor address.
2. **F-81a39c9757b1**, receiving the destination descriptor address and its then-current base and end fields.
3. **F-ccb8260361ca**, receiving the destination descriptor.
4. **F-ff1bdc376dcd**, receiving a saved destination base, the immediately preceding capacity-query result, and zero.

The destination base supplied to F-ff1bdc376dcd is read after F-81a39c9757b1 returns and before the capacity query. It is not reread after that query. Consequently, if the query changes the destination descriptor, the release-like call still receives the previously saved base.

The apparent intent is to populate new storage, dispose of the old range, and release old storage. These semantics remain conditional on the dependencies’ contracts.

#### Descriptor updates

After F-ff1bdc376dcd returns normally:

1. The destination base field is written with the saved replacement-base value.
2. F-250da423e5f7 is called with the source descriptor again.
3. The destination end is written as the destination’s then-current base plus 12 times that newly returned source count.
4. The destination storage limit is written as the destination’s then-current base plus 12 times the previously selected capacity \(C\).
5. The destination descriptor address is returned.

The base used for the final two calculations is reread after the final source query. It is not necessarily the allocation result if that query or another dependency has modified the descriptor through some other access path.

The source count used for the final end can differ from the source count used to select replacement capacity. There is no explicit check that it still fits.

### 4. Storage-reuse decision

When the initial destination query result is not smaller than the initial source query result, the function calls F-250da423e5f7:

1. With the destination descriptor.
2. With the source descriptor.

These new results, rather than the initial values, decide whether the destination must be extended.

### 5. Reuse while extending

If the newly queried destination count is smaller than the newly queried source count:

1. F-250da423e5f7 is called with the destination again. Its returned count defines the prefix boundary.
2. F-ac738f0c09a9 is called with:
   - The source’s current base.
   - That base plus 12 times the prefix count.
   - The destination’s current base.
3. F-250da423e5f7 is called with the source again.
4. The destination end is written as the destination’s current base plus 12 times that latest source count.
5. F-0d07845d70ac is called with:
   - The source’s then-current base plus 12 times the saved prefix count.
   - The source’s then-current end.
   - The destination’s then-current base plus 12 times the saved prefix count.
   - The destination descriptor address.
6. The function immediately returns the destination descriptor address.

The destination end is explicitly advanced **before** the suffix-processing call. If that call fails to return normally, the wrapper has already performed the end-field write.

The return value from F-ac738f0c09a9 is ignored on this path.

There is no explicit write to the destination storage-limit field on this path. That does not guarantee preservation: dependencies may modify it.

### 6. Reuse without extending

If the newly queried destination count is at least the newly queried source count:

1. F-ac738f0c09a9 receives the source’s current base and end and the destination’s current base.
2. Its return value is retained.
3. F-81a39c9757b1 receives:
   - The destination descriptor address.
   - The retained return value.
   - The destination’s then-current end.
4. F-250da423e5f7 is called with the source again.
5. An endpoint is calculated from the destination’s then-current base plus 12 times that latest source count.
6. The destination end is written with that endpoint.
7. The destination storage limit is written with the same endpoint.
8. The destination descriptor address is returned.

Thus, this path explicitly makes end and storage limit equal, even if the descriptor previously represented additional spare storage.

The value returned by F-ac738f0c09a9 is used as an opaque boundary argument. Its interpretation as the end of the processed destination prefix is inferred, not established locally.

## Side effects

**Direct writes**

For distinct descriptors, the wrapper can write the destination’s base, end, and storage-limit fields. The path-specific write order is:

| Path | Explicit descriptor write order |
|---|---|
| Identical descriptor addresses | None |
| Replacement storage | Base, then end, then storage limit |
| Reuse while extending | End only |
| Reuse without extending | End, then storage limit |

**Indirect effects**

The function invokes dependencies that may read or write element storage, inspect or mutate descriptors, allocate or release memory, or affect shared state. Their full side effects are unknown.

No assumption is made that a dependency preserves globals, leaves either descriptor unchanged, or operates only on explicitly supplied storage.

**Ownership**

The wrapper forwards an allocation result to a range-processing dependency and later stores that result in the destination descriptor. It also forwards a previously read destination base to a release-like dependency.

This establishes the order of handoff, not ownership guarantees. Allocation ownership, element lifetime, cleanup obligations, and the meaning of the release-like call require dependency contracts.

**Errors and interrupted execution**

There is no visible validation or recovery mechanism for:

- Invalid descriptor addresses or ranges.
- Overlapping source and destination storage.
- Allocation failure.
- Overflow or an undersized wrapped allocation request.
- Failure during range processing or cleanup.
- Changes to counts or descriptor fields between dependency calls.

If a dependency does not return normally, later calls, writes, and the final return are not established. No rollback behavior is visible.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Except for the identity example, they assume valid non-overlapping storage, ordinary count/capacity query meanings, stable descriptors during calls, successful range processing, and non-overflowing address calculations.

### Identical descriptors

If both descriptor arguments are the same address, the result is that address, with no dependency calls and no explicit descriptor accesses. Auxiliary values do not change this outcome.

### Replacement capacity

Suppose the destination count is 8, its capacity is 10, and the source count is 15 throughout processing.

The initial capacity comparison selects replacement storage. The growth candidates are 40 and 13, so the selected capacity is 40. The allocation request is 480 bytes with a second argument of zero.

After successful dependency execution, the destination base is the replacement base, its end is 180 bytes beyond that base, and its storage limit is 480 bytes beyond it.

### Source count larger than growth candidates

Suppose the destination count is 8, its capacity is 10, and the source count is 100.

The selected capacity is 100 rather than 40. The allocation request is 1,200 bytes. With stable inputs and successful dependencies, both end and storage limit become 1,200 bytes beyond the replacement base.

### Reuse with extension

Suppose the destination count is 2, its capacity is 8, and the source count is 5.

The prefix operation receives a 24-byte source prefix. The destination end is then written 60 bytes beyond its base, before the suffix operation processes the remaining source range.

The wrapper does not explicitly change the storage limit.

### Reuse without extension

Suppose the destination count is 7, its capacity is 10, and the source count is 3.

The full source range is passed to F-ac738f0c09a9. Its return value becomes the start boundary supplied to F-81a39c9757b1.

After successful processing, the wrapper sets both destination end and destination storage limit to 36 bytes beyond the current destination base. Preserving capacity 10 would not match the explicit writes on this path.

### Unsigned growth wrap

Suppose replacement-path queries produce destination count \(2^{32}-1\) and source count 1.

The two wrapped growth candidates are 31 and 2,684,354,557. The latter is selected. Multiplication by 12 produces a wrapped allocation argument of 2,147,483,612.

This establishes arithmetic behavior only. Such values do not establish a valid descriptor, usable allocation, or safe endpoint arithmetic.

## Uncertainties

The following remain **documented_only**:

- Dependency implementations, including whether they preserve descriptors or shared state.
- Element type and lifecycle semantics beyond the visible 12-byte stride.
- Exact allocation and release ownership rules.
- Validity requirements for null, empty, malformed, or overlapping ranges.
- Allocation-failure and partial-processing behavior.
- Whether any external synchronization guarantees stable descriptors.
- The rationale for replacing storage limit with end on the non-extending reuse path.
- Portable interpretation of overflowing signed-looking endpoint calculations.
- Behavior when query results change enough to invalidate an earlier branch decision or selected capacity.

The sequence-assignment interpretation is inferred intent. It must not replace the explicit call ordering, repeated queries, or descriptor writes specified above.
