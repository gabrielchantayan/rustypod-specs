# F-0167d0317c8a

## Purpose

F-0167d0317c8a performs two ordered memory updates: it writes an 8-bit value of one at offset two from a location selected through global state, then writes its supplied 32-bit value to a second location selected through global state.

The established behavior is a pair of stores. Interpreting the first store as setting a readiness, validity, or notification flag is inferred intent only. No such meaning is established by the supplied evidence. In particular, the first store occurs **before** the argument store, so the function does not establish a “write the payload, then publish readiness” sequence.

There are no visible branches, loops, explicit checks, or dependency calls.

## Behavior

### Established operation sequence

The source-level order is:

1. Obtain the base address through the first locator.
2. Write the 8-bit value one at offset two from that base.
3. Obtain the payload destination through the second locator.
4. Write the supplied 32-bit argument to that destination.
5. Return without a value.

This ordering matters when the first store changes memory that influences the second locator. The contract does not treat both destination addresses as having been captured at entry.

The offset of two applies to the first destination address. It is not an adjustment to the argument, an offset into the second destination, or a count of repeated writes.

### First update

The first update assigns the byte value one. It is not a read-modify-write operation on the destination byte.

Consequently, the previous byte value is not preserved:

- A previous zero becomes one.
- A previous one remains one in value, although the store is still present.
- Any other previous byte value becomes one.

This is not equivalent to setting one bit while preserving the remaining bits. At the represented memory-operation level, the assigned byte is exactly one.

The evidence establishes a one-byte destination access. It does not establish the layout or meaning of any containing structure, nor does it identify fields at neighboring offsets.

### Second update

The second update assigns the complete 32-bit input value to the selected payload destination.

There is no visible conditional treatment of zero, high-bit-set values, or any other payload pattern. There is no visible comparison with the old destination contents and no visible requirement that the value change.

The function does not explicitly read the previous payload value. It does not merge the argument with that value, increment it, mask it, or return it.

The byte order used to represent the 32-bit value in memory is not established by the supplied source alone. A byte-level expectation for this store must therefore be conditional on the target’s representation.

### Overlapping destinations

No non-overlap check is present.

If the marker destination lies within the four-byte payload destination, the payload store occurs later. Under ordinary writable-memory semantics, its final bytes determine the overlapping region. The marker byte is not guaranteed to remain one after completion.

If the marker destination overlaps storage used by the second locator, the first store may change the destination selected for the subsequent payload write. The second destination must therefore be understood using the locator state after the first store.

The source does not establish whether either overlap is possible in an actual deployment. These are conditional consequences of the visible ordering, not assertions about the program’s concrete memory layout.

### Repeated calls

### Marker already equal to one

### Marker overlaps the payload
