# F-e96ad6ec3695

## Purpose

F-e96ad6ec3695 specifies a context-dependent sequence of memory modifications, conditional record construction, memory traversal, and four indirect calls. No application-level purpose is established.

The supplied static representation contains rejected-instruction boundaries and reports omitted control-flow regions. It does not establish a complete, normally returning function. This contract describes the visible operations conditionally: execution must reach each operation, and preceding accesses and calls must permit continuation.

Three evidence categories apply:

- **Established static evidence:** represented value transformations, explicit access widths, address calculations, branch conditions, ordering, and call-result forwarding.
- **Inferred intent:** descriptive roles such as “context,” “descriptor,” and “record.” These names do not establish application semantics.
- **Documented-only unknowns:** undeclared global access widths, executable validity, ABI details, dependency behavior, ownership, and behavior outside the visible representation.

No runtime tests have been performed.

## Behavior

### Initial reads and writes

The descriptor address is read from context offset `+0x08`, followed by the payload at `+0x10`. Both reads precede the following stores:

| Order | Destination | Width | Value |
|---:|---|---:|---|
| 1 | Descriptor `+0x2a` | 16 bits | Top byte converted through a character-sized value |
| 2 | Address equal to signed top-byte value | 32 bits | Signed top-byte value |
| 3 | Same address `+0x04` | 32 bits | Descriptor address |
| 4 | Same address `+0x08` | 32 bits | Address Frame `+0x324` |
| 5 | Same address `+0x0c` | 32 bits | Descriptor address arithmetically shifted right by eight |
| 6 | Same address `+0x10` | 32 bits | Captured context payload |

The first store depends on unresolved character signedness. For top bytes below `0x80`, the halfword value is unambiguous. For top bytes at or above `0x80`, sign extension and zero extension differ.

Only after these stores are the descriptor’s working address, working quantity, and auxiliary quantity read, in that order. These are post-write observations. Aliasing with earlier destinations can change the values used subsequently.

### Zero-quantity adjustment

If the initial working quantity is zero:

1. The working address is increased by the signed top-byte value.
2. The descriptor’s first word is read as an address.
3. A 32-bit value is read through that address.
4. The auxiliary quantity becomes the fetched value minus the signed top-byte value.
5. The working quantity becomes the adjusted working address logically shifted right by 16.

This adjustment occurs at most once. A replacement quantity of zero does not repeat it. A nonzero initial quantity skips the dereference through descriptor offset zero.

After either outcome, an explicit byte store writes the descriptor’s top byte at the signed-top-byte address plus `0x0d`. This overlaps the earlier explicit word store at offset `0x0c`. Character signedness does not change the eight bits written here.

### Stack-derived setup and zero-address alternative

The address Frame `+0x324`, interpreted as signed 32-bit, is arithmetically shifted right by 20. Call the result the **frame quotient**.

The destination base is initially the frame quotient minus four. An explicit byte store then writes the low byte of the address Frame `+0x324` at the frame quotient plus nine. The first-call address component is initially Frame `+0x248`.

The current working address is tested for zero after any zero-quantity adjustment.

A zero working address selects this alternative:

- The destination base becomes Frame `+0x244`.
- A value from fixed address `0x0860b35c`, converted to a character-sized value, is written by an explicit byte store at the original signed-top-byte address plus `0x0d`. Its source access width is unknown.
- The signed top-byte working value is multiplied by sixteen for later calculations.
- The first-call address component becomes the arithmetic right shift by eight of the complete difference between the incoming word at Frame `+0x264` and sixteen times the frame quotient.
- The working address becomes the new destination base plus the multiplied top-byte working value.
- The auxiliary quantity becomes that address logically shifted right by 20.
- The working quantity is replaced by the incoming word at Frame `+0x1e8`.

The subtraction precedes the shift. Shifting only the incoming word before subtracting would specify different behavior.

### Main selection and record construction

Further processing requires the working address, arithmetically shifted right by 28, to be nonzero. Equivalently, at least one of its upper four bits must be set. This is not merely a negative-address test.

If the upper nibble is clear, the visible path reaches its final rejected-instruction boundary without the remaining operations.

Otherwise, an explicit 16-bit store writes the low half of the working quantity at destination base `+0x24`. The incoming word at Frame `+0x264` then selects two alternatives.

**Zero incoming word:** an explicit zero-byte store occurs at the address formed by adding Frame `+0x254` to the signed 32-bit interpretation of the address Frame `+0x210`. The path then reaches its final boundary. This address calculation must not be replaced by an assumed bounded stack access.

If the address Frame `+0x210` equals zero, this path reaches an immediate rejected-instruction boundary before record construction or the assignment at fixed address `0x5a`.

### Fixed-address gate and traversal

Next, the value associated with fixed address `0x22` is compared with zero. Its read width is unknown.

A nonzero value leads to rejected instruction data. The assignment at `0x5a` and pointer-slot assignment precede that boundary; traversal and calls do not occur.

For a zero value, traversal starts with zero unless the address Frame `+0x160` itself equals zero. That exceptional address condition selects these changes, in order:

- The arithmetic right shift by eight of Frame `+0x2c2` is assigned to the object at `0x7e`; destination access width is unknown.
- The pointer slot is assigned zero.
- The traversal value becomes `0x280`.

Another read follows exactly when signed 32-bit addition of `0x7e` to the fetched value would overflow. Continuation therefore occurs for fetched bit patterns from `0x7fffff82` through `0x7fffffff`, inclusive. The tested sum does not replace the traversal value.

### Global assignment, indirect calls, and final stores

After traversal terminates, the value associated with `0xa9` is assigned to the object at `0x3c`. Neither access width nor any conversion between those objects is established.

Next, a value associated with `0x0860b77c` supplies the operand of a left shift by four. The result is retained as a 32-bit working value. The source access width and exact source-type semantics are not independently established.

1. At `0x440000`.
2. At `0x220000` plus the retained value arithmetically shifted right by eight.

The visible continuation uses the retained shifted value rather than rereading `0x0860b77c`. This does not independently prove a machine-level callee-preservation convention. A rejected-instruction boundary follows.

## Acceptance examples

These are conditional static cases, not executed tests. Each assumes preceding operations complete and unspecified aliasing does not alter the stated conditions.

1. **Descriptor top byte `0x80`.** The signed top-byte value is −128, used as address `0xffffff80`. The descriptor halfword remains character-signedness-dependent. The later explicit top-byte store writes `0x80`.

2. **Initial working quantity zero.** Address adjustment and the descriptor-offset-zero dereference occur once. A replacement quantity of zero does not repeat the adjustment.

3. **Initial working quantity nonzero.** That dereference is skipped. The initial auxiliary quantity remains applicable unless the zero-address alternative replaces it.

4. **Zero-address alternative, frame quotient one, incoming word `0x100`.** The first-call component is obtained by shifting `0xf0` right by eight, giving zero. Subtracting sixteen after shifting `0x100` would not satisfy the contract.

5. **Working address `0x0fffffff`.** The main branch is skipped. Address `0x10000000` instead selects it despite being nonnegative.

6. **Main branch and zero incoming word.** The destination halfword store precedes the calculated zero-byte store. Record construction, traversal, and calls are not reached.

7. **Negative combined word.** Record stores are skipped. The subsequent assignment at `0x5a` still receives the 16-bit-converted value if the earlier stack-address boundary was not selected. Its actual write width remains unknown.

8. **Nonzero gate value at `0x22`.** The assignment at `0x5a` and pointer-slot assignment have occurred. No traversal read or call follows. This case makes no byte-width claim about the gate read.

9. **Exceptional traversal setup.** If Frame `+0x160` equals zero and the gate permits continuation, the assignment at `0x7e` precedes traversal’s first explicit 32-bit read at `0x284`. The assignment’s destination width remains unknown.

10. **Traversal threshold.** A fetched value of `0x7fffff81` terminates traversal. A fetched value of `0x7fffff82` requires another read at that value plus four.

11. **Traversal completes.** The value flow from `0xa9` to `0x3c` precedes the shifted-value calculation and first call. Neither global access may be required to be 32-bit without additional declarations.

12. **All dependencies return.** Three explicit byte stores occur, including two to the repeated destination. No normal function return is established afterward.
