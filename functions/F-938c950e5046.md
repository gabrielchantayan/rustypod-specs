# F-938c950e5046

The recovered behavior establishes three essential actions:

1. Preserve a 32-bit value from shared storage.
2. Invoke F-283eda65a14c with a value obtained from that same storage.
3. If the dependency returns a non-null address, invoke an indirect target selected through the returned object, passing both the object address and the preserved value.

The object-and-table structure suggests a virtual-operation wrapper, but that interpretation is inferred intent, not an established interface designation. The evidence does not identify the operation’s domain, the meaning of the shared value, or the responsibility of either dependency.

## Behavior

The wrapper first preserves the value obtained from the shared storage location.

It then evaluates that storage location for the argument to F-283eda65a14c and invokes that dependency once.

The preserved value and the dependency argument have distinct roles. If both evaluations observe the same value, the dependency and subsequent indirect target receive matching shared-value inputs. If an allowed intervening change causes the evaluations to differ, the dependency receives the later evaluation while the indirect target receives the earlier preserved value.

No claim is made that such an intervening change is possible under the actual memory model. The evidence does not describe volatility, atomicity, synchronization, or concurrent access. The distinction records the recovered evaluation structure without assuming a concurrency mechanism.

### Null-result path

After F-283eda65a14c returns, the wrapper compares its result with null.

If the result is null:

- The wrapper returns normally.
- It does not read an object header through that result.
- It does not read a dispatch-table entry.
- It does not perform the indirect invocation.

The dependency has already been invoked on this path. Its effects are not reversed, and null is not converted into an explicit error result.

### Non-null dispatch path

If the dependency result is non-null, the wrapper proceeds in this order:

1. Read the initial word at the returned address and interpret it as a table base.
2. Read the indirect target at byte offset 20 from that base.
3. Invoke that target with the returned address as the first explicit argument and the previously preserved 32-bit value as the second.

The object-header and target reads occur after the dependency has returned. Consequently, changes made by F-283eda65a14c to the returned object or associated table can affect dispatch. The wrapper does not establish a pre-call snapshot of those structures.

The wrapper does not re-read the shared storage location to construct the second indirect-call argument. A change to that storage during F-283eda65a14c does not, by itself, replace the preserved value.

If the indirect target returns normally, the wrapper then completes normally. No subsequent semantic action or explicit use of an indirect-call result is shown.
