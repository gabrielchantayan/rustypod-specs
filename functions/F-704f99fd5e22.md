# F-704f99fd5e22

## Purpose

F-704f99fd5e22 coordinates lookup of an object, conditional replacement of two caller-supplied 16-bit values, an optional 32-bit field copy, and subsequent processing.

The visible behavior is not transactional. Output writes precede the processing calls that determine the returned status. A nonzero processing result does not cause this function to restore earlier outputs.

A null lookup result leaves the pending status at decimal 82. A non-null lookup result containing a zero object address selects a dependency marked as non-returning in the supplied static representation.

The apparent intent is to replace unspecified input values with object-derived values before processing the selected object. The domain meanings of those inputs, the shared comparison value, and the processing operations are not established.

## Interface

The supplied representation exposes five inputs and a 32-bit integer return value.

| Input | Representation | Established use |
|---|---|---|
| Context | 32-bit integer carrying an address-like value | Passed to lookup and processing dependencies; used to form an address at byte offset `0x2AC`. |
| Selector | Opaque 32-bit value | Forwarded to lookup without visible interpretation. |
| First value location | Pointer to an unsigned 16-bit quantity | Read for lookup, reread after successful lookup, and conditionally overwritten. |
| Second value location | Pointer to an unsigned 16-bit quantity | Read for lookup, reread after successful lookup, and conditionally overwritten. |
| Optional output location | Nullable pointer to a 32-bit quantity | Receives a 32-bit object field when non-null and execution reaches output handling. |

The pending status and return value use the represented 32-bit signed integer type. Lookup failure returns 82 on normal completion. Other statuses come from processing dependencies.

Lookup returns either null or a handle identifying a cell containing an object address. The supplied representation reads that cell as a 32-bit integer and uses its contents as an address. The handle itself and the object it references are distinct storage.

The relevant object layout is:

| Byte offset from the currently read object address | Access width | Use |
|---|---:|---|
| `0x0C` | 16 bits | Source for the first replacement |
| `0x0E` | 16 bits | Source for the second replacement |
| `0x10` | 32 bits | Source for the optional output |

A shared comparison value also participates. Its declaration is absent. Its storage width, signedness, and exact type are therefore unknown.

A separate retained value is explicitly represented as unsigned 32-bit. Immediately after lookup, the shared value is assigned to that retained representation. This establishes the destination’s width and unsigned interpretation, not the shared value’s storage width or the width of its memory access. If the shared value has an integer type, its conversion to the retained unsigned 32-bit representation follows conversion to that width, including reduction modulo \(2^{32}\) where applicable.

### Validity requirements

Both 16-bit input locations must support reads during lookup argument preparation. On a successful lookup path, they must support subsequent reads and any selected writes.

The optional output may be null. If non-null and reached, it must support a 32-bit write.

A non-null lookup handle must support each address-cell read that execution reaches. Each object address subsequently obtained must support the selected field accesses. The initial nonzero check does not validate future address-cell contents.

The context must be suitable for all dependency-specific uses, including the address derived by adding `0x2AC`.

No visible checks establish pointer validity, alignment, object lifetime, or non-overlap. Invalid accesses have no visible recovery path. Address-overflow rules and the behavior of invalid address formation remain unresolved rather than being assigned wraparound semantics.

## Behavior

### Entry and lookup

The function initializes its pending return status to 82, or `0x52`.

It first calls an unidentified entry-side dependency with the context-derived address at offset `0x2AC`. Its result is not used to select success or failure. If it returns normally, execution proceeds.

F-80ad8bf07735 is then called with:

1. The context.
2. The selector.
3. The unsigned 16-bit value read from the first location.
4. The unsigned 16-bit value read from the second location.

Both value reads occur in preparation for lookup. Their relative evaluation order is not established by the supplied expression.

After lookup returns, the function obtains the shared comparison value and converts it into the retained unsigned 32-bit value. This happens before testing whether the returned handle is null. Consequently, even a lookup miss reaches this shared-value access.

No preservation guarantee is established for lookup. It may have changed caller storage, shared state, or the context. Lookup receives the values read for its arguments; later replacement decisions use fresh reads of caller storage.

### Null lookup handle

When lookup returns null:

- No direct output store is performed by this function.
- Neither processing dependency is called.
- The exit-side dependency is called.
- The pending status remains 82 and is returned if execution completes normally.

These statements concern this function’s direct behavior. They do not imply that entry, lookup, or exit dependencies leave caller-visible memory unchanged.

### Non-null handle and zero object address

For a non-null handle, the function reads the object address held in its cell.

If that address is zero, it calls F-a817d8d58c10 without visible arguments. The supplied static representation marks this call as non-returning. Under that model, output handling, processing, the normal exit-side call, and normal return are not reached.

The dependency implementation is unavailable. The mechanism of non-return—such as termination or a nonlocal transfer—is unknown. No recovery behavior is established for an unexpected return from this dependency.

### First replacement decision

For a nonzero object address, the function rereads the first unsigned 16-bit value and compares it with a fresh evaluation of the shared comparison value.

This comparison does **not** explicitly use the retained unsigned 32-bit copy. Because the shared value’s declaration is missing, the comparison’s complete conversion rules cannot be fixed from the supplied fragment.

In particular:

- The first caller value is known to originate from an unsigned 16-bit read.
- The other operand is the shared value in its undisclosed declared type.
- There is no visible explicit conversion of that shared operand to unsigned 32-bit for this comparison.
- There is no visible explicit truncation of it to 16 bits either.
- A full unsigned 32-bit comparison is established only under an additional type assumption that produces those comparison semantics.

The relative evaluation order of the caller-value read and the fresh shared-value evaluation within this comparison is not established.

If the comparison is equal, the function rereads the object address from the handle, reads the 16-bit field at offset `0x0C`, and writes that value to the first caller location. Otherwise, it performs no direct store to that location at this stage.

### Second replacement decision

After the first decision and any resulting store, the function rereads the second unsigned 16-bit value and compares it with the retained unsigned 32-bit value captured immediately after lookup.

Unlike the first comparison, this comparison has a known unsigned 32-bit retained operand. In the represented 32-bit integer model, the unsigned 16-bit input is compared by its numeric value against that full retained value. The retained operand is not truncated to 16 bits.

Thus, a retained value greater than 65535 cannot equal any possible second input value.

If equal, the function rereads the object address from the handle, reads the 16-bit field at offset `0x0E`, and writes it to the second caller location.

The second decision follows the first store, if any. Overlapping caller storage can therefore change the second value before its comparison. A change to the shared comparison storage after capture does not itself change the retained unsigned 32-bit value.

### Optional output

After both replacement decisions, the function checks the optional output pointer.

If non-null, it rereads the object address from the handle, reads the 32-bit field at offset `0x10`, and stores those bits to the optional output location.

This copy does not depend on either replacement comparison succeeding. If the pointer is null, this function does not perform this field read or output store.

### Processing and return

After output handling, F-ac83ba1267a4 receives the context and another read of the object address from the handle. Its returned status replaces the pending status.

If that status is nonzero, F-94c32ed4e255 is skipped.

If that status is zero, F-94c32ed4e255 is called with the context, and its returned status becomes the pending status. Zero from the first processing dependency therefore selects another operation rather than guaranteeing a final zero result.

The unidentified exit-side dependency is then called with the context-derived address at offset `0x2AC`. Its return value does not replace the pending status. If it returns normally, the function returns that pending status.

The visible normal-path order is therefore: entry operation, lookup, retained-value capture, handle-dependent output handling, selected processing calls, exit operation, return.

## Side effects

The selected direct output writes occur in this order:

1. A 16-bit write to the first value location.
2. A 16-bit write to the second value location.
3. A 32-bit write to the optional output location.

All occur before either processing call. There is no visible rollback following a nonzero status.

The object address is not captured once for the entire operation. The handle cell is read for the initial zero check, for each selected object-field access, and for the first processing call’s object argument. An earlier write that overlaps the handle can affect a later address read. The initial check alone does not ensure that later addresses are nonzero, unchanged, or valid.

Aliasing is neither checked nor visibly rejected. Relevant cases include:

- The two 16-bit locations designate the same storage.
- The optional output overlaps either 16-bit location.
- An output overlaps the shared comparison storage.
- An output overlaps the handle or object fields.

Such overlap can alter later comparisons, source values, or processing arguments. The optional output write is last among this function’s direct output writes, so it may overwrite earlier replacements.

No direct allocation, release, or object destruction is visible. The handle is not explicitly released by this function. These facts do not establish ownership transfer or imply that dependencies perform no allocation, retention, release, or destruction.

The entry and exit calls bracket normal execution. Synchronization or resource management is inferred intent only. Their placement does not establish mutual exclusion, protection against concurrent changes, or exceptional cleanup.

   Assume the shared value is unsigned 32-bit, remains 65536, and both inputs are zero. Neither comparison succeeds. The first uses the assumed unsigned 32-bit shared operand; the second uses the known unsigned 32-bit retained value. Neither comparison truncates 65536 to zero.
