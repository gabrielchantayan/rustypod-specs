# F-097e6ca37b4a

## Purpose

F-097e6ca37b4a processes one record in a stateful font-header parser. It dispatches comment handling, initializes an object, records header attributes, and can install a different record handler.

The apparent format is BDF. “Font name,” “size,” “bounding box,” and “pixel depth” are semantic interpretations supported by the visible labels and operations, not independently established format requirements.

The function is not a complete validator. It enforces two directive-order prerequisites but does not independently validate operand counts, numeric syntax, input-buffer bounds, or repeated directives.

Dispatch depends on results from F-7f14f1ab6851. Literal prefix matching is an interpretation of that dependency’s use. The supplied representation establishes its argument addresses, length arguments, call order, and selection of branches when its result is zero; its actual comparison semantics remain unknown.

## Behavior

### Entry snapshot and dispatch

Before any comparison, the function inspects the current object address. If nonzero, it saves the 32-bit value at object offset 16520; otherwise it saves zero. The name and properties allocations later use this entry snapshot, even if dependencies subsequently change the object or that field.

F-7f14f1ab6851 is first called with the input address, the address associated with `COMMENT`, and length argument 7. A zero result selects comment handling and bypasses all other directive dispatch.

After a nonzero result, the function reads flag 1:

- If clear, it enters initialization dispatch.
- If set, it attempts the properties, bounding-box, name-like, and size-like comparisons, in that order.

Recognized labels below identify comparison operands and branch meanings. They do not establish that F-7f14f1ab6851 performs literal byte-prefix comparison or requires keyword delimiters.

### Comments

On the comment branch, configuration offset 8 is read. Zero leaves the local result zero and performs no comment-processing call.

If enabled, the current object address is read. A zero address likewise leaves the result zero. Otherwise the function reads input byte 7:

- Zero selects input address plus 7 and input length minus 7.
- Nonzero selects input address plus 8 and input length minus 8.

Thus any nonzero byte at offset 7 causes one byte to be skipped; no whitespace test is visible.

F-4b1fb2933e65 receives the selected object address, adjusted input address, and adjusted length. Its status is returned.

The function does not verify that the input length covers byte 7 or either subtraction.

### Initialization

When flag 1 is clear, the function reads and saves parser-state offset 8248 **before** calling F-7f14f1ab6851 with the `STARTFONT` operand and length argument 9.

This resource read occurs even if the comparison subsequently returns nonzero. Such a result returns 176; the resource snapshot itself causes no local state write.

A zero comparison result initiates the following ordered changes:

1. Replace flags with 1.
2. Read the initialization-size global.
3. Clear the current object slot.
4. Call F-3ce007b692cc with the earlier resource snapshot, the loaded size, and a writable status location.

A nonzero status stops initialization. The flag replacement and object-slot clearing remain visible unless dependencies have changed them.

On zero status, the returned address becomes the current object. The function then reads the unknown object-field-offset global and writes a **freshly read** value from parser-state offset 8248 into that object-relative field. It next clears offset 8248.

The fresh value installed in the object need not equal the saved resource: either the comparison or allocation dependency may have changed the resource slot. Subsequent initialization calls continue using the earlier snapshot.

F-25fc36c1f916 receives the newly allocated address plus 16532 and the saved resource. On success, the registration-table base global is captured.

The function then makes 83 ordered calls to F-c33185036507, for indices 0 through 82. Each receives:

- A 32-bit value read from the next table entry.
- The index.
- The original allocation’s address plus 16532.
- The saved resource.

Entries are 16 bytes apart. The base is captured once, but entry values are read as the loop advances, not snapshotted together. A dependency can therefore affect a later entry before its read. The first nonzero registration status returns immediately.

After all registrations succeed, F-3ce007b692cc is called with the saved resource and size 16. Its returned address is written to offset 128 of the object **currently referenced by parser state**, before its status is tested.

### Size-like directive and depth normalization

The final comparison uses another unavailable four-byte operand, apparently associated with `SIZE`, and length argument 4. A nonzero result returns 3.

- A count other than exactly 5 causes a 16-bit value of 1 to be stored at object offset 16518.
- Exactly 5 causes token-vector slot 4 to be converted by F-b9ad687f6e4d. Its low 16 bits are stored at offset 16518.

Normalization operates on the saved unsigned 16-bit conversion result. Its highest set-bit position is used; zero retains position zero. The comparison value is the corresponding power of two for positions below 4, or 8 otherwise.

If the original value differs from that comparison value, the function stores twice the comparison value at current-object offset 16518. Only after this replacement does it read the signed 32-bit control field at the captured diagnostic base plus 220. A value greater than 1 triggers F-4457a9a44a68.

Consequently:

- 1, 2, 4, and 8 require no replacement.
- 0 becomes 2.
- 3 becomes 4.
- 5–7 become 8.
- 9–65535 become 16.

An original value of 16 still takes the replacement and conditional-warning path: it is compared with 8 and rewritten as 16.

Flag 4 is set after depth processing. The warning introduces no local nonzero status.

## Side effects

Changes are incremental. Failure can leave counts, allocation results, converted fields, cleared resources, or initialization flags installed without a corresponding completion bit.

No explicit release operation is visible. Repeated name-like or properties processing overwrites stored addresses without a visible local release. Dependencies may nevertheless allocate, release, or retain memory; their ownership rules are unknown.

Clearing the resource slot after installing its fresh value establishes a storage transition, not proof of ownership transfer.

Dependencies are not assumed to preserve shared state or globals. In particular:

- The entry context and initialization resource snapshot are distinct saved values.
- Initialization registration uses the original allocation’s embedded-region address.
- Many later stores reload the current object through parser state.
- Global values are read at the points described above, not treated as immutable constants.

On an error path, a completion bit may already have existed. “Not set by this path” does not mean it is cleared.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless explicitly varied, dependencies return the stated results without changing unrelated shared state, and all reached accesses are valid.

1. **Disabled comment processing:** A zero first comparison result and configuration offset 8 equal to zero produce result zero without F-4b1fb2933e65. The entry context snapshot has already occurred.

2. **Comment byte skipping:** With processing enabled and an object present, any nonzero byte at input offset 7 selects address plus 8 and length minus 8.

3. **Failed initialization comparison:** With flag 1 clear, offset 8248 is read before the initialization comparison. A nonzero result returns 176 even if that dependency changes the slot.

4. **Distinct initialization resources:** Suppose the saved resource is A and allocation changes offset 8248 to B. On allocation success, the unknown object field receives B and the slot is cleared; initialization dependencies receive A.

5. **Late initialization globals:** The size global is read after flags become 1 but before the object slot is cleared. A table-base change before successful embedded initialization completes affects the subsequently captured base; a later base-global change does not replace that capture.

6. **Interrupted registration:** Failure at index 12 means calls for indices 0–12 occur in order; later registrations and the 16-byte allocation are not reached.

7. **Properties allocation error:** Both count stores and the offset-80 address store precede the error return. This path does not set flag 16 or write the handler slot.

8. **Handler-global mutation:** If the replacement-handler global changes before its read, the later value is installed after flag 16 is set.

9. **Bounding-box arithmetic:** Height 10 and vertical offset −3 produce derived values 7 and 3. Height 32767 and offset 1 produce low-16-bit sum 32768.

10. **Name postprocessing failure:** After zero allocation status, the unidentified external call occurs with the three specified arguments. A subsequent nonzero postprocessing result returns without locally setting flag 2; no successful byte copy is presumed.

11. **Depth count and warnings:** Token count 6 stores depth 1. With count 5, raw low-16-bit values 0, 3, 8, 16, and 17 yield 2, 4, 8, 16, and 16. The diagnostic base is read in all five cases; its control field is read in all except the raw-8 case.
