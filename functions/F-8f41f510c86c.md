# F-8f41f510c86c

## Purpose

F-8f41f510c86c conditionally combines three 32-bit input words through one of two arithmetic dependency paths, then conditionally negates the resulting word. It also has an identity shortcut and a fixed-result fallback.

The apparent intent is a signed multiply-and-divide operation using magnitude arithmetic, a half-divisor adjustment, and a wider intermediate when required. That interpretation is **inferred intent**, not an established end-to-end arithmetic guarantee: the supplied evidence does not define the arithmetic semantics of the dependencies.

The established contract therefore describes path selection, intermediate values, dependency arguments, and final sign handling without assuming that a dependency performs division, addition, rounding, overflow detection, or saturation.

## Interface

The function accepts four 32-bit words:

| Input | Established role |
|---|---|
| First input | Participates in the identity shortcut, magnitude arithmetic, and final sign selection. |
| Second input | Compared with the third input for the identity shortcut; otherwise participates in magnitude arithmetic and final sign selection. |
| Third input | Participates in the identity shortcut, magnitude-based path selection, dependency arguments, and final sign selection. |
| Fourth input | Copied into temporary storage on the narrow arithmetic path. It is not explicitly passed as a dependency argument or directly used in the returned arithmetic. |

The result is one 32-bit word.

The same input bits are interpreted in different ways:

- Equality checks compare complete 32-bit words.
- Sign checks interpret a word as signed two’s-complement.
- Negation and the exposed unsigned arithmetic operate modulo \(2^{32}\).
- Selected comparisons use signed interpretation.
- The wide-product construction uses unsigned 16-bit halves and unsigned carry information.

The caller supplies no explicit pointer, buffer length, or ownership-bearing object. No input allocation or ownership transfer is established.

A global 32-bit threshold participates in path selection. Its value, initialization, permitted range, and synchronization rules are not supplied.

## Behavior

### 1. Identity shortcut

Before magnitude conversion or threshold-dependent processing, the function checks:

- whether the first input is zero; or
- whether the second and third inputs are equal.

If either condition holds, it immediately returns the first input unchanged.

This shortcut bypasses all dependency calls and final sign adjustment. In particular:

- A zero first input returns zero regardless of the other inputs.
- Equal second and third inputs return the first input even when both are zero.
- A negative first input is returned with its original bit pattern when the second and third inputs match.
- The fourth input has no established effect on this shortcut.

### 2. Magnitude-word construction

Otherwise, the function constructs a magnitude word for each of the first three inputs.

For a word whose signed interpretation is nonnegative, the magnitude word is unchanged. For a word whose signed interpretation is negative, the magnitude word is its modulo-\(2^{32}\) negation.

Ordinary negative signed values consequently become positive magnitude words. The exceptional input word `0x80000000` remains `0x80000000`. Its signed interpretation remains negative; it must not be treated as a positive signed magnitude in later comparisons.

For the remainder of this contract, the first, second, and third magnitude words are called the first magnitude, second magnitude, and divisor magnitude respectively. “Divisor” names an apparent role, not a proven dependency operation.

The function also prepares a half-divisor word using a signed arithmetic right shift of the divisor magnitude by one bit.

For a positive divisor magnitude, this equals the integer floor of half that magnitude. For `0x80000000`, the prepared word is `0xC0000000`; it is not the unsigned half `0x40000000`.

### 3. Threshold classification

Under a consistent value of the global threshold, the threshold-controlled branch treats the operands as small exactly when both of these signed comparisons hold:

- first magnitude is less than or equal to the threshold;
- second magnitude is less than or equal to the threshold.

The source reaches this result through an intermediate selection and signed subtraction/overflow tests rather than a direct pair of comparisons. The signed interpretation is material: `0x80000000` compares as negative.

The threshold appears in multiple expressions. The supplied evidence does not establish a single atomic threshold snapshot or behavior under concurrent modification. The simplified classification above is conditional on those observations being consistent.

### 4. Path selection

There are three non-shortcut outcomes.

**When both magnitudes satisfy the threshold classification:**

- A divisor magnitude with signed value at least `0x0002AFE0` selects the wide path.
- A divisor magnitude with signed value from 1 through `0x0002AFDF` selects the narrow path.
- A divisor magnitude with signed value zero or less selects the fixed-result fallback.

**When the magnitudes do not both satisfy the threshold classification:**

- A strictly positive signed divisor magnitude selects the wide path.
- A divisor magnitude with signed value zero or less selects the fixed-result fallback.

The lower-level divisor test contains an intermediate boundary at `0x0002A000`, but, for a consistent divisor magnitude, the actual wide-path boundary in the small-operands case is `0x0002AFE0`, or 176,096 decimal. There is no separate arithmetic path beginning at `0x0002A000`.

A third input of `0x80000000` produces a divisor magnitude that is negative under signed interpretation and therefore selects the fallback, unless the identity shortcut already returned.

### 5. Narrow arithmetic path

This path prepares one 32-bit argument by:

1. multiplying the first and second magnitude words, retaining the low 32 bits;
2. adding the prepared half-divisor word, again retaining the low 32 bits.

There is no explicit overflow rejection at this stage.

Before invoking the dependency, four temporary 32-bit words are populated with the original first, second, third, and fourth inputs, in that order. These are not the magnitude words.

The function then calls F-870c4fcf7295 with:

- the prepared 32-bit arithmetic argument;
- the divisor magnitude.

The returned 32-bit word becomes the candidate result for final sign handling.

The evidence does not establish how F-870c4fcf7295 interprets its first argument, whether its operation is signed or unsigned, or how it handles arithmetic exceptional cases. In particular, a wrapped intermediate must not be silently replaced in this contract by an unbounded mathematical product.

### 6. Wide arithmetic path

This path first constructs the full unsigned 64-bit product of the first and second magnitude words.

The construction uses 16-bit halves, cross-products, and carries. Its observable local representation consists of:

- a low 32-bit product word;
- a high 32-bit product word immediately following it.

A separate two-word temporary object contains:

- the prepared half-divisor word as its low word;
- zero as its high word.

The function then invokes F-bc5079bc5666 with three pointer arguments:

1. a pointer to the two-word product object;
2. a pointer to the two-word half-divisor object;
3. the same pointer as the first argument.

Thus, the first and third arguments alias exactly. Any valid interpretation of this call must allow for that aliasing; they are not independent input and output objects.

The dependency’s return value is not used. After it returns, the function obtains the high and low words from the product object and calls F-643f64d6dc60 with:

1. the current high word;
2. the current low word;
3. the divisor magnitude.

F-643f64d6dc60’s returned word becomes the candidate result.

The evidence establishes neither that F-bc5079bc5666 adds the two objects nor that F-643f64d6dc60 divides the resulting value. Those are plausible interpretations of the surrounding dataflow, not proven contracts.

In particular, the second call uses the product storage **after** the first dependency has had access to it. It must not be specified as necessarily receiving the original product.

### 7. Fixed-result fallback

When path selection rejects both arithmetic paths, the candidate result is `0x7FFFFFFF`.

No arithmetic dependency is called on this path. Final sign handling still applies.

This is an explicit fallback result, not evidence of a general saturation policy. The supplied body does not show a corresponding overflow check around dependency results.

### 8. Final sign handling

All non-shortcut paths converge on a final sign decision.

The function examines the sign bit of the bitwise exclusive-or of the original first, second, and third inputs. This bit is set exactly when an odd number of those inputs have their sign bits set.

- If that bit is clear, the candidate result is returned unchanged.
- If that bit is set, the candidate result is negated modulo \(2^{32}\).

The fourth input does not participate.

This sign adjustment applies equally to narrow-path results, wide-path results, and the fixed fallback. It does not depend on the candidate result being positive.

Consequences include:

- Negating zero still returns zero.
- Negating `0x80000000` returns `0x80000000`.
- The fallback can return either `0x7FFFFFFF` or `0x80000001`.
- A dependency result whose sign bit is already set is still subjected to the same bit-pattern negation rule.

## Side effects

The supplied body establishes these direct effects:

- Threshold-dependent processing reads a global threshold.
- The arithmetic paths write temporary local storage.
- The wide path exposes two local two-word objects to F-bc5079bc5666.
- Dependency calls occur in the order described above.

No direct global write, allocation, release, input-buffer mutation, logging, or external I/O appears in the supplied body.

That absence does not establish purity. The dependencies’ global writes, external effects, pointer retention, and ownership behavior are unknown.

The temporary objects are local storage. Their addresses are available during the wide-path dependency call; no valid post-return retention or ownership transfer is established. A dependency contract would be required before asserting that those addresses are not retained.

The narrow path also writes the fourth input into temporary storage. No explicit pointer to that storage is passed to its dependency. This supports “no direct result dependence is shown,” not an unconditional claim that the fourth input can never affect execution under every possible dependency or calling environment.

The evidence gives relative word layout for the two-word objects, but does not establish byte order or a portable external serialization.

## Acceptance examples

These are conditional static acceptance examples, not executed tests.

1. **Zero first input.**  
   First input zero, with arbitrary remaining words: return zero immediately. No dependency is called.

2. **Equal second and third inputs.**  
   First input `0xFFFFFFF9`, second and third inputs both zero: return `0xFFFFFFF9` unchanged. Do not apply the fallback or final sign logic.

3. **Small operands, positive divisor below the wide boundary.**  
   Assume a stable threshold of at least 3. Inputs 2, 3, and 4 select the narrow path. The prepared argument is 8: product 6 plus half-divisor 2. F-870c4fcf7295 receives 8 and 4. If it returns word \(R\), the function returns \(R\).

4. **Small operands at the boundary.**  
   Under a stable threshold admitting magnitudes 2 and 3, a third input of `0x0002AFDF` selects the narrow path. Changing it to `0x0002AFE0` selects the wide path.

5. **Threshold forces the wide path.**  
   Assume a stable threshold of 2. Inputs 3, 2, and 4 select the wide path. The initial product object contains low word 6 and high word zero; the adjustment object contains low word 2 and high word zero. The subsequent arithmetic result remains dependent on both dependency contracts.

6. **Zero divisor without shortcut.**  
   Inputs 1, 2, and zero do not meet the identity shortcut. They return the positive fallback `0x7FFFFFFF`, with no dependency call.

7. **Negative fallback.**  
   Inputs `0xFFFFFFFF`, 2, and zero return `0x80000001`: the fixed candidate is negated because the original inputs have odd sign parity.

8. **Exceptional divisor magnitude.**  
   Inputs 1, 2, and `0x80000000` select the fallback and return `0x80000001`. The divisor magnitude is not accepted as a positive signed value.

9. **Dependency result and sign parity.**  
   If an arithmetic path produces candidate 5, inputs with odd sign parity return `0xFFFFFFFB`; inputs with even sign parity return 5. This condition does not assert what arithmetic causes a dependency to produce 5.
