# F-e25f5a93732f

## Purpose

F-e25f5a93732f performs conditional dispatch for a node-like object using a caller-supplied context. It offers the object to an optional preliminary handler, then to one of two callbacks selected from the context’s dispatch table. If the selected callback returns zero, a further callback may be invoked for a particular relationship between the object and context.

The established behavior is an ordered sequence of eligibility checks, callback invocations, and early returns. A nonzero handler result terminates processing and is returned unchanged. Zero allows processing to continue where another eligible stage remains.

The interpretation of these stages as object processing, specialized handling, or fallback handling is inferred intent. The supplied evidence does not establish the application-level meaning of the object tags, callback slots, or return values.

## Interface

### Inputs

The function takes two inputs:

| Input | Role established by use |
|---|---|
| Context | Address of a structure whose first field supplies a dispatch-table address and whose field at byte offset 80 participates in a later comparison. |
| Object | Address of a structure whose 32-bit field at byte offset 4 controls dispatch and whose 32-bit field at byte offset 8 has a tag-dependent interpretation. |

The supplied representation uses integer-valued addresses for some accesses. The contract therefore describes byte offsets and 32-bit integer fields rather than asserting a portable native structure layout.

### Relevant layout

|---|---:|---|

| Object | 4 | 32-bit tag. This field is read at several separate stages. |

### Output

The return value is a 32-bit integer:

- A nonzero result from an invoked terminating handler is returned unchanged.
- Zero is returned if the selected primary callback returns zero and no final handler returns a nonzero result.

The function does not normalize nonzero values. Negative values and positive values are treated alike for continuation purposes.

A zero or nonzero result must not be described as success or failure without an external contract for the handlers. Here, zero means only that this function may continue processing.

### Preconditions

All memory accesses and indirect calls actually reached must be valid. In particular:

- The object must permit reading its field at byte offset 4.
- The context must permit reading its dispatch-table field when callback selection is reached.
- The selected dispatch-table entry must contain a callable target compatible with the two supplied arguments and integer return value.
- When the tag-22 branch is reached, the field at object offset 8 must supply an address that permits reading a 32-bit field at offset 4.
- When the final tag-15 comparison is reached, the object field at offset 8 and context field at offset 80 must be readable.
- If the final callback is required, dispatch-table offset 224 must contain a valid callable target.

There are no explicit null, bounds, alignment, or callback-presence checks. The function does not establish that either input may safely be null.

## Behavior

### 1. Preliminary eligibility and handling

The function first reads the object’s 32-bit tag at byte offset 4.

If that value is not 13, the preliminary dependencies are skipped.

If that value is 13:

1. F-468ee00d626a is called with the object as its only argument.
2. Its return value is compared with 111.
3. Only if the result equals 111 is F-6eaacb741065 called, with the context followed by the object.
4. A nonzero result from F-6eaacb741065 is returned immediately.
5. A zero result allows processing to continue.

The object tag is not rechecked between the two dependency calls. Thus, if F-468ee00d626a changes the object’s tag but returns 111, F-6eaacb741065 is still called.

The return value from F-468ee00d626a is an eligibility discriminator, not a propagated function result. Any value other than 111, including another nonzero value, merely skips F-6eaacb741065.

### 2. Primary callback selection

After the preliminary stage completes without an early return, the object’s tag at offset 4 is read again.

This is a fresh read. It is not necessarily the value observed before either preliminary dependency ran.

Selection then follows these rules:

- If the current tag is not 22, select the callback at dispatch-table offset 272.
- If the current tag is 22, read the address from object offset 8, then read the 32-bit tag at offset 4 of that related object.
  - If the related tag is 42, select dispatch-table offset 268.
  - Otherwise, select dispatch-table offset 272.

The related-object address and tag are not read on a non-22 branch.

After deciding which slot applies, the function reads the dispatch-table address from the context and obtains the callback from that slot. It then invokes the selected callback with the context followed by the original object.

The related object is used only for this selection. It is not substituted for the object argument passed to the callback.

If the callback returns nonzero, that exact value is returned immediately. The final eligibility check is skipped.

If the callback returns zero, processing proceeds to the final stage.

### 3. Final eligibility and handling

After a zero result from the primary callback, the function reads the object’s tag at offset 4 again.

If the current tag is not 15, it returns zero. It does not read the object’s field at offset 8 or the context’s field at offset 80 for the final comparison.

If the current tag is 15, the function:

1. Reads the 32-bit value at object offset 8.
2. Reads the 32-bit value at context offset 80.
3. Compares those values for equality.

If they differ, the function returns zero.

If they are equal, the function reads the context’s dispatch-table address again, resolves the callback at byte offset 224, and calls it with the context followed by the original object.

A nonzero callback result is returned unchanged. A zero callback result leads to a zero return.

### Read ordering and state visibility

The significant ordering is:

1. Initial object-tag read.
2. Any eligible preliminary dependency calls.
3. Fresh object-tag read for primary selection.
4. Conditional related-object address and tag reads.
5. Context dispatch-table read and selected primary callback lookup.
6. Primary callback invocation.
7. Fresh object-tag read for final eligibility, only after a zero primary result.
8. Conditional object comparison-field read, followed by context comparison-field read.
9. Fresh context dispatch-table read and final callback lookup, only after an equal comparison.
10. Optional final callback invocation.

These rereads matter when callbacks mutate state. For example, the primary callback can change the object to tag 15, change either comparison field, or replace the context’s dispatch table before returning zero. The final stage uses the subsequently read state.

This ordering describes the accesses established by the supplied representation. It does not establish atomicity, volatile semantics, synchronization, or safety under concurrent mutation.

### Call counts and termination

For a normally returning execution:

- F-468ee00d626a is called at most once.
- F-6eaacb741065 is called at most once.
- Exactly one primary callback is called unless the preliminary handler returns nonzero.
- The final callback is called at most once.
- At most four calls occur in total: the two preliminary dependencies, one primary callback, and the final callback.

There is no loop, retry, or recursive call established by the function itself. Behavior inside dependencies is outside this contract.

## Side effects

The function contains no direct stores to the supplied context, object, related object, or dispatch table. Its direct memory operations are reads.

Calls may nevertheless produce externally visible side effects. Neither dependency nor any indirect callback may be assumed to preserve:

- Object tags or payloads.
- The context’s comparison field.
- Dispatch-table contents or the context’s dispatch-table address.
- Global state.
- The validity or lifetime of referenced memory.

The function performs no explicit allocation, deallocation, reference-count adjustment, or ownership transfer. Passing an address to a dependency does not establish whether that dependency borrows, retains, consumes, or releases the referenced storage.

After any call that returns to a continuing path, all later required accesses must remain valid. For example, freeing the original object in the primary callback and returning zero would leave the subsequent tag read without a valid object unless some external lifetime rule prevents that situation.

No explicit error recovery, rollback, or cleanup appears. A handler may produce side effects before returning zero; the function does not undo them before trying a later stage.

An invalid access, invalid callback target, or nonlocal failure in a dependency is not converted into a defined error result here.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Each assumes valid memory, returning callees, and no mutations except those stated.

### Preliminary termination

Given an initial object tag of 13, F-468ee00d626a returns 111, and F-6eaacb741065 returns −7:

- Both dependencies are called in that order.
- The function returns −7.
- No primary or final callback is invoked.

### Discriminator mismatch

Given an initial object tag of 13 and a result of 112 from F-468ee00d626a:

- F-6eaacb741065 is not called.
- Primary selection proceeds using a fresh object-tag read.
- The value 112 is not returned merely because it is nonzero.

### Mutation during preliminary discrimination

Given an initial tag of 13, F-468ee00d626a changes that tag to 22 and returns 111, and F-6eaacb741065 returns zero:

- F-6eaacb741065 is called despite the changed tag.
- Primary selection observes tag 22.
- Selection between offsets 268 and 272 then depends on the related object’s current tag.

### Related-object specialization

Given a primary-selection tag of 22 and a related-object tag of 42:

- The callback at offset 268 is selected.
- It receives the original object, not the related object.
- If it returns 5, the function returns 5 without performing final eligibility reads.

With a related tag other than 42, offset 272 is selected instead.

### Default selection without related-object access

Given an initial tag of 8 and no intervening mutation:

- Neither preliminary dependency is called.
- The primary callback is selected from offset 272.
- The object’s field at offset 8 is not read for related-object selection.
- If the primary callback returns zero and leaves the tag at 8, the function returns zero without reading the final comparison fields.

### Final-stage activation by mutation

Given that the primary callback changes the object tag to 15, makes the object field at offset 8 equal the context field at offset 80, and returns zero:

- Final eligibility uses the changed state.
- The callback at offset 224 is invoked.
- Its nonzero result, if any, is returned unchanged.

If that primary callback also replaces the context’s dispatch-table address, the final callback is resolved from the replacement table.

### Final-stage mismatch

Given a zero primary result, a current object tag of 15, and unequal comparison fields:

- Both comparison fields are read.
- The final callback is not invoked.
- The function returns zero.

### All handlers decline

Given that every invoked handler returns zero:

- Eligible later stages are still considered.
- The function eventually returns zero.
- It does not retry any handler.
