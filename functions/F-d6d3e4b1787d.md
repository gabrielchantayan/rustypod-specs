# F-d6d3e4b1787d

## Purpose

F-d6d3e4b1787d conditionally modifies one byte in indirectly addressed storage. F-b7abcf60c990 supplies the gate: a zero result suppresses the local modification, while any nonzero result enables it.

Under an eight-bit destination interpretation, the modification replaces bit 2 with the lowest bit of the value input. Other contributing input bits can set destination bits 3 through 7; those bits are not cleared merely because the corresponding input bits are zero. Destination bits 0 and 1 remain unchanged.

**Inferred intent:** the function may be intended to control a flag. That interpretation does not restrict the value input to zero or one. The established behavior includes non-Boolean inputs and their effects on higher destination bits.

This contract is based on static evidence only. No runtime tests have been performed.

## Behavior

### Gate and observation boundary

The dependency receives the base-relative value at offset 96. Its result is used solely to distinguish zero from nonzero. Negative and positive nonzero results have the same enabling effect.

A zero result causes normal return without the local indirect-field access or byte assignment. This does not undo or suppress effects already performed by the dependency.

A nonzero result enables the local byte modification. Relevant storage is evaluated after the dependency returns; there is no established pre-call snapshot of the indirect-address field or old byte.

Consequently:

- A dependency change to the indirect-address field can redirect the subsequent modification.
- A dependency change to the destination byte can change the old value used by the modification.
- A dependency action that invalidates required storage can make subsequent accesses invalid, despite its nonzero result.

No preservation, purity, or lifetime guarantee is implied by the dependency’s gate role.

### Required byte relationship

The following bit-level contract assumes an eight-bit destination, defined input arithmetic, and a stable indirect address. Bit numbering starts at zero for the least significant bit.

| Destination bit or range | Required relationship |
|---|---|
| Bits 0–1 | Retain their old values. |
| Bit 2 | Equals input bit 0; its previous value is discarded. |
| Bits 3–7 | Remain set when previously set, and also become set when the corresponding input bit two positions lower is set. |

For nonnegative inputs with defined promoted arithmetic, input bits 0 through 5 can therefore contribute to the stored result. Higher input contributions do not survive conversion to an eight-bit destination.

Important consequences are:

- Zero clears destination bit 2 without clearing any other destination bit.
- One sets destination bit 2 without changing any other destination bit.
- Two can set destination bit 3 while clearing destination bit 2.
- Non-Boolean inputs are not normalized, rejected, or restricted to their lowest bit.
- Setting a higher destination bit is cumulative with its previous state; a zero input contribution does not clear it.
- Different inputs may produce the same stored byte because contributions above the stored width are discarded.

The enabled path expresses an assignment even when the resulting byte equals the old byte. This establishes a source-level assignment, not a mandatory distinct physical store.

### Access ordering and target stability

The dependency call completes before the conditional local accesses begin.

The indirect-address field participates separately in determining the old-byte location and the assignment destination. The evidence does not establish a single captured address shared by both uses. Nor does it establish which address expression is evaluated first.

With stable ordinary storage, both uses identify the same byte, so the result is an in-place modification satisfying the bit relationship above.

If the field changes between relevant evaluations, that same-location guarantee is unavailable. A value could be derived from one location and assigned through another address evaluation. This is a limitation on the contract, not a supported concurrent-update protocol.

The assigned value depends on the old-byte read. The relative timing of that read and evaluation of the assignment destination is not fully established. Exact machine load counts, store counts, and instruction ordering remain unknown.

### Arithmetic and representation boundaries

The address calculations use offsets 96, 100, and 396 without visible bounds or overflow checks.

For a signed 32-bit interpretation, each evaluated integer addition must stay within the signed 32-bit range to receive an ordinary defined-arithmetic interpretation. Neither wraparound nor recovery from overflow is established. A machine implementation might behave differently, but no such behavior is independently demonstrated here.

The value input’s signedness matters before destination conversion:

- With eight-bit characters and 32-bit integers, nonnegative values from 0 through 127 permit the relevant two-position upward shift without exceeding the signed integer range.
- If the character input is unsigned under that model, values through 255 also fit after the shift.
- If a high-bit character representation denotes a negative value, no portable result for the negative left shift is established by this evidence.

Destination truncation does not make an earlier invalid arithmetic operation valid. Negative-input behavior must therefore remain unresolved rather than being assigned an assumed low-byte result.

If destination storage is not eight bits wide, the eight-bit preservation table and examples are not an unconditional contract. The supplied byte-oriented representation supports that interpretation, but an independent type definition or ABI confirmation is unavailable.
