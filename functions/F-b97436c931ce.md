# F-b97436c931ce

## Purpose

F-b97436c931ce writes one four-byte value into storage described by a three-word control record. It either uses the initially recorded occupied end directly or enters a dependency-mediated path that selects replacement storage or backward shifting.

The apparent intent is insertion at the end of a contiguous collection of four-byte elements. That intent is inferred. The established behavior includes distinctions that a conventional append contract would hide:

- The initial branch tests address inequality, not available capacity or record validity.
- The insertion address is captured before dependency calls.
- Later operations reread selected control fields.
- The value source is read only when the insertion write is reached.
- Element destinations can alias the control record, changing fields beyond those explicitly assigned.
- Dependency preservation, memory ownership, and failure behavior are not established.

This contract describes the supplied static body, including malformed-state behavior where the operations are identifiable. It does not guarantee successful execution for arbitrary addresses.

## Interface

### Inputs and layout

The function accepts two addresses.

**Control-record address:** identifies three consecutive four-byte words:

| Byte offset | Contract name | Use |
|---|---|---|
| 0 | Storage base | Origin for offsets, traversal, and a release-like call |
| 4 | Occupied end | Initial insertion address and current extent |
| 8 | Storage limit | Initial branch comparison and capacity-related calculations |

These names describe observed uses, not enforced invariants.

**Value-source address:** identifies a readable four-byte word. The function does not snapshot this word on entry. Its eventual value can therefore depend on earlier record writes, storage writes, and dependency effects.

The representation uses 32-bit address-bearing words and four-byte elements. Pointer increments and decrements by one element correspond to four bytes. No byte-order conversion is shown; the operation transfers a four-byte word.

### Output

There is no explicit returned value. Observable results consist of:

- Control-record writes.
- Element-storage reads and writes.
- Dependency calls and their arguments.
- Dependency-defined effects.
- Abnormal completion or nontermination if an operation cannot complete.

### Requirements for ordinary successful behavior

Conventional collection behavior requires readable and writable control fields, suitable storage, valid source and destination addresses, meaningful address arithmetic, and dependencies that complete with compatible effects.

None of these requirements is validated comprehensively. In particular, the function does not establish:

- That base, end, and limit are ordered or aligned.
- That an unequal end and limit imply a writable slot.
- That the value source remains valid until its eventual read.
- That allocation succeeds.
- That dependencies preserve the record or globals.
- That element storage is disjoint from the control record.
- That concurrent mutation is safe.

## Behavior

### Initial observation and direct extension

The function captures the occupied-end address and compares that captured address with the storage-limit field.

If they differ, it performs these operations in order:

1. Writes the captured address plus four to the occupied-end field.
2. If the captured address is nonzero, reads the four-byte source word and writes it to the captured address.
3. Returns without calling a dependency.

The occupied-end update precedes the source read and destination write. Consequently, a source that aliases the occupied-end field supplies the updated field value, unless another applicable overlap changes it.

If the captured address is zero, the function writes four to the occupied-end field and skips both the source read and the element write.

There are no explicit assignments to the base or limit fields on this path. That does **not** establish that those fields remain unchanged: the element destination can overlap either field. Likewise, an element destination overlapping the occupied-end field can overwrite the end update.

Thus, “base and limit remain unchanged” applies only when the destination does not overlap those fields. “The final end is the captured end plus four” additionally requires that the element write not overwrite the occupied-end field.

The branch does not validate remaining capacity. An end numerically beyond the limit still selects this path whenever the two addresses differ.

### Initially equal end and limit

If the captured end equals the initially observed limit, the function next reads the base and limit, then calls F-ef3b831bc76c with the control-record address.

For branch selection, it subtracts the captured base from the captured limit, shifts that signed difference right by two bits, interprets the result as an unsigned 32-bit quantity, and compares it with the dependency result.

- If the derived unsigned quantity is less than or equal to the result, replacement processing follows.
- Otherwise, backward shifting follows.

The arithmetic is width-sensitive. A negative signed difference followed by a signed right shift is not equivalent to an ordinary nonnegative byte count divided by four. The final comparison is unsigned.

The comparison combines record values read before the call with a result returned by the call. It is not a fresh post-call snapshot. The dependency may have changed the record before the selected path begins.

### Replacement processing

#### Growth calculation

The function calls F-ef3b831bc76c a second time. This second result supplies two unsigned 32-bit growth candidates:

- The result plus 32.
- The result plus its unsigned half plus its unsigned eighth, with each fractional term obtained by a right shift.

The larger candidate is selected by unsigned comparison. A tie selects the second expression, with no numerical difference.

The additions are finite-width operations without an overflow check. The interpretation “add 32 elements or grow to approximately 1.625 times the count, whichever is greater” is valid only when the additions do not wrap.

The selected count is shifted left by two bits to form the byte request. Bits lost by this 32-bit shift are not recovered or checked.

#### Storage request and first range-like call

The function calls F-871e64ddc6de with the computed byte request and a second argument of zero. Its returned word is retained as the replacement base.

There is no explicit allocation-failure check before subsequent processing.

An unmapped dependency is then called with:

1. The base reread from the control record.
2. The insertion address captured on entry.
3. The replacement base.
4. The control-record address.

This resembles a prefix transfer, but the supplied evidence does not establish copying, moving, destruction, ownership transfer, record preservation, or global preservation.

#### Insertion write

After the first range-like call returns, the function rereads the base and calculates a destination by:

- Subtracting that current base from the captured insertion address.
- Clearing the low two bits of the resulting offset.
- Adding the replacement base.

For ordinary aligned storage, clearing the low bits leaves the offset unchanged. For other states, it changes the destination.

If the computed destination is nonzero, the function reads the value source and writes the four-byte word there. Otherwise, both operations are skipped.

The guard applies to the computed destination, not to the replacement base. A zero result from F-871e64ddc6de therefore does not necessarily suppress this write.

The source has not been captured earlier. Its value may reflect any preceding dependency effects or aliasing writes. The destination itself may overlap the control record, affecting subsequent field reads.

#### Second range-like call

The same unmapped dependency is called again with:

1. The insertion address captured on entry.
2. The occupied-end field reread from the record.
3. A destination calculated from the captured insertion address, the current base, and the replacement base using the same low-bit-cleared offset, then adding four bytes.
4. The control-record address.

The second destination is recalculated after the insertion write. It need not equal the previous destination plus four if that write altered the base field.

Under stable, conventional append assumptions, the source range described by the first two arguments is empty. The call nevertheless occurs.

The supplied expression does not establish a relative evaluation order among field reads used as arguments to this single call. Both occur after the insertion write and before the dependency executes.

#### Traversal, release-like call, and publication

The function calls F-ef3b831bc76c a third time and retains its result for the final occupied-end calculation.

It then reads the current base and advances an address cursor from that base in four-byte steps until it equals the occupied-end field. The loop body contains no element read, element write, or destruction call.

The loop tests the occupied-end field during traversal. No validation ensures that stepping by four reaches it. Unsuitable address relationships can prevent normal termination; exact consequences of signed address overflow are not fully established by the supplied representation.

After the loop, F-ff1bdc376dcd is called with:

1. The base retained before traversal.
2. The current limit minus that retained base, signed-shifted right by two.
3. Zero.

This resembles release of the prior allocation. Its actual ownership and failure semantics remain unknown.

Only after that call returns does the function publish these three four-byte record writes, in order:

1. Base becomes the replacement base.
2. Occupied end becomes the replacement base plus four times the third query result, plus four.
3. Limit becomes the replacement base plus four times the selected growth count.

The third query result, not either earlier query result, determines the published occupied end. Arithmetic overflow is not checked. No validation ensures that the published end lies within the published limit.

### Backward shifting

This path is selected when the unsigned count derived from the pre-query base and limit exceeds the first query result.

The function rereads the occupied end and writes that address plus four back to the occupied-end field.

If the reread end is nonzero, it reads the four-byte word immediately before that address and writes the word at that address. This destination can overlap the control record and overwrite the preceding end update or another field.

A backward source cursor is then positioned one element before the reread end. While that cursor differs from the insertion address captured on entry, the function moves both source and destination cursors backward by four bytes and copies the source word to the destination.

After the loop, it reads the value source and writes the word at the captured insertion address. This final write has no null-destination guard.

Both the end update and all backward copies precede the final source read. Aliasing can therefore change the inserted value.

If the query leaves the end unchanged, the initial backward cursor is already one element before the captured insertion address and moves farther backward. This is not an ordinary finite shift toward that target. Successful completion must not be promised for that state.

## Side effects

### Write visibility and aliasing

The function is not transactional:

- Direct extension writes the end field before reading and storing the inserted word.
- Backward shifting writes the end field before shifting and insertion.
- Replacement processing performs its release-like call before publishing the replacement record.
- Replacement publication comprises three separate writes.

No rollback is shown.

Element-storage writes are not restricted to memory outside the control record. In particular, on the direct path:

- A destination overlapping the base field can change the base.
- A destination overlapping the limit field can change the limit.
- A destination overlapping the end field can replace the just-written advanced end.

These effects follow from the ordinary element write, without any explicit assignment targeting the affected field. General claims of field preservation require corresponding non-overlap assumptions.

### Ownership

Four-byte elements are treated as words. No element-specific resource acquisition, destruction, or ownership policy is established.

The replacement path requests storage and later passes an old-base value to another dependency, but their allocation and release contracts are unknown. Neither transfer-like call can be assumed to preserve or release its source.

The value-source address is not retained or explicitly released by this body. That observation does not establish preservation by dependencies.

### Errors

There is no explicit status result, overflow report, allocation-failure branch, or general invalid-input rejection.

Invalid addresses may cause invalid reads or writes. Unreachable loop targets may prevent termination. Dependency exceptions, traps, nonlocal exits, or other failure conventions are **documented_only**.

## Acceptance examples

These are conditional static expectations, not executed tests.

### Ordinary direct extension

Assume the initial end differs from the limit, the original end is nonzero and identifies a writable four-byte slot, the source is readable, and that destination does not overlap any control-record field.

Then:

- The end field becomes the original end plus four.
- The original end receives the source word read after the end update.
- Base and limit remain unchanged.
- No dependency is called.

An independent source additionally ensures the source value is unaffected by the end update.

### Direct destination overlaps the base field

Assume the record begins at address 0x1000, its occupied end is 0x1000, and its limit is 0x2000. Let an independent readable source contain 0x9000. Assume all indicated word accesses are valid.

The function first writes 0x1004 to the occupied-end field at offset four. It then writes 0x9000 to the captured destination, address 0x1000.

The final base field is therefore 0x9000, despite the absence of an explicit base-field assignment on this path. The end is 0x1004, and the limit remains 0x2000.

Likewise, if the captured destination instead identifies the limit field and differs from the recorded limit value, the element write overwrites the limit field.

### Null direct destination

Given an initial end of zero and a nonzero limit:

- The end field becomes four.
- No element write occurs.
- The value source is not read.
- No dependency is called.

This is branch behavior, not an assertion of a valid collection state.

### Source aliases the end field

On the direct path, assume a valid nonzero destination disjoint from the record, and let the source identify the occupied-end field.

The stored word is the advanced end address because the field update precedes the source read.

### Stable replacement with 32 elements

Assume aligned, full storage containing 32 elements; all three query results equal 32; arithmetic does not wrap; and dependencies provide successful allocation and intended range transfers while otherwise preserving relevant state. Assume replacement storage and source do not overlap the record.

The growth candidates are 64 and 52 elements. The request is 256 bytes.

If all operations complete:

- The inserted word follows the 32 transferred elements.
- The published occupied end is 132 bytes after the replacement base.
- The published limit is 256 bytes after that base.
- The release-like call precedes replacement publication.

### Stable proportional growth

Under equivalent assumptions with 256 elements and query results of 256, the candidates are 288 and 416 elements. The request is 1,664 bytes, and the published occupied end is 1,028 bytes after the replacement base.

### Finite backward shift after a query mutation

Assume entry end and limit both equal a captured insertion address. Suppose the first query changes the current end to four bytes beyond that address and returns a value selecting backward shifting.

With valid, non-overlapping storage and an independent source, the function advances the current end by another four bytes, copies the word at the captured insertion address into the following slot, skips the backward loop because its cursor already equals the insertion address, and writes the source word at that insertion address.

This example requires the stated query mutation; it does not establish that the dependency actually performs it.
