# F-8b998a07b5e1

## Purpose

F-8b998a07b5e1 selects one of two indirect-operation paths according to whether its first argument is zero. Either path requires a positive signed size; otherwise, the function returns zero after reading two shared context references.

With a zero first argument, the function clears shared state, optionally invokes a notification before an operation, invokes the operation, optionally invokes a notification afterward, and conditionally writes one byte at the returned address.

With a nonzero first argument, it optionally invokes notifications before and after a different operation. This path has no direct state clear or returned-memory write.

**Inferred intent:** the paths resemble allocation and resizing. The supplied evidence does not establish those meanings, any dependency’s implementation, or memory ownership.

## Interface

### Arguments and result

| Position | Representation | Established use |
|---|---|---|
| First | 32-bit value | Tested for zero; forwarded unchanged on the nonzero path |
| Second | Signed 32-bit integer | Positive-size gate, operation and notification argument, marker-write threshold |
| Third | Opaque 32-bit value | Forwarded to operations and notifications |
| Fourth | Opaque 32-bit value | Forwarded to both operations and to zero-path notifications |
| Result | Pointer to a one-byte destination element | Zero for nonpositive size; otherwise the selected operation’s result |

The first argument is not directly dereferenced. Its interpretation as an existing-object address is plausible but unestablished. Any nonzero value, including a value interpreted as negative, selects the nonzero path.

Neither opaque argument is directly dereferenced. Their meanings are unknown.

### Shared storage

The following are specification labels, not implementation identifiers:

- **Context A:** context used for the zero-first-argument path.
- **Context B:** context used for the nonzero-first-argument path.
- **Marker reference:** shared reference used to obtain the source of the conditional destination-byte assignment.

At entry, the function reads and retains the Context B reference, then reads and retains the Context A reference. Both reads occur before a nonpositive size is rejected.

The established context accesses have these byte offsets:

| Context | Offset | Accessed field |
|---|---:|---|
| A | 0 | 32-bit state word |
| A | 4 | 32-bit state word |
| A | 12 | Required operation pointer |
| A | 40 | Optional notification pointer |
| B | 20 | Required operation pointer |
| B | 44 | Optional notification pointer |

The representation uses four-byte Context A slots and the listed Context B offsets. These accesses do not establish a complete object layout or an independent native ABI.

The marker-source declaration and pointee type are absent. Consequently, **the width of the source dereference is unknown**. The destination assignment writes one byte, but that does not establish a one-byte source read.

### Preconditions for defined execution

Execution requires accessible storage for the shared references read at entry.

For a positive size, the selected path additionally requires:

- Accessible context storage for every field actually read or written.
- A callable target at the required operation slot.
- A callable target for each notification actually invoked.
- Continued validity of any retained context used after a call.

The zero path requires writable state storage. If its operation returns nonzero and the size exceeds 2,048, it also requires:

- An accessible marker reference.
- Source storage valid for the actual dereference type and width, which are not supplied.
- A source value that can validly undergo the represented assignment conversion.
- A returned address permitting a one-byte write after the final notification.

The function does not check these conditions. A notification’s earlier nonzero presence check does not validate a different target subsequently loaded for invocation.

## Behavior

### Entry and rejected sizes

The function first captures Context B, then Context A.

A signed size of zero or less produces a zero result on either path. After the entry reference reads, such a request performs no shown context-field access, state clear, notification, operation, marker-source dereference, or destination-byte write.

In particular, a nonzero first argument with a nonpositive size does not cause a visible release call.

### Zero first argument and positive size

The sequence is as follows.

1. **Clear state through the current Context A reference.**

   The function obtains Context A through its shared reference for this write and stores a 32-bit zero at offset 0.

   This access is not expressed through only the retained entry-time Context A address. If the shared reference differs from its entry value, the state clear and subsequent retained-context accesses can affect different objects.

2. **Check the retained Context A notification slot.**

   The function tests the pointer at offset 40 of retained Context A.

   If the tested value is nonzero, it:

   - Writes a 32-bit zero at offset 4 of retained Context A.
   - Reads the notification target from that context slot for invocation.
   - Invokes it with four arguments: zero, requested size, third argument, fourth argument.

   If the tested value is zero, neither this offset-4 clear nor this notification occurs.

   The presence test and invocation are separate slot accesses. In particular, the offset-4 write lies between them. The representation does not establish a single saved notification target for both accesses.

3. **Invoke the required operation.**

   The operation target is read from offset 12 of retained Context A after the preceding notification, if any.

   It receives three arguments: requested size, third argument, fourth argument.

   Its returned pointer becomes the candidate result.

4. **Check and optionally invoke the after-notification.**

   The function checks offset 40 of retained Context A again. If nonzero, it reads the target for invocation and calls it with:

   - Candidate result.
   - Requested size.
   - Third argument.
   - Fourth argument.

   This notification occurs even if the candidate result is zero. Its return value does not replace the candidate result.

5. **Conditionally assign a destination byte.**

   If the candidate result is nonzero and the signed size is strictly greater than 2,048, the function obtains the marker source through the then-current marker reference, dereferences that source, converts the resulting value to the destination’s one-byte type, and writes the converted value at the candidate result address.

   The source dereference’s width is **documented_only** because the source declaration and pointee type are unavailable. It may not be described as necessarily reading exactly one byte.

6. **Return the candidate result.**

The two notification checks are independent. Earlier calls can modify the notification slot, so the function can execute both notifications, only the first, only the second, or neither.

Retaining Context A does not preserve its fields. A before-notification can change the operation target later read from offset 12. The operation can change the notification target used afterward.

The marker assignment occurs after the after-notification returns. The source reference and source value are not entry-time snapshots. Earlier calls can affect them. The destination write can overwrite a byte previously written by the operation or notification.

The function does not revalidate the candidate result after notification. An indirect callee that invalidates the returned storage can therefore make the later assignment invalid.

### Nonzero first argument and positive size

The sequence is as follows.

1. **Check for a before-notification through current Context B.**

   The presence check reads offset 44 through the current shared Context B reference, rather than solely through the retained entry-time address.

   If the checked pointer is nonzero, the invocation target is also obtained through the shared Context B reference. The call receives:

   - Original first argument.
   - Zero.
   - Requested size.
   - Third argument.

   The fourth original argument is not supplied.

   The shared reference and notification slot are not represented as one saved target spanning the presence check and invocation. No synchronization guarantee is established for changes between those accesses.

2. **Invoke the operation through retained Context B.**

   The function reads the operation target at offset 20 of the entry-time Context B address. It passes all four original arguments in their original order.

   The returned pointer becomes the candidate result.

3. **Read and optionally invoke the retained-context after-notification.**

   The function reads offset 44 of retained Context B into a retained notification target. If that target is nonzero, it invokes that target with:

   - Original first argument.
   - Candidate result.
   - Requested size.
   - Third argument.

   The fourth original argument is again absent.

4. **Return the candidate result.**

There is no direct state-word clear, marker-source access, or result-byte write on this path, regardless of size or result value.

A before-notification can replace the shared Context B reference without redirecting the later operation: that operation still uses the entry-time context. The notification can nevertheless alter fields within that retained context before they are read.

### Integer widths and threshold

The size gate is signed and 32-bit. Only values from 1 through 2,147,483,647 reach an operation.

For the zero path, the marker condition reduces to:

- Candidate result is nonzero.
- Signed size is strictly greater than 2,048.

The represented subtraction and signed-overflow comparison do not imply an unsigned threshold or an inclusive boundary.

For sizes reaching this check, subtracting 2,048 produces a value from −2,047 through 2,147,481,599. That range fits a signed 32-bit integer. Thus, the accepted positive-size domain introduces no subtraction overflow.

## Side effects

### Direct writes and reads

The direct writes are:

- A 32-bit zero at offset 0 of current Context A for every positive-size zero-path request.
- A 32-bit zero at offset 4 of retained Context A when the before-notification presence check succeeds.
- A one-byte write at the candidate result address when the zero-path marker condition holds.

The final write stores the marker-source value converted to the destination byte type. The source read’s width is unknown; it must not be narrowed to one byte merely because the destination is byte-sized. The missing source type also prevents a complete source-to-destination conversion contract.

The function directly reads shared references, context fields, and—conditionally—the marker source. It has no explicit handling for overlap among contexts, source storage, and returned storage. Such overlap can affect later reads according to the described ordering.

### Indirect effects and ownership

The operations and notifications have unavailable implementations. They must not be assumed to preserve:

- Shared references.
- Context fields.
- Marker storage.
- Input objects.
- Returned storage.

There is no separate visible release operation. That does not establish that memory is never released: an indirect dependency could release memory, transfer ownership, retain arguments, or invalidate addresses.

The evidence does not establish whether:

- The result denotes newly allocated or resized storage.
- The caller owns the result.
- The original object remains valid after either a zero or nonzero result.
- A zero result means failure.
- Notifications retain any supplied value.

A zero operation result is returned unchanged and still reaches an enabled after-notification.

### Errors and interrupted execution

The function has no visible error translation, retry, rollback, or required-operation null check.

If a dependency fails to return normally, later actions are not established to execute. Earlier state clears are not visibly undone.

Invalid storage or an invalid call target has no defined recovery behavior in the supplied evidence.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Unless otherwise stated, assume valid storage, callable targets, normal returns, and no changes except those described.

1. **Zero first argument, zero size.**  
   Context B and Context A references are read in that order. The result is zero. No context-field access, state clear, notification, operation, or marker access follows.

2. **Nonzero first argument, negative size.**  
   The result is zero after the entry reference reads. No operation, notification, or separate release call occurs.

3. **Zero first argument, positive size, notification slot remains zero.**  
   Current Context A’s offset-0 word becomes zero. Retained Context A’s offset-4 word is not directly cleared. F-indirect-01 receives the size and both opaque arguments.

4. **Zero first argument, size exactly 2,048, nonzero result.**  
   The operation and enabled notifications occur. There is no marker-source dereference or destination-byte write.

5. **Zero first argument, size 2,049, nonzero result.**  
   After the enabled after-notification returns, the then-current marker source is dereferenced. Its value is converted to the destination byte type and stored at the result address. The destination write is one byte; the source read width remains unspecified.

6. **Zero first argument, size above 2,048, zero result.**  
   An enabled after-notification receives zero. No marker-source dereference or destination-byte write follows.

7. **Before-notification clears Context A’s notification slot.**  
   The offset-4 clear and before-notification occur. If the operation leaves the notification slot zero, no after-notification occurs.

8. **Operation installs a Context A notification target.**  
   With an initially zero slot, there is no before-notification or offset-4 clear. A valid nonzero target installed by the operation is eligible for the after-notification.

9. **After-notification changes the marker reference.**  
   For a qualifying nonzero result, the subsequent assignment uses the replacement source reference. The expected destination byte is the value obtained from that source after conversion, not an entry-time marker snapshot. Validity of the source access depends on its unavailable type and width.

10. **Nonzero first argument, positive size above 2,048.**  
    F-indirect-03 receives all four original arguments. Notifications receive the first argument, zero or result, size, and third argument. This path performs no marker assignment.

11. **Nonzero-path operation returns zero.**  
    An enabled after-notification receives the original first argument followed by zero, size, and third argument. The enclosing result is zero.

12. **Before-notification replaces the Context B shared reference.**  
    The later operation and after-notification lookup remain directed at retained entry-time Context B. This does not guarantee that the retained object remains valid.
