# F-030a3110641a

## Purpose

F-030a3110641a performs a local restructuring of linked records. It promotes the record referenced by a pivot record’s field at byte offset +8, reconnects that promoted record to the pivot’s former incoming link, and makes the pivot the promoted record’s child at byte offset +12.

**Established static behavior:** the operation updates a root-reference slot or one neighboring record’s child-reference slot, together with several parent and child references. It returns no value and performs no explicit validation.

**Inferred intent:** if offset +4 is a parent reference, offset +8 is a left-child reference, and offset +12 is a right-child reference, this is a right rotation in a parent-linked binary tree. These field names describe the inferred structure; the observable contract is the offset-based behavior below. The routine does not establish ordering, balance, or membership properties.

## Interface

### Inputs and result

| Input | Interpretation |
|---|---|
| Container address | Address of an object whose four-byte field at offset +16 supplies an auxiliary-record address. |
| Pivot address | Address of the record to restructure. |
| Result | No returned value. Changes are communicated through memory writes. |

The supplied representation uses integer-valued addresses and four-byte accesses for all relevant fields. This contract therefore describes **32-bit reference fields occupying four bytes each**. It does not establish that the routine is portable to a process with wider native pointers.

There are no scalar counts, sizes, flags, or output-buffer arguments.

### Relevant layouts

Record fields:

| Byte offset | Width | Operational meaning |
|---|---:|---|
| +4 | 4 bytes | Parent reference |
| +8 | 4 bytes | Child reference selected for promotion |
| +12 | 4 bytes | Opposite-side child reference |

Container and auxiliary-record fields:

| Object | Byte offset | Width | Operational meaning |
|---|---:|---:|---|
| Container | +16 | 4 bytes | Auxiliary-record reference |
| Auxiliary record | +4 | 4 bytes | Root-reference slot |

Other fields are not directly addressed by the supplied routine. No complete record size, packing rule, alignment requirement, or byte order is established.

### Preconditions

For ordinary tree-rotation behavior:

- The container and pivot addresses must support the accesses described below.
- The pivot’s +8 field must identify an accessible promoted record. A zero value is not handled as an absent child.
- The auxiliary-record reference obtained from the container must identify an accessible root-reference slot.
- A nonzero transferred-child reference must identify a record with a writable +4 field.
- If the root-reference slot does not equal the pivot address, the pivot’s parent reference must identify a record whose +12 field can be read and whose selected child-reference field can be written.
- The records must have structurally appropriate relationships and must not overlap in ways that invalidate the intended topology.
- No concurrent or reentrant mutation may interfere if a coherent rotation is required.

These are caller obligations, not checks performed by the routine. Failure behavior for invalid addresses is not specified by the supplied evidence.

## Behavior

### Terms

The **pivot** is the record supplied by the second input.

The **promoted record** is selected once, by reading the pivot’s +8 field at entry. Its identity is retained for the remainder of the operation; it is not selected again after the pivot’s +8 field changes.

The **transferred child** is the reference initially read from the promoted record’s +12 field.

The **root-reference slot** is the four-byte location at offset +4 within the auxiliary record obtained through the container’s +16 field.

### Ordered memory actions

The following order is established by the supplied representation. Repeated reads are significant: the routine does not necessarily reuse an earlier value.

1. **Select the promoted record.**  
   Read the pivot’s +8 field and retain the resulting address.

2. **Replace the pivot’s promotion-side child.**  
   Read the promoted record’s +12 field and write that four-byte value into the pivot’s +8 field.

3. **Conditionally repair the transferred child’s parent.**  
   Read the promoted record’s +12 field again.
   - If this read is zero, perform no transferred-child parent write.
   - Otherwise, read the promoted record’s +12 field once more to obtain the destination record address, and write the pivot address into that record’s +4 field.

   Thus, the reference copied into the pivot, the reference tested for zero, and the reference used to locate the parent field come from separate reads. They agree under ordinary stable, non-overlapping storage, but the routine does not explicitly enforce that agreement.

4. **Give the promoted record the pivot’s current parent.**  
   Read the pivot’s +4 field and write its four-byte value into the promoted record’s +4 field.

5. **Locate and inspect the root-reference slot.**  
   Read the container’s +16 field. Using the resulting auxiliary-record address, read its +4 field and compare that value with the pivot address.

   This lookup occurs after the preceding child and parent-field mutations, not at entry.

6. **Reconnect the incoming reference.**
   - **Root case:** if the root-reference slot equals the pivot address, write the promoted-record address into that slot.
   - **Non-root case:** otherwise, read the pivot’s +4 field again to obtain the parent address. Read that parent’s +12 field.
     - If the field equals the pivot address, replace the parent’s +12 field with the promoted-record address.
     - Otherwise, write the promoted-record address into the parent’s +8 field.

   The final alternative does not verify that the parent’s +8 field previously referenced the pivot. Equality at +12 is the sole child-side test.

7. **Attach the pivot below the promoted record.**  
   Write the pivot address into the promoted record’s +12 field.

8. **Finish the pivot’s parent update.**  
   Write the promoted-record address into the pivot’s +4 field, then return without a value.

### Ordinary postconditions

For stable, valid, non-overlapping tree records, let:

- **P** be the pivot;
- **U** be the promoted record;
- **T** be U’s original +12 reference;
- **A** be P’s original +4 reference.

The resulting relationships are:

| Location | Result |
|---|---|
| P +8 | T |
| T +4, if T is nonzero | P |
| U +4 | A |
| U +12 | P |
| P +4 | U |
| Incoming reference that previously selected P | U |

The incoming reference is either the root-reference slot or a selected field of A. In the non-root case, A’s +12 field is selected when it equals P; otherwise A’s +8 field is selected.

U’s +8 field and P’s +12 field are not directly written. No payload, ordering key, balance indicator, color, or count field is directly updated.

### Arithmetic and value handling

All accessed fields are four bytes wide. Field contents used as references are copied or compared without an explicit range conversion.

Address calculations use fixed byte displacements: +4, +8, +12, and +16. No element-count multiplication or variable-length traversal occurs. The evidence does not establish behavior when an address calculation overflows, reaches unmapped memory, or violates platform alignment rules. Valid accessible address calculations are therefore a precondition, not a guaranteed wrapping behavior.

Zero has one explicit absence meaning: a zero value read from the promoted record’s +12 field suppresses the transferred-child parent update. No corresponding zero checks protect the pivot, promoted record, auxiliary record, or non-root parent.

## Side effects

The routine mutates caller-reachable storage in place. It does not construct or return a replacement object.

For an ordinary non-overlapping invocation, it performs:

- One write to the pivot’s +8 field.
- One optional write to the transferred child’s +4 field.
- One write to the promoted record’s +4 field.
- One write to the selected incoming-reference slot.
- One write to the promoted record’s +12 field.
- One write to the pivot’s +4 field.

That is five writes when the transferred child is absent and six when it is present.

There are no explicit allocation, release, callback, logging, or error-reporting operations in the supplied body. No transfer of allocation ownership is expressed. The caller remains responsible for keeping all accessed records alive.

The mutation is not presented as atomic or transactional. Intermediate states temporarily contain only part of the final linkage. There is no rollback path. If an access cannot complete, the supplied evidence does not define recovery or guarantee restoration of earlier writes.

The listed write locations are computed from memory contents. With overlapping records, malformed references, or concurrent mutation, they may alias other fields, including fields used later in the operation. In those cases, the ordered actions—not the ordinary postcondition table—define what the static evidence supports.

## Acceptance examples

These are **conditional static acceptance examples**, not results of runtime tests. Unless stated otherwise, records are distinct, storage is accessible and stable, and unrelated fields do not alias the affected fields.

### Root pivot with a transferred child

Initially:

- The root-reference slot contains P.
- P’s +8 field contains U.
- P’s +4 field contains A.
- U’s +12 field contains nonzero T.

After completion:

- The root-reference slot contains U.
- U’s +4 field contains A.
- P’s +8 field contains T, and T’s +4 field contains P.
- U’s +12 field contains P, and P’s +4 field contains U.

The root case does not force U’s parent to zero. It copies P’s parent value.

### Root pivot without a transferred child

If the root-reference slot contains P and U’s +12 field remains zero throughout the relevant reads:

- P’s +8 field becomes zero.
- No transferred-child parent write occurs.
- The root-reference slot becomes U.
- U’s +12 becomes P, and P’s +4 becomes U.

### Non-root pivot selected through the parent’s +12 field

If the root-reference slot does not contain P, P’s +4 contains A, and A’s +12 contains P:

- A’s +12 becomes U.
- The root-reference slot is not written.
- U’s +4 becomes A.
- The remaining local rotation updates occur as described above.

### Non-root pivot selected through the parent’s +8 field

If the root-reference slot does not contain P, A’s +12 does not contain P, and A’s +8 contains P:

- A’s +8 becomes U.
- A’s +12 is not directly written.
- The root-reference slot is not written.

### Inconsistent parent linkage

If the non-root parent’s +12 field does not contain P and its +8 field also does not contain P, the routine nevertheless overwrites the parent’s +8 field with U. It does not reject the inconsistency or search elsewhere for an incoming reference.

### Missing promoted record

If P’s +8 field is zero, the routine still attempts to access the selected record’s +12 field. No graceful empty-child result is specified. Any platform-specific failure outcome remains undocumented.
