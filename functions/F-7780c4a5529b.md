# F-7780c4a5529b

## Purpose

F-7780c4a5529b obtains a vector through a caller-supplied parsing interface, accepts an initial signed element count from 1 through 16, and converts the corresponding records into 32-bit values. Each converted value is written to two destination arrays associated with a context object.

The function reuses an associated object whose nonzero stored count matches the parsed count. If the object is absent or has a zero count, it invokes F-c14349e38b4d to prepare an object. A nonzero count mismatch is an error rather than a request to replace the object.

Completion is reported through a 32-bit status field in the parsing interface. No meaningful return value is established.

**Established static behavior:** count classification, object selection, dependency-call order, paired destination writes, restoration of two parsing fields after conversion, and final status publication.

**Inferred intent:** diagnostic wording suggests a weight vector. The numerical representation of the converted values and the later purposes of the two arrays are not established.

## Interface

### Arguments and representation

The function accepts:

- A **context address**, identifying storage with an associated-object pointer at byte offset 0x20c.
- A **parsing-interface address**, identifying mutable fields and indirect-call addresses.

The supplied representation uses 32-bit pointers, 32-bit integer fields, and 32-bit conversion results. The offsets below describe that representation, not a portable native layout.

### Context and associated object

| Location | Width | Meaning established here |
|---|---:|---|
| Context + 0x20c | 32 bits | Associated-object pointer |
| Associated object + 0x00 | 32 bits | Signed stored element count |
| Associated object + 0x88 | 32 bits | First destination-array base address |
| Associated object + 0x8c | 32 bits | Second destination-array base address |

The function explicitly handles a null associated-object pointer. A nonnull object must permit reading its stored count.

For a stable accepted count of \(n\), each destination array must permit \(n\) writable 32-bit entries at four-byte spacing. A nonzero stored count is compared with the parsed count, including when the stored count is negative.

### Parsing interface

| Byte offset | Width | Use |
|---|---:|---|
| 0x00 | 32 bits | First field replaced for each conversion and subsequently restored |
| 0x08 | 32 bits | Second field replaced for each conversion and subsequently restored |
| 0x0c | 32 bits | Final status |
| 0x28 | 32 bits | Element-conversion callback address |
| 0x3c | 32 bits | Vector-parsing callback address |

The fields at offsets 0x00 and 0x08 are opaque 32-bit values. Their concrete types are not established.

### Indirect-call interfaces

The vector-parsing callback receives, in order:

1. The parsing-interface address.
2. An address of invocation-local record storage spanning 192 bytes.
3. The integer capacity 16.
4. An address for a signed 32-bit output count.

The record storage accommodates 16 records with a 12-byte stride. This function consumes only the first and second 32-bit words of each processed record.

The element-conversion callback receives:

1. The parsing-interface address.
2. The integer zero.

Its result is an opaque 32-bit word. No result pattern is locally distinguished as an error.

### Preconditions and lifetime

Defined ordinary operation requires:

- Valid context and parsing-interface storage for the accesses described here.
- Callable indirect-call addresses whenever they are read and invoked.
- A vector-parsing callback that initializes the count before returning.
- Initialized first and second words for every record subsequently consumed.
- A usable selected object and destination addresses when conversion writes occur.
- After successful preparation, a usable object at the context’s associated-object field.

The function does not validate these conditions. It has no explicit null check for either top-level argument, either callback address, or either destination-array address.

The temporary records and output-count storage belong to this invocation. Dependencies must not use their addresses after the invocation ends. Retention and mutation during the invocation are not prevented by this function and can affect later reads.

## Behavior

### Capture the object before parsing

The function first reads and retains the associated-object pointer from context offset 0x20c.

It then invokes the vector-parsing callback through parsing-interface offset 0x3c, supplying the temporary records, capacity 16, and count address. The callback’s ordinary return value does not determine acceptance, status, or destination contents.

The retained object pointer is not automatically refreshed after parsing. If the callback replaces the context’s associated-object pointer, the function still considers the previously captured pointer unless a successful preparation call later causes a refresh.

The captured pointer must therefore remain usable if subsequent processing dereferences it. The function does not establish that parsing preserves its lifetime.

### Classify the count

After parsing returns, the count is interpreted as a signed 32-bit integer:

| Count used for classification | Local outcome |
|---|---|
| Negative | Select status 162, hexadecimal 0xa2 |
| Zero | Enter the invalid-nonnegative-count diagnostic path |
| Greater than 16 | Enter the same diagnostic path |
| 1 through 16 inclusive | Continue to object handling |

A negative count causes no diagnostic call, preparation call, or conversion call by this function.

For an invalid nonnegative count, the function performs these operations in order:

1. Call F-4457a9a44a68 with a diagnostic identifying the parsing operation.
2. After that call returns, read the count storage again.
3. Call F-4457a9a44a68 with the incorrect-number-of-designs diagnostic and that newly read signed 32-bit count.
4. Select status 3.

The second diagnostic’s count argument is **not necessarily the count returned by parsing or the count that caused rejection**. Parsing received the count’s address. If a dependency can reach that retained address and changes the count during the first diagnostic, the second diagnostic receives the changed value.

The branch decision is not reconsidered after the first diagnostic. Changing the count to an otherwise acceptable value does not resume object handling or conversion. The locally selected final status remains 3.

The diagnostic calls’ rendered bytes, output destination, and external formatting behavior are not established here.

### Reuse or prepare the object

On the accepted-count path, the function examines the captured object:

- If the pointer is nonnull, read its signed stored count.
- If the pointer is nonnull and that stored count is nonzero:
  - A matching count permits reuse.
  - A mismatch causes two ordered calls to F-4457a9a44a68, selects status 3, and skips preparation and conversion.
- If the pointer is null or the stored count is zero:
  - Invoke F-c14349e38b4d with the context address, current count, and integer zero.
  - A nonzero 32-bit result becomes the final status unchanged.
  - A zero result causes the associated-object pointer to be reread from context offset 0x20c.

A negative stored count follows the nonzero comparison path and cannot match an ordinarily accepted positive count.

After successful preparation, the function does not explicitly check the refreshed pointer, reread its stored count for validation, or validate its array bases.

### Save the parsing fields

After successful object handling, the function saves parsing-interface offset 0x00, followed by offset 0x08.

These are the values present after parsing and any preparation call, not necessarily the entry values. Earlier dependency mutations are therefore included in the saved state.

No other parsing-interface field is saved for restoration.

### Convert records and write paired results

The conversion index begins at zero. Each loop condition compares the index against the signed count read from the invocation-local count storage.

For a count that remains \(n\), the function processes indices zero through \(n-1\), in ascending order. Each iteration has this observable sequence:

1. Read the record’s first 32-bit word and write it to parsing-interface offset 0x00.
2. Read the record’s second 32-bit word and write it to parsing-interface offset 0x08.
3. Read the conversion-callback address from parsing-interface offset 0x28 and invoke it with the interface address and zero.
4. Read the selected object’s first destination base and store the callback’s 32-bit result at the current four-byte element offset.
5. Read the selected object’s second destination base and store the same result at the corresponding offset.
6. Advance the index and evaluate the next loop condition.

The third word of each 12-byte record is not consumed.

The callback address is obtained for each iteration. A conversion callback that changes that field can affect the next invocation.

The destination bases are not captured as an immutable pair before conversion. They are read as their respective stores are performed. The first destination write precedes the second base read and second destination write. Aliasing can therefore make the first write affect the second destination.

There is no branch on the conversion result. Every 32-bit return pattern is treated as data.

### Live-count behavior after validation

The initial range check is not repeated after preparation or conversion callbacks. The loop uses the count storage again rather than an immutable validated copy.

Consequently, if a dependency changes that storage through a retained address:

- A reduced count can shorten processing.
- A count made zero or negative before the first loop condition can cause no conversions.
- An increased count can cause additional iterations beyond the initially accepted count.
- An increase beyond 16 can cause record accesses outside the supplied 192-byte storage.

These are consequences of the visible read order, not guarantees of safe operation under arbitrary mutation. Record initialization, storage bounds, and address validity remain preconditions for accesses actually performed.

### Restore and publish status

After ordinary loop completion, the function:

1. Restores parsing-interface offset 0x00.
2. Restores parsing-interface offset 0x08.
3. Writes status zero to parsing-interface offset 0x0c.

Earlier ordinary exits instead write their selected status to offset 0x0c. They do not perform the conversion-path restoration.

The final status assignment follows all dependency activity on that ordinary path. A dependency’s earlier write to the status field is overwritten.

## Side effects

### Direct effects

The function directly:

- Replaces two parsing-interface fields before each conversion.
- Writes the conversion result into two destination locations per iteration.
- Restores the saved parsing fields after ordinary loop completion.
- Writes final status on every ordinary completion path.

It also supplies invocation-local record and count storage for the parsing callback to write. Those callback writes are dependency effects, not direct initialization by this function.

No direct heap allocation or release is established.

### Ownership and dependency mutations

No ownership transfer is established for the context, parsing interface, associated object, or destination arrays. The function does not directly release them.

F-c14349e38b4d, F-4457a9a44a68, and the callbacks may have effects beyond those consumed here. They must not be assumed to preserve globals, object identity, memory contents, or ownership. Whether preparation allocates, replaces, retains, or releases an object is documented_only.

### Partial updates and aliasing

There is no explicit rollback. If a callback does not return normally or a memory access fails after conversion begins, earlier writes may remain. Restoration and final status publication are not guaranteed on such paths.

The function does not reject overlapping arrays or overlap with the object, interface, or temporary storage. Ordered writes can affect later reads, including callback selection, destination bases, and temporary record contents.

The simple postcondition that both arrays contain the converted vector therefore requires noninterfering storage and dependency behavior.

## Acceptance examples

These are conditional static acceptance criteria, not runtime observations. Unless an example states otherwise, dependencies return normally, the count remains stable after parsing, and storage is valid and noninterfering.

### Negative count

If parsing writes −1, final status is 162. This function performs no diagnostic, preparation, or conversion calls. Parsing’s side effects are not undone.

### Invalid nonnegative count without mutation

If parsing writes 0 or 17 and the first diagnostic does not change the count, two diagnostic calls occur. The second receives that same count, and final status is 3. Preparation and conversion are skipped.

A count of 16 passes this boundary check.

### Invalid count changed during diagnostics

If parsing writes 17 and the first diagnostic changes the retained count storage to 2, the second diagnostic receives 2. The function still finishes with status 3 and performs no preparation or conversion.

If that first diagnostic instead changes the count to −5, the second diagnostic receives −5. The function does not switch to the negative-count status 162 because classification has already selected the invalid-nonnegative path.

### Existing matching object

Suppose the captured object has stored count 2, parsing supplies two records, and conversions return words \(A\) and \(B\).

Preparation is not called. The first two words of each record are presented through the parsing fields for its corresponding conversion. Both arrays receive \(A\) at index zero and \(B\) at index one.

The two parsing fields are restored to their values immediately before conversion processing. Final status is zero.

### Existing mismatching object

If the captured object has stored count 3 and parsing reports 2, two mismatch diagnostics occur and final status is 3. No replacement is prepared and no elements are converted.

### Preparation outcomes

If preparation is required and F-c14349e38b4d returns 7, final status is 7. No conversion or explicit rollback occurs.

If preparation returns zero and installs a usable object, the function rereads the context’s associated-object pointer and uses that object. Ordinary completion with valid storage ends with status zero.

If preparation also changes the retained count to zero, the conversion loop executes no iterations; the saved parsing fields are restored and final status is zero.

### Parsing-time object replacement

If a matching object was captured before parsing and parsing installs another object in the context, the captured object remains selected. The replacement is adopted only if execution reaches the successful preparation path and its pointer refresh.

### Conversion-time status write

If a conversion writes a nonzero interface status but otherwise returns normally, that write does not terminate processing. Ordinary loop completion restores the two saved fields and writes final status zero.

- **documented_only — Diagnostics:** exact output bytes and external effects are unknown. The second invalid-count diagnostic receives the count read after the first diagnostic returns, whether changed or unchanged.
- **documented_only — Exceptional completion:** invalid accesses, nonlocal exits, and dependencies that fail to return have no established completion contract.
- **documented_only — Status vocabulary:** numeric statuses 3 and 162 are established; broader symbolic meanings are not.

For a stable count from 1 through 16, record starts range from byte offset 0 through 180. The consumed words fit within 192 bytes. Destination element offsets range from 0 through 60 bytes.

These bounded offsets do not prove destination validity or prevent 32-bit address wrap for unsuitable base addresses. Arbitrary later count mutation invalidates those bounds; safe wrapping behavior is not established.
