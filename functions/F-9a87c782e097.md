# F-9a87c782e097

## Purpose

F-9a87c782e097 performs a fixed sequence of memory accesses and two dependency calls using a caller-supplied base address.

Its established behavior is to clear and copy four-byte fields relative to that base, call F-82648e96f301 with the base plus 48 bytes, and use the returned value to locate two writes and form an argument to F-401062e9ec7c. The second dependency’s result determines the destination of a final four-byte write.

Calling F-82648e96f301 with an address does **not** establish that the dependency initializes, reads, or writes memory at that address. Construction or initialization of a composite object is a possible interpretation of the overall sequence, but is **inferred intent**, not an established dependency behavior.

The contract specifies the visible accesses, their ordering, and their dependence on returned values. It does not assign object types or semantic meanings to the fields or external values.

## Behavior

### Initial storage transformation

Before either dependency is invoked, the function operates on eleven adjacent four-byte fields covering the half-open byte interval **[B+4, B+48)**.

The established order is:

| Stage | Accesses, in order |
|---|---|
| Initial zero stores | Four-byte zero stores at B+44, B+20, B+24, B+28, and B+32 |
| Copies | Four bytes from B+20 to B+4; then B+24 to B+8; then B+28 to B+12; then B+32 to B+16 |
| Remaining zero stores | Four-byte zero stores at B+36 and B+40 |

Each copy reads its source before writing its destination. Each source has already received a four-byte zero store.

Under ordinary stable-memory conditions, with no intervening modification, all eleven fields therefore contain zero immediately before the first dependency call. The function has not directly written the four bytes beginning at B.

This intermediate zeroed state is not the whole behavioral contract. The four source reads are part of the supplied access sequence. Replacing the copies with unconditional zero stores would omit those reads, which matters in any environment where the accesses are observable.

Nor is the intermediate state an unconditional final-state guarantee. Either dependency, or a later write through a returned address, may change the same storage.

### First dependency boundary

After all initial field accesses, the function calls F-82648e96f301 with **B+48** as its sole explicit argument.

Only the invocation and argument are established. The supplied body does not establish that this dependency accesses B+48, initializes an embedded region, preserves earlier fields, or returns its argument.

If the call returns normally, its result becomes R1. Subsequent addressing uses R1 rather than recomputing addresses from B.

### Writes between the dependencies

Following the first dependency’s return:

- The value supplied by E1 is read and written as a four-byte value at **R1−48**.
- A one-byte zero is then written at **R1+20**.

The external-value transfer precedes the byte store. Both precede the second dependency call.

The byte store directly affects only one byte. It does not establish that a larger field beginning at R1+20 is zero.

V1 is obtained after the first call. A value sampled before that call cannot be substituted without an additional preservation guarantee, which is not present.

### Second dependency boundary and final write

The function next calls F-401062e9ec7c with these explicit arguments, in order:

| Argument position | Value |
|---|---|
| First | R1+24 |
| Second | Zero |
| Third | Zero |

The evidence establishes the two zero values, but not their interface widths, parameter types, or meanings.

If this dependency returns normally, its result becomes R2. The function then reads the value supplied by E2 and writes it as a four-byte value at **R2−72**. It subsequently returns without an explicit result.

V2 is sampled after the second dependency returns. The function does not visibly cache it before that call.

### Address relationships and arithmetic

There is no established equality between R1 and B+48, or between R2 and R1+24. The function neither tests nor enforces either relationship.

The significant address adjustments are:

- B+48 for the first dependency argument.
- R1−48 for the first external-value destination.
- R1+20 for the byte destination.
- R1+24 for the second dependency’s first argument.
- R2−72 for the final destination.

These are byte displacements. The transferred four-byte values undergo no explicit arithmetic or byte-order transformation.

Behavior at integer overflow, address wraparound, invalid pointer conversion, or an invalid resulting address is **documented_only**. The normal-completion contract requires valid arithmetic and accesses rather than choosing an unsupported wraparound model.

## Side effects

- Two further four-byte writes through dependency-derived addresses.

### Aliasing and final state

The function contains no visible alias checks. The derived destinations may overlap:

- Fields accessed during the initial phase.
- Storage supplied to either dependency.
- Each other.
- External data locations.
- Other accessible storage.

The ordered accesses determine the direct effects when such overlap exists. For example, the first external-value write may change E2 before its later read. The contract does not require V2 to equal E2’s value at function entry.

The function does not unconditionally leave the initial fields zero. It also does not unconditionally leave R1+20 zero at return: the second dependency or the final write may change that byte.

No atomicity, synchronization, or inter-thread ordering guarantee is established. The listed ordering describes the supplied body; it is not a claim about a particular concurrent or memory-mapped-I/O execution model.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests.

### Stable initial storage

Given valid ordinary storage and no intervening modification, immediately before F-82648e96f301 is entered:

- The eleven four-byte fields at offsets 4 through 44 contain zero.
- The function has not directly written bytes B through B+3.
- The dependency receives B+48.

This example does not require the dependency to access or initialize that address.

### Observable copy-source reads

In an environment that observes individual memory accesses, the initial phase includes reads at B+20, B+24, B+28, and B+32, each after its source was cleared and before its corresponding destination write.

An implementation that merely produces the same zeroed bytes but omits those reads does not preserve this access sequence.

### First result equals B+48

If R1 equals B+48, the first external-value destination is B, the byte destination is B+68, and the second dependency receives B+72 as its first argument.

These are conditional address relationships, not unconditional object-layout claims.

### Both results produce a shared destination

If R1 equals B+48 and R2 equals B+72, both four-byte external-value writes target B.

The final direct write places V2 at B, replacing whatever four-byte value is present there at that point. Under ordinary stable-memory conditions after that write, B contains V2.

### First result refers elsewhere

If the first dependency returns some other valid address, the function still writes at R1−48 and R1+20 and passes R1+24 onward.

Substituting B-relative destinations would violate the established dependence on the returned value.

### Dependencies change external data

If the first dependency changes E1 before returning, V1 is obtained from E1 afterward. If the second dependency changes E2 before returning, V2 is obtained afterward.

Neither transfer is specified to use the corresponding location’s entry-time value.

### Invalid returned address

If R2 makes R2−72 invalid, no explicit validation or alternate return path intervenes before the final access. Earlier effects remain part of the execution history; the outcome of the invalid access is **documented_only**.
