# F-344c8978440f

## Purpose

F-344c8978440f coordinates three dependency calls and two single-byte state writes against one caller-supplied object address. On normal completion, it returns the 32-bit value 1.

The established behavior is an ordered sequence, not a demonstrated transaction: call a dependency using the address at object offset 8, write the supplied byte at offset 6, call another dependency using offset 8, call a third dependency using offset 16, and finally write the supplied byte at offset 4.

The semantic meanings of the two byte fields and the addressed regions are unknown. Interpreting the calls as locking, initialization, notification, cleanup, or resource release would exceed the supplied evidence.

## Behavior

### Established execution order

On an uninterrupted execution path, the observable operations occur in this order:

1. F-338d16f9ce72 is called with the address at object offset 8.
2. After that call returns, the supplied state byte is written to object offset 6.
3. F-1333331b2da1 is called with the address at object offset 8.
4. After that call returns, F-5bcae2eff9a7 is called with the address at object offset 16.
5. After that call returns, the supplied state byte is written to object offset 4.
6. The function returns the 32-bit value 1.

There are no visible branches, loops, retries, or conditional skips. Each dependency has one call site and is reached once if execution progresses normally to that point.

The two writes are distinct operations separated by two dependency calls. They must not be described as a simultaneous update of both fields.

### Intermediate and final state

The first dependency runs before either direct byte write. The second dependency runs after the offset-6 write and before the offset-4 write. The third dependency runs after the second dependency and before the offset-4 write.

Consequently, immediately after the offset-6 store, that byte contains the supplied state byte. This does not establish its value at return: either subsequent dependency could modify the same storage.

Immediately after the final store, offset 4 contains the supplied state byte. No later dependency call appears in this function. In the absence of concurrent or otherwise external modification, that is also the value at offset 4 when the function returns.

The supplied body does not read either byte before writing it. It does not compare old and new values, and it does not skip work when the requested byte already matches existing memory. Even an apparently redundant state request still reaches all three dependency calls, provided execution continues normally.

### Dependency effects and address identity

The first two calls receive the same derived address: object offset 8. This establishes equality of their address arguments, not preservation of the addressed contents between calls. The first dependency and the intervening offset-6 write may affect state relevant to the second dependency.

The third call receives object offset 16, eight bytes beyond the address supplied to the first two calls. This spacing does not prove that the regions are separate objects or that their accessible extents do not overlap.

The supplied object address is used for each offset calculation. No object pointer is loaded from a field, and no dependency return value replaces the base address.

### Arithmetic and width constraints

The represented address arithmetic adds the byte offsets 4, 6, 8, and 16 to a 32-bit address-bearing input. The evidence does not establish a supported overflow or wraparound policy. A conservative precondition is that these address calculations are valid in the target execution environment and identify the intended storage without relying on wraparound.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not reports of executed tests.

### Ordinary completion

Given valid addresses, no interfering execution, and dependencies that return normally, supplying state byte `0xA5` must produce the three calls and two byte writes in the established order, followed by a 32-bit return value of 1.

If the dependencies leave offsets 4 and 6 unchanged, both bytes contain `0xA5` on return.

### Full byte range

Under the same validity and normal-return conditions, state bytes `0x00`, `0x80`, and `0xFF` are copied as their respective eight-bit patterns. No visible Boolean conversion reduces `0x80` or `0xFF` to 1.

### Existing matching state

If offsets 4 and 6 already contain the requested byte, the function still calls all three dependencies and performs both writes. Matching prior state does not create a visible early-return path.

### Later modification of offset 6

Suppose the requested byte is `0x2C`, and a dependency running after the first write changes offset 6 to `0x91`. If execution otherwise completes, this function does not restore offset 6 to `0x2C`. It still performs the final offset-4 write with `0x2C`.

This example illustrates why “both fields equal the requested byte on return” requires an additional dependency-preservation condition.

### Modification of offset 4 before the final write

If a dependency modifies offset 4 and all calls subsequently return normally, the final explicit store overwrites that byte with the supplied state byte.

### Interrupted execution

If the first dependency does not return, neither direct write is reached. If the second dependency does not return, the offset-6 write has occurred, but the third call and offset-4 write are not reached. If the third dependency does not return, the offset-4 write and normal return are not reached.

These criteria specify ordering, not the mechanism of interruption or the state left by a dependency.
