# F-3678c8e0bd6c

## Purpose

F-3678c8e0bd6c conditionally processes a triangle described by three mutable records and a mutable context. It rejects certain flag combinations, determines an orientation bit, applies a context-controlled acceptance rule, optionally prepares record attributes, and submits either a triangle or a larger polygon through dependencies.

The geometry-processing interpretation is inferred from the determinant calculation, three-record input, optional clipping-like operation, and separate three-vertex and polygon submission calls. The established contract is the sequence of reads, mutations, dependency calls, and branching described below; rendering, clipping, lighting, and attribute-copy semantics are not established independently.

## Interface

**Inputs**

Four pointer-like, 32-bit address values:

1. A mutable context.
2. The first mutable record, designated **A**.
3. The second mutable record, designated **B**.
4. The third mutable record, designated **C**.

These designations describe argument positions, not storage ownership or distinctness.

**Output**

No explicit return value. Results are observable through dependency calls and memory mutations.

**Preconditions**

All accesses actually reached must address valid, suitably aligned storage. The context descriptor must be readable whenever its fields are reached. Nonnegative indices must identify usable attribute storage; this function performs no bounds checks.

Record distinctness is not checked. If records overlap one another or the context, earlier writes or dependency effects may affect subsequent reads.

## Behavior

### 1. Flag rejection and initial snapshots

The function first reads the three records’ 32-bit flags. If any bit from 2 through 7 is set in **all three** records, it returns immediately. No context access or dependency call is reached on this path.

If not rejected, it forms a six-bit activity mask from the union of those same flag positions. A nonzero mask later enables F-a6abddefd72e.

These are two separate flag computations. The contract does not require a particular ordering among the three reads within either combined expression, nor does it establish synchronization with concurrent writers.

The function then snapshots the coordinates needed for orientation. Later attribute preparation does not cause orientation to be recomputed.

### 2. Orientation calculation

Let each record have signed 32-bit coordinates \(x\), \(y\), and \(z\), taken from offsets `0x10`, `0x14`, and `0x1c`.

First, each coordinate is arithmetically shifted right by 12 bits. This preserves the sign and discards the low 12 bits; for negative values it is not equivalent to division rounded toward zero.

Using these shifted coordinates, the function calculates:

\[
D_s =
z_A(x_B y_C-x_C y_B)
-z_B(x_A y_C-x_C y_A)
+z_C(x_A y_B-x_B y_A).
\]

The products, subtractions, carries, and borrows collectively implement a signed 64-bit result. The shifted coordinate range is sufficiently small for this determinant to fit in signed 64-bit arithmetic.

The orientation bit is selected as follows:

- If \(D_s \leq -64\), the bit is **1**.
- If \(D_s \geq 64\), the bit is **0**.
- If \(-64 < D_s < 64\), the function evaluates the corresponding determinant using the original, unshifted coordinates and sets the bit to **1** only when that result’s 64-bit sign bit is set.

The unshifted calculation retains the low 64 bits of the determinant. Consequently, the fallback sign is the signed interpretation of a result modulo \(2^{64}\), not necessarily the sign of an unbounded mathematical determinant. Overflow must not be silently replaced with arbitrary-precision arithmetic.

A zero fallback result produces orientation bit **0**. There is no separate unconditional rejection for a zero determinant.

### 3. Context-controlled acceptance

The function compares the byte at context offset `0x901` with the calculated bit. Their inequality is the **orientation mismatch**.

This comparison is not a comparison of normalized Boolean values. For example, a stored byte value of two differs from either possible orientation bit.

Processing continues if either:

- The byte at `0x8ff` is zero; or
- The Boolean result of “byte at `0x914` equals one” equals the orientation mismatch.

Otherwise, the function returns without attribute preparation or submission.

### 4. Optional selected-attribute preparation

The signed descriptor index at offset `0x04` is read. A negative value skips this entire phase.

For a nonnegative index, the attribute selector is determined:

- Selector **0** when context byte `0x8fd` is zero.
- Otherwise, selector **2** when orientation mismatch is true and context byte `0x8fe` is nonzero.
- Otherwise, selector **1**.

When preparation is enabled by `0x8fd`, the function calls F-f370660ffa4f with the context, **C**, and the selector. After that call, it reads context byte `0x9ec`. If that byte equals one, it calls the same dependency for **A**, then **B**, using the same selector.

It then makes three F-02a35f55d6ef calls. Each call receives a selected-attribute address first and an indexed-attribute address second:

| Mode read at this phase | First call | Second call | Third call |
|---|---|---|---|
| `0x9ec` equals one | A selected attribute → A indexed address | B selected attribute → B indexed address | C selected attribute → C indexed address |
| Any other value | C selected attribute → A indexed address | C selected attribute → B indexed address | C selected attribute → C indexed address |

The arrows describe argument roles, not an independently established copy operation. F-02a35f55d6ef’s actual read/write semantics are unknown.

The descriptor pointer and its index are read again at multiple points in this phase:

- The initial nonnegative test uses an earlier read.
- A later read supplies A’s indexed address.
- Another read after the first dependency call supplies B’s indexed address.
- Another read after the second call supplies C’s indexed address.

Thus, dependency mutations can affect later addresses. The initial successful nonnegative check does not validate those later values. Likewise, the mode byte is read separately for preparation and selected-attribute routing; the two decisions need not agree if a dependency changes it.

### 5. Optional scalar attribute generation

The function next reads the signed descriptor index at offset `0x08`. A negative value skips this phase.

Otherwise, that index is retained for all direct stores in this phase.

The function reads C’s signed value at record offset `0x08`, negates it if negative, and calls F-96ada6d600f3 with the context and the resulting 32-bit value. It stores the dependency’s 32-bit result into C’s indexed slot.

It then reads context byte `0x9ec`:

- **Exactly one:** It independently transforms and stores B’s value, then independently transforms and stores A’s value. The call and store order is **C, B, A**.
- **Any other value:** It stores the result already obtained for C into A’s indexed slot, then B’s indexed slot. No additional scalar-transformation calls occur.

The sign-negation step has an important boundary: negating the 32-bit value \(-2^{31}\) cannot produce a positive signed 32-bit value. The supplied operations yield the same `0x80000000` bit pattern under 32-bit wraparound. A portable consumer must not assume this path produces a nonnegative signed value for every input.

Each scalar result is stored before a later dependency call. Earlier stores may therefore affect later reads when storage aliases.

### 6. Ordered record list and optional transformation

The function constructs an initial three-entry list of 32-bit record addresses:

- Orientation bit **1**: **A, C, B**.
- Orientation bit **0**: **A, B, C**.

The first record always remains first.

If the activity mask from the initial flags is zero, the count is three and this list is used directly.

Otherwise, the function calls F-a6abddefd72e with:

1. The context.
2. Initial count three.
3. The initial list.
4. A 64-byte temporary workspace.
5. An address through which the dependency can replace the active list pointer.

Its unsigned 32-bit return value becomes the output count. The active list pointer may still designate the original list or may designate other storage supplied by the dependency.

### 7. Final preparation and submission

For an output count of exactly **three**:

1. Call F-0a29566d2e48 for the first active-list entry.
2. Call it for the second entry.
3. Call it for the third entry.
4. Read context offset `0xa8c`.
5. Call F-306b6a90102c with that value and the three current list entries.

For an output count greater than **three**:

1. Visit the active list in increasing unsigned index order.
2. Call F-0a29566d2e48 once for each entry.
3. Read context offset `0xa8c`.
4. Call F-86f6806bc39e with that value, the active-list pointer, and the count.

Counts zero, one, and two cause no final preparation or submission calls.

The list entries used for submission are not established to be immutable across preparation calls. The submission handle is deliberately described as a late read, not an entry-time snapshot.

## Side effects

Direct record writes occur only in the optional scalar-generation phase. All other mutation attributable to dependency calls is dependency-defined.

There are no explicit allocation, deallocation, reference-count, or ownership-transfer operations in the supplied function. Temporary list storage and the 64-byte workspace are local to the invocation. Their use by dependencies does not establish permission to retain them after return.

The function provides no rollback. Attribute preparation and direct scalar stores can occur even when the later transformation returns fewer than three records and no submission follows.

There is no explicit error result, exception handling, pointer validation, count validation, or recovery from dependency failure. Faults or nonreturning dependency behavior are not converted into a status.

Address expressions use 32-bit pointer-like values and four-byte index scaling. Safe operation requires valid resulting addresses; the function supplies no protection against overflow, unsuitable indices, or a dependency returning an inadequately sized list.

## Acceptance examples

These are conditional contract examples, not executed tests.

1. **Common flag rejection.** If all three flag words contain bit 2, the function returns before orientation or context-dependent processing. Higher flag bits cannot cancel that rejection.

2. **Union without intersection.** If only A contains bit 2 and only B contains bit 3, the common-bit rejection does not occur. If context acceptance succeeds, F-a6abddefd72e is reached because the activity mask is nonzero.

3. **Orientation thresholds.** A shifted determinant of exactly \(-64\) selects bit 1 without fallback. Exactly \(64\) selects bit 0 without fallback. Values \(-63\), zero, and \(63\) require the unshifted fallback.

4. **Acceptance-mode equality.** With rejection enabled and orientation mismatch true, byte `0x914` must equal one to continue. A value of two does not satisfy that condition.

5. **Direct triangle path.** With no active flag bits, accepted context state, both descriptor indices negative, and orientation bit zero, the observable dependency sequence is preparation of A, B, C through F-0a29566d2e48, followed by F-306b6a90102c with A, B, C.

6. **Reversed order.** Under the same conditions but orientation bit one, both preparation and triangle submission use A, C, B.

7. **Shared scalar result.** With a nonnegative scalar index and mode byte not equal to one, one scalar-transformation call is made for C. Its result is stored in C, A, B order.

8. **Transformation removes submission.** If F-a6abddefd72e returns two, no F-0a29566d2e48 or submission call follows. Earlier attribute effects remain.

9. **Larger output.** If that dependency returns four and supplies a valid four-entry list, four ordered preparation calls precede one F-86f6806bc39e call. F-306b6a90102c is not used.
