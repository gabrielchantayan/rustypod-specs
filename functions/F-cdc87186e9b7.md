# F-cdc87186e9b7

## Purpose

F-cdc87186e9b7 searches for a target whose dependency-produced 32-bit value equals a requested value, then invokes an operation on that target with a caller-supplied 32-bit argument.

A mode argument selects one of three search forms:

- Mode 4 examines the object’s current backing-region base directly.
- Mode 3 searches directory entries through a nonzero, dependency-produced relative offset.
- Other modes search directory entries directly. Mode 5 additionally permits a fallback target after directory exhaustion.

The function returns either 0 or 11 on its explicit return paths. A return of 0 establishes that an operation dependency was invoked and returned; it does not establish that the dependency succeeded, because its return value is not checked.

“Object,” “directory,” and “target” are descriptive terms for the observed memory relationships, not established application-level types.

## Interface

### Arguments

1. **Object address**
   - Address of a mutable memory region.
   - The function reads fixed-offset fields and, outside mode 4, may overwrite its first byte.
   - The supplied evidence exposes a 32-bit address model.

2. **Requested comparison value**
   - A 32-bit integer compared for equality with results from F-d1e995cfb2d3.
   - No range restriction, normalization, or special sentinel handling is visible.

3. **Operation argument**
   - An opaque 32-bit value passed unchanged to F-cfb711b78946.
   - Whether it represents a scalar, address, handle, or another encoding is unknown.

4. **Mode**
   - A 32-bit integer.
   - Values 3, 4, and 5 have distinct behavior.
   - Every other value follows the ordinary directory-search path without fallback. There is no explicit invalid-mode rejection.

### Return value

| Value | Established meaning |
|---|---|
| 0 | A selected target was passed to F-cfb711b78946, that call returned, and the function reached its success return. |
| 11 | The direct target failed comparison, or directory search and any permitted fallback failed to produce a match. |

No separate status is exposed for malformed memory, failure inside a dependency, or an operation dependency reporting failure.

### Object layout used by this function

Offsets are byte offsets from the object address.

| Offset | Width | Observed use |
|---|---:|---|
| 0 | 8 bits | Saved before non-mode-4 preparation and restored only on the normal successful non-mode-4 path. |
| 8 | 8 bits | Unsigned displacement used to form the mode-5 fallback target. |
| 14 | 16 bits | Unsigned directory-start displacement, reread for each directory entry. |
| 20 | 16 bits | Unsigned entry count, read once after preparation. |
| 68 | 32 bits | Backing-region address, read at several independently observable points. |

The two 16-bit object fields use native multibyte loads. Their byte order is not established by the supplied representation alone. Directory offsets, in contrast, are explicitly assembled with the first byte as the high byte.

### Preconditions

Normal execution requires:

- Readable object fields for the chosen path.
- A writable first object byte when a non-mode-4 successful path reaches restoration.
- Readable directory bytes for every visited entry.
- Valid target memory and arguments according to the dependencies’ undocumented requirements.
- For mode 3, a valid output contract between this function and F-200380a3070f, particularly for the 16-bit offset subsequently consumed.

There are no visible null checks, allocation-bound checks, directory-bound checks, or target validation checks.

## Behavior

### Mode 4: direct-target path

Mode 4 bypasses preparation, entry-count loading, directory traversal, fallback processing, and first-byte save/restore.

The observable order is:

1. Read the 32-bit backing-region address from object offset 68.
2. Pass that address to F-d1e995cfb2d3.
3. Compare its result with the requested comparison value.
4. On inequality, return 11 immediately.
5. On equality, read object offset 68 again.
6. Pass this newly read address and the operation argument to F-cfb711b78946.
7. After that call returns, return 0.

The address used for comparison need not be the address used for the operation. A dependency may change the object’s backing-region field between the two reads. The function does not retain and reuse the first address.

### Shared setup for all other modes

For every mode other than 4:

1. Read and retain the byte at object offset 0.
2. Invoke F-8338e532dca9 with the object address and a second argument of zero.
3. Read the unsigned 16-bit entry count at object offset 20.
4. Begin traversal at directory index zero.

The count is captured after preparation. Changes to the count field during later dependency calls do not alter the traversal bound.

The directory-start displacement and backing-region address are not captured with the count. They are read again for each visited entry.

### Directory-entry interpretation

Entries are visited in increasing index order, from zero through the captured count minus one.

For each index:

- Read the unsigned 16-bit directory-start displacement from object offset 14.
- Form the directory byte position as that displacement plus twice the index.
- Read the 32-bit backing-region address from object offset 68.
- Obtain two bytes at that backing-region address plus the directory byte position and the following byte.
- Interpret those bytes as a big-endian unsigned 16-bit relative offset.
- Add that offset to the backing-region address captured for this entry to obtain the entry target.

The supplied representation establishes the two-byte interpretation but does not establish the relative evaluation order of the two individual byte loads.

The count can range from 0 through 65,535. For a visited entry, the largest index is 65,534. Consequently:

- Twice the index is at most 131,068.
- The directory byte position is at most 196,603.
- The second byte may be at position 196,604.
- An entry’s relative target offset is at most 65,535.

The directory-position arithmetic therefore does not overflow 32 bits solely because these fields contain their maximum values. Address additions remain 32-bit address calculations; the function performs no visible rejection of wrapping or out-of-range addresses.

### Mode 3: derived-target search

For each entry target in mode 3:

1. Invoke F-200380a3070f with the object address, entry target, and an address in local temporary storage.
2. Read a 16-bit field associated with that temporary output.
3. If the field is zero, skip comparison for this entry.
4. If nonzero, add its unsigned value to the entry target and pass the resulting address to F-d1e995cfb2d3.
5. Compare the dependency result with the requested comparison value.
6. On inequality, continue to the next directory entry.
7. On equality, form the operation target from the entry target and the temporary 16-bit field as read after the comparison call, then invoke F-cfb711b78946.

The temporary field is not visibly initialized by F-cdc87186e9b7 before F-200380a3070f is called. Correctness therefore depends on an undocumented output contract or other valid initialization supplied through that dependency.

The comparison address is formed before F-d1e995cfb2d3 runs. The operation address is formed afterward. Their equality must not be assumed if that dependency can alter the temporary field, directly or through a retained alias.

A matching entry ends traversal immediately after the operation call returns.

### Ordinary directory search

For every non-mode-4 mode other than 3, each entry target is passed directly to F-d1e995cfb2d3.

- A mismatch advances to the next entry.
- A match invokes F-cfb711b78946 with that captured entry target and the operation argument, then ends traversal.

Unlike the direct mode-4 and mode-5 fallback paths, this path uses the captured entry target for both comparison and operation. A later mutation of the object’s backing-region field does not itself change that captured address.

Duplicate matching entries are not all processed. Only the first visited match causes an operation.

### Exhaustion and mode-5 fallback

Traversal is exhausted when the index reaches the captured entry count without a match. A zero count reaches this state without reading any directory entry.

If the mode is not 5, exhaustion returns 11 immediately.

If the mode is 5:

1. Read the backing-region address and the unsigned byte at object offset 8.
2. Form the fallback target as backing-region address plus that byte plus 8.
3. Pass that target to F-d1e995cfb2d3.
4. On mismatch, return 11 immediately.
5. On equality, reread the backing-region address and the byte at offset 8.
6. Recompute the fallback target and pass it with the operation argument to F-cfb711b78946.

The fallback displacement ranges from 8 through 263 inclusive. No alignment requirement is enforced.

The fallback is attempted only after the entire captured directory range fails to match. An ordinary directory match in mode 5 prevents fallback processing.

The fallback comparison and operation can address different locations if F-d1e995cfb2d3 changes either contributing object field.

### Successful non-mode-4 completion

After a directory match or a successful mode-5 fallback operation returns, the function writes the originally saved byte back to object offset 0 and returns 0.

This restoration:

- Occurs after the operation dependency.
- Uses the byte saved before preparation.
- Can overwrite a change made by any intervening dependency.
- Does not restore any other object field.

Failure returns occur before this restoration. A return of 11 therefore does not imply rollback.

## Side effects

### Direct effects

The only explicit persistent memory write performed by this function is restoration of the first object byte on successful non-mode-4 completion.

Mode 4 performs no explicit object write. Unsuccessful non-mode-4 paths also perform no restoration write, even though preparation and other dependencies may already have changed state.

No allocation, deallocation, ownership transfer, or explicit resource-release operation is visible.

### Dependency effects

All four dependencies may have effects not described by the supplied evidence. Their names and call positions do not establish purity, memory ownership, preservation of object fields, or preservation of global state.

In particular:

- Preparation may alter fields that are read afterward.
- Per-entry calls may alter the directory displacement or backing-region address used on subsequent iterations.
- Changes to the count after its capture do not change the number of entries scheduled for traversal.
- A successful operation may alter the first object byte, but that byte is subsequently overwritten on non-mode-4 success.
- Early failure does not undo dependency effects.
- Abnormal termination inside a dependency prevents any later restoration or return described here.

The local temporary output in mode 3 is call-lifetime storage. Passing its address does not establish permission for a dependency to retain and later use it.

These examples are conditional static acceptance scenarios, not runtime observations. Unless a scenario says otherwise, assume valid memory, normal dependency returns, and no dependency mutations beyond those stated.

## Uncertainties

### Inferred intent

The layout and traversal suggest a compact, backing-region-relative directory, with mode 3 selecting a subordinate target and mode 5 allowing a secondary location. The domain meaning of those structures is not established.

Saving and conditionally restoring the first byte suggests temporary state management. It is not a general rollback mechanism and is not applied on failure.

### documented_only

The following remain undocumented rather than assumed:

- The native byte order of multibyte object fields.
- The semantic meaning of the first byte, directory entries, mode values, comparison values, and operation argument.
- The complete mode-3 temporary-output layout. The supplied representation places the consumed 16-bit field immediately after a 28-byte local area, but does not independently establish the dependency’s formal output structure or write extent.
- Whether mode-3 output is completely initialized on every call.
- Dependency side effects, alias retention, ownership rules, and failure behavior.
- Valid object sizes, backing-region sizes, alignment requirements, and concurrency rules.
- Platform behavior for invalid or wrapped addresses.
