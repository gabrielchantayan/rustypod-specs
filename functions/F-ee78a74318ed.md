# F-ee78a74318ed

## Purpose

F-ee78a74318ed conditionally creates and associates a payload-bearing record with a container, using a context value obtained from a dependency.

The successful path:

- Obtains a nonzero context value.
- Accepts a caller-supplied payload reference and a signed length.
- Obtains a container through a caller-provided slot, creating one when the slot is empty.
- Requires a container/context check to return zero.
- Creates a record and submits its payload field for population.
- Associates the record with the container.
- Writes the saved context into the record’s first word.
- Returns the 32-bit value 1.

All other returning paths return the 32-bit value 0. Failure handling is path-dependent: some failures only invoke a reporting dependency; others additionally submit both record and container references to cleanup and clear the caller’s slot.

“Container,” “record,” “population,” and “association” are descriptive roles inferred from access patterns. They do not establish the underlying object types, allocation mechanisms, or ownership contracts.

## Interface

The function has four inputs:

| Input | Representation visible in the supplied source | Role |
|---|---|---|
| Container slot | Pointer to a writable 32-bit word, or null | The word holds the container reference. It may be read, assigned a newly obtained container reference, or cleared. |
| Unused argument | 32-bit uninterpreted value | Not explicitly read, forwarded, or otherwise used by this function. |
| Payload reference | 32-bit integer used as a reference, with zero treated as absent | Passed to the length and payload-population dependencies. This function does not directly read the referenced bytes. |
| Length | Signed 32-bit integer | Compared against −1 and 64; potentially replaced by a dependency result; subsequently passed to payload population. |

The return value is a 32-bit word:

- **1:** The payload-population and association dependencies both returned nonzero, and the saved context was then written into the record’s first word.
- **0:** Any other normally returning outcome shown by the source.

The visible representation uses four-byte words and 32-bit reference values. This is a contract for the supplied representation, not a portable native-pointer interface.

The function directly accesses these fields:

| Object | Byte offset | Access |
|---|---:|---|
| Caller’s container slot | 0 | Read container reference; write a new reference or zero. |

A null container-slot pointer or zero payload reference is explicitly rejected, but only after the initial context dependency succeeds. A nonzero invalid reference is not made safe by these checks.

## Behavior

### 1. Acquire context before validating caller inputs

The first operation is a call to **F-aaeeb0735be1**, with argument 0.

If its result is zero:

1. Invoke **F-4fc89ec41a6d** with the three visible arguments 34, 125, and 131.
2. Return 0.

On this path, the function does not explicitly inspect the container slot, normalize the length, or invoke cleanup.

If the result is nonzero, retain that exact 32-bit value for subsequent checking and for the final record write. It is not reacquired later.

### 2. Check required references and normalize the initial length

With a nonzero saved context, a null container-slot pointer or zero payload reference leads to the generic rejection path described below.

Otherwise, if the length is exactly −1, call **F-1cb585febd84** with the payload reference and replace the working length with its result.

Next, compare the working length against 64 using the signed comparison visible in the source:

- Greater than 64: generic rejection.
- Equal to or less than 64: continue.

There is no explicit lower-bound rejection. In particular:

- Zero is admitted.
- Negative values other than −1 are admitted.
- A length-resolution result of −1 is admitted at this point.

The function itself performs no payload-size arithmetic and does not establish whether an admitted length is valid for the payload-population dependency.

### 3. Read or create the container

Only after the initial length check does the function read the caller’s container slot.

If the slot contains a nonzero reference, that reference becomes the working container. The newly-created-container initialization check is skipped.

If the slot contains zero:

1. Read the current container descriptor value and pass it to **F-e12621595ccc**.
2. Treat a zero result as a cleanup-path failure.
3. Otherwise, read the obtained container’s word at byte offset 0.
4. Call **F-8a2270f25b51** with that word and 0.
5. Treat a zero result as a cleanup-path failure.
6. Only after a nonzero result, write the obtained container reference into the caller’s slot.

Consequently, a newly obtained container is not published to the caller’s slot before the initialization check succeeds.

The creation dependency’s actual allocation behavior is unknown. The function only requires a usable nonzero result on the continuing path.

### 4. Check the container against the saved context

Call **F-e3cb7acb6263** with the working container and the saved context.

Its result controls two distinct paths:

- **Zero:** Continue toward record creation.
- **Nonzero:** Take the generic rejection path.

This function does not explicitly clean up or clear the container slot when this check returns nonzero. If the container was created during this invocation, the reference already published into the caller’s slot remains there, subject to any dependency side effects.

The interpretation “a matching record already exists” is plausible but not established by the supplied body. The contract depends only on zero versus nonzero.

### 5. Obtain and populate a record

Read the current record descriptor value and pass it to **F-e12621595ccc**.

A zero result enters the cleanup path.

For a nonzero record result:

1. If the working length is still exactly −1, call **F-1cb585febd84** again with the payload reference and replace the working length with its result.
2. Read the record’s word at byte offset 4.
3. Call **F-bbc440b3aefa** with that word, the payload reference, and the current working length.

A zero population result enters the cleanup path.

The second length-resolution opportunity matters only when the first resolution returned −1. There is **no second comparison against 64** after this later call. Therefore, a later result greater than 64 can reach payload population, provided all intervening operations succeed.

This is an observable control-flow property, not evidence that such a length is safe or intended.

### 6. Associate the record, then write its context

After a nonzero population result:

1. Read the working container’s word at byte offset 4.
2. Call **F-754616bec4de** with that word and the record reference.
3. If the association result is zero, enter the cleanup path.
4. Otherwise, write the saved context into the record’s word at byte offset 0.
5. Return 1.

The context write occurs **after** association returns successfully. The function does not explicitly initialize that field before passing the record to the association dependency.

Successful completion therefore requires the record reference to remain writable after association. Whether the association dependency retains, transfers, or otherwise manages the reference is not established.

### 7. Failure paths

#### Generic rejection

This path is used for:

- A null container-slot pointer, after successful context acquisition.
- A zero payload reference, after successful context acquisition.
- A working length greater than 64 at the initial length check.
- A nonzero container/context check result.

The function:

1. Invokes **F-4fc89ec41a6d** with the two visible arguments 34 and 126.
2. Returns 0.

No cleanup call or slot-clearing write is explicitly performed on this path.

#### Cleanup-path failure

This path is used for:

- A zero container-creation result.
- A zero initialization-check result for a newly obtained container.
- A zero record-creation result.
- A zero payload-population result.
- A zero association result.

The function performs these operations in order:

1. Invoke **F-4fc89ec41a6d** with 34, 126, and 65.
2. Invoke **F-ac669dc5909f** with the working record reference and the current record descriptor value.
3. Invoke **F-ac669dc5909f** with the working container reference and the current container descriptor value.
4. Write zero into the caller’s container slot.
5. Return 0.

The working record reference is initially zero, so cleanup may receive zero. Container-creation failure also causes container cleanup to receive zero.

Cleanup is not restricted to containers created by this invocation. A preexisting container is submitted to cleanup, and its caller slot is cleared, if a later record-stage operation fails.

## Side effects

### Explicit memory effects

The function can explicitly:

- Publish a newly obtained container reference to the caller’s slot.
- Write the saved context into the record’s first word.
- Clear the caller’s slot after cleanup-path failure.

It does not explicitly write the caller’s unused argument or payload storage. Payload modification, copying, retention, or allocation may occur within dependencies, but cannot be established here.

### Ordering and dependency interference

All described reads and writes occur in the stated order, assuming dependencies return normally.

In particular:

- The initial context call precedes caller-input rejection.
- Initial length resolution precedes the container-slot read.
- New-container publication precedes the container/context check.
- Record population precedes association.
- Association precedes the final context write.
- Error reporting precedes both cleanup calls.
- Both cleanup calls precede clearing the caller’s slot.

No dependency is assumed to preserve global state or caller-accessible memory. The working container and record references are retained locally; the container slot is not reread to select cleanup targets after those references have been obtained.

Descriptor values are read at their individual call sites. A descriptor supplied during cleanup is not established to equal the value supplied during creation, because intervening dependencies may modify it.

There is no explicit rollback after successful payload population or after a failed association attempt beyond the cleanup calls. Their ability to undo partial effects is unknown.

### Ownership

The body establishes which references are passed to cleanup, not whether cleanup frees, decrements, resets, or merely visits them.

On success, neither the record nor the container is submitted to cleanup by this function.

On generic rejection, neither is submitted to cleanup by this function.

On cleanup-path failure, both working references are submitted, including a preexisting container and possible zero references. Consumers must not assume failure preserves their original container.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, dependencies return normally, provide valid objects where required, and do not introduce additional memory mutations.

1. **Unavailable context overrides otherwise valid inputs.**  
   If context acquisition returns zero, the function reports with 34, 125, 131 and returns 0. It does not explicitly read the container slot.

2. **Invalid required reference after context acquisition.**  
   With a nonzero context and either a null slot pointer or zero payload reference, the function reports with 34, 126 and returns 0 without explicit cleanup.

3. **Upper boundary.**  
   An explicit length of 64 passes the initial length check. An explicit length of 65 is rejected before the container slot is read.

4. **Negative length other than the sentinel.**  
   An explicit length of −2 is not resolved and is not rejected by the initial check. If record creation is reached, −2 is passed to population. Final success still depends on population and association returning nonzero.

5. **Ordinary inferred length.**  
   For input length −1, if length resolution returns 12, that value is checked, then later passed to population. No second resolution occurs.

6. **Repeated sentinel resolution.**  
   If the initial resolution returns −1, and the second resolution later returns 80, population receives 80 without another upper-bound check. This does not assert that population accepts 80.

7. **New container followed by check rejection.**  
   If an empty slot receives a successfully initialized container but the container/context check returns nonzero, the function returns 0 through generic rejection. It does not explicitly clear the published slot or invoke cleanup.

8. **Failure affecting a preexisting container.**  
   With a nonzero initial slot, a zero container/context check, and failed record creation, cleanup receives zero for the record, then the preexisting container reference. The slot is subsequently cleared.

9. **Successful association ordering.**  
   If population and association both return nonzero, the saved context is written to the record only after association returns. The function then returns 1 without explicit cleanup.
