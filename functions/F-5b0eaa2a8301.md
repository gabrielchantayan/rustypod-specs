# F-5b0eaa2a8301

## Purpose

F-5b0eaa2a8301 resolves a request through identifier-based lookup, searches involving three caller-supplied record regions, and a fallback operation. Successful completion returns zero and publishes a 32-bit identifier, a 16-bit position, and an eight-bit indicator. Failure returns a selected nonzero status and clears those three outputs after record-processing calls.

The record regions are designated **first**, **middle**, and **third** by argument order. The terms **preceding** and **following** distinguish two search routes; they do not establish domain relationships or ordering between objects.

Search results are not ordinary error statuses in this interface. Their full 32-bit values control some acceptance decisions and supply the eventual indicator, truncated to eight bits. Preliminary processing, lookup, record processing, and fallback have separate status rules.

This contract describes established static behavior. Dependency semantics, resource ownership, and several initialization guarantees remain unresolved. No runtime tests have been performed.

## Interface

### Arguments and return value

| Argument | Established requirements and use |
|---|---|
| Context | A 32-bit address-like value passed to dependencies. A conditional direct access increments its signed 32-bit field at byte offset 100. |
| Request | A 32-bit address-like value. Zero selects failure status `0x308`; otherwise, executed request accesses must be valid. |
| First record region | Writable storage whose first 32 bits are directly accessed; also passed to dependencies. |
| Middle record region | Writable storage whose first 32 bits are directly accessed; destination for initial lookup and fallback. |
| Third record region | Writable storage whose first 32 bits are directly accessed; also passed to dependencies. |
| Identifier output | Writable 32-bit destination. |
| Position output | Writable 16-bit destination. |
| Indicator output | Writable eight-bit destination. |

The return value is a 32-bit status. Every ordinary completion writes all three scalar outputs.

Four bytes is only the minimum record extent established by direct accesses. Dependency requirements may be larger. The external-operation argument `0x14` does not, by itself, establish a record size or transfer length.

### Request and object layouts

Following successful preliminary processing, the request’s 32-bit field at byte offset 4 supplies the current identifier. Searches and fallback receive the address **28 bytes beyond the request base**, not an address loaded from that location. The layout and extent of this embedded request data are unknown.

Each record’s first 32-bit word is interpreted as an object address when the relevant route examines it.

| Object location | Established use |
|---|---|
| Base address | Input to certain identifier-helper calls. |
| Base address plus 4 | Input to preceding-route identifier-helper calls. |
| Byte offset 8 | Eight-bit marker compared with signed −1, corresponding to `0xFF`. |
| Byte offset 10 | A 16-bit eligibility value, also used later as an unsigned position bound. |

Eligibility requires the marker to match and the 16-bit value to be nonzero. Marker failure prevents the eligibility-value read. The nonzero test uses a signed 16-bit interpretation, but later position comparisons use an unsigned interpretation. Thus, `0x8000` satisfies eligibility and supplies a bound of 32768.

### Internal storage and validity

Dependencies receive a four-byte preliminary-result region, a four-byte main-position region, two separate four-byte side-position regions, a 128-byte scratch region, and a four-byte current-identifier destination. Only the first preliminary-result byte and the first 16-bit element of each side-position region are directly interpreted. The published position is the main position’s low 16 bits.

The preliminary-result, position, and scratch regions have no explicit local initialization before their initial dependency use. Defined behavior requires every subsequently consumed value to have been established. A successful dependency status alone does not document that guarantee.

There are no general pointer, extent, alignment, or overlap checks. All executed accesses require valid storage. A zero request does not exempt the record and scalar-output arguments from validity requirements.

No non-aliasing guarantee is established. Earlier stores can affect later reads when caller-provided regions overlap. The observable ordering below remains relevant, but independent final values cannot be promised for overlapping destinations.

Address additions require valid accessible locations; portable address-wraparound behavior is not established. Signed overflow of the context increment is unresolved.

## Behavior

### Qualification and initial lookup

The first, middle, and third record head words are cleared in that order before any dependency call. Only their initial four bytes are cleared.

A zero request selects status `0x308` without preliminary processing. For a nonzero request, F-60be901ce2de receives the context, request, and preliminary-result destination. Any nonzero result becomes the failure status.

After preliminary success, the request identifier is read. A zero first byte in the preliminary result bypasses initial lookup and leads to fallback preparation. A nonzero byte enables F-5f9a16493218 to look up that identifier into the middle record.

Initial lookup status zero permits middle-object examination. Status `0x24` instead permits fallback preparation. Every other nonzero lookup status selects failure. An ineligible middle object also leads to fallback preparation.

### Middle-search outcomes

An eligible middle object enables one increment of the signed 32-bit context field at offset 100. F-8a92d5d60703 then receives the context, the object referenced by the middle record, the embedded request address, and the main-position destination. Its return replaces the candidate indicator, whose initial value is zero.

A return of exactly one accepts immediately, without checking the position against a bound. Otherwise, the main position’s low 16 bits determine the route:

| Position condition | Outcome |
|---|---|
| Zero | Preceding route. |
| Nonzero and at least the unsigned middle bound | Following route. |
| Nonzero and below that bound | Fallback preparation. |

The zero-position decision does not read the middle bound. When the bound is needed, it is obtained through a fresh middle-record head read after the search.

The middle object address is not a stable snapshot across this stage. Marker and eligibility-value accesses obtain it separately, and the search obtains it again after the context increment. Aliasing or dependency changes can therefore make different accesses refer to different objects. No revalidation of the searched object is performed after the increment.

### Preceding-route outcomes

F-4055be9c3f18 first receives the address four bytes beyond the currently referenced middle object. A zero result accepts without replacing the current identifier. A nonzero result becomes the current identifier.

When the first result is nonzero, a separate invocation of F-4055be9c3f18 receives a freshly obtained middle-object address plus four. Its result supplies the identifier for lookup into the first record. The two helper results are independent; even a zero second result is used for lookup.

Any nonzero side-lookup status selects failure, including `0x24`. On successful lookup, the first object address is captured for its eligibility checks and, if eligible, its search. Ineligibility leads to fallback preparation.

The preceding search uses its own side-position destination and replaces the candidate indicator. Acceptance depends on both its result and position:

| Search outcome | Disposition |
|---|---|
| Result exactly one | Paired-operation acceptance, regardless of the side position or bound. |
| Other result; side position zero | Fallback preparation. |
| Other result; nonzero side position below the unsigned bound | Paired-operation acceptance. |
| Other result; nonzero side position at least the unsigned bound | Boundary acceptance. |

For the non-one boundary decision, the bound comes through the first record after the search; it need not belong to the object searched.

Boundary acceptance replaces the current identifier with the result of F-4055be9c3f18 applied to the current first object’s base address. Zero is accepted as that replacement. This form of acceptance performs no paired external operations and makes no local assignment to the main position.

Paired-operation acceptance invokes F-EXT-1 with third and middle record addresses, then invokes it with middle and first record addresses. Each invocation also receives `0x14`. After both calls, the first record head is cleared. Only then is the preceding-side position read and assigned to the main position’s low 16 bits; its upper 16 bits are locally preserved.

Entering this route establishes that the main position was observed as zero earlier, not that the published position must remain zero. Its destination has already been exposed to a dependency.

### Following-route outcomes

The first following-route invocation of F-4055be9c3f18 has an unresolved argument contract. It is not established as a zero-argument interface.

A zero result accepts without replacing the current identifier. A nonzero result becomes the current identifier and permits another helper invocation, this time using the current middle object’s base address. The second result supplies the lookup identifier for the third record.

Every nonzero third-record lookup status selects failure. Following successful lookup, the third object address is captured for eligibility and search. Ineligibility leads to fallback preparation.

The following search receives the following-side position destination and replaces the candidate indicator. Acceptance requires that position’s first 16-bit element to be strictly below the unsigned bound obtained through the third record after the search. Search result one has no exceptional acceptance rule here. Equality or a greater position leads to fallback preparation.

Accepted following-route processing invokes F-EXT-1 with first and middle record addresses, then with middle and third record addresses, each time also supplying `0x14`. After both calls, the third record head is cleared. The following-side position is then read and assigned to the main position’s low 16 bits, locally preserving its upper half.

On both side routes, the position ultimately assigned is read after the external operations and record-head clear. It need not equal an earlier position used for qualification.

### Fallback and completion

Fallback preparation processes the first, middle, and third records through F-b0f922796692 in order. A nonzero result stops preparation, skips later preparation calls, and selects failure with that result.

After three zero preparation results, F-5d3e17c1b8e7 receives the context, embedded request address, scratch region, current-identifier destination, middle record, and main-position destination, in that order.

Fallback status zero accepts and replaces the candidate indicator with one. Status `0x20` also accepts but leaves the candidate indicator locally unchanged. Every other status selects failure. Neither the current identifier nor the main position is reset locally before fallback.

Accepted completion writes the identifier output first, the main position’s low 16 bits second, and the indicator’s low eight bits third, then returns zero. There is no common final record-processing pass on acceptance.

Failure processes all three records through F-b0f922796692 in first–middle–third order. These calls are unconditional within failure processing, and their return values are ignored. The identifier, position, and indicator outputs are then cleared in that order, at widths of 32, 16, and eight bits, respectively. The selected failure status is returned.

A record may consequently be processed multiple times during one invocation. Failure processing does not locally clear record heads after the dependency calls.

## Side effects

Established direct caller-storage effects are the entry record-head clears, the conditional context increment, the applicable side-route record-head clear, and the ordered scalar-output writes.

Only an eligible middle-search path performs the context increment. Side searches do not repeat it. Later fallback or failure does not roll it back.

Dependency calls may modify records, objects, exposed internal destinations, or other accessible state under contracts not supplied here. Fresh record-head reads and late position reads must not be replaced with preservation assumptions. Likewise, a value written to an earlier output may overlap storage subsequently read for another output.

F-EXT-1 results do not influence local control flow. Neither its argument order nor `0x14` establishes copy direction, copy size, allocation, release, or ownership transfer.

F-b0f922796692 may have a reset or release purpose, but that is inferred intent only. This function establishes no complete allocation, retention, or release responsibility. Success and failure do not imply that any particular resource has been acquired or freed.

## Acceptance examples

These examples are conditional static consequences, not observed executions. All require valid accesses and defined values wherever consumed.

1. **Zero request.** Entry clears all three record heads. Preliminary processing is skipped. Failure processing visits all three records before clearing the scalar outputs and returning `0x308`.

2. **Lookup-status distinction.** Initial lookup returning `0x24` permits fallback preparation. Either side lookup returning `0x24` instead selects failure.

3. **Immediate middle acceptance.** An eligible middle search returns one and establishes position seven. Acceptance does not compare seven against the middle bound. The context increment has already occurred.

4. **Fresh middle bound.** A middle search returns two, establishes position five, and changes the middle record to reference an object whose bound is four. The following route is selected using four, not an earlier bound.

5. **Independent helper results.** Preceding-route helper results ten and eleven make ten the current identifier and eleven the first-record lookup identifier.

6. **Preceding boundary acceptance.** A preceding search returns a value other than one and establishes a nonzero position equal to the fresh bound. The boundary helper supplies the accepted identifier, even if its result is zero. No paired external operations or local main-position replacement occur.

7. **Preceding exact-one exception.** A preceding search returns one with side position zero. Paired-operation acceptance still applies. If the late side-position read remains zero, zero replaces the main position’s low half.

8. **Following equality.** A following search returns one with position equal to the fresh bound. Fallback preparation follows; result one does not override equality.

9. **Late position change.** Following position two qualifies against bound ten. If the external operations change the exposed side position to nine, and the subsequent record-head clear does not change it again, nine is assigned to the main position.

10. **Indicator truncation.** A qualifying following search returns `0x102`. Acceptance publishes indicator `0x02`; the search return is not treated as an error status.

11. **Fallback `0x20`.** Fallback establishes defined identifier and position values and returns `0x20`. A prior candidate indicator of two remains two rather than being locally replaced with one.

12. **Preparation failure.** First-record preparation succeeds and middle-record preparation fails. Third-record preparation is skipped. Failure processing nevertheless visits all three records and ignores their results before clearing outputs.

- The argument contract of the first following-route helper invocation.
- Complete record, object, and embedded-request layouts, including required extents and alignment.

- Dependency initialization, preservation, global-state, retention, and ownership guarantees.
- Whether every accepting path establishes a defined main position, especially fallback status `0x20` without an earlier defining search.
- Signed-overflow behavior of the context increment.
- Concurrency, reentrancy, and reference-invalidation rules.
- Overlapping-storage behavior beyond the established local read/write ordering.

The route names suggest adjacent records, and record processing suggests resource management. Those interpretations are inferred intent, not established behavioral requirements.
