## Behavior

### Iteration entry and initial access

Each iteration starts with a 64-bit working value. Initially this is composed from the first two inputs; subsequently it is the result of F-D07 from the preceding iteration.

Before modifying that working value, the function retains its high word as the iteration-entry address. It also captures the low eight bits of the fourth carried word.

The signed 32-bit interpretation of the working value’s low word is multiplied by 32, and the result is assigned to an unsigned 32-bit quantity. The function then attempts a 32-bit store of that quantity at the address numerically equal to the quantity.

Only after this store does it compare the quantity, as unsigned, with 20. The comparison does not validate or protect the access.

When the signed multiplication is defined, its result is a multiple of 32. Under the stated conversion interpretation, the only such result below 20 is zero. That case still attempts a 32-bit zero store at address zero.

### Short path

A scaled quantity below 20 selects zero as the argument for F-D03 and proceeds to the common continuation.

This path skips all longer-path stores, both longer-path calls, and the function’s direct assignments to the designated global. It does not initialize or replace the inherited address/data word, word pointer, offset word, or link-like state.

The absence of a direct global assignment on this path does not establish that dependencies leave the global unchanged.

### Longer path before F-D02

A scaled quantity of at least 20 enters the longer path.

The first additional access stores the inherited address/data word as 32 bits at the scaled address plus 88 bytes. The next access stores the low 16 bits of the inherited word-pointer address at the address/data word plus 14 bytes.

The third carried word is then replaced by the address/data word shifted left by two using unsigned 32-bit arithmetic.

Next, the function assigns the captured low-byte value to the designated global. This establishes the assignment’s source value, not a one-byte destination access. The function does not read the global’s previous contents to perform this assignment.

F-D01 is invoked afterward, with the inherited word-pointer address converted to unsigned 32 bits and logically shifted right by two. The link-like state is then assigned hexadecimal 0897EE1D, and F-D02 is invoked to obtain a represented 64-bit result.

The captured byte remains a separate represented value. A dependency’s modification of the global does not, by itself, replace the byte later used in the explicit 8-bit store.

### Longer-path accesses using F-D02’s result

Both halves of F-D02’s result are used as addresses without represented validation.

The first access writes the captured byte at twice the result’s low-word address. This address calculation includes a signed conversion and signed multiplication; arbitrary low-word values do not have established defined behavior.

The next access writes the low eight bits of the result’s high word at its low-word address plus **eight bytes**. The offset follows one 64-bit element, not one byte.

A 32-bit pointer value containing the iteration-entry address is then stored at twice the inherited signed offset. After that, the complete 64-bit F-D02 result is stored at its own low-word address.

The offset state is replaced with four times the iteration-entry address, using the represented signed conversion and multiplication. The address/data state is replaced by the inherited word-pointer address converted to a signed integer and shifted left by eight.

Three consecutive 32-bit stores then populate storage at the iteration-entry address:

| Byte offset | Stored value |
|---|---|
| 0 | Current third carried word |
| 4 | Updated address/data word |
| 8 | Inherited word-pointer address |

The iteration-entry address and F-D02’s high-word address are separate values. The former supplies this three-word destination; the latter supplies a branch-specific destination or later state calculation.

All destinations may overlap. Consequently, later stores may overwrite earlier byte stores, the stored pointer, or portions of the 64-bit result. No non-aliasing, object structure, or atomicity is established.

### Unresolved branch computation

After these stores, the branch quantity is derived from the inherited word-pointer address by conversion to a signed integer, left shift by 31, right shift by 32, conversion to unsigned 32 bits, and logical right shift by 20.

For a 32-bit signed intermediate, shifting right by 32 is outside the ordinary defined shift-count range. The signed left shift is also not generally defined for arbitrary pointer bit patterns.

The branch quantity therefore remains **documented_only**. It cannot be specified as always zero, sign-derived, or evaluated using masked shift counts without additional evidence. Both represented downstream paths must remain in the contract.

### Conditional zero branch

If the branch quantity is zero, the function first assigns zero to the designated global. As with the earlier assignment, the destination access width and affected storage extent are unknown.

The function then adds the current third carried word to the offset state and retains the result as the new offset state. The mixed signed/unsigned addition has unsigned 32-bit arithmetic under the represented widths; assigning its result back to signed state requires the applicable conversion semantics. Under the conditional bit-preserving interpretation, the retained bit pattern is the sum modulo \(2^{32}\).

That result is stored as 32 bits at F-D02’s high-word address. Zero is selected as the F-D03 argument.

This branch contains no software breakpoint. The global’s zero assignment is a branch-specific effect, not evidence of universal restoration or cleanup.

### Conditional nonzero branch

If the branch quantity is nonzero, it is stored as 32 bits at the address obtained by multiplying the third carried word by 256 and adding 32. These operations use unsigned 32-bit arithmetic.

The link-like state is then assigned hexadecimal 08790D52. The F-D03 argument is selected by taking the unsigned 32-bit product of the third carried word and 256, interpreting that product as signed, and shifting right by 29.

The function next executes software breakpoint immediate 4. The preceding store and argument selection occur before this breakpoint.

No breakpoint handler, termination rule, or state-preservation guarantee is supplied.

### Common continuation

The short path and both longer-path outcomes converge on F-D03, using the selected argument and the current link-like state. F-D03 supplies a represented 64-bit result.

The function first stores the low 16 bits of this result at its low-word address. It then multiplies the carried address/data word by 64 using unsigned 32-bit arithmetic and stores the product as 32 bits at the address numerically equal to that product.

Next, it reads and retains a 32-bit word through the current word pointer. A subsequent 16-bit store targets the address/data word plus four bytes. Under the stated truncating-storage interpretation, its stored bit pattern is the low 16 bits of the current word-pointer address plus four.

The function then reads a 32-bit pointer value at F-D03’s high-word address plus 80 bytes and replaces the carried word pointer with that value. The represented calculation includes a signed conversion and addition; exact behavior outside their defined range remains unresolved.

F-D04 and F-D05 are invoked in that order without explicit arguments. F-D06 follows with the retained 32-bit read value.

After F-D06, the link-like state is assigned hexadecimal 0897EDF1. The fourth carried word receives the current third carried word. F-D07 is then invoked with the retained read value logically shifted right by three. Its 64-bit result becomes the next iteration’s working value. Finally, the third carried word receives the retained read value, and execution repeats.

The retained read precedes the later 16-bit store, replacement-pointer read, and calls. Overwriting the memory from which it was read does not retroactively change that represented value.

The fourth-word update uses the third word before its final replacement. The next iteration’s captured byte therefore comes from that earlier third-word state, not necessarily from the retained read.
