# F-561b9cd0014b

## Purpose

F-561b9cd0014b recognizes one of three named encodings or initializes and populates a custom encoding from parser input.

Named recognition writes an encoding discriminator. Custom processing stores a count, obtains two dependency results, initializes an embedded name table, supplies default names, and processes explicit name assignments until a terminator or input exhaustion.

This contract describes statically established behavior, including incomplete validation and partial state changes. It does not establish allocator semantics, callback progress, resource ownership, or cleanup guarantees.

## Interface

### Inputs and result

The function accepts two addresses:

- A mutable destination/context object.
- A mutable parser object.

The represented interface uses 32-bit addresses and 32-bit integer words. There is no explicit return value. Results are observable through object fields, dependency calls, diagnostics, and writes into stored names.

Offsets below are byte offsets. They describe accessed storage, not complete object definitions.

### Preconditions and arithmetic

Every accessed object, callback target, input byte, dispatch pointer, global diagnostic object, table entry, and destination byte must be valid at the moment of access.

Counts, slots, and loop counters are represented as signed 32-bit integers. Resource values and addresses are 32 bits. No explicit nonnegative-count check, slot-range check, or arithmetic-overflow check is present.

Input guards use address additions and comparisons. Ordinary bounded-buffer interpretation requires contiguous storage and nonwrapping address arithmetic. Name lengths use a 32-bit cursor difference plus one. Stored-name selection uses a slot multiplied by four, followed by address additions. Behavior outside valid arithmetic and storage conditions is documented_only.

In particular, callbacks must not leave an unreadable cursor at the explicit-name selection point: that point dereferences the cursor before testing its relationship to the captured end bound.

## Behavior

### Entry and live dispatch reads

Before the first callback, the function captures the parser end bound and the pointer stored at context offset `0x1e4`.

It invokes the callback at parser offset `0x1c`, then reads the parser cursor. This cursor is both the initial input position and the initial saved position used by custom completion.

If that cursor is at or beyond the captured end, the function calls F-4457a9a44a68 with an out-of-bounds diagnostic, writes `3` to parser status, and returns.

Otherwise, F-cfad0582408b receives the byte read from that saved initial address. Subsequent dispatch does not rely solely on the byte supplied to this call:

- If the classifier returns zero, the function rereads the byte at the saved initial address. A value other than `[` selects named recognition.
- A nonzero classifier result selects custom processing without that conditional dispatch reread.
- Once custom processing is selected, the function separately rereads the byte at the same saved address to choose bracket or indexed mode.

These are live reads of input storage, not a single cached character. A classifier that changes the input byte can change the selected path or custom mode. The parser cursor itself is not reread to choose the address for these character checks.

Bracket mode therefore means that the custom-mode reread observed `[`. Indexed mode means that reread observed another byte; the function does not explicitly require a nonzero initial classifier result at this later point. Under stable input, indexed dispatch follows a nonzero result, but that is not an unconditional contract across differing live reads.

Character promotion for bytes above `127` is not established.

### Named recognition

The function attempts fixed-length comparisons through F-fca51b715561 in this order:

| Candidate | Comparison length | Minimum remaining input under nonwrapping arithmetic | Discriminator |
|---|---:|---:|---:|
| `StandardEncoding` | 16 bytes | 18 bytes | `2` |
| `ExpertEncoding` | 14 bytes | 16 bytes | `4` |
| `ISOLatin1Encoding` | 17 bytes | 19 bytes | `3` |

A comparison occurs only if its guard passes. A zero comparison result selects the candidate, writes the one-byte discriminator, and returns. Comparisons use the saved initial address, not a cursor refreshed after the classifier or preceding comparisons.

The guards are stricter than merely requiring the compared bytes. No delimiter check follows a successful prefix comparison. Additional non-delimiter characters do not prevent recognition if the dependency reports a match.

If no candidate matches, parser status becomes `162` (`0xa2`).

Named success does not directly advance the cursor, clear an existing status, reset custom counts, or release resources. Dependencies may independently change state.

### Custom count selection

Custom processing captures the value at parser offset `0x10` for later calls, then performs the separate input-byte reread that selects its mode.

- **Bracket mode:** count becomes `256`. The function increments the parser’s current cursor field by one. This increments the live field, which need not still equal the saved initial address.
- **Indexed mode:** the callback at parser offset `0x24` supplies the signed 32-bit count.

The callback at offset `0x1c` is then invoked. If the resulting cursor is at or beyond the captured end, the function returns without directly installing the count, requesting resources, or assigning the custom discriminator or a new status.

Otherwise, it stores the count first at context offset `0x170`, then at parser offset `0x60`. No count validation or parser-status check intervenes.

### Resource calls and initialization dispatch

The function calls F-6dd003795db7 with these six positional arguments:

1. The captured value from parser offset `0x10`.
2. `2`.
3. Zero.
4. The custom count.
5. Zero.
6. An address for a 32-bit status result.

It stores the returned 32-bit value at context offset `0x17c` before testing the reported status.

If that status is zero, it makes a second call with the same argument pattern except that the second argument is `4`. The returned value is stored at context offset `0x180` before its status is tested.

Interpretation of `2` and `4` as element sizes is inferred only. The dependency implementation does not establish allocation semantics or the meanings of either zero argument.

A nonzero reported status stops initialization and is copied to parser status.

After both calls report zero, the initialization target is resolved through two later reads:

- The function reads the first 32-bit word through the pointer captured from context offset `0x1e4`.
- It treats that word as another address and reads the callback address through it.

Only the outer pointer was captured at entry. The intermediate pointer and callback address are read at initialization time, after both resource calls. Earlier callbacks or dependencies can therefore affect these later reads by modifying the referenced storage. Changing the context field itself does not replace the captured outer pointer.

The resolved callback receives the embedded parser object at offset `0x64`, the custom count, and the captured parser-context value. A nonzero return is copied to parser status and terminates processing.

On success, the function invokes the name-storage callback for each signed index from zero through count minus one, supplying the embedded object, index, default text `.notdef`, and length `8`. Return values are ignored, and parser status is not inspected during this loop.

Zero and negative counts cause no default-name calls. They do not, by themselves, prevent resource calls, initialization, or entry into custom-content parsing.

### Custom-content processing

The function maintains a successful-explicit-name count, initially zero. Each iteration invokes the callback at parser offset `0x1c`, then reads the current cursor.

If that cursor is at or beyond the captured end, normal custom completion occurs: discriminator `1` is written, the parser cursor is replaced with the saved completion position, and the function returns. Input exhaustion does not itself produce a missing-terminator error.

#### Explicit terminators and diagnostic reads

A `def` prefix terminates parsing when four bytes are available and F-36b9d1fbbb1c returns nonzero for the byte following the three letters. The saved completion position becomes the address immediately after `def`, before the following byte.

A closing bracket terminates parsing with a saved completion position immediately after `]`. Both terminators are usable in either custom mode.

Each accepted explicit-terminator path accesses diagnostic state before completing:

- It reads a base address held in global storage.
- Through that base, it reads a signed 32-bit field at byte offset `0x7c`.
- If that field is greater than `5`, it calls F-4457a9a44a68 with an encoding-end diagnostic.

On the `def` path, these global and field reads occur after F-36b9d1fbbb1c returns a nonzero result. They precede any diagnostic call. The diagnostic base and level are not captured at function entry, and the delimiter classifier can affect the later values read.

After this diagnostic handling, completion writes discriminator `1` and the saved cursor. Input-exhaustion completion does not perform this diagnostic access.

The prefix alone is insufficient: `def` with no fourth byte, or with a following byte rejected by F-36b9d1fbbb1c, is not an accepted terminator.

#### Skipping versus selecting a slot

For nonterminating input, F-cfad0582408b classifies the byte at the iteration’s saved token position.

If its result is zero in indexed mode, the token-skipping callback is invoked. The completion position is then saved as that token’s original starting address, not the callback’s resulting cursor. Parser status is not directly checked on this skip path.

Otherwise, a candidate slot is selected:

- Bracket mode uses the successful-explicit-name count.
- Indexed mode calls the integer callback and then the normalization callback.

After those calls, the function reads the parser cursor and saves it as the completion position. It immediately dereferences that address to test for `/`.

There is no renewed cursor-versus-end check before this dereference. Only if the byte is `/` does the function test whether the cursor plus two is strictly below the captured end. Only after that guard passes does it compare the successful-name count with the custom count.

Thus the slash read is unconditional once this selection point is reached. The later guards do not make an unreadable cursor safe.

The count comparison limits successful insertions, not the selected slot. Negative or out-of-range indexed slots are not directly rejected.

#### Explicit-name storage

When the slash and both later guards pass, the function advances the parser cursor by one byte past `/` and saves that name-start address. It invokes the token-skipping callback, then checks parser status. A nonzero status returns immediately.

Otherwise, it captures the resulting cursor as the name end and invokes the name-storage callback with:

- The embedded name-table object.
- The selected slot.
- The saved name-start address.
- The 32-bit name-end difference plus one.

The callback result is written to parser status. A nonzero result returns immediately.

On success, the successful-name count increases. The function then reads the live table base at parser offset `0x7c`, reads the selected 32-bit name address at four times the slot offset, and writes a zero byte at the previously captured name-length offset within that name.

The table lookup occurs after the storage callback. The callback may therefore change the table used for termination. The termination offset remains based on the name end captured before that callback.

If any selection guard fails, no direct error is assigned and iteration resumes. Progress depends on callback behavior.

## Side effects

Direct writes include the discriminator, both count fields, both resource-result fields, parser cursor, parser status, and stored-name terminators.

The saved completion position can be:

- The initial post-normalization cursor.
- An unrelated token’s original start after skipping it.
- The cursor observed during slot selection.
- The address after an accepted slash.
- The address after an explicit terminator.

Consequently, end-of-input completion can move the parser cursor backward.

The operation is not transactional. Counts and resource results can remain installed after failure. Default names and explicit names can remain partially populated. Error returns do not perform normal custom-completion writes.

No release operation is directly visible. Dependencies may have additional effects, including global mutations and memory management. Their ownership, preservation, and cleanup behavior is not assumed.

## Acceptance examples

These are conditional static expectations, not executed tests. Assume valid storage, nonoverflowing arithmetic, and no unmentioned mutations.

1. **Initial bound reached.** If the first normalization leaves the cursor equal to the captured end, the bounds diagnostic is called and parser status becomes `3`.

2. **Live dispatch mutation.** If the classifier receives `[` but changes that saved input byte to a non-bracket and returns zero, named recognition is selected. Conversely, a nonzero return followed by a custom-mode reread of `[` selects bracket mode.

3. **Named prefix.** With at least 18 bytes remaining and a successful 16-byte comparison for `StandardEncoding`, discriminator `2` is written without a delimiter check. Exactly 16 remaining bytes do not satisfy that candidate’s guard.

4. **Bracket initialization.** If custom-mode selection observes `[`, count is `256`. With remaining input and successful dependencies, both count fields receive `256`, and default-name calls cover slots `0` through `255`.

5. **Early custom exhaustion.** If normalization after count selection reaches the end, no direct count installation or custom-discriminator write occurs.

6. **Late dispatch resolution.** If a resource dependency replaces the first word reachable through the captured dispatch pointer, initialization uses the callback reached through that replacement word. Replacing only context offset `0x1e4` does not change the captured pointer.

7. **Diagnostic mutation.** If the `def` delimiter classifier changes the global-held diagnostic base, the subsequent level read uses that changed base. Signed level `6` requests a diagnostic; level `5` or a negative level does not.

8. **Unsafe post-integer cursor.** If indexed integer reading and normalization leave an unreadable cursor, the slash dereference occurs before any renewed bounds guard. A successful-name count already equal to the custom count does not prevent that read.

9. **Name success.** If token skipping advances five bytes from the name start, storage receives length `6`. On success, a zero is written at offset five in the selected stored name.

10. **Unchecked slot.** With count `2` and no successful names, indexed slot `100` is not directly rejected. Safe continuation requires the callback and subsequent table access to support that slot.

11. **Second resource failure.** Both returned resource values are stored, parser status receives the second reported failure, and initialization dispatch is not resolved.

12. **Completion.** Accepted `def` leaves the cursor after its three letters; `]` leaves it after the bracket. Later input exhaustion instead restores the most recently saved completion position.
