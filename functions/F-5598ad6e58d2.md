# F-5598ad6e58d2

## Purpose

F-5598ad6e58d2 coordinates acquisition of a scratch token, preparation of metadata, gated scanning, and conditional processing. It returns a 32-bit status.

Processing is reached only when scanning returns zero and the scan-state slot is subsequently read as exactly one. The function does not explicitly reset that state after processing. If the state remains one after successful processing, another gate call occurs, but another scan does not.

“Acquisition,” “scratch,” “metadata,” “scanning,” and “processing” identify observable roles. Their application meanings, including whether tokens represent allocated memory, are not established.

## Interface

### Arguments

| Argument | Represented width | Visible use |
|---|---:|---|
| First context | 32 bits | Passed by value to preparation, gate, scanning, and processing. |
| Second context | 32 bits | Passed by value to preparation and scanning. |
| Mode | Unsigned 32 bits | Checked for clear low two bits; passed by value to processing if reached. |

Neither context is directly dereferenced by this function. Whether either represents a pointer, handle, identifier, or other value is **documented_only**. Applicable validity requirements depend on the receiving dependencies.

The mode passes the visible check exactly when its two least-significant bits are zero. This admits unsigned values divisible by four, including zero. The check does not establish pointer alignment, allocation size, or acceptance by processing.

### Result

The result is represented as a 32-bit integer:

- **1:** initial acquisition returns zero, or the mode fails the low-two-bit check.
- **0:** the final held status is zero and the scan state read after scratch cleanup is exactly one.
- **7:** the final held status is zero and the scan state read after scratch cleanup is anything other than one.
- **A dependency’s nonzero status:** preparation, scanning, or processing returned that status and caused work to end.

Dependency statuses are retained and returned without visible remapping. Their signed interpretation and meanings are **documented_only**.

The gate result is not a returned status. A nonzero gate result ends work without replacing the held status. Cleanup results are not used.

### Local storage and widths

The visible local storage includes:

- A 32-bit scan-state slot.
- Two separate 32-bit metadata slots, called the first and second metadata slots below.
- A 32-bit item slot.
- A four-byte preparation output region.
- A distinct four-byte scanning output region.
- An initial scratch token and a conditional per-item token, each represented by a 32-bit value.

Only the scan-state slot is explicitly initialized: it is set to zero before preparation. The metadata slots, item slot, and four-byte regions have no visible initialization before their addresses are first supplied to dependencies.

The four-byte regions are not directly inspected by this function. No internal field layout, byte order, string convention, or signedness is established.

The metadata and item slots are mutable storage, not immutable snapshots of earlier dependency results. Their addresses are exposed to dependencies. Every later use described below refers to the slot’s value at that use, subject to the unresolved rules for retained-pointer access.

## Behavior

### Initial acquisition and mode admission

The first dependency call is F-d33f6d597e5d with request value **512**. This call occurs before any mode-based rejection.

After the call:

- A zero token causes immediate return of 1.
- A nonzero token combined with a mode whose low two bits are not both zero also causes immediate return of 1.
- Otherwise, execution proceeds using the returned token as the scratch token.

Neither early-return path calls cleanup.

Thus an invalid mode does not avoid the acquisition call. If acquisition returns a resource-owning token, the invalid-mode path leaves that token without a cleanup call from this function. Whether that is a resource leak depends on the dependency’s ownership contract.

### Preparation

For an admitted mode and nonzero scratch token, the function first writes zero to the scan-state slot. It then calls F-4008d9582460 with:

1. First context.
2. Second context.
3. Address of the preparation four-byte region.
4. Address of the first metadata slot.
5. Address of the second metadata slot.

The returned value becomes the held status.

A nonzero preparation status bypasses the gate, scanning, per-item acquisition, and processing. Scratch cleanup still occurs, and the preparation status is returned.

A zero preparation status enters the gated scan phase. Defined downstream behavior requires defined metadata values at their actual read points; preparation success alone does not establish an undocumented output-initialization guarantee.

### Gate and admission to scanning

Each possible scan is preceded by a call to F-e27353dd9a60 with the first context.

After the gate returns:

- If its result is nonzero, work ends without the admission read of the scan-state slot.
- If its result is zero, the function reads the scan-state slot.
- A nonzero state ends work without scanning.
- A zero state permits a scan.

The gate therefore runs even when a previously nonzero state would prevent scanning. Its return value never replaces the held status.

For an admitted scan, the first metadata slot is read **after the gate returns** and after the state-admission check. It is not a metadata value captured before the gate. Because preparation received the slot’s address, mutation through a retained address during the gate or its dependencies cannot be excluded from the available evidence.

### Scanning

F-fd20b5807437 receives these arguments in positional order:

1. First context.
2. Second context.
3. Current value of the first metadata slot.
4. Address of the item slot.
5. Address of the scanning four-byte region.
6. Scratch token.
7. Address of the scan-state slot.

The scanning result replaces the held status.

If scanning returns nonzero, work proceeds directly to scratch cleanup. No per-item acquisition or processing occurs, regardless of any state or item writes made by scanning.

If scanning returns zero, the function reads the scan-state slot:

- **Exactly one:** proceed to per-item acquisition.
- **Zero:** return to the gate; another scan is possible if that gate returns zero and the admission state read is zero.
- **Any other value:** return to the gate. If the gate returns zero and the state remains nonzero, work ends without another scan.

A state other than zero or one is not directly returned as an error code. Its effect is determined by the subsequent gate, admission, and final-state checks.

There is no visible retry count, timeout, or delay. Zero-status scans can continue indefinitely while the state remains zero and gates keep returning zero.

### Per-item acquisition and processing reads

A zero-status scan followed by a state read of one reaches per-item acquisition.

The function reads the item slot and passes that 32-bit value to F-d33f6d597e5d. This is the **acquisition request value**. The returned token is not checked for zero.

Only after that acquisition returns does the function obtain the argument values for F-924f4530474b:

1. First context.
2. Current value of the item slot.
3. Current value of the second metadata slot.
4. Current value of the first metadata slot.
5. Token returned by per-item acquisition.
6. Original mode.

The processing item argument is a new read of the item slot, not necessarily the value used for the acquisition request. Scanning previously received the item slot’s address. If per-item acquisition or its dependencies can access a retained address and modify that slot, processing can receive a different value.

Likewise, processing reads both metadata slots after per-item acquisition returns. They are not frozen preparation results, and the first metadata argument need not equal the value previously supplied to scanning. Preparation exposed both metadata addresses, so intervening mutation cannot be excluded.

This function performs no explicit transformation of these slot values. That establishes neither value preservation across dependency calls nor equality between values read at different times. The supplied representation establishes argument positions and the intervening call boundaries, not a relative read order among the item and metadata arguments within the processing call.

The processing result becomes the held status. The function then calls F-5e3309c9d083 with the per-item token, including when that token is zero.

Only after per-item cleanup returns is the processing status used to choose subsequent control flow:

- Nonzero status leads to scratch cleanup.
- Zero status returns to the gate phase.

There is no explicit scan-state reset after processing. If it remains one, the next gate call occurs, but no further scan is admitted. Mutation of the previously exposed state slot could change that behavior; the function does not establish whether such retained-pointer access is permitted.

### Scratch cleanup and return selection

Every path reaching preparation also reaches a call to F-5e3309c9d083 with the scratch token, provided dependencies return normally and the scan phase terminates.

After scratch cleanup returns:

- A nonzero held status is returned without a final scan-state read.
- A zero held status causes a fresh scan-state read.
- State one produces result 0.
- Every other 32-bit state value produces result 7.

The final comparison occurs after cleanup, not before it. Where a dependency can access the previously exposed state slot, this function provides no preservation guarantee across cleanup.

## Side effects

### Direct writes and calculations

The function explicitly initializes the scan-state slot to zero. Other direct assignments retain dependency results and tokens locally. Writes to metadata, item storage, and the four-byte output regions are dependency-mediated.

The only visible calculation on mode is the low-two-bit test. There is no mode rounding or adjustment.

The initial acquisition request is exactly 512. The per-item acquisition request is the item slot’s value at the pre-acquisition read. Processing receives its own later read of that slot. Neither read is explicitly scaled, range-checked, rounded, or otherwise transformed.

No addition, multiplication, or size arithmetic is visible on these values, so no function-local arithmetic-overflow rule is required. Dependency interpretation of the 32-bit acquisition request remains unknown.

### Observable ordering

The established ordering includes:

- Initial acquisition before mode rejection.
- Scan-state initialization before preparation.
- Preparation before the first gate.
- Gate completion before scan admission and before reading metadata for an admitted scan.
- Successful scanning and a state-one read before per-item acquisition.
- Acquisition-request item read before per-item acquisition.
- Per-item acquisition completion before processing’s item and metadata reads.
- Processing before per-item cleanup.
- Per-item cleanup before any subsequent gate or scratch cleanup.
- Scratch cleanup before final state-based result selection.

These boundaries do not imply that dependencies preserve globals or previously exposed output storage.

### Ownership and lifetime

The call pattern suggests acquisition/cleanup pairing, but resource allocation and release are inferred roles.

An admitted scratch token receives one visible cleanup call on terminating, normally returning paths. Each reached per-item acquisition is followed by processing and one cleanup call with its returned token, even if zero.

The function does not establish:

- That scratch and per-item tokens are distinct.
- That processing does not consume, retain, or release a token.
- That cleanup accepts zero.
- That a cleanup call actually releases a resource.
- That dependencies preserve globals.

Output addresses designate invocation-local storage. Retention permissions, valid retention duration, and synchronization requirements are **documented_only**. Acceptance conditions involving retained-pointer mutation describe consequences if such access is valid; they do not authorize it.

Cleanup guarantees do not cover faults, nonlocal exits, nonreturning calls, or nontermination.

## Acceptance examples

These are conditional contracts, not observed executions. Unless a case explicitly introduces mutation, assume normal returns, defined required outputs, and no later mutation of exposed slots.

1. **Initial acquisition fails.** Initial acquisition returns zero. Result: 1, with no preparation or cleanup.

2. **Invalid mode after acquisition.** Initial acquisition returns nonzero and mode is 6. Result: 1. The acquired token receives no cleanup call.

3. **Unsigned boundary mode.** Mode is 4,294,967,292. Its low two bits are clear, so it passes the visible mode check. Processing acceptance of that value remains unspecified.

4. **Preparation fails.** Preparation returns nonzero status 12. Scratch cleanup occurs, then 12 is returned. No gate or scan occurs.

5. **Gate stops before scanning.** Preparation succeeds and the first gate returns nonzero. State remains zero through scratch cleanup. Result: 7, not the gate result.

6. **Metadata changes during a gate.** Preparation establishes first metadata value 10. During an admitting gate call, valid retained-address access changes it to 20. The scan receives 20.

7. **Scan error overrides state one.** Scanning returns status 9 and writes state one. No per-item acquisition or processing occurs. Scratch cleanup occurs, then 9 is returned.

8. **Another scan is needed.** Scanning returns zero and leaves state zero. A gate call must precede another scan. That scan reads the then-current first metadata value.

9. **Other nonzero state.** Scanning returns zero and writes state two. Another gate occurs. With state unchanged, no further scan or processing occurs, and the final result is 7.

10. **Item and metadata change during acquisition.** An admitted scan leaves item value 64 and state one. Per-item acquisition receives 64. During that call, valid retained-address access changes the item slot to 96 and the metadata slots to new defined values. Processing receives 96 and those new metadata values. No equality between its item argument and acquisition’s request is required.

11. **Zero per-item token.** Per-item acquisition returns zero. Processing is still called with zero, followed by cleanup with zero. Normal continuation requires those dependencies to support that input.

12. **Successful processing with stable state.** Processing returns zero and state remains one. Per-item cleanup occurs, then another gate, then scratch cleanup without another scan. Result: 0.

13. **Processing fails.** Processing returns status 13. Per-item cleanup precedes scratch cleanup. No subsequent gate occurs, and 13 is returned.

14. **Cleanup changes final state.** Work ends with held status zero and state one. If valid access during scratch cleanup changes state to zero, the final read produces result 7 rather than 0.
