# F-38c8a81d25d2

## Purpose

F-38c8a81d25d2 scans a resolved byte sequence and, upon the first qualifying decoded-value pattern, invokes a construction dependency followed by a delivery dependency.

Its established behavior consists of:

- Resolving two supplied 32-bit values, in order.
- Capturing a 32-bit field from the supplied object.
- Scanning the first resolved address using a stateful decoder.
- Applying a counter-based recognition rule to decoded values.
- Supplying saved scan boundaries and the second resolver result to a construction dependency.
- Reading a value from a fixed global storage location **after construction returns**.
- Passing the construction result and that newly read global value to a delivery dependency.

The function does not return an explicit result or report whether construction or delivery succeeded.

**Inferred intent:** the construction arguments resemble a prefix/replacement/suffix operation. The supplied evidence does not establish text encoding, template contents, constructed output format, or delivery semantics. Those interpretations are not guaranteed behavior.

## Behavior

### Resolution and context capture

The function initializes a local decoder-state slot from the fourth input. Its externally relevant initial read/call order is:

1. Read the first 32-bit pair element.
2. Call F-95b79f0a129e with that value.
3. Read the second 32-bit pair element.
4. Call F-95b79f0a129e with that value.
5. Read the 32-bit object field at byte offset 24.

The second element is not captured before the first resolver call. The object field is not captured before either resolver call. Resolver-induced changes to those locations can therefore affect the subsequently observed values.

The scan begins with:

- Current address equal to the first resolver result.
- Retained advance quantity equal to zero.
- Recognition counter equal to 3.
- Decoder-state slot containing the supplied initial state, unless modified through behavior outside the visible function’s guarantees.

If the first resolver result is zero, the function returns after both resolver calls and the object-field read. It does not decode, construct, read the delivery global, or deliver.

### Boundary-byte check

For a nonzero first resolver result, each outer scan iteration saves:

- The current address as that iteration’s boundary address.
- The retained advance quantity as that iteration’s boundary advance.

It then reads the byte at the saved boundary address.

If that byte is zero, the function returns immediately. That iteration makes no decoder call, and the function makes no construction call, delivery-global read, or delivery call.

The zero-byte check precedes advancement. It checks the saved current address, not necessarily the address supplied to the next decoder call.

### Decoder progression

After a nonzero boundary byte, the current address is advanced by the retained advance quantity. F-86b0b8e613c4 is then called with:

1. The advanced address.
2. The address of the local decoder-state slot.

Its 32-bit return value becomes the next retained advance quantity. The post-call value in the state slot determines classification.

If the state value equals `0x91`, the function immediately repeats advancement and decoding. Each repetition advances by the latest returned quantity and then calls the decoder again.

There is no direct zero-byte check between these repeated calls. A decoder may therefore be called on an address whose byte has not been checked by this function.

A state value of `0x91`:

- Does not independently increment the recognition counter.
- Does not reset the counter.
- Does not replace the saved boundary address or boundary advance.
- Can cause additional advancement before the outer iteration reaches classification.

The decoder-state slot is persistent across calls. It is not restored from the original input before each invocation.

### Counter transitions and recognition

Once decoding produces a value other than `0x91`, the function increments the counter once. It then applies the following rules:

| Decoded state value | Result |
|---|---|
| `0x70` or `0x62` | Reset the counter to zero and continue scanning. |
| `0x82`, `0x26`, or `0x05` | Recognize a match only when the incremented counter equals 2. |
| Any other value | Continue scanning with the incremented counter. |

An accepted-value candidate at the wrong count does not reset the counter.

Under non-overflowing counter evolution, recognition requires a reset value, followed by one classified nonreset value, followed by an accepted-value candidate. Ignored `0x91` results do not consume positions in that counting rule.

The counter’s initial value is 3. Thus an accepted-value candidate does not ordinarily qualify before a reset merely because it appears near the start of the sequence.

Each reset restarts the counting window. The function stops at the first recognition; it does not search for additional matches afterward.

## Acceptance examples

These are conditional consequences of the visible control flow, not runtime observations. Unless stated otherwise, they assume readable addresses, nonzero reached boundary bytes, completing dependencies, ordinary arithmetic, and no relevant dependency mutation.

### Null first resolution

If the first resolver returns zero, the second resolver still runs and the object field is still read. No decoding, construction, delivery-global read, or delivery occurs.

Returning immediately after the first resolver would violate the established operation order.

### Initially zero boundary byte

If the first resolved address is nonzero but its first byte is zero, the function returns without decoding. Both resolver calls and the object-field read have already occurred. The delivery-global location is not read.

### Qualifying sequence with unit advances

Suppose decoder calls at offsets 0, 1, and 2 each return advance 1 and leave these state values:

- Offset 0: `0x70`.
- Offset 1: an ordinary nonreset, nonignored value.
- Offset 2: `0x82`.

The counter becomes 0, then 1, then 2. Construction occurs once.

The saved boundary at recognition is offset 1, so the construction difference is 1 and the sixth construction argument is the original address plus 2.

After construction returns, the global value is read and supplied to one delivery call.

### Ignored value within the recognizing iteration

Suppose unit-advance decoding produces:

- Offset 0: `0x62`.
- Offset 1: an ordinary value.
- Offset 2: `0x91`.
- Offset 3: `0x26`.

Recognition occurs while decoding offset 3. The saved boundary remains offset 1, and the saved advance remains 1. Construction therefore receives difference 1 and suffix address offset 2, not offset 3 or 4.

No boundary-byte check is inserted between decoding offsets 2 and 3.

### Candidate at the wrong count

For `0x70` followed immediately by `0x05`, the latter increments the counter to 1 and does not qualify. If a zero byte is subsequently read at an outer boundary, the function returns without construction, global read, or delivery.

### A later reset

For `0x70`, an ordinary value, `0x62`, and `0x82`, the second reset sets the counter back to zero. The final candidate is counted as 1 and does not qualify.

### Construction changes the delivery global

Suppose the global storage contains value A before construction, and construction changes it to value B before returning. If no later mutation intervenes, delivery receives B as its fourth argument.

An implementation that captures A before construction would not preserve this behavior. No numeric width or application meaning is assumed for A or B.

### High-bit advance

If a saved boundary advance has bit 31 set, the sixth construction argument uses that advance with bit 31 cleared. Ordinary scan advancement still uses the full returned quantity.

This example does not establish that the corresponding scan addresses are valid or that wraparound is permitted.
