# F-9112acdf95b8

## Purpose

F-9112acdf95b8 advances state associated with a writable context. An initially nonzero pending length selects a capacity-limited numeric portion. An initially zero pending length instead triggers initialization, lookup, and conditional handler invocation. Depending on the outcome, the function modifies context fields, associated-object fields, and memory-mapped registers; returns a distinguished error; or executes a fallback sequence.

“Pending,” “capacity,” “request,” and “descriptor” are descriptive names inferred from use. The representation establishes numeric values and access sequences, not length units, device identity, hardware transfer size, or completion semantics.

## Interface

The function accepts two 32-bit arguments and returns an unsigned 32-bit result.

| Argument | Meaning |
|---|---|
| Context address | Address used to access the fields below. |
| Adjustment | Operand subtracted from the context field at offset `0xBC` when invoking an indirect handler. Otherwise unused. |

There are no visible preliminary checks for null pointers, alignment, bounds, accessibility, or valid register mappings. Every address used on the selected path must support the corresponding access.

### Indirect handler

A non-null lookup result identifies an object. Its first 32-bit word identifies a dispatch table; the callable entry is obtained at table byte offset `0x2C`.

The handler receives:

1. The lookup-result object address.
2. The address of context offset `0x90`.
3. The context word at `0xBC` minus the adjustment argument.

The subtraction is represented using signed 32-bit operands. Its behavior when the mathematical result falls outside the signed 32-bit range is unresolved. The handler result is interpreted as signed 32-bit.

The representation establishes these argument values and dispatch accesses, but does not establish a total evaluation order among the reads used to prepare the call.

## Behavior

### Entry decision

The first visible access reads the 32-bit pending length at context offset `0x98`.

If nonzero, the function reads the pending address at `0x9C` and enters the shared selection path in **pending mode**. Initialization, lookup, and handler invocation are skipped.

If zero, the function enters request dispatch. Later changes to the pending-length field do not restart this entry decision.

### Request initialization and lookup

The following operations occur in order:

1. Read the associated-object address at context offset `0x34` and call F-ddf4a1f94e38 with that address and zero.
2. After the call, read context offset `0x34` again and call F-e9576b7ad3a3 with that observation and zero.
3. Read the selector byte at `0x90`.

If this selector observation is `0x21`, select F-7c98cdf9320e. Otherwise, read the selector byte again. Select F-74af3c64851d only if the second observation is `0x22`; otherwise enter fallback.

The two selector comparisons do not share a captured value. In particular, a first observation other than `0x21` followed by `0x22` selects the second lookup. A second observation of `0x21` does not select the first lookup.

The selected lookup receives the context address and the low eight bits of a 16-bit read at context offset `0x94`.

A null lookup result enters fallback. A non-null result is used for the indirect handler call described above.

### Handler outcomes

- **Zero:** Read context offset `0xB4`, then enter shared selection in **handler-success mode**, with initial numeric length zero and internal mode value `0x80`.
- **Signed `-5`:** Return `0xFFFFFFFB` immediately.
- **Any other result:** Enter fallback.

Handler-success mode does not reload the pending length as its initial length. Handler changes to pending fields therefore do not substitute a nonzero length into this mode.

### Shared selection and pending-field writes

The two reachable modes provide these inputs:

| Mode | Initial length | Initial address | Saved control source |
|---|---:|---|---|
| Pending | Entry observation of `0x98` | Subsequent observation of `0x9C` | Control A |
| Handler-success | Zero | Post-handler observation of `0xB4` | Control B |

The function reads capacity from context offset `0xA0` and compares lengths as unsigned 32-bit values.

If initial length is less than capacity:

- Select the initial length.
- If that length is nonzero, write zero to `0x98`, then zero to `0x9C`.
- If that length is zero, perform neither pending-field write.

Otherwise:

- Write initial length minus capacity to `0x98`.
- Write initial address plus capacity to `0x9C`.
- Select capacity.

The subtraction in the latter branch cannot underflow because of the unsigned comparison. Address addition is unsigned 32-bit arithmetic and can wrap modulo \(2^{32}\).

After these possible writes, the function reads the associated-object address from `0x34`, then reads the mode-selected control register. It retains both observations for subsequent operations.

Only then does it reject a selected length greater than 64, returning `0xFFFFFFFF`. Earlier context writes remain effective. There is no visible rollback or subsequent programming write on this rejection path.

Handler-success mode always selects zero:

- With positive capacity, it performs no pending-field writes.
- With zero capacity, it writes zero to `0x98`, followed by the address obtained from `0xB4` to `0x9C`.

These consequences hold even if dependencies previously changed those fields.

### Pending-mode programming

For a selected length from zero through 64:

1. If nonzero, write the selected length to associated-object offset `0xA0`, then the original selected address to offset `0xA4`.
2. Write the saved Control A observation ORed with `0x04000000` to Control A.
3. Read Control B.
4. Write that observation back to Control B.
5. Return zero.

A selected length of zero suppresses only the two associated-object writes. It does not suppress either control-register sequence.

The Control B read and write are distinct observable accesses even if the written value equals the observation.

### Handler-success object and descriptor programming

The reachable handler-success path has selected length zero.

First, call F-8f180221fee0 without visible arguments. Write its 32-bit result to offset `0x80` of the associated object captured during shared selection. Do not reload the associated-object address after this call.

Next, write `0x20080000` to Descriptor B.

After that descriptor write, read the unresolved displacement global. Write the selected address masked with `0x7FFFFFFF` to the register-block base plus the observed displacement. The destination therefore depends on a global observation made after F-8f180221fee0 and after the Descriptor B write.

Then:

1. Call F-d7be9cfb4000 with zero and 64.
2. Obtain its secondary 32-bit output.
3. Add three using unsigned 32-bit wraparound, then clear the low two bits.
4. Write that rounded result to associated-object offset `0x38`.

No particular secondary result is established for these arguments. In particular, neither a zero result nor division semantics may be assumed.

A conditional replacement of a zero rounded result with 64 exists in the shared body, but additionally requires nonzero selected length. It is not reachable through the shown handler-success entry.

The shared body also contains a nonzero-length descriptor calculation involving F-d7be9cfb4000 with length minus one and 64, followed by an increment and a left shift of 19 bits. No shown entry reaches that calculation: pending mode takes its separate programming branch, and handler-success mode supplies zero. It does not establish another supported invocation mode.

### Shared-state early return

After the write to associated-object offset `0x38`, read the shared-state-base global and then read one byte at that base plus `4`.

If that byte is zero and the saved Control B observation satisfies

\[
(\text{saved Control B} \mathbin{\&} \texttt{0x03CC0000})
= \texttt{0x000C0000},
\]

perform these operations in order:

1. Read the shared-state-base global again.
2. Write the 32-bit value `0x80` at the newly observed base plus `0x18`.
3. Write `0x39` to Event.
4. Write saved Control B ORed with `0x04000000` to Control B.
5. Return zero.

The base used for the byte read need not equal the base used for the word write. No preservation guarantee connects these observations.

### Remaining handler-success control sequence

If the early return is not taken, inspect bits 18–19 of saved Control B. If both are set, call F-9c06a5856a0f with saved Control B bits 22–25, extracted as an unsigned value from zero through 15, and zero.

After this optional call:

1. Read Control B as the initial write candidate.
2. Read Descriptor A and test whether bits 29–30 are both set.
3. If they are not, retain the initial candidate.
4. If they are, read Control B again and form a candidate by ORing that observation with `0x84000000`.
5. In that case, read Descriptor A a second time. If bits 29–30 are no longer both set, read Control B once more and replace the candidate with that observation ORed with `0x8C000000`.
6. Write the resulting candidate to Control B and return zero.

Descriptor A bit 31 is excluded from both tests. The Descriptor A reads and conditional Control B rereads remain separate observations.

### Fallback

Fallback performs the following ordered sequence:

1. Read context offset `0x34`; call F-8b341d935c06 with that address, zero, and one.
2. Read context offset `0x34` again; call F-ddf4a1f94e38 with that address and `0x80`.
3. Read Control B.
4. Mask the observation with `0x03FDFFFF`, OR it with `0x00200000`, and write the result to Control B.
5. Read Control B again and return that observation.

The two dependency calls can receive different object addresses.

The register transformation clears bits 26–31 and bit 17, sets bit 21, and preserves the other bits.

## Acceptance examples

These examples are conditional consequences of static evidence, not executed tests. They assume accessible storage and dependencies that return as specified.

1. **Pending length below capacity.** With initial length 16 and capacity 64, write zero to pending length, then zero to pending address. Write 16 to associated-object offset `0xA0` and the original address to `0xA4`. Perform the pending-mode control-register sequence and return zero.

2. **Exact capacity.** With initial length 64 and capacity 64, write zero to pending length and original address plus 64 to pending address; do not clear that address merely because the remaining length is zero. Write 64 to associated-object offset `0xA0`, write the original address to offset `0xA4`, write saved Control A ORed with `0x04000000` to Control A, then read and rewrite Control B. Return zero. This establishes no length unit or resulting hardware transfer.

3. **Zero capacity with pending data.** With initial length 7 and capacity zero, write both pending fields back with their previously obtained values. Select zero, leave associated-object offsets `0xA0` and `0xA4` untouched, perform the pending-mode control sequence, and return zero.

4. **Oversized selected length.** With initial length 100 and capacity 80, first write remaining length 20 and original address plus 80. Read the associated-object address and Control A, then return `0xFFFFFFFF` without the later programming writes.

5. **Address wraparound.** With initial length and capacity both 16 and original address `0xFFFFFFF8`, write pending length zero and pending address `0x00000008`. The associated-object address field receives the original `0xFFFFFFF8`.

6. **Changing selector.** Observations `0x20` followed by `0x22` select F-74af3c64851d. A first observation of `0x21` selects F-7c98cdf9320e without a second selector read. Observations `0x20` followed by `0x21` enter fallback.

7. **Fallback object replacement.** If F-8b341d935c06 replaces context offset `0x34`, the subsequent F-ddf4a1f94e38 call receives the replacement address.

8. **Handler error.** A handler result of signed `-5` returns `0xFFFFFFFB`, without shared programming or fallback.

9. **Handler success.** With positive capacity, the function itself performs no pending-field writes. It selects zero, writes Descriptor B as `0x20080000`, then observes the displacement global and writes the top-bit-cleared post-handler address to the resulting register destination.

10. **Changing shared-state base.** When the first base addresses a zero byte at offset `4` and the saved-control condition passes, the word write at offset `0x18` uses the second base observation, even if different.

11. **Changing Descriptor A.** When its first observation has bits 29–30 set but its second does not, the final Control B candidate comes from the third Control B observation ORed with `0x8C000000`.
