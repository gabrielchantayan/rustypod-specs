# F-61361e57c83d

## Purpose

F-61361e57c83d traverses a bounded sequence of records, obtains integer identifiers from each retrieved record, conditionally updates a temporary bitmap-like collection, and submits that collection through an object obtained from the input context.

Two 32-bit context fields report a starting index and the last fully processed record index. The function invalidates both fields after traversal, before obtaining the object. It publishes the indices only when the object’s readiness method returns nonzero.

**Established static behavior:** entry gates, traversal, collection updates, result-field writes, two time-specific global reads, indirect dispatch, and conditional final storage handling occur in the order described below.

**Inferred intent:** the collection represents a selection of identifiers, potentially with duplicate suppression. The result fields describe the processed interval. Neither interpretation establishes the behavior of the called dependencies.

The function has no explicit return value or unified success/error result. No runtime tests have been performed.

## Interface

### Context argument

The sole argument is a 32-bit address-like value identifying a context. Direct accesses use the following layout:

| Context offset | Width | Access and role |
|---|---:|---|
| `0x1c` | 32 bits | Read for the entry gate; reread later for object-related acquisition |
| `0x2c` | 32 bits | Read as an indirect callback address when the earlier gates pass |
| `0x7c` | 32 bits | Written with an invalid sentinel, then conditionally the starting index |
| `0x80` | 32 bits | Written with an invalid sentinel, then conditionally the last processed index |

The body does not validate the context address or callback target. Memory must support every access actually reached.

The context callback receives two output-storage addresses: one for an eight-byte scratch region and one for a four-byte value. A zero callback result stops processing; any nonzero result permits continuation. Only the four-byte output is directly consumed afterward.

### Global inputs

Two distinct 32-bit global-backed values are read:

- **Metadata global:** read after F-aa715dc026b7 returns and copied into the collection, before testing whether the lookup result equals `-1`.
- **Publication-argument global:** read in the ready branch after writing context offset `0x7c` and before writing offset `0x80`. The captured value is later passed to F-85722f62e20a.

Neither global is established to be constant or preserved by dependencies. These descriptions identify their roles, not their addresses or initial contents.

### Preconditions

Normal continuation requires valid dependency outputs wherever they are consumed. This includes a usable callback output, usable record fields following accepted retrievals, an accessible object and dispatch table, callable method entries, and valid storage for every direct bitmap access.

The body does not enforce these conditions. It also does not initialize the context result fields on entry.

## Behavior

### Entry gates and metadata capture

The function performs these operations in order:

1. Read context offset `0x1c`; stop if zero.
2. Call F-8b2d02fa1959; stop if its returned handle is zero.
3. Call F-5126e2cd0d6c with that handle; stop unless its result equals exactly `4`.
4. Read and invoke the callback at context offset `0x2c`, supplying the two output addresses; stop if its result is zero.
5. Pass the callback’s four-byte output and integer `10` to F-d7be9cfb4000.
6. Pass the acquired handle and the transformed value to F-aa715dc026b7.
7. Read the current 32-bit metadata global and copy it to collection offset `+0`.
8. Stop if the starting-index result equals signed `-1`.

Thus, lookup failure still causes the metadata-global read and local metadata write. It does not cause allocation or either direct context-result write.

Other negative starting indices are not rejected at this gate. The handle and starting index are retained for subsequent use.

### Collection setup

For a starting index other than `-1`:

1. Call F-638beded7699 with `0x2000` and `0x31`.
2. Store its returned address at collection offset `+8`.
3. Set the one-byte marker at `+12` to `0x31`.
4. Call the unmapped preparation dependency with that storage address and byte count `0x2000`.
5. Set the 32-bit count at `+4` to zero.
6. Call F-766473d455b3 with the retained handle to obtain the traversal bound.

There is no allocation-failure branch. A zero allocation result is still passed to the preparation dependency.

The preparation call’s visible arguments do not establish zero-initialization, successful allocation, or safe handling of a null address. The bound is obtained once; traversal does not refresh it after each record.

### Record traversal

The current record index initially equals the starting index. The last-processed index initially has the 32-bit representation `0xffffffff`, interpreted here as signed `-1`.

Before each retrieval, the function compares the current index with the bound using a signed 32-bit less-than comparison. If the comparison fails, traversal ends without retrieving that candidate.

Otherwise, F-e9cd4e4f4802 receives the handle, current index, and record-output address:

- A result equal to `-1` ends traversal.
- Every other result permits processing of that record.
- The retrieval result does not determine the next record index.

For an accepted retrieval, the function calls F-9f8c9e1a456f with the record fields at `+16` and `+12`, respectively. This establishes argument placement, not an independently guaranteed ordering between those two memory reads.

After that call, it copies the then-current field at `+16` into the cursor. Consequently, preservation of that field across F-9f8c9e1a456f is not assumed.

The helper’s returned 32-bit value controls the identifier loop. Each condition evaluation tests the count for nonzero and also decrements it. The pre-decrement nonzero test determines whether an iteration executes:

- An initial zero produces no identifier-processing iterations.
- A positive count produces that many iterations, absent abnormal dependency behavior.
- A negative count is not treated as an empty record or an explicit error.

Each executed iteration:

1. Calls F-d3922c7fe0ec with the cursor’s address to obtain an unsigned 32-bit identifier.
2. Forms a word index from the identifier’s upper 27 bits by shifting right five.
3. Forms a bit position from the low five bits.
4. Calls F-88658862e573 with the collection address, word index, and bit position.
5. If the result is exactly zero, increments the collection’s current 32-bit count and then performs a 32-bit read-modify-write on the selected storage word.
6. If the result is nonzero, performs neither direct update.

The helper receives the collection by address. Its preservation of the count, storage address, marker, metadata, or storage contents is not established. A permitted direct update uses the collection state present after that call, not necessarily the original allocation state.

After all identifier iterations finish, the current record becomes the last fully processed index, and the next candidate is the current index plus one. A zero-identifier record therefore advances the last-processed index. A retrieval returning `-1` does not.

### Bitmap widths and bounds

The direct storage operation uses four-byte words and a 32-bit mask. The selected word is at the current storage base plus four times the word index; the selected bit is the identifier modulo 32. Bit position `31` is included.

The word index ranges from `0` through `134217727`. Its scaled byte offset ranges from `0` through `0x1ffffffc`; adding that offset to a storage address is not checked.

For an unchanged allocation of exactly `8192` bytes:

- There are `2048` four-byte words.
- Identifiers `0` through `65535` select words within the allocation.
- Identifier `65536` selects the first word beyond it.

No explicit identifier-range check appears. A nonzero result from F-88658862e573 suppresses the direct access, but no particular validation behavior can be attributed to that helper.

Signed count increments, identifier-loop decrements, and record-index increments are unchecked. The supplied representation does not establish portable source-language behavior after signed overflow; a wrapping interpretation must not be silently substituted.

### Result invalidation and object acquisition

After traversal ends, even if no record completed, the function directly writes:

1. `0xffffffff` to context offset `0x7c`.
2. `0xffffffff` to context offset `0x80`.

It then rereads context offset `0x1c` and passes that value to F-a2a2eb07db39 with three output addresses. This need not be the value observed at entry.

F-59c1430f85c2 receives the address of the eight-byte representation and the four-byte, two-byte, and one-byte outputs. The function clears the low bit of the representation’s first 32-bit word and retains the resulting object address.

For the readiness invocation, it reads the dispatch-table address from the object, reads the method entry at table offset `0x14`, and invokes that entry with the object address. No explicit null-object check precedes these reads.

### Ready-object branch and publication

If readiness returns zero, the ready branch is skipped. The invalid sentinels remain the function’s most recent direct result writes, although dependencies may have altered the fields.

If readiness returns nonzero, operations occur in this order:

1. Call F-8f4035bf2a29 with `0x21`.
2. Reload the dispatch-table address from the retained object address.
3. Read the method entry at the newly loaded table’s offset `0x28` and invoke it with the object address.
4. Pass its four-byte result and the collection address to F-5240c36738e7.
5. Initialize the four-byte scratch value to zero.
6. Reload the dispatch-table address from the same retained object address.
7. Read the entry at that table’s offset `0x1c` and invoke it with the object address, integer `2`, and scratch address.
8. Call F-3ecf06e452fb with integer `2`.
9. Write the original starting index to context offset `0x7c`.
10. Read and capture the current 32-bit publication-argument global.
11. Write the last fully processed index to context offset `0x80`.
12. Call F-85722f62e20a with `0x21` and the captured global value.

Only the object address is retained across the object-method calls. The dispatch-table address and method target are resolved anew for every invocation. In particular, the `0x28` resolution occurs after F-8f4035bf2a29, and the `0x1c` resolution occurs after F-5240c36738e7. Caching the initial table would not preserve the established behavior.

No checked delivery-result gate appears before publication. The scratch output from the `0x1c` method is not inspected.

### Final storage handling

After readiness testing and any ready-branch work, the function examines the current collection storage address. If it is nonzero, it also examines the current marker.

F-8349c252c168 receives the storage address and zero exactly when the address is nonzero and the marker is not `0x3a`. The initial marker `0x31` does not guarantee this condition still holds after dependencies have received the collection.

No explicit handle or object release appears.

## Side effects

Direct effects include context-result writes, metadata capture, collection-field initialization and updates, bitmap read-modify-writes, an allocation-like request, indirect calls, collection delivery, and conditional final storage handling.

The two global reads are time-specific inputs to these effects. The metadata capture occurs even on a starting lookup result of `-1`. The publication-argument capture occurs between the two successful-publication writes, not before them or after both.

Dependencies may mutate global state, context memory, collection fields, storage, or object dispatch state. No preservation guarantee is established.

The function is not shown to be transactional. Collection work precedes readiness testing; invalidation precedes object acquisition; publication consists of separate writes with an intervening global read.

Ownership is unresolved. F-8349c252c168 may have cleanup-like intent, but actual release semantics are not established. Nor is it established whether F-5240c36738e7 copies, retains, consumes, or modifies the collection. The caller must not infer post-return collection validity.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless specified otherwise, dependencies return normally and preserve unrelated state.

1. **Closed entry gate.** If context offset `0x1c` is zero, no dependency is invoked, neither global is read, and neither result field is directly written.

2. **Lookup failure still captures metadata.** If F-aa715dc026b7 returns `-1`, the current metadata global is read and copied into the collection. No collection allocation or direct context-result write follows.

3. **Metadata changed during lookup.** If F-aa715dc026b7 changes the metadata global before returning, the collection receives the value present after that call, not an earlier snapshot.

4. **Empty interval, ready object.** With starting index `5` and bound `5`, no retrieval occurs. A ready object still receives collection delivery, and publication writes `5` and `0xffffffff`.

5. **Retrieval failure after progress.** Starting at `7`, if record `7` completes and retrieval of `8` returns `-1`, successful publication writes `7` and `7`.

6. **Zero identifiers.** A retrieved record with count zero makes no identifier-generation calls but still becomes the last processed record.

7. **Conditional duplicate suppression.** With initially zero storage and no helper mutations, identifier `33` twice, a zero gate result first, and a nonzero result second cause one direct count increment and set bit `1` of word `1`. This does not prove duplicate recognition.

8. **Extent boundary.** Identifier `65535` selects bit `31` of word `2047`. Identifier `65536`, followed by a zero gate result and unchanged storage, causes an out-of-extent direct access for an `8192`-byte allocation.

9. **Changed dispatch tables.** If F-8f4035bf2a29 replaces the object’s table, U-04 resolves through that replacement. If F-5240c36738e7 replaces it again, U-05 resolves through the later table. The retained object address is unchanged.

10. **Publication-global timing.** The write to `0x7c` precedes capture of the publication-argument global; capture precedes the write to `0x80`; F-85722f62e20a receives that captured value.

11. **Not ready.** A zero readiness result skips delivery and publication-global capture. Both sentinels remain the latest direct result writes; final storage handling is still evaluated.

12. **Final marker suppression.** A nonzero current storage address with current marker `0x3a` suppresses F-8349c252c168.
