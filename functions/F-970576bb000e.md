# F-970576bb000e

## Purpose

F-970576bb000e conditionally constructs and submits a result using two converted inputs and a scan of the first converted input.

Established behavior:

- Both inputs are converted, and an object field is read, before the first conversion result is checked for null.
- Scanning advances a byte-oriented cursor using unsigned 32-bit quantities returned by a dependency.
- Two scanner states continue the current scan group; two others trigger construction.
- A null first conversion result or a zero byte at an outer scan checkpoint causes return without construction or submission.
- On a triggering path, construction completes before a value is read from a fixed global location. That newly read value supplies the fourth submission argument.
- At most one construction call and one submission call occur per invocation.

The apparent intent is a selective text transformation involving a prefix, the second converted input, and a suffix. This interpretation is inferred, not an established output contract. The scanner states and construction template have no supplied semantic definitions.

## Interface

The supplied representation establishes 32-bit input entries, object-field storage, scanner advancement quantities, scan-state storage, and construction-result storage. Checkpoint inspection reads one byte. Pointer-to-integer conversions used for the prefix displacement support a 32-bit address representation in this analysis; they do not independently establish the external calling convention.

The declaration of the global supplying the fourth submission argument is not provided. Its read width, signedness, and representation are therefore not established merely by its use as a call argument.

### Preconditions for defined execution

The function performs no explicit validation of the object address, input-pair address, or scanner-generated addresses. Normal execution requires:

- The first input entry to be readable before the first conversion.
- The second input entry to be readable after the first conversion returns.
- The object field at offset 0x18 to be readable after both conversions return.
- A non-null first converted address to remain usable for every reached checkpoint read and dependency access.
- Reached cursor additions, prefix-displacement arithmetic, and suffix-address calculations to be valid for their consumers.
- The submission-data global to be readable after construction returns, if submission is reached.

These are access requirements, not validations performed by the function. No buffer length is supplied or checked. Each dependency must also satisfy its own, otherwise unspecified, calling requirements.

## Behavior

### Preparation and read ordering

The function first initializes its addressable scan-state slot from the fourth argument. It then performs the following preparation in order:

1. Reads the first 32-bit input entry and invokes F-95b79f0a129e with that value.
2. After the first conversion returns, reads the second 32-bit input entry and invokes F-95b79f0a129e with that value.
3. After the second conversion returns, reads the object’s 32-bit field at offset 0x18.
4. Tests whether the first conversion result is null.

A null first conversion result therefore does not suppress the second conversion or the object-field read. It does suppress scanning, construction, the submission-data global read, and submission.

The two input entries are not captured simultaneously. If the first conversion changes the second entry, the second conversion receives the value present at the later read. Likewise, either conversion may affect the object field before it is captured.

The function retains the first converted address across the second conversion without checking whether the second call invalidated or modified the referenced storage. No dependency-preservation guarantee is established here.

### Outer scan groups

For a non-null first converted address:

- The cursor initially equals that address.
- The unsigned 32-bit advancement quantity initially equals zero.
- The scan-state slot retains the fourth argument unless a dependency has changed it through some independently available means.

At the start of each outer group, the function saves the current cursor as the group anchor and saves the current advancement quantity as the group’s incoming advancement.

It then reads one byte at the anchor. If that byte is zero, the function returns without construction, the submission-data global read, or submission.

This checkpoint precedes the group’s first cursor addition. It does not validate every address subsequently passed to the scanner.

### Scanner calls and state transitions

Each scanner call within a group is preceded by advancing the cursor by the current unsigned 32-bit advancement quantity. F-86b0b8e613c4 then receives:

- The advanced cursor.
- The address of the mutable 32-bit scan-state slot.

The scanner’s return becomes the advancement quantity for the next step. The function then branches on the state slot:

| State after the scanner returns | Result |
|---|---|
| 0x91 | Continue within the same group. |
| 0x93 | Continue within the same group. |
| 0x13 | Leave scanning and construct a result. |
| 0x73 | Leave scanning and construct a result. |
| Any other value | End this group and begin another outer group. |

Continuation within a group performs another cursor addition and scanner call without an intervening zero-byte checkpoint.

For an ordinary state outside these four values, the next outer group begins at the cursor just supplied to the scanner. The scanner’s return becomes that new group’s incoming advancement. The next checkpoint reads the byte at this cursor before applying that advancement.

Because the initial advancement is zero, the first scanner call receives the first converted address.

The function does not itself guarantee that the scanner writes the state slot. If the scanner leaves it unchanged, the branch uses the existing value. The initial scan-state argument can therefore affect control flow unless a separate scanner contract guarantees replacement.

### Widths, bounds, and progress

Cursor advancement uses the full unsigned 32-bit scanner result. The function does not clear its high bit before scanning.

The mask used later for the suffix address is a separate operation. It does not establish that scanner returns encode flags or that scanning should ignore their high bit.

There is no explicit:

- Maximum scanner-call count.
- Maximum displacement or buffer-bound check.
- Requirement for nonzero advancement.
- Recovery from invalid addresses.
- Progress guarantee.
- Timeout or cancellation condition.

Repeated 0x91 or 0x93 states can indefinitely postpone the next outer checkpoint. Other repeated states with zero advancement can repeatedly revisit the same checkpoint and scanner address.

Behavior when pointer arithmetic leaves valid storage, wraps an address, or otherwise exceeds the representation’s valid arithmetic domain is not established. Such cases must not be treated as accepted wrapping behavior.

### Result construction

A state of 0x13 or 0x73 triggers one call to F-1983453691c7 with these arguments, in order:

1. The previously captured 32-bit object field.
2. A fixed template address.
3. The displacement from the first converted address to the current group’s anchor, expressed through 32-bit signed integer conversions and subtraction.
4. The first converted address.
5. The second conversion result.
6. A suffix address calculated as the group anchor plus the group’s incoming advancement masked with 0x7fffffff.

The group anchor and incoming advancement remain those saved at the start of the current outer group. Within-group scanner calls do not update these saved construction inputs.

Consequently:

- The prefix displacement need not describe the triggering scanner cursor.
- The suffix uses the saved incoming advancement, not the triggering scanner call’s return.
- The suffix mask clears bit 31 and produces a numeric offset from zero through 2,147,483,647 inclusive.
- That numeric range does not establish a valid suffix address.

The prefix expression uses signed 32-bit arithmetic in the supplied representation. Its behavior when the converted addresses or their difference are not representable is unresolved; the evidence does not justify assuming modular subtraction.

The template’s contents are not supplied. The exact output bytes, interpretation of the displacement, and treatment of the converted values remain unknown.

### Late global read and submission

After F-1983453691c7 returns, the function reads a value from a fixed global location. It then calls F-475af1e83e55 with:

1. The original object address.
2. The construction result.
3. The 32-bit value 0xffffffff.
4. The value obtained by that late global read.

The fixed element is the global’s location, not its contents. The call passes the value read from that location; the source does not show passing the global’s address. The value itself could have any representation permitted by the unavailable declaration.

This ordering is observable. Construction or any earlier dependency may change the global, and the submission argument reflects its value when read after construction returns. The function does not use a snapshot taken before construction.

No read width is established for this global because its declaration is absent. In particular, the widths of neighboring arguments do not establish its width.

There is no intervening validation of the construction result. Submission is invoked even if that result represents failure under the construction dependency’s unknown contract. Any submission return value is unused, and the function then returns.

## Side effects

The explicit external-memory reads are:

- The first 32-bit input entry.
- The second 32-bit input entry, after the first conversion returns.
- The 32-bit object field at offset 0x18, after both conversions return.
- One byte at each reached outer scan checkpoint.
- The submission-data global, after construction returns and before submission, only on a triggering path.

The global read’s width is not established. The fixed template address is passed to construction; the function body does not itself show reading the template’s contents.

The body does not directly write the input pair, object fields, converted buffers, or submission-data global. Its direct writes are to local bookkeeping, including initialization of the scan-state slot. The scanner receives writable access to that slot.

Dependencies may have additional effects:

- Conversion occurs twice even when the first result is null.
- Scanning can occur an unbounded number of times.
- Construction and submission each occur once on a normally returning triggering path.
- Dependencies may mutate reachable memory or globals, including the global later read for submission.

The object field is captured once. Scanner-side or construction-side changes to that field do not cause a reread. In contrast, the submission-data global is first read after construction, so construction-side changes can affect submission’s fourth argument.

No allocation or release is explicit in this function. Conversion-result and construction-result ownership, aliasing, and lifetime remain unknown. Passing the construction result to submission does not establish ownership transfer, retention, or release.

There is no explicit error result, diagnostic, retry, or exception-handling path.

## Acceptance examples

These are conditional static consequences, not runtime observations. They assume dependencies return normally and every reached access and arithmetic operation is valid.

### Null first conversion

If the first conversion returns null:

- The second entry is still read and converted.
- The object field is still read afterward.
- No scanner or construction call occurs.
- The submission-data global is not read by this function.
- Submission does not occur.

### Empty first converted input

If the first conversion is non-null but its first byte is zero at the initial checkpoint, both conversions and the object-field read have already occurred. The function returns without scanning, construction, the submission-data global read, or submission.

### Immediate trigger

If the initial checkpoint byte is nonzero and the first scanner call reports 0x13:

- The scanner receives the first converted address.
- The prefix displacement is zero.
- The suffix equals the first converted address because the saved incoming advancement is zero.
- The triggering call’s returned advancement does not change that suffix.
- Construction returns before the submission-data global is read.
- One submission follows, using that read value.

State 0x73 produces the same control flow.

### Ordinary state followed by a trigger

Suppose the first scanner call returns advancement 3 and a state outside the four distinguished values. If the checkpoint byte at the original cursor remains nonzero, the next group starts at that same address with incoming advancement 3.

If its scanner call triggers construction:

- The scanner receives the original address plus three bytes.
- The group anchor remains the original address.
- The prefix displacement is zero.
- The suffix is the original address plus three bytes.

### Within-group continuation

Suppose the first scanner call reports 0x91 with advancement 2, and the next reports 0x13.

The second call receives the initial address plus two bytes, without another checkpoint. Both calls belong to the initial group. Construction still receives a zero prefix displacement and the initial address as its suffix. State 0x93 has the same continuation role.

### High-bit advancement

If a group begins with incoming advancement 0x80000005, its first scanning addition uses that full unsigned quantity. If execution validly reaches construction in that group, the saved advancement contributes only 5 to the suffix address.

This example does not authorize out-of-bounds access or assume address wrapping.

### Construction changes submission data

Suppose the submission-data global contains one value before construction, and F-1983453691c7 changes it to a different value before returning. If no subsequent mutation intervenes before the read, submission receives the changed value.

An implementation that captures the global before construction would not satisfy this ordering.
