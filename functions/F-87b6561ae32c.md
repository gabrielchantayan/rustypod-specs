# F-87b6561ae32c

## Purpose

F-87b6561ae32c initializes destination fields, invokes an operation through invocation-local workspace, performs teardown, and conditionally publishes successful results.

A saved worker status selects failure or success. On success, option `0x400` selects between:

- **Ordinary mode:** publish metrics, invoke geometry transformations, transform two metrics, optionally scale points and metrics, publish bounds, and invoke a final bounds-related dependency.
- **Deferred-transform mode:** publish two metrics and store four transform words and two translation words in an associated object, then set a one-byte marker.

“Geometry,” “metric,” “transform,” “translation,” and “bounds” are inferred role names, not established units, formats, or dependency semantics.

The operation is not transactional. Initialization writes and dependency effects occur before the status check. No rollback is visible.

## Interface

| Input | Representation | Established role |
|---|---|---|

The result is the saved 32-bit status returned by F-c8ad6e35cfe2. Zero enables successful postprocessing. Any nonzero value bypasses it and is returned unchanged after teardown. Other dependency results do not provide an independent error status.

## Behavior

### Entry preparation

The function captures the context reference from destination `+0x04`, then captures the dispatch-related reference from that context’s `+0x88`.

It reads source `+0x10` and stores the word at destination `+0xa4`, then reads source `+0x14` and stores the word at destination `+0xa8`.

When option `0x400` is set, the invocation-local options value is augmented with `0x03`. No caller-owned options storage is written.

The following preparation occurs in order:

1. Clear destination `+0x6e` with a 16-bit write.
2. Determine a Boolean-like value: one if both option bits `0x01` and `0x02` are clear, otherwise zero.
3. Clear destination `+0x6c` with a 16-bit write.
4. Place that Boolean-like value in the second word of a reusable two-word coordinate area.
5. Evaluate the first global word and store it at destination `+0x48`.
6. Initialize the first word of a four-word bounds area from option bits 16–19, producing a value from zero through fifteen.
7. Set the first coordinate word to zero.
8. Initialize the second bounds word from the second global word.
9. Initialize a workspace control word from the Boolean-like value.

The bounds area therefore has two explicit early assignments. Its third and fourth words have no explicit initialization in the supplied body before the bounds dependency receives the area. Intervening dependencies may affect its contents; it is not established to be an output-only buffer.

### Workspace lifecycle

The initialization callback is selected through the captured dispatch-related object and its current table reference. Its arguments, in order, are:

1. Workspace address.
2. Context reference freshly read from destination `+0x04`.
3. Source descriptor.
4. Destination.
5. Zero.

The freshly read context argument need not equal the context reference captured earlier if intervening effects have changed destination storage.

After initialization returns, a one-byte workspace mode field is set to one when option `0x400` is set, otherwise zero.

F-c8ad6e35cfe2 receives the workspace address and processing input. Its status is saved. Four workspace-associated transform words are then copied, in order, into a separate four-word local area.

The teardown callback next receives the workspace address. Its table reference is read again through the captured dispatch-related object. The table used for initialization is not assumed to remain unchanged. Any teardown return value is ignored.

The saved status is inspected only after teardown. Consequently, teardown occurs for both zero and nonzero worker status, provided preceding calls return normally.

Only the four transform words are explicitly snapshotted at this point. Metrics, translations, point-container information, and workspace controls used later are not all similarly copied before teardown. Their validity and contents after teardown require dependency contracts not supplied here.

### Nonzero status

A nonzero saved status is returned without further direct destination writes by this body.

Entry writes and dependency effects remain observable. This path establishes neither rollback nor resource release.

### Common success update

For zero status, destination `+0x7c` is read and replaced with a word preserving only its existing bit zero and setting bit `0x04`. All other bits are cleared.

The read observes the value after the workspace lifecycle, not necessarily the entry value.

### Ordinary success: initial publication and global evaluations

When option `0x400` is clear:

1. A worker-associated metric is written to destination `+0x28`, then `+0x38`.
2. The associated reference is read from destination `+0x9c`, and its marker at `+0x08` is cleared.
3. The captured context’s signed field at `+0xc8` is subtracted from its signed field at `+0xd0`. The result is arithmetically shifted right by sixteen.
4. That result is written to destination `+0x34`, then `+0x3c`.
5. The first global word is evaluated into a temporary.
6. The first global word is independently evaluated again, and this second value is stored at destination `+0x48`.
7. If the source reference is nonzero, its unsigned 16-bit classification at `+0x0e` is read and replaces the temporary value.
8. Only for a nonzero source reference is the temporary compared against `0x18`. A smaller classification causes destination `+0x7c` to be reread and bit `0x100` set, preserving its other then-current bits.

Both ordinary-success global evaluations precede the conditional classification read. They are additional to the entry evaluation.

The preliminary global value does not determine the classification update: a nonnull source replaces it with classification, while a null source bypasses the threshold test. Nevertheless, the preliminary evaluation remains part of the established access sequence. The unavailable global declaration and access semantics do not justify omitting or merging these evaluations.

### Ordinary success: transformation

F-f7742bc6b842 receives destination `+0x6c` and the saved four-word transform area. F-074238b57126 then receives destination `+0x6c` and two workspace-associated translation words.

The same two-word coordinate area is reused for both calls to F-baed69327072:

- Before the first call, its first word receives the then-current destination `+0x28`, and its second word becomes zero. After the call, the first component plus the first translation is stored at destination `+0x28`.
- Only after that store, the first word becomes zero and the second receives the then-current destination `+0x34`. After the second call, the second component plus the second translation is stored at destination `+0x34`.

Both calls receive identical coordinate-area addresses and identical transform-area addresses. Pointer identity and reuse are observable to the dependency.

The first addition is signed 32-bit arithmetic. The second component is unsigned, so the second addition converts the translation to unsigned and produces a result modulo \(2^{32}\).

The body does not refresh destination `+0x38` or `+0x3c` to match these transformed metrics. Translations are not frozen by the earlier transform copy, and dependencies receiving the transform area are not established to preserve it.

### Ordinary success: optional scaling

Option `0x01` bypasses the entire scaling block.

Otherwise, a workspace control word is examined. A second workspace-associated condition word is read for the skip decision only when the control is nonzero. Points are skipped when both conditions are nonzero.

Before either processing or skipping points, the function captures, in order:

1. Destination `+0xa4` as the first scaling operand.
2. Destination `+0xa8` as the second scaling operand.
3. The point-array reference from the point container’s `+0x04`.

Skipping points therefore does not avoid the point-container reference access.

If points are enabled, the signed 16-bit count is read once and widened. Nonpositive counts cause no point-component accesses. A positive count processes that many eight-byte records, at most 32,767.

For each record:

- Read the first component, pass it and the captured first operand to F-74efb2674226, and replace the component with the returned word.
- Then read the second component, pass it and the captured second operand to the same dependency, and replace it.
- Advance to the next eight-byte record.

After the point loop, or after skipping it, destination `+0x28` is read, scaled through F-74efb2674226 using the captured first operand, and replaced. Destination `+0x34` is then similarly processed using the captured second operand.

Metric scaling therefore occurs even when the point-skip conditions suppress all point processing.

### Ordinary success: bounds

F-960c2eabcfd8 receives destination `+0x6c` and the four-word bounds area prepared earlier.

After it returns, direct publication occurs in this order:

| Destination | Value |
|---|---|
| `+0x18` | Third bounds word minus first bounds word. |
| `+0x1c` | Fourth bounds word minus second bounds word. |
| `+0x20` | First bounds word. |
| `+0x24` | Fourth bounds word. |

The first subtraction is unsigned 32-bit arithmetic because the first bounds word is unsigned. Its result is modulo \(2^{32}\), notwithstanding the signed representation of the destination store. The second subtraction is signed 32-bit arithmetic.

Finally, F-6f91c5ea8ecb receives destination `+0x18` and the then-current word at destination `+0x34`. Its effects are unknown; the preceding stores need not describe the final bounds state.

### Deferred-transform success

When option `0x400` is set, the associated reference is captured from destination `+0x9c`. The function then writes, in order:

1. One worker-associated metric to destination `+0x20`.
2. Another worker-associated metric to destination `+0x28`.
3. The four saved transform words to associated offsets `+0x0c`, `+0x10`, `+0x14`, and `+0x18`.
4. Two translation words to associated offsets `+0x1c` and `+0x20`.
5. One to the associated marker at `+0x08`.

Ordinary-mode global reevaluations, classification handling, geometry calls, scaling, and bounds processing do not occur. Fields not written on this branch are not implicitly reset.

## Side effects

Direct effects comprise destination writes, associated-state writes, and conditional point-array replacement. Dependencies may have additional effects.

No explicit saturation or overflow checks are present. Unsigned addition and subtraction described above are modulo \(2^{32}\). Signed context subtraction, first transformed-metric addition, and second bounds subtraction do not establish portable signed-overflow wraparound. Exact signed results require representable intermediates or additional execution-model evidence.

Access timing matters:

- The first global is evaluated once at entry and twice more on ordinary success.
- The two ordinary-success evaluations are distinct and precede classification.
- The callback table is reread for teardown.
- Scaling operands are captured after transformation calls.
- Workspace-derived values may be read after teardown.
- Values published before later dependencies may be changed by those dependencies.

No exception handling, memory-fault recovery, synchronization, or rollback is visible.

## Acceptance examples

These are conditional static criteria, not executed tests.

1. **Failure lifecycle:** If the worker returns a nonzero status and teardown returns normally, teardown precedes return of that same status. Successful publication does not run; entry and dependency effects remain.

2. **Success bits:** If destination `+0x7c` is all ones at the common success update, that update produces `0x05`. Ordinary classification below `0x18` subsequently produces `0x105`, absent intervening mutation.

3. **Global evaluation order:** On ordinary success, the preliminary global evaluation precedes the independent evaluation used for destination `+0x48`; both precede classification. If those evaluations yield different words, the destination receives the second. Neither value substitutes for a nonnull source’s classification.

4. **Classification boundary:** With valid nonnull source storage, classification `0x17` triggers the `0x100` update; `0x18` does not. A null source would bypass the threshold test, but does not satisfy the earlier source-read precondition.

5. **Temporary identity:** Both F-baed69327072 calls receive the same coordinate-area address. The first metric store precedes reinitialization for the second call.

6. **Unsigned addition:** If the second transformed component is `0xffffffff` and its translation is two, destination `+0x34` receives `0x00000001` before optional scaling.

7. **Bounds preparation:** With option bits 16–19 equal to nine, the first bounds word is initially nine and the second initially receives the second global word. Their later values require intervening-preservation assumptions; this does not establish initialization of the remaining words.

8. **Bounds arithmetic:** Returned bounds words 10, 20, 35, and 70 cause direct stores of 25, 50, 10, and 70 at `+0x18`, `+0x1c`, `+0x20`, and `+0x24`. First word one and third word zero instead produce `0xffffffff` at `+0x18`. Final-dependency effects remain separate.

9. **Scaling boundaries:** Ordinary option `0x01` suppresses scaling but not transformations or bounds processing. With scaling enabled and both skip conditions nonzero, the point-array reference is still read and both metric-scaling calls still occur.

10. **Signed count:** With point processing enabled, count `0xffff` is negative and causes no component accesses. Count two causes four component-scaling calls in record order, followed by two metric-scaling calls.

11. **Deferred publication:** Successful option `0x400` processing writes transform and translation words before setting the associated marker to one, without ordinary postprocessing.
