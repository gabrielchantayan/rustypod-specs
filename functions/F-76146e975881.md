# F-76146e975881

## Purpose

F-76146e975881 dispatches an opaque caller value and a context reference to callbacks described by eight-byte entries. For an ordinary nonnegative entry count, dispatch proceeds from the highest index to index zero.

A mode argument selects direct traversal or a temporary-storage path. Direct traversal reads entries from a captured context storage address. The temporary-storage path requests storage, invokes an external operation consistent with copying entries, and then rereads the acquisition-result pointer slot to select the traversal address.

**The destination supplied to the copying dependency and the address subsequently used for traversal are not guaranteed to be equal.** The acquisition dependency receives the address of the result storage; whether it retains that address or enables later mutation is unknown.

Isolation from subsequent changes to original entry bytes is therefore conditional: the external operation must actually copy the required bytes, and the post-call traversal pointer must identify those copied bytes. An unchanged acquisition-result pointer slot is the straightforward case. No deep copy, general reentrancy protection, or ownership transfer is established.

All behavior below is derived from the supplied static representation. No runtime tests have been performed.

## Interface

### Arguments and result

| Input | Represented width | Meaning |
|---|---:|---|
| Context reference | 32 bits | Address of the context fields below; also passed to callbacks and the explicit failure dependency. |
| Caller value | 32 bits | Opaque value passed unchanged as the first callback argument. |
| Mode selector | 32 bits | Zero selects direct traversal; every nonzero value selects the temporary-storage path. |

The function has no explicit result value. It supplies no returned status distinguishing successful dispatch, absent storage, an empty sequence, or the explicit acquisition-failure path.

Addresses are represented by 32-bit quantities. A wider-pointer interface, particular calling convention, and portable pointer-conversion rules are not established.

### Context layout

| Byte offset | Width | Observed role |
|---|---:|---|
| `0x10` | 32 bits | Flag word read on the explicit null-acquisition path. |
| `0x2c` | 32 bits | Entry-storage address, read at multiple distinct points. |
| `0x30` | 32 bits | Entry count, initially captured and reread for the copy size. |

No direct writes to these context fields are visible.

The context must support the initial read at `0x2c`; there is no null-context check. Further readability requirements depend on the selected path.

### Entry layout and callback interface

Each entry occupies eight bytes:

| Entry-relative offset | Width | Meaning |
|---|---:|---|
| `0` | 32 bits | Opaque per-entry value. |
| `4` | 32 bits | Encoded callback address. |

Before invocation, the encoded callback address is masked with `0xfffffffc`, clearing its lowest two bits. The resulting address is invoked with:

1. The caller value.
2. The original context reference.
3. The selected entry’s opaque value.

The cleared bits are not passed separately. Their meaning is unknown; interpreting them as tags or flags is inferred intent only.

Every accessed entry must be readable, and every masked callback address must be a valid target for this invocation. No bounds, null-target, or executable-address checks are visible.

## Behavior

### Initial context reads

The function first reads the storage-address field at `0x2c`.

If that value is zero, it returns immediately. It does not read the count or flags, request storage, invoke the copying dependency, dispatch callbacks, or invoke cleanup.

Otherwise, it reads the count at `0x30` and then reads the storage-address field at `0x2c` again. These are distinct reads:

- The first storage read is a presence check.
- The count read establishes the traversal count.
- The second storage read establishes the direct-traversal base.

There is no visible synchronization or consistency check. A nonzero first storage read does not guarantee that the second read remains nonzero.

The captured count controls traversal even if dependencies or callbacks later change the context’s count.

### Direct traversal

With mode zero, no storage-acquisition or copying call occurs. Traversal uses the second storage-address read.

For a nonnegative captured count of \(N\), selected indices are \(N-1, N-2, \ldots, 0\). Count zero selects no entries.

At each selected index, the function obtains the encoded callback address and opaque value from that entry, masks the address, and invokes the callback. Both entry values are obtained before the invocation; the supplied representation does not establish a portable ordering between those two reads.

Entries are read when their turn is reached, not all at function entry. A callback that changes a pending entry can therefore affect a later invocation. Replacing only the context’s storage-address field does not redirect traversal, because the traversal base is already captured.

The callback’s normal return value is not consumed. A normally returning callback is followed by the next selected entry.

### Temporary-storage request and descriptor preparation

With any nonzero mode, F-10323b21a777 is called with three visible arguments:

1. The address of local acquisition-result storage.
2. Zero.
3. A requested byte count formed by shifting the captured count left by three bits.

After that call returns, the function reads a 32-bit pointer-like result and a second unsigned 32-bit result word. It prepares a separate cleanup descriptor containing:

- A copy of the pointer-like result.
- The second result word shifted logically right by three bits.

The descriptor is prepared before the external copying call. The logical right shift discards the low three bits and inserts zeros at the high end. The second word’s meaning is unknown; neither a capacity interpretation nor ownership semantics are established.

The acquisition-result storage has been exposed to F-10323b21a777 by address. No evidence establishes that the dependency forgets this address, preserves the result afterward, or prevents another dependency from changing it.

### Explicit null-acquisition path

If the acquisition-result pointer is zero at the null check:

1. The current context flag word at `0x10` is read.
2. Bit zero is set in the argument value.
3. F-aa175cfe6908 is called with the context reference, that modified flag value, and `0xffffffff`.
4. The function returns if the dependency returns normally.

There is no copy, callback dispatch, or final cleanup call on this branch.

The flag operation does not itself write the context. Any persistent flag update depends on F-aa175cfe6908.

Descriptor preparation precedes the null check, including the read of the second acquisition-result word. Whether F-10323b21a777 initializes that word on failure is unknown.

### External copy call and post-call pointer capture

For a nonzero acquisition result, F-EXT-01 receives:

1. The acquisition-result pointer value evaluated before this call, as destination.
2. A fresh read of context offset `0x2c`, as source.
3. A fresh read of context offset `0x30`, shifted left by three bits, as byte count.

The source and size reads occur after acquisition. Their relative evaluation order is not established by the supplied representation.

Acquisition size and traversal count use the original count, while copy size uses the later count. A mutation during acquisition can therefore make requested size, copied size, and traversed extent inconsistent. No reconciliation or rejection is visible.

**After F-EXT-01 returns, the function rereads the pointer from the acquisition-result storage and captures that value as the traversal base.** It does not simply retain the destination argument used for F-EXT-01.

Consequences:

- The traversal base can differ from the copy destination if the result slot changes during the external call.
- The earlier null check does not validate the post-call traversal base.
- No second null check or equality check is visible.
- A changed post-call pointer is used even if it does not identify the copied storage.

The original captured count still controls traversal.

### Temporary traversal and cleanup

Temporary-path dispatch interprets entries and invokes callbacks in the same reverse order as direct traversal, but uses the post-copy traversal base.

If the result slot remains unchanged and F-EXT-01 copies the required bytes, traversal reads the copied entries. Later changes to the original entry bytes then do not affect those copied bytes. This guarantee additionally requires that callbacks and other actors do not modify the temporary entries before they are read.

After the post-call traversal base is captured, later changes to the acquisition-result slot alone do not redirect traversal.

After all callbacks return normally, F-10323b21a777 is called again with two visible arguments:

1. The address of the cleanup descriptor prepared before F-EXT-01.
2. The captured post-copy traversal pointer.

These arguments need not describe the same address. If the acquisition-result slot changes during F-EXT-01, the descriptor’s pointer field retains the earlier copied value, while the second cleanup argument uses the later traversal value, absent independent modification of the descriptor itself.

The final call is consistent with cleanup, but its actual release behavior is unknown. The function does not visibly rebuild the descriptor to match the post-copy traversal pointer.

### Count and arithmetic boundaries

The captured count is represented as a signed 32-bit quantity. The loop tests for nonzero rather than positivity and decrements before accessing each selected entry.

A negative count is not treated as empty. It enters traversal and leads toward negative-index-style address calculations. No safe behavior is established for such input.

Requested and copied byte counts are formed by a left shift of three bits without a visible overflow check or widening conversion. The mathematical quantity \(8N\) fits an unsigned 32-bit word for nonnegative \(N \leq 536{,}870{,}911\), but that bound does not establish valid signed-shift semantics, valid address arithmetic, or sufficient accessible storage.

Overflowing shifts, decrements, index multiplication, and address calculations must not be assumed to wrap, saturate, or fail cleanly.

Count zero suppresses callbacks but does not bypass acquisition, copying, or cleanup when mode is nonzero and the initial storage check succeeds.

## Side effects

### Directly visible effects

The function reads context fields, acquisition-result storage, and selected entry bytes. It invokes dependencies and indirect callbacks, and writes local acquisition and cleanup state.

No direct write to original entry storage or context fields is visible. F-EXT-01 receives a destination address and may write there according to its unknown semantics.

Dependencies and callbacks may mutate context fields, global state, entry storage, escaped local storage, or ownership state. Their preservation behavior is not assumed.

### Ownership and lifetime

The original entry storage is used as a borrowed source. No visible call explicitly releases it.

Direct traversal requires the captured original storage to remain readable for every selected access. Changing the context field does not replace that requirement; freeing the captured storage can invalidate later reads.

The temporary path requires valid source and destination storage for the external operation. Subsequent traversal requires the **post-copy traversal address**, not merely the earlier destination, to remain valid.

The acquisition-result slot, copy destination, traversal address, and descriptor pointer field must not be treated as one immutable ownership identity. Their equality is conditional.

No dedicated temporary pointer is passed to callbacks. Opaque entry values or external state may nevertheless expose it indirectly.

### Abnormal exits

No local recovery mechanism is visible for invalid memory, invalid callback addresses, arithmetic failure, or dependency behavior outside the explicit null-result branch.

If a callback or dependency does not return normally, subsequent callbacks and final cleanup are not guaranteed. Exception-safe and nonlocal-exit-safe resource release are not established.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless stated otherwise, they assume valid memory, valid callback targets, representable arithmetic, and normally returning dependencies.

### Absent storage

If the first storage-field read returns zero, the function returns without reading the count or invoking any dependency or callback, regardless of mode.

### Direct reverse traversal

For count three and mode zero, callbacks run for indices two, one, and zero. Each receives the original caller value and context reference, followed by its entry value. No temporary-storage calls occur.

An encoded callback address of `0x1234567b` selects `0x12345678`; validity of that target remains a precondition.

### Pending-entry mutation

For two direct-mode entries, index one runs first. If it changes index zero’s value before returning, index zero’s invocation uses the changed value. Replacing only the context storage field does not redirect that access.

### Successful unchanged-result copy

For stable context fields and count two, acquisition requests sixteen bytes. If acquisition returns address \(A\), F-EXT-01 receives \(A\) and a size of sixteen.

If F-EXT-01 copies those bytes and the acquisition-result slot remains \(A\), traversal uses the copied entries at \(A\), in order one then zero. Cleanup follows with a descriptor containing \(A\) and a second argument equal to \(A\).

### Changed result during the external call

Suppose acquisition initially supplies \(A\), so the cleanup descriptor contains \(A\) and F-EXT-01 receives destination \(A\). If an allowed dependency side effect changes the acquisition-result slot to \(B\) before F-EXT-01 returns, traversal uses \(B\).

If \(B\) contains valid entries, those entries determine dispatch, whether or not F-EXT-01 copied data to \(A\). Cleanup receives the descriptor containing \(A\) and second argument \(B\). Its resource behavior for this mismatch is unknown.

If \(B\) is zero with a positive captured count, no second null check prevents an invalid entry access.

### Acquisition failure

If the acquisition-result pointer is zero and the subsequent flag read returns `0x20`, F-aa175cfe6908 receives `0x21` and `0xffffffff` as its second and third arguments. No copy, callback, or final cleanup call follows.

### Empty temporary traversal

With nonnull initial storage, captured count zero, and nonzero mode, acquisition still requests zero bytes. A null result takes the explicit failure path.

A nonzero result reaches F-EXT-01 using the freshly read count. After its return, the pointer slot is reread, no callbacks occur, and cleanup receives that post-call pointer. The earlier descriptor can contain a different pointer.

### Count mutation during acquisition

If the captured count is two but acquisition changes the context count to three, the requested size is sixteen bytes, the copy size is twenty-four bytes, and traversal still selects two entries. No consistency check repairs this mismatch.

Established static evidence includes fixed-offset context reads, eight-byte entry addressing, descending dispatch, callback-address masking, conditional acquisition, pre-copy descriptor preparation, post-acquisition context rereads, the explicit null-result branch, the **post-copy reread of the acquisition-result pointer**, and the final dependency call using that captured traversal pointer.
