# F-1cf78c395e57

## Purpose

F-1cf78c395e57 obtains an opaque object, offers it to handlers in an optional first-stage collection, and, if none returns a nonzero result, processes a fallback chain. The first nonzero handler result terminates processing and becomes the function’s result. If processing completes without such a result, the function returns zero.

Before a normal return, a nonnull object receives a virtual call at table byte offset +0x04. The call is established; its meaning as release, destruction, reference-count adjustment, or another operation is not.

“Dispatch object,” “handler,” “eligibility,” and “successor” describe inferred roles. The contract below distinguishes those interpretations from established call order, accesses, and branch conditions.

## Behavior

### 1. Acquire the dispatch object

The acquisition sequence is ordered:

1. Call F-f2ddcdbfb0c6 without explicit arguments.
2. Pass its result and the 32-bit constant 0x0000000C to F-c5a232e4455b.
3. Pass that result and the original input to F-05f371f0dba5.
4. Retain the final result as the dispatch-object pointer.

No intermediate result is checked locally. A null final result continues into first-stage and fallback processing.

After acquisition, initialize the handler-result state to zero.

### 2. Inspect and, conditionally, iterate the first stage

Call F-3fdd14ecd250 and retain its returned context for the first-stage decision.

Evaluate the 32-bit field at context offset +0x2C as the branch condition.

- If that evaluation is zero, skip iterator initialization, iteration, and iterator finalization.
- If it is nonzero, evaluate the field at the same context offset again to obtain the collection argument for F-538044b67754.

The conditional evaluation and argument evaluation are distinct in the supplied representation. No dependency call intervenes between them, and there is no second context lookup between them. Nevertheless, the contract does not replace the argument evaluation with the condition’s value or guarantee that the two values match. Whether these evaluations become distinct machine loads or can observe concurrent changes is unresolved.

On the nonzero branch, F-538044b67754 receives:

- The local iterator storage;
- The collection value from the argument evaluation;
- The 32-bit bit pattern 0xFFFFFFFE.

There is no second zero check on the argument value before this call.

After initialization:

1. Call F-6e4651b532dc with iterator storage and the element-output area.
2. If its result is zero, iteration is exhausted.
3. Otherwise, use the first pointer-sized output word as the element pointer and invoke its virtual target at +0x34 with the dispatch object.
4. Continue advancing while handler results are zero.
5. Stop on the first nonzero handler result.

No element-pointer null check precedes the virtual call. The dispatch object is passed even when null.

F-944b595e25e9 is called once on each normally completed initialized iteration path, whether iteration ends through exhaustion or a nonzero handler result.

After finalization:

- A nonzero handler result bypasses fallback processing.
- Exhaustion proceeds to fallback with the handler result still zero.

The decision to initialize and later finalize the iterator follows the conditional field evaluation. The collection actually supplied to initialization comes from the separate argument evaluation.

### 3. Capture the fallback head, then select eligibility mode

Fallback processing begins only when no first-stage handler has returned nonzero.

Call F-3fdd14ecd250 again. Read its returned context’s 32-bit field at +0x28 and retain that value as the initial candidate pointer.

This lookup occurs after any initialized iterator has been finalized. It is not replaced by reuse of the first-stage context. The two context results need not identify the same object.

After capturing the fallback head, select eligibility mode:

- A null dispatch object selects unrestricted mode without an object-mode call.
- A nonnull dispatch object receives the virtual call at +0x14.
  - A zero low 32-bit result selects unrestricted mode.
  - A nonzero low 32-bit result selects restricted mode.

This mode-selection call occurs even if the already captured fallback head is null. It does not cause the function to reread the context’s fallback-head field.

Mode is selected once for the fallback traversal, not recomputed for each candidate.

The represented high 32 bits do not affect an observed eligibility or traversal decision. The visible high-word initialization to 0x00000A00 on the null-object path likewise establishes no additional behavioral setting. The ABI significance of those high words remains unknown.

### 4. Process fallback candidates

At the loop boundary, stop if the current candidate is null or the handler-result state is nonzero. These tests do not themselves dereference a candidate.

For each nonnull candidate reached while the result is zero, behavior depends on the selected mode.

#### Unrestricted mode

Invoke the candidate’s virtual target at +0x30 with the dispatch object.

The function does not inspect the associated record as an eligibility prerequisite on this path.

#### Restricted mode

Read the candidate’s associated-record pointer at +0x0C, then read the 32-bit eligibility field at +0x0C within that record.

- If the eligibility field is zero, invoke the candidate’s virtual target at +0x30.
- If the field is nonzero, call F-35b8bd5fa9e0 with the dispatch object.
  - A nonzero result permits the candidate handler call.
  - A zero result skips the handler and leaves the handler-result state zero.

There is no associated-record null check before the eligibility-field read. The later termination check does not protect this earlier dereference.

The eligibility dependency is consulted separately for each reached candidate whose restricted-mode eligibility field is nonzero. The mode itself remains fixed.

#### After an invoked handler

Store the handler’s 32-bit result.

If it is nonzero, stop traversal immediately. Do not perform the post-handler associated-record read or the successor call.

#### After a zero handler result or skipped handler

Evaluate the candidate’s associated-record pointer at +0x0C for termination:

- If null, stop traversal with zero.
- If nonnull, invoke the candidate’s virtual target at +0x1C.

The low 32 bits of the represented 64-bit successor result become the next candidate pointer. The high word does not affect subsequent handler selection.

The termination evaluation is separate from the earlier restricted-mode eligibility access. An intervening eligibility dependency or handler may change the candidate’s associated-record pointer. No preservation of that field, virtual tables, or reachable objects is established.

The function has no visible cycle detection or traversal bound. If successor calls keep producing nonnull candidates, handlers keep returning zero or being skipped, and associated-record termination checks remain nonnull, processing can continue indefinitely.

### 5. Finalize the dispatch object and return

After either stage finishes normally:

- If the dispatch object is nonnull, invoke its virtual target at +0x04.
- If it is null, omit that call.
- Return the saved 32-bit handler result.

This final call follows iterator finalization whenever iteration was initialized. It also occurs when fallback has no candidates or completes without a nonzero handler result.

No explicit mechanism guarantees iterator or object finalization when a dependency faults, does not return, or exits nonlocally.

## Side effects

Established direct effects are local-state updates, context and object-field evaluations, virtual-table accesses, and the ordered dependency calls described above.

The supplied body contains no explicit write to a context field, fallback candidate, or associated record. It does pass local iterator and output storage to dependencies that may modify that storage.

Dependency effects are otherwise unconstrained by the visible body:

- Acquisition calls may change state before the first context lookup.
- Iterator operations, first-stage handlers, and iterator finalization may affect the later fallback lookup.
- The object-mode call occurs after the fallback head is captured and may change objects reachable through that retained pointer.
- Eligibility calls and handlers may affect later candidate-field evaluations and successor selection.
- Iterator finalization and the final object call may have externally visible effects.

The first-stage collection condition and collection argument are separate source-level evaluations. This is not, by itself, a concurrency, volatility, synchronization, or physical-load guarantee.

Ownership is unspecified. The function does not directly allocate or free memory in the supplied representation. The acquisition sequence and final virtual call do not establish whether the object is newly allocated, borrowed, reference-counted, transferred, released, or destroyed. No ownership or release responsibility is established for collection elements, candidates, or associated records.

## Acceptance examples

These are conditional obligations derived from static evidence, not runtime observations. Normal-return examples assume that reached accesses and calls are valid and return normally.

1. **A zero conditional collection value skips iteration.**  
   If the first-stage field’s conditional evaluation is zero, there is no collection-argument evaluation for iterator initialization, no iterator initialization, and no iterator finalization. Fallback processing begins.

2. **A nonzero condition does not fix the collection argument.**  
   If the conditional evaluation is nonzero and the subsequent argument evaluation supplies value A, F-538044b67754 receives A. The contract does not require A to equal the earlier value. If A is zero, initialization is still reached; behavior within that dependency for a zero collection is unspecified. This example does not assert that a value change is observable on the target machine.

3. **First-stage handling takes precedence.**  
   If an initialized iterator yields an element whose handler returns −7, iterator finalization occurs, fallback is skipped, the nonnull dispatch object receives its final call, and −7 is returned.

4. **An empty initialized iteration still finalizes.**  
   If the first iterator-advance call returns zero, iterator finalization occurs before the fallback context lookup and head read.

5. **Null objects still reach handlers.**  
   If acquisition yields null and first-stage processing does not handle the request, fallback uses unrestricted mode. A reached fallback handler receives null. If it returns 5, the function returns 5 without an object-finalization call.

6. **A null fallback head does not suppress mode selection.**  
   With a nonnull dispatch object and a null captured head, the object call at +0x14 still occurs. No fallback handler runs. The final object call occurs and zero is returned.

7. **Restricted eligibility may skip a handler.**  
   Given a valid associated record with a nonzero eligibility field and a zero result from F-35b8bd5fa9e0, the handler is skipped. A subsequent nonnull associated-record termination value leads to the successor call.

8. **A zero eligibility field bypasses the eligibility dependency.**  
   In restricted mode, a valid record whose eligibility field is zero permits the handler without calling F-35b8bd5fa9e0.

9. **A nonzero handler result bypasses termination inspection.**  
   If a fallback handler returns 9, no post-handler associated-record evaluation or successor call follows. After final object handling, 9 is returned.

10. **Handler mutation can terminate traversal.**  
    If a handler returns zero after changing its candidate’s associated-record pointer to null, and that change is visible to the subsequent evaluation, traversal ends without a successor call.

11. **A null record has mode-dependent consequences.**  
    In unrestricted mode, the handler runs before record-based termination is checked. In restricted mode, a null record is dereferenced for eligibility before that later check; normal completion is not established for that input.
