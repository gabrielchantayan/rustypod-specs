# F-013646405fff

## Purpose

F-013646405fff rearranges four-byte address-bearing links among an input object, an object selected through that input, and either an external anchor or an upstream object.

The link arrangement is consistent with a left rotation in a parent-linked binary tree: a pivot’s right-side object is promoted, its left-side link is transferred to the pivot, and the pivot becomes its left-side object. That interpretation is inferred intent. The established contract is the ordered memory-access behavior below, without a requirement that the objects actually form a tree.

The operation performs no structural validation and returns no status. In particular, selecting an upstream field for replacement does not always establish that the field previously referenced the pivot.

## Interface

### Inputs and output

The function accepts two address-bearing inputs:

- **Context address:** identifies storage whose field at byte offset `0x10` supplies an anchor address.
- **Pivot address:** identifies the object whose links are rearranged.

There is no explicit return value. Results are observable through writes to reachable storage.

The role names used here—context, anchor, pivot, promoted object, transferred object, and upstream object—describe how addresses are used during an invocation. They do not establish separate allocations, distinct types, ownership, or non-aliasing.

### Widths and layout

The supplied representation uses 32-bit integer address carriers and four-byte link fields. This contract describes that represented memory model, not a native 64-bit pointer layout. Offsets are measured in bytes.

| Role | Offset | Access and meaning within this operation |
|---|---:|---|
| Context | `0x10` | Read to obtain the anchor address |
| Anchor | `0x04` | Read for comparison with the pivot; conditionally replaced |
| Pivot | `0x04` | Read as an upstream value; finally replaced with the promoted address |
| Pivot | `0x0c` | Initially read to select the promoted object; replaced with a transferred link |
| Promoted object | `0x04` | Receives the pivot’s current upstream value |
| Promoted object | `0x08` | Read to obtain or inspect the transferred link; finally replaced with the pivot address |
| Transferred object | `0x04` | Conditionally receives the pivot address |
| Upstream object | `0x08` | Read for comparison with the pivot; replaced on an equal comparison |
| Upstream object | `0x0c` | Replaced on an unequal comparison, without checking its previous value |

Each listed access concerns four bytes. No payload fields, object size fields, balancing metadata, or other object layout are established.

The operation uses equality comparisons, address copying, and fixed-offset address calculations. It performs no link-value increment, size calculation, or ordering comparison. Signedness does not alter the intended bitwise equality distinctions, but the representation does not establish portable behavior for overflowing address calculations.

### Preconditions for ordinary completion

All effective addresses actually accessed must designate accessible storage of sufficient extent. Written fields must be writable. Any alignment requirements belong to the target environment and are not established here.

In particular:

- The pivot must permit the listed accesses at `0x04` and `0x0c`.
- Its initial `0x0c` value must permit accesses at `0x04` and `0x08`; the function does not check that address for zero.
- If the transferred-link comparison is nonzero, the address obtained by a subsequent read must permit a write at `0x04`.
- The context must permit a read at `0x10`.
- The anchor selected by that read must permit an access at `0x04`.
- On the non-anchor branch, the pivot’s then-current `0x04` value must permit the selected upstream accesses.

These are branch-sensitive requirements. A copied upstream value need not be dereferenceable when the anchor branch is taken.

For an ordinary-memory interpretation, effective-address calculations must also be valid in the target execution model. Neither wraparound addressing nor recovery from invalid arithmetic or memory access is established.

## Behavior

### Promotion selection and link transfer

The pivot’s initial `0x0c` value selects the promoted object. That selected address is retained for the later accesses associated with this role; the function does not reselect it from the pivot after overwriting the pivot’s link.

The promoted object’s `0x08` field supplies the value first written into the pivot’s `0x0c` field. This write occurs before any upstream-link transfer or anchor lookup.

The function then reads the promoted object’s `0x08` field again to decide whether to update a transferred object. A zero comparison result skips that update. A nonzero result causes another read of the same field; the address from that last read selects the object whose `0x04` field receives the pivot address.

These are distinct represented reads, not one saved transferred-link value reused throughout. Consequently:

- The value installed in the pivot need not equal the value tested for zero.
- The tested value need not equal the address ultimately used for the transferred-object write.
- The final destination address is not checked for zero independently.

For stable ordinary memory with distinct relevant fields, these reads observe the same value. That equality is a condition of the simplified interpretation, not a guarantee imposed by the routine. Aliasing may change a later read after an earlier write. Behavior under concurrent or read-sensitive memory additionally depends on the execution environment.

### Upstream-value transfer

After the optional transferred-object write, the pivot’s current `0x04` value is read and copied into the promoted object’s `0x04` field.

The source value is obtained at this stage, not saved at entry. Earlier writes can therefore affect it when storage aliases. The promoted object’s upstream field is written before the context is consulted.

### Anchor or upstream replacement

The context’s `0x10` field is read to select an anchor. The anchor’s `0x04` field is then read and compared with the pivot address.

If equal, that same selected anchor field receives the promoted address. This branch does not dereference an upstream object.

If unequal, the function reads the pivot’s current `0x04` field again to select an upstream object. This is a fresh read after the promoted object’s upstream field has been written; it is not necessarily the value copied in the preceding phase.

The upstream object’s `0x08` field is compared with the pivot address:

- Equality selects `0x08` for replacement with the promoted address.
- Inequality selects `0x0c` for replacement with the promoted address.

The latter branch does not inspect the previous value at `0x0c`. It can replace zero or an unrelated link without reporting a structural error.

Across all these alternatives, exactly one anchor-or-upstream field is written. The anchor comparison determines which path is taken; a zero upstream value or an inferred tree-root property does not determine that choice.

### Final attachment

After the selected anchor-or-upstream replacement, the promoted object’s `0x08` field receives the pivot address. The pivot’s `0x04` field then receives the promoted address.

These are the final two represented writes, in that order. The function returns without a result value.

### Conditional final-state interpretation

With stable ordinary memory and distinct relevant structural fields, completion has the following net effect:

- The pivot’s `0x0c` field contains the promoted object’s former `0x08` value.
- If that value was nonzero, the transferred object’s `0x04` field contains the pivot address.
- The promoted object’s `0x04` field contains the pivot’s former upstream value.
- Exactly one selected anchor or upstream link contains the promoted address.
- The promoted object’s `0x08` field contains the pivot address.
- The pivot’s `0x04` field contains the promoted address.

This describes the conventional rotation result under stated conditions. It does not replace the ordered-access behavior for aliased or changing storage.

## Side effects

Ordinary completion performs **five unconditional four-byte writes**, plus **one conditional four-byte write** when the transferred-link comparison is nonzero: **five or six writes total**.

The write order is:

| Order | Destination | Condition |
|---|---|---|
| 1 | Pivot, `0x0c` | Always |
| 2 | Transferred object, `0x04` | Only if the transferred-link comparison is nonzero |
| 3 | Promoted object, `0x04` | Always |
| 4 | One anchor or upstream field | Always; the alternatives collectively perform one write |
| 5 | Promoted object, `0x08` | Always |
| 6 | Pivot, `0x04` | Always |

The order labels include the optional write; omitting it leaves five writes. These counts concern represented write operations, not distinct physical destinations. Aliasing can make multiple writes target the same field.

The function mutates caller-reachable storage. It contains no explicit allocation, deallocation, resource acquisition, logging, callback, or external function invocation. No ownership transfer or object release is expressed.

There is no visible rollback or transaction mechanism. Several writes precede later dereferences, so a later access failure may occur after earlier modifications. The evidence does not establish a recoverable error result or the environment’s fault behavior.

No synchronization is visible. Intermediate link arrangements exist, and concurrent safety is not established.

Only the listed fields are explicitly accessed. Claims about unrelated conceptual objects require care because their storage may alias one of these fields.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Unless otherwise stated, assume valid effective addresses, stable ordinary memory, distinct relevant fields, and no concurrent changes.

### Anchor replacement with a nonzero transferred link

Suppose the anchor’s `0x04` field references the pivot, the pivot’s `0x0c` field references the promoted object, and the promoted object’s `0x08` field references a nonzero transferred object.

After completion:

- The pivot’s `0x0c` field references the transferred object.
- The transferred object’s `0x04` field references the pivot.
- The promoted object’s `0x04` field contains the pivot’s former upstream value.
- The anchor’s `0x04` field references the promoted object.
- The promoted object’s `0x08` field references the pivot.
- The pivot’s `0x04` field references the promoted object.

Exactly six four-byte writes occur. The pivot’s former upstream value is copied but not dereferenced on this branch.

### Upstream `0x08` replacement

Suppose the anchor’s compared field does not reference the pivot, while the pivot’s upstream object has the pivot address in its `0x08` field.

The upstream object’s `0x08` field receives the promoted address. Its distinct `0x0c` field is unchanged. The transfer and final attachment still occur.

The invocation performs five writes if the transferred-link comparison is zero, or six if nonzero. Selecting this upstream branch does not add a second replacement write.

### Unchecked upstream `0x0c` replacement

Suppose neither the anchor’s `0x04` field nor the selected upstream object’s `0x08` field equals the pivot address.

The upstream object’s `0x0c` field receives the promoted address even if it previously contained zero or referenced an unrelated object. The function produces no structural-error status.

This case must not be rejected merely because it fails the inferred tree interpretation.

### Zero transferred link

Suppose the promoted object’s `0x08` field remains zero throughout the early reads.

The pivot’s `0x0c` field becomes zero, and no transferred-object write occurs. The promoted object’s `0x08` field later receives the pivot address. Exactly five four-byte writes occur.

This zero handling does not apply to the promoted address itself: that address is dereferenced without a zero check.

### Different values on repeated transferred-link reads

If the environment permits the separate reads to produce different values, the first value determines the pivot’s replacement link, the second determines whether an optional write occurs, and the third—when reached—determines its destination.

A nonzero second value does not validate the third value. Ordinary completion in this case requires the destination selected by the third read to be writable at `0x04`.

### Promoted object aliases the pivot

Suppose the pivot’s initial `0x0c` field contains its own address.

The function performs no self-reference rejection. Subject to valid accesses, the ordered operations still apply. The final writes to the promoted object’s `0x08` and the pivot’s `0x04` both store the pivot address because the two roles identify the same object.

No valid-tree rotation outcome is implied.
