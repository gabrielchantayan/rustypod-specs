# F-7d79549af4b7

## Purpose

F-7d79549af4b7 selects one 28-byte record from a caller-supplied allocation state and clears specific fields in that record. It prefers a record from a linked available-record list. If that list is empty, it consumes the next record in the current contiguous region, allocating a new region when the current cursor equals its end marker.

The function returns no value. The selected record is observable through memory modifications and allocation-state changes, not through a returned address.

The organization suggests a record pool with reusable records and chained backing regions. That interpretation is inferred intent; the established behavior is the selection, allocation, state-update, and partial-clearing contract below.

## Interface

### Argument and result

The sole argument is a pointer to a writable state structure with four consecutive 32-bit fields:

| Byte offset | Width | Contract role |
|---|---:|---|
| 0 | 32 bits | Address of the current region descriptor, or zero |
| 4 | 32 bits | Address of the first available record, or zero |
| 8 | 32 bits | Address of the next unused record in the current region |
| 12 | 32 bits | End marker for the current region |

Addresses are represented using the 32-bit model visible in the supplied material. This contract does not establish a portable 64-bit layout.

The function has no explicit status result, selected-record result, or error result.

### Region descriptor

A newly allocated region descriptor occupies 12 bytes:

| Byte offset | Width | Meaning assigned by this function |
|---|---:|---|
| 0 | 32 bits | Previous region-descriptor address |
| 4 | 32 bits | Region capacity, measured in 28-byte records |
| 8 | 32 bits | Backing-storage address |

When calculating a new capacity, the function reads the capacity at offset 4 of the descriptor initially referenced by the state.

### Record layout

Each record occupies 28 bytes. The function uses or modifies these fields:

| Byte offset | Width | Use |
|---|---:|---|
| 0 | 1 byte | Cleared after selection |
| 4 | 32 bits | Cleared after selection |
| 8 | 32 bits | Cleared after selection |
| 12 | 32 bits | Available-list successor when selecting from that list; subsequently cleared |

Bytes 1–3 and 16–27 are not explicitly written by this function.

No semantic meaning beyond those accesses is established for the record fields.

### Preconditions

For ordinary successful execution:

- The argument must address a readable and writable 16-byte state structure.
- A nonzero available-record address must permit a 32-bit read at offset 12 and all subsequent clearing writes.
- When the available list is empty and the cursor differs from the end marker, the cursor must identify a record that permits those clearing writes.
- A nonzero region-descriptor address used for capacity calculation must permit a 32-bit read at offset 4.
- Allocation results used on the growth path must support the descriptor accesses and selected-record writes described below.
- Address arithmetic must produce usable addresses in the execution environment.

The function does not validate these conditions. It also does not enforce alignment, non-overlap, list integrity, or synchronization.

## Behavior

### 1. Selection from the available-record list

The first state field read is the available-record address at offset 4.

If that address is nonzero:

1. That address becomes the selected record.
2. A 32-bit successor address is read from offset 12 of the selected record.
3. The successor is written to the state's available-record field.
4. The selected record is partially cleared as specified below.

This path does not explicitly read or update the region-descriptor address, unused-record cursor, or end marker. It makes no dependency call.

The successor is captured before the record's offset-12 field is cleared. Thus, under a valid non-overlapping layout, clearing the selected record does not erase the successor just installed in the state.

### 2. Selection from the current contiguous region

If the available-record address is zero, the function reads the unused-record cursor at state offset 8 and compares it with the end marker at offset 12.

When the two addresses differ:

1. The existing cursor address becomes the selected record.
2. The cursor field is advanced by 28 bytes.
3. The selected record is partially cleared.

The comparison is equality only. There is no range check and no verification that a complete 28-byte record remains. A cursor beyond the end marker, or less than one record before it, still takes this path if the two addresses differ.

The end marker and region-descriptor field receive no explicit writes on this path.

### 3. Growth when the cursor equals the end marker

If the available list is empty and the cursor equals the end marker, the function calculates a new region capacity.

If the current region-descriptor address is zero, the capacity is 32 records.

Otherwise, the function reads the existing descriptor's 32-bit capacity, denoted here by \(C\), and computes two unsigned 32-bit candidates:

\[
A = C + 32
\]

\[
B = C + \lfloor C/2 \rfloor + \lfloor C/8 \rfloor
\]

Both expressions use 32-bit unsigned arithmetic, including wraparound. The divisions shown here correspond to unsigned right shifts. The larger candidate under an unsigned comparison becomes the new capacity \(N\). Equality selects the same numeric value regardless of branch choice.

For capacities where neither candidate overflows, this is growth by at least 32 records, with a larger approximately 1.625-times candidate for sufficiently large capacities. That interpretation must not replace the wrapped calculation at high values.

The function then performs these dependency calls in order:

1. F-871e64ddc6de with arguments 12 and 0, obtaining the region-descriptor address.
2. F-871e64ddc6de with arguments \(28N\) and 0, obtaining the backing-storage address.

The second call occurs before this function initializes any field of the new descriptor. The backing-storage size multiplication is also 32-bit and can wrap.

After both calls return, explicit writes occur in this order:

1. Store the backing-storage address at offset 8 of the new descriptor.
2. Read the state's region-descriptor address and store it at offset 0 of the new descriptor.
3. Store \(N\) at offset 4 of the new descriptor.
4. Store the new descriptor address into the state's region-descriptor field.
5. Read the backing-storage address from offset 8 of the new descriptor.
6. Store backing-storage address plus \(28N\) into the state's end-marker field.
7. Store backing-storage address plus 28 into the state's unused-record cursor.
8. Partially clear the first record at the backing-storage address.

The first record of the new region is therefore consumed immediately. Under ordinary successful, non-overlapping allocation, the next cursor points to the second record, and the end marker points immediately after the region.

The descriptor's predecessor is read from the state **after both dependency calls**. It is not necessarily the descriptor used earlier to calculate capacity. If a dependency changes the state, that later value determines the new predecessor link.

### 4. Partial clearing of the selected record

All successful selection paths converge on the following explicit write order:

1. Write a 32-bit zero at record offset 4.
2. Write a 32-bit zero at record offset 8.
3. Write a 32-bit zero at record offset 12.
4. Write a single zero byte at record offset 0.

This clears 13 bytes in total, not the entire 28-byte record.

Bytes 1–3 and 16–27 are outside these writes. On a path without dependency calls, and with valid non-overlapping state and record memory, they retain their previous values. On the growth path, their values depend on the allocation dependency and any other effects it has; zero initialization is not established.

## Side effects

### Explicit state changes

| Path | Explicit state changes |
|---|---|
| Available-record selection | Replace available-list head with the selected record's successor |
| Existing-region selection | Advance unused-record cursor by 28 bytes |
| New-region selection | Publish new descriptor, replace end marker, and set cursor to backing-storage address plus 28 |

Each path also performs the four clearing writes on the selected record.

The function itself does not explicitly clear or otherwise update the available-list head during growth. In particular, it does not restore that field to zero after the dependency calls.

### Memory acquisition and lifetime

Growth invokes F-871e64ddc6de twice and records both returned addresses in the state and descriptor graph.

The function contains no explicit release operation. Existing descriptors are linked rather than discarded by an explicit deallocation. This establishes reachability updates, not a complete ownership policy.

It is unknown whether F-871e64ddc6de allocates fresh memory, initializes memory, transfers ownership, modifies shared state, or has additional side effects.

### Failure and concurrency

There are no explicit null checks on either dependency result and no rollback sequence. If a returned address cannot support the subsequent accesses, the function proceeds toward invalid memory access rather than producing a defined error result. The precise platform-level failure is not established.

The updates are not transactional. For example, on the existing-region path, the cursor advances before record clearing. On the growth path, the descriptor is published before the end marker, cursor, and record clearing are complete.

No locking or atomic protocol is visible. Concurrent use, reentrant observation, and overlapping state, descriptors, or records are outside the ordinary successful-use assumptions. With overlap, earlier writes may affect later reads; the access order above remains material.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, they assume writable, non-overlapping objects, usable address arithmetic, and dependency calls that return suitable storage without changing the state.

### Available-record selection takes precedence

Given a nonzero available-list head whose successor field contains address \(Q\):

- That head record is selected even if the unused-record cursor equals the end marker.
- The available-list head becomes \(Q\).
- No dependency call occurs.
- The cursor and end marker receive no explicit writes.
- The selected record receives the four clearing writes in the specified order.

A zero successor makes the available-list head zero.

### Existing-region selection consumes one record

Given an empty available list and cursor \(P\) different from end marker \(E\):

- The record at \(P\) is selected.
- The cursor becomes \(P+28\).
- The end marker remains \(E\).
- No dependency call occurs.
- Only the specified fields of the selected record are cleared.

This remains the selected branch even if \(P\) is numerically beyond \(E\); the function does not reject that malformed state.

### Initial growth requests 32 records

Given an empty available list, equal cursor and end marker, and a zero region-descriptor address:

- The new capacity is 32.
- Dependency request sizes are 12 bytes and 896 bytes, in that order.
- The new descriptor records capacity 32 and the returned backing-storage address.
- With backing-storage address \(D\), the end marker becomes \(D+896\), and the cursor becomes \(D+28\).
- The record at \(D\) is partially cleared.

### Additive growth wins for capacity 32

Given an existing capacity of 32:

- The candidates are 64 and 52.
- The new capacity is 64.
- The backing-storage request is 1,792 bytes.

### Proportional growth wins for capacity 64

Given an existing capacity of 64:

### Integer truncation is significant

Given an existing capacity of 33:

### Record clearing is partial

Given a selected record whose bytes are all nonzero before clearing, and no overlapping state writes:

- Byte 0 and bytes 4–15 become zero.
- Bytes 1–3 and 16–27 remain unchanged.
- Clearing offset 12 occurs after its successor value has been consumed on the available-list path.

### Dependency mutation affects the predecessor link

If a dependency changes the state's region-descriptor address during growth and then returns normally:

- Capacity was calculated using the earlier state.
- The predecessor stored in the new descriptor is the state value read after both calls.
- The function does not restore the earlier descriptor value.

This example describes access timing, not a guarantee that such mutation is supported safely.
