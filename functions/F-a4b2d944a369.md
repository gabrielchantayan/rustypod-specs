# F-a4b2d944a369

## Purpose

F-a4b2d944a369 conditionally writes a caller-supplied integer value into a fixed field of caller-supplied storage. Two integer selectors identify the supported operation. Unsupported selectors or an out-of-range requested value instead select an error value for conditional recording.

The established behavior is:

- The supported selector pair is **1032 (`0x408`)** and **5633 (`0x1601`)**.
- With those selectors, requested values from **0 through 8,388,608 (`0x800000`), inclusive**, are written to storage element **542 (`0x21e`)**.
- Unsupported selectors select the fixed error value **1280 (`0x500`)**.
- Supported selectors with an invalid requested value select an error value read from an external integer object.
- A selected error is written to storage element zero only if the selected error is nonzero and the existing element-zero value is zero.

These are access-path descriptions, not guarantees that the external object and storage occupy disjoint memory. Aliasing can make an external-object read also a read of a storage element, or a storage write also a modification of the external object.

The application-level meanings of the selectors, destination field, and error values are unknown.

## Interface

### Arguments and result

The function receives four arguments, in order:

| Argument | Representation | Role |
|---|---|---|
| Storage | Pointer to integer storage | Base address for the conditional error slot and destination field |
| First selector | Integer | Identifies the supported operation when equal to 1032 |
| Second selector | Integer | Completes operation selection when equal to 5633 |
| Requested value | Integer evaluated using signed comparisons | Candidate value for storage element 542 |

There is no explicit return value. Observable results consist of memory accesses and any resulting storage changes. Return without an error-slot write does not establish success: the selected error may be zero, or an existing nonzero error may have prevented replacement.

### Integer widths and layout

The supplied representation uses integer objects and signed comparisons, but does not independently establish the target ABI or integer width.

Under a **32-bit signed integer, four-byte element model**:

- The three integer arguments each have a signed 32-bit value.
- Storage element zero occupies relative bytes **0–3**.
- Storage element 542 occupies relative bytes **2168–2171**, starting at **`0x878`**.
- A destination write therefore requires storage valid through relative byte 2171 under an ordinary contiguous-storage interpretation.
- The external object supplies one integer of the same represented type.

The element indices are established independently of that byte-size assumption. Pointer width, byte order, alignment, and the physical transaction sizes used to implement integer accesses remain undocumented.

There is no length argument and no visible storage-bounds validation.

### Access-dependent preconditions

Required memory accessibility depends on the selected path:

- An accepted request requires a readable external integer and a writable integer at storage element 542.
- Matching selectors with an invalid value require a readable external integer. If its sampled value is nonzero, storage element zero must be readable and must also be writable when its observed value is zero.
- Unsupported selectors require readable storage element zero, and writable element zero when its observed value is zero. They do not initiate a direct external-object access.
- Matching selectors, an invalid value, and a sampled external value of zero produce no access through the storage argument. The external-object read still occurs and may access memory within that storage if the objects alias.

No explicit null-pointer check is present. The absence of an access through the storage argument on one path does not establish a general interface guarantee accepting null or otherwise invalid pointers.

Aliasing does not remove the accessibility requirements of an access that occurs. For example, an accepted request whose destination overlaps the external object requires that destination to be writable even though its earlier external access was a read.

### Ownership and synchronization

The function does not visibly allocate, release, retain, or transfer ownership of memory. Storage lifetime remains a caller responsibility; the external object’s lifetime and ownership are undocumented.

No locking or atomic read-modify-write operation is visible. Callers must supply any synchronization required for shared memory.

## Behavior

### Operation selection

The first selector is tested by subtracting 1032 and comparing the result with zero. Only when that test matches is the second selector adjusted by subtracting 5632; its result must equal one.

Where these signed arithmetic operations are defined, the supported pair is therefore exactly:

- First selector: **1032**.
- Second selector: **5633**.

If the first selector fails its test, the second selector does not influence the outcome. Unsupported selection chooses error value 1280 without directly reading the external integer.

The subtraction operations introduce an arithmetic qualification. Under a strict signed 32-bit model, sufficiently negative selectors can overflow during subtraction. The supplied material does not establish whether the actual execution model wraps, traps, or excludes such inputs. Those cases are **documented_only**, not guaranteed ordinary rejections. The supported pair itself does not encounter this issue.

### Accepted requested values

Once both selectors match, the function reads the external integer **before** deciding whether the requested value is acceptable. This read occurs even when the request succeeds and the sampled external value is not needed for error recording.

The accepted interval is:

**0 ≤ requested value ≤ 8,388,608.**

An accepted request writes the requested value to storage element 542 and returns. It initiates no access to element zero through the storage argument and performs no preliminary read of the destination through that argument.

The supplied representation includes additional normalization checks inside the accepted branch. Under the same signed comparison model, those checks cannot change a value that has already passed the enclosing range test. The established result is an exact-value write, not saturation:

- Zero is stored as zero.
- 8,388,608 is stored unchanged.
- Negative values are rejected rather than converted to zero.
- Values greater than 8,388,608 are rejected rather than reduced to the maximum.

The destination write is not conditional on whether the destination already contains the requested value. No destination equality check is visible.

### Matching selectors with an invalid value

For a requested value outside the accepted interval, the previously sampled external integer becomes the selected error value.

There is no direct access to storage element 542 through the storage argument on this path. Nevertheless, the earlier external-object read accesses that element’s physical memory if the two alias.

No filtering of the selected external value is visible. A negative nonzero value is eligible for recording, just as a positive nonzero value is.

### Conditional error recording

Error recording depends on the selected error and the current error-slot value:

| Selected error | Observed storage element zero | Result through the storage argument |
|---|---|---|
| Zero | Not read | No access |
| Nonzero | Zero | Read element zero, then write the selected error there |
| Nonzero | Nonzero | Read element zero and leave it unchanged |

Unsupported selectors always take one of the nonzero-error cases because their selected error is 1280.

The function does not replace an existing nonzero error, accumulate errors, or explicitly clear an error on success. “First-nonzero-error retention” is a plausible interpretation of this rule, not an established application-level protocol or a concurrency guarantee.

## Side effects

### Ordered access paths

The following table describes the order of accesses expressed by the supplied representation. “External read” means a direct read of the external object. “Storage read” or “storage write” means an access through the storage argument.

| Path | Ordered accesses |
|---|---|
| Supported selectors, accepted value | External read; write storage element 542 |
| Supported selectors, invalid value, sampled external value zero | External read only |
| Supported selectors, invalid value, sampled external value nonzero | External read; read storage element zero; write element zero only if its observed value is zero |
| Unsupported selectors | Read storage element zero; write 1280 there only if its observed value is zero |

This establishes source-level access ordering, not hardware bus ordering, atomic visibility, or the exact number of physical transactions.

### Direct accesses versus physical-memory effects

The function directly reads, but does not directly assign to, the external object. Its only accesses **through the storage argument** target elements zero and 542.

Neither statement implies that the external object is physically unchanged or that no other storage element is accessed:

- **External object aliases element zero:** Every supported-selector call reads element zero’s memory through the external access. An accepted call therefore can read the error slot even though it does not read that slot through the storage argument.
- **External object aliases element 542:** An invalid-value call reads the destination’s memory through the external access. An accepted call reads that memory first and then overwrites it through the destination access, thereby also modifying the external object.
- **External object aliases another storage element:** Supported-selector calls read that other element’s memory, although no access to that index is initiated through the storage argument.
- **External object aliases element zero on an unsupported-selector call:** The element-zero read accesses the external object’s memory, and a conditional write of 1280 can modify it, despite the absence of a direct external-object access on this path.

Thus, “success does not inspect the error slot” is valid only as an access-path statement or under a non-aliasing assumption. Likewise, “rejection does not access the destination” and “the external object is not written” are not unconditional physical-memory guarantees.

The external value used for error selection is sampled before error-slot handling. A later write to overlapping memory does not cause the function to resample the external object.

### Preserved state and concurrency

There are no direct writes other than the accepted destination write and the conditional element-zero write. Physical preservation of an overlapping object depends on where those writes land.

An accepted call does not explicitly clear element zero. For ordinary distinct integer elements, its destination write does not overlap element zero; however, its external read may still access element zero.

The error-slot check and write are separate operations. Concurrent modifications can invalidate any interpretation that this is an atomic “record the first error” operation. No behavior for data races or special memory mappings is established.
