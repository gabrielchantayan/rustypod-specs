# F-51631ba6810e

## Purpose

F-51631ba6810e is a mode-selected comparison dispatcher for two record-like inputs. It either compares selected record fields directly or delegates comparison to opaque dependencies.

The established behavior includes four routes:

- Mode `1`: choose between extracted-representation comparison and comparison of fields at byte offset `0x20`.
- Mode `0x1000`: compare a flag at byte offset `0x1d`, then, when both flags are clear, compare unsigned 32-bit fields at byte offset `0x24`.
- Mode `0x8000`: compare unsigned 32-bit fields at byte offset `0x10`.
- Every other mode: query a dependency twice and either return a fixed result or compare the two nonzero results through another dependency.

The inferred intent is to supply a comparison callback supporting multiple sort criteria. That intent does not establish a universal ordering convention, a total order, or the meanings of the selected fields. In particular, dependency-generated comparison results are returned unchanged.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

|---|---|---|
| 1 | Comparison context | A 32-bit value forwarded unchanged to either comparison dependency. Its interpretation is unknown. |
| 2 | Left record | An address-bearing 32-bit value used for record-relative reads and, on one route, passed to an extraction dependency. |
| 3 | Right record | An address-bearing 32-bit value used for record-relative reads and passed to dependencies on some routes. |
| 4 | Reserved input | A 32-bit value with no explicit use in the supplied body. |

| 6 | Auxiliary input | A 32-bit value copied into local storage immediately before either call to F-9cd4380c8dec. No explicit argument forwards it to that dependency. |

The mode values are selectors, not independently combined flags. For example, mode `0x1001` follows the fallback route rather than combining the behavior of modes `1` and `0x1000`.

- `0x00000000`;
- `0x00000001`; or

The last value corresponds to `−1` under a signed 32-bit interpretation. Delegated routes return the selected dependency’s complete 32-bit result without normalization or range checking.

## Behavior

### Mode `0x1000`: flag-first, then unsigned field comparison

The function first reads the left flag byte and tests bit zero.

If the left flag is set:

1. It reads the right flag byte.
2. It returns `1` if the right flag is clear.
3. It returns `0` if the right flag is set.

Neither record’s field at `0x24` is read on this path.

If the left flag is clear:

1. It reads the right flag byte.
2. If the right flag is set, it returns `0xffffffff`.
3. If the right flag is clear, it compares the unsigned 32-bit fields at `0x24`.

For stable field contents, the unflagged comparison returns:

- `1` when the left field exceeds the right field;
- `0` when the fields are equal;
- `0xffffffff` when the left field is smaller.

The two-stage field comparison matters for observable access behavior. First, the function evaluates whether the right field is less than or equal to the left field. Only when that condition holds does it evaluate a second comparison asking whether the right field is strictly smaller.

The supplied body expresses fresh field accesses for that second comparison. It does not establish a cached snapshot spanning both comparisons. Exact operand-load order within either comparison, and whether an implementation retains or merges loads, are not established.

No dependencies are called on this mode’s explicit paths.

### Mode `0x8000`: unsigned field comparison

The function compares the unsigned 32-bit fields at `0x10`.

For stable field contents, it returns:

- `1` when the left field exceeds the right field;
- `0` when the fields are equal;
- `0xffffffff` when the left field is smaller.

The first comparison asks whether the right field is less than or equal to the left field. If true, a second comparison tests inequality between the fields. The supplied body again expresses field accesses in both comparisons; a single immutable snapshot is not established.

This route does not explicitly inspect the flag bytes or fields at `0x20` or `0x24`, and it calls no dependencies.

### Mode `1`: choose an extracted or scalar comparison

The function first reads the left flag byte and tests bit zero.

- If the left flag is set, it selects extracted-representation comparison without explicitly reading the right flag byte.
- If the left flag is clear, it reads the right flag byte. A set right flag selects extracted-representation comparison.
- If both tested flags are clear, it selects scalar comparison.

Thus, the extraction route is selected when either flag is set, but the right flag read is short-circuited when the left flag already determines the route.

#### Both flags clear

The function explicitly reads the right record’s 32-bit field at `0x20`, then the left record’s 32-bit field at the same offset.

It then copies the auxiliary input into a local 32-bit slot and calls F-9cd4380c8dec with:

1. the comparison context;
2. the left field value;
3. the right field value.

The dependency’s result is returned unchanged.

The field values are represented as signed 32-bit integers at this call boundary. The dispatcher itself does not compare them or establish whether the dependency treats them as numbers, addresses, handles, or another representation.

#### At least one flag set

The function invokes F-1bcb8114d17f twice, in this order:

1. With the left record, an address of a first local output area, and the right record as an additional supplied argument.
2. With the right record and an address of a distinct second local output area.

The extra argument supplied on the first invocation must not be silently omitted from this contract. Whether it is meaningful to the dependency is unknown.

After both calls return, F-aa53e7865743 is invoked with five supplied arguments:

1. the comparison context;
2. a pointer two bytes beyond the beginning of the first local output area;
3. the 16-bit value at the beginning of that first area;
4. a pointer two bytes beyond the beginning of the second local output area;
5. the low 16 bits of the 32-bit value read at the beginning of that second area.

The first local area is represented as a two-byte header followed by 510 bytes of storage. The second area’s full writable extent is not independently established by the supplied declarations.

A plausible interpretation is that each extraction produces a length-prefixed byte sequence. That is inferred intent, not an established format contract. The dispatcher does not validate either length against available storage.

F-aa53e7865743’s result is returned unchanged. The auxiliary input is not explicitly copied into local storage on this extraction route.

### Every other mode: dependency-result comparison

The function calls F-875f8fbbb5eb twice, sequentially:

1. First with no explicit arguments shown.
2. Then with the right record as the sole explicit argument shown.

The first result is retained before the second call. The supplied body does not establish that the first call receives the left record implicitly or explicitly.

Both calls occur before either result is used to decide the return path.

The two results are treated as 32-bit integers:

- First result zero, second result zero: return `0`.
- First result zero, second result nonzero: return `1`.
- First result nonzero, second result zero: return `0xffffffff`.
- Both results nonzero: copy the auxiliary input into local storage, then call F-9cd4380c8dec with the context, first result, and second result; return its result unchanged.

“Nonzero” includes negative signed values and values with the high bit set. There is no positivity test.

## Side effects

It uses local storage for extraction outputs and for a copy of the auxiliary input before scalar-comparison calls. The auxiliary copy has no explicit subsequent read in the supplied body. Its presence does not establish an undocumented dependency argument or a global-state update.

The function contains no explicit allocation, deallocation, ownership transfer, or global-variable access.

### Dependency effects and sequencing

- The first extraction finishes before the second extraction begins.
- Both extractions finish before F-aa53e7865743 is called.
- The first fallback query finishes before the second fallback query begins.
- Both fallback queries finish before F-9cd4380c8dec is called, if that comparison is selected.

The function does not explicitly inspect extraction status or query error indicators. Extraction return values are not used. A dependency failure encoded only in an ignored return value is therefore not explicitly handled by this function.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests.

1. **Flag precedence in mode `0x1000`.**  
   With the left flag set and the right flag clear, return exactly `1`, regardless of either `0x24` field. With both flags set, return exactly `0`.

2. **Unsigned boundary at `0x24`.**  
   In mode `0x1000`, with both flags clear and stable fields, left `0xffffffff` and right `0` produce `1`. Reversing those fields produces `0xffffffff`. A signed comparison producing the opposite results would violate the contract.

3. **Unsigned boundary at `0x10`.**  
   In mode `0x8000`, stable left `0x80000000` and right `0x7fffffff` produce `1`. Equal fields produce `0`, independent of flag-byte contents.

4. **Scalar forwarding in mode `1`.**  
   With both flags clear, if the left `0x20` field is `−3`, the right field is `7`, and F-9cd4380c8dec returns `0x12345678` for the supplied context and values, the dispatcher returns `0x12345678`. It does not reduce that result to a sign.

5. **Short-circuit flag access.**  
   In mode `1`, a set left flag selects extraction without an explicit dispatcher read of the right flag. This does not imply that the extraction dependency avoids reading that flag.

6. **Extraction call order and result forwarding.**  
   When mode `1` selects extraction, the left extraction precedes the right extraction, followed by F-aa53e7865743. If valid populated outputs cause that dependency to return `0xffffffff`, the dispatcher returns exactly that value.

7. **Fallback zero classification.**  
   For an unrecognized mode, query results `0` and `−8` produce `1`. Results `−8` and `0` produce `0xffffffff`. Both queries still occur in either case.

8. **Fallback delegation.**  
   For an unrecognized mode, nonzero query results `4` and `9` are forwarded, in that order, with the context to F-9cd4380c8dec. Its result is returned unchanged.

9. **Exact selector matching.**  
   Mode `0x1001` invokes the fallback-query route. It does not perform the flag-and-`0x24` comparison.

## Uncertainties

The following are documented_only:

- The first fallback query’s missing explicit record argument. It cannot safely be specified as a left-record query.
- The differing visible argument counts for the two extraction calls.
- The extraction output format, including whether the two-byte prefixes are lengths and what units they count.
- The second extraction buffer’s complete capacity and the dependencies’ bounds discipline.
- Whether extraction initializes every byte subsequently read, including the full 32-bit read used to obtain the second low-16-bit value.
- Dependency behavior on failure, including whether results distinguish errors from ordinary comparison values.
- Exact machine-load counts and operand ordering inside compound field comparisons.
- Behavior with concurrently changing record contents. Stable-value comparison tables do not establish atomic snapshots or synchronization.
- The purpose and external significance, if any, of copying the auxiliary input into local storage.
- The full ABI, pointer interpretation, and alignment requirements beyond the supplied 32-bit representations.

These unknowns prevent asserting a complete abstract sorting contract or unconditional safety for arbitrary records.
