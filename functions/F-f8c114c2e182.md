# F-f8c114c2e182

## Purpose

F-f8c114c2e182 selects an unsigned 32-bit result from an input value, caller-supplied object state, and, on one path, three dependency results.

Its established behavior has two main paths:

- Below an initial boundary, it compares the input against two observations of a lower boundary. With stable fields, inputs below the lower boundary return zero; inputs at or above it are incremented and accepted only if the increment remains strictly below the initial boundary.
- At or above the initial boundary but below an outer limit, it first asks a dependency about the following value. If that dependency returns zero, it obtains and transforms an opaque value, then conditionally constructs and checks a candidate.

Returning the original input on the lower-range path requires different lower-boundary observations: the first must be below the input and the second above it. It is not the stable-state behavior for inputs above the lower boundary.

Zero is the common rejection or no-result value. The evidence does not establish a separate error taxonomy, and an accepted arithmetic candidate can itself be zero.

Selection of a position or identifier is **inferred intent**, not an established semantic contract. No particular container, indexing scheme, or meaning for dependency results is established.

## Behavior

### Initial decision

The first direct object read is the 32-bit field at `0x74`.

- If the input is strictly below that observed value, the function takes the lower-range path.
- Otherwise, it considers outer-range eligibility.

Later reads of the same field are fresh observations. The initial value is not reused as a call-wide snapshot.

### Lower-range path: observation-dependent behavior

This path invokes no dependencies.

The function reads the lower-boundary field at `0x70` twice:

1. The first observation determines whether the input is less than or equal to the observed lower boundary.
2. The second observation determines whether the observed lower boundary is less than or equal to the input.

If the second observation is **greater than the input**, there is no increment and no further read of `0x74`:

- If the first observation was below the input, the function returns the original input.
- If the first observation was equal to or above the input, it returns zero.

If the second observation is **less than or equal to the input**, the earlier comparison no longer determines the result. The function increments the input by one and rereads `0x74`:

- The incremented value is returned if it is strictly below the newly observed boundary.
- Otherwise, the function returns zero.

The increment cannot wrap. This path was entered only because the original input was strictly below an unsigned 32-bit boundary, so the original input cannot be `0xFFFFFFFF`.

### Lower-range path: stable-state interpretation

If both lower-boundary observations and any repeated initial-boundary read see unchanged values, the behavior is:

| Relationship after entering the lower-range path | Result |
|---|---|
| Input below lower boundary | Zero |
| Input equal to lower boundary | Input plus one, if strictly below initial boundary; otherwise zero |
| Input above lower boundary | Input plus one, if strictly below initial boundary; otherwise zero |

Every row presupposes that the input is below the initial boundary. Equality with the initial boundary selects the other path.

Thus, with stable fields, **every lower-range input at or above the lower boundary is incremented before acceptance is decided**. None of those inputs returns unchanged.

The observation-dependent rules remain authoritative if values differ between reads. Their presence does not establish support for unsynchronized concurrent mutation or any particular memory model.

### Outer-range eligibility

When the input is not below the initially observed boundary, the function reads the unsigned 32-bit outer limit at `0x1D8`.

- If the input is greater than or equal to that limit, it returns zero without dependency calls.
- If the input is strictly below that limit, dependency processing begins.

With stable fields, dependency processing therefore requires:

\[
\text{initial boundary} \leq \text{input} < \text{outer limit}.
\]

If the initial boundary is at or above the outer limit, no input reaches dependency processing under stable state.

- A zero response permits the remaining dependency calls.

The increment cannot wrap: eligibility required the original input to be strictly below an unsigned 32-bit outer limit.

The immediate return is not checked against either boundary after the dependency call. It may equal the previously observed outer limit. Changes made by the dependency do not trigger additional validation on this branch.

### Opaque lookup and transformation

After a zero response from F-410844fa65a8, the function calls F-51d0c0e686a6 with the original object base and **original input**, not the incremented value.

That dependency produces an opaque 32-bit value. The function passes it unchanged as the second argument to F-073075d3cf3f, with the original object base as the first argument.

The intermediate value has no established interpretation as a pointer, allocation, handle, or index.

### Candidate construction

For a transformed result greater than one, candidate construction uses:

- A fresh 32-bit observation of the field at `0x74`.
- The global datum’s address contribution, as observed during this calculation.
- The unsigned 16-bit value at the resulting address.
- The low eight bits of that 16-bit value as the shift count.

The arithmetic relationship is:

\[
\text{candidate}
=
\text{fresh candidate base}
+
\bigl((\text{transformed result}-2)\ll\text{shift count}\bigr).
\]

The subtraction precedes the shift, and the shifted term is added to the base.

For shift counts from zero through 31:

- Subtracting two does not underflow because the transformed result exceeds one.
- The shift operates on an unsigned 32-bit value; bits shifted beyond that width are discarded.
- Addition is modulo \(2^{32}\), not checked or saturating arithmetic.

The mask limits the count to zero through 255, **not** zero through 31. For counts from 32 through 255, the supplied source-level expression does not establish a portable result. Those cases remain **documented_only**; no masked machine-count behavior, zero result, or other target-specific outcome is promised.

The global contribution and candidate base are both obtained after the dependencies. No ordering between those two observations is guaranteed by the expression.

### Final candidate check

After candidate calculation, the function freshly reads the outer limit at `0x1D8`.

- A candidate strictly below this fresh limit is returned.
- Any other candidate yields zero.

There is no lower-bound check and no forward-progress check. A candidate can be below the original input or below the candidate base because of modular arithmetic.

Zero is not separately rejected. If the candidate is zero and the fresh limit is positive, the function accepts and returns zero, indistinguishably from rejection at this interface.
