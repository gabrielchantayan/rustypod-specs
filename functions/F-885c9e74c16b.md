# F-885c9e74c16b

## Purpose

F-885c9e74c16b conditionally updates a byte in indirectly addressed state and writes a one-byte marker indicating that an update occurred.

The decision is based on a comparison between an existing byte and the complete requested integer value. If they compare equal, the function returns without writing either the destination byte or the marker. If they differ, the function stores a character-width conversion of the request at offset `0xB42` in the indirectly addressed state, then writes `1` at offset `0xB90`.

The supplied representation does not establish that the byte used for comparison is the byte subsequently updated. The comparison uses a separately supplied displacement whose value is not shown. Interpreting this operation as “update a value only when it changes” therefore requires an additional condition: that displacement must select the update destination.

The marker’s role as a dirty flag, notification flag, or pending-work flag is inferred intent, not established behavior.

## Interface

The function takes two integer-valued arguments:

- **Owner address:** identifies storage containing a state-address field at byte offset `0xF00`.
- **Requested value:** the integer compared against an existing character value and, on the update path, converted to character width for storage.

The source representation uses integer-sized values for both addresses and the requested value. A 32-bit integer/address model is consistent with that representation, but the excerpt does not independently establish the target ABI, pointer width, integer width, alignment rules, or character signedness. Those details remain environmental prerequisites rather than portable guarantees.

For a 32-bit interpretation, the state-address field occupies four bytes starting at owner offset `0xF00`. Character and marker accesses occupy one addressable byte each. The excerpt supplies no byte-order conversion for the state-address field; it is interpreted using the target’s native representation.

## Behavior

### Comparison

The function obtains a state address from the owner’s field at offset `0xF00`. It combines that address with the separately supplied displacement and reads one character from the resulting address.

The character value is promoted for comparison with the requested integer. The requested integer is not explicitly narrowed before this comparison.

This distinction is observable. A request that would produce the same stored byte after narrowing may still compare unequal to the existing character and therefore trigger both writes.

The comparison also depends on character signedness. For example, a byte with its high bit set can promote to a negative integer under a signed-character interpretation or a positive integer under an unsigned-character interpretation. The excerpt does not resolve which interpretation applies.

If the promoted character equals the requested integer, the function immediately returns:

- The destination at offset `0xB42` is not written.
- The marker at offset `0xB90` is not written.
- The existing marker is neither cleared nor normalized.

An equality result does not establish anything about the destination byte unless the comparison address is known to select that destination.

### Destination update

On a mismatch, the function reads the owner’s state-address field again. It does not explicitly retain and reuse the state address used by the comparison.

Using this newly read address, it stores the character-width conversion of the requested integer at offset `0xB42`.

The comparison therefore concerns the original integer request, while the write concerns its character-width conversion. These are different operations with potentially different representable ranges.

For requests representable by the destination character type, the stored character has the requested value. For out-of-range requests, the exact conversion depends on the target’s character type and language model. Under an unsigned 8-bit character interpretation, conversion reduces the value modulo 256. A signed-character interpretation does not justify an unconditional modulo-256 value contract from this excerpt alone.

### Marker update

After the destination write, the function reads the owner’s state-address field a third time and writes the one-byte value `1` at offset `0xB90` relative to that newly read address.

There is no test of the marker’s previous value. A mismatch takes this path even if the marker already contains `1`.

The function then returns.

### Ordering and repeated address resolution

The established source-level sequence is:

1. Resolve and read the comparison character.
2. Decide equality or mismatch.
3. On mismatch, resolve the destination address and write the converted request.
4. Resolve the marker address and write `1`.

The initial reads of the separate displacement and the owner’s state-address field have no specified relative evaluation order in the supplied expression.

The destination write precedes the later state-address-field read used for the marker. Consequently, aliasing can matter even without concurrency. If the destination byte overlaps the owner’s state-address field, the destination write can change the address subsequently used for the marker.

These are source-level dependencies and ordering constraints. The excerpt does not establish volatile accesses, atomic operations, synchronization, barriers, or a machine-level guarantee that every source-level read remains a separate hardware load.

## Side effects

### Equal path

There are no explicit memory writes. The function still performs the reads needed for the comparison.

In particular, a pre-existing marker remains unchanged, including when it already indicates an update.

### Mismatch path

There are two explicit one-byte writes, in order:

- The converted requested value at state offset `0xB42`.
- The value `1` at state offset `0xB90`.

No wider field is explicitly assigned, and no other state is explicitly cleared or updated.

## Acceptance examples

These examples are conditional static acceptance criteria, not runtime observations.

### 1. Equality leaves the marker untouched

Assume the comparison character promotes to integer `42`, and the requested value is `42`.

Expected result:

- No destination write occurs.
- No marker write occurs.
- A marker initially holding `0`, `1`, or another byte value retains that value.

### 2. Mismatch updates the destination before the marker

Assume valid ordinary memory, a stable state address, a comparison character of `10`, and a request of `11`.

Expected result:

- The character at state offset `0xB42` becomes `11`.
- The byte at state offset `0xB90` becomes `1`.
- The destination write precedes the marker write.

### 3. Distinct comparison and destination locations

Assume the comparison displacement is not `0xB42`, the comparison character is `7`, the destination character is `9`, and the request is `7`.

Expected result:

- The function returns on equality.
- The destination remains `9`.
- The marker remains unchanged.

This case rules out a contract that unconditionally compares the request with the destination byte.

### 4. Full-width comparison before narrowing

Assume unsigned 8-bit characters, a stable state address, a comparison displacement of `0xB42`, an existing destination byte of `0`, and a representable requested integer of `256`.

Expected result:

- The comparison is unequal: `0` is not `256`.
- The destination receives `0` after character conversion.
- The marker receives `1`.

The destination’s final byte matches its initial byte, but the marker is still written.

### 5. Signedness changes equality

Assume the comparison byte has representation `0xFF` and the request is `255`.

- With unsigned 8-bit characters, the promoted comparison value is `255`, so neither write occurs.
- With signed 8-bit characters where that representation denotes `−1`, the comparison is unequal, so the update path occurs.

The exact destination conversion in the second case requires the target’s signed-character conversion rules.

### 6. Re-resolved marker address

Assume the mismatch path’s destination write changes the owner’s state-address field through valid aliasing.

Expected source-level behavior:

- The destination write uses the state address obtained before that write.
- The marker address is calculated from the state-address field read afterward.
- The marker is not required to be written relative to the earlier state address.
