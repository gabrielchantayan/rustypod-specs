# F-c3056c36012a

## Purpose

F-c3056c36012a performs an ordered series of memory reads and writes through several linked records, then invokes an unresolved indirect target with three arguments.

The established behavior is memory mutation and control transfer. A higher-level purpose—such as initializing an object, updating a graph, or dispatching an operation—is not established. In particular, the supplied representation does not justify treating the operation as a conventional record initializer: it includes repeated writes, address-derived byte values, self-references, arithmetic-derived destinations, and a write-back of an unchanged field.

This contract preserves those effects rather than replacing them with an inferred algorithm.

## Interface

### Inputs

The visible interface has one explicit 32-bit argument, called the **input word** here.

The body also depends on three incoming values whose origins are not established by the visible interface:

- **Primary base:** an address used for the initial argument store and linked-record lookup.
- **Secondary base:** an address used throughout the operation, both as a record base and as a numeric value.
- **Auxiliary word:** a 32-bit value stored into the secondary record and subsequently used as an address through a fresh memory read.

These are effective inputs, even though their calling-convention locations and initialization requirements are unknown.

The function additionally consumes:

- Three 32-bit values from distinct global locations.
- An unresolved indirect call target.
- The contents of all memory reached by its ordered accesses.

### Widths and layout

The supplied representation establishes accesses of these widths:

| Access kind | Width |
|---|---:|
| Byte | 8 bits |
| Halfword | 16 bits |
| Word | 32 bits |
| Address-bearing record field | Represented as a 32-bit load or store |

Offsets below are hexadecimal byte offsets. Thus `+0x64` denotes the field shown at decimal offset 100 in the supplied material.

A “low byte” or “low halfword” is the least significant 8 or 16 bits of a value. These truncations are numerical operations; they do not depend on memory byte order.

Address-bearing values are represented in 32-bit fields, but the complete machine address model, alignment rules, and overflow behavior are not independently established.

### Output and completion

No result value is specified.

After the final listed memory operation, the function invokes an unresolved target with three arguments. If that invocation returns normally, the visible body returns without further explicit memory operations.

There is no established validation result, error code, rollback path, or local exception-handling behavior.

### Preconditions

Normal completion requires every executed read, write, and indirect invocation to be valid in the actual execution environment. This includes destinations formed by addition, multiplication by two, and conversion of a byte into an address-like value.

The function does not visibly check:

- Null or invalid addresses.
- Record extents.
- Alignment.
- Arithmetic overflow.
- Whether a field actually contains an address.
- Whether the indirect target is callable.

Distinct descriptive record names below do not imply distinct storage. Aliasing is permitted by the supplied evidence and can change later reads.

## Behavior

### Ordering and retained values

The following phases describe the established access order. Record names identify values obtained at particular reads; they are not declarations of ownership or independent objects.

A retained value remains the value originally read, even if its source field is subsequently overwritten. Conversely, an explicitly described fresh read must not be replaced by a previously retained value without an additional non-aliasing justification.

### 1. Initial stores and first linked records

The function first stores the input word at primary base `+0x20`.

It then reads a word from secondary base `+0x64`, retains the entire word as the **initial secondary word**, and stores its low byte at primary base `+0x09`.

Next it reads an address from primary base `+0x74`, identifying the **first record**. On that record, it:

- Stores the low byte of the secondary-base address at `+0x0D`.
- Reads the word at `+0x54` and writes that same word back to `+0x54`.
- Stores byte `0x74` at `+0x09`.

The unchanged-value write-back is part of the visible access sequence; it is not equivalent to no access for memory with observable reads or writes.

The auxiliary word is then stored at secondary base `+0x44`. The secondary-base address is stored as a word at first record `+0x34`.

Only after those stores does the function read first record `+0x04`, identifying the **second record**. It stores the retained initial secondary word at second record `+0x24`, then stores the low byte of the auxiliary word at secondary base `+0x19`.

### 2. Branch discovery and secondary-word replacement

The function reads and retains:

1. An address-like word from second record `+0x74`, called the **retained link**.
2. A word from second record `+0x04`, called the **replacement word**.
3. An address from secondary base `+0x74`, identifying the **branch root**.

It reads an address from branch root `+0x14` and stores the retained link at that destination’s `+0x54`.

It then reads branch root `+0x04`, identifying the **branch child**, and performs these writes in order:

- The initial secondary word’s low byte to secondary base `+0x0D`.
- The same byte to the same destination a second time.
- The replacement word to secondary base `+0x64`.
- Word `0x00000074` to branch child `+0x30`.

The branch root’s `+0x04` field is read again. Through that freshly obtained address, the function reads `+0x74`, identifying the **branch node**. The repeated lookup matters if preceding writes alias either field.

The function then freshly reads secondary base `+0x64`, retains its low byte as the **refreshed secondary byte**, and stores that byte at secondary base `+0x1D`.

### 3. Additional links, self-reference, and deep-record bytes

The function freshly reads secondary base `+0x44`, treats that value as an address, and reads an address from its `+0x14`. The result identifies the **selected record**.

It next:

- Stores the retained link at branch node `+0x34`.
- Stores the selected-record address at secondary base `+0x14`.
- Reads and retains the word at secondary base `+0x54` as the **previous secondary word**.
- Stores the secondary-base address’s low byte at selected record `+0x09`.

A further two-step lookup reads branch node `+0x04`, then that destination’s `+0x74`, identifying the **deep record**.

The following writes occur in order:

1. Retained link’s low byte to deep record `+0x15`.
2. Secondary-base address, as a word, to secondary base `+0x54`.
3. Branch-node address’s low byte to secondary base `+0x11`.
4. Previous secondary word’s low byte to deep record `+0x11`.

The function reads and retains a word from deep record `+0x64`, called the **deep word**. It then stores the refreshed secondary byte at secondary base `+0x09`.

### 4. Byte-oriented record updates

A fresh read of branch node `+0x04` identifies the **byte record**. This need not equal the earlier value read from that field.

The function:

- Stores the secondary-base address’s low byte at byte record `+0x09`.
- Reads and retains the word at byte record `+0x50`, called the **byte-record word**.
- Stores the deep word’s low byte at byte record `+0x11`.
- Again stores the secondary-base address’s low byte at byte record `+0x09`.
- Stores the entire deep word at secondary base `+0x14`.
- Stores the byte-record address’s low byte at secondary base `+0x0D`.
- Stores the byte-record word’s low byte at byte record offset `0x00`.

The two writes at byte record `+0x09` are separate visible operations, with other accesses between them.

### 5. Terminal-record updates

The function reads and retains a word from branch node `+0x74`, called the **indexed displacement**. It then reads branch node `+0x14`, identifying the **terminal parent**.

Before following that parent, it stores the byte-record address as a word at byte record `+0x54`.

A read of terminal parent `+0x04` identifies the **terminal record**. The subsequent writes are ordered as follows:

1. Byte `0x64` to terminal record `+0x10`.
2. Word `0x00000064` to secondary base `+0x54`.
3. Word `0x00000064` to terminal record `+0x40`.
4. Deep word’s low byte to secondary base `+0x0D`.
5. Terminal-record address’s low byte to terminal parent `+0x09`.
6. Entire deep word to secondary base `+0x24`.
7. Secondary-base address’s low byte to terminal parent `+0x11`.

Consequently, the earlier self-reference at secondary base `+0x54` is later replaced by `0x00000064` when these destinations do not participate in additional aliasing.

### 6. Arithmetic-derived addresses and global values

The function reads the first global word, called the **first global value**.

It then freshly reads secondary base `+0x74`, obtaining the **final root value**. This is a new read, not guaranteed to reproduce the earlier branch-root address. The low halfword of this value is retained.

The following operations occur in order:

- Store the final root value’s low halfword at the address formed by adding the final root value and secondary-base address.
- Store the first global value’s low halfword at twice the terminal-record address.
- Read one byte at the address formed by adding the indexed displacement and secondary-base address. Convert it through the represented plain-character interpretation into a 32-bit unsigned value, called the **dispatch value**.
- Store the final root value’s retained low halfword at the address formed by adding the first global value and final root value.
- Repeat the halfword store at final root value plus secondary-base address.
- Store word `0x00000045` at dispatch value `+0x45`.

The dispatch byte is read between the two stores to final root value plus secondary-base address. If those accesses overlap, that ordering can affect the dispatch value.

Next, in order, the function reads the **second global value**, reads the **third global value**, and freshly reads secondary base `+0x44` as the **final auxiliary-field value**.

It then:

- Stores byte `0x44` at dispatch value `+0x44`.
- Stores the third global value as a word at twice the second global value.
- Stores the second global value’s low halfword at retained link plus second global value.

The addition and multiplication destinations are byte addresses, not array indexing with an additional element-size multiplier.

### 7. Indirect invocation

The unresolved target receives:

1. The dispatch value bitwise-ORed with `0x44`.
2. The second global value.
3. The final auxiliary-field value.

The first argument uses bitwise OR, not addition. The third argument comes from the late read of secondary base `+0x44`, not directly from the original auxiliary input.

## Side effects

The function mutates the primary and secondary records, multiple transitively reached records, and arithmetic-derived destinations. It also reads three global locations.

No allocation, deallocation, reference-count operation, or ownership transfer is established by the visible body. Storing an address or passing a word to the unresolved target does not establish ownership.

All explicit stores precede the indirect invocation. Effects already performed are not visibly undone if a later access or invocation fails.

Unknown target behavior may include further memory mutation, resource management, non-return, or failure. None of those possibilities may be excluded on the basis of this body.

For aliased storage, the final state must be derived from the ordered accesses, not from a table of nominal final field values. A byte store can alter a later word or address read when their storage overlaps.

## Acceptance examples

These examples are conditional static expectations, not executed tests.

### Input propagation

Given valid non-aliasing primary storage, an input word of `0x12345678` is stored intact at primary base `+0x20`. A byte store elsewhere must not be substituted for this word store.

### Initial and refreshed byte distinction

If the initial secondary word is `0xAABBCC12`, the replacement word is `0x55667789`, and intervening accesses do not alias the relevant fields:

- Primary base `+0x09` receives `0x12`.
- The two early stores at secondary base `+0x0D` each write `0x12`.
- Secondary base `+0x64` receives `0x55667789`.
- Secondary base `+0x1D` and the later write at `+0x09` receive `0x89`.

Later writes to `+0x0D` remain required.

### Self-reference followed by replacement

With non-overlapping relevant storage, secondary base `+0x54` first receives the secondary-base address and later receives word `0x00000064`. Retaining only the final value is insufficient where write order is observable.

### Truncation and address scaling

If the second global value is `0x12345678`, the halfword stored at retained link plus that value is `0x5678`.

The separate word destination is twice `0x12345678`, subject to the execution environment’s address-arithmetic rules. There is no further scaling by four.

### Dispatch OR versus addition

If the dispatch value is `0x04`, the first indirect argument is `0x44`, not `0x48`. The word and byte stores preceding invocation use offsets `+0x45` and `+0x44`, respectively.

### Plain-character interpretation

For a dispatch source byte of `0x7F`, both signed and unsigned 8-bit interpretations produce dispatch value `0x0000007F`.

For `0x80`, an unsigned interpretation produces `0x00000080`; a signed interpretation followed by conversion to 32-bit unsigned produces `0xFFFFFF80`. Which case governs is documented_only pending character-signedness evidence.

### Aliasing-sensitive repeated lookup

If an intervening write changes branch root `+0x04`, the later lookup must use the changed field. Reusing the earlier branch-child address would not preserve the established behavior.

## Uncertainties

The following remain documented_only:

- The actual calling convention and origins of the three effective incoming values.
- Record types, valid extents, and higher-level field meanings.
- Plain-character signedness for dispatch-byte conversion.
- Machine byte order and its consequences for overlapping accesses.
- Address-space rules, overflow semantics, and alignment requirements.
- Whether destinations are ordinary memory, device memory, or otherwise externally observable.
- The values, mutability, and intended meaning of the three global locations.
- The indirect target’s identity and effects.
- Whether the unusual arithmetic-derived addresses and repeated operations accurately represent the intended executable behavior.

A 32-bit modular address model is plausible from the represented widths, but it is not independently established here. Signed arithmetic overflow must not be silently treated as defined portable behavior.

## Evidence

Established static evidence consists solely of the supplied function representation: explicit access widths, offsets, value truncations, access order, arithmetic-derived destinations, three global reads, and the final indirect invocation.

Descriptive record names in this contract express relationships among observed reads; they do not establish object types or non-aliasing.

Higher-level intent, ownership, and dependency behavior are not established. No runtime tests, execution traces, or independent implementation inspection have been performed.
