# F-13c400e6f056

## Purpose

F-13c400e6f056 repeatedly obtains an object through a replaceable pointer slot, invokes that object’s status operation, and processes objects whose status is not the 32-bit value −1. Processing consists of an optional associated-object callback followed by the obtained object’s completion operation.

When a status operation returns −1, the function stops processing and invokes F-a9c62fb9dbee with an address 304 bytes beyond the first argument.

This is an operational description, not a semantic identification of the objects or their methods. “Status,” “associated object,” and “completion” distinguish observable roles; they do not establish ownership, destruction, queue behavior, or resource release.

| First | 32-bit integer or address-sized value | Passed unchanged to F-413819d05b57 on each iteration; used to derive the final argument to F-a9c62fb9dbee. |
| Second | Uninterpreted 32-bit value | No direct use in the supplied body. |
| Third | Uninterpreted 32-bit value | No direct use in the supplied body. |

The fourth argument is an object pointer, not the address of a caller-provided pointer slot. The function creates its own slot and passes the address of that local slot to F-413819d05b57. Replacement of the slot therefore does not, by itself, replace a pointer variable belonging to the caller.

## Behavior

### Initial state and acquisition

The function first copies the fourth argument into its local object-pointer slot. It does not inspect or process that initial object before the first acquisition call.

Every iteration begins by calling F-413819d05b57 with:

1. The first argument, unchanged.
2. The address of the local object-pointer slot.

That dependency can observe the slot’s current value and can potentially replace it. The supplied body does not establish that replacement always occurs. If the dependency leaves the slot unchanged, subsequent behavior uses the value already present.

After the acquisition call returns, the function reads the slot and saves the resulting object pointer for that iteration. The null check and the subsequent status invocation use this acquired value.

The local slot persists across iterations. There is no explicit reset to the original fourth argument between acquisition calls.

### Null result

If the acquired object pointer is null, the function calls F-a817d8d58c10.

The supplied static representation marks this call as non-returning. Under that annotation, the function does not subsequently invoke a status operation, invoke a completion operation, perform finalization, or return normally on this branch.

The null check occurs after F-413819d05b57. Consequently:

- A null fourth argument does not itself force the null branch; acquisition may supply a non-null object.
- A non-null fourth argument does not prevent the null branch; acquisition may replace it with null.

The evidence does not establish whether F-a817d8d58c10 terminates a process, throws, transfers control elsewhere, or uses another non-returning mechanism.

### Status operation

For a non-null acquired object, the function reads the object’s dispatch-table pointer at byte offset 0, selects the entry at table byte offset 8, and invokes that entry with the acquired object as its sole explicit argument.

The result is compared with the 32-bit value −1, whose all-ones bit pattern is `0xffffffff`. This is an exact equality test, not a test for a negative value.

If the result equals −1, the loop ends immediately. For that terminal object, the function does not:

- Read the associated-object field at byte offset 4.
- Invoke the associated-object callback.
- Invoke the completion operation.

If the result differs from −1, processing continues. Zero, positive values, and negative values other than −1 all select this same continuation path.

The acquired object pointer saved before the status call remains the object used by the later operations in that iteration. The function does not reacquire an object between status and completion.

### Optional associated-object callback

After a nonterminal status result, the function reads the 32-bit associated-object pointer at byte offset 4 of the saved acquired object.

This read occurs after the status operation returns. Thus, if the status operation changes that field, the later read observes the field’s value at that later point, subject to the execution environment’s memory rules. The function does not use a value cached before the status call.

If the associated-object pointer is null, the callback is skipped.

If it is non-null, the function:

- Reads that associated object’s dispatch-table pointer at byte offset 0.
- Reads the entry at byte offset 0 of that table.
- Invokes the entry with the associated object as the first explicit argument and the acquired object as the second.

No callback result is inspected or used in the supplied body.

### Completion and repetition

After the optional callback returns—or immediately after the null associated-object check—the function invokes the acquired object’s completion operation.

It reads the acquired object’s dispatch-table pointer again and selects the entry at byte offset 4. The acquired object is the sole explicit argument. No result is inspected or used.

This dispatch-table read occurs after the optional callback. A callback that changes the acquired object’s table pointer can therefore affect which completion operation is selected. The function does not reuse the table pointer read for the earlier status operation.

On return from completion, execution begins another iteration with F-413819d05b57. There is no explicit iteration limit or other loop exit in the supplied body.

### Terminal finalization

When a status operation returns −1, the function invokes F-a9c62fb9dbee once with the first argument offset by hexadecimal `0x130`, equivalent to 304 bytes.

The offset is an address displacement, not an index into four-byte words. The function does not directly read the storage at that address before passing it to the dependency.

If F-a9c62fb9dbee returns, F-13c400e6f056 returns without an explicit result value.

The recovered expression does not establish portable signed-overflow behavior for forming this address. Inputs for which the offset produces an invalid address or exceeds the supported address range require additional platform evidence.

## Side effects

The function’s direct data writes shown in the supplied body are to its local pointer slot: initialization from the fourth argument and any changes made through the slot address passed to F-413819d05b57.

No direct write to an object field or global variable is shown. This does not imply that the overall operation is free of such writes. Every dependency and indirect operation may have additional side effects not established here.

For each normally completed nonterminal iteration, the observable call ordering is:

1. F-413819d05b57.
2. The acquired object’s status operation.
3. The associated-object callback, if the post-status associated-object field is non-null.
4. The acquired object’s completion operation.

For a terminal iteration, the order is acquisition, status, then F-a9c62fb9dbee. There is no associated callback or completion operation for that iteration.

Ownership is not established. In particular:

- Passing an object to completion does not prove that completion destroys or releases it.
- Passing an acquired object to the associated callback does not prove an ownership transfer.
- Stopping on −1 does not prove that the terminal object is retained, released, or a sentinel.
- The supplied body performs no explicit allocation or deallocation.

An operation that invalidates the acquired object before a required later dereference can make the remaining sequence unsafe. For example, a nonterminal status call must leave sufficient accessible state for the associated-field read, and a returning callback must leave sufficient accessible state for completion dispatch. Whether the actual callees satisfy those lifetime requirements is unknown.

## Acceptance examples

These examples are conditional static acceptance criteria, not reports of executed tests. Unless stated otherwise, all required addresses and table entries are valid, invoked operations return, and object lifetimes permit subsequent accesses.

1. **Immediate terminal object.**  
   Acquisition supplies a non-null object whose status returns −1. The function calls F-a9c62fb9dbee with the first argument plus 304 bytes, then returns if that dependency returns. It neither reads the object’s associated-object field nor invokes its completion operation.

2. **Nonterminal object without an associated object.**  
   Acquisition supplies an object whose status returns zero and whose associated-object field is null after status returns. No associated callback occurs. Completion runs once before the next acquisition call.

3. **Nonterminal negative status.**  
   Status returns −2. This does not end the loop. The associated-field check and completion follow exactly as for a zero status.

4. **Associated callback receives both objects.**  
   After a nonterminal status, the associated-object field points to a valid object. Its table-offset-0 entry receives that associated object first and the acquired object second. Completion of the acquired object follows if the callback returns.

5. **Status changes the associated-object field.**  
   The field is null before status, but status installs a valid associated-object pointer and returns a nonterminal value. The newly installed pointer controls the callback because the field is read after status.

6. **Callback changes completion dispatch.**  
   A callback replaces the acquired object’s dispatch-table pointer and returns. Completion is selected from byte offset 4 of the replacement table, provided the replacement remains valid.

7. **Acquisition replaces the initial object.**  
   The fourth argument identifies one object, but the first acquisition writes another into the local slot. Only the replacement is checked and processed during that iteration.

8. **Acquisition leaves the slot unchanged.**  
   On the first iteration, acquisition does not modify the slot. The fourth argument remains the selected pointer. On later iterations, unchanged-slot behavior uses the value then present; the function does not restore the original argument.

9. **Null acquisition result.**  
   Acquisition leaves or writes null in the slot. F-a817d8d58c10 is invoked before any object-table dereference. Under its non-returning annotation, finalization is not reached.

10. **No terminal status.**  
    Every acquisition and operation returns, all selected objects remain valid, and every status differs from −1. The function continues iterating; the supplied body supplies no independent termination condition.

## Uncertainties

The following remain **documented_only**:

- The semantic meaning of the first argument, the selected objects, the associated objects, and the terminal status.
- The second and third argument roles outside this body. Their direct non-use does not establish that callers may omit them or change the calling convention.
- The exact ABI, alignment requirements, and complete object layouts.
- All dependency effects not visible at these call sites, including changes to globals and shared state.
- Whether any dependency retains the local slot’s address. Retention would create a lifetime concern after this function returns.
- Allocation, deallocation, reference counting, and ownership transfer.
- Exception, cancellation, fault, or nonlocal-exit behavior.
- Synchronization and behavior under concurrent modification.
- Boundary behavior of the 304-byte address adjustment.
- Whether the non-return annotation on F-a817d8d58c10 accurately describes every reachable execution.

A repeated acquisition-and-processing interpretation is supported by the control flow. More specific descriptions such as queue draining, destruction, or lock release would be inferred intent rather than established behavior.
