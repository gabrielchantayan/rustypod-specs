# F-00d64b25d753

## Purpose

F-00d64b25d753 performs two setup calls, obtains a 32-bit saved value from a global, makes three receiver-associated indirect calls, and finally assigns zero through a pointer read from another global.

The established sequence is:

1. Invoke F-54e02808c68b without explicit arguments.
2. Invoke F-010f932ac12d with a global setup value and the caller’s second argument.
3. Read a shared global and assign its value to 32-bit local storage.
4. Make the first indirect call using a separate, direct read of the shared global.
5. Make the second and third indirect calls using the saved 32-bit assignment result.
6. Read the destination pointer and assign zero through it.

The distinction between the direct global argument and the saved value is material. The shared global’s declaration is unavailable. Assignment into 32-bit storage may convert or truncate its value. Consequently, even an unchanged shared global does not by itself establish equality between the first call’s shared-value argument and the saved value used by the later calls.

The application-level purpose is unknown. The visible sequence does not establish registration, rendering, notification, resource release, or any other domain-specific operation.

## Interface

### Explicit inputs

**Receiver.** The first argument is a pointer. Each indirect dispatch reads an integer-valued field at the receiver’s starting address, uses that value as a table-base address, and selects a callable entry at byte displacement **0x58**, or **88 bytes**.

The original receiver pointer is also supplied as the first argument to each indirect call. This function does not replace that pointer between calls. Dependencies may nevertheless change the storage it designates, including the table-address field.

The receiver and associated dispatch storage must support each lookup when it occurs. A successful earlier lookup does not establish validity for a later lookup.

**Auxiliary value.** The second argument is an opaque **32-bit value**. It is forwarded as the second argument to F-010f932ac12d without an explicit transformation in this body.

The body does not inspect it or supply it to the three indirect calls. Its signedness, interpretation, ownership significance, and any callee-side parameter conversion remain unresolved.

## Behavior

### Ordered setup

F-54e02808c68b is the first explicit operation. It receives no explicit arguments. Its return value, if any, is ignored.

Only after that call returns does the function obtain the setup value for F-010f932ac12d. That second dependency receives the setup value and the caller’s unchanged 32-bit auxiliary input.

The setup value is not captured before F-54e02808c68b. A change to its global location during the first dependency can therefore affect the second dependency’s argument.

F-010f932ac12d’s return value is also ignored. Neither dependency is established to preserve globals, receiver contents, dispatch tables, or memory ownership.

### Capture into 32-bit storage

After F-010f932ac12d returns, the shared global is read and assigned into 32-bit local storage.

The saved value is the **result of that assignment**, not necessarily a representation-preserving copy of the global’s entire value. The global’s unknown type and width prevent a complete conversion rule from being specified. Depending on the missing declaration and execution model, the assignment may preserve the value, narrow it, or apply another type-dependent conversion.

The second and third indirect calls both obtain their second argument from this same saved 32-bit value. The function does not refresh it after either intervening call.

The first indirect call instead obtains its second argument directly from another read of the shared global. Two separate issues must therefore remain distinct:

- The global may change between the capture read and the direct argument read, if the execution model permits such a change.
- Even without a change, assignment into 32-bit storage may produce a value or representation different from that supplied through the direct argument expression.

No explicit dependency call occurs between the capture and the first call’s direct shared-value read. Whether asynchronous changes or special access properties can distinguish those reads is unresolved.

If the saved value identifies an object or address, preserving the saved value does not preserve the object’s contents, lifetime, or validity.

### First indirect call

The first target is selected through the receiver-associated table at the 88-byte displacement. It receives:

1. The original receiver pointer.
2. The shared global supplied directly from a separate read.
3. The first item, read for this invocation.

This invocation follows the assignment into saved storage, but it does not use that saved storage for its second argument.

The supplied expression does not establish a total order among the target-resolution accesses, the direct shared-value read, and the first-item read. Their finer ordering is **documented_only**. The data needed to form the target and arguments must be obtained before the invocation, but no additional ordering guarantee is imposed here.

The return value is ignored.

### Second indirect call

After the first indirect call returns, the function resolves the receiver-associated target again at the same 88-byte displacement.

The second target receives:

1. The original receiver pointer.
2. The saved 32-bit assignment result.
3. The second item, read for this invocation.

The first target is not explicitly cached for reuse. Changes made by the first call to the receiver’s table-address field or selected table entry can affect this second lookup.

The second item is also read after the first call returns. It is not captured before that call, so mutations during the first call can affect the value supplied.

Changes to the shared global during the first call do not replace the saved 32-bit value. This remains true even if the direct shared value originally differed from the assignment result because of conversion.

No finer order between target resolution and the second-item read is established. The return value is ignored.

### Third indirect call

After the second indirect call returns, the function performs another lookup through the receiver-associated table at the same displacement.

The third target receives:

1. The original receiver pointer.
2. The same saved 32-bit assignment result used by the second call.
3. The third item, read for this invocation.

The second call may affect the third lookup and third-item read. It does not cause this function to recapture the shared global.

The second and third argument expressions use the same stored 32-bit value. This does not establish identical targets, identical item values, unchanged referenced objects, or any undocumented callee-side interpretation of those argument bits.

No finer order between target resolution and the third-item read is established. The return value is ignored.

### Final zero assignment

After the third indirect call returns, the function reads the clear-destination pointer and assigns zero through it.

The destination pointer is selected at this late stage rather than retained before the calls. A dependency that changes the pointer global can redirect the final write.

The assignment targets storage designated by the pointer. It is not a direct assignment to the pointer global itself, although aliasing could make the designated storage overlap that global.

The missing pointee declaration prevents a precise store width, alignment requirement, or zero representation from being specified. This is not evidence of an object-wide clear, a particular byte count, or a bytewise all-zero operation.

The function then returns without a value.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed test results.

### Stable state without representation assumptions

Given valid storage, normally returning dependencies, and an unchanged shared global:

- The first indirect call uses a direct read of that global.
- The second and third use the result of assigning the global’s value into 32-bit storage.
- Equality between the first argument value and the later saved argument value remains unresolved.

Stability alone is insufficient to establish equality.

### Stable state with representation-preserving assumptions

If, additionally, assignment into 32-bit storage preserves the relevant value and the applicable call-argument conversions preserve equality between the direct and saved forms, then all three calls receive equal shared-value-related arguments.

Under valid, stable dispatch and destination conditions, the item order is first, second, third, followed by the zero assignment after the third call returns.

### Setup mutations

If F-54e02808c68b changes the setup-value global, and no subsequent change intervenes before its read, F-010f932ac12d receives the changed setup value.

If F-010f932ac12d changes the shared global, the saved value is the 32-bit assignment result of the value read after that dependency returns.

### Separate reads with different values

Suppose the capture read obtains A, and a valid mutation under the applicable execution model causes the first call’s direct read to obtain B.

Then:

- The first call is supplied with B through its direct argument expression, subject to applicable argument conversion.
- The second and third calls are supplied with the saved **32-bit assignment result of A**, subject to applicable argument conversion.

The later calls are not necessarily supplied with the original value A unchanged. This example does not authorize unsynchronized concurrent access.

### Saved value survives later mutation

If the saved assignment result is S and the first indirect call changes the shared global, the second and third calls still use S.

This criterion concerns the saved value, not the contents or lifetime of any storage it might identify.

### Later dispatch and item changes

If the first call installs a different valid receiver-associated table and changes the second item, the second invocation uses its later lookup and later item read.

A third-item change during the second call similarly affects the third invocation if no later change intervenes before that read.

### Late destination selection

If the third call replaces the clear-destination pointer with another valid writable address, and no later change intervenes, the final zero assignment uses the replacement address. Its width remains unresolved.

### Nonreturn prevents the tail

If the second indirect call does not return normally, the third indirect call and final zero assignment are not reached through the ordinary sequence.
