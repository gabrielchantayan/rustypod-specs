# F-9d5d90660a7a

## Purpose

F-9d5d90660a7a performs an ordered sequence of dependency invocations, object-field accesses, one explicit four-byte replacement store, and a guarded indirect invocation.

The function first invokes a dependency using an input-object field, then captures a related-object address. After two further dependency calls, it conditionally invokes another dependency based on a comparison involving the related object. It then replaces the compared field regardless of the comparison result. Finally, it inspects a pointer obtained through shared storage and conditionally invokes a separately stored target.

These are established operations, not established application semantics. Descriptions such as “related object,” “notification,” and “replacement” identify roles in this contract. They do not establish destruction, release, unregistration, ownership transfer, or a particular application state.

This contract distinguishes:

- **Established static evidence:** operations and ordering represented in the supplied body.
- **Inferred intent:** plausible interpretation, not an acceptance requirement.
- **documented_only:** behavior or properties that the supplied evidence does not establish.

No runtime tests have been performed.

This invocation occurs before the read at P + `0xB0`. If the dependency changes that latter field and returns normally, the subsequent field read uses its post-call contents, subject to the execution platform’s memory semantics.

### 2. Capture the related-object address

Later related-object operations use this captured address. The function does not represent another read of P + `0xB0` to choose their destination.

### 4. Compare and conditionally invoke

After F-338d16f9ce72 returns, the function compares the four-byte word at R + `0x20` with the comparison word.

If they are equal, it invokes F-77781c8e0ff9 with these explicit argument positions:

1. The four-byte value at R + `0x28`.
2. The notification word.
3. The captured address R.

If they differ, that invocation is omitted. The payload access specifically addressed as R + `0x28` is also omitted. This does not guarantee that the same physical bytes are untouched by another access through an alias.

The representation does not establish the relative evaluation order of the two comparison operands. It also does not establish the relative order of the payload and notification-word reads used to prepare the invocation arguments. Those argument reads occur before entry into F-77781c8e0ff9.

The equality result is not rechecked after the conditional invocation returns.

### 5. Replace the related-object word

After the comparison branch completes normally, the function obtains four bytes from replacement storage and writes them to R + `0x20`.

This store occurs on both comparison outcomes. On the equality path, it occurs after F-77781c8e0ff9 returns.

Consequences established by this ordering include:

- The conditional invocation precedes this function’s replacement store.
- A value placed at R + `0x20` by that invocation is overwritten when the replacement store completes.
- The store destination still uses the captured R.
- The replacement value is obtained at this stage; it is not established as a constant retained before earlier dependency calls.

If the destination aliases another named location, the store also changes that location’s storage. Partial overlap is not excluded either. The resulting interpretation of partially overwritten values depends on the actual layout and endianness.

### 6. Re-read the shared handle and inspect its contents

After the replacement store, the function reads the shared handle slot again. It does not reuse the earlier handle argument merely because that argument was supplied to F-338d16f9ce72.

Through the newly read handle, it reads a four-byte value and treats that value as another address, denoted **Q**.

The handle dereference occurs before any check on Q. There is no represented check that the handle itself is zero or otherwise invalid.

The subsequent checks are:

- If Q is zero, the function skips the read through Q and skips the indirect invocation.
- If Q is nonzero, the function reads the first four-byte word at Q.
- The indirect invocation is eligible only if that word is nonzero.

A word with its high bit set satisfies the second guard when it is nonzero. The test is not a signed-positive test.

Because the handle-slot read follows the replacement store, aliasing between that slot and R + `0x20` may affect the handle used here. The function does not preserve the earlier slot contents against its own store.

### 7. Conditionally invoke the separate target

If Q and the word read at Q are both nonzero, the function invokes the target supplied by the indirect target slot.

The word read at Q is a guard, not the represented source of the target. No explicit arguments are shown for the invocation. Its complete calling convention, implicit inputs, and return type remain **documented_only**.

The target lookup belongs to the post-replacement invocation path. The evidence does not justify requiring the target-slot contents to remain unchanged across the replacement store. If the store aliases that slot, it may change the target subsequently used.

The precise underlying control-transfer mechanism is not established; the supported contract is the conditional invocation and absence of further represented work afterward.

## Acceptance examples

These examples are conditional criteria derived from static evidence, not executed tests. Each assumes valid reached accesses, normal return from preceding dependencies, and no interference beyond what the example states.

### Unequal comparison

- The payload read specifically through R + `0x28` is omitted.
- The replacement store still occurs.

### Equal comparison

If that dependency changes replacement storage, the subsequent replacement uses the bytes obtained afterward, not an assumed earlier constant.

### Relationship changes before capture

### Relationship changes after capture

If an intermediate dependency changes P + `0xB0`, later related-object accesses still use the already captured R. The old object’s continued validity remains necessary.

### Replacement aliases the relationship field

If R equals P + `0x90`, with valid address calculations and storage, the replacement store writes the four bytes at P + `0xB0`.

This is a direct effect of the single represented store, not an additional store operation. It does not retroactively change the captured R or cause the function to select a new related object.

### Replacement aliases the shared handle slot

If R + `0x20` coincides with the shared handle slot, the replacement store updates that slot before the final handle read.

The final dereference therefore uses the post-store handle representation. If it is invalid, the function has no represented guard preventing that dereference. If it is valid and contains a zero Q, the function skips the indirect invocation.

### Replacement aliases the target slot

If the replacement destination overlaps the indirect target slot, the store may change the target used when both final guards pass. The contract does not guarantee invocation of the slot’s pre-store value.

### Zero Q

If the final handle is valid and contains zero Q, there is no read through Q and no indirect invocation.

A zero handle is not this case: the handle is dereferenced before Q is tested.

### Final guard word

If Q is valid and nonzero but its first word is zero, the word is read and the invocation is skipped.

If that word is any nonzero four-byte value, including one with its high bit set, the separate target is invoked.

### Conditional invocation changes the comparison field

If F-77781c8e0ff9 changes R + `0x20` and returns normally, the replacement store subsequently overwrites those bytes. The comparison is not repeated.
