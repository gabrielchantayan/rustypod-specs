# F-844129fb10e8

## Purpose

F-844129fb10e8 obtains a 32-bit candidate value, locates an associated descriptor, rejects an already-present candidate, and attempts to place the candidate into the first zero-valued slot within a bounded array prefix.

The established behavior is narrower than a general insertion operation:

- A zero candidate is rejected.
- A candidate already present in the initial search range is rejected.
- A preparation dependency is called when two descriptor fields are equal.
- After that optional call, only zero-valued slots strictly within the newly read search bound are eligible.
- A successful placement increments a separate descriptor field before writing the candidate.
- If no eligible zero-valued slot exists, the function returns −1 without directly appending an element.

The apparent intent is to register a candidate in a collection containing reusable holes. The meanings of the descriptor fields and the preparation dependency are not established. In particular, a field that triggers preparation must not be assumed to be a conventional capacity field.

## Interface

### Inputs

The function has no explicit parameters. Its inputs are supplied through dependency results and the memory reachable from those results.

The dependency sequence begins with:

1. F-8157a180d901, called with the integer value 72.
2. F-fb045f7ae136, called with the first dependency’s 32-bit result and a second argument of zero.

The result of the second call is the **candidate**. If nonzero, it is passed to F-ecd921e533b1, whose result identifies the **descriptor**.

### Result

The result is a signed 32-bit integer:

| Result | Meaning established by the supplied material |
|---|---|
| −1 | The candidate was zero, the candidate was found during duplicate detection, or the later vacancy search found no eligible slot. |
| Nonnegative integer | The index of the first zero-valued slot found during the later search. Under valid, stable memory and defined arithmetic, the candidate is written to that slot before return. |

The same failure value covers multiple conditions. There is no separate error code for preparation failure, malformed descriptors, or inaccessible memory.

### Descriptor layout

The function accesses the following descriptor-relative fields:

| Byte offset | Width | Operational role |
|---|---:|---|
| +0x18 | 32 bits | Address of the slot array |
| +0x1c | 32 bits, interpreted as signed | Search bound |
| +0x20 | 32 bits | Field compared with the search bound before preparation, and incremented on successful placement |

Array elements are 32-bit values, spaced four bytes apart. Element index zero is at the array address; index one is four bytes later.

These are operational descriptions, not inferred type names. The supplied material does not establish whether +0x1c is a length, a high-water mark, or another kind of bound, nor whether +0x20 represents occupancy, capacity, or something else.

### Preconditions for defined completion

For execution to complete normally:

- Every dependency that is reached must return normally.
- The descriptor result must identify accessible memory for the fields used.
- Every slot address actually examined must be readable.
- On successful placement, the +0x20 field and selected slot must be writable.
- Address calculations and the successful increment must remain within the execution environment’s defined arithmetic and memory rules.

The function does not check these conditions. A nonzero candidate is not otherwise validated. Negative candidate bit patterns are not rejected merely because their signed interpretation is negative.

## Behavior

### 1. Acquire the candidate

F-8157a180d901 is called with 72. Its 32-bit result is then supplied to F-fb045f7ae136 together with zero.

If the candidate returned by F-fb045f7ae136 is zero, the function immediately returns −1. It does not call F-ecd921e533b1 or inspect a descriptor on this path.

There is no separate validity test on the first dependency’s result.

### 2. Obtain the descriptor

For a nonzero candidate, F-ecd921e533b1 is called with that candidate.

The returned value is used as a descriptor address without a null check, status check, or other visible validation. The function subsequently accesses the descriptor fields listed above.

### 3. Reject an existing candidate

Duplicate detection examines array elements in increasing index order, starting at zero.

The signed field at +0x1c supplies the upper bound. During this first search, that field is read again for each loop-condition evaluation; it is not captured once for the whole search.

For each index admitted by the current bound:

- The array address is read from +0x18.
- The corresponding four-byte element is read.
- That element is compared with the candidate.

An equality causes an immediate return of −1. No preparation call or direct descriptor write occurs after that match.

Zero-valued elements do not terminate duplicate detection. A hole before an existing matching candidate therefore does not permit insertion.

If the bound is initially zero or negative, the first search performs no element reads, provided the bound remains unchanged during the condition evaluation.

The duplicate test covers only the elements reached by this search. It does not establish global uniqueness outside that range or after later dependency side effects.

### 4. Conditionally call preparation

After duplicate detection completes without a match, the values at +0x20 and +0x1c are read and compared.

If equal, F-e3ce423fc856 is called with the address of the descriptor field at +0x18. This argument identifies the field containing the array address, not merely the array address stored in it.

This call precedes the vacancy search, even when a hole was present in the range already examined. The function does not first establish that preparation is necessary to obtain a free slot.

No returned status is checked. The dependency’s allocation behavior, failure behavior, and memory effects are unknown. It may change the array address or other reachable state; this contract does not assume that it preserves the search bound, slot contents, globals, or ownership.

If the two fields are unequal, the preparation dependency is not called. In particular, the visible condition is equality, not a less-than or greater-than capacity check.

### 5. Search for a vacant slot

After the optional preparation call, the signed field at +0x1c is read again and captured as the vacancy-search bound.

This search uses the captured bound throughout. It examines indices in increasing order, beginning at zero, and stops at the first element whose 32-bit value is zero.

For each examined index, the array address is read from the descriptor’s +0x18 field before the element is read.

Consequences:

- The first eligible hole is selected.
- A zero at an index equal to the bound is not inspected.
- A zero beyond the bound is not inspected.
- A nonpositive captured bound produces no element reads and no selected slot.
- Changes made by preparation affect this search because its bound and slot reads occur afterward.

If no zero-valued element is found, the selected-index result becomes −1. There is no direct append at the bound and no direct increase of +0x1c.

### 6. Commit a selected slot

For a slot found by the vacancy search, its index is nonnegative and strictly less than the captured bound. Under ordinary sequential execution with valid memory and defined arithmetic, the visible write conditions are therefore satisfied.

The commit order is:

1. Read the current 32-bit value at descriptor offset +0x20.
2. Increment it by one.
3. Write the incremented value back to +0x20.
4. Read the array address from +0x18.
5. Write the candidate into the selected four-byte slot.
6. Return the selected index.

This order matters: the metadata write precedes the slot write. The function provides no rollback if execution fails between those writes.

When no slot is found, neither of these direct writes occurs, and the function returns −1.

## Side effects

### Direct memory effects

On successful placement, the function directly writes:

- The field at descriptor offset +0x20, increased by one.
- The selected array element, replaced with the candidate.

It does not directly write the search-bound field at +0x1c or replace the array-address field at +0x18.

On zero-candidate rejection, duplicate rejection, and no-vacancy failure, the function performs no direct writes to these fields or slots. This is not a promise of no overall side effects: dependencies already called may have changed state.

### Ordering and failure visibility

The established call and access phases are ordered as follows:

1. Initial dependency calls.
2. Descriptor lookup, if the candidate is nonzero.
3. Duplicate search.
4. Optional preparation.
5. Vacancy search.
6. Metadata increment and write.
7. Candidate slot write.

The relative evaluation order of the two field reads used by the equality comparison is not independently established.

There are no explicit locks, atomic operations, rollback actions, or error-recovery paths. The repeated field reads do not establish a concurrency protocol. Concurrent mutation, aliasing between descriptor fields and slots, and dependency-driven state changes can affect observations; ordinary collection behavior requires suitable caller-side memory validity and exclusion assumptions.

### Ownership

The function contains no explicit release operation. Storing the candidate does not, by itself, establish ownership transfer, reference acquisition, or lifetime extension.

Likewise, passing the address of the array-address field to F-e3ce423fc856 does not establish whether that dependency allocates, reallocates, frees, borrows, or merely inspects storage.

## Acceptance examples

These examples are conditional static acceptance cases, not runtime observations. Unless otherwise stated, memory is valid, arithmetic is representable, state remains stable outside specified dependency effects, and dependencies return normally.

1. **Zero candidate**  
   If F-fb045f7ae136 returns zero, the result is −1. Descriptor lookup and preparation are not reached.

2. **Duplicate after an earlier hole**  
   Suppose the candidate is 17, the search bound is three, and the slots are `[0, 17, 0]`. Duplicate detection reaches index one and returns −1. The earlier hole is not filled, +0x20 is not directly incremented, and preparation is not called.

3. **First-hole placement without preparation**  
   Suppose the candidate is 17, the bound is three, +0x20 is one, and the slots are `[5, 0, 0]`. The fields are unequal, so preparation is skipped. The result is one, +0x20 becomes two, and slot one becomes 17. Slot two remains zero.

4. **Index zero is a valid success**  
   Suppose the candidate is 17, the bound is two, +0x20 is zero, and the slots are `[0, 5]`. The result is zero. The +0x20 field becomes one and slot zero becomes 17.

5. **No hole despite an out-of-range zero**  
   Suppose the candidate is 17, the bound is two, +0x20 is one, and readable storage contains `[5, 6, 0]`. Only the first two elements are searched. The result is −1, with no direct metadata or slot write.

6. **Equality triggers preparation before reuse**  
   Suppose the bound and +0x20 are both two, and the slots are `[0, 5]`. Preparation is called even though a hole exists. If it leaves relevant state unchanged, the result is zero, +0x20 becomes three, and slot zero becomes the candidate. This illustrates why a conventional capacity interpretation is not an established invariant.

7. **Preparation creates an eligible hole**  
   Suppose the initial bound is one, +0x20 is one, and slot zero does not match the candidate. Preparation changes the bound to two and leaves a zero at slot one. If no earlier slot is zero, the later search selects index one and writes there.

8. **Preparation introduces a duplicate**  
   Suppose the initial search finds no duplicate. Preparation then leaves slots `[17, 0]` with bound two while the candidate is 17. There is no second duplicate check. The function selects index one and writes another 17.

9. **Empty range remains empty**  
   Suppose both compared fields are zero and preparation leaves the bound zero. Preparation is called, but the later search examines no slots and returns −1. The function does not directly append a first element.

## Uncertainties

The following remain **documented_only**:

- The semantic meanings of the constant 72, candidate, descriptor, and metadata fields.
- Dependency failure conventions and nonlocal side effects.
- Allocation ownership and candidate lifetime requirements.
- Alignment guarantees, address validity, and concurrency rules.
- Recovery behavior for inaccessible memory.
- Exact machine behavior when signed increment, index scaling, or address addition exceeds its valid range.

The visible operations use four-byte values and four-byte slot spacing. Bounds and returned indices use signed comparisons. The supplied representation does not justify imposing a portable overflow rule. In particular, a successful increment of the signed 32-bit value 2,147,483,647 is outside the contract’s representable-arithmetic acceptance cases.

A reusable-hole registration operation is a plausible intent. Automatic append, uniqueness after preparation, transactional updates, and conventional size/capacity invariants are not established behavior.
