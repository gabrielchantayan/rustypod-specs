# F-7725b526e473

## Purpose

F-7725b526e473 rewires a linked structure around a supplied node and the node referenced by its offset-8 field. It replaces the supplied node in its incoming link, moves an intermediate subtree, and makes the supplied node a child of the replacement node.

**Inferred intent:** the field relationships are consistent with an in-place right rotation of a binary tree with parent links and a separately stored root link. This interpretation supplies the terms “parent,” “left,” and “right” below. The established behavior is the field access and update sequence; the source does not establish a particular tree type, balancing policy, or ordering invariant.

The operation does not search for a node, compare keys, inspect balance information, allocate storage, or explicitly release storage. Its caller must supply an appropriate structure.

## Behavior

### Established access and update sequence

The sequence below describes the supplied operation. Repeated reads matter: some references are reread after earlier writes rather than retained as one immutable entry-state snapshot.

1. **Select the pivot.**  
   Read the node’s offset-8 field. Retain that 32-bit value as the pivot address for the rest of the operation.

2. **Replace the node’s offset-8 reference.**  
   Read the pivot’s offset-12 field and copy its 32-bit contents into the node’s offset-8 field. The write occurs even if the copied value is zero.

3. **Conditionally repair the transferred child’s parent reference.**  
   Read the pivot’s offset-12 field again and compare it with zero.

   If nonzero, read that field again to obtain a destination object address, then write the node address into that object’s offset-4 field.

   If zero, omit this write. The function does not dereference a zero transferred-child address on this branch.

4. **Set the pivot’s parent reference.**  
   Read the node’s offset-4 field and copy its 32-bit value into the pivot’s offset-4 field.

5. **Locate and inspect the root slot.**  
   Read the container’s offset-16 field and derive the root-slot address by adding 4. Read the root-slot value and compare it with the node address.

   The root-slot address is determined at this stage, after the preceding writes. It is not established as an entry-time snapshot.

6. **Replace the incoming link to the node.**  
   There are two alternatives:

   - **Root case:** if the root-slot value equals the node address, write the pivot address into the root slot.
   - **Non-root case:** otherwise, reread the node’s offset-4 field to obtain the old parent. Read that parent’s offset-12 field. If it equals the node address, write the pivot address into that same offset-12 field. Otherwise, write the pivot address into the parent’s offset-8 field.

   The fallback to the parent’s offset-8 field is unconditional once the offset-12 comparison fails. The function does not verify that the offset-8 field actually contains the node address.

7. **Make the node the pivot’s right child.**  
   Write the node address into the pivot’s offset-12 field.

8. **Make the pivot the node’s parent.**  
   Write the pivot address into the node’s offset-4 field, then return.

This describes ordering between the separate operations visible in the source. It does not establish an instruction-level trace, atomicity, or synchronization guarantees.

### Result under ordinary tree preconditions

Assume distinct relevant objects, stable ordinary memory, and coherent parent/child links. Let the pivot initially be the node’s left child, and let the transferred child initially be the pivot’s right child.

After normal completion:

- The pivot occupies the node’s former incoming position:
  - as the root if the root slot identified the node; or
  - in the selected child field of the old parent.
- The pivot’s parent field contains the node’s former parent reference.
- The pivot’s right-child field identifies the node.
- The node’s parent field identifies the pivot.
- The node’s left-child field contains the pivot’s former right-child reference.
- If the transferred child is nonzero, its parent field identifies the node.

For a valid, nonoverlapping tree layout, the node’s right-child field and the pivot’s left-child field are not changed. No payload field is explicitly accessed.

## Side effects

For ordinary nonoverlapping storage, normal completion performs **five mandatory 32-bit writes**, plus **one conditional 32-bit write** when the transferred-child reference is nonzero.

The mandatory writes target:

1. The node’s offset-8 field.
2. The pivot’s offset-4 field.
3. Exactly one incoming-link field: the root slot or one old-parent child field.
4. The pivot’s offset-12 field.
5. The node’s offset-4 field.

The conditional write targets the transferred child’s offset-4 field.

This is an in-place mutation. There is no explicit allocation, deallocation, reference-count adjustment, callback, I/O operation, or named global access in the supplied body. Caller-supplied addresses may nevertheless refer to shared or globally reachable memory.

The operation is not transactional. Earlier writes are not rolled back if a later access fails. Intermediate states need not form a coherent tree, so the source does not support concurrent unsynchronized traversal or mutation.

No ownership transfer or lifetime change is established. In particular, changing parent and child references is not evidence that an object is retained, released, or newly owned.
