# F-793b94643d2e

## Purpose

F-793b94643d2e performs a preliminary operation and, when that operation returns zero, constructs a holder-managed value and inserts an associated node into a context-maintained collection.

Its established contract is an ordered sequence of dependency calls, branch decisions, direct memory accesses, and normal returns. Lookup-or-create behavior, synchronization, object allocation, and collection registration are inferred purposes, not independently established dependency semantics.

The normal return value is a 32-bit word:

- **0:** the preliminary operation returned zero, and a subsequent holder check also returned zero.
- **1:** the preliminary operation returned nonzero, or the creation-and-insertion path reached its normal end.

A return of 1 does not independently establish successful allocation, ownership transfer, or persistence of the function’s direct writes. Those properties depend on callees whose contracts are unavailable.

## Interface

The function accepts four arguments.

| Argument | Representation established by the supplied body | Use |
|---|---|---|
| Context | 32-bit address-bearing value | Supplies addresses of embedded fields and operation targets; also passed to dependencies. |
| Value | 32-bit word | Passed to the preliminary dependency and twice to the initialization dependency. |
| Mode | 32-bit word | Passed twice to initialization; tested against zero to select a later call. |

Destination is an apparent role, not proof of a pointer type. The function does not directly dereference Destination.

The local holder occupies one directly visible 32-bit word. Its address is passed to several dependencies. Their access requirements and the holder’s nominal type are **documented_only**.

### Context and node layout

| Location | Directly established use |

| Context + `0x18` | Address supplied to the node-producing dependency. |
| Context + `0x28` | One 32-bit read obtaining a saved collection-anchor address. |

The saved anchor’s offset-4 field is explicitly read twice and then written. There is **no explicit read of the anchor’s offset-0 field**.

The second offset-4 read supplies an address through which the function writes a 32-bit node address. That indirect write does not establish an offset-0 read of the anchor. If the loaded address happens to equal the anchor, the write targets the anchor’s offset-0 field; that is a conditional aliasing case, not an additional read.

The size and internal layout of the node payload beginning at offset 8 are unknown.

## Behavior

### Initial state and entry ordering

Before either entry operation, the function stores the original Destination word in the local 32-bit holder. It also retains copies of Context, Value, and Mode for later repeated initialization arguments and computes the first entry target.

The relevant ordering is:

1. Initialize the local holder with Destination.
2. Invoke the entry dependency on Context + `0x164`.
3. Invoke the entry dependency on Context + `0x148`.
4. Invoke F-151ab20ff1a3 with Context, Value, and Destination.

The holder initialization is not deferred until after entry. No later direct store restores Destination to the holder before holder construction.

The entry calls’ memory effects are unknown. Their placement must not be interpreted as a guarantee that they preserve global state, context fields, or other accessible storage. The established fact is the initial store’s position before both calls, not a universal guarantee about the holder’s contents after arbitrary dependency execution.

Entry results are not tested by this function. The visible body proceeds to the preliminary operation after both entry calls return.

### Preliminary bypass

The result of F-151ab20ff1a3 is tested against zero.

If nonzero, the function skips the entire creation path. It performs the exit operation on Context + `0x148`, then the exit operation on the previously computed Context + `0x164` target, and returns 1.

On this path:

- The initial local-holder store has occurred.
- No holder-construction, holder-check, or holder-finalization call occurs.
- No allocation-like, node-producing, payload, transfer, refresh, or mode-dependent call from the creation path occurs.
- No collection-link, count, or `0x1bc` write is performed directly by this function.

These exclusions do not constrain side effects of the entry, preliminary, or exit dependencies.

### Allocation-like request and holder construction

If the preliminary result is zero, F-8157a180d901 is called with `0x54`, meaning 84.

Its result is passed without an explicit null or failure check to F-55f9090ca681. That dependency receives seven arguments in this order:

1. The result from F-8157a180d901.
2. Value.
3. Context.
4. Mode.
5. The retained copy of Context.
6. The retained copy of Value.
7. The retained copy of Mode.

The repeated argument values are intentional features of the observed call interface. Their semantic roles are unknown.

The result of F-55f9090ca681 is then passed to F-6e5ee90f2ebb as its second argument; its first argument is the local holder’s address.

Next, F-194cdec98e23 receives the holder’s address. Its zero/nonzero result selects the remaining path. The function does not directly inspect the holder’s word to make this decision.

### Holder-check failure

If F-194cdec98e23 returns zero, the function:

1. Calls F-d62832ad54fc with the holder’s address.
2. Invokes the exit dependency on Context + `0x148`.
3. Invokes the exit dependency on the saved Context + `0x164` target.
4. Returns 0.

No node-producing call or direct collection modification occurs on this branch. The transfer-related call, all-ones state write, refresh-like call, and mode-dependent call are also absent.

This cleanup call does not prove release of the allocation-like result. Whether it destroys, releases, resets, or merely observes the holder is **documented_only**.

### Node preparation

If the holder check returns nonzero, the function reads the 32-bit field at Context + `0x28` and saves the resulting anchor address.

It then calls F-2bce23af7fb1 with Context + `0x18` and zero. The result is treated as the new node’s address.

The address corresponding to new node + 8 is tested against zero. If nonzero, F-e778256efd99 is called with:

1. New node + 8.
2. The holder’s address.

This is a test of the derived payload address, not a direct null-node test. Under ordinary nonwrapping address arithmetic, a zero node value produces a nonzero derived value of 8 and does not protect subsequent node accesses. Under a wrapping 32-bit address model, a node value of `0xfffffff8` would produce a zero derived address and skip the payload call, but the direct link writes would still follow. Exact address-wrap behavior is **documented_only**.

The anchor is captured before both the node-producing and optional payload calls. It is not reloaded from Context + `0x28` afterward. Those dependencies are not assumed to preserve the context field or the saved anchor’s referenced storage.

### Ordered insertion accesses

After node preparation, the function performs these direct accesses in order:

1. Write the saved anchor address to new node + `0`.
2. Read the 32-bit value at saved anchor + `4`.
3. Write that value to new node + `4`.
4. Read the 32-bit value at saved anchor + `4` again.
5. Write the new node address to the first 32-bit field at the address obtained by the second read.
6. Write the new node address to saved anchor + `4`.
7. Read the 32-bit count at Context + `0x2c`.
8. Add one and write the result to Context + `0x2c`.

The two anchor-link reads are distinct. The contract does not replace the second read with the first read’s value. In particular, aliasing or external mutation can make their results differ.

No explicit anchor-offset-0 read occurs in this sequence.

With conventional, stable circular doubly linked-list invariants, these writes insert the node immediately before the anchor. That interpretation is inferred and conditional. The observed accesses remain the contract when those invariants are not established.

The count operation has no range check or saturation branch. Exact overflow behavior cannot be resolved solely from the displayed 32-bit signed representation.

### Transfer-related call and subsequent operations

After the count update, the function:

1. Calls F-6e673595197b with the original Destination word and the holder’s address.
2. Writes `0xffffffff` to Context + `0x1bc`.
3. Calls F-b03c2a3a9cff with Context.
4. If the original Mode is nonzero, calls F-1a28d27dcc4e with Context and 10.
5. Calls F-d62832ad54fc with the holder’s address.
6. Performs the exit operation on Context + `0x148`.
7. Performs the exit operation on the saved Context + `0x164` target.
8. Returns 1.

Every nonzero Mode value enables the mode-dependent call; its magnitude and sign do not otherwise affect this branch.

No result from these calls is checked. The all-ones write is established at its position in the sequence, but subsequent dependencies may overwrite that field. Likewise, the function’s direct insertion writes do not guarantee that later dependencies preserve the resulting collection state.

There is no visible rollback after insertion and no explicit abnormal-exit cleanup mechanism.

## Side effects

The successful insertion path directly writes:

- Both 32-bit node link fields.
- A 32-bit field through the address obtained from the second anchor-offset-4 read.
- The anchor’s offset-4 field.
- The count at Context + `0x2c`.
- The all-ones state pattern at Context + `0x1bc`.

The local-holder initialization occurs before entry on every path, including the preliminary bypass. Additional holder effects are dependency-defined.

The paired entry and exit calls suggest synchronization. Their primitive type, exclusivity guarantees, recursion behavior, failure handling, and callback interactions are unknown. All creation-path operations occur between the second entry call and the first exit call in the visible sequence.

### Ownership and lifetime

The body establishes a lifecycle pattern, not ownership semantics:

- An allocation-like result is forwarded to initialization.
- An initialization result is supplied to a local-holder operation.
- The holder’s address is supplied to check, payload, transfer-related, and finalization operations.
- Finalization occurs once on either normally returning creation branch.
- Finalization does not occur on the preliminary bypass.

It is unknown whether any operation copies, retains, moves, shares, destroys, or releases an object. Neither node insertion nor the Destination-related operation establishes exclusive ownership. No explicit deallocation call for the initial allocation-like result is visible.
