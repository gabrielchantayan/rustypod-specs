# F-547af65833e6

## Purpose

F-547af65833e6 obtains one 32-byte record from a caller-supplied state object and partially initializes that record. It prefers a record referenced by the state’s reusable-record head. If that head is null, it consumes the next record from a sequential allocation region. When the sequential region is exhausted, it requests a new region and links a newly allocated region descriptor into the state.

The function has no explicit return value. Its observable results are memory writes, changes to allocation state, and calls to F-871e64ddc6de. In particular, it does not explicitly return the selected record’s address or store that address in a dedicated result field.

The interpretation as a reusable-record pool is inferred intent. The field accesses, branch conditions, allocation requests, and initialization writes described below are established by the supplied static representation.

### Region descriptor

A region descriptor occupies 12 bytes and has three 32-bit fields:

| Byte offset | Meaning established by use |
|---|---|
| 0 | Previous descriptor address |
| 4 | Region capacity, measured in 32-byte records |
| 8 | Region storage address |

When deriving a new capacity from an existing descriptor, the function reads only the existing descriptor’s field at offset 4. It does not traverse the descriptor chain.

### Selected record

A selected record is treated as a 32-byte slot. Its field at offset 12 supplies the next reusable-record address when selection uses the reusable-record head.

Every successful selection is followed by these writes:

| Byte offset | Width | Value |
|---|---:|---|
| 4 | 4 bytes | Zero |
| 8 | 4 bytes | Zero |
| 12 | 4 bytes | Zero |
| 0 | 1 byte | Zero |

The function does not explicitly initialize bytes 1–3 or 16–31.

## Behavior

### 1. Prefer the reusable-record head

The first state access reads the reusable-record head at offset 4.

If it is nonnull:

1. That address becomes the selected record.
2. The function reads the 32-bit value at selected-record offset 12.
3. It writes that value into the state’s reusable-record head.
4. It performs the common record initialization.

On this path, the function does not explicitly read or modify the sequential cursor, sequential end, or descriptor head. It makes no allocation request.

Only one reusable record is removed. Its successor is not followed, validated, or initialized. A null successor simply leaves the reusable-record head null.

The link must be read before the selected record’s offset-12 field is cleared.

### 2. Otherwise use the sequential cursor

If the reusable-record head is null, the function reads the sequential cursor at state offset 8 and compares it with the sequential end at offset 12.

When the two addresses differ:

1. The cursor value becomes the selected record.
2. The state’s sequential cursor is set to the selected address plus 32 bytes.
3. The common record initialization is performed.

The exhaustion test is equality only. There is no explicit ordering check, distance check, alignment check, or verification that a complete 32-byte slot remains.

Consequently, a cursor beyond the end, or a cursor fewer than 32 bytes before the end, is not rejected merely because the state is malformed. If the addresses differ, this path attempts to consume a slot.

### 3. Allocate a region when cursor equals end

When the cursor equals the end, the function computes a new record capacity.

If the descriptor head is null, the capacity is 32 records.

Otherwise, it reads the unsigned 32-bit capacity from offset 4 of the descriptor referenced by the state. Let that capacity be \(n\). It forms:

- An additive candidate: \(n + 32\).
- A growth candidate: \(n + (n \mathbin{\mathrm{logical}\ >>} 1) + (n \mathbin{\mathrm{logical}\ >>} 3)\).

Each addition uses 32-bit unsigned arithmetic. Intermediate overflow wraps modulo \(2^{32}\). The function selects the growth candidate when the additive candidate is less than or equal to it under unsigned comparison; otherwise it selects the additive candidate.

Thus the selected capacity is the unsigned maximum of the two already-wrapped candidates. It is not necessarily the larger unbounded mathematical result. There is no overflow check or capacity limit.

For capacities that do not overflow, the rule chooses the larger of:

- 32 additional records; and
- The previous capacity plus its separately truncated one-half and one-eighth components.

The separate shifts matter. Replacing them with one rounded multiplication by 1.625 would not preserve all results.

### 4. Request and publish the new objects

After computing the capacity, the function calls F-871e64ddc6de twice, in this order:

1. A request with arguments 12 and zero, producing the descriptor address.
2. A request with the selected capacity shifted left by five bits and zero, producing the storage address.

The storage-size argument is therefore the capacity multiplied by 32 modulo \(2^{32}\). No check detects loss of high bits. A zero-size storage request is possible for some wrapped capacities.

After both calls return, the explicit memory operations occur in this order:

1. Store the storage address at new-descriptor offset 8.
2. Read the state’s descriptor head and store that value at new-descriptor offset 0.
3. Store the selected capacity at new-descriptor offset 4.
4. Store the new descriptor address into the state’s descriptor head.
5. Read the storage address back from new-descriptor offset 8.
6. Set the state’s sequential end to that address plus the capacity multiplied by 32.
7. Set the state’s sequential cursor to that storage address plus 32.
8. Initialize the first record at that storage address.

The previous-head value linked into the new descriptor is read after both dependency calls. It must not be assumed to equal the value used earlier when deciding or calculating growth if a dependency can modify the state.

The computed capacity remains the one selected before the calls; there is no explicit capacity recomputation afterward.

The first record in a newly allocated region is consumed immediately. The cursor does not remain at the storage base.

### 5. Initialize the selected record

All selection paths converge on the same explicit write sequence:

1. Clear four bytes at offset 4.
2. Clear four bytes at offset 8.
3. Clear four bytes at offset 12.
4. Clear one byte at offset 0.

This is partial initialization, not clearing the entire slot. The one-byte write at offset 0 must not be expanded into a four-byte write without changing behavior.

These writes occur after the corresponding reusable-head or sequential-cursor update. The function provides no rollback if a later write cannot complete.

## Side effects

### State changes

Under a valid, nonoverlapping layout:

- Reusable-record selection changes only the reusable-record head and the selected record.
- Sequential selection without growth changes only the sequential cursor and the selected record.
- Growth additionally changes the descriptor head and sequential end, and initializes a new descriptor.

The descriptor chain is extended at its head. Existing descriptors are not explicitly modified or released.

### Allocation and ownership

The function requests two objects only on the growth path. It performs no explicit deallocation on any path.

The new descriptor retains the storage address and the previous descriptor address. This establishes persistent reachability through the state, but does not establish an ownership or destruction policy. The supplied material does not show who must eventually release either allocation, whether the dependency retains ownership, or whether returned memory is initially cleared.

### Ordering and interference

The ordering above describes explicit operations in the supplied static representation. It does not establish synchronization, atomicity, or instruction-level ordering guarantees.

There is no explicit locking. Concurrent mutation can invalidate the pool interpretation. Dependency-induced changes also matter: the contract does not assume F-871e64ddc6de preserves globals, the input state, or other reachable memory.

If the state, descriptors, and records overlap, record initialization can overwrite state fields or descriptor contents. No overlap detection is present. The ordinary field-role descriptions therefore require a suitable nonoverlapping layout.

### Errors

## Acceptance examples

These are conditional static acceptance cases, not executed tests. They assume valid, writable, suitably aligned, nonoverlapping storage and, where relevant, successful dependency calls that do not unexpectedly mutate the state.

- Select the reusable record.
- Replace the head with its offset-12 link.
- Make no dependency calls.
- Leave cursor and end unchanged.
- Perform only the specified partial record initialization.

- Select the cursor address.
- Advance the cursor by exactly 32 bytes.
- Leave descriptor head and end unchanged.
- Make no dependency calls.
- Preserve selected-record bytes 1–3 and 16–31.

### Initial region

Given a null reusable-record head, equal cursor and end, and a null descriptor head:

- Choose 32 records.
- Request 12 bytes, then 1,024 bytes, each with second argument zero.
- Link the new descriptor to a null previous head.
- Set its capacity to 32 and storage field to the returned storage address.
- Publish the descriptor.
- Set end to storage base plus 1,024 and cursor to storage base plus 32.

### Additive growth wins

Given an exhausted region whose descriptor capacity is 32:

- The additive candidate is 64.
- The growth candidate is \(32 + 16 + 4 = 52\).
- Choose 64 records and request 2,048 storage bytes.

### Proportional growth wins

Given an exhausted region whose descriptor capacity is 64:

- The additive candidate is 96.
- The growth candidate is \(64 + 32 + 8 = 104\).
- Choose 104 records and request 3,328 storage bytes.

### Separate truncation matters

Given an exhausted region whose descriptor capacity is 67:

- The growth candidate is \(67 + 33 + 8 = 108\).
- The additive candidate is 99.
- Choose 108 records, not 109.

### Overflow is not rejected

Given an exhausted region whose descriptor capacity is 0xFFFFFFFF:

- The additive candidate wraps to 31.
- The growth candidate wraps to 0x9FFFFFFD.
- Choose 0x9FFFFFFD by unsigned comparison.
- The storage-size argument wraps to 0xFFFFFFA0.
- No explicit overflow error is produced before requesting storage.

This example establishes arithmetic behavior, not that the resulting allocation and accesses can succeed safely.

### Equality is the entire exhaustion test

Given a null reusable-record head and distinct cursor and end addresses, even if their distance is less than 32 bytes:

- Do not allocate a new region solely because of that distance.
- Attempt sequential selection and initialization.
- Do not infer bounds validation from the region terminology.
