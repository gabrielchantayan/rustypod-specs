# F-5e43693288bd

## Purpose

F-5e43693288bd performs an allocation-or-resize operation using a caller-supplied context. Its visible paths request new storage, retain an existing block, absorb an adjacent block, or request replacement storage. Selected successful paths directly clear payload storage.

On successful address-changing replacement, a nonzero preservation selector enables a call to an unidentified external dependency with the new pointer, old pointer, and a bounded unsigned length. Copying is inferred intent, not established behavior: no independent contract establishes that this dependency copies bytes or restores any prefix.

Important observable distinctions are:

- Exact-size retention bypasses clearing, success counting, diagnostics, and final alignment enforcement.
- Clearing covers the recorded payload capacity, not just the requested size.
- Clearing precedes the unidentified preservation-related call.
- Replacement failure does not directly invoke the old-block-release dependency.
- Invalid metadata invokes a nonreturning dependency with path-specific arguments.
- Large requests can produce unexpectedly small encoded sizes through wrapping and masking.

These are static observations. Allocation policy, synchronization, ownership transfer, and dependency internals remain unresolved.

The function accepts seven arguments and ordinarily returns a payload pointer or null.

### Context layout

| Byte offset | Established access |
|---|---|
| 0 | A 32-bit accounting word reduced when an adjacent block is absorbed. |

The accounting and counter interpretations follow visible operations, not a complete context contract.

### Block layout

The first header word is eight bytes before the payload. Its fields are selected by:

- Size: `0x3FFFFFFC`.
- Low flags: `0x00000003`.
- High flags: `0xC0000000`.

The masked size is used as a total extent including the eight-byte header area. It is divisible by four but is not necessarily divisible by eight.

The next header address is obtained by adding the current masked extent to the current header address. A neighboring block considered for absorption has link words at header offsets 4 and 8. The complete header format is unknown.

### Preconditions and limits

There is no general validation of pointers, address ranges, arithmetic overflow, or metadata consistency. Safe use requires accessible context storage, readable existing-block metadata, accessible neighboring metadata on growth paths, writable link targets when links are followed, and sufficient accessible storage for all selected writes.

Address calculations and pointer conversions are represented using 32-bit values. Wider-pointer portability is not established.

Dependency effects are not constrained by this function’s visible body. Conditional examples below assume dependencies return where applicable and leave the stated later-path conditions intact; they do not assume general preservation of globals or memory.

## Behavior

### Conditional initialization and entry

Before processing the requested size, the function tests the low eight bits of the context word at offset 192. Only if those bits are zero does it test the low eight bits of the word at offset 204.

If the second test is nonzero, it writes byte value 1 at context offset 192 and calls F-ef3e50369ccb with the context and two zero arguments. The relationship between this addressed byte and the tested low-order bits depends on byte ordering.

Size normalization follows that call. F-c0fc6d033caa is then called with the context before either fresh allocation or existing-block processing. Its position suggests an entry operation; locking is not established.

### Request normalization

All request-normalization arithmetic is unsigned 32-bit arithmetic.

A provisional extent is formed by adding 3 to the requested size, masking with `0x3FFFFFFC`, and adding 8. Values below 16 are raised to 16. The normalized target extent is then obtained by adding 7 and masking with `0xFFFFFFF8`.

Consequently:

- Requests 0 through 8 produce target extent 16.
- Requests 9 through 16 produce target extent 24.
- Request `0xFFFFFFFF` produces target extent 16.
- Request `0xFFFFFFF9` produces target extent `0x40000008`.

This is not a checked conversion from requested bytes to available capacity. The first addition may wrap, and the first mask discards the top two bits. Furthermore, the target extent can contain bit 30 even though the header size field cannot encode that bit.

### Fresh allocation and existing-header validation

With no existing payload, F-64e6624e7275 receives the context, normalized target extent, and classification byte. Its return value becomes the candidate result. Null follows the ordinary failure path; nonnull proceeds to optional clearing and success counting.

With an existing payload, the function reads the raw first header word and extracts its masked extent. A zero raw word or a raw word with bit 0 set invokes F-a817d8d58c10. **The argument is the raw header word converted to a pointer**, not the header address.

These fatal paths do not visibly call F-e586bff64fb7 first. Nonzero metadata containing only other flag bits is not rejected by these checks alone; that does not establish its safety.

### Exact-size retention

If the original masked extent equals the normalized target extent, the function calls F-cd8cf53dc4ea with the context, existing header address, original masked extent, and classification. It then calls F-e586bff64fb7 and returns the original payload.

This path performs no direct clearing, counter increment, diagnostic-global capture, replacement request, preservation-related call, release call, or final alignment check. Dependency side effects remain possible.

### Adjacent growth

When the original extent is smaller than the target, the function reads the first word of the neighboring header.

Neighbor bit 1 takes precedence over all other growth decisions. If set, it invokes F-a817d8d58c10 **with the neighboring header address**.

Otherwise, absorption requires neighbor bit 0 to be set. It also requires the unsigned 32-bit sum of the original and neighboring masked extents to be at least the unsigned 32-bit value of requested size plus 8. This comparison uses the original request, not the normalized target.

If either requirement fails, F-64e6624e7275 is called for replacement storage. No direct old-header or free-list mutation precedes that replacement request.

When absorption proceeds, the observable mutation order is:

- Reduce the context word at offset 0 by the neighboring masked extent.
- Rewrite the current header with the combined masked size while retaining its high two and low two flag bits.
- Inspect the neighbor’s offset-8 link. If nonzero, write the neighbor’s offset-4 link into offset 4 of that target.
- Inspect the neighbor’s offset-4 link. If nonzero, write the neighbor’s offset-8 link into offset 8 of that target.
- Recompute the following header address from the updated current header and clear bit 1 there.

The link values are read during these operations, not captured as an immutable pair. Aliasing can therefore change values read later.

The original pre-growth extent is retained for later accounting arguments and preservation-length calculation.

### Retention and splitting

A retained block outside the exact-size path has its current masked extent read again. Splitting occurs only when that extent is strictly greater than the unsigned value obtained by adding 19 to the normalized target and masking with `0x3FFFFFFC`.

Three separate quantities govern the split:

| Quantity | Established behavior |
|---|---|
| Encoded current-block size | The normalized target masked with `0x3FFFFFF8`, combined with the current header’s preserved high two and low two flag bits. |
| Remainder-header address | Current header address plus the full normalized target extent. |
| Remainder size word | Current masked extent minus the full normalized target, using unsigned 32-bit subtraction. |

The encoded size therefore is **not always the normalized target**. The assignment removes bits 30–31 from the target’s size contribution. It neither relocates the remainder using the truncated size nor substitutes that truncated size into the remainder subtraction.

After writing the current header and the remainder size word, the function calls F-cc6c9b4a0f68 with only the context explicitly supplied. No complete remainder-header or link initialization is directly visible.

Whether splitting occurs or not, F-cd8cf53dc4ea receives the context, existing header address, original pre-growth extent, and classification. The existing payload then becomes the successful result.

### Clearing and success counting

Successful fresh allocation, successful replacement, and non-exact retained-block paths reach this stage.

If the clear selector equals exactly 1, the result header is reread. The function directly writes successive four-byte zeros starting at the payload, using recorded masked extent minus 8 as the byte count. For sane metadata, this clears the entire recorded payload capacity.

Other selector values do not cause direct clearing. Afterwards, the context counter at offset 12 is read, incremented, and written.

There is no guard against recorded extents below 8. The clearing count is represented through a signed 32-bit loop variable after an unsigned subtraction; malformed sizes can therefore produce underflow-derived counts and unsafe execution. No safe failure behavior is established for that case. The counter increment likewise has no visible overflow check.

### Exit and diagnostic reads

The common path calls F-e586bff64fb7 before diagnostics, preservation-related processing, release, or final alignment enforcement.

After that dependency returns, the function **unconditionally reads and captures an external 32-bit diagnostic value**, designated diagnostic value A here. This happens even for a successful result or a nonzero diagnostic selector.

The failure-diagnostic sequence requires all three conditions:

- Diagnostic selector is zero.
- Result is null.
- An external byte, accessed through an external pointer, is nonzero.

The byte flag is tested only after the first two conditions hold.

If enabled, three calls to F-404485218953 occur in this order:

| Call | Arguments and read timing |
|---|---|
| First | 1200 and a **new read of diagnostic value A**, distinct from the earlier capture. |
| Second | A separate external diagnostic value B, read **after the first call returns**, and the original captured A. |
| Third | 2400 and the original captured A shifted left by two. |

The first call is not guaranteed to receive the captured value. The second call may observe changes to B made by the first dependency. The latter two calls use the original captured A, rather than rereading it.

No allocation retry follows these calls. Their purpose and effects are unknown. The represented signed left shift has unresolved behavior for unrestricted diagnostic values.

### Address-changing replacement

If the old and resulting payloads are both nonnull and their addresses differ, a nonzero preservation selector causes the unidentified external dependency to be called with:

- Result payload pointer.
- Old payload pointer.
- Unsigned 32-bit length equal to the smaller of the requested size and the original masked extent minus 8.

The subtraction is unsigned and can underflow for malformed original metadata.

This establishes argument flow and call order only. It does not establish byte copying, overlap handling, prefix preservation, or any other memory effect. Any selected clearing has already happened before this call.

After the call returns—or immediately when preservation is disabled—F-69819188e4c5 receives the context, old payload, and classification byte.

No such release call occurs when replacement fails or returns the old address. Actual reclamation and ownership transfer require a dependency contract.

### Final alignment enforcement

On the common path, the function returns the result if its low three address bits are zero. Null satisfies this check.

Otherwise, F-a817d8d58c10 is invoked after all preceding effects. An unaligned candidate may therefore already have been cleared, counted, passed to the unidentified dependency, and associated with an old-block-release call.

Without an address-changing replacement, the alignment-failure argument is the diagnostic selector converted to a pointer. After such a replacement, it is the return value of F-69819188e4c5 converted to a pointer. The diagnostic sequence also assigns an intermediate argument value, but it requires a null result, which passes the alignment test on the represented path.

## Side effects

Directly established effects include initialization-byte mutation, adjacent-block accounting reduction, header and link writes, remainder-size-word creation, optional payload clearing, and successful-path counter increment.

The function also invokes dependencies with potentially broader effects. In particular:

- The preservation-related call may be intended to copy, but actual destination writes are unknown.
- The old-block-release call does not independently establish reclamation.
- Entry and exit calls do not independently establish synchronization.
- Diagnostic calls do not independently establish logging, delay, or termination.

No rollback is visible after direct mutation begins. Ordinary allocation failure returns null without a direct old-block-release call. Invalid metadata and failed final alignment instead reach a nonreturning dependency.

## Acceptance examples

These are conditional static criteria, not executed tests.

1. **Exact retention:** An existing extent of 24 and request 9 produce exact-size retention. Even with clear selector 1, the function performs no direct clearing or counter increment.

2. **Zero-byte fresh request:** Request 0 passes target extent 16 to F-64e6624e7275. If it returns accessible storage recording extent 16, clear selector 1 causes eight payload bytes to be zeroed.

3. **Selector equality:** Clear selector 2 does not enable clearing. Preservation selector 2 does enable the unidentified call when successful replacement changes the address.

4. **Clearing before preservation-related processing:** With original extent 32, request 40, and successful replacement at a different address, preservation enables a call with the result pointer, old pointer, and unsigned length 24. Selected clearing occurs first. Restoration of the first 24 bytes is not guaranteed by the available evidence.

5. **Replacement failure:** If replacement returns null, no direct F-69819188e4c5 call or success-counter increment follows. Dependency effects on the old allocation remain unknown.

6. **Distinct metadata-failure arguments:** Raw existing-header value 1 invokes F-a817d8d58c10 with pointer value 1. A growth neighbor with both low bits set invokes it with that neighbor’s header address, before absorption.

7. **Strict split threshold:** Target extent 32 yields threshold 48. Current extent 48 does not split; current extent 52 does, assuming execution reaches the retained-block split decision.

8. **Target versus encoded size:** Request `0xFFFFFFF9` normalizes to `0x40000008`. If splitting is reached with current extent 64, the encoded size becomes 8, the remainder write is addressed at header plus `0x40000008`, and its unsigned size word is `0xC0000038`. This criterion requires that distant address to be writable; it is not a claim of safe allocation behavior.

9. **Diagnostic read ordering:** If A is captured as 5 but its later first-call read observes 7, the first diagnostic call receives 7. If that call changes B to 11, the second receives 11 and captured value 5. The third uses captured value 5 shifted left by two.
