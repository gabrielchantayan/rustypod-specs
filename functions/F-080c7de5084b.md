# F-080c7de5084b

## Purpose

F-080c7de5084b conditionally changes the logical extent of a descriptor-backed sequence whose storage is addressed in 12-byte strides. Its three inputs are a descriptor address, an unsigned 32-bit requested extent, and a 32-bit value passed to element-processing dependencies.

**Inferred intent:** resize a sequence, preserving existing elements and initializing added elements from the supplied value.

**Established behavior:** the routine compares the requested extent with dependency results, then either adjusts the descriptor’s end field, expands within existing storage, or requests replacement storage and transfers ranges. The initial extent query has no explicit argument, unlike subsequent queries. Dependency implementations are unavailable. Consequently, ordinary resize semantics are conditional, not an unconditional contract.

There is no explicit return value or status result.

## Interface

### Inputs

| Input | Representation | Established use |
|---|---|---|
| Descriptor | Address of at least three accessible 32-bit words | Supplies the base, current-end, and storage-limit fields; receives updates |
| Requested extent | Unsigned 32-bit integer | Controls branch selection and growth amount |
| Supplied value | 32-bit word | Passed unchanged to element initialization and some element-operation calls |

The descriptor layout is:

| Byte offset | Field | Interpretation supported by use |
|---|---|---|
| 0 | Base | Beginning of element storage |
| 4 | Current end | End of the current logical range |
| 8 | Storage limit | End of available storage |

The field names describe how the routine uses the words; they do not establish an independently verified container type. Element addresses advance in increments of 12 bytes. The internal layout and ownership rules of an element are unknown.

The supplied value may represent an address, handle, or other encoded value. Its use as an argument to element-processing dependencies does not establish that it points to a readable 12-byte object.

### Outputs and state

The routine returns without an explicit result. Observable results can include:

- Changes to the descriptor’s three fields.
- Writes performed through element-processing dependencies.
- Allocation and old-storage handling through dependencies.
- Any additional effects of those dependencies.

No input validation, explicit failure result, or local rollback path is visible.

### Width and arithmetic requirements

The visible representation uses 32-bit integers and address-like values. Extent comparisons and storage-branch comparisons use unsigned 32-bit values. Some address differences and intermediary values pass through signed 32-bit representations.

The following operations are not visibly protected against overflow:

- Multiplication of an extent or capacity by 12.
- Requested extent minus a reported extent.
- Reported extent plus the growth amount.
- Growth-capacity calculations.
- Address additions, subtraction, and end-field reconstruction.

For a well-formed conventional sequence, differences between range endpoints must be nonnegative multiples of 12, and address calculations must remain representable. The function does not enforce those conditions.

Behavior for arithmetic outside those conditions must not be replaced with unbounded-integer resize semantics. In particular, the exact arithmetic contract of F-870c4fcf7295 remains unknown.

## Behavior

### 1. Initial decision

The first observable dependency operation is a call to F-edd755fc1cdd with **no explicit argument**. Its 32-bit result is compared with the requested extent.

- If the requested extent is less than or equal to that result, execution follows the non-growth path.
- Otherwise, execution follows the growth path.

The evidence does not establish that this first call reports the supplied descriptor’s extent. It must not be silently treated as equivalent to the later calls that explicitly receive the descriptor.

### 2. Non-growth path

The routine calls F-edd755fc1cdd with the descriptor.

If that result is less than or equal to the requested extent, the routine returns immediately. There are no explicit descriptor writes on this return path, although the dependency calls may have effects.

Otherwise:

1. The current-end field is read and retained.
2. The base field is read, and the requested boundary is calculated as base plus 12 times the requested extent.
3. The base field is read again for comparison with the retained end.
4. If those two values are equal, the routine returns.

The visible element-processing loop preceding the boundary adjustment executes zero times: its iterator is initialized to the same retained end used as its termination value. Therefore, this path makes no calls to F-390a12124e19.

Next, the routine rereads the current-end field. It advances a temporary address from the requested boundary in 12-byte steps until that temporary equals the reread end. This loop has no visible per-element operation.

It then calls F-870c4fcf7295 with:

- The retained earlier end minus the requested boundary.
- The constant 12.

Finally, it writes the current-end field as the reread end minus 12 times the dependency result.

Under stable descriptor contents and an ordinary exact-division interpretation of F-870c4fcf7295, this sets the current end to the requested boundary. That interpretation is conditional. No explicit destruction of removed elements, storage release, or base/storage-limit update is visible.

If the address-stepping loop cannot reach its endpoint in 12-byte increments, termination is not established.

### 3. Growth setup

On entering the growth path, the routine first saves the current-end field. It then queries F-edd755fc1cdd with the descriptor and subtracts that result from the requested extent using 32-bit unsigned arithmetic.

This difference is the growth amount.

If the growth amount is zero, the routine returns without further explicit writes.

Otherwise, it queries F-edd755fc1cdd again, then obtains a capacity-like value by calling F-870c4fcf7295 with the difference between storage limit and base, and the constant 12.

Replacement storage is selected when this capacity-like result is unsigned-less-than the sum of the latest reported extent and the growth amount. Otherwise, growth proceeds in the existing storage.

Because the saved end precedes several dependency calls, it is not necessarily equal to the current-end field used later. The routine does not refresh it.

### 4. Growth with replacement storage

The routine computes a new capacity using further extent queries:

1. Query the descriptor and add the growth amount to obtain a required-capacity candidate.
2. Query the descriptor again to obtain the basis for a growth-capacity candidate.
3. Calculate the larger of:
   - That basis plus 32.
   - That basis plus its unsigned right-shift-by-one value plus its unsigned right-shift-by-three value.
4. Select the larger of the growth-capacity candidate and the required-capacity candidate.

These additions use 32-bit arithmetic without visible overflow checks. Without overflow, the second growth expression is the basis plus the separately truncated halves and eighths; it is not necessarily a single rounded multiplication by 1.625.

The selected capacity is multiplied by 12 and passed to F-871e64ddc6de with a second argument of zero. The returned word is subsequently used as the replacement base. There is no visible null or failure check.

The dependency operations then occur in this order:

1. F-7466e437d24d receives the current base, the saved end, the replacement base, and the descriptor.
2. F-870c4fcf7295 receives the saved end minus the **currently read** base, and 12.
3. F-2441493e93b0 receives the replacement base plus 12 times that result, the growth amount, the supplied value, and the descriptor.
4. F-870c4fcf7295 is called again using the saved end minus a fresh base read, and 12.
5. F-7466e437d24d receives the saved end, the **currently read** current end, a replacement destination displaced by both the latest quotient and the growth amount, and the descriptor.
6. F-edd755fc1cdd receives the descriptor; its result is retained for the final end calculation.
7. The base field is read and retained. A temporary address advances from it in 12-byte steps until it equals the current-end field, which is read for each loop condition. No visible operation occurs inside this scan.
8. F-870c4fcf7295 receives the current storage limit minus the retained base, and 12.
9. F-ff1bdc376dcd receives that retained base, the preceding result, and zero.

Only after those calls does the routine explicitly replace descriptor fields, in this order:

1. Base becomes the replacement base.
2. Current end becomes replacement base plus 12 times the retained final extent query, plus 12 times the growth amount.
3. Storage limit becomes replacement base plus 12 times the selected capacity.

There is no explicit cleanup path for a dependency failure between allocation and installation.

### 5. Growth within existing storage

The routine reads the current-end field again. It also calculates an insertion boundary from the earlier saved end plus 12 times the growth amount.

It then **writes the current-end field first**, setting it to the freshly read end plus 12 times the growth amount. Element-processing calls occur after this descriptor change.

An unsigned address comparison selects one of two branches.

#### Fresh end at or below the insertion boundary

The routine:

1. Calls F-870c4fcf7295 with fresh end minus saved end, and 12.
2. Calls F-2441493e93b0 with the fresh end, growth amount minus that result, the supplied value, and the descriptor.
3. Calls F-7466e437d24d with saved end, fresh end, insertion boundary, and the descriptor.
4. Advances from saved end to fresh end in 12-byte steps, calling F-390a12124e19 at each address with the supplied value as a second argument.

When dependency calls leave descriptor fields stable, saved end and fresh end coincide. The initialization call then receives the full growth amount, the transfer range is empty, and the final loop executes zero times. The transfer call is nevertheless made.

#### Fresh end above the insertion boundary

The routine:

1. Calculates a source boundary as fresh end minus 12 times the growth amount.
2. Calls F-7466e437d24d with source boundary, fresh end, fresh end, and the descriptor.
3. Walks backward until the source boundary equals the saved end. Each iteration decrements a destination by 12 and calls F-390a12124e19 with **one explicit argument**.
4. Walks forward from saved end to the insertion boundary in 12-byte steps, calling F-390a12124e19 with the current address and the supplied value.

The one-argument call must not be expanded into an assumed two-argument operation. Its effective calling convention is unresolved.

## Side effects

### Explicit descriptor writes

- Non-growth path: at most the current-end field.
- Replacement-storage path: base, then current end, then storage limit, after old-storage handling.
- Existing-storage growth: current end before element initialization or transfer.

These orderings matter if dependencies inspect the descriptor or expose partial progress.

### Element and storage effects

The visible body contains no direct element-data writes. Such writes, construction, assignment, relocation, destruction, or release would occur through dependencies.

The empty scans are not evidence of element destruction. In particular, the non-growth path contains no executed element-processing call.

F-871e64ddc6de is used as an allocation-like operation. F-ff1bdc376dcd is used as an old-storage-release-like operation. Their exact ownership contracts are not established. The function visibly passes a base, a capacity-like count, and zero to the latter; it does not visibly pass a byte count.

Aliasing between the supplied value and existing storage is not checked. Its safety depends on dependency behavior and on whether earlier operations invalidate the referenced data.

## Acceptance examples

These are conditional contract examples, not executed tests. Unless stated otherwise, assume representable arithmetic, stable descriptor fields during dependency calls, exact division by 12, and extent queries consistent with the descriptor.

1. **Equal extent.**  
   The descriptor represents five elements, the request is five, and the initial query reports five. The descriptor-specific query also reports five. The routine returns without an explicit descriptor write or element-processing call.

2. **Shrink from five elements to two.**  
   The initial query reports at least two, and the descriptor-specific query reports five. Base and end differ. The boundary scan advances from base plus 24 to the old end. The final end is base plus 24. Base and storage limit remain explicitly unchanged. No element-processing or release dependency is called.

3. **Grow from two elements to five with sufficient capacity.**  
   The initial query reports two. Capacity is at least five. The growth amount is three. The current end is changed to base plus 60 before F-2441493e93b0 receives the old end, count three, the supplied value, and the descriptor. F-7466e437d24d is then called with an empty source range and destination base plus 60. No per-element loop iteration occurs.

4. **Grow from two elements to five with replacement storage.**  
   Existing capacity is two. The required capacity is five; the growth-capacity candidate is the larger of 34 and 3, hence 34. F-871e64ddc6de receives 408 and zero. The preserved prefix is submitted for transfer, then three added elements for initialization. Old-storage handling precedes descriptor replacement. The final descriptor spans five logical elements with capacity 34.

5. **Initial query differs from the descriptor query.**  
   The request is three, the initial no-argument query reports ten, and the descriptor-specific query reports two. The non-growth path returns immediately. It does not grow the descriptor to three. This is permitted by the visible branch structure.

6. **Dependency mutates the current end during growth setup.**  
   The saved end and freshly read end can differ. Selection of the in-place subbranch and its call counts must use the specified reads, not a normalized assumption that insertion always occurs at the latest end.

7. **Unaligned logical range.**  
   If an empty scan starts at an address that cannot reach its endpoint through repeated 12-byte increments, successful termination is not guaranteed. The contract does not promise validation or recovery.

## Uncertainties

The following remain **documented_only**:

- The effective argument source for the initial no-argument extent query.
- The actual semantics and side effects of every dependency.
- Whether the supplied value denotes an element address.
- Whether allocation failure returns, aborts, or propagates through another mechanism.
- Whether dependencies can fail after partial writes, and whether external cleanup exists.
- Exact signed arithmetic and address-wrap semantics outside well-formed representable ranges.
- The meaning of the one-argument element-operation call.
- Resource handling for removed elements, since the visible shrink path executes no element operation.
- Validity of empty ranges, null bases, overlapping transfers, and aliased initialization values.

The conventional resize interpretation does not resolve these unknowns.
