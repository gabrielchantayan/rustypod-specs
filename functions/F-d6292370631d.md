## Behavior

### Initial dependency sequence

The first indirect target is the incoming return/link-address value plus `0xFFE`. It receives the explicit 32-bit argument.

Five producer/consumer pairs follow, in order. Each producer has no represented explicit arguments; its opaque 32-bit result is passed to its corresponding consumer before the next producer is invoked.

One further indirect dependency then runs without represented explicit arguments. A character-sized auxiliary register value observed after this call supplies the next phase.

No local status checks appear between these calls. “Without explicit arguments” does not establish a complete machine-level calling convention. None of these dependencies is known to preserve globals, registers, memory, or ownership.

### First address-derived accesses

The auxiliary character value is converted to an integer and shifted left by two to form a byte-load address. The loaded character is then converted to an integer.

Both conversions depend on the unresolved signedness of the character type. A negative signed value also raises an unresolved left-shift issue.

The subsequent accesses occur in this represented order:

1. A 32-bit store writes the converted byte value at an address `0x70` bytes above that value.
2. A 32-bit load reads from an address `0x20` bytes above that value.
3. The loaded word is multiplied by `0x01000000`; the product is stored as 32 bits at its own value plus `0x40`.
4. A signed 16-bit value is loaded from an address formed by shifting the previously loaded word left by 25.
5. That halfword is sign-extended and stored as 32 bits at its own extended value plus `0x138`.
6. The extended value is multiplied by `0x10000`.
7. This product is stored as 32 bits at its own value plus `0x10`.
8. A 16-bit zero is stored at the product plus `0x138`.

These are address-derived accesses, not established fields of a typed object. No local null, bounds, alignment, or address-space checks are represented.

### Global capture, independent references, and overlapping accesses

A 32-bit global value is first captured for later use.

The next 32-bit store **does not use that captured value**. Its destination expression separately references the global and adds `0x40`; its value expression separately references the same global.

The contract therefore distinguishes three represented uses:

- The earlier capture.
- The global reference supplying the store’s destination calculation.
- The global reference supplying the stored value.

The evaluation order of the store’s two global references is unspecified. Neither reference is guaranteed to observe the captured value, and the two references are not guaranteed to observe equal values. This is a distinction in the supplied representation, not a guarantee of exactly three physical machine loads; actual load generation and observation semantics are unresolved.

The earlier capture supplies both subsequent operations:

- A 16-bit store writes its low 16 bits at its captured value minus `0x130`.
- An unsigned right shift by 24 extracts its high byte.

The extracted high byte determines a common address by a left shift of 17. At that address, the routine stores the extracted value multiplied by `0x10000` as 32 bits, then performs a 16-bit zero store at the same starting address.

A subsequent 32-bit store uses references to the 32-bit contents at that common address: one supplies the destination address and another supplies the stored value. Their relative evaluation order is unspecified. They need not observe equal values if memory changes between observations, and the representation does not establish a physical load count.

The halfword overwrite is not a complete word clear. Its effect on the word depends on endianness. Earlier stores may also alias globals or later load locations.

### Distinguished symbol and unresolved shift

The distinguished address-valued symbol is converted to an integer. That integer is stored as 32 bits at its own value plus `0x10`.

A byte-sized zero is then stored at the address obtained by multiplying the integer by `0x400` and subtracting `0x130`.

Another global supplies an address calculation: its value is multiplied by `0x10000000`, then reduced by `0x130`. A signed 32-bit word is loaded from that address and represented as being right-shifted by **32**.

This shift has no established portable result for a 32-bit operand. The contract does not replace it with zero, the original operand, or architecture-specific masked-shift behavior.

The represented result is stored as 32 bits at its own value minus `0x130`.

Two other globals are then captured in definite order:

1. The snapshot ultimately written at record offset `0x10`.
2. The snapshot ultimately written at record offset `0x0C`.

These captured values are not later reloaded for record construction.

### Derived addresses and pre-record calls

The unresolved shift result also supplies a longer address derivation. The represented arithmetic adds four using unsigned arithmetic, masks with `0xF0000000`, interprets the masked result as signed, and right-shifts it by 24. The following operations multiply by `0x100`, subtract `0x130` in an unsigned expression, mask with `0xFFFF`, right-shift by four, and multiply by `0x10000`.

The resulting address-like quantity is called the **derived base** in this contract. Its interpretation remains conditional on arithmetic and conversion semantics.

A 32-bit word is loaded from derived base plus `0x10`. That same loaded word supplies two retained quantities:

- The **scaled word**: multiplication by `0x10000`.
- The **shifted base**: left shift by 12.

These are related results, not independent inputs.

Six indirect calls follow in order. The first receives derived base plus scaled word. The second receives scaled word shifted left by five. The remaining four have no represented explicit arguments.

Only after those six calls does the routine load the record destination. It reads an **unsigned 16-bit value** at shifted base plus `0x2E`, then converts that value directly to an address. There is no represented base addition, pointer-width load, alignment adjustment, or validation.

Under the apparent 32-bit address model, the captured destination is therefore between `0x00000000` and `0x0000FFFF`, inclusive.

One more indirect call occurs after this capture and before the record stores. No destination reload follows that call.
