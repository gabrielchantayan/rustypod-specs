# F-89d51119aed6

## Purpose

F-89d51119aed6 repeatedly invokes a callback and inspects the integer stored at the address returned by that callback. A zero value permits progress toward normal completion. A nonzero value diverts execution to two ordered dependency calls, the second of which is marked as non-returning in the supplied static evidence.

The first callback invocation is unconditional: there is no initial comparison between the progress value and its limit. After each zero result, the function increments an inherited progress value and compares it with an inherited limit. If another iteration is needed, it obtains a replacement callback through an inherited pointer holder.

This is an observed control-flow contract, not a claim about application purpose. The callback may be checking a condition, and the nonzero path may represent failure handling, but those interpretations are not established.

## Behavior

### Entry and first invocation

The function enters the callback loop without first checking the progress value against the limit.

Consequently, a progress value already equal to or greater than the limit does not suppress the first callback invocation. The initial callback is used for that invocation regardless of the contents of the callback holder.

If the callback does not return, no later action by this function is reached.

### Result inspection

After the callback returns, the function reads the integer at the returned address and tests it for zero.

This read precedes:

- Either dependency call on the nonzero branch.
- Any progress increment on the zero branch.
- Any decision to complete normally.
- Any load of a replacement callback.

The callback-returned address is not merely a Boolean encoded as a pointer. A separate memory read through that address is required.

### Nonzero result

If the read integer is nonzero:

1. F-f8e663c32a06 is invoked.
2. If that invocation returns normally, F-feee9156a257 is invoked.

No explicit arguments are shown for either dependency call.

F-feee9156a257 is marked as non-returning in the supplied static evidence. The contract therefore records this as a terminal branch under that annotation. It does not invent a normal-return continuation for a dependency that violates the annotation.

There is no visible progress increment or replacement-callback read before these calls. No visible normal return is available on this branch.

If F-f8e663c32a06 itself does not return, the second dependency is not reached. Its behavior, including any state changes, is unknown.

### Zero result

If the read integer is zero, the function increments the progress value by one. It then performs a signed comparison:

- If the limit is less than or equal to the incremented progress value, the function returns normally.
- Otherwise, it loads a replacement callback through the callback holder and begins another iteration.

The completion decision uses the **incremented** value, not the incoming value.

No callback-holder read is required by the visible body when this comparison selects normal completion.

### Replacement callback selection

For a continuing zero-result iteration, the function first reads the base address through the callback holder. It then reads a callable address at a displacement of 64 bytes from that base. The loaded callable address becomes the callback for the next iteration.

This selection occurs after the preceding callback has returned, its result has been read as zero, and the progress comparison has determined that execution must continue.

The initial callback and later callbacks need not be identical. Each continuing iteration repeats the two-read selection process; the visible body does not cache the base address or callback slot across those selections.

A callback or another participant may change memory used by subsequent selections. The static evidence does not justify assuming that such memory remains unchanged. The routine itself provides no visible synchronization or snapshot guarantee.

### Arithmetic boundaries

The recovered progress and limit operations use signed integer interpretation. They must not be silently replaced with unsigned comparisons.

For values whose increment is representable in the recovered signed 32-bit type, the behavior above is directly described by the supplied arithmetic and comparison.

Incrementing the maximum signed 32-bit value is an unresolved boundary. The supplied representation does not establish whether the actual execution wraps, traps, or has another interpretation at that point. Acceptance claims that depend on overflow are therefore documented_only.

There is no separate visible iteration cap, timeout, cancellation check, or arithmetic guard.

## Acceptance examples

These examples are conditional static expectations, not runtime test results. Unless stated otherwise, all accessed addresses are valid, callbacks return normally, integer increments are representable, and no external mutation changes the stated values.

### First invocation despite an already-met limit

Given progress 10 and limit 3:

- The initial callback is invoked.
- If its returned integer is zero, progress becomes 11.
- The function returns normally.
- The callback holder is not read by the visible body.

An implementation that returns before invoking the initial callback would not match this behavior.

### Completion on the first zero result

Given progress 4 and limit 5, with the initial callback returning an address containing zero:

- Exactly one callback invocation occurs.
- Progress is incremented to 5.
- Normal completion follows without loading a replacement callback.

### Multiple zero results

Given progress 2 and limit 5, with every invoked callback returning an address containing zero:

- The initial callback produces the first zero result, advancing progress to 3.
- The callback holder and the slot at base plus 64 bytes are read to select the second callback.
- A second zero result advances progress to 4, followed by another callback selection.
- A third zero result advances progress to 5 and causes normal completion.
- There is no callback-selection read after the third result.

### Signed comparison

Given progress −3 and limit −1, with zero results throughout:

- The first result advances progress to −2, which is still below the limit.
- A replacement callback is selected.
- The second result advances progress to −1 and causes normal completion.

Treating these values as unsigned would not preserve the established comparison semantics.

### Immediate nonzero result

Given any progress and limit, if the initial callback returns an address containing −7:

- F-f8e663c32a06 is invoked.
- F-feee9156a257 is reached only if the first dependency returns.
- No progress increment or replacement-callback read occurs before those calls.

The same branch is selected for a stored value of 1.

### Callback-slot mutation

Given that another iteration is required, if the preceding callback changes the callable address in the subsequently read slot, that later slot read supplies the changed address for the next invocation.

This expectation requires the changed storage to remain valid and visible to the read. It does not establish any concurrent-memory ordering guarantee.

### Unreadable holder on a completing iteration

Given progress 4, limit 5, and an initial callback returning a readable zero integer, normal completion does not require reading the callback holder.

This does not make an unreadable holder generally safe: it is accessed if another iteration is required.
