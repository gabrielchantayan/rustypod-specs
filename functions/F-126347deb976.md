# F-126347deb976

## Purpose

F-126347deb976 performs a bounded, cursor-relative search across an indexed collection of objects and a corresponding indexed collection of 32-bit values.

For each candidate, it invokes an eligibility operation. If that operation returns nonzero, it invokes a second operation on the same object with the same value. A nonzero result from the second operation ends the search and causes the selected index to be written to the caller’s cursor.

The return value is a 64-bit composite containing the original context argument in its upper 32 bits and the final second-operation result in its lower 32 bits.

These statements describe behavior supported by the supplied static representation. The interpretation as a rotating or round-robin selection mechanism is inferred intent, not an additional guarantee.

## Interface

### Inputs

The function has three inputs:

1. **Context**
   - Represented as a 32-bit integer used as an address-bearing value.
   - A collection descriptor begins at byte offset 32 from this address.
   - The 32-bit word at that offset is also used as the base address of an array of object pointers.
   - The descriptor’s other contents, if any, are not established.

2. **Value-array reference**
   - A pointer to a readable 32-bit word.
   - That word supplies the base address of an array of 32-bit values.
   - The reference is dereferenced separately for each visited candidate. The array base is not captured once for the entire search.

3. **Cursor reference**
   - A pointer to a 32-bit signed integer.
   - Its initial contents establish the starting position.
   - The function reads this value before calling any dependency.
   - On a successful second operation, the function writes the selected index to this reference.

The two references are not required by the visible implementation to be distinct. Any aliasing must nevertheless leave all accesses valid. Aliasing can make writes through one access path visible through another.

### Required accessible layout

For a candidate index, the visible accesses require:

- A readable 32-bit object-array base at context offset 32.
- A readable 32-bit object pointer at a byte displacement of four times the candidate index from that base.
- A readable 32-bit value-array base through the value-array reference.
- A readable 32-bit value at the same indexed displacement from the value-array base.
- A readable dispatch-table pointer in the first word of the selected object.
- A callable entry at dispatch-table byte offset 20 for the eligibility operation.
- When eligibility is nonzero, a callable entry at dispatch-table byte offset 28 for the second operation.

Both operations receive the selected object address and the selected 32-bit value. The value is passed as a raw word; no signedness, pointer interpretation, or ownership meaning is established.

The source representation uses four-byte array entries and address-bearing words. This supports a 32-bit address model for the described accesses. It does not establish byte order or a portable native-pointer layout.

### Output

The result is a 64-bit bit pattern:

- Bits 63–32: the original context argument’s 32-bit representation.
- Bits 31–0: the final second-operation result’s 32-bit representation, or zero if no second operation returns nonzero.

This is concatenation of two words, not an arithmetic addition and not sign extension of the lower word. A negative second-operation result remains nonzero and is retained in the lower word without changing the upper word.

For defined, normally completing execution:

- The initial cursor must be readable even if the collection is empty.
- The cursor must be writable whenever a second operation can return nonzero.
- Every invoked dispatch entry must support the observed two-argument call and 32-bit result convention.
- Objects, tables, arrays, and references must remain usable for all subsequent accesses that execution reaches.
- Relevant index and address calculations must have valid semantics in the target execution environment.

There are no visible null, bounds, alignment, or dispatch-entry checks. The function does not report invalid inputs through a dedicated error result.

## Behavior

### Initial observation and count acquisition

The function first reads the cursor into a local search position. Later changes to the cursor storage do not replace that captured position.

It then calls F-0c14ee61f55d with the address at context offset 32. The returned 32-bit word is interpreted as an unsigned candidate count and retained for the entire search.

The count dependency may have side effects. In particular, the object-array base used during candidate processing is read after this call, not before it. The supplied evidence does not establish that the dependency preserves the cursor, collection descriptor, value-array reference, or any other reachable state.

The accumulated second-operation result starts at zero, and the attempted-candidate count starts at zero.

### Candidate order

A candidate is visited only while:

- Fewer candidates have been attempted than the captured unsigned count; and
- No second operation has yet returned nonzero.

The position advances before any candidate is accessed:

- If the current position compares equal to the captured count minus one, the next position is zero.
- Otherwise, the next position is the current position plus one.

Thus, for a positive count and an initial cursor within the collection, the search starts at the successor of that cursor. It does not start at the cursor itself.

With stable storage and an ordinary valid initial cursor, a fully unsuccessful search visits every index once, wrapping at the end, and visits the original cursor’s index last.

There is no general normalization of an arbitrary cursor. A cursor larger than the last valid index is not reduced modulo the count. A negative cursor is not generally rejected or repaired.

The wrap comparison uses the unsigned count. The supplied type representation therefore compares the position’s corresponding unsigned value against the unsigned count-minus-one value. For example, an initial position of −1 advances to zero for a count of three because the comparison is false and the signed increment is representable. This is an observable edge case, not evidence of general invalid-cursor support.

For a zero count, no position advancement or candidate access occurs. The count-minus-one expression is not needed by the loop body on that path.

### Per-candidate reads and calls

For each visited index, the observable order is:

1. Read the object-array base from context offset 32.
2. Read the selected object pointer from that array.
3. Read the value-array base through the value-array reference.
4. Read the selected 32-bit value.
5. Resolve and invoke the object’s dispatch entry at byte offset 20.
6. If its result is nonzero, resolve and invoke the object’s dispatch entry at byte offset 28.
7. If the second result is nonzero, write the selected index through the cursor reference.

The selected object pointer and selected value are retained between the two calls. They are not fetched again from their arrays before the second operation.

The dispatch-table pointer, however, is obtained again from the selected object for the second call. Consequently, a first operation that changes the object’s dispatch-table pointer can affect which second operation is invoked.

If the eligibility operation returns zero, the second operation is skipped. The search continues without a cursor write by this function.

If eligibility is nonzero but the second operation returns zero, the search also continues without a cursor write by this function.

Any nonzero second-operation result is accepted. The function does not distinguish positive success values from negative error-like values.

### Termination and state retention

A nonzero second-operation result causes a cursor write before normal return. No further candidate is processed.

Otherwise, the function attempts at most the captured count of candidates. On exhaustion, its lower return word is zero.

On an unsuccessful search, the function itself does not write the cursor. This does **not** guarantee that the cursor’s final contents equal its initial contents: a dependency or callback may have modified the same storage.

The captured count does not change if dependencies modify the collection descriptor. In contrast, the object-array base and value-array base are reread for subsequent candidates. Later attempts can therefore observe changed arrays while still using the original count and local search position.

No synchronization, mutation detection, rollback, or retry behavior is visible.

## Side effects

The function’s only explicit data write is the successful-candidate index written through the cursor reference. That write occurs after the second operation returns nonzero.

Other observable effects include:

- One call to F-0c14ee61f55d.
- Up to the captured count of eligibility calls.
- Up to the captured count of second-operation calls, each conditional on nonzero eligibility.
- Reads of the references, collection storage, selected objects, and dispatch tables in the order described above.

No allocation, deallocation, reference-count adjustment, or explicit ownership transfer is visible in F-126347deb976 itself. This does not establish whether its dependencies allocate, release, retain, or invalidate any object or value.

In particular, a first operation that invalidates the selected object can make the subsequent dispatch-table read invalid. Callers cannot assume such invalidation is safe merely because no ownership operation is visible in the outer function.

If a dependency does not return normally, the evidence does not establish any cleanup, cursor commit, or composite return.

- The cursor becomes zero.
- No other candidate is visited.
- The lower return word is seven.

### Exhausted search

Given a count of three and an initial cursor of one, the candidate order is two, zero, one.

If every eligibility result is zero:

- No second operation is called.
- The cursor is not written by this function.
- The lower return word is zero.

The same candidate order and lower return word apply if eligibility is always nonzero but every second operation returns zero.

### Nonzero negative result

Given a selected candidate whose second operation returns the 32-bit representation of −1:

- That candidate is accepted.
- Its index is written to the cursor.
- The lower return word is all one bits.
- The upper return word remains the original context word.

### Single candidate

Given a count of one and an initial cursor of zero, the next candidate is zero.

Exactly one eligibility call occurs. A second-operation call occurs only if eligibility is nonzero. A zero second-operation result ends the search by exhaustion, not by success.

### Mutation between the two operations

If eligibility replaces the selected object’s dispatch-table pointer and returns nonzero, the second operation is resolved through the replacement table.

If eligibility instead changes the corresponding object-array slot or value-array entry, those changes do not replace the already retained object pointer or value for that second call.

### Mutation before a later candidate

If an unsuccessful candidate changes either array base, the next candidate uses the changed base when that base is reread. The iteration bound remains the count captured earlier.

### Invalid initial cursor

Given a count of three and an initial cursor of five, the next computed position is six, not zero.

If the derived array accesses are invalid, normal completion is not promised. No bounds-error result is established.
