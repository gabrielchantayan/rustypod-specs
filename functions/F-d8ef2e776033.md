# F-d8ef2e776033

## Purpose

F-d8ef2e776033 conditionally prepares shared state, classifies a 32-bit selector, and produces a 32-bit output for recognized selectors.

There are 39 recognized selectors in two contiguous groups. Both groups cause selector conversion, shared-object processing, and result extraction. Only the first group consults a byte in the caller’s context and can request an additional operation.

Preparation occurs before selector classification. An unsupported selector therefore does not imply an absence of effects: preparation may write memory and invoke dependencies before the function returns zero.

This contract describes behavior established by the supplied static representation. The application meanings of the selectors, shared state, and extracted result are not established.

## Interface

### Arguments

| Argument | Representation | Direct use |
|---|---|---|
| Context address | 32-bit address-bearing value | For first-group selectors, identifies a byte at offset `0x18`, read after shared-object processing. |
| Unused argument | 32-bit value | Neither directly inspected nor forwarded. |
| Selector | 32-bit value | Classified by exact value; forwarded unchanged to F-cb0d857ba909 when recognized. |
| Output address | Pointer to a writable 32-bit location | Receives the extraction result on a normally completed recognized-selector path. |

The context need not support a direct access by this function for unsupported or second-group selectors. For a first-group selector, the byte at context offset `0x18` must be readable when that access occurs.

The output location is not directly accessed for unsupported selectors. On a recognized path, it must support a 32-bit write when extraction has returned.

These are requirements for this function’s own accesses. They do not establish the requirements imposed by dependencies or by aliasing with shared storage.

### Normal return

The return value is 32 bits:

- `0` for unsupported selectors, after any preparation effects.
- `1` for recognized selectors whose processing and output store complete normally.

The return is not the extracted result. Extraction may produce zero while the function writes zero and returns `1`.

There is no established error return for an invalid address, failed initialization, dependency failure, or unsuccessful output access.

Those destinations are not contractually collapsed into a single object.

## Behavior

### Preparation decision and unconditional captures

The function first inspects bit zero of the guard storage addressed through the guard-address source.

If that bit is set, the preparation attempt and its associated captures, stores, and calls are skipped. Selector classification follows.

If that bit is clear, the function calls F-b255b26284e6 with an address obtained from the guard-address source. Once that call returns, two shared values are captured in this order:

1. Preparation operand B.
2. The shared-object reference.

Both captures occur even if F-b255b26284e6 returned zero. They reflect the shared values available after the call, not necessarily the values present on entry.

A zero result skips the preparation stores and the two remaining preparation dependencies. Selector classification still proceeds. In particular, zero is not propagated as a preparation error that prevents recognized-selector processing.

### Authorized preparation and access ordering

Any nonzero result from F-b255b26284e6 authorizes the following ordered effects:

1. A 32-bit value from the initial first-word source is written at offset zero through a **separately read shared-object reference**.
2. A 32-bit zero is written at offset four through the **previously captured shared-object reference**.
3. Preparation operand A is read, and F-804adc29bbfb is called with:
   - the captured shared-object reference;
   - the newly read preparation operand A;
   - the previously captured preparation operand B.
4. After F-804adc29bbfb returns, the guard-address source is read for the address passed to F-d08d3ca17b81.
5. Selector classification follows after that call returns.

The first store’s destination is not specified as the captured reference. Only the second store and the first argument to F-804adc29bbfb explicitly reuse that capture. Equality of the separately read and captured references requires an additional stability assumption.

The initial first-word value is read for the first store. The representation does not establish a relative evaluation order between that value read and the separate destination-reference read.

Preparation operand A is not captured alongside operand B. Its read follows both stores, so earlier writes or dependency effects may affect the value supplied as operand A where aliasing permits. Operand B remains the value captured before the stores.

The guard address supplied to F-d08d3ca17b81 is obtained after F-804adc29bbfb returns. It is not guaranteed to equal the address used for the initial guard inspection or passed to F-b255b26284e6.

The return values of F-804adc29bbfb and F-d08d3ca17b81 do not control subsequent branches in this function.

No explicit store sets or clears the guard as part of this sequence. This does not exclude a guard change through aliasing or through dependency effects.

### Selector classification

All other 32-bit selector values are unsupported. Classification is exact; the function does not mask, truncate to a smaller selector width, normalize, or arithmetically transform the selector before recognition or forwarding.

For unsupported selectors, the function performs no selector-conversion, processing, context-controlled, or extraction call. It performs no direct output-address store and returns zero.

These exclusions apply after preparation. They do not undo preparation effects or constrain dependency effects on memory aliased by the output address.

### Common recognized-selector processing

For both recognized groups, F-cb0d857ba909 receives the original 32-bit selector.

After conversion returns, the shared-object reference is read for the first argument to F-151ab4bfe553. Its second argument is the 32-bit conversion result. Thus, a change to the shared-object reference during conversion can affect which object is processed.

The result of F-151ab4bfe553 does not select a success or failure branch. There is no direct validation of the converted value.

After the applicable group-specific behavior, the shared-object reference is read for a call to F-ecd1af0519f9. Its 32-bit result is stored at the output address, and the function returns `1`.

The extraction object need not equal the processing object: dependencies may change the shared-object reference between the relevant reads.

### First-group context behavior

For selectors `0x6F81` through `0x6F9A`, exactly one context byte is directly read at offset `0x18`, after F-151ab4bfe553 returns.

If that byte is zero, the function proceeds to extraction without calling F-abb7a1ff7712.

If that byte is nonzero, the function first reads the shared-object reference for a call to F-abb7a1ff7712, passing zero as its second argument. Extraction follows after that call returns.

Every nonzero byte qualifies, including `0x01`, `0x80`, and `0xFF`. The condition does not distinguish positive from negative interpretations of a byte.

The relevant value is the byte **at the time of this read**, not at function entry. Conversion, preparation, processing, or other permitted effects may change the byte before it is sampled.

The additional call’s result is not used to choose subsequent behavior.

### Second-group behavior

For selectors `0x6F9B` through `0x6FA7`, processing proceeds directly to extraction.

There is no direct context-byte read and no call to F-abb7a1ff7712 by this path, irrespective of the context’s contents.

## Side effects

### Direct reads and writes

The established direct writes are:

- A 32-bit initialization value at offset zero through a separately read object reference, when preparation is authorized.
- A 32-bit zero at offset four through the captured object reference, on the same preparation path.
- A 32-bit extraction result at the output address for recognized selectors that complete normally.

These stores do not establish a complete object layout, an eight-byte total object size, or a full-object clearing operation.

Direct reads include guard inspection, the preparation captures and later preparation-source reads described above, object-reference reads for recognized-selector calls, and the conditional one-byte context read. No direct output-value read is shown.

### Aliasing and ordering consequences

No non-aliasing restriction is established.

Preparation destinations may overlap shared sources. Consequently, a store can affect a value read later, including preparation operand A or a later object or guard reference. Already captured operand B and the captured object address are not replaced merely because their source storage changes.

The output location may overlap the context, an object, or shared storage. The output store occurs after extraction and all earlier listed calls. An overwrite through that store therefore cannot change the context byte already sampled by this invocation, although it may affect subsequent activity.

The absence of a direct output store on an unsupported path does not promise that the output location’s contents remain unchanged: another direct store or a dependency could affect aliased storage.

### Ownership, failure, and concurrency

No explicit allocation, deallocation, ownership transfer, or reference-count operation is established.

Passing an address to a dependency does not prove that the dependency borrows it, retains it, releases it, or preserves related globals. Such behavior remains unknown.

No rollback is shown. Effects completed before an invalid access, abnormal dependency exit, or other failure are not explicitly undone. Normal return guarantees apply only when the relevant calls and accesses complete.

The guard pattern suggests initialization intent, but does not establish mutual exclusion, memory-order guarantees, exactly-once preparation, or support for concurrent callers.

### Widths and address boundaries

The selector, extracted result, normal return, and explicit word stores are 32 bits. The context access is one byte. Offset `0x18` is 24 bytes; the second preparation store is four bytes beyond the captured object address.

There is no explicit bounds, null, alignment, or address-overflow validation. Applicable address computations and accesses must be valid under the target environment’s rules. The representation does not establish portable behavior for overflow, inaccessible storage, or misalignment.

Byte order is not established. The contract specifies word values and byte offsets rather than a byte-by-byte encoding of the 32-bit stores.

## Acceptance examples

The following are conditional static acceptance cases, not executed tests. Unless otherwise stated, calls return normally and all relevant accesses are valid.

### Unsupported boundary selectors

For `0x6F80` or `0x6FA8`, preparation is evaluated first. No selector conversion, processing, context access, additional operation, extraction, or direct output-address store follows. The normal return is zero.

Preparation effects remain permitted.

### First-group lower boundary with a sampled zero byte

For selector `0x6F81`, a set guard low bit at the initial inspection, and a context byte that is zero **when read after processing**:

- Preparation is skipped.
- Conversion receives `0x6F81`.
- Processing receives the conversion result.
- The context byte is read after processing returns.
- F-abb7a1ff7712 is skipped.
- Extraction supplies the stored 32-bit output, and the return is `1`.

A zero context byte only at entry is insufficient to require this outcome.

### Entry-zero byte changed before sampling

For selector `0x6F81`, suppose the context byte is zero at entry but becomes `0x80` during conversion or processing and remains so until the context read.

F-abb7a1ff7712 must then be called with second argument zero before extraction. An initially set guard bit does not prevent this outcome.

### First-group upper boundary

For `0x6F9A`, a sampled context byte of `0x80` requires the additional operation between processing and extraction. The extraction result is stored, and the normal return is `1`.

### Second-group boundaries

For either `0x6F9B` or `0x6FA7`, conversion, processing, and extraction occur without a direct context read or additional operation. A context address unsuitable for dereferencing does not by itself invalidate this function’s direct accesses on that path, provided it is not otherwise accessed through aliasing or dependencies.

### Zero preparation-attempt result

With a clear initial guard low bit and a zero result from F-b255b26284e6, operand B is captured first and the shared-object reference second.

Neither initialization store occurs. F-804adc29bbfb and F-d08d3ca17b81 are skipped. A recognized selector still proceeds normally.

### Distinct preparation observations

If the post-attempt captured object reference and the separately read first-store reference differ, the first initialization value is written through the latter. The zero at offset four and the first argument to F-804adc29bbfb use the captured reference.

This case describes the required behavior if such observations occur; it does not establish that concurrent mutation is supported.

### Post-store operand and post-call guard address

If the two preparation stores affect storage subsequently read as operand A, F-804adc29bbfb receives the value observed after those stores, not an entry-time value.

If F-804adc29bbfb changes the guard-address source, F-d08d3ca17b81 receives the address obtained after that change, not a saved earlier guard address.

### Successful preparation with an unsupported selector

Authorized preparation performs both stores, then F-804adc29bbfb, then F-d08d3ca17b81. An unsupported selector subsequently returns zero without a direct output-address store.

### Zero extraction result

For any recognized selector, extraction returning zero results in a 32-bit zero output and normal return `1`.
