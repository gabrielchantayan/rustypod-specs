# F-ef7617e95a4c

## Purpose

F-ef7617e95a4c recognizes a supplied selector using up to two comparisons and, for a recognized selector, conditionally invokes an indirect handler associated with a supplied object.

Its normal return is a 32-bit status value:

- **0:** neither selector comparison returned zero.
- **1:** a selector comparison returned zero, whether dispatch was suppressed or a selected handler was invoked and returned normally.

A return value of 1 establishes recognition, not successful application-level processing. The function does not inspect or propagate the selected handler’s return value.

The fixed selector labels suggest next-contact and previous-contact operations. That interpretation is **inferred intent**, not an established description of the selectors’ contents or the handlers’ effects. This contract uses **next path** and **previous path** only to distinguish the two branches.

### Address representation

The dispatch lookup uses an integer-based address calculation:

- Read the object’s initial **32-bit integer** field.
- Add the selected displacement, 0x124 or 0x128, in that integer representation.
- Convert the resulting integer to an address from which a callable target is read.
- Invoke the target obtained from that slot.

This is not native-width pointer arithmetic. The representation does not first load a native-width table pointer and then advance that pointer by an element count. It shows no multiplication by the size of a callable pointer.

The integer displacements are 292 and 296. Their difference is four. That difference does **not** independently establish the width of a callable slot, the native pointer width, or a complete dispatch-table ABI.

Machine-level behavior for integer overflow and integer-to-pointer conversion is **documented_only**. This contract does not assume wrapping arithmetic, truncation, sign extension, zero extension, or a particular mapping from integer values to valid addresses.

### Preconditions for normal completion

The requirements depend on the selected path:

- Each comparison that is reached must accept the original selector and the applicable fixed operand and return normally.
- The shared distinguished-value location must be readable when referenced.
- If dispatch is required, the object must support the initial 32-bit field read.
- The integer address calculation and subsequent conversion must yield an accessible callable-slot address under the execution environment’s rules.
- The selected slot must supply a callable target compatible with the invocation shown.
- The selected handler must accept the original object reference and request argument and return normally for this function to return normally afterward.

An unrecognized selector does not cause this function to read the object’s initial field. A recognized selector whose equality check suppresses dispatch likewise avoids that read. These path-specific facts do not establish that arbitrary invalid references are safe: dependency behavior remains unknown.

## Behavior

### Comparison order and recognition

The function first invokes **D-01** with the original selector value and the fixed next-path operand.

Only equality of the comparison result to zero matters. A negative nonzero result and a positive nonzero result have the same branch-selection effect.

After the first D-01 call returns, the function reads the shared 32-bit distinguished value into a retained snapshot. This read precedes selection of the branch based on the first comparison result.

If the first result is zero:

- The next path is recognized.
- No comparison against the previous-path operand occurs.
- Execution proceeds to the next-path equality check.

If the first result is nonzero, the function invokes D-01 again, using the original selector value and the fixed previous-path operand.

If the second result is nonzero, the function returns 0. It performs no object-field read or indirect dispatch of its own.

If the second result is zero, the previous path is recognized.

The next path therefore has precedence. If D-01 would return zero for either operand, a zero result from the first call prevents the second call entirely. This does not establish that the two operands are distinct or that D-01 implements any particular comparison algorithm.

### Dispatch suppression

For either recognized path, equality between the request argument and the applicable distinguished value suppresses dispatch. Suppression returns 1 without reading the object’s initial field.

The two paths use different source-visible observations:

| Recognized path | Value used for equality |
|---|---|
| Next | A reference to the shared distinguished value within the next branch |
| Previous | The retained snapshot captured after the first comparison and before the second |

The snapshot is read even when the first comparison recognizes the next path or both comparisons ultimately fail.

For the previous path, changes made to the shared value during the second D-01 call do not replace the retained snapshot. The request is compared against the earlier captured value.

For the next path, the supplied representation refers to the shared location again rather than using the retained snapshot. This establishes the distinction at the representation level. It does not establish volatile access, atomic access, synchronization, or two separate physical memory transactions.

No dependency is assumed to preserve shared state. In particular:

- The first D-01 call may affect the value captured afterward.
- The second D-01 call may affect the shared location, the object, or other dispatch-related state before the previous-path dispatch lookup.
- The function shows no restoration of dependency-modified state.

### Dispatch lookup and invocation

When a recognized path’s equality check fails, the function reads the object’s initial 32-bit integer address-bearing field.

The selected integer displacement is:

| Path | Displacement added to the 32-bit field | Handler role |
|---|---:|---|
| Next | 0x124, or 292 | D-02 |
| Previous | 0x128, or 296 | D-03 |

The addition occurs in the displayed integer representation before conversion to a callable-slot address. The offsets describe direct numeric displacements, not indices subject to implicit pointer-element scaling.

After conversion, the function reads a callable target from the selected address and invokes it with:

1. The original object reference.
2. The original 32-bit request argument.

D-02 and D-03 identify the two runtime-selected handler roles. They do not identify resolved implementations.

No object field or callable slot is shown being cached before the selector comparisons. Consequently, dependency changes to still-valid object or dispatch storage before lookup can affect the target subsequently selected.

The function performs no visible null check, address-range check, slot-bound check, target validation, or request-range validation. The behavior of invalid address calculations, invalid storage accesses, or incompatible callable targets is not established.

### Completion

If the selected handler returns normally, F-ef7617e95a4c returns 1.

It does not:

- Inspect the handler’s result.
- Retry dispatch.
- Invoke the other handler as a fallback.
- Recheck the distinguished value.
- Perform visible cleanup or state restoration after the call.

A handler-specific failure indication, if returned normally, does not change the status produced here.

## Side effects

### Direct reads and writes

The supplied representation shows reads, comparisons, integer address calculation, and dependency calls. It shows no direct writes to the object, dispatch storage, shared distinguished value, selector storage, or caller-provided output storage.

This does not establish that the overall operation is side-effect-free. The dependencies may mutate or invalidate state.

The important source-visible ordering is:

1. First D-01 call.
2. Shared-value snapshot read.
3. Either the next-path equality check, or the second D-01 call.
4. For a recognized path, its applicable equality check.
5. If equality fails, the object’s initial 32-bit field read.
6. Integer displacement addition and conversion to a slot address.
7. Callable-target read.
8. Selected handler invocation.

On an unrecognized selector, execution ends after the second comparison without dispatch lookup.

## Acceptance examples

These are conditional expectations from static evidence, not executed tests.

### Next path recognized; dispatch suppressed

Given that the first D-01 call returns zero and the request equals the value referenced by the next-path equality check:

- The shared snapshot read still occurs after the first call.
- No second comparison occurs.
- The function does not read the object’s initial field or a callable slot.
- No handler is invoked.
- The normal result is 1.

### Next path recognized; dispatch required

Given that the first comparison returns zero, the next-path equality check fails, all required storage and address operations are valid, and the selected handler returns normally:

- The initial object field is read as a 32-bit integer.
- The integer displacement 292 is added before conversion to a slot address.
- The callable target is read from that address.
- D-02 receives the original object reference and unchanged request.
- The function returns 1, regardless of the handler’s normal return value.

No expected numeric slot address is specified if the integer addition overflows or its conversion is not established.

### Previous path uses the retained snapshot

Given:

- The first comparison returns nonzero.
- The subsequent snapshot is 10.
- The second comparison returns zero.
- The request is 11.
- Dispatch requirements are satisfied and the handler returns normally.

The function dispatches through the address calculated using integer displacement 296, forwards request 11 unchanged, and returns 1.

### Second comparison changes shared state

Given that the snapshot is 10 and the second D-01 call changes the shared distinguished value to 11 before returning zero:

- A request of 10 suppresses previous-path dispatch and returns 1.
- A request of 11 requires previous-path dispatch, despite matching the newer shared value.

The second expectation assumes valid dispatch state and normal completion of the selected handler.

### Neither selector is recognized

If both comparisons return nonzero:

- The function returns 0.
- Its snapshot read still occurred between the calls.
- It performs no object-field read or indirect handler call.

Equality of the request with the snapshot or current shared value does not change this result.

### Recognition precedence

If the first comparison returns zero, the next path wins. A hypothetical zero result for the previous operand is irrelevant because that comparison is not performed.

### Request boundaries

For requests of 0, −1, −2,147,483,648, or 2,147,483,647, there is no visible request arithmetic, normalization, or clamping.

Equality with the applicable distinguished value suppresses dispatch. Otherwise, a recognized path forwards the same 32-bit request unchanged, subject to valid dispatch state.

### Invalid or unestablished addressing

If dispatch is required but the object field is inaccessible, the integer sum cannot be interpreted as a valid slot address, or the selected target is not callable, no defined recovery is established. Return value 0 is not an invalid-dispatch-state result.
