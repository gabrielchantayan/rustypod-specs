# F-36e5260b6de6

## Purpose

F-36e5260b6de6 conditionally removes a selected node from a linked container, performs color-dependent structural repair, calls a dependency on the removed node’s payload, and places the removed node on a container-maintained chain. It delivers a four-byte result through caller-provided storage.

The observed links support a tree interpretation: nodes have parent, left-child, and right-child references; a separate header holds root and extreme-node references. Ordered-tree deletion and red-black repair are inferred intent, not established correctness guarantees. In particular, repair sometimes uses a parent or relocated successor rather than a null replacement, and dependency behavior is unavailable.

This contract specifies direct behavior and visible call boundaries. It does not assume that dependencies preserve globals, container fields, node contents, or storage lifetime.

## Interface

The function accepts three arguments and has no explicit return value.

| Argument | Representation | Role |
|---|---|---|
| Result destination | Address of writable four-byte storage | Receives the final result word on normal completion |
| Container | Address represented by a 32-bit value | Supplies the header, removed-node chain head, and count |
| Selection slot | Address of readable four-byte storage | Supplies the initial reference and, on the removal path, a separately reread removal target |

The incoming result destination is not directly read. Its only direct write occurs at completion, including on the bypass path.

## Behavior

### 1. Initial observations and bypass

The function first reads the selection slot into a four-byte result temporary, then reads the container’s header reference into a separate four-byte temporary. It calls F-4ff56f8ab90f with the addresses of those two temporaries.

If that call returns nonzero, the function rereads the container’s header reference, uses that newly read value as the result, writes the result destination, and finishes.

The bypass path performs no direct structural removal, payload call, chain insertion, or count decrement. Effects of F-4ff56f8ab90f are not excluded.

If the call returns zero, the function calls F-af78fbc288e3 with the address of the result temporary. It then rereads the selection slot to obtain the node to remove.

Thus, the eventual result and removal target come from distinct observations:

- The result is the result temporary after preparation, subject to any subsequent indirect mutation.
- The removal target is the selection slot’s value reread after preparation.

They need not identify the same node.

### 2. Structural removal

The function first examines the selected node’s left child, then the right child as needed to distinguish the following cases. The selected node remains the node ultimately passed to payload handling and placed on the chain.

#### No children

The selected node’s parent is read and compared with the container’s current header reference.

If they match, the function writes, in order:

1. The saved parent reference into the header’s rightmost field.
2. The saved parent reference into the header’s leftmost field.
3. Zero into the header’s root field.

The header reference is reread to locate these fields. In the ordinary nonoverlapping case, both extrema therefore become the header itself.

Otherwise, the parent’s left-child field is inspected. If it equals the selected node, that field is cleared; otherwise, the parent’s right-child field is cleared. Each clearing is represented by four one-byte zero stores in increasing address order.

The function then examines the corresponding header extreme: leftmost for the left-child case, rightmost otherwise. If that extreme equals the selected node, it is replaced with the saved parent reference.

The parent becomes the repair reference. This branch does not use a null repair reference.

#### Exactly one child

The surviving child replaces the selected node.

First, the child’s parent is assigned the selected node’s parent. The function then examines the header root:

- If it identifies the selected node, the root becomes the child.
- Otherwise, the selected node’s parent is inspected. Its left link is replaced if that link identifies the selected node; otherwise, its right link is replaced.

Header extrema are updated conditionally, with the leftmost check preceding the rightmost check:

- If leftmost identifies the selected node, it becomes the selected node’s parent when the selected node has no right child. Otherwise, it becomes the terminal node reached by following left links from the replacement child.
- If rightmost identifies the selected node, it becomes the selected node’s parent when the selected node has no left child. Otherwise, it becomes the terminal node reached by following right links from the replacement child.

These are the actual tests, not a guarantee of correcting arbitrary inconsistent extrema.

The surviving child becomes the repair reference.

#### Two children

The function enters the selected node’s right subtree and follows left-child links to their terminal node. This node is called the successor here solely to describe its structural position. Its right child, possibly null, is the replacement at its former location.

The direct changes occur in this order:

1. The selected node’s left child receives the successor as its parent.
2. The successor receives the selected node’s left-child reference.
3. If the successor is the selected node’s immediate right child, its nonnull right child receives the successor as parent.
4. Otherwise:
   - The successor’s nonnull right child receives the successor’s former parent.
   - The successor’s former parent receives that right child in its left-child field.
   - The successor receives the selected node’s right-child reference.
   - That right child receives the successor as parent.
5. The header root, or the selected node’s incoming parent link, is redirected to the successor. For a nonroot node, the parent’s left field is used if it matches the selected node; otherwise, its right field is used.
6. The successor receives the selected node’s parent.
7. The successor’s original color byte is saved.
8. If the successor’s former right child is null, the successor itself becomes the repair reference. Otherwise, that child remains the repair reference.
9. The successor receives the selected node’s color.
10. The selected node receives the saved successor color.

The selected node is still the removed node. No payload transfer between the selected node and successor is directly visible. This branch contains no direct header-extreme update.

### 3. Repair entry and exit

Repair is skipped if the repair reference equals the container’s current header reference. Otherwise, repair is entered only when the removed node’s current color byte is nonzero.

For two-child removal, that gate examines the successor’s former color, now stored in the removed node.

At each repair iteration, the function first examines the current header root. It reaches the common repair exit if the repair reference is the root or, if not the root, its color is not exactly 1.

The common repair exit writes color 1 to the current repair reference, then continues to chain preparation and payload handling. Skipping repair entirely does not perform this common-exit color write.

### 4. Directional repair behavior

The function reads the repair reference’s parent and tests whether the repair reference equals that parent’s left child.

- In the left-child direction, the sibling is the parent’s right child. The sibling’s near child is its left child; its far child is its right child.
- In the opposite direction, the sibling is the parent’s left child. The near child is its right child; the far child is its left child.

The opposite direction is selected whenever the parent’s left child does not match; membership as the right child is not separately validated.

#### Exact visible call mapping

| Repair stage | Repair reference is parent’s left child | Opposite direction |
|---|---|---|
| Color-0 sibling adjustment | F-c357ce363f8c with container and current parent | F-6ca634842830 with container and current parent |
| Near-child adjustment | F-6ca634842830 with only container shown | F-c357ce363f8c with only container shown |
| Final adjustment | F-c357ce363f8c with container and current parent | F-6ca634842830 with container and current parent |

The parent argument at two-argument sites is read from the current repair reference’s parent field at the call site. No second argument may be inferred for the one-argument sites.

#### Missing sibling

If the sibling is null, the current repair reference is colored 0, the parent becomes the repair reference, and the loop repeats.

#### Color-0 sibling

A nonnull sibling with color 0 is colored 1. The repair reference’s current parent is colored 0, then the direction-specific color-0 sibling dependency is called.

After return, the function rereads the repair reference’s parent and that parent’s corresponding sibling field. If the sibling is now null, the current repair reference is colored 0 and repair advances to the reread parent. Otherwise, processing continues with the reread sibling.

#### Both sibling children absent or color 1

The near child is examined first. If it is absent or exactly color 1, the far child is examined. If both children are absent or exactly color 1, the sibling is colored 0, the current parent becomes the repair reference, and the loop repeats.

Absent children satisfy these particular black-like tests without dereferencing null.

#### Near-child adjustment and its null-sibling exit

Otherwise, the far child is examined again. If it is absent or exactly color 1:

1. The near child, when present, is colored 1.
2. The sibling is colored 0.
3. The direction-specific near-child dependency is called, with only the container argument shown.
4. The repair reference’s parent is reread.
5. That parent’s corresponding sibling field is reread.

If this newly read sibling is null, the function immediately takes the common repair exit. It colors the current repair reference 1 and proceeds to chain preparation and payload handling.

This path performs no final sibling-color assignment, no final parent or far-child recoloring, and no final adjustment call. It also does not advance the repair reference to its parent. Dependency-induced structural changes therefore affect control flow directly.

If the reread sibling is nonnull, processing continues to the final adjustment.

#### Final adjustment

The sibling receives the current parent’s color, then the current parent is colored 1. The sibling’s far child, if present, is colored 1. The direction-specific final dependency is called with the container and current parent.

The function then takes the common repair exit, coloring the current repair reference 1.

Color values are not generally normalized. The entry gate accepts any nonzero removed-node color, but loop continuation and child tests require exactly 1, while the initial sibling adjustment requires exactly 0.

### 5. Chain preparation, payload call, and completion

After structural removal and any repair, the function:

1. Reads the container’s chain head and writes it into the removed node’s +12 field.
2. Calls F-289ec4311c64 with the removed node’s payload address, at +16.
3. Writes the removed node into the container’s chain-head field.
4. Reads the container’s four-byte count, subtracts one, and writes it back.
5. Writes the result temporary to the result destination.

The payload dependency therefore runs after the removed node’s chain link has been prepared but before the direct chain-head replacement and decrement.

The count read occurs after that dependency returns. Any count change made by the dependency affects the value subsequently decremented. There is no checked subtraction or saturation. For a zero count, the displayed 32-bit decrement produces the all-ones word. Intended signedness and language-level treatment of signed overflow boundaries remain unestablished.

## Side effects

Direct effects include parent/child rewiring, header root and extreme changes, one-byte color writes, reuse of the removed node’s right-child field as a chain link, chain-head replacement, count decrement, and final result storage.

The removed node’s parent and left-child fields are not generally cleared. No direct allocation or storage-release operation is visible.

The payload call suggests cleanup, and chain insertion suggests reuse or deferred reclamation. Neither interpretation establishes ownership transfer, destruction semantics, or storage lifetime. If a dependency releases storage needed afterward, this body supplies no visible protection.

Dependencies may mutate shared state. A nonreturning dependency prevents later operations; no rollback is visible, and the result destination may remain unwritten after structural changes have occurred.

No synchronization, atomicity, or concurrent-access guarantee is established.

## Acceptance examples

These are conditional static acceptance examples, not executed tests.

### Bypass observes a changed header

If F-4ff56f8ab90f changes the container’s header and returns nonzero, the output is the header reference reread after that call. Direct removal, payload handling, chain insertion, and decrement do not occur.

### Result differs from removal target

If preparation leaves reference A in the result temporary and the selection slot supplies reference B when reread, removal operates on B and completion outputs A, provided later effects do not change that temporary or prevent completion.

### Sole-node removal

For a childless selected node whose parent is the header, with ordinary nonoverlapping storage and state-preserving dependencies, the writes establish rightmost = header, leftmost = header, then root = zero. Repair is skipped because its reference is the header. Chain preparation precedes the payload call; chain-head replacement and decrement follow it.

### Successor without a right child

For two-child removal with no successor right child, the relocated successor becomes the repair reference rather than null. The originally selected node receives the successor’s former color and remains the payload-handled and chained node.

### Left-direction repair calls

For a repair reference occupying its parent’s left link, a color-0 sibling causes F-c357ce363f8c to receive the container and current parent. If later conditions require near-child adjustment, F-6ca634842830 is called with only the container shown. A reached final adjustment calls F-c357ce363f8c with the container and current parent.

### Near-child dependency removes the sibling

Suppose either directional near-child adjustment is reached, its dependency returns normally, and the subsequent parent/sibling reread yields a null sibling. The function must color the current repair reference 1 and proceed to chain preparation and payload handling. It must not perform the final adjustment’s color assignments or dependency call.

The sibling reread uses the right field in the left-child direction and the left field in the opposite direction, including when the dependency changed the repair reference’s parent.

### Payload observes intermediate chain state

At payload-call entry, the removed node’s +12 field already contains the chain head read before the call. The function has not yet directly installed the removed node as chain head or decremented the count. If the dependency changes the count and returns normally, the subsequent decrement uses that changed count.
