# F-514f645f8582

## Purpose

F-514f645f8582 links a supplied record into a structure described by a two-slot header. Its established behavior is a fixed sequence of 32-bit reads and writes, selected by whether the header’s second slot initially contains zero.

For distinct, valid objects satisfying conventional linked-structure invariants, the operation is consistent with inserting a record at one end of a doubly linked sequence:

- The header’s first slot becomes the supplied record.
- The supplied record’s first link becomes zero.
- Its second link identifies the previous record at that end, if one exists.
- The previous end record’s first link is redirected to the supplied record.
- The header’s second slot is initialized only on the empty path.
- The supplied record’s third slot records the header address.

This linked-sequence interpretation is inferred intent. The memory operations below, including their ordering and branch condition, are the established contract. The function does not verify that the surrounding structure actually satisfies the inferred invariants.

| Supplied-record address | At least three consecutive 32-bit slots | Receives two links and the header address |

## Behavior

### Path selection

The first relevant access reads the header’s second 32-bit slot, at byte offset 4.

The function retains the result of the zero-versus-nonzero decision for the rest of the invocation. Later writes do not cause it to re-evaluate which path was selected.

In particular, the first header slot does not determine emptiness. An initially zero second slot selects the empty path even when the first slot contains a nonzero value. An initially nonzero second slot selects the nonempty path even when the first slot is zero.

### Empty path

When the initial second header slot is zero, the accesses occur in this order:

1. Write the supplied-record address to the header’s second slot.
2. Write the supplied-record address to the header’s first slot.
3. Write zero to the supplied record’s second slot.
4. Write zero to the supplied record’s first slot.
5. Write the header address to the supplied record’s third slot.

For distinct, non-overlapping objects, the resulting header has both slots pointing to the supplied record. Both record links are zero, and the record’s third slot points to the header.

The prior value of the header’s first slot is neither inspected nor followed on this path. Any prior contents of the record’s three slots are overwritten without being used to unlink, release, or otherwise process an earlier association.

### Nonempty path

When the initial second header slot is nonzero, the accesses occur in this order:

1. Write zero to the supplied record’s first slot.
2. Read the header’s first slot and write that value to the supplied record’s second slot.
3. Read the header’s first slot again and use the resulting address as the destination for a 32-bit write of the supplied-record address.
4. Write the supplied-record address to the header’s first slot.
5. Write the header address to the supplied record’s third slot.

The indirect write in step 3 targets the first slot of the addressed storage.

The two reads of the header’s first slot are distinct. The contract does not replace them with a single cached value. Under ordinary non-overlapping, exclusively accessed storage, both reads obtain the same existing-end address. Overlap or external modification can make that simplification invalid.

For distinct objects satisfying the inferred sequence invariants:

- The supplied record’s first link is zero.
- Its second link identifies the former active-end record.
- The former active-end record’s first link identifies the supplied record.
- The header’s first slot identifies the supplied record.
- The header’s second slot remains unchanged.
- The supplied record’s third slot identifies the header.

“Unchanged” here depends on non-overlap. The nonempty path does not explicitly assign the header’s second slot, but another write can affect it if the inputs or indirect destination alias that slot.

### No validation or recovery path

The function does not test either input for null, inspect link consistency, verify ownership, detect duplicates, or check whether the supplied record is already present.

There is no explicit failure branch, rollback, or status report. Earlier writes precede any later invalid access in the represented operation order; no transactional restoration is shown. The consequences of an invalid access are determined by the execution environment and are not specified here.

## Side effects

All established state changes are memory writes to the input objects or to storage addressed through the header’s first slot.

No allocation, deallocation, reference-count adjustment, callback, I/O, or named global access appears in the supplied body. No dependency call is present.

Writing the header address into the record’s third slot establishes a stored association. It does not establish a memory-management ownership transfer. The function neither acquires the supplied storage nor releases any storage previously referenced by the overwritten fields.

### Aliasing and repeated use

The operation is sensitive to overlap:

- If header and record storage overlap, a record-field write can change a header value before a subsequent read.
- If the supplied record is already the record identified by the header’s first slot, the indirect write can overwrite the zero previously written to the supplied record’s first slot.
- If the indirect destination overlaps the header, it can alter header state beyond the ordinary linked-sequence result.

Consequently, the ordinary postconditions are not guarantees for arbitrary overlapping inputs. The ordered accesses remain the relevant static description, provided each access remains meaningful in the execution environment.

The function does not remove an already-linked record from its former location. Reusing such a record can therefore leave other records with stale or inconsistent relationships.

### Concurrency

No lock, atomic operation, barrier, or concurrency protocol is established. The listed order describes the source-level accesses, not an atomic publication guarantee or a promise about hardware visibility.

Concurrent modification of the header or affected records is outside the established safe-use contract. A reader must not assume it can observe only the initial or final structure.

## Acceptance examples

These examples are conditional consequences of the static behavior. They are not reports of runtime tests.

### Empty header with distinct storage

Given a header whose second slot is zero and a distinct writable record:

- Both header slots must end with the record’s address.
- Both record link slots must end with zero.
- The record’s third slot must end with the header’s address.

The header’s original first-slot value does not affect this result.

### Nonempty, consistent sequence

Given a header with a nonzero second slot, a first slot addressing an existing end record, and a distinct new record:

- The new record must become the header’s first-slot target.
- Its second slot must identify the former end record.
- Its first slot must be zero.
- The former end record’s first slot must identify the new record.
- The header’s second slot must retain its prior value.
- The new record’s third slot must identify the header.

These results require valid, non-overlapping storage and no external mutation during the operation.

### Zero empty marker with a stale first-slot address

Given a zero second header slot and an arbitrary first-slot value, the function must take the empty path. It must replace the first-slot value without dereferencing it.

The operation does not reconcile or recover any structure that the stale value may once have referenced.

### Nonzero marker with a zero first-slot address

Given a nonzero second header slot and a zero first header slot, the function must select the nonempty path.

Before the indirect access through zero, it attempts to clear the supplied record’s first slot and copy zero into its second slot. There is no explicit diagnostic or fallback to the empty path. Whether execution faults, and what state is externally observable afterward, is environment-dependent.

### Existing contents in the supplied record

For a valid distinct record containing arbitrary prior links and a prior association, the function must overwrite all three relevant slots. It must not inspect the old association or perform a corresponding unlink or release operation.

### Supplied record already at the active end

If the header’s first slot already addresses the supplied record, the operation is not an idempotent insertion.

With otherwise distinct header storage, the nonempty path first clears the record’s first slot, then later writes the record’s own address into that same slot through the indirect destination. Its second slot also receives its own address. No duplicate-insertion rejection is present.
