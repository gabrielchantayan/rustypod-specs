# F-600167a3bf2e

## Purpose

F-600167a3bf2e directly updates up to three bytes of a caller-supplied object, performs conditional dependency-driven processing, and delegates final processing to F-876f4b90d114.

The byte at object offset `0xD4` is cleared before any dependency call. If two gates succeed, it receives a computed Boolean value. The bytes at offsets `0xB0` and `0xB1` are conditionally populated when the second argument is nonzero and separate availability queries succeed.

Every normal completion returns the 32-bit value 1. This result does not distinguish successful queries, unavailable values, skipped processing, or the value computed for `0xD4`.

These are structural behaviors, not established application semantics. Interpreting the fields as settings or the gates as capability checks is inferred intent only.

## Behavior

### 1. Initial store and first gate

The first direct object access stores zero at `0xD4`.

F-938c950e5046 is then called. Its result is treated as an object containing a dispatch-table address. The function reads that table address and obtains the method address at table byte offset `0xF8`.

Only after F-938c950e5046 returns and that method address has been obtained does the function read an external lookup-argument global. U-01, the method at `0xF8`, receives the returned object and the value from that global read.

The lookup argument is not established to be immutable. In particular, F-938c950e5046 may change the global before it is read.

If U-01 returns zero, gated processing is skipped. Otherwise, F-682adfd5a561 receives that result and `0x1700`. A zero return also skips gated processing.

On either skipped path, this function makes no second direct store to `0xD4`. The byte is not guaranteed to remain zero: dependencies may modify it or aliased storage.

### 2. Gated result production

When both gate results are nonzero, operations proceed in this order:

1. F-eb24201e389b receives a four-byte stack-backed temporary and the object address plus `0xB4`.
2. F-6a21f4f07f67 is called.
3. F-7a7a20db82de supplies the first comparison token.
4. F-e38e6836b640 receives the four-byte temporary and supplies an object.
5. The dispatch-table address of that object is read, and its method at byte offset `0x22C` is obtained.
6. U-02, that method, is invoked with a stack-backed output-region address and the resolved object.
7. F-b7af80e829ec supplies an object whose dispatch entry at `0xE0` is invoked as U-03, producing the second comparison token.
8. F-b7af80e829ec is called again; the new result supplies dispatch entry `0x120`, invoked as U-04 to produce an unsigned 32-bit quantity.

The two provider calls are distinct. They need not return the same object. U-03 and U-04 have no explicit arguments in the supplied call expressions; implicit receiver or calling-convention requirements remain unknown.

The output region’s full representation and required extent are not established. Its starting address is subsequently supplied to the content-checking and post-use dependencies.

### 3. Computed Boolean

The value directly written to `0xD4` is 1 if either:

- The content condition succeeds; or
- The captured comparison tokens are equal and the captured unsigned quantity is zero.

Otherwise it is 0.

The quantity calculation is a zero-only test. Its effective result is true for zero and false for every other unsigned 32-bit value. Although the arithmetic includes subtraction from 1, quantities greater than 1 are explicitly forced to the false case. Quantity 1 is also false.

The content condition uses this short-circuit sequence:

1. F-1b4a596f7de8 receives the output-region address. Zero means failure without calling F-f59976f504c7.
2. If the first check is nonzero, F-f59976f504c7 receives that address. Zero means failure without a second call.
3. If that return is nonzero, F-f59976f504c7 is called again. This second return is interpreted as unsigned 32-bit and passes exactly when it is at least `0x2710`.

The range expression rejects values below `0x2000`, then rejects values whose unsigned difference from `0x2000` is below `0x710`. Consequently:

- `0x00000000` through `0x0000270F` fail.
- `0x00002710` through `0xFFFFFFFF` pass.

The first and second F-f59976f504c7 returns are independent observations. The first only enables the second call; it is not reused as the range-tested value.

Both comparison tokens and the unsigned quantity have already been obtained before the content checks begin. Their equality-and-zero alternative affects the result only when the content condition fails.

### 4. Notification capture, store, and post-use calls

After the content checks and Boolean selection, the function reads a notification-argument global.

It then:

1. Stores the selected byte at object offset `0xD4`.
2. Calls U-05 with the previously captured notification argument.
3. Calls F-4e292a3dd745 with the output-region address.
4. Calls F-24edd96d1422 with the four-byte temporary.

The notification argument is therefore captured **before** the computed-byte store, although the notification call occurs **after** it. If the store aliases the global’s storage, U-05 still receives the captured pre-store value.

Neither the notification argument nor its global is established to be constant. Content-checking dependencies execute before the capture and may change it.

### 5. Optional-processing preparation

After either completing or skipping gated processing, the function captures an external base global.

It then writes four adjacent 32-bit stack slots, in increasing address order, with:

1. The first incoming argument.
2. The second incoming argument.
3. Either the initial lookup-method address or the first comparison token.
4. Either the incoming fourth argument or the method address obtained at `0x22C`.

The latter alternatives apply when gated processing was entered. The initial lookup-method address remains the third slot’s value if either gate failed.

These slots reuse storage previously available to gated processing. Their initialized values do not prove that dependencies leave them unchanged.

If the second argument is zero, both optional update sequences are skipped. The external-base capture and these temporary writes nevertheless occur.

### 6. First optional update

When the second argument is nonzero, the first availability sequence proceeds as follows:

1. Read the external base global **again**.
2. Read a 32-bit key at offset `0x0C` from this newly read base.
3. Call F-9b9c1c7483f4 with a destination starting at the fourth temporary slot, that key, and an input address starting at the third slot.
4. Capture the external context global.
5. Read the context global again for the first F-8094c3d72052 call, which also receives the preparation result.
6. Call F-8a5aadac202f on the preparation destination.
7. Act on the saved availability result.

The earlier captured base and the base used for this first key load are separate global reads. No dependency call separates them, but equality still requires a stability assumption.

Likewise, the captured context and the context supplied to the first availability call come from separate reads. Later calls use the captured context, not another global read.

If availability is zero, there is no direct store to `0xB0`.

If availability is nonzero:

1. Read the 32-bit key at offset `0x0C` from the **earlier captured base**.
2. Call F-9b9c1c7483f4 with a destination starting at the second temporary slot, the key, and an input address starting at the first slot.
3. Call F-cf946f91e683 with the captured context and preparation result.
4. Store its one-byte return at `0xB0`.
5. Call F-8a5aadac202f on this second preparation destination.

The supplied byte is not visibly normalized to Boolean.

### 7. Second optional update

The second sequence follows the first sequence, including its conversion and post-use call when applicable.

It uses a 32-bit key at offset `0x10` from the earlier captured base:

- Preparation for availability uses the fourth-slot destination and third-slot input address.
- F-8094c3d72052 receives the captured context and preparation result.
- F-8a5aadac202f runs before availability is acted upon.
- If availability is nonzero, a fresh key read at offset `0x10` precedes conversion preparation using the second-slot destination and first-slot input address.
- F-cf946f91e683 receives the captured context; its byte is stored at `0xB1`.
- The conversion temporary receives its F-8a5aadac202f call after the store.

All key loads after the first availability preparation use the captured base, but they reread the pointed-to key fields. Dependencies can therefore change the key used by a later preparation.

The context is not recaptured for the second sequence. Mutating the context global does not replace the saved value, although dependencies may mutate whatever that value references.

### 8. Final delegation

F-876f4b90d114 receives the first and second incoming arguments after all applicable processing.

Its result is ignored. If it returns normally, F-600167a3bf2e returns 1.

## Side effects

The direct object-store order is:

1. Zero to `0xD4`.
2. Optional computed 0 or 1 to `0xD4`.
3. Optional conversion byte to `0xB0`.
4. Optional conversion byte to `0xB1`.

There are no visible direct reads of the previous bytes at `0xB0` or `0xB1`. An unavailable value leaves the corresponding byte unwritten by this function; it does not explicitly clear it.

Global reads have observable timing:

- Lookup argument: after the initial provider and dispatch-entry retrieval.
- Notification argument: after content evaluation, before the computed-byte store.
- External base: captured once, then reread for the first availability key.
- External context: captured after the first preparation, then reread for the first availability call.

Dependencies execute between many operations. Their preservation of globals, object fields, keys, or stack contents is not established. The final state after F-876f4b90d114 cannot be inferred solely from this function’s direct stores.

Stack-backed storage is borrowed during calls. The body does not establish whether dependencies retain its address. Valid later use would require an independent lifetime mechanism.

Post-use calls resemble cleanup, but allocation, ownership transfer, reference counting, and release semantics are **documented_only**. No dependency may be assumed to release memory merely because of its position in the sequence.

## Acceptance examples

These are conditional static examples, not executed tests. They assume valid accesses and normally returning dependencies.

1. **Lookup fails; second argument is zero.**  
   The initial `0xD4` store occurs. Gated processing and optional probes are skipped. Base capture and temporary initialization still occur, followed by final delegation and return 1.

2. **The initial provider changes the lookup global.**  
   U-01 receives the value read after the provider returns and the `0xF8` entry is obtained, not an assumed entry-time value.

3. **The second gate fails.**  
   No gated temporary initialization, content checks, computed-byte store, or notification occurs. Optional processing remains independently controlled by the second argument.

4. **The initial content check returns zero.**  
   F-f59976f504c7 is not called. The computed byte is 1 exactly when tokens match and quantity is zero.

5. **The first range-provider return is zero.**  
   There is only one F-f59976f504c7 call. No hypothetical second result can make the content condition succeed.

6. **Range-provider returns are 1 and `0x2710`.**  
   With a nonzero initial content check, the content condition succeeds regardless of token mismatch or nonzero quantity.

7. **Range boundaries with the token alternative false.**  
   A second range-provider result of `0x270F` produces 0; `0x2710` produces 1. `0xFFFFFFFF` also passes the unsigned comparison.

8. **Matching tokens and quantity 1.**  
   Failed content checks produce 0. Quantity 1 does not satisfy the zero-only alternative.

9. **The computed store aliases notification-global storage.**  
   U-05 receives the value captured before the store, even if the stored byte changes that global’s representation.

10. **The two base-global reads differ.**  
    The first availability key comes from the second base value plus `0x0C`. Its conversion key, if needed, and both second-sequence keys come from the earlier captured base.

11. **The two initial context reads differ.**  
    The first availability call receives the second context read. Conversions and the second availability call receive the earlier captured context.

12. **Only the second availability query succeeds.**  
    No direct `0xB0` store occurs. The second conversion byte is stored at `0xB1`, before its post-use call.

13. **A conversion returns `0xA5`.**  
    The target byte receives `0xA5`, not 1.

14. **A dependency changes a captured base’s key field.**  
    A later preparation observes a fresh key load from that captured base; it need not reuse the earlier key value.
