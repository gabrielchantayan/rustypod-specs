# F-a4c3f74d7350

## Purpose

F-a4c3f74d7350 performs a lookup, consumes one sequence-counter value from the located entry, and asks a dependency to obtain or decode a record. If that operation succeeds and the record has one of two accepted discriminator values, the function publishes five scalar outputs and passes an additional record value to another dependency.

The established behavior is narrower than a complete protocol description. The supplied static representation establishes control flow, field widths, selected offsets, explicit writes, dependency calls, and return-value selection. It does not establish the meanings of the decoded fields, the dependencies’ internal behavior, or a complete record layout.

The operation is not visibly transactional: once lookup succeeds, the counter update precedes decoding and is not explicitly reversed on any later failure.

## Behavior

### 1. Lookup

The function calls F-b767e66f0906 with:

1. The context region at offset 0x408.
2. Argument 2 unchanged.
3. Storage into which the dependency can place an entry address.

A zero return causes an immediate return of 4.

On that branch, this function does not explicitly:

- Initialize its temporary record.
- Read or increment an entry counter.
- Invoke decoding or record cleanup.
- Write any of the five caller output locations.
- Invoke F-151ab4bfe553.

These statements concern operations visible in this function, not effects that the lookup dependency may perform.

Any nonzero lookup return selects the continuation path.

### 2. Initialize temporary state

The function passes the base of a temporary record workspace to F-0f4e5b1270b7.

This call occurs before the entry counter is read. Consequently, counter behavior is defined relative to the entry contents observed **after** initialization returns, not necessarily to the contents present when lookup returned.

The dependency’s exact initialization, allocation, ownership, and global-state effects are unknown.

### 3. Consume the entry counter

The function reads the unsigned 32-bit counter from the first entry word. Call the observed value the **consumed counter**.

It writes back:

**consumed counter + 1, modulo 2³².**

The explicit counter write occurs before the decoding call. There is no visible rollback on decoding failure or rejection of the record discriminator.

The value passed to decoding is only the consumed counter’s low 16 bits. Thus:

- The counter stored in the entry is 32 bits.
- Its explicit increment wraps at 2³².
- The sequence argument supplied to decoding ranges from 0 through 65,535.
- The sequence argument corresponds to the value before increment, not after increment.

No lock, atomic primitive, or synchronization mechanism is visible around the counter read and write.

### 4. Obtain or decode the record

The function calls F-cdd1e93d2e35 with six arguments, in this order:

1. The context region at offset 0x218.
2. The entry’s second 32-bit word.
3. The consumed counter masked to its low 16 bits.
4. The temporary record workspace.
5. One auxiliary four-byte storage area.
6. A second auxiliary four-byte storage area.

The entry’s second word is read for this call after the explicit counter update. The supplied representation does not establish a portable ordering among evaluation of otherwise independent call arguments.

A nonzero dependency return selects the decoding-failure path:

1. Call F-d9c6fcdd6df6 with the temporary record base.
2. Return 1.

This branch makes no explicit caller-output writes and does not invoke F-151ab4bfe553. The counter update has already occurred.

A zero dependency return selects record inspection.

### 5. Inspect the discriminator

A 16-bit discriminator at record-relative offset 0 controls acceptance:

- Value **1:** write byte value **1** to argument 4.
- Value **2:** write byte value **0** to argument 4.
- Any other value: call F-d9c6fcdd6df6, then read the designated global return value and return it.

The displayed discriminator representation is signed 16-bit, although signedness does not affect equality comparisons against 1 and 2.

On the unsupported-discriminator path, this function makes no explicit writes to arguments 4 through 8 and does not invoke the conversion dependencies or F-151ab4bfe553. Cleanup precedes the global return-value read. The return therefore cannot be described as a fixed pre-cleanup snapshot of that global.

### 6. Publish the remaining outputs

For an accepted discriminator, publication proceeds in the following order:

1. **Argument 4:** the discriminator-derived byte described above.
2. **Argument 5:** a byte containing bit 14 of a 16-bit record field at relative offset **0x38**.
3. **Argument 7:** the 32-bit result of F-4055be9c3f18 applied to record storage at relative offset **0x30**.
4. **Argument 8:** the 32-bit result of a second F-4055be9c3f18 call, applied to record storage at relative offset **0x34**.
5. **Argument 6:** the 32-bit record value at relative offset **0x58**.

The second byte output is exactly 0 or 1:

- Mask the 16-bit field with 0x4000.
- Shift the selected bit right by 14.
- Store the resulting byte.

Other bits of that field do not contribute to this explicit output.

Each conversion call completes before its result is written. The first converted result is written before the second conversion call begins. The direct record value for argument 6 is read after both conversion calls.

It is not established that conversion calls preserve record storage, caller-visible memory, or globals. In particular, the direct output must not be specified as an early snapshot taken before those calls.

### 7. Invoke the downstream operation and clean up

After writing argument 6, the function reads the 32-bit record value at relative offset **0x210** and calls F-151ab4bfe553 with:

1. Argument 3 unchanged.
2. That record-derived value.

No return value from this dependency controls the visible branch or final status.

The function then calls F-d9c6fcdd6df6 with the temporary record base and returns 0.

There is no explicit retraction of previously published outputs if downstream processing or cleanup changes other state. Behavior when a dependency does not return normally is not established.

## Side effects

### Explicit mutation

The visible explicit writes are:

- The located entry’s first 32-bit word, once lookup succeeds and initialization returns.
- Five caller output locations, only on the accepted-record path.

The output-write order is:

**argument 4 → argument 5 → argument 7 → argument 8 → argument 6.**

No explicit output initialization occurs at entry. No explicit failure-path clearing occurs.

A statement such as “outputs are unchanged on failure” is therefore valid only with the qualification that dependencies do not modify those locations through other references.

### Aliasing

No disjointness checks are visible.

If two output locations overlap, later explicit stores may replace bytes written by earlier stores. Intervening dependency calls must also be considered. The final memory state cannot generally be reduced to five independent output values unless the caller provides suitably separate storage and dependency effects are constrained.

If outputs overlap the entry or other shared state, publishing outputs may overwrite the earlier counter update. The function provides no protection against that situation.

### Temporary storage and ownership

The temporary workspace is supplied to initialization, decoding, and cleanup dependencies. Separate auxiliary storage is supplied to decoding.

The function itself contains no visible allocation or deallocation operation. This does **not** establish that its dependencies allocate nothing, retain nothing, or release particular resources.

F-d9c6fcdd6df6 is called on every normal continuation after the decoding dependency returns, including:

- Decoding failure.
- Unsupported discriminator.
- Accepted record after downstream processing.

Its placement supports describing it as a cleanup-stage dependency. Its actual ownership and release semantics remain unknown.

No cleanup call is visible on lookup failure.
