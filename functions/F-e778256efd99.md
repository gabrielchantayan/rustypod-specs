# F-e778256efd99

## Purpose

F-e778256efd99 copies an integer-encoded value from a source cell to a destination cell. If the captured value is nonzero, it then increments the integer cell located four bytes beyond the address represented by that value.

The destination write precedes both the read and the write involved in the increment. This ordering is part of the contract, particularly when the destination overlaps the incremented cell.

A reference-acquisition operation is a plausible interpretation: the copied value may identify an object whose reference count occupies an offset-four field. That interpretation is not established. The visible behavior establishes only a value copy and a conditional integer increment.

## Interface

The operation accepts two address-valued inputs:

- **Destination cell address:** identifies the integer cell to be overwritten.
- **Source cell address:** identifies the integer cell whose value is captured.

The operation has no explicit return value. Its observable results are memory changes.

### Representation and layout

The supplied representation uses an integer type for the source cell, destination cell, captured value, and incremented cell. It does not independently establish the target integer width, pointer width, byte order, or alignment requirements.

The relevant layout is:

| Location | Role | Access |
|---|---|---|
| Source address | Holds the value to capture | One read |
| Destination address | Receives the captured value | One write |
| Address represented by a nonzero captured value, plus four bytes | Holds the integer to increment | One read followed by one write |

The four-byte displacement is explicit. The width of the integer access is not independently proven by that displacement.

If the target uses 32-bit integers, the three cells above are each four bytes wide. That is a conditional platform interpretation, not an independently verified property of the target.

### Preconditions for defined completion

The source must identify a readable integer cell. The destination must identify a writable integer cell, including when the source contains zero.

For a nonzero captured value:

- Its interpretation as an address must be valid under the target’s integer-to-address rules.
- Adding the four-byte displacement must produce a valid address for the subsequent access.
- The resulting cell must support both an integer read and an integer write.
- Required alignment and access permissions must hold.
- Increment arithmetic must have defined behavior under the applicable execution model.

The operation contains no visible checks enforcing these conditions. No non-aliasing requirement is visible, but aliasing can alter the increment input because of the prescribed access order.

## Behavior

### Established access order

On a normally completing invocation, the operation performs these observable memory accesses in order:

1. It reads the source integer once and retains that value.
2. It writes the retained value to the destination.
3. If the retained value is nonzero, it reads the integer at the corresponding address plus four bytes.
4. It writes that last integer increased by one back to the same location.

The source is not visibly reread after the destination write. The zero/nonzero decision uses the retained value, not a later value from the source or destination.

For a zero captured value, the operation finishes after the destination write. It does not access an offset-four cell associated with zero.

For a nonzero captured value, the increment is unconditional after the destination write: there is no visible check of the existing field value, no saturation rule, and no special handling of negative values.

### Destination replacement

Any previous destination contents are overwritten without being read by this operation.

Consequently, there is no visible action associated with the value being replaced: no decrement, release, destruction, comparison, or transfer callback. If the destination previously represented a resource that requires such an action, satisfying that requirement is outside the established behavior.

The destination write occurs even when the destination already contains the captured value.

### Aliasing

Aliasing must be evaluated using the access order, rather than treating the copy and increment as independent effects.

If source and destination are the same cell, the operation still captures the value, writes it back, and performs the increment when that captured value is nonzero. Equality of the two input addresses does not suppress the increment.

If the destination is exactly the cell to be incremented, the destination write first replaces that cell with the captured address value. The subsequent increment therefore reads and increments that newly written value, not the cell’s original contents.

If the source is the cell to be incremented, the initial source read still determines both the destination value and the address used for the later increment. A later change to the source cell does not retroactively change the retained value.

Partially overlapping cells are not separately handled. Their effects depend on access width, byte order, alignment rules, and the target memory model; those details are not established here.

### Arithmetic boundaries

The increment has an explicit arithmetic delta of positive one. The address calculation has an explicit displacement of four bytes.

Neither operation has a visible overflow check. The available evidence does not establish whether boundary cases wrap, trap, or fall outside defined execution.

In particular, if the incremented field is a signed 32-bit integer, incrementing its maximum positive value cannot be promised to wrap to its minimum negative value. Such a promise would require additional execution-model evidence.

## Side effects

The direct side effects are:

- An unconditional write of the captured source value to the destination.
- A conditional read-modify-write of the offset-four integer cell.

There are no visible calls, allocations, frees, input/output operations, or direct accesses to named global state.

This does not establish that global state is preserved. Either input, or the address encoded by the source value, may designate global or shared memory.

There are no visible atomic operations, locks, fences, or other synchronization mechanisms. The increment is represented as a read followed by a write; it must not be treated as a guaranteed atomic increment. Concurrent access requires an external synchronization contract or additional target-specific evidence.

### Ownership and failure

No ownership transfer is established. The operation does not visibly allocate, release, or validate a resource, and it provides no evidence that the copied address remains valid after return.

There is no explicit status result or recovery path. Invalid addresses, access violations, alignment failures, and arithmetic boundary behavior are not converted into a reported error by the visible operation.

There is also no rollback. Because the destination write comes first, a failure during a later nonzero-path access may occur after the destination has already changed.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Each assumes valid accessible memory, compatible representations, and defined arithmetic unless stated otherwise.

### Zero source value

Given a source cell containing zero and a writable destination initially containing another value:

- The destination becomes zero.
- No increment-cell access occurs.
- The old destination value receives no separate processing.

### Nonzero value with disjoint cells

Given a source containing a valid encoded address, a separate destination, and an integer value of 7 at that address plus four bytes:

- The destination receives the captured encoded address.
- The offset-four integer becomes 8.
- The source remains unchanged by these writes because the relevant cells are disjoint.

### Destination already contains the source value

Given distinct source and destination cells holding the same nonzero encoded address, with 7 in the corresponding offset-four cell:

- The destination is written with that same address value.
- The offset-four integer becomes 8.

Value equality does not make the operation a no-op.

### Identical source and destination addresses

Given a single cell used as both inputs, containing a nonzero encoded address whose offset-four cell is separate and contains 7:

- The shared input cell retains its value.
- The offset-four integer becomes 8.

### Destination aliases the incremented cell

Given a nonzero captured value whose offset-four cell is also the destination:

- The destination first receives the captured value.
- The increment reads that newly written value.
- The final destination contains that value increased by one, provided the arithmetic is defined.

Its original contents do not supply the increment input.

### Negative increment-field value

Given a valid nonzero encoded address and an offset-four integer of −2:

- The field becomes −1 if the target representation and arithmetic support those values.
- No visible positivity check prevents the increment.

### Failure after the copy

Given a readable source containing a nonzero encoded address, a writable destination, and an inaccessible offset-four cell:

- The visible ordering places the destination write before the failing access.
- No explicit success or failure status is produced.
- The exact fault mechanism remains environment-dependent.
