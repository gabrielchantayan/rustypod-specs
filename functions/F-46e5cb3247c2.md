# F-46e5cb3247c2

## Purpose

F-46e5cb3247c2 applies two zero-status gates to an operation. If both gates return zero, it prepares a temporary record, increments a shared 16-bit field, invokes an indirect operation, derives and publishes a 32-bit value, writes a one-byte marker, and calls a final dependency.

The returned status comes exclusively from the gates. The indirect operation and later dependencies do not supply an alternative returned status.

This is an established description of the visible control flow. Interpreting the function as registration, activation, acquisition, or another application-level operation would be **inferred intent**. No such interpretation is required by this contract.

## Interface

### Arguments

The supplied representation exposes four arguments, each occupying one 32-bit word.

| Argument | Established use |
|---|---|
| First | An address-bearing value used for a 16-bit read at byte offset `0x10`; also passed unchanged to F-256e8a77aa59. |
| Second | An opaque 32-bit value passed unchanged to F-256e8a77aa59. |
| Third | An opaque 32-bit value placed in both temporary records at different positions. |
| Fourth | An opaque 32-bit value placed in the second word of the operation record. |

These uses do not establish application-level types, ownership transfer, or signed interpretations for the input words. In particular, although the third argument initially occupies an address-bearing position in the operation record, preparation occurs before that position is used for indirect dispatch.

### Return value

The result is a 32-bit status:

- If F-256e8a77aa59 returns nonzero, that status is returned unchanged.
- Otherwise, the status from F-43ce968102ca is returned unchanged.
- If both gates return zero, the function returns zero after the remaining visible sequence completes normally.

The result of F-bf18a6a8124b is stored in shared state, not returned. Return values from preparation, the indirect operation, and finalization are not used to select the enclosing function’s status.

### Temporary records

The supplied representation supports two temporary records, each containing two adjacent 32-bit words, for an eight-byte represented extent.

| Record | Initial contents | Contents before the second gate |
|---|---|---|
| Result record | First argument, second argument | Zero, third argument |
| Operation record | Third argument, fourth argument | Third argument, fourth argument |

The result record is rewritten only after the first gate returns zero. The operation record remains as initialized until F-7a117b899bf6 receives its address.

These names describe the records’ observed uses, not established external types. The evidence does not establish alignment requirements, complete external object layouts, or permission to access beyond the represented extents.

### Preconditions for normal execution

Every address actually accessed must support the indicated operation. In particular:

- After F-5f5f14cedda3 returns, the first argument must support a 16-bit read at offset `0x10`.
- The shared owner-reference slot must be readable after the first gate, including when that gate rejects.
- On the second-gate path, its shared member reads and computed 16-bit read must be valid.
- On the successful path, the retained owner must support the nested-pointer reads, and the selected nested states must support the specified field accesses.

- The resulting indirect target must support the observed invocation with two record addresses.

No visible null, bounds, alignment, or callable-target checks enforce these conditions. All normal-completion descriptions also require each invoked dependency to return normally and leave later accessed memory valid.

## Behavior

### Initial records and retained values

The function first initializes the two temporary records from the four argument words.

It calls F-5f5f14cedda3 without explicit arguments and retains its 32-bit result. It then reads a 16-bit field at offset `0x10` from the first argument’s object.

That field read occurs after F-5f5f14cedda3 returns and before the first gate is called. Consequently:

- Changes made by F-5f5f14cedda3 can affect the observed field value.
- Changes made later by the first gate do not refresh the retained value.
- The read occurs even on an invocation whose first gate subsequently returns nonzero.

### First gate and owner capture

F-256e8a77aa59 receives the original first and second arguments.

After that call returns, the function reads the shared owner-reference slot and retains its address-bearing value. This capture occurs before testing the gate result and therefore also occurs on first-gate rejection.

If the gate result is nonzero, the function returns it. No second-gate call, preparation, increment, indirect operation, value derivation, publication, or finalization follows on that path.

The captured owner is used for the later successful-path nested-pointer reads. The second gate obtains its shared arguments separately; it is not specified to use this captured owner.

### Second gate

If the first gate returned zero, the result record is rewritten to contain a zero first word and the original third argument as its second word.

F-43ce968102ca then receives four values:

1. A 32-bit member read at offset `0x04` from an owner selected through the shared owner-reference slot.
2. The retained 32-bit result of F-5f5f14cedda3.
3. A 16-bit value read at the address formed by adding a shared base value to another read of the owner’s offset-`0x04` member.
4. The retained 16-bit field from the first argument’s object.

The third argument’s address uses an unscaled byte-address addition. No multiplication by a 16-bit element size or bounds check is visible.

The shared owner-reference slot and its offset-`0x04` member appear in repeated reads. Their relative evaluation order within the argument expressions is not established by the supplied representation. This contract therefore does not require those reads to observe a single coherent owner or member value under external mutation.

If the second gate returns nonzero, that status is returned unchanged. No subsequent successful-path calls or direct shared-state writes occur.

### Preparation and counter update

When the second gate returns zero, F-7a117b899bf6 receives the operation-record address. At its entry, that record contains the original third and fourth arguments.

After preparation returns, the function reads a nested-state address from offset `0x04` of the retained owner. It then reads a 16-bit field at nested-state offset `0x2de`, adds one, and writes a 16-bit result back to that field.

The direct store retains the low 16 bits of the incremented value. For a value actually read by this increment:

| Read bit pattern | Stored bit pattern |
|---|---|
| `0x0000` | `0x0001` |
| `0x002a` | `0x002b` |
| `0x7fff` | `0x8000` |
| `0xffff` | `0x0000` |

The represented 16-bit addition does not require a saturation or overflow-error path: even the maximum unsigned 16-bit value plus one fits within a 32-bit intermediate, and the destination retains only 16 bits. The field’s semantic signedness remains unknown.

Crucially, the increment depends on the field value read **after preparation returns**, not on its value at function entry or before preparation. F-7a117b899bf6 may change the field without changing the nested pointer. It may also change the retained owner’s nested pointer and thereby change the increment target. No preservation guarantee is assumed for either.

### Indirect operation

After the increment, the function takes the current first word of the operation record as an address and reads a function pointer directly at byte offset `0x0c`.

The evidence shows this direct function-pointer field lookup, not an additional dispatch-table dereference.

The selected target receives:

1. The operation-record address.
2. The result-record address.

The counter store has already occurred when the indirect call begins. Its return value is not used to change the enclosing function’s returned status.

The callback can modify the supplied records. Subsequent consumers receive their then-current contents: the result record is passed to F-bf18a6a8124b, and the operation record is later passed to F-ec22bd8215d3. Neither record is visibly restored to its earlier contents.

### Derivation, publication, and finalization

After the indirect operation returns, F-bf18a6a8124b receives the result-record address. Its 32-bit return value is retained.

Only after that dependency returns does the function reread the nested-state address from offset `0x04` of the retained owner. Using this newly selected address, it performs two direct stores in order:

1. The derived 32-bit value at offset `0x2d8`.
2. The byte value `1` at offset `0x2dc`.

Both stores use the same retained publication address. The function does not reread the global owner-reference slot to select the publication owner.

The publication target can differ from the increment target. The indirect operation or F-bf18a6a8124b may change the retained owner’s nested pointer before the publication address is read.

Finally, F-ec22bd8215d3 receives the operation-record address. If it returns normally, the function returns the zero status from the second gate.

## Side effects

### Direct shared-state writes

The visible direct writes outside the temporary records occur only after both gates return zero.

| Target | Width | Effect |
|---|---:|---|
| Increment target, offset `0x2de` | 16 bits | Store the low 16 bits of the value read there plus one. |
| Publication target, offset `0x2d8` | 32 bits | Store F-bf18a6a8124b’s result. |
| Same publication target, offset `0x2dc` | 8 bits | Store `1`. |

Preparation precedes the increment. The increment precedes the indirect operation. Publication follows the indirect operation and derivation. Finalization follows both publication stores.

These are ordering statements for the represented execution, not claims of atomicity, locking, or cross-thread visibility.

### Dependency effects and ownership

Gate rejection does not imply absence of side effects: dependencies have already run. No dependency is assumed to preserve globals, pointed-to memory, or resource ownership.

The temporary records belong to this invocation. Their addresses are passed to dependencies, but this function does not visibly return or publish those addresses. Whether any dependency retains an address is unresolved; validity after the invocation would require a separate lifetime contract.

Preparation and finalization are descriptive roles only. The visible call pairing does not prove allocation, construction, destruction, release, or ownership transfer.

No rollback or compensating action is visible. A failure to return normally after an earlier store is not shown to restore that store.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Each assumes valid accesses and normal returns from invoked dependencies.

### First-gate rejection

If F-256e8a77aa59 returns a nonzero 32-bit status:

- F-5f5f14cedda3 and the first-object field read have already occurred.
- The shared owner-reference slot is read after the gate returns.
- The same status is returned.
- No second gate or successful-path operation follows.
- None of this function’s three direct shared-state writes occurs.

Dependency-originated effects remain possible.

### Second-gate rejection

If the first gate returns zero and the second returns nonzero:

- The second gate receives the first-object field value retained before the first gate, even if that gate changed the field.
- The second-gate status is returned unchanged.
- Preparation, increment, indirect operation, derivation, publication, and finalization do not occur.

### Successful publication

Assume both gates return zero. After F-7a117b899bf6 returns, the nested state selected for the increment contains `0x002a` at the instant of the direct 16-bit read. Also assume the nested pointer remains unchanged through publication, and F-bf18a6a8124b returns `0x89abcdef`.

Then:

- The direct increment stores `0x002b` before the indirect call begins.
- The 32-bit publication store writes `0x89abcdef`.
- The marker store subsequently writes `1`.
- Finalization is called afterward.
- Normal completion returns zero.

The counter precondition applies after preparation, not at function entry. An unchanged nested pointer alone would not establish the read value because preparation may modify the field in place.

These are the values written by the function, not unconditional final-state guarantees. Later dependency effects may change them.

### Increment wraparound

Assume both gates return zero and, after preparation returns, the field selected for the increment has bit pattern `0xffff` at the instant of the direct read.

The direct store writes `0x0000`, and the function proceeds to the indirect call without an overflow-status branch.

A value of `0xffff` observed only before preparation is insufficient to establish this outcome, even if the nested pointer does not change.

### Different increment and publication targets

Assume preparation leaves state A selected for the increment. After that increment, the indirect operation or derivation dependency changes the retained owner’s nested pointer to valid state B, which remains selected until the publication-address read.

A receives the counter store. B receives the derived value and marker. Changing only the global owner-reference slot does not replace the retained owner used for these successful-path reads.

### Callback changes to records

If the indirect operation changes the result record, F-bf18a6a8124b receives that changed record; the original third argument is not restored.

If the indirect operation changes the operation record, finalization receives its then-current contents rather than a reconstructed original argument pair.
