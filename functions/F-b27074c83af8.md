# F-b27074c83af8

## Purpose

F-b27074c83af8 performs a local pointer rearrangement consistent with a **left rotation of a parent-linked binary tree**. It promotes the selected node’s right child, moves that child’s left subtree into the selected node’s right-child position, reconnects the promoted node to the former parent or root slot, and makes the selected node the promoted node’s left child.

The pointer rearrangement is established by static evidence. The interpretation as a tree rotation is inferred intent: the function does not validate that its inputs describe a tree.

The function neither allocates nor releases storage, calls another function, nor reports a status. Its successful use depends on valid addresses and compatible writable layouts.

## Interface

### Inputs and terminology

The function accepts two address-bearing arguments:

- **Context**: identifies an object containing a reference used to locate the root slot.
- **Selected node**: identifies the node around which the rearrangement occurs.

For this contract:

- **Promoted node** means the address initially read from the selected node’s field at byte offset 12.
- **Transferred subtree** means the node, if any, referenced by the promoted node’s field at byte offset 8.
- **Former parent** means the parent reference read from the selected node when needed.
- **Root holder** means the object referenced by the context’s field at byte offset 16.
- **Root slot** means the four-byte field at byte offset 4 within the root holder.

These names describe roles, not independently verified object types.

### Widths and observed layout

The supplied representation uses 32-bit integer values and four-byte memory accesses for all references and fields involved. The node fields used are:

| Byte offset | Width | Operational role |
|---|---:|---|
| 4 | 4 bytes | Parent reference |
| 8 | 4 bytes | Left-child reference |
| 12 | 4 bytes | Right-child reference |

| Object | Byte offset | Width | Operational role |

A zero left-child reference on the promoted node is treated as absence of a transferred subtree. No other reference is explicitly checked for zero before dereferencing.

There are no accesses to byte offset 0 of a node in this function. Any payload, color, balance information, ownership metadata, or other fields are outside its established behavior.

The four-byte accesses establish field width, not byte order. The supplied material does not establish endianness, alignment requirements, or portability to a wider pointer representation.

### Output

There is no return value. Results are communicated solely through memory writes.

### Preconditions

For ordinary tree-rotation behavior:

- The selected node must reference readable and writable node storage.
- Its right-child field must identify a valid promoted node; a missing right child is not handled as a no-op.
- The promoted node’s parent and left-child fields must be accessible.
- Any nonzero transferred-subtree reference must identify storage with a writable parent field.
- The context’s root-holder field and the root holder’s root slot must be readable.
- If the selected node is the root, the root slot must be writable.
- Otherwise, the selected node’s parent reference must identify a parent whose relevant child field is readable or writable as used below.
- Node and holder storage must not overlap in ways that invalidate the intended field relationships.
- External mutation must not interfere with the operation if conventional rotation results are required.

These are safe-use preconditions, not checks performed by the function.

## Behavior

### Ordered memory effects

The operation is sequential and is not a transaction. Earlier changes may already have occurred if a later access fails.

1. **Choose the promoted node.**  
   The function reads the selected node’s right-child field once and retains that address as the promoted node for the remainder of the operation.

2. **Replace the selected node’s right-child reference.**  
   It reads the promoted node’s left-child field and writes that four-byte value into the selected node’s right-child field.

3. **Conditionally repair a transferred subtree’s parent reference.**  
   It reads the promoted node’s left-child field again and compares that value with zero.

   If that read is nonzero, it reads the same field once more and uses this last value as the address of the node whose parent field is overwritten with the selected node’s address.

   Thus, the value copied into the selected node’s right-child field, the value tested for zero, and the value used to locate the parent-field write arise from separate reads. They agree under stable, non-overlapping storage, but the function does not enforce agreement.

4. **Assign the promoted node’s parent reference.**  
   It reads the selected node’s current parent field and copies that value into the promoted node’s parent field.

5. **Locate and inspect the root slot.**  
   It reads the root-holder reference from context offset 16, then reads that holder’s root slot.

6. **Reconnect the promoted node above the selected node.**
   - If the root slot equals the selected node’s address, it writes the promoted node’s address into that root slot.
   - Otherwise, it reads the selected node’s parent field again, then reads that parent’s left-child field.
     - If the left-child field equals the selected node’s address, it overwrites that left-child field with the promoted node’s address.
     - Otherwise, it overwrites the same parent’s right-child field with the promoted node’s address.

   The final alternative does **not** verify that the parent’s right-child field previously referenced the selected node.

7. **Make the selected node the promoted node’s left child.**  
   It writes the selected node’s address into the promoted node’s left-child field.

8. **Finish the selected node’s parent link.**  
   It writes the promoted node’s address into the selected node’s parent field, then returns without a value.

This ordering matters. The selected node’s right-child link changes before root or parent reconnection. The promoted node’s left-child link changes near the end, and the selected node’s parent link changes last.

### Conventional result

With stable, valid, non-overlapping tree storage, the resulting relationships are:

- The promoted node occupies the selected node’s former root or parent-child position.
- The promoted node’s parent reference equals the selected node’s former parent reference.
- The selected node becomes the promoted node’s left child.
- The selected node’s parent becomes the promoted node.
- The promoted node’s former left subtree becomes the selected node’s right subtree.
- If that transferred subtree exists, its parent becomes the selected node.

The selected node’s left-child field and the promoted node’s right-child field are not directly written.

For a valid ordered binary tree, this is the usual structural left rotation. Preservation of ordering nevertheless depends on the input already satisfying the appropriate ordering invariant; the function does not compare keys or payloads.

### Root versus non-root selection

Root handling is determined exclusively by whether the root slot equals the selected node’s address. The function does not identify a root by testing whether the selected node’s parent is zero or a sentinel.

Even on the root branch, the selected node’s existing parent reference is copied into the promoted node’s parent field. Its meaning may be zero, a sentinel, or another convention; the function imposes no interpretation.

On the non-root branch, a selected node that is not found in its parent’s left-child field is treated as belonging in the right-child position. Inconsistent parent-child relationships are not rejected.

The function contains no explicit protection against address overflow, invalid references, or unsuitable alignment. ## Side effects

### Direct writes

Under the normal, non-overlapping layout, writes affect:

- The selected node’s right-child field.
- The transferred subtree’s parent field, if the promoted node’s re-read left-child reference is nonzero.
- The promoted node’s parent field.
- Either the root slot or one child field of the former parent.
- The promoted node’s left-child field.
- The selected node’s parent field.

There are five four-byte writes when no transferred-subtree parent update occurs, and six when it does. Root and non-root reconnection each contribute one write.

These counts describe write operations, not necessarily distinct locations. Aliasing can cause multiple operations to affect the same location.

## Acceptance examples

The following are conditional static expectations, not executed test results. Except where noted, assume valid, stable, non-overlapping storage and consistent parent-child links.

### Root rotation with a transferred subtree

Initially:

- The root slot references node A.
- A’s parent is P and its right child is B.
- B’s left child is C.

Expected result:

- The root slot references B.
- B’s parent is P.
- B’s left child is A.
- A’s parent is B.
- A’s right child is C.
- C’s parent is A.

P is copied without interpretation. No requirement that P be zero is imposed.

### Root rotation without a transferred subtree

Initially, the root slot references A, A’s right child is B, and B’s left-child field is zero.

Expected result:

- A’s right-child field becomes zero.
- No transferred-subtree parent-field write occurs.
- The root slot becomes B.
- B becomes A’s parent, and A becomes B’s left child.

A zero transferred-subtree reference does not prevent rotation.

### Non-root rotation from a left-child position

Initially, the root slot does not reference A, A’s parent is P, P’s left child is A, and A’s right child is B.

Expected result:

- P’s left-child field becomes B.
- B’s parent becomes P.
- The root slot is not written.
- The remaining links follow the conventional rotation result.

### Non-root rotation from a right-child position

Initially, A’s parent is P, P’s left child is not A, and P’s right child is A.

Expected result:

- P’s right-child field becomes B, the promoted node.
- P’s left-child field is unchanged.
- The root slot is not written.

### Inconsistent parent linkage

Suppose the root slot does not reference A, A’s parent is P, and neither child of P references A.

Provided execution reaches the reconnection step, the function still overwrites P’s right-child field with the promoted node. It does not reject the inconsistency. Such an input is outside the valid-tree precondition and may disconnect an unrelated subtree.

### Missing promoted node

Suppose A’s right-child field is zero.

There is no successful no-op behavior to accept. The function attempts to read a field through that zero reference before any explicit validity check. The resulting execution behavior is environment-dependent and documented_only.
