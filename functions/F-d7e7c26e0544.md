## Purpose

The apparent intent is to adjust a percentage-like property within the range 0–100 and emit two notifications after a change. That interpretation is **inferred intent**, not a complete behavioral rule: the observed arithmetic does not normalize every possible starting value into that range.

The established contract is the particular comparison, arithmetic, write, and dispatch sequence described below. Dependency names do not establish their ownership or side effects.

## Behavior

### 1. Obtain the comparison value

The function first reads the object field at byte offset 888 and passes that value to F-320e2ff1af37.

The returned signed integer becomes the **original value** used for all candidate calculations and for the later equality comparison. The function does not obtain a second original value after any dependency call.

This call occurs for every adjustment, including zero. Consequently, a zero adjustment is not a call-free operation.

### 2. Determine the candidate

The candidate depends on the sign of the adjustment.

#### Zero adjustment

The candidate equals the original value.

This leads directly to the unchanged-value return described below, regardless of whether the original value lies within 0–100.

#### Positive adjustment

The function compares the original value against **100 minus the adjustment**.

- If the original value is greater than or equal to that threshold, the candidate is 100.
- Otherwise, the candidate is the original value plus the adjustment.

This is not equivalent to first normalizing the original value into 0–100. For example, a sufficiently negative original value can remain negative after a positive adjustment.

Under signed 32-bit arithmetic, both operations on this path are representable:

- For a positive adjustment up to 2,147,483,647, subtracting it from 100 does not overflow.
- The addition is selected only when its result is less than 100. Because the adjustment is positive, that addition also cannot underflow.

#### Negative adjustment

For a negative adjustment whose negation is representable:

- If the original value is strictly less than the adjustment’s positive magnitude, the candidate is zero.
- Otherwise, the candidate is the original value plus the adjustment.

The strict comparison matters. If the original value equals the adjustment’s magnitude, the arithmetic branch produces zero rather than selecting the direct zero candidate. The subsequent observable update sequence is the same for those two ways of obtaining zero.

This path does not cap the result at 100. An original value above 100 can remain above 100 after a negative adjustment.

For representable negation, the selected addition does not overflow: it is reached only when the original value is at least the positive magnitude, so the result is nonnegative and no larger than the original value.

#### Minimum signed adjustment

For a 32-bit signed adjustment of −2,147,483,648, forming its positive magnitude is not representable as a signed 32-bit integer.

The supplied source representation does not establish whether the executable wraps, traps, or exhibits some other target-specific result. No portable candidate or update outcome is specified for that input. In particular, this contract does not assume saturating arithmetic or silently replace the calculation with a wider one.

### 3. Return if the candidate is unchanged

“Unchanged” refers only to equality with the saved dependency result. It does not mean the initial dependency had no side effects.
