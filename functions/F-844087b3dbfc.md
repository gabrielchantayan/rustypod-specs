# F-844087b3dbfc

## Purpose

F-844087b3dbfc performs an indirect preparation call, selects one of four dependencies using a discriminator stored in its input object, and returns the selected dependency’s result. When that result is nonzero, it passes six additional object fields to six dependencies, clearing each field immediately before its corresponding call.

The established behavior is dispatch followed by conditional, ordered handoff. Describing the selected dependency as a constructor, or the six later calls as ownership transfers, is inferred intent rather than a proven contract. The supplied evidence does not establish the meaning of the returned value, the kinds of resources represented by the fields, or whether any dependency retains, releases, copies, or merely inspects its arguments.

## Interface

**Input:** one pointer to a mutable, word-addressed object.

**Output:** an integer-valued result:

- Zero when the discriminator is unsupported.
- Zero when the selected dispatch dependency returns zero.
- Otherwise, the exact nonzero result returned by the selected dispatch dependency, regardless of the return values of the six subsequent dependencies.

The supplied representation uses integer-sized object slots and four-byte values. The layout below describes the resulting 32-bit word model. It is not independent verification of the original machine ABI, pointer representation, or source-level types.

## Behavior

### Initial preparation

Every invocation begins with the indirect call described above. This occurs even when the object initially contains an unsupported discriminator.

The discriminator is read only after this call returns. Consequently, dispatch uses the post-call discriminator. The initial call can also affect the values later supplied as dispatch arguments or handoff arguments; no preservation guarantee is established.

If the initial call does not return normally, the evidence establishes no completed dispatch or normal return.

### Dispatch selection

After preparation, the discriminator selects exactly one dependency:

| Discriminator | Selected dependency |
|---:|---|
| 4 | F-5a16e2aaaeda |
| 5 | F-1a2f84446571 |
| 6 | F-abab6b739a07 |
| 7 | F-018c6c49ff2c |

Any other value causes an immediate zero return after preparation. This includes negative values under the represented signed-integer interpretation. Unsupported values do not select a default dependency and do not initiate the six handoff calls.

All four supported paths supply these arguments:

1. The current word at object offset `0x1C`.
2. The address of the embedded region beginning at object offset `0x40`.
3. The current word at object offset `0x20`.
4. The current word at object offset `0x24`.

The path for discriminator 4 additionally supplies a fifth value whose origin is not established in the supplied representation. It is not shown being loaded from the object or initialized by this function. Its value, type, and intended role are **documented_only**.

No left-to-right ordering of the reads used to assemble a single call’s arguments is established. What is established is that dispatch follows the initial indirect call and uses the selected branch.

The dispatch result is tested for equality to zero. No positive-only success check is present: every nonzero result, including a negative result under a signed interpretation, enters the handoff phase.

### Zero-result path

If the selected dependency returns zero, F-844087b3dbfc returns zero without performing any of its six explicit field-clear operations or handoff calls.

This does not establish that the object remains unchanged. Both the initial indirect callable and the selected dependency have already executed, and their effects are unknown.

### Nonzero-result handoff

For a nonzero dispatch result, six handoffs occur in the following order:

| Order | Field offset | Dependency |
|---:|---|---|
| 1 | `0x30` | F-2d5a261f7028 |
| 2 | `0x34` | F-883bc65e5e44 |
| 3 | `0x28` | F-091ba89715cd |
| 4 | `0x2C` | F-07ce1348e67b |
| 5 | `0x38` | F-57f24941608a |
| 6 | `0x3C` | F-5f1bf108d7f7 |

Each handoff has three observable stages:

- Read that field’s current 32-bit value.
- Write zero to that same field.
- Invoke the listed dependency with the dispatch result as its first argument and the captured field value as its second argument.

The clear precedes the corresponding call. The next field is not captured until the preceding dependency has returned normally. Thus, the six values are not a snapshot taken before the handoff sequence.

Every listed call occurs even when its captured field value is zero. There is no per-field skip condition.

Each handoff receives the same saved dispatch result. Its own return value is ignored and does not determine whether the following handoff runs. Subject to normal return from dependencies, all six calls complete before the original dispatch result is returned.

A dependency may change a field that has not yet been read. A later handoff then uses that changed value. A dependency may also repopulate a field already cleared. This function does not revisit that field, so the final object is not guaranteed to have all six fields zero.

### Arithmetic and widths

Dispatch uses equality comparisons against four small constants. It does not use an index calculation, range expansion, or fallback arithmetic.

The explicit object mutations are six word-sized zero stores. The function performs no visible arithmetic on the dispatch result or the captured handoff values.

Address formation is limited to fixed object offsets and the indirect-call entry offset. Validity and addressability are preconditions; no overflow or bounds handling is shown.

## Side effects

The function directly performs:

- One initial indirect call on every path.
- One selected dispatch call for a supported discriminator.
- Six ordered field clears and six ordered handoff calls when the dispatch result is nonzero.

It performs no explicit allocation, release, copying of the embedded region, logging, retry, or rollback. Dependencies may perform such operations, but their behavior is not established here.

Clearing a field before passing its former value onward is consistent with relinquishing a reference. That interpretation is not sufficient to establish ownership transfer. In particular:

- A zeroed field does not prove the referenced resource was released.
- A successful return does not prove a dependency retained the resource.
- Ignored handoff return values provide no evidence that a handoff succeeded.
- No preservation guarantee exists for globals, object fields, or other reachable state across dependency calls.

The sequence is not established as atomic or reentrancy-safe. Reentrant execution may observe a partially cleared object. Concurrent access requires an external synchronization contract not supplied by this evidence.

If a dependency faults, throws through an applicable ABI, terminates execution, or otherwise fails to return normally, no rollback is shown. Clears already performed are not explicitly restored. The evidence does not establish a normal return value for such an interrupted execution.

## Acceptance examples

These are conditional behavioral criteria derived from static evidence, not executed tests.

1. **Unsupported discriminator after preparation.**  
   If preparation returns normally and leaves the discriminator equal to 3, the result is zero. None of the four dispatch dependencies or six handoff dependencies is called. Preparation’s own effects remain possible.

2. **Preparation changes the selected branch.**  
   If the discriminator is initially 4 but preparation changes it to 6, F-abab6b739a07 is selected. The initial value does not control dispatch.

3. **Supported dispatch returns zero.**  
   If the post-preparation discriminator is 5 and F-1a2f84446571 returns zero, the result is zero. This function performs none of the six handoff clears, even if the fields contain nonzero values.

4. **Successful ordered handoff.**  
   Suppose discriminator 7 selects F-018c6c49ff2c, it returns a nonzero value, and all dependencies return normally without modifying the six handoff fields. The handoff field values are captured in offset order `0x30`, `0x34`, `0x28`, `0x2C`, `0x38`, `0x3C`. Each field is zero before its corresponding call begins. All six fields are zero afterward, and the original dispatch result is returned.

5. **Zero field is still delivered.**  
   If the field at `0x34` is zero when its turn arrives, F-883bc65e5e44 is still called with zero as its second argument.

6. **Later field mutation affects a later call.**  
   If F-2d5a261f7028 changes the field at `0x34` before returning, F-883bc65e5e44 receives that new value, not the value present before the handoff phase.

7. **Repopulated field survives.**  
   If F-2d5a261f7028 repopulates the field at `0x30`, this function does not clear it again. A blanket postcondition requiring every handoff field to be zero would therefore be incorrect.

8. **Negative nonzero dispatch result.**  
   If a selected dependency returns negative one in the represented integer model, all six handoffs still occur and receive that same result as their first argument. Negative one is returned after normal completion.

9. **Discriminator 4’s unresolved argument.**  
   An acceptance claim about F-5a16e2aaaeda’s behavior is conditional on the actual fifth argument and calling convention. The supplied evidence does not justify substituting zero or any object field for it.

## Evidence
