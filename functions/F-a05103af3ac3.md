# F-a05103af3ac3

## Purpose

F-a05103af3ac3 coordinates a requested amount of data processing over a segmented object. It selects a segment-sized amount, invokes either a three-argument external operation or a destination-object callback, and updates the source object's progress and segment cursor.

The apparent intent is to transfer data from segmented storage to either a raw destination or another object. That interpretation is **inferred**, not fully established: the external three-argument operation has no supplied semantic definition, and the destination callback's implementation is unavailable.

The established behavior includes an unsigned initial capacity gate, signed comparisons within the processing loop, different handling of initial and later callback failures, and state updates whose results can depend on mutations performed by dependencies.

## Interface

The function accepts four arguments and returns a 32-bit unsigned result:

| Argument | Role established by the supplied body |
|---|---|
| Source object | Pointer to an object containing a dispatch-table pointer and mutable progress and segment fields. |
| Requested amount | Unsigned 32-bit amount to process. |
| Raw cursor | A 32-bit integer used as an argument to the external operation and incremented after accepted processing. Its use as a destination address is inferred. |
| Destination object | Optional object pointer. When non-null, selects callback-based processing instead of the external operation. |

The supplied representation uses 32-bit integer and pointer slots. The source-object layout accessed by this function is:

| Byte offset | Accessed role |
|---|---|
| `+0x00` | Dispatch-table pointer |
| `+0x08` | Mutable progress value |
| `+0x0c` | Mutable offset within the current segment |
| `+0x10` | Current segment reference |
| `+0x14` | Mutable progress mirror or checkpoint |

The descriptive names above identify observed uses, not proven domain meanings.

Dispatch-table entries used are:

- Source table `+0x30`: a query receiving the source object and returning a 32-bit value used by the initial capacity gate.
- Source table `+0x4c`: a query receiving the source object, its current segment reference, and its current segment offset; returns a 32-bit segment amount.
- Destination table `+0x10`: an operation receiving the destination object, a selected amount, and an address derived from the source segment; returns a 32-bit result.

A segment reference is also used as an address from which a next-segment reference is read at byte offset `+0x04`.

For normal execution, the objects, dispatch entries, segment links, and dependency-accessed memory must be valid for the accesses actually taken. The function does not locally validate them. Exact alignment, allocation sizes, buffer bounds, and permissible aliasing are not supplied.

## Behavior

### Entry validation and capacity gate

If the raw cursor is nonzero **and** the destination object is non-null, the function invokes F-a817d8d58c10 before querying the source or performing local state writes. That dependency is marked as non-returning in the supplied evidence. Its termination mechanism is unknown.

A null raw cursor with a non-null destination object is permitted by this check. A null raw cursor with a null destination object is also permitted; it is not rejected as an invalid raw address.

Otherwise, the function invokes the source object's `+0x30` dispatch entry once. It compares the requested amount with the returned value as **unsigned 32-bit quantities**.

- If the request is greater, it returns zero without performing the loop's local state updates.
- If the request is less than or equal, it enters processing with the whole request remaining.
- A zero request still performs this query. It subsequently returns zero without querying a segment or invoking a transfer operation.

The capacity query may have effects of its own. A zero return from this function therefore does not establish that nothing happened.

### Segment selection

At the start of each processing iteration, a zero remaining amount causes immediate return of the original requested amount.

For a nonzero remainder, the source object's `+0x4c` dispatch entry is invoked using the current segment reference and segment offset.

The returned segment amount and the remaining amount are then interpreted as **signed 32-bit integers** for comparison:

- If the signed segment amount is less than or equal to the signed remainder, the segment amount is selected. The iteration is initially classified as reaching a segment boundary.
- Otherwise, the remainder is selected. The iteration is initially classified as staying within the segment.

This is not an unsigned minimum. Values with bit 31 set can produce selections that do not correspond to an ordinary nonnegative amount bounded by the remainder.

### Raw-operation path

When the destination object is null:

1. F-ac3f8b08be7a is invoked with the source object's current segment reference.
2. Its returned 32-bit value is added to the source object's segment offset as read after that dependency returns.
3. The external three-argument operation is invoked with:
   - the derived address;
   - the current raw cursor;
   - the selected amount.
4. If that operation returns normally, the function proceeds to commit the full selected amount.

No return value from this external operation is inspected. There is no local short-transfer or failure handling on this path.

The external operation's argument meanings and copy direction are not established. In particular, the supplied body alone does not justify asserting conventional memory-copy semantics.

### Destination-object path

When the destination object is non-null:

1. F-ac3f8b08be7a is invoked with the source object's current segment reference.
2. A derived address is formed from its result and the source object's segment offset as read after the resolver returns.
3. The destination object's `+0x10` callback is invoked with the destination object, selected amount, and derived address.
4. Its 32-bit return value determines subsequent behavior.

There are three cases.

**Exact result.** If the callback result equals the selected amount bit-for-bit, that amount is accepted. The original segment-boundary classification is retained.

**Unequal result whose signed value is less than one.**

- If the remaining amount still equals the original request, the callback's result is returned directly as a 32-bit unsigned value.
- Otherwise, the source object's progress field at `+0x08` is read and copied to `+0x14`; the function returns the original request minus the remaining amount.

No ordinary iteration commit occurs for this case. The distinction between “initial” and “later” failure is implemented by comparing amounts, not by tracking whether a callback has previously run.

**Unequal result whose signed value is positive.** The callback result replaces the selected amount, and the iteration is forced to stay within the current segment.

There is no check that such a positive result is smaller than the selected amount or the remaining amount. A positive unequal result larger than requested is therefore accepted by the local logic.

### Committing an accepted amount

After an exact or positive unequal callback result, or after a normally returning raw operation, the function commits the accepted amount in this order:

1. Read the source progress field at `+0x08` and add the accepted amount.
2. Write the result to `+0x08`.
3. Write the same result to `+0x14`.
4. If staying within the segment, read the current segment offset.
5. Increment the function's local raw cursor by the accepted amount.
6. Update the segment cursor:
   - When staying within the segment, write the previously read offset plus the accepted amount to `+0x0c`.
   - When advancing, read the current segment reference, read its link at `+0x04`, write that link to `+0x10`, then write zero to `+0x0c`.
7. Subtract the accepted amount from the remaining amount and repeat.

The progress fields are written before the next-segment link is read. A failure while reading that link can therefore occur after progress has already changed.

The raw cursor is incremented even in destination-object mode, but it remains local and is not passed to that callback. The entry validation is not repeated.

### Arithmetic and termination

The amount variables and callback results are 32-bit quantities. Remaining-amount subtraction and returned progress differences use unsigned 32-bit arithmetic.

The supplied representation also performs additions involving signed integer fields and address-like integers. The apparent target behavior is 32-bit word arithmetic; portable signed-overflow semantics are not established by the supplied representation. Inputs requiring overflow of those signed expressions need target-specific clarification.

The loop has no local iteration limit or general progress check. For example, a zero segment amount with a positive ordinary remainder can cause a zero-length operation followed by segment advancement without reducing the remainder. Whether traversal eventually progresses or terminates depends on the segment structure and dependencies.

## Side effects

The function directly writes only these source-object fields:

- `+0x08`: progress after an accepted amount.
- `+0x14`: the same committed progress, or the current progress when returning after a later nonpositive callback result.
- `+0x10`: next-segment reference when advancing.
- `+0x0c`: updated offset or zero after advancing.

Dependencies run before these normal commit writes and can have additional effects. Their implementations are not supplied. They must not be assumed to preserve the source object, destination object, globals, segment structure, or memory ownership.

Several state values are deliberately read after dependency calls. Consequently, a dependency mutation can affect:

- the offset used to form the derived address;
- the progress value to which the accepted amount is added;
- the offset updated after processing;
- the segment reference used for advancement.

No allocation, release, reference-count change, or ownership transfer is directly visible in this function. That does not establish that dependencies perform none.

No rollback is visible. Effects of a dependency remain outside any local recovery mechanism, including when the function subsequently returns an error-like result.

## Acceptance examples

These are conditional static examples, **not executed tests**. Unless stated otherwise, dependencies return normally and do not mutate source state, arithmetic stays within ordinary nonnegative signed ranges, and all accessed memory is valid.

1. **Conflicting output arguments.** With a nonzero raw cursor and non-null destination object, F-a817d8d58c10 is invoked before the capacity query. No normal return is established.

2. **Request exceeds the gate.** A request of 9 and gate result of 8 produce return value zero. No segment query or processing operation is invoked, and this function performs no source-field writes.

3. **Zero request.** A zero request invokes the capacity query and returns zero. It performs no segment query or loop commit.

4. **Partial segment.** With request 3, segment amount 8, progress 10, and offset 2, successful processing accepts 3. Progress and its mirror become 13, offset becomes 5, and the segment reference remains unchanged. The return is 3.

5. **Exact boundary.** With request 4 and segment amount 4, an exact callback result of 4 advances to the segment link and sets offset to zero. The function returns 4 without another segment query.

6. **Initial callback failure.** If a positive selected amount receives callback result `0xffffffff`, the signed result is negative. With the remainder still equal to the original request, the function returns `0xffffffff`, not zero, and performs no normal commit.

7. **Failure after progress.** For request 10, suppose the first iteration accepts 4 and the next callback returns zero for a positive selected amount. The function copies current progress into its mirror and returns 4. The failing iteration does not advance the segment cursor.

8. **Positive short result.** With request 6, selected segment amount 6, and callback result 2, progress increases by 2 and offset increases by 2. The segment is not advanced, and processing continues with 4 remaining.

9. **Positive oversized result.** With request 2, selected amount 2, and callback result 3, the function accepts 3, stays within the segment, and obtains a remaining amount of `0xffffffff` by unsigned subtraction. It does not immediately return 2.

10. **Signed selection boundary.** With remaining amount 1 and segment amount `0x80000000`, the signed comparison selects `0x80000000` and initially classifies the iteration as reaching a boundary. Treating this as an unsigned minimum would contradict the supplied behavior.
