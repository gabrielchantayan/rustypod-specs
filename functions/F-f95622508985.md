# F-f95622508985

## Purpose

F-f95622508985 selects a position in a sequence of 48-byte records, requests transfers of preceding records when their signed 16-bit keys exceed the supplied signed 32-bit key, increments the container’s count, calls a dependency on the selected record, and writes the key’s low 16 bits there. When count has reached or exceeded capacity, it first attempts storage growth.

The inferred intent is insertion into an ascending-key array, with the new record cleared before its key is written. That successful-content interpretation requires valid caller state and suitable dependency behavior. The visible function does not establish that the clearing dependency writes zeros, that transfers preserve records, or that the selected address remains valid.

Important established properties are:

- Comparisons use the full signed 32-bit input key; storage retains only 16 bits.
- Existing equal-key records are not shifted past the new record.
- The growth ceiling is read at distinct evaluation points, not captured once.
- The storage dependency’s return value replaces the backing-address field before its reported status is checked.
- The output slot receives a locally selected address, or zero on an explicit early-error path. It does not independently certify storage validity or membership in the container’s backing storage at exit.
- The 64-bit return combines a status word with a path-dependent upper word.
- No rollback mechanism is visible.

### Container and record layout

| Byte offset from container address | Width | Observed interpretation |
|---|---:|---|
| 12 | 32 bits | Signed record count |
| 16 | 32 bits | Signed capacity |
| 20 | 32 bits | Backing-storage address |

Other container fields are not directly accessed.

Records have a 48-byte stride. The first two bytes of a preceding record are read as a signed 16-bit key and promoted for comparison with the input key. The remaining 46 bytes are not interpreted directly. Transfer requests cover all 48 bytes.

The final key write covers the first two bytes of the selected record. Byte order is not independently established by the supplied representation.

### Output and return

If execution reaches the common exit, the function performs one direct write to the output slot:

- Zero after capacity rejection or nonzero growth status.
- The locally selected address after the insertion path.

This output write follows the key write on the insertion path. External calls may have their own effects on the output slot if they can access it; their effects are unspecified.

The 64-bit return is a concatenation:

| Portion | Value |
|---|---|
| Low 32 bits | Final contents of the local status word |
| High 32 bits, without a storage-management call | Input key’s 32-bit representation |
| High 32 bits, with a storage-management call | Backing-address value read immediately before that call |

Capacity rejection occurs before a storage-management call, so its upper return word contains the input key. The upper word is neither uniformly a pointer nor uniformly a secondary status.

### Preconditions

Ordinary successful insertion requires:

- Accessible container fields and a writable output slot.
- Valid backing storage for every key read, transfer, clearing request, and key write.
- Dependency behavior compatible with the intended transfer, clearing, and storage-management operations.
- Arithmetic and address operations valid under the actual execution model.

Conventional sorted-container behavior additionally assumes nonnegative count and capacity, count no greater than capacity, and existing records ordered by their signed 16-bit keys. These conditions are not checked.

Aliasing the output slot with the container or record storage is not rejected. Its final write can overwrite state established earlier in the call.

## Behavior

### Initial reads and growth decision

The local status starts at zero, the prospective output address starts at zero, and the prospective upper return word starts as the input key’s representation.

The function first reads capacity, then reads count for a signed comparison.

- If capacity is greater than count, it skips growth.
- If capacity is less than or equal to count, it enters the growth path.

Thus count greater than capacity is not itself rejected. The growth calculation uses the cached capacity, not a fresh capacity read.

### Capacity-ceiling reads and rejection

The ceiling is an external signed 32-bit value. There is no established local snapshot of it.

The first ceiling read occurs only on the growth path. If that observed value is less than or equal to the cached capacity, the function:

1. Sets status to `0x40`, decimal 64.
2. Skips storage management and insertion.
3. Writes zero to the output slot.
4. Returns the input key’s representation in the high word and 64 in the low word.

There is no direct count, capacity, or backing-address update on this path. An aliased output slot can nevertheless overwrite one of those fields.

The broader meaning of status 64 is unknown.

### Growth proposal and conditional ceiling reads

If the first ceiling observation is greater than the cached capacity, the function calculates a proposed capacity by adding:

- The cached signed capacity.
- That capacity shifted right by two bits.
- Four.

For nonnegative capacity and representable arithmetic, this is:

**capacity + floor(capacity / 4) + 4**

It then evaluates the clamp conditions in this order:

1. Compare the proposal with the cached capacity.
2. Only if the proposal is not less than the cached capacity, read the ceiling again and compare whether that newly observed ceiling is less than the proposal.
3. If either condition succeeds, read the ceiling again and replace the proposal with this latest observation.

Consequently, the growth path has these ceiling-read patterns:

- Rejection: one read.
- Accepted growth without a clamp: two reads.
- Clamp caused by proposal less than cached capacity: two reads total; the upper-bound comparison is skipped.
- Clamp caused by the upper-bound comparison: three reads.

The value assigned during clamping need not equal the value that caused rejection to be bypassed or the value used in the upper-bound comparison. There is no subsequent validation of the assigned capacity against the count, cached capacity, or another ceiling observation.

The proposal-less-than-capacity condition resembles overflow handling. It does not establish portable signed-overflow behavior, nor does it prove all invalid arithmetic outcomes are detected.

### Storage-management call and status handling

After selecting the proposed capacity, the function reads the backing-address field. That value becomes the upper return word for the remainder of this invocation.

It calls F-6dd003795db7 with these arguments, in order:

1. Storage context.
2. Element size 48.
3. Cached original capacity.
4. Selected proposed capacity.
5. Backing address just read.
6. Address of the local 32-bit status word.

The dependency’s 32-bit return value is written to the container’s backing-address field before status is inspected.

If status is nonzero:

- Insertion is skipped.
- The output slot receives zero.
- No subsequent direct count or capacity update occurs.
- The backing-address replacement is not rolled back.
- The final low return word contains the status; the high word contains the pre-call backing address.

These statements do not exclude container changes made by the dependency itself.

If status is zero, the function writes the selected proposed capacity to the capacity field and proceeds. It does not independently reject a zero or otherwise unusable returned address.

### Position selection and transfer requests

On the insertion path, the function reads the backing-address field, then reads count to calculate the initial candidate:

**backing address + 48 × count**

For valid nonnegative count and sufficient storage, this is the position immediately after the existing records.

The backing address and candidate are retained locally. The function repeatedly:

- Tests whether the candidate is above the cached backing address.
- Only if that test succeeds, reads the signed 16-bit key 48 bytes before the candidate.
- Compares the signed 32-bit input key with that sign-extended record key.

If the input key is strictly smaller, F-U1 is called with:

1. Candidate address as destination.
2. Address 48 bytes before the candidate as source.
3. Byte count 48.

After a returning call, the candidate moves backward by 48 bytes. The next iteration again performs the address-boundary test before any preceding-key read.

The scan stops when the boundary test fails or the input key is greater than or equal to the preceding key. No preceding-key read is performed after a failed boundary test.

Under ordinary valid-container and transfer assumptions, records with greater keys move one position forward, and insertion follows existing equal-key records.

The cached backing address is not refreshed after transfer calls. The scan does not reread count during those calls.

### Count update, clearing request, and key write

After the scan:

1. Count is read again from the container.
2. That newly read value plus one is written back.
3. F-U2 is called with the selected address and byte count 48.
4. The low 16 bits of the input key are written to the selected address.
5. The selected address is written to the output slot.
6. The packed return is produced.

The count used here need not equal the count used to calculate the initial candidate, because intervening dependencies may have changed the field.

The count increment precedes F-U2 and the key write. F-U2’s exact byte effects are unknown: the visible call is not proof of zeroing. The function does not check a return status from F-U1 or F-U2 and shows no rollback if either call fails to return normally.

### Key-width consequences

For keys from −32768 through 32767, the comparison value agrees with the stored key’s later signed interpretation.

Outside that range, position selection and storage can disagree. For example, 32768 is greater than every signed 16-bit record key, but its low 16 bits represent −32768 when later read as signed 16-bit. The function neither rejects nor normalizes such inputs before comparing them.

## Side effects

### Direct effects and ordering

Depending on the path, the function directly:

- Reads capacity, count, backing address, and the external ceiling.
- Writes a storage dependency result into the backing-address field.
- Writes capacity only after observing zero growth status.
- Reads preceding records’ two-byte keys.
- Requests 48-byte transfers in reverse record order.
- Rereads and increments count after the transfers.
- Calls F-U2 before the two-byte key write.
- Writes the output slot at the common exit.

No direct release operation is visible.

### Ownership and pointer validity

The successful-path output is the locally selected address. Under valid storage and noninterfering dependency assumptions, it denotes the intended inserted record within the backing allocation.

That relationship is not unconditional. Transfer or clearing dependencies may alter the backing-address field, relocate or invalidate storage, or otherwise affect the selected address. The function does not reread the backing field to reconcile such changes before writing the key or output.

F-6dd003795db7’s ownership rules are unknown. The source does not establish whether old storage is released, retained, moved, or preserved. Returning the old backing-address bits in the upper word creates no established ownership right or release obligation.

### Interference and exceptional completion

External calls are boundaries with unspecified additional effects. They must not be assumed to preserve container fields, globals, storage validity, or retained references.

In particular, F-6dd003795db7 receives the status word’s address. Whether it retains or exposes that address is unknown. The low return word is the status value present at return, not a separately frozen success code.

No locking, transaction, exception recovery, or signal recovery is visible. Concurrent or reentrant mutation is not established as safe.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Content expectations assume valid arithmetic and storage, nonaliased output, successful normal returns, F-U1 copying the requested bytes, F-U2 zeroing the requested bytes, and dependencies preserving unrelated container state and local status. Growth-content expectations additionally assume successful storage management preserves existing records.

### Append without growth

With count 2, capacity 4, and keys 3 and 9, inserting 12:

- Makes no ceiling read, growth call, or transfer call.
- Selects the backing address plus 96.
- Changes count to 3 before calling F-U2.
- Under the clearing assumption, leaves key 12 followed by 46 zero bytes.
- Writes the selected address to the output slot.
- Returns high word 12 and low word zero.

### Insert before a larger key

With keys 3 and 9 and spare capacity, inserting 5 transfers the record keyed 9 forward by 48 bytes. The scan then reads key 3 and stops. Under the stated assumptions, the resulting keys are 3, 5, 9.

### Equal-key insertion

With keys 3, 5, 5, 9 and spare capacity, inserting 5 shifts only the final record. The new record follows both existing records keyed 5.

### Successful growth with stable ceiling

With count 8, capacity 8, and a ceiling that remains at least 14:

- The first ceiling read permits growth.
- The proposal is 14.
- The second ceiling read does not trigger a clamp.
- No third ceiling read occurs.
- The storage dependency is asked for capacity 14.
- Zero reported status permits the capacity write and insertion.
- The upper return word contains the pre-call backing address.

### Different ceiling observations during clamping

With count 8 and capacity 8, suppose the successive ceiling reads yield 20, 12, and 11:

- The first observation permits growth.
- The proposal is 14.
- The second observation triggers the upper-bound clamp.
- The third observation supplies the assigned proposal, 11.
- The storage dependency receives proposed capacity 11, not 12 or 20.

This case demonstrates that no single ceiling snapshot governs the request.

If instead the proposal-less-than-old-capacity condition holds under the execution model, the upper-bound comparison is skipped. The next ceiling read supplies the replacement proposal directly.

### Growth failure

If F-6dd003795db7 returns address P and leaves status 7:

- The backing-address field is written with P before status is checked.
- No insertion occurs.
- The output slot receives zero.
- No subsequent direct count or capacity write occurs.
- The return contains status 7 below the pre-call backing-address bits.

Dependency-originated state changes are not excluded.

### Capacity rejection

With count equal to capacity and the first ceiling observation no greater than capacity:

- Exactly one ceiling read occurs.
- No dependency is called.
- The output slot receives zero.
- The return contains status 64 below the input key’s representation.

### Out-of-range key

With existing key 0 and spare capacity, inserting 32768 selects the end without transferring that record. Its stored key is interpreted as −32768. Under ordinary content assumptions, the resulting signed-16-bit sequence is not ascending.

### Clearing-call interference

If F-U2 changes the container’s backing-address field and then returns, the function still writes the key and output using its previously selected address. Whether those accesses remain valid is unresolved. The output is not automatically adjusted to the changed field.
