# F-26bd5ca214f5

## Purpose

F-26bd5ca214f5 advances a mutable search state to the next candidate that produces a nonzero 16-bit result. It records the selected candidate and result in the supplied state object. If the initial state is ineligible for advancement, or the search reaches a dependency-reported stopping condition without selecting a candidate, it records an exhaustion sentinel and a zero result.

Two selection modes are established:

- **Direct mode:** derive the result from the candidate plus an adjustment, reduced to 16 bits.
- **Table mode:** read a two-byte, high-byte-first table value for the candidate, reject a raw zero value, and otherwise apply the adjustment and reject a zero adjusted result.

When the currently described range yields no selection, the function invokes F-0200cac86fa9. A nonnegative return permits another search iteration; a negative return ends the search.

An inferred interpretation is that the state describes successive mapping ranges and the dependency advances between them. The supplied evidence does not establish that domain meaning or the dependency’s actual state transitions.

## Interface

### Invocation and return

The function accepts one argument identifying a writable state object. The supplied representation carries this address in a 32-bit integer-sized parameter.

There is no explicit return value. The observable result is written into the state object.

The object must provide readable fields through offset `0x37` and writable result fields at offsets `0x18` and `0x1C`. If table mode is reached, the associated table storage must also be readable for every entry actually examined.

Null handling, bounds checking, alignment repair, allocation, and error reporting for invalid storage are not present in the supplied body. Valid addresses and suitable storage are preconditions, not checked outcomes.

### State layout

Offsets below are relative to the supplied state address. Field names are descriptive labels for this contract, not externally established names.

| Offset | Width | Interpretation |
|---|---:|---|
| `0x18` | 32 bits | Current candidate on entry; selected candidate or `0xFFFFFFFF` on completion |
| `0x1C` | 32 bits | Selected result, zero-extended from 16 bits; zero on exhaustion |
| `0x24` | 32 bits | Value read to construct the dependency’s second argument |
| `0x28` | 32 bits | Inclusive lower bound, compared as unsigned |
| `0x2C` | 32 bits | Inclusive upper bound, compared as unsigned |
| `0x30` | 32 bits | Additive adjustment; only its low 16 bits affect a selected result |
| `0x34` | 32 bits | Zero selects direct mode; nonzero is interpreted as a table base address |

The table contains two bytes per candidate position, starting at the current lower bound. Each entry is interpreted high byte first: the first byte supplies bits 15–8 and the second supplies bits 7–0. This table-byte ordering is established independently of the byte order used for the object’s 32-bit fields.

The supplied body does not establish a portable host-endianness or alignment contract for those 32-bit fields.

## Behavior

### Initial eligibility

The first relevant read is the 32-bit current-candidate field at `0x18`.

Advancement is attempted only if that unsigned value is below `0x0000FFFF`. The two comparisons in the supplied evidence jointly admit exactly the values from zero through `0x0000FFFE`.

Consequently:

- An entry value of `0x0000FFFE` is eligible and starts the search at `0x0000FFFF`.
- An entry value of `0x0000FFFF` is not eligible.
- Larger values, including `0xFFFFFFFF`, are not eligible.

If the entry value is ineligible, the function does not inspect range bounds, adjustment, or table mode, and does not call F-0200cac86fa9. It writes `0xFFFFFFFF` to `0x18`, then zero to `0x1C`, and returns.

The eligibility test is performed only once. It is not a general limit on candidate values reached later in the search.

### Candidate progression and range setup

For eligible input, the function starts with a working candidate one greater than the entry value. This increment cannot overflow: the largest eligible entry value is `0x0000FFFE`.

At the start of each search iteration:

1. The working candidate is compared with the current unsigned lower bound.
2. If it is smaller, it is raised to that lower bound.
3. The unsigned upper bound is read for this iteration.
4. Only if the candidate is at most that upper bound does the function inspect the mode field and scan the range.

The initial increment is not repeated after dependency calls. The working candidate remains local search state across those calls; it is not reloaded from `0x18`.

The lower-bound field can be read again while applying the clamp and while calculating a table address. With ordinary stable memory, these reads describe the same bound. The body provides no synchronization that would make concurrent changes safe or coherent.

### Direct mode

A zero field at `0x34` selects direct mode for the current scan.

For each candidate in the scan, the candidate and adjustment are added, and only the low 16 bits are retained. Thus the result is equivalent to addition modulo 65,536.

- A nonzero result selects the candidate.
- A zero result rejects it and advances the working candidate by one.

On selection, the function first writes the candidate to `0x18`, then writes the result as a 32-bit value to `0x1C`, and returns.

There is no table access in this mode.

The upper bound used by the inner scan is the value captured at the start of the iteration. The adjustment is read when evaluating a candidate; it is not captured once for the whole scan.

### Table mode

A nonzero field at `0x34` selects table mode for the current scan.

The initial table position is the table base plus twice the difference between the working candidate and the lower bound. Each rejected candidate advances the table position by two bytes.

For every examined entry:

- A raw 16-bit value of zero is rejected immediately. The adjustment is not read for that entry.
- A nonzero raw value is added to the adjustment, with the result reduced to its low 16 bits.
- An adjusted result of zero is rejected.
- Any other adjusted result selects the candidate.

On selection, the function writes the candidate to `0x18`, then the zero-extended result to `0x1C`, and returns.

A raw zero entry is therefore not interchangeable with a nonzero entry that becomes nonzero after adjustment. Zero is an unconditional table-entry rejection before adjustment.

The body may read the same entry bytes again when calculating the adjusted result after checking for raw zero. It does not promise one atomic 16-bit table read or a single read of each byte. Stable table contents are required for the ordinary entry-value interpretation above.

### Range exhaustion and dependency calls

If the working candidate is above the current upper bound, or the scan rejects all candidates through that upper bound, the function calls F-0200cac86fa9.

The call receives:

- The original state address.
- The 32-bit field at `0x24`, increased by one.

That field is read for each call. The caller does not itself store the incremented value back to `0x24`.

The dependency’s return value is interpreted as signed:

- A negative return ends the search.
- Zero or a positive return begins another iteration.

After a nonnegative return, the function reconsiders the working candidate against the then-current lower bound and obtains the then-current upper bound and mode as required. It does not reset the working candidate from the object’s current-candidate field.

If the dependency returns negatively, the function writes `0xFFFFFFFF` to `0x18`, then zero to `0x1C`, and returns.

### Integer boundaries and termination

Candidate values and range comparisons use 32-bit unsigned quantities. Scan increments therefore wrap from `0xFFFFFFFF` to zero.

This matters when the captured upper bound is `0xFFFFFFFF`: after rejecting that candidate, the unsigned candidate wraps to zero, which still satisfies the inclusive upper-bound comparison. The scan need not exit to the dependency. In table mode, the table position continues advancing by two bytes rather than being recalculated from the wrapped candidate.

No iteration limit or cycle detection is present. Termination requires a selection, a reachable negative dependency return, or initial ineligibility. Repeated nonnegative dependency returns without useful state changes can also prevent termination.

The addition used for the dependency’s second argument is represented as signed 32-bit addition. The evidence does not resolve its behavior at signed overflow. Likewise, address overflow and out-of-range table arithmetic have no established safe outcome.

## Side effects

The function’s explicit stores target only two fields:

- `0x18`: selected candidate or exhaustion sentinel.
- `0x1C`: selected nonzero result or zero.

These stores occur in that order. They are separate writes, not an atomic update. An observer can encounter an intermediate state between them.

Rejected candidates are not explicitly written to the current-candidate field. Before a dependency call, the object therefore need not reflect the working candidate or the progress of the current scan.

The explicit body does not write table contents, allocate storage, or release storage. This does not establish equivalent restrictions on F-0200cac86fa9.

Dependency calls may have additional side effects that are unknown here. In particular, the contract does not assume that the dependency preserves globals, retains object ownership, preserves table storage, or refrains from allocating or releasing memory. Any subsequent access after a nonnegative return requires the relevant object and table storage to remain valid.

The body provides no concurrency controls, transactional guarantees, or recovery for invalid memory accesses.

- Bytes `00 00`.
- Bytes `FF FF`.

Expected completion: candidate field `0x0000FFFF`, result field `0x0000FFFF`.

### Negative dependency result

Candidate `5` is rejected. The dependency is then called with the original state address and the field at `0x24` increased by one.

If the dependency returns negatively, expected final fields are `0xFFFFFFFF` and zero, regardless of earlier values in those two fields.

### Retained progress after a dependency call

Suppose a scan rejects candidate `5` and leaves its working candidate at `6`. The dependency returns nonnegatively and establishes a direct-mode range from `4` through `8`, with adjustment zero.

The next scan starts at candidate `6`, not `4` and not a value obtained by reloading `0x18`.

Expected completion: candidate field `6`, result field `6`, provided the dependency leaves valid storage.
