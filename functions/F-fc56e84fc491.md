# F-fc56e84fc491

## Purpose

F-fc56e84fc491 performs a two-stage lookup using a four-byte key and returns a four-byte result.

The first lookup has priority. Its result is interpreted as a pointer to a cell containing another pointer. If that cell supplies a non-null payload pointer, the function returns the four-byte value at that payload pointer without attempting the second lookup.

The second lookup is attempted only when the first lookup returns null or its returned cell contains a null payload pointer. The second lookup returns a payload pointer directly. A null result from this lookup produces a return value of zero.

The static evidence establishes this selection behavior. It does not establish the application-level meaning of the key, either lookup structure, or the returned value. “Lookup,” “cell,” and “payload” are descriptive terms, not claims about a particular container or ownership model.

## Interface

**Inputs**

- **Object address:** An address used to locate two embedded dispatch receivers, at byte offsets `0x50` and `0x24`.
- **Key:** An uninterpreted 32-bit value. The function copies this value into an addressable four-byte temporary before passing it to a lookup dependency.

**Output**

- One uninterpreted 32-bit value.
- Zero is returned when both lookup routes fail to provide a payload pointer.
- Zero can also be a successful payload value. The interface provides no separate success indicator.

**Width and representation**

The supplied representation uses 32-bit integer and result quantities. The first lookup’s returned cell is read as a 32-bit value and then interpreted as a pointer. Dispatch-table entries and addresses are also represented in a manner consistent with a 32-bit target.

This contract therefore describes the apparent 32-bit address model. It does not establish portability to a target with wider pointers. Endianness is not established; the function passes the address of the four-byte key rather than explicitly serializing it into a specified byte order.

The key has no visible range restriction. No signed comparison, arithmetic transformation, normalization, or byte-order conversion is applied to it.

**Required memory conditions**

For normal completion:

- The object address must support the receiver and dispatch reads actually reached.
- Every reached dispatch entry must identify a callable dependency with a compatible calling convention.
- Every non-null returned address that is subsequently dereferenced must refer to readable storage of the required width.
- Address formation, pointer representation, and alignment must be valid for the execution environment.

These are preconditions, not checks implemented by this function. A non-null address is not validated before use.

## Behavior

### First lookup

Before invoking any dependency, the function initializes a four-byte temporary with the original input key.

The first receiver is located at the object address plus `0x50`. The function reads the dispatch-table address stored at that receiver, then obtains the callable entry at byte offset `0x44` within that table.

It invokes the selected dependency with three arguments:

- The address of the first receiver itself, not the dispatch-table address.
- The address of the four-byte key temporary.
- The numeric length `4`.

The dependency’s result is interpreted as a cell address.

If that result is null, the function has no first-route payload pointer and proceeds toward the second lookup. It does not dereference the null result.

If the result is non-null, the function reads the first 32-bit word at that address and interprets that word as a payload pointer. No other part of the returned cell is inspected.

A non-null payload pointer selects the first route conclusively. The function reads one four-byte value from that pointer and returns it. The second lookup is not performed, including when the selected value is zero.

A null payload pointer causes the second lookup to be attempted.

### Second lookup

The second lookup is reached in exactly two ordinary cases:

- The first dependency returned a null cell address.
- The first dependency returned a non-null cell whose first word represents a null payload pointer.

Before dispatching the second lookup, the function writes the original input key into the same four-byte temporary again. Thus, an ordinary modification of the temporary through the first dependency’s key argument does not become the second lookup’s input key.

The second receiver is located at the object address plus `0x24`. Its dispatch-table address and the entry at table offset `0x44` are read when this route is reached, after the first dependency has returned. The function does not visibly cache this dispatch information before the first call.

The second dependency receives:

- The address of the second receiver.
- The address of the reinitialized key temporary.
- The numeric length `4`.

Unlike the first dependency’s result, the second dependency’s result is interpreted directly as a payload pointer. There is no intervening cell dereference.

If that pointer is null, the function returns the 32-bit value zero. Otherwise, it reads one four-byte value at the pointer and returns that value.

### Ordering and conditional access

The established sequence of relevant operations is:

1. Initialize the temporary from the input key.
2. Resolve and invoke the first dependency.
3. If its result is non-null, read the first word of its returned cell.
4. Either read the selected first-route payload, or reinitialize the key and resolve and invoke the second dependency.
5. On the second route, either return zero for a null pointer or read the selected payload.

The second receiver and its dispatch information are not accessed on a successful first route. Consequently, unusable second-route storage does not itself prevent a first-route return, provided it does not interfere with another required access.

Conversely, a first-route payload read that faults does not trigger fallback. Fallback depends on null pointer results, not on whether a non-null pointer can safely be read.

The second dependency can observe object or global state changed by the first dependency. No preservation of that state is established.

## Side effects

The function’s explicit writes are to its four-byte temporary:

- One initialization before the first lookup.
- One restoration to the original key before the second lookup, if reached.

There is no explicit write to the supplied object, either returned cell, or selected payload. This does not establish that the complete operation is read-only: both dependencies receive receiver addresses and an addressable key buffer, and their effects are unknown.

The dependencies may modify the key temporary during their calls. A second-route dependency’s modification is not subsequently used as a key by this function. However, returned storage may alias other storage; the function imposes no visible non-aliasing requirement. Reads through a returned pointer observe the contents at the time of the read.

The function performs no explicit allocation, release, ownership transfer, reference-count adjustment, locking, or cleanup. No ownership or lifetime guarantee can be inferred for memory returned by either dependency.

The key buffer has local lifetime. The function does not arrange persistent storage for it. Whether a dependency retains its address is unknown; use of that address after the local lifetime ends is not supported by any visible lifetime mechanism here.

No explicit error reporting or recovery is present beyond returning zero when the second route supplies no pointer. Dependency failures, invalid dispatch targets, invalid pointer reads, and other abnormal control transfers are not caught in the supplied body.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. All mentioned storage and callable targets are assumed valid unless a case explicitly concerns invalid access.

1. **First route supplies a value.**  
   F-indirect-01 returns a non-null cell containing a non-null payload pointer. That payload holds `0x12345678`. The result is `0x12345678`; F-indirect-02 is not called.

2. **First route supplies zero.**  
   The first cell contains a non-null pointer to a four-byte zero value. The result is zero, with no second lookup. A zero payload is not a miss.

3. **First cell address is null.**  
   F-indirect-01 returns null. F-indirect-02 returns a direct pointer to `0x89ABCDEF`. The result is `0x89ABCDEF`.

4. **First cell contains a null pointer.**  
   F-indirect-01 returns a valid cell whose first word is zero. The second lookup is attempted. If its result is null, the final result is zero.

5. **The second result is direct storage.**  
   F-indirect-02 returns a pointer to a word containing `0x10203040`. The function returns `0x10203040`; it does not interpret that word as another address.

6. **The first dependency changes the key buffer.**  
   The original key is `0x11223344`. F-indirect-01 overwrites the supplied temporary with another value and returns null. Before F-indirect-02 is invoked, the temporary is restored to `0x11223344`. This assumes normal execution without unrelated memory corruption.

7. **The first dependency changes fallback dispatch state.**  
   F-indirect-01 changes the second receiver’s dispatch-table reference and returns null. The second dispatch uses the subsequently read state, provided that state remains valid.

8. **Fallback storage is unusable but unnecessary.**  
   The first route supplies a valid payload pointer. The function returns its value without inspecting the second receiver’s dispatch information.

9. **A non-null payload pointer is invalid.**  
   The first cell supplies an unreadable non-null address. The function attempts the payload read; it does not fall back merely because the address is invalid. The resulting platform-specific failure is not converted into a normal zero result.
