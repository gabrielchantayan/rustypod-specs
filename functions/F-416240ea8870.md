# F-416240ea8870

## Purpose

F-416240ea8870 conditionally retrieves a 32-bit value from an indirectly referenced record.

The function first invokes a dynamically selected dependency, passing its own input pointer. A zero result from that dependency produces a zero return without reading the record reference or the requested record field. Any nonzero result causes the function to obtain the record reference from the input object and return the 32-bit value at byte offset 112 within that record.

The dependency therefore controls whether the field is read. Its semantic role—such as readiness check, initialization, or validation—is unknown. No such interpretation is required by this contract.

## Interface

### Input

The function accepts one pointer to an object-like memory region. The supplied representation treats that region as an array of 32-bit integer-sized words.

The following layout elements participate in the behavior:

| Location | Width or representation | Role |
|---|---|---|
| Input object, byte offset 0 | 32-bit address-bearing word in the supplied representation | Base address used to locate the indirect callable |
| Dispatch base, byte offset 8 | Callable pointer; native width is not independently established | Dynamically selected dependency |
| Input object, byte offset 8 | 32-bit address-bearing word in the supplied representation | Base address of the record, read only after a nonzero dependency result |
| Record, byte offset 112 | 32 bits | Value returned on the nonzero path |

The two uses of byte offset 8 refer to different bases: one is relative to the dispatch base, and the other is relative to the input object.

The indirect dependency receives the same input pointer supplied to F-416240ea8870. It is not passed a copy of the object or the record reference.

### Output

The function returns a 32-bit value:

- Exactly zero when the dependency returns zero.
- The 32-bit contents of the selected record field when the dependency returns nonzero and the subsequent reads complete normally.

The field value is returned without an explicit conversion, mask, range check, or normalization. The supplied representation does not establish its application-level type. It may be an integer, flags, a handle, an address representation, or another 32-bit quantity.

A zero return does not distinguish a zero dependency result from a successful field read whose contents are zero.

### Preconditions

For normal completion, the input pointer must permit the initial object access, the dispatch-base value must permit the callable-pointer access, and the selected target must be callable with the supplied argument and a compatible return convention.

On the nonzero path, the object must also remain accessible for the record-reference read, and the resulting record address must permit a 32-bit read at byte offset 112.

The function contains no explicit checks for null pointers, invalid addresses, insufficient object size, alignment, or an invalid callable target. Behavior when these preconditions fail is not defined by the supplied evidence.

## Behavior

### Dispatch and dependency invocation

Before the dependency runs, the function obtains the dispatch-base value from the beginning of the input object. It uses byte offset 8 from that base to obtain the indirect callable, then invokes that callable with the original input pointer.

The callable is selected before invocation. A change made by the dependency to the object's dispatch-base field does not cause this invocation to be redirected or repeated.

For specification purposes, the selected callable is identified as **F-INDIRECT-01**. This is a specification-local opaque dependency ID, not an established identity for a particular implementation.

### Conditional result

The dependency's result is treated as a 32-bit integer and compared with zero. There are two paths:

- **Zero:** return the 32-bit value zero. The function does not proceed to read the record reference or the record field.
- **Nonzero:** read the record reference from the third 32-bit word of the input object, then read and return the 32-bit field at byte offset 112 from that reference.

All nonzero dependency results select the same path. A negative result is not treated as a separate error case. The function does not return the dependency's nonzero result.

### Post-call state

The record reference is read after the dependency returns. It is not captured before the call.

Consequently, a dependency that changes the record reference can affect which record is consulted. If the dependency leaves a valid new reference in the object and returns nonzero, the field read uses that new reference. If it invalidates the object or record reference and returns nonzero, the function has no visible recovery or validation step.

Likewise, changes made by the dependency to the target field before returning can affect the returned value. No earlier field snapshot is visible.

### Observable access order

For ordinary execution without faults, the established order is:

1. Read the dispatch-base value from the input object.
2. Read the callable pointer at byte offset 8 from that base.
3. Invoke F-INDIRECT-01 with the original input pointer.
4. Examine its returned result.
5. Only for a nonzero result, read the record reference from the input object.
6. Read the 32-bit field at byte offset 112 from that record.
7. Return the selected 32-bit result.

This order does not describe accesses performed inside F-INDIRECT-01. That dependency may itself access the object, record, or unrelated state.

### Widths and address arithmetic

The supplied representation establishes 32-bit widths for the indexed object words, the dependency result used in the comparison, the selected field, and the function result. The object indexing places its third word at byte offset 8.

The dispatch and record offsets are byte offsets, not counts of pointer-sized entries. In particular, the callable's location is described as dispatch base plus 8 bytes; the evidence does not justify interpreting it as a particular numbered method under an independently assumed pointer width.

No checked arithmetic is visible for either address calculation. The evidence does not establish behavior when an address calculation exceeds the valid address range. Modular wrapping, trapping, and portability to a wider address model are not acceptance guarantees.

## Acceptance examples

These are conditional behavioral examples derived from static evidence. They are not reports of executed tests.

### Zero dependency result skips the record access

Given valid input and dispatch storage, if F-INDIRECT-01 returns zero normally, the function returns zero.

The record reference need not be readable for this function's own skipped record access. This does not excuse any record access performed by the dependency itself.

### Positive nonzero result selects the field

If F-INDIRECT-01 returns 1 and the post-call record reference identifies a readable record whose field at byte offset 112 contains 37, the function returns the 32-bit value 37.

The dependency result 1 is not itself returned.

### Negative nonzero result also selects the field

If F-INDIRECT-01 returns a negative 32-bit result and the post-call field contains 37, the function returns 37, provided the required accesses complete normally.

No separate negative-result error path is visible.

### Dependency replaces the record reference

Suppose the object initially refers to one record. During the call, F-INDIRECT-01 changes the object's record reference to a second valid record and returns nonzero.

The function reads the second record's field at byte offset 112. The first record's field does not determine the return value.

### Field contents are preserved

If the dependency returns nonzero and the selected field contains the 32-bit pattern `0xFFFFFFFF`, the function returns that pattern. Its interpretation as a signed number, unsigned number, or another value type is outside the established contract.

If the selected field instead contains zero, the function returns zero despite taking the nonzero dependency path.

### Invalid post-call record reference

If the dependency returns nonzero but leaves an inaccessible record reference, no successful return value is guaranteed. The function does not visibly convert the resulting access failure into a zero return.
