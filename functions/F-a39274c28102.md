# F-a39274c28102

## Purpose

F-a39274c28102 invokes an object-selected indirect target, constructs a temporary four-field record, and conditionally passes that record through an ordered dependency sequence. It returns a 64-bit value assembled from the record’s final first two 32-bit fields.

The initial invocation is unconditional on every normally executing path. Its second argument is a value read from external global storage after the indirect target has been captured and before that target is invoked. The evidence does not establish that this global value is constant or immutable.

The conditional sequence depends on a dependency result, the low byte of an object field, and an externally referenced flag. If those conditions pass, processing can include an associated reference and a separately obtained recipient.

“Eligibility,” “associated reference,” and “recipient” describe observable roles only. An application-level interpretation such as notification, dispatch, or registration is **inferred intent**, not established behavior.

## Interface

### Inputs

The visible interface has four arguments:

| Argument | Visible representation | Established use |
|---|---|---|
| Object reference | Pointer in the represented 32-bit layout | Supplies the indirect-call table, object fields, and an interior address |
| Second argument | 32-bit value | No visible use |
| Third argument | 32-bit value | No visible use |
| Payload | Opaque 32-bit value | Initializes the fourth field of the temporary record |

The second and third arguments are not explicitly read or forwarded. No restrictions on their values follow from the visible body.

The representation uses four-byte integer elements and 32-bit pointer-bearing fields. The offsets and return composition below describe that representation; a different-width interface is not established.

### Object accesses

| Byte offset | Access width | Role |
|---|---:|---|
| `0x00` | 32 bits | Reference to an indirect-call table |
| `0x34` | 32 bits | Associated reference, captured only after eligibility succeeds |
| `0x80` | No direct access established | Interior address supplied as data and as a dependency argument |
| `0xA0` | 32 bits, then narrowed to eight bits | Object contribution to eligibility |

The indirect target is read from byte offset `0x180` in the table referenced at object offset `0x00`.

Computing the address at object offset `0x80` does not itself read the contents at that address. The evidence establishes neither the size nor the type of the region beginning there.

### External inputs

Two distinct external-state inputs are visible:

- **Callback-argument storage:** global storage whose current value supplies the initial indirect invocation’s second argument. The read occurs after target capture and before invocation. Its value, width, and semantic type are not established.
- **Eligibility-flag reference:** external pointer-bearing storage whose referenced character-sized value is tested only if the preceding eligibility conditions succeed.

The callback argument is passed as a value obtained from storage. The source does not establish an address-of operation for that storage, nor does it establish that the stored value cannot change.

### Temporary record

The function initializes a contiguous, invocation-local record with four 32-bit fields:

| Record offset | Initial contents |
|---|---|
| `0x00` | Original object reference |
| `0x04` | Original object reference plus `0x80` bytes |
| `0x08` | Indirect target captured before the initial invocation |
| `0x0C` | Payload argument |

Dependencies receiving the record receive its address. They do not receive a detached copy through this interface. The visible function does not restore the initialized contents after dependency calls.

### Output

The 64-bit result contains:

- The final first record field in bits 31–0.
- The final second record field in bits 63–32.

This is a bit-pattern concatenation of two 32-bit values. Neither field is dereferenced to form the result, and neither is sign-extended into the other half.

If those fields remain unchanged after initialization, the result packs the original object reference into the low half and its `0x80`-byte interior address into the high half. If dependencies modify either field and those changes survive until return, the modified values are returned.

No separate success or error indicator is established.

## Behavior

### Initial target capture, global read, and invocation

The function first reads the object’s table reference and then captures the indirect target at table offset `0x180`.

After that capture, it reads the callback-argument value from external global storage. It invokes the captured target with the original object reference and that read value.

This ordering matters:

- The target is selected before the global argument value is read.
- The global argument value is read before the target is invoked.
- The invocation precedes both record initialization and the eligibility dependency.
- The invocation’s return value is not consumed.

The global read is not evidence of an immutable constant. Subject to otherwise unspecified synchronization rules, different invocations can observe different stored values.

The captured target is retained for later placement in the record. Changes made by the callback to the object’s table reference or table entry do not cause the function to reload the target for that record field.

The source does not establish that the callback preserves the object, global storage, referenced resources, or their validity.

### Record initialization

After the initial invocation returns normally, the function initializes the record in field order: original object reference, computed interior address, captured target, and payload.

The interior address is formed from the original input reference using a byte displacement of `0x80`. It is not loaded from an object member.

The target stored in the third field is the value captured before the invocation. The visible function does not invoke that target again through the record.

### Short-circuit eligibility checks

The function calls F-3fac671648b8 without explicit arguments and tests its result for zero.

Only if that result is nonzero does it read the 32-bit object field at offset `0xA0`. It narrows that value to eight bits and requires the narrowed value to be zero. Thus, the upper 24 bits do not affect eligibility.

Only if both conditions pass does the function obtain the external eligibility-flag reference and read the character-sized value it designates. That value must be nonzero.

The observable order is therefore:

1. Call F-3fac671648b8.
2. Conditionally read and narrow the object field.
3. Conditionally obtain and dereference the external flag reference.
4. Enter record processing only if all three conditions pass.

A failed condition skips every remaining eligibility read and the entire conditional dependency sequence, as applicable. Execution then proceeds to return composition.

The object and external-state checks use values available after the initial callback and after F-3fac671648b8. No entry-time snapshot of those values is established.

### Capture the associated reference and process the record

When eligibility succeeds, the function reads the 32-bit associated reference at object offset `0x34` and saves it.

It then calls F-e57b05520b65 with:

- The temporary-record address.
- The original object reference plus `0x80` bytes.
- That same interior address again.

The second and third arguments are equal computed addresses, not two separately loaded object fields. They are based on the original input reference, not on the record’s possibly mutable first field.

The associated reference is captured before this call. A change to object offset `0x34` during the call does not replace the captured value used by the next step.

The call’s return value is not consumed.

### Optional associated-reference processing

If the captured associated reference is nonzero, the function calls F-ee8733a08210 with the temporary-record address and the captured reference adjusted by `0xD0` bytes.

The adjustment is a byte displacement of `0xD0`, not a displacement scaled by the object’s four-byte element size. It is evaluated only for a nonzero captured reference.

A zero associated reference skips only this call. It does not prevent recipient lookup.

The representation uses a 32-bit integer for this saved reference and its adjustment. No overflow check is shown. The source does not establish a portable result for an overflowing adjustment or establish that an adjusted address remains valid.

### Recipient lookup and ordered processing

Next, the function calls F-ffe0d92c57b7 with the original object reference.

A zero result suppresses both remaining calls. A nonzero result is saved and supplied, with the same temporary-record address, to:

1. F-c9b5d17d8d1e.
2. F-4d037ecf0f82, after the preceding call returns normally.

There is no second lookup between these calls. The saved recipient value is reused even if the first call changes object state or lookup-related external state.

Record modifications from earlier calls remain available to later calls unless a dependency changes them again. In particular, the function does not reset the record between the two recipient-processing calls.

### Return composition

After the selected calls return normally, the function reads the first two record fields and combines their 32-bit patterns into the 64-bit result.

The remaining two fields do not directly contribute to the result. Their possible influence through dependency behavior is unknown.

## Side effects

### Direct effects

The visible body:

- Reads the object’s table reference and the selected table entry.
- Reads the initial callback’s second argument from external global storage.
- Invokes the captured indirect target once.
- Writes the four temporary-record fields.
- Calls F-3fac671648b8.
- Performs short-circuit-dependent object and external flag reads.
- Conditionally reads the associated reference and invokes the remaining dependencies.
- Reads the final first two record fields to form the result.

No direct write to the object, callback-argument storage, or eligibility-flag storage appears. This does not make the overall operation read-only: dependency effects are not established.

### Ownership and lifetime

The visible body contains no explicit allocation or release.

The record has invocation-local lifetime. Passing its address establishes access during dependency calls, not permission to retain that address after the function returns.

No ownership transfer, borrowing convention, reference counting, resource release, or retention policy is established for the object, interior address, associated reference, recipient, or payload. Unknown callees must not be assumed to preserve globals or to own, retain, or release memory.

A nonzero reference is only a control-flow condition here; it is not proof of validity.

### Preconditions and failures

Normal execution requires a readable initial object field, a readable selected table entry, accessible callback-argument storage, and an invocable selected target.

Further requirements depend on the path:

- If F-3fac671648b8 returns nonzero, object offset `0xA0` must be readable.
- If its low byte is zero, the external flag reference and referenced byte must be readable.
- If eligibility succeeds, object offset `0x34` must be readable.
- Every invoked dependency must receive arguments satisfying its own, otherwise unknown requirements.

The original object is reused after intervening calls. Callers and dependencies must provide whatever lifetime guarantees are needed for those later accesses; this function does not establish them.

No local error conversion, retry, rollback, exception handling, or recovery is visible. Faults, invalid addresses, abnormal returns, and nonlocal exits have no established outcome in this contract.

## Acceptance examples

These are conditional consequences of the static evidence, not runtime observations. Each assumes valid required memory and normal return from invoked dependencies.

1. **Callback argument changes between invocations.**  
   If callback-argument storage contains value A at one invocation’s read and value B at another’s, the respective indirect calls receive A and B. The contract does not replace either value with a fixed constant.

2. **Callback changes its argument’s backing storage.**  
   The callback receives the value read before invocation. If it subsequently changes that global storage, the visible function performs no second read of that storage. This does not imply a deep copy or constrain effects on objects that the value might reference.

3. **Initial callback changes the table entry.**  
   The third record field still receives the target captured before the callback. The changed table entry is not reloaded for record initialization.

4. **First eligibility result is zero.**  
   The callback and record initialization still occur. F-3fac671648b8 runs, but the object eligibility field and external flag are not read by the conditional expression. No later listed dependency runs. The initialized first two fields form the result.

5. **Only upper eligibility bits are set.**  
   With a nonzero first eligibility result and object field `0x00000100`, narrowing yields zero. The external flag is examined; this object value does not itself reject eligibility.

6. **The low eligibility byte is nonzero.**  
   With object field `0x00000001` and a nonzero first eligibility result, processing stops at the object check. The external flag is not read, and conditional record processing is skipped.

7. **External flag is zero.**  
   If the preceding checks pass but the referenced flag byte is zero, none of the conditional processing dependencies runs.

8. **Associated reference is zero; recipient is nonzero.**  
   F-e57b05520b65 runs, F-ee8733a08210 is skipped, and F-ffe0d92c57b7 still runs. Its nonzero result causes both recipient-processing calls in order.

9. **Associated field changes during record processing.**  
   If a valid nonzero associated reference is captured and F-e57b05520b65 then clears the object field, F-ee8733a08210 still receives the captured reference adjusted by `0xD0`.

10. **Return-bearing fields are modified.**  
    If a dependency leaves the first field as `0x11223344` and the second as `0x55667788`, with no later changes to them, the result is `0x5566778811223344`.

11. **Recipient state changes during the first recipient call.**  
    The second recipient call still receives the previously saved nonzero value. No new lookup occurs. Its validity after the first call remains a dependency-specific requirement.
