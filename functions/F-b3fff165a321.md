# F-b3fff165a321

## Purpose

F-b3fff165a321 conditionally removes a selected node from a linked tree structure, performs color-dependent structural repair, places the original selected node on a separate linked list, decrements a four-byte count, and writes a four-byte result to caller-provided storage.

The links, boundary caches, and color operations are consistent with red-black-tree deletion. That classification is **inferred intent**. The contract below specifies the visible operations rather than substituting a conventional tree algorithm.

An initial dependency controls whether removal occurs. A nonzero decision result bypasses the directly implemented removal work and returns the structure’s header reference as reread after that dependency.

Under stable, valid topology, the visible deletion branches establish a nonnull repair position: a surviving child, the removed leaf’s parent, a successor’s surviving right child, or the relocated successor itself. Missing siblings cause upward propagation through the retained parent; they do not independently establish a null repair position. Invalid references, inconsistent topology, or unknown dependency mutations remain possible causes of invalid access.

## Interface

### Arguments and result

The function accepts three arguments:

1. **Result storage:** an address receiving one four-byte value on normal completion.
2. **Structure address:** a 32-bit address-like value identifying mutable structure state.
3. **Selection storage:** an address containing a four-byte selected-node reference.

There is no explicit return value. Observable results consist of the final result-storage write, direct memory mutations, and dependency effects.

Selection storage is read before the initial decision call and again after a subsequent dependency on the removal path. The node actually removed therefore need not equal the reference read initially.

### Directly accessed layout

Offsets are in bytes. References and count fields occupy four bytes; colors occupy one byte.

“First” and “last” describe the boundary roles implied by the link operations. No key comparison, ordering relation, payload layout, or complete object size is established.

The header acts as a distinguished reference. In the single-node leaf case, the function writes the header reference into both boundary caches and zero into the root field.

### Preconditions and failure model

The function performs no general argument validation. Normal completion requires readable input storage, writable output storage, valid accessed fields, terminating child-chain traversals, and satisfaction of dependency preconditions.

The behavior descriptions assume ordinary, distinct layout fields and no aliasing that changes later reads unexpectedly. The function does not enforce those assumptions. In particular, selection storage, result storage, structure fields, and node fields are not checked for overlap.

Null children and null siblings have explicit handling. That does not make arbitrary null arguments or inconsistent parent links valid.

No explicit error code, rollback, exception translation, or recovery path is visible. Invalid accesses, nonterminating topology, or nonreturning dependencies can prevent the final output write after partial mutation.

## Behavior

### 1. Decision and result preparation

The function first reads the four-byte selection reference into a temporary slot, then reads the structure’s header reference into another temporary slot. It passes both slot addresses to F-f063d8ade9f7 and examines its integer result.

If the result is nonzero:

- The header reference is reread from the structure.
- That reread value is written to result storage.
- No directly implemented unlinking, color repair, list insertion, or count decrement occurs.

This branch does not imply that the dependency left the structure unchanged.

If the result is zero:

- F-34e6a1a966cb receives the address of the first temporary slot.
- After that call, selection storage is reread.
- This later selection reference identifies the node used for removal.

The temporary slot supplied to those dependencies is also the source of the eventual removal-path output. The visible structural operations do not compute a new output value or directly overwrite that slot. Its meaning—successor, iterator, original selection, or something else—is not established.

Both initial dependencies receive addresses of temporary storage. Their ability to alter those slots or other reachable state must not be excluded. Whether either dependency retains an address is **documented_only**.

### 2. Choosing the structural replacement

The selected node’s left link is examined first.

- **No left child, nonnull right child:** the right child is the replacement.
- **Nonnull left child, no right child:** the left child is the replacement.
- **Both children present:** starting at the right child, left links are followed until a node with no left child is reached. This node is called the structural successor. Its right child is the replacement at its former location.
- **Neither child present:** the separate leaf-disconnection path applies.

With two children, the successor is moved into the selected node’s position. No visible payload copy occurs. The original selected node remains the node eventually inserted into the removed-node list.

### 3. Leaf disconnection

For a childless selected node, its parent becomes the repair position.

If that parent equals the structure’s header reference, writes occur in this order:

1. The header’s last-node cache receives the parent/header reference.
2. The header’s first-node cache receives that reference.
3. The header’s root becomes zero.

The header address is obtained through the structure field for these accesses; it is not specified as an immutable entry snapshot.

Otherwise, the parent’s left link is compared with the selected node. If equal, that left link is cleared. If unequal, the right link is cleared without a separate membership check.

The clearing uses four one-byte zero stores in increasing address order. This is observably different from specifying one indivisible four-byte store.

The cleared side determines which boundary cache is inspected:

- Clearing the left link selects the first-node cache.
- Clearing the right link selects the last-node cache.

If that cache equals the selected node, it is changed to the parent. The opposite cache is not updated on this path.

### 4. Direct replacement by one child

When the selected node itself is structurally removed and a replacement child exists, the following mutations occur:

1. The replacement child receives the selected node’s parent.
2. If the header root identifies the selected node, the root receives the replacement.
3. Otherwise, the selected node’s parent is examined. Its left link is replaced if it identifies the selected node; otherwise its right link is replaced.
4. The first-node cache is conditionally updated.
5. The last-node cache is conditionally updated.

A boundary cache is changed only if it currently identifies the selected node.

For the first-node cache:

- If the selected node has no right child, the cache receives the selected node’s parent.
- Otherwise, a leftmost-node search begins at the replacement child, and the resulting reference is stored.

For the last-node cache:

- If the selected node has no left child, the cache receives its parent.
- Otherwise, a rightmost-node search begins at the replacement child.

These are the established branches, including their parent-reference alternatives. They must not be replaced by a generalized boundary recomputation.

The surviving replacement child is the repair position.

### 5. Successor relocation

When the successor differs from the selected node, mutation proceeds in this order:

1. The selected node’s left child receives the successor as parent.
2. The successor receives the selected node’s left-child reference.
3. The successor’s former position is handled.
4. The selected node’s incoming root or parent link is redirected to the successor.
5. The successor receives the selected node’s parent.
6. The successor and selected node exchange color bytes.

Handling the successor’s former position depends on whether it is the selected node’s immediate right child.

**Immediate right child:** if the successor has a right child, that child receives the successor as parent. There is no separate detachment from a deeper parent.

**Deeper successor:**

- Its nonnull right child, if present, receives the successor’s former parent.
- The former parent’s left link receives that right-child reference, including zero when absent.
- The successor receives the selected node’s right-child reference.
- That right subtree receives the successor as parent.

The incoming link is redirected using the same root-first, otherwise-parent-left-test rule as direct replacement.

The repair position is the successor’s former right child when nonnull. Otherwise, the relocated successor itself becomes the repair position. Thus absence of that child does not leave a null repair position.

After the color exchange, the original selected node carries the successor’s former color. That is the color tested by the repair gate. This relocation branch contains no explicit boundary-cache update.

### 6. Color-dependent repair

Repair is entered only when:

- The repair position differs from the structure’s current header reference; and
- The color of the node destined for the removed-node list is nonzero.

The gate accepts any nonzero color, not just 1.

Within repair, each iteration first checks whether the repair position equals the current root. If so, it proceeds to the final color write without needing to inspect that position’s existing color. Otherwise, propagation continues only while the position’s color equals exactly 1. A different color also leads to the final write.

The final repair write sets the current repair position’s color to 1.

The operations suggest that 0 means red and 1 means black, but those names are **inferred intent**. Tests involving children distinguish absence or exactly color 1 from other values; arbitrary nonzero colors are not universally treated as 1.

#### Direction and missing siblings

If the repair position is its parent’s left child, the sibling is the parent’s right child. Otherwise, the sibling is the parent’s left child.

In both directions, an initially null sibling is detected before its color is read. The retained reference still identifies the parent. The current repair position is recolored to 0, and repair continues from that parent.

After processing a color-0 sibling through a dependency call, the parent is reloaded from the current position before the sibling is reread. If that sibling is now absent, propagation again uses the reloaded parent.

Consequently, neither initial missing-sibling direction propagates through a null reference merely because the sibling is absent. No such structural null-repair path is established under stable, valid topology.

#### Present sibling

A sibling of color 0 is first changed to 1, and the parent is changed to 0. A direction-specific dependency is called. The current position’s parent and the corresponding sibling are then reread.

For a present sibling, its children are evaluated as follows:

- If both are absent or have color exactly 1, the sibling becomes color 0 and repair moves to the current position’s parent.
- Otherwise, if the sibling’s outer child is absent or color 1, a preliminary transformation occurs: the inner child is changed to 1 when present, the sibling becomes 0, and the complementary dependency is called.
- The sibling is then reread. If it is absent after this preliminary call, repair proceeds directly to the final color-1 write on the current position, rather than taking the missing-sibling propagation branch.
- With a present finishing sibling, the sibling receives the parent’s color, the parent becomes 1, and the outer child becomes 1 when present. A final direction-specific dependency is called, followed by the final color-1 write on the current repair position.

For a left-child repair position, “inner” means the sibling’s left child and “outer” its right child. For the opposite direction, these meanings are reversed.

Dependency-induced mutations can affect every explicitly reread parent, sibling, or root. The visible body does not establish those dependencies’ complete invariants.

### 7. List insertion, count, and output

After structural work and any completed repair, operations occur in this order:

1. The original selected node’s offset-12 field receives the structure’s current removed-list head.
2. The structure’s removed-list head receives that node.
3. The count is read and decremented by one, with a four-byte result stored back.
4. Result storage receives the temporary output-slot value.

The list head and count are read at this stage, not preserved from entry.

The count operation is represented as a 32-bit integer subtraction by one. There is no zero check, saturation, or underflow error branch. The source does not establish a portable signed-overflow policy at the minimum signed value; unconditional modular-counter semantics must not be assumed.

The removed node’s right-child field becomes its list link. Its parent and left-child fields are not cleared by this final insertion.

## Acceptance examples

These are conditional static expectations, not executed tests.

1. **Decision bypass.** If F-f063d8ade9f7 returns nonzero, normal completion writes the header reference reread after that call. The function performs no direct removal or count decrement. Dependency mutations remain possible.

2. **Single-node leaf.** With stable valid state and the selected leaf’s parent equal to the header, the last cache is written first, then the first cache, then the root is cleared. Repair is skipped because its position is the header. The selected node is prepended to the removed list and the count is decremented.

3. **Leaf on a parent’s left side.** The incoming left link is cleared through four ascending-address byte writes. If the first-node cache identifies the leaf, it becomes the parent. The parent—not a null child—is the repair position.

4. **One surviving child.** With a nonnull sole child and valid links, that child receives the selected node’s parent and replaces its incoming reference. It is also the repair position. Boundary updates follow the explicit cache branches.

5. **Immediate successor without a right child.** When both selected-node children exist and the right child has no left or right child, that right child is relocated. The relocated successor itself becomes the repair position. The original selected node is placed on the removed list.

6. **Deeper successor with a surviving right child.** The successor’s former parent receives that child in its left link, and the child receives the former parent. The successor takes the selected node’s position. Repair starts at the surviving child.

7. **Missing sibling in either direction.** If a nonroot color-1 repair position has a null opposite sibling, its color becomes 0 and repair proceeds from its parent. This applies whether the position is its parent’s left child or takes the opposite branch. If that parent is the root, the next root check leads to setting the parent’s color to 1.

8. **Sibling disappears after a preliminary transformation.** If the corresponding dependency returns and the reread sibling is null, the current repair position receives the final color 1. This case does not use upward missing-sibling propagation.

9. **Dependency-defined output.** If the temporary output slot contains a particular four-byte value at normal completion, that value is written to result storage. The contract does not independently promise a successor reference.
