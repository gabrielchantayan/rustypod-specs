# F-413c5594a7ec

## Purpose

F-413c5594a7ec parses one bounded block of pair-adjustment metadata and, when the block contains at least one record, appends a newly allocated descriptor to a context-owned linked structure.

The descriptor retains a translated address for the record data rather than copying the records. It also stores the record count, flags, a two-byte header value, the calculated record width, and keys derived from the first and last records.

A structurally valid block containing zero records is accepted without adding a descriptor. Allocation failures are returned through a dependency-supplied status. A short header or insufficient record data produces status 8 after releasing the allocated descriptor.

The interpretation as pair-adjustment metadata is inferred intent. The field extraction, validation, descriptor writes, and list updates below are established static behavior.

## Interface

### Arguments and result

The function accepts three arguments:

| Argument | Role |
|---|---|
| Input start | Address of the first byte of the candidate block. |
| Input limit | Address against which the header end and required record-data end are compared. Equality is accepted. |
| Context | Address of a mutable structure accessed through 32-bit slots. It supplies an allocation token, address-translation values, a list insertion location, and an accumulated count. |

The result is a 32-bit integer status:

- **0:** ordinary success, including a valid zero-record block.
- **8:** malformed or truncated input detected by this function.
- **Other dependency-supplied status:** an allocation-related failure reported by F-3ce007b692cc.

There is no returned descriptor pointer and no returned consumed-input position. A successful nonempty descriptor is exposed through context mutation.

The block begins with a four-byte header:

| Input offset | Width | Meaning in this function |
|---|---:|---|

| 3 | 1 byte | Flags controlling record width and key extraction. |
| 4 onward | Variable | Fixed-width records. |

Higher flag bits are retained but do not affect the visible parsing decisions.

## Behavior

### Entry and allocation

The function initializes a local 32-bit status to zero and reads the allocation token from context offset 0.

It then reads a signed 32-bit diagnostic-level field at byte offset 224 within a globally referenced object. If that value is greater than 1, it invokes F-4457a9a44a68 with an entry-diagnostic argument.

Only after this optional diagnostic does it call F-3ce007b692cc, passing:

- The previously captured allocation token.
- A requested size of 24 bytes.
- A reference to the local status.

The function branches on that status after the call. A nonzero status returns immediately, without input validation, descriptor initialization, or a visible release call.

A zero status is treated as allocation success. The returned address is not independently checked for nullness.

The captured allocation token is reused for any later release. Other context fields are read later; this function does not snapshot them before calling dependencies.

### Header validation and partial descriptor initialization

The function checks whether the address four bytes beyond the input start is less than or equal to the input limit.

If this check fails, it follows the malformed-input path below. No header-byte read occurs on that path.

If the check passes, it performs the following visible operations in order:

1. Reads the first input byte to obtain the working record count.
2. Reads the first input byte again and stores it at descriptor offset 4.
3. Reads header bytes 1 and 2, combines them as a high-byte-first 16-bit value, and stores that value at descriptor offset 6.
4. Reads header byte 3 as the flags and stores it at descriptor offset 5.
5. Computes and stores the retained-data address at descriptor offset 12.
6. Writes the calculated record width at descriptor offset 8.

The ordering between individual byte reads within a combined expression is not established. The repeated read of the first header byte is visible in the supplied representation; stability of input memory is a precondition for the ordinary interpretation that both reads yield the same count.

The retained-data address is:

**input start + 4 + (context word at offset 4 − context word at offset 148)**

The subtraction uses 32-bit unsigned-word arithmetic. This is an address translation, not a copy operation. No validation establishes that the resulting address identifies accessible or persistent record storage.

Record-width initialization begins with a stored value of 3. If flag bit 0 is set, that value is replaced with 5. If flag bit 1 is set, the stored width is then increased by 1. These intermediate descriptor writes precede validation of the full record span.

### Record-span validation

The function requires:

**input start + 4 + record count × record width ≤ input limit**

Equality succeeds. Extra bytes after the required span are permitted and ignored.

The maximum count-width product is 255 × 6 = 1530 bytes. Including the header, the maximum required block size is 1534 bytes. Thus, multiplication of the supported count and width values does not overflow a 32-bit integer. Address addition near the address-space boundary remains a separate, unchecked concern.

If the span check fails, the function follows the malformed-input path.

If the span check succeeds and the working count is zero, the function calls F-bf7242c98d06 on the allocated descriptor and returns the local status. It does not initialize endpoint keys or link the descriptor into the context. The established local status before this release call is zero.

### Endpoint-key extraction

For a nonzero count with a sufficient record span, the function extracts keys only from the first and last records. It does not iterate over intermediate records.

When flag bit 0 is clear:

- Each key uses the first two bytes of its record.
- The first byte becomes bits 16–23 of a 32-bit value.
- The second byte becomes bits 0–7.
- Bits 8–15 and 24–31 are zero.

For example, record-leading bytes 0x12 and 0x34 produce numeric key **0x00120034**.

When flag bit 0 is set:

- Each key uses the first four bytes of its record.
- Those four bytes form a 32-bit value in high-byte-first order.

For example, record-leading bytes 0x12, 0x34, 0x56, and 0x78 produce **0x12345678**.

The first-record key is stored at descriptor offset 16 before the last-record key is stored at offset 20. The last record begins at:

**input start + 4 + record width × (record count − 1)**

The subtraction is reached only for a nonzero count, avoiding count-minus-one underflow on the zero-record path.

For a single record, both stored endpoint keys derive from that same record. The function does not validate key ordering, uniqueness, or any relationship between the endpoints and intermediate records. Bytes after the key within each record are covered by the span check but are not interpreted here.

### Successful append

After writing both endpoint keys, the function:

1. Writes a zero 32-bit next link at descriptor offset 0.
2. Reads the insertion-location address from context offset 140 and writes the descriptor address through it.
3. Replaces context offset 140 with the descriptor address.
4. Reads the count byte from descriptor offset 4 and adds it to the 32-bit word at context offset 132.
5. Returns zero.

The descriptor’s next link occupies its first word. Consequently, storing the descriptor address as the new insertion location allows a later append to write through that first word.

The accumulated count uses unsigned 32-bit arithmetic and has no overflow check. Incrementing it can wrap modulo 2³².

### Malformed-input path

A short header and an insufficient record span share the same visible failure sequence:

1. Call F-bf7242c98d06 with the captured allocation token and allocated descriptor address.
2. Set the local status to 8.
3. Call F-4457a9a44a68 with a malformed-input diagnostic argument.
4. Return the local status.

The malformed-input diagnostic is not guarded by the entry diagnostic-level comparison.

A short header reaches release without descriptor initialization by this function. An insufficient record span reaches release after the header-derived fields have already been written. Neither path performs this function’s list append or accumulated-count increment.

### Ownership and lifetime

For a successful nonempty block, the function links the descriptor into the context and does not release it. The context structure thereby retains the descriptor.

For a zero-record block or detected truncation, the function invokes the release dependency. Whether that dependency actually frees memory, pools it, or performs other work is not established.

The function does not copy record contents. Safe later use of the retained address therefore requires an external lifetime and mapping guarantee. This function neither establishes that guarantee nor visibly acquires ownership of the input storage.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. They assume valid memory, ordinary nonwrapping address calculations, and dependencies that return normally without unexpected interference.

1. **One narrow record, exact boundary.**  
   A count of 1, flags 0, and exactly three record bytes after the header are accepted. If the first two record bytes are 0x12 and 0x34, both endpoint keys are 0x00120034. One descriptor is appended, the accumulated count increases by 1, and the result is zero.

2. **Two wide records with the extra-width bit.**  
   A count of 2 and flags 3 require twelve record bytes. Record width is 6. Keys come from bytes 0–3 of the first record and bytes 0–3 of the second record; the remaining two bytes of each record are not interpreted here.

3. **Empty block with a complete header.**  
   A count of zero and an input limit exactly four bytes after input start pass both bounds checks. The allocated descriptor is released, no descriptor is appended by this function, and the ordinary result is zero.

4. **Incomplete header.**  
   With fewer than four available bytes, allocation still occurs first. After allocation success, the descriptor is released, the malformed-input diagnostic is invoked, and the ordinary result is 8.

5. **Record data one byte short.**  
   Count 2 with flags 0 requires six record bytes. Five available record bytes fail validation. Header-derived descriptor fields have already been written, but endpoint keys and list linkage are not completed.

6. **Trailing bytes.**  
   A block with sufficient required data plus additional bytes is accepted. The additional bytes are not validated or consumed through a returned cursor.

7. **High flag bits only.**  
   Flags 0x80 select three-byte records, while the full value 0x80 is retained in the descriptor.

8. **Accumulated-count wraparound.**  
   An accumulated count of 0xffffffff followed by a successful one-record append becomes zero. No overflow status is produced.

9. **Allocation-reported failure.**  
   If F-3ce007b692cc reports a nonzero status, that status is returned without parsing the input or invoking this function’s release path.
