# F-134018bf5bf5

## Purpose

F-134018bf5bf5 performs a forward, element-by-element transfer over a source range delimited by two addresses. Each element is 16 bits wide. At each iteration, it copies the current source element only if the current destination address is nonzero. It advances both cursors by one element and returns the final destination cursor.

The zero-address check applies to the destination cursor on each iteration. It is not an initial validation of the destination argument and does not establish a general discard-output mode.

The established behavior is a sequential transfer, not a snapshot copy. Earlier destination writes can change source values read by later iterations when the ranges overlap.

## Interface

The function accepts three address-valued inputs:

| Input | Meaning |
|---|---|
| Source start | Address of the first 16-bit source element considered for transfer. |
| Source endpoint | Address used exclusively as the source-loop termination sentinel. |
| Destination start | Initial address at which a 16-bit element may be written. |

The result is an address-valued destination cursor advanced once for each completed iteration. It is not the original destination address, a copied-element count, or a status code.

Each element occupies two bytes. The address width, address representation, alignment requirements, byte order, and applicable pointer-arithmetic rules are not established by the supplied material. In particular, the interface does not establish a 32-bit or 64-bit address space.

There is no explicit length argument. The number of iterations is determined by repeated source-cursor advancement until equality with the source endpoint.

For an ordinary valid range of \(N\) elements, the endpoint is \(N\) element positions after the source start. With valid arithmetic throughout, the returned destination is \(N\) element positions after the destination start. The corresponding byte displacement is \(2N\). This describes the displacement; it does not assert that the function computes a byte count or that arbitrary values of \(N\) are representable.

### Caller obligations

For the normal copying case, the caller must supply:

- A source endpoint reachable from the source start by forward advancement in two-byte element steps.
- Valid source and destination cursor arithmetic throughout the operation.
- Readable source elements for every iteration whose destination cursor is nonzero.
- Writable destination elements for every iteration whose destination cursor is nonzero.
- Any alignment and object-lifetime conditions required by the execution environment.
- A permitted final destination cursor, even though that final cursor is not itself dereferenced.

The function performs no visible checks for these conditions.

An empty range requires no element access. Whether particular invalid address representations can nevertheless be compared or returned is an execution-environment question, not a guarantee supplied here.

## Behavior

### Range control

Before each iteration, the function compares the current source cursor with the source endpoint.

If they are equal, processing ends immediately. The endpoint is not read as an element merely because it terminates the range.

If they differ, the function considers exactly one source position, then advances to the next position. There is no less-than comparison, range-length calculation, or rejection of reversed endpoints.

Consequently, an endpoint numerically below the start is not treated as an empty range. Nor is an endpoint with an incompatible element offset automatically rejected. Neither case has a guaranteed successful outcome.

### Element access and advancement

For each entered iteration, the visible sequence is:

1. Test whether the current destination cursor is zero.
2. If it is nonzero, read one 16-bit element from the current source address and write that value to the current destination address.
3. Advance the destination cursor by one two-byte element.
4. Advance the source cursor by one two-byte element.
5. Compare the updated source cursor with the endpoint before any subsequent iteration.

When the destination cursor is zero, the conditional transfer is omitted. In particular, that iteration does not perform the source-element read associated with the transfer. Both cursor advancements remain present.

For an iteration that transfers an element, the source value is obtained before the corresponding destination write. That write occurs before the next iteration's source-element read. These are source-level ordering facts; instruction selection, cache behavior, and hardware access granularity are not established.

The destination cursor is tested anew on every iteration. An initially zero destination therefore does not mean that all iterations skip their transfers. The supplied representation advances that cursor after the skipped transfer. Whether execution may validly continue after arithmetic on a zero address is an unresolved environmental constraint.

### Completion and result

On normal completion, the function returns the destination cursor after all completed iterations.

The result advances according to iterations, not successful stores. An iteration with a zero destination cursor still contains a destination advancement.

No terminator, padding, metadata, or extra element is written. Source element values do not affect termination. A zero-valued element is copied like any other 16-bit value.

### Overlapping ranges

The traversal is always forward. There is no overlap detection, temporary buffer, or reverse traversal.

If a destination write changes a source element that will be read later, that later read observes the changed storage, subject to the execution environment's ordinary memory rules. The function therefore must not be specified as preserving all original source values for arbitrary overlap.

Identical source and destination starts produce read-then-write accesses to the same element on each iteration. For ordinary memory without external interference, this leaves element values unchanged. The accesses themselves are still present.

### Exceptional conditions

No explicit error result, recovery branch, rollback, or exception handling appears.

Invalid reads, invalid writes, invalid cursor arithmetic, or an unreachable endpoint do not have a defined failure response in the available evidence. The function does not promise to detect them.

If execution fails after earlier stores have completed, no mechanism in the supplied body restores those earlier values. Exact fault reporting and externally visible state at failure remain environment-dependent.

## Side effects

The direct memory side effects are conditional 16-bit writes through successive destination addresses. Each such write is preceded by a 16-bit read through the corresponding source address.

The source endpoint is used for equality comparison, not dereferenced as an endpoint object.

The three argument values are received by value. Advancing the cursors does not itself update caller-held pointer variables. Destination storage can, however, alias other caller-visible data, including source storage.

No allocation, deallocation, ownership transfer, reference-count operation, callback, global-variable access, or explicit synchronization is visible in the supplied body. The function neither acquires ownership of the supplied storage nor releases it.

There are no visible callees whose memory ownership or global-state behavior must be assumed. Concurrent access, memory-mapped I/O, and unusual memory access semantics are not specified by this contract.

## Acceptance examples

These examples are conditional behavioral expectations derived from static inspection. They are not reported runtime results. Except where stated otherwise, assume ordinary readable and writable memory, valid arithmetic, suitable alignment, and no concurrent mutation.

### Empty range

Given equal source-start and source-endpoint addresses:

- No source element is read.
- No destination element is written.
- Neither cursor advances.
- The result equals the destination start.

This also describes the visible control flow when the destination start is zero: the loop is not entered, so destination arithmetic is not attempted.

### Nonoverlapping transfer

Given three source elements with values `0x1234`, `0x0000`, and `0xFEDC`, and a separate valid destination range:

- Those three values are written to successive destination elements in that order.
- The zero-valued middle element does not stop processing.
- The result is three element positions, or six bytes, beyond the destination start.
- No fourth destination element is written.

These are element-value expectations, not assertions about byte order.

### One-element range

Given an endpoint one element after the source start and a valid nonzero destination:

- Exactly one source-element read and one destination-element write occur.
- Both cursors advance once.
- The returned address is one element beyond the destination start.

The endpoint itself need not designate a readable element merely to serve as the termination sentinel, provided the comparison and arithmetic are valid.

### Identical ranges

Given identical source and destination starts and a valid range of two elements:

- Each element is read and written back to its own address.
- Ordinary stored values remain unchanged.
- The result is two element positions beyond the destination start.

An implementation that simply skips all accesses would not preserve the access behavior represented here.

### Destination one element ahead

Given storage initially containing four elements `A`, `B`, `C`, `D`, a three-element source range beginning at the first element, and a destination beginning at the second:

- The first transfer writes `A` over `B`.
- The second transfer reads that newly written `A` and writes it over `C`.
- The third transfer reads the newly written `A` and writes it over `D`.

The resulting storage is `A`, `A`, `A`, `A`. This distinguishes forward sequential copying from snapshot-style overlap handling.

### Initially zero destination

Given a nonempty source range and a zero destination start, the first entered iteration skips both the element read and the element write, then reaches destination advancement.

A successful return, a particular resulting address, or safe behavior on a later iteration is **documented_only** unless the execution environment defines the relevant zero-address arithmetic and subsequent accesses. Zero must not be advertised as a supported whole-range discard mode.
