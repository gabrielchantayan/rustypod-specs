# F-08bf17e808b9

## Purpose

F-08bf17e808b9 conditionally changes a selected record, requests up to two transfers through an associated service, and records a successful-use sequence number. Its decisions depend on a requested inclusive range, a zero/nonzero mode, record fields, and service-supplied values.

Buffered-range management is inferred intent. Established behavior consists of reads, writes, dependency calls, descriptor construction, and branches on transfer results. The dependency invoked before metadata changes and after transfer failures is not independently established to copy memory. Preservation and restoration are therefore conditional interpretations.

Normal returns are:

- **1:** execution reaches success handling, including paths without transfers.
- **0:** a transfer returns nonzero, and failure handling completes.

Neither return guarantees final memory contents across dependencies with unknown effects.

## Behavior

### Arithmetic model

The inclusive requested end is requested start plus requested count minus one, evaluated as unsigned 32-bit arithmetic. Clearing its low seven bits produces an aligned comparison value. A zero requested count receives no special treatment.

Unsigned 32-bit arithmetic wraps modulo 2³². This rule does **not** establish wrapping semantics for signed intermediate operations or out-of-range conversions to signed storage.

In particular:

- In both initialized-record trailing branches, upper boundary plus one is first calculated unsigned, then assigned to a signed 32-bit trailing-start value. Conversion outside the signed range is unresolved.
- Service results used for those branches are held as signed 32-bit values.
- Their first adjustment calculation performs a **signed subtraction**, followed by an **unsigned addition of one**.
- Their replacement calculation performs both subtraction and addition of one with **signed operands**, then assigns the result to an unsigned count.
- The uninitialized-record adjustment instead uses the unsigned requested start, making both calculations unsigned.

A later unsigned operation does not make an earlier overflowing signed subtraction well-defined. Signed overflow and out-of-range signed conversions remain documented uncertainties.

Record selection also uses signed index arithmetic. Descriptor words and the zero-mode metadata extension involve unsigned calculations assigned to signed storage. Valid address ranges and all out-of-range signed conversions are unresolved; checked arithmetic must not be assumed.

### Initial operations

Before inspecting the initialized marker:

1. Query F-indirect-28.
2. If its unsigned result is below the aligned comparison value, query it again and select the second result. Otherwise select the aligned value.
3. Call F-4d1d429956da with temporary storage.
4. Call F-indirect-24 and retain its signed 32-bit result as the transfer stride.
5. Select and inspect the record.

The selected comparison bound is not necessarily a minimum. A second query result can exceed the aligned value.

Neither initial query nor the stride query shows an explicit receiver argument. Their dispatch is obtained through the context's service object. These calls occur even on immediate-acceptance paths, and their unknown mutations may affect subsequent reads.

### Initialized records: immediate acceptance

Only an initialized-marker byte equal to exactly 1 selects initialized processing.

Immediate acceptance requires the lower boundary to be no greater than requested start and either:

- Requested end is no greater than upper boundary; or
- Base position differs from the selected comparison bound, and extent boundary equals upper boundary.

This path bypasses F-copy-39, auxiliary handling, and transfers. It still performs success sequence writes and temporary finalization.

### Initialized records: transfer planning

If immediate acceptance fails, requested start below lower boundary enables a leading transfer:

- Start: requested start.
- Full count: lower boundary minus requested start.

No service-limit adjustment caps this leading count.

Trailing processing occurs only when upper boundary is below requested end.

**Zero mode:**

If upper boundary plus one is below requested start:

- Form the signed trailing start from unsigned upper boundary plus one.
- Set the unsigned candidate count to requested start minus upper boundary minus one.
- Perform the initialized-record service adjustment below.
- Enable the trailing transfer, even if its adjusted count is zero.

Whether or not that gap exists, calculate an additional metadata extension as the unsigned minimum of requested end and extent boundary, minus a newly read upper boundary, minus the trailing count. The trailing count remains zero when no gap was scheduled.

This extension is calculated unsigned and assigned to signed 32-bit storage. It is not clamped to a nonnegative distance. Its subsequent metadata additions combine it with unsigned values.

**Nonzero mode:**

- Form the signed trailing start from unsigned upper boundary plus one.
- Set the unsigned candidate count to extent boundary minus upper boundary.
- Perform the initialized-record service adjustment.
- Enable the trailing transfer only if the adjusted count is nonzero.

Requested end controls entry into this branch but does not directly cap its count.

### Service adjustment: initialized-record branches

Both trailing branches use the following type-sensitive sequence:

1. Query F-indirect-28 into a signed 32-bit result.
2. Subtract the signed trailing start using signed arithmetic.
3. Convert that subtraction result for unsigned addition of one.
4. Compare the resulting unsigned value with the unsigned candidate count.
5. If it is less than or equal to that count, query again.
6. For the replacement, subtract trailing start and add one using signed arithmetic; then assign the result to the unsigned count.

Equality triggers the second query. Its result may differ and can increase the count.

The first subtraction can overflow even though the subsequent addition is unsigned. The replacement can overflow in either signed operation. Conversion of trailing start can already be unresolved before either query calculation. Thus this adjustment has no unconditional modulo-2³² interpretation.

Where signed operations are representable, a negative signed replacement result converts to an unsigned count modulo 2³². That can produce a large count; it is not an error path or a nonnegative clamp.

### Initialized records: metadata writes

After planning, call F-copy-39 with temporary storage first, selected record second, and 0x39 third. Its return status does not control processing.

Then perform separate read-modify-write operations in this order:

1. Subtract the leading count from lower boundary.
2. Add trailing count and additional extension to upper boundary.
3. Add leading count, trailing count, and additional extension to accumulated count.

Field reads occur after F-copy-39 returns. Without a preservation contract for that dependency, these are not universally adjustments to entry-time values.

An ordinary destination-first copy would conditionally preserve the record before these writes. The call alone does not establish that effect.

### Records not marked initialized

Any initialized-marker value other than 1 selects this branch.

**Zero mode:** no initialization metadata writes, no transfers, and no preparation call to F-copy-39. Execution continues to auxiliary handling and success processing.

**Nonzero mode:**

1. Calculate an unsigned candidate count as the minimum of requested count and 128 minus the unsigned difference between requested start and base position.
2. Query F-indirect-28 into signed 32-bit storage.
3. Calculate query result minus requested start plus one using unsigned arithmetic, because requested start is unsigned.
4. If that unsigned result is less than or equal to the candidate count, query again and replace the count using the same unsigned calculation.
5. Enable a leading transfer even if the final count is zero.
6. Call F-copy-39 with temporary storage first, record second, and 0x39.
7. Write lower boundary = requested start.
8. Write upper boundary = requested start plus final count minus one.
9. Write accumulated count = final count.
10. Write initialized marker = 1.

Unlike initialized-record trailing adjustment, both query calculations here are unsigned modulo 2³²; there is no signed subtraction of two signed positions.

The 128-based expression is not validated as a distance within a block. With final count zero, upper boundary becomes requested start minus one modulo 2³², and the zero-count transfer remains enabled.

### Auxiliary-resource handling

Except on immediate acceptance, inspect the auxiliary-resource marker. Exactly 1 triggers:

1. Call F-fceaba74ea88 with the auxiliary-resource argument.
2. Write zero to the record marker.
3. Write zero to temporary-storage offset 0x38.

The argument field is not explicitly cleared. The stores occur after the dependency returns.

Resource release is inferred intent, not established ownership behavior. If preparation made an ordinary copy, the temporary-byte write modifies that conditional snapshot so ordinary reverse copying would restore a zero marker rather than the original value.

### Transfers

An enabled leading transfer precedes an enabled trailing transfer.

Each F-indirect-04 call receives:

- The service object as an explicit receiver.
- A pointer to a temporary two-word descriptor.
- Transfer start.
- The full count masked to its low 16 bits.

The descriptor words represent:

1. Transfer-buffer base plus stride multiplied by destination position minus record base.
2. Stride multiplied by the **full** transfer count.

For a leading transfer, destination position is the lower boundary reread after metadata and auxiliary handling; its separate transfer-start argument remains requested start. For a trailing transfer, destination position and transfer start use the calculated trailing start.

The unsigned record fields and counts cause these descriptor calculations to use unsigned arithmetic where mixed with signed stride or trailing start. The results are placed in signed 32-bit descriptor storage; out-of-range signed conversion is unresolved. In particular, signed stride does not establish that descriptor multiplication itself is signed.

Relevant fields and service dispatch are reread for each transfer. Effects of the first transfer may change the second descriptor or its dispatch.

A full count of 65,536 produces an explicit count argument of zero while still using 65,536 in descriptor-size arithmetic.

A zero transfer result permits continuation. Any nonzero result enters failure handling. A failed leading transfer prevents the trailing transfer.

### Failure handling

After the first failed transfer:

1. Call F-copy-39 with record first, temporary storage second, and 0x39.
2. Reload service dispatch and call F-indirect-68 with the receiver and failure argument.
3. Call F-e3f2f3fd5b21 with temporary storage.
4. Return 0.

Restoration is conditional on F-copy-39's semantics and the temporary bytes present at that time. Even ordinary copying restores those bytes, not necessarily entry-time contents.

The callback and finalizer run afterward and have no established preservation contract. Restoration at the reverse call's return therefore does not guarantee restoration at function return.

No visible operation reverses transfer-buffer effects, a previously successful transfer, or auxiliary dependency effects.

### Success handling

Every success path:

1. Reads the shared sequence counter and writes that value to the record's use sequence.
2. Reads the shared counter again, adds one as a 32-bit unsigned operation, and writes it back.
3. Calls F-e3f2f3fd5b21 with temporary storage.
4. Returns 1.

These are separate accesses, not an atomic fetch-and-increment. The increment wraps. The transfer-failure path does not directly perform these sequence writes. Finalization may alter their resulting state.

## Acceptance examples

These are conditional static expectations, not runtime results. Unless stated otherwise, assume valid storage, representable signed operations and conversions, and dependencies preserving relevant fields and temporary contents. Restoration examples additionally assume exact destination-first 57-byte copying.

1. **Covered request.** Initialized lower boundary 100, upper boundary 199, start 120, count 10: immediate acceptance. No transfer, auxiliary call, or F-copy-39 call occurs. Success sequence writes and finalization precede return 1. An auxiliary marker of 1 is not directly cleared.

2. **Leading extension.** Initialized coverage 100–199, start 90, count 20: leading transfer start 90, full count 10. Lower boundary becomes 90 and accumulated count increases by 10 before transfer. A zero transfer result permits success.

3. **Metadata-only extension.** Initialized lower 100, upper 109, extent 200, accumulated count 10; start 105, count 15, zero mode: no transfer. With preparation preserving the record, upper becomes 119 and accumulated count becomes 20.

4. **Extension beyond requested end.** Initialized lower 100, upper 109, extent 150; start 105, count 16, nonzero mode: candidate trailing start 110 and count 41. If the first query returns 200, the comparison value is 91, so no replacement occurs. Requested end 120 does not cap the transfer.

5. **Signed replacement boundary.** For initialized trailing start 100 and candidate count 10, first query 109 gives comparison value 10 and triggers a second query. If that returns 99, signed replacement arithmetic yields zero. Nonzero mode disables this trailing transfer; a scheduled zero-mode gap transfer remains enabled.

6. **Unresolved initialized arithmetic.** If trailing start is signed maximum and a signed query result is −2, the first subtraction is outside signed 32-bit range. No wrapped comparison value or resulting transfer count is specified. If a replacement query returns signed maximum with trailing start zero, its signed addition of one also overflows. These are documented-only cases.

7. **Unsigned initialization adjustment.** For an uninitialized record with base zero, start zero, requested count 10, and nonzero mode, a query value of −2 produces unsigned adjustment value 4,294,967,295. It exceeds candidate count 10, so no replacement occurs. Unlike example 6, this calculation does not require signed subtraction.

8. **Changing initial queries.** Aligned comparison value 256, first query 100, second query 400: selected bound 400, not 100 or 256.

9. **Zero-count initialization.** If initialization calculations yield zero, initialized marker becomes 1, upper becomes start minus one modulo 2³², and a leading transfer with explicit count zero is attempted.

10. **Conditional restoration.** Preparation captures a record with auxiliary marker 1. Auxiliary handling clears both marker locations. If a transfer fails and relevant temporary bytes remain intact, ordinary reverse copying restores captured range fields and marker zero at that call's return. Their persistence through function return additionally requires callback and finalizer preservation.
