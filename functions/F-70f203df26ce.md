# F-70f203df26ce

## Purpose

F-70f203df26ce coordinates acquisition of two prerequisite objects, processing of a request, conditional construction and registration of a result, optional completion reporting, and cleanup of a temporary object reference.

The function returns a 32-bit status and can separately write a 32-bit result-object value to caller-provided storage. **On normal completion, a nonzero retained result implies a zero returned status.** Result construction is reached only with zero status. Successful construction, registration, reporting, and final cleanup contain no subsequent assignment to that status. The represented calls do not receive its address.

Dependencies may change reachable memory and external state. That uncertainty affects field values, ownership, and dependency effects; it does not invalidate the status invariant established by the represented control flow.

“Request,” “intermediate object,” “service object,” “result,” “registration,” and “release-like” describe apparent roles. They do not establish concrete types or dependency semantics.

## Interface

### Arguments

The represented interface has five arguments:

| Argument | Width and role |
|---|---|
| Context address | 32-bit address used for nested reads, embedded receivers, and dependency arguments |
| Request address | 32-bit address of a record containing input words, flags, and object-reference fields |
| Opaque input | Uninterpreted 32-bit value forwarded to result construction and reporting |
| Reporting control | 32-bit integer; zero disables reporting, any nonzero value enables the reporting-status check |
| Optional output address | Zero, or an address writable for one 32-bit result value |

There is no explicit validation of the context, request, nested pointers, indirect-call tables, or output address. All accesses reached on an execution path require suitable readable or writable memory. A nonzero address alone does not establish that requirement.

### Return and output

The return is a 32-bit status. Its established sources are:

- `0x0000000C` for missing prerequisite objects or a zero result-construction return.
- The processing status returned by F-5265b5f84cfc.
- An external 32-bit status datum, conditionally substituted when request flag `0x00000100` is observed.

The retained result starts at zero. Only the return from F-3f2c67175ada changes it.

If the optional output address is nonzero, the retained result is written there after service cleanup. The function does not clear that output location on entry. A fault or nonlocal exit before the final write therefore has no established output-write guarantee.

On normal completion:

- A nonzero retained result implies status zero.
- A nonzero status implies a zero retained result.
- A zero result alone does not distinguish the failure paths.

## Behavior

### Acquisition and initial reads

The retained result is initialized to zero.

F-8157a180d901 is called with `0x34`, requesting a quantity of 52 bytes under the allocation-like interpretation. Its return is not checked before being forwarded.

The subsequent established order is:

1. Capture the request word at `0x10`.
2. Read the request object address at `0x04`, follow its first-word table address, and invoke the target at table byte offset `0x24`.
3. Read the context pointer at `0x58`, then the nested word at `0x18`.
4. Call F-c49bb656f717 with the allocation-like return, zero, the nested context word, the initial indirect-call return, and the captured request word.
5. Call F-a0f1188a9c7e to obtain the service-object value.

No explicit argument list is established for the initial indirect call or F-a0f1188a9c7e. The initial indirect-call return is consumed as a 32-bit value.

The service acquisition occurs even when F-c49bb656f717 returns zero. The captured request word remains the construction argument even if an intervening dependency changes the request field.

### Missing prerequisites

If the service value is zero:

- A nonzero intermediate object receives an indirect call through its table entry at byte offset `0x04`, with the object address as the visible argument.
- Status becomes `0x0000000C`.
- Processing and result construction are skipped.

If the service is nonzero but the intermediate value is zero:

- Status becomes `0x0000000C`.
- Processing and result construction are skipped.
- Final service cleanup still occurs.

Neither missing-prerequisite path explicitly clears request offset `0x1C`. If a service was obtained, final cleanup clears request offset `0x18` even when this execution never stored the service there.

### Publication and processing

When both prerequisite values are nonzero, the following operations occur in order:

1. Store the service address at request offset `0x18`.
2. Replace the low byte of the flags at request offset `0x14` with `2`.
3. Call F-1333331b2da1 with context address plus `0x38`.
4. Read the current request word at `0x04` and call F-5265b5f84cfc with the service, that word, and the intermediate object.
5. Call F-338d16f9ce72 with context address plus `0x38`.
6. Store the intermediate address at request offset `0x1C`.

The processing status is the return from F-5265b5f84cfc. The later request-object read is not guaranteed to equal the object address used for the initial indirect dispatch.

The processing-associated dependency pair is not sufficient evidence of a lock, mutual exclusion, or any particular memory-ordering guarantee.

### Selecting intermediate handling

A nonzero processing status always selects intermediate handling.

When processing returns zero, the function reads the current request flags and selects intermediate handling only if bit `0x00000100` is set.

The return from F-338d16f9ce72 does not independently alter that decision:

- For nonzero processing status, handling is already selected.
- For zero processing status, the value used in its place is the masked request flag.

Once handling is selected, the flags are read again. If bit `0x00000100` is set at this later read, the processing status is replaced with the external status datum.

These are distinct flag observations. No stability or concurrency guarantee is established. For example, selection based on a set flag does not prove that the replacement check also observes it set.

### Handling the intermediate object

On the selected handling path, the intermediate word at offset `0x04` is inspected.

If that word is zero:

- Invoke the object’s indirect table entry at byte offset `0x04`, passing the object address.
- After that call returns, clear request offset `0x1C`.

If that word is nonzero:

- Invoke F-5c33d20156b2.
- No explicit argument is established at this call site.
- Do not infer a direct clearing of request offset `0x1C`.

After either subpath, the retained intermediate value is set to zero.

If the resulting status is nonzero, result construction is skipped. If it is zero, construction proceeds with a zero intermediate argument. In particular, an external replacement status of zero can enable this path.

### Result construction

Every path entering result construction has zero retained status.

F-8157a180d901 is called with `0x38`, or 56. Its return is passed without a separate failure check to F-3f2c67175ada, together with the current intermediate value and the opaque input.

The return from F-3f2c67175ada becomes the retained result.

If that return is zero:

- Set status to `0x0000000C`.
- Read the current intermediate object’s word at `0x04`.
- Pass that word to F-5c33d20156b2.
- Skip registration.

There is no nonzero check before this intermediate-field read. If construction was attempted with a zero intermediate value and returns zero, the represented access is a 32-bit read at address `0x00000004`. Normal continuation requires that read and subsequent dependency invocation to complete; the supplied evidence does not establish that they can.

### Registration

A nonzero result selects registration, in this order:

1. Call F-338d16f9ce72 with context address plus `0x40`.
2. Copy the retained result into a temporary 32-bit slot.
3. Resolve the indirect target through the receiver at context offset `0x1C`, using table byte offset `0x1C`.
4. Invoke that target with the embedded receiver address and the temporary slot’s address.
5. Call F-1333331b2da1 with context address plus `0x40`.

The temporary slot is distinct from the retained result. A write confined to that slot does not change the result later reported or returned through the optional output.

No status assignment occurs in this branch. Consequently, normal continuation from nonzero construction retains status zero regardless of the return values of these registration-associated calls.

### Reporting

Reporting is attempted only when the reporting control is nonzero and status is not `0x20013003`.

The exclusion is an equality test derived from 32-bit subtraction: subtracting `0x20000003` and comparing the result with `0x00013000` excludes exactly `0x20013003`. It is not a status range.

F-d7901cd15a43 receives:

1. The context address.
2. The opaque input.
3. An external 32-bit reporting datum.
4. The current request word at `0x0C`.
5. The retained status.
6. The retained result.

Its return is ignored. After reporting returns, request offset `0x1C` is cleared if the retained result is nonzero.

Thus, with a nonzero result and reporting enabled, reporting is not excluded: the retained status is zero. Reporting-disabled execution does not perform this particular clear.

### Cleanup and return

If a nonzero service was obtained:

1. Clear request offset `0x18`.
2. Invoke the retained service object’s indirect table entry at byte offset `0x04`, passing the service address.

Cleanup uses the retained service value, not a reread of request offset `0x18`.

Finally, write the retained result if the output address is nonzero, then return the retained status. Reporting and cleanup do not assign that status.

## Side effects

Direct effects include request-field stores, indirect dispatch, dependency calls, and the optional output write.

The low-byte flag update is not rolled back. Request offset `0x18` is cleared whenever a service was obtained. Request offset `0x1C` is cleared only on the specified paths, not universally.

No non-aliasing requirement is stated. If the output address aliases a request field, the final output write occurs after the earlier field stores and service cleanup and can overwrite their effects.

Ownership remains unresolved:

- Release-like indirect calls do not prove destruction or reference-count decrement.
- Construction does not establish consumption of allocation-like storage.
- Registration does not establish transfer or retention of the result.
- Reporting does not establish release of request-associated objects.
- No explicit direct release of either allocation-like return is shown.
- Passing a temporary slot’s address does not establish permission to use it after the call.

Unknown dependencies may mutate reachable memory or external data. Their effects must not be assumed absent, nor expanded into unsupported mutation of retained scalar state whose address is not exposed.

## Acceptance examples

These are conditional static cases, not executed tests. Unless specified otherwise, dependencies return normally and do not introduce relevant mutations.

1. **Service unavailable, intermediate present.**  
   The intermediate release-like call occurs. Processing and construction do not. Status is `0x0000000C`; output, if supplied, receives zero. Reporting occurs only if enabled.

2. **Intermediate unavailable, service present.**  
   Status is `0x0000000C`. Final cleanup clears request offset `0x18` before the service release-like call, despite no earlier publication of that service.

3. **Ordinary success.**  
   Both prerequisites exist, processing returns zero, the selection flag is clear, and construction returns a nonzero result. Registration occurs. The returned status is zero, and the optional output receives that result.

4. **Registration modifies its temporary slot.**  
   Construction returns a nonzero result, and registration overwrites only the supplied temporary slot. The retained result remains the construction return; status remains zero.

5. **Successful reporting enabled.**  
   Construction returns a nonzero result and reporting control is nonzero. Reporting receives status zero and the retained result. After it returns, request offset `0x1C` is cleared.

6. **Low-byte replacement preserves the tested flag.**  
   Flags `0xA5A5017F` become `0xA5A50102`. Bit `0x00000100` remains set. Later decisions use later flag reads.

7. **Processing failure without replacement.**  
   Processing returns nonzero and the replacement check observes the flag clear. Intermediate handling occurs, construction is skipped, and the processing status is retained.

8. **Reporting exclusion.**  
   Retained status `0x20013003` suppresses reporting even when enabled. Service cleanup and the optional zero-result output write still occur.

9. **Construction failure with valid intermediate storage.**  
   Construction returns zero. Status becomes `0x0000000C`; the intermediate word at `0x04` is passed to F-5c33d20156b2. Registration does not occur.

10. **Zero replacement status.**  
    Intermediate handling installs zero status and clears the retained intermediate value. Construction receives zero as its intermediate argument. A nonzero construction return yields registration and status zero; a zero return selects the unchecked read at address `0x00000004`.
