# F-a1e36949e45c

## Purpose

F-a1e36949e45c obtains an object address from a dependency, installs three caller-supplied 32-bit words at fixed and metadata-selected locations, initializes additional fields, and makes two indirect calls with computed interior addresses. On normal completion, it returns the originally obtained object address.

The established behavior is an ordered sequence of memory accesses and calls. Constructor-like initialization and registration-like dispatch are inferred intent only. The evidence does not establish allocation, ownership transfer, field meanings, or the semantic purpose of either indirect call.

The visible address calculations and words are 32-bit. All offsets in this contract are byte offsets. “Header” means the 32-bit word at object offset zero, without implying a particular object model or language-level type. A header value is subsequently used as an address for metadata reads.

Successful execution requires valid storage at each actual access:

- Each source word must be readable when consumed. The three words are not read together at entry.
- The acquired object address must support the fixed writes. Their highest endpoint is `0x150`, exclusive.
- Each metadata-selected destination must support a 4-byte write, whether or not it lies within the fixed-write range or the same allocation.

These are access preconditions, not validations performed by the function. In particular, a header that has been replaced need not remain suitable for future metadata lookups merely because it was suitable for an earlier lookup. Each lookup depends on the header or saved value actually used at that point.

Alignment requirements, address-domain limits, and behavior on invalid accesses are not established.

## Behavior

### Acquisition and initial header

The first visible operation calls F-bf74dfda5df0 with the first and third arguments, in that order. Its result becomes the retained object address.

Only after this call returns does the function read the first 32-bit source word. Any effect of F-bf74dfda5df0 on the source storage can therefore affect that read.

The first source word is saved and written to object offset zero. This installs the initial header.

### Metadata-selected writes

Two 32-bit writes follow the initial header write.

For the first write:

- The saved first source word is used as a metadata address.
- A 32-bit displacement is read at that address minus `0x0C`.
- The second source word is written at the retained object address plus that displacement.

For the second write:

- The current object header is read afresh.
- A 32-bit displacement is read at that header address minus `0x10`.
- The third source word is written at the retained object address plus that displacement.

The first lookup uses the saved first source word; the second uses the current contents of object offset zero. Consequently, the first metadata-selected write can change the header used by the second lookup.

The second metadata-selected write can itself replace the header. For example, a second displacement of zero places the third source word at object offset zero. Later metadata lookups then depend on the header current at those later times, including any intervening dependency effects—not necessarily on either earlier header.

The three source words are not collectively snapshotted. Earlier writes can affect later source reads if the source region aliases the object or another modified location. Likewise, writes can alter metadata used by later lookups.

The statement sequence establishes that the first metadata-selected write completes before the second assignment. It does not establish the relative order of all reads within either assignment, such as the source-word read versus the reads used to determine the destination.

These examples are conditional static acceptance criteria. They are not executed tests.

- The third source word is written at object offset `0x40`.

- The second indirect call receives the object address plus `0x40`.

The fixed fields have their listed values after normal completion under the stated preservation assumptions. The returned address equals the acquisition result.

### First metadata-selected write replaces the header

Assume the initial displacement at the saved first source word minus `0x0C` is zero. The first metadata-selected write then places the second source word at object offset zero.

The immediately following displacement lookup must use that new header at address minus `0x10`. It must not use the originally installed header for this lookup.

If this second displacement is also zero, the ensuing write places the third source word at object offset zero, replacing the header again. The second source word therefore needs to support the immediately following metadata read, but need not support the metadata reads for either indirect call.

For normal completion, each later metadata read must be valid through the header current at that access. The third source word may supply that header, or a dependency may replace it before the lookup. No validity requirement is imposed on a superseded header for accesses that no longer use it.
