# F-05434e19c03a

## Purpose

F-05434e19c03a recursively processes selected child addresses, updates accounting, checks allocation metadata, and invokes allocator-related dependencies.

The established behavior is narrower than destruction or deallocation. This function directly performs traversal, metadata reads, counter writes, and dependency calls. The supplied evidence does not establish that any dependency releases storage, transfers ownership, synchronizes access, or preserves global state.

Recursive destruction with allocation accounting is inferred intent, not a guaranteed semantic outcome.

## Interface

### Input and result

The function accepts one 32-bit value interpreted as an object address. It has no explicit result.

A zero input returns immediately, without any shown memory access or dependency call. For nonzero input, every address reached on the selected path must support the required access. No recoverable error result or rollback mechanism is shown.

Addresses, child entries, displacement values, headers, and accounting words have a represented width of 32 bits. Two allocation metadata indices are unsigned 16-bit quantities. Arithmetic results below are described at the represented 32-bit width; this does not make an inaccessible computed address valid.

### Object layout

Offsets are relative to the supplied object address.

| Byte offset | Width | Meaning established by use |
|---|---:|---|
| −4 | 32 bits | Displacement subtracted from the object address |
| +8 | 32 bits | Zero/nonzero child-traversal control |
| +12 through +508 | 125 consecutive 32-bit entries | Child addresses |

The traversal control is not a child count. Any nonzero value selects all 125 slots.

After child processing, the function subtracts the then-current displacement at offset −4 from the original object address. The result is the **recovered base** used for allocation metadata.

### Allocation metadata

Offsets are relative to the recovered base.

| Byte offset | Width | Meaning established by use |
|---|---:|---|
| −16 | 32 bits | Header used for validation and masked-size accounting |
| −12 | Unsigned 16 bits | First allocator-counter index |
| −10 | Unsigned 16 bits | Second allocator-counter index |
| −8 | 32 bits | Amount used in the earlier two-word accounting update |

The amount at −8 and the size derived from the header are independent quantities. No equality or consistency check relates them.

Recovered base **8** is a special case. It bypasses header validation and subsequent allocator operations, but not the earlier accounting update, F-2fd8826557a4, or acquisition of the allocator context.

### Global accounting and allocator structures

An accounting global supplies context addresses with these field offsets:

| Offset | Width | Use |
|---|---:|---|
| +56 | 32 bits | Low-word source or destination |
| +60 | 32 bits | High-word source or destination |

The accounting global is read **four separate times**. These reads are not established to return the same context address. In particular, the high-word destination is retained from the first read, while the high-word source is selected by the third read and loaded only after the low-word store.

A separate global pointer source is dereferenced after F-2fd8826557a4 to obtain an allocator-context address. That address is retained for subsequent allocator operations.

Allocator-context locations are:

| Location | Direct operation |

## Behavior

### 1. Handle null input and traverse children

Zero input returns immediately.

For nonzero input, the function reads the traversal control at object offset +8. Zero skips all child entries and proceeds to current-object processing.

A nonzero control selects 125 recursive calls, provided preceding calls return. Child addresses are read and passed to F-05434e19c03a in ascending slot order: offset +12 first, then successive four-byte entries, ending at +508. Zero child values are passed too; those recursive invocations return immediately.

Child entries are read individually when reached, not captured before recursion. An earlier child invocation or its dependencies can therefore change the value later read from a sibling slot.

The control field is not rechecked between children. Changing it to zero after traversal starts does not by itself stop that traversal.

Current-object accounting starts only after all selected child invocations return. A nonreturning child prevents later siblings and current-object processing. No cycle detection, duplicate suppression, visited set, or recursion-depth limit is shown.

### 2. Retain the eventual high-word destination and recover the base

After child processing, the function performs the **first accounting-global read**. The resulting context address is retained as the base for the eventual high-word write at offset +60.

A second input-zero check follows this read. The supplied control flow has not changed the original input, so this check adds no reachable null-input case.

The function then reads the displacement at original-object offset −4 and subtracts it from the original object address to recover the allocation-related base.

There is no displacement validation. A nonzero object address can recover base 8, base zero, or another address. Only base 8 receives the later special treatment; recovered base zero does not cause an immediate return.

### 3. Perform the accounting update through four global reads

The accounting accesses have the following established order:

1. Retain the context from the first accounting-global read, as described above.
2. Recover the allocation-related base.
3. Read the 32-bit amount at recovered-base offset −8.
4. Perform the **second accounting-global read**, then load the low word from offset +56 of that context.
5. Perform the **third accounting-global read** and retain the address at offset +60 of that context as the high-word source. The high-word value is not yet loaded.
6. Perform the **fourth accounting-global read** to locate the low-word destination at offset +56.
7. Store the low-word subtraction result at that destination.
8. Load the high-word value from the source address established by the third read.
9. Store the adjusted high-word result at offset +60 of the context retained by the first read.
10. Call F-2fd8826557a4 with no explicit arguments.

Thus, the low-word source, low-word destination, high-word source, and high-word destination can belong to different contexts. There is no intervening dependency call within this accounting sequence, but no synchronization or global-stability guarantee is established either.

For the arithmetic, let:

- \(A\) be the captured unsigned 32-bit amount.
- \(L_{\mathrm{source}}\) be the low word loaded using the second global read.
- \(H_{\mathrm{after}}\) be the high word loaded using the third global read, **after** the low-word store.
- \(b=1\) if \(L_{\mathrm{source}}<A\), otherwise \(b=0\).
- \(s=0\) if the amount’s top bit is clear, otherwise \(s=-1\).

The low-word destination receives:

\[
(L_{\mathrm{source}}-A)\bmod 2^{32}.
\]

The separately retained high-word destination receives:

\[
(H_{\mathrm{after}}-s-b)\bmod 2^{32}.
\]

The borrow is derived from the captured low-word source and amount, not from the low-word destination’s previous contents.

If all four global reads return the same context, and no relevant aliasing or external modification changes its words, these operations implement subtraction of a **sign-extended** 32-bit amount from the two-word value. They are not generally subtraction of a zero-extended unsigned amount.

Without those conditions, describing the operation as an update to one two-word counter is incorrect. In particular, if the selected high-word source aliases the low-word destination, the high-word load observes the preceding low-word store.

No overflow, underflow, consistency, or atomicity check is shown.

### 4. Acquire the allocator context and handle base 8

After F-2fd8826557a4 returns, the function reads the allocator-context pointer source and dereferences it to obtain the allocator-context address.

This acquisition occurs before testing the recovered base against 8. The required pointer-source dereference must therefore be valid even on the special-case path.

If the recovered base is 8, the function returns. It does not read the header, validate it, call F-c0fc6d033caa, update allocator counters, or invoke the final allocator dependencies.

Earlier effects remain: accounting has already been updated and F-2fd8826557a4 has already been called. The amount read for this path is at represented address zero because it lies eight bytes before recovered base 8; accessibility remains a precondition.

### 5. Validate the allocation header

For any recovered base other than 8, the function checks the header at offset −16.

It invokes F-a817d8d58c10 if:

- The first header read is zero; or
- The first read is nonzero and bit 0 is set in a second header read.

The zero check short-circuits the second read. When the first read is nonzero, the bit test reads the header again rather than necessarily using the first value. No synchronization between these reads is established.

F-a817d8d58c10 is marked nonreturning in the supplied representation. The actual failure mechanism and diagnostics are unknown. No recovery or rollback is shown.

Validation occurs after the accounting writes, F-2fd8826557a4, and allocator-context acquisition. Invalid metadata therefore does not prevent those earlier effects.

### 6. Update allocator counters

After passing the header checks, the function calls F-c0fc6d033caa with the retained allocator-context address.

After that dependency returns, the function reads the first unsigned 16-bit metadata index and reads the header to obtain a size masked with **0x3FFFFFFC**. The mask clears bits 31, 30, 1, and 0. The resulting size is a multiple of four from zero through 1,073,741,820.

The function then performs these operations in order:

1. Subtract the captured size from context +548 + four times the first index.
2. Subtract the same size from context +780.
3. Read the second unsigned 16-bit index.
4. Subtract the same size from context +224 + four times the second index.
5. Subtract the same size from context +544.

All four size subtractions use the same captured size. Metadata changes made by F-c0fc6d033caa can affect the indices and size because those values are read after that call.

Next, F-09dcb55e8e0a is called with no explicit arguments. Its 32-bit result participates in address calculation without a shown range check. The representation treats that result as signed; a nonnegative or bounded result is not established.

The function then:

1. Decrements context +784 + four times that result.
2. Decrements context +912.
3. Reads the header again, masks it with 0x3FFFFFFC, and subtracts that newly obtained size from context +8.

The final size can differ from the earlier captured size. The header is not revalidated after either dependency.

All counter operations have represented 32-bit results, with no underflow check. If locations alias, their updates occur sequentially against then-current contents, not against a common initial snapshot.

The allocator-context address is not reacquired after F-c0fc6d033caa or F-09dcb55e8e0a. Changes to its global source do not redirect these subsequent accesses, although changes to the retained context’s contents can affect them.

### 7. Invoke final dependencies

After the seven direct allocator-counter writes, the function calls:

1. F-cc6c9b4a0f68 with the retained allocator-context address and the header address at recovered-base offset −16.
2. F-e586bff64fb7 with the retained allocator-context address.

The function returns if both calls return.

No direct pointer clearing, child-slot clearing, object-state marking, or storage-release primitive is shown.

## Side effects

- Four accounting-global reads.
- A low-word store followed by a high-word load and high-word store, with independently selected source and destination contexts.
- Seven allocator-counter writes on the accepted, nonspecial path.
- Dependency calls in the specified order.

No rollback restores earlier writes after failed validation or a nonreturning dependency.

Ownership transfer is not established. Passing a header address to F-cc6c9b4a0f68 does not prove that memory is freed, consumed, retained, or made reusable.

The caller must provide usable storage for all reached object fields, metadata, pointer sources, and counter locations. The evidence establishes no protection against stale references, repeated processing, concurrent modification, shared children, or cycles.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests.

1. **Null input.** Input zero returns without shown memory accesses or dependency calls.

2. **Traversal selection.** A zero control field causes no child-entry reads. Any nonzero control selects all 125 entries in ascending address order, assuming every recursive invocation returns.

3. **Live child reads.** If processing the first child changes the second child slot, the second recursive invocation receives the changed value. Changing the traversal control to zero does not stop the already-selected traversal.

4. **Stable-context borrowing.** With all four accounting-global reads selecting one unchanged context, amount 5, low word 3, and high word 7 produce low word 4,294,967,294 and high word 6.

5. **Stable-context sign extension.** Under the same stability conditions, amount 4,294,967,295, low word 10, and high word 7 produce low word 11 and high word 7.

6. **Different accounting contexts.** Suppose the four accounting-global reads select four distinct, disjoint contexts. The second supplies low word 3, the third supplies high word 9, and the amount is 5. The fourth context’s low word receives 4,294,967,294; the first context’s high word receives 8. Neither source field is itself changed by these two stores.

7. **High source aliases low destination.** Suppose the third read’s high-word source address equals the fourth read’s low-word destination address, with all other relevant locations disjoint. With amount 5 and captured low source 3, the low store writes 4,294,967,294. The subsequent high load observes that value, so the retained high destination receives 4,294,967,293.

8. **Special base.** If metadata recovers base 8 and all required earlier accesses are valid, accounting and F-2fd8826557a4 occur, and the allocator-context source is dereferenced. Header checks and allocator updates do not occur.

9. **Invalid header.** A zero first header read invokes F-a817d8d58c10 without the second header read. A nonzero first read followed by a second read with bit 0 set also invokes it. Earlier accounting effects remain.

10. **Zero masked size.** A stable header value of 2 passes validation and masks to zero. With disjoint valid counter locations, size-subtraction stores preserve their numeric values, but both count decrements and the final dependencies still occur.

11. **Changed final size.** If the initial captured size is 64 and F-09dcb55e8e0a changes the header to mask to 128, the first four size subtractions use 64 and the final context +8 subtraction uses 128, assuming no other relevant interference.
