# F-03b9616af95f

## Purpose

F-03b9616af95f conditionally removes a record from a linked structure associated with a table of record addresses.

The established behavior is narrower than a general-purpose removal operation: when bit 0 of the record’s status byte is set, the function may replace a table entry or update a predecessor’s link, may update a successor’s link, and then clears that status bit. It does not clear the record’s own link fields, validate structural consistency, release storage, or return a result.

Interpreting the status bit as “linked” or “active,” and the table entry as a list head, is inferred intent. Those names are useful descriptions, not independently established application semantics.

## Interface

The function accepts two address-valued inputs and has no defined return value:

| Input | Role established by accesses |
|---|---|
| Table base | Base address used to locate a four-byte table entry when the record’s status bit is set. |
| Record address | Address of the record whose status, table selector, and links are accessed. |

The supplied representation uses 32-bit integer quantities to hold addresses and table values. Each table entry and each link field occupies four bytes. The status access occupies one byte. This contract does not establish behavior for a wider-pointer implementation.

The accessed record layout is:

| Byte offset | Width | Role |
|---|---:|---|
| +8 | 4 bytes | Table selector used after subtracting one. |
| +12 | 4 bytes | Predecessor address; zero suppresses a predecessor update. |
| +16 | 4 bytes | Successor address; zero suppresses a successor update. |
| +20 | 1 byte | Status byte; bit 0 gates all structural work. |

Other record bytes are not explicitly accessed.

The selected table entry is four bytes wide and lies at a displacement equal to four times the selector minus one, with the subtraction performed before multiplication. Thus, a selector of 1 selects the entry at the table base; a selector of 2 selects the next entry.

### Preconditions

For a call to complete normally:

- The status byte at record offset +20 must be readable.
- If its bit 0 is set, the selector and both link fields must be readable as required by the chosen branches.
- The calculated table entry must be readable, even when the operation ultimately updates a predecessor instead of the table.
- Each destination selected for a write must be writable at the required width.
- Address calculation, alignment, and the represented integer operations must be valid for the execution environment.

A nonzero link is treated as an address without validation. Nonzero does not establish that the address is mapped, aligned, writable, or a member of the same structure.

For predictable linked-structure semantics, callers should also provide stable, non-overlapping records and table storage, with no concurrent mutation during the call. These are operational preconditions, not checks performed by the function.

## Behavior

### Status-gated no-op

The first explicit memory access reads the byte at record offset +20.

If bit 0 is clear, the function returns without explicitly reading the selector, either link, or any table entry. It performs no explicit write.

Other status bits do not activate the operation. For example, a status byte of 0x80 follows the no-op path.

The record address must still permit the initial status-byte read. This is not an unconditional null-safe operation.

### Table selection

If bit 0 is set, the function reads the four-byte selector at record offset +8, subtracts one, and uses four times the result as the displacement from the table base. It then reads the four-byte value at that location.

This table read occurs before deciding whether to update the table entry or a predecessor’s successor link. Supplying a usable predecessor does not eliminate the requirement for a valid table read.

No selector range check is present. In particular:

- Selector 1 selects displacement zero.
- Selector 0 arithmetically selects displacement −4, provided the arithmetic and resulting access are valid.
- Negative selectors can select locations before the table base.
- Large selectors can exceed the intended table or encounter arithmetic limits.

The supplied representation uses signed 32-bit integer operations for the selector-derived calculation. It does not establish a portable overflow policy. A contract must not silently replace this with checked arithmetic, unsigned indexing, or guaranteed modular wraparound.

### Table replacement or predecessor update

The table value already read is compared with the record address. The table-replacement branch requires both equality and a nonzero table value.

If both conditions hold, the function writes the record’s four-byte successor value into the selected table entry. It does not inspect or repair a predecessor’s successor field through the alternative branch.

Otherwise, the function reads the record’s predecessor field. If that field is nonzero, it writes the record’s successor value into the four-byte field at predecessor offset +16. If the predecessor field is zero, this phase performs no write.

These branches are mutually exclusive. A record that matches a nonzero selected table entry takes the table-replacement branch even if its predecessor field is also nonzero.

There is no check that a predecessor currently points to the record. Consequently, an inconsistent predecessor link is overwritten rather than rejected.

### Successor update

After the table-or-predecessor phase, the function reads the record’s successor field and checks it against zero.

If nonzero, it writes the record’s predecessor value into the four-byte field at successor offset +12. If zero, it skips that write.

This phase is independent of whether the preceding phase wrote anything. A successor’s predecessor field can therefore be updated even when the selected table entry does not match the record and the record’s predecessor is zero.

There is no check that the successor currently points back to the record.

### Status clearing and completion

After the structural phases, the function reads the status byte again and writes it back with bit 0 cleared. The other seven bits are preserved from this final read.

Under stable, non-aliasing conditions, a starting status of 0xA5 becomes 0xA4. The function does not replace the entire status byte with zero.

The record’s selector, predecessor field, and successor field receive no direct writes through those record-field locations. In the ordinary non-aliasing case, its links remain as stale references after removal.

### Observable ordering and repeated reads

The established phase order is:

1. Initial status read.
2. Selector read and selected table-entry read.
3. Optional table replacement or predecessor-link update.
4. Successor check and optional successor-link update.
5. Final status read and bit-clearing write.

The supplied source representation includes repeated link-field reads rather than an explicit single snapshot of the record. A later phase must not be specified as necessarily using values captured before an earlier write.

Within an assignment that both obtains a destination through a link and reads a value to store, the representation alone does not establish a complete machine-level ordering of those operand reads. Exact instruction sequencing, access counts after compilation, and volatile-memory behavior are documented_only unknowns.

## Side effects

For a stable, non-overlapping structure, the active path performs:

- At most one four-byte write to either the selected table entry or a predecessor’s successor field.
- At most one four-byte write to a successor’s predecessor field.
- One one-byte write clearing status bit 0.

The inactive path performs none of these writes.

No allocation, deallocation, ownership transfer, callback, logging, or external function call appears in the supplied body. In particular, unlinking does not establish that the record’s storage has been released or that the caller may release it safely.

The function provides no explicit error result, exception handling, rollback, lock, or atomic transaction. An invalid access can interrupt execution after earlier structural writes have occurred. The final status clear is not evidence of transactional protection.

Aliasing can change the ordinary interpretation. A predecessor, successor, or selected table entry may overlap the record or another accessed field. Earlier writes can then affect later reads. No alias rejection or self-link detection is present, so such cases cannot be described universally as preserving the record’s links or updating only distinct neighboring objects.

## Acceptance examples

The following are conditional static acceptance examples, not observed runtime results. Unless stated otherwise, storage is valid, arithmetic is representable, fields do not overlap, and no concurrent mutation occurs.

### Inactive record

Given a record whose status is 0xA4:

- The function reads that status byte.
- It performs no table or link access.
- It performs no write.
- The status remains 0xA4.

The table address and link contents need not be dereferenceable for this path, because the function does not use them.

### Removing the selected head

Given selector 1, a nonzero record address stored in the first table entry, zero predecessor, a nonzero successor, and status 0xA5:

- The first table entry becomes the successor address.
- The successor’s predecessor field becomes zero.
- The record’s status becomes 0xA4.
- The record’s own successor field remains unchanged.

### Removing an interior record

Given a selected table entry different from the record, nonzero predecessor and successor addresses, and status bit 0 set:

- The predecessor’s successor field becomes the successor address.
- The successor’s predecessor field becomes the predecessor address.
- The selected table entry remains unchanged.
- Status bit 0 is cleared.

These writes occur even if the neighboring fields did not previously reference the record.

### Removing a tail

Given a selected table entry different from the record, a nonzero predecessor, and zero successor:

- The predecessor’s successor field becomes zero.
- No successor destination is accessed.
- Status bit 0 is cleared.

### Removing a sole selected record

Given a nonzero selected table value equal to the record, with both links zero:

- The selected table entry becomes zero.
- No predecessor or successor destination is accessed.
- Status bit 0 is cleared.

### Mismatched table with no predecessor

Given a selected table entry different from the record, zero predecessor, and a nonzero successor:

- No table or predecessor write occurs.
- The successor’s predecessor field becomes zero.
- Status bit 0 is cleared.

This confirms that structural inconsistency does not produce an explicit error or prevent the successor phase.

### Repeated invocation

After a successful active invocation, a second invocation with no intervening changes observes bit 0 clear and performs no structural writes. This does not imply that the record’s retained links were erased.
