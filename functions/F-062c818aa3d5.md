# F-062c818aa3d5

This contract distinguishes:

## Behavior

Before the first explicit data-memory store, execution passes through an extended straight-line sequence of indirect invocations.

The initial target uses the incoming control-link value plus `0xFFE`. Later targets use successive code-associated anchors with the same displacement. This does not establish a function-pointer table or object dispatch interface.

Arguments include:

- Incoming values shifted left by seven or twelve.
- Low 32-bit call-result components frequently shifted left by eight.
- Retained transformations reused across intervening calls.
- High components passed unchanged, shifted, masked, or logically shifted right.
- Duplicate values in multiple argument positions.
- Explicit zeros, including transformations of already-zero values.

Calls with no displayed arguments are not established to consume no machine-state inputs.

No local status-based branch, retry, or error exit is represented in this phase. Nevertheless, unknown callees may modify shared storage, allocate or release memory, fail, redirect execution, or not return.

### Bit-field semantics

Represented masks select low fields of widths including 24, 22, 21, 20, 19, 18, 17, 16, 15, 14, 13, 12, 11, and one bit. Mask placement matters: restricting a value before shifting is not interchangeable with an unrestricted shift.

A logical right shift of a 64-bit carrier by 44 produces its high 32-bit component shifted right by twelve, rather than the unchanged high component.

Successive 32-bit shifts do not create a wider intermediate. Under truncating semantics, a left shift by 28 followed by another left shift by 28 produces zero.

These operations establish field selection and positioning only. Their domain meaning remains unknown.

### Opening memory mutations

The following descriptive roles identify retained values, not recovered object types:

- **Terminal components:** low and high 32-bit components of the last carrier before explicit stores.
- **Link base:** an earlier result shifted left by 25.
- **Primary base:** another earlier result multiplied by `0x02000000`.
- **Small base:** twice the result of masking an eight-bit-left-shifted value with `0x7FFF`, then logically shifting right by six.
- **Shifted payload:** an earlier result shifted left by eight.

The opening stores preserve several observable relationships:

- Terminal high plus `0x14` receives the link base as a word before link base plus nine receives the low byte of terminal high.
- Terminal low multiplied by 256, plus `0x54`, receives the primary base as a word.
- Link base plus nine is then written again, using the low byte of the link base.
- Primary base plus `0x14` receives zero before the byte at primary base plus five is read.
- Small base plus `0x14` receives zero before that loaded byte is transferred, zero-extended, to primary base plus `0x34`.
- Primary base plus `0x14` is read again. Small base plus `0x14` is subsequently zeroed again, followed by two consecutive byte stores at small base plus `0x15`, both using the low byte of that retained word.

Under 32-bit truncation, the link base has a zero low byte. Its second byte store therefore writes zero, but does not eliminate the earlier store.

The later primary-word read is a real represented dependency. Intervening aliased stores may change what it observes.

### Computed-address state manipulation

The next region uses loaded values as further addresses, without establishing object validity.

A fresh byte read at absolute address `0x05` becomes a zero-extended address base. Absolute address `0x01` receives the low byte of the small base. Stores through the byte-derived base, primary base, small base, and previously loaded words then interact.

A word loaded from the byte-derived base plus `0x54`, before that location is overwritten, is retained for subsequent scaling and stores. Call this the **retained anchor**. It supplies several later bases; it is not repeatedly recovered from that overwritten location.

Other established effects include:

- Primary base plus `0x11` receives the low byte of the shifted payload and later zero.
- Words loaded at offset `0x74` supply bases for stores at offset `0x54`.
- Some stores place a base into storage reached through that same base.
- Absolute address `0x54` receives twice the retained anchor.
- Absolute address `0x15` receives the low byte of the small base.
- Values scaled by four and eight drive later byte and word stores.

### Constant updates and shared-base capture

A later region stores `0x3A` as a byte, a halfword, and a word at related scaled destinations. These are distinct access widths, not three established text characters.

For the remaining description:

- **Adjusted anchor** is four times the retained anchor, minus `0x96`.
- **Update base** is four times the adjusted anchor.
- **Scaled target** is four times a word obtained through the later byte-derived offset-`0x74` read.
- **Late base** is twice that same word.

Update base plus `0x20` receives word updates in this order: `0x20`, `0x2F`, a zero-extended byte freshly read from update base plus four, and `0x20` again. That offset-four access is an 8-bit load, not the later 32-bit load from the same relative offset.

After these updates finish, the shared word at absolute address `0x087FBBBC` is read once. Its captured 32-bit value is the **captured shared base** used throughout the repeated-update section and into the final region.

This capture precedes the word store of `0x20` to absolute address `0x60`. Subsequent stores do not trigger a refresh of the captured shared base, even if they alias its source storage.

The final mutation region begins by reading the word at absolute address `0xA9`, then reading a word at scaled target plus `0x74`. Both precede the byte store to absolute address `0x3A`.

The `0x3A` byte is derived from eight times the adjusted anchor plus `0x30`, truncated to eight bits. The word captured from `0xA9` remains available for later use regardless of subsequent changes to its source.

After the `0x3A` store, words at late base plus `0x14` and update base plus four are captured, in that order. The latter is a 32-bit load, distinct from the earlier byte load at update base plus four.

Before setting absolute address `0x67`, the function performs computed stores that include:

- Low update-base byte at late base plus `0x0D`.
- Byte `0x6C` at update base plus eight.
- Low captured-shared-base byte at update base plus `0x0D` and plus nine.

Absolute address `0x67` then receives the low byte of the retained `0xA9` word. A word at late base plus `0x44` is read before a **fresh byte read from `0x67`** supplies the store at absolute address `0x21`.

### Fresh `0x67` reads and terminal dependencies

Two later byte stores to update base plus nine each obtain their payload from a separate fresh read of absolute address `0x67`.

They are not unconditional reuse of either the originally stored byte or the byte read for `0x21`:

- The first later read follows intervening computed-address stores, including the word store at captured shared base plus `0x44`.
- Between the two later reads, stores occur at late base plus nine and update base plus `0x44`, followed by a word read at update base plus `0x54`.

- Update base plus `0x14` is freshly read before later stores use its low byte.

A fresh word read at late base plus four supplies a new base. Twice that base receives halfword `0x65`; its offset-`0x64` word is captured before terminal destination base plus `0x54` receives word value 100.

The new base plus `0x74` is then freshly read. A subsequent late-base-plus-`0x64` read supplies another destination. The final stores include a word at that destination plus `0x54` and a word through twice the captured offset-`0x64` value.

**Required:** repeated updates continue using the captured base. Re-reading the shared word for each group is not equivalent. The capture occurs after the update-base-plus-`0x20` sequence and before the absolute-`0x60` store.

**Given:** observation distinguishes accesses.

### Fresh `0x67` reads may differ

**Required:** a later fresh read for update base plus nine uses the changed byte. Neither the original `0x67` store payload nor the earlier read for `0x21` is an unconditional substitute. The two later computed byte stores have separate reads.
