# F-9678b51c49d5

## Purpose

F-9678b51c49d5 rewires a linked node structure around a designated target node. Under the conventional interpretation that the fields at offsets +4, +8, and +12 are parent, left-child, and right-child links, respectively, the operation is a **right rotation**:

- The target’s left child becomes the promoted node.
- The promoted node’s former right subtree becomes the target’s left subtree.
- The target becomes the promoted node’s right child.
- The target’s former incoming link is redirected to the promoted node, either through a root-holder slot or through its former parent.

This tree interpretation is inferred intent. The established behavior is the ordered manipulation of four-byte fields described below. The function does not validate that its inputs form a tree.

There is no explicit result value, allocation, deallocation, callback, or error-reporting operation in the supplied body.

For a valid, non-aliasing tree configuration, the promoted node replaces the target at its former position. The target remains allocated and linked beneath the promoted node.

## Behavior

### Structural result under ordinary tree invariants

Let the promoted node be the node initially referenced by the target’s left-child field. Let the transferred subtree be the node initially referenced by the promoted node’s right-child field.

For stable, non-overlapping storage satisfying the tree preconditions, completion establishes:

| Link | Result |
|---|---|
| Target’s left child | Former right child of the promoted node |
| Transferred subtree’s parent, if that subtree is nonzero | Target |
| Promoted node’s parent | Target’s former parent |
| Target’s former incoming link | Promoted node |
| Promoted node’s right child | Target |
| Target’s parent | Promoted node |

The promoted node’s left-child field and the target’s right-child field are not explicitly modified.

The root case is selected by comparing the root-holder slot with the target address. It is **not** selected by testing whether the target’s parent-like field is zero.

### Transfer and parent-link preparation

The promoted-node address is first read from the target at offset +8. That address is retained for the remainder of the operation.

The promoted node’s field at +12 is then read and copied into the target’s field at +8. This detaches the promoted node from that child slot and substitutes its right-child value.

The function subsequently reads the promoted node’s +12 field again to decide whether to update a transferred subtree’s parent. The decision is therefore based on a fresh read, not necessarily the value just copied into the target.

If that fresh value is nonzero, the promoted node’s +12 field is read once more to obtain the address whose +4 field receives the target address.

For ordinary stable storage, these reads all identify the same transferred subtree. With aliasing or interfering writes, the value copied, the value tested, and the address used for the parent update can differ. In particular, the body does not provide a single captured transferred-subtree value governing all three actions.

After this optional parent update, the target’s +4 field is read and copied into the promoted node’s +4 field.

### Selection of the incoming link

Only after the preceding mutations does the function read the context’s +16 field to locate the root holder. It reads the holder’s +4 field and compares that value with the target address.

If the root slot equals the target, that slot is replaced with the promoted-node address. No former-parent child field is accessed in this branch.

Otherwise, the target’s +4 field is read again to obtain the former-parent address used for incoming-link repair. This is a fresh read after the promoted node’s parent-like field has already been written.

The function then reads that parent’s +12 field:

- If it equals the target address, the parent’s +12 field is replaced with the promoted-node address.
- Otherwise, the parent’s +8 field is replaced with the promoted-node address.

The fallback branch does not read the parent’s +8 field to verify that it contains the target. Consequently, malformed parent-child relationships are not rejected; the function can overwrite an unrelated left-child link.

### Final attachment

After repairing the incoming link, the function writes the target address into the promoted node’s +12 field.

Its final explicit store writes the promoted-node address into the target’s +4 field.

This ordering matters. The operation is not an atomic replacement of one valid tree with another. During execution, the links can describe an intermediate structure that does not satisfy the final parent-child relationships.

### Repeated reads and aliasing

Only the promoted-node address is established once and retained as the central node address. Several other values are deliberately described as fresh reads because the supplied body does not consistently reuse earlier values.

The ordinary rotation result assumes those reads see stable, coherent storage. If roles alias—for example, if the promoted node is the target, or if a holder field overlaps a node field—earlier writes may change subsequent reads. The body contains no special handling for such configurations.

The ordered field accesses remain the established behavior; a valid tree result for overlapping layouts is not promised.

## Side effects

### Memory mutations

For an ordinary non-overlapping configuration, the operation performs five unconditional four-byte stores and one additional four-byte store when the transferred subtree is nonzero.

The unconditional mutations affect:

1. The target’s left-child field.
2. The promoted node’s parent-like field.
3. Exactly one incoming-link location: the root slot, the former parent’s right-child field, or the former parent’s left-child field.
4. The promoted node’s right-child field.
5. The target’s parent-like field.

The conditional mutation affects the transferred subtree’s parent-like field.

Because addresses may alias, these are logical store destinations, not a guarantee of five or six distinct memory locations.

A zero transferred-subtree value is supported by a specific branch: its parent update is skipped. This must not be generalized into support for a zero target, zero promoted node, or zero root-holder address.

## Acceptance examples

These examples are conditional expectations derived from static inspection. They have not been executed.

### Root rotation with a transferred subtree

Assume the root slot names the target, the target’s left child is a distinct promoted node, and the promoted node’s right child is a distinct nonzero subtree.

On completion:

- The root slot names the promoted node.
- The promoted node’s parent-like field contains the target’s former parent-like value, whether that value is zero or nonzero.
- The promoted node’s right child is the target.
- The target’s parent is the promoted node.
- The target’s left child is the transferred subtree.
- The transferred subtree’s parent is the target.

The target’s former parent is not dereferenced through the non-root repair branch.

### Non-root target in a right-child slot

Assume the root slot differs from the target and the target’s parent has the target in its +12 field.

The parent’s +12 field becomes the promoted-node address. Its +8 field is not explicitly written by incoming-link repair. The remaining rewiring follows the structural result above.

### Non-root target in a left-child slot

Assume the root slot differs from the target, the parent’s +12 field differs from the target, and its +8 field names the target.

The parent’s +8 field becomes the promoted-node address. The parent’s +12 field is read but not written by incoming-link repair.

### Empty transferred subtree

Assume the promoted node’s +12 field remains zero throughout the transfer phase.

The target’s +8 field becomes zero, and no transferred-subtree parent update occurs. The promoted node still becomes the target’s parent, and its +12 field becomes the target address.

### Malformed incoming relationship

Assume a non-root target has an accessible parent, but neither child field of that parent names the target.

The function still replaces the parent’s +8 field with the promoted-node address because the +12 comparison fails. It does not report the inconsistency or preserve that unrelated left-child link.

### Missing promoted node

Assume the target’s +8 field is zero.

The body attempts to read the would-be promoted node’s +12 field. It does not return successfully merely because the child is absent. Whether this access faults or has some other effect is environment-dependent and documented_only.
