# F-7b527193a60e

## Purpose

F-7b527193a60e performs a fixed sequence of link updates involving a pivot node, the node referenced by its offset-8 link, and a root-reference structure supplied indirectly through a separate argument.

**Inferred intent:** the operation is a right rotation of a parent-linked binary tree. Under that interpretation, offset 4 is the parent link, offset 8 is the left-child link, and offset 12 is the right-child link. The pivot’s left child is promoted, and that child’s former right subtree becomes the pivot’s left subtree.

**Established behavior:** the routine rewires these fields without validating the tree, checking either argument for null, or checking that the promoted node exists. It also replaces either an indirect root reference or one link in the pivot’s former parent.

The tree interpretation is useful for describing valid inputs, but it does not add validation or behavior absent from the supplied evidence.

## Interface

### Inputs

Two machine-word arguments are supplied:

1. **Context address.** Used to locate a root-reference object through the 32-bit field at byte offset 16.
2. **Pivot address.** Identifies the node whose links are rearranged.

The supplied representation uses 32-bit integer and pointer-bearing fields. Each described link read or write occupies four bytes. The evidence supports a 32-bit address model; it does not establish a portable interface for a wider-pointer environment.

### Relevant layouts

The routine accesses the following fields:

| Object | Byte offset | Width | Use |
|---|---:|---:|---|
| Context | 16 | 4 bytes | Address of a root-reference object |
| Root-reference object | 4 | 4 bytes | Root link, compared against the pivot and conditionally replaced |
| Node | 4 | 4 bytes | Parent link under the tree interpretation |
| Node | 8 | 4 bytes | Left-child link under the tree interpretation |
| Node | 12 | 4 bytes | Right-child link under the tree interpretation |

Offsets are byte displacements from the relevant object address. The routine does not inspect any payload field or an offset-0 field.

For the behavioral description:

- **Pivot** means the node designated by the second argument.
- **Promoted node** means the address obtained from the pivot’s offset-8 field at entry.
- **Transfer subtree** means the node designated by the promoted node’s offset-12 field during the early link updates.
- **Former parent** means the address read from the pivot’s offset-4 field when the non-root branch needs it.

These names describe roles, not independently validated object types.

No error code, exception interface, or recovery result is established.

### Preconditions for an ordinary tree rotation

For the intended tree operation, the caller must supply:

- Readable context storage through its offset-16 field.
- A valid root-reference object whose offset-4 field is readable and, when the pivot is the root, writable.
- A valid pivot with accessible fields at offsets 4 and 8.
- A non-null promoted node with accessible fields at offsets 4 and 12.
- A valid writable offset-4 field in any non-null transfer subtree.
- If the pivot is not the recorded root, a valid former parent with a readable offset-12 field and a writable selected child field.
- A structurally consistent tree with distinct node roles where required by the rotation, and no concurrent mutation of the relevant links.

These are caller-side requirements for the intended result. The routine does not enforce them.

## Behavior

### Ordered accesses and updates

The following stages occur in source order. The ordering is material: some fields are read more than once, and later reads can observe earlier writes if objects overlap.

1. **Select the promoted node.**  
   Read the pivot’s four-byte offset-8 field and retain the resulting address for the rest of the operation. Subsequent changes to the pivot’s offset-8 field do not select a different promoted node.

2. **Replace the pivot’s left link.**  
   Read the promoted node’s offset-12 field and write that four-byte value to the pivot’s offset-8 field.

3. **Conditionally repair the transfer subtree’s parent link.**  
   Read the promoted node’s offset-12 field again and compare it with zero.

   - If it is zero, perform no transfer-subtree parent update.
   - If it is nonzero, read that same offset-12 field again to obtain an address, then write the pivot address to that addressed object’s offset-4 field.

   Thus, this stage uses separate reads rather than a single saved transfer-subtree value. For ordinary, non-overlapping tree nodes without concurrent mutation, those reads identify the same subtree. That equivalence is not guaranteed for arbitrary aliasing or external mutation.

4. **Give the promoted node the pivot’s previous parent link.**  
   Read the pivot’s offset-4 field and copy it into the promoted node’s offset-4 field.

5. **Locate and inspect the root reference.**  
   Read the context’s offset-16 field to obtain the root-reference object address. Read that object’s offset-4 field and compare it with the pivot address.

6. **Reconnect the promoted node above the pivot.**

   - **Recorded-root case:** if the inspected root-reference field equals the pivot address, write the promoted-node address into that same root-reference field.
   - **Non-root case:** otherwise, read the pivot’s offset-4 field to obtain its former parent. Read that parent’s offset-12 field and compare it with the pivot address.
     - If equal, write the promoted-node address into the parent’s offset-12 field.
     - Otherwise, write the promoted-node address into the parent’s offset-8 field.

   The non-root branch does not check whether the parent’s offset-8 field actually references the pivot. Failure of the offset-12 comparison is sufficient to select the offset-8 write.

7. **Attach the pivot below the promoted node.**  
   Write the pivot address into the promoted node’s offset-12 field.

8. **Set the pivot’s new parent.**  
   Write the promoted-node address into the pivot’s offset-4 field.

The routine then returns.

This ordering describes accesses established by the supplied representation. It does not establish a more detailed processor-level ordering between independent operand-address calculations within an individual assignment.

### Result for a valid, non-overlapping tree

Let the promoted node’s original right child be the transfer subtree. On completion:

- The pivot’s left child is the transfer subtree.
- If the transfer subtree is non-null, its parent is the pivot.
- The promoted node’s parent is the pivot’s original parent.
- The root reference or former parent’s selected child link now references the promoted node.
- The promoted node’s right child is the pivot.
- The pivot’s parent is the promoted node.

The promoted node’s left-child field and the pivot’s right-child field are not directly written. Payload fields are not directly accessed.

For a valid root rotation, the promoted node receives the pivot’s original parent-field value exactly as stored. The routine does not force that value to zero or to any particular sentinel.

## Side effects

### Memory mutation

On a valid input, the routine directly writes:

- The pivot’s offset-8 field.
- The transfer subtree’s offset-4 field, only if the relevant link is nonzero.
- The promoted node’s offset-4 field.
- Exactly one reconnection field:
  - The root-reference object’s offset-4 field;
  - The former parent’s offset-12 field; or
  - The former parent’s offset-8 field.
- The promoted node’s offset-12 field.
- The pivot’s offset-4 field.

This is five write operations when the transfer subtree is null and six when it is non-null. With overlapping objects, multiple writes can target the same storage; these counts describe operations rather than distinct destinations.

### Ownership and lifetime

The routine rearranges address values already supplied through the input structure. Callers remain responsible for ensuring that all required objects remain alive and accessible throughout the operation. The evidence does not establish a broader ownership policy.

### Partial updates and synchronization

The operation is not presented as transactional. The pivot’s offset-8 field is written before the context and root-reference fields are read. A failure during a later access can therefore occur after earlier links have changed.

No locks, atomic primitives, callbacks, logging, or explicit synchronization operations are visible. No concurrency safety guarantee is established.

No direct access to named global storage is visible. Because addresses are supplied indirectly, the routine can still modify storage that the surrounding program treats as global.

- No transfer-subtree parent field is accessed.

**Expected:** the former parent’s offset-8 field becomes the promoted node, with the remaining rotation updates performed normally.

### Missing promoted node
