# F-c78be994279e

## Purpose

F-c78be994279e rearranges a linked structure around a supplied node and the node referenced by its field at byte offset +8. It updates a root slot or an incoming parent link, transfers one intervening link, and makes the supplied node a child of the promoted node.

**Inferred intent:** If offset +4 is a parent link, +8 is a left-child link, and +12 is a right-child link, this operation is a right rotation. That interpretation explains the visible updates but is not required to describe them. The field names below are descriptive roles, not independently verified type information.

**Established behavior:** The operation performs the link updates directly. It does not validate the structure, allocate storage, release storage, report an error, or return a result value.

## Interface

The function accepts two address-bearing arguments:

| Argument | Role |
|---|---|
| Context address | Identifies an object whose field at byte offset +16 supplies the address of a separate root-holder object. |
| Subject address | Identifies the node around which the rearrangement occurs. |

The function has no explicit return value.

## Behavior

### Ordered field accesses and updates

The following is the order exposed by the supplied representation. It is a source-level ordering contract, not a claim that every read must become a separate hardware transaction.

1. **Capture the promoted node.**  
   The subject’s +8 field is read once to obtain the promoted-node address.

2. **Replace the subject’s +8 link.**  
   The promoted node’s +12 field is read. That value is written to the subject’s +8 field.

3. **Conditionally repair the transferred node’s parent link.**  
   The promoted node’s +12 field is read again and compared with zero. If it is nonzero, that field is read again to select the node whose +4 field receives the subject address.

   These are separate reads in the supplied representation. The value copied into the subject’s +8 field is not explicitly retained for the condition or the destination selection.

4. **Assign the promoted node’s incoming parent.**  
   The subject’s +4 field is read, and its value is written to the promoted node’s +4 field.

5. **Locate and inspect the root slot.**  
   The context’s +16 field is read to obtain the root-holder address. The holder’s +4 field is read and compared with the subject address.

6. **Redirect the incoming reference.**
   - If the root slot equals the subject address, the promoted-node address is written into that slot.
   - Otherwise, the subject’s +4 field is read again to obtain an incoming-parent address. That parent’s +12 field is read and compared with the subject address.
     - If equal, the parent’s +12 field is replaced with the promoted-node address.
     - If unequal, the parent’s +8 field is replaced with the promoted-node address.

   The fallback branch does not check whether the parent’s +8 field actually refers to the subject.

7. **Attach the subject beneath the promoted node.**  
   The subject address is written to the promoted node’s +12 field.

8. **Finish the subject’s parent update.**  
   The promoted-node address is written to the subject’s +4 field.

The root-slot comparison occurs after the transferred-link update and the promoted-parent update. The subject’s final parent update is the last visible write.

### Normal structural result

For a stable, non-overlapping structure satisfying the ordinary tree interpretation:

- The subject’s former left child becomes the replacement at the subject’s incoming position.
- The promoted node’s former right child becomes the subject’s left child.
- A nonzero transferred child receives the subject as its parent.
- The promoted node receives the subject’s former parent.
- The promoted node’s right child becomes the subject.
- The subject’s parent becomes the promoted node.

The operation does not traverse descendants or recompute metadata.

### Root and non-root selection

The root-slot comparison alone selects the root path. A zero parent address does not select it, and no consistency check reconciles the root slot with the subject’s parent field.

On the non-root path, the incoming parent’s +12 field has precedence. If both its +8 and +12 fields refer to the subject, only +12 is replaced. If neither refers to the subject, +8 is nevertheless overwritten.

### Aliasing and repeated reads

The normal rotation description assumes distinct, stable storage for the relevant roles. The function does not enforce that assumption.

If participating objects or fields overlap, an earlier write can change a later read. In particular:

- The promoted node’s +12 field is consulted repeatedly during the transferred-link update.
- The subject’s +4 field is read before the root comparison and may be read again afterward.
- The context and root-holder fields are not read until several node writes have occurred.

For such inputs, the ordered accesses above are the established description; a coherent tree result is not promised. There is no basis for assuming that a transferred-node parent write preserves other fields when storage overlaps.

Concurrent mutation is likewise not given defined synchronization semantics. No locking, atomic operation, or memory-order primitive is visible.

## Side effects

On an ordinary non-overlapping execution, the operation changes:

- The subject’s +8 field.
- The transferred node’s +4 field, only when the relevant transferred-link check is nonzero.
- The promoted node’s +4 field.
- Exactly one incoming-reference slot: the root holder’s +4 field, the incoming parent’s +12 field, or the incoming parent’s +8 field.
- The promoted node’s +12 field.
- The subject’s +4 field.

That is five field writes when the transferred link is zero and six when it is nonzero. These counts describe write operations, not necessarily distinct storage locations under aliasing.

The context’s +16 field is read but not directly written. No direct writes to payloads, counts, flags, colors, heights, or other metadata are visible.

All referenced storage is caller-provided. No ownership transfer, allocation, destruction, or release operation is visible. Re-linking nodes does not by itself establish ownership of those nodes.

There is no validation phase or rollback. If an invalid access interrupts execution, earlier writes may already have occurred. The supplied evidence does not establish the resulting exception, signal, diagnostic, return behavior, or recovery state.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, addresses identify distinct valid objects, memory remains stable during execution, and fields do not overlap.

### Root replacement with no transferred child

Given:

- The root slot identifies the subject.
- The subject’s +8 field identifies the promoted node.
- The promoted node’s +12 field is zero.
- The subject’s +4 field is zero.

Expected afterward:

No transferred-node parent write occurs.

### Non-root replacement through the parent’s +12 field

Given:

- The root slot does not identify the subject.
- The subject’s +4 field identifies an incoming parent.
- That parent’s +12 field identifies the subject.
- The promoted node’s +12 field identifies a transferred node.

Expected afterward:

- The parent’s +12 field identifies the promoted node.
- The promoted node’s +4 field identifies that parent.
- The subject’s +8 field identifies the transferred node.
- The transferred node’s +4 field identifies the subject.
- The promoted node’s +12 field identifies the subject.
- The subject’s +4 field identifies the promoted node.
- The root slot is unchanged.

### Non-root fallback through the parent’s +8 field

If the root slot differs from the subject and the incoming parent’s +12 field also differs from the subject, the parent’s +8 field is replaced with the promoted-node address.

This result applies even if the parent’s +8 field previously identified some other node. Acceptance must not impose a missing membership check.

### Both parent links identify the subject

If both parent child-link fields identify the subject, the +12 comparison succeeds. Only the parent’s +12 field is redirected; its +8 field remains unchanged, assuming no overlap.

### Root slot matches despite a nonzero parent field

If the root slot identifies the subject while the subject’s +4 field identifies another node, the root path still applies. The promoted node receives that nonzero parent address, but no child link in that parent is redirected.

This is established behavior on inconsistent input, not evidence that the resulting structure is valid.

### Null promoted address

A zero subject +8 field is not an empty-operation case. The function proceeds to access a field relative to that value. A successful no-op, error return, or defined failure mechanism is not established.
