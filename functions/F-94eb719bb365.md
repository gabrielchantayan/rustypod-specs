# F-94eb719bb365

## Purpose

F-94eb719bb365 selects a record through a caller-supplied handle, initializes two separate local values, invokes three dependencies using the address of the first local, writes a state byte in the selected record, and invokes a final dependency.

Selection occurs once, before any dependency call. A discriminator in the initially referenced record determines whether the selected address is the initial address or an alternate address stored within that record. The function does not follow a chain of alternate records.

**Established static behavior:** on the normal returning path, four dependency calls occur in a fixed sequence, with a one-byte write between the third and fourth calls. The function returns no explicit result.

**Inferred intent:** the first three calls may prepare, apply, and finalize some temporary state, and the byte write may mark a record as updated. These interpretations do not establish object boundaries, ownership transfer, resource release, or a semantic meaning for the byte.

## Behavior

### Record selection

The function reads the handle cell and retains the resulting initial record address.

It then reads the discriminator byte at initial-record offset `0x70`:

- Zero selects the initial record.
- Any nonzero value causes a read of the alternate address at initial-record offset `0x1c`; that address becomes the selected address.

Only a zero-versus-nonzero distinction is used. Whether the byte is interpreted as signed does not change that decision.

Selection involves at most one alternate-address read. The alternate record’s discriminator is not inspected, and no address tag removal is visible. An alternate address equal to the initial address is not specially handled.

The selected address is captured before the first dependency call. Later changes to the handle cell, discriminator, or alternate-address field do not trigger reselection. This does not guarantee that the captured storage remains allocated, writable, or otherwise valid.

### Local initialization and exposure

After selection, the function initializes the first 32-bit local from the first payload, then initializes the second 32-bit local from the second payload.

The first local’s address is subsequently supplied to three dependencies. The same address is used each time, with no intervening reinitialization by this function.

These facts establish a shared address through which the dependencies may affect the first local, subject to their contracts. They do not establish a shared two-word buffer. Any claim that a dependency can obtain the second payload by accessing four bytes beyond that address requires additional evidence about layout and valid access.

The separately forwarded first payload is not visibly reloaded from the first local. A valid mutation of that local therefore does not, by itself, change the scalar payload argument used later.

The initialization order is source-level evidence. Exact machine-store ordering, optimization, and the physical placement of the locals are not established.
