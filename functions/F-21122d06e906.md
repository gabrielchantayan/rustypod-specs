# F-21122d06e906

## Purpose

F-21122d06e906 dispatches an input record to a linked sequence of callbacks and, conditionally, processes that record against a collection stored in the associated state.

The established behavior has three collection-processing outcomes:

- Stop when a collection-entry operation returns nonzero.
- Copy the input into a destination supplied by a dependency and mark that destination with a one-byte value of 1.
- When no destination is supplied, perform collection maintenance, clear three one-byte fields, and either leave the leading record unchanged, replace it, or expand its four signed bounds.

Interpreting the four input words as rectangle coordinates and the final operation as a bounding-rectangle union is **inferred intent**. The contract below specifies the actual signed comparisons and writes independently of that interpretation.

The function has no explicit result value. Its observable effects are callback invocations, dependency invocations, memory reads, and memory writes.

## Interface

### Inputs

The function receives two addresses:

1. **Owner address.** Identifies a structure containing:
   - At byte offset `0x24`, a 32-bit pointer to associated state.
   - At byte offset `0x90`, a 32-bit value supplied as the first argument to each callback.

2. **Input address.** Identifies at least four readable 32-bit words, at offsets `0`, `4`, `8`, and `12`. Signed comparisons treat these words as signed 32-bit integers.

The source representation uses 32-bit integers and pointers, one-byte stores for marker fields, and a 64-bit temporary for paired values. It does not establish portable behavior on architectures with different widths.

### Associated-state layout

The state initially reached through the owner has these accessed fields:

| Byte offset | Access |
|---|---|
| `0x00` | First callback-node pointer; later also the collection-processing gate |
| `0x04` | Beginning of the collection region |
| `0x54` | Signed 32-bit enable/control value, sampled before callbacks |

Each traversed callback node has:

| Byte offset | Access |
|---|---|
| `0x04` | Optional callback address |
| `0x14` | Next-node pointer |

Within the collection region, entry addresses are separated by 20 bytes. An entry contains four 32-bit words at offsets `0`, `4`, `8`, and `12`, followed by an accessed one-byte marker at offset `16`. No behavior is established for the remaining three bytes of that 20-byte interval.

### Return and error interface

There is no explicit return value and no structured error reporting.

Several dependency results select an early return or a fallback. These results are not exposed to the caller as status codes. Invalid addresses, inaccessible memory, corrupted links, or dependency failures have no explicit local recovery path.

### Preconditions and ownership

For defined execution, every dereferenced address must remain valid for the relevant access. Callback nodes must remain readable when their callback and successor fields are accessed. Dependencies must accept the addresses supplied to them.

The function does not explicitly allocate or free memory. It borrows the input address and directly accesses owner-associated storage. Ownership, retention, allocation, and release behavior inside dependencies and callbacks are unknown. No assumption that those callees preserve memory or globals is justified.

## Behavior

### 1. Sample state and dispatch callbacks

The function first reads the associated-state pointer from owner offset `0x24`. It then samples the signed control value at state offset `0x54`, before invoking any callbacks.

Traversal starts with the node pointer at state offset `0x00`.

For each non-null node:

1. Read its callback field at node offset `0x04`.
2. If that field is non-null, invoke the callback with:
   - The value read from owner offset `0x90`.
   - The input address.
3. After the callback returns, or immediately if no callback exists, read the next-node pointer at node offset `0x14`.

This ordering allows a callback to alter the successor used by the traversal. The successor is not snapshotted before the callback.

The owner value at offset `0x90` is obtained for each callback invocation. It is not established as a single value cached for the whole traversal.

Callbacks are dispatched regardless of whether the previously sampled control value is positive. A null callback skips only that invocation; it does not stop traversal.

There is no cycle detection or traversal limit. A cyclic or continually extended callback chain can prevent the function from reaching collection processing.

### 2. Apply the post-callback collection gate

After traversal:

- If the sampled control value is zero or negative, return.
- If that sampled value is positive, obtain state through owner offset `0x24` again and inspect the first word of the currently referenced state.
- If that first word is zero, return.
- Otherwise, use the newly obtained state as the basis for collection processing.

The control value is not resampled after callbacks. Consequently, callback changes to state offset `0x54` do not alter the gate for this invocation.

Conversely, a callback change to the owner’s state pointer can change which state supplies the collection and its first-word gate. The original state supplies the control snapshot; the post-callback state supplies the subsequent collection address.

The source expression contains multiple accesses through owner offset `0x24`; an exact ordering between those expression-internal accesses is not established here. Their consistency requires stable storage during that expression.

Callback return values do not determine the collection-processing outcome: the nonpositive-control path returns, and the positive-control path replaces the temporary callback-result data with state-derived values.

### 3. Scan collection entries

The collection base is four bytes after the selected state base.

Starting with index zero, the function repeatedly:

1. Calls F-68329af2941a with the collection base.
2. Compares the index with that dependency’s unsigned 32-bit result.
3. If the index is smaller, calls F-fe188ad6021a with:
   - The collection base plus 20 times the index.
   - The input address.
4. Returns immediately if F-fe188ad6021a returns nonzero.
5. Otherwise advances the index modulo 256 and repeats.

The collection-size dependency is called on every loop condition, including the condition that ends the scan. The size is not cached.

The index is restricted to `0` through `255` by an explicit low-byte mask after increment. Thus:

- For a stable size from `0` through `255`, the scan can terminate after visiting the corresponding indices.
- For a stable size of `256` or greater, no index can reach the reported size. The scan repeats after index 255 unless an entry operation returns nonzero or a later size result permits termination.

This is an unsigned size comparison. The contract does not reinterpret a large returned value as a negative size.

### 4. Request a destination

If scanning finishes without an entry operation returning nonzero, the function calls F-12b0ae893f07 with the collection base.

If the result is non-null, that result is used as writable destination storage:

- Input words at offsets `4`, `8`, and `12` are read before the first destination write.
- Input word `0` is read and written to destination word `0`.
- The three previously read words are written to destination offsets `4`, `8`, and `12`, in that order.
- Destination byte `16` is set to `1`.
- The function returns.

No bytes at destination offsets `17` through `19` are explicitly written.

This path does not invoke the later maintenance or bound-expansion operations.

### 5. Perform fallback maintenance

If F-12b0ae893f07 returns null, the function performs these operations in order:

1. Call F-9ba16c1c2031 with the collection base as both arguments.
2. Clear the byte at state offset `0x28`.
3. Call F-12cb3c413baa with the collection base and the entry at index 2.
4. Clear byte `16` of entry 2.
5. Call F-12cb3c413baa with the collection base and the entry at index 3.
6. Clear byte `16` of entry 3.

The byte at state offset `0x28` is byte `16` of entry 1. Therefore, the explicit clears affect the marker bytes of entries 1, 2, and 3.

The function does not explicitly clear entry 0’s marker. Any changes to that marker caused by dependencies remain unspecified.

The maintenance calls precede the respective marker clears. Their internal reads, writes, and ownership effects are unknown; they must not be described as known copies, removals, or releases.

### 6. Classify the input and leading record

After fallback maintenance, call F-ddca41e891a8 with the input address.

- A nonzero result causes an immediate return.
- A zero result permits a second call to the same dependency, this time with the collection base.

If the second result is nonzero, replace the leading record’s four words with the input’s four words and return.

The replacement uses the same read-before-write pattern as the destination-copy path: input offsets `4`, `8`, and `12` are sampled first, followed by reading and writing input offset `0`, followed by writing the three saved words. No explicit marker update accompanies this replacement.

The semantic meaning of the predicate is unknown. Calling a record “empty,” “invalid,” or “degenerate” would be an inference rather than an established condition.

### 7. Expand the leading record

If both predicate calls return zero, update the leading record sequentially:

| Word | Result |
|---|---|
| `0` | Signed minimum of current leading word 0 and input word 0 |
| `1` | Signed minimum of current leading word 1 and input word 1 |
| `2` | Signed maximum of current leading word 2 and input word 2 |
| `3` | Signed maximum of current leading word 3 and input word 3 |

The writes occur in word order: `0`, `1`, `2`, then `3`.

Each later comparison occurs after the preceding write. The operation is not a snapshot-based four-word transaction. Aliasing or external mutation can therefore affect later reads.

The comparisons require no coordinate addition, subtraction, area calculation, or normalization. Signed 32-bit extremes remain ordinary comparison operands; no arithmetic overflow is introduced by the min/max operation itself.

## Side effects

Directly established effects include:

- Callback invocation in linked traversal order.
- Repeated size queries and per-entry operations.
- A possible four-word destination write followed by a one-byte marker write.
- Fallback maintenance calls followed by three ordered marker clears.
- Possible replacement or signed min/max modification of the leading record.

Early returns do not roll back earlier effects. In particular, a nonzero input predicate result occurs **after** maintenance and the three marker clears.

No explicit synchronization, locking, atomic access, diagnostic output, or exception handling is present. Concurrent mutation is not given a defined synchronization contract.

Aliasing is not rejected. However, behavior must follow the actual access order rather than assuming disjoint input and destination buffers. Dependency calls can also alter memory before subsequent local reads.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Unless stated otherwise, memory is valid, callbacks terminate, and dependencies do not introduce additional relevant mutations.

1. **Callbacks despite disabled collection processing.**  
   With a sampled control value of `0` and two reachable non-null callbacks, both callbacks run in traversal order. Collection dependencies are not called afterward.

2. **Control snapshot remains authoritative.**  
   With a sampled control value of `-1`, a callback changes that field to `1`. Traversal completes, but collection processing still does not begin.

3. **Post-callback state selection.**  
   With a sampled positive control value, a callback replaces the owner’s state pointer. If the new state’s first word is zero, the function returns without scanning its collection.

4. **Entry operation accepts the input.**  
   With stable size `3`, entry operations for indices `0` and `1` return zero, and the operation for index `2` returns nonzero. The function returns without requesting a destination.

5. **Destination insertion.**  
   Scanning terminates, and F-12b0ae893f07 returns a valid destination. For input words `(4, 6, 12, 18)`, those four values are written to the destination, and destination byte `16` becomes `1`. Fallback maintenance is not performed.

6. **Fallback effects survive rejection.**  
   The destination request returns null, and the input predicate later returns nonzero. Maintenance and the three marker clears have already occurred. No direct final write to the leading record’s four words follows that predicate result.

7. **Leading-record replacement.**  
   The input predicate returns zero and the leading-record predicate returns nonzero. The leading record receives the four input words. Its marker has no explicit final write on this path.

8. **Signed bound expansion.**  
   Both predicates return zero. With leading words `(10, -5, 20, 8)` and input words `(3, 2, 25, 7)`, the final leading words are `(3, -5, 25, 8)`.

9. **Full-width signed comparisons.**  
   In the expansion path, a minimum-position input of `-2147483648` wins against `0`; a maximum-position input of `2147483647` wins against `0`. The operation does not wrap those values through unsigned comparison.

10. **Eight-bit scan wraparound.**  
    With a size result fixed at `256` and every entry operation returning zero, indices cycle from `0` through `255` and back to `0`. The destination request is never reached.
