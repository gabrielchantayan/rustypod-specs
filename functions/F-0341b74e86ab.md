# F-0341b74e86ab

## Purpose

F-0341b74e86ab selects a signed 32-bit position and coordinates interactions associated with that selection. Its observable contract consists of optional preliminary activity, a choice between count-based selection and dependency-controlled admission, and final activity for selections other than −1.

The distinguished request value, 2,147,483,647, can select the last position implied by a positive count without admission. Other requests, and the distinguished request when the observed count is not positive, require an admission decision.

The names “position,” “count,” and “admission” describe observable roles. A collection-related operation is **inferred intent**, not an established application contract. The evidence does not establish removal, movement, destruction, resource release, or count adjustment.

This document specifies normal completion and the conditions required for it. Missing dependency behavior and unresolved execution semantics remain **documented_only**.

## Interface

### Inputs and result

| Item | Contract |
|---|---|
| Receiver | A reference to storage providing the fields and indirect interfaces described below. |
| Request | A signed 32-bit integer, ranging from −2,147,483,648 through 2,147,483,647. |
| Normal result | A signed 32-bit selected position, or −1 after admission rejection. |

The original request is supplied to preliminary lookup and, when needed, admission. Count-based selection does not retroactively change either input.

Admission is a zero/nonzero decision. Every nonzero result accepts the original request; its sign and magnitude do not supply a replacement position.

The result −1 is ambiguous. It can indicate rejection, acceptance of request −1, or count-based selection that produces −1 under differing count observations. All these cases omit final activity.

## Behavior

### Selection outcomes

The selection rules are:

| Condition | Selected position |
|---|---|
| Distinguished request and a positive eligibility count observation | One less than a subsequent count observation; admission is omitted. |
| Count-based selection unavailable and admission returns nonzero | Original request, unchanged. |
| Count-based selection unavailable and admission returns zero | No accepted selection; return −1 without final activity. |

Count-based eligibility and position formation use distinct count observations. They are not an established snapshot.

With a stable positive count, the distinguished request selects a value from zero through 2,147,483,646. With differing observations, the earlier positive value does not constrain the later value. A later zero produces selection −1 without admission. A later negative value can produce a negative selection, except where decrementing it exceeds signed 32-bit range.

Ordinary requests do not require the count observation used specifically to decide distinguished-request eligibility. Admission may accept negative requests, requests equal to or above the count, and the maximum signed request. No local range restriction is established beyond the described selection rules.

### Preliminary participation and its visibility

The field at receiver offset 40 controls preliminary participation through its character-converted value, not through a direct comparison of the stored 32-bit integer with zero.

When the converted value is nonzero, F-a582717c70ab receives the receiver and original request. A null result means no preliminary callback. A non-null result provides the object used to resolve the callback at its dispatch-table offset 4.

Lookup nullness affects callback participation only. It does not reject the request, replace it, or suppress the normal selection rules.

Preliminary lookup and any callback complete before count-based eligibility or admission. Their effects can therefore change the state that selection observes. The participation field is not checked again after those interactions.

The callback’s result has no established role in selection. Its application purpose, ownership effects, implicit inputs, and failure behavior are unresolved.

### Final activity

Selection −1 suppresses every final interaction. This applies even when admission accepted the request.

For any other selected position, final activity has a fixed completion order:

1. The conditional receiver interaction, if eligible.
2. The required receiver interaction.
3. F-d6032bc0598f.
4. Return of the selected position.

The conditional interaction is eligible when the selected position’s signed successor is strictly less than the count observed for that comparison, provided the successor is representable.

Its arguments have these established contents:

| Argument role | Content |
|---|---|
| Receiver | Original receiver reference. |
| First position-related value | Selected position plus one. |
| Second position-related value | One less than a separately observed count. |
| Marker | A 32-bit value with all bits set. |
| Four remaining positions | Four-byte values whose origins and meanings are unresolved. |

The comparison count and the argument-forming count are separate observations. No dependency invocation intervenes between them, but equality of the observations is not guaranteed by the evidence.

The two position-related arguments do not establish an interval convention. Inclusive endpoints, exclusive endpoints, and start-and-length semantics remain unproven.

The four unresolved argument positions need not contain different values. Their equality, stability, initialization source, and relationship to earlier dependency activity are unknown. They must not be specified as zero or as preserved across dependencies.

The required receiver interaction receives the receiver and the all-one-bits marker regardless of whether the conditional interaction occurred. F-d6032bc0598f then receives the receiver and selected position.

Return values from these final dependencies do not replace the selected position. Their effects can nevertheless determine whether normal completion remains possible.

The marker is 4,294,967,295 when interpreted as unsigned 32-bit data and −1 when interpreted as signed 32-bit data. Its application meaning is unresolved.

### State observation and arithmetic boundaries

Admission occurs before final eligibility is evaluated. An accepting admission dependency can therefore change the count or dispatch information used by final activity without changing the selected request.

When the conditional interaction occurs, its completion precedes resolution of the required receiver interaction’s dispatch target. A valid dispatch-table replacement by the conditional dependency can affect that later target. A single cached table for both interactions is not guaranteed.

The supplied representation does not resolve the relative order of argument-related reads and dispatch-target reads within an individual indirect invocation. It also does not establish atomicity, synchronization, hardware load behavior, or permission for concurrent mutation.

Signed 32-bit boundaries matter in three places:

- Accepting request 2,147,483,647 preserves that request, but its mathematical successor is outside signed 32-bit range.
- Count-based selection cannot represent the predecessor of −2,147,483,648 if that value is observed during position formation.
- A separately observed count of −2,147,483,648 cannot supply a representable decremented argument for the conditional interaction.

For a stable count and a representable selected-position successor, a successful strict comparison ensures that the count’s predecessor is representable. Separate observations remove that guarantee for the later argument-forming read.

No wrapping, trapping, rejection, or continuation is prescribed across an unresolved arithmetic boundary.
