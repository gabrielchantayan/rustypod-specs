# F-69d7f61d702d

## Purpose

F-69d7f61d702d conditionally adds one newly obtained column name to an active collection. It enforces a configured column limit, rejects duplicate names using a table-assisted comparison, expands entry storage at eight-entry boundaries, and initializes an accepted entry.

The function returns no value. Outcomes are communicated through collection changes, diagnostic state, dependency side effects, and—in one invalid-allocation-metadata case—a nonreturning failure dependency.

The column-management interpretation is supported by the diagnostic references, comparison behavior, and entry layout. The precise application-level meaning of a column and the provenance of its name are not established.

## Interface

### Input and representation

The sole explicit input is a pointer to a writable context. The supplied representation uses 32-bit pointer-sized values and 32-bit integer fields. Relevant offsets are byte offsets:

| Object | Offset | Meaning established by use |
|---|---:|---|
| Context | `0x00` | Pointer passed to allocation and diagnostic dependencies; also used to locate the column limit |
| Context | `0x04` | Diagnostic/status field; changed from zero to one on the limit-error path |
| Context | `0x08` | Existing diagnostic handle or pointer, later replaced on the limit-error path |
| Context | `0x40` | Counter incremented on the limit-error path |
| Context | `0x180` | Pointer to the active collection |
| Object referenced by context `0x00` | `0x58` | Signed 32-bit column limit |
| Active collection | `0x04` | Signed 32-bit entry count |
| Active collection | `0x08` | Pointer to contiguous entry storage |

Each entry occupies `0x14` bytes, or 20 bytes. On insertion:

- The first four bytes receive the newly obtained name pointer.
- The byte at entry offset `0x12` receives `0x62`.
- An external dependency is first invoked on the entire 20-byte entry with an argument of 20.

The effect of that external dependency is not independently established. In particular, the remaining entry bytes cannot unconditionally be specified as zero.

### Preconditions

For ordinary, defined operation:

- The context and each field reached on the selected path must be valid for the corresponding read or write.
- A non-null active collection must contain a valid count and storage pointer.
- Existing entries examined during duplicate checking must contain readable name pointers.
- Newly obtained and existing names must expose their first byte and whatever further representation the comparison and diagnostic dependencies require.
- The lookup-table address must permit indexing by every unsigned byte value encountered.
- Storage sizing and address arithmetic must remain representable and refer to valid objects.
- A newly obtained name that is rejected must support the allocation-metadata protocol described below.

The function does not explicitly validate these conditions. Negative counts, arithmetic overflow, invalid pointers, and malformed allocator metadata are not given a general recovery path.

### Output

There is no explicit return value. A normal return can mean:

- No active collection.
- Column-limit rejection.
- No name obtained.
- Duplicate-name rejection.
- Entry-storage growth failure.
- Successful insertion.

Those outcomes are distinguishable only through state and dependency behavior, not through a returned status.

## Behavior

### 1. Active-collection gate

The function first reads the active-collection pointer at context offset `0x180`.

If that pointer is null, it returns immediately. No name acquisition, duplicate scan, storage growth, or explicit diagnostic update occurs on this path.

The active-collection pointer used subsequently is the pointer captured by this initial read. The function does not explicitly reload it from the context after dependency calls.

### 2. Column-limit check

For a non-null active collection, the function compares the configured signed 32-bit limit with the entry count plus one.

If the limit is less than that proposed count, it performs the following actions in order:

1. Increments the 32-bit context counter at `0x40`.
2. Passes the current diagnostic field at `0x08` to F-94cb53877c15.
3. Calls F-adee04f6d176 with the context’s current `0x00` value, a diagnostic-format reference concerning excessive columns, and a stack-based argument reference.
4. Stores that dependency’s returned 32-bit value at context offset `0x08`.
5. Reads the context status at `0x04`; if it is zero, writes one.
6. Returns.

The status is examined after the diagnostic dependencies have run. A nonzero value present at that time is preserved. It is not necessarily the value present on entry.

The diagnostic argument construction is not recoverable from the supplied material. The exact resulting message and substitution values are therefore unspecified.

For counts whose addition by one is representable, the boundary is exact: a proposed count equal to the limit is allowed; a proposed count greater than the limit is rejected. Behavior at signed arithmetic overflow is not established by the supplied representation.

### 3. Name acquisition

If the limit permits another entry, the function calls F-e7c4e7dd076d with no explicit arguments.

It then captures the current lookup-table pointer from global state. If the returned name pointer is null, the function returns without an explicit collection write or cleanup call.

A null result is not explicitly converted into an error by this function. Any diagnostic or global changes performed inside the acquisition dependency remain outside this function’s established contract.

### 4. Duplicate scan

The function examines existing entries in ascending index order, starting at zero.

At each iteration it reads the collection’s current count to decide whether the scan has reached the end. Thus the count is not a fixed snapshot taken before all dependency calls.

For each examined entry:

1. Its name pointer is read from the first four bytes of the corresponding 20-byte slot.
2. The first byte of each name is interpreted as an unsigned value from 0 through 255.
3. Each byte indexes the captured lookup table.
4. The resulting table bytes are compared.
5. Only if those table bytes match does the function call F-e6db2171781a, passing the new name advanced by one byte first and the existing name advanced by one byte second.
6. A zero result from that dependency identifies a duplicate.

The function itself does not inspect the rest of either name. The lookup table’s contents and the comparison dependency’s equivalence rules are unknown. Case-insensitive comparison is a plausible interpretation, not an established guarantee.

On the first duplicate:

- F-2022b0f73f3b is called with the context, a duplicate-column-name diagnostic reference, and the newly obtained name pointer.
- The new name is sent through the shared rejection-cleanup path.
- No entry is appended by this function.

No additional matching entries are examined after the first duplicate is found.

### 5. Entry-storage growth

Once the scan index reaches or exceeds the current signed count, insertion proceeds.

The function tests the low three bits of the count. If they are all zero, it requests storage through F-eb8708ae5ace, supplying:

- The context’s current `0x00` value.
- The collection’s current entry-storage pointer.
- A 32-bit size expression corresponding to `(count + 8) × 20`.

For nonnegative counts without arithmetic overflow, this requests room for eight entries beyond the current count. The visible size expression uses unsigned 32-bit arithmetic; wrapping is possible outside ordinary valid sizes and is not rejected explicitly.

If the dependency returns zero, the function performs rejection cleanup on the new name and returns. It does not explicitly overwrite the collection’s storage pointer or append an entry.

If the dependency returns nonzero, that value is stored as the collection’s entry-storage pointer.

When the count is not a multiple of eight, no growth call occurs. Sufficient existing capacity is therefore a required collection invariant, not something checked here.

The dependency’s behavior for an existing allocation, including failure preservation, movement, copying, or release, is undocumented in the supplied material.

### 6. Entry initialization and publication

The destination address is computed from the collection’s storage pointer and current count, using a stride of 20 bytes.

The function then:

1. Invokes the unmapped external initialization dependency on that destination with size 20.
2. Writes the new name pointer into the entry’s first four bytes.
3. Writes `0x62` at entry offset `0x12`.
4. Reads the collection count again, adds one, and writes the result back.
5. Returns without invoking rejection cleanup.

The count update occurs after the two explicit entry-field writes. This is an observable ordering property, not a thread-safety guarantee.

Because the initializer is an unknown dependency, it cannot be assumed to preserve globals, the collection, or unrelated memory. The final increment uses the count present after that call, rather than an independently preserved original count.

## Side effects

### Collection and diagnostic state

The function explicitly writes:

- Context counter, diagnostic, and status fields on the column-limit path.
- The collection storage pointer after successful growth.
- The destination entry’s name pointer and marker byte on insertion.
- The collection count after insertion.

Dependencies can have additional effects. An early return or rejected insertion does not establish that the entire process state is unchanged.

### Rejected-name cleanup

Duplicate rejection and storage-growth failure share a cleanup path. It includes a null-pointer guard, although the ordinary entry into either rejection case follows a non-null acquisition result.

For a non-null rejected pointer:

1. A 32-bit value four bytes before the pointer is used to derive an allocation base by subtraction from that pointer.
2. A 32-bit accounting quantity is read eight bytes before the derived base.
3. A global two-word accounting value is updated.
4. F-2fd8826557a4 is called with no explicit arguments.
5. An allocator-state pointer is then loaded from another global location.

The accounting update is ordered low word first, high word second:

- The low word at accounting-state offset `0x38` is reduced by the accounting quantity modulo \(2^{32}\).
- The high word at `0x3c` is reduced by the quantity’s signed sign-extension contribution and by the borrow from the low-word subtraction.

Accordingly, this is not unconditionally subtraction of a zero-extended unsigned 32-bit quantity from a 64-bit total.

If the derived allocation base equals the numeric address eight, cleanup stops after the accounting update, F-2fd8826557a4 call, and allocator-state global load.

Otherwise, the function reads a 32-bit header sixteen bytes before the allocation base. A zero header or a header with its least significant bit set causes a call to F-a817d8d58c10, which is represented as nonreturning. The earlier accounting changes have already occurred.

For an accepted header:

1. F-c0fc6d033caa is called with the captured allocator-state pointer.
2. A 16-bit index at allocation-base offset `-0x0c` selects a 32-bit counter beginning at allocator-state offset `0x224`.
3. The header masked with `0x3ffffffc` is subtracted from that counter and from the counter at `0x30c`.
4. A 16-bit index at allocation-base offset `-0x0a` selects a counter beginning at `0xe0`; the same quantity is subtracted there and at `0x220`.
5. F-09dcb55e8e0a is called with no explicit arguments.
6. Its returned index selects a counter beginning at `0x310`; that counter and the counter at `0x390` are each decremented by one.
7. The counter at allocator-state offset `0x08` is reduced by the masked header value read at this later point.
8. F-cc6c9b4a0f68 is called with the allocator-state pointer and the header address.
9. F-e586bff64fb7 is called with the allocator-state pointer.

These counters use 32-bit operations. Underflow is not explicitly checked.

The later header read matters: the value used at allocator-state offset `0x08` must not be assumed identical to the value used for the earlier four accounting subtractions if an intervening dependency can modify it.

### Ownership

Successful insertion retains the acquired pointer in the entry; no name copy is visible.

Rejected names enter an allocator-specific disposal sequence. This supports an intended transfer-or-dispose model, but does not establish the ownership contracts of the acquisition, diagnostic, storage-growth, or final allocator dependencies. In particular, the duplicate diagnostic dependency is not proven to leave the name untouched.

## Acceptance examples

These are conditional contract examples, not executed tests. They assume valid memory, representable ordinary counts, and dependencies that do not unexpectedly mutate the relevant collection.

1. **Inactive collection.** If context offset `0x180` is null, the function returns without acquiring a name or explicitly changing the context.

2. **Limit exceeded.** With count three and limit three, the function takes the diagnostic path before name acquisition. The context counter is incremented, the diagnostic value is replaced, and a status that is zero when checked becomes one.

3. **Exact limit permitted.** With count two and limit three, acquisition is reached. Equality between the proposed count and limit does not reject the operation.

4. **No candidate.** If acquisition returns null, no duplicate comparison, growth call, or explicit insertion occurs.

5. **First-byte mismatch.** If an existing name and candidate map to different lookup-table bytes, the suffix-comparison dependency is not called for that pair.

6. **Duplicate.** If the table bytes match and F-e6db2171781a returns zero, the duplicate diagnostic is requested, the candidate enters cleanup, and no entry is appended.

7. **Insertion without growth.** With count five, adequate existing capacity, and no duplicate, no growth dependency is called. Slot five receives the initializer call, candidate pointer, and marker `0x62`; the count becomes six.

8. **Eight-entry boundary.** With count eight and no duplicate, the requested growth size is 320 bytes. A nonzero result replaces the storage pointer before slot eight is initialized.

9. **Growth failure.** With count eight and a zero growth result, the function does not explicitly replace the storage pointer or increment the count. The candidate enters rejection cleanup.

10. **Invalid cleanup header.** If rejected-name metadata derives a base other than eight and the header is zero or odd, F-a817d8d58c10 is reached after the initial accounting update and cleanup hook. No normal return is specified.

## Uncertainties

The following remain **documented_only**:

- Exact name acquisition, encoding, termination, and comparison semantics.
- Lookup-table contents and whether matching is case-insensitive.
- Exact diagnostic text and stack-based formatting arguments.
- The entry initializer’s effects on the 20-byte region.
- Storage-growth allocation, copying, failure, and ownership guarantees.
- Global-state changes, callbacks, and memory ownership within every dependency.
- Intended behavior for negative counts, invalid capacity, overflowed addresses, or wrapped allocation sizes.
- Allocator metadata validity rules beyond the explicit header checks.
- Whether allocator dependencies implement locking, release memory, or perform additional accounting.
- Concurrency and reentrancy guarantees.

The eight-entry growth pattern, type-like marker, and allocator-style cleanup suggest implementation intent. They do not establish additional guarantees.
