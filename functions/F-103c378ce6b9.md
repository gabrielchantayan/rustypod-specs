# F-103c378ce6b9

## Purpose

F-103c378ce6b9 coordinates two dependencies using a 32-bit state field accessed through a global reference. An entry-time state value selects one of two behaviors:

- **Zero entry value:** perform an initialization write, then attempt the dependent operation repeatedly. A nonzero auxiliary status causes a read, left shift, and write before the next attempt.
- **Nonzero entry value:** reject values with more than one set bit; otherwise make one dependent attempt and return according to its auxiliary status.

The function does not establish the semantic meaning of the state, inputs, intermediate result, or auxiliary status. Describing the state as a capacity, size, alignment, or allocation unit would be inferred intent.

The function independently reads the global reference for three distinct purposes: capturing a base for later accesses, locating the entry field, and, only on the zero-entry branch, locating the initialization destination. These accesses need not identify the same object if the reference changes.

This contract is based on static evidence. No runtime tests have been performed.

- The initialization base requires a writable 32-bit field on the zero-entry branch.

### Result

The function returns a represented 32-bit value:

| Result | Condition |
|---|---|
| 0 | An attempted operation produces a zero auxiliary status. |
| 0x53 | The captured entry value is nonzero and has more than one set bit. |
| 0x54 | The captured entry value has exactly one set bit and the single attempt produces a nonzero auxiliary status. |

The zero-entry branch has no explicit failure return for repeated nonzero statuses. It may not terminate.

These return conditions assume that all required memory accesses and dependency calls complete normally.

## Behavior

### Ordered global-reference and entry accesses

Before calling either dependency, the function performs these accesses in order:

1. Read the global reference and retain that address as the captured base.
2. Independently read the global reference again.
3. Read the 32-bit field at offset 4 from the address obtained by the second reference read.
4. Select a branch using that captured entry value.

The entry classification is therefore not necessarily a classification of the field at the captured base.

If the entry value is zero, the function then independently reads the global reference a third time and writes the initial value to offset 4 from that third address. This initialization write is not necessarily directed to either the captured object or the object whose field was read for classification.

The function’s explicit global-reference reads number two on the nonzero-entry branch and three on the zero-entry branch. Attempts and retry updates do not reload that reference: they use the captured base. Dependencies may independently access or modify the global reference; their behavior is unknown.

The selected branch does not change in response to later state or reference mutations.

### Zero entry value: initialization and repeated attempts

After the independent initialization lookup and write, the function begins an attempt using the captured base, regardless of where initialization occurred.

Each attempt proceeds in this order:

1. Read the 32-bit field at offset 4 from the captured base.
2. Call F-d7be9cfb4000 with that field value first and Input C second.
3. Obtain its represented 32-bit result.
4. Call F-1e0edc6e0bc9 with Input A, Input B, that result, and literal zero, in that order.
5. Test the associated auxiliary status for zero.

A zero auxiliary status causes return of 0 without a further explicit field write.

A nonzero auxiliary status causes the function to:

- Read the field at offset 4 from the captured base again.
- Left-shift that newly read value by one position.
- Write the result back to that same field.
- Begin another attempt, including another field read.

The retry update uses a post-call field read, not necessarily the value supplied to F-d7be9cfb4000. A dependency mutation can therefore change the value being shifted. The following attempt also reloads the field rather than relying on a private progression.

No validation is applied to the initial value. Zero, multiple-set-bit patterns, and high-bit patterns are not rejected before the first attempt. If initialization targeted a different object, the first attempted value instead comes from the captured object’s field.

There is no visible attempt limit, timeout, overflow check, rollback, or return of 0x54 on this branch.

The shift is represented using a signed intermediate and a 32-bit destination. Ordinary fixed-width left shifting would discard bits beyond bit 31. However, the supplied static representation does not establish source-language behavior for negative operands or signed overflow, nor independently prove exact machine behavior in those cases. Such cases remain **documented_only**. Small positive shifts that stay within the signed range do not require resolving that uncertainty.

### Nonzero entry value: validation and one attempt

The function validates the captured entry value as an unsigned 32-bit bit pattern. A nonzero value is accepted exactly when it contains one set bit.

The predecessor used by this check is computed only for nonzero values. For the full unsigned 32-bit range, subtracting one from a nonzero value requires no underflow. The validation accepts every single-bit pattern, including 0x80000000; it does not require a positive signed interpretation.

If the value has multiple set bits, the function returns 0x53 without calling either dependency or explicitly writing a field.

For an accepted value, the function:

1. Calls F-d7be9cfb4000 with the captured entry value and Input C.
2. Calls F-1e0edc6e0bc9 with Input A, Input B, the first dependency’s result, and zero.
3. Returns 0 for a zero auxiliary status, or 0x54 for a nonzero auxiliary status.

This branch does not reload a state field to obtain the first dependency’s argument. It performs no initialization lookup, explicit field write, shift, or retry.

### Auxiliary-status boundary

The value controlling the decision after F-1e0edc6e0bc9 is represented as an auxiliary integer value available after the call. Only its zero/nonzero classification is used.

The static representation does not establish whether this is an intentional secondary return component, an ABI-specific result, or a register value requiring additional calling-convention evidence. It is not identified here as the dependency’s conventional primary return value or as a semantic error code.

## Side effects

### Direct writes

All explicit field writes occur on the zero-entry branch:

- One initialization write to the field addressed through the third global-reference read.
- One retry write to the captured-base field after each nonzero auxiliary status.

Those destinations coincide only when their base addresses coincide. The function does not reconcile differing destinations.

A successful attempt causes no further direct write. Any state mutation performed by dependencies remains visible unless another effect outside this function changes it.

The nonzero-entry branch performs no explicit field writes, including when it returns 0x53 or 0x54.

### Reference changes and state separation

The function does not explicitly write the global reference. Nevertheless, changes made elsewhere can affect its independent entry and initialization lookups.

Once the captured base has been obtained, later changes to the global reference do not retarget this function’s attempt reads or retry updates. Conversely, initialization may target a newly referenced object without initializing the captured object.

No lock, atomic snapshot, transaction, synchronization, or rollback mechanism is shown. The distinct access targets are established by the static representation; the circumstances under which the reference can change are not.

### Dependency effects, ownership, and abnormal completion

F-d7be9cfb4000 is called before F-1e0edc6e0bc9 on every attempt. Neither dependency is assumed to preserve globals, the captured object, or other accessible memory.

No direct allocation, deallocation, resource acquisition, or release is shown. Forwarding an intermediate result does not establish ownership transfer. The function also supplies no demonstrated guarantee that dependencies preserve or release resources identified by the inputs.

No explicit exception handler or fault-recovery path is present. If an access faults or a dependency does not return normally, subsequent calls, updates, and ordinary return conditions are not established by this contract.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless an example explicitly changes the reference or field, assume a stable global reference, valid storage, normally returning dependencies, no concurrent interference, and no dependency mutations.

### Invalid existing state

Given entry value 3:

- Capture a base, independently locate and read the entry field, then reject its multiple-set-bit value.
- Return 0x53.
- Make no third reference read for initialization.
- Call neither dependency and perform no explicit field write.
- Ignore the initial value.

### Valid existing state

Given entry value 8:

- Call F-d7be9cfb4000 with 8 and Input C.
- Forward its result with Input A, Input B, and zero to F-1e0edc6e0bc9.
- Return 0 for zero auxiliary status, or 0x54 otherwise.
- Do not retry or explicitly modify the field.

An entry value of 0x80000000 follows this same one-attempt path because it contains exactly one set bit.

### Initialization need not satisfy existing-state validation

Given entry value zero and initial value 3:

- Write 3 through the initialization lookup.
- With the stable-reference assumption, the first attempt reads and uses 3.
- Do not reject it for having multiple set bits.
- Return 0 if the first auxiliary status is zero.

Thus 3 can be rejected as an existing value but attempted after initialization.

### One retry

Given entry value zero, initial value 4, a first nonzero status, and a second zero status:

- Initialize the field to 4.
- Attempt using 4.
- Read 4 again, shift it to 8, and store 8.
- Attempt using a fresh read of 8.
- Return 0, leaving the field at 8 under the no-mutation assumption.

### Mutation before the retry update

Given the preceding initialization to 4, suppose a dependency changes the captured-base field to 12 before the first attempt produces nonzero status:

- The retry update reads 12 and writes 24.
- The next attempt uses 24 absent another intervening change.
- The function does not derive the retry value from the earlier argument 4.

### Three distinct reference targets

Suppose the first global-reference read identifies object Alpha, the second identifies object Beta, and the third identifies object Gamma. Assume valid storage, Beta’s entry field is zero, Alpha’s field is 8, and the initial value is 3.

Then:

- Classification uses Beta’s zero field.
- Initialization writes 3 to Gamma’s field.
- The first attempt reads Alpha’s field and uses 8, not 3 or zero.
- If the auxiliary status is nonzero and no dependency changes Alpha, the retry writes 16 to Alpha’s field.
- Subsequent attempts continue using Alpha even if the global reference later changes.

The function itself does not initialize Alpha or write Beta in this example.

### Zero initialization with persistent nonzero status

With a stable reference, entry value zero, initial value zero, and no dependency mutations:

- Every attempt reads zero.
- Every retry update leaves zero.
- If every auxiliary status is nonzero, the function continues without an explicit terminating error.

## Uncertainties

The following remain **documented_only**:

- Semantic meanings, units, valid domains, and ownership requirements of inputs and intermediate results.
- The auxiliary status’s formal calling-convention origin.
- Dependency effects on memory, globals, resources, reentrancy, and abnormal completion.
- Exact high-bit and overflow behavior of the represented signed retry shift.
- Whether and how external actors can change the global reference between its distinct reads.
- Storage alignment, address arithmetic outside valid objects, memory-mapped behavior, and access-fault handling.
- Any external invariant guaranteeing eventual zero auxiliary status.

A plausible intent is repeated doubling until a usable state is found, followed by reuse of a single-bit state. That interpretation is not required by the observed behavior and provides no termination guarantee.

The possibility of different capture, classification, and initialization targets is not merely an unspecified dependency effect: their independent reference lookups are established. What remains unknown is whether execution conditions permit those lookups to return different addresses.
