# F-a8b6994fec21

## Purpose

F-a8b6994fec21 conditionally obtains a descriptor-associated word, processes a separate working word, and writes the result of two successive transformations to a caller-supplied destination.

The observable control flow has two distinct status mechanisms:

- A selector determines whether one of two lookup dependencies is called. Selector values other than 2 or 3 cause an immediate return of 19.
- After either supported lookup, a processing dependency determines whether transformation and output occur.

A lookup failure does **not** itself become the returned status and does **not** prevent subsequent processing. However, the word used by the second transformation is explicitly initialized only when the lookup returns zero. Consequently, supported-selector paths with a nonzero lookup result have an unresolved input to that transformation if processing subsequently succeeds.

This is a source-facing contract. “Lookup,” “descriptor,” “processing,” and “transformation” describe observable roles, not established application semantics.

## Interface

### Explicit inputs

The function has four explicit arguments, in this order:

| Position | Contract role | Width and use |
|---|---|---|
| 1 | Output destination | Address at which one 32-bit word is written on the successful processing path. |
| 2 | Unused explicit argument | A 32-bit value with no explicit read or forwarding operation in this function. |
| 3 | Initial lookup working value | An integer copied into a local working slot before dependency calls. Its eventual value is used as an address when a supported lookup returns zero. |
| 4 | Initial processing working word | A 32-bit word copied into a separate local working slot before dependency calls. That slot is later passed by address to F-2202f6bea913. |

The supplied representation uses four-byte words and an integer/address model consistent with a 32-bit target. Exact machine ABI details are not supplied. In particular, the pointer width, signed-address interpretation, alignment rules, and argument-passing locations are not independently established.

### Return value

The return is an integer status:

- **19** when the selector result is neither 2 nor 3.
- **The nonzero result of F-2202f6bea913** when a supported selector is followed by a nonzero processing result.
- **0** after both transformation calls and the final output store complete.

The supported lookup’s return value is not propagated as the function’s status.

### Output and validity requirements

On the output-producing path, the first argument must designate storage suitable for a four-byte write. The function performs no explicit destination validation.

When a supported lookup returns zero, its resulting lookup working value must identify an address from which a four-byte word at byte offset 12 can be read. No null, bounds, alignment, lifetime, or object-type check appears before that read.

For supported selectors, the global-derived address used to obtain the lookup context must likewise support a four-byte read at byte offset 8.

These are requirements for the corresponding operations to complete normally, not checks enforced by the function. The behavior of invalid accesses is outside the supplied evidence.

## Behavior

### 1. Establish working state

Before calling a dependency, the function:

- Establishes an internal status of zero.
- Copies the third argument into the lookup working slot.
- Copies the fourth argument into the processing working slot.

These copies occur before the selector call. Later operations use the working slots, including dependency-written values, rather than necessarily using the original arguments.

The second explicit argument does not participate in the visible computation.

### 2. Select the lookup route

The function calls F-ccde8fa781e9 without explicit arguments.

Its returned integer selects one of three routes:

| Selector result | Action |
|---|---|
| 2 | Call F-87f3118a2e5f. |
| 3 | Call F-c439699f0cde. |
| Any other value | Set the return status to 19 and skip lookup, processing, transformation, and the explicit output store. |

For either supported selector, the function obtains the lookup context by reading a four-byte word at byte offset 8 from a global-derived base. This read occurs **after** the selector returns.

The supplied representation does not establish a separately captured, pre-selector context value. A contract must therefore not assume that selector-side changes to global state are irrelevant.

### 3. Invoke the selected lookup

Both lookup routes receive the same forms of explicit inputs:

1. The four-byte context word read from the global-derived base plus 8.
2. The address of the lookup working slot.

The selected dependency can therefore replace the lookup working value through the supplied address.

Only one lookup dependency is called. A selector result of 2 does not also call the selector-3 dependency, and vice versa.

The lookup result controls one immediate action:

- If the lookup returns **zero**, the function reads a four-byte word at byte offset 12 from the address represented by the lookup working value **after the lookup returns**. This becomes the descriptor-associated transformation input.
- If the lookup returns **nonzero**, that read is skipped.

There is no explicit check that the lookup working value changed. A zero-returning lookup that leaves it unchanged causes the offset-12 read to use the value originally supplied as the third argument.

The lookup result does not change the internal status from zero. Thus, a nonzero lookup result still leads to the processing step.

### 4. Process the separate working word

For either supported selector, the function calls F-2202f6bea913 with the address of the processing working slot.

The slot was initialized from the fourth argument. Its contents at this point are not guaranteed to remain equal to that argument: earlier dependencies execute before this call, and their complete effects are unknown.

F-2202f6bea913’s return value becomes the function’s status:

- A **nonzero** result ends the function without either transformation call or the explicit output store.
- A **zero** result permits transformation and output.

When the selected lookup returned zero, the descriptor-associated word was already read before this processing call. Therefore, the function does not defer that read until it knows processing will succeed.

### 5. Transform and publish

After processing returns zero, the function makes two calls to F-d7be9cfb4000 in a fixed order:

1. The first call receives the 32-bit value **4096** as its first argument and the current processing working word as its second argument.
2. The second call receives the descriptor-associated word as its first argument and the first call’s returned 32-bit word as its second argument.

The second call’s returned word is then written to the destination supplied in the first explicit argument. The function returns zero.

There is no explicit interpretation of either transformation result as an error. A zero-valued result, for example, is still written if that is what the second call returns.

The evidence does not establish whether F-d7be9cfb4000 combines flags, constructs an encoding, performs arithmetic, or implements some other operation. The constant 4096 must not be assigned a more specific meaning without additional evidence.

### 6. Unresolved transformation input after lookup failure

The function explicitly assigns the descriptor-associated word only on a zero lookup result. Nevertheless, a nonzero lookup result can be followed by successful processing and both transformation calls.

On that path, the second transformation’s first input is not established by the explicit arguments and assignments shown. The supplied representation indicates a carried machine-state value rather than a value initialized by this function.

Accordingly:

- Do not substitute zero.
- Do not reuse the third or fourth argument by assumption.
- Do not treat the lookup error as an automatic early return.
- Do not claim a deterministic final output from the four explicit arguments alone.

The origin and stability of this carried value are **documented_only**.

## Side effects

### Explicit memory operations

The function’s visible memory operations include:

- Initialization of two local working slots.
- For a supported selector, a four-byte context read at global-derived base plus 8.
- For a zero lookup result, a four-byte read at the resulting lookup address plus 12.
- For a zero processing result, one four-byte output write after both transformation calls.

The byte offsets are literal byte offsets. No aggregate layout beyond these accessed words is established.

The context read precedes the selected lookup. The descriptor-associated read, when present, follows the lookup and precedes processing. The output write follows both transformations.

### Dependency effects and aliasing

Dependencies may have additional effects not visible here. Their implementation contracts are unavailable. In particular, this contract does not assume that they:

- Preserve globals.
- Avoid modifying externally reachable memory.
- Preserve storage that aliases the output destination.
- Allocate, retain, transfer, or release memory.
- Return normally for every input.

Thus, “no explicit output store” does not prove that the destination’s contents remain unchanged across the call. A dependency could affect the same storage through an alias or global reference.

Likewise, the final explicit store occurs after all dependency calls on the successful path. If the output destination aliases previously read storage, the store can overwrite that storage only after the function has obtained the values used for transformation.

### Ownership and lifetime

No allocation, deallocation, or ownership-transfer operation is explicitly visible in this function.

Both working-slot addresses passed to dependencies refer to local state. They are valid for their immediate calls. The supplied evidence does not establish whether a dependency retains either address or whether retention is permitted by a wider contract. No continued lifetime after this function returns should be promised.

The two working slots are distinct local values in the supplied representation. A public contiguous-record layout for those slots is not established.

## Acceptance examples

These are conditional acceptance cases derived from static evidence. They are not executed tests.

### Unsupported selector

Given that F-ccde8fa781e9 returns 4 and returns normally:

- The function returns 19.
- Neither lookup dependency is called.
- The context read at offset 8 is skipped.
- Processing and transformation calls are skipped.
- The function performs no explicit output store.

The same branch applies to every selector result other than 2 and 3.

### Selector 2, successful lookup and processing

Assume:

- The selector returns 2.
- The context read produces word **C**.
- F-87f3118a2e5f receives **C**, changes the lookup working value to valid address **A**, and returns zero.
- The four-byte word at **A + 12** is **D**.
- F-2202f6bea913 returns zero and leaves processing word **W**.

Then:

- F-c439699f0cde is not called.
- **D** is read before processing.
- The first transformation receives 4096 and **W**.
- The second receives **D** and the first transformation’s result.
- The second transformation’s returned word is written to the destination.
- The function returns zero, assuming all operations complete normally.

### Selector 3 with processing failure

Assume the selector returns 3, its selected lookup returns zero, the offset-12 read succeeds, and processing returns 7.

Then:

- F-c439699f0cde is the selected lookup.
- The descriptor-associated read occurs even though processing later fails.
- Neither transformation is called.
- No explicit output store occurs.
- The function returns 7.

### Lookup failure followed by processing failure

Assume a supported selector, a nonzero lookup result, and processing result 9.

Then:

- The offset-12 descriptor read is skipped.
- Processing still occurs.
- No transformation or explicit output store occurs.
- The function returns 9, not the lookup result.

### Lookup failure followed by processing success

Assume a supported selector, a nonzero lookup result, and processing result zero.

The visible flow reaches both transformations and the output store if execution completes normally. However, the first argument to the second transformation is unresolved. An acceptance case must not assert an exact stored word without independently establishing that carried input.

### Lookup leaves the working address unchanged

Assume the selected lookup returns zero without modifying its working slot.

The offset-12 read uses the address value initially supplied as the third argument. Successful completion therefore requires that address plus 12 to support the four-byte read; returning zero alone does not establish validity.
