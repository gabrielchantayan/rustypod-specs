# F-99ddbb167733

## Purpose

F-99ddbb167733 performs a bounded, ordered lookup of an integer key in a table and returns a pointer.

The search examines at most 3,920 records, starting with the first record. The first record whose key equals the input determines the result. If no record matches, the function returns the address of a separate fallback object.

This is a lookup contract, not an allocation or validation contract. The function does not establish that a returned pointer is non-null, readable, writable, uniquely owned, or associated with a particular object type.

The behavior below is established from the supplied static representation unless explicitly marked as inferred or unknown. No runtime tests have been performed.

## Interface

### Input

The function accepts one integer search key.

The supplied representation uses an `int` for this input and for each table key. The intended interpretation is a 32-bit integer comparison. The representation does not independently establish the machine ABI or integer data model; the 32-bit interpretation is therefore conditional on the represented target using 32-bit integers.

There is no distinguished input value in the visible behavior. Zero, negative values, and positive values all follow the same search procedure. No range check, normalization, masking, or conversion is visible before comparison.

### Output

The function returns a pointer with no exposed pointee structure.

There are two result cases:

- **Match:** the pointer value stored in the pointer field of the first matching record.
- **No match:** the address of a separate fallback object.

A matching pointer is returned as stored. In particular, a null pointer in a matching record is not replaced by the fallback address. The function does not dereference the returned pointer.

The fallback result is an object address, not a pointer value loaded from that object. Its contents and intended interpretation are not established.

### Implicit inputs and layout

The function depends on an externally held table base. Records have an eight-byte stride:

| Record-relative offset | Meaning |
|---|---|
| 0 | Stored result pointer |
| 4 | Integer comparison key |

The search covers record indices 0 through 3,919 inclusive. There is no visible length field, sentinel key, terminator pointer, or caller-supplied record count.

A layout with a four-byte pointer followed by a four-byte integer is consistent with these offsets and the stride. That conventional 32-bit layout is inferred rather than independently established by an ABI declaration. The supplied representation does not state the width of a pointer load.

### Preconditions

For defined, successful execution, every table access actually reached must be valid under the target’s memory and alignment rules:

- Each examined record must have a readable key field.
- A matching record must have a readable pointer field.
- Address calculations must designate the intended records without invalid address overflow.
- The external table base must support the accesses made through it.

A full unsuccessful search requires readable key fields across all 3,920 records. An early successful search does not require this function to inspect later records.

These preconditions are not checked by the function.

## Behavior

### Ordered search

The function begins with record index zero. It reads that record’s key and compares it with the input.

If the keys differ, it advances to the next record. This continues in ascending record order until either a match is found or the final permitted record has been examined.

The record count is exactly 3,920, corresponding to the bound `0xF50`. The bound is a count, not a maximum valid index. Consequently:

- The first examined record is index 0.
- The last possible examined record is index 3,919.
- Index 3,920 is never examined.
- At least one key comparison is attempted on every invocation that reaches the lookup normally.

There is no empty-table case in the visible interface.

### Successful lookup

When a key matches, the function reads the pointer field associated with that record and returns that pointer value immediately.

This establishes first-match precedence. If multiple records contain the same key, only the earliest matching record determines the result. A later match does not override an earlier one, even if the earlier pointer is null.

For a first match at index \(k\), under a stable and valid table configuration:

- Keys at indices 0 through \(k\) are examined in ascending order.
- The pointer field at index \(k\) is read after its key has matched.
- Pointer fields of preceding nonmatching records are not read by the visible function.
- Records after index \(k\) are not examined.

The function returns the pointer value, not the address of the record’s pointer field and not the address of the record itself.

### Unsuccessful lookup

If every examined key differs from the input, the function returns the fallback object’s address after examining the key at index 3,919.

On this path, the visible function does not read any record’s pointer field. It also does not read the fallback object’s contents to obtain its result.

The fallback address is not established as a unique failure discriminator. A matching record could contain that same address. The return value alone therefore need not distinguish a successful lookup from an unsuccessful one.

### Arithmetic and boundaries

The index advances by one per unsuccessful comparison. Its visible values remain between zero and 3,920, including the terminal value used to end the search.

Record addresses use an eight-byte stride. The largest offsets relative to the selected table base are:

| Access | Largest starting offset |
|---|---:|
| Record pointer field | 31,352 bytes |
| Record key field | 31,356 bytes |

With four-byte integer keys, the final key occupies byte offsets 31,356 through 31,359. A contiguous table using the conventional four-byte-pointer layout therefore spans 31,360 bytes.

These offsets do not threaten overflow in a 32-bit unsigned index calculation. They do not establish that adding those offsets to an arbitrary table base is safe.
