# F-2f1a529549b6

## Purpose

F-2f1a529549b6 performs an in-place pointer rearrangement consistent with a left rotation in a parent-linked binary tree. The second argument identifies the pivot node. The pivot’s right child is promoted, the promoted node’s left subtree becomes the pivot’s right subtree, and the pivot becomes the promoted node’s left child. A root reference or a parent’s child reference is updated to retain the subtree’s connection to the surrounding structure.

The tree interpretation is inferred from the field relationships. The established behavior is a sequence of four-byte memory reads and writes. The function does not verify that the supplied objects form a tree, that parent and child references agree, or that required addresses are valid.

No runtime tests have been performed.

## Interface

### Arguments and result

The function accepts two address-bearing arguments:

- **Container:** identifies an object containing a reference at byte offset 16 to a separate root-reference holder.
- **Pivot:** identifies the node whose right-side connection is rearranged.

The supplied representation uses 32-bit integer and pointer-sized quantities. Structural references occupy four bytes. The arguments are used as addresses rather than as numeric values for comparisons or ordering.

The function has no specified return value and no explicit success or failure result.

### Preconditions

For ordinary tree-rotation behavior:

- The pivot and its right child must identify valid, suitably aligned node storage.
- The container’s field at offset 16 must identify a valid root-reference holder.
- All fields read must be accessible; all fields written must be writable.
- A nonzero middle-subtree reference must identify storage with a writable parent field.
- If the pivot is not the recorded root, its parent reference must identify storage with accessible child fields.
- Parent, child, and root references must be mutually consistent.
- No concurrent actor may modify the participating structure during the operation.

These conditions are not checked. A null pivot, missing right child, or missing root-reference holder is not treated as an empty case.

## Behavior

### Successful effect on a consistent tree

For a valid tree with a pivot that has a right child, the function changes the local topology as follows:

| Relationship | Before | After |
|---|---|---|
| Pivot’s right child | Promoted node | Middle subtree |
| Middle subtree’s parent, if nonzero | Promoted node | Pivot |
| Promoted node’s parent | Pivot | Pivot’s former parent |
| Surrounding root or parent connection | Pivot | Promoted node |
| Promoted node’s left child | Middle subtree | Pivot |
| Pivot’s parent | Former parent | Promoted node |

The pivot’s left-child field and the promoted node’s right-child field are not explicit write targets.

The function does not read node keys or payloads. It performs no ordering comparisons, balance calculations, color changes, height updates, or count updates. Preservation of a search-tree ordering is conditional on the input already satisfying the appropriate ordering invariant.

### Observable access ordering

The operation is not atomic. Its ordering matters for invalid inputs, overlapping objects, and observation during execution.

**The middle subtree is transferred first.** The function obtains the promoted-node reference from the pivot’s right-child field. It reads the promoted node’s left-child field and writes that value into the pivot’s right-child field.

It subsequently reads the promoted node’s left-child field again to decide whether a parent update is needed. If that read is nonzero, the field is read again to obtain the address whose parent field will be written. The parent value written there is the pivot reference.

Thus, the source does not establish a single retained middle-subtree value shared by the assignment, the condition, and the write destination. With stable, nonoverlapping storage these reads agree. With interference or aliasing, they need not.

**The promoted node receives a parent reference before the external connection changes.** The pivot’s parent field is read and copied to the promoted node’s parent field. This happens after the middle-subtree transfer and its conditional parent repair.

**The surrounding structure is reconnected next.** The root-reference holder is obtained through the container’s field at offset 16. Its root field is compared with the pivot reference:

- If equal, that root field is replaced with the promoted-node reference.
- Otherwise, the pivot’s parent field is read again. If that parent’s left-child field equals the pivot reference, the left-child field is replaced with the promoted-node reference.
- If the left-child comparison fails, the parent’s right-child field is replaced with the promoted-node reference without checking its existing value.

The non-root path therefore depends on the pivot’s parent field at that later point, not on a separately retained copy of its original value.

**The pivot is attached last.** The promoted node’s left-child field is set to the pivot reference. The final explicit write sets the pivot’s parent field to the promoted-node reference.

Consequently, the surrounding root or parent connection has already changed before the pivot’s final parent update.

### Root selection and inconsistent relationships

Root status is determined solely by comparing the root-reference holder’s root field with the pivot reference. The pivot’s parent field is not used to decide whether the pivot is the root.

On the root path, the pivot’s parent value is still copied to the promoted node. The function does not normalize that value to zero or to a sentinel.

On the non-root path, only the parent’s left-child field is checked for equality with the pivot. Failure of that comparison selects the right-child field unconditionally. If neither child field names the pivot, the function still overwrites the right-child field. It does not report or repair that inconsistency.

A failure during a later access can follow earlier structural writes. In particular, the pivot’s right-child field is changed before the root-reference holder is accessed. The function therefore provides no all-or-nothing failure guarantee.

The exact runtime consequence of an invalid access is not established by the supplied source.

## Side effects

The function mutates existing storage reachable through its arguments. Its explicit write targets are:

- The pivot’s right-child field.
- The middle subtree’s parent field, conditionally.
- The promoted node’s parent field.
- Either the root-reference holder’s root field or one child field of the pivot’s parent.
- The promoted node’s left-child field.
- The pivot’s parent field.

With distinct, stable objects, the zero-middle-subtree path performs five four-byte writes; the nonzero-middle-subtree path performs six.

There is no explicit allocation, release, ownership transfer, payload copy, logging, I/O, or synchronization. The operation changes structural reachability, but that does not establish any memory-ownership policy.

No other fields are explicit write targets. However, if objects overlap, a write through one role can also change storage serving another role. The ordinary tree postconditions are therefore conditional on suitable non-aliasing relationships.

Intermediate states can contain temporarily inconsistent parent and child links. The source provides no basis for concurrent-reader safety, lock-free use, or a memory-ordering guarantee.

## Acceptance examples

These are conditional contract examples derived from static evidence, not executed tests. Unless stated otherwise, assume valid, stable, distinct objects and consistent parent links.

### Root rotation with a nonempty middle subtree

Initially:

- The recorded root is the pivot.
- The pivot’s right child is the promoted node.
- The promoted node’s left child is a nonzero middle subtree.
- The pivot’s parent field contains the tree’s root-parent convention.

After normal completion:

- The recorded root is the promoted node.
- The promoted node’s parent contains the pivot’s former parent value.
- The promoted node’s left child is the pivot.
- The pivot’s parent is the promoted node.
- The pivot’s right child is the middle subtree.
- The middle subtree’s parent is the pivot.

The pivot’s left child and the promoted node’s right child remain unchanged.

### Non-root rotation where the pivot is a left child

If the recorded root differs from the pivot and the pivot’s parent names the pivot in its left-child field, that field is replaced with the promoted node. The recorded root remains unchanged. The other local relationships change as described above.

### Non-root rotation where the pivot is a right child

If the recorded root differs from the pivot and the parent’s left-child field does not name the pivot, the parent’s right-child field is replaced with the promoted node.

For a consistent tree in which the pivot was that right child, this reconnects the rotated subtree correctly.

### Empty middle subtree

If the promoted node’s left-child field remains zero throughout the relevant reads:

- The pivot’s right-child field becomes zero.
- No middle-subtree parent write occurs.
- The root-or-parent reconnection and final pivot attachment still occur.

This does not permit the pivot’s right child itself to be zero; the promoted node is dereferenced before any such check.

### Inconsistent non-root parent relationship

If the pivot is not the recorded root, but its parent names some other node in both child fields, the function overwrites that parent’s right-child field with the promoted-node reference. There is no explicit error indication.

Acceptance of that observable write does not imply that the resulting structure is a valid tree.

### Missing promoted node

If the pivot’s right-child reference is zero, the function attempts to read a field through that value. There is no established successful no-op behavior. The resulting runtime outcome is documented only.
