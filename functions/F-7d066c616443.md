# F-7d066c616443

## Purpose

F-7d066c616443 multiplies an unsigned, multiple-limb value by a single unsigned 32-bit factor, modifying the limb storage in place. Limbs are processed from least significant to most significant. A nonzero carry remaining after the original limbs have been processed is written as one additional limb.

The routine also writes a 16-bit limb count in the supplied descriptor. It does not remove leading zero limbs, allocate storage, check capacity, or report arithmetic or memory errors.

**Established static behavior:** the operation is a sequence of unsigned limb multiplications and carry propagation, followed by a count-field write.

**Inferred intent:** the descriptor represents a variable-length, nonnegative integer in radix \(2^{32}\), with preallocated room for possible growth.

**Important boundary:** when the original count is 65,535 and a final carry is nonzero, the routine writes the additional limb but stores zero in the 16-bit count field. It does not reject or saturate this overflow.

## Interface

### Inputs

The routine takes two arguments:

1. **Factor:** an unsigned 32-bit integer, ranging from 0 through \(2^{32}-1\).
2. **Descriptor address:** an address used to access both a 16-bit count and a stored pointer to limb storage.

The routine returns no value. Results are observable through memory writes.

### Limb layout

Each limb is an unsigned 32-bit quantity. Consecutive limbs occupy consecutive 32-bit elements, with a stride of four bytes.

For an original count \(n\), the intended mathematical interpretation is:

\[
A=\sum_{i=0}^{n-1} a_i\,2^{32i}
\]

where \(a_0\) is stored at the address obtained from the descriptor. This establishes **limb significance order**, not the byte order within each limb.

No requirement that the highest active limb be nonzero is checked.

### Storage preconditions

For ordinary nonoverlapping use:

- The descriptor must support reading its count and pointer fields and writing its count field.
- If the original count is positive, the limb pointer must address that many readable and writable 32-bit elements.
- If multiplication produces a final carry, one additional writable 32-bit element must exist immediately after the original active limbs.
- To guarantee representable count growth, either the original count must be below 65,535 or the caller must ensure that no final carry occurs.

The routine contains no capacity argument or capacity check. Providing an extra limb of storage prevents an out-of-bounds carry write but does not prevent 16-bit count wraparound.

## Behavior

### Initial reads

The routine first reads and retains the descriptor’s unsigned 16-bit count. It then reads and retains the limb pointer from descriptor offset 4.

The count is not subsequently reread to control processing. The stored pointer field is also not reread.

These reads occur even when the original count is zero. A zero count therefore does not exempt the descriptor’s pointer field from being readable.

### Limb processing

The carry initially equals zero. The routine processes exactly the number of limbs specified by the original count, in increasing address order.

For each limb, the observable sequence is:

1. Read that limb’s current 32-bit value.
2. Form the unsigned product of that value and the factor, then add the incoming carry.
3. Write the low 32 bits of that result back to the same limb.
4. Retain the high 32 bits as the carry for the next limb.

Using \(B=2^{32}\), the arithmetic relationship for each position is:

\[
t_i=a_i m+c_i,\qquad
r_i=t_i\bmod B,\qquad
c_{i+1}=\left\lfloor t_i/B\right\rfloor
\]

Here \(m\) is the factor, \(c_0=0\), and \(r_i\) is the value written to the current limb.

The product and addition use 64-bit unsigned arithmetic semantics. Even allowing any unsigned 32-bit incoming carry, the maximum sum is:

\[
(B-1)^2+(B-1)=B^2-B
\]

This fits in 64 unsigned bits. The extraction of the upper half is a logical, unsigned extraction; values with bit 63 set do not produce a sign-extended carry.

The loop index is 16 bits wide. For the largest possible original count, the processed indices are 0 through 65,534. The next index value is 65,535, which fails the continuation condition. Thus the processing loop itself does not wrap around or become infinite at the maximum count.

### Final carry and count update

After all original limbs have been processed:

- **Zero final carry:** no additional limb is written. The original count is written back to the descriptor.
- **Nonzero final carry:** the carry is written into the next limb position, immediately after the original active range. Only then is the descriptor count written as the original count plus one, reduced to 16 bits.

The final count write occurs on both branches, including when its stored value is unchanged.

For nonoverlapping valid storage, the resulting active limbs represent the exact mathematical product whenever the resulting limb count is representable. The count need not be minimal because the routine does not normalize leading zeros.

### Zero count

With an original count of zero:

- The descriptor count and pointer field are read.
- No limb is read or written.
- No carry limb is appended.
- Zero is written to the descriptor count.

The factor does not alter this behavior. The extracted limb pointer is not dereferenced on this path, although the validity of its stored representation remains a platform-level matter.

### Zero and unit factors

A zero factor does not trigger an early return. With positive count, every original limb is read and then overwritten with zero. The original count is retained, so a nonempty representation becomes an equally long all-zero representation.

A factor of one likewise does not skip processing. Each original limb is read and written, the final carry remains zero, and the original count is retained.

### Aliasing

No overlap check appears in the routine.

The ordinary integer interpretation assumes that limb writes do not overwrite descriptor fields or otherwise violate the platform’s memory-access rules. If overlap is permitted by the execution environment, the operation order still matters:

- The original count and initial limb pointer have already been retained before any limb write.
- Overwriting a descriptor field during limb processing does not cause either field to be reread.
- Each limb’s input comes from memory when that limb is reached.
- The final count write occurs after every limb write, including an appended carry write.

Consequently, overlapping storage can make descriptor writes alter limb data or limb writes alter descriptor data. Such arrangements are not established as supported integer representations.

## Side effects

The explicit writes are limited to:

- One 32-bit write for each original active limb.
- One additional 32-bit write if and only if the final carry is nonzero.
- One final 16-bit write to the descriptor count.

The routine does not explicitly update the descriptor’s pointer field. An overlapping limb region could nevertheless overwrite that field.

There are no explicit allocations, releases, external calls, logging operations, or global-state accesses in the supplied body. The routine uses caller-supplied storage throughout. No ownership transfer is expressed.

There is no error return or explicit recovery path. Invalid addresses, unsuitable alignment, insufficient writable capacity, and unsupported memory overlap are not detected. Their consequences depend on the execution environment; this contract does not assign a particular fault, exception, or partial-result guarantee.

The operation is not transactional. Limb writes precede the final count update. If execution stops during processing, memory can contain a partially transformed value while the count field has not yet received its final write.

No synchronization or atomicity guarantee is established.

## Acceptance examples

These are conditional acceptance examples derived from static evidence, not results of runtime tests. Unless stated otherwise, assume valid, nonoverlapping storage and sufficient writable capacity. Limb lists are ordered from least significant to most significant.

### Empty representation

Given count 0, an accessible descriptor pointer field, and any factor:

- The result count is 0.
- No limb storage is accessed.
- The descriptor count is still written.

### Product without growth

Given count 2, limbs \([3,4]\), and factor 2:

- The original limb locations become \([6,8]\).
- The count remains 2.
- No third limb is written.

### Carry propagation within the existing range

Given count 2, limbs \([\text{0xFFFFFFFF},0]\), and factor 2:

- The first limb becomes `0xFFFFFFFE`.
- Its carry contributes one to the second limb.
- The second limb becomes 1.
- The final carry is zero, so the count remains 2.

The result is \([\text{0xFFFFFFFE},1]\).

### Appended carry

Given count 1, limb \([\text{0xFFFFFFFF}]\), factor 2, and room for another limb:

- The original limb becomes `0xFFFFFFFE`.
- The next limb receives 1.
- The count becomes 2 after the appended limb is written.

### Maximum-width factor and limb

Given count 1, limb \([\text{0xFFFFFFFF}]\), factor `0xFFFFFFFF`, and room for growth:

- The original limb becomes 1.
- The appended limb becomes `0xFFFFFFFE`.
- The count becomes 2.

This follows from:

\[
(2^{32}-1)^2=\text{0xFFFFFFFE00000001}
\]

### Zero multiplication preserves length

Given count 3, limbs \([7,0,9]\), and factor 0:

- All three limbs become zero.
- The count remains 3.
- No extra limb is written.

Reducing the count to zero would not match the established behavior.

### No normalization

Given count 3, limbs \([5,0,0]\), and factor 1:

- The limb values remain \([5,0,0]\), with each position written.
- The count remains 3.

### Maximum-count wraparound

Given count 65,535, factor 2, and valid storage containing zero in every original limb except `0x80000000` in the highest position:

- The highest original limb becomes zero.
- A carry of 1 is written at limb index 65,535.
- The descriptor count becomes 0 because 65,536 is reduced to 16 bits.

This is count overflow, not normalization or a reported error.
