# F-e075c68987d5

## Purpose

F-e075c68987d5 conditionally scans a bounded sequence of entries associated with a caller-supplied context. It first checks a leading value against a caller-supplied discriminator. If that value matches, it consumes additional header information, derives an entry count from the low 16 bits of another dependency result, and searches for an entry whose identifying value is exactly 2.

For a matching entry, the function obtains two additional values. If both operations report zero status, it stores the first value in the caller’s output location and returns zero. The second value is consumed but not exposed by this function.

The established behavior is a sequence of dependency calls, status checks, one context-field read on each nonmatching entry, and a conditional output write. Describing this as a record parser or lookup operation is inferred intent, not an established format definition.

### Result

The function returns:

- **Zero** after explicitly writing a successful result to the output location.
- **A nonzero status value** when one of the explicitly checked early operations or entry-identifier operations reports that status.
- **2** when the discriminator does not match, the entry count is zero, or the loop finishes without a successful result.

These result classes overlap numerically. A dependency-reported status of 2 is indistinguishable from the function’s own fallback result of 2.

### Storage and validity requirements

For the success path, the output location must permit a 32-bit write. The function does not validate that pointer before writing.

For a nonmatching entry, the context must permit a 32-bit read at byte offset 8. The dependencies may impose additional context requirements that are not visible here.

The local status object is a 32-bit integer. Its address is passed to F-10d2ce969adf and F-8f49ed59b67e. Whether these dependencies always initialize that object, retain its address, or have additional aliasing behavior is not established.

The function itself performs no visible allocation or release. No ownership transfer for the context or output storage is established.

## Behavior

### Leading discriminator check

The function initializes its local status to the expected discriminator, then calls F-10d2ce969adf with the context and the address of that status.

The status is checked before the returned value is compared with the expected discriminator:

- A nonzero status is returned immediately.
- With zero status, a returned value unequal to the expected discriminator causes the function to return 2.
- Only equality with zero status enters header processing.

Initializing status from the expected discriminator is observable to the dependency receiving its address. It is not equivalent to initializing status to zero. In particular, a dependency that leaves the status untouched can cause an immediate nonzero return when the expected discriminator is nonzero.

The discriminator comparison uses the full 32-bit values. There is no visible masking to a smaller width.

### Header processing

After a successful discriminator match, the function performs these operations in order:

1. It calls F-10d2ce969adf again with the same context and status address. The returned value is discarded. A nonzero status is returned immediately.
2. It calls F-d8528f8db63b with the context and the numeric argument 16. That dependency’s return value replaces the local status. A nonzero result is returned immediately.
3. It calls F-8f49ed59b67e with the context and status address. A nonzero status is returned immediately. Otherwise, the low 16 bits of the returned 32-bit value become the entry count.

The meaning of the numeric argument 16 is not established. It must not be specified as a byte skip, absolute position, alignment, or record size without dependency evidence.

The high 16 bits of the count-producing result do not affect this function’s loop bound. Thus the effective entry count ranges from 0 through 65,535.

If that count is zero, the function returns 2 without entering the loop.

### Entry processing

The function attempts at most the effective entry count’s number of iterations. The loop index starts at zero and increases by one after every unsuccessful iteration. Since the count is at most 65,535, the visible loop-index increment does not approach the maximum signed 32-bit value.

Each iteration begins by calling F-10d2ce969adf with the context and status address to obtain an entry identifier.

If this operation leaves a nonzero status, the function immediately returns that status. The returned identifier is not used in that case.

With zero status, the identifier determines one of two paths.

### Identifier equal to 2

For an identifier exactly equal to 2, the function calls F-10d2ce969adf to obtain a candidate output value.

If this operation leaves a nonzero status:

- The second value operation for that entry is not called.
- The output location is not explicitly written.
- The function does not immediately return that status.
- Processing advances to the next loop iteration, if one remains.

If the candidate operation leaves zero status, the function calls F-10d2ce969adf once more. This second returned value is discarded.

If that second operation also leaves zero status, the function:

1. Writes the saved candidate value to the output location as a 32-bit value.
2. Returns zero immediately.

If the second operation leaves a nonzero status, the function does not write the candidate and does not immediately return the error. It advances to the next iteration, if any.

Consequently, an identifier of 2 does not guarantee that the function stops searching. A later matching entry can provide the successful result after an earlier matching entry’s value operation reports an error.

The status storage is not explicitly reset before the next iteration. After a matching-entry value error, the next identifier operation receives the address of storage still containing that error. Whether the operation clears or replaces it is dependency-defined.

### Identifier not equal to 2

For any other identifier with zero status, the function:

1. Reads a 32-bit integer from the context at byte offset 8.
2. Forms a second argument by adding 8 to that value.
3. Calls F-e40a3ceddab2 with the context and that computed argument.
4. Discards the dependency’s return value and advances to the next iteration.

The context-field read occurs after the identifier operation and its status check. It is not a value cached before the scan. Each execution of this path obtains the field anew.

No explicit status argument is supplied to F-e40a3ceddab2, and no explicit check follows the call. This does not prove that the call succeeds, preserves the context, or has no global effects.

The addition is shown as signed 32-bit integer arithmetic. Behavior when adding 8 exceeds that type’s representable range is not established by the supplied evidence. This contract does not choose wrapping arithmetic or a defined overflow failure.

### Exhaustion

If no iteration reaches the successful output write, the function returns 2 after the loop.

This includes exhaustion immediately after a matching-entry value operation reports a nonzero status. Such a status is not automatically returned: at the loop boundary, the fallback return is 2.

## Side effects

### Direct effects

The visible direct effects are:

- Initialization and subsequent updates of local status storage.
- Passing that storage’s address to two dependencies.
- A 32-bit context-field read on each nonmatching-entry path.
- One explicit 32-bit output write on success.

There is no direct output write on a discriminator mismatch, checked error return, zero count, unsuccessful matching-entry attempt, or loop exhaustion.

That guarantee concerns this function’s explicit write. It does not establish that the output storage remains unchanged if it aliases context storage or memory modified by a dependency.

### Ordering

On the success path, the output write occurs only after the candidate operation and the subsequent discarded-value operation have both left zero status. The candidate is saved across the second operation; the second returned value does not replace it.

No further dependency call occurs after the explicit output write.

For a nonmatching entry, the context-field read and F-e40a3ceddab2 call occur before the next entry-identifier operation.

No rollback is visible. If an earlier operation advances a stream, mutates the context, or changes external state, returning an error or 2 does not visibly undo it.

### Ownership and shared state

The function does not visibly acquire ownership of any supplied storage or dependency result. It does not visibly free or close anything.

The dependencies’ effects on global state, backing storage, resource lifetimes, and context position are unknown. The function provides no visible synchronization. Reentrancy and thread safety are therefore not established.
