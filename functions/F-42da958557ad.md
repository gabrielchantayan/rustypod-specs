# F-42da958557ad

## Purpose

F-42da958557ad selects a 32-bit result using a pointer-shaped input token, a stored comparison key, and six stored result values.

The function is not an unconditional lookup over six fixed tokens. It first gives the stored comparison key priority. If the input does not equal that key, a signed comparison determines which subset of fixed tokens is eligible for recognition. An unmatched or ineligible token produces zero.

The visible body does not dereference the input, allocate memory, write state, or call another function. Its apparent purpose is a small, state-dependent token-to-value mapping. The application meaning of the tokens and returned values is unknown.

## Interface

### Input

The function accepts one pointer-shaped value whose declared pointee is one byte wide.

The input is used only for:

- Equality comparison with a stored key.
- Conversion to a signed integer for an ordering comparison.
- Equality comparison with five fixed address-shaped tokens.

No input byte is read. The visible body therefore imposes no requirement that the input identify readable storage. This is a statement about the operations shown, not a guarantee that every fabricated pointer representation is valid under an unspecified calling environment.

A null input is not rejected specially. It participates in the same comparisons as any other input.

### Output

The function returns one 32-bit value:

- The stored primary result when the input equals the stored key.
- One of five stored token results when the input satisfies both a branch condition and the corresponding fixed-token equality.
- Zero otherwise.

The returned bits are not visibly interpreted as a pointer, status, signed quantity, or ownership-bearing handle. Zero is not an unambiguous failure indicator: a selected stored result may itself contain zero.

## Behavior

### Primary-key priority

The first decision compares the input with the comparison key for equality.

If they are equal, the function reads and returns the primary result immediately. Neither signed ordering nor any fixed-token match affects that result.

This priority also applies when the comparison key has the same value as one of the five fixed tokens. For example, equality with a key of `0xC422` selects the primary result, not the result associated with the fixed token `0xC422`.

### Branch selection after an equality miss

If the initial equality comparison fails, the function compares the comparison key and the input after converting both to a signed integer type.

The relevant relation is:

- **Greater-than branch:** the signed interpretation of the input is greater than the signed interpretation of the key.
- **Lower-or-equal branch:** that strict relation is false.

This is not an unsigned address-order comparison. An implementation must not silently replace it with unsigned numeric ordering.

The supplied representation uses an explicit signed integer conversion, but does not independently establish the execution environment’s integer width or pointer-to-integer conversion rules. A 32-bit signed interpretation is consistent with the represented environment; exact conversion behavior remains an environmental prerequisite rather than a fully proven portable property.

If the comparison key remains stable and the relevant conversions preserve distinct values, the lower-or-equal branch follows an initial equality miss and therefore ordinarily represents a strictly lower input. The contract retains “lower-or-equal,” because that is the actual branch complement; it does not assume key stability or injectivity of an unspecified conversion.

### Greater-than branch

Only two fixed tokens are eligible in this branch:

1. `0xC422`, which selects its associated result.
2. `0xD444`, which selects its associated result.

The checks occur in that order. A match returns immediately.

Inputs equal to `0x0565`, `0x1888`, or `0x2565` do not select their associated results in this branch. If neither eligible token matches, the function returns zero.

### Lower-or-equal branch

Only three fixed tokens are eligible in this branch:

1. `0x0565`, which selects its associated result.
2. `0x1888`, which selects its associated result.
3. `0x2565`, which selects its associated result.

The checks occur in that order. A match returns immediately.

Inputs equal to `0xC422` or `0xD444` do not select their associated results in this branch. If none of the three eligible tokens matches, the function returns zero.

The `0x1888` token is represented as the address of a fixed location in the supplied evidence. Its contents are not read. Recognition depends on address equality, not on a value stored at that location.

### Read sequence and short-circuiting

At the level of the supplied function body, the observable decision sequence is:

1. Consult the comparison key for the initial equality check.
2. On equality, read the primary result and return.
3. On inequality, consult the comparison key for signed branch selection.
4. Evaluate only the fixed-token comparisons belonging to the selected branch.
5. Read only the result associated with a successful match, or return literal zero if no match succeeds.

There is no visible eager read of all result slots. An unselected result has no role in determining the return value.

The comparison key appears in two separate expressions. The evidence does not establish an atomic snapshot spanning them, nor does it establish volatile accesses or exact machine-load counts. Accordingly, this contract distinguishes source-level decision order from a guaranteed hardware access trace. Behavior under concurrent state modification is documented_only.

### Arithmetic and boundaries

The function performs no visible addition, subtraction, multiplication, indexing, size calculation, or range iteration. There is no arithmetic overflow path within the shown logic.

The significant width-sensitive operation is conversion to signed integer before ordering. Signed-boundary behavior must be derived from the actual environment’s conversion rules, not from the small hexadecimal spelling of the recognized tokens.

All five fixed tokens are nonzero. An input of zero therefore reaches a fixed-token miss unless it first equals the comparison key.

## Acceptance examples

The examples below are conditional specifications, not test results.

Unless stated otherwise, assume that referenced state remains stable during the call, that input and key conversion use ordinary 32-bit signed interpretations, and that the listed small positive tokens retain their numeric values.

### Primary-key match overrides token mapping

Given a comparison key of `0xC422`, a primary result of `0x11223344`, and a different result associated with `0xC422`:

- Input `0xC422` must return `0x11223344`.
- The fixed-token result must not override the primary-key match.

The same precedence applies to each other fixed token.

### Both branch groups can be reachable under one key

Given a comparison key of `0x5000`:

| Input | Required selection |
|---|---|
| `0x0565` | Result associated with `0x0565` |
| `0x1888` | Result associated with `0x1888` |
| `0x2565` | Result associated with `0x2565` |
| `0xC422` | Result associated with `0xC422` |
| `0xD444` | Result associated with `0xD444` |
| `0x5000` | Primary result |
| `0x6000` | Zero |

These outcomes follow from branch eligibility plus exact equality; there is no range mapping.

### A known token can be ineligible

Given a comparison key of `0x1000`, input `0x1888` takes the greater-than branch and must return zero. Its lower-or-equal-branch result is not eligible.

Given a comparison key of `0xE000`, input `0xC422` takes the lower-or-equal branch and must return zero. Its greater-than-branch result is not eligible.

### A selected result can be zero

Given a comparison key of `0x5000` and a zero result associated with `0xD444`, input `0xD444` must return zero through a successful token match.

A caller cannot distinguish that case from an unmatched-token result using the return value alone.

### Null input

If the comparison key is null, a null input must return the primary result.

If the comparison key is non-null, a null input matches none of the fixed tokens and must return zero, provided the required comparisons and conversions are defined in the execution environment.

### Signed ordering differs from unsigned ordering

Assume a 32-bit environment where a comparison key with representation `0x80000000` converts to the minimum signed 32-bit value. Input `0x0565` is then greater than the key under signed ordering.

It must take the greater-than branch and return zero, rather than selecting the result associated with `0x0565`. This example is conditional on the stated conversion behavior.
