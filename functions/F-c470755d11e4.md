# F-c470755d11e4

## Purpose

F-c470755d11e4 performs an in-place structural transformation on linked records. Under a conventional binary-tree interpretation, it is a **left rotation**: the supplied node’s right child is promoted into its position, and the supplied node becomes the promoted node’s left child.

The established behavior is a fixed sequence of 32-bit memory reads and writes. The tree interpretation is inferred from the offsets and link updates; the function does not validate that interpretation.

The operation includes a special case for replacing a distinguished root link. It neither allocates storage nor invokes another function. It does not update balancing metadata, payloads, counts, or any other fields outside the locations identified below.

## Interface

### Inputs

The function accepts two values represented as 32-bit integers in the supplied source:

- **Context address:** Identifies a record containing, at byte offset `+0x10`, a 32-bit value used as the address of a separate anchor record.
- **Node address:** Identifies the record to be moved downward by the transformation.

Both inputs are used as addresses. The source provides no validation of address validity, alignment, object extent, or access permissions.

The address held at the supplied node’s `+0x0c` field is the **promoted node address**. It must identify accessible storage for normal completion. A zero promoted-node address is not handled as an empty-child case.

### Observed layouts

All offsets are byte offsets. Each listed access reads or writes four bytes.

| Record | Offset | Observed role |
|---|---:|---|
| Context | `+0x10` | Address of an anchor record |
| Anchor | `+0x04` | Distinguished node link, interpreted as the root link |
| Node-like record | `+0x04` | Parent link |
| Node-like record | `+0x08` | Left-child link |
| Node-like record | `+0x0c` | Right-child link |

These roles describe how the fields are used, not a complete type definition. Nothing establishes the contents of offset zero, the total allocation size, or the layout of payload and metadata fields.

### Output

There is no return value. The result is communicated entirely through writes to the supplied structures and records reached through their links.

### Preconditions for ordinary tree semantics

For the conventional left-rotation interpretation to hold:

- The context, anchor, supplied node, and promoted node must be valid for the accesses described below.
- The promoted node must be the supplied node’s right child.
- A nonzero left-child link of the promoted node must identify a record whose parent field is writable.
- If the supplied node is not the distinguished root, its parent link must identify an accessible parent record.
- That parent must link to the supplied node through one of its child fields.
- The relevant records and fields must not overlap in ways that cause earlier writes to change later link reads unexpectedly.
- No concurrent or reentrant activity may interfere with the accessed fields.

These are conditions for the ordinary interpretation, not checks performed by the function.

## Behavior

### Ordered memory operations

The following order is established by the supplied source. Repeated reads are significant: a later read is not necessarily represented by a previously captured value.

1. **Select the promoted node.**  
   Read the four-byte right-child field at the supplied node’s `+0x0c` offset. Retain that value as the promoted node address.

2. **Replace the supplied node’s right-child link.**  
   Read the promoted node’s left-child field at `+0x08`. Write that value to the supplied node’s right-child field at `+0x0c`.

3. **Conditionally repair the transferred child’s parent link.**  
   Read the promoted node’s left-child field again and compare that value with zero.

   - If zero, perform no transferred-child parent write.
   - If nonzero, read the promoted node’s left-child field once more. Use this latest value as a record address and write the supplied node address to its parent field at `+0x04`.

   Thus, the value tested for zero and the value used to locate the parent-field write come from separate reads.

4. **Copy the supplied node’s parent link to the promoted node.**  
   Read the supplied node’s parent field at `+0x04`. Write that value to the promoted node’s parent field at `+0x04`.

5. **Locate and inspect the distinguished root link.**  
   Read the context field at `+0x10` as the anchor address. Locate the anchor’s field at `+0x04` and read its value. Compare that value with the supplied node address.

6. **Replace the incoming link to the supplied node.**

   - **Root-link match:** If the distinguished root link equals the supplied node address, write the promoted node address to that root-link field.
   - **No root-link match:** Read the supplied node’s parent field again. From that parent record, read the left-child field at `+0x08`.
     - If the parent’s left-child field equals the supplied node address, write the promoted node address to that left-child field.
     - Otherwise, write the promoted node address to the parent’s right-child field at `+0x0c`.

   The fallback does not read or verify the parent’s right-child value before overwriting it.

7. **Make the supplied node the promoted node’s left child.**  
   Write the supplied node address to the promoted node’s left-child field at `+0x08`.

8. **Complete the supplied node’s new parent link.**  
   Write the promoted node address to the supplied node’s parent field at `+0x04`.

There are no loops and no explicit early returns.

### Normal structural result

Assume stable, non-overlapping records with consistent tree links. Let:

- **N** be the supplied node.
- **P** be N’s original right child, the promoted node.
- **B** be P’s original left child.
- **Q** be N’s original parent.

After normal completion:

- N’s right-child link is B.
- If B is nonzero, B’s parent link is N.
- P’s parent link is Q.
- The incoming link that previously selected N selects P:
  - the distinguished root link, if it selected N; otherwise
  - Q’s left-child link, if that link selected N; otherwise
  - Q’s right-child link.
- P’s left-child link is N.
- N’s parent link is P.

For distinct ordinary node records, N’s left-child field and P’s right-child field remain untouched. Other fields remain untouched unless they alias one of the written addresses.

### Root handling

Root status is determined solely by equality between the anchor’s distinguished link and the supplied node address.

A null parent link does not independently establish that the supplied node is the root. Likewise, a nonzero parent link does not prevent the root branch from being taken.

On the root branch, the promoted node receives the supplied node’s existing parent-link value. The function does not explicitly clear that value or replace it with the anchor address.

Address calculations add fixed byte offsets: `+0x04`, `+0x08`, `+0x0c`, or `+0x10`. There are no variable-length calculations, shifts, multiplications, or size-dependent copies.

No overflow or alignment checks are present. Valid address calculations are a precondition rather than a documented wrapping-address feature.

## Side effects

### Writes

Under non-overlapping, stable-record conditions, the function performs:

- Five four-byte writes when the promoted node’s left-child link is zero.
- Six four-byte writes when that link is nonzero.

The five unconditional write roles are:

1. Supplied node’s right child.
2. Promoted node’s parent.
3. Selected incoming link: root, parent-left, or parent-right.
4. Promoted node’s left child.
5. Supplied node’s parent.

The optional sixth write changes the transferred child’s parent.

### Ownership and lifetime

No allocation, deallocation, reference-count operation, destructor invocation, or external call appears.

The function rewires existing references. It does not establish ownership transfer or extend the lifetime of any record. All records needed by subsequent accesses must remain alive throughout the operation.

There are no callees whose memory-ownership or global-state behavior must be assumed.

### Intermediate states

The update is not atomic. Earlier writes occur before later link repairs.

For example, the supplied node’s right child is replaced before the incoming root or parent link is redirected. The promoted node’s left child is changed before the supplied node’s parent is finally updated.

No lock, transaction, rollback, or explicit synchronization is present. Concurrent readers cannot be assumed to observe a consistent tree during the operation.

### Errors and malformed structures

The function returns no success or failure indication and contains no explicit error reporting.

Invalid storage may prevent completion after some writes have already occurred. The source supplies no recovery behavior.

Malformed but accessible links can produce destructive changes without detection. In particular, when the root link does not match and the parent’s left-child link does not match, the parent’s right-child link is overwritten regardless of its previous value.

Aliasing may also change subsequent reads and branch decisions. The normal structural result above is therefore conditional, not a guarantee for arbitrary overlapping records.

### Root rotation with no transferred child

Initially:

- The anchor’s root link selects N.
- N’s right child is P.
- P’s left child is zero.
- N’s parent is Q.

Expected result:

- The root link selects P.
- P’s parent is Q.
- P’s left child is N.
- N’s parent is P.
- N’s right child is zero.
- No transferred-child parent write occurs.

This example does not require Q to be zero; the function copies it unchanged.

### Rotation beneath a parent’s left link

Initially, the root link does not select N, Q’s left child is N, N’s right child is P, and P’s left child is B, where B is nonzero.

Expected result:

- Q’s left child becomes P.
- The root link remains unchanged.
- P’s parent becomes Q.
- P’s left child becomes N.
- N’s parent becomes P.
- N’s right child becomes B.
- B’s parent becomes N.

### Rotation beneath a parent’s right link

Initially, the root link does not select N, Q’s left child is not N, and Q’s right child is N.

Expected result: Q’s right child becomes P, with the remaining rotation updates as described above. Q’s left-child field is read but not written.

### Inconsistent incoming parent links

Initially, the root link does not select N, and neither of Q’s child links selects N.

Expected behavior: the function still writes P into Q’s right-child field. It does not reject the structure or search for another incoming link.

### Root selection takes precedence

Initially, the root link selects N, while N’s stored parent identifies a record whose child links are inconsistent with N.

Expected behavior: the root branch is taken. The function copies N’s parent value to P but does not inspect that parent’s child fields.

### Missing promoted node

Initially, N’s right-child link is zero.

Expected behavior: there is no empty-child return path. The function attempts to read a field at offset `+0x08` from the zero-valued address before its first write. Successful no-op behavior is not established.
