# F-56ed9675f3da

## Purpose

F-56ed9675f3da conditionally updates destination pixel storage using source pixel storage. It supports four combinations of 16-bit and 32-bit storage, selects indirect conversion targets, and distinguishes zero, full, and intermediate source opacity.

**Inferred intent:** format-aware rectangular pixel compositing.

**Established limits:** the supplied static representation does not establish the conversion equations, combination equations, complete packing interface, or all mixed-width scratch inputs. This contract does not replace unresolved behavior with conventional alpha blending.

## Interface

### Entry and return

The function accepts one 32-bit address-like argument identifying an operation record. It has no explicit return value or error-status output.

Accessed operation fields, descriptors, global slots, pixel addresses, and dependency targets must be valid. No null checks, clipping, allocation-size checks, alignment checks, or arithmetic-overflow checks are visible.

### Operation record

Offsets are byte offsets from the supplied address.

| Offset | Width | Observed role |
|---|---:|---|
| `0x0C` | 32 bits | Source starting row |
| `0x10` | 32 bits | Source starting column |
| `0x1C` | 32-bit pointer | Source descriptor |
| `0x24` | 32 bits | Source byte stride |
| `0x48` | 32 bits | Destination starting row |
| `0x4C` | 32 bits | Destination starting column |
| `0x50` | 32 bits | Destination ending row |
| `0x54` | 32 bits | Destination ending column |
| `0x58` | 32-bit pointer | Destination descriptor |
| `0x60` | 32 bits | Destination byte stride |

Nominal width is destination ending column minus starting column. Nominal height is destination ending row minus starting row. No source ending coordinates are consulted.

### Surface descriptors

| Offset | Width | Observed role |
|---|---:|---|
| `0x00` | 32-bit pointer | Pixel-buffer base |
| `0x08` | 32 bits | Storage selector, tested against `0x10` and `0x20` |
| `0x10` | Unsigned 16 bits | Format value, including selection bit `0x2000` |

Storage width alone does not establish channel encoding.

For pixel size \(B\), the initial pixel address is formed as:

\[
\text{base}+\text{starting row}\times\text{byte stride}
+\text{starting column}\times B
\]

The source and destination independently use \(B=2\) or \(B=4\). Direct pixel loads and stores have the corresponding 16-bit or 32-bit width.

### Channel and packed-word layouts

Channel scratch records consist of four consecutive bytes, described here as red, green, blue, and opacity. These names express inferred graphics intent.

Explicitly assembled 32-bit words have numeric layout:

\[
(\text{opacity}\ll24)\;|\;(\text{red}\ll16)\;|\;
(\text{green}\ll8)\;|\;\text{blue}
\]

This establishes bit positions, not memory endianness or the destination converter’s stored encoding.

## Behavior

### Dispatch and rejection

The source descriptor is obtained first. Its storage selector is tested for 16-bit storage; failure leads to a separate observation testing for 32-bit storage. If both tests reject their observed values, the function returns without obtaining the destination descriptor.

After a supported source branch is selected, the destination selector is similarly tested for 16-bit storage and, if necessary, separately for 32-bit storage. Unsupported destination storage returns without pixel processing.

Repeated selector reads are distinct observations. A changing descriptor is not equivalent to one immutable selector.

Additional gates apply:

| Source → destination | Required comparison outcome |
|---|---|
| 16 → 16 | The second comparison of cached source format against G5 must report equality |
| 16 → 32 | A later source-format observation compared against G5 must report equality |
| 32 → 16 | A later unsigned 16-bit source-format observation must equal `0x1888` |
| 32 → 32 | No source-format equality gate |

For 16 → 16, passing the second comparison is not sufficient to establish initialized traversal: the first comparison independently selects the scratch base.

### Global slots and converter selection

The following labels identify global slots, not dependency identities.

| Slot | Role |
|---|---|
| G1 | Default converter target for 16-bit storage |
| G2 | Alternate 16-bit converter target, selected by format bit `0x2000` |
| G3 | Default converter target for 32-bit storage |
| G4 | Alternate 32-bit converter target, selected by format bit `0x2000` |
| G5 | Operand used in the 16-bit-source format comparisons |

**G5’s storage width and type are unresolved.** The supplied representation provides neither its declaration nor an explicit load-width annotation. Its signedness, comparison conversions, and value must not be inferred from the width of the source-format operand.

Once a converter-selection stage is reached, slot observations occur as follows:

- **16 → 16 source:** G1 is read, then G2 if the cached source format has bit `0x2000` set.
- **16 → 16 destination:** a separate destination-format observation selects exactly one slot. G1 is read for a clear bit; G2 for a set bit. Width calculation occurs between the two conditional read positions.
- **16 → 32:** G1 is read before the source-format selection observation, with G2 read if selected. G3 is then read before the destination-format selection observation, with G4 read if selected.
- **32 → 16:** G3 is read before the source-format selection observation, with G4 read if selected. Height and width are calculated before G1 is read for destination selection; G2 is subsequently read if selected.
- **32 → 32:** G3 is read for source selection, with G4 read if selected. Width is calculated before a separate G3 read for destination selection, again optionally followed by G4.

A default-slot read still occurs when its target is replaced by an alternate target.

Selected targets are cached before pixel processing. Later dependency calls do not cause these slots to be reloaded. Separately selected source and destination targets can differ even when they originate from the same global slot. Conversely, changing a slot during pixel processing does not change the already selected target.

### Format observations and G5 comparisons

**16 → 16.** The unsigned 16-bit source format is zero-extended into a cached 32-bit value. That cached value supplies source converter selection, source extraction, and both G5 comparisons.

The destination format is separately cached, also from an unsigned 16-bit read, for destination extraction and packing. A later destination-format read controls destination converter selection; it need not match the cached format.

After converter selection and width initialization, G5 is observed twice:

1. The first comparison with the cached source-format value selects the normal or alternate scratch base.
2. Height is calculated.
3. The second comparison with the same cached source-format value controls return.

A first mismatch followed by a second equality continues with the alternate scratch base. The required width and format contents at that base are not established.

The cached source operand is established as a zero-extended 32-bit value. This does **not** establish that G5 occupies 32 bits, or that the comparison is an unsigned 32-bit comparison.

**16 → 32.** Source format is observed for converter selection, then observed again after destination converter selection for comparison against G5. This comparison directly uses an unsigned 16-bit source-format read. Its comparison conversions depend on G5’s unresolved type.

There is one G5 observation in this branch. The resulting mismatch decision selects a scratch base and, after height calculation, causes return. An equality result continues on the normal base, but the loop-width and extraction-format inputs still lack visible initialization.

**32 → 16.** Source format is observed for converter selection and later read again for comparison with `0x1888`. Source extraction receives an explicitly prepared `0x1888`, rather than necessarily using the converter-selection observation. Destination format controls converter selection, but the destination extraction and packing format input is not visibly initialized.

**32 → 32.** Format reads select converters. Channel extraction is performed directly from converted words; there is no corresponding extraction-format argument.

Stable descriptors and globals are therefore additional assumptions for a conventional single-format interpretation, not guarantees established by this function.

### Traversal and arithmetic

With initialized, nonnegative dimensions and scratch inputs, processing proceeds left to right within each row, then to the next row. Both pixel pointers advance past transparent positions.

After each row, the correction added to an already advanced pointer is:

\[
\text{byte stride}-\text{width}\times\text{pixel size}
\]

For a complete positive-width row, the next row begins one stride beyond the previous row’s start.

The representation uses 32-bit arithmetic, signed loop comparisons, and unsigned bit operations. It does not establish a portable signed-overflow policy. Ordinary use requires representable dimension differences, products, address calculations, and row corrections.

Nonpositive height prevents pixel processing in every supported branch. Metadata observations, converter-slot reads, address calculations, format gates, and scratch writes can nevertheless precede return.

In initialized scalar-loop paths, zero or negative width produces no pixel visits, but row corrections still incorporate that width. The 16 → 32 branch does not establish that its actual loop width equals nominal width.

The 32 → 32 branch handles an odd width with one leading pixel before its signed paired-loop test. Zero width produces no visits. An odd negative width can therefore process one leading pixel per positive-height row, despite the negative signed width. Negative dimensions are not generally safe empty rectangles.

### Common pixel decisions

For each visited position, the direct source pixel load and source conversion precede any direct load or store of the corresponding destination pixel.

Subject to the branch-specific opacity-test qualification:

- **Zero opacity:** no direct destination pixel load or store.
- **Full opacity:** replacement without loading the old destination pixel.
- **Intermediate opacity:** destination load and conversion precede combination and replacement.

These statements concern direct accesses by this function. Dependencies may access other memory or previously exposed scratch addresses.

In 32 → 16, the full-opacity condition is represented as a plain-character comparison with −1. Whether byte `0xFF` satisfies it depends on character interpretation. Other paths visibly compare an unsigned opacity value with 255.

### 16 → 16

With the normal initialized scratch base, width and both extraction formats are established.

Each source pixel is loaded as unsigned 16 bits, passed through the selected source converter, and supplied to F-1e2f295ee27c with the cached source format and a channel-output address.

For full opacity, the caller prepares outgoing scalar value 255, calls F-936c8a3c5816 with cached destination format and source colors, then invokes the destination converter without explicit arguments in the supplied representation. Its 16-bit result is stored.

For intermediate opacity, the destination is loaded, converted, and extracted using cached destination format. Destination opacity is saved before F-16bb7e4b5a50 receives result, destination-channel, and source-channel addresses.

After that call:

- Result color bytes are copied into destination-channel scratch.
- The maximum of the previously observed source opacity and saved destination opacity is selected.
- Result opacity is copied into destination-channel scratch.
- The selected maximum is written to the outgoing scalar slot.
- Destination-channel opacity is overwritten with that maximum.
- Result colors are supplied to F-936c8a3c5816 before destination conversion and a 16-bit store.

The two destination-channel opacity writes are distinct visible caller actions. Their relevance extends to dependencies that retain a scratch address. The caller-selected maximum is established; its final encoding through the unresolved packing interface is not.

### 16 → 32

The supplied representation does not visibly initialize the loop-width slot or either extraction-format slot. A deterministic rectangular operation for this combination is **documented_only**, not established.

Conditional on reaching a pixel with meaningful extracted channels:

- Zero source opacity skips direct destination access.
- Full opacity causes explicit packing of source colors with opacity 255, destination conversion, and a 32-bit store.
- Intermediate opacity causes destination load, conversion, and extraction, followed by F-86dd6fb1ad71 with explicit argument 255 and then F-35c2e4297234.

For intermediate opacity, the caller saves destination opacity before those two dependencies. Afterwards it overwrites destination-channel opacity with the maximum of saved destination opacity and the earlier source opacity. That maximum and the destination color bytes then present are explicitly packed, converted, and stored.

The unresolved extraction arguments do not erase the separately established converter-selection observations.

### 32 → 16

Width and row corrections are initialized. Source extraction uses `0x1888`. Destination extraction and packing use a format input whose initialization is absent from the supplied representation.

If the plain-character full-opacity test succeeds, the caller prepares outgoing scalar 255, calls F-936c8a3c5816 with source colors, invokes the destination converter without explicit arguments, and stores its 16-bit result.

For intermediate opacity, destination conversion and extraction precede F-86dd6fb1ad71 with explicit argument 255, followed by F-35c2e4297234. The destination-channel opacity byte present after those calls is copied into the outgoing scalar slot. Destination colors are then supplied to F-936c8a3c5816 before conversion and storage.

This branch imposes no explicit maximum-opacity rule.

### 32 → 32

Converted words are separated directly into channel bytes. F-1e2f295ee27c is not called.

A full-opacity converted source word is passed unchanged to the destination converter. Intermediate opacity causes destination conversion followed by F-16bb7e4b5a50. All four result bytes are copied into destination-channel scratch and explicitly packed for destination conversion and storage. No caller-imposed opacity maximum appears.

An odd width processes one leading pixel, followed by pairs. Within each pair, the first pixel’s conversion and possible store complete before the second source pixel is read.

The leading-pixel branch prepares source-channel scratch even for transparent and fully opaque pixels. Paired processing prepares those channel records only when combination is needed.

## Side effects

Direct persistent writes target destination pixels. No direct operation-record or descriptor writes are visible. Temporary scratch is written and its addresses are passed to dependencies.

No direct allocation, release, or ownership transfer appears. This does not establish dependency ownership behavior. Scratch-address arguments do not establish permission to retain or use those addresses after return.

Source and destination may alias. No snapshot, overlap-safe copying, or rollback mechanism is visible. An earlier destination write can affect a later source read.

Dependencies are not assumed to preserve globals, scratch, or unrelated memory. Cached converter targets remain cached, but dependency effects on exposed scratch can affect later observations.

There is no visible recovery or status reporting for invalid addresses, dependency failure, or partially completed updates.

## Acceptance examples

These are conditional static scenarios, not executed tests.

1. **Unsupported source storage.** If both source-selector observations fail their respective tests, return occurs without destination-descriptor access or pixel processing.

2. **Zero height.** With valid reached metadata and nominal height zero, there are no pixel accesses. Earlier converter selection and format comparisons can still occur.

3. **Default then alternate.** In 16 → 32, a source selection observation with bit `0x2000` set causes G1 to be read before G2. The selected G2 target is cached.

4. **Changing converter slot.** If a dependency changes G3 during 32 → 32 processing, subsequent conversions use the already selected targets rather than reloading G3.

5. **Different destination-format observations.** In 16 → 16, a cached destination format with selection bit clear and a later selection observation with it set cause G2 selection while extraction and packing retain the earlier cached format.

6. **Two G5 outcomes.** In 16 → 16, a first comparison reporting mismatch and a second reporting equality permit continuation with the alternate scratch base. Nominal width alone does not establish subsequent traversal.

7. **G5 type unresolved.** A cached source-format value of `0x1888` does not by itself prove either G5 comparison succeeds. G5’s observed value and applicable comparison conversions must also be established. No 32-bit G5 load is required by this contract.

8. **Single mixed-width G5 observation.** In 16 → 32, if the comparison reports mismatch, height is calculated before return. There is no second G5 observation that can reverse that decision.

9. **Transparent pixel.** In an established traversal, zero source opacity causes no direct destination load or store, while both traversal pointers advance.

10. **Opaque 32 → 32 pixel.** Converted source word `0xFF123456` reaches the destination converter unchanged. The converter result is stored without loading the previous destination pixel.

11. **16 → 16 intermediate opacity.** Source opacity 80 and saved destination opacity 170 select maximum 170. Result opacity is first copied into destination scratch and then overwritten with 170; outgoing scalar is also 170. Final encoded opacity remains conditional on the packing interface.

12. **Three-pixel 32 → 32 row.** The leading pixel is followed by a pair in column order. Each possible store completes before the next source pixel load.

13. **Unresolved mixed-width width.** Nominal width four does not establish four visits in 16 → 32 because its loop-width initialization is absent.

14. **First color above 127.** First color byte `0xE0` passes through plain-character conversion before F-936c8a3c5816. Requiring unsigned integer value 224 would need additional signedness and ABI evidence.
