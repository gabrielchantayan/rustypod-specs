# F-4990728d74c1

## Purpose

F-4990728d74c1 produces a comparison-like integer result from two object addresses and an opaque 32-bit argument.

It first compares unsigned 16-bit fields at byte offset 6 in the two objects. A smaller first field produces positive one; a larger first field produces negative one. Equal fields lead to conditional preparation, two setup calls, and repeated comparison of dependency-produced integer values.

The equal-field path is stateful. It accesses global state, invokes dependencies, exposes addresses of local storage, and may continue indefinitely. The evidence does not establish that the dependency-produced values are characters, bytes, or elements of either input object.

This contract distinguishes established static behavior from inferred intent and unresolved dependency behavior. No runtime tests have been performed.

### Return value

The recovered result is an integer, treated as 32 bits in this model.

For stable input fields:

- A smaller first unsigned field returns **positive one**.
- A larger first unsigned field returns **negative one**.
- Equal fields enter the dependency-driven path.

On that path:

- Unequal dependency results return **the first result minus the second**.
- Equal zero results return **zero**.
- Equal nonzero results cause another iteration.

The subtraction is not normalized to positive or negative one. Its portable behavior when the mathematical difference exceeds the signed 32-bit range is unresolved.

There is no separate status output, explicit error result, or locally recognized dependency-failure value.

## Behavior

### Initial context capture and field comparisons

Before comparing object fields, the function evaluates a global context-pointer location and retains the resulting pointer for later use.

It then compares the unsigned 16-bit fields at byte offset 6:

1. A less-than comparison that succeeds returns positive one immediately.
2. Otherwise, an equality comparison is evaluated.
3. Equality enters the dependency-driven path.
4. Failure of that equality comparison returns negative one.

The representation contains field-access expressions in both comparisons; it does not establish a single cached field value per input across the whole decision. The evaluation order of the two field operands within either comparison is unspecified by the supplied evidence.

Consequently, descending comparison polarity is established for stable fields, but a coherent snapshot is not established if field contents change between evaluations.

Neither early-return branch calls a dependency. Both occur after the entry evaluation of the global context-pointer location.

### Three distinct evaluations of the global context-pointer location

The function uses the global context-pointer location in three separate expressions:

| Evaluation | When it occurs | What it controls |
|---|---|---|
| Entry capture | Before the object-field comparisons | Retains a pointer used later by F-d08d3ca17b81 and F-3f12fb57a2c4. |
| Flag-test evaluation | Only after the field-equality branch is taken | Selects the context object whose four-byte word at byte offset 12 is tested for bit 0. |
| Conditional argument evaluation | Only if the tested bit is clear | Selects the context object used to form the offset-12 address passed to F-b255b26284e6. |

The flag-test expression and the conditional argument expression refer directly to the global location. Neither is specified as using the entry-captured pointer.

These are separate evaluations in the supplied representation, not a claim that execution necessarily performs three physical memory reloads. The evidence provides neither an atomic snapshot across them nor a synchronization guarantee.

If the global pointer remains unchanged, all three evaluations identify the same context object. If different values become visible at these evaluations under an execution model that permits that behavior, the entry-captured object, flag-tested object, and object addressed for F-b255b26284e6 can differ. In particular, the helper’s argument is not necessarily the address of the word whose bit was tested.

There is no visible dependency call between the flag test and construction of F-b255b26284e6’s argument. This absence does not convert the two expressions into a documented snapshot guarantee.

### Conditional preparation

After entry into the equal-field path, the function evaluates the global context pointer for the flag test and examines bit 0 of the four-byte word at byte offset 12 from that pointer.

The condition is short-circuited:

- If bit 0 is set, F-b255b26284e6 is not called, and preparation is skipped.
- If bit 0 is clear, the global context-pointer location is evaluated again to form an offset-12 address for F-b255b26284e6.
- A zero return from F-b255b26284e6 skips preparation.
- Any nonzero return enables preparation.

When enabled, preparation consists of these calls in order:

1. **F-1fbcf28c587c** receives a value from a separate global location and the numeric argument **512**.
2. **F-804adc29bbfb** receives the four-byte result of F-1fbcf28c587c as its first argument. Its second and third arguments come from two other global locations, in their established positional order.
3. **F-d08d3ca17b81** receives the address at byte offset 12 from the **entry-captured context pointer**.

The value 512 has no established unit. It is not established to be a byte count, allocation size, capacity, or limit.

The global values supplied as the second and third arguments to F-804adc29bbfb are evaluated after F-1fbcf28c587c returns. Changes that the earlier dependency makes to those locations can therefore affect the later call. The relative evaluation order of those two argument expressions is not established.

F-d08d3ca17b81 does not use a fresh evaluation of the global context-pointer location. If a dependency replaces that global pointer, this call still uses the entry-captured object. Continued validity of that object is not guaranteed by the visible body.

### Unconditional equal-field setup

After preparation completes or is skipped, two calls occur in order:

1. **F-3f12fb57a2c4** receives the four-byte value then stored at byte offset 0 of the entry-captured context object, followed by the first object address.
2. **F-44362605ab79** receives the opaque third argument unchanged.

The offset-0 value is read at this stage, rather than saved at entry. Preparation dependencies can affect this argument by modifying the captured object, provided the object remains valid.

Neither setup call’s return value controls a visible branch.

The second object address is not explicitly passed to either setup dependency or any other dependency. The evidence therefore does not establish how, or whether, the later generated values relate to that object.

### Repeated comparison

The comparison loop executes at least once if setup returns normally.

Each iteration has this call order:

1. F-d3922c7fe0ec receives the address of a first local stack location.
2. F-5afffd4d8a24 is called without explicit arguments, producing the first integer result.
3. F-d3922c7fe0ec receives the address of a distinct second local stack location.
4. F-5afffd4d8a24 is called again without explicit arguments, producing the second integer result.

The two local addresses are four bytes apart in the recovered stack layout. Their contents, types, initialization requirements, and relationship to dependency-maintained state are not established. The visible body does not initialize them before passing their addresses.

The resulting pair determines control flow:

- If the results differ, return the first minus the second.
- Otherwise, if their equal value is zero, return zero.
- Otherwise, repeat the entire iteration.

Zero is terminating only as an equal pair. One zero and one nonzero value follow the subtraction rule. Equal negative values continue just like equal positive values.

There is no visible iteration limit, timeout, cancellation mechanism, or progress guarantee.

## Acceptance examples

These are conditional consequences of static control flow, not executed tests. Unless otherwise stated, assume stable readable input fields, satisfied dependency preconditions, normally returning dependencies, and representable subtraction results.

1. **Smaller first field:** Fields 7 and 9 return positive one. The entry context-pointer evaluation occurs; no dependency is called, and neither later context-pointer expression is reached.

2. **Larger unsigned field:** Fields 65535 and 0 return negative one. The first field is the unsigned value 65535, not signed negative one.

3. **Flag suppresses the helper:** Equal fields reach the flag test. If the selected word has bit 0 set, neither F-b255b26284e6 nor the preparation sequence runs. The conditional argument evaluation is skipped. Setup and comparison still follow.

4. **Helper declines preparation:** With bit 0 clear, the conditional argument expression is evaluated and F-b255b26284e6 runs. A zero result skips only preparation, not setup or comparison.

5. **Helper enables preparation:** Any nonzero helper result causes F-1fbcf28c587c, F-804adc29bbfb, and F-d08d3ca17b81 to run in that order.

6. **Distinct context selections:** Suppose a permitted execution exposes context A at entry, context B at the flag-test evaluation, and context C at the conditional argument evaluation. If B’s flag bit is clear, F-b255b26284e6 receives C’s offset-12 address, not necessarily B’s or A’s. If preparation runs, F-d08d3ca17b81 receives A’s offset-12 address. This example specifies consequences of differing evaluations, not support for unsynchronized pointer mutation.

7. **Replacement during preparation:** If a preparation dependency replaces the global context pointer, F-d08d3ca17b81 still uses the entry-captured object. F-3f12fb57a2c4 subsequently reads that object’s current offset-0 word, assuming the object remains valid.

8. **Immediate zero termination:** A first generated pair of 0 and 0 returns zero after one iteration.

9. **Continuation followed by difference:** A pair of 12 and 12 continues. A subsequent pair of 3 and 8 returns negative five. Across these two iterations, each loop dependency is called four times.

10. **One-sided zero:** A pair of 0 and 5 returns negative five rather than taking the equal-zero termination path.

11. **Equal negative values:** A pair of negative one and negative one continues. The visible function does not interpret that pair as an error.

12. **Unbounded continuation:** If every generated pair is equal and nonzero, no normal return is reached through the visible loop.
