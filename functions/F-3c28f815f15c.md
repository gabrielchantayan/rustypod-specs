# F-3c28f815f15c

## Purpose

F-3c28f815f15c coordinates a stateful traversal through opaque dependencies and returns a packed 64-bit result.

The established behavior is narrower than a conventional search or iterator contract:

- It initializes local traversal state from two caller-supplied 32-bit words and a separate 32-bit argument.
- It requests a candidate at least once.
- A zero status from the candidate-producing dependency ends traversal without reading a candidate record.
- A nonzero status causes examination of the candidate’s first 32-bit word.
- Traversal stops successfully when that word represents the original input pointer, or when the original input pointer has the all-ones 32-bit representation.
- On successful termination, it captures a 32-bit field at byte offset 44, invokes a success-only dependency, performs cleanup, and returns a pointer/value pair packed into 64 bits.
- On zero-status termination, it performs cleanup and returns a pointer in the upper half with zero in the lower half.

**Inferred intent:** the comparison of a candidate’s first word with the original pointer resembles traversal of linked records. Neither the record type nor the traversal algorithm is established. This contract does not assign application-level meanings such as “parent,” “owner,” or “result code” to the observed fields.

## Interface

### Inputs

The function accepts four arguments, in this order:

| Argument | Established representation | Observed use |
|---|---|---|
| Context word | 32 bits | Passed to initialization and, on successful termination, to a second dependency. |
| Origin pointer | Pointer represented in 32 bits | Seeds a mutable local cursor and remains the comparison target during traversal. |
| First state word | 32 bits | Initializes the first word of addressable local traversal storage. |
| Second state word | 32 bits | Initializes the adjacent second word of that storage. |

The context word and the two state words have no established internal interpretation. They must not be assumed to be handles, flags, lengths, or ownership tokens.

The pointer width is supported by the supplied representation’s 32-bit pointer packing, four-byte record indexing, and explicit formation of a 64-bit result from two 32-bit components. Behavior under a different pointer-width model is not established.

### Local storage exposed to dependencies

Two distinct pieces of local storage are made addressable:

1. **Traversal state:** two adjacent four-byte words, initially containing the third and fourth arguments in that order.
2. **Cursor slot:** one pointer-width slot, initially containing the origin pointer.

The initialization, advancement, and cleanup dependencies receive the address of the first traversal-state word. Advancement also receives the address of the cursor slot.

The visible storage establishes those initial values and addresses. It does not establish a complete dependency-defined state layout or authorize accesses beyond the available local storage.

### Candidate layout

For any candidate examined after a nonzero advancement status, the wrapper uses only these locations:

| Byte offset | Width | Interpretation within this function |
|---|---|---|
| 0 | 32 bits | Bit pattern interpreted as a pointer and compared with the original origin pointer. |
| 44 | 32 bits | Payload captured only when traversal is terminating successfully. |

The intervening bytes have no established meaning. The two fields need not have related semantics.

### Output

The function returns a 64-bit quantity formed from:

- **Upper 32 bits:** the cursor-slot value read after cleanup.
- **Lower 32 bits:** zero on zero-status termination, or the captured field from byte offset 44 on successful termination.

This is bit packing, not an arithmetical combination that sign-extends the payload. A payload with its highest bit set remains confined to the lower 32 bits.

Although the declared result is signed, the construction is best specified by its 64-bit representation. If interpreted as a signed 64-bit integer, its sign depends on the highest bit of the returned cursor representation.

There is no independent success bit. A zero payload on successful termination can produce the same return representation as zero-status termination if their final cursor values are equal.

## Behavior

### Initialization

Before invoking a dependency, the function:

- Places the origin pointer in the cursor slot.
- Places the first state word at the start of traversal-state storage.
- Places the second state word in the adjacent four-byte position.

It then calls **F-8ca21d3a8cca**, passing the traversal-state address followed by the context word.

The return value of this dependency is not used. Its mutations to traversal state can affect subsequent calls. The function does not restore the two initial state words before advancing.

### Advancement and zero-status termination

After initialization, the function calls **F-b38a3aba0e18**, passing:

1. The traversal-state address.
2. The cursor-slot address.

This call occurs at least once. Neither a null origin pointer nor an all-ones origin pointer skips it.

The advancement status is tested as a 32-bit integer:

- Zero selects the zero-status termination path.
- Every nonzero value, including a negative signed value, selects candidate examination.

On a zero status, the function calls **F-d0d3f100effc** with the traversal-state address. After that call returns, it reads the cursor slot and returns its 32-bit representation in the upper half of the result, with zero in the lower half.

This branch does not perform either candidate-field read. In particular, it does not dereference the cursor merely to construct the result.

A zero status does not imply that the cursor remains equal to its input value. Advancement received a writable cursor-slot address and may have changed it before returning zero.

### Candidate examination and continuation

After each nonzero advancement status, the function reads the 32-bit word at byte offset zero of the current candidate and treats that word as a pointer representation.

It compares that representation with the original origin pointer.

- If they are equal, traversal terminates successfully.
- If they are unequal and the original origin pointer is all ones, traversal also terminates successfully.
- If they are unequal and the original origin pointer is not all ones, the function requests another advancement.

The candidate’s first-word read precedes the all-ones-origin stopping decision. Consequently, the all-ones origin is not a guard against an invalid candidate pointer. A nonzero advancement status must still leave a candidate whose first word is readable.

The original origin pointer remains the comparison target. Replacing the cursor through advancement does not replace that target.

There is no established iteration limit, timeout, repeated-candidate detection, or progress check. If advancement continually returns nonzero and produces candidates that fail the stopping condition for a non-sentinel origin, the function continues indefinitely.

### Successful termination

Once the stopping condition holds, the function reads the 32-bit payload at byte offset 44 of the current candidate.

It then invokes these dependencies in order:

1. **F-e39ea2a6fc7d**, with the context word.
2. **F-d0d3f100effc**, with the traversal-state address.

Only after both calls return does the function obtain the cursor value used for the upper half of its return value. The lower half uses the payload captured before either call.

This ordering matters if a dependency changes the candidate, associated state, or any cursor-slot alias retained by an earlier dependency. The wrapper does not reread the payload after the success-only dependency or after cleanup.

No preservation of global state, candidate contents, or cursor aliases is established for these dependencies.

### Normal-path call counts

Assuming all dependencies return normally and all required memory accesses are valid:

- Initialization occurs exactly once.
- Advancement occurs one or more times.
- Cleanup occurs exactly once on either terminating path.
- The success-only dependency occurs exactly once on successful termination and never on zero-status termination.

These counts do not guarantee cleanup after a memory fault, nonlocal exit, or dependency that does not return.

## Side effects

### Direct memory accesses

The function directly initializes and updates its local storage and reads candidate fields as described above.

No direct write to a candidate record is visible. This does not establish that candidate records remain unchanged: dependencies may modify memory through arguments, retained aliases, or other state.

The wrapper’s relevant observable order is:

- Local initialization.
- Initialization dependency.
- One or more advancement calls, interleaved with first-word reads after nonzero statuses.
- On success, payload read, then success-only dependency.
- Cleanup.
- Final cursor-slot read and return construction.

On zero-status termination, cleanup follows the zero-status advancement without a candidate-field read.

### Ownership and lifetime

No direct allocation, deallocation, reference-count adjustment, or ownership transfer is established by the wrapper.

The dependency names used here imply no ownership policy. In particular, the dependency described as cleanup is known to be called at termination; it is not thereby established to release memory.

The traversal-state address and cursor-slot address designate local storage. Whether dependencies retain those addresses is unknown. Their use after this function returns would require a separate valid lifetime arrangement not established here.

The function does not directly dereference the final cursor after cleanup. Any later dereference by the caller requires independent evidence that the returned pointer remains valid.

### Invalid inputs and failures

No explicit validation or error translation is visible.

A nonzero advancement status requires a readable first word at the current cursor. Successful termination additionally requires a readable four-byte field at byte offset 44. Null, stale, unmapped, or otherwise invalid cursor values are not converted into a defined error result by this wrapper.

The advancement dependency’s zero status is the only explicit status-based alternate termination path. Its application-level meaning is unknown; it must not automatically be described as an error or exhaustion.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Each example assumes valid required memory accesses and normal dependency returns.

### Immediate zero status with a replaced cursor

Given advancement first returns zero after storing pointer representation `0x12345678` in the cursor slot, and cleanup leaves that slot unchanged:

- No candidate-field read occurs.
- The success-only dependency is not called.
- The result is `0x1234567800000000`.

This remains true even if the origin pointer had a different representation.

### Immediate matching candidate

Given a non-sentinel origin, the first advancement returns nonzero, the candidate’s first word equals the origin, its payload is `0x89ABCDEF`, and the final cursor representation is `0x00102030`:

- Exactly one advancement occurs.
- The payload is read before the success-only dependency.
- The result is `0x0010203089ABCDEF`.

The payload’s highest bit does not fill any bits in the upper half.

### Several candidates before a match

Given two nonzero advancement results whose candidates’ first words differ from a non-sentinel origin, followed by a third nonzero result whose candidate’s first word matches:

- Three advancement calls occur.
- Each candidate’s first word is examined.
- Only the third candidate’s payload is read by the wrapper.
- The success-only dependency precedes cleanup.

### All-ones origin

Given origin representation `0xFFFFFFFF` and a nonzero first advancement status:

- The first candidate’s first word is still read.
- The function then terminates successfully regardless of whether that word matches the origin.
- Its payload must be readable.

If the first advancement instead returns zero, termination takes the zero-status path without candidate examination.

### Mutation after payload capture

Given successful termination captures payload `0x11223344`, a later dependency changes the candidate’s payload, and a valid retained cursor-slot alias changes that slot to `0x55667788` before the final read:

- The lower half remains `0x11223344`.
- The upper half is `0x55667788`.
- The result is `0x5566778811223344`.

This example is conditional on such aliasing being valid; the wrapper does not establish that dependencies retain an alias.

### Null origin and nonzero status

A null origin is not rejected. If advancement produces a valid candidate whose first word is zero, that candidate satisfies the matching condition. If advancement leaves the cursor null and returns nonzero, the wrapper attempts a first-word read through that cursor rather than returning a defined null-input error.

## Uncertainties

The following are **documented_only**:

- The meanings of the context and state words.
- The complete traversal-state layout and dependency access requirements.
- The traversal algorithm, record type, and semantic meanings of offsets zero and 44.
- Whether zero advancement status means exhaustion, failure, cancellation, or another condition.
- Why the all-ones origin has special stopping behavior.
- Dependency mutation of globals, candidate memory, or retained aliases.
- Allocation, release, ownership transfer, and returned-pointer lifetime.
- Reentrancy, concurrency safety, and dependency behavior on abnormal exits.
- Whether intended callers restrict origin values or require guaranteed termination.

The linked-record interpretation is inferred intent, not an established requirement.

## Evidence

This contract is based solely on the supplied static function representation and the supplied opaque dependency mapping.

Established evidence includes argument widths, local initializations, dependency argument order, the zero/nonzero status branch, candidate reads at byte offsets zero and 44, stopping-condition order, terminal dependency order, and 64-bit return packing.

No dependency implementations were available. No runtime tests have been performed. The acceptance examples are conditional consequences of the visible behavior, not observations of execution.
