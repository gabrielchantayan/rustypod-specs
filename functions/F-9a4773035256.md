# F-9a4773035256

## Purpose

F-9a4773035256 rewires a linked structure around an existing node and the node referenced by its link at byte offset `0x0C`. It also updates either a distinguished root slot or one link in the existing node’s parent.

Under a conventional binary-tree interpretation, this is a left rotation: the right child replaces the original node, the replacement’s left subtree becomes the original node’s right subtree, and the original node becomes the replacement’s left child. That interpretation is inferred intent. The established behavior is the sequence of four-byte reads and writes described below; no tree validation, balancing, allocation, or ownership transfer is shown.

The operation has no return value. Its result is expressed through mutations to caller-accessible memory.

## Behavior

### Ordered memory operations

The following order is established at the source-operation level. It is not a promise about individual machine instructions, atomicity, or hardware-visible access counts.

1. **Select the replacement.**  
   Read the original node’s four-byte field at offset `0x0C`. Retain that value as the replacement-node address for the remainder of the operation.

2. **Move a downward link to the original node.**  
   Read the replacement node’s field at offset `0x08`. Write that four-byte value to the original node’s field at offset `0x0C`.

3. **Conditionally repair the moved node’s parent link.**  
   Read the replacement node’s `0x08` field again and compare the value with zero.

   If it is nonzero, read that field again to obtain the destination address, then write the original-node address to the destination’s field at offset `0x04`.

   If the tested value is zero, omit this parent-link write.

   The condition and destination are obtained through separate source-level reads. The function does not explicitly retain the value from step 2 for these later uses.

4. **Give the replacement the original node’s upward link.**  
   Read the original node’s field at offset `0x04`. Write its value to the replacement node’s field at offset `0x04`.

5. **Locate and inspect the distinguished root slot.**  
   Read the context’s field at offset `0x10` to obtain the anchor address. Read the anchor’s field at offset `0x04` and compare it with the original-node address.

6. **Reconnect the replacement from above.**

   - If the root slot equals the original-node address, write the replacement-node address to that root slot. Do not perform the parent-link selection described in the other branch.
   - Otherwise, read the original node’s `0x04` field again to obtain its parent address. Read that parent’s field at offset `0x08`.
     - If the parent’s `0x08` field equals the original-node address, write the replacement-node address to that field.
     - Otherwise, write the replacement-node address to the parent’s field at offset `0x0C`.

   The final alternative is unconditional once the first-link comparison fails. The function does not check that the parent’s `0x0C` field actually references the original node.

7. **Place the original node below the replacement.**  
   Write the original-node address to the replacement node’s field at offset `0x08`.

8. **Complete the original node’s upward link.**  
   Write the replacement-node address to the original node’s field at offset `0x04`.

The function then returns without a value.

### Result under ordinary, stable storage

When the relevant objects are distinct, the structure is well formed, and no outside mutation occurs:

- The original node’s former second child becomes the replacement node.
- The replacement’s former first child becomes the original node’s second child.
- If that transferred child is nonzero, its parent becomes the original node.
- The replacement receives the original node’s former parent reference.
- The root slot or the original parent’s selected child link now references the replacement.
- The replacement’s first child becomes the original node.
- The original node’s parent becomes the replacement.

The original node’s first-child field and the replacement node’s second-child field are not directly written.

These structural postconditions depend on the stated preconditions. They are not unconditional guarantees for overlapping objects or inconsistent links.

### Branch precedence and inconsistent input

Root-slot equality has precedence over parent-link selection. If the root slot equals the original node, the function updates the root slot even if other links suggest a different structural relationship.

In the non-root branch, equality of the parent’s first link has precedence. If both parent links reference the original node, only the first link is replaced.

If neither parent link references the original node, the second link is nevertheless overwritten. No inconsistency is reported.

## Side effects

### Writes

For ordinary distinct storage, the operation performs five unconditional four-byte writes:

1. Original node, offset `0x0C`.
2. Replacement node, offset `0x04`.
3. Exactly one selected attachment slot: root slot, parent offset `0x08`, or parent offset `0x0C`.
4. Replacement node, offset `0x08`.
5. Original node, offset `0x04`.

It performs one additional four-byte write when the transferred-node condition is nonzero: the selected destination’s field at offset `0x04`.

The source does not write the context’s `0x10` field. It reads that field to locate the root slot.

### Intermediate states and failures

The operation is not transactional. It changes the original node’s downward link before updating the replacement’s parent or its attachment from above. It updates the attachment before completing the final two node-link writes.

No rollback, lock, synchronization, error return, or explicit exception handling is shown. If an access fails after earlier writes have completed, the source provides no restoration mechanism. The exact fault behavior and the state observable after a fault are environment-dependent and remain undocumented here.

- The parent’s second link is not directly written.

### Non-root node selected through the fallback branch

Initially, the root slot differs from the original-node address, and the parent’s first link does not reference the original node.

Expected result: the parent’s second link is overwritten with the replacement-node address. This is the selected behavior whether or not that second link previously referenced the original node.

### Zero transferred child

Initially, the replacement’s first link is zero and remains stable through the relevant reads.

Expected result:

- Zero is written to the original node’s second link.
- No transferred-node parent-field write occurs.
- Root or parent reconnection and the final two link writes still occur.

A zero transferred child is supported by an explicit branch. A zero replacement node is not.

### Both parent links reference the original node

Initially, the root slot differs from the original node, and both parent links reference it.

Expected result: only the parent’s first link is changed to the replacement. The second link remains unchanged by the attachment step. The function does not diagnose or repair the duplicate reference.
