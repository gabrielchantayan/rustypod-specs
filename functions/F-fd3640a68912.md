# F-fd3640a68912

## Purpose

F-fd3640a68912 conditionally returns a 32-bit entry from an owner-associated table. It derives a candidate position from either an associated-object lookup or the owner’s current entry count, applies mode-dependent position adjustment, checks eligibility, optionally reverses the position, and accesses a selector-specific table. A missing table may trigger a preparation dependency before the access is retried.

The function returns zero on numerous rejection paths. Some rejected positions also clear a bit in the owner’s state. A particular position-wrap path may invoke two additional dependencies.

**Inferred intent:** the function appears to select a preceding or boundary-relative entry, with configurable wrapping and reversed table ordering. The meanings of the entries, modes, and selector are not established.

## Interface

### Arguments

The interface has five arguments:

| Argument | Observed representation | Role |
|---|---|---|
| Owner | 32-bit address-valued argument | Provides count metadata, mode, state flags, and selector-specific table pointers. |
| Associated object | 32-bit argument | Zero selects a count-based path; nonzero is passed to an association dependency. |
| Selector | 32-bit argument | Passed to position resolution and used to address an owner table-pointer slot. Zero prevents entry retrieval after the second availability check. |
| Reverse control | 8-bit character value | Any nonzero value enables reversal of the accepted candidate position. |
| Control mask | Unsigned 8-bit value | Bits `0x01`, `0x02`, and `0x04` affect specific branches. Other bits have no direct effect in this function. |

The return value is one 32-bit word. Zero is both the function’s rejection/unavailability result and a possible table-entry value; the interface does not distinguish these cases.

### Preconditions and ownership

For every path that accesses owner fields, those fields and any followed pointers must be readable. The rejection-state update additionally requires a writable state-flags byte.

A zero owner is **not** generally supported. The function avoids dereferencing it during count reads, but other paths still dereference owner-relative fields. For example, with a successful initial availability check and a zero associated object, a zero owner eventually reaches a state-flags access.

The selector is not range-checked. Beyond its zero check, it is used directly in address formation. Callers must ensure that the resulting table-pointer slot is valid and that address arithmetic and table indexing address the intended storage.

No direct allocation, deallocation, or ownership transfer is visible. The returned word is not established to be a pointer or an owned resource. Dependencies may have additional ownership effects; these are unknown.

## Behavior

### 1. Initial availability and count snapshot

The function first calls **F-3b037d560480** without arguments.

- If it returns zero, the function returns zero immediately.
- No owner-field access is visible before this call.

After a nonzero result, the function obtains the **initial count**:

- A zero owner produces an initial count of zero without following the metadata pointer.
- Otherwise, it reads the metadata pointer at owner `+0x40`, then the unsigned 16-bit count at metadata `+0x2e`.

This initial count remains the bound used by the first candidate eligibility comparison. Later count reads do not replace that saved bound.

### 2. Candidate derivation

#### Zero associated object

When the associated object is zero, the candidate becomes initial count minus one using 32-bit arithmetic.

The function then enters the common negative-position check. This path does not call the association or position-resolution dependencies and does not inspect the mode field.

#### Nonzero associated object

The function calls **F-6ef0016a253f** with the owner and associated object.

- A zero result causes an immediate zero return.
- Otherwise, that result and the selector are passed to **F-6fa4e01d8d29**.

The 32-bit result of F-6fa4e01d8d29 becomes the candidate.

Only after these dependencies return does the function read the owner’s state and, conditionally, its mode. Consequently, dependency-induced changes to those fields can affect the following adjustment.

### 3. Mode-dependent adjustment

The function first tests state bit `0x08`.

- If it is set, the candidate is decremented once.
- If it is clear, the signed 16-bit mode is read.

The mode cases, when bit `0x08` is clear, are:

| Mode | Adjustment |
|---|---|
| `0` | Decrement candidate once. |
| `1` | Decrement candidate once, then apply the special wrap behavior below. |
| `2` | Decrement only when control bit `0x04` is set. Otherwise retain the candidate. |
| Any other signed 16-bit value | Return zero immediately. |

An unsupported mode returns without the common rejected-position state update.

#### Mode 1 special handling

After the decrement:

- If control bit `0x02` is set, do not wrap. Continue to the common negative-position check.
- If control bit `0x02` is clear and the decremented candidate is nonnegative as a signed 32-bit value, retain it.
- If control bit `0x02` is clear and the candidate is negative, reload the count through the owner metadata pointer and set the candidate to that refreshed count minus one.

This wrap-time count reload does **not** replace the initial count used by the first upper-bound comparison.

After assigning the wrapped candidate, the function conditionally performs additional calls:

1. Read state bit `0x01`.
2. If that bit and control bit `0x01` are both set, call **F-8a6c49c858cd** with the owner and a literal zero.
3. If that dependency returns nonzero, call **F-df1f4510064d** without arguments.

The return from F-df1f4510064d is not used. These calls occur before checking whether the wrapped candidate is negative or outside the initial count.

### 4. First candidate eligibility check

The candidate must be nonnegative under signed 32-bit interpretation and strictly less than the initial count under signed comparison.

For the mode-1 path that retains a nonnegative decremented candidate, nonnegativity has already been established. Other relevant paths explicitly check for a negative candidate before the upper-bound comparison.

A negative candidate or one at least as large as the initial count enters the rejected-position state path:

- Read the owner state-flags byte.
- If state bit `0x01` and control bit `0x01` are both set, clear state bit `0x04`.
- Return zero.

The write preserves the other bits of the state-flags byte used for that update. The update expression reads the state byte again after the condition succeeds; the function does not establish an atomic read-modify-write guarantee.

### 5. Second availability check and refreshed bound

For a candidate that passes the first comparison, the function calls **F-3b037d560480** again.

If that result is zero, or if the selector is zero, the function returns zero. The second availability call still occurs when the selector is zero.

Otherwise, the function reloads the metadata count, again treating a zero owner as a count of zero. It compares the candidate against this **retrieval count** using an unsigned comparison.

- If the candidate is not strictly below the retrieval count, return zero.
- This rejection does not execute the rejected-position state update.

Thus, a candidate must satisfy both the saved initial bound and this later bound. Count growth after the initial snapshot cannot rescue a candidate that already failed the first comparison; count shrinkage can reject one that passed it.

### 6. Position reversal and entry retrieval

After the refreshed unsigned bound check succeeds, the function calls **F-3dfc1640191e** with the owner and two addresses of temporary storage.

The visible function does not consume the contents written to those temporary locations. The dependency’s return value is not used. Its other effects are unknown.

If reverse control is nonzero, the candidate is replaced by:

\[
\text{retrieval count} - \text{candidate} - 1
\]

The retrieval count is the snapshot obtained **before** F-3dfc1640191e. There is no further count reload or bound check after that call.

The function then accesses the selector-specific table pointer:

- If the slot is nonzero, proceed directly to entry retrieval.
- If it is zero, call **F-60950fd9e511** with the owner, then reread the slot.
- If the slot is still zero, return zero.
- Otherwise, return the 32-bit word at table `+0x10 + 4 × candidate`.

The table pointer is read again for the final entry access. The function does not explicitly retain one table-pointer snapshot across the nonzero check and final dereference.

## Side effects

### Direct memory effects

The only explicit nonlocal write is clearing state bit `0x04` on the rejected-position path, conditional on both the owner and control bit `0x01` being set.

Other paths returning zero do not perform that particular update merely because they failed. These include:

- Either availability dependency returning zero.
- Association lookup returning zero.
- Unsupported mode.
- A zero selector after the second availability call.
- Failure against the refreshed count.
- A table slot remaining zero after preparation.

### Dependency-mediated effects

Dependencies can execute before later rejection, including:

- Association and position resolution before mode rejection.
- Wrap-related calls before a wrapped candidate fails its bounds.
- The second availability check before selector-zero rejection.
- F-3dfc1640191e before table availability is known.
- F-60950fd9e511 before a final zero result caused by an absent table.

No preservation of owner fields, global state, table contents, or memory ownership is established for these calls. In particular, the function’s saved counts and candidate may coexist with owner state modified by a dependency.

No explicit exception, diagnostic, or status object is produced. Invalid memory access behavior is not specified by the supplied evidence.
