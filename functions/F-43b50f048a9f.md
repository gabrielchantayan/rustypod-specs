# F-43b50f048a9f

## Purpose

F-43b50f048a9f builds or extends a code-indexed record table while composing corresponding content into a destination resource. It combines a caller-supplied prefix of existing records with additional records obtained through an indirectly referenced object.

The observable contract includes:

- A 16-bit mapping from scanned code values to record indices, with `0xffff` used for rejected entries.
- Twenty-byte records whose first two words describe accumulated horizontal positions for successfully processed additional entries.
- Calls that prepare, transform, compose, and release temporary resource views.
- An optional final operation that copies the existing-record prefix and composes an additional caller-supplied resource.
- A returned status controlled by the additional-entry processing callback, not a count of accepted entries.

These structural effects are established by the supplied static evidence. Interpreting the resources as graphical surfaces and the records as glyph-like metrics is inferred intent, not a required semantic interpretation.

Each mapping entry occupies two bytes. The entry for a scanned code is addressed relative to the descriptor’s starting code. Accepted entries receive the low 16 bits of the current record index; rejected entries receive `0xffff`.

A record occupies 20 bytes. Its first two 32-bit words are treated as position-like endpoints. The remaining 12 bytes are copied but not directly interpreted by this function.

The return value is a signed 32-bit status:

- Initially `1`.
- Replaced by each result from the additional-entry processing operation.
- Returned as `0` if that operation returns zero and stops the scan.
- Otherwise returned as the latest nonzero result, or `1` if that operation was never invoked.

A nonzero return therefore does not necessarily equal `1`, and it does not report how many records were produced.

**Preconditions:** All addresses actually accessed must be valid for their respective reads, writes, and indirect calls. Buffer capacity, valid resource references, suitable object layout, and compatible dependency calling conventions are caller obligations. There are no visible null checks, bounds checks, allocation-failure branches, or structured error objects.

## Behavior

### Preparation

Before scanning codes, the function prepares two resource contexts.

First, it creates a four-word region description containing zero, zero, argument 4, and argument 3. It calls F-634f9fbe35da with the descriptor’s destination resource, that description, argument 5, and two zero arguments.

It then:

1. Calls F-970cd717d3d2 on the destination resource.
2. Initializes a destination view through F-1ade66241a82.
3. Reads the object currently referenced through argument 1.
4. Reads the signed 16-bit value at object byte offset 80 and sign-extends it to 32 bits.
5. Forms another four-word description containing zero, zero, argument 4, and that signed value.
6. Calls F-cec144b59c0b to prepare a temporary resource using that description, argument 5, and two zero arguments.
7. Initializes a second view over the temporary resource through F-1ade66241a82.

These operations precede all mapping writes. Their return values, where any exist, are not visibly tested.

The scan cursor begins at the descriptor’s unsigned 16-bit starting code. The accepted-record index and accumulated endpoint both begin at zero.

### Existing-record prefix scan

The first scan continues while the accepted-record index is less than argument 10. It is **not bounded by the descriptor’s upper code bound**.

For each current code:

1. F-88658862e573 is called with argument 2 and the current code shifted right by five.
2. If the result is zero, the corresponding mapping entry is written as `0xffff`.
3. Otherwise:
   - F-008d77a63c85 is called with argument 2, the current code, and zero.
   - The mapping entry is written with the current accepted-record index, narrowed to 16 bits.
   - The first two words of the corresponding record in argument 9 are read.
   - Their difference is added to the accumulated endpoint.
   - The accepted-record index advances using the masking rule below.
4. The code cursor advances using the same masking rule.

This phase does not copy the existing records into the output-record array. Its direct table effect is the mapping; its accumulated endpoint is used by later composition.

There is an important static ambiguity: this call to F-88658862e573 visibly supplies two arguments, whereas the second scan visibly supplies three. A contract for the dependency’s actual ABI cannot be recovered here. In particular, the first scan cannot be specified as definitively testing the individual code’s low-five-bit position.

### Counter arithmetic and termination

Both counters advance by adding one and applying the 32-bit mask `0xfffeffff`.

This clears bit 16; it is not a general conversion to 16 bits. Because the local counters begin within the unsigned 16-bit range, their ordinary sequence cycles from `65535` back to `0`.

Consequences include:

- Argument 10 greater than `65535` cannot be reached by this locally maintained accepted-record index.
- A first scan that never obtains enough nonzero lookup results has no explicit termination safeguard.
- The first scan may continue beyond the descriptor’s upper bound.
- A second scan whose stable upper bound is `65535` does not terminate by cursor exhaustion; it requires a zero processing result or some relevant external state change.

These are observable control-flow properties, not validated input cases.

### Additional-record scan

After the prefix scan, the function scans while the current code is less than or equal to the descriptor’s current upper bound.

For each code:

1. F-acff1e21fa9a is called with the address of a temporary 20-byte record.
2. F-88658862e573 is called with argument 2, the code shifted right by five, and the code’s low five bits.
3. If that lookup returns zero, the mapping entry is set to `0xffff`.
4. Otherwise, an indirect object operation is invoked through dispatch-table byte offset 12. It receives the current object, current code, and temporary record.
5. If that operation returns zero, the mapping entry is set to `0xffff`.
6. If both operations return nonzero, processing continues as described below.

Rejected entries do not advance the accepted-record index or accumulated endpoint. The temporary-record initializer still runs for every second-phase iteration, including rejected entries.

For an accepted entry, ordering is significant:

1. F-008d77a63c85 is called with argument 2, the current code, and zero.
2. The mapping entry is written with the current accepted-record index.
3. The output-record address is computed from the descriptor’s output-record base and that index.
4. Twenty bytes are copied from the temporary record into the output record.
5. F-970cd717d3d2 is called on the temporary resource.
6. An indirect operation through dispatch-table byte offset 60 is invoked on the object then referenced by argument 1. It receives the temporary record, current code, and two 32-bit fields from the prepared temporary resource.
7. Its result replaces the function’s return status.

If this processing result is zero, scanning stops immediately. The function does **not** undo the mapping write, state-update call, or 20-byte record copy. It also does not advance the accepted-record index or accumulated endpoint for that entry.

On a nonzero result:

- The width is computed as the temporary record’s second 32-bit word minus its first.
- Two fresh four-word region descriptions are formed, each initially containing zero, zero, argument 4, and that width.
- F-d156b0b83eb3 is called on the destination-side description with the accumulated endpoint and zero.
- F-b774eb6cb163 is called with the destination view, temporary-resource view, both descriptions, `255`, and zero.
- The already selected output record’s first word is replaced by the old accumulated endpoint.
- The width is added to that endpoint.
- The accepted-record index advances using the mask rule.
- The output record’s second word is replaced by the new accumulated endpoint.

The remaining 12 output-record bytes remain those copied before the processing operation, except for effects that dependencies or aliases may independently introduce.

The width is read **after** the processing operation. If that operation modifies the temporary record, the width used for placement may differ from the first two words originally copied into the output record.

### Optional final copy and composition

When argument 7 is nonzero, the following block runs after either normal scan completion or a zero processing result:

1. Copy `argument 10 × 20` bytes from argument 9 to the descriptor’s current output-record base.
2. Form two descriptions containing zero, zero, argument 4, and argument 8.
3. Initialize a view over argument 7 through F-1ade66241a82.
4. Compose it into the destination view through F-b774eb6cb163, using the descriptions, `255`, and zero.
5. Release that optional view through F-282eebd7c413.

Thus this block is not success-only behavior. A return value of zero does not imply that the optional copy or composition was skipped.

When argument 7 is zero, neither the prefix copy nor this optional composition occurs.

### Final cleanup

On the visible normal control-flow paths, cleanup occurs in this order:

1. Release the temporary-resource view through F-282eebd7c413.
2. Pass the prepared temporary resource to F-03144a4f049b.
3. Release the destination view through F-282eebd7c413.
4. Return the retained status.

No exception, fault, or nonlocal-exit cleanup behavior is established.

## Side effects

Direct persistent writes are made to the mapping and output-record arrays. Dependency calls may additionally modify the lookup state, destination resource, temporary resource, referenced object, or other state.

There is no transactional guarantee:

- Rejections overwrite mapping entries.
- Accepted entries update lookup state before record processing completes.
- A failed processing operation leaves a mapped, copied record behind.
- Successful entries may already have been composed before a later failure.
- The optional final operation still runs after a processing failure.

The implementation repeatedly reads descriptor fields and the object-reference slot rather than establishing an immutable snapshot. It also retains some derived pointers and prepared views across dependency calls. In particular, an output-record pointer selected before processing is reused for subsequent endpoint writes.

Accordingly, dependencies must not be assumed to preserve globals, descriptor contents, object identity, or memory validity. If they alter these inputs, later accesses may use different bases or objects while earlier cached references remain in use.

No direct allocation or direct release of caller-provided arrays is visible. Temporary resource ownership, reference acquisition, and destruction semantics are dependency-defined. Cleanup-shaped calls do not by themselves establish ownership transfer.

Arithmetic is 32-bit in the supplied representation. No overflow checks are present for endpoint differences, accumulated endpoints, address-offset calculations, or the optional copy-size multiplication. A negative record width is not explicitly rejected. Exact overflow semantics require confirmation of the execution model; this contract does not substitute mathematical unbounded arithmetic.

## Acceptance examples

These examples are conditional on valid memory, compatible dependencies, and no unmentioned mutation of inputs.

1. **No prefix and an empty interval.** With argument 10 equal to zero, starting code greater than the upper bound, and argument 7 zero, neither scan writes mapping entries or records. Preparation and final cleanup still occur. The return is `1`.

2. **Two existing records with widths 3 and 5.** Suppose argument 10 is two and the first three prefix lookup results are nonzero, zero, nonzero. The three mapping entries become `0`, `0xffff`, and `1`. The accumulated endpoint becomes eight. The next phase begins at the following code. Existing records are not copied merely because this prefix scan succeeded.

3. **Successful additional record.** Suppose the current record index is two, the accumulated endpoint is eight, and the post-processing temporary endpoints are four and eleven. If processing returns seven, composition uses width seven. Output record two ends with endpoints eight and fifteen, the next record index is three, and the retained status becomes seven.

4. **Processing failure after acceptance.** If lookup and record retrieval succeed but processing returns zero, the mapping and initial 20-byte copy remain. No composition or endpoint rewriting occurs for that entry. Scanning stops, optional final work still runs if enabled, and the return is zero.

5. **Rejected additional code.** A zero lookup or zero record-retrieval result writes `0xffff`; it does not increment the record index or endpoint. No processing call is made for that code.

6. **Upper bound `65535`.** With no processing failures and stable inputs, reaching code `65535` causes the next code to become zero. The second scan does not finish by exceeding that bound.
