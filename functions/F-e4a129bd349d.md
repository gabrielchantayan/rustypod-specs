# F-e4a129bd349d

## Purpose

F-e4a129bd349d conditionally requests storage, invokes a three-argument transfer dependency, and writes a zero byte. It returns a 64-bit value combining a 32-bit status cell and a retained 32-bit storage-request result.

The established sequence is:

1. Capture a context-associated word.
2. Invoke F-bb77071485ff with writable data and length cells.
3. If its return is zero, invoke F-3ce007b692cc with an incremented length and a writable status cell.
4. If that status cell is zero immediately after the storage request, invoke the transfer dependency and then write a zero byte.
5. After either storage-request status outcome, invoke F-0d113f438a9d.
6. Read the status cell for the upper half of the return value.

The apparent intent is to obtain a zero-terminated copy of helper-provided data and then finalize the helper-provided data state. That interpretation is inferred. Exact transfer semantics, ownership, release behavior, and preservation of the destination contents are not established.

The writable cells are important to the contract. Dependencies receive their addresses and could expose those addresses to later dependencies while this invocation remains active. Consequently, a branch decision, a transfer length, a terminator position, and the final status can reflect different observations of mutable state.

## Interface

### Inputs

The visible interface uses four arguments in a 32-bit addressing model.

| Argument | Representation | Established use |
|---|---|---|
| Context reference | Address of a readable 32-bit word | Used for an initial indirect lookup; passed unchanged as an argument value to F-bb77071485ff and F-0d113f438a9d. |
| Input word | 32-bit integer | Passed by value to F-bb77071485ff. Its meaning is unknown. |
| Initial length | Signed 32-bit integer in the supplied representation | Initializes a writable length cell. |
| Initial data word | Opaque 32-bit word | Initializes a writable data cell. |

Before any dependency call, the function reads the word addressed by the context reference, treats it as a base address, and reads a 32-bit word at byte offset 28 from that base. This second word is captured for the later storage request.

Both reads must be valid for execution to reach the first dependency normally. A subsequent first-stage failure does not bypass them. No null, alignment, bounds, or address-validity checks are visible.

### Output

The return value is a 64-bit bit pattern:

| Bits | Contents |
|---|---|
| 63–32 | The status cell’s 32-bit value when read for the return |
| 31–0 | The retained 32-bit return from F-3ce007b692cc, or zero if that dependency was not called |

Composition preserves the two 32-bit patterns. It is not a signed arithmetic combination.

The lower field starts at zero. Once F-3ce007b692cc returns, its result replaces that field regardless of its reported status. The function does not subsequently replace the lower field merely because another dependency changes status or data.

The upper field is **not necessarily the status observed immediately after F-3ce007b692cc**. That dependency receives the status cell’s address and could make it accessible to later dependencies. The return reads the cell after the transfer path, if taken, and after F-0d113f438a9d.

Therefore:

- On first-stage failure, the upper field is the nonzero first-stage return on the ordinary sequential path; no later dependency is called.
- On the storage-request path, the upper field is the status cell’s value after the subsequent operations have returned.
- Zero in the upper field does not by itself prove that the transfer branch ran.
- A nonzero upper field does not by itself prove that the transfer branch was skipped.

No independent overall-success flag is produced.

## Behavior

### Initial capture and first dependency

The context-associated word is captured before F-bb77071485ff runs. The function does not reread the context chain to obtain the storage-request argument.

The data and length arguments initialize distinct writable 32-bit cells. F-bb77071485ff receives:

- The original context reference.
- The input word by value.
- The data cell’s address.
- The length cell’s address.

Its 32-bit return is assigned to the status cell.

If that return is nonzero, no storage request, transfer call, explicit zero-byte store, or finalization call occurs. The retained lower return field remains zero. No explicit rollback of the first dependency’s effects is performed.

If its return is zero, execution continues to the storage request. The data and length cells may already differ from their initial arguments.

### Storage request and branch decision

F-3ce007b692cc receives:

- The previously captured context-associated word.
- The length observed for this call, incremented by one.
- The status cell’s address.

The status cell is zero when this call begins because the first dependency returned zero.

The storage-request return is retained independently of status. After the call returns, the function reads the status cell to decide whether to perform the transfer and byte store:

- Zero selects that path.
- Nonzero skips both operations.

If F-3ce007b692cc leaves the status cell unchanged, the transfer path is selected. The function does not validate the returned destination word independently.

This branch decision is made once. A later change to status does not retroactively change which branch was taken, and no second status check precedes the byte store.

### Separate length and data observations

The supplied body establishes three distinct length observation points:

| Observation | Use |
|---|---|
| Before F-3ce007b692cc | Form the requested size by adding one. |
| After F-3ce007b692cc, if its status is zero | Supply the transfer dependency’s length argument. |
| After the transfer dependency returns | Compute the explicit zero-byte store address. |

These values are not guaranteed to match.

F-bb77071485ff receives the length cell’s address. It could expose that address through shared state or another mechanism. F-3ce007b692cc and the transfer dependency could consequently modify the cell during this invocation even though neither receives it directly in its visible argument list.

The same concern applies to the data cell. Its transfer argument is the value observed after the storage request, not necessarily the value initially supplied or the value immediately left by F-bb77071485ff.

These are valid within-frame aliasing possibilities, distinct from the separate issue of accessing expired stack storage after return. The evidence does not establish that such exposure occurs, but it also supplies no dependency contract excluding it.

The source does not establish a required relative evaluation order among arguments of an individual call. The relevant guarantees are the observation stages separated by dependency calls.

### Transfer and explicit termination

If the post-storage-request status is zero, the unidentified transfer dependency receives:

1. The retained destination word.
2. The then-current data word.
3. The then-current length.

Its return value is ignored.

After it returns normally, the function reads the length again and writes one zero byte at the retained destination plus that length.

The directly established behavior is a three-argument call followed by a byte store. An exact copy of the specified number of bytes is not established without the transfer dependency’s contract.

The zero-byte store occurs even if the transfer dependency has changed the status cell to a nonzero value. Conversely, a transfer-time length change affects the store position but cannot change the length argument already passed to that transfer call.

The store is an observable event, not an unconditional guarantee about memory at function return. F-0d113f438a9d runs afterward and has unknown memory effects. It could alter or invalidate the destination if a separate dependency contract permits that behavior.

### Finalization and final status

After a normally returning storage request and any selected transfer/store operations, F-0d113f438a9d is invoked with:

- The original context-reference argument value.
- The data cell’s address.

It runs after both zero and nonzero storage-request statuses. Its return value is ignored.

The data cell is not explicitly inspected afterward. However, the status cell is read afterward to form the return value. If a prior dependency exposed the status address, F-0d113f438a9d could change that cell despite not receiving it directly.

Thus, finalization can affect the returned upper field without affecting the already-completed branch decision. It can also change memory or shared state; the body does not establish preservation guarantees.

There is no visible exception handling or fault recovery. Finalization is not guaranteed after a dependency fails to return normally or after an invalid transfer or byte-store access.

### Widths and arithmetic

The relevant words and arithmetic operands are 32 bits in the supplied representation. The length is represented as signed.

For a length from zero through 2,147,483,646, adding one remains within the signed 32-bit range. At 2,147,483,647, the increment exceeds that range. No explicit widening, overflow check, or rejection is shown.

The evidence does not settle language-level versus machine-level overflow behavior. It therefore does not establish a wraparound contract.

Negative lengths are not rejected. They affect the size expression, transfer argument, and destination-relative byte-store position according to their values at the respective observation points. Dependency interpretation and address-arithmetic behavior outside valid ranges remain unknown.

Safe successful execution requires valid arithmetic and memory access at each stage. The requested size alone does not prove sufficient capacity for a later, potentially changed transfer length or terminator position.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Examples requiring normal completion also require valid accesses and normally returning dependencies.

1. **First-stage failure**

   Given valid initial context reads, if F-bb77071485ff returns 9, no later dependency is called. On the ordinary sequential path, the returned upper field is 9 and the lower field is zero.

2. **Stable ordinary success**

   Suppose F-bb77071485ff returns zero with length 3. Assume the length remains 3 through the storage request and transfer. F-3ce007b692cc must receive size 4. If it returns a destination and leaves status zero, the transfer must receive that destination, the data word observed for that call, and length 3. After transfer returns, the explicit store must write zero at destination plus 3, followed by F-0d113f438a9d.

   The lower return field must retain the destination. The upper field is zero only if intervening dependencies leave the status cell zero. Destination contents at return additionally depend on later dependencies preserving them.

3. **Storage-request failure with a retained result**

   Suppose F-3ce007b692cc returns a nonzero destination word and writes status 7. The transfer and explicit terminator store must be skipped. F-0d113f438a9d must still run.

   The lower field must retain that returned word. The upper field is 7 only if the status cell remains 7 through finalization. If finalization changes the exposed status cell to zero, the upper field must instead be zero, without any transfer having occurred.

4. **Stable zero length**

   Suppose the first stage succeeds with length zero, and that length remains zero through the storage request and transfer. The requested size must be one. With zero storage-request status, the transfer must still be called with length zero. After its return, the first destination byte must be written as zero, then finalization must run.

   Final status and preservation of that byte at return require the corresponding dependencies to leave them unchanged.

5. **Changing length across stages**

   Suppose the first stage leaves length 3. During the storage request, an exposed length-cell address is used to change it to 5. The requested size is still 4, but a selected transfer must receive length 5. If transfer then changes the cell to 2, the explicit zero store must target destination plus 2.

   This example requires independently valid storage and transfer behavior; the request for size 4 does not establish safety for a transfer of length 5.

6. **Status changes after branch selection**

   Suppose the storage request leaves status zero, selecting transfer. If transfer changes the exposed status cell to 11, the byte store must still occur after transfer returns. If finalization then changes status to 12, the upper return field must be 12.

7. **Context mutation**

   If the first dependency changes the context-associated field, the storage request must nevertheless receive the word captured before that dependency. Resource validity after the mutation is a separate precondition.

8. **Unusable destination**

   If the storage request leaves zero status but returns an unusable destination, no additional destination check is performed. Successful transfer, termination, finalization, and return are not guaranteed.
