# F-4394984c4257

## Purpose

The supplied static representation establishes an ordered sequence of indirect calls, 32-bit arithmetic, byte accesses, and four-byte word accesses. It does not establish an application-level purpose.

This contract describes the visible behavior conditionally: each operation is reached only if preceding calls return and preceding memory accesses complete. The represented path terminates at an invalid-instruction boundary, not a demonstrated normal return.

The contract preserves direct accesses to low absolute addresses and distinguishes captured values from later memory reads. It does not reinterpret suspicious addresses as ordinary object fields or assume that dependencies preserve memory.

### Widths and notation

A **word** is 32 bits; a byte is 8 bits. The following notation describes represented machine-word calculations:

- \(w(x)\): the low 32 bits of \(x\).
- \(b(x)\): the low 8 bits of \(x\).
- \(s_n(x)=w(x\,2^n)\).
- \(m(x)=x\mathbin{\&}\texttt{0x3fffffff}\).
- \(\operatorname{lo}(x)\), \(\operatorname{hi}(x)\): the low and high 32-bit halves of a represented 64-bit result.

Address sums and scaled address calculations use \(w\) unless their explicitly bounded operands make wrapping impossible. Right shifts used below are logical shifts of unsigned words or zero-extended bytes.

Some represented calculations involve signed multiplication or left shifts. Modulo-\(2^{32}\) notation describes their apparent machine-word effect, not a claim of portable signed-language semantics. Exact behavior at signed overflow or negative left-shift operands remains unresolved without instruction-level confirmation.

A word access covers four bytes. Endianness, alignment requirements, and address-space semantics are not established.

### Preconditions for completing the visible path

Completion requires callable indirect targets, compatible execution state, returning dependencies, and accessible memory for every reached read and write. Any required memory lifetime must survive intervening dependency effects.

These are conditions on execution, not validations performed by the function. No visible checks establish them.

## Behavior

### Call-block notation

**F-D001** through **F-D028** identify ordered call blocks, not necessarily distinct callable functions.

Unless another profile is stated, a block consists of an initial call with the listed arguments followed by four calls with no explicit argument expressions. Its named result is the final call’s result.

A **short block** consists of the listed argument-bearing call followed by one call without explicit arguments. **F-D011** and **F-D025** each contain three calls without explicit arguments. **F-D018** contains one argument-bearing call only.

“No explicit arguments” describes the supplied representation. It does not establish a true zero-argument signature or exclude consumption of live register, stack, or global state.

The following subsections specify the order of direct accesses and calls. All named results are captured specification values. Repeated reads remain distinct even when their address expressions are equal.

## Side effects

Repeated offsets do not establish a common structure layout. Their bases arise from different captured results and arithmetic. Absolute addresses `0x0d` and `0x11`, and byte-indexed destinations in `0x11`–`0x110`, remain literal represented addresses.

No disjointness is established among accessed regions. Aliasing may make earlier writes affect later reads. Calls between accesses may also change memory, so neither repeated writes nor repeated reads may be collapsed merely because their address expressions match.

No ownership transfer, borrowing discipline, or lifetime guarantee is established. Dependencies may allocate, release, retain arguments, modify globals, or alter accessed memory; their behavior is unknown. Passing a word does not establish that it is a valid pointer.

## Acceptance examples

These are conditional static obligations, not executed tests.

1. **Early masking can be behaviorally equivalent.**  
   For **B** = `0xc0000005`, **B₄** is `0x14`, the store address \(w(16B+\texttt{0x14})\) is `0x64`, **Bₘ** is `5`, and **Bq** is `1`. Using **Bₘ** for those two scaled calculations produces the same value and address. This example documents calculation order but does not distinguish implementations that normalize earlier.

2. **Byte truncation does not truncate an address calculation.**  
   For **C** = `0x23`, **C₈** is `0x118`. The corresponding byte stores write `0x18`, while the word-field address \(C_8+\texttt{0x34}\) is `0x14c`, not `0x4c`.

3. **Intervening effects require a fresh read.**  
   If the first read at \(w(M_{32}+1)\) yields `3`, its indexed write targets `0x14`. If intervening dependencies change that byte to `9`, the later zero write selected by **I** targets `0x1a`.

4. **Captured byte and full shifted word differ.**  
   For **O** = `0x12345678`, **Oᵦ** is `0xcf`, while \(O\gg3\) is `0x02468acf`. The later word store uses the latter.

5. **Final clearing destinations may differ.**  
   If the two reads at **Yₐ** yield `0xff` and `0`, their zero stores target `0x110` and `0x11`, respectively.

6. **Equal numeric targets do not establish equal interfaces.**  
   The two identified calls targeting `0x0882ff03` satisfy represented address equality. Acceptance does not require assuming identical return layouts or confirmed executable behavior.

7. **Failure does not imply rollback.**  
   If a dependency does not return after a completed store, later operations are not reached. No visible behavior requires restoring the earlier contents.
