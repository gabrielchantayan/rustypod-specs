# F-47d20836978f

## Purpose

F-47d20836978f obtains one 20-byte record from a caller-supplied allocation state and partially clears that record. It first uses an available-record chain, otherwise consumes the next record from a contiguous region. If that region is exhausted, it requests a new region and a 12-byte descriptor through F-871e64ddc6de.

The function has no explicit return value. Its observable results are changes to the allocation state, any newly created descriptor, and the selected record.

**Established static evidence:** the selection precedence, allocation requests, arithmetic, and writes described below are directly supported by the supplied function.

**Inferred intent:** the state appears to manage reusable records backed by a chain of allocated regions. Descriptions such as “available-record chain,” “cursor,” and “capacity” name apparent roles; they do not establish contracts for other functions.

**Unknown:** how callers identify or subsequently use the selected record. This function does not explicitly publish a selected-record pointer through a return value or a dedicated output field.

## Interface

### Input state

The sole argument is an address of mutable state containing at least four consecutive 32-bit words:

| Byte offset | Interpretation in this function |
|---|---|
| 0 | Address of the current region descriptor, or zero |
| 4 | Address of the first available record, or zero |
| 8 | Address of the next unused record in the current region |
| 12 | Address marking the end of the current region |

These are operational interpretations, not independently established type declarations. The supplied representation uses 32-bit integer fields to hold addresses. Portability to an environment with a different address width is not established.

The state pointer is not checked for null. The function also does not validate alignment, region bounds, descriptor consistency, or the integrity of the available-record chain.

### Region descriptor

A descriptor occupies 12 bytes:

| Byte offset | Meaning |
|---|---|
| 0 | Link to a preceding descriptor |
| 4 | Unsigned 32-bit record capacity |
| 8 | Address of record storage |

When growth is required and the state’s descriptor address is nonzero, only the capacity at descriptor offset 4 is needed to choose the requested capacity. Creating the new descriptor also reads the state’s descriptor address again, after both dependency calls, to establish the new link.

### Record layout

A record has a 20-byte stride. This function accesses these portions:

| Byte offset | Width | Use |
|---|---:|---|
| 0 | 1 byte | Cleared after selection |
| 4 | 4 bytes | Cleared after selection |
| 8 | 4 bytes | Cleared after selection |
| 12 | 4 bytes | Available-chain successor when selecting from that chain; then cleared |

Bytes 1–3 and 16–19 are not explicitly written by this function. The implementation does not initialize the entire record.

### Output and validity requirements

There is no explicit result value or error status.

For a normally completing call, all memory actually accessed must be valid for its respective read or write. In particular:

- The four-word state must be accessible.
- A nonzero available-record address must permit a 32-bit read at offset 12 and the record writes listed above.
- On the cursor path, the selected cursor address must permit those record writes.
- On growth, a nonzero existing descriptor must permit reading its capacity.
- Both dependency results must support the uses described below.

These are necessary memory-safety conditions, not checks performed by the function. Conventional, nonoverlapping state, descriptor, and record storage is also needed for the ordinary interpretations below. Deliberate overlap can make earlier writes alter later reads.

## Behavior

### 1. Select from the available-record chain when possible

The function first reads the address at state offset 4.

If that address is nonzero:

1. That address is selected as the record to clear.
2. The 32-bit successor value is read from selected-record offset 12.
3. The successor is written to state offset 4.
4. The selected record is partially cleared in the order specified below.

This branch does not consult the cursor, the region-end field, or the descriptor to decide whether allocation is needed. It makes no dependency calls.

Under nonoverlapping storage, state offsets 0, 8, and 12 remain unchanged. There is no traversal or validation of the successor. A successor equal to the selected record, an address already used elsewhere, or an invalid address is not rejected during this call.

### 2. Otherwise select the cursor

If the initially read available-record address is zero, the function reads the cursor at state offset 8 and compares it with the address at state offset 12.

If they differ:

1. The cursor address already read is selected.
2. The address 20 bytes beyond it is written to state offset 8.
3. The selected record is partially cleared.

The comparison is equality only. The function does not establish that the cursor is below the end, suitably aligned, or separated from the end by at least 20 bytes. A malformed cursor that differs from the end still takes this path.

No dependency call occurs on this path. Under nonoverlapping storage, the descriptor field and region-end field remain unchanged.

### 3. Grow when cursor equals end

If the available-record address is zero and the cursor equals the region end, the function computes a new record capacity.

If the descriptor address at state offset 0 is zero, the capacity is 32 records.

Otherwise, the unsigned 32-bit capacity is read from descriptor offset 4. Let that value be \(C\). Two candidates are computed:

\[
A = C + 32
\]

\[
B = C + (C \mathbin{\mathrm{>>}} 1) + (C \mathbin{\mathrm{>>}} 3)
\]

The additions use unsigned 32-bit arithmetic. Each result therefore wraps modulo \(2^{32}\). The right shifts operate on the unsigned capacity and correspond to division by 2 and 8 with truncation.

The chosen capacity is \(B\) when \(A \leq B\) in unsigned comparison, and \(A\) otherwise. Equivalently, it is the unsigned maximum of the two computed candidates—not the maximum of their unbounded mathematical equivalents.

The function then performs these operations in order:

1. Calls F-871e64ddc6de with arguments 12 and 0, retaining its result as the new descriptor address.
2. Calls F-871e64ddc6de with arguments equal to the new capacity multiplied by 20, and 0, retaining its result as the record-storage address.
3. Writes the record-storage address to new-descriptor offset 8.
4. Reads state offset 0 and writes that value to new-descriptor offset 0.
5. Writes the new capacity to new-descriptor offset 4.
6. Writes the new descriptor address to state offset 0.
7. Reads the storage address from new-descriptor offset 8 and selects it as the record address.
8. Writes the address at that storage base plus capacity times 20 to state offset 12.
9. Writes the selected record address plus 20 to state offset 8.
10. Partially clears the selected record.

The storage-request multiplication is unsigned 32-bit arithmetic and can wrap. The end-address calculation also uses the capacity-times-20 expression; there is no overflow or fit check. Successful storage sufficient for the intended region cannot be inferred merely from the requested capacity.

The read used to link the new descriptor occurs **after both dependency calls**. It is not necessarily the same descriptor address used earlier to obtain the capacity. If the dependency changes the state, the link can reflect that changed state.

### 4. Partially clear the selected record

Every normally completing selection path ends with the following explicit writes, in this order:

1. A 32-bit zero at record offset 4.
2. A 32-bit zero at record offset 8.
3. A 32-bit zero at record offset 12.
4. A one-byte zero at record offset 0.

There is no whole-record clearing operation. In particular, clearing offset 0 does not explicitly clear the other three bytes of the first 32-bit word.

This is the logical access order shown by the supplied representation. Atomicity, synchronization, and externally observable machine-level ordering under concurrent access are not established.

## Side effects

### State transitions

With valid, nonoverlapping storage and no relevant dependency interference:

- **Available-record path:** removes the selected head from the available-record chain by replacing the head with its successor.
- **Cursor path:** advances the cursor by one 20-byte record.
- **Growth path:** installs a new descriptor, sets the end of its storage region, and advances the cursor past the first record in that region.

The selected record is partially cleared on every path.

### Allocation and ownership

The growth path makes exactly two direct calls to F-871e64ddc6de: one for the descriptor and one for the record region.

No explicit deallocation occurs. The new descriptor stores a link to the descriptor address read after the dependency calls. This is consistent with retaining previous regions, but ownership, lifetime, allocator bookkeeping, and eventual release are not established.

The function must not be described as guaranteeing that F-871e64ddc6de preserves globals, leaves the input state untouched, returns distinct allocations, or transfers ownership in any particular way. Those properties are unavailable from the supplied evidence.

### Errors and partial progress

There are no explicit checks for failed dependency results and no explicit error return, rollback, or cleanup.

For example, a zero descriptor result is still used as a write destination after the second call returns. A zero storage result is still stored in the descriptor and subsequently used as the selected-record address. Whether execution faults, terminates inside the dependency, or exhibits another outcome depends on unavailable runtime and dependency behavior.

Mutations precede the record-clearing sequence. An interruption or invalid access can therefore leave an advanced cursor, an updated available-record head, or an installed descriptor without a fully cleared record.

## Acceptance examples

These examples are conditional static expectations, not runtime test results. Unless stated otherwise, assume valid nonoverlapping storage, representable address calculations, and normally returning dependencies with usable results.

### Available record takes precedence

Given a nonzero available-record head with successor address \(S\), the function selects that head, writes \(S\) to state offset 4, and performs the four record-clearing writes.

This remains the selected path even if the cursor equals the end. No growth call is made.

### Cursor consumes one record

Given a zero available-record head, cursor address \(P\), and an end address different from \(P\), the function selects \(P\), writes \(P+20\) to the cursor field, and partially clears the record at \(P\).

It does not verify that \(P+20\) lies within the region.

### First region uses 32 records

Given no available record, cursor equal to end, and a zero descriptor address, the dependency calls receive sizes 12 and 640, each with second argument zero.

If the state remains unchanged during those calls, the new descriptor links to zero, records capacity 32, and stores the returned storage address. The end becomes storage base plus 640; the cursor becomes storage base plus 20.

### Growth can choose either candidate

With existing capacity 32, the additive candidate is 64 and the shift-based candidate is 52. The chosen capacity is 64, yielding a 1,280-byte storage request.

With existing capacity 64, the candidates are 96 and 104. The chosen capacity is 104, yielding a 2,080-byte request.

### Unsigned overflow is not rejected

With existing capacity \(2^{32}-1\), the additive candidate wraps to 31. The shift-based candidate wraps to 2,684,354,557, which is selected by unsigned comparison.

Multiplying that capacity by 20 wraps to a storage-request value of 2,147,483,588. The function does not reject this discrepancy between capacity and requested bytes. This example specifies arithmetic behavior, not a safe allocation scenario.

### Clearing leaves unspecified bytes alone

If an already available record contains recognizable bytes at offsets 1–3 and 16–19, those bytes receive no explicit writes from this function. The specified zero writes affect only offset 0 and the three 32-bit fields at offsets 4, 8, and 12.

### Dependency changes the descriptor field

If capacity is read from descriptor \(D_1\), but a dependency call changes state offset 0 to \(D_2\), the new descriptor links to \(D_2\), assuming no additional overlapping-memory effects.

The capacity remains the value computed before the calls.
