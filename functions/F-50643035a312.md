# F-50643035a312

## Purpose

F-50643035a312 searches successive byte positions for a four-byte, big-endian value accepted by two dependent operations. At each position, a first dependency decides whether a second dependency is attempted. A position succeeds only when both dependencies return zero.

On success, the function publishes the address of the matching position, a four-byte result supplied through the second dependency, and the number of byte positions skipped. If every permitted position fails, it publishes the number of positions examined and returns a distinct exhaustion status.

This is a sliding-window search: adjacent candidates overlap by three bytes. The supplied count limits candidate starting positions, not the total number of readable bytes.

The control flow and data transfers below are established by the supplied static representation. The semantic meanings of the context, dependency results, and published four-byte value remain unknown.

## Interface

The function has five arguments and returns a four-byte status.

| Argument | Role and representation |
|---|---|
| Context | An opaque four-byte value forwarded to both dependencies. The function does not itself dereference it. |
| Cursor cell | Address of a caller-provided four-byte cell containing the initial byte address. The cell is read on entry and written on success. |
| Result cell | Address of a caller-provided four-byte destination. Written on success with the value obtained through the second dependency. |
| Candidate limit | An unsigned 32-bit number of candidate starting positions to examine. |
| Progress cell | Address of a caller-provided unsigned 32-bit destination. Written on every ordinary return. |

The cursor is represented through a four-byte cell in the supplied representation. Portability to an execution environment with a different pointer representation is not established.

The ordinary return statuses are:

- **0:** A candidate was accepted.
- **3:** No candidate was accepted within the supplied limit, including a limit of zero.

No other ordinary return status is established.

### Preconditions

For defined execution under the represented memory model:

- The cursor cell must be readable on entry, even when the candidate limit is zero.
- The progress cell must be writable whenever the function reaches an ordinary return.
- If success occurs, the cursor cell and result cell must be writable.
- Each examined candidate must permit reads at offsets zero through three from its starting address.
- The dependencies’ own preconditions must hold. Those preconditions are not available here.

For a positive limit of \(N\), a search that examines every position accesses byte offsets zero through \(N+2\), inclusive, from the initial address. Thus, in a stable contiguous buffer, \(N+3\) readable bytes suffice for the complete search. This is a mathematical extent requirement, not an observed 32-bit length calculation.

The function does not validate any of these conditions.

## Behavior

### Entry and zero-limit behavior

Before determining whether any candidate may be examined, the function reads the cursor cell and obtains the initial byte address. It initializes the number of skipped positions to zero and its eventual exhaustion status to 3.

If the candidate limit is zero:

- No candidate bytes are read.
- Neither dependency is invoked.
- The function writes zero to the progress cell.
- It returns 3.

The cursor-cell read still occurs. A zero limit does not make an unreadable cursor cell acceptable. The address obtained from that cell is not dereferenced along this path.

### Candidate interpretation

At each permitted position, the function obtains four consecutive unsigned bytes. Their interpretation is big-endian:

- Offset zero contributes bits 31–24.
- Offset one contributes bits 23–16.
- Offset two contributes bits 15–8.
- Offset three contributes bits 7–0.

For example, bytes `12 34 56 78` produce the unsigned 32-bit value `0x12345678`.

There is no sign extension of individual bytes. The combination occupies exactly 32 bits. All byte values, including zero and values with the high bit set, participate normally.

The supplied expression establishes the four byte locations and their contributions. It does not establish a portable temporal order among those four reads. In particular, it is not a sufficient contract for a device requiring a specified order of byte accesses.

The candidate value is assembled before the first dependency is called. If the second dependency is called, it receives that same assembled value; the function does not rebuild it from memory between dependency calls.

### Dependency gating

The first call for a candidate is to **F-6103190b7ded**, with:

1. The original context value.
2. The assembled unsigned 32-bit candidate value.

If this dependency returns any nonzero value, the candidate fails and the second dependency is not invoked.

If it returns zero, the function calls **F-572311e78cc8**, with:

1. The original context value.
2. The same candidate value.
3. The address of a four-byte temporary workspace.
4. The address of a four-byte temporary result cell.

A zero return from this second dependency accepts the candidate. Any nonzero return rejects it.

Only equality to zero matters. Positive and negative nonzero dependency results take the same rejection path. Dependency error codes are not propagated as the function’s return value.

### Rejected positions and search bounds

After rejection, the function advances its private candidate address by exactly one byte and increments its unsigned 32-bit skipped-position count by one.

Before reading another candidate, it checks whether the skipped count has reached the limit. Accordingly:

- A positive limit permits at most that many candidate attempts.
- Permitted starting offsets are zero through one less than the limit.
- The function never attempts a candidate starting at the limit itself.
- On complete exhaustion, the reported skipped count equals the supplied limit.

The count does not wrap during ordinary bounded iteration. Even for a limit of `0xFFFFFFFF`, the last possible increment reaches `0xFFFFFFFF`, after which the limit check exits before another increment.

The function’s address progression is separate from that count argument. Address-space exhaustion, invalid pointer arithmetic, or an inaccessible four-byte window is not converted into an exhaustion result.

Rejected candidates do not cause a direct cursor-cell or result-cell write by this function.

### Successful publication

When both dependencies return zero for a candidate, the function performs these caller-visible stores in this order:

1. It writes the accepted candidate’s byte address to the cursor cell.
2. It writes the four-byte temporary result to the result cell.
3. It writes the skipped-position count to the progress cell.

It then returns 0.

The published cursor points to the start of the accepted window. It does not point after the four-byte window and is not advanced by four bytes.

The progress value is the accepted starting offset relative to the initial cursor. It excludes the successful candidate from the skipped count. Success at the initial position therefore reports zero, although one candidate was examined.

### Exhaustion publication

When the limit is reached without success, the function writes the skipped-position count to the progress cell and returns 3.

It does not directly publish its advanced private cursor and does not directly write the result cell. Therefore, with distinct output storage and dependencies that leave that storage untouched, both cells retain their entry values on exhaustion.

### Aliasing and changing memory

The supplied behavior does not establish a non-aliasing guarantee for the three caller-provided cells.

If their storage overlaps, later stores can overwrite bytes written by earlier stores. For example, if the result and progress destinations are the same four-byte cell, the final successful contents are the skipped count, not the temporary result.

Similarly, an exhaustion write to an overlapping progress destination may alter storage also used as the cursor or result cell, despite the absence of a direct exhaustion write through those arguments.

The search uses its private candidate address rather than reloading the cursor cell at every iteration. A dependency changing the cursor cell therefore does not, by itself, redirect the next candidate address.

Input bytes are read afresh for each attempted window. Dependency-induced changes to the backing storage can affect later windows. No snapshot of the search region is made.

## Side effects

The function’s directly established external memory effects are:

- One entry read from the cursor cell.
- Four byte reads for each candidate attempted.
- A cursor-cell store and a result-cell store on success.
- A progress-cell store on every ordinary return.

These are in addition to dependency effects, which are unknown.

The function provides two temporary storage addresses to F-572311e78cc8. Each designates four bytes. Neither temporary is explicitly initialized before use, and neither is explicitly reset between candidate attempts.

The function does not inspect the workspace contents. It uses the temporary result only when F-572311e78cc8 returns zero. Consequently, a meaningful published result requires an appropriate dependency contract: the visible body alone does not guarantee that a successful dependency call supplies a fully initialized four-byte result. If it does not, the result may depend on earlier temporary contents or be indeterminate under the applicable execution model.

No direct allocation, deallocation, ownership transfer, synchronization, or global-memory access is visible in this function. Those absences do not constrain its dependencies. In particular, the available evidence does not establish that a dependency preserves globals, leaves caller storage unchanged, or refrains from acquiring or releasing resources.

The temporary addresses refer to call-local storage. Their availability after this invocation ends is not established. Whether the dependency retains them is unknown.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Unless otherwise stated, assume accessible memory, distinct output cells, and dependencies that leave input bytes and caller output cells unchanged.

### Zero candidate limit

Given any initial cursor-cell value and a limit of zero:

- Neither dependency is called.
- No byte is read through the obtained cursor.
- Progress becomes zero.
- Cursor and result cells retain their values.
- The return status is 3.

The cursor cell itself must still be readable.

### Success at the initial position

Given a limit of one and initial bytes `12 34 56 78`, suppose:

- F-6103190b7ded returns zero for `0x12345678`.
- F-572311e78cc8 writes `0xAABBCCDD` to its result destination and returns zero.

The function returns 0, publishes the initial cursor address, publishes `0xAABBCCDD`, and reports progress zero. There is no second candidate attempt.

### First-dependency rejection

Given a limit of one, suppose F-6103190b7ded returns a nonzero value.

F-572311e78cc8 is not called. The function returns 3 and reports progress one. It does not directly write either the cursor or result cell.

### Overlapping windows

Given bytes `01 23 45 67 89` and a limit of two, suppose the first candidate is rejected and the second is accepted.

The candidate values are, in order:

- `0x01234567`
- `0x23456789`

Success publishes the initial address plus one byte and reports progress one. The search does not advance by four bytes between candidates.

### Second-dependency rejection

Given a first-dependency return of zero, followed by a nonzero second-dependency return, the candidate is rejected.

Any value written to the temporary result during that failed attempt is not directly published for that attempt. Search continues if the limit permits. Dependency side effects are not rolled back.

### Exhaustion does not mean zero attempts

Given a limit of three and rejection at all three positions, the function returns 3 and reports progress three. It has examined windows beginning at offsets zero, one, and two, requiring reads through offset five.

### Aliased result and progress destinations

Suppose a candidate succeeds at offset two, the second dependency supplies `0xAABBCCDD`, and the result and progress arguments designate the same four-byte cell.

The result store occurs first, followed by the progress store. The final shared cell contains the 32-bit value two.
