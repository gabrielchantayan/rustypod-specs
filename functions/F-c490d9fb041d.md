# F-c490d9fb041d

## Purpose

F-c490d9fb041d destructively transforms links in existing records. It follows one four-byte record field recursively, then inserts the current record at a head field associated with an anchor, and finally continues through another four-byte record field.

Insertion reuses the recursive traversal field as the inserted record’s chain link. No record allocation, record copying, or explicit deallocation appears in the supplied body.

Flattening a tree-like structure into a chain is a plausible intent, not an established input contract. The function neither checks nor establishes that its input is a tree, that records are uniquely reachable, or that the traversed records are separate from an existing chain.

The unconditional contract is the sequence of reads, recursive processing, and writes below. Claims about a well-formed resulting chain require additional separation and structural assumptions.

## Interface

### Inputs

The function takes two address-bearing values represented as 32-bit integers in the supplied representation:

- **Anchor address.** Its four-byte field at offset 4 supplies the current head and receives each inserted record’s address.
- **Starting record address.** Zero means there is no record to process in this invocation. A nonzero value is used as the address of the first current record.

The anchor value is passed unchanged to recursive invocations. An unchanged anchor argument does not imply unchanged memory at that address.

These values are used as addresses despite their integer representation. The evidence does not establish portable pointer conversion rules, restrictions to positive signed values, or behavior on platforms with wider addresses.

### Output

There is no return value or explicit success status. Normal completion is represented by return to the caller; the useful result is in mutated memory.

The function can fail to return because traversal does not terminate or because execution encounters an environment-dependent failure. No error-reporting or recovery interface is visible.

### Relevant storage layout

| Location | Access width | Role |
|---|---:|---|
| Anchor + 4 | 4 bytes | Head value read and replaced during insertion |
| Record + 8 | 4 bytes | Continuation read after recursive processing |
| Record + 12 | 4 bytes | Recursive successor when read; chain link when overwritten |

Offsets are byte offsets. No full record size, payload layout, allocation boundary, alignment requirement, or enclosing type is established.

All three stored values are handled at four-byte width. There is no visible widening to a larger address representation or copying of adjacent fields.

### Preconditions for normal, memory-safe completion

The function does not validate its inputs. Successful execution requires:

- Every reached record’s fields at offsets 8 and 12 to be readable when accessed.
- Every insertion destination at record offset 12 and anchor offset 4 to be writable.
- The anchor head to be readable when an insertion occurs.
- Address calculations and address interpretation to be valid in the execution environment.
- Reached storage to remain available for the accesses performed.
- Recursive and iterative processing to terminate within available execution resources.

These requirements apply to the accesses actually reached. A zero starting record does not require a dereferenceable anchor.

Acyclicity, unique reachability, and disjoint storage are not checked preconditions. They are useful sufficient assumptions for some structural conclusions, but the function does not enforce them.

## Behavior

### Empty invocation

A zero starting record causes immediate return without accessing any referenced anchor or record fields.

This statement concerns structure accesses in the supplied body. It is not a claim that calling and returning require no machine-level stack or execution-state accesses.

### Processing order

For each nonzero current record, the established sequential order is:

1. Read its four-byte field at offset 12.
2. Recursively invoke F-c490d9fb041d with the same anchor value and the value just read as the starting record.
3. After that invocation returns, read the current record’s four-byte field at offset 8 and retain the value as this invocation’s continuation.
4. Read the four-byte head at anchor offset 4.
5. Store that head value into the current record’s field at offset 12.
6. Store the current record address into the anchor’s field at offset 4.
7. Continue with the retained continuation, stopping when it is zero.

The current record address is retained across recursive processing. The function does not reload it from the anchor before inserting that record.

The continuation is captured **after** recursive processing, not before it. If recursive processing changes the storage at the current record’s offset 8, the changed value determines continuation.

Likewise, insertion uses the anchor head read after recursion returns. It does not preserve an invocation-entry head for later use.

Once captured, the continuation is retained across the two insertion writes. If either insertion write aliases the continuation’s storage, this invocation still continues using the previously captured value.

### Insertion and sequential intermediate state

When the head field and record-link field are distinct storage locations, insertion performs two logical changes:

- The record link becomes the head value read immediately before insertion.
- The anchor head becomes the current record address.

The old head is copied as a four-byte value. It is not inspected or dereferenced merely because it is the old head.

The supplied body establishes an intermediate state in **sequential abstract execution**: the record-link assignment has occurred, but the anchor-head assignment has not yet occurred.

This does not establish that another thread, an asynchronous observer, or a device can observe that intermediate state. Physical write ordering, atomicity of either four-byte access, cross-observer visibility, and concurrent-use semantics remain unknown.

### Traversal order and resulting links

For a finite traversal with no revisits, non-overlapping relevant fields, and no interfering mutation, insertion order is determined by:

- Recursive processing through offset 12.
- Insertion of the current record.
- Continuation through offset 8.

For distinct inserted records, the final links connect those records in reverse insertion order. The earliest inserted record receives the initial head value as its link, provided recursive processing and insertion do not otherwise alter the anchor field before that earliest insertion.

This link-assignment result is not, by itself, proof that an original chain survives as a suffix.

To conclude that the result is the inserted records followed by an unchanged preexisting chain, additional conditions are required:

- The initial head must identify an established chain, or be its empty sentinel.
- The preexisting chain’s linkage storage must be disjoint from the processed records and all insertion writes.
- The inserted records must not already belong to that chain.
- Relevant storage must remain unchanged except for the specified insertion effects.

Under those conditions, the preexisting chain is preserved after the reverse-insertion-order prefix. Without them, only the exact assignments are assured.

In particular, an initial head value can identify a record that is also processed. Copying that value into the processed record’s link can create a cycle even when traversal itself terminates.

### Destructive updates and aliasing

Each completed insertion overwrites the current record’s offset-12 field. Its earlier traversal value is not retained there.

There is no direct assignment to a field designated as record offset 8. Preservation of such fields nevertheless requires non-overlap: a continuation field can share storage with an anchor field or record-link field that is written.

The function does not reject:

- An anchor overlapping a traversal record.
- Overlapping fields belonging to different records.
- A record reached through multiple paths.
- Cycles in either traversal relation.
- Intersection between processed records and the initial chain.

For example, if the current record’s offset-12 field is the same four-byte location as the anchor’s offset-4 field, insertion first writes the location’s current value back to itself, then stores the current record address there. The two logical roles do not acquire independent stored values.

A previously inserted record can be revisited. On that visit, its rewritten offset-12 field is treated as a recursive successor. There is no visited set or processed marker.

### Termination and partial progress

An invocation terminates when its current record becomes zero. Each recursive invocation must return before its caller reads the continuation or inserts its current record.

An unchanged recursive self-reference causes repeated recursive descent before that record can be inserted. Iterative cycles can cause repeated processing, but their later behavior also depends on rewritten links and the evolving head.

No rollback exists in the supplied body. Completed insertions remain in memory if later execution fails or does not terminate. A caller can remain uninserted while deeper invocations have already modified storage.

## Side effects

For each completed nonzero iteration, excluding accesses performed by recursive invocations, the function performs:

- One four-byte read of record offset 12.
- One four-byte read of record offset 8 after recursion returns.
- One four-byte read of anchor offset 4.
- One four-byte write to record offset 12.
- One four-byte write to anchor offset 4.

The two writes occur in that order in sequential abstract execution. Aliasing can make several listed accesses refer to the same storage.

These are static access semantics, not guarantees about generated instruction counts or external visibility.

## Acceptance examples

These are static, conditional acceptance scenarios, not executed tests. Unless an example states otherwise, referenced fields occupy valid, non-overlapping storage, and there is no interfering mutation. Letters designate record addresses; **H** designates a four-byte initial head value.

### 1. Empty starting record

Given a zero starting record, the function returns without accessing referenced record or anchor fields.

The anchor need not be dereferenceable for this path.

### 2. One isolated record and an arbitrary initial head

Given:

- The anchor head is H.
- A has zero at offsets 8 and 12.

After return:

- The anchor head is A.
- A’s offset-12 field is H.
- A’s offset-8 field remains zero.

H need not identify readable storage because this execution copies H without following it. These assignments alone do not establish that H heads a valid preserved chain.

### 3. Offset-8 continuation

Given:

- The anchor head is H.
- A’s offset-12 field is zero and offset-8 field is B.
- Both traversal fields of B are zero.

Insertion order is A, then B. The final assignments are:

- Anchor head: B.
- B’s offset-12 field: A.
- A’s offset-12 field: H.

If H heads a valid chain disjoint from these records and all insertion writes, that chain is preserved after B and A. Otherwise, only the listed links are established.

### 4. Recursive successor

Given:

- The anchor head is H.
- A’s offset-12 field is B and offset-8 field is zero.
- Both traversal fields of B are zero.

Insertion order is B, then A. After return, the anchor head is A, A links to B, and B’s offset-12 field contains H.

The recursively processed record is inserted first but appears after its caller in the final inserted-record prefix.

### 5. Both successor fields populated

Given:

- The anchor head is H.
- A’s offset-12 field is B and offset-8 field is C.
- Both traversal fields of B and C are zero.
- A, B, and C are distinct.

Insertion order is B, A, C. Final assignments are:

- Anchor head: C.
- C’s offset-12 field: A.
- A’s offset-12 field: B.
- B’s offset-12 field: H.

An unchanged suffix beginning at H is guaranteed only under the separate preexisting-chain conditions.

### 6. Initial head intersects the processed record

Given:

- The anchor head is A.
- A’s offset-8 and offset-12 fields are both zero.
- The anchor fields do not overlap A’s fields.

Processing terminates after one insertion. The final anchor head is A, and A’s offset-12 field is A.

Thus, a terminating traversal of one distinct record can create a self-cycle. No preserved original-chain suffix may be claimed.

### 7. Recursive self-reference

Given A’s offset-12 field points to A and no mutation interrupts that relation, processing recursively re-enters A before any insertion of A.

The supplied behavior provides no normal termination condition for that descent. Acceptance must not require return or a cycle diagnostic.

### 8. Sequencing is not an observer guarantee

For an ordinary insertion into distinct fields, the abstract execution places the record-link write before the anchor-head write.

Acceptance may require that sequential effect. It must not require an external observer to detect the intermediate state, or assume either four-byte write is atomic, without additional platform evidence.
