# F-3317362fe54d

## Purpose

F-3317362fe54d advances a storage-management state by one reusable entry or one 12-byte sequential slot.

Established behavior has two mutually exclusive paths:

- If the state contains a non-null reusable-entry pointer, replace that pointer with the link stored at the pointed-to address and return immediately.
- Otherwise, ensure that the sequential region is not exactly exhausted, allocating and linking a new region when its cursor equals its limit, then advance the cursor by 12 bytes.

The function returns no entry address and initializes no entry contents. A caller must obtain any selected entry through conventions outside this function.

The apparent intent is to consume one slot from a pool composed of linked allocation blocks and a reusable-entry chain. That interpretation is inferred from the layouts and updates; the supplied evidence does not establish the wider pool API, ownership rules, or caller protocol.

## Interface

### Inputs

The function accepts:

1. A pointer to a writable state record.
2. An integer allocation-mode argument.

The state record has four relevant consecutive fields:

| Byte offset | Name used in this contract | Role |
|---|---|---|
| 0 | Block head | Address of the newest block header, or zero |
| 4 | Reusable head | Address of a reusable entry, or zero |
| 8 | Cursor | Current sequential-position address |
| 12 | Limit | End-position address for the current sequential region |

The supplied representation uses integer fields to carry addresses. This contract describes the evident 32-bit address and word model: each listed field is four bytes, and the record occupies at least 16 bytes. The source representation alone is not independent confirmation of the original target ABI.

The allocation-mode argument is tested only for equality with zero:

- Zero selects capacity growth.
- Any nonzero value selects a capacity of exactly one when a new region is needed.
- The argument has no observable effect when reuse is available or the cursor differs from the limit.

### Block and entry layouts

A block header contains three four-byte fields:

| Byte offset | Meaning |
|---|---|
| 0 | Previous block-header address |
| 4 | Capacity, in 12-byte slots |
| 8 | Payload address |

A reusable entry must expose a readable four-byte link at offset zero. This function does not inspect the rest of such an entry.

The payload is treated as a sequence of slots with a stride of 12 bytes. No slot-internal layout is established, except that a reusable entry supplies its next-link word at its own address.

### Output

There is no return value. Results are communicated through state mutation and, on the allocation path, writes to a newly obtained block header.

### Preconditions

For defined, successful operation:

- The state pointer must identify a suitably aligned, readable and writable record.
- If the reusable head is nonzero, it must identify a readable link word.
- If capacity growth consults an existing block, the block head must identify a readable capacity field at offset 4.
- Both dependency calls on the allocation path must return addresses suitable for the accesses subsequently performed.
- The sequential-state invariant must make a 12-byte advance valid whenever the cursor differs from the limit, or after a new payload is installed.
- Address formation and cursor arithmetic must be representable under the actual execution model.

The function does not check these conditions.

No synchronization is visible. Concurrent access requires an external protocol; this function does not provide atomic allocation or atomic state transitions.

## Behavior

### 1. Reusable-entry path takes precedence

The function first examines the reusable head.

If it is nonzero, the function reads the link word at the address represented by that head and stores the link into the reusable-head field. It then returns.

Consequences:

- The block head, cursor, and limit are not deliberately changed on this path.
- Cursor exhaustion is not examined.
- The allocation-mode argument is irrelevant.
- No allocation dependency is called.
- The removed entry is not cleared, initialized, or returned.
- The new reusable head may be zero, another entry address, or even the same address. There is no link validation or cycle detection.

These statements describe accesses requested by the function. If the pointed-to entry overlaps the state record, aliasing can affect the resulting values.

### 2. Sequential exhaustion is an equality test

When the reusable head is zero, the function compares the cursor and limit for exact equality.

If they differ, no new block is allocated. The function proceeds directly to the final 12-byte cursor advance.

There is no ordering test and no remaining-space calculation. In particular:

- A cursor beyond the limit is not rejected.
- A cursor fewer than 12 bytes below the limit is not rejected.
- Misaligned cursor values are not rejected.
- A nonzero reusable head would have bypassed this comparison entirely.

Thus, valid range and stride invariants are caller obligations, not enforced conditions.

### 3. Capacity selection on exhaustion

When the cursor equals the limit and no reusable entry is available, the function chooses a new capacity.

For a nonzero allocation-mode argument, capacity is exactly one. It does not inspect the previous block’s capacity for this decision.

For a zero allocation-mode argument:

- If the block head is zero, capacity is 32.
- Otherwise, the function reads the unsigned capacity word at offset 4 of the block identified by the current block head.

For an existing capacity \(n\), the two candidates are:

- Linear candidate: \(n + 32\).
- Growth candidate: \(n + \lfloor n/2 \rfloor + \lfloor n/8 \rfloor\).

The larger candidate is selected. Equality selects the growth candidate, with no numerical difference in the result.

The additions and comparison use unsigned values in the supplied representation. Under the evident 32-bit model, additions wrap modulo \(2^{32}\), and comparison occurs after wrapping. This is not an unbounded mathematical growth formula.

For ordinary, non-overflowing capacities, the growth candidate is approximately 1.625 times the old capacity, with each shifted term rounded down separately.

There is no minimum-capacity correction after wrapped arithmetic. In particular, a wrapped result is not rejected merely because it is smaller than the previous capacity.

### 4. Two dependency calls occur in order

After selecting capacity, the function calls F-871e64ddc6de twice:

1. With a requested size of 12 and a second argument of zero.
2. With a requested size of capacity multiplied by 12 and a second argument of zero.

The first result is used as the new block-header address. The second result is used as the payload address.

The payload-size multiplication uses unsigned arithmetic in the supplied representation. Under the 32-bit model, it wraps modulo \(2^{32}\). No overflow check precedes the second call.

The first returned header is not initialized by this function before the second call. Both dependency calls finish before the visible header initialization begins.

There is no explicit check for a null or otherwise unusable return value.

### 5. Header initialization and state publication

After both dependency calls return, the function performs these writes in the following source-visible order:

1. Store the payload result into the new header’s payload field.
2. Read the state’s block head and store that value into the new header’s previous-block field.
3. Store the selected capacity into the new header’s capacity field.
4. Store the new header address into the state’s block-head field.
5. Read the payload field back from the new header.
6. Store that reread payload address into the state’s cursor.
7. Store the reread payload address plus capacity times 12 into the state’s limit.

The previous-block value is read after both dependency calls. It is not necessarily the same value consulted earlier when capacity was selected.

Likewise, the payload address used to establish cursor and limit is obtained by rereading the header, rather than exclusively retaining the dependency’s return value.

These ordering details matter if dependencies mutate shared state or returned storage aliases existing records. The function provides no isolation against such effects. It does not recheck the reusable head or exhaustion condition after the dependency calls.

Under ordinary disjoint-allocation assumptions, the new header links to the former block head, the payload starts at the returned payload address, and the limit is one byte-address span of capacity times 12 beyond that address.

### 6. Final cursor advance

After any needed allocation, or immediately when the cursor and limit originally differed, the function advances the current cursor by 12 bytes.

This update reads the cursor then present in the state and stores the incremented result back. On an ordinary successful new-region path:

- The cursor ends at payload address plus 12.
- The limit remains payload address plus capacity times 12.
- The first slot has been consumed according to the sequential-position convention.
- For capacity one, the resulting cursor equals the limit.

The final increment appears as signed integer addition in the supplied representation. Unlike the explicitly unsigned capacity arithmetic, behavior at signed overflow cannot be established as defined wrapping from this evidence. Valid callers must avoid that boundary unless the actual binary execution semantics are separately established.

## Side effects

### State changes

The function deliberately changes:

- Only the reusable head on the reuse path.
- Only the cursor on a non-exhausted sequential path.
- Block head, cursor, and limit on the new-block path.

It does not deliberately write the reusable head on the new-block path. Changes made by dependencies are not necessarily preserved or undone uniformly: this function overwrites some state fields afterward and leaves others alone.

### Memory writes

The allocation path initializes the three header fields. It does not write payload contents.

The reuse path reads but does not clear the removed entry’s link word. No entry destructor, reset, or content initialization is visible.

### Allocation and ownership

Two storage requests occur for each new block: one header request and one payload request.

The function retains both returned addresses in the linked block structure. It does not visibly release any previous header, previous payload, reusable entry, or newly returned allocation.

This does not establish that F-871e64ddc6de performs conventional heap allocation, transfers ownership, or leaves other memory unchanged. Those are dependency-contract questions.

### Failure behavior

There is no explicit error result, rollback, or cleanup path.

If a dependency signals failure by returning an unusable address, subsequent accesses are not guarded. If a dependency terminates, raises an exception, or otherwise fails to return normally, behavior is governed by that dependency and the execution environment.

Because the dependency semantics are unknown, the evidence does not establish a recoverable out-of-memory contract.

## Acceptance examples

These are conditional acceptance cases derived from static evidence. They are not reports of executed tests.

### Reusable entry overrides exhaustion

Given a nonzero reusable head pointing to a readable link, and even if cursor equals limit:

- The reusable head becomes that link.
- No dependency call occurs.
- The allocation-mode argument does not affect behavior.
- Cursor and limit receive no deliberate writes.

This holds even if the link points back to the same entry; no cycle check is performed.

### Sequential advance without allocation

Given reusable head zero and cursor unequal to limit, with a valid representable cursor advance:

- Cursor increases by 12.
- No dependency call occurs.
- Block head and limit receive no deliberate writes.

The same branch is taken if cursor is beyond limit. That input is not validated into safety; it merely fails the equality test.

### Initial growth-mode block

Given:

- Reusable head zero.
- Cursor equal to limit.
- Block head zero.
- Allocation mode zero.
- Successful, disjoint dependency results with no relevant state mutation.

The requested sizes are 12 and 384. The new header records capacity 32, previous block zero, and the payload result. Final cursor is payload plus 12; limit is payload plus 384.

### Growth from capacity 32

Under the same ordinary allocation assumptions, but with an existing block capacity of 32:

- The linear candidate is 64.
- The growth candidate is 52.
- New capacity is 64.
- Payload request size is 768.

The new header links to the block head read after the dependency calls.

### Growth from capacity 64

For existing capacity 64:

- The linear candidate is 96.
- The growth candidate is 104.
- New capacity is 104.
- Payload request size is 1,248.

### Nonzero allocation mode

Given exhaustion, no reusable entry, and any nonzero allocation-mode value:

- New capacity is one regardless of the old block capacity.
- The two requested sizes are 12 and 12.
- With ordinary successful allocation, final cursor equals the newly established limit.

### Dependency changes block head

If a dependency changes the state’s block head before header initialization, and all ensuing accesses remain valid, the new header links to that changed head. A capacity previously calculated from an older head is not recalculated.
