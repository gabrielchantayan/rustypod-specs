# F-51311962b4c4

## Purpose

F-51311962b4c4 selects a record from a globally associated singly linked list, or initializes a record obtained from a separate context slot, then passes the resulting record to F-d4c4416ace75.

Selection uses two identity fields and a 16-bit record value compared against a 32-bit unsigned request. The routine is not an exhaustive nearest-match search: an exact match ends traversal, and an improving distance of one also ends traversal, potentially before a later exact match.

**Established behavior:** record selection, partial initialization, dependency invocation, and pointer return are visible in the supplied static evidence.

**Inferred intent:** the list appears to contain reusable records, while the separate context slot supplies a record when reuse is unsuitable. Neither allocation nor the dependency’s role is established.

## Interface

### Inputs

The routine receives three 32-bit arguments:

| Argument | Interpretation established by use |
|---|---|
| Object reference | A 32-bit value compared with a record field. On the initialization path, it is also treated as an address from which a 16-bit value is read at byte offset 2. |
| Secondary identity | A 32-bit value compared with a record field and copied into two fields during initialization. No signed arithmetic is performed on it. |
| Requested value | An unsigned 32-bit value used for equality, distance calculations, and the final reuse decision. It is not narrowed to 16 bits before comparison. |

Although the first two arguments are represented as signed-width values in the supplied material, their relevant behavior is bit-pattern equality and copying. The object reference additionally has pointer semantics on the initialization path.

### Output

The routine returns the record pointer passed to F-d4c4416ace75.

The dependency’s return value, if any, does not determine this result. The pointer is retained across the call and returned afterward. This does not establish that the referenced storage remains valid after the dependency executes.

There is no explicit error result or success flag.

## Behavior

### Initial state acquisition

The routine obtains a context through the global context reference. It then reads the list-head pointer at context offset 4 and reads the global initial distance limit.

It begins with no selected record. The initial distance limit is a selection bound, not an existing candidate.

The captured context is reused for the later context-slot read and dependency call. The routine does not reacquire the context after traversal or after the dependency executes.

### Traversal and eligibility

Records are visited in next-pointer order from the captured head.

For each non-null record:

1. Its 32-bit object-reference field is read and compared with the first argument.
2. Only if that comparison matches is its 32-bit secondary-identity field read.
3. Only if both identities match is its 16-bit selection field read for the exclusion check.
4. A selection field whose signed 16-bit interpretation is −1, equivalently bit pattern `0xFFFF`, makes the record ineligible.
5. For an eligible record, the selection field is read again and interpreted as an unsigned 16-bit value.

These are distinct selection-field reads in the static evidence. No synchronization or stable-snapshot mechanism is established. Acceptance examples below assume stable memory.

A record failing an identity or exclusion check does not alter the selected record or best distance.

Unless traversal terminates early, the next pointer at record offset 0 is read after processing the record. A null next pointer ends traversal. There is no cycle detection or traversal bound.

### Exact-match selection

The eligible record’s unsigned 16-bit value is compared directly with the full unsigned 32-bit requested value.

If equal:

- That record becomes the selected record.
- The distance used for the final decision is zero.
- Traversal stops without reading that record’s next pointer.

This exact-match path does not require improvement over the global initial distance limit.

With stable record contents, an exact match is possible only for requested values from 0 through 65534. A stored value of 65535 is excluded before exact matching.

### Distance-based selection

For an eligible, non-exact record, the routine calculates the unsigned absolute difference between the full requested value and the zero-extended record value. It retains only the low 16 bits of that difference:

\[
D = |T-K| \bmod 65536
\]

Here, \(T\) is the unsigned 32-bit requested value and \(K\) is the unsigned 16-bit record value.

The operands are compared before subtraction, so the subtraction uses the larger operand minus the smaller. The subsequent 16-bit mask is significant: large differences can become small distances or zero.

This is neither ordinary unbounded absolute distance nor shortest circular distance.

A record replaces the selected record only when its calculated distance is **strictly less** than the current best distance. On replacement, its distance becomes the new best distance.

Consequences:

- Equal distances retain the earlier selected record.
- A distance equal to the initial global limit does not establish a candidate.
- A zero initial limit prevents all distance-based selections, but not exact-match selection.
- A non-exact record can produce distance zero when the requested value is outside the 16-bit range.

After an improving selection, distance one ends traversal immediately. Distance zero obtained through masking does **not** trigger this particular early exit; traversal continues unless a later exact match occurs.

A distance of one that does not improve the current limit does not terminate traversal.

### Final reuse decision

Once traversal ends, the routine uses the selected record and the current best distance.

It takes the initialization path if either:

- No record was selected; or
- The unsigned requested value is strictly smaller than the final best distance.

Otherwise, it reuses the selected record without directly modifying its fields.

Thus, finding a candidate does not necessarily mean that candidate is passed to the dependency. For example, requested value zero causes any positive-distance candidate to be rejected at this final step.

### Initialization path

The routine reads the record pointer from offset 8 of the captured context. It does not allocate storage directly, check the pointer for null, or establish that the record is unused.

It performs the following writes in order:

| Order | Destination offset | Width | Written value |
|---:|---:|---:|---|
| 1 | 8 | 32 bits | Object-reference argument |
| 2 | 24 | 32 bits | Secondary-identity argument |
| 3 | 12 | 16 bits | Zero |
| 4 | 28 | 32 bits | Zero |
| 5 | 32 | 16 bits | Zero |
| 6 | 36 | 32 bits | Secondary-identity argument |
| 7 | 40 | 16 bits | Zero |

After those seven writes, it reads a 16-bit value at byte offset 2 from the object reference. It then writes the 16-bit field at record offset 34:

- One if the object value equals `0x482B`.
- Zero otherwise.

The flag write occurs after the object read. If the object storage aliases the destination record, the read observes memory after the preceding initialization writes, not necessarily the object’s entry-state contents.

The next pointer and all other unlisted record bytes are left untouched by the direct initialization sequence. The requested value is not copied into the record; the selection field is explicitly set to zero.

### Dependency call and return

On every normally completing path, the routine calls F-d4c4416ace75 once with:

1. The captured context.
2. The selected or initialized record pointer.

The routine then returns that same pointer.

No post-call record read, validity check, or dependency-status check is established.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, memory is valid and stable, the list is finite, and F-d4c4416ace75 returns normally. Record identities match the arguments where a record is described as eligible.

1. **Empty list initializes the context-provided record.**  
   Given a null list head and a valid initialization-record pointer, that record receives the specified writes. Its flag becomes one when the object’s 16-bit field equals `0x482B`, otherwise zero. The dependency receives it, and its pointer is returned.

2. **Exact match bypasses a zero selection limit.**  
   Given requested value 20, initial limit zero, and an eligible record with selection value 20, that record is selected despite the zero limit. It is not directly initialized.

3. **Distance equal to the initial limit is insufficient.**  
   Given requested value 10, initial limit two, and a sole eligible record with value 12, no candidate is established. The context-provided record is initialized.

4. **Equal-distance ties retain the earlier candidate.**  
   Given requested value 10, initial limit greater than two, and eligible records with values 8 then 12, the first record remains selected. The final comparison permits reuse because 10 is not smaller than two.

5. **An improving distance of one can hide a later exact match.**  
   Given requested value 10, initial limit greater than one, and eligible records with values 11 then 10, traversal stops at the first record. Its next pointer is not read, and it is reused.

6. **A selected candidate can still cause initialization.**  
   Given requested value zero, initial limit greater than one, and a first eligible record with value one, traversal stops on that record. Since zero is smaller than one, the routine instead initializes and passes the context-provided record.

7. **Excluded selection value is not an exact match.**  
   Given requested value 65535 and a record whose selection field is `0xFFFF`, that record is excluded. If there are no other selectable records, initialization occurs.

8. **Wide requested values can produce masked distance zero.**  
   Given requested value 65541, initial limit greater than zero, and an eligible record with value five, the full values are unequal but their distance masks to zero. That record becomes a candidate. This masked zero does not itself terminate traversal. If no later exact match occurs, the candidate is reused.

9. **Partial initialization preserves unlisted bytes.**  
   Given an initialization record containing preexisting data, its next pointer and unlisted bytes remain unchanged by this routine’s direct writes. This expectation applies before the dependency executes; no equivalent post-call preservation is established.
