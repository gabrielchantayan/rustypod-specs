# F-7e7a566f4283

## Purpose

F-7e7a566f4283 locates a record associated with a requested 32-bit key in a linked record structure. Depending on a selection flag, an existing record with that key is either immediately acceptable or acceptable only when two status words both contain the all-ones value.

The traversal distinguishes two situations:

- At a record whose key matches, it either returns that record or continues through a dedicated continuation link. If that link is empty, it invokes F-f49ea9c0baa4 and may attach the returned pointer.
- At a record whose key differs, it recursively searches one branch and then, only if necessary, another branch.

A null result means that the executed path produced no acceptable or newly supplied record. It does not establish that no matching record exists elsewhere in the reachable structure: some links are deliberately not searched, and dependency failure can terminate a matching-key path.

This is a static behavioral contract. No runtime tests have been performed.

## Interface

### Inputs

The function receives three arguments:

| Argument | Meaning |
|---|---|
| Starting record pointer | A nullable pointer to the record at which traversal begins. |
| Requested key | A 32-bit integer compared for equality against a record’s key word and passed unchanged to F-f49ea9c0baa4. |
| Selection flag | An integer interpreted only as zero versus nonzero. Nonzero permits immediate acceptance of any encountered record whose key matches. |

Negative and positive nonzero selection flags have the same effect. No additional flag bits are interpreted.

### Result

The result is a record pointer or null.

A non-null result is either:

- An encountered record whose key and acceptance conditions passed; or
- The exact non-null pointer returned by F-f49ea9c0baa4.

The function does not validate a dependency-produced record before returning it. In particular, the dependency’s result is not checked for the requested key, status values, record size, or structural compatibility.

### Record layout

The supplied representation uses 32-bit words. Link fields encode pointers in those words.

| Byte offset | Width | Observed role |
|---|---:|---|
| 0 | 32 bits | Branch searched second when the current record’s key differs. |
| 4 | 32 bits | Branch searched first when the current record’s key differs. |
| 8 | 32 bits | Continuation link followed when the current record’s key matches but is not accepted. This is the only field explicitly written by this function. |
| 16 | 32 bits | Second status word tested for the all-ones value. |
| 20 | 32 bits | First status word tested for the all-ones value. |
| 36 | 32 bits | Record key. |

The status sentinel is the 32-bit bit pattern `0xFFFFFFFF`, corresponding to −1 in the comparison shown. It is not an arbitrary negative value.

The layout does not establish a complete record type. Fields at other offsets have no demonstrated role in this function. A record whose key is examined must provide readable storage through the key field, ending at byte offset 39. Additional access requirements depend on the path taken.

### Preconditions

For defined, successful execution:

- Each non-null pointer actually dereferenced must designate valid storage for the accessed fields.
- Encoded links that are followed must be valid record pointers or null.
- The relevant storage must satisfy the execution environment’s alignment and pointer-representation requirements.
- A continuation field must be writable if a non-null dependency result is to be attached there.
- The traversed structure and dependency behavior must permit termination if termination is required.

The function performs no pointer validation, cycle detection, traversal bound, or recursion-depth check. Null is explicitly handled; invalid non-null pointers are not.

## Behavior

### Null starting pointer

A null starting pointer returns null immediately.

No record fields are accessed, and F-f49ea9c0baa4 is not called on this path.

### Matching-key record

For a non-null current record, the function first reads its key word and compares it with the requested key.

If the keys match, acceptance is determined as follows:

1. A nonzero selection flag causes the current record to be returned immediately.
2. With a zero selection flag, the status word at offset 20 is tested against `0xFFFFFFFF`.
3. Only if that first status word matches is the status word at offset 16 tested against `0xFFFFFFFF`.
4. If both status words match, the current record is returned.
5. Otherwise, traversal proceeds through the continuation field at offset 8.

Thus, a nonzero flag bypasses both status reads. With a zero flag, failure of the offset-20 test bypasses the offset-16 read.

An accepted record is returned without inspecting its continuation or either mismatch branch.

### Rejected matching-key record

A matching-key record that fails the status condition is not itself returned.

If its continuation is non-null, that linked record becomes the next current record. The requested key and selection flag remain unchanged, and normal key comparison resumes there.

The continuation target is not assumed to share the current record’s key. If its key differs, the mismatch-branch behavior applies at that target.

At the expression level, the supplied representation reads the continuation once to obtain the next traversal pointer and again to test for null. For stable ordinary storage, these observations agree. The representation does not justify an exact machine-load count or a concurrency-safe interpretation of inconsistent observations.

If the continuation is null, the function calls F-f49ea9c0baa4 with the requested key as its sole explicit argument.

- If the dependency returns null, the function returns null without performing an attachment write.
- If the dependency returns a non-null pointer, the function writes that pointer into the rejected record’s continuation field and returns the same pointer.

The function does not search that rejected record’s two mismatch branches before calling the dependency. It also does not validate the dependency result against the selection flag or status condition.

There is no retry following a null dependency result.

### Mismatching-key record

If the current record’s key differs from the requested key, neither its status fields nor its continuation field participates in the local search decision.

The function instead:

1. Reads the branch at offset 4 and recursively searches that branch with the same key and selection flag.
2. Returns immediately if that recursive search produces a non-null result.
3. Otherwise, reads the branch at offset 0 and recursively searches it with the same arguments.
4. Returns that second search’s result, including null.

The branch at offset 0 is read only after the first recursive search has returned null. It is not captured before that search begins. Consequently, any relevant mutation performed during the first search can affect the pointer subsequently read from offset 0.

Branch precedence is strict. A non-null result from the offset-4 branch wins even if the offset-0 branch could also produce a result.

There is no ordering comparison between keys. A mismatch does not select a branch based on whether the requested key is numerically smaller or larger.

### Mixed traversal and failure propagation

A dependency call can occur inside either recursive branch. Its effect on the enclosing search depends on its result:

- A non-null dependency result propagates outward as a successful result and prevents later sibling searches.
- A null dependency result returns null from that matching-key path. An enclosing mismatching-key invocation may then continue into its second branch.

Accordingly, one top-level invocation can call F-f49ea9c0baa4 more than once if earlier calls return null and later branches reach other rejected matching-key records with empty continuations.

A rejected matching-key record does not itself fall back to its mismatch branches after dependency failure. Any later search comes from an enclosing recursive invocation.

### Integer behavior

The function compares keys for equality; it performs no key arithmetic, range calculation, ordering, increment, or normalization.

The requested key is forwarded unchanged to recursive invocations and to F-f49ea9c0baa4. The status condition requires exact equality with the 32-bit all-ones sentinel.

Field locations use fixed offsets. No data-dependent index or size computation appears in the supplied representation.

## Side effects

### Explicit mutation

The function has one demonstrated record-write operation: after F-f49ea9c0baa4 returns non-null, it stores that pointer into the continuation field of the rejected matching-key record whose empty continuation triggered the call.

The ordering is:

- Observe that continuation as null.
- Invoke F-f49ea9c0baa4.
- Receive a non-null pointer.
- Store the pointer into that same record’s continuation field.
- Return the pointer.

There is no post-call check that the continuation is still null. If the dependency changes that field and returns normally, the subsequent attachment write replaces its intervening value.

This function performs no explicit detachment, deallocation, status update, or key update.

### Dependency effects and ownership

The dependency’s internal effects are unknown. Its name and call position do not establish allocation, initialization, ownership transfer, global-state preservation, or memory release behavior.

The returned pointer alone does not specify whether the caller owns the record, borrows it, or must eventually release it. Attaching a dependency-produced pointer establishes a structural link, not a demonstrated ownership policy.

Safe completion of the attachment path requires the original rejected record to remain writable across the dependency call. If the dependency invalidates that storage, the supplied function contains no recovery mechanism.

### Resource and failure behavior

Mismatch traversal uses recursive calls. Continuation traversal is represented as iteration, although a continuation can lead to a key mismatch and thereby introduce recursion.

No explicit error object, diagnostic, exception handling, or failure code other than null is shown. A null result does not distinguish an empty search from dependency failure.

Cycles can prevent termination. Deep branch traversal can exhaust call-stack resources. Neither condition is detected or handled by the demonstrated logic.

## Acceptance examples

These examples are conditional consequences of the static control flow, not executed tests. Unless stated otherwise, records are valid, field values remain stable during access, and dependencies return normally.

1. **Empty starting structure.**  
   Given a null starting pointer, the result is null. No dependency call occurs.

2. **Nonzero flag accepts a matching record.**  
   Given a matching-key record and selection flag −3, that record is returned regardless of its status values. Its status and link fields are not needed on this path.

3. **Zero flag accepts only the exact sentinel pair.**  
   Given a matching-key record, a zero flag, and both status words equal to `0xFFFFFFFF`, the record is returned. A status value of −2 does not satisfy the sentinel test.

4. **First status failure short-circuits the second read.**  
   Given a matching-key record and zero flag, if the status at offset 20 is not the sentinel, acceptance fails without reading the status at offset 16. Continuation processing follows.

5. **Continuation search returns an existing record.**  
   Given a rejected matching-key record whose continuation points to a matching-key record with both sentinel statuses, the second record is returned under a zero flag. No dependency call is required.

6. **Empty continuation receives a supplied pointer.**  
   Given a rejected matching-key record with null continuation, if F-f49ea9c0baa4 returns pointer P, that continuation becomes P and the result is P. Acceptance does not depend on P’s key or statuses because they are not inspected.

7. **Dependency failure does not search local mismatch branches.**  
   Under the preceding conditions, if the dependency returns null, the matching-key path returns null even if its offset-4 or offset-0 branch could contain an acceptable record. The function performs no attachment write; the dependency’s own mutations remain unspecified.

8. **First mismatch branch has precedence.**  
   Given a mismatching-key record whose offset-4 branch returns P, the result is P. The offset-0 branch is not read or searched by that invocation.

9. **Second branch is observed after first-branch failure.**  
   Given a mismatching-key record whose first recursive search returns null, the function then reads its offset-0 branch. If that field changed during the first search, the later read determines the second search target.

10. **Repeated dependency failure can precede later success.**  
    Given a mismatching-key record whose first branch reaches an empty rejected match and receives null from the dependency, the second branch is still eligible for search. If it reaches another such record, another dependency call may occur.
