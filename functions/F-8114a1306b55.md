# F-8114a1306b55

## Purpose

F-8114a1306b55 rewires a linked node structure around a selected node and that node’s link at byte offset +8. Under a conventional binary-tree interpretation, this is a **right rotation**: the selected node’s left child becomes the local subtree root, and that child’s former right subtree becomes the selected node’s left subtree.

That interpretation is inferred intent. The established behavior is a sequence of four-byte field reads and writes. The function does not check tree validity, confirm that the selected node has the expected child, or verify all reciprocal links before modifying memory.

The operation also changes the structure’s recorded root when the selected node matches the root entry reached through the first argument. Otherwise, it changes a link in the selected node’s recorded parent.

## Interface

### Inputs

The function receives two address-bearing arguments:

| Argument | Role |
|---|---|
| **Context** | Address of an object containing, at byte offset +16, an address of a separate root-holder object. |
| **Selected node** | Address of the node around which links are rewired. |

The supplied representation uses integer-valued arguments as addresses. All explicitly accessed fields occupy four bytes. This supports a 32-bit address-bearing layout for the described operation; it does not establish portability to a different pointer width.

The first argument is not itself the address of the root slot. There is an indirection through its field at +16.

These are explanatory roles, not additional stored fields.

### Output

There is no explicit return value. The function communicates its result through memory changes.

There is no success flag, error code, or returned replacement-root address. A caller that needs the new local root must obtain it from the resulting links or retain the relevant address independently.

### Preconditions

For ordinary, well-formed tree use:

- The selected node and pivot must be valid, accessible node objects.
- The pivot must be nonzero. A zero selected-node +8 field is not handled as an empty-child case.
- The context’s root-holder address must designate readable storage with a writable root slot when that slot is updated.
- A nonzero transferred-subtree address must designate a node whose +4 field is writable.
- If the selected node does not match the recorded root, its parent-like address must support the reads and writes described below.
- Relevant fields must remain stable during the operation for the conventional rotation result to apply.
- The objects must not overlap in ways that make a field update change another field that will later be read.

These are validity requirements, not checks performed by the function.

## Behavior

### Established access and mutation sequence

The function performs the following phases in order. Later failures do not undo earlier writes.

1. **Obtain the pivot and replace the selected node’s +8 link.**

   The pivot address is read from selected node +8. The four-byte value at pivot +12 is then copied into selected node +8.

   Consequently, the first modification occurs before the function reads the context’s root-holder field or decides whether the selected node is the recorded root.

2. **Repair the transferred subtree’s parent-like link, if present.**

   Pivot +12 is read again and compared with zero.

   If that read is nonzero, the function reads pivot +12 again to obtain the destination node address, then writes the selected node’s address into that node’s +4 field.

   There is no corresponding write when the tested value is zero.

   The value copied in the first phase is not the only observation of pivot +12. Without stable memory, the copied link, the value tested for zero, and the address used for the parent-link write need not agree.

3. **Assign the pivot’s parent-like link.**

   The current value at selected node +4 is copied to pivot +4.

   This reads the selected node’s parent-like field after the preceding writes. It is not an entry-time snapshot.

4. **Locate and inspect the recorded root.**

   The function reads the address at context +16 and forms the root-slot address at that object’s +4 field. It reads that slot and compares its value with the selected node’s address.

   If they match, the root slot is replaced with the pivot address.

5. **Otherwise, update one link in the selected node’s recorded parent.**

   If the root comparison did not match, the function reads selected node +4 again to obtain a parent address.

   It inspects that parent’s +12 field:

   - If the field equals the selected node’s address, it replaces parent +12 with the pivot address.
   - Otherwise, it replaces parent +8 with the pivot address.

   The fallback write is unconditional within the second branch. The function does **not** first check that parent +8 points to the selected node.

6. **Make the selected node the pivot’s +12 child.**

   Pivot +12 is set to the selected node’s address.

7. **Complete the selected node’s parent-like link.**

   Selected node +4 is set to the pivot address.

The function then returns normally if all accesses complete.

This sequence describes the field accesses established by the supplied representation. It does not specify a finer machine-level ordering between address calculations and source reads within an individual assignment.

### Result for a well-formed, stable tree

Let the selected node be **S**, its initial left child be **P**, P’s initial right child be **T**, and S’s initial parent be **A**.

When these objects and slots are valid and non-overlapping:

- S’s left link becomes T.
- If T is nonzero, T’s parent link becomes S.
- P’s parent link becomes A.
- The incoming link previously identifying S is changed to P:
  - the root slot if S was the recorded root;
  - otherwise A’s right link if that link equaled S;
  - otherwise A’s left link.
- P’s right link becomes S.
- S’s parent link becomes P.

For distinct conventional tree nodes, P’s left link and S’s right link are unchanged. Payload fields and other unrelated fields are not explicitly accessed.

The root case copies S’s former parent-like value into P’s parent-like field. The function does not independently clear that field. A zero parent for the new root follows only if the original root’s parent field was zero.

### Decisions depend on stored addresses, not validated topology

Root status is determined solely by equality with the root slot. The function does not infer root status from a zero parent link.

For the non-root case, the parent’s right link is checked first. If it matches S, that link is updated even if the parent’s left link also equals S. If it does not match, the left link is overwritten regardless of its previous value.

No cycle detection, descendant check, reciprocal-parent validation, or balancing operation is present.

## Side effects

### Memory writes

In the ordinary non-overlapping case, a successful invocation performs:

- **Five four-byte writes** when the transferred subtree is zero.
- **Six four-byte writes** when it is nonzero.

Those writes target:

1. Selected node +8.
2. Transferred subtree +4, conditionally.
3. Pivot +4.
4. Either the root slot or one parent child-link slot.
5. Pivot +12.
6. Selected node +4.

These counts describe executed writes, not necessarily distinct destinations. Aliasing may cause multiple writes to the same storage.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed test results. Unless stated otherwise, referenced objects are valid, distinct, non-overlapping, and stable throughout the operation.

### Recorded root with an empty transferred subtree

Initially:

- The root slot contains S.
- S’s parent field is zero.
- S’s left link contains P.
- P’s right link is zero.

After normal completion:

- The root slot contains P.
- P’s parent field is zero.
- P’s right link contains S.
- S’s parent field contains P.
- S’s left link is zero.

No transferred-subtree parent write occurs.

### Recorded root with a nonzero former parent field

Initially, the root slot contains S, but S’s parent field contains a nonzero address A.

After normal completion, the root slot contains P and P’s parent field contains A. The function does not normalize the new root’s parent to zero or update A’s child links through the non-root branch.

### Non-root selected through its parent’s right link

Initially:

- The root slot does not contain S.
- S’s parent field contains A.
- A’s right link contains S.
- S’s left link contains P.
- P’s right link contains T, where T is nonzero.

After normal completion:

- A’s right link contains P.
- P’s parent field contains A.
- S’s left link contains T.
- T’s parent field contains S.
- P’s right link contains S.
- S’s parent field contains P.
- The root slot is unchanged.

### Non-root fallback does not validate the left link

Initially, the root slot does not contain S, S’s parent field contains A, and A’s right link does not contain S.

The function writes P into A’s left link even if that slot previously contained an unrelated node. This is established behavior for inconsistent topology, not a validation failure.

### Both parent child links identify the selected node

If both A’s left and right links contain S, the right-link comparison succeeds. A’s right link becomes P; A’s left link remains S, assuming no aliasing with other written slots.

### Missing pivot

If S’s left link is zero, the function attempts to access the field at offset +12 from that zero address. It does not return early as a no-op. Normal completion is not guaranteed, and no particular diagnostic is established.
