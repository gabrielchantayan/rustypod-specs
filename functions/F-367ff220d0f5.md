# F-367ff220d0f5

## Purpose

F-367ff220d0f5 dispatches a message-like record through an ordered sequence of handlers associated with a receiver.

The established behavior is a short-circuiting dispatcher: a handler’s nonzero result terminates processing and is returned unchanged. A zero result permits processing to continue. Some handlers are selected by the record’s primary discriminator, others by a secondary discriminator or by equality between a record field and receiver state.

The interpretation of nonzero as “handled,” and zero as “not handled,” is inferred intent. The established contract is only the control-flow distinction between zero and nonzero; no particular positive or negative result has an independently established meaning.

The routine does not take a stable snapshot of the record or receiver. It rereads selected fields between handler calls. Changes made by earlier handlers can therefore alter later dispatch decisions.

## Interface

### Inputs

The routine receives two arguments:

1. **Receiver address.** An address of an object containing a dispatch-table address and comparison fields.
2. **Record address.** An address of a record containing a primary discriminator and discriminator-dependent data.

Both original argument values are passed, in the same order, to every invoked handler. No replacement record or receiver is constructed.

The supplied representation uses 32-bit integer fields and 32-bit address-bearing words. Offsets below are byte offsets. A separate platform ABI description is not available, so these widths describe the supplied representation rather than a portable host-language interface.

### Receiver layout used by this routine

| Byte offset | Width in supplied representation | Role |
|---|---:|---|
| 0x00 | 32 bits | Address of the current dispatch table |
| 0x50 | 32 bits | Comparison value used by the final conditional handler |
| 0xC0 | 32 bits | Comparison value used by one initial conditional handler |

The dispatch table contains callable entries at these byte offsets:

| Table offset | Invocation condition |
|---|---|
| 0x14C | Initial discriminator is 0x0F and its comparison field matches the receiver field at 0xC0 |
| 0x124 | A fallback-stage record has discriminator 0x16 and nested discriminator zero |

| 0x0E0 | After the main fallback handler returns zero, discriminator 0x0F has a comparison field matching the receiver field at 0x50 |

The entries’ concrete function identities and implementations are unknown. Each is invoked with the original receiver and record addresses and is expected to provide an integer result compatible with the dispatcher’s return value.

### Record layout used by this routine

| Byte offset | Width | Role |
|---|---:|---|
| 0x04 | 32 bits | Primary discriminator |
| 0x08 | 32 bits | Comparison value for discriminator 0x0F, or nested-record address for discriminator 0x16 |
| 0x0C | 32 bits | Secondary discriminator for initial discriminator 0x13 |

For discriminator 0x16, the word at record offset 0x08 is interpreted as an address. The nested record’s 32-bit word at offset 0x04 supplies the nested discriminator.

The routine does not inspect the record word at offset zero.

### Output

The result is a 32-bit integer:

- The first nonzero handler result encountered on the selected path is returned unchanged.
- If no invoked handler returns nonzero, the result is zero.

There is no normalization to one, no aggregation of handler results, and no separate error encoding established here. Negative nonzero results short-circuit just as positive results do.

### Preconditions

Every field actually read must be accessible when it is read. Every selected dispatch-table entry must identify a callable target using the required calling convention.

In particular:

- The record’s primary discriminator must be readable immediately upon entry.
- Discriminator-specific fields need to be valid only when their corresponding branch reads them.
- A fallback-stage discriminator of 0x16 requires a readable nested-record address and nested discriminator.
- A selected indirect call requires a readable receiver dispatch-table address and callable entry.
- Objects needed after a handler returns zero must remain valid for the subsequent reads and calls.

No null checks, bounds checks, record-size checks, dispatch-target validation, or lifetime enforcement are established.

## Behavior

### 1. Initial specialized dispatch

The routine first reads the record’s primary discriminator at offset 0x04.

It selects at most one initial handler:

| Initial discriminator and condition | Selected handler |
|---|---|
| 0x27 | F-54014c626648 |
| 0x13, with secondary discriminator 0x7681 | F-b5d0e10d98f4 |
| 0x13, with secondary discriminator 0x7682 | F-4fcdc0742c81 |
| 0x0F, with record offset 0x08 equal to receiver offset 0xC0 | Receiver dispatch entry at 0x14C |
| Any other case | No initial handler |

For discriminator 0x13, the secondary discriminator at offset 0x0C is read for the 0x7681 selection. If that selection does not match, the same field is read again for the 0x7682 selection. There is no handler call between these two reads.

The supplied arithmetic tests subtract 0x7681 for the first comparison and subtract 0x7600 before comparing against 0x82 for the second. At the represented 32-bit width, the respective matching values are 0x7681 and 0x7682. These are exact-value selections, not ranges or masked comparisons. No particular portable-language signed-overflow policy is established by the supplied representation.

For discriminator 0x0F, the record comparison field at offset 0x08 is read before the receiver comparison field at offset 0xC0. The indirect handler is selected only if those 32-bit values are equal.

If an initial handler is called:

- A nonzero result is returned immediately.
- A zero result transfers control to the fallback sequence.

If no initial handler qualifies, processing enters the same fallback sequence directly. The routine does not try another initial handler after an initial handler returns zero.

### 2. Optional zero-nested-discriminator handler

On entering fallback processing, the routine rereads the record’s primary discriminator.

If it is 0x16:

1. The nested-record address is read from record offset 0x08.
2. The nested discriminator is read from nested-record offset 0x04.
3. If that discriminator is zero, receiver dispatch entry 0x124 is invoked.

A nonzero result from entry 0x124 is returned immediately. A zero result permits the next stage.

If the primary discriminator is not 0x16, or its nested discriminator is not zero, entry 0x124 is not invoked.

This stage uses current memory contents, not the primary discriminator read at function entry. An initial handler that returns zero may therefore change whether this stage runs.

### 3. Required main fallback handler

The routine reads the primary discriminator again, independently of the preceding stage.

- If it is 0x16, the routine rereads the nested-record address and nested discriminator.
- If the resulting nested discriminator is 0x2A, dispatch entry 0x10C is selected.
- Otherwise, dispatch entry 0x110 is selected.

Exactly one of these two handlers is called whenever this stage is reached.

This second nested-discriminator inspection is independent of the inspection used to decide whether to call entry 0x124. In particular, a zero-returning call to entry 0x124 may change the primary discriminator, nested-record address, nested discriminator, or dispatch table before this selection occurs.

Even when entry 0x124 is not invoked, the source establishes separate reads for the two fallback decisions. It does not establish one cached nested discriminator shared by both stages.

A nonzero result from the selected main fallback handler is returned immediately. A zero result leads to the final conditional stage.

### 4. Final conditional handler

After the main fallback handler returns zero, the routine rereads the primary discriminator.

If it is 0x0F:

1. The comparison value at record offset 0x08 is read.
2. The receiver comparison value at offset 0x50 is read.
3. If the values are equal, dispatch entry 0x0E0 is invoked.

A nonzero result from entry 0x0E0 is returned unchanged. Otherwise, the routine returns zero.

If the primary discriminator is not 0x0F, or the comparison fails, entry 0x0E0 is not called and the routine returns zero.

The final comparison uses receiver offset 0x50, not the offset 0xC0 used for the initial 0x0F selection. Neither comparison implies the other.

### Ordering and reread rules

The observable order of handler invocations is constrained to:

1. At most one initial specialized handler.
2. Optionally entry 0x124.
3. Exactly one of entries 0x10C and 0x110, if processing has not already returned.
4. Optionally entry 0x0E0.

Any nonzero result stops this sequence.

The receiver’s dispatch-table address is obtained for each indirect call when that call is selected. No single dispatch-table snapshot is established across the entire operation. A handler’s changes to the receiver’s dispatch-table address may affect subsequent indirect calls.

No execution can invoke more than four handlers under this control flow. Whether a particular handler sequence is reachable also depends on the record and receiver state observed at each stage, including mutations performed by preceding handlers.

## Side effects

The routine contains no established direct writes to the receiver, record, nested record, or dispatch table. Its own visible memory operations are reads and handler invocations.

Its transitive side effects are unknown because the called functions are not supplied. The contract therefore does not assert that any handler:

- Preserves the record, receiver, dispatch table, or globals.
- Preserves a nested-record address or its contents.
- Allocates or releases memory.
- Leaves ownership unchanged.
- Avoids external I/O, reentrancy, or other observable activity.

No explicit allocation, release, ownership transfer, locking, or rollback is established within this routine itself. Passing an address to a handler does not, by itself, establish an ownership transfer.

A handler that returns zero may leave changes visible to later handlers. The dispatcher neither restores prior state nor compensates for earlier side effects. A later nonzero result does not undo earlier calls.

The supplied body establishes no recovery path for an invalid memory access, invalid indirect target, or a handler that does not return normally.
