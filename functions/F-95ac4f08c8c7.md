# F-95ac4f08c8c7

## Purpose

F-95ac4f08c8c7 updates a caller-supplied target, increments a field in an associated object, selects an entry through either a table lookup or a fallback dependency, and invokes an indirect operation on that entry. After a final dependency returns, it stores the retained one-byte dispatch result in the target.

The established contract is an ordered sequence of memory accesses and calls. The supplied representation does not establish that the function initializes an object, registers a resource, allocates storage, or balances reference ownership.

This document distinguishes:

- **Established static evidence:** accesses, widths, conditions, arguments, and ordering visible in the supplied representation.
- **Inferred intent:** plausible semantic interpretations that are not requirements.
- **documented_only unknowns:** behavior requiring dependency bodies, platform information, or other evidence not supplied here.

No runtime tests have been performed.

The body directly writes **seven four-byte target fields**, at +0x34, +0x10, +0x38, +0x14, +0x0C, +0x08, and +0x04. The associated-object increment and final one-byte target write are separate operations.

The final store affects exactly one byte. It does not itself clear or replace the three following bytes.

### Associated-object layout

The address read from target +0x18 is placed in a temporary address slot.

| Offset | Width | Established use |

| +0x0C | 4 bytes | Read as an unsigned lookup bound |

The incremented field is represented as a signed 32-bit integer. Its semantic meaning is not established.

### Entry and dispatch layout

Each table entry occupies four bytes and supplies an entry address.

A selected entry must support these accesses:

- Its first four bytes supply a dispatch-table address.
- The four-byte dispatch-table slot at +0x1C supplies a callable address.
- That callable is invoked with the selected entry address and the integer 32.

The caller retains one byte from the callable’s result. The supplied body does not establish the callable’s full return convention or the interpretation of that byte.

These layouts describe accesses, not complete object types or allocation sizes.

## Behavior

### 1. Initial target writes

The function first performs these four-byte writes in order:

1. Mode to target +0x34.
2. The derived binary value to target +0x10.
3. Zero to target +0x38.
4. Zero to target +0x14.
5. Zero to target +0x0C.

The derived value is exactly:

| Unsigned mode | Stored value at +0x10 |
|---:|---:|
| 0 | 1 |
| 1 | 0 |
| 2 through 4,294,967,295 | 0 |

The supplied representation includes subtraction, but modes greater than one cause its intermediate result to be replaced with zero before storage. No wrapped or negative subtraction result is committed to this field.

Next, the function reads global value A as a four-byte quantity. It then writes 6 to target +0x08, followed by the captured A value to target +0x04.

Consequently, the global read precedes both of those writes. If storage aliases, the captured value—not a later reread—is used at +0x04.

### 2. Global capture and associated-object update

The function reads another four-byte global value, designated B, and retains it for a possible fallback call.

It then reads target +0x18 into the temporary associated-object slot. Through that initially loaded address, it reads the four-byte field at +0x1C, adds one, and writes the result back.

This increment precedes entry lookup and all dependency calls shown in the body. A later replacement of the temporary address does not redirect the already completed increment.

For inputs where the increment is representable as a signed 32-bit value, the stored result is the previous value plus one. At 2,147,483,647, the representation alone does not establish wrapping, trapping, or another overflow outcome. No explicit overflow guard is present.

**Inferred intent:** the increment may be usage or reference bookkeeping. That interpretation does not establish ownership or require a compensating decrement.

### 3. Direct entry lookup

A global pointer supplies access to an unsigned 32-bit lookup index.

The function compares an index read through that pointer with the unsigned bound at associated-object +0x0C. The comparison is strict:

- If the index is less than the bound, the table address at associated-object +0x08 is used to read a four-byte entry.
- Otherwise, the candidate entry is null.

On the successful branch, table selection uses an index read through the global pointer and a four-byte stride.

The comparison and table selection contain separate accesses to the index location. A single retained index snapshot is not established. The contract also does not impose an evaluation order on independent operand reads within the comparison or table-address expression.

With stable inputs:

- An index equal to the bound fails the comparison.
- A zero bound admits no unsigned index.
- An in-range table entry can still contain null.

If the index or the global pointer changes between accesses, the comparison does not necessarily validate the index subsequently used for selection. Stability or external synchronization is not supplied by this body.

The table offset involves multiplication by four in the supplied 32-bit representation. There is no separate scaled-index overflow check or address-wrap check. A successful unsigned comparison alone does not establish that the resulting address is valid.

### 4. Fallback entry selection

If the candidate entry is null, F-6553c4e9e5b8 is invoked with five arguments in this order:

1. The address of the temporary associated-object slot.
2. The global pointer to the lookup-index location.
3. The integer 1.
4. The integer 32.
5. The previously captured global value B.

Its return value becomes the selected entry address.

Passing the temporary slot by address permits the dependency to change its contents. The body does not copy the resulting slot contents back to target +0x18.

The slot address also escapes to this dependency. The representation supplies no guarantee that the dependency refrains from retaining that address or making it available to other operations.

A non-null direct candidate skips F-6553c4e9e5b8. A null fallback result is not checked before dispatch.

### 5. Indirect dispatch

The function obtains the callable through the selected entry’s dispatch-table slot at +0x1C. It invokes that callable with the selected entry address and 32.

One byte of the result is retained for the final target write.

There is no visible validation of the selected entry, its dispatch-table address, or the callable address. Normal completion therefore requires those addresses to support the indicated reads and call.

### 6. Final dependency and result commit

After dispatch returns normally, the function calls F-07fef63861ea with the address of the **same temporary associated-object slot** used for the fallback call.

The identity of that slot is established. Its contents at this point are not guaranteed to equal either:

- The address initially loaded from target +0x18; or
- A replacement address written by F-6553c4e9e5b8.

In particular, dispatch occurs between fallback and the final dependency. Its mutation behavior is unknown, and the slot address may already have escaped through the fallback call. A guarantee that a fallback replacement remains in the slot requires an additional no-intervening-mutation condition.

Only after F-07fef63861ea returns normally does the function store the retained dispatch byte at target +0x3C. It does not reread the dispatch result or use a result from the final dependency for this store.

## Side effects

The body directly performs:

- Seven four-byte target writes.
- One four-byte incrementing read-modify-write through the initially loaded associated-object address.
- One final one-byte target write.
- A conditional call to F-6553c4e9e5b8.
- An indirect call on every path reaching dispatch.
- A call to F-07fef63861ea after dispatch returns normally.

There is no visible rollback, retry, explicit error result, exception handler, or recovery branch for an invalid selected entry.

If a later access fails or a dependency does not return normally, preceding writes may already have occurred. The final byte store is not reached unless both dispatch and the final dependency return normally. Dependencies may overwrite earlier values; the listed direct writes are not guarantees that those values persist through the entire call.

No allocation or release operation is directly identified in the body. Dependencies may allocate, retain, release, or transfer ownership, but none of those effects is established here.

No preservation guarantee applies to globals, the target, the associated object, the entry table, dispatch metadata, or the escaped temporary slot across dependency calls.

Aliasing is not excluded. Earlier writes may affect later reads if these storage regions overlap. The access order must therefore be retained rather than replaced by an assumption that all fields and globals are independent.

No synchronization protocol or atomic increment is established. The function does not itself provide a coherent snapshot of mutable lookup state.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Unless a scenario states otherwise, assume valid non-overlapping storage, stable lookup inputs, a representable increment, and normally returning dependencies. Post-call field values additionally require that dependencies do not overwrite the relevant fields.

### Zero mode and a direct entry

Given mode zero, counter 10, index 2, bound 3, and a non-null entry at position 2:

- The direct target writes include zero at +0x34 and one at +0x10.
- The counter is written as 11 before lookup.
- F-6553c4e9e5b8 is skipped.
- The selected entry is dispatched with 32.
- If dispatch yields byte 0xA7, F-07fef63861ea runs before the final store of 0xA7 at target +0x3C.

### Nonzero mode boundaries

For mode one or mode 4,294,967,295, target +0x34 receives that exact unsigned 32-bit mode and +0x10 receives zero. The maximum unsigned mode is not treated as a negative input to the mode comparison.

### Index equal to bound

Given stable index 4 and bound 4, the bounds comparison fails. No direct table-entry read is selected by that branch. F-6553c4e9e5b8 supplies the entry used for subsequent dispatch.

### Null entry within the bound

Given index 1, bound 3, and a null table entry at position 1, the entry is read and the fallback dependency is then called. The body does not return a separate “not found” result.

### Fallback replacement without intervening mutation

Suppose the fallback changes the temporary associated-object slot to a replacement address:

- The increment has already affected the originally loaded associated object.
- The body makes no corresponding write to target +0x18.
- F-07fef63861ea receives the same slot address.
- **Only if no intervening operation changes the slot** does that final dependency receive the slot still containing the fallback replacement.

### Fallback replacement followed by mutation

If the slot address escapes during fallback and the indirect callable changes that slot through an available reference, the final dependency still receives the same slot address, but the fallback replacement is not guaranteed to remain its contents.

### Final dependency does not return normally

If dispatch yields a byte but F-07fef63861ea does not return normally, the final target +0x3C store is not reached. Earlier writes have already occurred, subject to any subsequent dependency mutations. No rollback is visible.

### Null fallback result

If fallback returns null, the body proceeds toward dispatch-table access through that null result. Graceful failure is not an established behavior.
