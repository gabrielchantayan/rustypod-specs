# F-266e3c63db59

## Purpose

F-266e3c63db59 conditionally copies a byte sequence into storage associated with a destination context, then records a length in that context.

The source describes a leading-byte gate: processing proceeds only when an initially calculated byte extent is nonzero and the first source byte equals zero. The leading byte is excluded from the copy. Every other leading-byte value causes the function to return a global rejection value without performing its explicit destination writes.

The destination layout suggests a payload region followed by length metadata. That interpretation is inferred intent, not a demonstrated capacity guarantee. The function performs no explicit bounds check.

## Interface

### Inputs

The function accepts two address-valued arguments, represented in the supplied source as integer-sized values:

| Input | Required fields |
|---|---|
| Destination context | At byte offset `0x30`, an address identifying destination-associated storage. |
| Source descriptor | At byte offset `0x04`, a 32-bit signed quantity used in extent calculations; at byte offset `0x08`, a source-data address. |

The destination-associated storage has two relevant locations:

| Offset from destination-associated storage | Use |
|---|---|
| `0x410` | First byte of the copy destination. |
| `0x510` | Location receiving a 32-bit length value after the copy. |

The function also accesses two global values:

- A 32-bit scale value used in extent calculations.
- A 32-bit rejection value returned on either explicit rejection path.

These descriptive names do not imply that the globals are immutable, validated, or independently synchronized.

### Output

The result is a 32-bit scalar:

- Zero after the accepted copy-and-length-update path completes.
- The rejection global’s value when the initial extent is zero or the leading source byte is nonzero.

The rejection value is not established to be nonzero. Therefore, a zero return value alone does not necessarily distinguish an accepted operation from rejection.

## Behavior

### 1. Establish the initial extent

The function first saves the scale global in a local scalar. It then calculates an initial extent using another source-level access to that global multiplied by the source descriptor’s quantity field.

The two scale accesses are distinct in the supplied representation. Under stable memory they yield the same value. The contract does not assume that they must agree under external mutation.

The initial extent controls both the first rejection decision and, if accepted, the number of bytes copied. The saved scale value is retained for the later metadata calculation.

If the initial extent is zero:

- The source-data address need not be read.
- No source byte is read.
- The destination-associated storage address is not needed.
- No explicit destination write occurs.
- The rejection global is read and returned.

### 2. Check the leading source byte

For a nonzero initial extent, the function reads the source-data address from offset `0x08` of the source descriptor and reads its first byte as an unsigned value.

Acceptance at this stage is exact:

- A byte value of zero proceeds.
- Every value from 1 through 255 rejects.

On rejection, the function returns the rejection global without performing its explicit copy or metadata write.

The source does not establish a broader interpretation of this byte, such as a type code, protocol version, validity marker, or encoding selector.

### 3. Capture the copy endpoints and extent

After a zero leading byte is observed, the function calculates the copy count as the initial extent minus one, represented in a 32-bit unsigned loop bound.

It reads the source-data address again and advances that address by one byte. This becomes the copy source.

It also reads the address at offset `0x30` of the destination context and adds `0x410`. This becomes the copy destination.

Consequences:

- The leading byte is not copied.
- The pointer used for the leading-byte check and the pointer used for the payload copy come from separate descriptor-field reads.
- The copy uses captured source and destination addresses; it does not reread the descriptor or context pointer on every byte.
- The copy count is fixed before copying begins.

If the source-data address changes between its two reads, the checked leading byte and copied payload can belong to different locations. No locking, validation, or snapshot mechanism is shown.

### 4. Copy in an address-dependent direction

The function chooses the copy direction by comparing the captured destination and source addresses.

If the destination address compares lower than the source address:

- Byte offsets are processed in increasing order, beginning at zero.
- Each source byte is read before the corresponding destination byte is written.

Otherwise:

- Byte offsets are processed in decreasing order, beginning with the last byte of the copy extent.
- Each source byte is read before the corresponding destination byte is written.

This direction selection accommodates overlapping byte ranges under ordinary linear address ordering:

- A destination below the source uses ascending order.
- A destination above the source uses descending order.
- Equal source and destination addresses use descending order.

Equality is not treated as an early exit. A nonzero copy count still causes byte reads and writes at the same addresses.

A zero copy count causes no payload-byte access, regardless of the selected direction. However, the source and destination address fields needed to establish the copy endpoints are still read.

The overlap-preserving interpretation assumes valid ranges and ordinary address ordering. The source does not establish behavior for address wraparound or comparisons outside the actual platform’s supported address model.

### 5. Recalculate and store metadata

After all payload-byte operations finish, the function writes a 32-bit length value.

The stored value is calculated from:

- The scale value saved before the initial extent calculation.
- A fresh read of the source descriptor’s quantity field.
- A subtraction of one from their product.

The destination-associated storage address is also read again from offset `0x30` of the destination context. The metadata store targets offset `0x510` from this freshly obtained address.

The source establishes that these operations occur after the copy. It does not establish the relative evaluation order of the fresh quantity read and the fresh destination-associated address read within the final assignment.

These rereads matter when storage aliases:

- A copy that overwrites the descriptor’s quantity can affect the recorded length.
- A copy that overwrites the context’s destination-associated address can redirect the final metadata store.
- A copy that overwrites the scale global does not replace the scale already saved for the metadata calculation.
- The recorded length need not equal the number of bytes copied if the relevant values differ between their reads.

After the metadata write completes, the function returns zero.

### Arithmetic boundaries

For stable, positive inputs with a representable initial product, the ordinary copy count is that product minus one.

Examples of boundary behavior include:

- Product zero: reject before reading the source pointer or leading byte.
- Product one, with a zero leading byte: copy no payload bytes, store zero, and return zero.
- Product greater than one, with a zero leading byte: copy the product minus one bytes, then store the recalculated length.

A negative initial product is not explicitly rejected. Subtracting one and converting to the unsigned loop bound can produce an extremely large copy count. For example, a representable initial product of negative one yields an unsigned copy count of 4,294,967,294.

The multiplication can exceed the signed 32-bit range. Subtracting one from the minimum signed 32-bit value also exceeds that range. The supplied representation does not establish whether such cases wrap at the machine level or require another interpretation. They must not be treated as validated or safe inputs.

## Side effects

### Explicit writes

An accepted operation can perform:

1. One byte write per copied payload byte, in the selected direction.
2. One final 32-bit metadata write.

Neither rejection path performs these explicit destination writes.

There is no separate clearing, terminator append, padding operation, or write of the leading source byte.

### Capacity and layout interaction

The payload start at `0x410` is 256 bytes before the metadata location at `0x510`. This establishes spacing, not a checked payload capacity.

Under ordinary linear addressing, a copy of 257 or more bytes reaches the metadata location. The final metadata store then occurs after those payload writes. No explicit check prevents this overlap or a still larger overrun.

The accessible size of the destination allocation remains a caller precondition.

The supplied body contains no function calls. There is therefore no callee-mediated ownership behavior to infer.

### Failure and partial effects
