# F-4c45257d6cf7

## Purpose

F-4c45257d6cf7 reads an unsigned leading byte from an input region, stores that value capped at 31 into an output region, then invokes a target obtained from a global slot. The invocation receives pointers immediately after the input and output leading bytes, in output-first order.

The global target is read **after** the output-leading-byte store. The visible behavior therefore does not establish a fixed callee or a target captured before the store. If the output store can overlap writable storage belonging to the target slot, that store can affect which target is subsequently read.

Interpreting the leading byte as a length, count, or record header is **inferred intent**, not established behavior. Capping it does not establish that the invocation processes at most 31 bytes.

## Interface

### Inputs

The function receives two byte-addressed pointers, in this order:

1. **Input pointer:** identifies the leading byte read by the local transformation.
2. **Output pointer:** identifies the leading byte written by the local transformation.

The input value is an unsigned 8-bit quantity ranging from 0 through 255. The local store writes an unsigned 8-bit value ranging from 0 through 31.

There is no visible explicit length, capacity, allocation descriptor, ownership token, or error-output parameter.

### Implicit input: global target slot

The function also reads a global slot supplying the indirect invocation target. This is an implicit input to control flow, distinct from the two explicit pointer arguments.

The representation establishes the target read after the output-leading-byte store. It does not establish:

- The slot’s storage width or target encoding.
- Whether the slot is writable.
- Whether supplied storage can overlap the slot.
- Whether the slot changes between invocations.
- Whether the invoked target preserves the slot.

The value used for target selection must therefore be understood as the value obtained by that post-store read, not an assumed initial or permanent value.

### Outputs and return

The function has no explicit return value. Its directly established output is the leading-byte store. Further effects depend on the selected target.

No result from the indirect invocation is visibly consumed or exposed as this function’s result. Normal completion is represented after the invocation returns. The supplied representation does not establish behavior when the target fails to return, faults, or transfers control elsewhere.

The locally written byte is not necessarily the final value at the output pointer: the selected target may subsequently modify it or affect its storage lifetime.

### Minimum preconditions

For the represented local operations and invocation to proceed validly:

- The input pointer must permit reading one byte.
- The output pointer must permit writing one byte.
- Advancing each supplied pointer by one byte must be valid in the applicable execution model.
- The global target slot must permit the represented read after the output store.
- The target obtained from that read must be valid for the represented invocation and argument interface.

These requirements do not establish the selected target’s complete preconditions. Its required storage extents, alignment, lifetimes, overlap restrictions, and execution-state requirements remain unknown.

A one-byte region can suffice for a local byte access without sufficing for the complete operation. A pointer immediately beyond such a region is not established as safe for the selected target to dereference.

## Behavior

### Established local sequence

The visible ordering is:

1. Read the leading byte through the input pointer.
2. Cap the captured unsigned value at 31.
3. Store the resulting byte through the output pointer.
4. Read the global slot supplying the indirect invocation target.
5. Invoke the target obtained from that read with:
   - first argument: output pointer advanced by one byte;
   - second argument: input pointer advanced by one byte.
6. Return normally if the invocation returns normally and execution otherwise remains valid.

The input-byte read precedes the output-byte write. The output-byte write precedes both target selection and invocation.

There is no visible branch that skips the target read or invocation because the input byte is zero, already within range, or above 31. Invalid execution can prevent later operations from completing; the sequence is not a guarantee of progress despite faults.

The representation does not require an additional ordering claim about the internal evaluation of pointer offsets beyond their use as the stated invocation arguments.

### Leading-byte transformation

For an original input value from 0 through 31 inclusive, the local store writes that same value.

For an original input value from 32 through 255 inclusive, the local store writes 31.

The comparison is unsigned. Values from 128 through 255 are above the bound, not negative.

The transformation is a cap, not a mask, modulo reduction, or subtraction. In particular, an input value of 32 produces a local store of 31, not 0.

No relationship between this byte value and the selected target’s processing extent is established. The captured value is not visibly supplied as a separate scalar argument.

### Widths and arithmetic

The captured input and stored result are each one byte, interpreted as unsigned 8-bit values. Every possible stored result is representable without truncation.

Each invocation argument advances its respective supplied pointer by exactly one byte. This is a byte offset, not an increment by a larger element size.

The visible representation does not establish:

- Machine pointer width.
- Width or encoding of the global invocation target.
- Multibyte fields or byte order within either supplied region.
- A length calculation based on the leading byte.
- Permitted address wraparound.

The one-byte offsets must not be interpreted as permission to wrap an address or to cross otherwise invalid storage boundaries.

### Argument order and layout

The wrapper receives input first and output second. The indirect invocation receives the advanced output pointer first and the advanced input pointer second.

For each supplied pointer, the visible layout identifies only a leading-byte position and a position immediately after it. It does not establish a string, terminator, fixed-size record, payload length, or total region capacity.

Passing an advanced pointer does not itself restrict the selected target’s accessible range. In particular, it does not prove that the target cannot access either preceding leading byte or unrelated global storage.

### Aliasing between supplied regions

There is no visible alias or overlap check.

If both supplied pointers identify the same byte, the original byte is captured before that byte is overwritten. The local result is therefore the cap applied to the original value. Both invocation arguments then identify the same advanced position.

If the output pointer identifies the byte immediately after the input pointer, the local output store changes the byte at the invocation’s second argument before the invocation begins.

The wrapper consequently does not establish snapshot semantics or overlap-safe processing. Complete support for any overlapping arrangement depends on the selected target’s unresolved contract.

### Aliasing with the global target slot

The representation does not establish that the global slot is disjoint from supplied storage.

If the output-leading-byte store overlaps writable bytes used to represent the target, the store occurs before the target is read. Under that condition, target selection uses the slot after the store, not a previously captured target.

The resulting target cannot be calculated from the available evidence: slot width, encoding, byte order, and the particular overlapping byte are unknown. Such a store could leave the selected target unchanged, select another valid target, or leave no valid callable target.

This is a conditional consequence of ordering, not an assertion that the slot is actually writable or reachable through either supplied pointer.

### Overlap affecting subsequent input

Given an output pointer equal to the input pointer advanced by one byte:

- The local store writes the bounded input-leading value at that overlapping position.
- The invocation’s second argument identifies the position just written.

The selected target therefore receives access to potentially modified input storage, not a guaranteed original snapshot.

### Output overlapping the target slot

Suppose the output-leading byte overlaps a writable byte of the global target slot and the input-leading byte is 32:

- The local store writes 31 to the overlapping byte.
- The target slot is then read in its post-store state.
- Any invocation uses the target obtained from that read.

An expectation that the pre-store target must be invoked would contradict the established ordering. The actual selected target and its validity remain unresolved without the slot’s layout and encoding.

### Target changes across invocations

Suppose the slot contains one valid target during an invocation’s post-store read and a different valid target during a later invocation’s post-store read.

Each invocation uses its respective read value. The wrapper does not establish caching of the first target or stable dependency identity.
