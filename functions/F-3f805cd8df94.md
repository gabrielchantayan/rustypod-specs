# F-3f805cd8df94

## Purpose

F-3f805cd8df94 records an incoming 32-bit object-reference value in a caller-provided output region. If that reference is nonzero, it also transfers the existing 32-bit value at byte offset 396 within the referenced object into the output region, then replaces that object field with another supplied 32-bit value.

The established behavior is a small, ordered sequence of memory accesses. The interpretation of the output as a saved state, exchange record, or restoration token is inferred intent only. No subsequent restoration operation, resource management protocol, or object lifecycle is established.

## Interface

The function takes three inputs and returns no value:

| Input | Representation | Established role |
|---|---|---|
| Object reference | A 32-bit value represented as an integer in the supplied source | Always recorded in the second output word. Zero suppresses all object-field accesses. A nonzero value supplies the base address for the field at byte offset 396. |
| Output address | Address of storage accessed in 4-byte units | Receives the object reference at byte offset 4. When the object reference is nonzero, also receives the previously observed object-field value at byte offset 0. |
| Replacement value | An uninterpreted 32-bit value | Written to the object field when the object reference is nonzero. |

The relevant output layout is:

| Byte range relative to output address | Width | Behavior |
|---|---:|---|
| 0–3 | 32 bits | Written only for a nonzero object reference |
| 4–7 | 32 bits | Written on every normal invocation |

The relevant object layout is:

| Byte range relative to object base | Width | Behavior |
|---|---:|---|
| 396–399, equivalently offset `0x18c` | 32 bits | Read and then replaced for a nonzero object reference |

These offsets describe logical access locations, not proof of a complete object structure. No other fields, tags, lengths, or allocation boundaries are established.

The function does not validate its addresses. Successful execution requires the actual accesses on the selected branch to be valid under the execution environment’s address, alignment, and memory-access rules.

For a zero object reference, the output word at byte offset 4 must be writable. The first output word is not accessed by this function on that branch.

For a nonzero object reference, both output words must be writable, and the object field must be readable and writable. The output region and object storage need not be disjoint according to the supplied source; overlapping storage changes the results through the access order described below.

The replacement value has no established type beyond its 32-bit width. In particular, zero is not treated specially.

## Behavior

### Unconditional output update

The first observable memory operation is a 32-bit write of the supplied object-reference value to the output word at byte offset 4.

This write occurs before the zero-reference decision has any effect on object-field access. It also occurs before the object field is read. Consequently, an overlapping output region can modify the object field before that field’s value is captured.

### Zero-reference branch

If the supplied object reference is zero, the function completes after the unconditional output update.

On this branch:

- The second output word becomes zero.
- The first output word is left unchanged by this function.
- No object-field read occurs.
- No replacement-value write occurs.
- The replacement value has no effect on memory.

The function does not initialize the whole output region. A caller must not treat the first output word as newly produced data after a zero-reference invocation.

### Nonzero-reference branch

If the supplied object reference is nonzero, the remaining operations occur in this order:

1. Read the 32-bit field at byte offset 396 from the supplied object base.
2. Write that observed value to the first output word.
3. Write the supplied replacement value to the same object-field address.
4. Return without a result value.

“Previously observed field value” means the value obtained at the field-read step. It does not necessarily mean the value that existed before entry: the earlier write to the second output word may already have changed it through aliasing.

There is no comparison between the old and replacement values. Even when they are equal, the source specifies the same read and write sequence.

### Widths and address arithmetic

Each identified data access is 32 bits, or four bytes. The output offset of 4 follows from indexing one 4-byte element beyond the output base. The object-field offset is 396 bytes, not 396 elements.

The object reference is represented by a 32-bit integer in the supplied source and is used in address formation. The source does not independently establish pointer width, address-space translation, or a portable overflow rule for adding 396 to that value.

This contract therefore does not promise modulo-\(2^{32}\) address wrapping. Inputs for which field-address formation overflows, produces an invalid address, or violates the target’s addressing rules are outside the established successful-access cases.

### Overlapping storage

No disjointness check or temporary buffer is present.

If the second output word occupies the object-field address, the unconditional reference write changes the field before the field read. The first output word consequently receives the object-reference value, rather than the field’s entry value. The final replacement write then changes the shared field/second-output location to the replacement value.

If the first output word occupies the object-field address, the captured value is initially written back to that same location. The subsequent replacement write overwrites it. The final first output word therefore contains the replacement value, not a separately retained copy of the old field.

These are consequences of the established access sequence, not special-case alias handling.

## Side effects

The function directly mutates caller-addressed storage:

- One 32-bit output write occurs on the zero-reference path.
- Two 32-bit output writes and one 32-bit object-field write occur on the nonzero-reference path.
- One 32-bit object-field read occurs on the nonzero-reference path.

Those counts describe access operations, not necessarily distinct storage locations.

No allocation, deallocation, dependency call, explicit global access, logging, or synchronization is shown. Nevertheless, the input addresses could designate globally accessible storage; the absence of named global accesses does not imply an absence of effects visible elsewhere.

Copying a reference or field value does not establish ownership transfer. The function neither acquires nor releases a resource through any visible mechanism. The ownership and lifetime obligations associated with the supplied addresses and copied values remain external to this contract.

There is no error result, rollback mechanism, or explicit recovery path. A failed access may occur after an earlier write has already taken effect. The source does not establish which fault, exception, or termination behavior the execution environment would produce.

No atomicity, thread-safety, or memory-ordering guarantee is established. The stated sequence describes the supplied function’s accesses; it is not a synchronization contract for concurrent callers or observers.

## Acceptance examples

These examples are conditional on valid addresses and supported memory accesses. They are derived from static evidence, not executed tests.

### Zero object reference preserves the first output word

Given an output region whose first word contains an existing marker, a zero object reference, and any replacement value:

- The second output word becomes zero.
- The first output word retains its marker.
- No object-field access is attempted.

It would be incorrect to require both output words to become zero.

### Nonzero reference with disjoint storage

Given a valid nonzero object reference, a field containing `0x11223344`, a separate writable output region, and replacement value `0xaabbccdd`:

- The second output word receives the supplied object-reference value.
- The first output word receives `0x11223344`.
- The object field ends with `0xaabbccdd`.

No behavior for other object fields is implied.

### Zero replacement value

Given a valid nonzero object reference and disjoint output storage, a zero replacement value still selects the nonzero-reference branch:

- The existing field value is captured in the first output word.
- The reference is recorded in the second output word.
- The object field becomes zero.

The branch condition depends on the object reference, not the replacement.

### Second output word aliases the object field

Given a valid nonzero reference and an output address placing its second word exactly at the object-field address:

- The initial output write stores the reference into the field.
- The following field read observes that reference.
- The first output word receives that reference.
- The final field write replaces the shared second-output/field word with the replacement value.

Requiring the second output word to retain the reference would be incorrect for this layout.

### First output word aliases the object field

Given a valid nonzero reference and an output address equal to the object-field address:

- The second output word receives the reference.
- The old field value is read and written to the first output word.
- The final replacement write overwrites that same first word.

The final first output word contains the replacement value.
