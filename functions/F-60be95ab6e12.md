# F-60be95ab6e12

## Purpose

F-60be95ab6e12 populates an eight-byte region of a caller-provided destination using fields from a source record and a selected table entry.

The destination fields comprise five unconditionally populated bytes and three conditionally populated bytes. The conditional fields are first cleared. A flag in the selected table entry determines whether the first conditional field is populated; a separately read source byte then determines whether the remaining two fields are populated.

This is a byte-level transformation, not a validated record-conversion API. The available static evidence establishes offsets, access widths, arithmetic, and control flow. It does not establish application-level meanings for the fields.

## Interface

### Arguments

The function accepts three address-bearing arguments, in this order:

1. **Destination address.** Identifies the storage to modify.
2. **Source address.** Identifies the record supplying the selector and several output bytes.
3. **Context address.** Identifies storage containing the table-base value.

The supplied representation uses integer-valued addresses and a 32-bit table-base load. This contract describes the corresponding 32-bit address model. The actual calling convention, native pointer representation, and rules governing invalid or overflowing address arithmetic are **documented_only** unknowns.

### Return value

The function has no explicit return value. It provides no success indicator, error code, or returned destination address.

### Memory layout

All offsets below are byte offsets from the corresponding address.

| Region | Offset | Access width | Role |
|---|---:|---:|---|
| Context | `0xD4` | 4 bytes | Table-base value |
| Source | `0x02` | 1 byte | Value copied to destination offset `0x04` |
| Source | `0x03` | 1 byte, unsigned | Table-entry selector |
| Source | `0x1E` | 1 byte | Value copied to destination offset `0x08` |
| Source | `0x40` | 1 byte | Addend for destination offset `0x05` |

| Source | `0x42` | 1 byte | Second conditional value |
| Source | `0x43` | 1 byte | Third conditional value |
| Selected entry | `0x30` | 4 bytes | Word whose low eight value bits contribute to destination offset `0x05` |
| Selected entry | `0x38` | 4 bytes | Word whose low eight value bits become destination offset `0x06` |

The selector chooses a table entry at a stride of `0x40` bytes:

**Selected-entry address = table-base value + unsigned selector × 64.**

The selector ranges from 0 through 255. Its scaled displacement therefore ranges from 0 through `0x3FC0`, without overflow in that multiplication. Whether adding that displacement to the table base produces a valid address is not checked.

## Behavior

### Entry selection

Before performing any destination write, the function reads the table-base value and the source selector, computes the selected-entry address, and retains that address for the remainder of the call.

The relative order of the table-base read and selector read within this calculation is not established by the supplied expression. Both precede the first destination write.

The selector is explicitly unsigned. For example, a selector byte of `0xFF` selects displacement `0x3FC0`, not a negative displacement.

Later writes that overlap the context’s table-base storage or the source selector do not cause the function to select another entry. Later reads from the already selected entry can nevertheless observe changes to that entry’s storage.

### Unconditional population

After selecting the entry, the function performs these destination writes in order:

| Order | Destination offset | Stored byte |
|---:|---:|---|
| 1 | `0x04` | Source byte at `0x02` |
| 2 | `0x05` | Low eight bits of the sum described below |
| 3 | `0x06` | Low eight value bits of the four-byte entry word at `0x38` |
| 4 | `0x07` | Entry byte at `0x3D` |
| 5 | `0x08` | Source byte at `0x1E` |
| 6 | `0x09` | Zero |
| 7 | `0x0A` | Zero |
| 8 | `0x0B` | Zero |

The byte stored at destination offset `0x05` is:

**(low eight value bits of the entry word at `0x30` + source byte at `0x40` + 26) modulo 256.**

This is wrapping byte arithmetic, not saturation. Any carry beyond the low eight bits is discarded.

The entry accesses at `0x30` and `0x38` are four-byte reads even though only eight bits of each loaded value affect an output byte. A replacement must not assume that reading a single byte is equivalent in access width, fault behavior, or interaction with special memory. The low eight *value bits* also must not be identified with the lowest-addressed byte without knowing endianness.

The source expression does not establish the relative order of the two operand reads contributing to destination offset `0x05`. Both occur before that byte is written. Each later output assignment obtains its input after the preceding destination assignment has completed.

Signed versus unsigned interpretation of the byte-sized arithmetic inputs does not change the resulting modulo-256 output. The supplied evidence does not establish a broader application-level signed interpretation for these fields.

### Conditional population

Only after all three conditional destination bytes have been cleared does the function read the entry flag at offset `0x3C`.

If the flag is zero:

- Destination offsets `0x09`, `0x0A`, and `0x0B` remain zero.
- Source offsets `0x41`, `0x42`, and `0x43` are not read through this conditional path.

If the flag is nonzero:

1. The function reads source offset `0x41` and writes that byte to destination offset `0x09`.
2. It reads source offset `0x41` again.
3. If the second read equals `0x01`, destination offsets `0x0A` and `0x0B` remain zero.
4. Otherwise, it reads source offset `0x42` and writes destination offset `0x0A`, then reads source offset `0x43` and writes destination offset `0x0B`.

Any nonzero flag enables the first conditional copy; the flag need not equal one.

The two accesses to source offset `0x41` are distinct. The byte copied to the destination is not necessarily the byte used for the comparison. In ordinary stable, nonoverlapping memory they agree. With overlapping storage or externally changing memory, they may differ.

There is no further processing after this conditional population.

### Overlap and read timing

The function does not snapshot the source record or table entry before writing the destination. Overlap therefore matters.

For example:

- An early destination write can alter a source field that is read later.
- Clearing destination offsets `0x09`–`0x0B` can alter the entry flag before it is read.
- Writing destination offset `0x09` can alter source offset `0x41` before its second read.
- Writing destination offset `0x0A` can alter source offset `0x43` before its read.

These are consequences of the access order, not explicit overlap-handling features. No evidence establishes that the surrounding API promises support for overlapping arguments. A contract-preserving implementation must either preserve these ordered-access consequences or rely on an independently established nonoverlap precondition; none is supplied here.

## Side effects

On an ordinary completed execution, the function explicitly writes only destination offsets `0x04` through `0x0B`. It does not initialize the preceding four destination bytes or any trailing storage.

The three conditional bytes always receive an initial zero write, even when subsequently overwritten. Consequently, an implementation that merely computes final values and writes each byte once would not preserve the complete write sequence.

Arguments are used as access locations; no evidence indicates that ownership is consumed or retained. Aliasing can make destination writes also modify storage described as source, context, or table memory.

Execution is not transactional. If a later access fails, earlier writes may already have occurred. The exact fault mechanism and resulting process behavior are outside the supplied evidence.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence. **They have not been executed.** Except where overlap is explicitly stated, assume valid, stable, nonoverlapping ordinary memory.

### Disabled conditional fields

Given:

- Source `0x02` = `0xA5`
- Source `0x1E` = `0x7C`
- Source `0x40` = `0x03`
- Selected-entry word `0x30` = `0x123456F0`
- Selected-entry word `0x38` = `0x89ABCDEF`
- Entry `0x3D` = `0x22`
- Entry flag `0x3C` = zero

Destination offsets `0x04` through `0x0B` finish as:

**`A5 0D EF 22 7C 00 00 00`**

The arithmetic byte is `0xF0 + 0x03 + 0x1A`, reduced modulo 256. No conditional-path reads of source `0x41`–`0x43` occur.

### Enabled flag with comparison value one

If the entry flag is `0x80` and both reads of source `0x41` return `0x01`, destination `0x09` finishes as `0x01`. Destination `0x0A` and `0x0B` finish as zero. Source `0x42` and `0x43` are not read.

This demonstrates that the flag is tested for nonzero, whereas the source comparison is specifically against one.

### Enabled flag with comparison value zero

If the flag is nonzero, both source `0x41` reads return zero, source `0x42` is `0x66`, and source `0x43` is `0x99`, the final conditional bytes are:

**`00 66 99`**

Zero does not suppress the last two copies. Only comparison value `0x01` does.

### Maximum selector

For selector `0xFF`, the entry address is the table base plus `0x3FC0`, provided that addition and the resulting accesses are valid. No clamp or fallback entry is selected.

### A write changes the comparison read

Suppose destination offset `0x08` aliases source offset `0x41`, source offset `0x1E` contains `0x01`, and the entry flag remains nonzero.

The unconditional write to destination `0x08` places `0x01` into source `0x41` before either conditional read. The conditional copy therefore writes `0x01` to destination `0x09`, and the second read suppresses the final two copies.

This illustrates why an initial snapshot of source values would not generally preserve behavior.
