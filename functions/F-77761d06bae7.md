# F-77761d06bae7

## Purpose

F-77761d06bae7 requests storage for an object, initializes selected fields, resolves a provider, installs named facilities, and conditionally attempts to open a resource. On normal return, it writes an object address or zero to a caller-supplied output location and returns a status reduced to eight bits.

“Provider,” “registration,” and “resource opening” are inferred roles based on arguments and subsequent use. The established behavior is the visible sequence of memory accesses, dependency calls, branches, publication, and status conversion.

An error does not necessarily produce a null output. Only a final status equal to the full 32-bit value 7 causes the cleanup dependency to run and the published address to be replaced with zero. Other statuses can accompany a nonzero address to a partially initialized object.

## Interface

| Input | Representation | Established use |
|---|---|---|
| Resource input | Opaque 32-bit value | Forwarded unchanged to F-94e50f72111d; not directly dereferenced here. |
| Output location | Address of a writable 32-bit slot | Receives the selected object address immediately before normal return. |
| Requested flags | Unsigned 32-bit value | Masked for object storage and for F-94e50f72111d. |
| Provider selector | Opaque 32-bit value | Passed to F-2e88c9fc2422 and, on a zero resolution result, to F-a061acf353ed. |

The return is a 32-bit unsigned value in the range 0–255. It contains the low eight bits of the final result from F-0b90d48d906b; the upper 24 bits are zero.

Addresses and word-sized fields are 32 bits in the supplied representation. Byte stores affect one byte. All object offsets below are byte offsets.

The function requests 0x180 bytes, or 384 bytes. Successful allocation alone does not establish valid initialization: the function reads some object state before explicitly assigning it, and dependencies can affect subsequently accessed state.

Normal completion requires:

- A valid output slot that remains writable until publication.
- Writable storage for every direct object access.
- Valid targets for accesses through object-held pointers.
- Initial-state guarantees sufficient for the reads described below.
- Dependencies returning normally and leaving any subsequently used memory accessible.

No explicit validation of these requirements is visible. In particular, the output slot is not initialized early, and no defined recovery is established for invalid or destructively aliased pointers.

## Behavior

### Allocation and initial writes

The first call is F-1c177d5ba9f6 with size 0x180.

If it returns zero, the initialization body is skipped. Execution still reaches the final F-0b90d48d906b call with a zero object address. Allocation failure does not directly determine the returned status.

For a nonzero allocation, the following operations occur in order:

| Order | Access or operation |
|---:|---|
| 1 | Store word 8 at +0x4c. |
| 2 | Store word 0x000000ff at +0x18. |
| 3 | Store word zero at +0x38. |
| 4 | Read and retain an initialization-state global. |
| 5 | Store word zero at +0x3c. |
| 6 | Store word 2 at +0x04. |
| 7 | Store the retained initialization-state value at +0x40. |
| 8 | Store the address of the allocation at +0x14c into +0x08. |
| 9 | Call an unidentified external dependency with destination +0x50, a global-supplied source value, and 0x28. |
| 10 | Store byte 1 at +0x1c. |
| 11 | Store byte 0xff at +0x21. |
| 12 | Store word zero at +0x24. |
| 13 | Read the word at +0x0c, combine it with 0x00008040 by bitwise OR, and write the result back. |

The +0x0c operation preserves existing bits; it is not a complete initialization. Its prior contents therefore matter.

The unidentified external call has the shape of a transfer operation, but neither its identity nor the units of its third argument are established. A 40-byte copy must not be assumed.

F-c247d7bfe027 is then called three times, with trailing arguments 3 and 0. Its first argument addresses these object-relative regions, in order:

1. +0x114.
2. +0x128.
3. +0x0f4.

The direct return values are ignored. No preservation of object fields or globals by these calls is established.

### Provider resolution

F-2e88c9fc2422 receives the provider selector. After it returns, the function:

1. Reads and retains a fallback-state global.
2. Stores the provider result as a word at +0x00.

The fallback value is captured after provider resolution, not before it, and before storing the provider result.

If the provider result is zero:

1. The retained fallback value is stored at +0x40.
2. F-a061acf353ed receives the object, status 1, a fixed diagnostic-format address, and the original provider selector.
3. Execution proceeds to final status handling.

This branch does not perform named registrations, facility lookups, or resource opening. The diagnostic is apparently about an unavailable provider, but its formatting and interpretation depend on F-a061acf353ed.

### Initial named registrations and first gate

A nonzero provider result causes four calls to F-8685dec604a9:

| Order | Name | Two numeric arguments after name | Callback/data argument | Final argument |
|---:|---|---|---|---:|
| 1 | BINARY | 1, 0 | Shared global-supplied value | 0 |
| 2 | BINARY | 3, 0 | Shared global-supplied value | 0 |
| 3 | BINARY | 2, 0 | Shared global-supplied value | 0 |
| 4 | RTRIM | 1, 1 | Shared global-supplied value | 0 |

Every call receives the object first. The direct results are ignored.

The callback/data global is supplied separately at each call site. An earlier dependency may change it; the four arguments are not contractually one captured value.

After all four calls, the byte at +0x1e is read. This byte is distinct from the explicitly initialized bytes at +0x1c and +0x21.

If +0x1e is nonzero, the function stores the retained fallback value at +0x40 and proceeds to final status handling. All subsequent lookups, NOCASE registration, and resource opening are skipped.

If +0x1e is zero, the precise sequence is:

1. Call F-4a95613e1504 with the object, 1, BINARY, 6, and 0.
2. After that call returns, read and retain a second callback/data global.
3. Store the BINARY lookup result as a 32-bit address at +0x2c.
4. Call F-8685dec604a9 with the object, NOCASE, 1, 0, the retained second callback/data value, and 0.
5. Reread the address currently stored at +0x2c.
6. Store byte 1 at offset +5 through that reread address.
7. Call F-4a95613e1504 with the object, 1, NOCASE, 6, and 0.
8. If this second lookup returns nonzero, store byte 2 at offset +5 through its returned address.

The second callback/data global is captured **before** the BINARY lookup result is stored at +0x2c. The NOCASE registration receives that captured value.

The BINARY marker write has no null check. Its target is determined by rereading +0x2c after NOCASE registration, not by retaining the earlier lookup result. Thus, even a valid BINARY lookup result does not establish that the later write is valid: the intervening dependency may change the field.

The NOCASE marker write is conditional on a nonzero lookup result, but no further target validation is visible.

### Flag transformation and opening attempt

The function forms a 32-bit masked value using 0xffff80f7. This clears bit 3 and bits 8 through 14, counting bit 0 as the least significant bit. All other bits are preserved.

That masked value is stored at +0x10.

F-94e50f72111d then receives, in order:

1. The object.
2. The unchanged resource input.
3. Zero.
4. The integer 2000.
5. The masked flags with bit 8 forced on.
6. An address four bytes beyond the pointer currently stored at +0x08.

The stored flags always have bit 8 clear; the opening-call flags always have it set. The transformation uses bitwise masking and OR, not arithmetic addition.

The output address is derived from the current +0x08 field. Although that field was initially assigned the allocation address plus 0x14c, no dependency-preservation guarantee establishes that it still has that value.

If F-94e50f72111d returns a nonzero 32-bit result:

1. F-a061acf353ed receives the object, the complete opening result, and zero.
2. The retained fallback value is stored at +0x40.
3. Execution proceeds to final status handling.

The opening result is neither truncated before that diagnostic call nor returned directly by this function.

### Successful-opening initialization

A zero opening result leads to the following ordered operations through the pointer field at +0x08:

| Order | Operation |
|---:|---|
| 1 | Read the current +0x08 pointer, then read a word at its +0x04 offset. Pass that word and the object to F-96819d3b47ed. |
| 2 | After the call returns, read the current +0x08 pointer and store the returned word at its +0x14 offset. |
| 3 | Call F-96819d3b47ed with the object and zero. |
| 4 | After that call returns, read the current +0x08 pointer and store the returned word at its +0x2c offset. |
| 5 | Store a fixed static address at offset +0x00 through the current +0x08 pointer. |
| 6 | Store byte 3 at offset +0x09 through the current +0x08 pointer. |
| 7 | Store another fixed static address at offset +0x18 through the current +0x08 pointer. |
| 8 | Store byte 1 at offset +0x21 through the current +0x08 pointer. |
| 9 | Read a success-state global and store its word value at object offset +0x40. |

The field at +0x08 is consulted again after dependency calls. The read supplying the first F-96819d3b47ed argument and the destination receiving its result may therefore use different base addresses.

If the initial +0x08 assignment remains unchanged, these accesses lie within the requested allocation. That observation does not establish pointer preservation or dependency write bounds.

The static addresses appear to identify named subobjects, but their contents and semantic roles are not established.

After the success-state assignment, the byte at +0x1e is read again:

- If nonzero, execution proceeds directly to final status handling. There is no direct fallback-state assignment on this branch.
- If zero, the following calls occur in order:
  1. F-a061acf353ed with the object, zero, and zero.
  2. F-48141463f6eb with the object.
  3. F-8444dd50b4c6 with the object.
  4. F-0b90d48d906b with the object.

If this intermediate status result is exactly zero, F-a061acf353ed is called again with only two visible arguments: the object and zero. A missing visible argument must not be treated as an explicit zero.

The intermediate status does not replace the final status query.

### Final status, cleanup, and publication

Every normally returning path reaches a final call to F-0b90d48d906b with the allocation address, which may be zero.

The full 32-bit final result controls cleanup:

- Exactly 7: call F-ff6d0e3505c3 with the object address, then select zero for publication.
- Any other value: do not make this cleanup call; select the allocation address for publication.

The selected address is then written to the output slot. The function returns the final status masked with 0xff.

The equality comparison precedes truncation. Consequently, status 0x00000107 returns 7 without triggering cleanup.

## Side effects

Direct writes affect the allocated object, memory reached through object-held or dependency-returned addresses, and the caller’s output slot.

The output write occurs after the final status query and any cleanup call. There is no earlier output initialization. A nonreturning dependency or invalid memory access may prevent publication entirely.

No direct global writes are visible. Global reads occur at distinct stages, and dependencies may change globals between those reads. A retained value need not equal the global’s later contents.

Ownership is only partially established:

- Storage is requested from F-1c177d5ba9f6.
- Its address can be published even after an error.
- F-ff6d0e3505c3 receives that address when the full final status equals 7.
- The cleanup dependency’s actual release, closure, and ownership behavior is unknown.

A nonzero published address does not establish successful opening or complete initialization. A returned value of 7 does not by itself establish cleanup. A zero published address does not establish that any allocation was released.

Dependencies may modify object state, globals, resources, or external systems. Their effects are not restricted to their inferred roles.

## Acceptance examples

These are conditional consequences of the static evidence, not executed tests. Unless an example specifically concerns an invalid access, assume dependencies return normally and all required accesses are valid.

1. **Allocation returns zero.** Initialization and provider resolution are skipped. The final status dependency receives zero, and zero is published. If the final status is exactly 7, cleanup also receives zero before publication.

2. **Provider resolution returns zero; final status is 1.** The fallback global is captured after resolution. The provider result is stored at +0x00, then the retained fallback value at +0x40, followed by the diagnostic call. No named registrations or opening occur. The allocation address is published, and the return is 1.

3. **The first +0x1e read is nonzero.** All four initial registrations have occurred. Neither lookup nor NOCASE registration nor opening occurs. The retained fallback value is assigned at +0x40 before final status handling.

4. **BINARY lookup returns an address and the second callback/data global contains a value at capture time.** The global read occurs before storing that address at +0x2c. The NOCASE registration receives the captured value. The subsequent marker write uses a fresh read of +0x2c.

5. **NOCASE registration replaces +0x2c with a different valid address.** Byte 1 is written at offset +5 through the replacement address, not necessarily through the BINARY lookup result.

6. **The address reread from +0x2c is zero.** The function attempts the unguarded byte write at offset +5 through that zero base. No graceful error result for this condition is established.

7. **Requested flags are 0xffffffff.** If opening is reached, +0x10 receives 0xffff80f7 and F-94e50f72111d receives flags 0xffff81f7.

8. **Opening returns a nonzero value.** That complete value is forwarded to F-a061acf353ed. Successful-opening initialization is skipped, and the fallback assignment follows the diagnostic call. The eventual return still depends on the final status query.

9. **Opening succeeds and the second +0x1e read is nonzero.** The embedded writes and success-state assignment have occurred. Post-open processing calls and the intermediate status query are skipped. The path does not directly replace the success state with fallback state.

10. **Opening succeeds, the second gate is zero, and intermediate status is zero.** Both post-open processing dependencies run. The intermediate query is followed by the two-visible-argument F-a061acf353ed call. A separate final query determines publication and return.

11. **Final status is exactly 7.** Cleanup precedes publication; zero is published; the return is 7.

12. **Final status is 0x00000107.** Cleanup is not called. The allocation address is published, and the return is 7.

## Uncertainties

The following remain **documented_only**:

- Semantic object type, provider interpretation, resource-input encoding, and numeric registration-argument meanings.
- Initialization guarantees for the read-modify-write word at +0x0c and the gate byte at +0x1e.
- The unidentified external dependency’s operation, transfer extent, and units.
- Dependency signatures, side effects, global preservation, pointer preservation, and memory ownership.
- Whether the cleanup dependency frees storage, closes resources, or performs other actions.
- Meanings of state-global values and the two static addresses.
- The calling convention behind F-a061acf353ed’s differing visible argument counts.
- Behavior on invalid pointers, dependency failure outside normal return, or concurrent mutation.
- Thread safety, reentrancy, and synchronization requirements.
- Behavior omitted from the supplied representation. Its annotations about removed unreachable regions do not independently establish additional behavior.
