# F-84370e32ba69

## Purpose

F-84370e32ba69 conditionally extracts two 16-bit values from a four-byte input prefix and then attempts three ordered invocations of F-87bda57f63f9.

On represented normal-return paths, the function returns a 32-bit value of either zero or one. It returns one only when the unsigned size argument exceeds three and all three dependency invocations return nonzero results.

Failure is not transactional. When the size gate passes, both prefix stores occur before any dependency invocation. The function does not undo those stores or any dependency effects when it returns zero. Conversely, the stores do not guarantee final destination contents: a dependency invocation may subsequently modify either destination through aliases.

The established behavior is extraction followed by conditional dispatch. The meanings of the extracted values and the operations performed by the dependency are not established.

## Behavior

### Size gate

The function first compares N with three using an unsigned comparison.

For N equal to zero, one, two, or three, it returns zero without:

- Reading any prefix byte.
- Writing either destination.
- Invoking F-87bda57f63f9.

Every other unsigned 32-bit value passes the gate. Values with the high bit set are not rejected as negative sizes.

### Prefix extraction and stores

After the gate passes, the function forms B, four bytes beyond the input base.

It then constructs the first 16-bit value from the first two input bytes:

- Byte zero supplies bits 15 through 8.
- Byte one supplies bits 7 through 0.

That value is stored to the first destination before the extraction and store of the second value.

The second 16-bit value uses:

- Byte two as bits 15 through 8.
- Byte three as bits 7 through 0.

That value is stored to the second destination. Both destination stores precede the first dependency invocation.

The input encoding is therefore most-significant-byte first for each value. The stores write 16-bit scalar values; the supplied representation does not independently establish the byte order of those values in destination memory.

Within each two-byte extraction, the representation establishes which bytes contribute and their significance, but not a portable relative evaluation order for the two individual reads. Both reads needed for the first value precede its store. That store precedes the reads used to construct the second value.

There are no null checks, overlap checks, or destination-capacity checks.

### First dependency invocation

The first invocation of F-87bda57f63f9 receives:

1. B.
2. N, unchanged.
3. The fifth argument, unchanged.

The address skips the four-byte prefix, but the size-like argument is not reduced by four. This is established argument construction, not evidence that the resulting extent is safe.

If R1 is zero, the function returns zero and makes no further dependency calls.

If R1 is nonzero, execution continues. There is no check that R1 is positive, no check that it is at most N, and no check that advancing B by R1 identifies valid storage.

### Second dependency invocation

After a nonzero R1, the function computes L1.

The subtraction is represented as unsigned 32-bit arithmetic, followed by retention of only the low 16 bits. Consequently, L1 is between zero and 65,535 inclusive, including when subtraction underflows.

The second invocation receives:

1. B advanced by R1 bytes.
2. L1, with all bits above bit 15 clear.
3. The sixth argument, unchanged.

The address displacement uses the full signed result R1. It is not reduced to its low 16 bits.

If R2 is zero, the function returns zero without a third invocation.

If R2 is nonzero, execution continues without checking its sign or its relationship to L1.

### Third dependency invocation

After nonzero R1 and R2, the function computes L2 by subtracting R2 from L1 using the represented unsigned 32-bit arithmetic and retaining the low 16 bits.

The third invocation receives:

1. The address formed by advancing B by R1 bytes and then by R2 bytes.
2. L2, with all bits above bit 15 clear.
3. The seventh argument, unchanged.

The source represents successive address advances. It does not establish a separate signed 32-bit addition of R1 and R2 before address formation. Address validity and overflow behavior remain subject to the target address model.

If R3 is zero, the function returns zero. Otherwise, it returns one.

No fourth invocation occurs. The function does not use R3 to advance an address or compute a remaining extent.

### Arithmetic and success conditions

The two retained subtraction results are modulo 65,536. Underflow does not itself cause rejection.

Negative dependency results pass the nonzero checks. For R1 and R2, they also participate in address displacement and subtraction. This establishes the wrapper’s treatment of those results, not that the dependency permits negative results.

Success requires only the size gate and three nonzero results on normal-return paths. It does not require:

- Positive dependency results.
- Monotonic forward address movement.
- A zero remaining extent.
- Consumption of all supplied storage.
- A sum of results equal to N.
- Preservation of the prefix values after the dependency calls.

The function adds no explicit recovery path for invalid accesses, abnormal dependency termination, or other execution failures.

## Side effects

### Direct memory effects

When N exceeds three, the function directly performs two ordered 16-bit stores. The first is to the third argument’s destination; the second is to the fourth argument’s destination.

Both occur before the first dependency call, including when that call subsequently returns zero. There is no wrapper-level rollback on any failure path.

These are statements about stores that occur, not guaranteed final memory contents. The dependency may overwrite either destination before returning, including before returning zero.

The function contains no explicit allocation, deallocation, ownership transfer, or direct global-state update. This does not establish that dependency invocations lack such effects.

### Aliasing and observable ordering

If both destinations designate the same valid 16-bit object and do not overlap the input, the second store replaces the first before dependency execution. That object retains the second value only if no later effect changes it.

If the first destination overlaps input bytes two or three, its store can change the bytes used for the second extraction. The function does not snapshot all four prefix bytes before writing outputs. The second value reflects the bytes read after the first store, subject to valid target access semantics.

If either destination overlaps storage later accessed by the dependency, the dependency is called after both stores and may observe their effects.

Partial overlaps depend on native storage representation, alignment, and access validity. The function supplies no special overlap handling.

### Dependency effects and ownership

A zero return does not imply that completed dependency invocations had no effects. A one return does not imply that the extracted output values remain intact.

No available dependency contract establishes whether an invocation:

- Modifies input storage or either destination through aliases.
- Changes global or shared state.
- Allocates or releases memory.
- Retains, transfers, or consumes resources.
- Preserves storage or resources needed by a later invocation.
- Returns normally for every argument combination.

The wrapper performs no explicit lifetime or ownership check between calls. Later calls are reached after nonzero results, but safe composition still depends on the dependency’s actual effects and requirements.
