# F-dd27e24bc327

## Purpose

F-dd27e24bc327 obtains a node, copies an eight-byte input value into its payload, attaches the node at a caller-selected position, performs color-dependent structural repair, and writes the obtained node’s address to an output location.

The established behavior is defined by the accesses, conditions, dependency calls, and ordering below. Red–black-tree insertion is inferred intent: the routine examines parents and uncles, recolors nodes, invokes complementary structural helpers, and assigns color one to the final root.

The routine does not search for an insertion position. The caller supplies a parent and a side hint. A comparison dependency selects the attachment side only when the parent is not the current header and the hint is zero.

No explicit success status, duplicate rejection, allocation-failure recovery, or rollback is present.

## Behavior

### Node acquisition and payload transfer

F-57a123ecc9c9 is called first, with the container address.

Payload copying is conditional on the obtained node address plus 0x10 being nonzero. When that condition holds, the first input word is read and written to node offset 0x10 before the second input word is read and written to node offset 0x14.

This is an ordered pair of four-byte transfers, not an established atomic eight-byte copy. If the first destination overlaps the second source word, the second read can observe the first write.

The condition is not a null-node check. Under wrapping 32-bit address arithmetic, it excludes an obtained address of 0xFFFFFFF0, whereas zero passes the condition and leads to writes at addresses 0x10 and 0x14. The underlying exceptional-address semantics remain documented_only. No clean allocation-failure behavior follows from this guard, and skipping the payload copy does not skip later node accesses.

### Count update and attachment selection

After the conditional copy, the four-byte count-like field at container offset 0x14 is read, incremented by one, and written back. This precedes comparison, attachment, and repair.

No overflow check or saturation is shown. The supplied representation expresses signed 32-bit addition; its behavior at the signed overflow boundary is unresolved. Modulo-2³² behavior is not an established contract.

The current header address is then read from container offset 0x10. The first attachment branch is selected when either the supplied parent equals that header or the side hint is nonzero.

Otherwise, F-bcefa5957e76 is called with:

1. The container address plus 0x19.
2. The original value address.
3. The supplied parent address plus 0x10.

A nonzero result selects the first attachment branch; zero selects the second. Comparison therefore examines the original input location, not necessarily an unchanged copy of the new node’s payload.

On entering this comparison path, two saved 32-bit operands used by a later structural-helper invocation are both set to zero. Without comparison, they retain the original side hint and supplied parent address. The comparison result does not change this distinction.

### Attachment writes

In the **first attachment branch**, the supplied parent’s 0x08 field receives the new node address. The header address is then reloaded.

- If the reloaded header differs from the supplied parent, its 0x08 field is read and replaced with the new node address only if it equals the supplied parent.
- If the reloaded header equals the supplied parent, its 0x04 field receives the new node address. The header address is reloaded again, and that header’s 0x0C field unconditionally receives the new node address.

With a stable header and a header-valued parent, these writes populate header offsets 0x08, 0x04, and 0x0C in that order.

In the **second attachment branch**, the supplied parent’s 0x0C field receives the new node address. The header address is then reloaded, and its 0x0C field is replaced with the new node address only if the field currently equals the supplied parent.

Both branches finish by writing the supplied parent address into the new node’s 0x04 field.

Header reloads occur after preceding writes and, where applicable, after comparison. They must not be replaced conceptually with a header captured before those operations. Neither helper preservation nor harmless aliasing is established.

There is no direct initialization of the obtained node’s color or child fields.

### Repair entry and stopping conditions

Repair initially uses the new node as its working node.

Each iteration first reloads the container’s header and that header’s root. If the working node equals the root, repair stops without reading its parent’s color.

Otherwise, the working node’s parent address and the parent’s color byte are read. Any nonzero parent color stops repair. A zero parent color causes the routine to obtain the grandparent through the parent link and inspect the grandparent’s left child.

Color zero enables repair; nonzero suppresses it. Direct color writes use zero and one. Other nonzero byte values are accepted by branch conditions rather than automatically normalized.

### Parent on the grandparent’s left side

If the parent equals the grandparent’s left child, the uncle is captured from the grandparent’s right-child field.

A nonnull uncle with color zero selects recoloring:

- The captured parent and uncle receive color one, in that order.
- The working node’s current parent and grandparent links are followed to write color zero to the grandparent.
- Those links are followed again to select the next working node.

No structural helper is called in that iteration.

For a null uncle or an uncle with nonzero color, structural adjustment is selected. If the working node is the captured parent’s right child, F-a3d85cb09a50 is called with the container and captured parent; the working node then becomes that captured parent.

The working node’s current parent receives color one. Its current grandparent receives color zero. F-d202fbc49f1c is then called with the container and a grandparent address obtained through current parent links.

The ancestry used after a helper call is read after that call. The final helper pivot is also obtained after the preceding color writes; it is not specified solely by the ancestry captured at iteration entry.

### Parent not on the grandparent’s left side

Otherwise, the captured grandparent’s left child is treated as the uncle. The routine does not separately verify that the parent is the right child.

A nonnull zero-colored uncle selects the same recoloring-and-upward progression described above.

For a null uncle or a nonzero-colored uncle, the routine checks whether the working node is the captured parent’s left child. If so, it invokes F-d202fbc49f1c using the six displayed operands specified under Dependencies, then makes the captured parent the working node.

It next writes color one to the working node’s current parent, writes color zero to its current grandparent, and calls F-a3d85cb09a50 with the container and a grandparent address obtained through current links after those writes.

### Finalization

After repair stops, the routine reloads the header, reads its root address, and writes one to that root’s color byte. There is no null-root check.

Only then does it write the originally obtained node address to the result location. If that location aliases tree storage, this last write can modify the structure after repair and final recoloring.

## Acceptance examples

These are conditional static examples, not executed tests. They assume valid reached storage and dependency effects compatible with the stated scenario.

### Insertion using the header as parent

With a stable header equal to the supplied parent, comparison is skipped regardless of the hint. After payload handling and count increment, header offsets 0x08, 0x04, and 0x0C receive the new node address in order. The new node’s parent becomes the header.

Repair immediately recognizes the node as root. Its color becomes one before its address is written to the result location.

### Hint-selected first branch

With a non-header parent and a nonzero hint, comparison is skipped. The parent’s left-child field receives the new node. The header’s 0x08 field changes only if its later-read value equals the supplied parent. This attachment branch does not directly update header offset 0x0C.

### Comparison-selected second branch

With a zero hint, a non-header parent, and comparison result zero, comparison occurs after payload handling and count increment. The parent’s right-child field receives the new node. Header offset 0x0C changes only if it equals the supplied parent at the conditional read.

Both saved operands for any later six-operand call are zero, regardless of the original parent address.

### Nonzero parent color

For a non-root working node whose parent color is nonzero, repair stops without a repair-time structural-helper call. Final root recoloring still occurs. If the parent is not that final root and does not alias another write target, its nonzero color is not normalized by this stopping condition.

### Zero-colored uncle

With a zero-colored parent and a nonnull zero-colored uncle, the captured parent and uncle receive one, then the current grandparent receives zero. Repair advances through reread ancestry. Neither structural helper is called during this iteration.

### Mirrored inner case with null uncle

Suppose the parent is not the grandparent’s left child, that left-child value is null, and the working node is the parent’s left child.

F-d202fbc49f1c is invoked before recoloring, with a zero third operand and the captured 32-bit grandparent address as its fourth operand. If comparison was skipped, operands five and six retain the original hint and supplied parent. Current-ancestry recoloring and F-a3d85cb09a50 follow.

### Mirrored inner case with nonzero-colored uncle

Under the same structural conditions but with a nonnull uncle whose captured color is 0xA5, the third operand is that uncle’s captured address and the fourth is 0x000000A5, not the grandparent address.

If comparison was entered earlier, operands five and six are both zero, whether comparison returned zero or nonzero.

### Obtained address zero

If F-57a123ecc9c9 supplies zero, the payload guard does not reject it under the described 32-bit interpretation. Clean failure, an unchanged count, and a null output are not established outcomes.
