# F-bc1164d6ef99

## Purpose

F-bc1164d6ef99 updates three 64-bit fields in a state object. A signed comparison selects between a record-derived update and a sentinel update.

On the record-derived path, the function publishes a record’s base value, multiplies its coefficient by a signed 32-bit state operand, and passes the resulting two-word product together with a context word to F-1e0edc6e0bc9. It stores the dependency’s result and then stores that result plus the previously captured base.

On the sentinel path, it sets the base and final fields to the maximum signed 64-bit value and clears the intermediate field.

The application meaning of these values is not established. In particular, the source does not establish units, the dependency’s mathematical operation, or the semantic meaning of the sentinel.

This contract describes static evidence only. No runtime tests have been performed.

## Behavior

### Selection

The function first reads the descriptor address from state offset `0x8C`, then reads the signed index from state offset `0x58`. It compares that index with the signed count at descriptor offset `0x00`.

The record-derived path is selected exactly when:

**signed index < signed count**

Otherwise, the sentinel path is selected.

Consequences include:

- An index equal to the count selects the sentinel path.
- An index greater than the count selects the sentinel path.
- A negative index is not independently rejected.
- A negative count does not necessarily select the sentinel path: a still-smaller signed index passes the comparison.

The descriptor address and index obtained here are retained for subsequent record selection. The function does not reread the count or reevaluate the branch.

### Record-derived path: capture and publish the base

The function reads the record-array address from descriptor offset `0x04` and calculates the selected record address using the captured index and the `0x18`-byte stride.

The address calculation uses 32-bit quantities. No explicit overflow handling or bounds check is present. The source does not justify treating overflow in its signed address expressions as a portable wrapping guarantee.

The base is then accessed and published in this order:

1. Read the base’s high 32-bit word at record offset `0x0C`.
2. Capture the full 64-bit base at record offset `0x08` for the eventual final addition.
3. Read the base’s low 32-bit word at record offset `0x08`.
4. Write that low word to state offset `0x40`.
5. Write the high word obtained in the first step to state offset `0x44`.

**All three base reads occur before the first publication write.** Therefore, with stable ordinary memory and completed publication stores, overlapping state and record storage alone cannot make the captured base differ from the published base.

The separate reads do matter under concurrent mutation or unusual memory-read semantics: the high-word read, full-width capture, and low-word read need not then describe the same observed value. The function provides no synchronization or snapshot mechanism.

The source expresses the full-width capture as a 64-bit read. Its underlying physical access granularity and atomicity are not established.

### Record-derived path: select the coefficient

After publishing both base words, the function reads the operand from state offset `0x5C`.

It then rereads the record-array address from offset `0x04` of the previously captured descriptor and calculates a record address again using the captured index. It reads the coefficient’s low and high words from this second selected address.

This second array-address read is significant. Earlier publication writes can alter the descriptor’s array-address field through aliasing. In that case, the coefficient may come from a different location than the base.

The function does not reload the descriptor address from the state or reload the index. Changes to those state fields do not replace the values already captured for selection.

### Record-derived path: product

The coefficient contributes a 64-bit bit pattern. The operand contributes a signed 32-bit multiplier.

To specify the word arithmetic, let:

- **U** be the operand’s unsigned 32-bit bit pattern.
- **L** be the coefficient’s unsigned low word.
- **H** be the coefficient’s unsigned high word.
- **S** be zero if the operand’s sign bit is clear, and negative one otherwise.

The product’s low word is the low 32 bits of **U × L**.

Its high word is the low 32 bits of:

**S × L + U × H + floor((U × L) / 2³²)**

Thus, the resulting 64-bit bit pattern is the low 64 bits of the coefficient multiplied by the signed 32-bit operand. Choosing signed or unsigned interpretation for the same coefficient bit pattern does not change those low 64 result bits.

The product is staged in this order:

1. Write the high word to state offset `0x54`.
2. Write the low word to state offset `0x50`.

There is no multiplication overflow report or saturation.

### Record-derived path: dependency and final result

After staging the product, the function reads the 32-bit context word at offset `0x64` and invokes F-1e0edc6e0bc9 with four 32-bit argument words:

| Position | Value |
|---|---|
| First | Computed product low word |
| Second | Computed product high word |
| Third | Context word |
| Fourth | Zero |

The product arguments come from the computed values, not from rereading the staged intermediate field.

Because the context read occurs after the base and product stores, aliasing with those destinations can affect the context word supplied to the dependency.

On normal return, the dependency supplies a 64-bit result. The function then:

1. Stores that result at state offset `0x50`.
2. Adds it to the previously captured full-width base.
3. Stores the sum at state offset `0x48`.

The addition does not reread the published base or the record. Dependency changes to either location do not substitute a different base for this addition.

The source expresses an ordinary signed 64-bit addition, without an explicit overflow check or saturation. A representable mathematical sum determines the final value. For sums outside the signed 64-bit range, exact execution behavior remains documented_only; this contract does not assert portable wrapping.

The post-call stores explicitly replace the intermediate and final fields. No other dependency modifications are restored.

### Sentinel path

When the signed comparison fails, the function performs these stores in order:

1. `0xFFFFFFFF` to state offset `0x40`.
2. `0x7FFFFFFF` to state offset `0x44`.
3. Zero to state offset `0x50`.
4. Zero to state offset `0x54`.
5. The 64-bit value `0x7FFFFFFFFFFFFFFF` to state offset `0x48`.

On completed execution, the base and final fields therefore contain the maximum signed 64-bit value, and the intermediate field contains zero.

This path does not read the descriptor’s array-address field, access records, read the context word, or call F-1e0edc6e0bc9. It still requires the initial descriptor and count reads.

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, storage is stable, valid, and disjoint; relevant arithmetic is defined; and the dependency returns normally.

- The base field becomes `100`.
- The staged product is `30`.
- The dependency receives `(30, 0, 7, 0)`.

The staged product is `0xFFFFFFFFFFFFFFFE`. The dependency receives product low word `0xFFFFFFFE` and high word `0xFFFFFFFF`.

Treating the operand as unsigned positive `4294967295` would produce a different, incorrect high word.

### Nonzero coefficient high word

Given coefficient `0x0000000100000000` and operand `2`, the staged product is `0x0000000200000000`.

The dependency receives product low word zero and high word `2`. Using only the coefficient’s low word would fail this condition.

### Equality and negative bounds

With index `4` and count `4`, the sentinel path is selected. No record access or dependency call occurs. Both base and final fields become `0x7FFFFFFFFFFFFFFF`; the intermediate field becomes zero.

With index negative one and count `2`, the record-derived path is selected. When the address arithmetic is defined, the selected address is one record stride before the array base. Successful completion requires readable storage there.

With index negative two and count negative one, the record-derived path is also selected. A negative count is not itself a sentinel condition.

### Stable overlapping base storage

Suppose the selected record base is `100`, and the publication destinations overlap the record’s base storage. Assume stable ordinary memory and valid accesses.

The separate high-word read, full-width capture, and low-word read all precede publication. The captured base and the completed published base therefore agree at `100`; overlap alone does not create disagreement.

This condition does not promise that the record storage remains unchanged after publication, or that later aliased reads are unaffected.

### Publication changes the coefficient source

Suppose the base-publication destinations overlap the descriptor’s array-address field. If publication changes that field to another valid array address, the second address calculation uses the changed address.

The captured base remains from the first selection. The coefficient comes from the second selection using the same captured index. The branch condition is not reevaluated.

### Dependency changes the published base

Given a captured base of `100`, suppose the dependency changes the published base field and returns `12`.

If subsequent accesses remain valid, the final field becomes `112`. The dependency’s change to the published base is not repaired by this function.
