# F-fd2427b753bc

## Purpose

F-fd2427b753bc maps two character codes to component identifiers, optionally publishes a two-component descriptor, and attempts component processing in first-then-second order through a shared mutable context.

Between the two component attempts, it snapshots four context words, clears two of those words, and installs the supplied displacements. After a failed second lookup or successful second processing, it restores the four saved words and clears both displacement fields. A second-processing error bypasses this restoration.

Descriptor publication is additional behavior, not an alternative to component processing. Successful publication is followed by the component-processing sequence.

**Inferred intent:** the operation combines a base character and an accent. This interpretation follows from the diagnostic subject and two-component structure; it does not establish coordinate units, resource ownership, or dependency semantics.

## Interface

The interface has five 32-bit arguments and a signed 32-bit result.

| Argument | Meaning established by this function |
|---|---|
| Context address | Address of the shared readable and writable context. |
| Horizontal displacement | Signed 32-bit value installed unchanged for the second component; also shifted right by 16 for descriptor publication. |
| Vertical displacement | Signed 32-bit value treated analogously. |
| First character code | Opaque 32-bit value passed unchanged to F-d006504fe20d. |
| Second character code | Opaque 32-bit value passed unchanged to F-d006504fe20d. |

Addresses and directly accessed words are 32 bits in the supplied representation. All offsets below are byte offsets.

## Behavior

### 1. Capture the mapping object and map both codes

The function reads the parent address from context offset `0x04`, then the mapping-object address from parent offset `0x28c`.

It calls F-d006504fe20d first with that mapping-object address and the first code, then with the same captured address and the second code. The second call occurs even if the first mapping result is negative.

Changes made by the first dependency call do not cause the mapping-object pointer to be reloaded for the second call. Changes to the object at that address may nevertheless affect the second mapping.

Both results are interpreted as signed 32-bit values. If either is negative, the function calls F-4457a9a44a68 twice: first with an operation-identifying diagnostic, then with an invalid-character-code diagnostic. It returns `0xa0`.

That rejection path does not read the descriptor-mode flag or perform the later explicit descriptor and context writes. Dependency effects remain possible.

Nonnegative mapping results, including zero, proceed without further visible identifier validation.

### 2. Conditionally obtain descriptor capacity

After accepting both mappings, the function reads the byte at context offset `0x52`.

A zero byte skips descriptor publication entirely, including both metadata-global reads.

For a nonzero byte, the function:

1. Reads the descriptor-related object address from context offset `0x08`.
2. Reads a 32-bit pointer at descriptor-related object offset `0x9c`.
3. Dereferences that pointer to obtain the descriptor-container address.
4. Calls F-d0804a542462 with the captured container address and a count of two.
5. Immediately after that call returns, reads the **full 32-bit first metadata-global word**.
6. Only then checks the allocation result.

A nonzero allocation result is returned immediately after the metadata read. Thus allocation failure prevents subsequent descriptor writes and component-processing calls, but does **not** prevent the first metadata-global access.

The first metadata word is a captured value, not an established constant. Allocation-time changes to that global can affect the captured value. No immutability or global-preservation guarantee is supplied.

### 3. Initialize and publish descriptors

After a zero allocation result, the function reads a 32-bit descriptor-storage address from captured container offset `0x50`.

It then performs these writes relative to that storage address, in order:

| Relative offset | Width | Value |
|---|---:|---|
| `0x00` | 32 bits | First mapped identifier. |
| `0x04` | 16 bits | Low 16 bits of the first metadata word captured before the allocation-result check. |
| `0x08` | 32 bits | Zero. |
| `0x0c` | 32 bits | Zero. |
| `0x20` | 32 bits | Second mapped identifier. |
| `0x24` | 16 bits | Two. |
| `0x28` | 32 bits | Horizontal displacement arithmetically shifted right by 16 bits. |
| `0x2c` | 32 bits | Vertical displacement arithmetically shifted right by 16 bits. |

The two component descriptions begin 32 bytes apart. These accesses do not establish the complete record layout or initialize intervening fields. In particular, each 16-bit write leaves the adjacent two bytes unwritten by that operation.

The shifted displacements are signed 32-bit results. Negative fractional values round downward under this shift, rather than toward zero. The unshifted operands remain available for later context writes.

Publication then proceeds in this order:

1. Write the 32-bit value two at descriptor-related object offset `0x80`.
2. Read the 32-bit word at container offset `0x30`.
3. Write that word at descriptor-related object offset `0x84`.
4. Read the **full 32-bit second metadata-global word**.
5. Write that captured word at descriptor-related object offset `0x48`.
6. Write the 32-bit value two at container offset `0x4c`.

The second metadata-global read occurs after the write at offset `0x84`, unlike the earlier metadata read before allocation-result checking. Neither global is established as immutable. Their values are sampled at distinct points.

Container offsets `0x30` and `0x50` have distinct visible uses: the former supplies a publication word; the latter supplies the descriptor-storage address. Their equality is not established.

The descriptor-related and container addresses remain those captured before allocation. The function does not re-traverse their pointer chain afterward.

### 4. Prepare component processing

Whether descriptor mode was disabled or publication succeeded, the function next reads context offset `0x0c` and passes that 32-bit value to F-90cd2aa8d620.

No result from this dependency controls the subsequent path. Its effects are otherwise unknown.

### 5. Attempt the first component

The function reloads the pointer at captured parent offset `0x28c`, adds `0x494`, and calls F-bb77071485ff with:

- The derived service address.
- The first mapped identifier.
- Addresses of two local 32-bit output slots.

A nonzero lookup result skips first-component processing and post-processing, but execution continues toward the second component.

A zero lookup result causes F-7310a068ba7a to receive the original context address and the two output values.

If processing returns nonzero, that result is returned immediately. The first post-processing call, state snapshot, second lookup, and restoration are not reached.

If processing returns zero, the function reloads captured parent offset `0x28c`, adds `0x494`, and calls F-0d113f438a9d with the derived address and the address of the first output slot.

This fresh read means the post-processing service address can differ from the lookup service address. No dependency is assumed to preserve the parent’s pointer field.

### 6. Snapshot state and install second-component displacements

Following either a failed first lookup or successful first processing and post-processing, the function reads and saves four context words in this order:

1. `0x38`.
2. `0x3c`.
3. `0x30`.
4. `0x34`.

The saved values describe the context at this point, after the preceding dependencies, not necessarily its entry state.

It then writes, in order:

1. Zero at `0x30`.
2. Zero at `0x34`.
3. The full horizontal displacement at `0x28`.
4. The full vertical displacement at `0x2c`.

It does not save the previous displacement-field values.

### 7. Attempt the second component

The function again reloads captured parent offset `0x28c`, adds `0x494`, and calls F-bb77071485ff for the second identifier, reusing the two local output slots.

If lookup returns nonzero, processing and post-processing are skipped. The lookup result is retained for return after restoration.

If lookup returns zero, F-7310a068ba7a receives the context and the two output values.

- Nonzero processing result: return immediately, bypassing restoration.
- Zero processing result: reload the service pointer again and call F-0d113f438a9d with the derived address and first output-slot address.

After the second post-processing call, the eventual result is explicitly set to zero. Its return value, if any, does not determine success.

### 8. Restore selected state

A failed second lookup or successful second processing reaches these writes, in order:

1. Zero at context offset `0x28`.
2. Saved word at `0x38`.
3. Saved word at `0x3c`.
4. Saved word at `0x30`.
5. Saved word at `0x34`.
6. Zero at `0x2c`.

The function then returns the second lookup error or zero, respectively.

These writes overwrite intervening changes to the four saved fields. They do not restore entry displacement values, undo changes to other fields, or reverse dependency effects.

## Side effects

The operation is not transactional.

Descriptor initialization and publication precede the preparation, lookup, processing, and post-processing dependencies. This function performs no explicit descriptor rollback on later errors. **Whether descriptors or publication fields retain their published values after those dependencies execute is unknown:** the dependencies may mutate them.

Other established effects and limits are:

- Mapping and diagnostic dependencies can act before an invalid-code return.
- The first metadata-global read occurs even on descriptor-allocation failure.
- First-component dependencies can change the state later snapshotted for restoration.
- A second-processing error bypasses all explicit restoration.
- Normal restoration clears displacements instead of restoring their former values.
- No explicit restoration covers unlisted context fields or dependency-owned state.

No component-data allocation or release operation is directly established by this body. F-d0804a542462 is requested to support two descriptors, but its allocation and ownership policies are unknown.

F-0d113f438a9d follows only successful lookup and successful processing. A processing error after successful lookup does not reach it. Its placement suggests finalization, but release, transfer, and leak conclusions require unavailable dependency contracts.

The local output slots are reused across component attempts. The function passes their values to processing only after a zero lookup result. Whether dependencies retain slot addresses or acquire resources through them is unresolved.

## Acceptance examples

These are conditional expectations from static evidence, not runtime observations. Memory validity and the stated dependency outcomes are prerequisites.

1. **First mapping is negative.** Both mapping calls occur. Two diagnostic calls follow in order, then the result is `0xa0`. Descriptor-mode access and component lookup do not occur.

2. **Descriptor mode is zero.** Neither metadata global is read by this function. Descriptor allocation and publication are skipped, but preparation and component attempts continue.

3. **Descriptor allocation returns a nonzero error.** The first metadata global is still read as a full 32-bit word before that error is returned. Descriptor-storage access, descriptor writes, the second metadata read, and component processing do not follow.

4. **The first metadata global contains `0x1234abcd` when sampled after allocation.** On allocation success, the 16-bit write at descriptor-storage offset `0x04` receives `0xabcd`. Its upper neighboring two bytes are not written by that operation.

5. **Publication reaches the second metadata read.** The write at descriptor-related offset `0x84` has already occurred. The value read from the second global then supplies the 32-bit write at offset `0x48`; an earlier value is not substituted.

6. **Horizontal displacement is `0x00018000`.** Descriptor publication writes one as its horizontal displacement. Second-component setup writes the full `0x00018000` into the context.

7. **Vertical displacement is signed negative 32768, represented by `0xffff8000`.** Its descriptor displacement is negative one, represented by `0xffffffff`, not zero.

8. **First lookup fails, but second lookup and processing succeed.** First processing and post-processing are skipped. The second component is attempted, restoration occurs, and the result is zero.

9. **Second lookup fails.** Second processing is skipped. The four saved words are restored in the specified order, displacements are cleared, and the lookup error is returned.

10. **Second processing fails.** Its error is returned without second post-processing or explicit restoration. Final field values depend on setup writes and dependency effects.

11. **Entry displacement fields are nonzero and restoration is reached.** Both fields end as zero, not their entry values.

12. **Descriptor publication succeeds before a later processing error.** Publication writes occurred and this function does not roll them back. Their values at return are not guaranteed if intervening dependencies modify the objects.
