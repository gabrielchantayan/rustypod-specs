# F-75c201811aba

## Purpose

F-75c201811aba traverses a pointer-linked structure using an external comparison-like dependency, conditionally evaluates a retained candidate, and writes one 32-bit result to caller-provided storage. It also returns a 64-bit value whose two halves describe aspects of the traversal rather than necessarily reproducing the stored result.

The structure resembles a header-based ordered tree, but that interpretation is inferred intent, not an established container contract. In particular, the retained candidate is updated to the link followed after a zero comparison result, not to the node just examined. This distinction is observable and must not be replaced with conventional tree-search behavior.

The supplied evidence establishes this function’s local control flow and explicit memory accesses. It does not establish the comparison relation, the representation of node values, memory ownership policies, or the behavior of either dependency.

## Interface

The function accepts four arguments:

| Argument | Established use |
|---|---|
| Output address | Address at which the function ultimately writes one 32-bit word. Its 32-bit address representation also supplies the low half of the return value if traversal executes no iterations. |
| Container address | Base address used to locate a structure pointer and an embedded dependency context. |
| Query operand | A 32-bit value passed unchanged to the comparison-like dependency. It may represent a pointer, scalar, or other token; the evidence does not resolve its semantic type. |
| Fourth operand | A 32-bit value with no subsequent observable use in this function. It does not influence the established result or call sequence. |

The return value is 64 bits:

- Bits 63–32 contain the final retained candidate’s 32-bit representation.
- Bits 31–0 contain the original output address’s 32-bit representation if the traversal body never executes.
- Bits 31–0 are zero if the traversal body executes at least once.

These are bitwise fields, not a promise of a meaningful signed 64-bit integer. The high half is not necessarily the word written to the output address.

## Behavior

### Initial observations

Before making any dependency call, the function performs these reads in order:

1. Read the structure/header address from container offset 0x10.
2. Read the initial traversal address from offset 0x04 of that structure/header.
3. Read container offset 0x10 again and retain this second observed address as the initial candidate.

The two container-field reads are distinct. They must not be collapsed into a single observation in the behavioral contract. Without an external stability guarantee, the structure supplying the initial traversal address and the structure supplying the initial candidate need not be the same.

The low return half initially represents the output address. A zero initial traversal address skips traversal entirely and preserves that low half.

### Traversal

Traversal continues while the current traversal address is nonzero.

At the beginning of every iteration, the function establishes zero as the eventual low return half. Consequently, one or more iterations always produce a zero low half, irrespective of the final selection.

For each nonzero current traversal address, the function calls F-f75c770a6cd7 with:

1. The address at container base plus 0x19.
2. The address at current traversal object plus 0x10.
3. The unchanged query operand.

The dependency result is tested only for zero versus nonzero. No ordering among different nonzero values is used.

- **Zero result:** After the call returns, read the 32-bit link at current object offset 0x08. Make that loaded value both the next traversal address and the retained candidate.
- **Nonzero result:** After the call returns, read the 32-bit link at current object offset 0x0c. Make that loaded value the next traversal address. Leave the retained candidate unchanged.

The link read occurs after the dependency call. If the dependency modifies the current object, traversal observes the relevant link as it exists after that modification.

A zero comparison result can set the candidate to zero. There is no substitution of the current object for a zero link and no separate preservation of the last nonzero object.

A nonzero comparison result never updates the candidate. Thus, the candidate can remain the initially retained structure/header address throughout an arbitrarily long traversal.

Traversal ends only when the current traversal address becomes zero. There is no visited-set tracking, cycle detection, iteration limit, or structural validation.

### Candidate evaluation and selection

When traversal ends, the retained candidate is fixed as the high half of the eventual return value.

The function then reads container offset 0x10 again to obtain a structure/header address for comparison with the candidate.

If the candidate equals this newly observed address:

- Do not call F-fcff71612ea5.
- Do not make a post-traversal call to F-f75c770a6cd7.
- Proceed to the fallback selection described below.

If the candidate differs from this newly observed address:

1. Call F-fcff71612ea5 with the candidate’s 32-bit value.
2. Take its 32-bit result.
3. Call F-f75c770a6cd7 with:
   - Container base plus 0x19.
   - The unchanged query operand.
   - The result from F-fcff71612ea5.
4. Test this result for zero versus nonzero.

The post-traversal comparison reverses the query’s relative position compared with traversal: the query is the third argument during traversal and the second argument during candidate evaluation.

A zero post-traversal result selects the retained candidate for the output store. No further container-field read occurs on that selection path.

A nonzero post-traversal result selects the fallback path.

### Fallback selection

The fallback path performs a fresh read of container offset 0x10 and selects that 32-bit value for the output store.

This read occurs even when candidate evaluation was skipped because the candidate equaled the preceding header observation. The selected value is therefore the value from this final read, not necessarily the value against which the candidate was compared.

If dependencies mutate the container’s field, the fallback can reflect those mutations. No preservation of that field by either dependency is assumed.

### Final store and return

After selecting either the candidate or the fallback value, the function writes exactly one 32-bit word to the output address.

It then returns the packed 64-bit value described in the interface:

- High half: retained candidate.
- Low half: original output address if traversal was skipped; otherwise zero.

The return’s high half remains the candidate even when the output store uses a different fallback value.

## Acceptance examples

These examples are conditional static acceptance cases, not runtime test results. Unless a case states otherwise, assume valid memory, normally returning dependencies, no unmentioned mutation, and a stable nonzero structure/header address.

### Empty traversal

The initial traversal address is zero.

- No traversal comparison occurs.
- The candidate remains the initially retained header.
- Candidate evaluation is skipped because the candidate equals the post-traversal header observation.
- The final fallback read supplies the output word.
- The return high half is the candidate header.
- The return low half is the output address’s 32-bit representation.

### Traversal using only nonzero results

A nonempty traversal follows offset-0x0c links until it reaches zero, and every traversal comparison returns nonzero.

- The candidate remains the initially retained header.
- Candidate evaluation is skipped under the stability assumption.
- The output receives the fallback header.
- The return high half is that retained header; the low half is zero.

### Zero comparison followed by a null link

The first traversal comparison returns zero, and that object’s offset-0x08 link is zero.

- Traversal terminates with candidate zero.
- Because the header is nonzero, F-fcff71612ea5 is called with zero.
- If it returns normally, the final comparison is performed.
- If that comparison returns zero, the output receives zero.
- If it returns nonzero, the output receives the freshly read fallback header.
- In both normally completing outcomes, the entire 64-bit return is zero.

This case must not be rewritten to select the object that supplied the null link.

### A retained nonzero candidate survives later traversal

A zero comparison follows an offset-0x08 link to a nonzero object. Subsequent comparisons return nonzero and eventually follow an offset-0x0c link to zero.

- The retained candidate is that earlier nonzero link destination.
- Later nonzero comparisons do not replace it.
- If candidate evaluation returns zero, the output receives that candidate.
- Otherwise, the output receives the fallback header.
- The return high half remains the candidate in either case, and the low half is zero.

### Dependency mutation affects fallback

Candidate evaluation is entered. During its dependency calls, container offset 0x10 changes to another readable address value. The final comparison returns nonzero.

- The fallback read observes the field after those calls.
- The output receives that later field value.
- The return high half remains the pre-evaluation candidate.

### Repeated header observations differ

Traversal is initially empty, but the first and second reads of container offset 0x10 observe different values.

- The first value supplies the location from which the zero traversal address was read.
- The second value becomes the candidate.
- Subsequent candidate selection depends on later field observations.
- The low return half still contains the output address, even if post-traversal dependency calls occur.
