# F-8124f61dc7bb

## Purpose

F-8124f61dc7bb conditionally replaces an incoming link to a recognized object, updates allocation-related accounting, and passes the object’s allocation-header address to a dependency.

**Established static behavior:** null input and recognition mismatch return immediately. For recognized input, completion of list traversal leads to dependency invocation, header validation, and accounting whether or not the object was found in the list. Any selected list-link replacement precedes header validation.

**Inferred intent:** the routine appears to release a registered allocation while maintaining size and count statistics. Actual reclamation, ownership transfer, and synchronization are not established.

There is no explicit success or failure result. Outcomes include early return, return after mutations and dependency calls, invocation of a represented nonreturning error dependency, nontermination during traversal, or failure caused by invalid storage or dependency behavior.

No disjointness is established between list storage, object fields, allocation-prefix storage, and accounting destinations. Consequently, writes described as accounting or link updates can also change object or prefix fields when their addresses overlap.

## Behavior

### Recognition gate

Null input returns without object access, direct memory writes, or dependency calls.

For nonnull input, the 32-bit recognition word is compared with the external expected value. Mismatch returns before owner, list, or prefix processing.

A match establishes neither list membership nor allocation validity or release permission.

### List processing

The owner field supplies the address used to read the owner’s head slot.

If the observed head equals the object, the routine replaces the owner’s head slot with the object’s successor. The owner field is accessed again to locate the write destination; a single immutable owner snapshot is not established.

Otherwise, traversal begins at the observed head:

- A null current node ends traversal without link replacement.
- A nonnull current node supplies a successor for continuation.
- A separate successor access is compared with the object.
- A matching comparison selects replacement of that current node’s successor with the object’s successor.
- A nonmatching comparison continues using the successor loaded for continuation.

The separate successor accesses need not observe the same value if storage changes. Under stable storage, this searches for a predecessor of the object.

Only one selected incoming-link destination is explicitly written during this phase. There is no dedicated operation to clear the object’s recognition word, owner, successor, or prefix. This is not a preservation guarantee: the selected link destination can overlap those fields, and later accounting writes can overlap them as well.

An empty list or unsuccessful finite traversal still reaches the initial dependency and subsequent header-processing path. Membership is not a release guard.

There is no cycle detection. A cycle that never satisfies the successor comparison can prevent completion.

### Initial dependency and state capture

After list processing finishes, F-2fd8826557a4 is called without explicit arguments.

Only after it returns does the routine read the indirect external state pointer. The captured base is retained for direct accounting operations and later state-bearing dependency arguments.

F-2fd8826557a4 has no established preservation contract. Entry-time header values therefore do not determine subsequent validation. Its effects on links, external pointers, and storage lifetime are also unknown.

### Header validation

The routine examines the 32-bit control word at object offset −8.

A zero observation invokes F-a817d8d58c10. Otherwise, a separate control-word access tests bit 0; a set bit also invokes F-a817d8d58c10.

F-a817d8d58c10 is represented as nonreturning. No later accounting or normal return is established after that invocation.

The checks are not one atomic observation. Under stable storage, validation accepts any nonzero control word with bit 0 clear. It does not require a positive extracted size: a word of 2 passes and produces size zero.

List processing and F-2fd8826557a4 precede validation. The routine contains no rollback of earlier writes on the error path. Whether a dependency independently reverses them is unknown.

### First accounting phase

After validation passes, F-c0fc6d033caa is called with the captured state base.

If it returns, the routine performs these ordered observations and updates:

1. Reads the unsigned 16-bit index at object offset −4.
2. Reads the control word and captures its value masked with 0x3ffffffc.
3. Subtracts the captured size from state offset 0x224 plus four times the first index.
4. Subtracts that same size from state offset 0x30c.
5. Reads the unsigned 16-bit index at object offset −2.
6. Subtracts the captured size from state offset 0xe0 plus four times the second index.
7. Subtracts that size from state offset 0x220.

The mask excludes bits 0–1 and 30–31. Its result is a multiple of four between 0 and 0x3ffffffc inclusive.

Validation is not repeated after F-c0fc6d033caa. The captured size need not derive from either value observed during validation.

These are successive read-modify-write operations. Overlapping destinations accumulate effects in execution order. An earlier accounting write can also change the second prefix index before it is read, or change the control word used in the later phase. The first captured size remains the operand for all four initial subtractions even if its source storage subsequently changes.

### Count updates and later size read

F-09dcb55e8e0a is called without explicit arguments. Its represented signed 32-bit result selects the count address at state offset 0x310 plus four times that result.

The selected count is decremented by one. The word at state offset 0x390 is then decremented by one.

Next, the routine reads the control word again, applies mask 0x3ffffffc, and subtracts that newly extracted size from state offset 0x08.

The later size can differ from the first captured size because of dependency effects, overlapping direct writes, or other mutation. No renewed zero or low-bit validation precedes this subtraction.

The final subtraction follows both count updates. The representation does not establish a separate evaluation order between reading its destination value and reading its header operand.

The captured state base remains in use even if a dependency changes the external state-pointer location. Continued validity of the captured address is required.

### Header handoff and return

After all direct accounting updates, F-cc6c9b4a0f68 receives:

- The captured state base.
- The allocation-header address at object offset −8.

If it returns, F-e586bff64fb7 receives the same captured state base. If that call returns, this routine returns.

There is no subsequent explicit object or prefix read by this routine after the handoff. The dependency calls may nevertheless access or modify that storage. Neither reclamation nor ownership transfer is established.

## Side effects

### Direct mutations and overlap

Depending on the path, the routine directly writes:

- One owner head slot or predecessor successor slot.
- Four size-accounting destinations using the first captured size.
- One indexed count destination and one aggregate count destination.
- One final size-accounting destination using a later header read.

There are no explicit field-targeted clearing operations for the recognition word, owner, successor, or allocation prefix. Nevertheless, any of those fields can be modified or cleared by an overlapping link or accounting write.

For example, when the captured state base equals the object address minus eight, state offset 0x08 is the object’s recognition word. A final subtraction of 32 from an existing word of 32 writes zero there. No dependency mutation is needed for that clearing.

Dependencies can introduce additional changes or reverse earlier effects. Even without dependency writes, overlap between this routine’s own destinations and other storage prevents general field-preservation guarantees.

### Widths and arithmetic

Addresses, control words, accounting words, and counts are represented as 32-bit quantities. Prefix indices are unsigned 16-bit quantities ranging from 0 through 65,535.

Four times a prefix index ranges from 0 through 262,140 before addition of the field displacement and state base. No bounds or address-overflow checks are visible.

No explicit branch handles subtraction underflow or decrement of zero. At the represented 32-bit operation level, subtraction stores the low 32-bit result; decrementing zero produces 0xffffffff. This describes stored-width behavior, not permission to access an invalid address or a general guarantee about source-language overflow semantics.

The count-selection result has no established valid range. Negative and excessive values are not rejected. Its scaling and address formation have no established overflow-safety contract.

### Ownership, synchronization, and failure

Unlinking precedes the header handoff. Neither establishes ownership transfer.

No explicit synchronization surrounds list traversal. Dependency placement alone does not establish locking or unlocking semantics.

Concurrent mutation, reentrancy, and dependency-induced invalidation have no demonstrated safety contract. The routine contains no rollback mechanism; an error or later failure can follow earlier visible writes.

## Acceptance examples

These are conditional static criteria, not executed tests.

### Null or unrecognized input

Null input returns without object access or dependency calls.

A nonnull input whose readable recognition word mismatches returns without owner or prefix access. Those other fields need not be valid for this path.

### Head and interior removal

For a recognized object observed as the head, with stable valid owner and link storage, the owner’s head slot receives the object’s successor before F-2fd8826557a4.

For a stable list with a predecessor whose successor equals the object, that predecessor’s successor receives the object’s successor.

These statements describe the selected link writes, not preservation of object fields. Such preservation additionally requires disjoint destinations and absence of other mutations.

### Object absent

For a recognized object with an empty owner list, no list replacement occurs. F-2fd8826557a4 is still called. If it returns, state capture and header validation follow.

### Invalid header after unlinking

Suppose head replacement completes, F-2fd8826557a4 returns, state capture succeeds, and the validation zero-check observes zero. F-a817d8d58c10 is invoked after the link write.

A zero value only at entry is insufficient to predict this result. The intervening dependency has no preservation contract.

### Stable size with disjoint storage

Suppose all relevant control-word reads observe 0x00000022, all accessed storage is valid, accounting destinations are mutually distinct and disjoint from the object and prefix, and dependencies do not modify relevant storage.

Validation passes. The masked size is 32. Each initial size destination decreases by 32, both count destinations decrease by one, and state offset 0x08 decreases by 32.

### Changed size between phases

If validation passes, the first size read yields 32, and the later read yields 64, the initial four subtractions use 32 and the final subtraction uses 64. This remains conditional on the selected accesses being valid. No second validation is performed.

### Zero extracted size

If relevant control-word reads observe 2 and all required storage remains valid, validation passes and size subtractions use zero. Count decrements and the final dependency calls still occur if preceding dependencies return.

### Aliased count destinations

If F-09dcb55e8e0a returns 32, the indexed count destination is state offset 0x390. With valid storage and no intervening mutation, that same word is decremented twice.

A decrement that reads zero stores 0xffffffff without selecting an explicit underflow error path.

### Accounting clears the recognition word

Suppose:

- The expected recognition value and initial recognition word are both 32.
- The recognized object has a valid owner with an empty list.
- The captured state base equals the object address minus eight.
- The control word remains 32 through the later size read.
- Both prefix indices and the count-selection result are zero.
- Earlier accounting destinations are valid and do not overlap the object or prefix.
- Dependencies return without altering these conditions.

The final accounting destination, state offset 0x08, is the recognition word. Its value changes from 32 to zero because the masked size is 32.

This is a direct accounting write that clears an object field, despite the absence of a dedicated recognition-clearing operation.
