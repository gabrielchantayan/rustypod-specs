# F-5a81e62a0329

## Purpose

F-5a81e62a0329 transforms selected fields of caller-supplied mutable storage in place. Its directly expressed operations reverse the byte order of 32-bit words and 16-bit halfwords, and exchange and byte-reverse selected pairs of adjacent words.

Field selection and processing order are fixed. Field contents do not select branches or determine how many dependency calls occur. The function accepts no storage length and provides no conversion-status result.

**Established static evidence:** fixed scalar accesses, arithmetic, writes, temporary-storage use, and external-call ordering.

**Inferred intent:** conversion of selected record fields between byte-order conventions. The record’s identity and the intended conversion direction are not established.

Six additional fields are processed through an unavailable dependency. Interpreting those operations as eight-byte reversals requires a conditional dependency contract; it is not an unconditional property of the visible body.

## Behavior

### Scalar transformations

A word reversal maps numeric value `0x11223344` to `0x44332211`. The directly handled words use unsigned 32-bit operations; right shifts introduce zero bits, and results retain 32 bits.

A halfword reversal maps `0x1234` to `0x3412`. Its destination write is exactly 16 bits, including cases where the input is obtained from a 32-bit read. Higher intermediate bits do not survive that write.

For each direct pair reversal:

1. The lower-addressed original word is read.
2. The higher-addressed original word is read.
3. The lower-addressed destination receives the reversed higher-addressed original word.
4. The higher-addressed destination receives the reversed lower-addressed original word.

Both inputs therefore precede either write. These operations do not require a single 64-bit load, store, or arithmetic operation.

### Staged fields and repeated observations

Each staged field issues nine calls to **F-unknown-01**:

- Calls one through eight receive eight distinct temporary destination addresses, the same record-field source address, and integer value `8`.
- Call nine receives the record-field address as destination, the temporary result address as source, and integer value `8`.

The temporary destinations and result storage are reused across staged fields. They are not newly allocated output objects.

Under synchronous eight-byte-copy behavior, each inbound call fills a two-word temporary region. The function assembles two result words from selected byte contributions, with the reversed second source word placed before the reversed first source word. The outbound call then copies that result to the record field.

For each of the first five staged fields:

| Inbound call | Selected contribution under the copy interpretation |
|---:|---|
| 1–4 | Respectively, bytes zero through three of the first source word, numbered from least significant to most significant |
| 5–8 | Respectively, bytes zero through three of the second source word, using the same numbering |

Contributions from calls one through seven are extracted before the next inbound call. The eighth contribution is obtained after call eight. Result-word assembly follows, then the outbound call.

The sixth staged field, at `0x1E4`, has different timing: all eight inbound calls finish before the temporary contents are read and combined. Later inbound calls can therefore affect earlier contributions if the dependency modifies previously supplied temporary destinations.

Even with exact eight-byte copying, changing record contents between calls can produce a result assembled from multiple observations. There is no guaranteed coherent eight-byte snapshot.

The dependency’s integer argument is visibly `8`; its interpretation as a byte count remains inferred. The function’s subsequent reads require usable contents in the relevant temporary locations. If the dependency does not establish those contents, the body provides no alternate initialization or recovery path.

## Side effects

### Record mutation and intermediate visibility

Direct scalar stores affect only the destinations in the schedule. The body does not directly clear skipped fields, initialize padding, or rewrite an entire contiguous record extent.

A claim that every other record byte remains unchanged additionally requires F-unknown-01 to avoid writes outside its intended destinations.

Updates are incremental. Earlier writes remain applied while later fields and dependency calls are processed. There is no transaction boundary or rollback mechanism.

The two stores of a direct pair are separate. Reading both original words first does not make the update indivisible.

### Ownership and lifetime

No allocation, deallocation, or ownership transfer is directly expressed. Caller storage is used in place, and temporary addresses are passed to F-unknown-01.

The dependency’s ownership and retention rules are unknown. The supplied body does not establish that it preserves globals, avoids releasing supplied storage, or refrains from retaining temporary pointers. Treating it as a synchronous, non-owning copy requires an additional contract.

### Errors and abnormal termination

There is no explicit validation, error branch, status return, or recovery path.

Invalid scalar accesses, invalid address formation, or unmet dependency requirements have no specified successful outcome. If execution faults or a dependency call fails to return normally, previously completed writes may remain visible.

### Conditional staged reversal

Assume F-unknown-01 synchronously copies exactly eight bytes, preserves unrelated storage and earlier temporary destinations, does not retain pointers, and the represented arithmetic produces the described 32-bit results.

If offsets `0xA8–0xAF` remain `01 23 45 67 89 AB CD EF` throughout the inbound calls, the staged operation writes `EF CD AB 89 67 45 23 01`.

It still issues eight inbound calls and one outbound call. Fewer calls are not equivalent where dependency-call visibility matters.

### Partial-word write

Assume the target places a word’s numeric low half at its lower-addressed two bytes. If the word at index `0x24` is `0xA1B21234` when its halfword operation reads it, the operation writes low-half value `0x3412`. Without intervening modification, the containing word becomes `0xA1B23412`.

The upper half participates in the represented word read but is not directly written.

### Storage boundaries

- A contiguous 384-byte region covers the direct scalar access span through `0x17F`. It does **not** by itself establish valid formation of the address at `0x1E4` or satisfy the dependency’s requirements.
- Under an exact eight-byte-copy contract, a contiguous 492-byte record covers the final copy span through `0x1EB`. An extent shorter than 492 bytes does not cover that span.
- Without that dependency contract, being shorter than 492 bytes alone does not identify a proven dependency overrun: actual access requirements remain unknown.
- Even 492 bytes does not prove complete safety for an arbitrary dependency.
- A null pointer or storage lacking a required scalar access has no specified successful result. Graceful rejection or rollback must not be expected.

### Skipped storage and repeated application

Under dependency behavior confined to the intended copy destinations, word index `0x07` remains unchanged because no direct transformation selects it.

With valid ordinary memory, stable inputs, the expected low-half address interpretation, and the stated copy and arithmetic assumptions, two complete invocations restore the transformed fields. The transformation is an involution under those conditions, not an idempotent operation.
