# F-56c3b4c706c6

## Purpose

F-56c3b4c706c6 conditionally processes a dependency-supplied address, updates accounting fields in a captured context, and passes the address of an associated metadata header to another dependency.

The visible behavior is consistent with releasing an allocation and reducing allocation-accounting totals. That interpretation is **inferred intent**, not an established ownership contract: the dependency bodies are unavailable, and the visible function does not itself establish whether memory is released.

The established behavior is a sequence of dependency calls, metadata checks, context-field updates, and a final pair of dependency calls. The order matters because metadata and context fields can alias, and called dependencies may modify memory.

## Interface

### Invocation and result

- No explicit arguments.
- No explicit return value.
- The initial dependency, F-87a6c5964799, supplies the value that controls whether any further processing occurs.
- A zero result causes an immediate normal return.
- A nonzero result is treated as an address associated with metadata immediately before it.
- An invalid initial metadata word invokes F-a817d8d58c10, which is represented as non-returning.

No error code, success flag, or updated address is returned to the caller.

### Implicit inputs

The function consumes:

1. The result of F-87a6c5964799.
2. A context address read from a global pointer slot after F-2fd8826557a4 returns.
3. Metadata preceding the dependency-supplied address.
4. Existing accounting values in the captured context.
5. An index returned by F-09dcb55e8e0a.

The global pointer slot is an implicit input. Its initialization, synchronization, ownership, and validity requirements are not established.

## Behavior

### 1. Obtain a candidate

The first observable dependency call is F-87a6c5964799, with no explicit arguments.

If its result is zero, the function returns immediately. In that branch, it does not call the other dependencies, read the context pointer slot, inspect preceding metadata, or perform the context writes described below. F-87a6c5964799 may nevertheless have its own side effects.

For a nonzero result, the function calls F-2fd8826557a4, also with no explicit arguments.

Only after that call returns does the function read the context address from the global pointer slot. Thus, a change to that slot made by F-2fd8826557a4 affects which context this invocation uses.

Once captured, the context address is retained for the remaining operations. Later changes to the global pointer slot do not cause the visible function to select a different context.

### 2. Check the initial header

The function examines the 32-bit word eight bytes before the supplied address.

The rejection condition is either:

- The entire word is zero; or
- Bit 0 is set.

The check is short-circuited: a zero first observation is sufficient for rejection. Otherwise, the expression contains another header read to test bit 0. This distinction matters if the memory can change between observations.

On rejection, F-a817d8d58c10 is invoked without explicit arguments. The supplied representation marks this dependency as non-returning. There is no visible recovery path, normal error return, rollback, or continuation after that call.

The header check occurs after F-2fd8826557a4 and the context-pointer read, but before F-c0fc6d033caa or any direct accounting write.

Acceptance of the header does not establish that its accounting amount is positive. For example, a header containing only bit 1 is nonzero with bit 0 clear, yet its later masked amount is zero.

### 3. Enter dependency-controlled context processing

After a successful header check, the function calls F-c0fc6d033caa with the captured context address.

Its name, synchronization role, and effects are unknown. In particular, it is not safe to assume that it preserves the metadata, context contents, global state, or memory ownership.

The header is not validated again after this call. Metadata used for the following updates is read after the call returns.

### 4. Apply four updates using one retained amount

The function next reads the unsigned 16-bit index at relative offset −4 and selects the context word at offset 0x224 plus four times that index.

It then reads the header word and retains the value obtained by masking with 0x3FFFFFFC. The mask keeps bits 2 through 29 and clears bits 0, 1, 30, and 31.

Consequently, the retained amount:

- Is a multiple of four.
- Can be zero.
- Cannot exceed 0x3FFFFFFC.
- Does not include any of the four cleared bits, regardless of their possible metadata meaning.

Four read-modify-write updates follow in this order:

1. Subtract the retained amount from the selected word relative to 0x224.
2. Subtract the retained amount from the word at 0x30C.
3. Read the unsigned 16-bit index at relative offset −2, then subtract the retained amount from the selected word relative to 0x0E0.
4. Subtract the retained amount from the word at 0x220.

The second metadata index is therefore read after the first two writes. It must not be treated as an index captured at function entry.

The four subtractions use the same retained amount even if an earlier write changes the header through aliasing. Each destination’s prior value is read when that destination is updated; the function does not take a common snapshot of all four counters.

### 5. Update two counts

After those four writes, the function calls F-09dcb55e8e0a without explicit arguments.

Its returned integer selects the context word at offset 0x310 plus four times that value. The function decrements that word by one, then decrements the word at offset 0x390 by one.

No visible range check constrains the returned index. Unlike the two metadata indices, it is not shown as a zero-extended 16-bit quantity.

These count updates occur regardless of whether the previously retained masked amount was zero.

### 6. Update the final amount field

The function next updates the context word at offset 0x008 by subtracting the header word masked with 0x3FFFFFFC.

This is a fresh header read, not reuse of the amount retained for the earlier four updates. F-09dcb55e8e0a or preceding writes may therefore cause the final subtraction to use a different amount.

The final destination value and this fresh header value are inputs to the same subtraction expression. The supplied representation does not establish an independent ordering between those two operand reads. Both precede the destination write.

### 7. Invoke final dependencies

After all seven direct context writes, the function calls:

1. F-cc6c9b4a0f68 with the captured context address and the metadata-header address.
2. F-e586bff64fb7 with the captured context address.

If both calls return, F-56c3b4c706c6 returns normally.

The visible function makes no subsequent access through the supplied address or metadata-header address after F-cc6c9b4a0f68. This does not establish whether that dependency releases, retains, transfers, or merely inspects memory.

## Side effects

### Direct effects

On the normal nonzero path, the function performs seven 32-bit context writes in the order described above.

These are sequential updates, not a transaction. There is no visible rollback if a dependency fails, does not return, or invalid memory is encountered after some updates have completed.

The function does not directly write the metadata header or either 16-bit metadata index as a distinct operation. However, a selected context destination could alias metadata; separation is not checked.

### Indirect effects

Every dependency may have effects outside the visible body. No preservation guarantee is established for globals, context contents, metadata, or memory lifetime.

In particular:

- F-2fd8826557a4 executes before context selection.
- F-c0fc6d033caa executes before the metadata used for accounting is read.
- F-09dcb55e8e0a executes between the four retained-amount updates and the count/final-amount updates.
- The last two dependencies execute after all direct accounting updates.

### Arithmetic and bounds

The two metadata indices range from 0 through 65,535. Their four-byte scaling ranges from 0 through 262,140 bytes before adding the fixed context-relative offset.

No visible checks enforce:

- Sufficient context extent for either metadata-selected location.
- A valid range for the index from F-09dcb55e8e0a.
- Nonzero counts before decrementing.
- Sufficient accounting totals before subtraction.
- Valid address arithmetic.
- Alignment or accessibility of the metadata and context words.

The amount-field stores retain 32-bit results; they do not saturate or report underflow. An unsigned 32-bit interpretation gives modulo-2³² subtraction.

The count decrements and some address calculations are shown using signed integer expressions. Exact signed-overflow and address-overflow semantics are **documented_only**: the supplied representation does not justify a portable language-level promise for those cases.

Safe execution requires valid, appropriately accessible storage for every address actually selected, and memory lifetimes sufficient for all accesses. Dependencies must not invalidate storage before its remaining uses unless their broader contract provides another valid mechanism.

## Acceptance examples

These are conditional contract examples, not executed tests.

### Zero candidate

If F-87a6c5964799 returns zero, the function returns without calling any other listed dependency. No metadata or context accesses are made by the visible function.

### Rejected header

If the supplied address is nonzero and the first header observation is zero, F-2fd8826557a4 and the context-pointer read have already occurred. F-a817d8d58c10 is then invoked; no direct accounting updates precede it.

For a stable nonzero header whose bit 0 is set, the same rejection follows.

### Ordinary distinct destinations

Assume:

- All accessed storage is valid.
- Dependencies return normally and preserve relevant memory.
- All seven selected destinations are distinct.
- The header remains 0x00000040.
- Every amount destination initially contains 1,000.
- Both count destinations initially contain 3.
- Indices select valid locations.

The four retained-amount destinations and the final amount destination each become 936. Both count destinations become 2. The final dependencies receive the captured context, with F-cc6c9b4a0f68 additionally receiving the address eight bytes before the original supplied address.

### Accepted zero amount

Under the same validity and preservation assumptions, a stable header of 0x00000002 passes validation but produces a masked amount of zero.

The five amount-update operations still occur, storing unchanged numeric values if there is no interference. The two counts are still decremented, and both final dependencies are still called.

### Different final amount

Suppose the retained amount is 64, and F-09dcb55e8e0a changes the header so its masked value becomes 128 while preserving all required storage.

The first four amount updates subtract 64. The final update at context offset 0x008 subtracts 128. No header revalidation occurs.

### Aliased amount destinations

If the first metadata index is 58, its destination is context offset 0x30C, also the second amount destination.

With a retained amount of 64, an initial value of 1,000, and no other interference, that word becomes 936 and then 872. The updates must not be collapsed into independently calculated stores from the original value.

## Evidence
