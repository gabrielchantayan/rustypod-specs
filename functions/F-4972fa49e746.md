# F-4972fa49e746

## Purpose

F-4972fa49e746 records that an indexed item has been considered and, when that item resolves to an eligible record, inserts its record pointer into an object-resident ordered list.

The established behavior has two distinct effects:

- A bit is checked and, on a first visit, set before the item’s record is resolved or its eligibility is checked.
- An eligible record is inserted according to an unsigned 32-bit ordering key. Under stable-memory assumptions, equal-key records already in the list remain before the newly inserted record.

Consequently, the bit records an attempted consideration, not necessarily a successful insertion. An absent or ineligible record still leaves the bit set.

The interpretation of this structure as a “considered-item set” and an “ordered list” is inferred intent. The bit manipulation, eligibility check, comparisons, and stores are established by the supplied static representation.

## Interface

### Inputs and result

The function takes two inputs:

1. An address of a mutable object.
2. An unsigned 32-bit item index.

No explicit result value is supplied. Observable results consist of memory changes, early return behavior, and an unresolved indirect transfer after an insertion.

The supplied representation uses 32-bit integer and pointer slots. The layout below describes that representation; it does not establish portability to a different pointer width, integer width, or byte order.

### Object layout

Offsets are byte offsets from the input object address.

| Offset | Width | Interpretation |
|---|---:|---|
| `0x000` | 32 bits | Address of a descriptor |
| `0x110` | 32 bits | Considered-item bit field |
| `0x114` | 32 bits | Signed list count |
| `0x118 + 4k` | 32 bits per slot | Record pointer at zero-based list position `k` |

The descriptor contains a 32-bit table address at descriptor offset `0x08`.

The selected table entry starts at the table address plus the item index multiplied by `0x18` bytes. A 32-bit record pointer is read at entry offset `0x04`. No other entry field is visibly inspected.

Each relevant record exposes:

| Record-relative offset | Width | Interpretation |
|---|---:|---|
| `0x04` | 32 bits | Unsigned ordering key |
| `0x09` | 8 bits | Eligibility byte |

A zero eligibility byte rejects the record. Every nonzero byte value is accepted; the function does not require the value to equal one.

### Preconditions for ordinary operation

The function performs no visible validation of object addresses, descriptor addresses, table bounds, list capacity, or existing list pointers.

For a normal insertion, callers must provide:

- Readable and writable object storage covering the fields and destination list slots used.
- A valid descriptor and selected table entry.
- A readable candidate record when the selected pointer is nonzero.
- A nonnegative list count consistent with the initialized list slots.
- Readable existing records for all ordering-key comparisons reached.
- Space for one additional pointer.
- Arithmetic that does not exceed the supported address range or overflow the signed count.
- An index whose mask construction has defined behavior in the actual execution environment.

For the intended ordered-list result, the existing list must already be sorted by nondecreasing unsigned key, and relevant memory must remain stable during the operation.

These are safe-use requirements, not checks performed by the function.

## Behavior

### 1. Construct and check the considered-item mask

The function constructs a bit mask by shifting a value of one left by the low eight bits of the item index.

The full item index remains available for table selection. Truncation to eight bits applies only to the shift count.

The function reads the bit field at object offset `0x110`. If the selected mask intersects the stored bit field, it returns immediately.

On this early-return path:

- No bit-field write is visible.
- No descriptor or table access is visible.
- No list count or list entry access is visible.
- No unresolved indirect transfer is reached.

For shift counts from zero through 30, the supplied expression supports the ordinary single-bit interpretation without a signed top-bit shift. The representation does not establish the exact machine behavior for all larger counts. In particular, the eight-bit truncation must not be treated as proof that the count is subsequently reduced modulo 32.

### 2. Mark the item before resolving its record

If the mask was not already present, the function writes the bit field with that mask set.

This store occurs before descriptor lookup, table access, candidate eligibility evaluation, or list modification.

The function then:

1. Reads the descriptor address from the beginning of the object.
2. Reads the table address at descriptor offset `0x08`.
3. Locates the selected entry using the full unsigned item index and a stride of 24 bytes.
4. Reads the record pointer at entry offset `0x04`.

If that record pointer is zero, the function returns. The bit remains set, and no list insertion occurs.

If the pointer is nonzero, the function reads the byte at record offset `0x09`. If that byte is zero, the function returns, again retaining the newly set bit.

There is no visible rollback if record resolution fails, the record is ineligible, or a later memory access fails.

### 3. Find the insertion position

For an eligible record, the function reads the signed count at object offset `0x114`.

It examines existing list positions beginning at zero. For each reached position, it compares:

- The candidate record’s 32-bit unsigned key at offset `0x04`.
- The existing record’s 32-bit unsigned key at offset `0x04`.

The first existing record with a strictly greater key determines the insertion position. Equal keys do not stop the scan.

For a stable, correctly sorted list, this places the candidate after every existing record with an equal key.

The candidate key appears in the comparison expression for each iteration rather than being explicitly retained once for the whole search. The supplied representation does not establish a single immutable key snapshot in the presence of concurrent or aliased modification. It also does not establish which comparison operand’s memory read occurs first within an individual comparison.

The function does not compare record identities. Distinct indices resolving to the same record pointer can therefore produce duplicate pointers in the list, provided their considered-item checks permit both operations.

### 4. Append when no greater key is found

If the scan reaches the captured count without finding a strictly greater existing key, the function appends.

The visible store order is:

1. Store the captured count plus one into the count field.
2. Store the candidate pointer into the slot at the captured count.
3. Reach an unresolved indirect transfer.

This ordering exposes an intermediate state in which the count has increased but the appended pointer has not yet been stored.

For a valid empty list, this path changes the count from zero to one and writes the candidate pointer into the first slot.

A negative captured count also immediately selects this path because the initial scan position is zero. Such input is not validated and can address storage before the intended first list slot. No meaningful ordered-list guarantee is established for that malformed state.

### 5. Insert before a greater key

If a strictly greater key is found, the function shifts the suffix of the pointer array one slot toward higher addresses.

The shift proceeds from the existing tail toward the insertion position. This direction preserves the original suffix when source and destination slots overlap.

The visible store order is:

1. Copy the last existing pointer into the new tail slot.
2. Continue copying backward until the insertion slot has been opened.
3. Store the candidate pointer into the insertion slot.
4. Read the current count field and store that value plus one.
5. Reach an unresolved indirect transfer.

The count update on this path is expressed as a read-modify-write of the count field after the pointer stores. It is not expressed solely in terms of the originally captured count.

With stable, nonoverlapping state, the resulting count is the previous count plus one, and the relative order of all preexisting pointers is preserved.

### 6. Arithmetic limits

Table selection uses the full 32-bit index multiplied by 24. The mask’s eight-bit shift-count truncation does not limit this table offset.

The supplied representation carries the table-address calculation through a 32-bit quantity. No bounds check is visible. Large indices can overflow the offset calculation or select memory outside the intended table; exact address-conversion behavior remains environment-dependent.

List bounds and count arithmetic use signed 32-bit values. There is no visible protection against incrementing the maximum signed count, nor against invalid pointer arithmetic caused by a malformed count.

## Side effects

### Established local effects

Depending on the path taken, the function can:

- Set a bit in the object’s considered-item field.
- Increase the list count.
- Store a candidate record pointer.
- Move existing record pointers to higher-indexed slots.

The visible body does not write record keys or eligibility bytes. It stores record pointers without visibly copying record contents.

No allocation, deallocation, reference-count adjustment, or explicit ownership transfer appears before the unresolved transfers. Pointer insertion alone does not establish that the list owns the records.

### Partial state and synchronization

The operation is not visibly transactional.

- The bit is set before candidate validation.
- The append path updates the count before storing the appended pointer.
- The insertion path moves pointers before updating the count.

No locking, atomic operation, capacity check, or recovery mechanism is visible. Concurrent observers or writers require an external synchronization contract that is not supplied.

### Effects after insertion

Both successful insertion paths reach an unresolved indirect transfer. Its target and effects are unknown.

Accordingly, the local list state immediately before that transfer is established, but the final state visible after the complete invocation is not guaranteed solely by this body. The unknown target could modify memory, alter ownership, fail, or not return.

## Dependencies

No separately identified dependency is supplied beyond F-4972fa49e746 itself.

There are two unresolved indirect-transfer sites: one after append and one after insertion before an existing record. No opaque dependency IDs are available for their destinations, so this contract does not invent them.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, they assume valid storage, an unambiguous mask shift, sufficient capacity, nonoverlapping object and record fields, and no concurrent changes.

### Already considered

Given index 3 and a considered-item field containing bit 3, the function returns without descriptor lookup or list modification.

This path does not require the descriptor or selected table entry to be usable because neither is reached.

### Null selected record

Given index 3, bit 3 initially clear, and a selected table entry containing a null record pointer:

- Bit 3 becomes set.
- The list count and entries remain unchanged.
- No indirect transfer is reached.

A second invocation with unchanged state returns at the considered-item check.

### Ineligible record

Given a clear considered-item bit and a nonnull selected record whose byte at offset `0x09` is zero, the function sets the bit and returns without inserting.

Changing that byte to nonzero afterward does not, by itself, enable a retry: the considered-item bit still blocks the same index.

### Empty list

Given count zero and an eligible candidate with key 12, the local append sequence first stores count one, then stores the candidate pointer in slot zero, then reaches the unresolved transfer.

Any assertion about the state after the complete invocation additionally requires a contract for that transfer.

### Middle insertion

Given existing keys `[4, 9, 15]` and an eligible candidate with key 7, the local list before the unresolved transfer has keys `[4, 7, 9, 15]` and count four.

The pointer for key 15 moves before the pointer for key 9, preventing overlap from destroying the original suffix.

### Equal-key placement

Given existing keys `[4, 9, 9, 15]` and a candidate with key 9, the candidate is inserted after both existing key-9 records and before key 15.

This follows from the strict unsigned comparison.

### Unsigned ordering

Given existing keys `[1, 0x80000000]` and a candidate key `0x7FFFFFFF`, the candidate is inserted between them. Keys with the high bit set are not treated as negative.

### Distinct indices selecting one record

If two supported, distinct indices have clear mask bits and both resolve to the same eligible record pointer, separate invocations can insert that pointer twice. There is no visible pointer-deduplication check.
