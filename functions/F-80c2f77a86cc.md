# F-80c2f77a86cc

## Purpose

F-80c2f77a86cc searches acquired regions of 16-bit words for a value differing from a saved comparison value. It derives a candidate position, checks that position against a context bound, modifies the selected word, and requests a commit.

**Inferred intent:** allocation or claiming of a bitmap position. The available evidence does not establish the transformation dependency’s semantics or the argument supplied to its second invocation. Consequently, the reported position cannot be guaranteed to identify a particular bit changed by the word update.

**Established behavior:** success returns zero and writes the candidate to the caller’s result destination. Explicit failure invokes a cleanup dependency, writes zero to that destination, and returns an error. A word modification preceding commit failure is not locally rolled back.

## Interface

### Inputs and directly accessed layout

The function accepts:

- A **32-bit context address**, passed to dependencies and used for direct field accesses.
- A **result address**, identifying writable storage for one 32-bit unsigned value.

The directly accessed context fields are:

| Byte offset | Width | Local use |
|---|---:|---|
| 0x20 | 32 bits | Unsigned exclusive upper bound for the candidate |
| 0x24 | 32 bits | Decremented after successful commit |
| 0x2c | 32 bits | Updated after successful commit by setting bit zero |

No local checks establish nullness, alignment, accessibility, nonoverlap, or broader context validity.

### Return and result

The return value is a 32-bit integer:

- **0:** commit returned zero and the local success writes completed.
- **0x22**, decimal **34:** the candidate was not strictly below the bound.
- Otherwise, the nonzero error returned by acquisition or commit on the path taken.

On success, the result destination receives the 32-bit candidate. On explicit failure, it receives zero after cleanup returns.

A result value of zero does not distinguish success from failure: candidate zero can succeed.

### Temporary storage

The function provides dependencies with:

- Five 32-bit temporary-state slots. Only the first is explicitly initialized, to zero.
- Storage for one region address.
- Storage for two 16-bit quantities.

Only the first 16-bit quantity is explicitly consumed locally. Region-address and quantity outputs have no established initialization before acquisition.

The acquisition dependency receives the **address of the region-address output storage**, not merely its value. Whether it retains access to that storage is unknown. This matters because the function rereads that storage after calling another dependency.

### Preconditions and ownership

Ordinary completion requires accessible context fields, a writable result destination, and readable or writable region storage wherever the selected path accesses it. A successful acquisition must establish usable outputs for subsequent operations.

A reported quantity below two does not produce a safely skipped empty region: the function reads the halfword immediately before the reported region address.

No ownership transfer, allocation, release, region-lifetime guarantee, or permission for retaining temporary-storage addresses is established.

## Behavior

### Initialization

Before the first acquisition, the function:

1. Reads a 32-bit global comparison value and retains it.
2. Initializes an accumulated position to zero.
3. Writes zero to the first temporary-state slot.

The comparison value is not refreshed between acquisitions. Changes to its originating global after this read do not change the retained value used by subsequent scans.

### Acquisition and scan setup

The function invokes **F-778071b4c8bc**, supplying the context, temporary state, region-address output storage, and two-halfword output storage.

A nonzero return selects the common failure path without local inspection of the region outputs.

After a zero return, the function:

1. Reads the first 16-bit quantity.
2. Unsigned-shifts it right by one, obtaining a scan count from zero through 32,767.
3. Reads the region-address output and uses that value as the scan’s starting address.

The scan-start address is therefore established before scanning. It is not necessarily the base address later used in candidate arithmetic.

### Scanning and repeated reads

For a positive scan count, the function reads successive 16-bit words in increasing address order. Each read value is zero-extended and compared with the retained 32-bit comparison value. Scanning stops at the first differing word or after consuming the count.

A retained comparison value above 65,535 cannot equal any zero-extended 16-bit word.

After the loop, the function separately reads and compares the halfword immediately before the final scan pointer:

- After stopping on a differing word, this rereads that word.
- After exhausting a positive scan count, this rereads the last scanned word.
- With a zero scan count, this reads the halfword immediately before the scan-start address.

This additional read determines whether the function continues to another region or derives a candidate. The decision does not simply reuse the last scan value. A word that changes between reads can therefore alter the path.

For example, a word that differed during scanning but matches during the additional comparison causes region continuation rather than candidate derivation.

### Continuing to another region

If the additional comparison finds equality, the function rereads the first 16-bit quantity, multiplies it by eight, adds that amount to the accumulated position, and requests another region.

The advancement uses the entire quantity, not twice the number of words actually scanned. Thus, for an odd quantity, the final unpaired byte is not scanned, but its eight-position contribution is included in the accumulation.

The byte-count interpretation is inferred intent. The established arithmetic is an increment of eight times the reported quantity.

There is no local iteration limit or explicit end-of-sequence return. A sequence that continues to compare equal can keep requesting regions indefinitely unless a dependency or external event changes the outcome.

### Selecting and transforming a word

If the additional comparison finds inequality, the function retains the address of the halfword just compared as the **selected-word pointer**.

It then reads that halfword again and passes the value to **F-0ec8efa9c769**. This argument read is distinct from both the scan read, when present, and the additional comparison read.

The first transformation result determines a within-word offset:

- If bit 15 is clear, the offset is zero.
- Otherwise, the offset counts consecutive set bits beginning at bit 15.
- The count is capped at 15.
- Bit 0 does not distinguish offset 15 from any further position.
- Bits above bit 15 do not affect the offset.

For example, low-halfword results 0xFFFE and 0xFFFF both produce offset 15.

### Candidate displacement and base-address reread

**After the first F-0ec8efa9c769 invocation returns**, the function rereads the region-address output storage for the candidate-displacement calculation.

Two addresses must be distinguished:

- The **selected-word pointer**, retained from scanning and still identifying the word selected for modification.
- The **then-current region-address output**, read after the transformation call and used as the displacement base.

The candidate combines:

1. The accumulated position from preceding regions.
2. Sixteen times the word displacement between the retained selected-word pointer and the reread base.
3. The within-word offset.

For ordinary nonwrapping, nonnegative, even address differences, the displacement contribution is eight times the byte difference, equivalently sixteen times the number of intervening halfwords.

There is no guarantee that the reread base equals the scan-start address. Acquisition received the output storage’s address, and retention of that address is unresolved. The transformation dependency must not be assumed to preserve the storage merely because its explicit first-call argument is a word value.

If the base changes during the transformation call, the candidate can change while the selected-word pointer remains unchanged. The later word update still targets the retained selected-word pointer; it does not reselect a word relative to the new base.

The represented calculation uses 32-bit address values, a signed address-difference expression, a right shift by one, multiplication by sixteen, and addition. The final candidate is held and compared as an unsigned 32-bit value. No overflow or address-order validation is shown. Portable semantics for negative, wrapped, or otherwise abnormal address differences are not established.

### Bound check

After the first transformation call and candidate calculation, the function reads the unsigned 32-bit field at context offset 0x20.

The candidate must be **strictly less** than this bound.

If the candidate equals or exceeds the bound:

- The error becomes 0x22.
- The function takes the common failure path.
- No local selected-word update has occurred.

The bound is read at this point, not before acquisition or transformation. Dependency changes to the bound before this read can affect acceptance.

### Word update and commit

For an accepted candidate, the function invokes **F-0ec8efa9c769** a second time. The supplied representation establishes no argument for this invocation.

After that call returns, the function:

1. Retains the low 16 bits of its result.
2. Reads the selected word again through the retained selected-word pointer.
3. ORs the two 16-bit values.
4. Stores the result to that selected word.

The update preserves bits set in this fresh word read. It does not establish that exactly one bit changes, that any bit changes, or that the changed bits correspond to the candidate.

The function then calls **F-f7c5b7585b2d** with the context, temporary state, zero, and 0x100.

A nonzero commit result selects the common failure path. The selected-word store has already occurred, and there is no local rollback before cleanup.

### Successful completion

If commit returns zero, the function performs these operations in order:

1. Reads context offset 0x24, subtracts one, and writes the 32-bit result back.
2. Reads context offset 0x2c, ORs it with one, and writes the result back.
3. Writes the candidate to the caller’s result destination.
4. Returns zero.

These context values are read after commit returns, rather than restored from earlier snapshots.

The decrement has no underflow check or saturation. At the target-width representation level, decrementing zero produces the all-ones 32-bit pattern.

The cleanup dependency is not explicitly called on success.

### Common failure path

Acquisition error, bound rejection, and commit error share this sequence:

1. Call **F-b0f922796692** with the context and temporary state.
2. Write zero to the result destination.
3. Return the selected error.

Cleanup’s own return value does not replace the selected error. Its other effects are unknown.

## Side effects

Established direct writes are:

- Initialization of the first temporary-state slot.
- A selected-word OR update after candidate acceptance.
- A context-field decrement after commit success.
- Setting context flag bit zero after commit success.
- A final 32-bit result write on either explicit return path.

Dependencies may additionally alter context, globals, region data, and storage to which they have access. In particular, the candidate’s base is read from acquisition’s output storage **after** the first transformation call; that storage is not treated as immutable.

No local allocation or explicit deallocation is shown. “Acquisition,” “commit,” and “cleanup” describe call placement and inferred roles, not proven ownership or transactional guarantees.

No atomicity or synchronization is established for the read-modify-write operations.

Aliasing is neither prohibited nor specially handled. If the result destination overlaps context or region storage, the final result write can overwrite preceding effects. On success it follows both context updates; on failure it follows cleanup.

## Acceptance examples

These are conditional static examples, not executed tests. Unless varied explicitly, assume accessible stable memory, ordinary nonwrapping address arithmetic, nonoverlapping result storage, an unchanged region-address output, and no additional relevant dependency effects.

### Candidate zero succeeds

Given a differing first word, no preceding-region contribution, a first transformation result with bit 15 clear, and a bound greater than zero:

- The candidate is zero.
- Commit success leads to return zero and result zero.
- The context counter is decremented and flag bit zero is set.

The return value, not the result alone, distinguishes this success from explicit failure.

### Region and word contributions

A preceding matching region reporting quantity four contributes 32.

If the next selected word is one halfword after the base and the transformation result begins with set bits 15 and 14 followed by clear bit 13, the candidate is:

**32 + 16 + 2 = 50.**

Bound 51 accepts. Bound 50 rejects with error 34, cleanup, and result zero, without a local word update.

### Base changes during the first transformation

Suppose the accumulated contribution is 32 and the retained selected-word pointer is four bytes after the scan-start address. The within-word offset is two.

If the region-address output remains unchanged, the candidate is **32 + 32 + 2 = 66**.

If that output instead changes during the first transformation call to an address two bytes after the scan start, the reread displacement is one halfword and the candidate is **50**.

With bound 60, the unchanged-base case rejects, while the changed-base case permits the update and commit. In the latter case, the update still targets the originally retained selected-word pointer.

This example is conditional on such a storage change; it does not assert that a dependency actually performs it.

### Offset cap

First transformation results 0xFFFE and 0xFFFF both produce offset 15. Rejecting the latter solely because its low 16 bits are all set would add behavior not established here.

### Commit failure after modification

Given selected-word value 0x0010 and second transformation low-halfword result 0x0004, the local update stores 0x0014 before commit.

If commit returns nonzero, cleanup follows, the result becomes zero, and the commit error is returned. Final region contents depend on subsequent dependency effects; no local rollback occurs.

### Odd or short quantity

For quantity five, two words are scanned. If the additional comparison matches, accumulation advances by **40**, not 32.

For quantity zero or one, the main scan reads no words, but the additional comparison reads the halfword immediately before the scan-start address. Such an input requires that read to be valid.

- Whether the first quantity formally measures bytes.
- Meaning of the second quantity.
- Required initialization of the untouched temporary-state slots.
- Transformation semantics and second-call argument convention.
- Whether acquisition retains temporary or output-storage addresses.
- Whether the region-address output changes during transformation.

These unknowns must not be resolved by assuming conventional bitmap, byte-order conversion, allocator, or transaction behavior.
