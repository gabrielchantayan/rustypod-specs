# F-8b67804fb31e

## Purpose

F-8b67804fb31e conditionally processes a caller-supplied address using metadata immediately before that address and accounting storage selected through a captured global context.

For a nonzero input address whose header passes the visible checks, the function performs seven explicit 32-bit accounting updates and invokes dependencies with the captured context and the header address.

**Inferred intent:** the updates resemble removal of an allocation from accounting, followed by an operation on its block header. Actual storage release, ownership transfer, and synchronization are not established by the supplied body.

The accounting destinations are computed addresses, not proven-disjoint structure fields. They may overlap one another, the metadata, or storage at and beyond the caller-supplied address. This aliasing possibility applies throughout the contract.

## Interface

| Input | Visible representation | Established use |
|---|---|---|
| First argument | Opaque 32-bit value | Not explicitly read, forwarded, or used in a calculation. |
| Second argument | 32-bit integer interpreted as an address | Zero causes an immediate return. A nonzero value selects metadata access and further processing. |

There is no explicit return value or returned status.

Let **P** denote the nonzero address supplied as the second argument, and **B** the context address captured during processing. These are explanatory address labels.

The supplied representation uses 32-bit address calculations, 32-bit counter accesses, and unsigned 16-bit selector accesses. It does not independently establish all target-language overflow rules or hardware address behavior.

### Metadata layout

| Address | Access width | Established use |
|---|---:|---|

| P − 4 | 16 bits, unsigned | First accounting selector. |

The quantity mask is `0x3ffffffc`. It retains header bits 2 through 29 and excludes bits 0, 1, 30, and 31.

No explicit access is addressed as payload through P or a positive payload offset. This does **not** establish that payload storage is untouched: computed accounting addresses may reach P or any overlapping storage.

## Behavior

### Zero-address path

If the second argument is zero at entry, the function returns immediately.

This path performs no explicit memory access and invokes no dependency. The first argument does not affect that decision.

### Setup and context capture

For a nonzero second argument, the function invokes:

1. F-187ab9ba4eb6 without explicit arguments.
2. F-2fd8826557a4 without explicit arguments.

A further zero check appears between these calls, and another nonzero guard appears after context capture. The visible body does not assign a replacement value to the second argument, so these checks do not establish an additional ordinary path for a value that entered nonzero.

After F-2fd8826557a4 returns, the function reads the context address from a global location and retains it as B. Context selection therefore occurs after both setup calls.

Subsequent explicit accounting calculations and context arguments use this captured address. Changing the global location afterward does not itself redirect those operations. Dependencies may nevertheless modify the storage at B, invalidate it, or otherwise affect its usability; no preservation guarantee is supplied.

### Header validation and rejection

The function first reads the 32-bit header at P − 8 and tests whether it is zero.

- A zero value selects rejection immediately.
- A nonzero value causes a further read of the header for the bit-0 test.
- If bit 0 is set in that further read, rejection is selected.
- Otherwise processing continues.

Validation is therefore not necessarily based on one snapshot. If the first read is nonzero and the second read becomes zero, the bit-0 test does not reject that second value.

Rejection invokes F-a817d8d58c10 without explicit arguments. The supplied representation marks this dependency as non-returning. Under that annotation, rejection prevents all subsequent explicit accounting writes and final dependency calls.

The concrete outcome of rejection—termination, exception, trap, or another nonlocal transfer—is unresolved. No returned error code is shown. Effects of the two setup dependencies and context capture have already occurred before rejection.

### Initial quantity updates

After successful validation, the function invokes F-c0fc6d033caa with B.

Only after this dependency returns does the function obtain the selector and quantity used for the initial updates. The observable sequence is:

1. Read the unsigned 16-bit selector at P − 4.
2. Read the header at P − 8 and mask it with `0x3ffffffc`.
3. Read and write the destination at B + `0x224` + four times the first selector, subtracting that quantity.
4. Read and write B + `0x30c`, subtracting the same quantity.
5. Read the unsigned 16-bit selector at P − 2.
6. Read and write B + `0xe0` + four times the second selector, subtracting the retained quantity.
7. Read and write B + `0x220`, subtracting the retained quantity.

The initial masked quantity is retained across all four subtractions. It is not recomputed if a preceding write changes the header.

The second selector is read after the first two accounting writes. If either destination overlaps that selector, the later read can observe the modified storage. Similarly, a write overlapping the header can affect later header reads without changing the already retained quantity.

There is no revalidation after F-c0fc6d033caa. Header or selector changes made by that dependency are used at their subsequent read points, even if the resulting header would have failed the earlier validation.

### Count updates and final quantity update

After the four initial subtractions, the function invokes F-09dcb55e8e0a without explicit arguments. Its result is represented as a 32-bit signed integer and used as an index with a four-byte stride.

The function then:

1. Decrements the 32-bit destination at B + `0x310` + four times that result.
2. Decrements the 32-bit destination at B + `0x390`.
3. Updates the 32-bit destination at B + `0x8` by subtracting the header at P − 8 masked with `0x3ffffffc`.

The final update reads the header again. It does not reuse the initial quantity. F-09dcb55e8e0a and both count updates occur before this final update, so their effects can change the header value used there.

The supplied expression does not establish a sequencing guarantee between the final destination-value read and the header read within that update. Both supply the subtraction whose result is stored at B + `0x8`.

No result-range check precedes use of F-09dcb55e8e0a’s result. Negative values, large values, and address-arithmetic overflow have no visible recovery branch.

### Final calls

After all seven explicit updates, the function invokes:

1. F-cc6c9b4a0f68 with B and P − 8.
2. F-e586bff64fb7 with B.

If both return normally, the function returns without a value.

The address passed to F-cc6c9b4a0f68 is the header address, not P. That header may already have been changed by an aliased accounting write or a dependency. No explicit header access follows this call, but this alone does not establish release or transfer of ownership.

### Arithmetic, overlap, and failure

Each selector has a range of 0 through 65,535. Multiplication by four yields 0 through 262,140 before the context address and fixed offset are added.

A masked quantity is a multiple of four from zero through `0x3ffffffc`. An accepted header can produce zero; `0x00000002` is an example.

No counter-underflow, overflow, saturation, or consistency check is visible. Quantity subtractions use a 32-bit unsigned masked operand and produce 32-bit stored results. Under the represented 32-bit unsigned arithmetic, subtracting a larger quantity wraps modulo \(2^{32}\).

The count decrements are represented with signed 32-bit accesses. The source does not independently settle language-level signed-overflow behavior at the minimum signed value. Saturation or an explicit error response must not be inferred.

Aliased destinations are updated sequentially, not as separate abstract counters. Earlier writes can affect later destination reads, selector reads, or header reads. Partial overlap also remains possible; its exact byte-level effects depend on unresolved alignment and endianness properties.

There is no visible rollback. A fault or nonlocal exit after some updates can leave their effects in place.

## Side effects

On a normally completing nonzero path, the body performs seven explicit 32-bit stores:

- Four subtractions using one retained masked quantity.
- Two decrements.
- One subtraction using a newly read masked header quantity.

A zero quantity does not eliminate the corresponding read-modify-write operations.

The explicit stores target computed accounting addresses. There is no separately addressed assignment to the header, selectors, or payload through their P-relative roles. Nevertheless, those same bytes can be written when an accounting destination aliases them.

For example, if B equals P − 8, the final destination B + `0x8` is P. The final accounting update then directly reads and writes storage at P. Other context placements or indexed destinations can overlap the header or selectors.

The body also reads the context-selection global and metadata, and invokes dependencies in the stated order. Dependency effects are not limited by the visible argument lists. They may include mutation of globals or storage, synchronization, failure, or reclamation; none of these is established or excluded.

## Acceptance examples

These are conditional static deductions, not observed executions.

### Zero input

With a zero second argument, the function returns without dependency calls or explicit memory accesses, regardless of the first argument.

### Stable invalid headers

With a nonzero P and a header that remains zero during validation, both setup dependencies execute and B is captured before F-a817d8d58c10 is invoked.

With a stable header of `0x00000011`, the zero test passes and the low-bit test selects the same rejection dependency.

Under its non-returning annotation, neither case reaches an explicit accounting write.

### Accepted zero quantity

Assume a stable header of `0x00000002`, accessible nonaliasing destinations, and dependencies that return normally without changing relevant storage.

Validation succeeds. All five quantity updates subtract zero, both count destinations decrease by one, and both final dependencies execute. This is not a no-op path.

### Stable ordinary accounting

Assume a stable header of `0x00000020`, valid selectors and indexing result, nonaliasing destinations, no arithmetic boundary crossing, and dependencies that leave relevant storage unchanged.

The four initial quantity destinations and the final quantity destination each decrease by 32. Both count destinations decrease by one. F-cc6c9b4a0f68 receives P − 8.

### Header changed after initial accounting

Assume the initial masked quantity is 32 and F-09dcb55e8e0a changes the header so its later masked quantity is 64. Assume no subsequent count write changes that header and all addresses remain usable.

The first four subtractions use 32. The final subtraction uses 64. No new validation intervenes.

### Global context changed after capture

Assume a dependency called after capture changes the global context location but leaves B usable.

Subsequent explicit accounting addresses and context arguments still use B. The context-selection global is not reloaded.

### Final destination overlaps storage at P

Assume B equals P − 8, the header remains `0x00000020` until the final quantity read, and other updates do not overlap the header or the word at P.

The final accounting destination is P. If that word contains `0x00000100` before the final update, it becomes `0x000000e0`.

This is a write to storage at P through a computed accounting address, despite the absence of an explicitly payload-addressed access.

### Final destination overlaps the header

Assume B equals P − 16, the header remains `0x00000020` until the final update, earlier destinations do not overlap it, and relevant dependencies preserve it.

The final destination B + `0x8` equals P − 8. The update subtracts 32 from the header word containing 32 and stores zero there.

F-cc6c9b4a0f68 subsequently receives that same header address. The function does not reject the newly zero header before making the call.
