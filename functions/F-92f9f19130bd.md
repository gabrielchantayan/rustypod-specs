## Acceptance examples

These are static, conditional acceptance criteria. They assume valid required memory, compatible dispatch where reached, normal dependency returns, and no unspecified interference with the stated observations.

1. **First-decision precedence.** If F-867a1fcaaaab returns any nonzero value, the result is `2` after finalization. The second decision and dispatch are not reached.

2. **Stored status bypasses the guard.** If both decisions return zero and the field at `0x1C` contains `37` when read, the result is `37`. A nonzero byte at `0x14` does not change that selection because the byte is not directly read on this path.

3. **Any nonzero guard byte.** If the first decision returns zero, the second returns nonzero, and the guard byte is `0x80`, the result is `21`. No object lookup follows.

4. **Successful addition.** If the indirect operation returns zero and leaves the counter at `100` and count at `7`, the function stores `107` before finalization and returns zero. Continued presence of `107` after finalization additionally requires that finalization not modify that storage.

5. **Post-operation state.** If the operation changes the counter to `40`, changes the count to `3`, and returns zero, the direct store is `43`, regardless of their earlier values.

6. **Nonzero operation result.** If the operation returns `9`, the function returns `9` after finalization and performs no direct post-operation count read or counter write. This does not rule out writes inside dependencies.

7. **Negative in-range count.** If the operation returns zero and the subsequent operands are `10` and `−3`, the direct store is `7`. No explicit negative-count rejection occurs.

8. **Count/counter alias.** If the count address identifies context offset `0x20`, that location holds `6` after the operation returns zero, and both reads observe `6`, the function stores `12`.

9. **Token replacement with later preservation.** If initialization replaces token A with B and nothing subsequently changes it before the finalization argument is evaluated, finalization receives B. An indirect operation still receives A as its fifth argument.

10. **Token replacement followed by another change.** If initialization replaces A with B, and a later dependency or the indirect operation changes the exposed token to C before the finalization argument is evaluated, finalization receives C. Initialization’s replacement alone does not guarantee receipt of B.

11. **Lookup-mediated argument change.** If F-a6226d4de001 changes the field at `0x18` to `55`, and it remains `55` until argument preparation reads it, the indirect operation receives `55` as its second argument.
