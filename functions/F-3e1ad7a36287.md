# F-3e1ad7a36287

## Purpose

F-3e1ad7a36287 coordinates ordered, rectangle-based operations on an object: context preparation, an optional leading element, two possible repeated regions, an optional trailing element, two optional overlays, and a final callback followed by normal-path cleanup calls.

Graphical composition is **inferred intent**. The established behavior is the visible argument construction, storage access, arithmetic, branching, dependency-call order, and virtual dispatch. Actual drawing, rectangle construction, clipping, context initialization, and resource lifetime semantics are not established by this body.

“Leading,” “trailing,” “fill,” and “overlay” identify placement roles, not application-level meanings.

## Interface

| Input | Established use |

| Opaque 32-bit value | Not directly read or forwarded by the visible body. |

There is no explicit return value or visible error status. Results are expressed through calls and their effects.

### Geometry and arithmetic

Four-word rectangles are described as **left, top, right, bottom**. Width and height denote right minus left and bottom minus top. These names describe the arithmetic, not an established coordinate system or endpoint convention.

Coordinates, spans, dimensions, and arithmetic intermediates are represented as 32-bit integers. Comparisons of spans and heights are signed. Centering uses signed integer division by two, truncating toward zero.

The contract does not assign portable results to signed overflow, including subtraction, addition, or negation of the minimum signed value. Numerical examples assume representable intermediate results.

Valid readable and writable storage, callable dependencies, and compatible resource lifetimes are prerequisites. The body performs no visible validation of them. A resource can be required even when its associated display flag is disabled.

## Behavior

### Entry and preparation

The first call is virtual slot 0x134, with the object as its sole visible argument.

After that call returns, the four input-rectangle words are copied in component order into local storage. Entry-callback changes to the input memory therefore affect the snapshot. The body makes no later direct reads through the original rectangle reference.

Preparation then proceeds in this order:

1. F-a521ccd1cb72 receives the object and storage subsequently read as two 32-bit components.
2. F-d156b0b83eb3 receives the rectangle snapshot, the negated second component, and the negated first component.
3. F-a4c26c2b4842 receives temporary context storage.
4. F-7fa874cbac7a receives the object and that storage.
5. F-42388505f940 receives a context-associated 32-bit value plus four bytes.
6. F-960363c07b32 receives the object and four-word geometry storage.

The caller subsequently reads those output areas. Successful production of offsets, context state, and geometry is an **unverified dependency contract**, not a postcondition established by this body. In particular, calling F-a4c26c2b4842 does not itself prove initialization.

The geometry words are copied into a baseline rectangle and a working rectangle. Initially, both copies match the words read from F-960363c07b32’s output area. The working top and bottom control later vertical placement. The baseline left supplies the horizontal origin; baseline top and bottom participate in leading placement and cap calculation.

The original geometry output area is retained separately for the final callback. It is not the working rectangle.

### Common submission sequence

Every reached rendering submission calls:

1. F-ee8733a08210 with local source-rectangle storage and the input snapshot previously passed to F-d156b0b83eb3;
2. F-ee8733a08210 with local destination storage and that same snapshot;
3. F-945301cd184f with a captured resource value, context storage, source storage, destination storage, and 255.

That it writes the corresponding rectangle is inferred, not verified. Subsequent adjustment and submission use the destination storage regardless of what it wrote.

### Leading element

If the flag at 0xE0 is nonzero:

- Capture the resource at 0xE4.
- Call F-c24767c70ad0 with geometry-output storage and that resource.
- Copy the resulting four words into source storage.
- Advance working top by the queried bottom minus top.
- Call F-66c32a9130af with destination storage and coordinates corresponding to baseline left, baseline top, baseline left plus queried width, and baseline top plus queried height.
- Perform the common submission sequence.

The working-top update occurs before F-66c32a9130af and both adjustment calls. Later source changes do not cause that already-completed update to be recalculated.

### Trailing reservation and span selection

If the flag at 0xD0 is nonzero, F-c24767c70ad0 receives the current resource at 0xD4. Its output bottom minus top is subtracted from working bottom. No submission occurs at this point.

Next, virtual slot 0x114 is called with the object. Its 32-bit result is passed to F-0a7faecb7263 together with the object, the fields at 0xAC and 0xB0, and the working-rectangle reference.

F-0a7faecb7263’s return is treated as a signed initial span. The working rectangle is exposed by reference; its preservation is not established.

### Initial repeated region

A zero initial span skips this stage entirely.

For a nonzero initial span:

1. Capture the resource at 0xF4.
2. Query it through F-c24767c70ad0 and copy the output into source storage.
3. Query the current resource at 0xEC, regardless of the flag at 0xE8.
4. Calculate a cap as baseline height minus the latter query’s height.
5. Replace the requested span with the cap if the cap is smaller under signed comparison.

The cap uses baseline height, not the current working gap. It does not explicitly subtract the leading height or trailing reservation. Capping can produce zero or a negative value. The loop tests **nonzero**, not positive.

For each entered iteration:

- Query the captured repeated resource again into a separate four-word output area.
- Copy those words into local source storage.
- If remaining span is signed-less-than queried height, replace local source bottom with queried top plus remaining span.
- Cache a subtraction amount: local source bottom minus the query-output top.
- Pass destination storage to F-66c32a9130af with baseline left, current working top, baseline left plus queried width, and current working top plus the cached amount.
- **After F-66c32a9130af returns**, reread local source bottom and top and add their then-current difference to the then-current working top.
- Perform the common submission sequence.
- Subtract the cached amount from remaining span.

The cached subtraction amount and the working-top increment are distinct calculations. Initially, the copied source top equals the query-output top. Nevertheless, F-66c32a9130af can, through previously retained references or other dependency effects, alter exposed source storage before the increment is calculated. Equality of the two amounts therefore requires preservation of the relevant source components across that call.

Later adjustment or submission effects do not recalculate either the completed top update or the cached subtraction amount.

The preliminary query is additional to the per-iteration queries. It is not a cached substitute for them.

### Boundary capture and remaining-space fill

After the initial repeated region, working top is saved as a boundary anchor.

The flag at 0xD8 is read. If nonzero, the signed working-bottom-minus-working-top gap is calculated. The flag is read again for the entry condition. Entry requires a nonzero flag and a strictly positive calculated gap.

Upon entry:

- Capture the resource at 0xDC.
- Query it once and copy its output into source storage.
- Recalculate remaining span as the then-current working bottom minus working top.
- Enter a loop while that span is nonzero.

The preliminary query occurs between the positivity check and the recalculation. Because working storage was previously exposed to F-0a7faecb7263, the body does not establish that the recalculated span remains positive.

Each fill iteration uses the same ordering as the initial-region loop:

- Fresh query and source copy;
- Conditional source-bottom shortening;
- Cached subtraction amount calculated before F-66c32a9130af;
- Destination-storage call with four calculated coordinates;
- Working-top increment calculated afterward from then-current local source bottom minus top;
- Source adjustment, destination adjustment, submission;
- Remaining-span subtraction using the cached amount.

Here too, constructor-time mutation can make the working-top increment differ from the amount subtracted from remaining span. Neither repeated stage performs horizontal repetition.

The fill stage does not update the separately saved boundary anchor.

### Trailing element and overlays

The trailing flag at 0xD0 is read again. If nonzero, the current resource at 0xD4 is captured and queried. Its output is copied into source storage. F-66c32a9130af receives coordinates based on baseline left, current working top, and the queried width and height; the common submission sequence follows.

There is no explicit working-top advance for this trailing operation. Its location is not forced to the reserved working bottom. Reservation and rendering use separate flag reads and resource queries.

If the boundary-overlay flag at 0xE8 is nonzero, the current resource at 0xEC is captured and queried. After copying source geometry, the body directly writes destination components in this order:

1. Right: baseline left plus queried width;
2. Bottom: saved boundary anchor plus queried height;
3. Left: baseline left;
4. Top: saved boundary anchor.

The common submission sequence follows. This stage does not call F-66c32a9130af.

If the centered-overlay flag at 0xC0 is nonzero, the current resource at 0xC4 is captured and queried. After copying source geometry, destination components are written in this order:

1. Top: boundary anchor minus queried height divided by two;
2. Bottom: queried height plus the newly written destination top;
3. Right: baseline left plus queried width;
4. Left: baseline left.

The common submission sequence follows. For a positive odd height, truncation toward zero places the smaller half above the anchor.

The fixed submission order is leading element, initial-region tiles, fill tiles, trailing element, boundary overlay, centered overlay, omitting stages not entered.

## Side effects

The visible body writes local storage but does not directly assign object fields or the caller’s rectangle. Dependencies and callbacks can still modify those locations through accessible or aliased references.

Flags and resource fields are read at their respective stages, not snapshotted together at entry. Earlier calls can therefore change later participation, resource selection, or query results. Once captured, a stage’s resource value is reused for that stage’s submissions and loop queries.

Source and destination storage is reused across stages and exposed to dependencies. Retention of those pointers cannot be excluded. No dependency is assumed to preserve globals, previously exposed storage, object state, or resource geometry.

No ownership transfer, resource release, context acquisition, or deallocation is established. The paired context-associated calls and final temporary-storage calls suggest lifetime management, but their actual effects remain unknown.

There is no visible null check, error branch, progress safeguard, or recovery mechanism. The cleanup sequence is established only for normal execution in which preceding calls return and loops terminate.
