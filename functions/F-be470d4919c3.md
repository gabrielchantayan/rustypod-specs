# F-be470d4919c3

## Purpose

F-be470d4919c3 searches buffered input for a candidate accepted by a classification, parsing, and validation sequence. It maintains a position field in a caller-supplied context and may update two additional context fields when it finds a successful candidate.

A parser-directed continuation path updates context state and begins another input acquisition. Once that path has been taken, a later ordinary success no longer replaces one of the context fields.

The established return values are a 32-bit zero for success and a 32-bit value of three for certain input-acquisition failures or a particular scan-boundary rejection. These are not exhaustive guarantees of termination: the visible scan has a boundary condition that can be bypassed.

Names such as “position,” “candidate,” and “continuation” describe observed roles. The supplied evidence does not establish a file format, protocol, unit system, or public error-code vocabulary.

## Interface

### Inputs

The function receives two 32-bit arguments:

- **Context address.** Interpreted as the address of a mutable object containing fields and an indirect input interface.
- **Mode value.** Tested only for equality to zero. All nonzero values have the same visible effect within this function.

The mode value is retained for the entire invocation. Context changes do not change which mode branch the function takes.

### Context layout

Offsets are byte offsets from the context address. The supplied evidence uses 32-bit address and field accesses except for the explicitly identified byte field.

| Offset | Width | Observed use |
|---|---:|---|
| `+0x04` | 32 bits | Address of an input-interface object. |
| `+0x14` | 32 bits | Metadata field written on continuation and, conditionally, on ordinary success. |
| `+0x20` | 32 bits | Position-like field used to anchor candidates and position validation. |
| `+0x38` | 32 bits | Candidate-result field written on ordinary success when mode is zero. |
| `+0x5c` | 8 bits | Continuation indicator inspected after successful parsing and cleared on continuation. |

The input-interface object begins with a 32-bit address of a dispatch table. Two callable entries are accessed at byte offsets `+0x14` and `+0x10` within that table.

This layout does not establish the complete size or ownership of either object. Callers must provide valid storage for the accessed fields and valid dispatch structures for the paths exercised.

### Outputs and working storage

The function returns a 32-bit status:

- **0:** parsing and subsequent validation both returned zero, and the continuation branch was not taken for that candidate.
- **3:** the input precheck returned nonzero, the input transfer did not report exactly 4096, or classification rejected the pair at scan offset 4095.

The function uses a 4096-byte temporary input buffer and three 32-bit parser-output slots:

- a candidate result;
- an extent-like value;
- a metadata value.

Only the extent-like slot is explicitly initialized, to zero, at function entry. It is not reinitialized between candidates or acquisitions. The other two slots have no established initial value before the parser is called.

There is no explicit allocation, release, or ownership transfer in the function body. Whether a candidate result represents an address, handle, integer, or owned resource is unknown.

## Behavior

### 1. Invocation state

The function begins with an internal continuation-history indicator set to false and the parser extent slot set to zero.

The history indicator becomes true only when the parser-directed continuation path is taken. Once true, it remains true for the rest of the invocation.

### 2. Input acquisition

At the beginning of every acquisition cycle, the function:

1. Reads the 32-bit position field at context offset `+0x20` and retains that value as the cycle’s scan anchor.
2. Resets the scan offset to zero.
3. Calls the input-interface dispatch entry at table offset `+0x14`.

No explicit arguments are visible for that precheck call. An implicit receiver or other calling-convention inputs cannot be established from the supplied representation.

If the precheck returns nonzero, the function returns three immediately. It does not perform the transfer call on that path.

If the precheck returns zero, the function calls the input-interface dispatch entry at table offset `+0x10`. The visible arguments are:

- the input-interface object;
- the temporary buffer address;
- the transfer amount 4096;
- the value 2;
- the value 0.

The transfer must report exactly 4096 for scanning to begin. Any other result returns three immediately, including a smaller positive value, zero, or a negative value under a signed interpretation.

The interface object and dispatch information are obtained again for the transfer call. They are not required by the visible function to remain equal to their precheck values.

The scan anchor is captured **before** both calls. If either dependency changes the context position, subsequent candidate anchoring still uses the earlier captured value.

### 3. Pair classification

At each scan offset, the function obtains two adjacent bytes from the temporary buffer and constructs a 16-bit value:

- the byte at the current offset supplies bits 15 through 8;
- the following byte supplies bits 7 through 0.

This is a high-byte-first interpretation of the pair, independent of the machine’s native byte order. The evidence establishes which byte contributes which bits, but not a mandatory physical read order between the two byte accesses.

The function passes the context and this pair value to F-d870bb18410f.

If classification returns nonzero:

- at offset 4095, the function returns three;
- at any other offset, it advances the scan offset by one and tries again.

If classification returns zero, the function enters candidate parsing. In particular, a zero classifier result at offset 4095 bypasses the only visible scan-boundary return.

### 4. Candidate parsing

For a classifier-accepted pair, the function first writes the context position as the cycle’s retained anchor plus the current scan offset.

It then calls F-f7a411326f9f with:

- the context;
- the address of the candidate-result output slot;
- the address of the extent output slot;
- the address of the metadata output slot.

A nonzero parser return rejects this attempt and advances scanning by one byte. The function does not restore the context position or undo any parser side effects.

A zero parser return causes the function to inspect the byte at context offset `+0x5c`:

- if nonzero, it takes the continuation path;
- if zero, it attempts validation.

No extent, candidate, or metadata range checks appear between parser success and these uses.

### 5. Validation and ordinary success

For successful parsing with a zero continuation indicator, the function:

1. Reads the context position after the parser has returned.
2. Retains that value as the position to restore if validation succeeds.
3. Writes a temporary validation position equal to the retained value plus the parser extent minus two.
4. Calls F-b797f5c5de2a with the context and candidate result.

The retained position is the **post-parser** value. It need not equal the candidate anchor written before parsing.

If validation returns nonzero, scanning advances by one byte. The function does not restore the retained position on this path. Any validation-side mutations also remain unless changed by later execution.

If validation returns zero, the function performs these direct writes in order:

1. Restores the retained post-parser position to context offset `+0x20`.
2. If mode is zero, writes the candidate result to context offset `+0x38`.
3. If mode is zero and no earlier continuation occurred, writes the metadata result to context offset `+0x14`.
4. Returns zero.

For nonzero mode, neither result-field write is performed on this ordinary-success path. Position restoration still occurs.

A validator change to the position field is therefore overwritten on success. The supplied body does not otherwise roll back validator changes.

### 6. Continuation

When parsing returns zero and the continuation indicator is nonzero, validation is skipped.

The function then:

1. Marks its internal continuation-history indicator true.
2. Reads the current context position.
3. Writes that position plus the parser extent minus two back to offset `+0x20`.
4. Clears the byte at offset `+0x5c` to zero.
5. Writes the parser metadata to offset `+0x14`, regardless of mode.
6. Begins a new input-acquisition cycle.

The next cycle captures its scan anchor after these writes. The buffer is refilled through the input interface rather than scanned further from the previous candidate.

The history indicator suppresses the ordinary-success metadata write for all later cycles in the invocation. It does not suppress later continuation-path metadata writes.

### 7. Widths, arithmetic, and scan bounds

Context position, parser extent, and scan offset are represented as 32-bit quantities. Relevant arithmetic consists of:

- cycle anchor plus scan offset;
- current position plus extent minus two;
- scan offset plus one.

There is no visible overflow check, saturation, lower-bound check, or extent validation. The evidence does not justify promising checked mathematical-integer behavior or a portable signed-overflow interpretation. Acceptance involving overflowing values is documented_only.

The pair access has a critical boundary consequence: offset 4095 requires a byte at offset 4096, beyond the declared 4096-byte buffer. This access occurs before the classifier result can trigger the boundary return.

Further, if classification returns zero at offset 4095 and parsing or validation subsequently rejects the candidate, scanning advances to offset 4096. No unconditional upper-bound check then prevents additional out-of-buffer accesses.

A safe bounded scan is therefore **not** established. Adjacent storage must not be treated as a valid implicit extra input byte.

## Side effects

Direct context writes are path-dependent:

| Path | Direct effects |
|---|---|
| Precheck or transfer failure | No direct context-field write in that acquisition before returning; dependency effects may remain. |
| Classifier-accepted pair | Position is written before parsing. |
| Parser rejection | No rollback of the position or parser changes. |
| Validation attempt | Position is adjusted before validation. |
| Validation rejection | No position restoration by this function. |
| Ordinary success | Position restored; candidate and metadata written under the stated mode and history conditions. |
| Continuation | Position adjusted, continuation byte cleared, metadata replaced. |

Classification rejection itself does not cause a direct context write, but F-d870bb18410f may have side effects. The same qualification applies to every dependency.

The function does not establish transactional failure semantics. Returning three does not imply that input state, context fields, or external state are unchanged.

The temporary buffer and parser-output slots are passed by address to dependencies. Their validity is limited to this invocation; no retention permission is established. Whether dependencies retain those addresses is unknown.

## Acceptance examples

These examples are conditional contracts, not observed executions. Unless stated otherwise, arithmetic is nonoverflowing, memory accesses are valid, and dependencies do not introduce additional changes.

1. **Precheck failure.**  
   If the acquisition precheck returns nonzero, the result is three and the transfer entry is not called.

2. **Short transfer.**  
   If precheck succeeds and transfer reports 4095, the result is three. No pair is classified from that acquisition.

3. **Pair interpretation.**  
   If the buffer begins with bytes `0x12` and `0x34`, the first classifier invocation receives the pair value `0x1234`.

4. **Ordinary success in zero mode.**  
   Suppose the cycle anchor is 100, classification accepts offset 4, and parsing succeeds without changing the position from 104. If the parser supplies extent 10 and validation succeeds, validation is entered with position 112. The function then restores position 104, writes the candidate field, writes the metadata field if no continuation occurred, and returns zero.

5. **Post-parser position controls validation.**  
   Under the preceding conditions, if parsing instead leaves position 200, validation is entered with position 208. Successful validation restores position 200, not 104.

6. **Nonzero mode.**  
   If parsing and validation succeed with no continuation, a nonzero mode still produces return zero and position restoration. This function does not directly replace either the candidate field or metadata field on that success path.

7. **Continuation precedes later success.**  
   If successful parsing leaves position 200, extent 12, and a nonzero continuation byte, the function writes position 210, clears the byte, writes parser metadata, and reacquires input without validating that candidate. A later ordinary success in zero mode writes its candidate result but does not replace metadata.

8. **Validation rejection is not rollback.**  
   If validation is entered at position 112 and returns nonzero without changing it, position remains 112 immediately after the rejection. The next classifier invocation follows after the scan offset advances.

9. **Boundary result is conditional.**  
   At offset 4095, a nonzero classifier result returns three only after the two-byte pair access. A zero result followed by parser rejection advances scanning beyond that offset. This example does not grant defined behavior to the out-of-buffer access.
