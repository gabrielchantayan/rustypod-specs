# F-64f743a2929d

## Purpose

F-64f743a2929d initializes a temporary context, repeatedly invokes a dependency that receives an addressable 32-bit candidate slot, and examines a 32-bit field associated with each candidate reported as available. Iteration stops when either:

- The iteration dependency returns zero.
- A candidate’s field at byte offset 32 equals the function’s second argument.

Both normal termination paths invoke a finalization dependency before constructing the return value.

The established behavior is a search-like operation with a packed 64-bit result. Interpreting the temporary context as an iterator, the candidates as objects, or finalization as resource release is inferred intent, not an established dependency contract. In particular, a zero iteration status does not, by itself, establish an error rather than ordinary exhaustion.

| Second | Match value | Used as the initial contents of the candidate slot before initialization, and as the equality target for candidate fields during iteration. Its supplied type is unsigned 32-bit. |

The last two arguments are copied into local storage. The dependencies receive the address of that storage, not an address to the caller’s argument storage.

### Temporary storage and layout

The visible local arrangement contains three consecutive 32-bit words:

| Byte offset relative to the context address | Contents before initialization |
|---|---|
| −4 | Candidate slot, initially containing the match value |
| 0 | First context word |
| +4 | Second context word |

Thus, the two known context words occupy eight bytes, and the candidate slot immediately precedes them. No additional context extent, alignment requirement, or semantic field layout is established.

F-8ca21d3a8cca receives the context address. F-b38a3aba0e18 receives both that address and the address of the candidate slot. F-d0d3f100effc receives the context address.

After initialization returns normally, the function explicitly overwrites the candidate slot with zero. It does not explicitly restore either context word.

### Output

The result is a 64-bit bit pattern whose upper and lower halves have path-dependent meanings:

- **Zero-status termination:** the lower 32 bits are zero; the upper 32 bits are the candidate slot’s contents after finalization returns.
- **Field-match termination:** the lower 32 bits are the candidate value captured immediately after the successful iteration call; the upper 32 bits are the candidate slot’s contents after finalization returns.

The supplied return type is signed 64-bit, but the visible return construction is best specified in terms of bits. If bit 63 is set, a caller interpreting the result as signed will observe a negative value. There is no established negative-error convention.

No separate Boolean result, count, or explicit error code is returned.

## Behavior

### Initialization

Before calling any dependency, the function prepares the three-word local arrangement described above. The candidate slot initially contains the match value, and the two context words contain the third and fourth arguments.

It then calls F-8ca21d3a8cca with:

1. The address of the first context word.
2. The initialization value.

The function does not inspect a return value from this call. Any mutations the dependency makes to the context remain available to subsequent calls.

On normal return from initialization, the function writes zero to the candidate slot. Consequently, a candidate-slot value left by initialization does not directly become the first iteration’s starting value. Initialization’s other effects are not rolled back.

### Iteration and candidate inspection

At least one iteration call is attempted following normal initialization. There is no pre-loop candidate test.

Each iteration calls F-b38a3aba0e18 with the context address and the candidate-slot address. After that call returns, the function reads the candidate slot and captures its 32-bit contents for a possible lower return half. This read occurs before the status is tested.

The dependency’s status is tested only for equality with zero:

- Zero takes the zero-status termination path.
- Any nonzero 32-bit status takes the candidate-inspection path. Negative statuses are not treated specially.

On a zero status, the function does not read the candidate’s field. It proceeds directly to finalization.

On a nonzero status, the function uses the current candidate-slot value as an address-bearing 32-bit quantity. It adds 32 bytes and reads a 32-bit unsigned field from the resulting address. That field is compared with the match value.

The comparison is exact 32-bit equality. It is not a range test, signed ordering comparison, masked comparison, string comparison, or comparison against a field stored in the temporary context.

If the field differs from the match value, another iteration call follows. The function does not explicitly clear the candidate slot between iterations. Therefore, unless a dependency changes it, the previous candidate value remains in the slot passed to the next iteration.

If the field equals the match value, iteration stops and the function proceeds to finalization.

There is no explicit iteration limit. A dependency that returns nonzero indefinitely while producing only nonmatching fields can cause the function to continue indefinitely.

### Address arithmetic and access requirements

The candidate slot is a 32-bit unsigned quantity, and the visible arithmetic adds the constant 32 to it. The exposed arithmetic is therefore a 32-bit unsigned addition; it does not establish a widened, nonwrapping address calculation. At that width, values near the maximum can wrap before pointer interpretation.

For a nonzero-status iteration to complete its field inspection normally, the resulting address must permit the required 32-bit read under the execution environment’s address and alignment rules. The function performs no visible null check, range check, overflow check, or accessibility check before that read.

A zero candidate value is not inherently treated as an end marker. If the iteration status is nonzero while the candidate slot is zero, the function attempts the field read at address 32.

Byte order and support for unaligned accesses are not established by the supplied evidence.

### Finalization and return construction

Both normal termination paths call F-d0d3f100effc once with the context address.

The function constructs the return value only after finalization returns. This ordering matters because the upper return half comes from a fresh read of the candidate slot after the call.

For zero-status termination:

- The captured candidate value from before the status test is not used in the lower half.
- The lower half is zero.
- The upper half is the candidate slot’s post-finalization value, zero-extended and shifted left by 32 bits.

For field-match termination:

- The lower half is the candidate value captured immediately after the iteration dependency returned.
- The upper half is the candidate slot’s post-finalization value.

If finalization leaves the candidate slot unchanged, a field match returns the same 32-bit candidate value in both halves. That duplication is conditional, not an unconditional guarantee.

Although finalization is not explicitly passed the candidate-slot address, the evidence does not rule out its accessing the slot through retained state, surrounding-storage access, or other aliasing. The contract therefore does not assume the pre-finalization and post-finalization values are equal.

## Side effects

The function explicitly writes its temporary storage, invokes three external dependencies, and reads a candidate-associated field on each nonzero-status iteration.

The observable order on a normal execution is:

1. Prepare the local candidate and context words.
2. Invoke initialization.
3. Overwrite the candidate slot with zero.
4. Invoke the iteration dependency.
5. Read the candidate slot.
6. Test the iteration status.
7. For a nonzero status, read and compare the candidate field.
8. Repeat iteration if the field does not match; otherwise finalize.
9. After finalization, read the candidate slot for the upper return half.

For a zero status, step 7 is skipped and finalization follows the status test.

No direct global write, heap allocation, heap release, or write to candidate storage is visible in the function body. The dependencies may have such effects; their behavior is not supplied. Their effects must not be treated as absent.

The temporary storage belongs to this invocation. Passing its address does not establish an ownership transfer. Whether dependencies retain addresses, allocate resources, release resources, or invalidate candidates is unknown. In particular, returning candidate bits does not establish that the referenced storage remains live after finalization.

There is no visible exception handler, access-fault recovery, or alternative cleanup mechanism. Finalization is established for the two normal loop exits, not for a dependency that fails to return or for an invalid field access that prevents normal control flow.

## Acceptance examples

These examples are conditional behavioral criteria derived from the visible operations. They are not runtime observations.

### Immediate zero status

Assume initialization returns normally, the first iteration call returns zero without changing the candidate slot, and finalization leaves that slot unchanged.

The candidate slot was explicitly zeroed before iteration. No candidate field is read. Finalization is called once, and the return bit pattern is zero.

### Zero status with a nonzero candidate slot

Assume the first iteration call writes `0x12345678` to the candidate slot and returns zero. Assume finalization leaves the slot unchanged.

No field at the candidate-derived address is read. The return bit pattern is `0x1234567800000000`, not zero and not two copies of the candidate value.

This demonstrates that zero iteration status does not imply a zero return value.

### First candidate matches

Assume the first iteration call returns nonzero and writes candidate value `0x00001000`. Assume a valid 32-bit read at address `0x00001020` yields the match value, and finalization leaves the slot unchanged.

There is one iteration call, one candidate-field read, and one finalization call. The return bit pattern is `0x0000100000001000`.

### Nonmatch followed by match

Assume the first iteration call produces a valid candidate whose field differs from the match value. Assume the second produces candidate value `0x00003000`, whose field equals the match value.

The function inspects both fields in order and finalizes only after the second comparison. If finalization preserves the slot, the result is `0x0000300000003000`. The first candidate does not appear in the result.

### Nonmatch followed by zero status without a slot update

Assume one nonzero-status iteration leaves candidate value `0x00004000`, whose field does not match. The next iteration returns zero without changing the slot, and finalization preserves it.

The function does not inspect the candidate field again on the zero-status iteration. It returns `0x0000400000000000`.

### Finalization changes the upper half

Assume a matching iteration captures candidate value `0x00005000`. If finalization changes the candidate slot to `0x00006000` through an available alias, the return bit pattern is `0x0000600000005000`.

The lower half remains the pre-finalization snapshot; the upper half reflects the later read.

### Nonzero status with an invalid candidate

Assume an iteration returns nonzero but leaves a candidate-derived field address that cannot be read.

The visible function does not convert this condition into zero-status termination. Normal completion and finalization are not guaranteed.
