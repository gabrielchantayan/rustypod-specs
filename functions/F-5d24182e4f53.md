# F-5d24182e4f53

## Purpose

F-5d24182e4f53 obtains an object through F-7fba0909c452 and performs a selector-dependent operation:

- Copies an object byte to caller-provided storage.
- Reads a 32-bit object field and copies its least significant byte to caller-provided storage.
- Invokes F-2b0e3ae2b483 and then writes four Boolean bytes.
- For an unrecognized selector, conditionally changes the object's first 32-bit field from zero to `0x00000500`.

A null object result causes an immediate return after the lookup call.

These are established structural behaviors of the supplied static representation. The semantic meanings of the selectors, fields, and value `0x500` are unknown. Describing the first field as an error indicator would be inferred intent, not an established interface guarantee.

All field-value conditions in this contract apply when the corresponding field is read **after F-7fba0909c452 returns**, unless explicitly stated otherwise. That dependency executes before dispatch and may mutate accessible state. Values present before the invocation do not, by themselves, determine the later query result or conditional update.

No runtime tests have been performed.

## Behavior

### Lookup precedes every branch

F-7fba0909c452 is invoked once before selector dispatch and before any explicit object-field or destination access by this function.

If its result is null, the function returns immediately. It does not explicitly read an object field, write the destination, update the first field, or invoke F-2b0e3ae2b483.

This is not a side-effect-free path: the lookup has already executed, and its effects are unspecified.

If the result is non-null, that returned address is used as the object base. No second lookup is visible. Subsequent field reads observe state available at those reads, not necessarily state present before the lookup.

### Selector `0x0B52`: direct byte copy

The function reads one byte at object offset `0x08FE`, then writes that value to destination offset zero.

The value is preserved as an eight-bit quantity. It is not converted to a Boolean: `0x00`, `0x01`, `0x80`, and `0xFF` remain those respective byte values.

The source read precedes the destination write. No other explicit destination write or first-field access occurs on this path.

### Selector `0x0B72`: low byte of a 32-bit field

The function reads the represented 32-bit field at object offset `0x09C4`. It writes the least significant eight bits of that value to destination offset zero.

The source access and result width differ:

- The represented source field is 32 bits.
- The destination write is eight bits.
- The upper 24 bits are discarded.
- Nonzero results are not normalized to one.

The field read precedes the destination write. No explicit first-field read or update occurs.

The truncation rule is numerical. Identifying the result with the byte at the field's lowest memory address additionally requires knowledge of byte order.

### Selector `0x80AB`: low byte of a second 32-bit field

This path uses the same 32-bit-to-eight-bit truncation rule, but the source field is at object offset `0x09F4`.

Only destination offset zero is explicitly written. No explicit first-field access occurs.

### Selector `0x0C23`: dependency followed by four Boolean stores

The function first invokes F-2b0e3ae2b483 with two pointer arguments:

1. A stack-associated address belonging to the represented current invocation.
2. An interior object address at byte offset `0x0944`.

The second argument is the address within the object, not a pointer value loaded from that location. The dependency's return value is not explicitly consumed.

If the dependency returns normally, four destination bytes are written in ascending offset order:

| Destination offset | Portion of the represented extraction value | Stored byte |
|---|---|---|
| `0` | Bits 0–7 | `0` if zero, otherwise `1`. |
| `1` | Bits 8–15 | `0` if zero, otherwise `1`. |
| `2` | Bits 16–23 | `0` if zero, otherwise `1`. |
| `3` | Bits 24–31 | `0` if zero, otherwise `1`. |

The higher-byte selections use unsigned 32-bit right shifts by 8, 16, and 24 bits followed by byte-sized nonzero tests. No shift reaches or exceeds the 32-bit width. A selected byte of `0x80` or `0xFF` produces the Boolean byte `1`, not its original magnitude.

The supplied representation names the fourth argument as the extraction source after the call. However, the dependency receives a stack-associated address whose layout and accessible extent are unresolved. It is therefore not established that extraction always uses the fourth argument's entry value.

Nor is a single stable snapshot across all four stores independently established. Examples specifying a single extraction value require that value to remain stable throughout the four evaluations. Earlier destination stores and dependency-accessible storage must not invalidate that premise.

There is no explicit destination read, and no explicit first-field update on this path.

### Unrecognized selectors: conditional first-field update

For every selector other than the four recognized values, the function reads the 32-bit field at object offset zero.

- If the value read is zero, it writes `0x00000500` to that same field.
- If the value read is nonzero, it performs no explicit write to that field.

The function then returns without an explicit destination write.

The determining value is the one observed after lookup, not necessarily the invocation-entry value. Thus:

- A field that was initially zero need not receive `0x500` if lookup changes it to nonzero before the read.
- A field that was initially nonzero can receive `0x500` if lookup clears it before the read.

Every nonzero 32-bit pattern follows the same no-write branch. Signed interpretation does not change the zero comparison. The read and conditional store are separate operations; no atomic compare-and-set is visible.

## Side effects

### Explicit writes

The function's explicit writes are limited to:

- One destination byte on each of the three field-query paths.
- Four destination bytes on the Boolean-extraction path.
- One 32-bit object-field write on the unrecognized-selector path, conditional on a zero read.

Recognized selectors do not explicitly inspect, initialize, clear, or otherwise update the first object field.

These are limits on this function's visible operations, not guarantees that all other memory remains unchanged. Dependencies may have additional effects.

### Ordering and aliasing

For a one-byte query, the selected object value is read before the destination store. If destination and source overlap, the value written comes from that preceding read.

Destination storage may also overlap other object fields. For example, a recognized query can modify the first field indirectly if the destination points into it, despite not executing the conditional-update path.

For `0x0C23`, F-2b0e3ae2b483 completes before the first explicit destination store. Stores then occur at offsets zero, one, two, and three. The four-byte result is not visibly atomic.

No synchronization, locking, rollback, or concurrent-state guarantee is established. The conditional first-field update is not protected against intervening mutation by another actor.

### Failures

The only explicit null check is on the object returned by F-7fba0909c452.

There is no visible error return, destination validation, exception handler, or recovery mechanism. Invalid storage or a dependency failure may prevent normal completion; the exact manifestation depends on the execution environment.

If a later destination store fails after earlier stores complete, no rollback is shown. If either dependency does not return normally, subsequent operations are not reached.

## Acceptance examples

These are conditional cases derived from static evidence, not executed tests. Required storage must be valid, and dependencies must return normally where later behavior is described. Field values below are specified **at their corresponding post-lookup reads**, not merely at invocation entry.

1. **Null object**  
   If F-7fba0909c452 returns null, every selector returns without an explicit destination write or object-field access by this function. F-2b0e3ae2b483 is not called. Lookup effects remain possible.

2. **Byte preservation**  
   With selector `0x0B52`, if the byte read at object offset `0x08FE` after lookup is `0xA7`, destination offset zero receives `0xA7`, not `1`.

3. **Low-byte truncation**  
   With selector `0x0B72`, if the post-lookup 32-bit read at `0x09C4` yields `0x12345680`, destination offset zero receives `0x80`.

4. **Second field selection**  
   With selector `0x80AB`, if the post-lookup 32-bit read at `0x09F4` yields `0xABCDEF00`, destination offset zero receives zero. The field at `0x09C4` is not explicitly read on this path.

5. **Mixed Boolean extraction**  
   With selector `0x0C23`, if the extraction source remains `0x80000100` throughout the four post-call evaluations, destination offsets zero through three receive `0`, `1`, `0`, and `1`. The dependency call precedes these stores.

6. **Nonzero-byte normalization**  
   Under the same stability condition, an extraction value of `0xFF807F01` produces `1`, `1`, `1`, and `1`.

7. **Unrecognized selector observing zero**  
   With selector zero, if the first-field read after lookup yields zero, the function writes `0x00000500` to that field. It performs no explicit destination write.

8. **Unrecognized selector observing nonzero**  
   With selector `0xFFFFFFFF`, if the first-field read after lookup yields any nonzero 32-bit value, the function performs no explicit write to that field.

9. **Lookup changes an initially zero field**  
   If the first field is zero at invocation entry but lookup changes it to `7`, and the unrecognized-selector path subsequently reads `7`, the conditional `0x500` store does not occur.

10. **Lookup clears an initially nonzero field**  
    If the first field is nonzero at invocation entry but lookup clears it, and the unrecognized-selector path subsequently reads zero, the function writes `0x00000500`.

11. **Recognized selector bypasses conditional initialization**  
    With selector `0x0B52`, a first field that is zero after lookup receives no explicit conditional-update write. It remains zero only if destination aliasing and other mutation do not change it.
