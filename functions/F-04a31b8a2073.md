# F-04a31b8a2073

## Purpose

F-04a31b8a2073 performs an unconditional byte update after a dependency returns, then conditionally dispatches one callback using priority-ordered candidate selection.

The established behavior is:

1. Call F-c26f463fe480.
2. Write the byte value `1` at offset `+1` from its returned address.
3. Evaluate a global table-base expression and read the four-byte candidate at offset `+0`.
4. Only if that candidate is zero, evaluate the global table-base expression again and read the four-byte candidate at offset `+4` from that second evaluated base.
5. If the selected candidate is nonzero, resolve and invoke its indirect callback with a receiver address and integer `1`.

There are at most two candidate reads and one callback invocation. The two candidate accesses are not independently established to use the same base value.

**Inferred intent:** the byte update may mark a state, and the callback may notify a preferred recipient. Neither interpretation is required by the static evidence. The contract concerns the accesses, selection, and dispatch, not application-level meanings.

## Behavior

### Dependency call and byte replacement

F-c26f463fe480 is called once, with no explicit arguments, before the function’s explicit byte write, candidate selection, or callback lookup.

After it returns normally, the function writes `1` into the byte at offset `+1` from its returned address. The old byte value is not inspected before replacement. The represented write does not itself overwrite adjacent bytes.

The returned address is not checked for zero or validity. Failure of this write has no represented recovery path.

The dependency may change global state before returning. The byte write may also affect later inputs through aliasing. Consequently, selection uses the state encountered after both the dependency call and the byte write; no entry-time snapshot is established.

### Candidate selection and global-base evaluations

After the byte write, the function evaluates the global table-base expression for the first candidate access. It reads the four-byte value at offset `+0` from that evaluated base.

If this first candidate is nonzero:

- It is selected.
- The fallback base evaluation is not reached.
- The fallback candidate is not read.
- Callback lookup proceeds from the selected candidate.

If the first candidate is zero:

- The function evaluates the global table-base expression again.
- It reads the four-byte value at offset `+4` from the base obtained by that second evaluation.
- That second value is the final candidate.

A nonzero second candidate is selected for callback lookup. A zero second candidate produces normal return without callback lookup or invocation.

The second evaluation is not specified as reuse of a cached first base. Nor is equality of the two evaluated bases independently established. If the base remains stable, selection behaves as a search of the first two four-byte positions in one table. Without that stability assumption, it reads position zero from the first evaluated base and, conditionally, position one from the second evaluated base.

These are claims about represented evaluations and accesses, not exact physical memory-load counts after compilation. The material does not establish volatile semantics, atomicity, compiler caching rules, or a synchronization mechanism governing base changes.

Selection is bounded. It does not examine a third candidate, retry a zero candidate, or dispatch to multiple candidates. A nonzero first candidate prevents fallback even if its callback chain is unusable.

### Callback resolution and invocation

For a selected nonzero candidate, the field at offset `+0x10` supplies:

- The receiver address passed as the first callback argument.
- The starting address for resolving the callback target.

Target resolution reads the address-bearing value at offset zero from the receiver-related address, then reads the callable address at offset `+0x14` from the resulting dispatch-table address.

The callback is invoked with two explicit arguments:

1. The receiver address obtained from the selected candidate’s `+0x10` field.
2. Integer `1`.

The supplied representation contains separate uses of the `+0x10` field for argument preparation and target resolution. It does not establish their relative evaluation order or guarantee that both uses observe the same value if that field changes. Exact physical load counts are likewise not established.

With a stable field and stable callback chain, the receiver argument and target lookup correspond to the same receiver. Stability is a precondition for that correspondence, not a guarantee supplied by this function.

There is no explicit zero check on the receiver-related address, dispatch-table address, or callable target. No callback result is consumed. If the callback returns normally, the function returns without a further explicit candidate read, byte write, or dispatch.
