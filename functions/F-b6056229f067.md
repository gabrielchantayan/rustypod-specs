# F-b6056229f067

## Purpose

F-b6056229f067 writes a repeated record layout through a globally supplied destination pointer and writes two 32-bit constants into a caller-supplied object.

The repeated layout contains 13 record positions at a 20-byte stride. Each position receives four 32-bit fields and one 8-bit flag. Values come from global source cells, constants, and arithmetic on four captured seeds.

**Established static behavior:** the supplied body has an unconditional sequence of reads and writes, with no visible calls, branches, validation, allocation, or cleanup.

The destination slot is evaluated **twice**. The first evaluation captures the base used by all table stores except the first. The first store—the initial tag—uses a separate evaluation of that slot. If the two evaluations produce different addresses, that initial tag is written to a different base from the remaining fields.

**Inferred intent:** the repeated writes resemble configuration-table initialization. The meanings of the payloads, tags, flags, and object fields are not established. The constants 5 and 7 are not proven to be counts, and the flags are not proven to mean enabled or disabled.

## Behavior

### Destination evaluation and initial store

The opening sequence establishes these ordering constraints:

1. Read and retain signed seed A.
2. Evaluate the destination slot and retain the resulting captured base.
3. Perform the initial-tag assignment, which separately reads the destination slot and the initial-tag source, then writes the tag at initial-store base + 12.
4. Continue with record 0’s remaining fields through the captured base.

The relative evaluation order of the **second destination-slot read** and the **initial-tag source read** is not established by the supplied assignment. Both supply that assignment; neither is specified here as preceding the other.

There are therefore two destination-slot evaluations in the supplied representation, not one. After the initial-tag assignment, there are no further destination-slot reads.

A change between the two evaluations can split the destinations. A change after the second evaluation does not redirect subsequent stores, because those stores use the captured base.

### Seed capture points

Later uses of a captured seed do not reread its global source. An earlier write that changes B, C, or U before its capture can affect the retained value. A write after capture does not change the retained value.

### Per-record access order

Record 0 has this store order:

**Initial tag through the separately evaluated base → first payload through the captured base → second payload → fixed field → flag.**

The first and second payload sources are read for their respective assignments. Their stores occur before the fixed-field store. The initial-tag assignment has the evaluation-order limitation described above.

Records 1–11 have this store order:

**Tag → first payload → fixed field → second payload → flag.**

For each of these records:

- The first payload source is read and stored before the second payload source is read.
- The second payload is captured before the fixed-field store.
- The captured second payload is stored after the fixed-field store.

The seed captures listed above intervene at their specified positions.

Record 12 has this store order:

**Tag → literal-zero first payload → second payload → fixed field → zero flag.**

Its final payload source is read after the first payload has been written as zero and before the second-payload store.

Every flag store affects one byte. It does not itself clear the following three bytes.

These are ordering properties of the supplied representation, not guarantees of atomicity, volatile access, inter-thread visibility, or synchronization.

### Object-field stores

The store of 5 at object offset 0x24 occurs after record 5’s flag and before record 6’s tag.

The store of 7 at object offset 0x20 occurs after record 7’s flag and before record 8’s tag.

Neither object field is explicitly rewritten later as an object field. Later table writes can still overwrite either location if the regions overlap.

### Arithmetic

A, B, and C are signed 32-bit values. Each is stored directly as a tag and incremented by one for the next tag.

For seeds from −2,147,483,648 through 2,147,483,646, that increment is representable. For a seed equal to 2,147,483,647, a portable overflow result is not established. Signed overflow is not silently treated as wrapping.

U is unsigned 32-bit. Its additions and subtraction are modulo \(2^{32}\):

- U + 1 wraps to zero for U = 0xFFFFFFFF.
- (U OR 0x02) + 1 wraps when the OR result is 0xFFFFFFFF.
- (U OR 0x0C) − 0x1C wraps on unsigned underflow.

No saturation, collision detection, or range validation appears.

### Aliasing and changing inputs

Disjointness is not established among the source cells, destination slot, object, captured-base storage, and initial-store destination.

Consequently:

- The initial-tag store can modify a source needed later.
- Any earlier write can affect a payload or not-yet-captured seed.
- Object stores can alter later source reads or table fields.
- Later table stores can replace earlier object values.
- Overwriting the destination slot after the captured-base read does not change the retained base.
- The second destination-slot evaluation still matters for the initial-tag store.
- Overwriting the slot during or after that store does not cause a third evaluation.

External changes can affect inputs not yet read, but no synchronization protocol is visible. The contract does not promise that unsynchronized external modification is valid or that a particular machine-level observation will occur.

## Side effects

The body contains:

- 52 explicit 32-bit record-field stores.
- 13 explicit 8-bit flag stores.
- Two additional 32-bit object-field stores.

That is **67 explicit stores**, accounting for 229 bytes of store widths.

When the two bases agree and object storage is disjoint from the table, these stores modify 229 distinct bytes: 221 table bytes and eight object bytes. With different bases, the initial-tag store moves four of those table-store bytes to its separate target. Overlap can reduce the distinct-byte count and alter final values.

No existing table field is explicitly read before replacement. However, a source read can access the same storage through aliasing.

The direct record-field stores do not initialize trailing bytes 17–19. Those bytes can still be affected by overlapping object stores or by the separately targeted initial-tag store.

No allocation, release, reference-count operation, ownership transfer, callback, logging operation, or external invocation appears. Copying a 32-bit payload does not establish that it is a pointer or grant ownership of anything it might identify.

There is no explicit rollback. If execution stops before completion, earlier completed stores are not explicitly undone. Exact fault behavior and post-fault state remain unspecified.

## Acceptance examples

These are conditional deductions, not executed tests. Unless stated otherwise, assume valid accesses, defined arithmetic, stable sources, equal destination evaluations, and non-overlapping storage.

### Ordinary initialization

For A = 10, B = 20, C = 30, and U = 0, records 1–12 receive tags:

**10, 11, 20, 21, 30, 31, 0, 1, 2, 3, 12, 0xFFFFFFF0.**

Record 0 receives the initial tag. Records 0–11 receive their corresponding payload pairs. Record 12 receives zero and the final payload.

Every fixed field becomes 3. Flags are 1 for records 0–11 and 0 for record 12. Object offsets 0x24 and 0x20 become 5 and 7.

### Different destination evaluations

Suppose the first destination-slot evaluation yields base X and the second yields distinct base Y. Assume the relevant destinations do not overlap each other or any sources.

The initial tag is stored at Y + 12. Every remaining table store uses X. In particular, X + 12 is not explicitly initialized and retains its prior contents under these assumptions.

This case does not require or establish whether the second slot read precedes the initial-tag source read.

### Destination slot overwritten by initialization

Suppose the initial-tag store overwrites the destination slot itself, after both required evaluations have supplied their values.

Later table stores still use the first captured base. They do not follow the newly written slot contents.

Similarly, a later payload or object store that changes the slot does not redirect any remaining table store.

### OR rather than addition

For U = 2, records 7–12 receive tags:

**2, 3, 2, 3, 14, 0xFFFFFFF2.**

Replacing U OR 0x02 with U + 2 would violate this case.

### Unsigned wrapping

For U = 0xFFFFFFFF, records 7–12 receive tags:

**0xFFFFFFFF, 0, 0xFFFFFFFF, 0, 0xFFFFFFFF, 0xFFFFFFE3.**

### Untouched trailing bytes

If bytes 17–19 of each record contain known patterns, and no separately targeted or overlapping write touches them, those patterns remain unchanged.

A wider flag store that clears those bytes would not match the established write footprint.

### Object/table overlap

Suppose object offset 0x24 aliases record 6’s tag, without other relevant overlap.

The object store writes 5 first. The next table store replaces it with C + 1, assuming defined arithmetic. The final object field therefore need not contain 5.

### Signed boundary
