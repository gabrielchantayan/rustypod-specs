# F-af667771d6ce

## Purpose

The established behavior distinguishes only zero from nonzero. When the inspected field is zero, the function calls F-8157a180d901 with 556, calls F-9d85917b099a, and stores the second dependency’s 32-bit result through a previously captured object base. Whether initialization occurs or is skipped, the normal return comes from a final field read through that captured base.

Lazy initialization or caching is an inferred purpose, not an established semantic contract. The field is not proven to contain a pointer, an owned resource, or a success indicator. In particular, storing zero does not prevent another initialization attempt.

This contract describes static evidence only. No runtime tests have been performed.

## Behavior

### Base capture and decision

The function first captures the global object base. That captured value determines the destination of the possible result store and the location of the final return read.

It then compares the four-byte field at offset 8 from the globally referenced base with zero. The condition does not explicitly use the captured base.

Only equality to zero controls the branch. Every nonzero 32-bit field pattern skips initialization, including patterns whose high bit is set. No positivity check, range check, or pointer-validity check is present.

### Nonzero condition

When the inspected field is nonzero:

- Neither dependency is called.
- The function performs no explicit field write.
- The function reads the field at offset 8 from the captured destination base and returns those 32 bits.

The return is not specified as reuse of the value inspected by the condition. It is defined by the final field read.

Consequently, a nonzero condition implies the same nonzero return only when both accesses select the same field and that field remains unchanged. A changed field, or a difference between the condition base and captured base, can produce a different return, including zero.

### Zero condition

When the inspected field is zero, the established order is:

1. F-8157a180d901 is invoked with 556.
2. If that invocation returns normally, F-9d85917b099a is invoked without explicit arguments.
3. If the second invocation returns normally, its 32-bit result is stored at offset 8 from the captured destination base.
4. The function reads that destination field and returns the 32 bits obtained by that read.

The first dependency’s return value, if any, is not consumed by this function. This does not make its execution irrelevant: its state changes may affect the second dependency or the validity of subsequent accesses.

The second dependency’s result is stored without a visible success check, nonzero check, conversion to a Boolean, or retry. Every 32-bit result pattern follows the same store path.

There is no field-condition recheck between the calls or before the store. If either dependency changes the destination field, the later explicit store overwrites that intermediate field value, provided the destination remains valid.

There is also no condition recheck after the store. The final read determines the return even if the field has changed since the store. A zero dependency result therefore establishes that zero is written; it does not unconditionally establish a zero return.

### Repeated invocations

There is no separate completion marker in the supplied function.

If a later invocation inspects the same field while it still contains zero, both dependencies are invoked again. A zero result can therefore leave the condition that triggers initialization unchanged.

A later invocation skips the dependency calls only if its own condition observes a nonzero field. A previous nonzero result is insufficient to guarantee this: the global may select another object, or the field may have changed.
