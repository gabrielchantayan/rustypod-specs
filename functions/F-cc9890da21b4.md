# F-cc9890da21b4

## Purpose

F-cc9890da21b4 conditionally updates a context-associated record, processes members of a supplied object, and performs accounting and allocation-related operations for that object.

The established sequence is:

1. Perform the optional context-associated update.
2. Return if the original object argument is zero.
3. Invoke four unconditional and up to two conditional member-processing calls.
4. Recover an allocation anchor and update global accounting.
5. Either return for a special anchor value or validate allocation metadata, update allocator counters, and invoke final dependencies.

“Object,” “allocation,” and “cleanup” describe inferred roles. The visible accesses and calls support those interpretations but do not establish ownership transfer, memory release, or synchronization semantics.

## Interface

### Arguments and result

The function receives:

- A context address, accessed as an address of 32-bit words.
- A 32-bit object-address value. Zero selects the explicit null-object path.

There is no explicit return value or status result. One validation branch invokes a dependency identified as non-returning.

The supplied representation uses 32-bit addresses, 32-bit ordinary fields, unsigned 16-bit allocator indices, and an 8-bit context flag. Indexed addresses use four-byte scaling.

The context must support the initial reads even when the object argument is zero. No initial context-null check is present. Every later access requires accessible storage at the address reached by that path; the function does not validate storage extents.

## Behavior

### 1. Optional context-associated update

The function first reads the associated-record address at context offset `0x180`, then captures the context word at offset `0x00`.

If the associated-record address is zero, it skips the suppression-byte read and the update calls. Otherwise, it reads the byte at context offset `0x198`. A nonzero byte suppresses the update.

When enabled, the update proceeds in this order:

1. F-1a5398bcc6b3 receives the captured context word and original object argument.
2. After that call returns, the associated-record word at `0x2C` is read.
3. F-8661793c1ec4 receives the captured context word, the newly read record word, and the result of F-1a5398bcc6b3.
4. Its result is written to that record’s word at `0x2C`.

Both the record address and context word remain the values captured before these calls. A dependency’s change to the context’s record pointer does not redirect the final store. A change to the captured record’s field during F-1a5398bcc6b3 does affect the subsequent field read.

The object-null check occurs afterward. Consequently, this update can execute with a zero object argument.

### 2. Null-object return

If the original object argument is zero, the function returns after the optional update.

This path does not read object members, capture the accounting-global pointer, recover an allocation anchor, or perform allocation accounting.

### 3. Ordered member processing

For a nonzero object, the following operations occur in order:

1. Read the word at `0x20`. If bit 0 is set, read `0x1C` and pass its value to F-94cb53877c15.
2. Read the word at `0x18`. If bit 0 is set, read `0x14` and pass its value to F-94cb53877c15.
3. Read `0x08` and pass its value to F-841dc33ee157.
4. Read `0x0C` and pass its value to F-841dc33ee157.
5. Read `0x10` and pass its value to F-e5380ae57ea1.
6. Read `0x38` and pass its value to F-6c7ac9769d41.

Only bit 0 controls each conditional call. A clear bit skips both the associated member read and its call. No member-value null check suppresses a selected call.

Reads are staged across dependency calls rather than captured together. An earlier dependency can affect a later flag, member argument, or allocation adjustment if it changes the corresponding storage. No preservation guarantee for those locations is established.

### 4. Anchor recovery and global accounting

Immediately after F-6c7ac9769d41 returns, the function captures the accounting-global pointer. This happens **before** reading the object adjustment or allocation amount. That captured address supplies the destination of the eventual high-word store.

The remaining sequence distinguishes several independently obtained addresses:

1. Read the adjustment at original object offset `−0x04` and subtract it from the original object address.
2. Read the 32-bit amount at the resulting anchor’s offset `−0x08`.
3. Reload the accounting-global pointer and read its low word at `0x38`. Retain that low-word value.
4. Reload the accounting-global pointer again and capture the address of its high word at `0x3C`. The high-word value is not yet read.
5. Reload the accounting-global pointer again for the low-word destination. Store the retained low-word value minus the amount at this address plus `0x38`.
6. After the low-word store, read the high-word value through the high-word read address captured in step 4.
7. Adjust that high-word value and store the result at `0x3C` relative to the **original accounting pointer captured immediately after the last cleanup call**.

Thus, the low-word source, low-word destination, high-word source, and high-word destination are not established to belong to one accounting object merely because they originate from the same global reference.

The low-word subtraction is a 32-bit word subtraction. The high-word adjustment subtracts:

- The amount’s sign-extension word: zero if bit 31 is clear, or `0xFFFFFFFF` if bit 31 is set.
- A borrow contribution of one if the retained low-word value is unsigned-less-than the amount, otherwise zero.

These contributions and stored results are interpreted at 32-bit word width. No saturation or underflow rejection is visible.

**Conditional arithmetic interpretation:** If all accounting-global reads identify the same stable object, its words do not interfere through aliasing, and no intervening mutation affects the operands, the two stores implement subtraction of the amount interpreted as a signed 32-bit integer from a 64-bit high/low pair, modulo \(2^{64}\).

Without those conditions, the contract is the ordered accesses above, not one coherent two-word subtraction. In particular:

- The low result may be written to an object different from its source.
- The high result may be written to an object different from its source.
- The high-word read observes storage after the low-word store and can therefore observe that store if the locations alias.
- A low-word store that aliases the accounting-global reference cannot change either already captured high-word address.

No dependency call occurs within this sequence. That does not establish atomicity, absence of aliasing, or protection from external mutation.

### 5. Allocator selection and sentinel return

After the global-accounting stores, F-2fd8826557a4 is called without explicit arguments. The function then loads an allocator-state address through a separate global reference.

Only after that load does it compare the allocation anchor with the numeric address value `8`.

If the anchor equals `8`, the function returns. This path has already performed member processing, accounting-pointer capture, anchor recovery, the amount read, global-accounting stores, F-2fd8826557a4, and the allocator-state load.

It skips all subsequent header checks, allocator-counter updates, and final dependency calls. The meaning of this sentinel and whether F-2fd8826557a4 requires balancing are not established.

### 6. Header validation

For any other anchor, the function checks the 32-bit header at anchor offset `−0x10`.

It first tests whether the header is zero. If it is not zero, it tests whether bit 0 is set. Either a zero header or a set bit 0 invokes F-a817d8d58c10, identified as non-returning.

Global accounting has already changed. No rollback is visible.

A nonzero header with bit 0 clear passes. Bit 1 and the upper two bits are not independently rejected. The supplied representation shows separate header references for the zero and bit tests; it does not establish volatile access semantics or exact generated memory-read granularity.

### 7. Allocator accounting and final calls

After validation, F-c0fc6d033caa receives the selected allocator-state address.

After that call returns, the function reads the first unsigned 16-bit index, then reads the header and obtains a size by masking with `0x3FFFFFFC`. The mask clears the low two and high two bits. The result is a multiple of four from zero through `0x3FFFFFFC`.

Using that captured size, it performs these ordered 32-bit read-modify-write operations relative to the selected allocator state:

1. Subtract size at `0x224 + 4 × first index`.
2. Subtract size at `0x30C`.
3. Read the second unsigned 16-bit index.
4. Subtract size at `0x0E0 + 4 × second index`.
5. Subtract size at `0x220`.

The header used for this size is read after F-c0fc6d033caa, so it need not equal the header that passed validation. There is no repeated validity check at this point.

F-09dcb55e8e0a is then called without explicit arguments. Its 32-bit integer result selects the word at allocator offset `0x310 + 4 × result`, which is decremented by one. The word at `0x390` is then decremented by one.

Finally, the header is reread and masked with `0x3FFFFFFC`. This newly obtained size is subtracted from the word at allocator offset `0x08`. It need not match the size used for the earlier four subtractions.

The final calls are:

1. F-cc6c9b4a0f68 with the selected allocator-state address and allocation-header address.
2. F-e586bff64fb7 with that same selected allocator-state address.

Normal completion follows. The selected allocator-state address is retained across these calls and earlier allocator operations; later changes to its global source do not themselves redirect it.

## Side effects

Direct writes comprise:

- The optional associated-record update.
- The low and high global-accounting stores, potentially through different accounting objects.
- The allocator size and count updates described above.

No explicit operation clears object fields, resets ownership flags, or changes the caller’s stored object address. Direct writes are not guaranteed to avoid object storage if supplied addresses alias it.

No bounds checks protect either unsigned 16-bit index or the integer returned by F-09dcb55e8e0a. The latter is not established to be nonnegative. Indexed fields can overlap other fields; coincident addresses receive sequential updates rather than independent logical-counter treatment.

The function does not establish that any dependency preserves globals, object storage, headers, or allocator state. Nor does it establish which dependency releases or retains memory. Continued execution requires that every later reached access remain valid despite earlier calls.

If a dependency does not return, later operations do not occur. There is no visible local recovery or transaction boundary.

## Acceptance examples

These are conditional static expectations, not executed tests. Except where stated otherwise, dependencies return normally, relevant storage remains accessible, and no aliasing or mutation changes the stated operands.

1. **Null object, enabled update.** A nonzero record address and zero suppression byte cause both update calls and the record store, followed by return. No member-processing or allocation-accounting operation follows.

2. **Absent record.** A zero associated-record address skips the suppression-byte read. The context word at `0x00` is still read. A zero object then returns.

3. **Flag selection.** A word value of `2` at object offset `0x20` skips reading and processing `0x1C`; a value of `3` selects it. A selected member value of zero is still passed.

4. **Stable accounting with borrow.** With one stable, noninterfering accounting object, high `3`, low `0x10`, and amount `0x20` produce high `2`, low `0xFFFFFFF0`.

5. **Stable accounting with a negative amount.** With both words zero and amount `0xFFFFFFFF`, the result is high zero, low one. This is subtraction of signed `−1`, not subtraction of unsigned `4294967295`.

6. **Accounting pointer changes after initial capture.** Suppose the pointer initially identifies one accounting object, then changes before the low-word read and remains pointed at a second object. With no other interference, the low read and low store use the second object; the high read also uses the second object, but the high result is stored in the first object. No single-object 64-bit subtraction describes this outcome.

7. **High-read aliasing.** If the captured high-word read address coincides with the low-store destination, the high calculation reads the newly stored low result. An expectation based on a pre-store high value is invalid.

8. **Sentinel anchor.** Anchor `8` still reaches the amount read, global accounting, F-2fd8826557a4, and allocator-state load. It skips validation and all later allocator operations.

9. **Invalid header.** Zero or bit 0 set invokes F-a817d8d58c10 after global accounting, without allocator-specific counter updates or rollback.

10. **Zero masked size.** A stable header value of `2` passes validation and gives size zero. Size counters undergo zero subtraction; both count decrements still occur.

11. **Header mutation.** If F-c0fc6d033caa changes an accessible header, the first four size subtractions use its post-call masked value without revalidation. If F-09dcb55e8e0a later changes the header, the final subtraction at allocator offset `0x08` uses the later masked value.
