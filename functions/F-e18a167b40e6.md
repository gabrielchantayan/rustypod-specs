# F-e18a167b40e6

## Purpose

F-e18a167b40e6 conditionally disconnects a record from a linked structure, optionally invokes F-682cc3fccb47 with a derived address, and clears three 32-bit fields in the record.

The established behavior is controlled by the record’s field at offset `0x04`:

- If that field is zero, the function returns without modifying memory or invoking its dependency.
- If that field is nonzero, the function repairs selected links, optionally performs the dependency call, and then clears the fields at offsets `0x04`, `0x0C`, and `0x08`, in that order.

The structure is consistent with a bucketed, doubly linked collection. That interpretation is inferred intent, not a prerequisite for describing the actual memory operations. In particular, the function does not independently establish that the record belongs to the supplied container or that its links are consistent.

## Interface

The function accepts two machine-level arguments:

1. **Container address**: identifies storage containing a mode byte, an address-calculation component, a bucket-count-like value, and a bucket-array address.
2. **Record address**: identifies storage containing the activity discriminator and two link fields.

The supplied representation uses 32-bit integer arguments as addresses and four-byte address-bearing fields. This contract describes that represented 32-bit address model; it does not establish portability to a wider-pointer environment.

## Behavior

### Inactive-record path

The first operation is a four-byte read of the record field at `0x04`.

If its value is zero, execution returns immediately. In particular:

- Neither link field is read.
- No container field is read.
- No bucket entry or linked record is accessed.
- F-682cc3fccb47 is not called.
- Neither stale nor nonzero link values are cleared.

Zero therefore acts as a gate, not as a request to normalize all record fields.

### Nonzero-record path

If the initial discriminator read is nonzero, the function proceeds through the following phases.

#### 1. Repair the successor-side back-link

The function reads the record field at `0x08`.

If that field is nonzero, it writes the record’s current four-byte value at `0x0C` into the four-byte field at offset `0x0C` of the record addressed by the `0x08` link.

Under the conventional list interpretation, the successor’s predecessor becomes this record’s predecessor.

If the `0x08` field is zero, this write is skipped.

This phase precedes the decision between updating a bucket entry and updating the other linked record.

#### 2. Repair either a bucket entry or the predecessor-side forward-link

The function reads the record field at `0x0C` and branches on whether it is zero.

**When the field is zero:**

The function computes a bucket-entry address using:

- The current four-byte value at record offset `0x04`.
- The current four-byte value at container offset `0xCC`.
- The current bucket-array base at container offset `0xD0`.

Let the first value be \(h\), the second \(n\), and the bucket-array base \(B\). The selected index is:

\[
i = h \mathbin{\&} ((n - 1) \bmod 2^{32})
\]

The destination is the four-byte entry beginning at \(B + 4i\), subject to the represented address arithmetic. The value written is the record’s current four-byte value at `0x08`.

This is a bit-mask calculation, not general remainder division. It is not equivalent to \(h \bmod n\) for arbitrary \(n\).

**When the field is nonzero:**

The function writes the record’s current four-byte value at `0x08` into the four-byte field at offset `0x08` of the record addressed by the `0x0C` link.

Under the conventional interpretation, the predecessor’s successor becomes this record’s successor.

The bucket-array fields are not needed on this branch.

#### 3. Optionally invoke the dependency

After the structural write in phase 2, the function reads the container byte at `0x14`.

- If the byte is zero, no dependency call occurs.
- If the byte is nonzero, F-682cc3fccb47 is called once.

For the call, the argument is the sum of:

- The current four-byte container field at `0x3C`.
- The record address.
- The constant `0x38`.

This is an address-like scalar passed directly to the dependency. The visible function does not dereference that sum before calling.

The dependency call occurs after the link or bucket updates and before the three final clearing writes. Under valid, nonaliasing storage, it therefore runs after disconnection but while the record’s activity and link fields have not yet been cleared by this function.

That observation does not establish what the dependency reads, modifies, owns, or releases.

#### 4. Clear the record fields

If the optional dependency call is skipped or returns normally, the function performs three four-byte zero writes in this order:

1. Record offset `0x04`.
2. Record offset `0x0C`.
3. Record offset `0x08`.

The function then returns.

These writes use the original record-address argument. The function does not visibly reload a replacement record address after the dependency call.

### Read timing and aliasing

The record fields are reread at different phases. They are not all captured in an immutable entry-time snapshot.

Consequently, if a link-target write overlaps the current record or container, it can affect later branch decisions, address calculations, or values being copied. The source does not contain an explicit aliasing defense.

The reliable sequencing is between phases and final writes. The supplied representation does not establish an exact machine-level order for evaluating independent operands within a single address or value expression.

The conventional unlink interpretation therefore assumes valid structural relationships and nonpathological aliasing. A general contract must retain the actual conditional accesses rather than promise snapshot-based unlinking.

## Side effects

On the inactive path, there are no direct writes.

On the active path, direct writes comprise:

- At most one successor-side back-link write.
- Exactly one selected bucket-entry or predecessor-side forward-link write, if execution reaches that phase successfully.
- Three final zero writes, if execution reaches normal completion.

The function does not directly clear the container’s mode byte, decrement a count, resize a table, erase a payload, or release an allocation in the supplied body.

## Acceptance examples

These examples are conditional behavioral expectations derived from the supplied static evidence. They are not reports of executed tests.

Unless stated otherwise, assume valid writable storage, no interfering concurrent access, no aliases that change later reads, representable address calculations, and a normally returning dependency.

### Inactive record with stale links

Given a zero field at record offset `0x04`, both link fields may contain nonzero values without being accessed or cleared.

Expected result: immediate return, unchanged memory, and no dependency invocation. Container validity is irrelevant to this path because it is not read.

### Interior record

Given a nonzero discriminator, a nonzero successor link, and a nonzero predecessor link:

- The successor’s `0x0C` field receives the predecessor link.
- The predecessor’s `0x08` field receives the successor link.
- No bucket entry is updated.
- The mode byte determines whether the dependency is called.
- On normal completion, the record’s three fields are cleared in the specified order.

### First record in a bucket

Given a nonzero discriminator, a nonzero successor link, and a zero predecessor link:

- The successor’s `0x0C` field is written with zero.
- The selected bucket entry receives the successor link.

For example, with discriminator `0x2B` and container value `16` at `0xCC`, the index is `0x2B & 0x0F`, namely `11`. The bucket write occurs at byte offset `44` from the bucket-array base.

### Last record with a predecessor

Given a nonzero discriminator, zero successor link, and nonzero predecessor link:

- No successor-side write occurs.
- The predecessor’s `0x08` field is written with zero.
- No bucket entry is updated.

### Sole record in a bucket

Given a nonzero discriminator and two zero links:

- No linked-record field is written.
- The selected bucket entry is written with zero.
- Optional dependency invocation and final clearing follow.

### Non-power-of-two bucket parameter

With discriminator `7` and container value `6` at `0xCC`, the selected index is:

\[
7 \mathbin{\&} 5 = 5
\]

It is not `1`, the result of remainder division by six. Acceptance must follow the mask calculation rather than inferred hash-table intent.

### Zero bucket parameter

With zero at container offset `0xCC`, the 32-bit subtraction produces an all-ones mask, so the index equals the discriminator’s 32-bit pattern.

The function does not reject this condition. Successful completion still requires the resulting destination to be valid. This is not evidence that a zero bucket parameter is a supported container state.

### Enabled dependency

Given a nonzero mode byte, the dependency is called after the structural writes but before the final clears.

If it returns while leaving the record writable, the caller performs the three zero writes even if the dependency changed those fields. No preservation of other dependency-modified state is established.
