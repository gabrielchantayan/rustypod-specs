# F-144056a67d05

## Purpose

F-144056a67d05 is a state-mutating operation with a nominal 64-bit result. Its visible behavior includes indirect calls, width-specific memory accesses, processor-specific operations, a potentially unbounded loop, and multiple termination forms.

An application-level purpose is **documented_only**. The supplied representation does not establish an allocator, object constructor, record-processing API, or protocol operation.

This contract describes established static evidence, subject to warnings about invalid instruction data, incomplete control-flow recovery, and overlapping global storage. It does not establish that every represented path is executable.

## Interface

### Explicit inputs and additional entry state

The nominal interface has four 32-bit integer inputs:

- **First input:** used in an address for a halfword zero store and in shifted address arithmetic.
- **Second input:** used in arithmetic right shifts, a call argument, and a shift count.
- **Third input:** selects the initial route.
- **Fourth input:** determines a destination for a 32-bit function-address store; its sign extension subsequently participates in address arithmetic.

The operation also consumes incoming register state, link-derived target information, processor state, global storage, and secondary register results from dependencies. Four integer arguments alone therefore do not establish a sufficient calling interface.

Exactly **two incoming stack words** are read by the represented body:

| Stack-relative offset | Width | Visible use |
|---|---:|---|
| `0x110` | 32 bits | Argument to a call following the record-like stores |
| `0x278` | 32 bits | Argument to an earlier call in the preparation sequence |

These offsets identify locations in the supplied representation’s stack coordinate system; a complete calling convention is not established. The words are consumed at their respective call sites, not visibly snapshotted at entry. Earlier dependencies could affect their contents if aliasing permits.

The slot at offset `0x130` is **not a third incoming input**. Its incoming contents are never explicitly read. The loop body assigns a 32-bit XOR-derived value to it. Stack addresses at offsets zero and `0x12C` are also exposed to dependencies; the accessible extents and effects of those exposures are unknown.

### Result and errors

The nominal result is 64 bits. Its low and high 32-bit halves are used independently as arithmetic values and addresses.

Normal represented returns either:

- Construct a result whose low half is twice a selected 32-bit value and whose high half is a global word minus 84; or
- Return the 64-bit result of an unresolved terminal dependency.

No success convention, error-number scheme, pointer-return convention, or ownership transfer is established. Other paths may loop, fault, encounter invalid instruction data, or fail to return from a dependency or processor service.

### Widths and preconditions

The representation distinguishes 8-, 16-, 32-, and 64-bit accesses. Unsigned byte and halfword reads are zero-extended; the signed halfword read is sign-extended. Narrow stores retain the corresponding low bits. Concatenation of two 32-bit halves is not sign extension.

Signed-overflow and unsigned-carry predicates must retain their distinct meanings. Expressions containing overflowing signed arithmetic, signed left shifts, or excessive shift counts are not assigned portable language semantics here. Conditional bit-pattern examples assume explicitly stated 32-bit machine behavior.

Normal completion requires valid effective addresses for all reached accesses and valid dependency targets under the actual calling convention. No general bounds, alignment, null-pointer, or fault-recovery checks are visible.

## Behavior

That route performs the following visible operations in order:

1. Store a 16-bit zero at the first input plus an incoming register-derived offset.
2. Derive an address expression by shifting the first input left once, arithmetically shifting it right once, and subtracting 82.
3. Call F-U01 with 45 and a global word.
4. Read a byte at the derived address plus another incoming register value plus nine.
5. Call F-U02 with the second input arithmetically shifted right by five, minus 79, and the byte.
6. Store a 32-bit reference to F-0d1559cd79ec at the fourth input arithmetically shifted right by thirteen, plus 74.
7. Reduce the working fourth-input value to its arithmetic right shift by 31.

The reduced value is zero or all one bits under the stated signed interpretation. It is used numerically, not merely as a Boolean.

F-U02’s 32-bit result minus 56 is arithmetically shifted by a count derived from the shifted second input plus 21, masked to eight bits, then doubled. Counts outside the ordinary 32-bit range remain an unresolved machine-semantics issue.

The doubled value supplies three predicates:

- Unsigned comparison against `0xFFFFFFCD`.
- Signed overflow when adding 50.
- Negativity of that addition’s 32-bit result.

A byte is read at the reduced fourth-input value multiplied by `0x40000`. F-U03 then returns a 64-bit value. A byte is stored at its low-half address plus the reduced value multiplied by `0x20000`; the stored byte is the low byte of that offset. With the stated zero/all-one sign extension and ordinary 32-bit bit-pattern arithmetic, the stored byte is zero.

If the negativity and signed-overflow predicates agree, execution enters the shared continuation with:

- F-U03’s complete 64-bit result;
- A retained working value of 13;
- The unsigned predicate computed above;
- The byte read from the sign-derived address.

Otherwise, the preparation base becomes the reduced fourth-input value shifted left by 28, and execution enters the main preparation route. When the initial third-input condition is false, that route instead uses the incoming preparation base unchanged.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests.

1. **Initial boundary:** with signed arithmetic right shifts, third inputs 0 and 511 select the special route; 512 and −1 do not.

2. **Stack inputs:** the body consumes incoming words at offsets `0x110` and `0x278`. Changing only the initial contents of offset `0x130` supplies no additional explicit input read. Dependency-mediated reads remain unconstrained.

3. **Stack assignment ordering:** when the loop reaches F-U35 and continues normally, the XOR-derived value is assigned at offset `0x130` after F-U35 and before F-U36. If F-U36 can access that slot, its view is subject to the intervening assignment and any aliasing effects.

4. **Captured global:** if F-U35 changes the global used for XOR, the represented XOR still uses the word captured before the call.

5. **Halfword extension:** a saved unsigned halfword of `0xFFFF` produces a four-byte store of `0x0000FFFF` at the low-half address plus twelve. Its separate halfword store contains `0xFFFF`.

6. **Signed offset:** a signed-halfword value of −2 makes the subsequent halfword read use the captured global base minus two, not plus 65,534.

7. **Distinct bytes:** if the preparation byte is 3 and the branch byte is 7, the earlier direct word read uses address 55; the later word read uses F-U18’s result plus seven.

8. **Overflow selection:** signed word `0x80000000` minus address value 1 selects signed overflow. Subtracting 20 from 10 does not.

9. **Untruncated addition:** branch byte 255 produces 273 when increased by 18, not 17.

10. **Overflow-route byte:** if its byte read yields `0xAB`, the later four-byte store at the returned base plus `0x07000044` contains `0x000000AB`.

11. **Exit visibility:** the loop’s word store at the current high-half address plus 62 occurs before its early-return test. The later stack assignment at offset `0x130` is not reached on that exit.

12. **Terminal distinction:** the no-carry overflow route performs its byte store before invalid-data termination; it does not establish a numeric failure result.
