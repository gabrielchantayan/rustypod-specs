# F-7bb7a5041e89

## Purpose

F-7bb7a5041e89 conditionally replaces a destination object's leading handle with a source object's leading handle, then performs a common sequence that updates destination-associated state.

The visible behavior has two distinct parts:

- When the destination and source addresses differ, the function processes any existing destination handle, clears that handle if processing continues, and invokes a dependency with the destination address and the source's then-current leading handle.
- Regardless of address equality, normal execution performs several dependency calls involving destination-associated storage, then writes the 32-bit values 1 and 0 at destination offsets 4 and 8.

The handle processing resembles reference-counted release, and the replacement resembles assignment. Those are inferred intentions, not established ownership guarantees. The dependencies' implementations are unavailable.

This contract describes the supplied static representation. It does not establish that any input is safe at runtime, that any dependency succeeds, or that a path annotated as non-returning actually terminates.

## Behavior

### 1. Local argument storage

Before the main conditional work, the function stores all four argument values in local slots.

The local source-address and destination-address slots later escape through pointer arguments. No explicit subsequent use of the copied third and fourth arguments is visible. Physical accessibility of neighboring stack storage is not an established interface.

### 2. Distinct-address processing

This section is skipped entirely when the destination address equals the source address.

If the addresses differ, the function first reads the destination's leading handle.

#### Initially zero destination handle

If the observed handle is zero:

- The decrement and release-like processing is skipped.
- No explicit clearing store is performed by this branch.
- Execution proceeds to the replacement dependency call.

#### Initially nonzero destination handle

If the observed handle is nonzero:

1. F-fcc813560ee5 is called with no explicit arguments.
2. After that call returns, the destination handle is read again to locate its offset-4 field.
3. The 32-bit value at that offset is decremented by one and written back.
4. The resulting value determines the next branch.

The handle used for the decrement is not established to be the same as the handle tested before F-fcc813560ee5. That dependency's behavior is unknown.

No atomic primitive is visible for the decrement. A synchronization interpretation of the surrounding calls is only inferred.

For ordinary representable values, the decrement has its usual arithmetic meaning: 1 becomes 0, and 0 becomes −1. The behavior at signed 32-bit overflow is not established by the supplied representation; no overflow handling is visible.

#### Nonzero decrement result

If the decremented value is nonzero:

1. F-6aa19fb2caee is called with no explicit arguments.
2. If it returns, the destination's leading handle is written with zero.

The test is equality with zero, not positivity. A negative result follows this branch as well.

#### Zero decrement result

If the decremented value is zero:

1. The function reads the 32-bit field at offset 0 of the destination's then-current handle.
2. If that field is nonzero:
   - F-2c1e193aae3f is called with no explicit arguments.
   - If it returns, F-feee9156a257 is called with no explicit arguments.
3. If execution continues, F-6aa19fb2caee is called with the destination's then-current handle as its explicit argument.
4. After that call returns, the destination handle is read and saved as a candidate address.
5. If the candidate address is zero, candidate-relative processing is skipped.
6. If the candidate address is nonzero:
   - Its 32-bit field at offset 8 is tested.
   - If that field is nonzero, F-a600efb7b035 is called with no explicit arguments. If it returns, the offset-8 field is read again from the saved candidate address and passed to F-feee9156a257.
   - If execution continues, F-feee9156a257 is called with the saved candidate address.
7. If execution continues beyond this branch, the destination's leading handle is written with zero.

The calls to F-feee9156a257 are marked as non-returning in the supplied representation. That annotation is not independent evidence of the dependency's actual behavior. If a reached invocation does not return, no later operation in this function occurs.

The second read of the candidate's offset-8 field is significant: the value passed after F-a600efb7b035 returns need not equal the nonzero value that selected the branch. The candidate address itself is retained across that call rather than reloaded from the destination.

#### Replacement invocation

If distinct-address execution reaches this point, F-ce09ef551642 is called with:

1. The original destination address.
2. The source's leading 32-bit handle, read for this invocation after the preceding processing.

No visible check is made on a return value.

The source handle is not captured before processing the old destination handle. Dependencies invoked earlier can therefore affect the source value subsequently supplied, if they have access to that storage. Partial overlap between source and destination storage is not detected.

1. F-7806320ebb81 receives the address of the local source-address slot, followed by the address of the local destination-address slot.
2. Its 32-bit result is passed to F-0211f3a6dffa, together with the address at destination offset 12.

## Side effects

### Direct memory effects

Depending on the path, the function directly:

- Reads the destination and source leading handles.
- Reads and writes a 32-bit count-like field through a destination handle.
- Reads two additional handle-relative fields.
- Clears the destination's leading handle.
- Writes 1 and then 0 to destination offsets 4 and 8.
- Supplies local-slot addresses and destination-associated addresses to dependencies.

These operations are ordered by the control flow described above. No total ordering is established among separate reads used to form a single dependency invocation's arguments.

### Ownership and lifetime

The function appears to release an old shared resource and associate a replacement resource. The evidence does not establish:

- Whether a dependency frees memory.
- Whether replacement increments any ownership count.
- Whether local-slot helper calls construct or destroy owned objects.
- Whether dependencies retain pointers passed to them.
- Whether dependencies preserve globals or unrelated memory.

In particular, the destination handle is not cleared before the release-like calls. A non-returning call can prevent that clearing store and all replacement and common-update work.

### Errors and partial state

There is no visible error return or rollback.

If a dependency does not return, raises an exception, transfers control elsewhere, or encounters invalid memory, prior writes may remain observable. The source representation does not specify unwind behavior.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Conditions about dependency behavior are explicit assumptions.

### Equal addresses

Given identical valid source and destination addresses, with every common-sequence dependency returning:

- No count decrement, explicit handle clearing, or F-ce09ef551642 invocation occurs.
- The common update sequence still occurs.
- The final explicit stores write 1 at offset 4 and 0 at offset 8.
- If the address-taking dependencies leave both local address slots unchanged, both 32-bit halves of the return value equal the supplied address.

### Distinct addresses with an initially zero handle

Given distinct valid addresses and an initially zero destination handle:

- The count-processing dependencies are skipped.
- F-ce09ef551642 receives the destination address and the source's handle as read at that point.
- If all subsequent dependencies return, the common sequence and final stores occur.

No claim is made about the final leading handle without F-ce09ef551642's contract.

### Count decreases from two to one

Assume the initial handle is nonzero, F-fcc813560ee5 returns without changing it, and its count-like field is 2:

- The function writes 1 to that field.
- It calls F-6aa19fb2caee without an explicit argument.
- If that call returns, it clears the destination handle before invoking F-ce09ef551642.
- The zero-count candidate-processing branch is not taken.

### Count decreases from zero to minus one

Under the same stability assumptions, but with a count-like value of 0:

- The written result is −1.
- The nonzero-result branch is selected.
- There is no visible validation rejecting the initial zero count.

### Zero-count path stops before replacement

Assume a count decreases from 1 to 0, the subsequently observed offset-0 field is nonzero, F-2c1e193aae3f returns, and the following F-feee9156a257 does not return:

- The count write has occurred.
- The later clearing store, replacement invocation, common sequence, and final destination stores do not occur.

### Local-slot mutation changes the result

- That slot's final value supplies the upper half of the return value.
- The original destination argument still determines the explicit final stores.
