# F-4709071bb5c1

## Purpose

F-4709071bb5c1 writes either zero or the address of a newly initialized, three-word record into a caller-supplied output slot. On normal completion, it returns the address of that slot.

Its established behavior is:

1. Unconditionally invoke F-8157a180d901 with 40, then acquire a candidate through F-ad8359a4d411.
2. Optionally check a nonnull candidate using F-378863f3e00b. An exactly zero checking result triggers an indirect call on the candidate and excludes it from record creation.
3. Clear the output slot.
4. If a candidate remains, invoke F-8157a180d901 with 12, initialize three 32-bit fields in the returned storage, and publish that storage address.

The record may be an ownership-bearing handle, but that is **inferred intent**, not an established ownership contract. The visible operations do not establish allocation semantics, reference counting, object destruction, or caller cleanup obligations.

The second argument does not directly influence branches, dependency arguments, memory accesses, or the returned value. Its application-level meaning is unknown.

The checking argument is tested for zero, not positivity. Any nonzero bit pattern enables checking when a candidate exists. No visible arithmetic, conversion, range validation, or normalization is applied to it.

### Return value

On normal completion, the function returns the original output-slot address.

This return value is not a separate success indicator. With valid, non-overlapping storage and dependencies that return normally without invalidating required accesses:

- A zero output means no candidate was published.
- A nonzero output identifies the initialized record.

A zero output does not distinguish null acquisition from rejection by the checking dependency.

### Record representation

The record uses 12 bytes arranged as three consecutive 32-bit words:

| Byte offset | Value written |
|---|---|
| 0 | Candidate address |
| 4 | Integer 1 |
| 8 | Integer 0 |

The supplied representation stores addresses in 32-bit words. This contract describes that represented address model; it does not establish a native wider-pointer layout.

The field offsets are fixed. The visible body performs no variable-length calculation, size multiplication, or candidate-address arithmetic. The last two fields have established initial values but unknown semantic meanings.

For normal completion:

## Behavior

### Initial calls

The first visible operation is an unconditional call to F-8157a180d901 with 40.

The returned value is discarded. This does not make the call optional: its effects occur before candidate acquisition on every invocation that reaches and completes it. It occurs even on paths that ultimately publish no record.

Next, F-ad8359a4d411 is invoked with no visible arguments. Its result becomes the candidate.

No explicit dataflow connects the discarded first result to the candidate. A connection through hidden state is possible but **documented_only**. The two calls must not be collapsed into a presumed single allocation or construction operation.

The function has not directly written the output slot at this stage. Dependencies may have their own effects; preservation of the output slot or other memory is not established.

### Optional checking

F-378863f3e00b is called only when both the candidate and the checking argument are nonzero.

It receives:

1. The candidate address.
2. The unchanged checking argument.

Its represented 32-bit integer result controls the next step:

- Nonzero: retain the candidate for record creation.
- Exactly zero: perform the rejection dispatch.

Negative nonzero results take the same path as positive nonzero results. The checking result is neither returned nor stored in the record.

If the candidate is null, checking is skipped regardless of the checking argument. If the checking argument is zero, checking is skipped regardless of the contents of a nonnull candidate.

### Rejection dispatch

After an exactly zero checking result, the function resolves an indirect target through the candidate:

1. Read the candidate’s first 32-bit word as a dispatch-table address.
2. Read the callable address at byte offset 4 from that table.
3. Invoke that callable with the candidate address as its sole visible argument.

These reads occur after F-378863f3e00b returns. If that dependency changes the candidate’s first word or the table entry, the subsequent dispatch uses the changed contents. The function does not preserve or use a previously read dispatch target.

The indirect call’s result is unused. If it returns normally, the candidate is excluded from subsequent record creation.

This operation resembles cleanup or destruction, but that interpretation is **inferred intent**. The visible body does not establish whether the call releases memory, changes ownership, destroys an object, or merely performs another action. Nor does it establish that checking leaves the candidate valid for dispatch.

### Output clearing

After acquisition and any checking and rejection dispatch, the function writes a 32-bit zero into the output slot.

The ordering is observable:

- Clearing follows the unconditional request with 40.
- Clearing follows candidate acquisition.
- Clearing follows checking when checking occurs.
- Clearing follows the indirect call when rejection occurs.
- Clearing precedes the conditional request with 12.

Therefore, there is no general guarantee that the output is cleared if an earlier dependency fails to return, transfers control elsewhere, or prevents execution from reaching this store.

If no candidate remains, no request with 12 occurs. The function returns the output-slot address after clearing the slot.

### Record initialization and publication

If a candidate remains after output clearing, the function invokes F-8157a180d901 with 12.

It uses the returned address without a visible validity check. The direct writes then occur in this order:

1. Candidate address to record offset 0.
2. The 32-bit value 1 to record offset 4.
3. The 32-bit value 0 to record offset 8.
4. Record address to the output slot.

No dependency call is visible between these four stores. The function then returns the output-slot address.

For valid, non-overlapping storage, the record fields are initialized before its address is published through the output slot. This establishes visible operation order only. It does not establish atomic publication, memory barriers, synchronization, or safety for concurrent readers.

If the storage result is null or unusable, the function still attempts the first record store. The visible body supplies no defined null-output failure return for that condition.

### Aliasing

The function does not enforce separation among the output slot, candidate storage, dispatch table, and record storage.

The ordinary final record layout requires that the output slot not overlap the record. Otherwise, the final publication store may overwrite a record field or part of one.

An output slot overlapping the candidate can modify candidate storage when cleared. This happens after checking and any rejection dispatch, but before the request with 12 on the retained-candidate path.

Aliasing can also matter inside dependencies. Because their effects are unknown, the function does not guarantee that addresses remain valid or that memory remains unchanged across calls.

For overlapping storage, the direct access sequence remains established, but the ordinary postconditions are not guaranteed. There is no visible overlap repair or defensive copy.

## Side effects

The direct writes are:

- One 32-bit output clear on every path reaching output initialization.
- Three 32-bit record-field stores on the retained-candidate path, provided execution reaches each store.
- One 32-bit output publication store after those fields are written.

The function does not directly read the output slot’s previous value. It does not visibly release, inspect, or otherwise manage an object referenced by that previous value before overwriting the slot.

Dependencies and the indirect target may have additional effects. Their preservation of globals, output memory, candidate contents, or unrelated state is not established. Reentrant activity is not excluded by the supplied evidence.

Ownership is **documented_only**:

- The result of the request with 40 is discarded; its ownership disposition is unknown.
- The candidate is stored without a visible retain operation.
- Rejection dispatch does not establish release or destruction.
- The record’s two integer fields do not establish a reference-counting protocol.
- No record-disposal operation or caller release requirement is supplied.

There is no visible error-code return, diagnostic operation, rollback sequence, or exception handler. Earlier dependency effects and completed writes are not visibly undone if later execution fails.

## Acceptance examples

These examples are conditional criteria derived from static evidence, not executed tests. Except where stated otherwise, they assume normal returns, valid accesses, and non-overlapping output and record storage.

### Null acquisition

Given that F-ad8359a4d411 returns null:

- F-8157a180d901 has already been called with 40.
- F-378863f3e00b is skipped even if the checking argument is nonzero.
- No rejection dispatch occurs.
- The output slot is cleared.
- No request with 12 occurs.
- The returned value is the output-slot address.

### Checking disabled

Given a nonnull candidate and a zero checking argument:

- Checking and rejection dispatch are skipped.
- The output slot is cleared before the request with 12.
- Usable returned storage receives the candidate address, 1, and 0, in that order.
- The record address is then written to the output slot.

### Nonzero checking result

Given a nonnull candidate, a nonzero checking argument, and a nonzero checking result:

- F-378863f3e00b receives the candidate and unchanged checking argument.
- Rejection dispatch is skipped.
- Record creation and publication proceed.

A negative nonzero checking argument enables checking. A negative nonzero checking result retains the candidate.

### Zero checking result

Given a nonnull candidate, a nonzero checking argument, and a zero checking result:

- Dispatch-table contents are read after checking returns.
- The selected callable receives the candidate.
- If that call returns normally, the output slot is cleared.
- No request with 12 occurs and no record is published.

Whether the candidate was released is not an acceptance condition established by this function.

### Checking changes the dispatch target

Given that checking returns zero after changing the candidate’s dispatch-table reference, and the resulting accesses are valid:

- Rejection dispatch follows the changed reference.
- No pre-check dispatch-table value is used.

If checking invalidates the candidate instead, safe dispatch is not guaranteed.

### Unusable record storage

Given a retained candidate and an unusable result from the request with 12:

- The function’s direct output clear has already occurred.
- No validity guard precedes the first record store.
- Normal completion with a zero output is not established.

The exact runtime consequence is **documented_only**.

### Existing output value

Given a preexisting nonzero output value:

- The visible body does not read it or invoke cleanup based on it.
- The slot is overwritten with zero.
- If record initialization completes, the slot is subsequently overwritten with the new record address.

### Output overlapping a record field

Given that the output slot coincides with the record field at offset 4 and all accesses remain valid:

- Initialization writes 1 to that field.
- Final publication subsequently writes the record address to the same word.

The ordinary final layout therefore does not hold for this overlap.
