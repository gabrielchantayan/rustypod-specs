# F-6405c52151a7

## Purpose

F-6405c52151a7 performs two ordered collection searches and publishes an opaque eight-byte result through caller-provided storage.

The first search filters records using a comparison key, a numeric selector, and a mode selector. Two unconditional dependency calls then determine whether the second search is eligible. Qualifying records cause explicit replacement of a local two-word accumulator. Neither search stops after a replacement.

The last explicit replacement determines the published result only if subsequent dependency effects do not change the accumulator. In particular, the gate dependency receives the accumulator’s address; its behavior is not established as read-only.

The search-and-replacement structure is established by static evidence. Interpreting the second search as a fallback, or the result as a string, resource, reference, or owning handle, is inferred intent rather than an established contract.

## Behavior

### Root capture and initialization

The function captures the current shared-root reference and initializes its local accumulator to two zero-valued 32-bit words.

The captured root does not supply every subsequent root access:

- The first-collection presence check independently accesses the shared global and examines that root’s `+8` field.
- If present, the first-collection count lookup accesses the shared global again and obtains the count through that root’s `+8` field.
- First-search retrieval calls use the captured root.
- Second-collection access uses the captured root.

There is no equality check or synchronization establishing that these global-based accesses identify the captured root.

### Indirect retrieval-call evaluation

Each retrieval call in either search contains **two separate source-level evaluations** of the captured root’s relevant collection field:

1. One obtains the collection used to locate the dispatch table and its entry at `+0x3c`.
2. The other obtains the collection reference passed as the receiver argument.

For the first search, both expressions refer to the captured root’s `+8` field. For the second search, both refer to its `+4` field.

The relative evaluation order of the dispatch-target expression and receiver-argument expression is unspecified. The supplied body does not establish a single collection reference captured once and reused for both purposes.

Dispatch-target/receiver agreement therefore requires the relevant collection field to remain stable across those evaluations, or otherwise to yield the same reference. If they yield different references, the call uses an entry selected through one collection and a receiver obtained through the other. Whether such a call is valid depends on the objects and dependency contract.

This distinction concerns source-level evaluations. It does not establish an actual machine-load count, an intervening mutation, or defined behavior under concurrent mutation.

### First collection search

The first search is entered only when the global-based presence check finds a nonzero first-collection reference. Its initial signed 32-bit count is retained as the loop bound.

Indices begin at zero and increase by one while strictly less than that count. A zero or negative count causes no retrieval calls.

Each iteration invokes D-02 with the separately evaluated receiver reference, the signed 32-bit index, and the address of a local record-reference output slot. Dispatch selection follows the separate evaluation described above.

Immediately after retrieval returns, the function copies the output slot’s contents into a saved record reference, before checking retrieval status. A zero status skips matching for that iteration. A nonzero status enables these steps:

1. D-01 receives the unchanged comparison key and the address at retrieved-record offset `+2`.
2. Only a zero comparison result permits reading the signed 16-bit field at saved-record offset `+0x88`.
3. That field is converted to unsigned 32-bit and compared with the complete numeric selector.
4. If the numeric comparison succeeds, exact mode selector `0x80` bypasses mode filtering. Otherwise, the unsigned byte at saved-record offset `+0x84` must equal the complete mode selector.
5. A qualifying record invokes F-118ba0cf6531 with temporary result storage, a 32-bit value obtained at record offset `+0x98`, zero, and a normalized flag.
6. The function explicitly replaces the accumulator’s first word and then its second word from the temporary storage.

The flag is bit 2 of the **requested mode selector**, normalized to zero or one.

The result-production input is obtained through the record reference reread from the retrieval-output slot. It is not necessarily obtained through the saved reference used for numeric and mode checks. D-01 executes before those field reads and may modify accessible records or, if otherwise reachable to it, the output slot. The saved reference remains the basis for the numeric and mode reads.

The signed conversion preserves negative values modulo the unsigned 32-bit range. A field value of `−1` becomes `0xffffffff`, not `65535`; `−32768` becomes `0xffff8000`.

Mode comparison does not truncate the selector. Except for exact wildcard `0x80`, a selector above `255` cannot equal an unsigned byte.

Iteration continues after every replacement. A later qualifying record can replace an earlier result, including with two zero words. This is an explicit assignment rule, not a guarantee against dependency-mediated mutation.

### Unconditional gate calls

After the first search, including when it was skipped, F-1ff036655d4b receives the address of a separate eight-byte local scratch area. The caller does not explicitly initialize that area first.

Its 32-bit return value and the accumulator’s address are passed to F-d80d71162f57.

A zero gate return suppresses the second search. A nonzero return permits its collection-presence check. Neither apparent accumulator emptiness nor the existence of a first-search match independently controls this branch.

The gate may have access to both accumulator words. No supplied contract establishes that it preserves them or refrains from retaining their address. Later dependency effects on exposed storage must therefore be distinguished from this function’s explicit replacements.

### Second collection search

When the gate returns nonzero, the function obtains the second-collection reference from captured-root offset `+4`. A zero reference skips the search. Otherwise, the signed 32-bit count is read through that reference and retained as the loop bound.

Indices begin at zero and increase while strictly less than the retained count. Nonpositive counts cause no retrieval calls.

Each iteration dispatches D-02 using separate collection-field evaluations for dispatch selection and the receiver argument. Neither is guaranteed to identify the collection that supplied the retained count.

A zero retrieval status skips matching. For a nonzero status, F-4a6c0bf0740c receives the 32-bit value at retrieved-record offset `+0x0c` and the original comparison key. Only a zero comparison return permits further processing.

After comparison, subsequent record accesses reread the retrieval-output slot:

- Exact requested mode `0x80` bypasses the filtering-byte read.
- Otherwise, the unsigned byte at the current record’s `+0x10` must equal the full mode selector.
- A surviving candidate is passed to F-76eb2ffc0351 with a record reference, the full numeric selector, and a mode byte obtained from offset `+0x10` before the resolver executes.

The resolver’s record argument and mode-byte expression both refer to the retrieval slot. Their argument-evaluation order is not specified. The body does not establish a record snapshot across comparison, filtering, and resolution.

A zero resolver result causes no result-production call and no explicit accumulator replacement for that iteration. It does not establish accumulator preservation by dependencies.

For a nonzero resolver result:

- The result-production value comes from offset `+0x98` of the returned object.
- The result flag comes from a new mode-byte read through the record reference then held in the retrieval-output slot, after the resolver returns.
- The flag is that byte’s bit 2, normalized to zero or one.

The post-resolver flag need not match the bit in the mode byte supplied to the resolver. The resolved object need not be the record used for comparison or filtering.

### Publication

At normal completion, the function stores the accumulator’s first word at the output destination, then its second word at destination offset `+4`.

These are two 32-bit stores, not an established atomic eight-byte publication. There is no explicit success or failure return.

## Side effects

### Ordering and stability

The broad order is first search, scratch dependency, gate dependency, optional second search, and output publication.

Within a first-search candidate, comparison precedes numeric-field reading; numeric success precedes any required mode-field reading; result production follows the filters.

Within a second-search candidate, comparison precedes filtering and resolution. Successful resolution precedes the mode read used for the result flag.

The function does not establish a collection or record snapshot:

- Global-based root accesses are distinct from captured-root access.
- Counts remain fixed while collection fields are reevaluated.
- Each indirect retrieval independently evaluates its dispatch-selection collection and receiver collection, without a specified order between those evaluations.
- Record-slot contents and mode bytes are reread at the points described above.

No supplied dependency contract guarantees preservation of globals, collection fields, record contents, output slots, or escaped local storage. Conversely, source-level reevaluation alone does not prove that any value changes.

For a positive signed 32-bit count, the loop index need only reach that count. The represented iteration does not require incrementing past the signed 32-bit maximum.

### Storage and ownership

The same local retrieval-output slot is reused across calls and searches. Its address is passed to D-02. The accumulator’s address is passed to the gate. Local scratch and temporary result storage are also passed to dependencies.

Each successful result-production path copies two words into the accumulator without an explicit release of the previous result. No final cleanup call is visible for the accumulator, scratch area, or temporary result storage.

These observations establish neither a leak nor borrowed ownership. Allocation, reference counting, retention, destruction, and ownership transfer remain unknown. Address exposure is not evidence that retention is safe after the function returns.

### Errors and incomplete execution

Zero retrieval statuses skip candidates. Zero comparison results permit further matching. A zero resolver result skips explicit replacement. A zero gate return disables the second search. These outcomes are not identified as function-level errors.

No recovery, rollback, exception handler, or error object is visible. Invalid accesses, dependency failures, and nonreturning calls may prevent publication. Interruption between the output stores may leave only the first word written.

## Acceptance examples

These are conditional static acceptance criteria, not runtime results.

1. **Absent collections.** With a valid stable root, both collection fields zero, and gate dependencies preserving the accumulator, publication writes two zero words. Both gate calls still occur.

2. **Last first-search replacement.** If records at indices zero and two qualify and produce distinct results, the latter is the last explicit first-search replacement. It is published if the gate disables the second search and subsequent dependencies preserve it.

3. **Signed numeric boundary.** A first-record numeric field of `−1` can match selector `0xffffffff`, subject to other filters. It cannot match selector `65535`.

4. **Full-width mode matching.** Selector `0x104` does not match byte `0x04`. Exact selector `0x80` bypasses mode filtering.

5. **Wildcard flags.** With requested mode `0x80`, first-search result production receives flag zero. Second-search result production instead uses bit 2 of the post-resolver mode byte.

6. **Resolver changes mode.** If the resolver receives mode `0x04`, changes the relevant record’s mode to zero, leaves the slot identifying that record, and returns a valid nonzero object, result production receives flag zero.

7. **Comparison changes the slot.** If the second-search comparison dependency changes the slot to another valid record, subsequent record accesses use the reread slot rather than necessarily using the compared record.

8. **Zero resolution.** A candidate resolving to zero causes no result-production call or explicit replacement for that iteration. Accumulator preservation additionally requires dependencies not to mutate it.

9. **Gate controls eligibility.** A nonzero-looking first-search result does not prevent a gate-enabled second search. A zero accumulator does not override a zero gate return.

10. **Later second-search result.** Without intervening accumulator mutation, the later of two second-search replacements supersedes earlier replacements at publication.

11. **Retained count, changed collection.** If the count comes from one collection and both subsequent retrieval-call evaluations consistently yield another valid collection, retrieval uses the latter’s dispatch and receiver with the earlier count.

12. **Independent dispatch and receiver evaluations.** In either search, stability across both collection-field evaluations ensures agreement. If the evaluations yield different collections, the selected dispatch and receiver need not agree. No acceptance criterion may require dispatch selection to occur first or infer a particular machine-load count.

13. **Nonpositive count.** A retained count of zero or a negative value causes no retrieval calls for that search. Gate processing and publication remain reachable.
