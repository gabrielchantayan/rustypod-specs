# F-2a9b2e552b00

## Purpose

F-2a9b2e552b00 dispatches a 32-bit request against an object and a 32-bit selector. Depending on the request, it publishes a scalar, an object-relative address, a dependency result, a resource lookup result, or an address associated with formatted text.

A conditional shared-state refresh precedes dispatch. Unsupported requests and selector mismatches can therefore invoke dependencies before returning status `0`.

**Established static evidence:** dispatch conditions, visible memory accesses, argument expressions, call sequencing, explicit output stores, and return construction.

**Inferred intent:** “refresh,” “resource,” “formatting,” and “shared text” describe apparent roles, not established dependency semantics.

**documented_only:** dependency internals, concrete shared values, ownership rules, and runtime behavior. No runtime tests have been performed.

## Interface

### Arguments and return

| Item | Contract |
|---|---|
| Object | A 32-bit address-like value. Used for relative addresses, field reads, and dependency arguments. |
| Selector | A 32-bit value compared with shared constants. Its input bit pattern becomes the return’s upper word. |
| Request | A 32-bit dispatch value. Explicit cases cover `0x8900`–`0x892e`. |
| Output location | Address receiving one explicit 32-bit store on designated paths. Not initialized unconditionally. |
| Return | A 64-bit value: input selector in bits 63–32; status `0` or `1` in bits 31–0. |

Status `1` does not imply an explicit output store. Status `0` does not imply absence of side effects.

Throughout this contract, **“no output store” means no explicit store by this function**. Dependencies may modify output memory, including through aliases. Unchanged output contents require an additional nonmutation assumption.

There are no visible null, bounds, capacity, alignment, or type checks. Every accessed address and indirect target must satisfy the requirements of the selected path. Dependency failures are not visibly translated into status codes.

## Behavior

### Entry, refresh, and captures

Read Gate’s pointed-to word. If zero, return status `0`, with no output store and no refresh or dispatch calls.

Otherwise, begin with status `1`, retain local storage containing the request and output address, and inspect bit zero of the Flags word at offset `8`.

When that bit is clear:

1. Call F-b255b26284e6 with the refresh handle.
2. If its result is nonzero, call F-398e0e9a318a with the shared text object and the address of the refresh descriptor.
3. Pass that result and two shared constants, in their represented argument order, to F-804adc29bbfb.
4. Call F-d08d3ca17b81 with the refresh handle.

After refresh processing, perform these shared reads in this order:

1. Capture B.
2. Capture A.
3. Read Base and capture that read plus `5`.
4. Read Base again and capture that read plus `0x82`.
5. Read Base again and capture that read plus `0x60`.
6. Read Base again and capture that read minus `0x2a`.

These are four separate Base reads, not derivations from one snapshot. Call the resulting values **Q5**, **Q82**, **Q60**, and **QM**. All occur before dispatch, including for unsupported requests.

The captured A and B are used by `0x891f`. Other A/B comparisons described below use fresh reads. “Current Base” also means a fresh read, not one of these captures.

No dependency is assumed to preserve globals. Later shared-object arguments are read at their respective uses rather than assumed to retain earlier identities.

### Width and arithmetic

Addresses, fields, tokens, query values, and explicit output stores are represented at 32-bit width. Address addition and query-offset arithmetic have no visible overflow checks. The representation alone does not settle language-level signed-overflow behavior.

The split subtraction in `0x8901` explicitly accounts for low-word borrow, producing a 64-bit difference bit pattern. `0x8917` expresses multiplication by `100` at 32-bit width, without established widening or overflow handling.

### Resource operations and token-read timing

Two distinct resource operations recur:

- **R1:** call F-9d0ecc5f6adf for a context; call F-c0b020cd3882 with that context and a token.
- **R2:** call F-9d0ecc5f6adf for a context; call F-ea9442e8ddbb with that context and a token.

A zero token is passed normally. It does not force a zero result.

**Token-read timing is part of the contract:**

| Paths | Token timing |
|---|---|
| Query-based resource paths, including the B branch of `0x891f` | Select and capture the token after the query but before F-9d0ecc5f6adf. |
| `0x8902`, `0x8903` | Read the request-specific token after F-9d0ecc5f6adf. |
| Fixed-token B-only requests | Read the fixed token after F-9d0ecc5f6adf. |
| Recognized A-branch results of `0x891f` | Select the result branch, call F-9d0ecc5f6adf, then read that branch’s token. |
| `0x8915` and byte-`0`/byte-`1` branches of `0x892b`/`0x892c` | Call F-9d0ecc5f6adf, then read Y or N. |

Consequently, mutation of a token slot by F-9d0ecc5f6adf affects the latter paths, but not a token already captured by a query-based path.

Token selection can also read candidates that are not ultimately used:

- Three-result families read the first candidate before testing the first result, then the second candidate if needed. The third candidate is read only on the third result.
- Two-result families read the first candidate before testing its condition; the second is read only when selected.
- `0x8912` reads candidates in order Y, the `0x608f` token, the `0x6090` token, stopping at a match; N is read only for `0x608d`.
- `0x8914` similarly visits its `0x608e`, `0x608f`, and `0x6090` candidates before conditionally reading its `0x608d` token.
- The B branch of `0x891f` visits candidates in result order `0x6033`, `0x6034`, `0x6035`, `0x6036`, `0x6037`, `0x6032`; its `0x6038` token is read only when selected.

Unless stated otherwise, a handled path explicitly stores its 32-bit result and returns status `1`.

## Side effects

The function’s explicit nonlocal writes are its selected 32-bit output stores. Formatting destinations and shared text are passed to dependencies; their modifications are delegated behavior.

Observable sequencing includes:

- Gate validation before refresh.
- Refresh before ordered shared captures.
- Queries before token selection and resource calls.
- Token reads before or after context acquisition as specified.
- Formatting before publication of its destination address.
- Shared-text update before subsequent extraction.
- Final output store only after the result-producing calls return.

Output may alias object fields, shared storage, or dependency-visible memory. No disjointness check, rollback, exception handling, or dependency-error translation is visible.

No allocation or release semantics are established. The local-storage calls in combined formatting do not prove construction/destruction or ownership transfer. Object-relative addresses are not newly allocated results. Dependency-produced addresses have unknown ownership and lifetime; subsequent calls may invalidate backing storage. Passing local storage does not establish permission to retain its address beyond the invocation.

## Acceptance examples

These are conditional criteria, not executed tests.

1. **Disabled Gate:** a zero pointed-to word produces status `0`, preserves the selector in the upper return word, and performs no refresh, dispatch call, or explicit output store.

2. **Unsupported request:** with Gate enabled, refresh flag clear, and refresh predicate nonzero, perform the refresh sequence and ordered captures before returning status `0`.

3. **Handled without publication:** for `0x892b`, inspected byte `2` produces status `1` and no explicit output store. Output contents remain unchanged only if refresh and F-fdd3c46f3034 do not modify that memory.

4. **Pre-context token capture:** for `0x8904` with result `0x605a`, capture its token before F-9d0ecc5f6adf. If that dependency changes the slot, use the previously captured value.

5. **Post-context token read:** for matching-B request `0x891d`, if F-9d0ecc5f6adf changes its fixed-token slot, use the value read after that call.

6. **Shared-text retention:** for `0x891f`, require selector equal to captured A **and unequal to captured B**. With result `0x6039`, skip resource lookup/update, extract the shared-text result, and publish it.

7. **Selector collision:** if captured A and B coincide, `0x891f` result `0x6039` instead follows B: capture token zero, perform R2, and publish that result.

8. **Annotated call returns:** for `0x8915` with zero predicate, if F-a817d8d58c10 returns, acquire context, read Y afterward, complete R1, and publish its result.

9. **Borrow-sensitive subtraction:** first value `0x0000000100000001`, second `0x0000000200000000`, produce difference `0x00000000ffffffff`; F-419ea168c9cf receives high word zero twice.

10. **Zero token is not zero output:** an unlisted `0x8904` query result passes token zero through R1 and publishes the dependency result.

11. **Independent Base reads:** if the four ordered Base reads observe different values, Q5, Q82, Q60, and QM must derive from their respective reads, not a common snapshot.

12. **Address versus content:** `0x890d` publishes `object+0x34`; `0x8918` reads that field, completes formatting, then publishes `object+0x44`.
