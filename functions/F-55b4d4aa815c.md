# F-55b4d4aa815c

## Purpose

F-55b4d4aa815c advances through a requested number of source bytes, submitting successive portions to a three-argument transfer dependency and advancing a cursor in a caller-supplied state object. Whenever the updated cursor reaches or exceeds the object’s current limit, it invokes F-4613ccbcea05. Processing continues only while bytes remain and the most recent boundary-handler result is nonzero.

The apparent intent is to fill a bounded destination region and let F-4613ccbcea05 handle a full region. That interpretation is inferred, not established: the supplied evidence does not define either dependency’s implementation, the ultimate destination of transferred data, or the ownership of any storage.

The return value is a continuation status, not a byte count. A zero result can occur even after the entire requested length has been submitted, because boundary handling occurs before the next completion check.

- Each invocation of F-4613ccbcea05 replaces it with that dependency’s result.

Consequently, successful completion is not guaranteed to return exactly `1`. For example, a boundary handler result of `7` remains `7` unless a later boundary call replaces it.

## Behavior

### Entry and empty requests

The function initializes its recorded status to `1` and its submitted-byte count to zero.

It enters the processing loop only when both conditions hold:

1. The submitted-byte count is less than the unsigned requested length.
2. The recorded status is nonzero.

A requested length of zero therefore returns `1` without reading the state fields, calling either dependency, or directly accessing source storage. No state or source validity requirement arises from this function’s own operations on that path.

### Selecting a portion

At the beginning of each iteration, the function derives an available amount from the 32-bit limit-minus-cursor difference. That result is used as an unsigned 32-bit quantity.

The remaining requested amount is the requested length minus the submitted-byte count. Because the loop requires the submitted count to be less than the request, this subtraction has no unsigned underflow during ordinary execution.

The selected amount is the unsigned minimum of:

- The computed available amount.
- The remaining requested amount.

No explicit check establishes that the cursor is below or equal to the limit before this calculation. An inverted cursor/limit relationship is therefore not rejected. In the apparent 32-bit machine arithmetic, a negative mathematical difference can become a large unsigned amount instead of indicating no space.

### Transfer submission

The transfer dependency receives three arguments:

1. The destination base field plus the cursor field.
2. The source reference plus the submitted-byte count.
3. The selected unsigned 32-bit amount.

The destination base and cursor are read while preparing this call. Their values are not explicitly retained from the earlier available-space calculation.

The dependency is invoked even when the selected amount is zero. The function contains no zero-length-call suppression.

No transfer return value is used. A dependency that reports an error solely through a return value cannot stop this function through that value. A dependency may nevertheless affect execution through memory changes, exceptions, faults, nonreturning behavior, or other mechanisms outside the supplied evidence.

Calling this operation a “transfer” is descriptive. The call shape suggests a destination/source/length operation, but actual byte-copy semantics are not established.

### Progress accounting and cursor update

After the transfer dependency returns normally:

1. The submitted-byte count increases by the selected amount.
2. The function reads the cursor field again.
3. It adds the selected amount to that newly read cursor.
4. It writes the resulting 32-bit value to the cursor field.

The cursor update is therefore not necessarily based on the cursor that formed the transfer destination. If the dependency modifies the state object directly or through aliasing, the post-call cursor value controls the update.

The submitted-byte count records the amount passed to the dependency, not a confirmed amount copied. There is no short-transfer report or adjustment.

For the local submitted count, the selected amount cannot exceed the remaining request. Thus, under the recovered unsigned arithmetic, that count does not wrap while advancing toward a request of at most `2³² − 1`.

### Boundary handling

After writing the cursor, the function reads the limit field and compares it with the just-computed cursor value using an unsigned comparison.

If the limit is less than or equal to that value, F-4613ccbcea05 is invoked with the state reference. Its result becomes the recorded status.

This ordering has several consequences:

- The cursor write occurs before the boundary-handler call.
- Equality triggers the handler; exceeding the limit is not required.
- The handler is invoked even if the transfer just satisfied the entire request.
- A zero handler result prevents subsequent iterations but does not undo the transfer or cursor update.
- A nonzero handler result does not itself establish that the cursor, limit, or base changed.

If the handler returns normally, the next loop-condition check determines whether processing continues. Any subsequent iteration rereads the relevant state fields.

### Termination and progress

Normal return occurs when either:

- The submitted-byte count reaches the requested length; or
- F-4613ccbcea05 returns zero.

The function does not return the submitted count. If the handler stops processing early, the caller cannot obtain the amount submitted from the return value alone.

A zero-sized transfer can produce no local progress. With a stable cursor equal to the limit, each such iteration calls the transfer dependency with length zero, writes the unchanged cursor, and invokes F-4613ccbcea05. If that handler repeatedly returns nonzero without making positive progress possible, the loop can continue indefinitely.

There is no retry limit or independent no-progress detection.

## Side effects

### Directly established effects

For each entered iteration that reaches the corresponding operations, this function:

- Reads the limit and cursor to calculate availability.
- Reads the destination base and cursor to prepare the transfer call.
- Calls the transfer dependency.
- Rereads the cursor after that call.
- Writes the updated cursor.
- Rereads the limit for the boundary comparison.
- Conditionally calls F-4613ccbcea05.

The supplied evidence establishes these phase boundaries. It does not establish the relative machine-level order of individual field reads within a single arithmetic expression or among call-argument expressions.

The only direct state write shown is to the 32-bit cursor field at `+0x10`.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, assume valid address arithmetic, normal dependency returns, and no dependency mutation except the changes explicitly described.

1. **Empty request.**  
   Requested length is zero. The result is `1`; neither dependency is called and no state field is accessed.

2. **Request fits strictly before the limit.**  
   Cursor is `4`, limit is `16`, and requested length is `5`. One transfer is submitted at destination base plus `4`, using the original source reference and amount `5`. The cursor becomes `9`. F-4613ccbcea05 is not called, and the result is `1`.

3. **Request exactly fills the region.**  
   Cursor is `4`, limit is `16`, and requested length is `12`. One amount-`12` transfer occurs, then the cursor becomes `16`. The boundary handler is called despite there being no remaining requested bytes. If it returns zero, this function returns zero even though all requested bytes were submitted.

4. **Processing spans a boundary.**  
   Cursor is `6`, limit is `10`, and requested length is `7`. The first transfer amount is `4`. After the cursor reaches `10`, the handler returns nonzero and sets the cursor to `0`, the limit to `10`, and the base to another valid region. The next transfer uses that new base, source reference plus `4`, and amount `3`. The final cursor is `3`; the returned status is the earlier nonzero handler result.

5. **Boundary handler stops before completion.**  
   Under the previous initial values, the handler instead returns zero after the amount-`4` transfer. No second transfer occurs. The result is zero. The unsubmitted remainder is `3`, but it is not returned.

6. **Initially full region.**  
   Cursor equals limit and the request is nonzero. The transfer dependency is first called with amount zero. Assuming it leaves the state unchanged, the cursor is written unchanged and the boundary handler is called. If that handler returns zero, the function returns zero without positive progress.

7. **Transfer dependency changes the cursor.**  
   A selected transfer amount is `3`. During the call, the dependency changes the cursor to `20` and the limit to `30`. The function then writes cursor `23`, not the pre-call cursor plus `3`, and does not call the boundary handler.

8. **Inverted cursor and limit.**  
   Cursor is `12`, limit is `8`, and the request is `5`. Under wrapping 32-bit subtraction, the computed availability is `2³² − 4`, so the selected amount is `5`, not zero. A transfer is submitted at base plus `12`. With unchanged fields, the cursor becomes `17` and boundary handling follows. This is not evidence that such storage access is valid.
