# F-3151c4d67249

## Purpose

F-3151c4d67249 performs a forward search within a collection associated with a caller-supplied object. It resolves a search operand through a dependency, examines eligible collection entries in ascending index order, and returns the first index whose comparison reports equality.

The search normally begins immediately after the supplied position. A negative resulting start position is clamped to zero. The function distinguishes failure to resolve the search operand from completion without a match.

This search interpretation is inferred intent. The established behavior is narrower: a captured collection handle, a nonzero resolved value, a single signed bound, indexed entry access, and a comparison result of zero control the outcome. The supplied evidence does not establish the collection’s concrete type, the operand’s domain, or the comparison’s equivalence rules.

### Object and entry layout

The function relies on two layouts:

1. The object-reference argument points to a location containing an object address. A signed integer-sized collection handle is read at byte offset `0x24` from that object address.
2. Each entry address returned by F-6bbddce1b930 points to storage whose first four bytes provide the value passed to F-9878699bd825.

No other object fields or entry fields are directly accessed. The collection handle may be pointer-like, but its concrete type and internal layout are not established.

The object-reference argument is therefore an additional level of indirection, not the object address itself.

|---|---|

## Behavior

### Initial read and operand resolution

The function first reads the object address through the object-reference argument. It then reads and retains the collection handle from offset `0x24` of that object.

Only after those reads does it call F-83fcd2d25cd8 with the four-byte search operand.

This order is observable and significant:

- A failing object read can occur before operand resolution is attempted.
- Operand resolution is attempted even when the previously read collection handle is zero.
- The collection handle is captured before the resolver runs.
- If the resolver changes the object reference or the object’s collection field, the function does not reload either to select a different collection.

If F-83fcd2d25cd8 returns zero, the function immediately returns `-2`. It does not adjust the prior position, query a bound, retrieve an entry, or compare an entry.

A nonzero resolver result is retained as the second argument for each subsequent comparison. The function performs no further validation of that value.

### Absent collection

After successful operand resolution, a zero captured collection handle causes the function to return `-1`.

The prior-position increment is not executed on this path. Consequently, even the largest signed prior-position value does not encounter that increment when resolution fails or the collection handle is zero.

### Start-position calculation

With a nonzero collection handle and a nonzero resolved value, the function adds one to the supplied prior position. If the resulting signed value is negative, it replaces it with zero.

For ordinary signed 32-bit inputs where the addition is representable:

- Any prior position from the minimum signed value through `-1` produces a start index of zero.
- A prior position of zero produces a start index of one.
- A nonnegative prior position below the maximum signed value produces the next integer index.

Thus, for defined arithmetic, a nonnegative prior position is excluded from the search. Negative prior positions request a search beginning at index zero rather than negative-index access.

The maximum signed 32-bit prior position, `2,147,483,647`, is an unresolved arithmetic boundary. Incrementing it is not representable as a signed 32-bit integer. The supplied representation does not establish whether the actual executable wraps, traps, or has some other effective behavior. This contract does not assume that it wraps and then clamps to zero.

### Bound acquisition

After calculating the start index, the function calls F-10b760faca36 once with the captured collection handle. Its result is used as a signed upper bound.

This call occurs even if the start index will be outside the returned range. There is no separate early rejection based solely on the start index.

The bound is not refreshed during the search. Changes to the underlying collection do not cause another bound query.

The function examines indices strictly less than the retained bound. A zero or negative bound therefore causes no entry retrieval for a defined, nonnegative start index.

### Entry traversal and comparison

Eligible entries are examined in increasing index order, beginning at the calculated start index.

For each examined index, the observable sequence is:

1. F-6bbddce1b930 receives the captured collection handle and the current index.
2. The function reads the first four-byte word at the returned address.
3. F-9878699bd825 receives that word as its first argument and the retained resolver result as its second argument.
4. A comparison result of zero causes immediate return of the current index.
5. Any nonzero comparison result advances the index by one and continues if it remains below the retained bound.

The comparator’s nonzero values are not otherwise interpreted. Positive and negative nonzero results both mean “continue” to this caller. They are not propagated as errors or used to change traversal direction.

The entry address is not checked for zero before dereferencing. A zero first word, by contrast, is passed directly to the comparator; the function does not reject or skip it.

When multiple eligible entries would compare equal, the function returns the lowest eligible index reached under this traversal order. Entries after that match are not retrieved or compared by this invocation.

If the loop reaches its bound without a zero comparison result, the function returns `-1`.

### Arithmetic boundaries within the loop

For a defined nonnegative starting index and a signed 32-bit bound, the loop increment itself does not require overflow: an examined index is strictly below the bound, so it is at most `2,147,483,646`. Its increment can reach `2,147,483,647`, after which the strict bound comparison prevents another iteration.

This does not resolve the separate overflow question in the initial prior-position increment.

## Side effects

### Direct reads and writes

The function directly reads:

- The object address stored through the first argument.
- The collection handle at object offset `0x24`.
- The first four-byte word of each retrieved entry.

It makes no explicit writes to caller-supplied object or entry storage. Its visible local state consists of captured values, the retained bound, and the advancing index.

No direct global-variable access is shown.

No explicit allocation, deallocation, retain, release, or ownership-transfer operation appears in this function.

These observations do not establish ownership rules for dependency arguments or results. No claim is made that returned storage is borrowed, owned, persistent, or safe to release.

### Error handling

The visible return-code handling recognizes only:

- A zero resolver result, producing `-2`.
- Search completion without a match, producing `-1`.

There is no explicit recovery for invalid memory, an unusable collection handle, a failed entry lookup, or a dependency that does not return normally. A negative bound is treated as an empty search range rather than distinguished as an error. A nonzero comparator result is treated as a mismatch regardless of its possible meaning within the comparator.

## Acceptance examples

The following are conditional acceptance scenarios, not executed tests. Unless otherwise stated, they assume valid memory, normally returning dependencies, stable usable storage, and defined arithmetic.

### Resolution failure takes precedence over collection handling

Given a readable object whose captured collection handle is either zero or nonzero, if F-83fcd2d25cd8 returns zero:

- The result is `-2`.
- The initial object and collection-field reads have already occurred.
- No bound query, entry lookup, or comparison occurs.

### Missing collection still resolves the operand

Given a captured collection handle of zero and a nonzero resolver result:

- The resolver is called.
- The result is `-1`.
- No prior-position increment, bound query, entry lookup, or comparison occurs.

### Negative position starts at zero

Given a prior position of `-5`, a bound of three, and comparison outcomes of nonzero at index zero followed by zero at index one:

- The start index is zero.
- Entries zero and one are retrieved and compared in that order.
- The result is one.
- Entry two is not retrieved.

The same start index is obtained from a prior position of `-1`.

### Nonnegative position excludes itself

Given a prior position of two and a bound of five:

- The first eligible index is three.
- Index two is not examined, even if it would compare equal.
- If index three mismatches and index four matches, the result is four.

### Empty eligible range

Given a prior position of four and a returned bound of five:

- The calculated start index is five.
- The bound is queried once.
- No entry is retrieved.
- The result is `-1`.

Likewise, a zero or negative bound produces no entry retrieval from a defined nonnegative start index.

### Nonzero comparator outcomes all continue

Given eligible indices zero through two and comparator outcomes of a negative nonzero value, a positive nonzero value, and zero:

- All three indices are examined in order.
- Neither nonzero result is returned to the caller.
- The function returns two.

### Collection-field mutation does not redirect the scan

Given a nonzero collection handle captured before resolution, if the resolver changes the object’s collection field but leaves the captured collection usable:

- The bound query and entry lookups still use the captured handle.
- The replacement field value is not reloaded.

If the resolver instead invalidates the captured collection, normal completion is not established.

### Maximum prior position

Given a prior position of `2,147,483,647`:

- Resolver failure still produces `-2` without performing the increment.
- Successful resolution with a zero collection handle still produces `-1` without performing the increment.
- Successful resolution with a nonzero collection handle reaches the unresolved signed-overflow boundary; no normal search result is specified here.
