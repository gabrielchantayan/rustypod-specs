# F-847f7be0c201

## Purpose

F-847f7be0c201 returns a four-byte Boolean result indicating whether an indirectly referenced record and a directly supplied record have equal values in two selected four-byte fields.

The comparison is conditional and ordered:

- A zero address obtained from the indirect input produces a negative result without accessing either record.
- The fields at byte offset 4 are compared first.
- The fields at byte offset 8 are read and compared only when the offset-4 fields match.

This is a selected-field comparison, not a whole-record comparison, a recursive comparison, or a comparison of record addresses. Distinct records can produce a positive result. The same record address does not bypass the field reads.

These statements describe established static behavior. Interpreting the fields as a type tag, length, pointer, identifier, or payload is not supported by the supplied evidence.

## Interface

### Inputs

The function has two inputs:

| Input | Meaning | Required accessible storage |
|---|---|---|
| Indirect record reference | Address of a storage location holding the first record’s address | One readable four-byte address-bearing word |
| Direct record reference | Address used to access the second record | Readable four-byte fields at offsets 4 and, conditionally, 8 |

The supplied representation uses four-byte integer values to carry and compare record addresses and field contents. The indirect input itself is pointer-typed. The complete machine pointer ABI is not independently established.

The first input must identify readable storage even when its stored value is zero. Passing a null or otherwise invalid address as the first input is not equivalent to supplying a readable location containing zero.

The second input has no explicit null check. Its accessibility matters only after the stored first-record address is found to be nonzero.

### Record layout

Only the following portions of each record are examined:

| Byte range relative to record address | Interpretation established here |
|---|---|
| 0–3 | Not read as a record field |
| 4–7 | First four-byte comparison field |
| 8–11 | Second four-byte comparison field, read only after the first fields match |

No minimum allocation size, complete record definition, alignment rule, or field ownership model is independently supplied. The execution environment must permit each access actually reached.

The initial four-byte read through the indirect input is distinct from these record-field accesses. With aliasing, that initial storage location could overlap a record; the function imposes no explicit separation requirement.

### Output

The result occupies four bytes and is exactly one of:

- **1:** the stored first-record address was nonzero, and both selected field pairs compared equal.
- **0:** the stored first-record address was zero, or a reached field comparison failed.

The equality comparisons operate on four-byte integer values. Signedness does not change whether two successfully read values are equal. No ordering comparison, conversion to text, or comparison of pointed-to contents occurs.

### Preconditions

For a normal return:

- The initial address-bearing word must be readable.
- If that word is nonzero, both offset-4 fields must be readable.
- If those offset-4 fields match, both offset-8 fields must also be readable.
- Address formation and each reached four-byte load must be valid under the target execution environment.

There is no established recovery contract for violating these preconditions.

## Behavior

### Initial read and empty-reference case

The first observable data access is a four-byte read through the indirect input. Its value selects the first record.

If that value is zero, the function returns 0. Neither selected field of either record is accessed. In particular, the direct record reference need not be dereferenced on this path.

The stored first-record address is captured by this initial read. There is no second read of the indirect storage location. Changing that location afterward does not, by itself, select a different first record for the remaining accesses.

### First comparison

For a nonzero stored address, the function reads the four-byte field at byte offset 4 from each record and compares the resulting values for equality.

The supplied expression establishes that both offset-4 operands participate before the decision to continue. It does not establish a left-before-right evaluation order between those two reads. Consumers must not depend on which record’s offset-4 field is accessed first.

If the values differ, the function returns 0. Neither offset-8 field is read on that path.

### Second comparison

If the offset-4 values match, the function proceeds to the offset-8 fields.

The supplied representation establishes this order:

1. Read the first record’s four-byte field at offset 8.
2. Read the direct record’s four-byte field at offset 8.
3. Compare the two values and return 1 for equality or 0 for inequality.

No additional record fields are consulted. The offset-4 values are not reread before returning.

### Comparison boundaries

The function compares values, not record identity:

- Different record addresses can yield 1.
- Equal record addresses do not cause an immediate positive return.
- Equal offset-4 fields alone are insufficient.
- Differences outside the two selected fields do not affect the result unless they affect the validity or observed values of a reached access.

The behavior is also shallow. If an offset-8 value happens to represent an address, only that four-byte value is compared. No access through it is present.

### Arithmetic and consistency

The only record-address displacements are 4 and 8 bytes. There is no count, loop, multiplication, variable displacement, or accumulation.

The function performs no explicit overflow or address-range validation. The supplied representation does not justify a portable wraparound rule for addresses near the end of the representable range. Such inputs require a target-specific account of address formation and memory access; they are not established normal-return cases.

The reads do not form an established atomic snapshot. There is no visible lock, retry, version check, or consistency validation. Where the execution environment permits memory to change between accesses, the result reflects the values observed by the reached reads. Behavior under data races or device-specific access rules is not established.

## Side effects

There are no explicit memory writes, allocations, deallocations, calls, or global-state accesses in the supplied function.

In particular, the function does not:

- Replace or clear the stored first-record address.
- Modify either record.
- Transfer ownership of either record or the indirect storage.
- Retain an input address in persistent storage.
- Release memory on either result path.

Memory reads remain observable where the execution environment makes them observable, such as certain device-memory mappings. The source alone does not establish that ordinary integer loads are suitable for such mappings or provide required device-access semantics.

An invalid reached access may prevent a normal return. No error code, exception translation, diagnostic, or cleanup behavior is implemented here. Whether an invalid access traps, faults, or has another consequence is outside the established contract.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not runtime test results. Unless an example says otherwise, assume stable ordinary memory, valid address formation, and all reached accesses being readable.

| Condition | Required result and access behavior |
|---|---|
| The indirect storage contains zero. | Return 0. Do not access either record’s offset-4 or offset-8 field. |
| The stored first-record address is nonzero; the offset-4 fields contain 7 and 9. | Return 0. Read both offset-4 fields; do not read either offset-8 field. |
| Both offset-4 fields contain 7; both offset-8 fields contain 42. | Return 1 after reading both field pairs. |
| Both offset-4 fields contain 7; the offset-8 fields contain 42 and 43. | Return 0 after reading both field pairs. |
| The records have different addresses but equal selected field values. | Return 1. Address inequality is not a rejection condition. |
| The records have equal selected field values but differ in bytes 0–3 or other unexamined storage. | Return 1. Those differences do not participate in the comparison. |
| Both record references select the same stable, readable record. | Return 1 after the ordinary field reads; no identity shortcut is established. |
| Matching offset-8 values represent addresses of different or invalid underlying objects. | Return 1 if the offset-4 values also match. The offset-8 values are not dereferenced. |

Additional boundary criteria:

- If the indirect storage contains zero, an otherwise unusable direct record reference does not cause a record access through this function.
- If the offset-4 fields differ, inaccessible offset-8 storage is not reached.
- If the offset-4 fields match but an offset-8 access is invalid, no normal-return result is specified.
- If the first input does not identify readable address-bearing storage, the zero-reference shortcut cannot be relied upon: the initial read itself is required.
- Field values with the high bit set are not rejected, normalized, or treated as sentinels. Equality of the read values remains the criterion.
