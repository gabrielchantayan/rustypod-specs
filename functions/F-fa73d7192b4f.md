# F-fa73d7192b4f

## Purpose

F-fa73d7192b4f conditionally transforms caller-supplied bytes and writes them to a payload location selected through a descriptor and a record lookup. Eligibility depends on the descriptor, two flag checks, lookup success, two header bytes, and a comparison between a decoded size and the requested size plus 20. A size mismatch invokes an additional dependency before payload processing can proceed.

**Established static behavior:** the accepted payload-processing path returns zero. Rejection paths return values from **five external status slots**, or propagate a nonzero result from F-35c7724f8775. A separate external value is the flag multiplier, not a sixth status.

**Inferred intent:** the function appears to update an encoded record, potentially requesting a storage or size adjustment first. Neither the record’s application-level meaning nor the adjustment dependency’s actual operation is established.

This contract describes the supplied static representation. It does not establish portable language semantics for arbitrary integer-derived addresses or arithmetic overflow.

## Behavior

### Initial eligibility

Checks occur in this order:

1. Reject a null descriptor.
2. Otherwise, read its base field and reject a zero value.
3. Otherwise, reject a zero source address when the requested byte count is nonzero.

Each rejection returns the initial-argument status.

The source condition accepts zero length, rejects a null source for length one, and also rejects a null source for every larger unsigned length. There is no special exemption for large counts.

A null descriptor is not dereferenced. A zero initial base prevents flag evaluation and dependency calls. Zero length does not bypass subsequent validation.

### Flag checks

The function multiplies the descriptor’s 32-bit flag-bearing field by an external multiplier and tests bit 0 of the product. If set, it returns the first flag status.

Only if that check passes does it evaluate the field-and-multiplier expression again and test bit 1. If set, it returns the second flag status.

For stable inputs, bit 0 therefore has priority over bit 1. These are product-bit checks, not necessarily checks of the raw descriptor bits.

The two expressions are separate evaluations. The contract does not replace them with one saved product or require their inputs to remain unchanged. The static representation does not establish a finer ordering between the field read and multiplier read within either expression.

Only the low product bits affect these decisions. Their values are determined by the corresponding low input bits; higher product bits do not affect the branch conditions.

### Record lookup

After both flag checks pass, F-e81ed1edd673 receives:

1. The descriptor address.
2. The opaque lookup context.

A zero result causes return of the lookup-failure status. A nonzero result is retained as the record offset.

There is no explicit offset-range check. A nonzero result is not proven to be positive, within an allocation, or safe to add to a base.

After successful lookup, the descriptor base is read again. This newly read value selects the header. The initial eligibility read does not constrain this later value: lookup may have changed it, and no repeated nonzero check occurs.

### Header validation

The byte at relative offset 15 is checked first. Its value is multiplied by 23 and narrowed to eight bits; the narrowed result must be zero.

Only if that check succeeds is the same check performed on the byte at relative offset 14.

Because multiplication by 23 is invertible modulo 256, either narrowed product is zero exactly when its input byte is zero. Thus both original bytes must be zero.

Consequences:

- A nonzero byte at offset 15 returns the header-rejection status without the explicit offset-14 read.
- A zero byte at offset 15 permits the offset-14 check.
- A nonzero byte at offset 14 returns the same status.
- Size decoding is reached only after both checks pass.

Signed interpretation of an input byte does not change this eight-bit zero-test equivalence.

### Size decoding

The four bytes at relative offsets 0–3 contribute to a 32-bit decoded size. For each byte \(b_i\), define:

\[
q_i=(23b_i)\bmod 256.
\]

The resulting size is:

\[
S=2^{24}q_0+2^{16}q_1+2^8q_2+q_3.
\]

This is most-significant-byte-first assembly from individual bytes, not a native-endian word load. The supplied expression does not establish a sequential left-to-right read order among these four bytes.

The visible 16-bit conversions do not reduce the input-byte range: byte values 0–255 remain representable. The assembled value is retained as 32 bits. This description captures the width-sensitive result of the supplied representation, rather than promising that every equivalent signed expression would be portable.

### Size comparison and dependency result

Let \(N\) be the requested byte count. The requested total is:

\[
Q=(N+20)\bmod 2^{32}.
\]

There is no overflow rejection for this addition.

If \(S=Q\), F-35c7724f8775 is skipped and the accepted-path return value is zero.

Otherwise, F-35c7724f8775 receives three 32-bit values:

1. The saved record offset.
2. \(Q\).
3. The low 32 bits of the record offset plus \(S\).

The third argument is an offset-derived endpoint. It is not adjusted by the descriptor base.

A nonzero dependency result is returned unchanged, without entering the payload loop. A zero result allows payload processing.

This call site does not establish that the dependency allocates, resizes, moves data, updates metadata, or verifies capacity. Its successful return does not prove any of those properties.

### Destination selection

After size acceptance, the descriptor base is read once more. The payload destination is selected by adding the saved record offset and 20 to this base.

This read occurs whether adjustment was skipped or returned zero. There is no new base-validity check and no repeated header validation.

The selected base and offset are then retained for payload processing; the descriptor is not explicitly reread for each byte. Consequently, payload writes that modify descriptor storage do not cause the loop to recompute its destination from the modified descriptor.

### Transformation and traversal

For a source byte with bit-pattern value \(x\), the written byte is:

\[
T(x)=(19x+124)\bmod 256.
\]

This is the eight-bit result of the supplied arithmetic. Signed-byte interpretation does not change the final byte pattern.

Direction is selected by an unsigned comparison between the source address and the selected payload destination address:

- Source address less than or equal to destination: process indices \(N-1\) down to 0.
- Source address greater than destination: process indices 0 through \(N-1\).

For each index, the source byte is read before its corresponding transformed byte is written. There is no complete source snapshot.

For ordinary valid, nonwrapping overlapping ranges, this direction preserves the original source bytes needed by later iterations. Equal addresses select backward, in-place transformation.

That overlap property is not a general guarantee for wrapping address ranges, concurrent mutation, memory-mapped effects, or arbitrary aliasing with other state.

After the loop, the function returns zero. For zero length, destination selection and direction selection still occur, but the loop performs no source-byte reads or payload-byte writes.
