# F-aeb20ad41215

## Purpose

F-aeb20ad41215 expands each input byte into two lookup-table-derived bytes and submits each pair to a caller-supplied callback. Processing stops at the first callback result equal to zero.

For an ordinary, valid, nonnegative byte count, successful completion returns twice that count. A zero callback result instead produces a return value of −1. A separate integer argument gates processing: when it is zero, no input bytes are processed and no callback is invoked, but the doubled-count return calculation still occurs.

The apparent intent is a hexadecimal-style encoding operation. That interpretation is **inferred**, not established: the table contents are unavailable, and the function itself does not establish that its output consists of hexadecimal characters.

This contract distinguishes source-visible behavior from target-specific details and unresolved callback behavior. No runtime tests have been performed.

## Interface

The function accepts four arguments:

| Argument | Role |
|---|---|
| Callback | Indirect callable receiving the context value, a pointer to temporary storage, and the integer value 2. Its result is interpreted as an integer. |
| Context/gate | Integer passed unchanged to each callback. Zero also disables all iteration and callback invocation. |
| Input | Pointer to a byte sequence. The function advances its own traversal position; it does not return an updated pointer. |
| Count | Signed integer used to form the end position, initialize temporary storage, and calculate the normal return value. |

The result is an integer:

- **−1:** a callback returned exactly zero.
- **Twice the supplied count:** processing completed without a zero callback result, or processing was disabled by a zero context/gate value, subject to the arithmetic qualifications below.

### Widths and representation

The supplied representation explicitly identifies:

- Input elements and lookup-table elements as 8-bit bytes.
- A 4-byte temporary storage object.
- A 2-byte subregion of that object that is replaced before each callback.
- A callback payload length of exactly 2.

A 32-bit integer model is strongly indicated by the supplied representation, but a complete target ABI is not provided. Signed overflow, pointer arithmetic, byte order, and calling convention must therefore not be silently assigned portable semantics.

For a 32-bit signed integer model, a straightforward defined nonnegative success domain is:

- Count from 0 through 1,073,741,823.
- Valid input and pointer arithmetic for that count when processing is enabled.
- Valid callback and lookup-table access whenever an iteration occurs.

The upper bound ensures that doubling the count remains representable as a positive signed 32-bit integer.

### Callback payload layout and lifetime

The callback receives a pointer to a 4-byte temporary object, but the accompanying length is 2. Only the designated two-byte payload is intended by this call to be consumed as output.

Before iteration begins, the whole temporary object is initialized from the count. Before each callback, its low-order 16 bits are replaced by the two table-derived bytes. The remaining 16 bits are not explicitly reset on later iterations.

The same temporary storage is reused across callbacks within one invocation. Its lifetime does not extend beyond the invocation. No ownership transfer or allocation is established. A callback that needs to retain the output must copy the relevant bytes while they are valid.

## Behavior

### 1. Capture the lookup-table reference

The function first obtains a lookup-table base value from global state. This occurs even when the context/gate value is zero.

The captured base is used for subsequent table accesses. The function does not explicitly reload that global base on each iteration. Capturing the base does not snapshot the table contents: callbacks or other agents may still change bytes at that base.

No table initialization, validity check, or content check is performed here.

### 2. Apply the processing gate

If the context/gate value is zero:

- No end position is formed in the guarded processing block.
- No input bytes are read by the loop.
- No table entries are accessed by the loop.
- No callback is invoked.
- The function proceeds to its normal return calculation.

A nonzero context/gate value enables processing. Its magnitude and sign otherwise have no locally established significance; the original integer is passed to the callback.

### 3. Establish the traversal boundary

For enabled processing, the end position is formed by adding the count to the input pointer. Temporary storage is initialized with the count.

Traversal uses pointer inequality against that end position. It advances forward by one byte after each successful callback. There is no separate check that the count is nonnegative.

For a valid positive count and stable execution, this produces one callback per input byte. For zero count, the initial traversal position equals the end position, so no callback occurs.

Negative counts are not a supported reverse-traversal mode. The function still advances forward, even though the computed end position would lie before the starting position under ordinary address ordering. No reliable termination, memory-safety, or output guarantee is established for that case.

### 4. Construct each two-byte payload

For the current input position, the function selects two table entries:

- One indexed by the byte’s high nibble, in the range 0 through 15.
- One indexed by the byte’s low nibble, also in the range 0 through 15.

The selected entry for the low nibble occupies the high-order byte of the constructed 16-bit value. The selected entry for the high nibble occupies its low-order byte.

The callback receives a memory pointer, not that numeric value directly. Consequently, memory byte order matters:

- On a little-endian target, the two payload bytes are the high-nibble table entry followed by the low-nibble table entry.
- On a big-endian target, the low-order 16-bit assignment and the first two bytes at the object’s address do not have the same relationship. The supplied representation alone is insufficient to establish an equivalent two-byte payload contract.

The source-visible expression refers to the current input byte more than once. It does not establish one atomic input snapshot or an ordering between the two lookup operands. The ordinary “two nibbles of the same byte” interpretation requires the input byte to remain stable during payload construction.

Both table selections finish before the callback is invoked. The relative order of the input reads and table-entry reads within payload construction is not established.

### 5. Invoke and interpret the callback

The callback is invoked with:

1. The original context/gate integer.
2. The address of the temporary object.
3. The integer length 2.

The callback result is tested only for equality with zero:

- Zero causes an immediate return of −1.
- Any nonzero value permits traversal to continue, including a negative value.

A nonzero result does not establish that two bytes were actually consumed or written elsewhere. The function neither checks for an exact byte count nor retries partial consumption.

After a zero callback result, there is no further iteration or input-position advancement in this invocation. Earlier callback side effects are not rolled back.

### 6. Return the normal result

If no callback returns zero, the function returns the count shifted left by one bit.

For nonnegative counts whose doubled value is representable in the target signed integer type, this is twice the original count. It is not a sum of callback return values and does not reflect callback-reported byte consumption.

For negative counts or counts whose doubling exceeds the applicable signed range, the precise result is **documented_only**. The supplied representation does not justify promising signed wraparound or a portable result.

The disabled-processing path uses this same return calculation. A positive doubled return value therefore does not, by itself, prove that any callback was invoked.

## Side effects

Locally established effects are limited to:

- Reading the global lookup-table base.
- Reading input bytes and table entries when iteration occurs.
- Writing the temporary object.
- Invoking the indirect callback.

There is no explicit allocation, deallocation, input mutation, table mutation, or global-state write in the function body.

Callback effects are unrestricted by the available evidence. In particular:

- The callback may modify input that has not yet been processed.
- It may modify table contents used by later iterations.
- It may modify the global table-base value. Such a change does not replace the base already captured by this invocation.
- It may write through the temporary-storage pointer. The function replaces the low-order 16 bits before the next callback, but does not explicitly restore the other 16 bits.
- It may retain pointers, alter external state, or fail to return. None of those behaviors is constrained here.

The function performs no explicit cleanup after callback failure. It does not reclaim callback-managed resources or undo previously emitted output.

No thread-safety or reentrancy guarantee is established. Stable storage and appropriate synchronization are external requirements if concurrent access could otherwise invalidate the input, table, or callback state.
