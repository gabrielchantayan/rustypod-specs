# F-e2836660e375

## Purpose

F-e2836660e375 updates a descriptor and its referenced array of 32-bit words using a 32-bit unsigned input.

Two distinct behaviors are established:

- If dependency F-8f8b4462085f returns a nonzero result, the function replaces the descriptor’s logical contents with the input’s low 16 bits, represented as either zero words or one word.
- If that dependency returns zero, the function adds the full 32-bit input to an existing sequence of words, propagating unsigned carry and appending a remaining nonzero value when the original sequence is exhausted.

The second behavior is consistent with adding a small unsigned value to a multiprecision integer stored least-significant word first. That numerical interpretation is inferred intent, not an independently established descriptor type. The observable contract is the word-level behavior below.

The dependency is called on every invocation. Its result changes the interpretation of the input, particularly when the input is nonzero but its low 16 bits are zero.

## Behavior

### Entry and dependency call

The established order is:

1. Read the descriptor’s unsigned 16-bit count and retain that value.
2. Call F-8f8b4462085f with the descriptor pointer.
3. Choose replacement or addition according to whether its result is nonzero or zero.

The dependency can therefore observe the descriptor before this function makes any explicit write. Conversely, any dependency changes occur before this function’s subsequent descriptor and array accesses.

The retained count survives as the addition branch’s traversal bound even if the dependency changes the descriptor count. The dependency is not assumed to preserve the descriptor, its referenced allocation, unrelated globals, or ownership state.

### Replacement after a nonzero dependency result

Only the low 16 bits of the input determine the replacement.

The function first writes zero to the descriptor count. It then reads the array reference from the descriptor and writes the zero-extended low 16 bits of the input to array element zero.

If those low 16 bits are nonzero, the function finally writes one to the descriptor count. Otherwise, it leaves the count at zero.

Consequently:

- A low-half value of zero produces count zero and a physically stored zero in the first array word.
- A nonzero low-half value produces count one and that value in the first array word.
- Input bits 16–31 do not affect either result.
- The captured entry count is irrelevant to this branch.
- No other array element is directly cleared or rewritten by this branch.

The count-zero write precedes the first-word write. For a nonzero low half, the final count-one write follows the first-word write. These are distinct stores; the operation is not an atomic descriptor replacement.

Even the zero-count outcome requires writable first-word storage. Zero logical length does not suppress the first-word write.

### Addition after a zero dependency result

The full 32-bit input is used in this branch. Traversal starts at array element zero, with the input as the pending addend.

At each position, the function first determines whether it has reached the retained entry count:

- If it has reached that count, it performs the append behavior described below when the pending addend is nonzero, then returns.
- If it has not reached that count but the pending addend is zero, it returns without accessing that array word.
- Otherwise, it reads the current array word and writes back the unsigned 32-bit sum of that word and the pending addend.

The stored sum is reduced modulo \(2^{32}\). The next pending addend is exactly the unsigned carry from that addition: zero if the mathematical sum is less than \(2^{32}\), and one otherwise.

Thus the first addition can use any 32-bit addend. Every later addition uses only a carry of one; if there is no carry, traversal stops before another word is accessed.

The array-reference field is accessed for the word operations rather than captured once before traversal. The shown accesses separately obtain the word’s read and write addresses through that field. With a stable descriptor these identify the same element; no stable address is guaranteed if memory changes during execution.

### Append behavior

When traversal reaches the retained entry count with a nonzero pending addend, the function:

1. Reads the descriptor’s **current** 16-bit count.
2. Writes that count plus one back as a 16-bit value.
3. Obtains the array reference from the descriptor and writes the pending addend at the **retained entry count** index.
4. Returns.

The count used for incrementing and the count used for positioning are deliberately distinguished in this contract. The former is read at append time; the latter was captured before the dependency call.

Under a stable descriptor:

- With an entry count of zero, a nonzero input is appended intact as the first 32-bit word.
- With a nonzero entry count, an append can occur only after carry propagates through every counted word. The appended value is then one.

Count arithmetic is stored at 16-bit width. Incrementing a current count of 65,535 therefore writes zero. There is no visible rejection, saturation, or separate overflow indication.

The count increment precedes the append-word write. An interrupted or invalid append can therefore leave the count changed before the new word has been stored.

### Traversal bounds and arithmetic

The retained count is between zero and 65,535 inclusive. No addition iteration accesses an index equal to that retained count; that index is reserved for a possible append.

The index update includes a mask that clears bit 16. This does not change any index reached here: traversal can advance from 65,534 to 65,535, and the bound check then exits before another increment. It does not wrap traversal back to element zero.

The greatest append index is 65,535, whose byte displacement is 262,140. Although that displacement fits in 32 bits, the validity and representability of the resulting address still depend on the referenced allocation and target addressing rules.

## Acceptance examples

These are conditional static acceptance examples, not runtime test results. Unless stated otherwise, assume valid writable storage, no overlap or concurrent mutation, and a dependency that leaves the descriptor unchanged.

### Replacement discards the high half

Given input `0x12345678` and a nonzero dependency result:

- The count is written as zero.
- Element zero is written as `0x00005678`.
- The count is then written as one.
- Later elements are not directly modified.

### Replacement can produce logical zero from nonzero input

Given input `0x00010000` and a nonzero dependency result:

- The count becomes zero.
- Element zero is explicitly written as zero.
- There is no final count-one write.

The input’s nonzero high half does not produce a stored word.

### Zero addition makes no direct changes

Given input zero and a zero dependency result, no descriptor or array write is made by this function after the dependency returns, regardless of the captured count.

The initial count read and dependency call still occur. Any dependency effects remain observable.

### Addition stops without carry

Given a captured count of two, words `[5, 9]`, input three, and a zero dependency result:

- Element zero becomes eight.
- Element one is neither read nor written by the addition traversal.
- The count remains two.

### Carry propagates into the next word

Given count two, words `[0xFFFFFFFF, 7]`, input one, and a zero dependency result:

- Element zero becomes zero.
- Element one becomes eight.
- No append occurs, and the count remains two.

### Carry appends a new high word

Given count two, words `[0xFFFFFFFF, 0xFFFFFFFF]`, sufficient capacity, input one, and a zero dependency result:

- Elements zero and one become zero.
- The count is changed from two to three.
- Element two is then written as one.

### Empty addition preserves all 32 input bits

Given count zero, input `0x89ABCDEF`, sufficient capacity, and a zero dependency result:

- The count becomes one.
- Element zero is written as `0x89ABCDEF`.

This differs from replacement, which would store only `0x0000CDEF`.

### Dependency mutation separates the two count roles

Suppose the captured count is two, but the dependency changes the count to seven and returns zero. Suppose the referenced array then contains two leading `0xFFFFFFFF` words and has sufficient storage. For input one:

- Carry processing uses two words because the captured bound is two.
- Appending changes the current count from seven to eight.
- The appended one is written at element two, not element seven.

### Count overflow is not rejected

Given captured and current count 65,535, that many words all equal to `0xFFFFFFFF`, sufficient storage for an additional word, input one, and a zero dependency result:

- All counted words become zero.
- The count increment stores zero.
- Element 65,535 is written as one.

This is a consequence of the visible 16-bit count arithmetic, not a claim that such a descriptor is supported by the surrounding system.
