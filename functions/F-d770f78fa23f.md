# F-d770f78fa23f

## Purpose

F-d770f78fa23f processes an ordered sequence of fixed-width numeric fields from a byte buffer. Each field descriptor specifies a width, inclusive signed bounds, a following-byte requirement or terminal marker, and a destination for a 32-bit result.

The function returns the number of fields it directly committed. A field commits only after classification, accumulation, bounds checking, and any required following-byte comparison succeed. A rejected field causes an immediate return of the existing count.

The apparent intent is fixed-width decimal parsing. The established acceptance rule is not an independent ASCII-digit check: each numeric byte must index a dependency-provided classification entry whose value is exactly `0x20`. Accepted bytes contribute their unsigned byte value minus 48 to decimal-weight accumulation.

The function performs no direct rollback of earlier commits. This does not guarantee that earlier destination contents remain unchanged: later stores may overlap them, and the dependency’s effects are unknown.

This is a static behavioral contract. No runtime tests have been performed.

## Interface

### Input buffer

The first input identifies a byte buffer. No explicit buffer length is supplied, and null termination is not required by the visible processing.

For a nonnegative width, the function attempts to process exactly that many numeric bytes, stopping earlier on classification failure. A nonterminal field then examines one following byte. Successful continuation begins immediately after that byte.

A zero byte has no general end-of-input meaning:

- Within the numeric portion, it is subject to the classification rule.
- A zero following-byte encoding selects terminal behavior rather than requiring a zero byte.
- Consequently, this descriptor format cannot express “consume a zero-byte separator and continue.”

The caller must provide readable storage for every byte actually evaluated. A successful terminal field does not require a trailing byte to be read.

### Descriptor layout

Each represented descriptor consists of five consecutive 32-bit words:

| Position | Interpretation |
|---|---|
| 1 | Signed width |
| 2 | Signed inclusive lower bound |
| 3 | Signed inclusive upper bound |
| 4 | Following-byte encoding; zero marks the terminal field |
| 5 | Address of a writable 32-bit integer destination |

The represented descriptor size is 20 bytes. Addresses and the following-byte encoding occupy 32-bit words in this representation.

The visible interface explicitly supplies the input pointer and only the first three descriptor words. Processing nevertheless traverses consecutive five-word descriptors through the apparent argument-storage area. The precise calling convention needed to provide the remaining words is not established. This is not evidence of a portable variadic interface.

For each field, all five words are captured before its numeric processing begins. The descriptor cursor advances by five words before any dependency invocation for that field. The next descriptor is not fetched unless the current field commits and is nonterminal.

### Result

The result is a signed 32-bit committed-field count, initially zero.

Within the nonoverflowing domain:

- Zero means that this function completed no field destination stores.
- Each successful field adds one, including a terminal field.
- Classification, bounds, or separator rejection returns the count accumulated before that field.
- No separate status identifies the rejection reason.
- No consumed-byte count or updated input pointer is returned.

The count describes this function’s completed commits, not the final contents of destination memory after unknown dependency effects or overlapping writes.

## Behavior

### Field setup

The function captures the current descriptor’s width, bounds, following-byte encoding, and destination. Its numeric accumulator starts at zero, and its field cursor starts at the current input position.

Subsequent modification of descriptor backing storage does not, by itself, recapture the current descriptor. Future descriptors remain exposed to modification before they are fetched.

For nonnegative widths, the numeric loop attempts the specified number of bytes. Its condition tests whether the remaining width is nonzero and also decrements that signed counter, including the final condition evaluation that observes zero. A zero width therefore skips the numeric body; it does not invoke the dependency.

Negative widths are outside the predictable-use domain described here. They do not mean an empty field. Their decrement behavior and overflow risks are addressed under Uncertainties.

### Classification and evaluation order

For each attempted numeric byte:

1. F-2a4c402ba617 is called with no explicit arguments.
2. After that call returns, the function evaluates a classification expression using an indirectly obtained table base and the unsigned current input byte.
3. The selected classification byte must equal `0x20`.
4. Only after classification succeeds is the accumulation expression evaluated.
5. The field cursor then advances by one byte.

The classification expression obtains a 32-bit table-base value through the dependency’s returned address. The current input byte, interpreted as an unsigned value from 0 through 255, selects one byte at that offset from the base.

The supplied expression does **not** establish whether the indirect table-base load or the input-byte evaluation occurs first. Both contribute to classification, after the dependency call. Their relative evaluation order must remain unspecified in this contract.

The current input byte appears once in the classification expression and again in the accumulation expression. These are two source-level evaluations, not a guarantee of two distinct physical memory reads. The pointers are not volatile, and the supplied material does not establish a hardware access trace.

The established sequencing is that classification must succeed before the accumulation expression is evaluated. If classification fails:

- The function returns the existing count.
- The current field does not reach its bounds checks.
- Its following byte is not examined.
- Its destination receives no direct store from this field.
- No later numeric byte or descriptor is processed by this function.

A new dependency call occurs for every attempted numeric byte. The function does not establish one fixed classification table for an entire field or invocation.

### Accumulation and integer widths

Within a domain where the represented arithmetic yields the corresponding signed result, the numeric recurrence is:

\[
A_{\text{next}} = 10A_{\text{current}} + B - 48
\]

Here, \(B\) is the unsigned byte value used by the accumulation expression.

The exact classification rule remains independent of that formula. For example, an accepted byte need not be an ASCII digit. If its value is below 48, the mathematical contribution is negative.

The expression’s types impose an important qualification:

- The accumulator and multiplication by 10 use signed 32-bit integer arithmetic.
- The byte is explicitly converted to an unsigned integer.
- Combining that unsigned value with the signed product makes the additions use unsigned arithmetic in the represented 32-bit model.
- The result is assigned back to the signed 32-bit accumulator.

Signed multiplication overflow is not checked. Unsigned arithmetic is modular, but conversion of an unsigned result outside the signed range is not specified portably by the supplied text alone. Therefore, an unrestricted wrapping signed-decimal parser is not an established contract.

For ordinary accepted ASCII digits whose intermediate values stay within the nonnegative signed range, the recurrence has its conventional decimal interpretation.

### Inclusive bounds

After the numeric loop finishes, the function checks:

1. Whether the signed accumulator is below the lower bound.
2. If not, whether it is above the upper bound.

Either rejection returns the existing count without committing the current field. Both bounds are inclusive.

If the lower bound exceeds the upper bound, no signed accumulator value can pass both checks.

A zero-width field retains accumulator zero. It proceeds only if its bounds include zero.

### Following byte and terminal marker

Only after both bounds pass does the following-byte encoding affect acceptance.

For a nonzero encoding, the function evaluates the byte immediately after the numeric portion. That byte is zero-extended and compared against the full captured encoding in the represented 32-bit address model.

Consequences:

- Encodings from 1 through 255 can match the corresponding byte.
- A nonzero encoding outside that range cannot match any zero-extended byte.
- The encoding is compared, not dereferenced.
- A mismatch rejects the field before its destination store.
- Classification or bounds rejection prevents this following-byte evaluation.

A zero encoding marks a terminal field. In that case, the function neither reads nor compares a following input byte.

### Commit and continuation

After all applicable checks succeed, the function directly:

1. Stores the accumulator as a 32-bit integer at the captured destination.
2. Computes the next input position as one byte beyond the numeric portion.
3. Increments the committed-field count.
4. Returns if the field is terminal; otherwise, begins the next descriptor.

For a nonterminal field, the input-position update moves past the separator already examined.

For a terminal field, the same pointer update is computed without a separator read. The updated pointer is not returned or used for another field. This does not prove that a trailing byte exists; pointer-arithmetic validity remains a separate precondition.

## Side effects

### Direct destination stores

The function performs one direct 32-bit destination store for each committed field, in field order. It performs no such store for a field rejected by classification, bounds, or separator comparison.

There is no direct rollback action. If three fields commit and the fourth fails, this function does not restore the three earlier destination locations to their pre-call contents.

That statement is deliberately narrower than saying all three stored values remain unchanged. Their final contents also depend on:

- Whether destinations overlap.
- Whether earlier stores change later input or descriptors.
- Whether dependency calls modify destinations or other relevant storage.

Repeated destination addresses are not prohibited by the visible processing. A later successful store to the same address replaces the earlier stored value.

### Aliasing and changing descriptors

No operation-wide snapshot of input, descriptors, or classification data is established.

A destination store can change later input if the destination overlaps that input. It can also change a future descriptor before that descriptor is captured.

Similarly, F-2a4c402ba617 may modify future descriptors before a later field begins. Predicting later field behavior from the initially supplied descriptors therefore requires an explicit assumption that neither the dependency nor overlapping stores modify those descriptors.

The current descriptor is already captured before its numeric processing and commit. Modification of its backing words does not itself change those captured values.
