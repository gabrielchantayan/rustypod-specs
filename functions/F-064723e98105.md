# F-064723e98105

## Purpose

Its externally visible behavior depends on configuration words read during execution. The supplied evidence does not establish a fixed action sequence, output length, traversal direction, or termination guarantee.

Three byte-write sites are established:

A byte-transformation or initialization purpose is plausible, but inferred. No particular encoding, format, or application-level algorithm is established.

### Candidate and accumulator transformation

Action zero replaces the current candidate with a byte-valued arithmetic transformation of the seed, mixing state, derived state, and transform factor.

The candidate calculation has these established characteristics:

- It uses signed 16-bit interpretations of the seed, mixing state, and transform factor.
- It uses the unsigned low halfword of the derived state.
- It combines those inputs through multiplication, addition, and an inclusive bitwise combination.
- It includes an intermediate signed-halfword reduction before the final byte reduction.
- It does not use the previous candidate, saved candidate, clear offset, or secondary-store offset.

The final candidate depends only on the low byte of each contributing state value and transform-factor value. Higher bits cannot propagate downward through the represented operations. This is a property of this candidate calculation, not of the separate accumulator calculation.

One useful consequence is that the candidate’s least significant bit equals the least significant bit of the sum of the contributing mixing-state and seed values. This consequence assumes stable configuration during the calculation.

The accumulator undergoes a separate full-width arithmetic transformation using its previous value, the transform factor, and scale. It does not depend on the newly produced candidate. The result retains a 32-bit bit pattern.

The transform factor is referenced multiple times. The body does not establish a single snapshot shared by the candidate and accumulator calculations.

Action three is a distinct reset operation: candidate becomes 169 and accumulator becomes zero. It does not reset the saved candidate, offsets, seed, mixing state, or derived state.

### Paired-write action

Action one performs two byte stores in an established order. It also calculates a primary position, updates mixing and derived state, and chooses a successor.

#### First store and position calculation

The first store obtains the current secondary destination through the context’s +8 field and applies the existing secondary-store offset.

Its byte value is the low byte of the current candidate multiplied by −103. It does not use the saved candidate or accumulator.

Only after this store does the routine read the store coefficient and store correction used to calculate the primary position. That position depends on:

- The saved candidate.
- The dispatch word captured before the first store.
- The post-first-store coefficient and correction values.

The position calculation uses the saved candidate, not the current candidate. It does not use the clear offset or secondary-store offset.

A write that changes the dispatch-word storage does not alter the dispatch word already captured for this action. A write that changes the coefficient or correction storage can affect the immediately following position calculation.

#### Pre-second-store scale reads

After calculating the position, the routine computes and retains a scale-derived contribution for later mixing arithmetic. This contribution combines a signed high-bit extraction of the captured dispatch word with a scale read made before the second store.

The primary destination address uses another scale reference: the calculated position is scaled and applied to the entry-captured destination base.

These are distinct uses. The retained contribution is not recomputed after the second store, and it must not be replaced by a later scale value.

#### Second store

The second store writes the low byte of the accumulator multiplied by 87.

Its destination is the entry-captured base plus the scaled primary position. The clear offset has no role in this address.

If the first store modifies the context’s +4 field, the second store still uses the address captured at entry. If both effective destinations coincide, both stores occur, and the second byte is the final value at that address.

#### Post-store state and branch

Only after the second store does the routine read the mixing factor for the mixing-state update. The update depends on the calculated position, the captured dispatch word and values derived from it, and the retained pre-second-store scale contribution.

The derived state is subsequently replaced using the new mixing state and another mixing-factor reference. A single mixing-factor snapshot is not established for all these references.

The paired-write branch then uses:

- The calculated position.
- Captured dispatch-word information.
- The retained pre-second-store contribution.
- A later scale read.
- A later read of arithmetic factor P.

The branch tests a high-bit result. It is not an established bounds check, completion test, or comparison against a buffer length.

For a stable store-selector configuration:

- A zero branch bit selects store selector minus one.
- A one branch bit selects store selector.

The two successor alternatives are formed through separate configuration reads after the second store: the decremented alternative is read first, and the undecremented alternative afterward. If the configuration changes between these reads, they need not be adjacent values.

This action does not replace the candidate, saved candidate, accumulator, seed, clear offset, or secondary-store offset.

### Clear, offset, and seed actions

Action two writes zero to the entry-captured destination plus the clear offset. It reads the clear successor after the write. Consequently, aliasing that successor’s storage can affect the next dispatch.

The clear offset starts at zero. Action six replaces it with one; it does not increment it.

Action seven replaces the seed with zero. Action eight replaces it with the configured seed value. Both then read the seed successor. Neither action changes a destination or performs a byte store.

### Accumulator gate

Action nine evaluates a configuration-dependent arithmetic predicate of the accumulator.

The predicate uses full-width arithmetic, factors P, Q, and R, masks S and T, and fixed byte-boundary constants. Its sign result determines which of two successors is selected. The evidence does not justify interpreting it as a conventional range, overflow, or buffer-validity check.

Under sign-propagating signed-shift semantics:

- A negative predicate result chooses the incremented gate-selector alternative.
- A nonnegative result chooses the base gate-selector alternative.

After evaluating the predicate, the action:

- Replaces the secondary-store offset with the accumulator scaled by the scale value read at that point.
- Reads an incremented gate-selector alternative and then a separate base alternative.
- Copies the current candidate into the saved candidate.

With stable configuration, the alternatives are gate selector plus one and gate selector. If their reads observe different configuration values, that adjacency is not guaranteed.

The gate leaves the accumulator and current candidate unchanged. Saving the candidate does not force a later paired write to use that same candidate for its first byte: a later transformation or reset can change the current candidate independently.

## Acceptance examples

These are conditional static expectations, not runtime test results.

1. **Immediate return.** If the entry selector and dispatch bias select action four, the entry destination capture and dispatch reads occur before return. No byte store occurs.

2. **Initial clear.** If action two executes before action six, it writes zero at the captured destination with offset zero.

3. **Repeated offset setting.** Executing action six twice still leaves the clear offset at one. A following clear targets the captured base plus one.

4. **Reset followed by paired write.** If action three is followed directly by action one, the first stored byte is 1 and the second is zero. This assumes both calculated destinations are valid. The first result follows from byte reduction of the reset candidate’s store transformation.

5. **Saved and current candidates differ.** If action nine saves a candidate and action zero subsequently changes the current candidate, a following paired write derives its first byte from the changed candidate but its primary position from the saved one.

6. **Coincident destinations.** If both paired-write addresses coincide, the second byte overwrites the first. The first store can still affect intervening configuration reads if that address also aliases configuration.

7. **First-store configuration alias.** If the first store changes the store coefficient, the primary-position calculation uses the changed coefficient. If it changes dispatch-word storage instead, this action continues using the dispatch word captured before the store.

8. **Second-store scale alias.** If the second store changes scale storage, later branch arithmetic can observe the changed scale. The retained pre-second-store scale contribution remains unchanged.

9. **Captured versus refreshed destination.** Changing the context’s +4 field after entry does not redirect primary or clear stores. Changing the context reference or its +8 field can redirect a later secondary store.

10. **Default-selector cycle.** If action five repeatedly resolves back to action five under stable configuration, dispatch continues without returning or writing bytes.
