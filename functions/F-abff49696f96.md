# F-abff49696f96

## Purpose

F-abff49696f96 repeatedly obtains integer values from dependencies and conditionally applies them to a record-assembly state machine in a caller-supplied object. Direct effects include recording lengths and content, updating an eight-bit additive accumulator, selecting a destination, and conditionally marking and announcing completion.

The function returns only when the status dependency at the beginning of an iteration returns nonzero. Marker rejection, checksum rejection, and record completion do not themselves return.

**Established static behavior:** call ordering, event filtering, access widths, parser transitions, destination writes, checksum arithmetic, and completion calls.

**Inferred intent:** the state machine resembles a framed input protocol with start recognition, short or extended length, content, and an additive checksum. Value retrieval is not established to consume input, advance a cursor, or inspect a stream.

## Behavior

### Iteration and event gate

At entry, the function captures the scratch base and computes the embedded-object address. Each iteration then starts with F-24a5fb3d1fec on that embedded object.

A nonzero result returns immediately, without an explicit reset or finalization. A zero result permits the following sequence:

1. Write `0xFFFFFFFF` into the fourth-argument-associated temporary, then into the third-argument-associated temporary.
2. Call F-b9d333145f3e.
3. Call F-ca2888499290 with that result first, the address of the fourth-argument-associated temporary second, and the address of the third-argument-associated temporary third.
4. Call F-a87ac504992e with the embedded-object address. Its 32-bit result is the iteration’s primary value.
5. Perform any marker checking described below.
6. Evaluate the low eight bits of the temporary supplied as F-ca2888499290’s second argument.

Only gate bytes 3 and 4 qualify. The other temporary is not directly examined by this body.

The gate is evaluated after value retrieval and optional marker checking. A nonqualifying gate therefore does not suppress those earlier calls. It starts another iteration without comparison, dispatch, or the ordinary post-dispatch update.

Sentinel initialization does not guarantee the eventual gate byte. F-b9d333145f3e runs after initialization; F-ca2888499290, primary-value retrieval, and optional marker-check dependencies also run before evaluation. Their retention and side effects are unknown. In particular, a dependency could have retained the temporary’s address from an earlier call. F-ca2888499290 leaving its second argument’s target unchanged is therefore insufficient to establish a remaining value of `0xFFFFFFFF`.

An untouched sentinel rejects the event **only if no intervening dependency changes the gating temporary**. Likewise, a value written by F-ca2888499290 determines qualification only if its low byte remains unchanged until evaluation.

### Marker checking

A primary value equal to the full-width integer `0xAA` triggers an additional F-24a5fb3d1fec call:

- A nonzero result marks the sequence rejected, without a second value call.
- A zero result permits another F-a87ac504992e call. The sequence is rejected unless that result equals the full-width integer 1.

The second value is only a marker-check result. It does not replace the saved primary value.

After marker checking, the current gating byte is examined:

- A nonqualifying gate starts another iteration without a direct parser-state reset, even when marker checking rejected the sequence.
- A qualifying gate with marker rejection causes a direct state-byte write of 0 and starts another iteration, skipping comparison and post-dispatch update.
- A qualifying gate without rejection proceeds to comparison.

Thus, `0xAA` followed by marker result 1 can reach dispatch as the primary value `0xAA`.

### Comparison before dispatch

For every qualifying, non-rejected iteration, F-external-01 receives:

- The current 32-bit field at object offset `0x854`.
- The freshly read comparison-argument global.

Both reads follow the event, primary-value, and optional marker-check calls. Their relative argument-evaluation order is not established.

A nonzero comparison result causes a direct state-byte write of 0. A zero result causes no such write, but does not establish that the dependency preserved state. Dispatch reads the state after this call and any direct reset.

A timeout interpretation is inferred intent, not established semantics.

### State 0: start recognition

Only primary value `0x55`, compared at full width, triggers start handling:

1. Clear the accumulator byte.
2. Call F-1468513d650e with the object address.
3. Unless its result is 3, assign the destination address as the object address plus the current selection field multiplied by `0x206`, plus `0x22`.
4. Write state 1.

The selection field is read after the dependency returns. The dependency may therefore influence destination calculation.

Result 3 suppresses the direct destination assignment; it does not clear the destination. Any address left by earlier execution or dependency effects remains relevant. The accumulator is not cleared again after this dependency.

Other primary values cause no direct state-0 dispatch writes.

### State 1: length selection

In order:

1. If the destination is nonzero, write the primary value’s low 16 bits at destination offset `0x02`.
2. Store the full 32-bit primary value in the remaining-count field.
3. Add the primary value’s low byte to the current accumulator, retaining eight bits.
4. Write state 2 for a full-width zero value, otherwise state 4.

The nonzero path has no 512-value cap. For example, `0x100` selects state 4 despite having a zero low byte.

### State 2: extended-length high portion

The primary value shifted left by eight bits is stored in the 32-bit scratch location at captured-base offset `0x0C`. Next, its low byte is added to the accumulator, and state 3 is written.

No eight-bit mask precedes the shift. Negative inputs or inputs whose shift exceeds the signed range have unresolved source-language behavior. Nonnegative byte-range inputs avoid that issue.

### State 3: extended-length completion

The current 32-bit scratch value is added to the full primary value. The function then:

1. Writes the combined result’s low 16 bits at destination offset `0x02`, if the destination is nonzero.
2. Compares the combined result as unsigned against `0x200`.
3. Stores the unsigned minimum of that result and `0x200` into the remaining-count field.
4. Adds the primary value’s low byte to the accumulator.
5. Writes state 4.

The destination receives the uncapped low 16 bits; the internal count is capped at 512. The addition precedes the unsigned cap, so the cap does not resolve possible signed overflow in forming the sum.

The scratch value is read here, not retained privately from state 2. Intervening writers can change it.

### State 4: first content value

In order:

1. If the destination is nonzero, write the primary value’s low byte at offset `0x04`.
2. Decrement the 32-bit remaining count.
3. Add the primary value’s low byte to the accumulator.
4. Set the subsequent-content index to zero.
5. Write state 5.

There is no direct transition to checksum handling when this decrement produces zero.

### State 5: subsequent content

In order:

1. If the destination is nonzero, write the primary value’s low byte at destination offset `0x05 + current index`.
2. Increment the 32-bit index.
3. Compute the remaining count minus one and store it.
4. Add the primary value’s low byte to the accumulator.
5. Write state 6 only if the computed count equals zero.

When the computed count is nonzero, this dispatch does not assign the state byte. It does not write the count’s low byte as the state.

A count of zero becomes −1 under ordinary in-range signed arithmetic and does not trigger the transition. There is no less-than-or-equal termination rule.

### State 6: checksum and completion

The zero-extended accumulator byte is added to the primary value using 32-bit unsigned arithmetic. The sum’s low byte is stored into the accumulator.

If the computed low byte is zero and the destination is nonzero:

1. Write 1 at destination offset `0x00`.
2. Read the selection field and pass it to F-a62e1bd60223.
3. Store that dependency’s 32-bit result into the selection field.
4. Call F-external-03 with `0x20`.

Whether or not this conditional sequence runs, the function then clears the destination field and writes state 0.

The success decision uses the computed checksum result, not a subsequent accumulator reread. Completion marking precedes the selection-field read. Completion dependencies run before the final destination and state clears.

Checksum failure does not undo prior destination writes. This body does not clear the destination’s completion marker at start or on failure.

### Post-dispatch update and unrecognized states

Every recognized-state dispatch is followed by F-external-02; its 32-bit result is stored at object offset `0x854`. This includes state 0 when the primary value is not a start value, unsuccessful checksum handling, and state 5 without a transition.

An unrecognized state skips this call and storage and resumes iteration. A preceding nonzero comparison result can first reset an unrecognized state to 0, making that iteration a recognized-state dispatch.

Dependencies may introduce additional effects. A direct reset is not a guarantee that other fields are unchanged.

## Side effects

Established direct effects comprise dependency calls, parser-field writes, destination writes, shared-scratch accesses, fresh comparison-global reads, and conditional notification with `0x20`.

No explicit error result, rollback, capacity check, synchronization, or cancellation mechanism appears. Nonzero top-level status leaves partial assembly without direct cleanup. Execution may continue indefinitely if that status remains zero.

Calling the value dependency establishes an invocation and a returned integer, not stream consumption. The optional second value call has the same limitation.

The scratch location can be shared across invocations. Reentrancy and thread safety are not established. Writable temporary addresses are exposed to a dependency; retention and later modification are unknown. These unknowns affect the event gate as well as memory-safety assumptions.

## Acceptance examples

These are conditional static predictions, not executed tests. Unless otherwise stated, assume valid nonaliasing storage, qualifying gate bytes at evaluation, zero comparison results, arithmetic within defined ranges, and no dependency modifications to the illustrated fields or scratch.

1. **Immediate return.** A nonzero first top-level status result returns without event, value, comparison, or post-dispatch calls.

2. **Positional gate, with preservation condition.** If F-ca2888499290 writes 3 through its second argument and 2 through its third, the event qualifies **provided the gating low byte remains 3 until evaluation**. Reversing the writes rejects the event provided the gating byte remains 2. Subsequent dependencies can otherwise change the outcome.

3. **Sentinel retention is conditional.** If no dependency changes the gating temporary after initialization, its low byte remains `0xFF` and the event does not qualify. Merely knowing that F-ca2888499290 did not write that target is insufficient: another intervening dependency could modify it through a retained address.

4. **Nonqualifying gate still permits calls.** With gate byte 2 at evaluation, primary-value retrieval has already occurred. A primary result of `0xAA` also causes marker checking before rejection by the gate. No consumption conclusion follows.

5. **Marker rejection.** With a qualifying gate, primary `0xAA`, zero additional status, and marker result 2, the state is directly reset to 0 without dispatch or post-dispatch update. Marker result 1 instead allows primary `0xAA` to proceed.

6. **Global lifetimes.** A dependency changing the comparison-argument global before comparison changes the value supplied to F-external-01. Changing the scratch-base global does not redirect this invocation’s scratch accesses; changing the captured location’s contents can affect extended length.

7. **Ordinary completion.** Starting in state 0, values `0x55`, 3, `0x10`, `0x20`, `0x30`, `0x9D` complete a record if start handling establishes a valid destination. Length 3 and three content bytes are stored. Their sum with the checksum is `0x100`, so completion marking, selection advancement, and notification occur.

8. **Extended-length cap.** Values 3 and 0 in states 2 and 3 produce length `0x0300` if scratch remains unchanged. The destination receives `0x0300`; the internal count becomes `0x0200`.

9. **Length-one boundary.** Length 1 followed by one content value leaves state 5 with count zero. The next primary value is treated as subsequent content and produces count −1, not immediate checksum handling. An extended count of zero similarly enters state 4 without a zero-content shortcut.

10. **Null destination or checksum failure.** A zero checksum low byte with a null destination skips completion marking and both success dependencies. A nonzero checksum low byte skips them regardless of destination. Both paths clear destination and state; neither rolls back earlier destination writes.

11. **Unrecognized state.** With state 7 and a zero comparison result that preserves state, dispatch skips the post-dispatch update. A nonzero comparison result instead resets state to 0, after which normal state-0 handling and the update occur.
