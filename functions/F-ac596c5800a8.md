# F-ac596c5800a8

## Purpose

F-ac596c5800a8 routes an event-like record through a receiver’s indirect dispatch entries. It recognizes two conditions that select distinct primary handlers. A primary handler suppresses fallback only when its return value is nonzero. Unrecognized records, and recognized records whose primary handler returns zero, enter a common fallback path.

The fallback path invokes a receiver-associated provider. If that provider returns a non-null object pointer, the function forwards the original record pointer to an indirect handler on that object.

The routing behavior is established by the supplied static representation. Descriptions such as “event,” “receiver,” “provider,” and “handled” are inferred role names, not established application semantics.

## Interface

### Inputs

The function has three incoming arguments:

1. **Receiver pointer.** Points to an object whose first 32-bit word is interpreted as a dispatch-table pointer.
2. **Record address.** Identifies memory containing the routing fields described below. Although represented as an integer in the supplied material, this argument is used as an address.
3. **Additional pointer-valued argument.** Its incoming value does not affect any established branch, indirect call target, or argument passed onward.

The third argument’s lack of effect follows from the control flow: when the pointer comparison relevant to routing is reached, the comparison uses a separately loaded global value rather than the incoming third argument. On other paths, that comparison is not evaluated.

### Output

There is no explicit return value or status result.

The primary handler’s result is used only as a zero-versus-nonzero decision. The fallback provider’s result is interpreted as either null or an object pointer. The forwarding handler’s result, if any, is ignored.

## Behavior

### Initial routing decision

The function first reads the 32-bit discriminator at record offset 4. That captured value controls the routing decision; the visible body does not reread it.

#### First primary condition: discriminator `0x21`

For discriminator `0x21`, the function:

1. Reads the pointer-sized value at record offset 8.
2. Reads the global comparison token.
3. Compares those two values.

If they differ, the first primary condition fails. In that case, the record word at offset 12 and the global high-half selector are not read by this condition.

If they match, the function next reads the 32-bit word at record offset 12, then reads the global high-half selector. It interprets the record word as an unsigned 32-bit bit pattern for splitting into halves:

- The upper half is the word shifted right by 16 bits.
- The lower half is the word masked to its least significant 16 bits.

The first primary condition succeeds only when both of the following hold:

- The upper half equals the global high-half selector.
- The lower half is zero.

The selector itself is not visibly reduced to 16 bits. Consequently, if its stored comparison value exceeds `0xFFFF`, no upper half of a 32-bit record word can equal it.

When this condition succeeds, the function selects the receiver’s dispatch entry at offset `0xDC`.

#### Second primary condition: discriminator `0x13`

If the first primary condition does not succeed, the function checks whether the captured discriminator is `0x13`.

Only for `0x13`, it reads the 32-bit word at record offset 12 and subtracts `0x8200`. The second primary condition succeeds when that result equals `0x25`. In the represented 32-bit arithmetic, the matching record word is therefore `0x8225`.

When this condition succeeds, the function selects the receiver’s dispatch entry at offset `0xE0`.

This path does not read the record field at offset 8 or either global comparison location.

#### Other cases

The function proceeds directly to fallback when:

- The discriminator is neither `0x21` nor `0x13`.
- The discriminator is `0x21`, but its pointer comparison fails.
- The discriminator is `0x21`, its pointer comparison succeeds, but either half-word condition fails.
- The discriminator is `0x13`, but the numeric selector condition fails.

The two primary conditions cannot both select a handler in one invocation because they require different discriminator values.

### Primary invocation

After selecting either primary entry, the function obtains its target through the receiver’s current dispatch-table pointer and invokes it with two explicit arguments, in order:

1. The original receiver pointer.
2. The original record address.

The visible primary result is a 32-bit integer:

- **Nonzero:** return immediately; do not enter fallback.
- **Zero:** enter fallback.

Negative results count as nonzero. No individual nonzero value receives special treatment.

The function does not copy the record or restore any memory a primary handler changes. Thus, after a zero result, fallback receives the same record address but may observe contents changed by the primary handler.

### Fallback invocation

Fallback is identical whether reached directly or after a primary handler returns zero.

The function reads the original receiver’s dispatch-table pointer and obtains the entry at offset `0xCC`. It invokes that entry with **no explicit arguments in the supplied representation**.

This absence of explicit arguments is significant: the representation does not establish that the provider receives the receiver as an ordinary argument. Conversely, it does not prove that every machine-level argument register is empty or irrelevant.

The provider result is treated as a pointer:

- **Null:** return without forwarding.
- **Non-null:** read the returned object’s dispatch-table pointer, obtain its entry at offset `0x30`, and invoke that entry with:
  1. The returned object pointer.
  2. The original record address.

After the forwarding call returns normally, F-ac596c5800a8 returns. It neither inspects a forwarding result nor performs another routing attempt.

### Access ordering and limits

The visible control flow establishes these ordering constraints:

- The discriminator read precedes all routing-specific reads.
- On the `0x21` path, the offset-8 read precedes the comparison-token read.
- The offset-12 word and high-half selector are read only after the pointer comparison succeeds, with the record word read first.
- A primary dispatch target is obtained only after its condition succeeds.
- Fallback dispatch lookup occurs only after fallback is selected, including after a primary returns zero.
- The returned object’s dispatch lookup occurs only after the provider returns non-null.

After a primary call, fallback performs a new receiver dispatch lookup. It does not reuse the primary dispatch-table pointer. A primary handler that changes the receiver’s table can therefore affect which fallback provider is invoked.

These are static sequencing facts. No atomicity, synchronization, hardware memory-ordering guarantee, or concurrency-safe snapshot is established.

## Side effects

The visible body performs no direct writes to record memory, receiver memory, global storage, or dispatch tables. It performs no visible allocation, deallocation, reference-count adjustment, or ownership transfer.

Observable effects can nevertheless arise through its indirect calls:

- A selected primary handler may run once.
- The fallback provider may run once.
- The forwarding handler may run once, and only after a non-null provider result.

Each invocation makes at most three such calls: a primary handler returning zero, the fallback provider returning non-null, and the forwarding handler.

No dependency is assumed to preserve globals, receiver state, record contents, dispatch tables, or memory lifetimes. The visible function does not compensate for dependency-side changes.

Passing the original pointers establishes aliasing, not ownership. The available material does not establish whether any dependency borrows, retains, releases, or consumes an object or record.

There is no visible error reporting, retry, cleanup, or recovery path. Null is explicitly checked only for the fallback provider’s result. Invalid receiver pointers, record addresses, dispatch tables, or call targets are not converted into a defined status by this function. If a dependency does not return normally, no subsequent action in this function is established.
