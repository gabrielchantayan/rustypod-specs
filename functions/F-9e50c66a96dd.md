## Behavior

For a valid invocation, the function obtains an address-bearing word from the beginning of the supplied object. That address determines the base used to locate the dispatch entry 256 bytes later.

The contents of that entry select the operation to invoke. The selected operation receives these arguments in order:

1. The original object pointer.
2. The word obtained from object element index 12.
3. The original four-byte second input.

The object pointer is not visibly replaced by an interior pointer, copied object, or adjusted receiver. The additional object word is forwarded as a value, rather than as the address of its storage location.

The visible operation is unconditional. There is no branch selecting a fallback, skipping a null entry, or substituting a default additional argument.

### Observable ordering

The dispatch-base read must supply the address used for the dispatch-entry lookup. Thus that dependency establishes an order: the table entry cannot be resolved from that base until the base value has been obtained.

The additional argument is obtained from the object before control enters the selected operation. Its value is the loaded word supplied for that invocation; the contract does not describe passing a live reference to the object field.

The available representation does **not** establish the relative order of the additional-argument read and all dispatch-resolution reads. In particular, it must not be treated as proof that the field at offset 48 is read either before or after the dispatch entry.

No object-memory write is visible before control transfer. No wrapper-level read, write, cleanup action, or additional dispatch is visible after the selected operation completes.

These ordering limits matter for memory-mapped storage, concurrent mutation, aliasing, and fault analysis. A stronger sequence of physical memory accesses is not established.
