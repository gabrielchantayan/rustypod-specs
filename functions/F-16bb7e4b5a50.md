# F-16bb7e4b5a50

## Purpose

F-16bb7e4b5a50 transforms two four-byte input records into a four-byte destination record. The fourth byte of the second argument selects between:

- A direct, ordered copy from the third argument when that byte is zero.
- A dependency-assisted integer combination of the two inputs when that byte is nonzero.

The arithmetic is consistent with combining three color-like channels and an opacity-like channel. That interpretation is **inferred intent**, not an established format requirement. The supplied evidence does not establish a color space, channel naming convention, premultiplication convention, or standardized compositing rule.

The observable contract includes exact byte accesses, dependency-call placement, integer truncation, and behavior under overlapping buffers. It must not be replaced with an idealized floating-point blend.

## Interface

The function accepts three pointer arguments, in this order:

| Argument | Contract role |
|---|---|
| Destination | Address at which four result bytes are written. |
| Input A | Address of a four-byte input record. Its byte at offset 3 controls the branch. |
| Input B | Address of a four-byte input record. It supplies the copied record or contributes to the combined result. |

Each record has byte offsets 0, 1, 2, and 3. Bytes are unsigned eight-bit quantities, with values from 0 through 255. Offsets 0–2 are treated symmetrically by the arithmetic. Offset 3 has a distinct control and result role.

The function has no returned value. Its directly observable result is the destination contents and any effects of the dependency it calls.

### Preconditions

For ordinary completion:

- Input A must permit a read at offset 3.
- Input B must permit the reads selected by the branch.
- The destination must permit four individual byte writes.
- On the nonzero branch, Input A must also permit reads at offsets 0–2.
- The dependency must return normally if completion of the enclosing function is required.

No null-pointer check, length check, alignment check, or access-failure recovery is present in the supplied representation. These are byte accesses; no wider alignment requirement is visible.

The zero branch does not read Input A offsets 0–2. Consequently, a contract requiring those three bytes to be readable even on that branch would be stronger than the observed behavior.

No non-overlap requirement is shown. Overlap is meaningful because accesses occur in a specific order.

### Integer interpretation

The arithmetic below describes the supplied representation using eight-bit bytes and 32-bit signed and unsigned integer intermediates. These widths have not been independently verified against an executable.

Unsigned 32-bit arithmetic wraps modulo \(2^{32}\). Conversion to an output byte retains the low eight bits. The combined-channel computation ultimately selects bits 10–17 of a 32-bit product; it does not clamp the numerical result into the byte range.

## Behavior

### Initial observations

The function first reads:

1. Input A offset 3, retaining its unsigned value as \(s\).
2. Input B offset 0, retaining that byte.

These reads precede branch selection and any dependency call. In particular, Input B offset 0 is read even when \(s=0\).

### Zero-control branch

When \(s=0\), the function performs an ordered four-byte copy from Input B:

1. Write the previously retained Input B byte 0 to destination offset 0.
2. Read Input B offset 1 and write it to destination offset 1.
3. Read Input B offset 2 and write it to destination offset 2.
4. Read Input B offset 3 and write it to destination offset 3.

The dependency is not called.

For disjoint buffers, the destination becomes an exact copy of Input B. With overlap, this is a forward sequence of individual reads and writes, not a snapshot copy and not an overlap-safe bulk move. An earlier destination write can change a later source byte before that byte is read.

Input A offsets 0–2 are not consulted on this branch.

### Nonzero-control branch

When \(s\) is between 1 and 255 inclusive, the function reads Input B offset 3 before calling the dependency. Define:

\[
a = \text{Input B byte 3} + 1.
\]

Thus \(a\) ranges from 1 through 256; it is not an eight-bit quantity.

It then computes the integer:

\[
d =
a +
\left\lfloor
\frac{(s+1)(255-a)}{256}
\right\rfloor.
\]

The floor in this expression reflects the signed right shift in the supplied representation. In particular, when \(a=256\), the shifted quantity is negative. Its result is \(-1\), not zero, for every permitted nonzero \(s\).

For the nonzero branch:

\[
2 \le d \le 255.
\]

Some useful boundary results are:

- If Input B byte 3 is 255, then \(a=256\) and \(d=255\).
- If Input B byte 3 is 254, then \(a=255\) and \(d=255\).
- If \(s=255\), then \(d=255\), regardless of Input B byte 3.

The function calls **F-870c4fcf7295** with the ordered arguments:

1. The integer 1024.
2. The computed integer \(d\).

Let \(m\) denote the 32-bit result returned by that dependency. Its mathematical meaning is not established by the supplied evidence.

After the dependency returns, the function reads, in order:

1. Input B offset 1.
2. Input B offset 2.
3. Input A offset 0.
4. Input A offset 1.
5. Input A offset 2.

The three Input A channel values are used to compute retained per-channel intermediates. All these reads and intermediate calculations occur before the first destination write.

This placement is significant: Input B byte 0, Input B byte 3, and Input A byte 3 were retained before the call. Input B bytes 1–2 and Input A bytes 0–2 are obtained after the call. The contract cannot assume that the dependency leaves their backing storage unchanged.

### Combined-channel arithmetic

For each channel offset \(j\) from 0 through 2, let:

- \(f_j\) be the Input A channel byte read after the dependency call.
- \(b_j\) be the retained Input B channel byte. For channel 0 this is the pre-call value; for channels 1 and 2 it is the post-call value.

Define:

\[
p_j = s f_j + 1,
\]

\[
q_j = \left\lfloor \frac{p_j}{256} \right\rfloor,
\]

\[
t_j = a(b_j-q_j)+p_j.
\]

Here:

- \(p_j\) is between 1 and 65026.
- \(q_j\) is between 0 and 254.
- \(b_j-q_j\) can be negative as a mathematical integer.

The supplied expression performs the subtraction and subsequent channel arithmetic using unsigned 32-bit conversions. Nevertheless, the completed \(t_j\) expression has the same result as the mathematical expression above: it is nonnegative and fits within 16 bits. One way to see this is to write \(p_j=256q_j+r_j\), where \(0\le r_j\le255\), giving:

\[
t_j = a b_j + (256-a)q_j + r_j.
\]

The destination channel is determined by:

\[
w_j = \bigl((m \bmod 2^{32})t_j\bigr)\bmod 2^{32},
\]

\[
\text{destination byte }j
=
\left\lfloor\frac{w_j}{1024}\right\rfloor\bmod256.
\]

This describes the low-byte result of the supplied signed conversion and right shift without treating a possibly negative signed product as a mathematical division.

Consequences:

- The multiplication by the dependency result can wrap at 32 bits.
- There is no saturation to 0 or 255.
- There is no rounding adjustment at the final shift.
- An unexpected dependency result is not validated or rejected.

### Final writes

After the nonzero branch has collected its channel inputs and computed their intermediates, it writes:

1. Combined channel 0 to destination offset 0.
2. Combined channel 1 to destination offset 1.
3. Combined channel 2 to destination offset 2.
4. \(d\), converted to a byte, to destination offset 3.

Since \(d\) is already between 2 and 255, that last conversion loses no information.

Unlike the zero branch, these final writes cannot change an input channel that the function itself still needs to read: all such reads have already occurred. This does not constrain earlier effects of the dependency.

## Side effects

The function itself visibly writes four destination bytes on either normally completing branch. It makes no explicit allocation, deallocation, ownership transfer, or global-variable access in the supplied representation.

Those observations do **not** establish that:

- The dependency allocates or frees nothing.
- Globals remain unchanged.
- Input backing storage remains unchanged across the dependency call.
- A pointer retained by another component remains valid.
- Writes are atomic as a four-byte record.

The destination is updated one byte at a time. If an access fails partway through, earlier writes may already have occurred; no rollback mechanism is shown.

On the nonzero branch, the dependency runs before any destination write made directly by this function. The dependency could have its own effects on the destination through independently accessible state. Such effects are outside the supplied body’s direct-write sequence.

No input storage is explicitly released by this function. No permission to release or retain memory can be inferred for the dependency.

These examples are conditional static expectations, not runtime test results. Byte lists are ordered by offsets 0–3.

- Destination and inputs are disjoint and accessible.

\[

Expected final region:

\]

Each write changes the next source byte before it is read. An implementation producing a snapshot copy instead would not match this access-order behavior.

\[
a=1,\qquad d=1+\lfloor508/256\rfloor=2.
\]

The dependency receives \((1024,2)\). If it returns normally, destination byte 3 becomes 2, independent of its returned multiplier.

### Maximum Input B fourth byte

Given Input B byte 3 equal to 255 and any nonzero Input A byte 3, \(a=256\). The signed shifted adjustment is \(-1\), yielding \(d=255\).

A result of zero caused by first truncating \(a\) to a byte would violate the contract.

### Dependency timing

If the dependency changes Input B byte 0 and Input B byte 1, the channel-0 computation still uses the byte-0 value retained before the call. The channel-1 computation uses the byte-1 value read after the call.

Similarly, changing Input A byte 3 during the call does not change the retained control value \(s\), while changing Input A byte 0 can affect the later channel-0 computation.
