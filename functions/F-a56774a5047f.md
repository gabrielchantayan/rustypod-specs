# F-a56774a5047f

## Purpose

F-a56774a5047f coordinates a write transaction using a caller-supplied object, a 16-byte task-file image, shared transfer-control fields, command submission, completion waiting, and final status translation.

**Established static behavior:** it validates the object and a nonzero count, conditionally waits for pending recovery, prepares and transfers the task-file image, configures shared control storage, submits a command, and interprets completion and transfer status. Its returns distinguish validation failures, a generic transaction failure, and a result supplied by a status translator.

**Inferred intent:** diagnostic wording and the task-file command byte suggest a write-multiple operation with a recovery command. This does not establish the underlying transport, all hardware field meanings, transfer units, or storage durability.

This contract describes static evidence only. No runtime tests have been performed.

## Behavior

### Entry and validation

The captured context is obtained and the local 16-byte image is initialized to zero before validation. Capturing the pointer does not itself read the pointed-to context.

Validation has the following precedence:

1. A null object returns 7 without an object dereference.
2. Otherwise, the 32-bit word at object offset 0 is compared with the shared expected marker. A mismatch returns 7.
3. Only after a matching marker is the 32-bit word at object offset 68 read. Zero returns 7.
4. Only after all object checks pass is the count tested. Zero returns 9.

An invalid object therefore takes precedence over a zero count. These early returns invoke no dependency and perform no explicit store through the context or control-block pointers. They do not perform the second shared-context global read used for the recovery predicate.

No additional local validation checks address range, count range, transfer-value alignment, buffer extent, storage capacity, or consistency between truncated and full count representations.

### Pending recovery

After successful validation, the function rereads the shared-context pointer global and tests the byte at offset 0 of the resulting predicate context.

If that byte is zero, no recovery-wait call occurs. In particular, this branch does not test or clear the captured context’s flag.

If the byte is nonzero, F-9f56f351b49c is called without explicit arguments:

- A zero result selects a recovery-wait failure diagnostic through F-1b7fa166ef25, then return 91.
- A nonzero result causes a zero byte to be written at offset 0 of the captured context, then processing continues.

On the failure path, this function performs no explicit flag clear. The wait and diagnostic dependencies may have effects not visible in this body.

Even if the shared-context global changes during a dependency call, subsequent explicit context accesses still use the captured pointer value. That does not guarantee that the captured context’s contents remain unchanged.

2. Calls F-7b64e40fc88e without explicit arguments.

### Submission failure

- If status bit 4 is clear, no recovery-command call is made.

- The primary submission-failure diagnostic is emitted, then the function returns 91.

### Completion waiting

A nonzero submission result causes another control-block-pointer read through the captured context and a write of 16 to control-block offset 4.

F-3b92aaed087c is then called with the object and scalar 2.

Only result 31 selects the designated timeout branch:

2. If it returns zero, a recovery-failure diagnostic is emitted, followed by a byte write of 1 to captured-context offset 0.
3. A timeout diagnostic is emitted.
4. The control-block pointer is reread through the captured context, and 1 is written to its offset 56.
5. The function returns 91.

Every completion-wait result other than 31 proceeds to final status processing, including zero and other nonzero results.

- A zero status result selects a data-transfer failure diagnostic and return 91.
- A nonzero status result is passed unchanged to F-08590c35a166.
- A zero translation result returns 0 without an error diagnostic.
- A nonzero translation result selects a transfer-status diagnostic and is returned unchanged.

## Side effects

Explicit shared stores are relative to the captured context or a control-block pointer read from it. There are no explicit stores addressed through the object argument itself. **This does not establish object immutability:** the object may overlap context or control storage. For example, if a retrieved control-block pointer equals the object pointer, the control-field stores also modify object storage.

Such overlap is not detected or rejected. Dependencies receiving the object may additionally modify it. More generally, aliasing can affect later reads of shared fields; the source does not establish independent allocations.

Control-block pointers are reread at several stages, so the explicit stores need not target one unchanged allocation. The writes at offsets 68 and 76 are the exception: they use one retrieved pointer with no intervening dependency call.

Important ordering constraints include:

- The write of 3 precedes object preparation and image transfer.
- The write of 512 precedes F-7b64e40fc88e.
- Transfer-value and count writes follow that call, in that order.
- The write of 16 occurs only after successful submission.
- On the ordinary completion path, the offset-56 write precedes final status retrieval.
- On timeout, timeout logging precedes the offset-56 write.
- Recovery-failure logging precedes the pending-flag write, which precedes the primary submission or timeout diagnostic.

Diagnostics are calls, not assumed inert events. Their implementations may affect shared state.

The image has local lifetime, and its address is passed to F-09f149a3091f. No explicit allocation, ownership transfer, release, rollback, locking, or restoration occurs in this body. Safe retention of the image address beyond the call requires a dependency guarantee not supplied here.

## Acceptance examples

These are conditional criteria, not executed tests. They assume required memory accesses are valid and dependencies return normally.

1. **Validation precedence:** A null object and zero count return 7. No dependency or recovery-predicate read occurs.

2. **Count validation:** A matching marker and nonzero object word at offset 68, together with zero count, return 9 before the second shared-context global read.

3. **Separate context observations:** If the entry capture yields context \(C\), while the later global read yields distinct context \(P\), the recovery predicate reads \(P\)’s flag. If it is nonzero and recovery waiting succeeds, the explicit clear targets \(C\)’s flag. This criterion specifies pointer use without asserting how differing observations arise.

4. **Zero predicate flag:** Under the same distinct-context condition, a zero flag in \(P\) skips recovery waiting and performs no explicit flag clear, even if \(C\)’s flag is nonzero.

5. **Image encoding:** Address `0x12345678` and count `0x00009abc` produce words `0x129a0000`, `0x00000000`, `0x78bc0000`, and `0x35403456`. Under little-endian storage, the bytes are `00 00 9a 12 00 00 00 00 00 00 bc 78 56 34 40 35`.

6. **Count boundary:** Count `0x00010000` passes validation, produces zero image count bytes, supplies submission argument `0x80000000`, and is written in full as `0x00010000` at control-block offset 76. Device acceptance remains unknown.

7. **Transfer masking:** Transfer value `0x80000001` produces value 1 at control-block offset 68.

8. **Aliased object storage:** If a control-block pointer retrieved for an explicit store equals the object pointer, that store modifies object-relative storage. No object-immutability guarantee applies.

9. **Submission recovery failure:** Zero submission result, set status bit 4, and zero recovery result produce recovery-failure logging, a captured-context flag write of 1, then primary submission-failure logging. Return is 91.

10. **Timeout:** Completion result 31 always invokes recovery. Timeout logging precedes the offset-56 write of 1, and return is 91.

11. **Other completion results:** Any result other than 31 continues to final status retrieval; it does not independently establish success.

12. **Translated error:** Nonzero final status translated to 42 produces a transfer-status diagnostic and returns 42 unchanged.
