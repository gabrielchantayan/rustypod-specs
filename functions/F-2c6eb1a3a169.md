# F-2c6eb1a3a169

## Purpose

F-2c6eb1a3a169 selects one 20-byte record from a caller-supplied pool state and partially initializes that record. It prefers a record from a linked list of available records. If that list is empty, it consumes the next record in the current contiguous storage region, allocating and linking a new region when the current region is exhausted.

The function has no explicit return value. Selection is observable through changes to the pool state and writes to the selected record; the selected address is not explicitly returned or stored in a dedicated output field.

**Inferred intent:** this is a pool-acquisition or record-reservation operation. The available-record list likely supports reuse, and the descriptor chain likely tracks allocated regions. These interpretations do not establish any release protocol, eventual owner, or behavior of other operations.

## Interface

### Input

The sole argument is an address of mutable pool state. The visible representation consists of four consecutive 32-bit fields:

| Byte offset | Role in this operation |
|---|---|
| +0 | Address of the current region descriptor, or zero |
| +4 | Head address of the available-record list, or zero |
| +8 | Address of the next unused record in the current region |
| +12 | End address used to detect exhaustion of the current region |

The supplied representation uses 32-bit integers for addresses and state fields. This contract describes that representation; it does not establish portability to a different pointer width.

A region descriptor occupies 12 bytes:

| Byte offset | Content written or read |
|---|---|
| +0 | Link to the previous current descriptor |
| +4 | Unsigned 32-bit region capacity, measured in records |
| +8 | Address of the region’s record storage |

Records have a 20-byte stride. This operation accesses the following portions of a selected record:

| Byte offset | Access |
|---|---|
| +0 | Writes one zero byte |
| +1 through +3 | No direct access |
| +4 through +7 | Writes a zero 32-bit word |
| +8 through +11 | Writes a zero 32-bit word |
| +12 through +15 | Reads a next-list address on the reuse path, then writes a zero 32-bit word |
| +16 through +19 | No direct access |

### Output

There is no explicit return value and no explicit success or failure status.

Normal completion means that the applicable pool-state updates and all four initialization writes have occurred. It does not mean that all 20 bytes of the selected record have been cleared.

### Preconditions

For a safe normal execution:

- The pool-state address must designate readable and writable storage for the four fields.
- A nonzero available-list head must designate a record whose link at offset +12 is readable and whose initialization fields are writable.
- When the available list is empty and the next-unused address differs from the end address, the next-unused address must designate a writable record.
- If growth is needed and the descriptor address is nonzero, its capacity field at offset +4 must be readable.
- Both dependency calls on the growth path must provide storage suitable for the accesses that follow.
- Capacity, byte-count, and address calculations must be compatible with the actual allocated storage.

The function does not validate these conditions. It also does not establish synchronization against concurrent changes to the pool or record storage.

## Behavior

### 1. Choose between reuse and contiguous storage

The function first reads the available-list head from pool-state offset +4.

If that address is nonzero, it selects that record. It reads the 32-bit link at record offset +12 and writes that value into the pool’s available-list head. This removes the selected record from the list before clearing the record’s link field.

On this path, the function does not directly inspect or change the descriptor head, next-unused address, or end address. It makes no dependency calls.

If the available-list head is zero, the function reads the next-unused address and compares it with the end address:

- If they differ, the next-unused address is selected without allocating a region.
- If they are equal, the function takes the growth path.

Exhaustion is tested by equality only. There is no ordering check, range check, or check that the next-unused address lies within the current region. A malformed state in which the next-unused address is beyond the end still follows the non-growth path if the addresses differ.

### 2. Determine capacity when growth is required

If the current descriptor address is zero, the new capacity is 32 records.

Otherwise, the function reads the current descriptor’s unsigned 32-bit capacity, denoted here by \(n\), and computes two candidates:

\[
a = n + 32
\]

\[
b = n + (n \mathbin{\mathrm{>>}} 1) + (n \mathbin{\mathrm{>>}} 3)
\]

The right shifts are unsigned. In a non-overflowing calculation, the second expression is:

\[
n + \lfloor n/2 \rfloor + \lfloor n/8 \rfloor
\]

The new capacity is \(b\) when \(a \leq b\), and \(a\) otherwise. Equality therefore selects the second candidate, although the resulting numeric value is the same.

The additions and comparison use unsigned 32-bit values. Consequently, the growth rule is a comparison of the computed 32-bit results, not an unbounded-integer maximum. Overflow can make the chosen capacity smaller than the old capacity. There is no explicit rejection of zero or wrapped capacities.

The record-storage request size is the chosen capacity multiplied by 20, again in a 32-bit unsigned expression. That multiplication can wrap independently of the capacity calculation. No overflow check is visible.

### 3. Request and publish a new region

The growth path calls F-871e64ddc6de twice, in this order:

1. With first argument 12 and second argument zero.
2. With first argument equal to the computed record-storage byte count and second argument zero.

The first result is used as a descriptor address. The second result is used as the record-storage address.

After both calls return, the function performs these state changes in order:

1. Writes the second result to the new descriptor’s storage-address field at +8.
2. Reads the pool’s then-current descriptor head and writes it to the new descriptor’s previous-link field at +0.
3. Writes the computed capacity to the new descriptor at +4.
4. Writes the new descriptor address to pool-state offset +0.
5. Reads the new descriptor’s storage-address field and uses that address as the selected record.
6. Writes the computed end address—selected address plus capacity multiplied by 20—to pool-state offset +12.

The previous-descriptor link is taken from the pool state **after both dependency calls**, not necessarily from the value observed before them. No guarantee is available that those calls preserve the pool or other shared state.

The descriptor is published in the pool before the end address, next-unused address, and selected record initialization are completed. The visible operation is therefore not an atomic publication of a fully updated pool.

The function does not test either dependency result before using it. It does not release the first allocation if the second call fails or does not return normally.

### 4. Advance contiguous consumption

Whenever selection came from contiguous storage, with or without growth, the function writes:

\[
\text{next-unused address} = \text{selected address} + 20
\]

to pool-state offset +8.

This occurs before the selected record is initialized.

The reuse path does not perform this update.

### 5. Partially initialize the selected record

All selection paths finish with these writes, in this order:

1. Zero a 32-bit word at record offset +4.
2. Zero a 32-bit word at record offset +8.
3. Zero a 32-bit word at record offset +12.
4. Zero one byte at record offset +0.

There is no full-record clearing operation. Bytes +1 through +3 and +16 through +19 are not directly written by this function.

On the reuse path, the old link at +12 has already been read and installed as the pool’s new available-list head before that field is cleared.

## Side effects

### Pool-state mutation

The fields directly changed depend on the selected path:

| Path | Direct pool-state writes |
|---|---|
| Reuse an available record | Available-list head |
| Consume existing contiguous storage | Next-unused address |
| Grow and consume new storage | Descriptor head, end address, next-unused address |

Every path also performs the four selected-record initialization writes.

### Allocation and lifetime

Only the growth path invokes F-871e64ddc6de. The function retains the two returned addresses in the descriptor structure and pool state. It does not directly release an existing descriptor, an existing storage region, or a selected record.

This establishes retention and linking behavior, not ownership policy. Whether the dependency allocates memory, transfers ownership, uses an arena, or has some other storage contract is unknown.

The available-record link is overwritten during initialization. After normal completion, the selected record no longer contains its former next-list address at offset +12.

### Errors and partial state

There is no explicit error branch, rollback, or error reporting.

If an invalid address, failed allocation, or other abnormal condition prevents completion, the visible logic does not provide a recovery guarantee. Depending on where execution stops, possible partial effects include:

- The available-list head has advanced, but record initialization is incomplete.
- Storage has been requested without the new descriptor being published.
- The descriptor head has changed while other pool fields remain stale.
- The next-unused address has advanced before record initialization completes.

The precise fault, exception, termination, or nonlocal-control behavior is not established.

The stated write order describes the visible operation under ordinary, non-overlapping storage assumptions. Unusual aliases between the pool state, descriptors, and selected record can make record writes also modify control fields. Such aliases are neither detected nor assigned a safe contract.

## Acceptance examples

These examples are conditional on valid, appropriately aligned, non-overlapping storage, ordinary dependency behavior as explicitly stated, and successful completion. They are specification examples, not executed tests.

### Reuse takes precedence over region exhaustion

Given a nonzero available-list head pointing to record A, with A’s link pointing to record B:

- A is selected even if the contiguous region is exhausted.
- The pool’s available-list head becomes B.
- No dependency call occurs.
- The descriptor head and contiguous cursor fields are not directly changed.
- A’s words at +4, +8, and +12 and its byte at +0 become zero.
- A’s bytes +1 through +3 and +16 through +19 retain their prior values under the non-aliasing assumption.

### Consume an existing unused record

Given an empty available list, a next-unused address P, and an end address different from P:

- P is selected.
- The next-unused address becomes P + 20.
- No dependency call occurs.
- The descriptor head and end address are not directly changed.
- P receives the specified partial initialization.

This behavior does not require that the end address be greater than P; validity of the region is a caller-side precondition.

### Create the first region

Given an empty available list, equal next-unused and end addresses, and a zero descriptor head:

- The chosen capacity is 32.
- Dependency requests are 12 bytes followed by 640 bytes, each with second argument zero.
- If those calls return descriptor D and storage S, and leave the descriptor head zero, D links to zero, records capacity 32, and stores S.
- The pool’s descriptor head becomes D.
- Its end becomes S + 640.
- Its next-unused address becomes S + 20.
- The first record at S receives partial initialization.

The original equal cursor values need not themselves be zero to select this path.

### Grow using the additive candidate

Given exhaustion and an old descriptor capacity of 32:

- The candidates are 64 and 52.
- The new capacity is 64.
- The storage request is 1,280 bytes.

### Grow using the fractional candidate

Given exhaustion and an old descriptor capacity of 64:

- The candidates are 96 and 104.
- The new capacity is 104.
- The storage request is 2,080 bytes.

### Preserve a dependency-visible descriptor-head change

If a dependency call changes the pool’s descriptor head before both calls have completed, the new descriptor’s previous link receives the value read after those calls. It is not required to receive the descriptor address used earlier to read the old capacity.

### Handle extreme capacities only as documented

For a capacity that causes 32-bit arithmetic to wrap, acceptance must use the wrapped capacity candidates and wrapped storage-size expression. This is not a guarantee of safe allocation or record access. No expected graceful-error outcome is established for such a state.
