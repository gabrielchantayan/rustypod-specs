# F-bae8961d34e4

## Purpose

F-bae8961d34e4 traverses eight-byte coordinate records under the control of corresponding two-bit tags. It selects and saves a starting coordinate pair, dispatches operations to three dependencies, and terminates on a closing operation, a dependency failure, or an explicitly rejected tag sequence.

Coordinate transformation, component exchange, traversal decisions, dependency arguments, and direct context writes are established by the supplied static evidence. Interpreting the dispatched operations as geometric segments is inferred intent; the dependencies’ actual output is not established here.

The result is a normalized 32-bit status:

- **0:** the dependency on the terminating path returned zero.
- **1:** a dependency returned nonzero, or the function detected a local tag error.

A zero result does not independently establish that any particular geometric output was produced.

### Records, tags, and transformation

Each coordinate record contains two 32-bit integer components: the first at byte offset zero and the second at byte offset four. Consecutive records are eight bytes apart. Corresponding tags are individual bytes; only their low two bits affect decisions.

A component transformation left-shifts the stored 32-bit component by the low eight bits of a shift configuration, then subtracts a 32-bit subtraction operand. Component exchange occurs after the relevant transformations.

Configuration sampling depends on the path:

- **Initialization:** one shift value and one subtraction value serve all four boundary components.
- **Tag-one dispatch:** the first component’s expression reads `0x1c` and `0x08`; the second component’s expression separately reloads both fields. There is no shared configuration snapshot for this pair.
- **Two-control-record dispatch:** one shift value and one subtraction value serve all six components.

Thus the same subtraction operand is used throughout an initialization or two-control-record group, but it is not unconditionally the same for both components of a tag-one record. If memory remains stable, the separate tag-one reads naturally obtain equal values.

The evidence does not establish portable results for invalid shift counts, negative signed left shifts, overflowing shifts, signed subtraction or addition overflow, or address arithmetic overflow. Deterministic numerical acceptance cases require ordinary representable arithmetic or separately established target semantics.

### Storage and ownership preconditions

Storage must remain valid for every reached access and dependency call. The function visibly performs no allocation, release, or ownership transfer.

Relevant storage requirements extend beyond a simple inclusive index interval:

- A tag-zero start moves retained coordinate and tag positions one record and one byte backward. That adjustment alone is not a dereference of the preceding coordinate record or tag byte.
- An accepted two-control-record operation reads a prospective endpoint even when that endpoint is beyond the effective traversal boundary.
- Dependencies may access additional storage under contracts not supplied here.

Aliasing, concurrent mutation, and dependency-driven invalidation have no established safety guarantees. Dependencies must not be assumed to preserve context, globals, backing storage, or ownership.

## Behavior

### Initialization and boundary reads

The function reads the coordinate-array base from `0x88`, the shift configuration from `0x1c`, and the subtraction operand from `0x08`. It forms positions for the original start and end records.

Using those sampled configuration values, the visible component-read sequence is:

1. Original start, first component.
2. Original start, second component.
3. Original end, second component.
4. Original end, first component.

Both boundary pairs are transformed before initial-tag validation. If the indices coincide, the same record is still read through these separate expressions. A nonzero exchange selector exchanges components in both transformed pairs.

The function then reads the tag-array address from `0x8c` and establishes the initial tag position. These boundary accesses occur even if the initial tag will immediately cause rejection.

### Initial tag selection

The initial tag’s low two bits determine the following behavior.

**Tag 2:** write decimal 20 to `0x30`, then return 1. The normal starting-pair stores and all dependency calls are skipped.

**Tag 0:** move the retained current coordinate position backward by one record and the retained tag position backward by one byte. Read the original end tag using another read of the context tag-array address.

- If the end tag is 1, choose the transformed original end pair as the starting pair and move the effective end position backward by one record.
- Otherwise, choose the componentwise average of the transformed original start and end pairs. The effective end position remains unchanged.

Each average adds two signed 32-bit transformed components and divides by two. For a representable negative odd sum, division truncates toward zero. The second-component average is evaluated before the first-component average. Addition-overflow behavior is unresolved.

**Tag 1 or tag 3:** retain the transformed original start pair. Tag 3 is not rejected at entry.

### Save the starting pair

After successful initial-tag handling, the function writes:

1. Selected second component to `0x4c`.
2. Selected first component to `0x48`.

It also retains the selected pair locally for closing operations. Later dependency changes to these context fields do not replace that retained pair.

There is no visible clearing of `0x30`. Successful completion therefore does not imply that the error field is zero.

### Iteration boundary and ordinary closure

At the beginning of each traversal iteration, the retained current coordinate position is compared with the effective end position.

If the current position is at or beyond the effective end, call **F-a5ba8c521633** with the context and retained starting pair. Return 0 for a zero dependency result, otherwise 1.

These are pointer-position comparisons in the supplied representation. Their interpretation as index ordering depends on valid, nonwrapping address arithmetic.

### Next tag 1

When traversal remains open, the next coordinate record and next tag are considered.

For a next tag of 1:

1. Transform the next record’s first component, reading `0x1c` and `0x08` for that component.
2. Transform its second component, independently reloading `0x1c` and `0x08`.
3. Apply component exchange if requested.
4. Call **F-a5ba8c521633** with the context and resulting pair.

The first component’s transformation is completed before the second component’s transformation. The supplied expression representation does not establish a portable ordering among all individual memory operands within either expression.

A nonzero dependency result terminates with 1. On zero, the next coordinate and tag positions become current and traversal continues.

Neither coordinate-array nor tag-array replacement pointers are loaded from the context to perform this advancement.

### Next tag 0

A next tag of 0 enters run processing through **F-13ef22e32264**.

Before looking past the current zero-tag candidate, compare its coordinate position with the effective end:

- If the candidate is at or beyond the boundary, call F-13ef22e32264 once and terminate with its normalized status.
- Otherwise, advance one record and one tag byte, then inspect that following tag.

The following tag controls the next action:

| Following tag | Behavior |
|---|---|
| 1 | Call F-13ef22e32264; on zero, resume outer traversal with this tag-one record current |
| 0 | Call F-13ef22e32264; on zero, continue scanning the run |
| 2 or 3 | Write 20 to `0x30` and return 1 without dispatching that tag to another branch |

Any nonzero F-13ef22e32264 result immediately returns 1.

This branch performs no direct coordinate transformations or starting-pair updates. Each dependency invocation receives only the context. It does not receive the scanning positions, candidate coordinates, or an explicit endpoint.

### Next tag 2 or 3

Either next-tag value enters the same two-control-record branch. The first control tag need not equal 2.

The second control record is two records after the current position:

- If that position is beyond the effective end, reject without reading its tag.
- Otherwise, read its tag and require its low two bits to equal 2.

Rejection writes 20 to `0x30` and returns 1.

After acceptance, sample `0x1c` and `0x08` once for the complete transformation group. Transform the two control records and a prospective endpoint three records after the current position.

The visible coordinate-read order is:

1. First control, first component.
2. Second control, first component.
3. Prospective endpoint, second component.
4. Second control, second component.
5. First control, second component.
6. Prospective endpoint, first component.

Apply component exchange to all three resulting pairs.

The prospective endpoint is read **before** deciding whether to use it. Its storage must therefore be accessible even when closure will substitute the retained starting pair.

Call **F-ed044fef08a3** with the context, first control pair, second control pair, selected endpoint pair, another value equal to the context address, and the original start and end indices.

Endpoint selection determines continuation:

- **Prospective endpoint beyond the effective end:** pass the retained starting pair and terminate with the dependency’s normalized result.
- **Prospective endpoint at or before the effective end:** pass its transformed pair. On nonzero, return 1. On zero, advance the retained coordinate and tag positions by three records and continue.

No endpoint-tag validation is visible.

When the prospective endpoint is exactly at the effective end and the dependency succeeds, the next iteration calls F-a5ba8c521633 for ordinary closure. In contrast, the beyond-boundary case terminates directly after F-ed044fef08a3.

## Side effects

### Direct writes and failure behavior

The established direct writes are limited to:

- Starting second component at `0x4c`, followed by starting first component at `0x48`.
- Decimal 20 at `0x30` on explicit tag rejection.

There are no visible direct writes to coordinate records or tags, except that aliasing with the context could make these accesses overlap; no safe aliasing contract is established.

Dependency failure does not itself cause a local write of 20. There is no rollback or visible cleanup call. Earlier starting-pair writes and dependency effects remain observable after a later failure.

### Retained addresses and mutable data

Both traversal cursors are retained across dependency calls:

- Replacing `0x88` does not rebase the retained coordinate traversal.
- Replacing `0x8c` does not redirect subsequent tag reads from the retained tag cursor.

This address retention does not snapshot array contents. Changes to coordinate values at retained addresses can affect later coordinate reads. Changes to tag bytes in retained backing storage can affect later tag decisions.

Tag contents are not established as being loaded exactly once per logical decision; the supplied representation contains repeated masked tag expressions.

Configuration has different retention rules:

- Initialization retains one configuration sample for both boundary pairs.
- Each later tag-one component separately reloads both transformation fields.
- Each two-control-record operation samples configuration once for its six components.

A dependency’s configuration changes can therefore affect later transformations without changing already retained boundary pairs. A dependency’s changes to saved starting fields likewise do not change the local closing pair.

These observations describe visible accesses, not a guarantee that concurrent mutation is supported or that dependencies leave retained storage valid.

- Transform and dispatch the second record through F-a5ba8c521633.
- If that call succeeds, call the same dependency with the retained starting pair for closure.
- Either call returning nonzero makes the overall result 1.

The second record’s two components each reload the shift and subtraction fields.

### Distinct tag-one sampling

Consider a tag-one record with components `(2, 3)`, no exchange, and an observation in which the first transformation reads shift 1 and subtraction 0, while the second reads shift 0 and subtraction 1.

The dispatched pair is `(4, 2)`, not a pair derived from one shared configuration snapshot. This is a conditional description of the visible reload behavior, not a claim that concurrent mutation is supported.

### Initial rejection

With initial tag 2:

- Both boundary coordinate pairs have already been read and transformed.
- Write 20 to `0x30`.
- Return 1 without starting-pair stores or dependency calls.

### Tag-zero start selection

With initial tag 0 and original end tag 1:

- Retain the transformed original end pair as the starting pair.
- Move current coordinate and tag positions backward once.
- Move the effective end backward once.
- Any later F-ed044fef08a3 call still receives the original indices.

If the averaging alternative is selected and corresponding transformed components are −4 and 1, their midpoint component is −1, assuming representable addition.

### Tag-sequence boundaries

A next tag 3 followed by a second control tag 2 can reach F-ed044fef08a3. A second control tag 3 instead causes local rejection.

However, tag 2 or 3 encountered while scanning a tag-zero run causes rejection there; it does not start the two-control-record branch.

### Beyond-boundary endpoint

When the second control is exactly at the effective end and has tag 2:

- Read the following record’s coordinates.
- Pass the retained starting pair as the endpoint to F-ed044fef08a3.
- Terminate from that call’s status without an additional closure call.

### Tag-pointer replacement

Suppose a successful dependency replaces `0x8c` with another tag-array address, while leaving retained backing storage valid.

Subsequent tag decisions still use the old retained cursor. Changing only the replacement array does not redirect them. Changing a subsequently examined byte in the retained backing storage can change a later decision.

### Failure without local error assignment

If a dependency returns −7, the overall result is 1. This failure alone does not cause the function to assign 20 to `0x30`.
