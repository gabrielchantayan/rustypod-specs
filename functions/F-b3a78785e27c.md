# F-b3a78785e27c

## Purpose

F-b3a78785e27c processes two chain-head locations in a fixed phase order: the first head is processed until it is observed to be zero, then the second head is processed until it is observed to be zero.

For each nonzero head, the established action is to **replace the active head with the selected record’s stored successor, then resolve and invoke an indirect operation through that record**. This is not unconditionally removal. In particular, if the record is its own successor, the head replacement leaves the head referencing the same record when the operation begins.

With suitable structural assumptions, this behavior can drain two chains. Destruction, deallocation, ownership transfer, and successful termination are not established.

Each phase rereads its active head after every normally returning invocation. Processing therefore follows live state, including changes made by indirect operations, rather than a chain captured at entry.

## Interface

### Input and relevant storage

The function accepts one pointer to mutable state. The supplied representation identifies the following integer-word locations:

| Storage | Word index | Role |
|---|---:|---|
| State | 0 | First chain head |
| State | 2 | Second chain head |
| Selected record | 0 | Dispatch-structure address |
| Selected record | 77 | Successor value |

State word 1 is not separately addressed by the routine.

A zero head ends its phase. A nonzero head is interpreted as a record address. The record’s first word supplies a dispatch-structure address; the indirect target is loaded at byte offset 4 from that address.

### Widths and addressing

The representation stores heads, successors, and dispatch addresses in integer words and subsequently uses those values as addresses. It is consistent with a 32-bit integer/address model, but does not independently establish the original ABI.

Under a four-byte integer-word model:

| Field | Byte offset from containing storage |
|---|---:|
| First head | 0 |
| Second head | 8 |
| Record dispatch address | 0 |
| Record successor | 308, or 0x134 |

The dispatch-target offset is explicitly **4 bytes**, independently of the indexed-word calculations above.

The original integer width, data-pointer width, function-pointer width, alignment requirements, byte order, and integer-to-pointer conversion rules remain unresolved. In particular, this contract does not reinterpret the layout as native 64-bit pointers.

The successor is copied as a word without numeric adjustment. There is no record counter, decrementing length, or arithmetic transformation of a successor. Field-address calculations still depend on the actual execution model; the source does not establish checked arithmetic or defined behavior for invalid addresses.

### Output

There is no explicit result value. Observable outcomes are:

- Head-value replacements.
- Indirect invocations and their ordering.
- Effects performed by those invocations.
- Normal return, continued execution, or failure to return.

No indirect-call return value is explicitly consumed.

### Preconditions for defined, normal execution

State storage must support the head accesses actually reached. A normal completion reaches both head locations. The input pointer is not checked for nullness or validity.

For every selected record:

- Its successor field must be readable.
- The active head location must be writable.
- Its dispatch-address field must remain readable after the head replacement.
- The dispatch structure must support the target load at byte offset 4.
- The loaded target must be callable under the actual calling convention.
- Any context required by that target must be valid.

These are execution requirements, not validations performed by the function. Dispatch validity must hold at dispatch-resolution time, not merely when the record is first selected.

## Behavior

### First phase

The function reads the first head. If the value is zero, it proceeds to the second phase.

Otherwise, that value selects a record. The logical access and invocation order is:

1. Read the selected record’s successor.
2. Write that value into the first head.
3. Read the selected record’s dispatch-structure address.
4. Read the indirect target at dispatch-structure byte offset 4.
5. Invoke that target.
6. If it returns normally, read the first head again.

The next selection is determined by the newly read head. It is not necessarily determined by the successor written before the call: the operation may replace, clear, or repopulate the head.

The first phase ends only when its head read observes zero. Until that happens, the function does not begin its second-head processing sequence. Aliasing or indirect-operation effects can nevertheless access storage also used by the second head.

### Second phase

After the first phase observes zero, the function reads the second head.

Each nonzero value selects a record. The function follows the same successor-read, head-write, dispatch-resolution, invocation, and head-reread sequence, using the second head as the destination of the replacement.

When a second-head read observes zero, the function returns.

There is no later first-phase pass. If a second-phase operation repopulates the first head, the routine does not return to it during this invocation.

### Head replacement is not unconditional removal

The direct transition is replacement of the active head with the selected record’s successor.

If the successor differs from the selected record’s address, and the relevant storage is noninterfering, the replacement makes the active head stop directly referencing that selected record. This does not prove that the record is unreachable elsewhere.

If the successor equals the selected record’s address, the head still references that record after replacement. With unchanged relevant storage, the indirect operation begins with that same head value.

A zero successor makes the active head zero before invocation, provided the head write has its ordinary, noninterfering effect. The operation may subsequently change it again.

The routine does not clear the selected record’s successor or dispatch field. It performs no separate unlinking operation and does not update predecessor records.

### Aliasing and dispatch resolution

The source establishes no separation among state storage, records, and dispatch structures.

Dispatch resolution occurs **after** the head write. If the active head location overlaps the selected record’s dispatch-address field, the dispatch read uses the storage as modified by that write. The dispatch address is not saved before the replacement.

Other overlaps can likewise change the effects of ordinary field writes. Any statement that unrelated fields remain unchanged requires nonoverlapping storage or a more specific alias analysis.

The access sequence describes the routine’s own logical behavior. It is not a memory-ordering guarantee for concurrent execution.

### Mutation, repetition, and termination

Indirect operations may alter the active head, the other head, record fields, dispatch structures, globals, or storage validity. No preservation contract is supplied.

Consequently:

- A first-phase operation can change which first-chain record is selected next.
- A first-phase operation can change the second head before that phase begins.
- A second-phase operation can change subsequent second-phase selection.
- A second-phase operation can repopulate the first head without causing another first-phase pass.

Repeated addresses are not detected. A record may be selected repeatedly in one phase, selected in both phases, or reintroduced by an operation.

Each phase must eventually observe zero for normal completion, and every invocation encountered before completion must return normally. An initially finite chain does not ensure termination if operations keep adding work. A cycle does not by itself prove nontermination if operations can break it.

For a self-successor record, normally returning operations that preserve the relevant fields and leave the active head at the value written by the routine cause repeated selection of that same record.

## Side effects

### Direct effects

The only explicit writes are successor-value replacements of the active head.

There is no separate direct operation to:

- Initialize or clear state word 1.
- Clear a record’s successor or dispatch field.
- Allocate or release storage.
- Record a processed count.
- Restore an earlier head after failure.

These statements describe the routine’s explicit operations. Aliased storage may change as a consequence of a head write, and indirect operations may perform additional writes or memory-management actions.

### Ownership and lifetime

No ownership transfer or release obligation is established. Advancing a head can be consistent with cleanup, but does not itself establish destruction or deallocation. A self-successor replacement does not even make the active head stop referencing the selected record.

The selected record’s relevant storage must remain valid through the post-replacement dispatch resolution. What the invoked operation does to that storage is unknown.

After an invocation returns, there is no further access through **that iteration’s saved record pointer**. The next direct access is to the active head. This does not imply that the record address will never be read again: a later iteration or the second phase may select it again.

Accordingly, release by an operation is compatible with subsequent execution only when later accesses remain valid. If another head or successor still refers to released storage, this routine has no protection against selecting it.

### Errors and partial progress

There is no explicit error result, validation branch, recovery path, or rollback.

The ordering distinguishes failure points:

- Before the successor read completes, the iteration has not yet performed its head write.
- Before a successful head write, no completed head replacement is established.
- After a successful head write, dispatch resolution and invocation occur with that replacement already performed.

The function does not restore the old head if a later action fails. The effects of a faulting or partially completed machine access depend on the execution environment.

If an indirect operation does not return normally, the routine does not proceed through its ordinary loop continuation. Exception unwinding, nonlocal transfer, process termination, and machine-fault handling are not established.

No explicit locks, atomic operations, barriers, or concurrency protocol are visible.

## Dependencies

The only call dependency is an indirect target resolved separately for each selected record.

No opaque function ID is supplied for those targets. They therefore remain unresolved dependencies; assigning a concrete identity would invent evidence. The supplied function ID identifies F-b3a78785e27c itself, not the indirect callees.

The visible call expression supplies no explicit arguments. That does not establish that the machine-level call has no receiver or contextual inputs. The following remain unknown:

- Target signatures and calling conventions.
- Implicit receiver or contextual arguments.
- Register and stack inputs.
- Return-value conventions.
- Ownership and release behavior.

The function does not establish that different records share one target or that repeated selections of one address resolve to an unchanged target.

## Acceptance examples

These are conditional criteria derived from static evidence, not runtime observations. Unless an example states otherwise, assume valid, suitably aligned, noninterfering storage; callable targets; normally returning operations; and no external mutation.

### Both heads are zero

Given both heads are zero:

- The first head is read before the second.
- No record or dispatch field is accessed.
- No head replacement or indirect invocation occurs.
- The function returns normally.

### One terminal record per phase

Given the first head references A, the second references B, both successors are zero, and operations preserve the relevant fields and leave both heads at the values established by the routine:

- The first head becomes zero before A’s invocation.
- A’s invocation precedes B’s.
- The second head becomes zero before B’s invocation.
- Both heads are zero on return.

### Two first-phase records

Given the first head references A, A’s successor is B, B’s successor is zero, and operations preserve relevant fields and head values:

- The first head becomes B before A’s invocation.
- B is selected after A returns.
- The first head becomes zero before B’s invocation.
- Second-phase processing starts only after B returns and the first head is read as zero.

### Operation replaces the active head

Given A’s successor is B, but A’s operation sets the active head to valid record C:

- The routine first writes B into that head.
- After the operation returns, selection follows the reread value C, assuming no intervening mutation.
- Processing B is not guaranteed.

### Self-successor

Given the active head references A, A’s successor is A, and each operation preserves relevant fields and the active head:

- Each replacement leaves the head referencing A.
- Each invocation begins with the active head still referencing A.
- Returning from the operation causes A to be selected again.
- The phase does not terminate under those continuing conditions.

If an operation instead clears the active head and returns, the phase ends on the next head read.

### Both heads reference the same record

Given both heads initially reference A and A’s successor is zero, additionally require that every invoked operation:

- Returns normally.
- Preserves A’s relevant fields and storage validity.
- Leaves both heads at their current values established by the routine.

With valid, noninterfering storage and no external mutation:

- A is selected exactly once in the first phase.
- A is selected exactly once in the second phase.
- Both heads are zero on return.

Preserving A’s validity and only the other head is insufficient for these counts: an operation could reinsert A into the active head. Changing its successor, failing to return, or invalidating its storage also defeats the stated premises.

### Second phase repopulates the first head

Given a second-phase operation installs valid record C into the first head:

- The routine continues second-phase processing.
- It does not restart the first phase.
- If later actions leave the first head unchanged and the second phase terminates, the first head still references C on return.

### Dispatch failure after replacement

Given a readable successor and a successful head write, but dispatch resolution cannot complete:

- The head replacement precedes the failure.
- No rollback is specified.
- Normal return is not guaranteed.
- The precise fault or error manifestation is environment-dependent.

## Evidence

**Established static evidence:** two sequential head-processing phases; head locations at state words 0 and 2; successor at record word 77; dispatch address at record word 0; target load at dispatch byte offset 4; successor read and head replacement before dispatch resolution; active-head rereading after normally returning calls; no first-phase restart; no explicit result, validation, allocation, release, cycle detection, or rollback.
