# F-48005ab658e3

## Purpose

F-48005ab658e3 constructs byte lookup tables in caller-supplied storage. Each table contains 256 entries. Tables are grouped into blocks of 16 tables, so each block occupies 4,096 bytes.

For a positive block count, every table applies an exclusive-OR transformation to its input index before selecting a byte from a shared lookup table. The last output block additionally applies a table-specific exclusive-OR mask to the selected byte.

This describes the established transformation, not its intended application. A cryptographic or other domain-specific purpose is not established by the supplied source.

## Interface

The function has three integer-valued arguments and no explicit return value:

| Argument | Meaning |
|---|---|
| Block count, \(n\) | Controls the ordinary-block loop and the location of the mandatory final block. |
| Source address, \(S\) | Base address for selector bytes and final-block mask bytes. |
| Destination address, \(D\) | Base address used to calculate output locations. |

Although the two address arguments are represented as integers in the supplied source, their derived values are used as memory addresses.

The function also uses a shared address-bearing cell. It reads this cell twice at entry:

1. The first value becomes the lookup-table base, \(L\).
2. The second value, minus 64 bytes, becomes the offset-table base, \(O\).

These are separate reads. Their values need not be assumed equal if the shared cell can change between them. When both reads return the same address, the offset table occupies the 64 bytes immediately preceding the lookup table.

The offset table contains 16 entries, each read as a four-byte integer. Denote the value of entry \(j\) by \(P_j\), for \(0 \leq j < 16\). Entries are loaded when needed, not copied into a private array at entry.

The lookup table is accessed through byte reads at offsets 0 through 255 from \(L\). Selector bytes and mask bytes are also read as bytes. Output writes are one byte each.

### Widths and representation

The supplied representation uses integer and unsigned-integer arithmetic, four-byte offset-entry spacing, and byte accesses. A 32-bit interpretation of the integer types is consistent with that representation; the source does not independently establish the compiler’s complete integer and address model.

Under that interpretation:

- The block count and offset entries are signed 32-bit integers.
- The table-entry counter is an unsigned 32-bit integer, taking values 0 through 255 for actual accesses.
- Byte reads produce values in the range 0 through 255.
- Exclusive-OR of a selector byte and an entry index remains in the range 0 through 255.
- Exclusive-OR of a lookup byte and a mask byte also remains in that range.

Endianness affects interpretation of the four-byte offset entries. It does not affect the individual byte operations. The required endianness is not established here.

### Preconditions

For defined, successful execution, callers must provide valid memory for every address actually accessed and satisfy the target’s alignment requirements for integer loads.

All evaluated integer arithmetic must be valid under the actual execution model. This includes count multiplication, address addition, address subtraction, and intermediate expressions—not merely the simplified final addresses below. The function does not establish a wrapping-address contract.

For the ordinary positive-count use case, a destination region of \(4096n\) bytes starting at \(D\) covers the output. Source requirements depend on the offset values; the implementation does not constrain those values to a 16-byte range.

No ownership transfer is expressed. The function neither allocates nor releases memory.

## Behavior

### Entry state

Before producing output, the function reads the shared address-bearing cell twice to obtain \(L\) and \(O\) as described above. Subsequent changes to that cell do not directly change these saved bases.

This does not freeze the contents of the lookup table, offset table, source memory, or destination memory. Those contents can affect later accesses.

### Ordinary blocks

For \(n > 1\), the function first produces output blocks numbered \(b=0\) through \(n-2\), in ascending order.

Within each block, it processes table positions \(j=0\) through 15 in ascending order. Within each table, it processes entry indices \(x=0\) through 255 in ascending order.

For each entry, the operation is:

- Read the four-byte offset at \(O+4j\).
- Read the selector byte at \(S+16b+P_j\).
- Use the selector byte exclusive-OR \(x\) as the lookup-table index.
- Read the selected lookup byte.
- Write that byte to \(D+4096b+256j+x\).

For stable, nonoverlapping input data, this gives:

\[
\operatorname{output}[4096b+256j+x]
=
\operatorname{lookup}
\left[
\operatorname{source}[16b+P_j]\mathbin{\oplus}x
\right].
\]

The equation is a value description, not a promise that the selector or offset is read only once per table. Both are read again for every entry.

### Mandatory final block

After the ordinary-block loop, the function adjusts its source-address value by \(16n\). It then always produces one block of 16 tables, regardless of whether \(n\) is positive, zero, or negative.

The final block’s destination base is:

\[
D+4096(n-1).
\]

For each table position \(j=0,\ldots,15\), and each entry index \(x=0,\ldots,255\), the function:

- Reads the offset entry at \(O+4j\).
- Reads the selector byte at \(S+16(n-1)+P_j\).
- Forms the lookup index by exclusive-OR with \(x\).
- Reads the lookup byte and the mask byte at \(S+16n+j\).
- Writes their exclusive-OR to \(D+4096(n-1)+256j+x\).

For stable, nonoverlapping input data:

\[
\operatorname{output}[4096(n-1)+256j+x]
=
\operatorname{lookup}
\left[
\operatorname{source}[16(n-1)+P_j]\mathbin{\oplus}x
\right]
\mathbin{\oplus}
\operatorname{source}[16n+j].
\]

The mask byte is read for each output entry. The source does not cache one mask value for the entire table.

The final block has the same ordering as ordinary blocks: table position first, entry index second, both ascending.

### Zero and negative counts

The count does not act as a conventional “number of blocks, with zero meaning no work” parameter.

- If \(n=1\), the ordinary-block loop is skipped and one final block is written at \(D\).
- If \(n=0\), one final block is written at \(D-4096\). Its selector addresses are based at \(S-16\), and its mask addresses are based at \(S\).
- If \(n<0\), the ordinary-block loop is also skipped. One final block is written at \(D+4096(n-1)\), provided all arithmetic and memory accesses are valid.

No count validation or early return prevents these accesses.

### Read and write ordering

The established iteration order is block, table, then entry. Each entry’s store occurs after evaluation of the values needed for that store.

The offset entry is read before the selector byte because it determines that byte’s address. The selector byte is read before the indexed lookup access because it determines the lookup index.

For the final-block expression, the supplied source does not establish which of the lookup-byte read and mask-byte read occurs first. Both provide operands for the value stored. A contract must not impose an ordering between those two reads without additional evidence.

## Side effects

The explicit writes are byte stores to the calculated destination locations.

For valid positive \(n\), execution performs \(4096n\) byte stores and fills the \(n\) consecutive output blocks in ascending address order.

For valid \(n \leq 0\), it performs 4,096 byte stores to the mandatory final block. These writes are before \(D\), not within a zero-length region beginning at \(D\).

There are no explicit writes to the shared address-bearing cell, no explicit memory allocation or release, and no explicit external calls.

Aliasing is significant:

- Destination writes can overwrite source selectors or masks.
- They can overwrite lookup-table bytes.
- They can overwrite offset-table entries.
- If the destination overlaps the shared address-bearing cell, the stores can modify that cell, although the two saved bases have already been obtained.

Because offsets, selectors, lookup bytes, and masks are read repeatedly, earlier stores can change later results when these regions overlap. The function does not provide snapshot or overlap-safe semantics.

No locking, synchronization, rollback, or error-reporting mechanism appears. A fault can occur after some output has already been written. The behavior of faults and concurrent modification is not specified by this function.

## Acceptance examples

These examples are conditional specifications, not results of execution. Unless stated otherwise, assume stable inputs, no relevant overlap, valid arithmetic, valid memory, and equal values from the two initial shared-cell reads.

### One block

Given \(n=1\), only the final-block transformation applies.

For table position 3 and entry index 5:

- The selector is read from \(S+P_3\).
- The mask is read from \(S+19\).
- The output location is \(D+773\).

If the selector is 18, the lookup index is \(18\oplus5=23\). If lookup entry 23 is 160 and the mask is 15, the stored byte is \(160\oplus15=175\).

No unmasked ordinary block is produced first.

### Two blocks

Given \(n=2\):

- The first block occupies \(D\) through \(D+4095\).
- The final block occupies \(D+4096\) through \(D+8191\).

For table position 0, entry index 7, suppose:

- \(P_0=0\).
- The selector at \(S\) is 2.
- Lookup entry 5 is 100.

The first block receives 100 at \(D+7\), because \(2\oplus7=5\).

For the corresponding final-block entry, the selector comes from \(S+16\), and the mask comes from \(S+32\). If that selector is also 2 and the mask is 3, the byte written at \(D+4103\) is \(100\oplus3=103\).

### Zero count

Given \(n=0\) and sufficient accessible storage before both nominal bases:

- The function still writes 4,096 bytes.
- The first destination byte is at \(D-4096\).
- The last is at \(D-1\).
- Table position \(j\) uses a selector at \(S-16+P_j\).
- Its mask comes from \(S+j\).

Treating zero as a no-op would violate the observed control flow.

### Unrestricted offsets

If \(P_4=37\), table position 4 uses a selector 37 bytes beyond the applicable source-block base. It does not reduce 37 modulo 16.

If an offset is negative, it selects a location before that base, subject to valid arithmetic and memory access. The source contains no range check.

### Changed backing memory

If an earlier destination store changes a selector location that a later iteration reads, the later iteration uses the changed byte. An implementation that first snapshots all selectors would not preserve this behavior.
