# F-6bae58038ce6

## Purpose

F-6bae58038ce6 conditionally processes a positive quantity associated with a shared context and a selected fixed-stride record. It can query availability, transform the quantity through auxiliary dependencies, request a result with three output words, conditionally update record-associated state, and add a reported quantity to record-level and context-level totals.

The established behavior is the sequence of calls, checks, reads, and writes described below. Interpreting these operations as queue consumption, resource replacement, or accounting is inferred intent, not an established dependency contract.

The function returns the 32-bit value **0** on its normal paths and **3** at three explicit failure gates. A return of 0 does not necessarily mean that records or totals changed. A return of 3 does not imply that earlier dependency effects were rolled back.

## Interface

### Inputs and result

The function accepts two values represented as 32-bit integers in the supplied static representation:

- **Context address:** used as the base address for shared fields and indexed records.
- **Record index:** multiplied by **0x50**, or 80 bytes, to select a record-relative address base.

The selected base is the context address plus the index multiplied by 80. Record fields below are addressed relative to this selected base; shared fields are addressed directly relative to the context.

The result is a 32-bit word with these explicitly returned values:

| Result | Established meaning |
|---|---|
| 0 | Execution reached the normal return, including paths that perform no work. |
| 3 | The availability query returned nonzero, the result request returned exactly 2, or the conditional record operation returned nonzero. |

The function does not expose its temporary output words directly to the caller.

### Preconditions

The caller must provide addresses and an index for which all accesses on the executed path are valid. The function performs no explicit null, index-range, alignment, or buffer-size validation.

The dependencies receive addresses of temporary 32-bit output words. Those outputs must be initialized whenever the function subsequently consumes them. In particular:

- A zero status from the availability query must leave its quantity output usable.
- Any result-request status other than 2 permits inspection of its reported-quantity output.
- A positive reported quantity can lead to use of the other result-request outputs.

The source does not establish that dependencies satisfy these requirements for every possible status.

The behavior of invalid address arithmetic, signed overflow, and inaccessible or misaligned memory is not established by the supplied representation.

## Behavior

### 1. Select the record and inspect its gate

The selected base is computed before the first gate-byte read.

If the byte at selected offset 0x1284 is nonzero, the function returns 0 immediately. It makes no dependency calls and performs no explicit writes on this path. Every nonzero byte has this effect; the test is not restricted to a flag value of 1.

If the byte is zero, processing continues.

### 2. Query an initial quantity

The function reads the shared handle at context offset 0x1060 and calls **F-1c86b33764dc**, supplying that handle and an address for a temporary 32-bit quantity output.

If the dependency returns any nonzero status, the function returns 3. It does not inspect the quantity output on this path.

If the status is zero, the output quantity is compared with zero as a signed 32-bit value:

- Zero or negative: return 0 without making further calls.
- Positive: continue.

Consequently, a quantity whose high bit is set does not enter the positive-quantity path under the signed interpretation shown.

### 3. Optionally replace the quantity

For a positive initial quantity, the function reads the signed 32-bit field at context offset 0x1080.

If that field is 1 or less, the original positive quantity is retained.

If that field is greater than 1, the function performs these calls in order:

1. Call **F-1c7710595b35** with the initial quantity.
2. Call **F-fdb31af1de99** with the preceding call’s 32-bit result and the word at selected offset 0x127c.
3. Call **F-c9e0501fef5b** with no explicit arguments and use its 32-bit result as the replacement quantity.

The word at selected offset 0x127c is read for the second call, after the first call has completed. The second call’s return value is ignored.

A replacement quantity of exactly zero is changed locally to 1. No other replacement value is adjusted. In particular, the function does not repeat the positive-quantity check after this transformation. A negative replacement quantity can therefore be passed to the next dependency.

### 4. Request a result

The function calls **F-e162eb24ee4a** with six arguments in this order:

1. The shared handle read from context offset 0x1060.
2. The retained or replacement quantity.
3. An address for a 32-bit reported-quantity output.
4. An address for a 32-bit first payload output.
5. An address for a 32-bit second payload output.
6. The word read from context offset 0x1394.

The shared handle is read again for this call; the function does not explicitly retain the handle used by the earlier query. Dependency changes to the context can therefore affect the handle supplied here.

Only a return status of **exactly 2** triggers an immediate return of 3. Other statuses, including nonzero statuses other than 2, do not independently stop execution.

After a status other than 2, the function compares the reported quantity with zero as a signed 32-bit value:

- Zero or negative: return 0 without the conditional record operation or explicit state updates below.
- Positive: continue.

The reported quantity, rather than the requested quantity, determines both later total increments.

### 5. Recheck the gate and conditionally update associated state

For a positive reported quantity, the function reads the selected gate byte again.

This is a fresh read. The earlier zero result is not reused. Dependencies called in between may have changed the gate.

If the gate is now nonzero, the function skips the associated-state operation and its accompanying word replacements, but still proceeds to increment both totals.

If the gate remains zero, the function calls **F-e3a1bffa31a1** with:

1. The shared handle read again from context offset 0x1060.
2. The current word at selected offset 0x1248.
3. The first payload output from the result request.

If this call returns any nonzero status, the function returns 3. Neither total increment nor either explicit associated-word replacement is performed after this failure. Effects already produced by dependencies remain outside any rollback guarantee.

If the call returns zero, the function:

1. Reads and compares the 32-bit words at selected offsets 0x125c and 0x1244.
2. If they are equal, writes the first payload to selected offset 0x125c.
3. Writes the second payload to selected offset 0x1248, regardless of whether the comparison succeeded.

The comparison occurs after the dependency returns. Changes that dependency makes to either comparison field can affect the outcome.

The gate is not checked again after this call. A gate change made by the dependency does not itself suppress these following writes.

### 6. Increment totals

For every positive reported quantity that reaches this stage, the function performs two read-modify-write operations in this order:

1. Add the reported quantity to the 32-bit value at selected offset 0x1254 and write the result there.
2. Add the same reported quantity to the 32-bit value at context offset 0x1074 and write the result there.

The context total is read after the selected-record total has been written. The function does not explicitly snapshot both totals before updating either.

It then returns 0.

The supplied representation uses signed integer expressions for these additions. It does not establish a portable overflow contract. Saturation, overflow reporting, or guaranteed modulo-\(2^{32}\) behavior must not be assumed.

## Side effects

### Explicit writes

Depending on the path, the function itself can write:

- Selected offset 0x125c: first payload, only following a successful conditional record operation and equality of the two comparison fields.
- Selected offset 0x1248: second payload, following a successful conditional record operation.
- Selected offset 0x1254: incremented selected-record total.
- Context offset 0x1074: incremented context total.

When all four writes occur, their order is the order listed above.

The function does not explicitly modify the gate, shared handle, transformation-control field, auxiliary argument, or comparison reference.

### Dependency effects and repeated reads

No dependency is established to preserve shared memory, global state, or the selected record. The repeated reads of the handle, the second gate read, the post-call comparison, and the later total reads must therefore remain semantically distinct.

The source establishes call order and the sequencing between calls and subsequent operations. It does not establish the evaluation order of independent argument reads within a single call expression, nor the relative order of the two reads used in the equality comparison.

There is no explicit synchronization, atomic update, transaction, rollback, or concurrency guarantee.

### Ownership and lifetime

The function contains no explicit allocation or deallocation operation. This does not establish that its dependencies allocate nothing or release nothing.

The meanings and ownership of the handle, payloads, existing associated word, and auxiliary return value are unknown. Passing a word to a dependency does not by itself establish ownership transfer.

Addresses of temporary output storage are supplied to two dependencies. The function consumes those outputs during the invocation. Whether either dependency retains these addresses is not established; valid use after the storage lifetime cannot be inferred.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Unless specified otherwise, assume valid memory, initialized dependency outputs, no unmentioned dependency mutations, distinct relevant storage locations, and arithmetic within the signed 32-bit range.

1. **Initially gated record.**  
   With a nonzero initial gate byte, the result is 0. No dependency is called and no explicit context or record write occurs.

2. **Availability-query failure.**  
   With an initial zero gate and query status −1, the result is 3. No transformation or result request follows. The same holds for every nonzero query status.

3. **No positive availability.**  
   With query status zero and quantity zero or −4, the result is 0. The transformation-control field is not needed, and no result request or total update follows.

4. **Transformation threshold and zero replacement.**  
   With initial quantity 8 and transformation control 2, all three transformation dependencies run in the stated order. If F-c9e0501fef5b returns zero, the result request receives quantity 1. With transformation control 1 instead, those calls are skipped and the request receives 8.

5. **Negative transformed quantity.**  
   With a positive initial quantity, transformation enabled, and replacement result −3, the result request receives −3. The function does not reject it through another positivity check.

6. **Result-request status distinction.**  
   A result-request status of 2 produces result 3 and prevents subsequent explicit updates. A status of 1 does not itself prevent processing: with initialized positive reported quantity, execution continues.

7. **Nonpositive reported quantity.**  
   With result-request status zero and reported quantity zero, the result is 0. There is no second gate read, conditional record operation, payload replacement, or total increment.

8. **Gate becomes nonzero during dependencies.**  
   Suppose the gate starts at zero but is nonzero at its second read, and the reported quantity is 4. The conditional record operation and both payload-related writes are skipped. A selected total of 10 becomes 14, and a context total of 100 becomes 104.

9. **Conditional record operation fails.**  
   With a positive reported quantity, second gate value zero, and conditional-operation status 7, the result is 3. No subsequent payload write or total increment occurs. Earlier dependency effects are not undone.

10. **Successful update with equal comparison fields.**  
    Suppose the conditional operation succeeds, both comparison fields contain 20 afterward, the payloads are 30 and 40, and the reported quantity is 3. The function writes 30 to offset 0x125c, then 40 to offset 0x1248, then increments the selected total and context total by 3 in that order.

11. **Successful update with unequal comparison fields.**  
    Under the preceding conditions but with unequal comparison fields, offset 0x125c is unchanged by this function. Offset 0x1248 is still replaced, and both totals are still incremented.
