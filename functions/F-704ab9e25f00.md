# F-704ab9e25f00

## Purpose

F-704ab9e25f00 processes an input byte range into a destination selected by a descriptor and a 32-bit type value. A descriptor-provided callback takes precedence over all built-in processing.

Built-in handling provides:

- A one-byte scalar conversion.
- An empty-input case that initially stores the value 1.
- Three dependency-mediated conversion paths.
- Generic-object creation or reuse, followed by either direct input attachment or dependency-mediated population.
- Optional indirection through a tagged wrapper.
- Error reporting and path-dependent failure cleanup.

The semantic names of the type values and descriptor mode are not established. Direct input attachment and clearing the transfer flag suggest an ownership handoff, but neither ownership nor release obligations are established by this function alone.

The function has six arguments and a 32-bit result.

|---|---|---|

The built-in path returns 1 on success and 0 on a handled failure. The callback path returns the callback’s 32-bit result unchanged, without Boolean normalization. Invalid memory accesses and dependencies that do not return normally are outside these ordinary return guarantees.

### Path-dependent preconditions

The descriptor must permit reading its provider field. A nonzero provider must permit reading its callback field. A selected callback determines its own additional requirements; this function performs no built-in destination or mode access before invoking it.

Without a callback:

- The descriptor must permit reading its mode.
- The destination must support the word accesses required by the selected path.
- Any wrapper or object subsequently dereferenced must identify suitable storage.
- Type 1 with length 1 requires a readable input byte.
- Generic-object handling requires a readable transfer-flag byte. Direct attachment also requires that byte to be writable.
- Dependency-mediated input requirements remain governed by the corresponding dependency.

No general null-pointer, buffer-bound, negative-length, alignment, or arithmetic-overflow validation is visible. No non-aliasing requirement is explicitly checked. Aliasing among arguments and reachable fields can make earlier writes affect later reads.

## Behavior

### Callback precedence

The function first reads the provider address from descriptor offset +16. If that address is nonzero, it reads the callback address from provider offset +20.

When both addresses are nonzero, it invokes the callback with eight arguments, in this order:

1. Original destination address.
2. Input address.
3. Signed length.
4. Type.
5. Transfer-flag address.
6. Descriptor address.
7. Zero.
8. Original destination address again.

The callback result is returned immediately. No built-in mode selection, conversion, reporting, or cleanup follows a normally returning callback.

A nonzero provider with a zero callback falls through to built-in handling. An absent provider does not require accessing a callback field.

### Effective destination and wrapper selection

Built-in handling reads the descriptor mode at offset +4.

For any mode other than −4, the original destination is the effective destination, and the retained wrapper address is zero.

For mode −4, the function:

1. Reads a wrapper address from the original destination.
2. If that address is zero, calls F-c810c23e5619 without explicit arguments and writes its result into the original destination.
3. Reads the selected wrapper’s tag at offset +0.
4. If the tag differs from the requested type, calls F-75e0e102872c with the wrapper address and requested type.
5. Uses wrapper offset +4 as the effective destination.

There is no visible zero-result check between wrapper creation and the tag read. A zero creation result therefore does not produce a handled allocation-failure return; ordinary continuation requires a usable wrapper address.

The selected wrapper address and original outer destination address are retained for later completion. They are not selected again by rereading the outer destination after intervening dependency calls. The effects of the wrapper-adjustment dependency are unknown; this function does not independently verify that it changed the tag.

### Type selection

The following exact 32-bit values select special handling:

| Type | Action |
|---|---|
| 1 | Require length 1; read and zero-extend one input byte into the effective destination. |
| 2 | Invoke F-816ea8e29abb, then postprocess the resulting object on success. |
| 3 | Invoke F-a44aa498dc69. |
| 5 | Require length 0; store 1 into the effective destination before success completion. |
| 6 | Invoke F-20c5febe7f6c. |
| 10, 258, 266 | Same conversion and postprocessing as type 2. |
| All other values | Generic-object handling. |

One decision interprets the type as signed, but this does not make high-bit-set values scalar special cases. Values from 2147483648 through 4294967295 reach generic-object handling.

For type 1 with a length other than 1, or type 5 with a length other than 0, the function calls F-4fc89ec41a6d with visible arguments 13 and 108. If the reporter returns, common failure completion follows.

The invalid-length type-1 path does not read the input byte. Type 5 performs no visible input-data read. Its valid empty-input case does not require the input address to identify readable data for this function’s own operations.

### Dependency-mediated conversions

F-a44aa498dc69, F-20c5febe7f6c, and F-816ea8e29abb receive:

1. Effective destination address.
2. Address of a local input cursor initialized from the input argument.
3. Original signed length.

The dependencies can modify the local cursor through the supplied address. This function does not expose an updated cursor as a return value or write it through a caller-provided input-pointer slot.

A zero conversion result selects common failure completion. Any nonzero result selects success, with additional processing for types 2, 10, 258, and 266.

For those four types, successful conversion is followed by:

1. Reading the resulting object address from the effective destination.
2. Reading its 32-bit word at offset +4.
3. Retaining only bit 8 of that word, using mask 256.
4. Combining that retained bit with the full requested type by bitwise OR.
5. Writing the resulting word back at offset +4.

Thus the resulting word is $(\text{old word} \mathbin{\&} 256) \mathbin{|} \text{type}$. No other old bits survive. Requested type bits are not cleared; types 258 and 266 already contain bit 8.

No validation of the resulting object address precedes this postprocessing. A nonzero conversion result alone is insufficient for ordinary continuation unless the destination contains an address suitable for these accesses.

### Generic-object selection

The function reads an object address from the effective destination.

If it is zero:

- F-f9450f0778b9 is called with the requested type.
- A zero result leads to the two-argument reporting call with 13 and 108, then common failure completion if reporting returns.
- A nonzero result is written into the effective destination.

If the existing object address is nonzero, the requested type is written into its word at offset +4.

There is no corresponding explicit type-field write for a newly created object. Its initialization is delegated to F-f9450f0778b9.

Only after this creation or reuse processing does the function examine the transfer-flag byte. Dependency effects or aliasing before that read can therefore affect which branch is selected.

### Generic-object direct attachment

A transfer flag that is nonzero **when examined** selects direct attachment.

The visible sequence is:

1. Read the object’s field at offset +8.
2. If that field is nonzero, call F-5990a26eaaa3 without explicit arguments.
3. Store the input address into object offset +8.
4. Store the original length into object offset +0.
5. Write zero to the transfer-flag byte.
6. Complete successfully.

The attachment-field condition is evaluated only within this nonzero-transfer-flag branch. A nonzero field at offset +8 by itself does not cause F-5990a26eaaa3 to be called.

No input-byte copying is visible on this path. A zero input address is stored without local rejection. A negative length is stored as its 32-bit representation without normalization or rejection.

F-5990a26eaaa3 is not visibly passed the previous attachment value or the object address. Its position before replacement does not establish that it releases the previous attachment, nor that it preserves the object or any global state. Ordinary continuation requires the subsequent writes to remain valid.

### Generic-object population

A zero transfer flag selects F-bbc440b3aefa, called with the selected object address, input address, and signed length.

This branch does not inspect the object’s offset-8 field for purposes of calling F-5990a26eaaa3. It does not make that call, even if the field is nonzero.

A nonzero population result leads to success. A zero result causes the following ordered actions:

1. Call F-4fc89ec41a6d with visible arguments 13, 108, 65, 0, and 0.
2. Call F-6c81b0b12feb with the selected object address.
3. Write zero into the effective destination.
4. Perform common failure completion.

This sequence applies to newly created and reused objects. The object argument retained for F-6c81b0b12feb is the selected object address; it is not obtained by rereading the effective destination after population or reporting.

### Success and failure completion

Built-in success normally returns 1.

There is one additional success write when a nonzero retained wrapper is present and the requested type is 5: wrapper offset +4 is set to zero. On the ordinary valid wrapper path, this overwrites the earlier value 1. In direct mode, the stored value remains 1 unless affected by aliasing or external effects.

Common failure completion:

1. Calls F-09da5253a1e1 with the retained wrapper address, or zero in direct mode.
2. If wrapper mode was selected, writes zero to the original outer destination.
3. Returns 0.

The cleanup call occurs even when its argument is zero. Clearing the outer destination occurs after that call returns.

Direct mode has no general destination-clearing step on failure. Generic population failure explicitly clears its effective destination before common cleanup; conversion failures and invalid scalar lengths have no equivalent direct-mode clearing operation in this function.

## Side effects

Visible effects can include publication of wrapper or object addresses, scalar stores, type-field changes, attachment replacement, length storage, transfer-flag clearing, effective-destination clearing, and outer-destination clearing. Dependencies can add further effects.

Processing is not transactional:

- Wrapper publication and adjustment can precede a later failure.
- A reused generic object’s type is changed before the transfer flag is examined.
- Population may partially change an object before returning zero.
- Cleanup dependencies may change state before subsequent explicit slot clearing.
- A conversion failure does not imply that its destination remained unchanged.

The direct-attachment path retains an input address and clears a flag. Interpreting those actions as transfer of ownership is inferred intent, not an established allocation or release contract. No dependency is assumed to preserve global state, preserve caller-reachable memory, or own or release an allocation.

Observable ordering here describes the supplied representation’s explicit operations and calls. It does not establish machine-level atomicity, concurrent visibility, or synchronization guarantees.

## Acceptance examples

These are conditional static criteria, not executed tests. Unless an example states otherwise, required memory is valid, dependencies return normally, and aliasing or dependency effects do not invalidate the stated conditions.

1. **Callback bypasses built-in validation.** A selected callback receives type 1 and length 0 despite the built-in length rule. If it returns 7, F-704ab9e25f00 returns 7 without built-in reporting or cleanup.

2. **Unsigned byte widening.** In direct mode, type 1 with length 1 and input byte 255 writes the 32-bit value 255 and returns 1.

3. **Invalid scalar length.** In direct mode, type 1 with length 2 reports using 13 and 108, then calls F-09da5253a1e1 with zero and returns 0. This path performs no explicit input-byte read or destination write.

4. **Empty-input representation.** Type 5 with length 0 writes 1 in direct mode. With a valid wrapper, it writes 1 into the payload and later overwrites that payload with zero before returning 1.

5. **Preserving only bit 8.** For type 2, suppose F-816ea8e29abb succeeds and the resulting object’s offset-4 word is 768. Postprocessing writes 258.

6. **Nonzero flag selects attachment.** On a generic-object path, a flag value of 2 when examined selects attachment. The function stores the input address and length, clears the flag, and does not call F-bbc440b3aefa.

7. **Existing attachment notification requires direct attachment.** If the transfer flag is nonzero when examined **and** the selected object’s offset-8 field is nonzero when read, F-5990a26eaaa3 is called before the replacement input address is stored.

8. **An existing attachment alone is insufficient.** If the transfer flag is zero when examined, a nonzero offset-8 field does not trigger F-5990a26eaaa3. The function calls F-bbc440b3aefa instead.

9. **Population failure ordering.** If F-bbc440b3aefa returns zero, five-argument reporting precedes F-6c81b0b12feb, which precedes effective-destination clearing. Common cleanup follows. In wrapper mode, outer-destination clearing follows common cleanup.

10. **High-bit type remains generic.** Type 2147483648 selects generic-object handling, not a scalar conversion.

11. **Direct attachment accepts an unchecked negative length.** With a generic type and a nonzero transfer flag, length −1 is stored as the 32-bit pattern 4294967295. This function performs no local length error report on that path.
