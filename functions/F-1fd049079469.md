# F-1fd049079469

## Purpose

F-1fd049079469 performs two ordered indirect operations on a primary object, then repeatedly consults a stateful dependency and performs two indirect operations for each nonzero result.

The established dispatch order differs between the two phases:

- Primary object: dispatch-table byte offset **0x94**, then **0x90**.
- Each nonzero advancement result: dispatch-table byte offset **0x90**, then **0x94**.

The second dispatch in each pair is resolved after the first call returns. In the repeated phase, the local object-pointer field is also read again. Consequently, the two repeated-phase operations need not target the same object: a dependency can have retained or exposed the address of that field, allowing the first operation to change its contents before the second lookup.

The function also invokes dependencies before and after the repeated phase. “Initialization,” “advancement,” “finalization,” and “traversal” are inferred role descriptions based on call placement. The supplied representation does not establish a container model, enumeration order, resource-management protocol, or semantic meaning for either dispatch offset.

### Result

The initialization dependency, finalization dependency, and indirect object operations have no return values consumed by this function. Only the advancement dependency’s result affects local control flow.

Observable results may include dependency calls and changes made by those dependencies to objects, exposed local state, globals, or other shared storage. Those effects are not defined by this function alone.

### Widths and layout

The representation establishes four-byte opaque fields and four-byte integer arithmetic units. It is consistent with a 32-bit address model, but does not independently establish the complete ABI.

Relevant layout facts are:

- An object’s leading field supplies its dispatch-table address.
- Dispatch entries are selected at byte offsets **0x90** and **0x94** from that address.
- Initialization receives the primary-object address advanced by ten four-byte units: **40 bytes**, or **0x28**.
- The local representation places two four-byte opaque fields before a pointer field, apparently also four bytes wide.

The 0x28 argument is an address, not a value loaded from that address. Neither dispatch offset is an element index or an offset directly into the object.

- The primary object’s leading dispatch-table field must be readable for both initial lookups.
- Each dispatch-table entry selected at the time of lookup must be readable and callable under the actual ABI.

## Behavior

### Local preparation

Before any dependency or indirect operation, the function stores local copies of the two opaque inputs and the initial object pointer.

These are shallow copies. The function does not directly copy the pointed-to object or perform an explicit retain, release, allocation, or deallocation.

The first opaque field becomes the base address passed to initialization, advancement, and finalization. Advancement additionally receives the address of the local object-pointer field. The supplied function does not establish the full state format or how far dependencies may access through these addresses.

### Initial operations on the primary object

The function first reads the primary object’s dispatch-table address and invokes the entry at byte offset **0x94**, explicitly supplying the primary object pointer.

After that call returns normally, it reads the primary object’s dispatch-table address again and invokes the entry at byte offset **0x90**, again explicitly supplying the primary object pointer.

The second lookup is not based on an established cached table address. If the first operation replaces the table address while leaving the object valid, the second operation resolves through the replacement.

Both calls precede initialization. Their return values do not control progression.

### Initialization

The function invokes **F-8ca21d3a8cca** with:

1. The address of the first local opaque field.
2. The primary-object interior address at byte offset **0x28**.

The function does not load the contents at offset 0x28 to form the second argument. It supplies the interior address itself.

Because the primary-object operations occur first, initialization can observe changes those operations made to relevant storage. No earlier snapshot is restored.

The initialization result is ignored. Progression depends on its returning normally, not on a checked success value.

### Advancement

The function invokes **F-b38a3aba0e18** with:

1. The same local-state base address.
2. The address of the local object-pointer field.

Its result is tested as a four-byte integer against zero:

- **Zero:** skip the repeated-phase operations and proceed to finalization.
- **Any nonzero value:** perform the two repeated-phase operations.

There is no positive-only condition. A result interpreted as negative still selects the body if its four-byte value is nonzero.

The source does not establish that advancement must overwrite the pointer. It may use the existing value, replace it, or interact with it in another way. The wrapper does not inspect whether the pointer changed.

### Operations following a nonzero result

For each nonzero advancement result:

1. The function reads the local object-pointer field, reads the designated object’s dispatch-table address, and invokes the entry at byte offset **0x90**.
2. After that call returns, the function reads the local object-pointer field again, reads the object designated at that time, and invokes the entry at byte offset **0x94**.

No explicit arguments appear on either repeated-phase indirect call. This differs from the primary-object calls, which explicitly supply the primary pointer. The actual ABI may involve implicit context, but that is not established here.

There is no direct assignment by this function to the local pointer field between the two calls. That does **not** establish pointer preservation. Advancement has received the field’s address; a dependency may retain it or expose it to other callees. The first operation can therefore affect the pointer used for the second lookup through such an alias.

Two independent changes can affect the second dispatch:

- The pointer field may designate a different object.
- The designated object’s dispatch-table address may have changed.

Thus, “two operations per nonzero result” is established; “two operations on the same object” requires an additional preservation condition.

After both operations return normally, advancement is called again with the same two local-storage addresses.

The wrapper imposes no iteration limit, duplicate suppression, requirement that the pointer change, or special treatment for a pointer equal to the primary object.

### Normal termination

When advancement returns zero, no repeated-phase dispatch occurs for that result. The function invokes **F-d0d3f100effc** with the local-state base address, then returns if that dependency returns normally.

Finalization is reached even if the first advancement result is zero, provided all preceding calls return normally.

The source establishes no alternate finalization route for failed indirect calls, abnormal dependency exits, or nontermination.

## Side effects

### Direct effects and delegated effects

The function directly writes its local input copies and reads object dispatch information. It contains no explicit object-field assignment, global assignment, allocation, deallocation, or reference-count operation.

That statement applies only to the wrapper’s direct actions. It does not constrain dependency effects. Unknown callees may change globals, shared objects, dispatch tables, exposed local state, ownership, or resource state.

### Exposed storage and ownership

Dependencies receive addresses into:

- Local state beginning with the first opaque field.
- The local object-pointer field, explicitly during advancement.
- Primary-object interior storage beginning at offset 0x28.

Changing the local pointer copy does not itself overwrite a caller-owned variable that held the original input pointer. Access through that pointer may nevertheless affect shared objects.

No ownership transfer is explicitly established. The source neither proves that dependencies acquire ownership nor proves that they refrain from releasing objects or retaining addresses.

The local state’s lifetime ends when this invocation ends. Passing its address does not extend that lifetime. Whether dependencies retain the address, and whether any retained use is valid, remain unresolved.

### Ordering and abnormal execution

The calls are sequential in the described order. The function introduces no explicit synchronization, concurrent work, retry, rollback, or recovery.

Zero is the only locally recognized stopping result. The wrapper does not distinguish exhaustion from a dependency-specific error represented by zero.

If an invoked operation does not return normally, subsequent calls are not guaranteed. The normal finalization call is not evidence of exception-safe or failure-safe cleanup.

## Acceptance examples

These examples are conditional consequences of static evidence, not runtime observations. Unless stated otherwise, they assume valid accesses, compatible calling conventions, and normal returns.

### Immediate termination

If the first advancement returns zero, the call order is:

1. Primary dispatch at 0x94.
2. Primary dispatch at 0x90.
3. F-8ca21d3a8cca.
4. F-b38a3aba0e18.
5. F-d0d3f100effc.

No repeated-phase dispatch occurs. The wrapper need not dereference the initial local object pointer.

### One supplied object with pointer preservation

If the first advancement leaves a valid object pointer and returns nonzero, the pointer field remains unchanged between the two body lookups, and the next advancement returns zero, both body operations resolve through that object: first 0x90, then 0x94.

The object’s table is still read separately for each operation. Pointer preservation alone does not imply table preservation.

Without the pointer-preservation condition, the second operation is guaranteed only to use the pointer present at its own lookup.

### Pointer replacement between operations

If advancement leaves a pointer to one valid object and returns nonzero, the first operation resolves offset 0x90 through that object.

If that operation changes the exposed local pointer field to another valid object before returning, the second operation resolves offset 0x94 through the replacement object. It does not use a cached copy of the first object pointer.

### Repeated object with pointer preservation

If successive nonzero advancements leave the same valid object pointer, and the pointer field is preserved between the two lookups in each body execution, that object receives both operations for every nonzero result. There is no deduplication.

If preservation is not assumed, repeated advancement results selecting the same object establish repeated first lookups through that object, but do not establish that every second lookup uses it.

### Negative advancement result

If advancement returns a negative four-byte integer and leaves a valid pointer, the body executes. An implementation that accepts only positive results would differ from the established condition.

### Dispatch-table replacement

If the primary 0x94 operation replaces the primary table with another valid table, the following primary 0x90 lookup uses the replacement.

Likewise, if a repeated-phase 0x90 operation changes its object’s table and the local pointer still designates that object, the following 0x94 lookup uses its then-current table.

### Invalid pointer before either lookup

If advancement returns nonzero but leaves an invalid pointer, the first lookup has an unmet validity precondition.

If the first operation instead makes the local pointer invalid before returning, the second lookup has an unmet validity precondition. Neither case has wrapper-level rejection or safe-skip behavior. The precise runtime failure is unresolved.

### Nontermination

If every advancement returns nonzero and every body operation returns normally, the function continues without an internal limit. Normal finalization is never reached.
