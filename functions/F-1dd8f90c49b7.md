# F-1dd8f90c49b7

## Purpose

F-1dd8f90c49b7 performs a bounded, first-match lookup over a fixed-size table. It compares an unsigned input against the unsigned 16-bit key at the start of each table record. On the first equal key, it returns the single byte at offset 2 within that record. If no key matches, it returns zero.

The lookup examines at most 205 records, in ascending record order. Records have a 16-byte stride. The supplied static evidence establishes the meaning of only the first three bytes of a record: a two-byte key followed by a one-byte result. It does not establish the purpose of the remaining 13 bytes.

A returned zero is ambiguous: it can mean either that no matching key was found or that the first matching record contained a zero result byte. No separate success indicator is exposed.

## Interface

### Input

The function receives one unsigned integer argument.

The recovered representation identifies this argument as a 32-bit unsigned value. Each table key is read as an unsigned 16-bit value and compared numerically with that argument. Consequently:

- Inputs from 0 through 65,535 can match a stored key.
- Inputs from 65,536 through 4,294,967,295 cannot match any stored key.
- The argument is not truncated to 16 bits before comparison.
- An out-of-range argument does not cause an early rejection; the lookup still attempts all 205 key reads.

The 32-bit interpretation follows the supplied recovered types. An independent ABI declaration was not provided.

### Output

The function returns one byte:

- The byte at record offset 2 for the first matching key; or
- Zero after all 205 keys have been examined without a match.

The recovered return type establishes an eight-bit result, not a signed numerical interpretation. A stored result byte with its high bit set is returned as that byte. How a caller subsequently extends or interprets it is outside this contract.

### Global table access

The table address is obtained through global state. The supplied representation accesses an address-bearing slot at byte offset 8 from a globally supplied root.

The table records have this layout:

| Byte offset within record | Width | Established use |
|---|---:|---|

There is no explicit table-length argument. The record count is fixed at 205 regardless of external allocation size or record contents.

## Behavior

### Search order and termination

The function begins at record index 0. It reads and compares that record’s key before deciding whether to continue.

If the key is unequal to the input, the function advances by one record and repeats. It visits indices 0 through 204, inclusive. Record index 205 is never examined.

The search ends immediately when a key matches. Later records are not read by the displayed lookup logic. Duplicate keys therefore resolve to the earliest matching record in traversal order, assuming a stable table.

If record 204 also fails to match, the function returns zero. Neither a zero key nor a zero result byte terminates an unsuccessful search early.

### Key comparison

Each key is a two-byte unsigned value. Its numerical value is compared with the full unsigned input; there is no masking, signed-key interpretation, or narrowing of the argument.

This distinction matters for inputs larger than 65,535. For example, an input of 65,536 does not match a stored key of zero. The function nevertheless performs the same bounded key search and returns zero if execution completes normally.

The byte order used to interpret the two-byte key is the target’s native byte order. The supplied fragment does not independently establish that byte order, so a portable byte-level fixture must specify it separately.

### Successful lookup

On equality, the function obtains the table address again through the displayed global access expression and reads one byte at the matching record’s offset 2. That byte is returned immediately.

This second table-address access is significant. The supplied representation does not retain a single table pointer for the entire lookup or even necessarily for both accesses associated with a match.

Under stable global state, the key and result come from the same record in the same table. If the table-address slot can change between the comparison and the result read, the result access can use a different table address while retaining the matching record index. The function contains no visible synchronization or consistency check.

### Unsuccessful lookup

If all 205 keys differ from the argument:

- Exactly 205 key accesses are reached in the displayed logic.
- No result-byte access is reached.
- The return value is zero.

The function does not distinguish an input outside the 16-bit key range from an ordinary absent key.

### Widths and address arithmetic

The traversal index is represented as an unsigned 32-bit value. During normal traversal it ranges only from 0 through 205, so neither incrementing it nor multiplying a visited index by the 16-byte record stride overflows that width.

The final record’s key begins at byte offset 3,264 from the table base. Its two-byte key occupies offsets 3,264 and 3,265. Its result occupies offset 3,266.

Accordingly, for a stable contiguous table:

- A full unsuccessful scan reaches bytes through offset 3,265.
- A match at the final record additionally reaches offset 3,266.
- The lookup does not access the final record’s remaining 13 bytes.

These are access extents, not evidence of an allocated object’s size. Although 205 complete 16-byte records occupy 3,280 bytes, the function itself does not validate that allocation extent.

Adding these offsets to an invalid or boundary-adjacent base address may still produce an invalid access. The bounded index does not establish the safety of the resulting addresses.
