# F-0463af715b9c

## Purpose

F-0463af715b9c advances a mutable position and returns a 32-bit word associated with the resulting position.

It first advances within the current object. If the advanced position fails a signed comparison against that object’s count-like field, it searches for another object through F-64f743a2929d. A candidate whose count-like field is nonzero becomes the current object, with position zero. Value retrieval then occurs through an indirect operation associated with the selected object.

If the search terminates without selecting an object, the function decrements the then-current position and returns zero.

“Position,” “count,” and “object index” describe inferred roles. The established behavior is the field access, arithmetic, comparison, mutation, and call sequence below. In particular, the function does not establish that positions are nonnegative, counts are positive, or the search index is monotonic.

## Behavior

### 1. Advance the current position

The function reads the current object’s count-like field at offset `0x0C`, then reads the position from state offset `0x04`.

It increments that position by one and stores the incremented value back to the state **before** deciding whether it can retrieve from the current object.

The branch condition is a signed, strict comparison:

- If the incremented position is less than the previously read count-like value, the function proceeds directly to indirect retrieval.
- Otherwise, it enters the candidate search.

There is no separate nonnegative-position check. A negative position can satisfy the comparison. Likewise, the count-like value is not validated as positive.

Equality with the count-like value enters the search; it does not retrieve from the current object.

Arithmetic at signed limits is not fully specified by the supplied static evidence. Ordinary-range behavior is established; overflow behavior is documented under Uncertainties.

### 2. Search for a replacement object

The search begins with a relative distance of one.

Each lookup invokes F-64f743a2929d with:

1. The explicit lookup-context argument.
2. The current object’s field at offset `0x20`, plus the current relative distance.

The base field is read from the object identified by the state at that point. It is not captured once at function entry.

The first lookup occurs unconditionally after entering the search. The search limit is not checked before that lookup. Consequently, the function may request an index greater than the stored limit on its first search attempt.

After each lookup returns, the relative distance is incremented before the result is handled.

#### Nonzero lookup result

A nonzero result is treated as an object address. The function reads its count-like field at offset `0x0C`.

- **Nonzero candidate count:** The candidate address is stored at state offset `0x00`. The position is then set to zero. The function proceeds immediately to indirect retrieval.
- **Zero candidate count:** The search terminates immediately. No further candidate lookup is attempted.

Candidate acceptance uses a zero/nonzero test, not a positive-value test. A negative count-like value therefore qualifies for selection.

The nonzero-result path does not check the search limit before accepting the candidate or stopping on an empty candidate.

#### Zero lookup result

A zero result does not itself terminate the search.

The function constructs the next prospective index using the now-incremented relative distance and a fresh read of the current object’s base field. It compares that index, as a signed value, with the state’s limit:

- If the prospective index is less than or equal to the limit, another lookup occurs.
- If it is greater than the limit, the search terminates.

The limit is reread when this continuation decision is made. Neither the current-object address, its base field, nor the limit is guaranteed to retain its entry value across a dependency call.

For a stable state and representable arithmetic, this produces successive lookup indices starting at base plus one. That description is conditional: dependency side effects could change subsequent indices or the stopping condition.

### 3. Handle unsuccessful search termination

Search terminates unsuccessfully in either of these cases:

- A nonzero lookup result identifies an object whose count-like field is zero.
- A zero lookup result is followed by a failed continuation comparison.

The function then reads the position currently stored in the state, subtracts one, stores the result, and returns zero.

This is a decrement of the **then-current** position, not restoration from a saved entry value. If dependencies leave the position unchanged, it cancels the initial increment. If they modify the position, that modification affects the final value.

The function does not explicitly restore the current-object address, base field, or search limit. It also does not undo dependency side effects.

### 4. Retrieve and return a word

Both successful paths converge on the same indirect retrieval behavior:

- The current-object path uses the advanced position.
- The replacement-object path first installs the candidate and sets position zero.

The function obtains the indirect target through the address-like word at current-object offset `0x08`, then reads the target at offset `0x40` in the referenced structure.

The recovered call operands include:

- The address of the current object’s field at offset `0x08`.
- The position read from the state.
- The indirect target itself.
- The fourth explicit argument.
- Two incoming machine-state values of unresolved meaning.

The exact calling convention requires independent confirmation. In particular, the extra recovered operands must not be promoted into a stable public API without further evidence.

The indirect operation’s result is treated as an address of a readable 32-bit word. The function dereferences that address and returns the word.

There is no visible null check on that returned address. No explicit state update or release occurs after the word is read.

## Acceptance examples

These examples are conditional static acceptance criteria, not runtime observations. Unless stated otherwise, assume valid memory, representable arithmetic, and dependencies that do not modify the state or relevant object fields.

### Advance within the current object

Given position `2` and count `5`:

- Position becomes `3`.
- No lookup occurs.
- D-01 is invoked for position `3`.
- If its returned address contains `0x12345678`, the function returns that word.

### Equality enters search

Given position `4` and count `5`:

- Position first becomes `5`.
- Retrieval from the old object does not occur merely because the position equals its count.
- The first lookup uses the old object’s base index plus one.

### First lookup is not limit-gated

Given base index `10`, limit `10`, and an initial advance requiring search:

- The function still performs a lookup for index `11`.
- If that lookup returns zero, the continuation comparison considers index `12`.
- Because `12` exceeds `10`, the function stops, decrements the position, and returns zero.

### Missing candidate followed by an accepted candidate

Given base index `20` and limit `22`:

- A zero result for index `21` allows a lookup for index `22`.
- If index `22` returns an object with a nonzero count, that object becomes current and position becomes zero.
- D-01 is then invoked through the selected object.

### Empty candidate stops the search

If the first lookup returns a valid object whose count is zero:

- No second lookup occurs, even if the limit permits more indices.
- The candidate is not explicitly installed.
- The then-current position is decremented, and zero is returned.

### Negative candidate count is accepted

If a lookup returns a valid object whose count is `-1`:

- The candidate passes the nonzero test.
- It becomes current, position becomes zero, and retrieval proceeds.
- The function does not reapply the initial signed position-versus-count comparison after selection.

### Failure decrement is not transactional rollback

If a lookup changes the state position to `40` before returning a result that terminates search unsuccessfully:

- The final position becomes `39`.
- The function does not restore the entry position.

### Retrieved zero remains a successful retrieval path

If D-01 returns a valid address containing zero:

- The function returns zero after dereferencing that address.
- Return-value equality alone cannot distinguish this path from search failure.
