# F-c19e8ee32570

## Purpose

F-c19e8ee32570 conditionally replaces a destination’s active record range with records obtained from a source, then returns the original destination object address.

The supplied static evidence is consistent with assignment between contiguous containers of 24-byte records. It includes a self-assignment bypass, a storage-replacement path, and two paths that reuse existing storage. That container interpretation is **inferred intent**, not an established contract of the dependencies.

An important observable detail prevents describing this simply as conventional container assignment: when existing destination storage is reused and the destination’s reported length is at least the source’s reported length, the routine writes both the destination’s second and third words to the resulting active-range endpoint. If the third word represents storage capacity, this path discards the previously represented spare capacity. By contrast, the other storage-reuse path returns without directly writing the third word.

## Interface

### Inputs

The routine accepts four arguments:

| Argument | Established role |
|---|---|
| Destination object address | Address of a writable object whose first three 32-bit words are accessed on applicable paths. Also the returned address. |
| Source object address | Address of an object whose first two 32-bit words are read on applicable paths and which is passed to a query dependency. |
| First auxiliary value | Unsigned 32-bit value copied into temporary storage on non-self-assignment paths. It does not determine any subsequent call argument, branch, object write, or returned value in the supplied routine. |
| Second auxiliary value | Unsigned 32-bit value with the same observable limitation as the first auxiliary value. |

The two auxiliary values are overwritten before the temporary storage containing them is used to select an allocation size. Their initial values therefore have no established effect on externally visible behavior.

### Object and record layout

The visible operations use this object layout:

| Byte offset | Width | Visible use |
|---|---:|---|
| 0 | 32 bits | Base address of a record range. |
| 4 | 32 bits | Endpoint of an active record range. |
| 8 | 32 bits | Updated endpoint on some paths; consistent with a storage-limit field. |

Record-address calculations use a stride of **24 bytes**. This routine does not expose the internal layout of a record.

The supplied representation uses 32-bit integer words for both stored addresses and integer calculations. It does not establish a portable interface for wider pointers.

For description below:

- **Length query** means F-beaa3d5aacef.
- **Capacity query** means F-f4be0af7d6d1.

These names describe inferred roles. The observable contract is the sequence of dependency calls and use of their returned values; their definitions are not supplied.

### Output

Every explicit normal return produces the original destination object address. There is no explicit status or error return.

### Preconditions

For normal completion on a non-self-assignment path, the caller must provide objects, ranges, and dependency behavior compatible with the operations described below. In particular:

- Accessed object words must be readable or writable as required.
- Ranges passed to record-processing dependencies must satisfy those dependencies’ requirements.
- Any storage returned for use as a record range must be usable by the subsequent dependency.
- The empty endpoint-walking loops must be able to reach their compared endpoints.
- Address and size calculations must produce usable results.

No visible validation enforces these conditions. Null objects, overlapping objects, inconsistent endpoints, allocation failure, and arithmetic overflow are not handled by explicit local error branches.

## Behavior

### 1. Identical object addresses

The routine first compares the source and destination object addresses.

If they are identical, it returns the destination address immediately. It performs no dependency calls and no object-field reads or writes.

This is address identity, not a comparison of record contents. Distinct objects referring to the same storage do not take this bypass.

### 2. Initial classification

For distinct object addresses, the routine:

1. Calls the length query on the source.
2. Calls the capacity query on the destination.
3. Compares the two returned values as unsigned 32-bit quantities.

If the destination capacity-query result is less than the source length-query result, it takes the storage-replacement path. Otherwise, it takes a storage-reuse path.

These initial query results are not uniformly reused. Later decisions and endpoint calculations make fresh calls. A dependency that changes an object or returns different values across calls can therefore affect subsequent behavior.

### 3. Storage replacement

This path begins by querying the source length again, followed by the destination length.

The requested record count is the unsigned maximum of:

- The newly queried source length.
- The newly queried destination length plus 32.
- The newly queried destination length plus its value shifted right by one bit, plus its value shifted right by three bits.

The shifts correspond to unsigned division by two and eight, rounding down. All additions in this selection operate at 32-bit unsigned width. They can wrap before the comparisons select a result.

The routine then performs the following sequence:

1. Calls F-871e64ddc6de with the selected count multiplied by 24 and a second argument of zero.
2. Calls F-6375e6fe2adb with the source’s current base word, the source’s current active-end word, the returned allocation address, and the destination object address.
3. Reads and retains the destination’s current base word.
4. Advances a cursor from that retained base by 24 bytes repeatedly until it equals the destination’s active-end word.
5. Calls the capacity query on the destination.
6. Calls F-ff1bdc376dcd with the retained base address, that capacity-query result, and zero.
7. Writes the returned allocation address into the destination’s base word.
8. Calls the length query on the source again.
9. Writes the destination’s active-end word using the destination’s then-current base word plus 24 times that latest source length.
10. Writes the destination’s third word using the destination’s then-current base word plus 24 times the selected allocation count.

The endpoint-walking loop has an empty body. There is no visible per-record cleanup call, destructor call, or payload access in it. Its operational significance is iteration and endpoint comparison, including possible failure to terminate for incompatible endpoints.

The order around F-6375e6fe2adb matters: the old destination base is read **after** that dependency returns. The routine does not establish that the dependency leaves destination metadata unchanged. Similarly, the capacity query occurs before F-ff1bdc376dcd, and the new base is installed only after F-ff1bdc376dcd returns.

There is no explicit check of the allocation result before it is passed to F-6375e6fe2adb.

### 4. Reuse when the destination reports fewer active records

If the initial capacity comparison permits reuse, the routine next calls the destination length query and then the source length query. It compares those results as unsigned 32-bit quantities.

When the destination result is smaller, it:

1. Queries the destination length again and retains that result as the prefix record count.
2. Calls F-caa7e3389c1d for a source prefix beginning at the current source base and ending at that base plus 24 times the retained prefix count, with the current destination base as the output address.
3. Queries the source length again.
4. Writes the destination’s active-end word using its current base plus 24 times that latest source length.
5. Calls F-6375e6fe2adb for the source suffix, from the current source base plus 24 times the retained prefix count to the current source active end, targeting the current destination base plus the same byte offset. The destination object address is also passed.
6. Returns the destination address immediately.

The active-end write occurs **before** the suffix-processing call. The routine therefore exposes an updated active endpoint to that dependency.

There is no direct write to the destination’s third word on this path. Its final value is not guaranteed to be unchanged: dependencies receive addresses through which they may affect state, and their contracts are unavailable.

The prefix count used for the suffix offset is the repeated destination-length result, not necessarily the value that caused this branch to be selected.

### 5. Reuse when the destination reports at least as many active records

If the fresh destination length is not less than the fresh source length, the routine:

1. Calls F-caa7e3389c1d with the source’s current base, its current active end, and the destination’s current base.
2. Uses the returned address as a cursor.
3. Advances that cursor by 24 bytes until it equals the destination’s active-end word.
4. Queries the source length again.
5. Computes an endpoint from the destination’s then-current base plus 24 times that latest length.
6. Writes that endpoint to the destination’s active-end word.
7. Writes the same computed endpoint to the destination’s third word.
8. Returns the destination address.

The loop again has no visible payload operation or cleanup call. The returned address from F-caa7e3389c1d determines its starting point; it is not recomputed from the source length.

Both equal-length and shorter-source cases take this path. A distinct empty source also takes this path under conventional nonnegative length and capacity results, including when the destination is empty.

## Side effects

### Direct object changes

The routine directly writes only destination metadata:

- Storage replacement: base, active end, then third word.
- Reuse with a shorter reported destination length: active end only.
- Reuse with an equal or longer reported destination length: active end, then third word.
- Identical addresses: no writes.

These statements concern direct writes by F-c19e8ee32570. They do not constrain dependency effects or writes caused by overlapping object storage.

### Record processing and memory ownership

The routine delegates record processing to F-caa7e3389c1d and F-6375e6fe2adb. It does not visibly copy individual record bytes itself.

The storage-replacement path obtains an address from F-871e64ddc6de and later passes an old destination address to F-ff1bdc376dcd. Allocation and release are plausible interpretations, but their exact ownership contracts are unknown. In particular, the supplied evidence does not establish:

- Whether the allocation-like call can return a failure value.
- Whether either record-processing dependency acquires or releases resources.
- Whether F-ff1bdc376dcd releases storage, and what units its second argument uses.
- Whether a dependency changes destination metadata or unrelated global state.
- Whether any dependency preserves source state.

No rollback, exception handler, or explicit error recovery appears in the routine. Effects completed before a dependency fails or fails to return are not locally undone by any visible mechanism.

### Read and write ordering limits

The ordering above distinguishes dependency calls and intervening metadata accesses. Within an individual call, the relative evaluation order of separate argument expressions is not established by the supplied representation.

Object fields are reread at several points rather than captured once at entry. Consequently, a contract that assumes immutable source metadata or unchanged destination metadata across dependency calls would be stronger than the evidence.

## Acceptance examples

These are conditional static acceptance examples, not reported test executions. Unless stated otherwise, assume query dependencies report conventional stable record counts, record-processing dependencies behave consistently with their supplied ranges, they preserve relevant metadata, and all arithmetic and storage accesses are valid.

### Identical addresses

Given identical source and destination object addresses:

- The result is that same address.
- No dependency is called.
- No metadata or record storage is accessed by this routine.

### Storage replacement with the additive minimum dominant

Given a destination length of 8, destination capacity of 10, and source length of 12:

- Replacement is selected.
- The two growth candidates are 40 and 13 records.
- The selected count is 40.
- F-871e64ddc6de receives 960 bytes and zero.
- On normal completion, the active end is 288 bytes after the installed base, and the third word is 960 bytes after that base.

### Storage replacement with the source requirement dominant

Given destination length and capacity both 8, and source length 100:

- Replacement is selected.
- The source requirement exceeds both growth candidates.
- The selected count is 100, requesting 2,400 bytes.
- The final active end and third word both designate 2,400 bytes after the installed base.

### Reuse with a growing active range

Given destination length 2, destination capacity 8, and source length 5:

- No allocation-like call occurs.
- F-caa7e3389c1d receives a 48-byte source prefix.
- The active-end word is written to destination base plus 120 before F-6375e6fe2adb receives the remaining source suffix.
- This routine does not directly write the third word.

### Reuse with a shrinking active range

Given destination length 5, capacity 8, and source length 2, and assuming F-caa7e3389c1d returns destination base plus 48:

- The endpoint walk advances through the remaining 72 bytes in three 24-byte steps.
- No per-record cleanup call occurs in that walk.
- Both active end and third word are written to destination base plus 48.

### Distinct empty source

Given a zero-length source and a valid destination:

- The equal-or-longer destination reuse path is selected under stable conventional queries.
- F-caa7e3389c1d is still called with an empty source interval.
- If it returns the destination base and the walk terminates, both endpoint fields are ultimately written to that base.

### Wrapped allocation-byte calculation

If the selected unsigned count is 178,956,971, multiplying it by 24 at 32-bit unsigned width yields 8. The visible allocation-like call therefore receives 8, not the mathematical product 4,294,967,304.

This example establishes arithmetic behavior, not successful or safe execution afterward.

## Uncertainties

The following are **documented_only**:

- Exact semantics and side effects of every dependency.
- Record contents, construction rules, destruction rules, and overlap support.
- Whether the third word is formally a capacity endpoint.
- Allocation failure behavior and nonlocal error propagation.
- Validity of null addresses or partially overlapping objects.
- Stability of query results across calls.
- Effects of concurrent mutation.
- The intended machine-level treatment of address calculations represented through signed 32-bit intermediates. The evidence does not justify treating every such expression as defined, portable signed arithmetic.
- Whether compiler optimization removes the empty endpoint walks in an executable build.

The unsigned count-selection arithmetic and allocation-size multiplication are explicitly 32-bit operations. Other address calculations must not be assumed to offer overflow protection merely because they use a 24-byte stride.

## Evidence

The established behavior above derives solely from the supplied static function body and opaque dependency mapping.

Direct evidence includes address-identity bypass, dependency call order, unsigned comparisons and growth calculations, 24-byte address stepping, three destination metadata offsets, branch-specific writes, and normal return values.

Container assignment, length and capacity terminology, record construction or assignment, and allocation or release roles are inferred interpretations. They are not independently established dependency contracts.

No runtime tests have been performed.
