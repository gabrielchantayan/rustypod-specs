# F-96dd39e1380e

## Purpose

F-96dd39e1380e performs a selector-controlled update of one byte or returns a fixed result without accessing the supplied storage.

Two selector values request a write: 0 selects byte value 2, and 15 selects byte value 7. Their return results differ. Every other selector produces return value 14 without an explicit access through the base input.

The evidence establishes these numeric effects, not their application meaning. It does not establish that the byte represents an object state, that 14 denotes an error, or that returning the base value transfers an object to the caller.

This contract describes normal completion and identifies the conditions required for it. Invalid address formation and failed memory accesses have no established recovery behavior.

## Interface

### Inputs and result

The interface has two integer inputs and one integer result.

| Item | Established role | Representation limits |
|---|---|---|
| Base input | Determines the location of the selected byte write; supplies the result for selector 15 | Declared in the same signed integer category as the result; exact width and address interpretation are not independently established |
| Selector input | Selects the write and return outcome | Integer comparisons distinguish 0 and 15 from all other values |
| Result | Reports 0, 14, or the unchanged base input | Same declared integer type as the base input |

The interface does not explicitly accept a typed storage object, an object length, or an ownership token. Treating the base input as a usable address therefore requires an execution-environment convention beyond its integer type.

No narrowing of the selector to one byte is established. Selection depends on the complete supplied integer value, not merely its low bits.

The constants 0, 2, 7, 14, 15, and 40 are exactly representable in the declared integer category. Their presence does not determine the type’s precise width. In particular, the evidence does not independently establish a 32-bit or 64-bit interface.

### Storage location

For either writing selector, the destination is one byte at displacement 40 decimal, equivalent to hexadecimal 28, from the address represented by the base input.

| Storage property | Contract |
|---|---|
| Displacement | 40 bytes from the base |
| Access extent | One byte |
| Possible stored values | 2 or 7 |
| Required previous value | None |
| Required containing layout | Not established |

The displacement is not multiplied by a structure-element size. The result for selector 15 remains the base input, not the displaced destination.

Normal completion on a writing path requires valid address arithmetic and a writable destination byte. The evidence establishes no larger object-size requirement, allocation provenance, or object-layout guarantee.

## Behavior

### Outcome selection

The complete normal-completion relationship is:

| Selector | Destination effect | Result |
|---|---|---|
| 0 | Store byte value 2 at displacement 40 | 0 |
| 15 | Store byte value 7 at displacement 40 | Original base input |
| Every other integer value | No explicit access through the base input | 14 |

The destination’s previous contents do not influence selection, the stored value, or the result. No destination read is established before the write.

Selector 1 belongs to the fallback case. A separate inequality involving 1 appears in the supplied evidence, but it does not create a fourth outcome: an ordinary integer equal to 15 is necessarily unequal to 1.

Negative selector values and positive values other than 15 also use the fallback outcome, except that zero has its designated write outcome. There is no established range interpretation, bitmask interpretation, or selector normalization.

### Observable ordering

A selected byte write occurs before normal return. The result is not returned first with a deferred update.

For selector 15, the returned integer comes from the base input rather than from a read of the destination. Updating the destination does not change which integer the function returns.

No explicit destination read precedes or follows either write. No other externally visible data-memory access is established by the function body. This statement concerns the represented behavior, not incidental instruction fetches, calling-convention storage, or implementation-specific machine activity.

When neither writing selector applies, destination address formation is not required by the established path. The fallback outcome therefore does not require the base input to designate writable storage.

### Arithmetic and abnormal completion

The displacement is added to an integer base before the resulting value is used as a byte address. Whether that addition is valid depends on the integer range and the target’s address-conversion rules.

No portable wraparound guarantee is established. A base near the upper limit of its integer type must not be assumed to wrap to a small destination address. A negative base must not be assumed either invalid or usable without the target’s address conventions.

The body contains no explicit destination validation or recovery operation. If address formation or the write cannot complete validly, the evidence does not establish a normal result, replacement status, rollback, or retry.

Consequently, the result table applies to writing cases only when their memory operation completes normally. It must not be interpreted as promising that selector 0 always returns successfully regardless of the base input.

## Side effects

For valid ordinary writable memory, either writing outcome changes only the designated byte. No write to adjacent bytes or replacement of a larger field is expressed.

The write remains part of the selected behavior when the byte already contains the requested value. There is no established comparison-and-skip mechanism. Identical final byte contents therefore do not imply that no write occurred.

No allocation, release, ownership transfer, retained reference, callback, or explicit global-variable access appears in the supplied body. The function does not establish responsibility for creating or destroying the storage. The caller or execution environment must provide sufficient lifetime and access permission for a selected write.

The absence of an explicit global reference does not prevent the destination from aliasing globally accessible storage. Effects depend on what address the caller supplies; no specific global object is identified.

No synchronization operation, atomic-access contract, or cross-thread ordering guarantee is established. A one-byte access alone is insufficient evidence for a portable concurrency guarantee.

For memory-mapped devices or other special storage, a byte write may have effects beyond changing an ordinary memory cell. Those effects are **documented_only** and are not defined here.

## Acceptance examples

These are conditional criteria derived from static evidence, not executed tests. Unless stated otherwise, writing examples assume ordinary writable memory, valid address formation, a valid call, and no interfering execution.

### Zero selects the first byte value

Given a valid base and any previous destination-byte value, selector 0 leaves the byte at displacement 40 containing 2 and returns 0.

Neighboring ordinary-memory bytes remain unchanged by this function. The previous destination value does not affect the result.

### Fifteen preserves the base as the result

Given a base representing valid writable storage at displacement 40, selector 15 leaves that byte containing 7 and returns the original base integer.

The returned integer is not increased by 40. It is also not the stored byte value.

### One has no separate update behavior

Given selector 1 and any base integer admitted by the calling interface, normal execution returns 14 without an explicit access through that base.

The appearance of a comparison involving 1 does not justify expecting a special write or a distinct result.

### Larger selectors are not reduced to a byte

Given selector 256, the result is 14 and no displaced write occurs.

Although 256 has a zero low byte in an eight-bit-byte representation, that observation does not select the zero case. The full integer selector controls the outcome. Likewise, selector −1 produces the fallback result.

### An unusable destination does not affect fallback selection

Given a base whose displaced address would not be writable, a selector other than 0 or 15 still selects return value 14 without the established path attempting that write.

This criterion does not certify the base for a later writing call. It also assumes that passing the integer itself satisfies the calling convention.

### Existing matching contents do not eliminate the write

Given a destination already containing 7, selector 15 still selects a byte write of 7 and returns the base input.

For ordinary memory, the final contents match the initial contents. For special storage, whether repeating the write has additional consequences remains outside the established contract.

### Repeated calls replace the designated byte

Given a stable valid destination, a selector-0 call followed by a selector-15 call returns 0 and then the base input. After both calls, the designated byte contains 7.

Reversing the call order leaves the byte containing 2. No hidden counter or accumulated state is required by the evidence.

### Invalid writing calls have no promised fallback

Given selector 0 or 15 and an invalid displaced destination, this contract does not require return value 14.

The fallback result belongs to selector selection, not to an established memory-access error handler.

A selector-controlled state transition is a plausible interpretation, but it is inferred intent rather than an additional acceptance requirement.

## Evidence

Static evidence establishes two selector-dependent one-byte writes at displacement 40, using values 2 and 7. It also establishes the three result outcomes: 0, the original base input, and 14.

The fallback classification follows from integer equality and inequality. No explicit calls, destination reads, allocation operations, or recovery handlers appear.

The interface supplies integer type information but does not independently identify the target ABI or address model. Those omissions constrain claims about width, overflow, and pointer interpretation.

No runtime tests, execution traces, or observed memory results have been performed. The acceptance examples specify behavior under their stated preconditions; they are not reports of successful execution.
