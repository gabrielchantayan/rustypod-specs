# F-d00013ba7e83

## Purpose

F-d00013ba7e83 is a globally controlled state machine with two observable memory-processing operations:

- A transfer phase that calls F-870c4fcf7295 four times and performs four one-byte transfers.
- A transformation phase that performs three successive writes to one computed byte address, using additional computed byte reads.

Its only explicit normal return is the 32-bit value zero.

**Established static evidence:** global values control dispatch, arithmetic, address selection, and progression. Their values are not supplied. Consequently, neither a particular state sequence nor termination is established. Execution need not capture the arguments, perform a transfer, or transform a byte before returning.

**Inferred intent:** the routine appears to combine a four-position byte transfer with state-driven byte transformation. No higher-level algorithm or data format is established.

This contract describes visible operations and their ordering without assuming stable globals, independent memory regions, or undocumented dependency behavior. Unresolved matters are **documented_only**.

## Behavior

### Numeric and memory model

The representation distinguishes one-byte memory elements, byte-sized character intermediates, signed 16-bit values, and signed and unsigned 32-bit arithmetic.

Important distinctions are:

- Masking with hexadecimal FFFF retains the low 16 bits as a nonnegative quantity.
- Conversion to signed 16-bit followed by extension can instead produce a negative value. Low bits FFFF correspond to −1 under the represented signed interpretation.
- Some products are formed before masking. A later mask does not establish that preceding signed arithmetic was overflow-free.
- Some expressions use signed remainder with divisor 256. Negative operands prevent unconditional replacement by an unsigned low-byte mask.
- Signed right shifts and signed overflow require target-level interpretation.
- Plain character signedness is not supplied.

Each explicit destination or target store writes one byte. Under ordinary low-eight-bit truncation, stored values are interpreted modulo 256. This does not make all intermediate arithmetic unsigned or fully specified.

The routine exposes no contiguous destination layout. Each transfer destination depends on an auxiliary dependency result.

### Initialization and dispatch

The routine captures a working multiplier from a global during initialization. It initializes its saved scalar state, counters, offsets, and pointers to zero, including the active transformation pointer and saved byte-region pointer. The input arguments are not initially installed as active state.

The initial dispatch value is read from another global.

At every dispatch, the routine reads:

1. A stride-related global.
2. An address-control global.
3. The selector-offset global used with the current dispatch value.

The first two samples are retained for uses within the selected branch. Subsequent reads of the same global need not return the same value.

Selectors 0 through 7 have explicit branches. Every other selector enters the transfer phase. There is no explicit iteration limit.

### Transfer phase

For this section, the following labels describe distinct quantities, not source identifiers:

- **Working scale:** the multiplier cached during initialization.
- **Dispatch stride:** the stride-related value cached at the current dispatch.
- **Separate doubled stride:** twice a fresh read of the stride-related global near transfer entry.
- **Transfer position:** a position computed before the first dependency call.
- **Secondary input:** another computed integer retained for the later dependency calls.

The transfer-position and secondary-input calculations use saved state, complements, masks, and additional global reads. Their complete address interpretation and range are unresolved.

The separate doubled stride is not unconditionally twice the dispatch stride. The routine samples the underlying global separately.

The four stages are:

| Stage | First explicit dependency input | Transfer source |
|---|---|---|
| First | Working scale × transfer position | Saved region, offset 0 |
| Second | Working scale × (transfer position + dispatch stride) | Saved region, first saved offset |
| Third | Working scale × (transfer position + separate doubled stride) | Saved region, second saved offset |
| Fourth | Working scale × (transfer position + 3 × dispatch stride) | Saved region, third saved offset |

After argument capture, the three saved offsets are respectively 13, 76, and 25. Before capture, they and the saved pointer are zero.

The first dependency call shows one explicit argument. Each later call also receives the same retained secondary input. All four calls provide an auxiliary result used in the corresponding destination address:

**selected destination base + working scale × dispatch stride × auxiliary result**

This relationship does not establish the auxiliary result’s meaning, signedness, range, or true interface width.

Each call completes before its corresponding explicit source read and store. Each store completes before the next call. Source bytes are therefore not collected into an entry-time snapshot.

#### Transfer global-read ordering

The following distinctions are established:

1. The dispatch stride and working scale remain cached for all four destination calculations.
2. The separate doubled stride is captured before the first dependency call and is reused for the third call and later arithmetic.
3. After the third store, a progression-mask global is read and combined with saved arithmetic state.
4. The fourth dependency call occurs after that mask read.
5. After the fourth call returns, a progression multiplier is read.
6. The fourth source byte is then read and its destination byte stored.
7. After the fourth store, further progression globals are read during the remaining progression calculation.
8. The next-dispatch global is read after that calculation.

The progression multiplier sampled between the fourth call and fourth store is cached and used in both subsequent progression calculations. One progression quantity incorporates the transfer position advanced by four dispatch strides. The other incorporates the previously captured mask combination, the separately doubled stride, additional post-store global reads, and scaling by 65,536 followed by a signed right shift of 16.

No finer order is established between global operands within a single expression.

These timings are observable under dependency mutation or destination/global aliasing. In particular:

- A fourth-call mutation can affect the newly read progression multiplier, but cannot retroactively alter the cached progression mask.
- A fourth store that overwrites the multiplier’s global storage does not replace the multiplier already cached for progression.
- A fourth store can affect progression globals read afterward.
- Changes to stride storage during dependency calls do not replace either cached stride quantity.

The phase resets a working counter, installs the saved byte-region address as the transformation base, and resumes dispatch. It does not itself return.

### Transformation phase

Selector 0 computes a target at:

**active transformation base + working scale × current transformation position**

The counter updated at the end of this branch is distinct from that position. The branch does not itself advance the transformation position.

Before the first target write, the routine computes three neighbor-related quantities using global factors, offsets relative to the current position, remainder by 256, and low-16-bit masking. A doubled-stride quantity is also obtained from a fresh stride-global read. These are not all derived from a single global snapshot.

The target then receives three ordered one-byte stores:

1. The original target byte is converted into a character-sized intermediate using multiplication by −33 and addition of −69. That intermediate multiplied by 31 is stored.
2. The intermediate is combined with reads through a first computed neighbor address and global-dependent arithmetic and bitwise operations. The updated intermediate multiplied by 31 is stored.
3. The updated intermediate is combined with reads through two further computed neighbor addresses and additional factors. The final byte is stored.

Under ordinary byte truncation, the first store is equivalent to adding 165 modulo 256 to the original target byte. This equivalence describes only the first write.

The first neighbor address appears in multiple read operands during the second assignment. Those operands are not guaranteed to constitute a single cached byte read. If that address aliases the target, the reads follow the first store.

The later neighbor reads follow the second store. Aliasing can therefore make them observe the second stored value. The representation does not establish left-to-right ordering among independent reads within one expression.

#### Transformation global-read ordering

The address-control global has three distinct samples:

- Its dispatch-time sample contributes to the first neighbor-address calculation.
- A new sample is captured after the first target store and before the second store. It is retained for one of the final assignment’s neighbor addresses.
- Another sample is read after the second store for the other neighbor-address calculation.

These samples cannot be merged merely because they refer to the same global storage.

After the second store, the routine also captures a counter-update multiplier. It subsequently samples a byte-sized transformation factor before the final assignment. Other factors appearing in address and byte expressions remain visible reads rather than assumed immutable constants.

After the third store:

- Another counter-update factor is read.
- The counter is updated using the previously cached multiplier, this newly read factor, addition of hexadecimal 8505, and retention of the low 16 bits.
- The next-dispatch global is read.
- The masked counter value becomes the current working value, and dispatch resumes.

Thus a second-store overwrite of global storage can affect samples taken afterward. A third-store overwrite cannot replace the counter-update multiplier already cached after the second store, but can affect the counter-update factor or next-dispatch value read afterward.
