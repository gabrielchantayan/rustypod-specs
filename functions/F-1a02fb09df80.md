# F-1a02fb09df80

## Purpose

F-1a02fb09df80 attempts to recognize a 26-byte header beginning with the four bytes `VBRI`, extract its numeric fields into a caller-supplied context, and transfer a following variable-length region into that context.

Recognition and completion are distinct outcomes:

- **0:** A complete header was obtained, but its four-byte signature did not match.
- **1:** The signature matched, a size-dependent gate passed, and the subsequent positioning and transfer operations reported the required results.
- **2:** The initial positioning or header transfer failed, or a recognized header did not lead to a completed subsequent transfer.

A recognized header causes context updates before the function knows whether the subsequent transfer will succeed. Return value 2 therefore does not imply unchanged state.

The apparent purpose is to load variable-bitrate indexing information. That interpretation is inferred from the signature and field relationships; the established contract is the byte processing and state changes described below.

## Behavior

### 1. Initial positioning

The function obtains an indirect callback from interface-table byte offset `+0x14` of the interface object referenced by context `+0x04`.

It invokes that callback with five arguments:

1. The interface object.
2. The selected callback address itself.
3. The context base-position value plus `0x24`.
4. Zero.
5. Zero.

Only a callback result of zero permits further processing. Any other result produces return value 2 without a header transfer.

The addition uses a 32-bit position value; no widened addition or overflow rejection is visible. Inputs requiring position overflow handling therefore have no validated safe behavior in this evidence.

### 2. Header transfer and signature check

After successful initial positioning, the function obtains the transfer callback from interface-table byte offset `+0x10`, using the interface reference then present in context `+0x04`.

It requests:

- Destination: temporary storage.
- Count: 26.
- Final argument: 2.

The returned value must equal 26 exactly. A short result, a negative result, or any other unequal result causes return value 2. There is no retry or completion loop.

For an exact-length result, the first four bytes must be, in order, `V`, `B`, `R`, and `I`. The comparison is byte-exact; there is no case folding or alternate-signature handling.

A signature mismatch returns 0. None of the direct context updates described below occurs on this path. The preceding callbacks may nevertheless already have changed external or context state.

### 3. Recognition-state updates

For a matching signature, the function performs these direct writes in order:

1. Store the one-byte value 1 at context `+0x5d`.
2. Store the one-byte value 1 at context `+0x5c`.
3. Store the one-byte value 1 at context `+0x614`.
4. Read the current 32-bit base-position value from context `+0x20`.
5. Store that value at context `+0x618`.
6. Decode header bytes 10–13 and store the resulting 32-bit unsigned value at context `+0x600`.
7. Decode header bytes 14–17 and store the resulting 32-bit unsigned value at context `+0x58`.

The base-position read in this phase is separate from the read used for initial positioning. If an earlier callback changed context `+0x20`, the saved value and subsequent position use the newer value.

These updates precede the size gate and the second positioning operation. They are not rolled back on later failure.

### 5. Remaining header fields

After that dependency returns, the function decodes the four 16-bit big-endian fields and writes zero-extended 32-bit values in this order:

1. Header bytes 18–19 to context `+0x604`.
2. Header bytes 20–21 to context `+0x60c`.
3. Header bytes 22–23 to context `+0x608`.
4. Header bytes 24–25 to context `+0x610`.

The subsequent transfer count comes from multiplying the decoded values at header offsets 18 and 22. It is calculated from the decoded temporary header bytes, not by rereading the two context fields after publication.

### 6. Transfer-size gate

Both factors are unsigned 16-bit values, each ranging from 0 through 65,535. Their product fits in 32 unsigned bits, with maximum value 4,294,836,225.

The resulting 32-bit pattern is then tested as a signed 32-bit value against `0x5a1`, or 1,441. Processing continues only when that signed value is less than 1,441.

Consequently:

- Products from 0 through 1,440 pass.
- Products from 1,441 through 2,147,483,647 fail.
- Products from 2,147,483,648 through 4,294,836,225 have negative signed interpretations and pass.

This is not a reliable unsigned upper bound of 1,440 bytes.

If the gate fails, the function returns 2. All direct recognition and decoded-field writes have already occurred.

### 7. Subsequent positioning and transfer

If the size gate passes, the function obtains the positioning callback again from the interface object currently referenced by context `+0x04`.

It calls that callback with the same five-argument shape as before, except that the position is the base value saved during recognition plus `0x3e`. This uses the saved value, not a new read of context `+0x20`.

A nonzero result causes return value 2 without the subsequent transfer.

For a zero result, the function obtains the transfer callback again and invokes it with:

- The current interface object.
- Destination address: context `+0x5e`.
- Count: the 32-bit product described above.
- Final argument: 2.

The transfer result must equal the requested count’s 32-bit value exactly. Equality produces return value 1; inequality produces return value 2.

A zero count is not special-cased. It still requires the second positioning call and a transfer call whose result compares equal to zero.
