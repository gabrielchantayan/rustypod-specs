# F-798b2f89ac14

## Purpose

F-798b2f89ac14 obtains a cursor from a field in a caller-supplied object and, for a nonnegative requested count, invokes F-d3922c7fe0ec repeatedly to update that cursor. Processing stops when either the requested number of invocations has occurred or the byte at the current cursor is zero. The function returns the final cursor.

This is a contract for bounded **dependency invocations**, not an established contract for advancing by bytes, characters, or other logical units. The meaning and distance of each cursor update depend on F-d3922c7fe0ec.

A negative count produces a null return without accessing the supplied object. A null cursor loaded from the object also produces a null return without invoking the dependency.

The apparent intent is to locate a position within a zero-terminated sequence. That interpretation is inferred; the established behavior is the cursor-loading, byte-checking, and bounded-call sequence described below.

## Behavior

### Negative request

The signed negativity test occurs before any object-field access.

If the requested count is negative, the function returns null. It does not load the cursor field, inspect sequence bytes, or call F-d3922c7fe0ec.

There is no visible diagnostic, exception construction, or error-state update associated with this branch.

### Initial cursor acquisition

For a nonnegative request, the function loads the pointer-valued field at byte offset 4 from the supplied object address.

This is the sole direct read of that object field. The function retains the loaded value in a local cursor slot. Subsequent dependency calls receive access to that local slot, not the address of the object’s cursor field.

If the loaded cursor is null, the function returns null immediately. It does not inspect a byte through that pointer and does not invoke the dependency.

The field load is not skipped for a zero count. Consequently, an invalid object address can still cause an invalid memory access when the requested count is zero.

### Zero request

For a zero request with a non-null loaded cursor, the function returns that cursor unchanged by its own logic.

The exhausted invocation allowance prevents a cursor-byte read. Therefore, a cursor need not point to readable sequence storage merely to be returned for a zero request, provided loading the pointer field itself is valid.

### Positive request

For a positive request and a non-null initial cursor, each potential iteration has this observable order:

1. Determine whether the number of completed dependency calls is still less than the requested count.
2. Only if another call is permitted, read the single byte at the current cursor and compare it with zero.
3. Only if that byte is nonzero, invoke F-d3922c7fe0ec with the address of the local cursor slot.
4. After the dependency returns normally, increase the completed-call count by one.

The dependency can replace the local cursor through the address it receives. The next iteration uses the resulting cursor value.

A zero byte ends processing before another dependency call. That cursor, which points at the zero byte, is then returned.

Exhausting the requested count also ends processing. On this termination path, the function does not read a byte through the final cursor. It returns whatever pointer value remains in the local slot after the last permitted dependency call.

### Invocation bound and arithmetic

For a nonnegative requested count, normal execution performs no more than that many dependency calls.

The call counter begins at zero and increases by one only after a dependency call returns normally. Under the 32-bit signed-count interpretation, the counter does not overflow: even for the maximum positive request, the last increment reaches 2,147,483,647, after which the count comparison prevents another iteration.

No direct cursor arithmetic is established in this function. Any movement to another byte, character, record, or unrelated location is attributable to the dependency.

The field lookup uses byte offset 4. No address-range or wraparound validation is visible. Behavior for invalid, misaligned, or otherwise unusable field addresses is outside the established successful-execution contract.

### Dependency-produced cursor edge cases

An initially null cursor is explicitly handled. A cursor changed to null by F-d3922c7fe0ec is not given the same protection.

- If the dependency assigns null on the last permitted call, the next count check stops processing without a cursor-byte read, and the function returns null.
- If it assigns null while further calls remain available, the next iteration attempts a byte read through null. The function provides no defined error return for that situation.
- If it leaves the cursor unchanged at a nonzero byte, the function may call it repeatedly at that same location until the invocation allowance is exhausted.
- If it moves the cursor to a zero byte, that byte is checked only if another invocation remains available. Otherwise, the pointer is returned without inspecting its contents.

The function neither requires nor verifies forward progress. Its local loop is count-bounded, but overall completion also depends on each dependency call returning.
