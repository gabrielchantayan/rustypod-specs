# F-7ec140c78f52

## Purpose

F-7ec140c78f52 conditionally changes a selector stored in an object, invokes associated transition operations, and notifies a separate dependency using a value obtained from that object.

The established behavior is a comparison-driven transition:

- If the stored selector already equals the requested selector, the function invokes the notification dependency and returns 1.
- Otherwise, it invokes a preparation dependency, conditionally invokes another dependency according to the selector then present in the object, stores the requested selector, invokes a transition dependency, and invokes the notification dependency.
- On the changed-selector path, a nonzero transition result additionally causes a one-byte field to be set to 5. The function returns the transition result unchanged.

The names “selector,” “preparation,” “transition,” and “notification” describe roles in this contract, not established domain semantics. The evidence does not establish whether the selector represents a resource, mode, index, handle, or another kind of value.

## Interface

The function accepts two inputs:

| Input | Representation | Role |
|---|---|---|
| Object address | Address-bearing value in the supplied representation | Identifies the object containing the fields read and written by this function; also passed to three dependencies. |
| Requested selector | 32-bit integer value | Compared with, and conditionally stored into, the object’s selector field. |

The result is a 32-bit integer:

- Exactly 1 on the initially equal-selector path, provided the notification call returns normally.
- The exact result returned by F-590305259b63 on the changed-selector path, provided subsequent execution returns normally.

The function does not normalize the transition result to a Boolean. Zero, positive nonzero values, and negative values remain distinct return values.

The following object-relative locations are directly relevant:

| Byte offset | Access width | Direct use |
|---|---:|---|
| `0x34` | 4 bytes | Read as the argument passed to F-9118c9e0e63e. |
| `0xC1` | 1 byte | Written with the value 5 only when the changed-selector path obtains a nonzero transition result. |
| `0xC4` | 4 bytes | Read for selector comparisons and written with the requested selector during a transition. |

Offsets are measured in bytes from the object address. The selector occupies offsets `0xC4` through `0xC7`; the notification argument occupies `0x34` through `0x37`. The one-byte write at `0xC1` does not directly overlap either four-byte field.

The supplied representation supports these access widths. It does not independently establish byte order, alignment requirements, a portable calling convention, or the meaning of the four-byte notification argument.

## Behavior

### Initial comparison

The first direct object access is a four-byte read of the selector at offset `0xC4`. That value is compared with the requested selector.

The comparison selects one of two paths. Later mutations by dependencies do not cause the function to revisit this initial branch decision.

### Initially equal selector

When the initially read selector equals the requested selector:

1. The function reads the four-byte value at offset `0x34`.
2. It invokes F-9118c9e0e63e with that value.
3. After the call returns normally, it returns 1.

On this path, the function itself does not:

- Invoke F-713822eb4f24.
- Invoke F-e1ece1dbf991.
- Invoke F-590305259b63.
- Write the selector field.
- Write the byte at `0xC1`.

This is not a side-effect-free early return: F-9118c9e0e63e is still called. Its return value does not determine the result of F-7ec140c78f52.

If F-9118c9e0e63e changes the object through some independently available reference or global state, those changes are not checked or reversed by this function. In particular, the function still returns 1 after normal completion of that call even if the stored selector no longer equals the requested selector.

### Initially different selector

When the initially read selector differs from the requested selector, the observable sequence is:

1. Invoke F-713822eb4f24 with the object address and the numeric argument 500.
2. After that call returns, read the four-byte selector at offset `0xC4` again.
3. If this newly read selector is nonzero, invoke F-e1ece1dbf991 with the object address.
4. Store the requested selector as a four-byte value at offset `0xC4`.
5. Invoke F-590305259b63 with the object address and retain its integer result.
6. Read the four-byte value at offset `0x34`.
7. Invoke F-9118c9e0e63e with that value.
8. After that call returns, write the one-byte value 5 at offset `0xC1` if the retained transition result is nonzero.
9. Return the retained transition result.

The second selector read is significant. The condition for invoking F-e1ece1dbf991 depends on the selector after F-713822eb4f24 returns, not necessarily on the value observed at entry.

For example, a nonzero initial selector does not guarantee that F-e1ece1dbf991 is invoked: F-713822eb4f24 may leave the selector zero. Conversely, an initially zero selector does not prevent that invocation if F-713822eb4f24 leaves it nonzero.

There is no new comparison against the requested selector after preparation. Even if F-713822eb4f24 changes the selector to the requested value, the function continues on the changed-selector path. A nonzero value then triggers F-e1ece1dbf991, followed by the selector store and transition call.

### Result handling and field updates

The requested selector is stored before F-590305259b63 executes. There is no explicit rollback when that dependency returns zero.

The notification dependency runs after F-590305259b63, regardless of whether the retained result is zero or nonzero. The value supplied to notification is read after the transition call, so it can reflect changes made by preceding dependencies.

The byte at `0xC1` is written only after the notification dependency returns normally:

- Retained result zero: no direct write to `0xC1`.
- Retained result nonzero: write exactly one byte with value 5.

A negative result is nonzero and therefore triggers the write. The evidence does not justify interpreting every nonzero result as success.

When the retained result is zero, the function does not clear or otherwise restore `0xC1`. Its final value depends on its earlier contents and any dependency effects.

The retained transition result is not replaced by the notification dependency’s return value.

### Arithmetic and boundaries

No arithmetic is performed on the requested selector. It is compared for equality and stored without explicit range reduction, increment, decrement, or sign-based filtering.

Zero has a special role only in the second selector check. A requested selector of zero is not rejected. Any nonzero selector value satisfies the condition for F-e1ece1dbf991 when present at that check.

The constant 500 is passed directly to F-713822eb4f24. Its unit and semantic meaning are unknown.

## Side effects

Direct effects of F-7ec140c78f52 are limited to the listed object accesses and dependency invocations.

On the changed-selector path, the function directly writes:

- Four bytes at `0xC4`, containing the requested selector.
- Conditionally, one byte at `0xC1`, containing 5.

These direct writes do not establish final object values in all circumstances. F-590305259b63 and F-9118c9e0e63e execute after the selector store and may have effects not visible in this evidence. No preservation of the selector, notification argument, adjacent fields, or global state may be assumed.

The direct write of 5 occurs after notification. Thus, if notification itself modifies `0xC1`, a nonzero retained transition result causes this function’s later write to supersede that modification at that byte.

There is no directly visible allocation, deallocation, ownership transfer, global access, or synchronization operation. This does not establish that the dependencies perform none of those actions.

No explicit error-reporting mechanism is provided for invalid storage or failed dependency execution. The function contains no visible recovery path for a dependency that does not return normally. Later calls, writes, and the ordinary return are conditional on preceding operations completing normally.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not reports of executed tests. Each assumes valid storage and normal return from all invoked dependencies.

### Equal selector

- Only F-9118c9e0e63e is invoked by this function.
- Its argument is the value read from `0x34`.
- The function returns 1.
- This function performs no direct selector or marker-byte write.

### Transition from zero

- F-e1ece1dbf991 is skipped.
- The selector is directly set to 9 before F-590305259b63.
- Notification follows the transition call.
- A transition result of zero is returned as zero and causes no direct write to `0xC1`.

### Preparation changes the cleanup condition

Given an initial selector of 4 and a requested selector of 8:

- If F-713822eb4f24 leaves the selector zero, F-e1ece1dbf991 is skipped.
- If it leaves any nonzero value, F-e1ece1dbf991 is invoked before the store of 8.

The entry value alone is insufficient to decide this invocation.

### Nonzero result is preserved

Given a changed-selector path where F-590305259b63 returns −3:

- F-9118c9e0e63e is invoked before the marker-byte write.
- The byte at `0xC1` is then directly set to 5.
- The function returns −3, not 1.

### Notification observes a later argument value

Given that F-590305259b63 changes the four-byte field at `0x34` from one value to another:

- The subsequent notification receives the later value.
- This function does not use an entry-time snapshot of that field.

### No rollback on zero result

Given a changed-selector path where dependencies do not modify the selector after its direct store, and F-590305259b63 returns zero:

- The requested selector remains stored.
- Notification still occurs.
- The function returns zero without restoring the previous selector.
