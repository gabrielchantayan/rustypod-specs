# F-16423b2a3bda

## Purpose

F-16423b2a3bda prepares one 24-byte record selected from a caller-supplied state object. It prefers a record linked through the state’s reusable-record field. If that field is null, it consumes the record at the state’s current sequential position, allocating a new storage block when the current position equals the recorded endpoint.

The function clears selected fields of the chosen record, not the entire record. It updates the state to remove or consume that record.

The apparent intent is a record-pool acquisition operation. That interpretation is inferred from the layout and transitions. The established interface has no explicit return value and does not explicitly store a separate “selected record” result.

## Interface

### Input and result

The function accepts one pointer to mutable state. The supplied representation uses four consecutive 32-bit words:

| Byte offset | Contract name | Observed role |
|---|---|---|
| 0 | Block-chain head | Address of the most recently linked allocation descriptor, or zero |
| 4 | Reusable-record head | Address of the next reusable record, or zero |
| 8 | Sequential position | Address of the next sequential record |
| 12 | Sequential endpoint | Address compared with the sequential position to decide whether another block is needed |

These names describe observed uses, not confirmed source-level types.

The function has no explicit return value. Callers must not depend on a returned record address or status code.

### Supporting layouts

An allocation descriptor occupies 12 bytes:

| Byte offset | Width | Observed content |
|---|---:|---|
| 0 | 32 bits | Previous block-chain head |
| 4 | 32 bits | Record capacity |
| 8 | 32 bits | Backing-storage address |

The selected record has a 24-byte stride. Only these record locations have established meanings for this operation:

| Byte offset | Width | Use |
|---|---:|---|
| 0 | 8 bits | Cleared after selection |
| 4 | 32 bits | Cleared after selection |
| 8 | 32 bits | Cleared after selection |
| 12 | 32 bits | Next reusable-record address when selected from the reusable chain; subsequently cleared |

The function does not directly access bytes 1–3 or 16–23 of the selected record.

### Representation and arithmetic

The supplied representation is consistent with a 32-bit address and integer model: pointer-bearing state fields and descriptor fields occupy four bytes, and arithmetic quantities used for capacity are unsigned 32-bit values. Exact target ABI details are not independently available.

Capacity calculations use unsigned 32-bit arithmetic, including wraparound. The byte-count calculation also uses that width. A high bit set in the stored capacity does not make the growth comparison signed.

### Preconditions

For an ordinary successful operation:

- The state pointer must identify accessible storage for all four state words.
- A nonzero reusable-record head must identify a writable record with a readable four-byte link at offset 12.
- If sequential allocation occurs without allocating another block, the sequential position must identify a writable record.
- If a nonzero block-chain head is consulted for growth, its capacity word at offset 4 must be readable.
- Each allocation dependency call must provide storage usable by the subsequent accesses.
- The resulting record and descriptor accesses must satisfy the target’s alignment and address-validity requirements.

The function does not check these conditions. In particular, it does not establish that a sequential position unequal to the endpoint is actually inside a valid allocation.

## Behavior

### Record-source precedence

The first state field inspected is the reusable-record head.

A nonzero value always selects the reusable-record path. The sequential position, sequential endpoint, block-chain head, and block capacity are not inspected by that path.

Only when the reusable-record head is zero does the function inspect the sequential position and endpoint.

### Selection from reusable records

When the reusable-record head is nonzero:

1. That address becomes the selected record address.
2. The four-byte value at record offset 12 is read.
3. That value is written to the state’s reusable-record head.
4. The selected record is partially cleared as specified below.

The link is therefore read before it is overwritten. This preserves the next reusable-record address even though the selected record’s link field is subsequently zeroed.

For distinct, valid state and record storage, this path does not change the block-chain head, sequential position, or sequential endpoint. It performs no allocation calls.

There is no cycle detection, membership check, or validation of the link. For example, a self-referential link can leave the reusable-record head pointing to the same record even though that record’s link is then cleared.

### Selection from existing sequential storage

When the reusable-record head is zero, the function reads the sequential position and compares it with the sequential endpoint.

If the two addresses differ:

- The current sequential position becomes the selected record address.
- The state’s sequential position is written with the selected address plus 24 bytes.
- The selected record is partially cleared.

The endpoint is used only for equality. The function does not compare address ordering, calculate remaining bytes, or verify that a whole record fits.

Consequently, a position beyond the endpoint does not trigger allocation merely because it is beyond it. A position fewer than 24 bytes before the endpoint is likewise not rejected.

### Allocating another block

If the sequential position equals the sequential endpoint, the function computes a capacity for a new block.

If the block-chain head is zero, the new capacity is 32 records.

Otherwise, it reads the existing head descriptor’s capacity and calculates two unsigned 32-bit candidates:

- The existing capacity plus 32.
- The existing capacity plus its value shifted right by one bit, plus its value shifted right by three bits.

Each arithmetic result is subject to 32-bit wraparound. The second candidate is selected when it is greater than or equal to the first candidate under unsigned comparison; otherwise, the first is selected.

For values that do not overflow, this selects the larger of a 32-record increment and approximately 1.625 times the previous capacity, with each shifted contribution truncated separately. This growth interpretation must not replace the actual wrapped arithmetic at large values.

The function then makes two dependency calls, in this order:

1. Request 12 bytes, with a second argument of zero.
2. Request the new capacity multiplied by 24 bytes, with a second argument of zero.

The capacity multiplication is a 32-bit calculation. Overflow is not detected, and the request is not widened before multiplication.

After both calls return normally, the function performs the following direct writes and reads in order:

1. Store the backing-storage result in the new descriptor at offset 8.
2. Read the state’s current block-chain head and store it in the new descriptor at offset 0.
3. Store the computed capacity in the descriptor at offset 4.
4. Store the descriptor address in the state’s block-chain head.
5. Read the backing-storage address from descriptor offset 8.
6. Set the sequential endpoint to that backing address plus the capacity multiplied by 24.
7. Set the sequential position to that backing address plus 24.
8. Partially clear the record at the backing address.

The first record of the new block is therefore consumed immediately.

The block-chain head used as the descriptor’s predecessor is read after both dependency calls. It is not necessarily the same value that was inspected earlier to decide the growth calculation. Unknown dependency side effects must not be assumed absent.

### Partial record clearing

All three selection paths converge on the same clearing sequence:

1. Write four zero bytes at record offset 4.
2. Write four zero bytes at record offset 8.
3. Write four zero bytes at record offset 12.
4. Write one zero byte at record offset 0.

This is 13 bytes of explicit clearing within a 24-byte record.

Bytes 1–3 and 16–23 are not initialized by this function. For separately allocated, nonoverlapping storage, they retain whatever values they had before these writes. Their values in newly allocated storage depend on the allocation dependency and cannot be assumed to be zero.

State updates precede record clearing. The function does not first initialize the record and then commit the state transition.

## Side effects

### State and storage mutations

The direct mutation set depends on the selected path:

| Path | State fields directly written | Other direct writes |
|---|---|---|
| Reusable record | Reusable-record head | Selected record’s cleared fields |
| Existing sequential storage | Sequential position | Selected record’s cleared fields |
| New allocation | Block-chain head, sequential endpoint, sequential position | All three descriptor words and selected record’s cleared fields |

The zero reusable-record head is not explicitly rewritten on either sequential path.

The operation does not copy the old backing storage into the new block. It links a new descriptor to a previous descriptor address instead.

### Ownership

The function directly retains the two allocation results through the new descriptor and the state’s block-chain head. It does not directly release an existing descriptor, backing allocation, or selected reusable record.

This establishes retained reachability, not a complete ownership contract. The eventual release mechanism, allocator pairing requirements, and responsibility for destruction are unknown. The dependency must not be assumed to preserve memory or global state merely because it receives an allocation-sized argument.

### Failure and concurrency

There is no explicit status result, null-result check, overflow check, rollback, or error translation.

If a dependency returns an unusable address, subsequent accesses can fail. If an access fails after a state update, no restoration is specified by the visible operation. Exceptions, process termination, and allocator-specific failure behavior are unknown.

There is no explicit synchronization. The observed access order is not an atomicity or thread-safety guarantee.

Unless otherwise stated, the field-level postconditions assume distinct, valid storage. If the state, selected record, or descriptor storage overlaps, later writes can overwrite earlier state or descriptor contents.

## Acceptance examples

These are conditional contract examples derived from the static representation. They are not runtime test results.

### Reusable record takes priority

Given a valid state whose reusable-record head identifies record A, and record A’s offset-12 link identifies record B:

- The reusable-record head becomes B.
- A receives the four clearing writes in the specified order.
- No allocation dependency is called.
- For nonoverlapping state and record storage, the sequential position and endpoint remain unchanged.

This remains the selected path even if the sequential position equals the endpoint.

### Last available sequential record

Given a zero reusable-record head, a valid sequential position P, and an endpoint equal to P plus 24:

- No allocation is requested.
- P is the selected record.
- The sequential position becomes the endpoint.
- Only the specified fields of P are cleared.

A later invocation can trigger allocation if the reusable-record head is still zero and the two sequential addresses still compare equal.

### First block

Given a zero reusable-record head, equal sequential addresses, and a zero block-chain head, assume the dependency returns distinct valid storage and does not mutate the state:

- The requests are 12 bytes and 768 bytes, in that order.
- The new descriptor records predecessor zero, capacity 32, and the returned backing address.
- The state’s block-chain head becomes the descriptor address.
- The endpoint becomes backing address plus 768.
- The sequential position becomes backing address plus 24.
- The first backing record receives the partial clearing sequence.

### Capacity growth without overflow

Under otherwise valid new-block conditions:

- Previous capacity 32 produces candidates 64 and 52, selecting 64 and requesting 1,536 backing bytes.
- Previous capacity 64 produces candidates 96 and 104, selecting 104 and requesting 2,496 backing bytes.

These examples exercise both alternatives in the unsigned comparison.

### Capacity overflow is not rejected

Given a previous capacity of 4,294,967,295:

- Adding 32 wraps to 31.
- Adding the two shifted contributions wraps to 2,684,354,557.
- The latter is selected by unsigned comparison.
- Multiplication by 24 wraps to a request of 4,294,967,224 bytes.

The function performs no explicit overflow rejection. Whether such a request can succeed is outside the established contract.

### Unusual endpoint relation

Given a zero reusable-record head and a sequential position unequal to the endpoint, the function does not request a new block solely because the position is numerically greater than the endpoint.

Successful completion still requires the selected record’s accessed bytes to be valid. This example establishes the equality-only branch condition, not safety for malformed state.
