# F-b2734593857a

## Purpose

F-b2734593857a obtains a nullable candidate address and conditionally records that address in a caller-supplied receiver. A non-null candidate is eligible for this direct attachment sequence only when a related 32-bit status word is zero. That sequence stores the candidate address, invokes a receiver-selected indirect operation, and writes one byte derived from an input value.

A non-null candidate whose status word is nonzero instead selects a candidate-associated indirect operation. A null candidate selects neither indirect operation.

Preparatory dependency calls precede candidate acquisition. A final dependency call receives a local work-area address on every normally continuing branch. The represented 64-bit return value combines a fixed upper word with a lower word indicating whether the zero-status attachment branch was selected.

“Candidate,” “receiver,” “status,” and “attachment” describe the observed data flow. They do not establish application semantics, ownership, resource release, or overall success.

### Null candidate

If candidate acquisition returns zero:

- No candidate fields are dereferenced.
- Neither indirect target is invoked.
- The conditional attachment logic performs no direct receiver access.
- The attachment-result flag remains zero.
- Execution continues to the final work-area operation.

These are limits on this function’s direct conditional operations. They do not constrain effects of the dependencies.

### Non-null candidate with zero status

For a non-null candidate, the caller first reads the address at candidate offset 48, then reads the 32-bit status word at offset 28 in the addressed record.

If the status word is zero, the ordered attachment operations are:

1. Store the candidate address as a 32-bit word at receiver offset 8.
2. Set the attachment-result flag to one.
3. Read the receiver’s dispatch-table address at receiver offset 0.
4. Read the indirect target at dispatch-table offset 20 and invoke it with the receiver address as its single explicit argument.
5. After the indirect call returns, store the low eight bits of the original primary value at receiver offset 12.

The candidate-address store precedes dispatch-table lookup and callback invocation. Under ordinary valid-memory conditions, the callback can observe the stored candidate address. The dispatch table is read after the store rather than captured beforehand; aliasing must be evaluated using this order.

The receiver byte write follows the callback. The callback is not guaranteed to observe the new byte. If it changes that byte and returns with the receiver still writable, the subsequent direct write replaces its value.

That direct operation writes only one byte. It does not itself replace the following three bytes. Other dependency effects remain unconstrained.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Each assumes valid required storage and normal completion unless stated otherwise.

1. **Null candidate.** If F-f11aec34c97f returns zero, neither indirect target is invoked. The final work-area operation occurs, and the return value is `0x0000800000000000`.

2. **Zero-status candidate.** If candidate acquisition returns a non-null candidate whose related status word is zero, its address is stored at receiver offset 8 before the receiver-selected call. The receiver byte is written after that call returns. Normal completion returns `0x0000800000000001`.

3. **Any nonzero status.** Status values `1`, `0x80000000`, and `0xffffffff` all select the candidate-associated indirect operation. The direct receiver attachment writes do not occur, and normal completion returns `0x0000800000000000`.

4. **Byte truncation.** For primary input `0x123456ab`, the zero-status branch’s byte store writes `0xab`. The dependencies receiving the original primary input receive all 32 bits. The other bytes adjacent to receiver offset 12 are not changed by this byte store itself.

5. **Callback ordering.** If the receiver-selected callback writes `0x77` at receiver offset 12, and the primary input’s low byte is `0xab`, the subsequent direct store leaves `0xab` immediately after that store. A post-return assertion additionally requires that the final dependency and other allowed effects do not change it.

6. **Returned destination overlaps the first work-area word.** Suppose F-b9acea4b06ad changes that word to `0x11111111` and returns its address. If shared word A is then read as `0x22222222`, the caller’s subsequent store replaces the earlier modification with `0x22222222`. Candidate acquisition sees that value only if intervening effects, including F-8157a180d901, do not change it.

7. **Returned destination overlaps the second work-area word.** Under equivalent conditions for the second word, the shared-word-A store replaces that word instead. Candidate acquisition still receives the address of the first word and the work area’s then-current contents.

8. **Earlier work-area changes survive conditionally.** If F-b9acea4b06ad modifies the work area, its returned destination does not overlap the modified bytes, and intervening effects preserve them, candidate acquisition receives those modifications. Its separate fourth argument remains the original primary value regardless.

9. **Late shared-word-B read.** If a selected indirect operation changes shared word B, and nothing changes it again before the final read, the first work-area word receives that changed value before F-22abefe7f288 is called.

10. **Null receiver on a non-attachment path.** If candidate acquisition returns zero, this function’s conditional logic does not dereference the receiver. This does not guarantee that unknown dependencies tolerate every surrounding state, nor does it make a null receiver valid on the zero-status branch.
