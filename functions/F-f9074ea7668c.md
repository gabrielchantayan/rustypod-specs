# F-f9074ea7668c

## Purpose

F-f9074ea7668c derives two boundaries through separate searches, counts calls to a traversal dependency until a comparison dependency returns exactly 1, and then invokes a final dependency using the resulting boundary state.

The established sequence is two searches, counted traversal, and a final operation. An ordered-container range operation is plausible intent, but the evidence does not establish a container type, ordering relation, iterator interpretation, or final-operation semantics. In particular, element removal is not an established postcondition.

On normal completion, the return value is the accumulated traversal count, not a result supplied by the final dependency.

## Interface

### Inputs and result

The function accepts two arguments:

- **Object address:** a 32-bit integer address carrier used to locate fields and embedded regions.
- **Search argument:** an opaque 32-bit value forwarded unchanged to the search dependency. Whether it represents a key, pointer, handle, or scalar is unresolved.

The result is a 32-bit integer count. It starts at zero and is incremented once before each call to the traversal-advance dependency. Representable counts are established; behavior after signed 32-bit overflow is not.

### Preconditions and validation limits

Normal completion requires that every executed memory access be valid and every invoked dependency return normally. In particular:

- The object’s header-address field must be readable.
- Each header address used to obtain a traversal start must permit reading its field at `0x04`.
- Each selected link field at a nonzero traversal address must be readable.
- Both searches must eventually reach a zero traversal address.
- The comparison-and-advance sequence must eventually produce a comparison result of exactly 1.
- Dependencies must operate compatibly with the supplied local storage sizes and lifetimes.

Both searches explicitly test whether the current traversal address is zero before invoking the search dependency or accessing that location’s link fields. A zero traversal start is therefore supported by the visible search control flow.

The function does **not** validate the object address or header address before dereferencing them. The traversal zero checks do not protect those earlier accesses, and a nonzero traversal address is not otherwise validated.

The evidence uses 32-bit address carriers and fields. Exact machine address-wrap behavior, alignment requirements, and invalid-access consequences remain unresolved.

## Behavior

### First boundary search

The function obtains the first traversal start by reading the object’s header-address field and then reading that header’s field at `0x04`. It separately rereads the object’s header-address field to initialize the first boundary.

These are distinct reads, not one shared header snapshot. If external mutation occurs between them, the starting traversal address and initial boundary can derive from different header values.

Before each search iteration, the current traversal address is tested against zero. If it is zero, the search ends without a search-dependency call or node-link access for that address.

For a nonzero traversal address, F-31a0b2b5649a receives, in order:

1. The object-relative address at `0x51`.
2. The current traversal-relative address at `0x10`.
3. The search argument.

Only zero versus nonzero is significant for this dependency’s result:

- **Zero:** the function reads the current location’s `0x08` link, continues at that address, and replaces the first boundary with that same link value.
- **Nonzero:** the function reads the current location’s `0x0C` link and continues there, leaving the first boundary unchanged.

The boundary update records the selected **next address**, not the address whose search decision was just obtained. Consequently, a zero link can become the boundary.

The selected link is read after the dependency returns. A dependency-induced change to that link can therefore affect the next step. The function does not fetch both links or cache the selected link before the call.

### Second boundary search

After the first search ends, the function obtains a new traversal start through a fresh read of the object’s header-address field followed by a read at header offset `0x04`. A separate reread of the object’s header-address field initializes the second boundary.

The second search does not reuse the first search’s starting address or header snapshot. Changes during the first search can affect these later reads.

As in the first search, a zero traversal address ends the search before any search-dependency call or node-link access for that address.

For each nonzero address, F-31a0b2b5649a receives:

1. The object-relative address at `0x51`.
2. The search argument.
3. The current traversal-relative address at `0x10`.

The last two arguments are reversed relative to the first search.

The result selects behavior as follows:

- **Zero:** read the current location’s `0x0C` link and continue there without changing the second boundary.
- **Nonzero:** read the current location’s `0x08` link, continue there, and replace the second boundary with that next address.

Here too, the selected link is read after the dependency returns, and an updated boundary may be zero.

No visible mechanism requires the searches to observe an unchanged structure or a stable ordering relation.

### Preparation for counted traversal

After the second search terminates, the local traversal record has the initial contents specified in the interface: first boundary, zero, zero, first boundary. The separate boundary word receives the second-search boundary, and the count starts at zero.

The searches make scratch writes within the local record, but all four words have the specified initial values before the record address is first passed to the comparison dependency. The search dependency does not receive the record address as an argument.

### Counted traversal

F-eac694802fc1 receives the traversal-record address followed by the separate boundary-word address.

A return value of **exactly 1** ends this phase. Any other value causes the function to increment the count and then call F-357c4c54c6ea with the traversal-record address. Comparison is repeated after that call returns.

Consequences include:

- A first comparison result of 1 produces no advance calls and leaves the count at zero.
- Results such as 2 or −1 do not terminate traversal merely because they are nonzero.
- Each advance call is preceded by a count increment.
- The count does not independently measure nodes visited, successful advances, or elements modified.
- There is no progress check or iteration limit.

Both dependencies receive addresses of local state. The function does not restore the traversal record or separate boundary after they return. Changes made through those addresses may affect subsequent comparisons and the final operation.

If comparison never returns exactly 1, the function does not reach the final operation. Overflow and other abnormal behavior may intervene; indefinite execution is not guaranteed to remain well-defined.

### Final operation and return

After the terminating comparison returns, the function first copies the current separate boundary word into a new local word. It then copies the current fourth traversal-record word into another local word.

F-8310debf75fb receives, in order:

1. The address of the uninitialized four-byte output region.
2. The object-relative address at `0x38`.
3. The address of the copy from the fourth traversal-record word.
4. The address of the copy from the separate boundary word.

The supplied boundary values are therefore sampled **after** the terminating comparison. They need not equal the original search results.

The final dependency is called even when the traversal count is zero. Its return value, if any, is ignored. Writes to the output region and boundary copies are not subsequently consumed by this function.

If the final dependency returns normally, the function returns the accumulated count.

### Non-Boolean comparison results

### Mutation during a search decision

### Mutation before final sampling

### Changed start between searches
