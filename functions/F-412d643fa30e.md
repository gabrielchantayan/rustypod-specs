# F-412d643fa30e

## Purpose

F-412d643fa30e coordinates a chunked transfer using two alternating descriptors and two associated state locations. Each chunk is first offered to an input-side operation, then submitted to a processing-side operation. Between submissions, the function invokes a dependency on the state associated with the opposite descriptor.

The alternating arrangement suggests double-buffered processing, but concurrency, completion, and resource-release semantics are not established. The contract therefore describes calls, ordering, and state selection without treating those calls as proven waits, releases, or ownership transfers.

The function returns no explicit value. Its reported result is a four-byte status written through the first argument. Some failure paths record a status that is not subsequently selected for output; those paths are part of the observed behavior, not corrected here.

## Interface

The six arguments, in order, are:

| Argument | Role and representation |
|---|---|
| Output status | Writable storage accessed as two consecutive 16-bit elements. |
| Context | A word-addressed structure, accessed through 32-bit fields and embedded state addresses. |
| Input object | An object whose dispatch table supplies an operation at byte offset `0x0c`. |
| Initial position | A 32-bit integer used as the starting processing position. |
| Requested amount | A 32-bit integer multiplied by an initial value obtained from the processing object. |
| Auxiliary value | An opaque 32-bit value forwarded to processing submissions. |

The context is accessed at these byte offsets:

| Offset | Observed use |
|---|---|
| `0x00` | Reference to the processing object. |
| `0x30`–`0x3f` | First 16-byte descriptor, comprising four 32-bit words. |
| `0x34` | Also read independently as the chunk-limit source. |
| `0x40`–`0x4f` | Second 16-byte descriptor, comprising four 32-bit words. |
| `0x54` | Address passed as the first descriptor’s associated state location. |
| `0x58` | Address passed as the second descriptor’s associated state location. |

The overlap at `0x34` is significant: the chunk-limit field is also the second word of the first descriptor.

Each descriptor passed to another operation is a temporary four-word copy, not the address of the descriptor inside the context. A descriptor is copied again before processing submission, so modifications made to the temporary by the input operation are not directly forwarded to the processing operation.

The output requires four writable bytes. The context must support all listed accesses, and its referenced objects must support the observed indirect calls. No null checks, bounds checks, dispatch-table validation, or argument validation are visible.

The supplied representation uses 16-bit status elements and 32-bit words. Exact ABI details, pointer provenance rules, and behavior for invalid addresses remain unspecified.

## Behavior

### Initialization and transfer sizing

The function first reads the unsigned 32-bit word at context offset `0x34`. It derives a fixed chunk cap:

- For values below `65,536`, the cap is the value shifted right by one bit.
- For values at or above `65,536`, the cap is `32,768`.

Thus, inputs of zero or one produce a zero cap. The cap is not recomputed if a dependency subsequently changes the context.

Next, the function calls the processing object’s dispatch operation at byte offset `0x24`. Its result is multiplied by the requested amount to form the remaining transfer quantity, which is subsequently treated as unsigned 32-bit.

The displayed multiplication uses signed integer operands before assignment to unsigned storage. Behavior when that signed product is not representable is not established by the supplied evidence. Modulo-\(2^{32}\) multiplication must not be adopted as an unconditional contract without additional machine-level evidence.

Two temporary status areas are then passed, in order, to F-603a53835f04, each with three trailing zero arguments:

1. Primary status, associated with the first descriptor.
2. Secondary status, associated with the second descriptor.

The names describe their use here, not their externally defined status meanings. Initialization values and the dependency’s exact write extent are unknown.

### Empty-transfer path

At the top of each iteration, the function tests the remaining quantity.

If it is zero:

1. F-fceaba74ea88 is called with the context address at offset `0x58`.
2. The first 16-bit element of the secondary status is written to the output.
3. The second 16-bit element of the secondary status is written to the output.
4. F-9b718979506d is called on the secondary status.
5. F-9b718979506d is called on the primary status.
6. The function returns.

This path applies both to an initially empty transfer and to a later loop re-entry with nothing remaining. It does not skip the state-location call merely because no transfer was requested.

### First-descriptor phase

For a nonzero remaining quantity, the first chunk size is the unsigned minimum of the remaining quantity and the fixed cap.

The function copies the first descriptor’s four words, in ascending field order, into temporary storage. It calls the input object’s operation at dispatch-table offset `0x0c`, passing:

- The input object.
- The requested chunk size.
- The temporary descriptor’s address.

The returned 32-bit quantity must equal the requested chunk size exactly. Both a smaller return and a larger return take the mismatch path.

On a mismatch, F-7f008c1060db is called on the primary status with arguments `0x22`, zero, and zero.

- If no first-descriptor submission has yet succeeded, the function proceeds directly to primary-status output.
- Otherwise, it first calls F-fceaba74ea88 on the context address at `0x58`, then proceeds to primary-status output.

There is no retry of the mismatched chunk.

On an exact input return, the function:

1. Captures the current processing-object reference.
2. Calls that object’s dispatch operation at offset `0x24`.
3. Calls F-d7be9cfb4000 with the chunk size and the operation’s result.
4. Retains a 16-bit result for the processing submission.
5. Recopies all four words of the first descriptor from the context.
6. Calls the captured object’s operation at dispatch offset `0x0c`.

The processing submission receives the object, temporary descriptor address, current position, 16-bit converted quantity, context address `0x54`, primary-status address, and auxiliary value, in that order.

A nonzero processing return causes F-7f008c1060db to be called on the primary status with `0x22`, zero, and zero, followed immediately by primary-status output. No additional state-location call is made on this failure path.

After a zero processing return:

- The requested chunk size is subtracted from the remaining quantity.
- The processing-object reference is fetched again from the context.
- Its operation at offset `0x24` is called again.
- F-d7be9cfb4000 is called again with the chunk size and this new result.
- The resulting integer is added to the current position.

The conversion used for position advancement is therefore a separate call from the conversion used for submission. It is not established that the two conversions produce equal results.

After the first successful first-descriptor submission, a local first-use flag is cleared and no opposite-state call is made at that point. After every later successful first-descriptor submission, F-fceaba74ea88 is called on the context address at `0x58`.

If no quantity remains, the function calls F-fceaba74ea88 on the context address at `0x54`, then outputs the primary status.

### Second-descriptor phase

If quantity remains after a successful first-descriptor phase, a second chunk is selected using the same cap and unsigned minimum rule.

The second descriptor is copied from context offsets `0x40`–`0x4f`. The input operation is called with this temporary copy and the second chunk size.

If its returned quantity differs from the requested size:

1. F-7f008c1060db is called on the secondary status with `0x22`, zero, and zero.
2. F-fceaba74ea88 is called on the context address at `0x54`.
3. The primary status—not the secondary status—is selected for output.

Consequently, the status marked by this mismatch is not directly copied to the caller.

For an exact input return, conversion and descriptor recopying follow the same pattern as in the first phase. The processing submission instead receives context address `0x58` and the secondary-status address.

If this processing call returns nonzero, the function marks the **primary** status with `0x22`, zero, and zero, then immediately outputs it. This differs from the second-phase input-mismatch path, which marks the secondary status.

After a successful second-descriptor submission:

1. The chunk size is subtracted from the remaining quantity.
2. A fresh processing-object lookup, offset-`0x24` call, and F-d7be9cfb4000 call determine the position increment.
3. The current position is advanced.
4. F-fceaba74ea88 is called on context address `0x54`.
5. F-ec61551795ee is called on the primary status.

A nonzero predicate result repeats the loop. A zero predicate result calls F-fceaba74ea88 on context address `0x58`, then outputs the primary status.

The predicate can therefore terminate the transfer while quantity remains. Conversely, even when the second phase reduces the remaining quantity to zero, the predicate is still called before the next empty-transfer check.

### Primary-status output and finalization

Every primary-status output path performs the following sequence:

1. Write the primary status’s first 16-bit element to the output.
2. Copy the primary status’s second 16-bit element into the secondary status’s second-element storage.
3. Write that copied element to the output’s second 16-bit location.
4. Call F-9b718979506d on the secondary status.
5. Call F-9b718979506d on the primary status.
6. Return.

The intermediate overwrite of the secondary status is observable to its finalization dependency. It must not be treated merely as an irrelevant temporary assignment.

## Side effects

The function directly writes the output status and its own temporary storage. It also passes mutable-looking addresses to dependencies:

- Temporary descriptor storage.
- Both temporary status areas.
- Context state locations at `0x54` and `0x58`.
- The input and processing objects.

Those dependencies may mutate reachable state. Their effects are not limited by the supplied evidence.

No direct allocation, deallocation, buffer-content copying, or ownership transfer is visible. Descriptor copying copies four words, not the memory potentially described by those words. Whether F-fceaba74ea88 waits, releases, resets, or performs another action is unknown.

The output is written before the two finalization calls. Without dependency contracts or aliasing restrictions, it is not established that the output remains unchanged after those calls.

The context’s processing-object reference is read repeatedly rather than held for the entire invocation. Within an individual processing phase, however, the object captured before conversion is also used for submission, even if an intervening dependency changes the context reference.

Descriptor fields are read separately. No atomic 16-byte snapshot or synchronization guarantee is established.

## Acceptance examples

These examples are conditional static acceptance criteria, not runtime results. Status-element expectations assume the relevant dependencies establish readable status elements.

1. **Initially empty transfer.**  
   If the initial product is zero, no input or processing submission occurs. The call on context address `0x58` occurs before secondary-status output. Finalization order is secondary, then primary.

2. **Single successful first chunk.**  
   Suppose the remaining quantity is 20 and the chunk cap is 32. An exact input return of 20 followed by a zero processing return exhausts the quantity. Position conversion still occurs. The call on state `0x54` precedes primary-status output. The secondary descriptor is not submitted.

3. **First input mismatch.**  
   If the first requested chunk is 16 and the input operation returns 15 or 17, the primary status is marked. No processing submission or state-location call occurs before output.

4. **Second input mismatch.**  
   After one successful first phase, suppose the second input operation returns a quantity different from the requested chunk. The secondary status is marked, state `0x54` is passed to F-fceaba74ea88, and the primary status is output.

5. **Second processing failure.**  
   If the second input operation succeeds exactly but the second processing submission returns nonzero, the primary status is marked. There is no subsequent position increment, state-location call, or predicate call on that path.

6. **Predicate stops with work remaining.**  
   After two successful submissions, a zero result from F-ec61551795ee causes state `0x58` to be passed to F-fceaba74ea88 and the primary status to be output, even if the remaining quantity is nonzero.

7. **Two chunks finish and predicate permits continuation.**  
   If the second phase exhausts the quantity and the predicate returns nonzero, loop re-entry takes the empty-transfer path. The selected output is then the secondary status.

8. **Zero cap with nonzero quantity.**  
   If the cap source is zero or one, requested chunks are zero. Exact zero input returns and successful submissions do not reduce the remaining quantity. If the predicate continues to return nonzero and dependencies return normally, the loop does not terminate.

9. **Dependency changes descriptor contents.**  
   If the input operation changes the descriptor stored in the context, the subsequent recopy can observe those changes. Changes only to the input operation’s temporary descriptor are discarded by that recopy.
