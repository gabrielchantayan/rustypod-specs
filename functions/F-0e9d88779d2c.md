# F-0e9d88779d2c

## Purpose

F-0e9d88779d2c configures two adjacent 28-byte subrecords within a selected 56-byte record. It assigns a shared-state-derived 32-bit value to each subrecord, then conditionally marks each subrecord active and resets an associated 32-bit field.

The two assigned values come from separate reads of the same shared 32-bit cell. The first subrecord receives the first sampled value. The second receives the second sampled value plus 16,384. The second subrecord’s assignment occurs before the first subrecord’s assignment.

A zero assigned value suppresses that subrecord’s flag and reset writes. It does not cause the existing flag or reset field to be cleared.

**Inferred intent:** the assigned fields may represent two backing-storage addresses separated by 16 KiB. The available evidence establishes only the integer values, layout, and conditional writes—not the meaning or validity of any referenced storage.

## Interface

### Inputs

The function takes two inputs represented as 32-bit signed integers:

- **Record-region base:** used as an address-like value.
- **Record index:** multiplied by 56 and added to the base to select a record.

The selected record begins at:

**record-region base + record index × 56**

This address calculation is not checked. No record count, allocation size, or explicit bounds are supplied.

The function also reads one shared 32-bit integer cell twice. These are separate source-level reads; the contract must not collapse them into a single sample.

### Output

The function has no return value. Its results are memory updates to the selected record.

There is no explicit success status, failure status, exception conversion, or diagnostic output.

### Record layout

Each selected record is 56 bytes long and contains two 28-byte subrecords. The following fields are accessed:

| Offset within selected record | Width | Role established by behavior |
|---|---:|---|
| 8 | 1 byte | First subrecord’s conditional flag |
| 12 | 4 bytes | First subrecord’s assigned value and condition input |
| 16 | 4 bytes | First subrecord’s conditional reset field |
| 36 | 1 byte | Second subrecord’s conditional flag |
| 40 | 4 bytes | Second subrecord’s assigned value and condition input |
| 44 | 4 bytes | Second subrecord’s conditional reset field |

Equivalently, each subrecord has accessed fields at relative offsets 8, 12, and 16. The second subrecord begins 28 bytes after the first.

The flag write sets exactly one byte to 1. It is not a write of a 32-bit Boolean. Each assignment or reset at the other listed offsets is four bytes wide.

The remaining bytes are not explicitly read or written by this function.

## Behavior

### Shared-state sampling and value assignment

The function first reads the shared cell and retains that 32-bit value for the first subrecord.

It then computes the selected record address. During assignment to the second subrecord, it reads the shared cell again and adds 16,384 to that second sample.

The observable source-level order is:

1. Read the shared cell for the first subrecord’s eventual value.
2. Compute the selected record address.
3. Read the shared cell again and calculate the second sample plus 16,384.
4. Write that calculated four-byte value at record offset 40.
5. Write the retained first sample at record offset 12.
6. Process the first subrecord.
7. Process the second subrecord.

Thus, the write at offset 40 precedes the write at offset 12, although subsequent conditional processing visits the first subrecord first.

The two samples need not be assumed equal. If the shared cell remains stable, the assigned values differ by 16,384, provided that addition has a defined result. If the samples differ, no fixed relationship between the two assigned values is established.

This is a source-level behavioral ordering. The evidence does not independently establish hardware memory-ordering guarantees, volatile semantics, or safe concurrent observation of intermediate states.

### Conditional processing

Exactly two subrecords are processed, in ascending subrecord order.

For each subrecord, the function reads the four-byte field at relative offset 12 and compares it with zero.

If that field is nonzero:

- The byte at relative offset 8 is written with 1.
- After that flag write, the four-byte field at relative offset 16 is written with zero.

If that field is zero:

- The flag byte is not written.
- The reset field is not written.

The condition is a zero/nonzero test. It does not validate a pointer, check an address range, distinguish positive from negative values, or inspect the contents of any storage represented by the assigned value.

Both value assignments happen before either subrecord’s condition is tested. The conditional processing explicitly rereads the assigned fields rather than merely testing the retained shared-cell samples. Under ordinary noninterfering execution, those reads see the values just assigned. The function provides no synchronization guaranteeing that result in a concurrently modified record.

### Preservation and partial initialization

A nonzero assigned value produces a flag of 1 and a reset field of zero for that subrecord.

A zero assigned value preserves the prior contents of those two fields. Consequently:

- A previously set flag can remain set even when the newly assigned value is zero.
- A previous nonzero reset-field value can survive when the newly assigned value is zero.
- The function is not a complete record initializer.
- The function is not an unconditional “disable on zero” operation.

There is no early exit based on either subrecord’s value. A zero first-subrecord value does not prevent processing of the second subrecord.

### Integer boundaries

The record-selection stride is 56 bytes, and the shared-value adjustment is 16,384. The supplied representation uses 32-bit integer quantities.

The evidence does not establish checked arithmetic or a portable overflow policy. In particular, the contract does not promise modular wraparound for:

- The index multiplied by 56.
- Addition of that product to the base.
- The second shared-cell sample plus 16,384.
- Address calculations for individual fields.

For a signed 32-bit second sample, adding 16,384 remains representable when the sample is at most 2,147,467,263. The addition does not underflow for any representable signed 32-bit sample.

A second sample of −16,384 produces zero without overflow. A second sample of zero produces 16,384, so it activates the second subrecord rather than suppressing its conditional writes.

## Side effects

On a normal path, the function performs:

- Two source-level reads of the shared cell.
- Two unconditional four-byte writes to the selected record.
- Two four-byte reads for the zero/nonzero conditions.
- For each nonzero condition, one one-byte write followed by one four-byte write.

It performs no explicit allocation, deallocation, copying of an entire record, or traversal of backing storage.

No ownership transfer is established. In particular, writing address-like values into the record does not prove that the function owns, acquires, validates, releases, or dereferences the represented storage.

There is no direct assignment to the shared cell. However, the evidence does not establish that the destination record is disjoint from that cell. If a destination write overlaps the shared cell, that write can change it through aliasing. Both shared-cell samples have already been taken before the record writes begin.

No rollback behavior is present. If a memory access faults after earlier writes have completed, the function contains no explicit mechanism to restore the prior record. Exact fault delivery and visibility remain execution-environment concerns.

## Acceptance examples

These examples are conditional specifications, not observed runtime results. Unless otherwise stated, they assume valid, nonoverlapping storage, defined arithmetic, no external interference, and stable shared state.

### Stable positive shared value

Given a stable shared value of 4,096:

- Offset 40 receives 20,480 before offset 12 receives 4,096.
- Offset 8 becomes 1, followed by offset 16 becoming zero.
- Offset 36 becomes 1, followed by offset 44 becoming zero.
- Unlisted record bytes remain unchanged by this function.

### Stable zero shared value

Given a stable shared value of zero:

- Offset 40 receives 16,384.
- Offset 12 receives zero.
- Offsets 8 and 16 retain their prior contents.
- Offset 36 becomes 1.
- Offset 44 becomes zero.

An implementation that clears offsets 8 and 16 in this case would not match the established behavior.

### Stable negative value producing a zero second assignment

Given a stable shared value of −16,384:

- Offset 40 receives zero.
- Offset 12 receives −16,384.
- The first subrecord’s flag becomes 1 and its reset field becomes zero.
- The second subrecord’s flag and reset field retain their prior contents.

The negative first value still satisfies the nonzero condition.

### Distinct shared-cell samples

If the first source-level sample is zero and the second is −16,384, and the execution model permits those observations:

- Both assigned fields receive zero.
- Neither flag is written.
- Neither reset field is written.

This example specifies the consequence of distinct samples; it does not assert that unsynchronized concurrent modification is safe or defined.

### Selecting a later record

Given record index 3 and valid arithmetic, the selected record begins 168 bytes after the supplied base.

The six accessed field offsets are relative to that selected record. The function does not initialize preceding records merely because it selects a later one.

### Preserving stale conditional fields

Given a zero first assigned value, an existing first flag byte of 7, and an existing first reset value of 99:

- The first assigned-value field becomes zero.
- The flag remains 7.
- The reset field remains 99.

The condition controls whether writes occur, not whether those preserved values are sensible.
